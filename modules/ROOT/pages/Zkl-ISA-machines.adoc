= Unprivileged Architecture: Machines
ifdef::env-site[]

_This chapter is normative._

All values, bit slices, concatenations, and finite-field operations in this chapter follow the conventions of <<Zkl-notation.adoc#KLEE-Notation>>. Specifically, the byte at the lowest address occupies the least significant bits, and the `@` operator places its left operand in the more significant bits—opposite to the `{vvert}` used by referenced standards. No Machine may deviate from these conventions.

This chapter specifies KLEE instruction behavior for supported Machines. Some Machines are defined generically for primitives meeting certain properties (e.g., GCM works with AES or SM4), while others are tied to specific primitives (e.g., Ascon).

<<KLEE-exec-encodings>> gives the encoding of each Machine of this specification in the MDH field _Machine_,
which has two sub-fields: _Type_ in bits [11:4] and _Mode_ in bits [3:0].
For some classes of Machines, _Mode_ specifies a subtype;
other groups of Machines may subdivide _Machine_ differently.

== Definition of a Machine in KLEE

The following information fully defines a Machine:

Parameters:::
+
--
These include:

* the _block size_ `b`, the bit length of the basic unit of information that the Machine processes, usually the block size of its main underlying primitive;
* the _key size_ `k`, also in bits, for Machines that hold a key;
* the _granularity_, usually equal to `b`. “Last blocks”, such as those of the AD or of the plaintext or ciphertext, may be shorter than `b`: if the length of such a block is set explicitly and the next input is longer, the input is truncated, its excess most significant bits being ignored; and
* any other parameter needed to instantiate the Machine with compatible primitives.
--

Data Structures:::
+
--
These include:

. *Provisioning Input*:
its fields, in the order in which they appear in the PI,
each with its length.
The PI is implicitly zero-padded at the end to a multiple of 128 bits.
+
Every PI starts with the MDH. The *Provisioning Input* tables of the Machines therefore start at position ii,
this field being always in the first position:
+
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)   | Field
|   i  | 128           | MDH
|===

. *Internal State*:
the information kept in the internal state of a CC, which is needed to define the Machine and its semantics.
It must exist internally, but its representation and format are not prescribed.
The Internal State always contains the MDH.
A key field of the Internal State holds the key itself, also when the PI or the SCC carries a System Key Identifier in its place (<<Zkl-ISA-unpriv.adoc#KLEE-system-keys>>).

. *Serialized Content*:
the plaintext of the `Content1` of the SCC:
its fields, in the order in which they appear in an SCC, each with its length.
It is implicitly zero-padded at the end to a multiple of 128 bits,
and does not include the MDH.
--

Machine-Specific Functions:::
Any other function that is specific to the Machine.

State Machine:::
+
--
The state machine is defined by:

. the list of the *States* that the Machine may assume, each with its representation as <<Zkl-ISA-unpriv.adoc#KLEE-State-field>> specifies;
. the complete list of *allowed state transitions*, with the prerequisites of each, the required `kl.setst` Form and the meaning of any auxiliary parameter to it, and any other condition that triggers a transition without a `kl.setst`; and
. the *allowed* or *expected* instructions in each State, and their semantics.
  Besides configuration and export sequences, a State typically permits only certain Forms of `kl.exec`, `kl.setst` and `kl.derive`.
A Form D `kl.exec` or a Form A `kl.setst`, with the required KLIOBUF setup (<<Zkl-ISA-unpriv.adoc#KLEE-usage-input-output>>), may be used in their place; other Forms are prohibited.
`kl.input` and `kl.output` are always allowed, since they access no locker, and are thus unrelated to the state machine.
Rule <<KLEE-MGR-not-allowed-instructions>> in <<KLEE-Machine-rules>> states the behavior precisely.
--

[[KLEE-algo-notation]]
=== Notation in the Machine Descriptions

The following nomenclature is specific to the Machine specifications:

* `INPUT` is the input data of `kl.exec` or `kl.setst`: the input vector register,
  or the KLIOBUF (<<Zkl-ISA-unpriv.adoc#KLEE-usage-input-output>>).

* `OUTPUT` is the output data of `kl.exec`: the output
  vector register, or the KLIOBUF (<<Zkl-ISA-unpriv.adoc#KLEE-usage-input-output>>).

* `KLLEN` is the operand length in bits: `VL*SEW` for a vector operand, and
  `kliobuftop` {times} 8 for a KLIOBUF operand. `kliobuftop`, like every
  other KLIOBUF CSR and like `klstart`, is a number of bytes.
  For KLIOBUF operands, `kliobuftop` plays the role of `VL` and `klstart` that of
  `vstart`: the transfer window is bytes [0, `kliobuftop`-1], and `klstart` is
  the position within it at which processing starts or resumes
  (<<Zkl-ISA-unpriv.adoc#KLEE-CSR-kliobuftop>>).

[[KLEE-Machine-rules]]
== General Rules for Machines

Besides the State-Specific General Rules (SGR) of <<Zkl-ISA-unpriv.adoc#KLEE-State-management>>,
the following Machine General Rules (*MGR*) apply to all Machines, unless stated otherwise.

[horizontal]
[[KLEE-MGR-not-allowed-instructions,MGR1]]MGR1:: A usage instruction, or Form thereof, that may modify the state of a locker, and that
the current State of the Machine in that locker does not explicitly allow,
transitions the locker to Error State _Invalid_.
`kl.clearads` is allowed in every Valid State (Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-clearads>>).
+
An illegal-instruction exception is raised instead only where the Form is unavailable to the
implementation at all, or is a KLIOBUF substitution that <<Zkl-ISA-unpriv.adoc#KLEE-usage-input-output>> forbids, rather than merely wrong for the state.

[[KLEE-MGR-granularity,MGR2]]MGR2:: If `KLLEN` does not satisfy the granularity constraints of the Machine in its current state — for instance, it is not a whole multiple of the block size where the Machine requires one — the instruction performs no operation and the locker transitions to Error State _Invalid_.

[[KLEE-MGR-one-klexec-per-block,MGR3]]MGR3:: _Single- and Multi-block `kl.exec`._
In a State that processes whole blocks of `b` bits, one `kl.exec` applies the per-block operation of the State
`KLLEN`/`b` times, for `i` = 0, `b`, `2b`, {ellipsis}, `KLLEN` − `b` in that order, consuming `INPUT[i+b-1:i]` if the State
takes an input and producing `OUTPUT[i+b-1:i]` if it produces an output. Blocks are thus taken and produced from the least
significant position upwards, here and throughout this specification.
+
A State that the Machine describes as processing a single block, such as a last-block, tag-finalize or verify State, processes
exactly one block whatever `KLLEN` is; a further `kl.exec` in a last-block State is governed by Rule <<KLEE-MGR-single-last-block>>.

[[KLEE-MGR-recomputed-fields,MGR4]]MGR4:: A field that a Machine can derive inexpensively
from other fields of the same CC may be omitted from the Serialized Content. It is then recomputed when an import
completes, that is by the `kl.mgmt` with `#kl_cfg_management_end`, and whenever a field it depends on
is modified, for instance when `kl.derive` overwrites a key field or an explicit operation of the Machine regenerates it. A Machine states only the derivation itself, and marks such a field “(derived)” in
its *Internal State*.

[[KLEE-MGR-atomic-randomness,MGR5]]MGR5:: Whenever a Machine requires a random value, if the RBG cannot supply it, Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-rbg-failure>> applies.
Such an internal random value, such as a signing nonce or an ephemeral scalar, is generated and consumed only for the purpose of the scheme which requires it, and for no other instance of the original use or any other purpose.
This Rule excludes the reuse of an internal random value which may be used by some algorithms to enforce nonce reuse.
Rule <<KLEE-MGR-progress-discard>> ensures this.

[[KLEE-MGR-progress-discard,MGR6]]MGR6:: _Implementation-defined interruption of long-running operations._
A State in which a `kl.exec` or `kl.derive` may be interrupted under Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-long-running-no-data>> admits, besides `kl.setst` and configuration instructions, only that one instruction (and Form). Interruption is governed by the following sub-rules:

. Each such Machine and State designates one field _P_ that is zero whenever no such operation is in an interrupted state, and non-zero from the first precise halt of one until its completion.
. The encoding of the progress within _P_ is implementation-defined, and the value recorded at a halt before completion is never zero.
. The instruction issued in such a State may, if _P_ is non-zero, either resume the interrupted operation or restart it, in which case internally _P_ is first reset to zero.
. Every random value and every intermediate value generated for the operation (the "material"), kept in a state field or in the ADS, is meaningful for resumption only if _P_ is non-zero.
. Any material *must* be regenerated if the operation is restarted instead of resumed.
It is up to the algorithm implemented in the Machine to establish whether these values are kept upon completion of the operations.
. If _P_ is non-zero, _P_ is zeroed, and the material destroyed, on every transition of the locker's _State_, including a same-State `kl.setst`, a transition to _Ready_ or to an Error State, by `kl.clearads`, and by an import that completes without `Content2`, whatever the reason (Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-long-running-no-data>>).
. If the Machine is cloned, the copy of the original Machine will have _P_ set to zero and the material destroyed.
. _P_ is not cleared, and the material is not destroyed, by an interrupt, export or import.
. When the operation completes, _P_ is set to zero, but it is up to the algorithm encoded in the Machine to establish whether the material is kept or destroyed.

[[KLEE-MGR-fixed-width-input,MGR7]]MGR7:: Where a state consumes from `INPUT` a single value of fixed width — the field it assigns, or the
operand it is defined over — a `KLLEN` greater than that width is truncated: only that many least
significant bits of `INPUT` are considered, and the rest are ignored; a smaller `KLLEN` violates
the granularity of the state (Rule <<KLEE-MGR-granularity>>). The width is not necessarily the block size `b`.

[[KLEE-MGR-clear-output,MGR8]]MGR8:: When a state writes fewer than `KLLEN` bits to `OUTPUT`, the remaining bits of `OUTPUT` are
cleared. This concerns the bits *within* the operand; the elements beyond `VL` are governed by the
tail-agnostic policy of <<Zkl-ISA-unpriv.adoc#KLEE-KLV>>.

[[KLEE-MGR-load-long-field,MGR9]]MGR9:: A State _X_ that loads a long field from `INPUT`, or emits one to
`OUTPUT`, using multiple `kl.exec` instructions records the amount transferred so far in a state
field _W_ (e.g., _MachineUse_ of the MDH).
+
Each such state names the field _W_ and its unit, bits or bytes.
+
Upon entering State _X_, _W_ is zeroed.
_W_ rises monotonically by the amount of data actually transferred, in the unit of _W_: by `KLLEN` or `KLLEN/8` for a
`kl.exec` that completes, and by the bytes of the committed prefix for one that halts (Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-block-iterated-instructions>>), so that its
resumption adds only the remainder. _W_ is not reset when the field completes.
+
Entering a loading state also zeroes the field, so that reloading replaces it.
+
Where the loading is performed by `process_VLI`
(<<KLEE-process-VLI>>), it is invoked with `block` = `state` = the field, `max_len` = `b` = `n` = its
size, `cumul_len` = _W_, `mode` = `assign`, and `process_block` and `finalize` both equal to `None`.
+
Once _W_ reaches the size of the field, the transfer is complete. A State that emits a field then
transitions to _Success_, unless the Machine defines another transition at that point. In a loading State,
unless State _X_ defines a transition of its own at that point, no further `kl.exec` is allowed in it and
issuing one transitions the locker to Error State _Invalid_. Excess data in a final loading transfer is ignored; an
emitting `kl.exec` that would carry _W_ past the field size invalidates the locker. Where _W_ is a
field of the MDH, `kl.restrict*` may not write it (<<Zkl-ISA-unpriv.adoc#KLEE-instruction-restrict>>).
+
A `kl.setst` that leaves a loading State _X_ before _W_ reaches the size of the field leaves the field
unconfigured: the field, and any length of it that the Machine set on entering _X_, are zeroed, and the flag,
if any, that records that the field holds a value stays clear. A same-State `kl.setst`, which restarts the load
(Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-same-state>>), and `kl.clearads`, which leaves the _State_ unchanged, do not
leave _X_. A Machine whose next State needs the field states this as an entry condition (Rule <<KLEE-MGR-policy-gate>>).
+
A Machine may keep in _StateExtension_ a flag per loaded field, recording that the field holds a configured value,
such as the `Has` flags of the ECC, ML-KEM and ML-DSA Machines and the `HasKey` of HMAC. Unless the Machine states otherwise, such a flag is
cleared on entering the loading State of its field, set when the load completes and passes the checks of Rule
<<KLEE-MGR-check-on-write>>, and also set by an operation of the Machine that computes the field; it is readable with
`kl.getstx`. Each Machine lists its flags, their bit positions, and any departure from this pattern.

[[KLEE-MGR-single-last-block,MGR10]]MGR10:: _Single final block._
A State that processes a single final block, such as _Enc_Last_Block_, _Dec_Last_Block_ or _Hash_Absorb_Last_Block_,
admits one `kl.exec`, which processes that block (Rule <<KLEE-MGR-one-klexec-per-block>>), or none, where the Machine
explicitly allows an empty final block that needs no `kl.exec`, as OCB does for the AD (<<KLEE-OCB-mode>>).
Unless the Machine defines a transition of its own on completion of that `kl.exec`, the locker remains in the State,
and any further `kl.exec` issued in it transitions the locker to Error State _Invalid_, its output window being zeroed
(Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-usage-locker-error-state>>): a second final block is not a continuation of the input
but an attempt to manipulate the internal state of the Machine.

[[KLEE-MGR-policy-gate,MGR11]]MGR11:: _Policy gate and entry conditions._
Each Machine states which bit of _MachinePolicy_, if any, enables the operation of each of its States, and the conditions
that must hold on entering a State.
A `kl.setst` into a State whose operation _MachinePolicy_ disables, or whose stated entry conditions are not met,
transitions the locker to Error State _Invalid_.
Where a Machine says that a transition is possible "if encryption is allowed", resp. "if decryption is allowed", the operation
is enabled by _MachinePolicy_[0], resp. _MachinePolicy_[1]; where encryption and decryption are the same operation, as in
<<KLEE-keystream-modes>>, either bit enables it. A signature Machine is gated by _MachinePolicy_[0] for signature
generation and _MachinePolicy_[1] for verification, and a MAC Machine that verifies a tag internally, such as
<<KLEE-CMAC-mode>>, by _MachinePolicy_[0] for the output of the tag and _MachinePolicy_[1] for its verification
(<<Zkl-ISA-unpriv.adoc#KLEE-Machine-field>>).
A Machine states what a State requires — the `Has` flags, the mode, and the other configuration of the CC that the State
uses — as entry conditions of that State. An instruction executed in the State checks a condition only if the condition
can change while the locker is in the State, or if it is a check of Rule <<KLEE-MGR-check-on-read>>; such a condition is
stated with the instruction, and its violation also transitions the locker to Error State _Invalid_, unless it is a data
error (Rule <<KLEE-MGR-config-data-error>>).

[[KLEE-MGR-config-data-error,MGR12]]MGR12:: _Configuration errors and data errors._
A _configuration error_ is a private key, or another field loaded to configure the CC, that the referenced standard
rejects, such as a malformed private key, or a value whose encoding violates a constraint of its representation, such as the
zero most significant bits of secp521r1 (<<KLEE-ECC>>). It transitions the locker to Error State _Invalid_, and the CC
must be reconfigured before it can be used.
A _data error_ is a ciphertext, tag, signature, message representative or public key that is malformed or does not
verify, such as an ML-KEM encapsulation key that fails its check, or a point that an operation uses — a peer's point,
a public key or a generator — that is not a valid point of the curve.
It transitions the state machine to _Failure_, which is a Valid State.
Each Machine states which of its checks are of which kind.

[[KLEE-MGR-check-on-read,MGR13]]MGR13:: _Checks when a field is read._
When an operation reads a field, it performs the checks that depend on the operation or on more than one field
— for instance the validity of a point in the role the operation gives it, the range of `Scalar` against the group
order, or the consistency of a public key with a private key — before it changes any state. A failure is classified
by Rule <<KLEE-MGR-config-data-error>>: a data error leads to _Failure_, a configuration error to Error State _Invalid_.
A check that depends only on the field itself is made when the field is written (Rule <<KLEE-MGR-check-on-write>>) and need not be
repeated when it is read, since the KLF guarantees the integrity of the locker (<<Zkl-ISA-unpriv.adoc#KLEE-KLF>>);
a Machine may nevertheless require a repeat as a means to detect a corruption of the KLF, as secp521r1 does
(<<KLEE-ECC>>), and a repeated check that fails transitions the locker to Error State _Invalid_.

[[KLEE-MGR-check-on-write,MGR14]]MGR14:: _Checks when a field is written._
A check that a Machine attaches to a field and that depends on that field alone — such as the zero most significant
bits of secp521r1, the well-formedness of an ML-DSA `privkey`, or the input checks of cite:[nist-fips-203] on an
ML-KEM key — is performed whenever the field is written: at the completion of its load (Rule <<KLEE-MGR-load-long-field>>),
of a `kl.derive` into it, of the provisioning that carries it, and of an import that restores it. A failure is
classified by Rule <<KLEE-MGR-config-data-error>>: for a private key or another configuring field it is a configuration error, and the
locker transitions to Error State _Invalid_; for a public key it is a data error, and the state machine transitions
to _Failure_.
The validity of a curve point is not checked when the point is written: it depends on the role that an operation gives
the point, and is checked when the point is read (Rule <<KLEE-MGR-check-on-read>>).

[[KLEE-MGR-tag-verify,MGR15]]MGR15:: _Verification of a tag._
A Machine that verifies a tag or a MAC without disclosing the value it computes does so by a Form C `kl.setst` naming
_Hash_Verify_, whose auxiliary operand carries the expected value. The comparison takes a time independent of the values
compared, and transitions the state machine to _Success_ if they match and to _Failure_ otherwise (Rule
<<KLEE-MGR-config-data-error>>). Where the Machine enters _Hash_Verify_ by itself, for instance on completing its last
block, the `kl.setst` naming _Hash_Verify_ is a same-State `kl.setst` that performs the comparison. The exception is a
Machine whose tag is an input of the decryption itself, the SIV of <<KLEE-GCM-SIV-mode>>: the tag is supplied before the
decryption, and the `kl.exec` that completes the tag computation performs the comparison.

[[KLEE-truncation-vs-length]]
== Input and Output Padding, Truncation, Byte Granularity

The caller must pad inputs shorter than a full vector length, and pass their actual lengths to the Machine, typically through `kl.setst`, unless the Machine specifies otherwise and pads internally.

Cryptographic inputs are normally supplied through vector registers or the KLIOBUF, in whole bytes. For a standard that permits arbitrary bit lengths, the caller specifies the bit length of the final input piece, usually as a `kl.setst` parameter, and the Machine truncates that input to it. Outputs are not necessarily truncated: the caller must discard any excess bits.

This occurs, for instance, with the `last_blk_len` parameters in <<KLEE-GCM-mode>>, <<KLEE-GCM-SIV-mode>>, <<KLEE-OCB-mode>>, <<KLEE-Ascon-AEAD128>>, and <<KLEE-hash-functions-MACs-XOFs>>. Such a parameter specifies a truncation of the passed input, not its length; a `KLLEN` smaller than `last_blk_len` violates the granularity of the state (Rule <<KLEE-MGR-granularity>>). Procedure `process_VLI` receives field lengths in bits, but `kl.exec` always transfers whole bytes, and the last input may be truncated internally.

Where a standard's formula requires a bit count, it is obtained by multiplying the byte count by 8, as with the length block of GHASH in <<KLEE-GCM-mode>>.

[horizontal]
[[KLEE-MGR-last-blk-len,MGR16]]MGR16:: A `last_blk_len`, or any other parameter giving the bit length of a final input piece, is a multiple of 8,
unless the Machine states that its referenced standard orders the bits within a byte as <<Zkl-notation.adoc#KLEE-Notation>> does,
so that a truncation of the last byte to its least significant bits is the bit string that the standard defines (as for <<KLEE-Ascon-AEAD128>>).
A value that the Machine does not admit transitions the locker to Error State _Invalid_.
Whether zero is admissible depends on the Machine.

[[KLEE-keystream-modes]]
=== CTR/XCTR Keystream Generation

In CTR mode, the sum of the lengths of IV and counter equals the block size of the underlying keyed PRP or PRF, to whose input they are concatenated.
(((KLEE, Machine, keystream generation)))

In XCTR modes, both IV and counter have the same size as the block size of the underlying keyed PRP or PRF, and are ``xor``ed together to form its input.

Parameters:::
* `b` = block size (8|`b`).
* `k` = key size (8|`k`).
* `j` = counter size: 32 in CTR mode, `b` in XCTR mode.
* `n` = IV size (8|`n`).
* In CTR mode, `b = n + j`; in XCTR mode, `b = n = j`.
* Granularity: `b`.

Data Structures:::
* *Provisioning Input*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)   | Field
|  ii  | `k` or 64     | `key` or System Key Identifier
|===
--

* *Internal State*:
 ** `key`: `k` bits.
 ** `IV`: `n` bits.
 ** `ctr`: `j` bits.

* *Serialized Content*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
|  Pos. | Size (Bits)   | Field
|   i  | `k` or 64       | `key` or System Key Identifier
|  ii  | `n`             | `IV`
|  iii  | `j`             | `ctr`
|===
--

Machine-Specific Functions:::
* `keystream_block(p) -> c` -- usually an encryption function.
* `tick_ctr()` -- increases the counter `ctr` by one.

State Machine:::
* *States:*
  ** _Ready_: The CC is ready.
  ** _Operate_: In this state the CC will produce a keystream.

* *Allowed State Transitions:*
 ** _Ready_ -> _Operate_, if encryption or decryption is allowed (Rule <<KLEE-MGR-policy-gate>>): the keystream serves both.
 ** _Operate_ -> _Ready_.

* *Behavior:*
 ** Upon entering State _Ready_, `IV` is set to 0, and `ctr` to 0 in CTR mode and to 1 in XCTR mode, whose counter starts
    at 1 as in the XCTR of HCTR2 cite:[cryptoeprint-2021-1441].
// (`ctr` is set to 1 if the Machine is LFSR-based).

 ** To transition to State _Operate_, a Form C ``kl.setst`` instruction is expected.
  *** This sets the value of `IV` to `INPUT`.
  *** `INPUT` is truncated to its `n` least significant bits (Rule <<KLEE-MGR-fixed-width-input>>). The bound is `n`, the width of the `IV` field, and not `b`: in
      CTR mode `b` = `n` + `j`, so the IV is narrower than a block, and `ctr`, not `INPUT`,
      supplies the remaining `j` bits of the counter block. In XCTR mode
      `n` = `b`, and the two bounds coincide.

  ** In State _Operate_, (multi-block) ``kl.exec`` instructions are expected to be of Form C.
     “``kl.exec OUTPUT, Kn|K(Xn)``” performs:
+
--
  . If in CTR mode, then:
  .. `tmp ← keystream_block(bswap(ctr) @ IV)`,
  . else: (i.e., if in a XCTR mode)
  .. `tmp ← keystream_block(IV xor ctr)`,
  . `tick_ctr()`, and
  . `OUTPUT ← tmp`.


--

 ** In States _Ready_ and _Operate_, a Form B
    ``kl.setst Kn|K(Xn), \#kl_state_set_aux_value, Xs`` sets the initial
    counter: `ctr` {leftarrow} `bin(Xs, j)`. This is the “set initial counter”
    capability of the CTR and XCTR Machines; it supports random access into a
    keystream, for example to resume an interrupted stream. Setting the counter is an
    operation, not a State (<<KLEE-operation-immediates>>).

NOTE: There is no check on `ctr` wrapping around to its initial value (<<KLEE-nonce-reuse>>).

A return to State _Ready_ lets the CC be reused with a new IV.

Example pseudocode is given in <<Zkl-pseudocode.adoc#KLEE-pseudocode-keystream-modes>> (for the case `b` = `KLLEN` = 128).

[[KLEE-XEX-XTS-modes]]
=== XEX/XTS modes

The XTS mode was designed for storage confidentiality cite:[DBLP-journals-ieeesp-Martin10] and made into a Recommendation by NIST in 2010 cite:[nist-SP-800-38E]. XTS is based on the XEX construction, formalized by Phillip Rogaway cite:[DBLP-conf-asiacrypt-Rogaway04], to design _Tweakable Block Ciphers_ cite:[DBLP-conf-crypto-LiskovRW02]. A Tweakable Block Cipher (TBC) is a block cipher which, besides the key and the plaintext or ciphertext, also takes a tweak as input. The tweak is used together with the key to select the permutation computed by the block cipher.

The XEX construction builds a TBC `Ẽ` from a block cipher `E`, with key `K`, tweak `T`, and plaintext `P`, as follows:

`{fournbsp}{fournbsp}` `Ẽ(K, T, P) = E(K, P xor M) xor M` `{nbsp}{nbsp}` where `{nbsp}{nbsp}` `M = E(K, T)` `{nbsp}{nbsp}` is called a _mask_.

In XEX mode, once the mask is computed, each successive block updates it by a Galois multiplication, instead of updating the tweak and encrypting it again.

The NIST standard uses two different keys, one for the data encryption path and one for the encryption of the tweak; KLEE follows this convention.
(((KLEE, Machine, XEX)))

Parameters:::

* `b` = block size (8|`b`).
* `k` = key size (8|`k`).
* Granularity: `b`.

Data Structures:::

* *Provisioning Input*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
|  Pos. | Size (Bits)     | Field
|  ii   | `k` or 64       | `key1` or System Key Identifier
| iii   | `k` or 0        | `key2` if _KeyType_ = 0, else empty (a single SKID retrieves both keys)
|===
--

* *Internal State*:
 ** `key1`: `k` bits.
 ** `key2`: `k` bits.
 ** `mask`: `b` bits.

* *Serialized Content*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)   | Field
|  i  | `k` or 64     | `key1` or System Key Identifier
| ii  | `k` or 0      | `key2` if _KeyType_ = 0, else empty (a single SKID retrieves both keys)
| iii  | `b`           | `mask`
|===
--

Machine-Specific Functions:::

* `enc_blk(K, p) -> c` encrypts block `p` using the key `K`, and returns the result `c`.
* `dec_blk(K, c) -> p` decrypts block `c` using the key `K`, and returns the result `p`.
* `update_mask(mask) -> mask` updates the mask by multiplication with a generator
of GF(2^b^). For `b` = 128 this is multiplication by `x` modulo
`x^128^ + x^7^ + x^2^ + x + 1`, where `V[i]` is the coefficient of `x^i^`, as in
cite:[nist-SP-800-38E]. That is,
+
`{fournbsp}{fournbsp}` `update_mask(V)` = `V << 1` `{fournbsp}` if `V[127]` = `0`
+
and
+
`{fournbsp}{fournbsp}` `update_mask(V)` = `(V << 1) xor (zeros(120) @ 0b10000111)`
`{nbsp}{nbsp}` otherwise.
+
An instantiation with `b` {ne} 128 must state its own reduction polynomial.

//  For `b` = 128 the field is GF(2)[`x`] modulo
//  `x^128^ + x^7^ + x^2^ + x + 1`.
//
//  A 128-bit value `V` represents the element whose coefficient of `x^k^` is `V[k]`,
//  as in cite:[nist-SP-800-38E] and IEEE 1619. `update_mask(V)` is multiplication by
//
//  A Machine instantiating XEX or XTS with a block size `b` {ne} 128 must state its own
//  reduction polynomial; this specification defines `update_mask` only for `b` = 128.

State Machine:::

* *States:* _Ready_, _Encrypt_, and _Decrypt_ (defined as before, cf. <<KLEE-ECB-mode>>).

* *Allowed State Transitions:*
 ** _Ready_ -> _Encrypt_, if encryption is allowed (Rule <<KLEE-MGR-policy-gate>>).
 ** _Ready_ -> _Decrypt_, if decryption is allowed (Rule <<KLEE-MGR-policy-gate>>).
 ** _Encrypt_, _Decrypt_ -> _Ready_.

* *Behavior:*
 ** In State _Ready_:
  *** The `mask` field is set to zero.
 ** The ``kl.setst`` instruction to transition to either _Encrypt_ or _Decrypt_ is expected to be of Form C.
    It sets the tweak, and the `mask` field is used to store it: `mask <- INPUT`.
  *** `INPUT` is truncated to its `b` least significant bits (Rule <<KLEE-MGR-fixed-width-input>>).
  *** Then, the following operations are performed:
  . `mask <- enc_blk(key2, mask)`
+
--
KLEE architects only the two-key construction of cite:[nist-SP-800-38E]: the tweak is
always encrypted under `key2`, which the data path never evaluates, so the raw value is
safe to use as the initial mask. The single-key XEX construction, in which the mask is
`{alpha}` {interpunct} `enc_blk(key1, T)`, is *not* architected: provisioning `key2`
equal to `key1` re-creates it *without* the required multiplication by `{alpha}`, which
cite:[DBLP-conf-asiacrypt-Rogaway04] shows to be vulnerable. Provisioners must therefore
supply two independent keys, and a System Key Identifier must resolve to two independent
keys in the SKS.
--
// The extra `update_mask` in the single-key case is required, not incidental. With one key
// the raw value `enc_blk(key1, T)` is both a mask and a value the same key can be asked to
// encrypt, which cite:[DBLP-conf-asiacrypt-Rogaway04] shows to be vulnerable; the
// construction therefore starts from `{alpha}` {interpunct} `enc_blk(key1, T)`. With two
// independent keys the data path never evaluates `key2`, so the raw value is safe to use and
// no multiplication is needed. An implementation must not "simplify" the two branches into
// one.

  ** In States _Encrypt_ and _Decrypt_, (multi-block) ``kl.exec`` instructions are expected to be of Form A.
    “``kl.exec OUTPUT, Kn|K(Xn), INPUT``” performs the following operations:
+
--
  . `OUTPUT` is computed as follows:
  .. In State _Encrypt_, `OUTPUT <- mask xor enc_blk(key1, INPUT xor mask)`.
  .. In State _Decrypt_, `OUTPUT <- mask xor dec_blk(key1, INPUT xor mask)`.
  . `mask <- update_mask(mask)`.
--
//

A return to State _Ready_ lets the CC be reused with a new tweak.

Encryption pseudocode is provided in <<Zkl-pseudocode.adoc#KLEE-pseudocode-basic-IV-mode>>;
decryption is similar.


[[KLEE-XTS-from-XEX]]
==== Procedure: XTS and Ciphertext Stealing from an XEX Context

cite:[nist-SP-800-38E] adds two things to the XEX construction above: the tweak is the
data unit sequence number, and a data unit whose length is not a multiple of `b` is
completed by ciphertext stealing. Both are obtained from the XEX CC as specified, with no
further architectural support; this subsection says how, so that an XEX Machine can be
used to realize SP 800-38E without invention.

*The tweak.* The value supplied as `INPUT` on the transition to _Encrypt_ or _Decrypt_ is
the data unit sequence number encoded on `b` bits in little-endian order, i.e., `bin(i, b)` in the
notation of <<Zkl-notation.adoc#KLEE-Notation>>.

*Ciphertext stealing.* Let the data unit be `m` full blocks followed by a final partial
block of `s` bits, with `0` < `s` < `b` and `s` a multiple of 8, and number the blocks
`P~0~` {ellipsis} `P~m-1~`, `P~m~`. Recall that each block uses the current `mask` and then
advances it (Rule <<KLEE-MGR-one-klexec-per-block>>), so the `j`-th block processed after the tweak was set, counting
from 0, is processed at mask index `j`.

Encryption needs no reordering, because SP 800-38E consumes the mask indices in their
natural order:

  . Issue `kl.exec` for `P~0~` {ellipsis} `P~m-2~`, obtaining `C~0~` {ellipsis} `C~m-2~`.
  . Issue `kl.exec` for `P~m-1~`, obtaining `CC` at mask index `m-1`.
  . `C~m~` {leftarrow} `CC[s-1:0]` and `CP` {leftarrow} `CC[b-1:s]`.
  . Issue `kl.exec` for `CP @ P~m~`, obtaining `C~m-1~` at mask index `m`.
  . The ciphertext is `C~0~` {ellipsis} `C~m-2~`, `C~m-1~`, `C~m~`, in that order, with
    `C~m~` the final `s` bits.

Decryption consumes mask index `m` before mask index `m-1`, and a mask only ever advances.
The two are obtained from one context by cloning it once, immediately before the last two blocks:

  . Issue `kl.exec` for `C~0~` {ellipsis} `C~m-2~`, obtaining `P~0~` {ellipsis} `P~m-2~`.
    The `mask` of the locker is now at index `m-1`.
  . `kl.clone` the locker into a second locker, which is therefore also at mask index `m-1`.
  . On the clone, issue one `kl.exec` whose output is discarded. This consumes mask index
    `m-1` and leaves the clone at index `m`.
  . On the clone, issue `kl.exec` for `C~m-1~`, obtaining `PP` at mask index `m`.
  . `P~m~` {leftarrow} `PP[s-1:0]` and `CP` {leftarrow} `PP[b-1:s]`.
  . On the original locker, still at mask index `m-1`, issue `kl.exec` for `CP @ C~m~`,
    obtaining `P~m-1~`.
  . Clear the clone.

The cost of decryption is therefore one `kl.clone` and one discarded block operation per
data unit, independently of its length. `CP @ P~m~` and `CP @ C~m~` place the
partial block in the least significant bits, where the first `s`/8 bytes of the
string live under <<Zkl-notation.adoc#KLEE-Notation>>.

If `s` = 0 no stealing takes place and both directions are the plain XEX sequence over
`m` blocks.

[[KLEE-tweakable]]
=== Generic Tweakable Block Ciphers

The specification of a generic tweakable block cipher resembles that of a block cipher in ECB mode.
Because `kl.exec` lacks two-input variants and uses a single input buffer, the tweak is set with a separate instruction.
If the block and tweak sizes differ, the vector length may need reconfiguring between operations, unless the tweak is shorter than the block, in which case the tweak-setting instruction truncates its auxiliary input to the bits it needs.

Some commonly used TBCs are `Deoxys` cite:[Deoxys-141], `Skinny` cite:[DBLP-conf-crypto-BeierleJKL0PSSS16], `QARMA` cite:[DBLP-journals-tosc-Avanzi17], and `QARMAv2` cite:[DBLP-journals-tosc-AvanziBDEGNR23].

Parameters:::

* `b` = block size (8|`b`).
* `k` = key size (8|`k`).
* `t` = tweak size (8|`t`).
* Granularity: `b`.

Data Structures:::

* *Provisioning Input*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)   | Field
|  ii  | `k` or 64     | `key` or System Key Identifier
|===
--

* *Internal State*:
 ** `key`: `k` bits.
 ** `tweak`: `t` bits.

* *Serialized Content*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)   | Field
|   i  | `k` or 64     | `key` or System Key Identifier
|  ii  | `t`           | `tweak`
|===
--

State Machine:::

* *States:* _Ready_, _Encrypt_, and _Decrypt_, defined as before.

This Machine has no state of its own. Setting the tweak is an operation, not a State (<<KLEE-operation-immediates>>):
the _State_ field therefore only ever holds _Ready_, _Encrypt_, _Decrypt_, or one of the states common to all Machines.

* *Allowed State Transitions:*
 ** _Ready_ -> _Encrypt_, if encryption is allowed (Rule <<KLEE-MGR-policy-gate>>).
 ** _Ready_ -> _Decrypt_, if decryption is allowed (Rule <<KLEE-MGR-policy-gate>>).
 ** _Encrypt_ -> _Decrypt_ and _Decrypt_ -> _Encrypt_, subject to the same conditions.
 ** In each of _Ready_, _Encrypt_ and _Decrypt_, the set-tweak operation below, which is not a transition (<<KLEE-operation-immediates>>).

 * *Behavior:*
  ** In State _Ready_:
   *** Upon entering the state, the `tweak` field is cleared.
  ** In each of States _Ready_, _Encrypt_ and _Decrypt_, a Form C `kl.setst` can be issued.  `kl.setst Kn|K(Xn), #kl_state_set_aux_value, INPUT` performs `tweak <- INPUT` and leaves the _State_ field unchanged. `INPUT` is truncated to its `t` least significant bits (Rule <<KLEE-MGR-fixed-width-input>>).
  ** In State _Encrypt_, respectively _Decrypt_, (multi-block) `kl.exec` instructions must be of Form A, where “``kl.exec OUTPUT, Kn|K(Xn), INPUT``” encrypts, resp., decrypts, `INPUT` into `OUTPUT`.
  ** This Machine does not automatically update the tweak value: the same `tweak` applies to every block until the set-tweak operation is issued again.

[[KLEE-process-VLI]]
=== Procedure: Processing Variable Length Inputs into a Fixed Length Output

Many Machines process variable-length inputs into fixed-length outputs, for instance to hash, or to derive an internal fixed-length IV from a variable-length external one. They do so in specific States (e.g., _Hash_Absorb_), called _Current_State_ here, whose semantics this section describes.

The Procedure follows the granularity of the calling Machine, which in some cases simplifies the inner loop and the computation of `amount` in obvious ways.

A Machine invokes it as:

```
process_VLI(max_len,
            block, b,        state, n,
            input_base,      block_base,      state_offset,      cumul_len,
            process_block(), finalize(),      mode,              granularity).
```
where the parameters are all _references_ to certain variables of the caller Machine:

 * `max_len` is the total length of the data to be absorbed, *in bits*. If not defined by the caller or by the Machine, `max_len` is zero for the purpose of defining this procedure.
 * `block` contains the current block being filled internally before processing. Its size is `b` bits.
 * `state` is the output buffer. It may be the same as `block`. Its size is `n` bits.
 * `input_base` is the base offset of the data moved from the ``kl.exec``'s input into `block`.
 * `block_base` is the base bit-offset within `block`. Each time this value reaches `b`, the data in `block` is processed.
 * `state_offset` is the offset within `state` for XORing with the input data, for instance, for sponge constructions.
 * `cumul_len` is the cumulative length of the data absorbed so far by the procedure, or `None` if not tracked.
 * `mode` is either `assign` or `xor_accumulate`, and selects how incoming data is combined with
   the destination, as specified in Step 4.b below. It is *not* inferred from whether `block` and
   `state` denote the same variable.

[IMPORTANT]
====
`input_base`, `block_base` and `cumul_len` — the last whenever it is tracked — shall denote
distinct storage locations. They
advance independently — `input_base` is reset at the start of every `kl.exec`, whereas
`block_base` and `cumul_len` persist across instructions — so binding any two of them to the same
location makes the procedure advance that location several times per iteration and is a malformed
invocation.

When `mode` is `xor_accumulate`, the caller shall satisfy `state_offset` + `b` {le} `n`. The
destination index reaches `block_base` + `amount` + `state_offset`, while `amount` is bounded only
by `b` − `block_base`, so a larger `state_offset` would write past the end of `state`.

`mode` is an explicit parameter because the two combining rules are not interchangeable.
`xor_accumulate` is required by sponge constructions, which XOR the input directly into the rate
portion of the state; `assign` is required wherever a field is *loaded* rather than absorbed, in
particular for key and key-like material. Selecting `xor_accumulate` where `assign` is meant
combines the incoming value with whatever the field already held, which for a key field yields a
key that neither party chose, silently and without any error indication.
====

The state variables `input_base`, `block_base`, and `cumul_len` are not initialized by this procedure, so that several calls to it can concatenate their results.
It is the caller's responsibility to ensure that any necessary variable is initialized to zero.
A Machine that enters a state with `mode` = `assign`, and whose destination field must hold a
defined value once loading completes, shall zero that field on entry to the state.

*Units.* `max_len`, `b`, `n`, `input_base`, `block_base`, `state_offset`, `cumul_len`, and `amount` are
all counted in bits, to support values of `max_len` that are not multiples of 8 bits.
However, the routine only supports values of `b` and `n` that are multiples of 8 bits,
and all `kl.exec` instructions transfer whole bytes and never a fraction of a byte.
As a consequence, `input_base` is always a multiple of 8, and so is `block_base`, except after the final transfer of a
`max_len` that is not a multiple of 8, which ends the instruction (step 4.g).

Finally, two parameters are functions of the called Machine:

* `process_block()=process_block(block, state)` is a function that processes the current block into `state`.
It may
   be given as `None`, in which case no such call is made and `state` is not used.
* `finalize()` is a function that finalizes the processing of the input data. It may have to complete the current block according to rules defined in the Machine as part of the finalization. It may also be given as `None`, in which case no such call is made.

Passing `None` for both reduces the procedure to its accounting of partial progress across
`kl.exec` instructions, which is what a Machine needs when it merely has to fill a long
field from memory and has no per-block processing to perform.

If the caller Machine needs to process the last block separately, it may invoke this procedure twice with the length of the last block as the `max_len` parameter and a different `process_block()` function.

The optional parameter `granularity` specifies the transfer unit for inputs: every transfer in a sequence (`INPUT` of `kl.exec` or the auxiliary vector input of `kl.setst`) — except possibly the last — must have a `KLLEN` that is a whole multiple of `granularity`.
The final transfer may be shorter or internally truncated to `max_len` − `cumul_len` (<<KLEE-truncation-vs-length>>); consequently, `max_len` need not be a multiple of `granularity`.
For example, with `granularity` = 128, a 96-bit IV is supplied in a single transfer, either as a 96-bit vector or as a 128-bit vector with excess bits truncated.

//

*Internal State Variables*:::
Besides `max_len`, `block`, and `state`, which are fixed for the duration of the hash computation, and `input_base`, `block_base`, and `cumul_len`, additional variables may be defined by the Machine and used by `process_block()` and `finalize()`.

*State Machine Behavior*:::

** When entering State _Current_State_:
 . If `max_len` is set by the caller, it is passed as a parameter to a Form B `kl.setst` instruction and `max_len` is set to the auxiliary argument `Xs`.
 . Otherwise, `max_len` is set by the Machine, and the `kl.setst` instruction used to transition to this state must be of Form A.

** While in State _Current_State_, only ``kl.exec`` instructions of Form B are expected, whereby
 “`kl.exec Kn|K(Xn), INPUT`” processes the data block `INPUT` as follows.
+
--
. If `max_len != 0` and `cumul_len >= max_len`, then the locker transitions to Error State _Invalid_.
. `input_base <- 8` {interpunct} `klstart`, which is 0 when the instruction starts and the point of progress when it resumes.
  `input_base` is counted in bits (see *Units* above) while `klstart` is a number of bytes
  (<<Zkl-ISA-unpriv.adoc#KLEE-CSR-klstart>>), hence the conversion; no other information distinguishes a start from a resumption.
. While `(input_base < KLLEN)` do
.. If `max_len` != 0 then `amount <- min(KLLEN - input_base, b - block_base, max_len - cumul_len)`,
   else `amount <- min(KLLEN - input_base, b - block_base)`.
   `amount` is always strictly positive, so the loop terminates.
.. if `mode` = `assign` then:
 ... ``block[block_base + amount - 1 : block_base] <- INPUT[input_base + amount - 1 : input_base]``.
.. else, that is if `mode` = `xor_accumulate`:
 ...  XOR ``INPUT[input_base + amount - 1 : input_base]`` to ``state[block_base + amount + state_offset - 1 : block_base + state_offset]``.
.. `input_base <- input_base + amount`.
.. `block_base <- block_base + amount`.
.. If `cumul_len` is not `None`, then `cumul_len <- cumul_len + amount`.
.. If (`block_base` = `b`) then:
 ... `process_block(block, state)`, if it is not `None`.
 ... `block_base <- 0`.
.. If `max_len` != 0 and `cumul_len = max_len` then:
 ... `finalize()`, if it is not `None`.
 ... The instruction is terminated, even if `input_base < KLLEN`.
.. *Here*, and only here, the instruction may be interrupted, with
   `klstart <- input_base / 8`.
   Every iteration but the last of a window ends with a full block, so a halt here always leaves `block_base` = 0.
   The interruption points of _Current_State_ (<<Zkl-ISA-unpriv.adoc#KLEE-CSR-klstart>>) are therefore 0 and every multiple of `granularity` (every byte offset without one) at which the `block_base` that the locker holds is 0: they are determined by architected state alone, without the value that `block_base` had when the halted instruction started.
   `input_base` is a whole number of bytes at this point, so the division is exact; the
   procedure defines no interruption point at a finer granularity, so `klstart` never has
   to describe a position inside a byte. The conversion matches the one State
   _Hash_Output_ performs on the output side (<<KLEE-hash-functions-MACs-XOFs>>).
--
+

** If the caller transitions to a different state, `finalize()` is performed before transitioning, unless `finalize` = `None`
   or the Machine states otherwise.
   Unless the State loads a field under Rule <<KLEE-MGR-load-long-field>>, or the Machine states otherwise, transitioning to the same State `_Current_State_` is not allowed, and any attempt to do so causes the locker to transition to Error State _Invalid_ (Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-same-state>>).

[[KLEE-GCM-mode]]
=== GCM Mode

The GCM mode was designed by David McGrew and John Viega cite:[DBLP-conf-indocrypt-McGrewV04] and became a NIST Recommendation in 2007 cite:[nist-SP-800-38D].
It is currently defined only for 128-bit block ciphers; the definition will be extended to other block sizes if needed.
(((KLEE, Machine, GCM)))

Parameters:::

* `k` = key size (64|`k`).
* `b` = 128 = block size in bits.
* `c` = 32 = counter size in bits.
* Granularity: `b`.

Data Structures:::

* *Provisioning Input*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)   | Field
|  ii  | `k` or 64     | `key` or System Key Identifier
|===
--

* *Internal State*:
+
--
** `key`: `k` bits.
** `J0`:  `128` bits. Big-endian as in the AES-GCM spec. `J0`[127:96] is the current GCTR counter, and `start_ctr` its initial value; the counter occupies bytes 12 to 15 of the counter block, big-endian, as in cite:[nist-SP-800-38D].
** `auth_key` (derived): `128` bits. Rule <<KLEE-MGR-recomputed-fields>> applies.
** `tag`: `128` bits. This field stores the authentication tag.
** `start_ctr`: an integer in the range 0 to 2^32^-1. The initial value of the GCTR counter. It is serialized as `bin(start_ctr,32)`.
** `last_blk_len`: an integer in the range 0 to 127. The length of the last block of a plaintext or ciphertext.
--
+
In the internal state, variables `len`, `input_base`, `block_base`, `cumul_len`, `J0_padding` may overlap with `J0` or be separate fields.
The latter may be necessary if the implementation of Procedure `process_VLI` (<<KLEE-process-VLI>>) works with integers of a different length.

* *Serialized Content*:
+
--
[cols="^8%,<15%,<15%,<62%",options="header"]
|===
|  Pos. | Size (Bits)   | Field          | Description
|  i    | `k` or 64     | `key`          | Key value or System Key Identifier
| ii    | 128           | `J0`           | Big-endian as in the AES-GCM spec. `J0`[127:96] is the current GCTR counter.
|  iii  | 128           | `tag`          | {empty}
|   iv  | 32            | `start_ctr`    | The initial counter: `start_ctr` = `int(bswap(J0[127:96]))`, the last four bytes of the *initial* `J0` read as a big-endian integer, serialized here as `bin(start_ctr,32)`. If the running counter returns to this value, an error is returned. It is also used to generate the tag mask.
|   v  | 16            | `last_blk_len` | {empty}
|===

While in state _Set_Aux_Value_, `J0` is replaced by the following fields:

[cols="^8%,<15%,<15%,<62%",options="header"]
|===
| Pos.  | Size (Bits)     | Field       | Description
| ii.a  | 16              | `len`       | Total length of the IV, in bits. Maximum supported size is 1024 bytes (8192 bits).
| ii.b  | 16              | Padding     | `input_base` is not serialized: it is reset by every `kl.exec` (<<KLEE-process-VLI>>).
| ii.c  | 16              | `block_base`| Amount of data, in bits, absorbed so far into the current block. Each time this value reaches `b`, the block is processed.
| ii.d  | 48              | `cumul_len` | Cumulative length, in bits, of the data absorbed so far.
| ii.e  | 32              | `J0_padding`| Zero.
|===
--

NOTE: There are no fields for the lengths of the AD and of the plaintext, as they are maintained by the calling software.

Machine-Specific Functions:::
+
--
* `enc_blk(key, p) -> c` encrypts block `p` using the key, and returns the
  result `c`.

* `absorb(data)` absorbs data into the hash function by performing:
  . `tag <- tag xor data`.
  . `tag <- Galoismul(tag, auth_key)`.

* `Galoismul(a, b)` is multiplication in the GHASH field of cite:[nist-SP-800-38D] {sect}6.3, in the representation of that section.
+
The field is GF(2)[x] modulo `x^128^ + x^7^ + x^2^ + x + 1`.
A 128-bit value `V` represents the element whose coefficient of
`x^8i+j^`, for `0` {le} `i` < `16` and `0` {le} `j` {le} `7`, is `V[8i + (7-j)]`.
+
In other words, the byte order runs forward (“little endian”:
the byte at offset 0 contains the coefficients of `x^0^` through `x^7^`,
the byte at offset 1 contains the coefficients of `x^8^` through `x^15^`,
and so on) while the bit order is reversed within each byte:
in the byte at offset 0, bit 0, the least significant bit, is the coefficient of `x^7^`,
bit 1 that of `x^6^`, and so on.
--

State Machine:::

* *States:*
+
--
Besides _Ready_, _Success_, and _Failure_, the GCM Mode Machines make use of the following states:

 ** _Set_Aux_Value_: Used to set the IV and then compute `J0` once left.
 ** _Hash_Absorb_: Process Associated Data (AD) into the tag.
 ** _Encrypt_: Encrypt the plaintext and absorb the ciphertext into the tag.
 ** _Enc_Last_Block_: Encrypt the final, fractional block of the plaintext.
 ** _Enc_Tag_Finalize_: Finalize the encryption tag, prepare to return its value.
 ** _Decrypt_: Absorb the ciphertext into the tag and decrypt it.
 ** _Dec_Last_Block_: Decrypt the final, fractional block of the ciphertext.
 ** _Dec_Tag_Finalize_: Finalize the encryption tag and keep it internally.
 ** _Hash_Verify_: Compare the tag against a user supplied value.

The Associated Data (AD) and the plaintext or ciphertext are absorbed into `GHASH`
differently, which places two obligations on the
caller:

* *For the AD*, the caller must zero every bit of the final block beyond the actual end
  of the AD. `GHASH` absorbs that block whole, following cite:[nist-SP-800-38D].
  No state is required to process a fractional last AD block.

* *For the plaintext and ciphertext*, the caller must *not* rely on zero-padding, which
  would both leak keystream and produce a non-conforming tag: a final block
  shorter than `b` must go through State _Enc_Last_Block_, resp. _Dec_Last_Block_.
--

* *Allowed State Transitions:*
 ** _Ready_ -> _Set_Aux_Value_ -> _Hash_Absorb_.
 ** _Set_Aux_Value_ -> _Set_Aux_Value_, which restarts the IV (see below).
 ** _Hash_Absorb_ -> _Encrypt_, if encryption is allowed (Rule <<KLEE-MGR-policy-gate>>).
 ** _Hash_Absorb_ -> _Decrypt_, if decryption is allowed (Rule <<KLEE-MGR-policy-gate>>).
 ** _Encrypt_ -> { _Enc_Last_Block_ -> } _Enc_Tag_Finalize_ -> _Success_.
 ** _Decrypt_ -> { _Dec_Last_Block_ -> } _Dec_Tag_Finalize_ -> _Hash_Verify_ -> _Success_ or _Failure_.

* *Behavior:*
 ** In State _Ready_ :
  *** The following initialization operations are performed:
   . `auth_key <- enc_blk(key, zeros(b))`, and
   . `tag <- zeros(b)`

  ** To transition to State _Set_Aux_Value_, a Form B ``kl.setst`` instruction is
     expected, “``kl.setst Kn|K(Xn), #kl_state_set_aux_value, Xs``”, whose auxiliary
     parameter sets the length of the IV in bits: `len <- Xs`.
     `Xs` must satisfy `8` {le} `Xs` {le} `8192` and be a multiple of 8;
     for any other value, `0` included, the locker transitions to Error State _Invalid_.
     Upon entering the state, `tag` is cleared: `tag <- zeros(b)`.

  ** When entering State _Set_Aux_Value_, `input_base`, `block_base`, `cumul_len` are set to zero.
     A same-State Form B `kl.setst` into _Set_Aux_Value_ restarts the IV, as for every loading State (Rules
     <<Zkl-ISA-unpriv.adoc#KLEE-GR-same-state>> and <<KLEE-MGR-load-long-field>>): `len` {leftarrow} `Xs`, and `tag`, `block_base` and
     `cumul_len` are zeroed, discarding the part of the IV absorbed so far.

  ** State _Set_Aux_Value_ is implemented as
  Procedure `process_VLI` (<<KLEE-process-VLI>>) as: +
  `process_VLI(len, block=tag, b, state=tag, b, input_base, block_base, 0, cumul_len, process_block(), finalize(), mode=xor_accumulate, granularity=b)`, where `len` is the IV length in bits, and
  `mode` is `xor_accumulate` because `GHASH` absorbs each block by XORing it into the accumulator
  before multiplying, and
   *** if `len != 96`, `process_block()`, performs `tag <- Galoismul(tag, auth_key)`, otherwise it does nothing.
   *** `finalize()` is defined as follows:
    . If `len = 96`, then:
      .. `J0 <- bswap(bin(1,32)) @ tag[95:0]`.
+
The value of `J0` is `IV {vvert} 0^31^ {vvert} 1` of cite:[nist-SP-800-38D] {sect}7.1, where the IV occupies bytes 0 to 11, i.e.
`J0[95:0]`, and the counter occupies bytes 12 to 15 as a *big-endian* integer.

    . If `len != 96`, then let `s <- 128 ⎡len/128⎤ - len`, and the computation of `J0 := GHASH(IV {vvert} 0^s+64^ {vvert} bswap(bin(len,64)), auth_key)` is completed by performing:
      .. if `block_base != 0`, then `tag <- Galoismul(tag, auth_key)`
      .. `tag <- tag xor (bswap(bin(len,64)) @ zeros(64))`
      .. `tag <- Galoismul(tag, auth_key)`
      .. `J0 <- tag`
    . `start_ctr <- int(bswap(J0[127:96]))`,
    . `tag <- zeros(b)`, so that State _Hash_Absorb_ starts the Associated Data hash from the
      value `GHASH` requires and does not inherit the hash of the IV.
    . Transitions to state _Hash_Absorb_.

  ** A `kl.setst` that leaves _Set_Aux_Value_ before the IV is complete does not perform `finalize()`: as Rule
     <<KLEE-MGR-load-long-field>> prescribes for a load left incomplete, the partial IV is discarded, and `tag`, `J0`,
     `len`, `block_base` and `cumul_len` are zeroed. Entering _Hash_Absorb_ requires a complete IV
     (Rule <<KLEE-MGR-policy-gate>>): _Hash_Absorb_ is reached only through `finalize()`, and a `kl.setst` naming it
     in _Set_Aux_Value_ transitions the locker to Error State _Invalid_.

[NOTE]
====
The IV is absorbed into `tag`, not into `J0`, and only the finished value is copied to `J0`.
`tag` is free for this because `_Set_Aux_Value_` is reachable only from _Ready_, which clears it,
and zero is GHASH's initial value in any case — whereas ``J0``'s slot in the Serialized Content
carries `len`, `block_base` and `cumul_len` while this state is active. Accumulating
into `J0` would place the running hash and those counters in the same 128 bits, so a CC exported
part-way through a non-96-bit IV could not resume.
====

 ** In State _Hash_Absorb_, (multi-block) ``kl.exec`` instructions of Form B are expected, whereby ``kl.exec Kn|K(Xn), INPUT`` absorbs a data block into `tag`, i.e.:
+
--
 . `absorb(INPUT)`.
--
** In State _Encrypt_, (multi-block) ``kl.exec`` instructions are expected to be of Form A.
   “``kl.exec OUTPUT, Kn|K(Xn), INPUT``” encrypts `INPUT` into `OUTPUT`, and
   absorbs `OUTPUT` into the `tag`, namely:
+
--
  * `local ctr : int` - the running counter, as an integer.

[]
  . `ctr <- int(bswap(J0[127:96]))`   // convert counter from big-endian to little-endian
  . `ctr <- (ctr + 1) mod 2^32^`.
  . If `ctr` = `(start_ctr - 1) mod 2^32^`, then: (process at most  2^32^ - 2 blocks)
   .. the locker transitions to Error State _Invalid_.
   . else:
  .. `J0[127:96] <- bswap(bin(ctr,32))`.  // convert updated counter back to big-endian
  .. `tmp <- INPUT xor enc_blk(key, J0)`.
  .. `absorb(tmp)`.
  .. `OUTPUT <- tmp`.
--
** To transition to State _Enc_Last_Block_, a Form B `kl.setst` instruction is issued, whereby
`last_blk_len`, the bit length of the last block, is set to the auxiliary argument `Xs`.
A value of zero, larger than 127, or not a multiple of 8, causes the locker to transition to Error State _Invalid_.
Although cite:[nist-SP-800-38D] admits any bit length, it numbers the bits of a byte from the most significant, which does not map onto a truncation to the least significant bits, so `last_blk_len` is restricted to multiples of 8 (Rule <<KLEE-MGR-last-blk-len>>).
Any excess bits provided by the following Form A ``kl.exec`` are ignored.

** In State _Enc_Last_Block_, a single Form A ``kl.exec`` instruction can be issued.
   “``kl.exec OUTPUT, Kn|K(Xn), INPUT``” encrypts `INPUT` into `OUTPUT`, and
   absorbs `OUTPUT` into the `tag`, namely:
+
--
  * local `ctr : int` – the running counter, as an integer.
  * `local tmp : bits(b)`

[]
  . If `last_blk_len = 0`, the final block has already been processed: the locker transitions to Error State _Invalid_ (Rule <<KLEE-MGR-single-last-block>>).
  . `ctr <- int(bswap(J0[127:96]))`
  . `ctr <- (ctr + 1) mod 2^32^`.
  . If `ctr` = `(start_ctr - 1) mod 2^32^`, then:
   .. the locker transitions to Error State _Invalid_.
  . else:
   .. `J0[127:96] <- bswap(bin(ctr,32))`
   .. `tmp <- (zeros(128-last_blk_len) @ INPUT[last_blk_len-1:0]) xor (zeros(128-last_blk_len) @ enc_blk(key, J0)[last_blk_len-1:0])`.
   .. `absorb(tmp)`.
   .. `OUTPUT <- tmp`.
   .. `last_blk_len <- 0`
--


** To transition to State _Enc_Tag_Finalize_, a Form C `kl.setst` instruction is issued with the following value, computed by the software itself:
+
--
[none]
* `INPUT <- bswap(bin(len_in_bits(plaintext), 64)) @ bswap(bin(len_in_bits(AD), 64))`.

The authentication tag is then computed and retained internally, as follows:

. `absorb(INPUT)`.
  . `tag <- tag xor enc_blk(key, bswap(bin(start_ctr,32)) @ J0[95:0])`.

`INPUT` is truncated to its 128 least significant bits (Rule <<KLEE-MGR-fixed-width-input>>).
--

** {empty}
In State _Enc_Tag_Finalize_, a single ``kl.exec`` instruction of Form C is expected.
“``kl.exec OUTPUT, Kn|K(Xn)``” writes the `tag` to `OUTPUT`, and the state transitions to _Success_.

** {empty}
+
--
In State _Decrypt_, (multi-block) ``kl.exec`` instructions are expected to be of Form A.
``kl.exec OUTPUT, Kn|K(Xn), INPUT`` absorbs the ciphertext `INPUT` into `tag`, then decrypts `INPUT` into `OUTPUT`, namely:

 * local `ctr : int` – the running counter, as an integer.
 * `local tmp : bits(b)`

[]
 . `ctr <- int(bswap(J0[127:96]))`.
 . `ctr <- (ctr + 1) mod 2^32^`.
 . If `ctr` = `(start_ctr - 1) mod 2^32^`, then:
  .. the locker transitions to Error State _Invalid_.
 . else:
  .. `absorb(INPUT)`.
  .. `J0[127:96] <- bswap(bin(ctr,32))`.
  .. `OUTPUT <- INPUT xor enc_blk(key, J0)`.
--

** To transition to State _Dec_Last_Block_, a Form B `kl.setst` instruction is issued, whereby
`last_blk_len`, the bit length of the last block, is set to the auxiliary argument `Xs`.
A value of zero, larger than 127, or not a multiple of 8, causes the locker to transition to Error State _Invalid_.
// , as it does in the other modes that take a final-block length (<<KLEE-OCB-mode>>, <<KLEE-CMAC-mode>>, <<KLEE-Ascon-AEAD128>>).

** In State _Dec_Last_Block_, a single Form A ``kl.exec`` instruction can be issued.
   “``kl.exec OUTPUT, Kn|K(Xn), INPUT``” absorbs the zero-padded final block of the
   ciphertext into the `tag` and decrypts `INPUT` into `OUTPUT`, namely:
+
--
  * local `ctr : int` – the running counter, as an integer.
  * `local tmp : bits(b)`

[]
  . If `last_blk_len = 0`, the final block has already been processed: the locker transitions to Error State _Invalid_ (Rule <<KLEE-MGR-single-last-block>>).
  . `ctr <- int(bswap(J0[127:96]))`
  . `ctr <- (ctr + 1) mod 2^32^`.
  . If `ctr` = `(start_ctr - 1) mod 2^32^`, then:
   .. the locker transitions to Error State _Invalid_.
  . else:
  .. `tmp <- zeros(128-last_blk_len) @ INPUT[last_blk_len-1:0]`.
  .. `absorb(tmp)`.
  .. `J0[127:96] <- bswap(bin(ctr,32))`.
  .. `OUTPUT <- tmp xor (zeros(128-last_blk_len) @ enc_blk(key, J0)[last_blk_len-1:0])`.
  .. `last_blk_len <- 0`
--

** To transition to State _Dec_Tag_Finalize_, a Form C ``kl.setst`` instruction is expected to provide the following value, which must be set by the software:
+
--
[none]
* `INPUT <- bswap(bin(len_in_bits(plaintext), 64)) @ bswap(bin(len_in_bits(AD), 64))`

The authentication tag is computed as follows:

. `absorb(INPUT)`.
  . `tag <- tag xor enc_blk(key, bswap(bin(start_ctr,32)) @ J0[95:0])`.
--
+
`INPUT` is truncated to its 128 least significant bits (Rule <<KLEE-MGR-fixed-width-input>>).

** To transition to State _Hash_Verify_, a Form C ``kl.setst`` instruction
   is expected, to provide the value against which the internally computed tag
   must be compared (Rule <<KLEE-MGR-tag-verify>>). If the values match, the state
   transitions to _Success_; otherwise, it transitions to _Failure_.

** `auth_key` is a derived field (Rule <<KLEE-MGR-recomputed-fields>>): `auth_key <- enc_blk(key, zeros(128))`.

[[KLEE-GCM-with-IV-mode]]
=== GCM with Set IV

The mode of operation “GCM with a Set IV” is a variant of GCM in which the initialization vector (IV) is predefined rather than generated randomly.
This variant _cannot_ be emulated with an ECB CC because that would reveal the internal data.

This Machine is the same as GCM (<<KLEE-GCM-mode>>) except for the setting of the IV, which is omitted: the IV, as `J0`,
is carried in the Provisioning Input, so State _Set_Aux_Value_ and everything that GCM specifies for it do not apply,
and _Hash_Absorb_ is entered from _Ready_. The differences follow.

Data Structures:::

* *Provisioning Input*:
+
--
[cols="^8%,<15%,<15%,<62%",options="header"]
|===
|  Pos. | Size (Bits)   | Field       | Description
|  ii   | `k` or 64     | `key`       | Key value or System Key Identifier
| iii   | 128           | `J0`        | {empty}
|===
--

* *Internal State*: {empty}
+
--
Same as for GCM.

Upon provisioning, `start_ctr <- int(bswap(J0[127:96]))`, i.e. the last four bytes of `J0` read as a big-endian integer.
--

* *Serialized Content*: {empty}
+
--
Same as for GCM.
--

* *States and Allowed Transitions:* {empty}
+
--
Same as for GCM, with the following exceptions:

** There is no state _Set_Aux_Value_. The transition is from _Ready_ to _Hash_Absorb_.
--

* *State Machine Behavior:* {empty}
+
--
The differences with respect to GCM are:

 ** To transition to State _Hash_Absorb_: The ``kl.setst`` instruction must be of Form A, i.e., _without any additional inputs_, since the IV is already included in the PI.
 ** Entering State _Ready_ does not re-initialise `J0` or `start_ctr`: a later message continues the counter of the previous one and uses the same tag mask. Software that needs to reuse the initial `J0` keeps a copy of the initial SCC.
// ** No transition back to State _Ready_ is allowed. This is one of the Machine-specific
//    prohibitions contemplated by <<KLEE-State-field>>.
//    Allowing it would reinstall the same
//    nonce and permit keystream reuse, which Ascon-AEAD128, unlike a misuse-resistant mode,
//    does not survive.
--

NOTE: This Machine protects the confidentiality of the IV, not against its reuse (<<KLEE-nonce-reuse>>).

[[KLEE-GCM-SIV-mode]]
=== GCM-SIV Mode

The GCM-SIV mode is described in cite:[DBLP-journals-iacr-GueronLL17] and cite:[RFC8452].
It is currently defined only for 128-bit block ciphers; the definition will be extended to other block sizes if needed.
(((KLEE, Machine, GCM-SIV)))

While the decryption state machine of GCM-SIV is similar to that of GCM, the encryption state machine is different:

* During encryption, the _Hash_Absorb_ state absorbs the entire associated data and plaintext. The _Enc_Tag_Finalize_ state then absorbs the lengths and produces the SIV/tag. Finally, the _Encrypt_ state performs a second pass to encrypt the plaintext using the SIV/tag as the initialization vector.
* During decryption, the _Hash_Absorb_ state absorbs only the associated data. The _Decrypt_ state decrypts the ciphertext and simultaneously absorbs the plaintext into the hash. Finally, the _Dec_Tag_Finalize_ state absorbs the lengths, produces the SIV/tag, and internally compares it to the provided SIV/tag.

//

Parameters:::

* `k` = key size, either 128 or 256: cite:[RFC8452] defines AES-GCM-SIV only for these two.
* `b` = 128 = block size.
* `c` = 32 = counter size.
* Granularity: `b`.
* The authentication tag is `b` = 128 bits long.
* A message holds at most 2^32^ blocks, the final partial block included, which is the `P_MAX` of cite:[RFC8452] {sect}6.

Data Structures:::

* *Provisioning Input*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)   | Field
|  ii  | `k` or 64     | `key` or System Key Identifier
|===
--

* *Internal State*:
  ** `key`: `k` bits.
 ** `enc_key` (derived): `k` bits.
 ** `auth_key` (derived): 128 bits. Rule <<KLEE-MGR-recomputed-fields>> applies to both.
 ** `nonce`: 96 bits.
 ** `ctr`: an integer in the range 0 to 2^32^, held on 33 bits and serialized on 32 bits as `bin(ctr mod 2^32^, 32)`.
    `ctr` = 2^32^ is reached only after the last block of a message of 2^32^ blocks, and any further block invalidates the locker.
    An image exported with `ctr` = 2^32^ is imported with `ctr` = 0: this gives no capability beyond re-importing an SCC saved before the first block of the message.
 ** SIV: 128 bits.
 ** `tmp`: 128 bits.
 ** `last_blk_len`: 7 bits (value between 0 and 127).

* *Serialized Content*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
|  Pos. | Size (Bits)     | Field
|    i  |  `k` or 64      | `key` or System Key Identifier
|   ii  |  96             | `nonce`
|  iii  |  32             | `ctr`
|   iv  |  128            | SIV
|    v  |  128            | `tmp`
|   vi  |  16             | `last_blk_len`
|===
--

//

Machine-Specific Functions:::

* `enc_blk(key, p) -> c` encrypts block `p` using the key, and returns the result `c`.
* `RFC8452_KeyDeriv(k, key, nonce)` derives the per-nonce message-encryption and
  message-authentication keys of cite:[RFC8452] {sect}4:
+
[[KLEE-GCM-SIV-KeyDeriv]]
.AES-GCM-SIV Key Derivation
[]
----
function RFC8452_KeyDeriv(k : int, key : bits(k), nonce : bits(96))
    → struct{enc_key : bits(k), auth_key : bits(128)} =
{
  local A : array [0..5] of bits(128);
  local E : bits(k);
  local i : int;

  foreach(i from 0 to k/64 + 1) do:
    A[i] ← enc_blk(key, nonce @ bin(i,32));
  foreach(i from 2 to k/64 + 1) do:
    E[64*i-65 : 64*i-128] ← A[i][63:0];

  return struct { enc_key = E, auth_key = A[1][63:0] @ A[0][63:0] };
}
----
+
The loop makes `k`/64 + 2 calls, four for `k` = 128 and six for `k` = 256, and keeps the low
64 bits of each: these are the “first eight bytes” of cite:[RFC8452] under <<Zkl-notation.adoc#KLEE-Notation>>.
* `absorb(data)` absorbs data into the hash function by performing a step of POLYVAL:
  . `tmp <- tmp xor data`.
  . `tmp <- Montmul(tmp, auth_key)`

State Machine:::
  * *States:*
+
--
Besides _Ready_, _Success_, and _Failure_, the GCM-SIV Machine makes use of the following states:

 ** _Set_Aux_Value_: Set the value of `nonce`.
 ** _Set_Aux_Value_2_: Set the SIV.
 ** _Hash_Absorb_: Process AD and, if encrypting, also the plaintext into the partial tag (this is accumulated in the state variable `tmp`).
 ** _Encrypt_: Encrypt the plaintext.
 ** _Enc_Last_Block_: Encrypt the final, fractional block of the plaintext.
 ** _Enc_Tag_Finalize_: Finalize the SIV with the AD and PT lengths, prepare to return its value.
 ** _Decrypt_: Absorb the ciphertext into the partial tag and decrypt it.
 ** _Dec_Last_Block_: Decrypt the final, fractional block of the ciphertext.
 ** _Dec_Tag_Finalize_: Finalize the tag with the AD and CT lengths, then compare it against the SIV.
--

* *Allowed State Transitions:*
 ** _Ready_ -> _Set_Aux_Value_.
 ** _Set_Aux_Value_ -> _Set_Aux_Value_2_ or _Hash_Absorb_.
 ** _Set_Aux_Value_2_ -> _Hash_Absorb_.
 ** For encryption: _Hash_Absorb_ -> _Enc_Tag_Finalize_ -> _Encrypt_ { -> _Enc_Last_Block_ }.
  *** Transition to _Enc_Tag_Finalize_ possible only if encryption is allowed (Rule <<KLEE-MGR-policy-gate>>).
  *** The encryption path ends in _Encrypt_ or _Enc_Last_Block_, not in _Success_: the tag has already been output by the
      _Enc_Tag_Finalize_ `kl.exec`. The next message starts with a return to _Ready_ (Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-to-ready>>).
 ** For decryption: _Hash_Absorb_ -> _Decrypt_ -> { _Dec_Last_Block_ -> } _Dec_Tag_Finalize_ -> _Success_ or _Failure_.
  *** Transition to _Decrypt_ possible only if decryption is allowed (Rule <<KLEE-MGR-policy-gate>>).

* *Behavior:*
** In State _Ready_ :
  *** Upon entering the state, the following initialization operations are performed:
   . `nonce`, `ctr`, `tmp`, `SIV <- 0`.

** To enter state _Set_Aux_Value_, a Form C `kl.setst Kn|K(Xn), #kl_state_set_aux_value, INPUT` is expected.
    Then, the following operations are performed:
+
--
   . `nonce` <- `INPUT[95:0]`
   .  (`enc_key`, `auth_key`) `<-` `RFC8452_KeyDeriv(k, key, nonce)`
--
+
Repeating the instruction is harmless: it overwrites `nonce` and recomputes `enc_key` and `auth_key` before any other operation.

 ** To enter state _Set_Aux_Value_2_, a Form C `kl.setst Kn|K(Xn), #kl_state_set_aux_value_2, INPUT` is expected.
    Then:
+
--
   . SIV <- `INPUT`
--
+
[NOTE]
====
This state is used during decryption.
Invoking it during encryption is harmless: the encryption path reaches _Encrypt_ only through the _Enc_Tag_Finalize_ `kl.exec`, which overwrites `SIV` with the synthetic value, so an externally set `SIV` is never used as the encryption keystream.
Skipping it during decryption is also harmless, being equivalent to setting SIV to zero,
and so is repeating it: it overwrites the SIV field, on which no other state depends.
====

** The transitions to States _Hash_Absorb_, _Enc_Tag_Finalize_, _Decrypt_, and _Dec_Tag_Finalize_ are
   performed with Form A `kl.setst` instructions. State _Encrypt_ is *not* entered by `kl.setst`:
   it is reached only from the _Enc_Tag_Finalize_ `kl.exec` above, which synthesizes `SIV` first, so
   a `kl.setst` naming _Encrypt_, in any State including _Encrypt_, is a not-allowed transition and invalidates the locker
   (Rule <<KLEE-MGR-not-allowed-instructions>>). This prevents an externally supplied `SIV` from being
   used as the encryption keystream input.

** {empty}
+
--
In State _Hash_Absorb_, (multi-block) Form B ``kl.exec`` instructions are expected.

Such an instruction absorbs its `INPUT` into the internal state variable `tmp`, i.e., it performs `absorb(INPUT)`.

The caller must zero every bit of a final partial block beyond the actual
end of the data being absorbed—the AD, and on the encryption path also the plaintext.
cite:[RFC8452] {sect}4 specifies both the AD and the plaintext as zero-padded to a multiple of 16 bytes.
--

** In State _Enc_Tag_Finalize_, a ``kl.exec`` instruction of Form A is expected. Its input value
+
--
[none]
  *** `INPUT <- bin(len_in_bits(plaintext), 64) @ bin(len_in_bits(AD), 64)`,
--
+
is set by the user.
Then, “``kl.exec``” finalizes the SIV computation by performing:
+
--
  . `absorb(INPUT)`.
  . `tmp <- enc_blk(enc_key, 0 @ tmp[126:96] @ (tmp[95:0] xor nonce))`.
  . `SIV <- tmp` and `OUTPUT <- SIV`.
  . The state transitions to _Encrypt_.
--
+
`INPUT` is truncated to its 128 least significant bits (Rule <<KLEE-MGR-fixed-width-input>>).

** In State _Encrypt_, (multi-block) Form A ``kl.exec`` instructions are expected.
      Issuing “``kl.exec OUTPUT, Kn|K(Xn), INPUT``,” encrypts `INPUT` into `OUTPUT`
      as follows:
+
--
  . If `ctr` = 2^32^, then the locker transitions to Error State _Invalid_: the block would be one more than a message may hold.
  . ``OUTPUT <- INPUT xor enc_blk(enc_key, 1 @ SIV[126:32] @ bin((int(SIV[31:0]) + ctr) mod 2^32^, 32)),``
  . `ctr <- ctr + 1`.
--
** To transition to State _Enc_Last_Block_, a Form B `kl.setst` instruction is issued, whereby
`last_blk_len`, the bit length of the last block, is set to the auxiliary argument `Xs`.
cite:[RFC8452] expresses this length in bytes, so `last_blk_len` must be a multiple of 8 (Rule <<KLEE-MGR-last-blk-len>>).
A value of zero, larger than 120, or not a multiple of 8, causes the locker to transition to Error State _Invalid_.

** In State _Enc_Last_Block_, a single Form A ``kl.exec`` instruction is expected.
      Issuing “``kl.exec OUTPUT, Kn|K(Xn), INPUT``,” encrypts `INPUT` into `OUTPUT`
      as follows:
+
--
. If `last_blk_len = 0`, the final block has already been processed: the locker transitions to Error State _Invalid_ (Rule <<KLEE-MGR-single-last-block>>).
. If `ctr` = 2^32^, then the locker transitions to Error State _Invalid_: the block would be one more than a message may hold.
    . ``OUTPUT <- zeros(128-last_blk_len) @ (INPUT[last_blk_len-1:0] xor enc_blk(enc_key, 1 @ SIV[126:32] @ bin((int(SIV[31:0]) + ctr) mod 2^32^, 32))[last_blk_len-1:0]),``
    . `ctr <- ctr + 1`.
    . `last_blk_len <- 0`
--

** In State _Decrypt_, (multi-block) Form A ``kl.exec`` instructions are expected.
   “``kl.exec OUTPUT, Kn|K(Xn), INPUT``” decrypts `INPUT` into `OUTPUT` and then absorbs the plaintext `OUTPUT` into `tmp`:
+
--
. If `ctr` = 2^32^, then the locker transitions to Error State _Invalid_: the block would be one more than a message may hold.
. ``OUTPUT <- INPUT xor enc_blk(enc_key, 1 @ SIV[126:32] @ bin((int(SIV[31:0]) + ctr) mod 2^32^, 32))``,
. `absorb(OUTPUT)`.
. `ctr <- ctr + 1`.
--
** To transition to State _Dec_Last_Block_, a Form B `kl.setst` instruction is issued, whereby
`last_blk_len`, the bit length of the last block, is set to the auxiliary argument `Xs`.
A value of zero, larger than 120, or not a multiple of 8, causes the locker to transition to Error State _Invalid_: cite:[RFC8452] defines the mode over byte strings, so the same rule applies on both the encryption and the decryption path.

** In State _Dec_Last_Block_, a single Form A ``kl.exec`` instruction is expected.
      Issuing “``kl.exec OUTPUT, Kn|K(Xn), INPUT``,” decrypts `INPUT` into `OUTPUT` and
      absorbs the zero-padded plaintext into the partial tag, as follows:
+
--
. If `last_blk_len = 0`, the final block has already been processed: the locker transitions to Error State _Invalid_ (Rule <<KLEE-MGR-single-last-block>>).
. If `ctr` = 2^32^, then the locker transitions to Error State _Invalid_: the block would be one more than a message may hold.
    . ``OUTPUT <- zeros(128-last_blk_len) @ (INPUT[last_blk_len-1:0] xor enc_blk(enc_key, 1 @ SIV[126:32] @ bin((int(SIV[31:0]) + ctr) mod 2^32^, 32))[last_blk_len-1:0]),``
    . `absorb(OUTPUT)`.
    . `ctr <- ctr + 1`.
    . `last_blk_len <- 0`
--

** In State _Dec_Tag_Finalize_, which performs the comparison itself since the SIV is an input of the decryption (Rule <<KLEE-MGR-tag-verify>>),
    a single ``kl.exec`` instruction of Form B is expected,
    namely “``kl.exec Kn|K(Xn), INPUT``”, where the user is responsible for setting
+
--
[none]
  ***  `INPUT <- bin(len_in_bits(plaintext), 64) @ bin(len_in_bits(AD), 64)`.
--
+
``kl.exec`` then performs the following operations:
+
--
  . `absorb(INPUT)` (which modifies `tmp`).
  . `tmp <- enc_blk(enc_key, 0 @ tmp[126:96] @ (tmp[95:0] xor nonce))`.
    . If `tmp` = `SIV`, then:
    ..  `State <- kl_state_success`
    . else:
    ..  `State <- kl_state_failure`
--
+
`INPUT` is truncated to its 128 least significant bits (Rule <<KLEE-MGR-fixed-width-input>>).

** `enc_key` and `auth_key` are derived fields (Rule <<KLEE-MGR-recomputed-fields>>):
(`enc_key`, `auth_key`) <- `RFC8452_KeyDeriv(k, key, nonce)`.

[[KLEE-OCB-mode]]
=== OCB Mode

Only the OCB3 variant of OCB is architected, following RFC{nbsp}7253 cite:[RFC7253] and cite:[DBLP-journals-joc-KrovetzR21].
The state machine closely follows RFC{nbsp}7253, with two differences: little-endian bit numbering is used instead of big-endian, and zero-based indexing instead of one-based.
This specification defines OCB only for block ciphers with 128-bit blocks.
Generalization to other widths is straightforward, supported by the security proof of the original algorithm and a lower bound on nonce length from cite:[cryptoeprint-2023-326].

Parameters:::
+
--
* `b` = 128 = block size, assumed to be a power of 2.
* `k` = key size. Currently, it can only be 128, 192, or 256.
* `MAX_BLOCKS` = 2^48^ = maximum number of blocks, a final partial block included, in the AD or in the plaintext.
  cite:[RFC7253] places no limit on the length of a message, so this is a bound of this specification.
  The recommendation of cite:[RFC7253] {sect}5 that a key encrypt at most 2^48^ blocks in total is left to the caller,
  as is the reuse of an IV, and with it of the tag mask, in <<KLEE-GCM-with-IV-mode>>.
* Granularity: `b`.
--

Data Structures:::

* *Provisioning Input*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)   | Field
|  ii  | `k` or 64      | `key` or System Key Identifier
|===
--

* *Internal State*:
  ** `key`: `k` bits.
 ** `N`: `120` bits.
 ** `N_len`: 7 bits. Bit length of the nonce. It cannot exceed 120.
 ** `L*`, `offset`, `hash_A`, `checksum_P` : 128 bits each. The derived values `L$` and `L[0]` (Behavior) may be cached or recomputed.
 ** `tag_len`: 8 bits. Bit length of the tag. Currently, the allowed values are 64, 96, and 128.
 ** `last_blk_len`: `7` bits. Length of the last block of AD or plaintext/ciphertext in bits. It is between 0 and 120 (`b` - 8) and must be a multiple of 8, since cite:[RFC7253] defines OCB over byte strings (Rule <<KLEE-MGR-last-blk-len>>). A value that is not a multiple of 8, or that exceeds 120, causes the locker to transition to Error State _Invalid_.
 ** `index`: 49 bits, corresponding to `i` in the loops in RFC{nbsp}7253. It ranges from 0 to `MAX_BLOCKS` + 1 = 2^48^ + 1.
 **  `L~i~` (derived): array of 128 bit values, with `i` up to `floor(log_2(MAX_BLOCKS))`. Rule <<KLEE-MGR-recomputed-fields>> applies.

* *Serialized Content*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
|  Pos. | Size (Bits) | Field
|   i   | `k` or 64   | `key` or System Key Identifier
|   ii  | 120         | `N`
|  iii  |   7         | `N_len`, the bit length of the nonce
|   iv  |   1         | Padding
|    v  | 128         | `L*`; the derived `L$` and `L[i]` are recomputed or re-derived upon import
|   vi  | 128         | `offset` (current offset)
|  vii  | 128         | `hash_A`
| viii  | 128         | `checksum_P` (used also for the final tag)
|   ix  |  49         | `index`
|    x  |   2         | `tag_len`, encoded as `tag_len`/32 − 2
|   xi  |   7         | `last_blk_len`
|===
--

//

Machine-Specific Functions:::

* `enc_blk(K,p) -> c` encrypts block `p` using the key `K` and returns the result `c`.
* `dec_blk(K,c) -> p` decrypts block `c` using the key `K` and returns the result `p`.
* `ntz(n)` = the number of trailing zero bits in the base-2 representation of the positive integer `n`.
Formally, `ntz(n)` is the largest integer `x` for which `2^x^` divides `n`.
* `ocb_pad(X, n)` = the `b`-bit value holding the `n`-bit partial block `X[n-1:0]`
  followed, in string order, by a single `1` bit and then zeros. This is
  `X {vvert} 1 {vvert} 0^127-n^` of cite:[RFC7253] {sect}4.2, and under
  <<Zkl-notation.adoc#KLEE-Notation>> it is
+
`{fournbsp}{fournbsp}` `ocb_pad(X, n)` = `zeros(120-n) @ 0b10000000 @ X[n-1:0]`.
+
The terminating `1` is the *most significant* bit of byte `n/8`, not bit `n` of the
value: in string order it immediately follows the last data bit, and within a byte the
first bit of the string is that byte's most significant bit. `ocb_pad` is defined for
`n` a multiple of 8 with `0` {le} `n` {le} 120; for `n` = 0 it is
`zeros(120) @ 0b10000000`.
* `double(S)`: doubling in the OCB3 field.
Note that cite:[RFC7253] specifies this operation over a big-endian string, hence:
+
`{fournbsp}{fournbsp}` `double(S) <- bswap(update_mask(bswap(S)))`.
* `nonce_be(N, n)` = the big-endian view of the `n`-bit nonce bit string held in `N`.
  cite:[RFC7253] treats the nonce as a bit string whose first bit is the most significant, so
  when it is serialized into bytes the final, possibly partial byte is *left-aligned*: its
  `r` = `n` mod 8 most significant bits carry nonce and its remaining bits are padding. With
  `q` = {lceil}``n``/8{rceil} the number of bytes so occupied,
+
`{fournbsp}{fournbsp}` `nonce_be(N, n)` = `bswap(N[8q-1:0], q) >> ((8 - r) mod 8)`.
+
The first bit of the nonce string is `nonce_be(N, n)[n-1]` and the last is bit `0`.
For `r` = 0 this reduces to `bswap(N[n-1:0])`, so a nonce occupying a whole number of bytes is
unaffected. `bswap` alone cannot express the general case, since it is defined only over byte
strings.

//

State Machine:::
* *States:*
+
--
Besides _Ready_, _Success_, and _Failure_, the Machines implementing OCB Mode make use of the following states:

 ** _Set_Aux_Value_: Set the length and the value of the nonce.
 ** _Hash_Absorb_: Set the tag length, and process the AD.
 ** _Hash_Absorb_Last_Block_: Set the length of the final block (mandatory, can be zero) of the AD and process it.
 ** _Encrypt_: Process the plaintext by absorbing it into the tag and encrypting it.
 ** _Enc_Last_Block_: Provide the last block of the plaintext, then process it.
 ** _Enc_Tag_Finalize_: Return the tag.
 ** _Decrypt_: Process the ciphertext by decrypting it and absorbing the plaintext into the tag.
 ** _Dec_Last_Block_: Provide the last block of the ciphertext, then process it.
 ** _Hash_Verify_: Compare a user-provided value with the internally computed tag.
--

* *Allowed State Transitions:*
 ** _Ready_ -> _Set_Aux_Value_ -> _Hash_Absorb_ -> _Hash_Absorb_Last_Block_
 ** _Hash_Absorb_Last_Block_ -> _Encrypt_, if encryption is allowed (Rule <<KLEE-MGR-policy-gate>>).
 ** _Hash_Absorb_Last_Block_ -> _Decrypt_, if decryption is allowed (Rule <<KLEE-MGR-policy-gate>>).
 ** _Encrypt_ -> _Enc_Last_Block_ -> _Enc_Tag_Finalize_ -> _Success_.
 ** _Decrypt_ -> _Dec_Last_Block_ -> _Hash_Verify_ -> _Success_ or _Failure_.

* *Behavior:*
** The Machine makes frequent use of the following values:
+
--
  . `L* = enc_blk(K, zeros(128))`
  . `L$ = double(L*)`
  . `L[0] = double(L$)`
  . `L[i] = double(L[i-1])`, computed for all `i` with `0 < i` {le} `floor(log_2(MAX_BLOCKS))` (possibly lazily).

An implementation may store these values in the ADS at SCC export and retrieve them at import, or recompute them at import, which is likely to be faster.
--

** In State _Ready_ :
  *** The following initialization operations are performed:
   . `N <- zeros(120)`.
   . `N_len <- 0`.
   . `hash_A <- zeros(128)`
   . `checksum_P <- zeros(128)`
   . `index <- 0`

** To move to _Set_Aux_Value_, a Form B `kl.setst` is expected, where the auxiliary argument `Xs` sets the nonce length `N_len`. `N_len` must satisfy `6` {le} `N_len` {le} `120`; any other value causes the locker to transition to Error State _Invalid_.
Every bit length in that range is admissible: the nonce is a bit string and need not occupy a whole number of bytes.
+
[NOTE]
====
cite:[RFC7253] itself places no lower bound on the nonce length. KLEE requires at least 6 bits
because a shorter nonce leaves the `bottom` and `Stretch` derivation of cite:[RFC7253] {sect}4.2
without enough entropy to remain sound, as analyzed in cite:[cryptoeprint-2023-326]. An
implementation of this specification is therefore not a general RFC{nbsp}7253 implementation for
nonces shorter than 6 bits.
====

** In State _Set_Aux_Value_, ``kl.exec`` instructions are expected to be of Form B, namely
   “``kl.exec Kn|K(Xn), INPUT``”, which sets `N` to the `q` = {lceil}``N_len``/8{rceil} bytes of
   `INPUT` that carry the nonce, namely `N <- zeros(120 - 8q) @ INPUT[8q-1:0]`, with the
   `(8 - N_len) mod 8` least significant bits of byte `q-1` cleared. Those bits are the padding
   of the final, partial byte of the nonce string; they are not part of the nonce and are ignored.
  *** If “``kl.exec Kn|K(Xn), INPUT``”, is repeated, it rewrites `N`.

** To move to _Hash_Absorb_, a Form B `kl.setst` instruction is expected, where the auxiliary argument `Xs` sets the tag length `tag_len`.
   The admissible values for this argument are 64, 96, or 128.
   Any other value causes the locker to transition to Error State _Invalid_.
  *** The following operations are performed:
  . `index <- 1`
  . `tag_len <- Xs`.
  . `offset <- zeros(b)` – this is `Offset~0~` in the RFC.
  . `L* <- enc_blk(key, zeros(b))` – this is `L~*~` in the RFC.
  . `L$ <- double(L*)`
  . `L[0] <- double(L$)`
  . `L[i] <- double(L[i-1])`, performed lazily for all `i` with `0 < i` {le} 48.

** In State _Hash_Absorb_, (multi-block) `kl.exec` instructions are expected to be of Form B, whereby “``kl.exec Kn|K(Xn), INPUT``” absorbs a data block into `hash_A`, i.e.:
+
--
 . If `index` > `MAX_BLOCKS`, then the locker transitions to Error State _Invalid_, and the instruction terminates: the block would be one more than a section may hold.
 . `offset = offset xor L~ntz(index)~`.
 . `hash_A <- hash_A xor enc_blk(key, INPUT xor offset)`.
 . `index <- index + 1`.
--
** To move to _Hash_Absorb_Last_Block_, a Form B `kl.setst` operation is expected, to set the length of the final block of the AD in `last_blk_len`.

** In State _Hash_Absorb_Last_Block_, a single Form B `kl.exec`, “``kl.exec Kn|K(Xn), INPUT``”, absorbs the last block of the AD into `hash_A`:
+
--
  * `tmp : bits(b)`

[]
  . If `last_blk_len = 0`, the final block is empty or has already been processed: the locker transitions to Error State _Invalid_ (Rule <<KLEE-MGR-single-last-block>>).
  . If `index` > `MAX_BLOCKS`, then the locker transitions to Error State _Invalid_, and the instruction terminates: the block would be one more than a section may hold.
  . `offset <- offset xor L*`
  . `tmp <- ocb_pad(INPUT, last_blk_len) xor offset`
  . `hash_A <- hash_A xor enc_blk(key, tmp)`
  . `last_blk_len <- 0`
--
+
An empty final block of the AD, set with `last_blk_len` = 0, needs no `kl.exec`: the next instruction is the `kl.setst` into _Encrypt_ or _Decrypt_.

** Upon entering states `_Encrypt_` or `_Decrypt_`, by a Form A `kl.setst`, the “setup” and “init” stages of the OCB algorithm are performed:
+
--
 * `Nonce_be : bits(128)` – this is `Nonce` in the RFC, in the big-endian view.
 * `Ktop : bits(128)`, `Ktop_be : bits(128)`
 * `Stretch_be : bits(192)` – this is `Stretch` in the RFC, in the big-endian view.
 * `bottom : int`

[]
 . `offset`, `L*`, `L$` are defined as when entering State _Hash_Absorb_.
 . `Nonce_be <- bin(tag_len mod 128, 7) @ zeros(120 - N_len) @ 1 @ nonce_be(N, N_len)`
 . `bottom <- int(Nonce_be[5:0])`
 . `Ktop <- enc_blk(key, bswap(Nonce_be[127:6] @ zeros(6)))`
 . `Ktop_be <- bswap(Ktop)`
 . `Stretch_be <- Ktop_be @ (Ktop_be[127:64] xor Ktop_be[119:56])`
 . `index <- 1`
 . `offset <- bswap(Stretch_be[191-bottom : 64-bottom])`
--
+
[NOTE]
====
cite:[RFC7253] {sect}4.2 specifies these variables over a big-endian bit string, with
positions numbered from 1. They are therefore computed here in the `bswap` view of <<Zkl-notation.adoc#KLEE-Notation>>.
====

** In State _Encrypt_, (multi-block) `kl.exec` instructions are expected to be of Form A:
“``kl.exec OUTPUT, Kn|K(Xn), INPUT``” absorbs the plaintext `INPUT` into the `tag` and encrypts `INPUT` into `OUTPUT`, namely:
+
--
 . If `index` > `MAX_BLOCKS`, then the locker transitions to Error State _Invalid_, and the instruction terminates: the block would be one more than a section may hold.
 . `offset = offset xor L~ntz(index)~`.
 . `checksum_P <- checksum_P xor INPUT`
 . `OUTPUT <- offset xor enc_blk(key, INPUT xor offset)`
 . `index <- index + 1`.
--
** To move to _Enc_Last_Block_, a Form B `kl.setst` instruction is expected to be issued to set the bit length of the final block of the plaintext in `last_blk_len`.

** {empty}
+
--
In State _Enc_Last_Block_, if `last_blk_len` is nonzero, a single ``kl.exec`` instruction of Form A
   “``kl.exec OUTPUT, Kn|K(Xn), INPUT``” is expected.
In this case, the following operations are performed:

 * `tmp : bits(b)`

[]
 . If `index` > `MAX_BLOCKS`, then the locker transitions to Error State _Invalid_, and the instruction terminates: the block would be one more than a section may hold.
 . `offset <- offset xor L*`
 . `tmp[last_blk_len-1:0] <- enc_blk(key, offset)[last_blk_len-1:0]` // PAD in RFC{nbsp}7253
 . `OUTPUT <- zeros(128-last_blk_len) @ (INPUT[last_blk_len-1:0] xor tmp[last_blk_len-1:0])`
 . `tmp <- offset xor ocb_pad(INPUT, last_blk_len)`
 . `checksum_P <- enc_blk(key, checksum_P xor tmp xor L$) xor hash_A` // tag

On the other hand, if `last_blk_len` is zero, only a ``kl.exec`` instruction
of Form D, “``kl.exec Kn|K(Xn)``”, is expected, which performs:

. `checksum_P <- enc_blk(key, checksum_P xor offset xor L$) xor hash_A`

In both cases the state then transitions to _Enc_Tag_Finalize_.
--

** In State _Enc_Tag_Finalize_, only a single ``kl.exec`` instruction of Form C,
   “``kl.exec OUTPUT, Kn|K(Xn)``”, is expected, which performs `OUTPUT <-
   zeros(b-tag_len) @ checksum_P[tag_len-1:0]`. The state then transitions to _Success_.

** In State _Decrypt_, (multi-block) ``kl.exec`` instructions are expected to be of Form A.
   Such a ``kl.exec`` decrypts `INPUT` into `OUTPUT`, and absorbs the
   plaintext `OUTPUT` into the `tag`, namely:
+
--
  * `tmp : bits(b)`

[]
  . If `index` > `MAX_BLOCKS`, then the locker transitions to Error State _Invalid_, and the instruction terminates: the block would be one more than a section may hold.
  . `offset = offset xor L~ntz(index)~`.
  . `tmp <- offset xor dec_blk(key, INPUT xor offset)`
  . `checksum_P <- checksum_P xor tmp`
  . `OUTPUT <- tmp`
  . `index <- index + 1`.
--
** To move to State _Dec_Last_Block_, a Form B `kl.setst` is expected,
   which sets the bit length of the final block of the
   ciphertext in `last_blk_len`.

** In State _Dec_Last_Block_, if `last_blk_len` is nonzero,
only a single ``kl.exec`` instruction of Form A “``kl.exec OUTPUT, Kn|K(Xn), INPUT``” is expected.
In this case, the following operations are performed:
+
--
   * `tmp : bits(b)`

[]
   . If `index` > `MAX_BLOCKS`, then the locker transitions to Error State _Invalid_, and the instruction terminates: the block would be one more than a section may hold.
   . `offset <- offset xor L*`
   . `tmp[last_blk_len-1:0] <- enc_blk(key, offset)[last_blk_len-1:0]` // PAD in RFC{nbsp}7253
   . `OUTPUT <- zeros(128-last_blk_len) @ (INPUT[last_blk_len-1:0] xor tmp[last_blk_len-1:0])`
   . `tmp <- offset xor ocb_pad(OUTPUT, last_blk_len)`
   . `checksum_P <- enc_blk(key, checksum_P xor tmp xor L$) xor hash_A` // tag
   . The state transitions to _Hash_Verify_.

On the other hand, if `last_blk_len` is zero, only a ``kl.exec`` instruction
of Form D, “``kl.exec Kn|K(Xn)``”, is expected, which performs:

. `checksum_P <- enc_blk(key, checksum_P xor offset xor L$) xor hash_A`
  . The state transitions to _Hash_Verify_.
--

** To complete the decryption algorithm, a Form C ``kl.setst``
   operation is expected, a same-State `kl.setst` into _Hash_Verify_ (Rule <<KLEE-MGR-tag-verify>>), to
   compare the `tag_len` least significant bits of `INPUT` with the
   `tag_len` least significant bits of `checksum_P`:
+
--
  . If the values match, the state transitions to _Success_; otherwise, it transitions to _Failure_.
--

[[KLEE-OCB-with-nonce-mode]]
=== OCB with Set Nonce

The mode of operation “OCB with a Set Nonce” is a variant of OCB (<<KLEE-OCB-mode>>) in which the nonce is
carried in the Provisioning Input, as <<KLEE-GCM-with-IV-mode>> is GCM with the IV so carried.

Data Structures:::

* *Provisioning Input*:
+
--
[cols="^8%,<15%,<15%,<62%",options="header"]
|===
|  Pos. | Size (Bits)   | Field       | Description
|  ii   | `k` or 64     | `key`       | Key value or System Key Identifier
| iii   | 120           | `N`         | The nonce, in the format of the `INPUT` of the _Set_Aux_Value_ `kl.exec` of <<KLEE-OCB-mode>>.
|  iv   | 7             | `N_len`     | The bit length of the nonce.
|   v   | 1             | Padding     | {empty}
|===
--

* *Internal State*: {empty}
+
--
Same as for OCB.

Upon provisioning, `N_len` is set from the PI, and `N` is set from the PI as the _Set_Aux_Value_ `kl.exec` of <<KLEE-OCB-mode>> sets it from its `INPUT`.
An `N_len` outside [6, 120] causes the locker to transition to Error State _Invalid_ (Rule <<KLEE-MGR-check-on-write>>).
--

* *Serialized Content*: {empty}
+
--
Same as for OCB.
--

* *States and Allowed Transitions:* {empty}
+
--
Same as for OCB, with the following exceptions:

** There is no state _Set_Aux_Value_. The transition is from _Ready_ to _Hash_Absorb_.
--

* *State Machine Behavior:* {empty}
+
--
The differences with respect to OCB are:

 ** The Form B `kl.setst` that sets `tag_len` and transitions to State _Hash_Absorb_ is issued in State _Ready_.
 ** Entering State _Ready_ does not clear `N` and `N_len`: a later message uses the same nonce. Software that needs another nonce provisions another locker.
--

NOTE: This Machine protects the confidentiality of the nonce, not against its reuse (<<KLEE-nonce-reuse>>).

[[KLEE-CMAC-mode]]
=== CMAC Functions

{empty}
(((KLEE, Machine, CMAC)))
CMAC is an algorithm for message authentication codes constructed from a block
cipher. It was designed by Tetsu Iwata and Kaoru Kurosawa and became a NIST
Recommendation in May 2005 cite:[nist-SP-800-38B].

Parameters:::

* `b` = block size of the underlying block cipher.
* `k` = key size (8|`k`).
* Granularity: `b`.

Data Structures:::

* *Provisioning Input*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)   | Field
|  ii  | `k` or 64     | `key` or System Key Identifier
|===
--

* *Internal State*:
  ** `key`: `k` bits.
 ** `hash`: `b` bits.
 ** `last_blk_len`: an integer in the range 0 to `b`, serialized on 32 bits.

* *MachinePolicy*: _MachinePolicy_[0] enables the output of the CMAC, by the Form C `kl.exec` in State _Hash_Output_,
  and _MachinePolicy_[1] its verification, by the `kl.setst` into _Hash_Verify_ (Rule <<KLEE-MGR-policy-gate>>).
  A CC with _MachinePolicy_ = 0b10 can verify a CMAC but never disclose one. A _MachinePolicy_ of 0 is admissible,
  but makes no sense, since the locker can then neither output nor verify a CMAC (<<Zkl-ISA-unpriv.adoc#KLEE-Machine-field>>).

* *Serialized Content*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
|  Pos. | Size (Bits)   | Field
|    i  | `k` or 64     | `key` or System Key Identifier
|   ii  | `b`           | `hash`
|  iii  | 32            | `last_blk_len`
|===
--

//

Machine-Specific Functions:::

* `enc_blk(key, p) -> c` encrypts block `p` using the key `key`, and returns the result `c`.
* `double` is the OCB3 doubling of <<KLEE-OCB-mode>>.
* `gen_subkeys(K) -> (K1,K2)` generates subkeys `K1` and `K2` from the master key `K` as follows:

 . `L <- enc_blk(K, zeros(b))`
 . `K1 <- double(L)`
 . `K2 <- double(K1)`
 . return `(K1, K2)`.


State Machine:::

* *States:*
 ** _Ready_: The CC is ready.
 ** _Hash_Absorb_: Absorb data into the CMAC function.
 ** _Hash_Absorb_Last_Block_: Set the length of the last block to absorb, then absorb it.
 ** _Hash_Output_: Output the CMAC.
 ** _Hash_Verify_: Compare the CMAC with a value supplied by software, without disclosing it.
 ** _Success_: The CC has completed the CMAC operation.
 ** _Failure_: A CMAC verification has failed.

* *Allowed State Transitions:*
 ** _Ready_ -> _Hash_Absorb_ -> _Hash_Absorb_Last_Block_ -> _Hash_Output_ -> _Success_.
 ** _Hash_Output_ -> _Hash_Verify_ -> _Success_ or _Failure_, if verification is allowed (_MachinePolicy_[1], Rule <<KLEE-MGR-policy-gate>>).
 ** From any valid state to State _Ready_ (Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-to-ready>>).
* *Behavior:*
 ** In State _Ready_:
  *** `last_blk_len <- 0`
  *** `hash <- zeros(b)`

 ** The `kl.setst` into _Hash_Absorb_ is of Form A.

 ** In State _Hash_Absorb_, (multi-block) ``kl.exec`` instructions are expected to be of Form B. +
 “``kl.exec Kn|K(Xn), INPUT``”, absorbs the data block `INPUT` into the hash as follows:
+
--
   . `hash <- enc_blk(key, hash xor INPUT)`.
--
 ** Upon issuing a Form B “``kl.setst Kn|K(Xn), #kl_state_hash_last_block, Xs``” where `Xs` contains the bit length of the last block, the following happens:
   . if `Xs > b`, or if `Xs` is not a multiple of 8, then the locker transitions to Error State _Invalid_.
     The multiple-of-8 requirement (Rule <<KLEE-MGR-last-blk-len>>) is what makes the position of the padding bit below
     well-defined; `Xs` = 0 is admissible and is the empty-message case.
   . `last_blk_len <- Xs`.

 ** In State _Hash_Absorb_Last_Block_, only a single ``kl.exec`` instruction of Form B may be issued, i.e., “`kl.exec Kn|K(Xn), INPUT`”, to absorb the data block `INPUT`. `INPUT` is truncated to its `b` least significant bits (Rule <<KLEE-MGR-fixed-width-input>>).
+
--
  . `(K1, K2) <- gen_subkeys(key)`.
  . if `last_blk_len` = `b`, then:
    .. `tmp <- hash xor INPUT xor K1`
  . else, that is if `0` {le} `last_blk_len` < `b`:
    .. `tmp <- hash xor (zeros(b - 8 - last_blk_len) @ 0b10000000 @ INPUT[last_blk_len-1:0]) xor K2`
    .. If `last_blk_len` = 0, `INPUT` is not read and the padded value is `zeros(b-8) @ 0b10000000`.
  . `hash <- enc_blk(key, tmp)`
  . The state is changed to _Hash_Output_.
--

** In State _Hash_Output_, there are two options:

. If _MachinePolicy_[0] is set, a single ``kl.exec`` instruction of Form C can be issued, i.e., “``kl.exec OUTPUT, Kn|K(Xn)``”, to output the hash into `OUTPUT`.
   Bits of `OUTPUT` beyond the `b`-th are cleared.
   Upon issuing that instruction, the CC transitions to State _Success_.

 . Alternatively, if _MachinePolicy_[1] is set, a Form C ``kl.setst Kn|K(Xn), #kl_state_hash_verify, INPUT`` enters State _Hash_Verify_.

** On entering State _Hash_Verify_, the `b` least significant bits of `INPUT` are compared with `hash`, and the state transitions to _Success_ if they match, to _Failure_ otherwise (Rule <<KLEE-MGR-tag-verify>>).
   Software thus verifies a CMAC without the computed value ever being written to a register or to memory.
   Verification of a truncated CMAC is instead performed in software, after emitting the tag.

//

Pseudocode is given in <<Zkl-pseudocode.adoc#KLEE-CMAC-mode-example>>.

[[KLEE-hash-functions-MACs-XOFs]]
=== Hash and MAC Functions, and XOFs

{empty}
(((KLEE, Machine, general hashing)))
(((KLEE, Machine, MAC functions)))
(((KLEE, Machine, XOF)))
This section defines an interface for hash and MAC functions.
The variety of constructions rules out a completely general interface,
but this one describes most common functions, such as SHA2 cite:[nist-fips-180-4], SHA3, and SHAKE cite:[nist-fips-202].

Parameters:::

* `b` = block size (8|`b`). This is the size of an absorbed block and may be different from the size of the internal state that is kept by the function. For a sponge function, this value is the _rate_.
* `t` = tag length (8|`t`). This is the size of the digest, or of the block output each time in a XOF. The present description assumes `t` {le} `b`.
* `n` = size of the internal state kept by the function (8|`n`). For a sponge function, `n-b` is the _capacity_ of the function.
* `k` = key size (8|`k`). Present only if keyed, i.e., a MAC.
* `state_offset` = offset into the state where the block is to be absorbed.
* `tag_offset` = offset of the tag into the state (for instance, when squeezing sponges).
* Granularity: can vary depending on the Machine. This is usually the full length of a vector or vector group.

Data Structures:::

* *Provisioning Input*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)             | Field
.2+|  ii  | If keyed: `k` or 64  | `key` or System Key Identifier
<|          If unkeyed: 0          | none: the Provisioning Input is the MDH only
|===
--

* *Internal State*:
 ** `key`: `k` bits. Present only if keyed, i.e., a MAC.
 ** `state`: `n` bits.
 ** `last_blk_len`: int. Present only if the Hash/MAC needs to provide special handling of a final block beyond caller-managed padding and appending the length.
 ** `input_base`/`output_base` (same field): int. Offset within input/output to read from/write to.
 ** `block_base`: int. Length of absorbed data so far for the current block. Only if required by the algorithm implemented by the Machine.
 ** `cumul_len`: int. Cumulative length of data absorbed so far.
 ** `block`: `b` bits.  Included only if a partial block is maintained separately—for instance when the inputs are not directly absorbed into `state`.

* *Serialized Content*:
+
--
[cols="^6%,<21%,<18%,<55%",options="header"]
|===
|  Pos. | Size (Bits)          | Field             | Notes
.2+| i  | If keyed: `k` or 64  | `key` or SKID     | --
<|        If unkeyed: 0        | none              | --
|   ii | `n`                  | `state`           | --
|  iii | 16                   | `last_blk_len`    | Present only if the Hash/MAC needs to provide special handling of a final block beyond caller-managed padding and appending the length.
|   iv | 16                    | `block_base`     | Amount of data, in bits, stored so far into `block` or accumulated (usually XORed) into `state`.  Only if used by the Machine, else zero padding.
|    v | 16                    | Padding          | --
|   vi |  16                   | Padding          |--
|   vii | 64                   | `cumul_len`       | Cumulative length of the data absorbed so far. Present only if incorporated into the hash by the Machine, or under HMAC (<<KLEE-HMAC>>), else absent.
|  viii | `b`                  | `block`           | Only if `block_base` is defined and the block is stored separately from the `state`.
|===

`input_base`/`output_base` is not serialized: it is reset by every `kl.exec` and restored from `klstart` on resumption.
--

//

NOTE: An unused `last_blk_len` or `block_base` is zero padding; an unused `cumul_len` is absent.
If all three are unused, rows iii to vii are omitted, as is `block`.

Machine-Specific Functions:::

* `process_block()`: Process `block` into the hash or MAC.
* `process_last_block()`: Process `block` into the hash or MAC, using a function
  for the last block.
* `finalize()`: Process the `state` into the digest value. We assume this
  either re-uses `block` (the entire digest, or a unit of XOF output should not
  be bigger than that) or the digest will be part of `state`.
* `update()`: Updates the `state` during the digest output stage.

State Machine:::

* *States:* _Ready_, _Hash_Absorb_, _Hash_Absorb_Last_Block_ (optionally), _Hash_Output_ and _Success_.

 ** _Ready_: The CC is ready.
 ** _Hash_Absorb_: Absorb data into the hash function.
 ** _Hash_Absorb_Last_Block_: Set the length of the last block to absorb, then absorb it.
    Some Machines may not support this state.
 ** _Hash_Output_: Output the hash.
 ** _Success_: The CC has completed the operation (XOFs do not have this state).

* *Allowed State Transitions:*
 ** _Ready_ -> _Hash_Absorb_ -> { _Hash_Absorb_Last_Block_ -> } _Hash_Output_ -> _Success_.
 ** If the Machine is a XOF, there is no transition from _Hash_Output_ to _Success_.
 ** From any valid state to State _Ready_ (Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-to-ready>>).

* *Behavior:*
 ** In State _Ready_:
  *** `last_blk_len`, `block_base`, `cumul_len` and `block` are set to zero.
  *** `state`: the initial value is set as specified by the Machine.

 ** In State _Hash_Absorb_, we enter Procedure `process_VLI` (<<KLEE-process-VLI>>) as:
`process_VLI(max_len, block, b, state, n, input_base, block_base, state_offset, cumul_len, process_block(), None, mode)`,
where `max_len` is the Machine-defined maximum length of the data to be absorbed, in bits, and `state_offset` is Machine-defined.
`finalize` is `None` in this invocation: `finalize()` is performed once, on entering State _Hash_Output_.
`mode` is `assign` for a construction that fills a separate `block` and then processes it into
`state` through `process_block()`, and `xor_accumulate` for one that absorbs the input directly into
`state`, as a sponge does; each instantiation states which it uses.

 ** Upon issuing a Form B “`kl.setst Kn|K(Xn), \#kl_state_hash_last_block,
    Xs`” where `Xs` contains the length of the last block, the following
    happens:
+
--
 . if `block_base` != 0, then the locker transitions to Error State _Invalid_. (The previous block is not complete.)
 . if `Xs > b`, then the locker transitions to Error State _Invalid_.
 . if `Xs = 0`, then the locker transitions to Error State _Invalid_.
 . if `Xs` is not a multiple of 8, then the locker transitions to Error State _Invalid_ (Rule <<KLEE-MGR-last-blk-len>>).
 . `last_blk_len <- Xs`.
--
+
The state then transitions to _Hash_Absorb_Last_Block_.

** State _Hash_Absorb_Last_Block_ is very similar to _Hash_Absorb_; the differences
   are:
 *** `last_blk_len` is used in place of `b` for the amount of data to be absorbed.
 *** `process_last_block()` is called instead of `process_block()` in Step 4.g.
 *** The instruction is terminated after `process_last_block()`—only one block
     is absorbed—and the state transitions to _Hash_Output_.

** Where _Hash_Absorb_Last_Block_ is not used, the `kl.setst` from _Hash_Absorb_ into _Hash_Output_ is of Form A,
   unless the Machine states otherwise. A same-State `kl.setst` into _Hash_Output_ is not allowed (Rule <<KLEE-MGR-no-hash-output-repeat>>).

** In State _Hash_Output_, hash functions and XOFs behave differently.
 *** Upon entering the state, the following operations are first performed:
 . `block[t - 1 : 0] <- finalize()`
 . `block_base <- 0`
*** For each Form C `kl.exec` instruction “`kl.exec OUTPUT, Kn|K(Xn)`”, the
    following operations are performed:
+
--
    * `amount : int`, `{nbsp}` amount of data to copy from `block` to `OUTPUT`

[]
   . `output_base <- 8 {interpunct} klstart` // 0 when the instruction starts
    . while (`output_base` < `KLLEN`) do: // as long as there is room in the OUTPUT
     .. `amount <- min(KLLEN - output_base, t - block_base)`
     .. ``OUTPUT[output_base + amount - 1 : output_base] <- `` +
           ``{fournbsp}{fournbsp}<- block[block_base + amount - 1 : block_base]``
     .. `output_base <- output_base + amount`
     .. `block_base <- block_base + amount`
     .. if (`block_base` = `t`) then:
      ... if we are in a Hash function, any bits of `OUTPUT` beyond `output_base` are cleared,
          the state transitions to _Success_, and the instruction returns.
      ... `update()`
      ... `block_base <- 0`
      ... *Here* the instruction can be interrupted, with `klstart <- output_base / 8`.
          A halt here leaves `block_base` = 0. The interruption points of _Hash_Output_ are therefore, for an XOF, 0 and every byte offset at which `block_base` is 0; a hash function, which emits its whole output in one instruction, has 0 only.
--

[[KLEE-SHA-2]]
=== SHA-2 Family Specific Rules

{empty}
(((KLEE, Machine, SHA-2)))
The primitives of the SHA-2 family cite:[nist-fips-180-4] — SHA-224, SHA-256, SHA-384,
SHA-512, SHA-512/224, and SHA-512/256 — are instantiations of the algorithm specified in
<<KLEE-hash-functions-MACs-XOFs>>, and only the differences with respect to the behavior described
there are given here.

Parameters:::

* The word size `w`, and `b`, `n`, and `t`, as given in <<KLEE-SHA-2-parameters>>; the
  internal state consists of the eight `w`-bit chaining variables of
  cite:[nist-fips-180-4].
* Granularity: 32 bits, with the same meaning as in <<KLEE-SHA-3>>.

[[KLEE-SHA-2-parameters]]
.Parameters of the SHA-2 family
[%autowidth,float="center",align="center",cols="<,^,^,^,^",options="header"]
|===
| Function    | `w` | `b`  | `n`  | `t`
| SHA-224     |  32 |  512 |  256 | 224
| SHA-256     |  32 |  512 |  256 | 256
| SHA-384     |  64 | 1024 |  512 | 384
| SHA-512     |  64 | 1024 |  512 | 512
| SHA-512/224 |  64 | 1024 |  512 | 224
| SHA-512/256 |  64 | 1024 |  512 | 256
|===


Data Structures:::

* *Provisioning Input*: as for <<KLEE-SHA-3>>, the MDH only.

* *Internal State*:

   ** `state`: `n` bits, holding the eight chaining variables `H~i~` big-endian:
      `state[(i+1)w-1 : iw]` = `bswap(bin(H~i~, w))`, for `0` {le} `i` < 8.
   ** `block` (`b` bits).
   ** `block_base`.
   ** `cumul_len` only when operating under HMAC (<<KLEE-HMAC>>).

* *Serialized Content*: as prescribed by <<KLEE-hash-functions-MACs-XOFs>>, with `last_blk_len`
  unused (replaced by padding) and `block` present.

Machine-Specific Functions:::

* `process_block()`: applies the compression function of cite:[nist-fips-180-4] {sect}6 for the
  selected function to absorb the current `block` into `state`, message word `j` being
  `int(bswap(block[(j+1)w-1 : jw]))`, for `0` {le} `j` < 16.
* `finalize()`: `None` for stand-alone hashing — padding and length encoding are the
  caller's responsibility. When operating under HMAC, `finalize()` applies the padding of
  cite:[nist-fips-180-4] {sect}5.1 internally; see <<KLEE-HMAC>>.

State Machine:::

* *States:* _Ready_, _Hash_Absorb_, _Hash_Output_, and _Success_. There is no
  _Hash_Absorb_Last_Block_ state: the caller supplies the padded message as whole blocks.

* *Allowed State Transitions:*
 ** _Ready_ -> _Hash_Absorb_ -> _Hash_Output_ -> _Success_.
 ** From any valid state to State _Ready_ (Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-to-ready>>).

* *Behavior:*
 ** In State _Ready_, `state` is set to the initial hash value of the selected function
    per cite:[nist-fips-180-4] {sect}5.3, and `block_base` and, when it is tracked, `cumul_len` are zeroed.
 ** In State _Hash_Absorb_, Procedure `process_VLI` (<<KLEE-process-VLI>>) is
    entered as
    `process_VLI(max_len=0, block, b, state, n, input_base, block_base, 0, cumul_len, process_block(), None, mode=assign)`,
    where `cumul_len` is `None` in stand-alone hashing, so that the length of the input is neither
    tracked nor bounded, and is tracked under HMAC, whose padding uses it. `mode` is `assign`: the SHA-2 family fills a separate `block` and then applies
    the compression function to it and `state` with a result in `state`.
 ** Upon transitioning to State _Hash_Output_ in stand-alone hashing, `block_base` must
    be zero — the padded message is a whole number of blocks — otherwise the locker
    transitions to Error State _Invalid_.
 ** In State _Hash_Output_, the `t`-bit digest is taken from `state`, not from `block`. The
    output loop of <<KLEE-hash-functions-MACs-XOFs>> therefore reads
    `state[block_base + amount - 1 : block_base]` in place of
    `block[block_base + amount - 1 : block_base]`, and the entry step
    `block[t - 1 : 0] <- finalize()` is not performed, `finalize()` being `None` here. The bytes
    so emitted are the chaining variables in the big-endian encoding, truncated to `t` bits.
    Once `t` bits have been made available the state transitions to _Success_.

[[KLEE-SM3]]
=== SM3 Specific Rules

{empty}
(((KLEE, Machine, SM3)))
The ShangMi 3 hash function, standardized as GB/T 32905-2016, follows exactly the rules
of the SHA-2 family (<<KLEE-SHA-2>>) with `w` = 32, `b` = 512, `n` = 256, and `t` = 256:
it has a big-endian representation with the same padding rule, word mapping and `state`
layout as SHA-256, and the same state machine. The initial hash value and the compression
function are those of the SM3 standard.
Under HMAC (<<KLEE-HMAC>>, `SM3_HMAC`), SM3 behaves as SHA-256 does under HMAC: `cumul_len` is tracked and serialized,
and `K0` is `b` = 512 bits.

[[KLEE-HMAC]]
=== HMAC

Hash function acceleration suffices to compute HMACs, but an environment may want to keep the HMAC key secret or hidden.
This section extends <<KLEE-hash-functions-MACs-XOFs>> accordingly.

Under HMAC, the Machine, not the caller, performs the padding and length encoding of the hash function, at finalization.  For SHA-2 (<<KLEE-SHA-2>>) and SM3 (<<KLEE-SM3>>), standard padding is applied over the total absorbed length (`b` + `cumul_len` bits for the inner hash, `b` + `d` bits for the outer) using `cumul_len`, which is maintained under HMAC.  For SHA-3, the suffix-and-padding of <<KLEE-SHA-3>> applies.

Parameters:::
+
--
* `b` = input block size of the underlying hash function.
* `d` = digest size of the underlying hash function, i.e. the length of its output.
* Granularity: same as that of the underlying hash function.

The two padding constants of cite:[nist-fips-198-1] are:

* `ipad` = the byte `0x36` repeated `b`/8 times, and
* `opad` = the byte `0x5c` repeated `b`/8 times,

both therefore `b` bits long. Every byte of each constant has the same value, so their
representation does not depend on the byte order of <<Zkl-notation.adoc#KLEE-Notation>>.
--

Data Structures:::

* *Provisioning Input*:
+
--
The Machines implementing HMAC algorithms exist in two variants, distinguished by their encoding in the _Machine_ field (<<KLEE-exec-encodings>>): by _Type_ for the SHA-2 and SHA-3 HMACs, and by _Mode_ for `SM3_HMAC`.

The PI of the variant that starts with “No Initial Key” (NIK) contains only the MDH.

The PI of the variant with the “Key in PI” (KIP) has the following format:

[cols="^7%,<23%,<70%",options="header"]
|===
| Pos. | Size (Bits)               | Field
|  ii  | `b^*^`                    | `K0`, the key already reduced to `b` bits (see below), or 64 bits if a system key or randomly generated.
|===

The key provisioned or held in a CC is the value `K0` as defined in cite:[nist-fips-198-1] {sect}3: the key padded with zeros to `b` bits if it is shorter, or hashed and then padded if it is longer.
Deriving `K0` from the original key is the responsibility of whoever provisions it.
--

* *Internal State*:
  ** `hash_fn_state`: this is the entire state of the underlying hash function.
     We assume it has fields corresponding to the following ones:
  *** `state`: `n` bits.
  *** `last_blk_len`: int. Present only if the underlying hash function provides special treatment for a last block that goes beyond padding and appending the length. The latter is the caller's responsibility.
  *** `input_base`: int. Offset within input/output to read from/write to.
  *** `block_base`: int. Length of absorbed data so far for the current block. Only if needed by the Machine.
  *** `cumul_len`: int. Cumulative length of data absorbed so far, tracked by every HMAC Machine (for the `K0` load in _Set_Key_, and for the padding of SHA-2 and SM3).
  *** `block`: `b` bits.  Included only if a partial block is maintained—for instance when the inputs are not directly absorbed into `state`.
 ** `K0`: `b` bits, the value `K0` as per cite:[nist-fips-198-1] {sect}3.
 ** `HasKey` (NIK variant only): Boolean, bit 0 of _StateExtension_, recording that `K0` holds a completely loaded key.
    It follows the pattern of Rule <<KLEE-MGR-load-long-field>>: it is cleared at provisioning and on entering _Set_Key_, and set
    when the load of `K0` completes, by `kl.exec` or by `kl.derive`. The KIP variant does not use _StateExtension_.

* *Serialized Content*:
+
--
[cols="^7%,<23%,<70%",options="header"]
|===
| Pos. | Size (Bits)              | Field
|  i   | variable                 | Serialized Content of the underlying hash function, in its entirety, including its own padding to a multiple of 128 bits.
| ii   | `b^*^` or 64             | `K0`, where `b^*^` = `b` as in the Provisioning Input; 64 bits for a System Key Identifier.
|===
--

//

State Machine::: {empty}
+
--
This family of Machines inserts state _Set_Key_ between _Ready_ and _Hash_Absorb_.

The two variants differ only in how the key first reaches the CC.

In the KIP variant, `K0` is carried in the Provisioning Input.
The key may be given by value or, with _KeyType_ = 1, as an SKID, which includes a randomly generated value.
A KIP CC cannot be re-keyed.

In the NIK variant, the Provisioning Input carries no key. `K0` must be loaded in State _Set_Key_ before _Hash_Absorb_ can be entered:
entering _Hash_Absorb_ requires `HasKey` (Rule <<KLEE-MGR-policy-gate>>), and leaving _Set_Key_ before `K0` is complete zeroes it (Rule <<KLEE-MGR-load-long-field>>).
A loaded key is kept across a return to _Ready_, so that one load of `K0` serves any number of messages.
--
+
* *Allowed State Transitions:*
 ** For the NIK variant: _Ready_ -> _Set_Key_ -> _Hash_Absorb_ -> and the rest as in the underlying hash function, and
    _Ready_ -> _Hash_Absorb_ once `K0` is loaded (`HasKey`)
 ** For the KIP variant: _Ready_ -> _Hash_Absorb_ -> and the rest as in the underlying hash function
 ** From any valid state to State _Ready_ (Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-to-ready>>).

* *Behavior:*
 ** Upon entering State _Set_Key_, `K0` is zeroed, `HasKey` is cleared, and `input_base`, `block_base` and
    `cumul_len` are set to zero. Re-entering _Set_Key_, including by a same-State `kl.setst`
    (Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-same-state>>), therefore restarts the load and replaces the key rather than
    combining the new value with the old one.

 ** Once in State _Set_Key_ the `b`-bit value `K0` is loaded by one or more Form B
    ``kl.exec`` instructions, through Procedure `process_VLI`
    (<<KLEE-process-VLI>>) entered as
+
`{fournbsp}` `process_VLI(b, block=K0, b, state=K0, n=b,` +
`{fournbsp}{fournbsp}{fournbsp}{fournbsp}{fournbsp}` `input_base, block_base, state_offset=0, cumul_len,` +
`{fournbsp}{fournbsp}{fournbsp}{fournbsp}{fournbsp}` `process_block=None, finalize=None, mode=assign)`,
+
where `mode` is `assign` because `K0` is *loaded* into its field, not absorbed into it.
When `cumul_len` reaches `b` the load is complete and `HasKey` is set.
A `kl.derive` into `K0` (<<KLEE-derive-endpoints>>) writes all `b` bits of it and leaves `cumul_len` = `b`, completing the load.

** Upon entering _Hash_Absorb_:
  . `state` is set to the initial value of the underlying hash function.
  . `block`, `block_base` and `cumul_len` are set to zero, discarding any value left by the loading of `K0` in _Set_Key_.
  . `K0 xor ipad` is computed and absorbed in the underlying hash function; this absorption is not counted in `cumul_len`.
  . Then the semantics of the underlying hash function are executed, absorbing the message.
** When entering state _Hash_Output_:
+
--
   * local `inner : bits(d)`

[]
   . If needed, finalize the inner hash `H((K0 xor ipad) {vvert} message)`, whose `d`-bit
    value is then in `state[d+tag_offset-1 : tag_offset]`.
  . `inner <- state[d+tag_offset-1 : tag_offset]`.
  . Reinitialize `state` to the initial value of the underlying hash function `H`.
  . `absorb(K0 xor opad)` as per `H`.
  . `absorb(inner)` as per `H`, so that the outer hash digests
    `(K0 xor opad) {vvert} H((K0 xor ipad) {vvert} message)`, as
    cite:[nist-fips-198-1] {sect}4 requires.
  . Finalize `H`. The `d`-bit HMAC value is available in State
    _Hash_Output_ exactly as for `H`, and is provided to the caller following ``H``'s semantics.
--

[[KLEE-SHA-3]]
=== SHA-3 Family Specific Rules

{empty}
(((KLEE, Machine, SHA-3)))
The Machines of the SHA-3 family, currently SHA3-224, SHA3-256, SHA3-384, SHA3-512, SHAKE128 and SHAKE256 are
all parameter choices of KECCAK cite:[DBLP-conf-eurocrypt-BertoniDPA13] standardized by NIST cite:[nist-fips-202].
They are instantiations of the Machine of <<KLEE-hash-functions-MACs-XOFs>>; this section gives only the differences.

//

Parameters:::

* `n` = 1600.
* `c` = capacity, `b` = rate = 1600 - `c`, and `t` = the number of bits made available by
  each application of `P()` in the output stage, all as given in
  <<KLEE-SHA-3-parameters>>.
* Granularity: 32 bits. This is the smallest element width that may be used for the
  vector inputs of `kl.exec`, not a constraint on the length of the hashed message.

[[KLEE-SHA-3-parameters]]
.Parameters of the SHA-3 family
[%autowidth,float="center",align="center",cols="<,^,^,^,^,<",options="header"]
|===
| Function |  `c` | `b` = 1600 - `c` | `t` | XOF? | Suffix `D`
| SHA3-224 |  448 |       1152       |  224 |   no |   `01`
| SHA3-256 |  512 |       1088       |  256 |   no |   `01`
| SHA3-384 |  768 |        832       |  384 |   no |   `01`
| SHA3-512 | 1024 |        576       |  512 |   no |   `01`
| SHAKE128 |  256 |       1344       | 1344 |  yes | `1111`
| SHAKE256 |  512 |       1088       | 1088 |  yes | `1111`
|===

For the four fixed-output functions, `t` is the digest length, which is `c`/2, and a
single squeeze suffices. For the two extendable-output functions, `t` is the full rate
`b`, since a sponge makes exactly `b` bits available between successive applications of
the permutation.

Data Structures:::

The *Provisioning Input* contains only the MDH.

* *Internal State*:
  ** `state`: `n` bits.
 ** `input_base`: int.
 ** `block_base`: int.
 ** `cumul_len`: int, under HMAC (<<KLEE-HMAC>>) only.

* *Serialized Content*:
+
--
[%autowidth,cols="^,<,<",options="header"]
|===
| Pos. | Size (Bits)   | Field
|   i  | 1600            | `state`
|  ii  | 16              | `block_base`, in bits
| iii  | 64 or 0         | `cumul_len`, under HMAC (<<KLEE-HMAC>>) only
|===

`input_base` is not serialized: it is reset at the start of every `kl.exec` and restored from
`klstart` on resumption (<<KLEE-process-VLI>>), so it carries no state across a context switch.
`last_blk_len` is absent because SHA-3 does not use it.
--

//

Machine-Specific Functions::: {empty}
 * `P()`: computes `KECCAK-p[1600, 24]` on `state`, with result in place.
 * `process_block()`: there is no explicit operation to copy data into
   `state`, as the inputs are directly XORed into it; instead, `process_block`
   applies `P()` to the state.
 * `update()`: updates the `state` during the digest output stage.  It applies `P()` to the state.

//

State Machine::: {empty}
* *States:* _Ready_, _Hash_Absorb_,
  _Hash_Output_ and _Success_.

* *Allowed State Transitions:*
 ** _Ready_ -> _Hash_Absorb_ -> _Hash_Output_ -> _Success_.
 ** From any valid state to State _Ready_ (Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-to-ready>>).

* *Behavior:*
 ** In State _Ready_, `state` is zeroed.
 ** In State _Hash_Absorb_, the input data is directly XORed to `state`,
 through Procedure `process_VLI` (<<KLEE-process-VLI>>), invoked as:
`process_VLI(max_len=0, state, b, state, n, input_base, block_base, 0, None, process_block(), None, mode=xor_accumulate)`.
 ** Upon transitioning to State _Hash_Output_:
 The suffix-and-padding string `S` = `pad10*1`, appended to `D`, is generated, where `D` is the domain-separation suffix given in <<KLEE-SHA-3-parameters>> and `pad10*1` appends a `1`, then as many `0` bits as required, then a final `1`, so that `block_base` + `|S|` is a positive multiple of `b`. Then, the resulting additional block is absorbed:

 . If the bit length of `S` is `b - block_base`:
    .. `S` is directly XORed to the rate part of the state, and
    .. `P()` is applied.
   . If the bit length of `S` is `2 b - block_base`:
    .. The first `b - block_base` bits are XORed to the rate part of the state,
    .. `P()` is applied,
    .. the remaining `b` bits are XORed to the rate part of the state, and
    .. `P()` is applied again.

 ** In State _Hash_Output_, a digest or XOF is extracted following the generic hash function/XOF rules.
  The four SHA3-``n`` functions make a single `t`-bit digest available and then transition to _Success_.
  SHAKE128 and SHAKE256 are XOFs: they never transition to _Success_, and output may be squeezed indefinitely.

The rest of the Machine follows <<KLEE-hash-functions-MACs-XOFs>>.

[[KLEE-KMAC]]
=== KMAC128, KMAC256, KMACXOF128, and KMACXOF256

{empty}
(((KLEE, Machine, KMAC)))
KMAC is the keyed MAC built on cSHAKE, standardized by NIST in cite:[nist-SP-800-185].
It is defined only over the SHA-3 permutation, so its implementation depends on implementing SHA-3.
This section describes only the differences with respect to <<KLEE-SHA-3>>, on which it builds.

Parameters:::

* `n` = 1600.
* KMAC128 and KMACXOF128 use `c` = 256 and rate `b` = 1344 bits (168 bytes);
  KMAC256 and KMACXOF256 use `c` = 512 and rate `b` = 1088 bits (136 bytes).
* `t` = `b`, as for the extendable-output functions of <<KLEE-SHA-3-parameters>>.
* `L` = the requested output length in bits, set on the transition to _Hash_Output_.
* Granularity: 32 bits, with the same meaning as in <<KLEE-SHA-3>>.

Data Structures:::
+
--
A CC does not hold the key `K` and the customization string `S` in their raw form. It
holds the two rate-sized blocks that cite:[nist-SP-800-185] derives from them,
prepared by whoever provisions the CC:

`{fournbsp}{fournbsp}` `cshake_block` = `bytepad(encode_string("KMAC") {vvert} encode_string(S), b/8)`, and +
`{fournbsp}{fournbsp}` `key_block{nbsp}{nbsp}{nbsp}` = `bytepad(encode_string(K), b/8)`,

where `bytepad`, `encode_string` and `left_encode` are as defined in cite:[nist-SP-800-185] {sect}2.3:

[%autowidth,float="center",align="center",cols="<,^,^,^",options="header"]
|===
| Function           | rate `b`/8 | maximum \|`K`\| | maximum \|`S`\|
| KMAC128/KMACXOF128 | 168 bytes | 163 bytes | 157 bytes
| KMAC256/KMACXOF256 | 136 bytes | 131 bytes | 125 bytes
|===

A provisioner presented with a longer key must reduce it beforehand; this specification
does not define how, since cite:[nist-SP-800-185] does not.

With _KeyType_ = 1, the PI and the SCC carry a System Key Identifier in place of `key_block` (<<>>).
The SKS returns the key `K`, and the KLEE unit forms `key_block` = `bytepad(encode_string(K), b/8)` from it;
a `K` longer than the maximum in the table above is a SKID that the SKS may not resolve, and the
locker transitions to Error State _Invalid_ (<<Zkl-ISA-unpriv.adoc#KLEE-system-keys>>).
With the all-ones SKID (<<Zkl-ISA-unpriv.adoc#KLEE-KeyType-field>>), `K` is a random value of `c`/2 bits,
from which `key_block` is formed in the same way.
`cshake_block` is always carried by value.
--
+
* *Provisioning Input*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)   | Field
|  ii  | `b`           | `cshake_block`
| iii  | `b` or 64     | `key_block` or System Key Identifier
|===
--

* *Internal State*: as for <<KLEE-SHA-3>>, with the addition of
 ** `cshake_block`, `key_block`: `b` bits each; and
 ** `L`: 32 bits, the requested output length in bits.

* *Serialized Content*: as for <<KLEE-SHA-3>>, with `cshake_block`, `key_block` and `L`
  appended, and padding to a multiple of 128 bits. Explicitly:
+
--
[%autowidth,cols="^,<,<",options="header"]
|===
| Pos. | Size (Bits) | Field
|   i  | 1600        | `state`
|  ii  | 16          | `block_base`
| iii  | 48          | Padding
|  iv  | `b`         | `cshake_block`
|   v  | `b` or 64   | `key_block` or System Key Identifier
|  vi  | 32          | `L`
|===
--

//

Machine-Specific Functions:::

 * `P()`, `process_block()` and `update()` are as in <<KLEE-SHA-3>>.
 * `right_encode(x)`, as in cite:[nist-SP-800-185] {sect}2.3, is the value `x`
   written as an unsigned big-endian integer on the smallest possible positive number `m`
   of bytes, followed by a single byte holding `m`.

//

State Machine:::

* *States:* _Ready_, _Hash_Absorb_, _Hash_Output_ and _Success_.

* *Allowed State Transitions:* as in <<KLEE-SHA-3>>.

* *Behavior:* as in <<KLEE-SHA-3>>, with the following differences.

 ** In State _Ready_:
  . `state` is zeroed.
  . `cshake_block` is XORed into the rate and `P()` is applied.
  . `key_block` is XORed into the rate and `P()` is applied.

 ** To transition to State _Hash_Output_, a Form B `kl.setst` instruction is expected for `KMAC128` and `KMAC256`,
    whose auxiliary argument sets `L`, the output length in bits.
    `L` must satisfy 0 < `L` < 2^32^; any other value causes the locker to transition to Error State _Invalid_.
+
For `KMACXOF128` and `KMACXOF256`, a Form A `kl.setst` instruction is expected, and `L` is assumed to be zero in the following.

  ** Upon transitioning from _Hash_Absorb_ to State _Hash_Output_:
  . `right_encode(L)` is absorbed, continuing from the current `block_base`.
  . The suffix and padding string `S` = `pad10*1` appended to `D` is generated and
    absorbed exactly as in <<KLEE-SHA-3>>, but with the cSHAKE domain-separation suffix
    `D` = `00` in place of the `1111` of the raw SHAKE functions.

 ** In State _Hash_Output_, for `KMAC128` and `KMAC256`, `L` counts the bits still to be made
    available. The output loop of <<KLEE-hash-functions-MACs-XOFs>> takes
    `amount` {leftarrow} `min(KLLEN - output_base, t - block_base, L)` and then performs the following operations:
+
--
. `L` {leftarrow} `L - amount`.
. If `block_base` = `t` and `L` > 0, `update()` is applied.
. If `L` = 0, the bits of `OUTPUT` beyond `output_base` are cleared, and the state transitions to _Success_.
--
+
The output thus consists of {lceil}``L``/8{rceil} bytes for the value of `L` set on entering _Hash_Output_;
the last of them holds the final `L` mod 8 bits, if any, in its least significant bits.
+
For `KMACXOF128` and `KMACXOF256`, arbitrarily many bits can be squeezed,
following the semantics of <<KLEE-hash-functions-MACs-XOFs>>, producing `KLLEN` bits for each `kl.exec`,
and the Machine never transitions to _Success_.

[[KLEE-Ascon-AEAD128]]
=== Ascon-AEAD128

{empty}
(((KLEE, Machine, Ascon)))
Ascon is a public permutation cite:[DBLP-journals-joc-DobraunigEMS21] standardized by NIST cite:[nist-SP-800-232] together with various cryptographic algorithms designed around it.

In Ascon-AEAD128, the caller is responsible for applying ``pad(``{nbsp}{interpunct}``, 128)`` to the associated data, so that the Machine in State _Hash_Absorb_ absorbs a whole number of 128-bit blocks.
The final block of the plaintext or ciphertext must *not* be padded by the caller: it is supplied through State _Enc_Last_Block_, resp. _Dec_Last_Block_, whose `last_blk_len` argument gives its length in bits, and the Machine applies ``pad(``{nbsp}{interpunct}``, 128)`` to it internally.
Padding it in software as well corrupts both the ciphertext and the tag.

Parameters:::

* `b` = 128.
* `k` = 128.
* Granularity: 128 bits.

Data Structures:::

* *Provisioning Input*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)   | Field
|  ii  | 128 or 64     | `key` or System Key Identifier
|===
--

* *Internal State*:
  ** `key`: 128 bits.
 ** `state[0 .. 4]`: five 64-bit words, i.e., 320 bits.
 ** `tag_len`: 8 bits as int.
 ** `last_blk_len`: 9 bits as int.

* *Serialized Content*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)     | Field
|    i | 128 or 64       | `key` or System Key Identifier
|   ii | 64              | `state`[0]
|  iii | 64              | `state`[1]
|   iv | 64              | `state`[2]
|    v | 64              | `state`[3]
|   vi | 64              | `state`[4]
|  vii | 16              | `last_blk_len`
| viii | 16              | `tag_len`
|===
--

Machine-Specific Functions:::
* `ASCON(p)` applies `p` rounds of ASCON to the `state`.
* `pad(x,r)` appends the bit 1 to the bit string `x`, followed by the bit string `0^j^` where `j` = `(- |x| - 1) mod r`: `pad(x,r) = 0^j^ @ 1 @ x`.

State Machine:::

* *States:*
 ** _Ready_: The CC is ready.
 ** _Hash_Absorb_: Set the nonce, and process the AD.

 ** _Encrypt_: Encrypt the plaintext.
 ** _Enc_Last_Block_: Encrypt the last block of the plaintext.
 ** _Hash_Output_: Return the tag.

 ** _Decrypt_: Decrypt the ciphertext.
 ** _Dec_Last_Block_: Decrypt the last block of the ciphertext.
 ** _Hash_Verify_: Compare a user-provided value with the internally computed tag.

 ** _Success_: The Machine has completed its operation without errors.
 ** _Failure_: The Machine has completed its operation with an authentication failure.

* *Allowed State Transitions:*
 ** _Ready_ -> _Hash_Absorb_.
 **  _Hash_Absorb_ -> _Encrypt_, if encryption is allowed (Rule <<KLEE-MGR-policy-gate>>).
 **  _Hash_Absorb_ -> _Decrypt_, if decryption is allowed (Rule <<KLEE-MGR-policy-gate>>).
 ** _Encrypt_ -> _Enc_Last_Block_ -> _Hash_Output_ -> _Success_. A `kl.setst` into _Enc_Last_Block_ with `Xs` = 0 enters _Hash_Output_ directly, after padding the empty final block; there is no direct transition from _Encrypt_ to _Hash_Output_.
 ** _Decrypt_ -> _Dec_Last_Block_ -> _Hash_Verify_ -> _Success_ or _Failure_. A `kl.setst` into _Dec_Last_Block_ with `Xs` = 0 enters _Hash_Verify_ directly, after padding the empty final block; there is no direct transition from _Decrypt_ to _Hash_Verify_.

* *Behavior:*
** In State _Ready_ :
  *** The following initialization operations are performed:
   . `state[0] <- 0x00001000808c0001`
   . `state[1] <- key[63:0]`
   . `state[2] <- key[127:64]`
   . `state[3] <- zeros(64)`
   . `state[4] <- zeros(64)`
   . `tag_len <- 128`

** In State _Ready_, a Form B `kl.setst Kn|K(Xn), \#kl_state_set_aux_value, Xs` sets
   `tag_len` {leftarrow} `Xs`. Admissible values satisfy 64 {le} `Xs` {le} 128; any other
   value causes the locker to transition to Error State _Invalid_
   (cite:[nist-SP-800-232] {sect}4.3 admits 32 to 63 bits only after a risk analysis, which KLEE does not provide for).
   Setting the tag length is an operation, not a State (<<KLEE-operation-immediates>>).

** [[KLEE-Ascon-AEAD128-nonce-setup]]To transition to State _Hash_Absorb_, a Form C ``kl.setst`` is expected, whose `INPUT` sets the nonce as follows:
+
--
  . `state[3] <- INPUT[63:0]`
    . `state[4] <- INPUT[127:64]`
    . `ASCON(12)`
    . `state[3] <- state[3] xor key[63:0]`
    . `state[4] <- state[4] xor key[127:64]`
--
+
`INPUT` is truncated to its 128 least significant bits (Rule <<KLEE-MGR-fixed-width-input>>).

** In State _Hash_Absorb_, only (multi-block) ``kl.exec`` instructions of Form B are expected.
“``kl.exec Kn|K(Xn), INPUT``” absorbs a data block into the state, i.e.:
+
--
 . `state[0] <- state[0] xor INPUT[63:0]`
 . `state[1] <- state[1] xor INPUT[127:64]`
 . `ASCON(8)`
--
+
If the associated data is empty, the caller must issue no ``kl.exec`` instruction in this state (hence, no permutation is applied).

** Upon entering State _Encrypt_ or _Decrypt_, by a Form A `kl.setst`, the following domain separation
   operation is performed:
 . `state[4] <- state[4] xor (1 << 63)`

** A same-State `kl.setst` into _Hash_Absorb_, _Encrypt_ or _Decrypt_ transitions the locker to Error State
   _Invalid_ (Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-same-state>>): repeating the operations performed on entering these States (the nonce
   setup and the domain separation) would create internal states that cite:[nist-SP-800-232] does not define.
   This applies to every variant of this Machine.

** In State _Encrypt_, (multi-block) ``kl.exec`` instructions are expected to be of Form A, whereby “``kl.exec OUTPUT, Kn|K(Xn), INPUT``” encrypts `INPUT` into `OUTPUT`, namely:
+
--
 . `state[0] <- state[0] xor INPUT[63:0]`
 . `state[1] <- state[1] xor INPUT[127:64]`
 . `OUTPUT <- state[1] @ state[0]`
 . `ASCON(8)`
--
** To transition to State _Enc_Last_Block_, a Form B ``kl.setst`` instruction must be issued, whose
auxiliary argument `Xs` is the bit length of the final block. `Xs` need not be a multiple of 8 (Rule <<KLEE-MGR-last-blk-len>>):
cite:[nist-SP-800-232] is written in little-endian bit order, so `pad` places the terminating `1` at bit position `Xs` for any `Xs`. It performs:
+
--
. If `Xs` > 127, then: the locker transitions to Error State _Invalid_.
. If `Xs` is zero, then:
.. `state[0] <- state[0] xor 1` (this is `pad(∅,128)` = `zeros(127) @ 1`)
..  The state machine then transitions to State _Hash_Output_.
. else:
.. `last_blk_len <- Xs`
--
+
If `last_blk_len` is non-zero, the instruction does _not_ cause a transition to State _Hash_Output_; instead, the state machine waits for a Form A `kl.exec`, as described next.

** State _Enc_Last_Block_ is entered only when `last_blk_len` is non-zero. In it,
exactly one `kl.exec` instruction of Form A is expected, to encrypt the last block.
It performs:
+
--
* `tmp : bits(b)`

[]
. `tmp <- pad(INPUT[last_blk_len-1:0], 128)`
. `state[0] <- state[0] xor tmp[63:0]`
. `state[1] <- state[1] xor tmp[127:64]`
. `tmp <- state[1] @ state[0]`
. `OUTPUT <- zeros(128-last_blk_len) @ tmp[last_blk_len-1:0]`
(Only the 128 lsbs of `OUTPUT` are written to.)
.  The state machine then transitions to State _Hash_Output_.
--
+
In State _Enc_Last_Block_ only one 128-bit block is processed.

** In State _Hash_Output_, only one ``kl.exec`` instruction of Form C is expected to be issued, to compute the tag.
“`kl.exec OUTPUT, Kn|K(Xn)`”  performs:
+
--
 . `state[2] <- state[2] xor key[63:0]`
 . `state[3] <- state[3] xor key[127:64]`
 . `ASCON(12)`
 . `state[3] <- state[3] xor key[63:0]`
 . `state[4] <- state[4] xor key[127:64]`
 . `OUTPUT <- zeros(128 - tag_len) @ (state[4] @ state[3])[tag_len-1:0]` (Only the 128 lsbs of `OUTPUT` are written to.)
 . The state machine then transitions to State _Success_.
--
+
In this state only one 128-bit block is processed.

** In State _Decrypt_, (multi-block) ``kl.exec`` instructions are expected to be of Form A, i.e.,
 `kl.exec OUTPUT, Kn|K(Xn),INPUT`. This operation performs:
+
--
* `tmp : bits(128)`

[]
. `tmp <- (state[1] xor INPUT[127:64]) @ (state[0] xor INPUT[63:0])`
. `state[0] <- INPUT[63:0]`
. `state[1] <- INPUT[127:64]`
. `ASCON(8)`
. `OUTPUT <- tmp`
--

** To transition to State _Dec_Last_Block_, a Form B ``kl.setst`` instruction must be issued, whose
auxiliary argument `Xs` is the bit length of the final block. `Xs` need not be a multiple of 8 (Rule <<KLEE-MGR-last-blk-len>>):
cite:[nist-SP-800-232] is written in little-endian bit order, so `pad` places the terminating `1` at bit position `Xs` for any `Xs`. It performs:
+
--
. If `Xs` > 127, then: the locker transitions to Error State _Invalid_.
//A partial final block of 127 bits is legal:
//  `Xs` is a truncation of an already-transferred block, not a transfer length, so
//  <<KLEE-truncation-vs-length>> applies and it need not be a multiple of 8. Ascon's
//  `pad` places the terminating `1` at bit position `Xs` for any `Xs`, because
//  cite:[nist-SP-800-232] is written in little-endian bit order.
. If `Xs` is zero, then:
.. `state[0] <- state[0] xor 1`
..  The state machine then transitions to State _Hash_Verify_.
. else:
.. `last_blk_len <- Xs`
--
+
If `last_blk_len` is non-zero, the instruction does _not_ cause a transition to State _Hash_Verify_; instead, the state machine waits for a Form A `kl.exec`, as described next.

** In State _Dec_Last_Block_, only one ``kl.exec`` instruction of Form A is expected to be issued, to decrypt the last block.
The `kl.exec` instruction performs:
+
--
* `S_r : bits(128)` – the rate part of the state
* `P : bits(128)`

[]
. `S_r <- state[1] @ state[0]`
. `P <- zeros(128-last_blk_len) @ (S_r[last_blk_len-1:0] xor INPUT[last_blk_len-1:0])`
. `OUTPUT <- P`
. `S_r <- S_r xor pad(P[last_blk_len-1:0], 128)`
. `state[0] <- S_r[63:0]`
. `state[1] <- S_r[127:64]`
. The state machine transitions to State _Hash_Verify_
--
+
In State _Dec_Last_Block_, only one 128-bit block is processed.

** In State _Hash_Verify_, which the decryption path enters by itself, the tag is verified by a same-State Form C
“``kl.setst Kn|K(Xn), #kl_state_hash_verify, INPUT``” (Rule <<KLEE-MGR-tag-verify>>), which performs
+
--
. `state[2] <- state[2] xor key[63:0]`
. `state[3] <- state[3] xor key[127:64]`
. `ASCON(12)`
. `state[3] <- state[3] xor key[63:0]`
. `state[4] <- state[4] xor key[127:64]`
. `INPUT[tag_len-1:0]` is compared to `(state[4] @ state[3])[tag_len-1:0]`.
. If the values match, the state transitions to _Success_;
  otherwise, it transitions to _Failure_.
--
+
`INPUT` is truncated to its 128 least significant bits (Rule <<KLEE-MGR-fixed-width-input>>). No `kl.exec` is allowed in State _Hash_Verify_.

Like GCM with Set IV, Ascon-AEAD128 has a variant with a set nonce.
The nonce is then not supplied on the transition into State _Hash_Absorb_, which
therefore uses a Form A ``kl.setst`` instead of the Form C of <<KLEE-Ascon-AEAD128>>, and the
PI has the following form.

+
--
[cols="^8%,<15%,<15%,<62%",options="header"]
|===
| Pos. | Size (Bits)   | Field    | Description

| iii  | 128           | `nonce`  | {empty}
|===
--

* *Internal State*: {empty}
+
--
Same as for Ascon-AEAD128, with in addition:

 ** `nonce`: 128 bits.

In State _Ready_, words 3 and 4 of `state` are initialized thus:

. `state[3] <- nonce[63:0]` and
. `state[4] <- nonce[127:64]`.
--

* *Serialized Content*: {empty}
+
--
Same as for Ascon-AEAD128, followed by:

[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)     | Field
|   ix | 128             | `nonce`
|===

`nonce` is serialized so that a return to State _Ready_ after an import can reload words 3 and 4 of `state`.
--

* *States and Allowed Transitions:* {empty}

--
Same as for Ascon-AEAD128.
--

* *State Machine Behavior:* {empty}
+
--
The difference with respect to Ascon-AEAD128 is

 ** To transition to State _Hash_Absorb_, the ``kl.setst`` instruction must be of Form A,

    skipped, and the transition performs only the remaining ones:
+
  . `ASCON(12)`
  . `state[3] <- state[3] xor key[63:0]`
  . `state[4] <- state[4] xor key[127:64]`
--

NOTE: This Machine protects the confidentiality of the nonce, not against its reuse (<<KLEE-nonce-reuse>>).

Everything else is as for Ascon-AEAD128.

[[KLEE-Ascon-Hash256]]
=== Ascon-Hash256

In this mode, the caller is responsible for padding the inputs.

Parameters:::

* `b` = 64.
* Granularity: `b`.

Data Structures:::

The *Provisioning Input* contains only the MDH.

* *Internal State*:
  ** `state[0 .. 4]`: five 64-bit words, i.e., 320 bits.
 ** A `countdown`, an integer going from 3 down to 0, is stored in bits [1:0] of _MachineUse_

* *Serialized Content*:
+
--
[%autowidth,cols="^1,<1,<3",options="header"]
|===
|  Pos. | Size (Bits)   | Field
|    i  | 64              | `state`[0]
|   ii  | 64              | `state`[1]
|  iii  | 64              | `state`[2]
|   iv  | 64              | `state`[3]
|    v  | 64              | `state`[4]
|===
--

Machine-Specific Functions:::

* `ASCON(p)` applies `p` rounds of ASCON to the `state`.

State Machine:::

* *States:* _Ready_, _Hash_Absorb_, _Hash_Finalize_, and _Success_.

* *Allowed State Transitions:*
 ** _Ready_ -> _Hash_Absorb_ -> _Hash_Finalize_ -> _Success_.

* *Behavior:*
 ** In State _Ready_ :
  *** The following initialization operations are performed:
   . `state[0] <- 0x0000080100cc0002`
   . `state[1] <- zeros(64)`
   . `state[2] <- zeros(64)`
   . `state[3] <- zeros(64)`
   . `state[4] <- zeros(64)`
   . `ASCON(12)`

  ** In State _Hash_Absorb_, only (multi-block) ``kl.exec`` instructions of Form B are expected to be issued.
 “``kl.exec Kn|K(Xn), INPUT``” absorbs a data block into the state, i.e.:
+
--
 . `state[0] <- state[0] xor INPUT`
 . `ASCON(12)`
--
** The `kl.setst` into _Hash_Absorb_ and into _Hash_Finalize_ is of Form A. Upon entering _Hash_Finalize_, `countdown` is set to 3.
   A same-State `kl.setst` into _Hash_Finalize_ is not allowed (Rule <<KLEE-MGR-no-hash-output-repeat>>).

** In State _Hash_Finalize_, at most four ``kl.exec`` instructions of Form C
   are expected to be issued. To compute the tag, “``kl.exec OUTPUT, Kn|K(Xn)``” performs
+
--
. If `countdown` != 3, then:
.. `ASCON(12)`
. `OUTPUT[63:0] <- state[0]`
. If `countdown` = 0 then:
.. Transition to State _Success_.
. else:
.. `countdown <- countdown - 1`
--
+
If `KLLEN` {ge} `128`, these operations are executed `KLLEN/64` times, writing to `OUTPUT`[63:0] the first time, then to `OUTPUT`[127:64], `OUTPUT`[191:128], and `OUTPUT`[255:192]. If more than one ``kl.exec`` instruction is required, writing restarts from `OUTPUT`[63:0].
If `countdown` reaches zero before the entire output register is written, the unwritten bits are cleared: this may occur, for instance, if `KLLEN` = `192` or `KLLEN` = `256`.
This is rarely a problem, since output vectors are usually configured for 64-bit, 128-bit or 256-bit blocks, which need four, two or one ``kl.exec`` instructions, respectively.

//

NOTE: There is no need to provide keyed versions of this algorithm.
A trusted entity can achieve the same effect by providing a CC after first absorbing some secret content into it, and the same CC can be reused for multiple invocations by keeping a copy of the original SCC.

[[KLEE-Ascon-XOF128]]
=== Ascon-XOF128

The Machine is the same as Ascon-Hash256 (<<KLEE-Ascon-Hash256>>) with the following differences:

. The IV written to `state[0]` in State _Ready_ is `0x0000080000cc0003`.
. The `countdown` is used in a different way:

** Upon entering _Hash_Finalize_, `countdown` is set to 1.

** In State _Hash_Finalize_, each Form C “``kl.exec OUTPUT, Kn|K(Xn)``” performs, for
   `i` = 0, 1, {ellipsis}, `KLLEN`/64 − 1:
+
--
. If `countdown` = 0, then `ASCON(12)`.
. `OUTPUT[64i+63 : 64i] <- state[0]`.
. `countdown <- 0`.
--
+
`ASCON(12)` is thus applied before every output word except the first, as in
cite:[nist-SP-800-232] Algorithm 6.

. As much output as desired can be produced in State _Hash_Finalize_, and the Machine never transitions to State _Success_.

[[KLEE-Ascon-CXOF128]]
=== Ascon-CXOF128

Ascon-CXOF128 differs from Ascon-XOF128 in two ways:
the IV is `0x0000080000cc0004`, and the message is prepended with the customization string `Z`. The states and their semantics are otherwise identical to Ascon-XOF128. The caller absorbs in _Hash_Absorb_, before the message, the block `bin(len_in_bits(Z), 64)` followed by `Z` padded as the message is, i.e. `Z~0~` {ellipsis} `Z~m~` of cite:[nist-SP-800-232] {sect}5.3, and ensures that `len_in_bits(Z)` {le} 2048, which the Machine does not check.

[[KLEE-ECC]]
== Elliptic Curve Cryptography

The Elliptic Curve Machines provide:

. Scalar multiplication with known and unknown base point.
//This can be used to implement Diffie-Hellman key exchange.
. ECDSA/EdDSA signature generation and verification.

The x25519 and x448 Machines (<<KLEE-X25519-X448>>) provide only the former.

[NOTE]
====
Due to the wide variety of KDFs, hash functions, and formats, general KEM and PKE support is impractical.
Among all elliptic curve standards, only the Chinese SM2 standards fully specify an integrated encryption scheme cite:[GMT-0003-4-2012].
Their implementation is left to user code via scalar multiplication.
Any resulting key exposed in environment memory should be immediately used to provision a locker and then erased.
====

Provisioning an elliptic curve into a locker sets the `Generator` field to the default base point (“generator”) that the standards listed below define for the curve.
The field may be overwritten, and a `kl.setst` to _Ready_ may restore the default base point.

All values (integers, coordinates, etc.) are in little-endian format.

Parameters:::
+
--
The parameters used in this section are:

 . The bit length `b` of the main fields, such as coordinates, signature R and S fields, scalars;
 . The bit length `h` of the hash used in the signature scheme. For the ECDSA curves, the
   value placed in the `Hash` field is the message digest already reduced as prescribed by
   cite:[nist-fips-186-5] {sect}6.4, that is, its leftmost `min(N, outlen)` bits, where `N`
   is the bit length of the group order and `outlen` that of the digest. Performing that
   reduction is the caller's responsibility, as is choosing an approved hash function.
   For SM2 the value placed in `Hash` is `e` = `SM3(Z~A~ {vvert} M)` of
   cite:[GMT-0003-2-2012], where `Z~A~` = `SM3(ENTL~A~ {vvert} ID~A~ {vvert} a {vvert} b {vvert} x~G~ {vvert} y~G~
   {vvert} x~A~ {vvert} y~A~)`. Both are computed by the caller, which is possible because every
   input to `Z~A~` is public; the KLEE unit computes neither.
   For the Edwards curves the field is used differently, and only in pre-hash mode; see
   <<KLEE-EdDSA>>;
 . The bit length `j` of the random number used as nonce in signature generation;
 . The number `u` of coordinates used to represent a point (`u` can be 1 or 2); and
 . The number `v` of elements used to represent a signature (`v` can be 0, 1 or 2, where `v` = 0
   denotes a curve for which no signature scheme is provided).

The parameters for the defined curves are:

* NIST curves cite:[NIST-SP-800-186,nist-fips-186-5]:
  ** secp256r1 (NIST P-256): `b` = `h` = `j` = 256, `u` = `v` = 2.
  ** secp384r1 (NIST P-384): `b` = `h` = `j` = 384, `u` = `v` = 2.
  ** secp521r1 (NIST P-521): `b` = 576 (55 msbs set to zero), `h` = `j` = 576 (55 msbs set to zero), `u` = `v` = 2.
* Edwards curves for signatures cite:[RFC8032,nist-fips-186-5]:
  ** ed25519:  `b` = 256, `h` = 512; `u` = 1, `v` = 2.
  ** ed448: `b` = 456, `h` = 512; `u` = 1, `v` = 2.
* Montgomery forms of Edwards Curves for key-exchange only cite:[RFC7748]:
  ** x25519 (curve25519): `b` = 256; `u` = 1, `v` = 0.
  ** x448 (curve448): `b` = 448; `u` = 1, `v` = 0.
* Brainpool cite:[RFC5639,RFC8734]:
  ** brainpoolP256r1: `b` = `h` = `j` = 256; `u` = `v` = 2.
  ** brainpoolP384r1: `b` = `h` = `j` = 384; `u` = `v` = 2.
  ** brainpoolP512r1: `b` = `h` = `j` = 512; `u` = `v` = 2.
* SM2 cite:[GMT-0003-1-2012,GMT-0003-2-2012,GMT-0003-3-2012,GMT-0003-4-2012]: `b` = `h` = `j` = 256; `u` = `v` = 2.

Depending on the specification of the algorithm, non-compressed or compressed points may be used:
for the Edwards curves, `u` = 1 because a point is transmitted in the compressed form of
cite:[RFC8032] {sect}5, a single `b`-bit string, and `v` = 2 because a signature is the pair
(`R`, `S`), each a `b`-bit string: an Ed25519 signature is 512 bits and an Ed448
signature 912 bits. Note that `b` = 456 for ed448, the compressed point and each
signature component being 57 bytes rather than 56. `h` = 512 for both because the `Hash`
field, in pre-hash mode, holds the 64-byte `PH(M)`; no value of `j` is given because
these curves do not use `RndNum` (<<KLEE-EdDSA>>).

For the Montgomery curves, `u` = 1 because a point is represented by its _u_-coordinate alone
(cite:[RFC7748] {sect}5), a single `b`-bit string, and `v` = 0 because the x25519 and x448 Machines provide key
exchange only; for the same reason no value of `h` or `j` is given (<<KLEE-X25519-X448>>).
Although related to the Edwards curves, they are listed separately: the point representation differs, as does
`b` for x448 and ed448.

All curves specified here are defined over prime fields.
For secp521r1 the 55 most significant bits of each coordinate of `Generator` and `SecondPt`, of `Scalar`,
of each component of `Signature`, of `Hash`, and of `RndNum` must be zero. A write of one of these fields with any of those bits set causes the locker to
transition to Error State _Invalid_ (Rule <<KLEE-MGR-check-on-write>>). The check is repeated when _Point_Mul_, _Sign_Generate_ or _Sign_Verify_
uses a value, and a violation then also causes the locker to transition to Error State _Invalid_ (Rule <<KLEE-MGR-check-on-read>>):
a value can reach the locker without a check, for instance as a resumed `RndNum`, and this check is one of the ways a
corruption of the locker file is detected.

A point is _valid_ if it is a point of the curve other than the point at infinity and, where the cofactor is not 1, of the
prime-order subgroup; for the Edwards curves, its encoding must also decode as cite:[RFC8032] {sect}5.1.3, resp. {sect}5.2.3,
prescribes. Whenever _Point_Mul_, _Sign_Generate_ or _Sign_Verify_ uses `Generator` (for the Edwards curves, only _Point_Mul_ does, <<KLEE-EdDSA>>) or `SecondPt` and the point is not
valid, the state transitions to _Failure_: this is a data error (Rule <<KLEE-MGR-config-data-error>>), not a configuration error, whether the
point is a peer's point, a public key or a generator. The check is made when the point is read (Rule <<KLEE-MGR-check-on-read>>).
For the Montgomery curves no such check is made: the check of <<KLEE-X25519-X448>> replaces it.

State Machine::: {empty}
+
--
* *States:*
Besides
_Ready_ (1),
_Success_ (46),
_Failure_ (47),
ECC Machines define:
 ** _Set_Generator_ (2)
 ** _Set_Scalar_ (3)
 ** _Point_Mul_ (4)
 ** _Sign_Generate_ (5)
 ** _Sign_Verify_ (6)
 ** _Set_Hash_ (7)
 ** _Set_SecondPt_ (8)
 ** _Set_Signature_ (9)
 ** _Output_ (10)
--

* *Allowed State Transitions:*
+
--
The five states _Set_Generator_, _Set_Scalar_, _Set_Hash_, _Set_SecondPt_, and
_Set_Signature_ are collectively termed the _Set_ states.

 ** _Ready_ -> any _Set_ state. Entering _Set_Hash_ or _Set_Signature_ requires _MachinePolicy_ {ne} 0 (Rule <<KLEE-MGR-policy-gate>>):
    the fields `Hash` and `Signature` exist only if signature generation or verification is allowed.
 ** One can freely transition between any two _Set_ states, and from a _Set_ state to
    itself. Re-entering a _Set_ state erases the field it sets and clears the
    corresponding ``Has``__Var__ flag, so a value may be replaced by loading it again.
 ** From _Ready_ or from any _Set_ state -> one of the following, whose conditions are entry conditions (Rule <<KLEE-MGR-policy-gate>>):
  *** _Point_Mul_;
  *** _Sign_Generate_ only if `HasHash` holds *and* `Scalar` holds a
      configured private key, that is `1` {le} `int(Scalar)` `<` `n`, where `n` is the order
      of the group. A freshly provisioned CC has `Scalar` = 0 and so does not qualify.
    (For the EdDSA curves, <<KLEE-EdDSA>>, the behavior is different.)
  *** _Sign_Verify_ only if `HasSecondPt`, `HasHash`, and `HasSignature`.
 ** _Point_Mul_ -> _Output_ -> _Success_.
 ** _Sign_Generate_ -> _Output_ -> _Success_.
 ** _Point_Mul_, _Sign_Generate_ -> _Failure_, when a point that the operation uses is not valid (Rule <<KLEE-MGR-config-data-error>>).
 ** _Sign_Verify_ -> _Success_ or _Failure_.

[none]
* State _Set_Generator_ sets a group generator, or the default one.
* State _Set_Scalar_ sets a scalar for scalar multiplication, or a private key.
* For each __Var__ {in} {`SecondPt`, `Signature`, `Hash`},
the Boolean variable ``Has``__Var__ follows the pattern of Rule <<KLEE-MGR-load-long-field>>, and is held in the _StateExtension_ field as
given in <<KLEE-ECC-StateExtension>>. `HasRndNum`, also held there, is set only while a signature operation holds
`RndNum`, as stated below (Rule <<KLEE-MGR-progress-discard>>): `RndNum` is drawn, never loaded. There is no such flag for `Generator` or for `Scalar`:
`Generator` holds the curve's default value from provisioning onwards, until it is replaced, and `Scalar`
is zero until set, which is not a legal private key and therefore needs no flag. A load of either that is left
incomplete zeroes the field (Rule <<KLEE-MGR-load-long-field>>): a zero `Generator` is not a valid point, and a zero `Scalar` not a
configured private key.
--

* *Behavior:*

 ** Provisioning sets `Generator` to the default of the curve, and `Scalar` to zero.

 ** All the “set” and “output” operations follow Rule <<KLEE-MGR-load-long-field>> of
<<KLEE-Machine-rules>>, with the progress recorded in `block_base`, in bytes.

 ** To transition to State _Set_Generator_, a Form A or B `kl.setst` is used.

 *** If no parameter is given, or the value of the GPR used in the Form B `kl.setst` is zero:
  . The default generator of the curve is set.
  . A state change operation can be issued, including to states that require a set `Generator`.

 *** Otherwise:
  . `Generator`, of length `ub`/8 bytes, is loaded using (multi-block) `kl.exec` instructions of Form B, following Rule <<KLEE-MGR-load-long-field>>.
  . Once it is complete, a state change operation can be issued, including to states that require a set `Generator`.

 ** To transition to any of the States _Set_Scalar_, _Set_Hash_, _Set_SecondPt_, or _Set_Signature_ a Form A `kl.setst` is used.
  *** If there is a current value in the corresponding field _X_ = `Scalar`, `Hash`, `SecondPt`, or
      `Signature`, it is erased, and, for the three fields that have one, the Boolean ``Has``_X_ is
      set to False. `Scalar` has no such flag: it is simply set to zero, which is not a legal
      private key.
  *** Field _X_ is then loaded using (multi-block) `kl.exec` instructions of Form B, following
      Rule <<KLEE-MGR-load-long-field>>, and ``Has``_X_ is set once the field is complete, where that flag exists.

 ** It is also allowed to transition to _Set_Scalar_ using a Form B `kl.setst` with a non-zero value in the GPR.
    In this case, a random value is set (Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-rbg-failure>> applies if the RBG fails), no further
    `kl.exec` is issued, and the generated value is never disclosed: it leaves
    the locker only as part of an SCC.

 ** *Random numbers and retry rules.*
  *** For signature generation the KLEE unit uses a random number.
    `HasRndNum` is set while it is in use. The random number is never supplied by
    software, and never leaves the locker except, when a signature operation is interrupted, in the
    encrypted part of an SCC.
  *** For the ECDSA curves—the NIST and Brainpool parameter sets of this section—the signature is recomputed with a fresh secret whenever a degenerate value arises. cite:[nist-fips-186-5] {sect}6.4.1 requires a retry whenever `r` = 0 or `s` = 0.

  *** For SM2 the corresponding conditions of cite:[GMT-0003-2-2012] apply instead, namely a retry
if `r` = 0, if `r` + `k` = `n`, or if `s` = 0.

  *** The Edwards curves do not use a random secret and thus do not have retry rules.

 ** In State _Point_Mul_, a single Form D ``kl.exec Kn|K(Xn)`` performs a scalar
    multiplication:

  . If `Scalar` does not satisfy `1` {le} `int(Scalar)` < `n` (Rule <<KLEE-MGR-check-on-read>>), the locker
    transitions to Error State _Invalid_.
  . The base point `P` is `SecondPt` if `HasSecondPt` is set (multiplication by an
    unknown point, e.g., a Diffie-Hellman peer value), and `Generator` otherwise
    (multiplication of the known base, e.g., public-key generation).
  . The implementation must verify that `P` is a valid point (as defined above); if not, the state
    transitions to _Failure_.
  . `SecondPt` {leftarrow} `int(Scalar)` {interpunct} `P`, encoded as in <<KLEE-ECC>>, and
    `HasSecondPt` is set.
  . `OutputType` {leftarrow} False, and the state transitions to _Output_.

 ** In State _Sign_Generate_, a single Form D ``kl.exec Kn|K(Xn)`` generates a
    signature over the base point `Generator`, with private key `d` = `int(Scalar)`
    and message value `e` = `int(Hash)`:

  . If `Generator` is not a valid point, the state transitions to _Failure_.
  . For the NIST and Brainpool curves, the signature (`r`, `s`) is computed as
    specified in cite:[nist-fips-186-5] {sect}6.4.1; for SM2, as specified in
    cite:[GMT-0003-2-2012]. If `Progress` is zero, the per-signature secret `k` is drawn from the RBG
    (<<Zkl-ISA-unpriv.adoc#KLEE-Prerequisites>>, Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-rbg-failure>>) into `RndNum`, with `HasRndNum` set for the duration of the
    operation; otherwise the interrupted operation is resumed with the `RndNum` held (Rule <<KLEE-MGR-progress-discard>>). The retry rules above apply.
  . On completion, `Signature` {leftarrow} (`r`, `s`) and `HasSignature` is set;
    `RndNum` is destroyed and `HasRndNum` cleared.
  . `OutputType` {leftarrow} True, and the state transitions to _Output_.

 ** In State _Sign_Verify_, a single Form D ``kl.exec Kn|K(Xn)`` verifies
    `Signature` against the public key held in `SecondPt` and the message value
    `e` = `int(Hash)`, as specified in cite:[nist-fips-186-5] {sect}6.4.2 for the
    NIST and Brainpool curves and in cite:[GMT-0003-2-2012] for SM2. All checks
    those specifications require — the ranges of `r` and `s`, and the validity of
    the public key, and of `Generator`, as points — are performed; if any fails, or the signature
    equation does not hold, the state transitions to _Failure_, else to _Success_.

 ** When the operations in states _Point_Mul_ and _Sign_Generate_ are completed, the state transitions to _Output_ and:
   . If the output is a point, then `OutputType` <- False, and if the output is a signature, then `OutputType` <- True.
     This allows the KLEE implementation to determine not only which output must be written out, but also its length.
     *** If `OutputType` = False, the output is in `SecondPt`.
     *** If `OutputType` = True, the output is in `Signature`.
   . In State _Output_, the result is emitted using (multi-block) `kl.exec` instructions of Form C, respecting Rule <<KLEE-MGR-load-long-field>>.
     . Once the output is complete the state transitions to _Success_ (Rule <<KLEE-MGR-load-long-field>>).

 ** Upon returning to State _Ready_:
  *** If a Form B `kl.setst` is used, the parameter `Xs` determines which of the fields
 `Generator`, `Scalar`, `SecondPt`, `Hash`, and `Signature` are reset, erased, or kept for
 further operations. This is determined by Bits 0 to 6 of `Xs`; Bits 7 and above are reserved, and a non-zero value in them
 transitions the locker to Error State _Invalid_. First the copies are made, both from the values held
 before the instruction, so that with Bits 4 and 5 both set the two points are exchanged:
   **** If Bit 4 is set, then `Generator` is copied onto `SecondPt`, and `HasSecondPt` is set.
   **** If Bit 5 is set and `HasSecondPt` was set, then `SecondPt` is copied onto `Generator`; with `HasSecondPt` clear, Bit 5 has no effect.
  *** Then the fields are reset or erased:
   **** If Bit 0 is set, then `Generator` is reset to the default value.
   **** If Bit 1 is set, then `SecondPt` is erased and `HasSecondPt` is cleared.
   **** If Bit 2 is set, then `Scalar` is erased.
   **** If Bit 3 is set, then `Hash` is erased and `HasHash` is cleared.
   **** If Bit 6 is set, then `Signature` is erased and `HasSignature` is cleared.
  *** Every field whose bit is clear is retained. A Form A `kl.setst` sets no bit and
      therefore leaves `Generator`, `Scalar`, `SecondPt`, `Hash`, and `Signature`
      unmodified.

** {empty}
+
--
`Progress`, bits [13:1] of _MachineUse_, is the field used following rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-long-running-no-data>> for Point Multiplication,
Signature Generation and Signature Verification; what an implementation exports to allow resumption
typically includes precomputed multiples of the base point.
Rule <<KLEE-MGR-progress-discard>> applies: any state transition out of these States zeroes `Progress`, destroys `RndNum` and clears `HasRndNum`, and the operation restarts.

An importing implementation that keeps the Auxiliary Data Section must also be willing to trust the
random number generator of the originating implementation. If it is not, it discards that Section
together with `RndNum` (Position vii, if present) and restarts the operation.

[[KLEE-X25519-X448]]
=== X25519- and X448-Specific Rules

{empty}
(((KLEE, Machine, X25519)))
(((KLEE, Machine, X448)))
The x25519 and x448 Machines implement the functions `X25519` and `X448` of cite:[RFC7748] {sect}5, and with them
the Diffie-Hellman key exchange of cite:[RFC7748] {sect}6. Of the operations of <<KLEE-ECC>> they provide only
scalar multiplication. They differ from the other curves in three respects: a point is a single coordinate,
the scalar is an arbitrary `b`-bit string, and no input point is rejected. This subsection states the
consequences; everything not restated here follows <<KLEE-ECC>>.

Parameters:::

* The curves are the Montgomery curves `v^2^` = `u^3^` + `A` {interpunct} `u^2^` + `u` of cite:[RFC7748] {sect}4:
  curve25519 for x25519, with `p` = 2^255^ - 19 and `A` = 486662, and curve448 for x448, with
  `p` = 2^448^ - 2^224^ - 1 and `A` = 156326.
  curve25519 is birationally equivalent to the Edwards curve of ed25519; curve448 is related to that of ed448
  by an isogeny of degree 4. The Machines are nevertheless distinct, and points and private keys are not
  interchangeable between them.
* A point is represented in compressed form, by its _u_-coordinate alone: `u` = 1. This is the X coordinate
  of `Generator` and `SecondPt` in <<KLEE-ECC>>, and is not to be confused with the parameter `u`.
  A public key and a shared secret are thus 32 bytes for x25519 and 56 bytes for x448.
* There is no signature scheme: `v` = 0, and `h` and `j` are not defined.
* `X25519(k, u)` and `X448(k, u)` map a scalar and a _u_-coordinate, both `b`-bit strings, to a `b`-bit
  string, decoding their inputs as cite:[RFC7748] {sect}5 prescribes:
 ** the scalar is _clamped_: for x25519, bits 0, 1, 2 and 255 are cleared and bit 254 is set; for x448,
    bits 0 and 1 are cleared and bit 447 is set;
 ** for x25519, bit 255 of the _u_-coordinate is ignored; and
 ** a _u_-coordinate not smaller than `p` is reduced modulo `p`.
* The private key is the unclamped `b`-bit string held in `Scalar`, which holds a
  *configured private key* when it is non-zero. It is not compared with the order of the group.

Data Structures:::
+
--
Those of <<KLEE-ECC>>, with the following changes:

* *MDH*:
 ** _MachinePolicy_ must be zero; a non-zero value is unsupported Metadata
    (<<Zkl-ISA-unpriv.adoc#KLEE-Metadata-validity>>).
 ** Of the _StateExtension_ bits (<<KLEE-ECC-StateExtension>>) only `HasSecondPt` is used: a PCCC or SCC
    with any of the bits 1 to 3 set is invalid Metadata (<<Zkl-ISA-unpriv.adoc#KLEE-Metadata-validity>>).
 ** `OutputType` (<<KLEE-ECC-MachineUse>>) is always False, the only output being a point.

* *Internal State*: `Generator` and `SecondPt` are each a single `b`-bit string, a _u_-coordinate.
  `SecondPt` holds the peer's public key and, after a scalar multiplication, the public key of the locker
  or the shared secret.
  `Signature`, `Hash` and `RndNum` do not exist.

* *Serialized Content*: Positions i to iv of <<KLEE-ECC>>, with `u` = 1; Positions v to vii are always empty.
  Hence
+
`{fournbsp}{fournbsp}` `varlen` <- (`HasSecondPt` != 0) {interpunct} ``b``/8.
--

State Machine:::

* *States:* besides _Ready_ (1), _Success_ (46) and _Failure_ (47), only the following States of <<KLEE-ECC>>:
 ** _Set_Generator_ (2)
 ** _Set_Scalar_ (3)
 ** _Point_Mul_ (4)
 ** _Set_SecondPt_ (8)
 ** _Output_ (10)

+
_Sign_Generate_, _Sign_Verify_, _Set_Hash_ and _Set_Signature_ are not defined: a `kl.setst` that names one of them
transitions the locker to Error State _Invalid_ (Rule <<KLEE-MGR-not-allowed-instructions>>).

* *Allowed State Transitions:* those of <<KLEE-ECC>> between the States above, the _Set_ states being
  _Set_Generator_, _Set_Scalar_ and _Set_SecondPt_:
 ** _Ready_ -> any _Set_ state; between any two _Set_ states, and from a _Set_ state to itself.
 ** From _Ready_ or from any _Set_ state -> _Point_Mul_.
 ** _Point_Mul_ -> _Output_ -> _Success_.
 ** _Point_Mul_ -> _Failure_, when the result is the all-zero string (Rule <<KLEE-MGR-config-data-error>>).

* *Behavior:*

** Provisioning sets `Generator` to the base point of cite:[RFC7748] {sect}4.1, resp. {sect}4.2, that is to the
   _u_-coordinate 9 for x25519 and 5 for x448, and `Scalar` to zero.

** `Generator`, `SecondPt` and `Scalar` accept every `b`-bit string: no check is made when they are written
   (Rule <<KLEE-MGR-check-on-write>>).

** A Form B `kl.setst` to _Set_Scalar_ with a non-zero value in the GPR sets `Scalar` to `b` random bits,
   as cite:[RFC7748] {sect}6 generates a private key.

** In State _Point_Mul_, a single Form D ``kl.exec Kn|K(Xn)`` performs a scalar
   multiplication, in the following steps, which replace those of <<KLEE-ECC>>:

  . If `Scalar` does not hold a configured private key (Rule <<KLEE-MGR-check-on-read>>), the locker
    transitions to Error State _Invalid_.
  . The base point `P` is `SecondPt` if `HasSecondPt` is set (the peer's public key), and `Generator` otherwise
    (public-key generation). `P` is not checked for validity: the function is defined for every `b`-bit string
    (therefore, also _u_-coordinates of points on the quadratic twist).
  . `R` {leftarrow} `X25519(Scalar, P)`, resp. `X448(Scalar, P)`.
  . If `R` is the all-zero string, as it is for every `P` of small order, the state transitions to _Failure_,
    and `SecondPt` and `HasSecondPt` are left unchanged. This check, optional in cite:[RFC7748] {sect}6, is
    mandatory here, and is made in constant time.
  . Otherwise `SecondPt` {leftarrow} `R`, `HasSecondPt` is set, `OutputType` {leftarrow} False, and the state
    transitions to _Output_.

** A key exchange consists of two scalar multiplications with the same `Scalar`. The first, with
   `HasSecondPt` clear and the default `Generator`, yields the public key, which is output and sent
   to the peer. The second, after the peer's public key has been loaded in State _Set_SecondPt_, yields the
   shared secret `K`.
+
[NOTE]
====
cite:[RFC7748] {sect}6 uses `K` not as a key, but as the input of a key derivation function,
together with the two public keys. Since `SecondPt` is a source endpoint of `kl.derive` (<<KLEE-derive-endpoints>>,
Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-shared-secret>>), `K` can reach another locker without being exposed in
environment memory.
====

** Upon returning to State _Ready_ with a Form B `kl.setst`, Bits 3 and 6 of `Xs` have no effect, since `Hash`
   and `Signature` do not exist.

** Rule <<KLEE-MGR-progress-discard>> applies to _Point_Mul_, with no `RndNum` to destroy.

[[KLEE-EdDSA]]
=== EdDSA-Specific Rules

{empty}
(((KLEE, Machine, EdDSA)))
EdDSA, standardized in cite:[RFC8032] and cite:[nist-fips-186-5], does not fit the
division of labour used by the other curves of <<KLEE-ECC>>, under which the caller hashes
the message and the KLEE unit performs only the group arithmetic. Both of its hash
invocations take material the caller does not hold:

`{fournbsp}{fournbsp}` `r{nbsp}`  = `H(dom {vvert} prefix {vvert} M)`, where `prefix` is secret, and +
`{fournbsp}{fournbsp}` `k'` = `H(dom {vvert} R {vvert} A {vvert} M)`, where `R` = `r` {interpunct} `B` is computed inside.

The Machine therefore needs to perform the hashing itself. This subsection states the
consequences; everything not restated here follows <<KLEE-ECC>>.

Parameters:::

* `H` is `SHA-512` for ed25519 and `SHAKE256`, with a 114-byte output, for ed448.
* The private key, or *seed*, is the `b`-bit string held in `Scalar`; `Scalar` holds a
  *configured seed* when it is non-zero.
* `dom` is `dom2(x, ctx)` for ed25519 and `dom4(x, ctx)` for ed448, as defined in
  cite:[RFC8032] {sect}2 and {sect}5.2, with `x` = 0 in pure mode and 1 in pre-hash mode.
  For ed25519 in pure mode with an empty context, `dom` is the empty string.

Pure and pre-hash modes:::
+
--
In *pure* mode the unit hashes the message itself; in *pre-hash* mode the caller supplies
`PH(M)`, 64 bytes for both curves, in the `Hash` field. Which modes an implementation
offers depends on the hash extensions it provides:

[%autowidth,float="center",align="center",cols="<,<,<",options="header"]
|===
| Curve extension | Also implements | Modes available
| `Zkled25519c` | --           | Ed25519ph only
| `Zkled25519c` | `Zklesha2h`  | Ed25519 and Ed25519ph
| `Zkled448c`   | --           | Ed448ph only
| `Zkled448c`   | `Zklesha3h`  | Ed448 and Ed448ph
|===

The curve extension alone must provide enough of `H` to hash the fixed-size inputs above,
which are a few hundred bytes at most. Absorbing a message of arbitrary length is what
requires the general hashing machinery, and hence `Zklesha2h` or `Zklesha3h`, respectively.

The _AuxInfo_ field of the MDH (<<Zkl-ISA-unpriv.adoc#KLEE-MachineUse>>) is used as follows:
bit 0 records the modes a CC may use, only pre-hash mode with bit 0 = 0, and pure mode as well with bit 0 = 1;
bits [2:1] hold `msg_pass` (see the State Machine below); and bits [15:3] are reserved.
At provisioning and at import, bit 0 = 1 on an implementation that does not offer pure mode for the curve,
or a non-zero reserved bit, is unsupported Metadata, and raises a KLEE unsupported-Metadata exception (<<Zkl-ISA-unpriv.adoc#KLEE-Metadata-validity>>).
This allows an M-mode handler to emulate pure mode where the hardware does not offer it
(<<Zkl-ISA-unpriv.adoc#KLEE-error-architecture>>); a handler that cannot resolve the exception, including for a reserved value,
transitions the locker to Error State _Unsupported_.
Bit 0 of _AuxInfo_ is not changed by provisioning or by a transition to _Ready_; bits [2:1] of a PI are ignored and zeroed upon
provisioning, and bits [2:1] are zeroed upon entering State _Ready_.
--

Data Structures:::
+
--
In addition to the fields of <<KLEE-ECC>>:

* `ctx`: 255 bytes, and `ctxlen`: 8 bits, the context string of cite:[RFC8032]. It is
  optional for ed25519 and mandatory, though possibly empty, for ed448. Both are zero
  upon provisioning and upon entering State _Ready_, and are set in State _Set_Ctx_.
* `msg_pass`: 2 bits, held in bits [2:1] of _AuxInfo_. In State _Msg_Absorb_ it identifies the open pass: 0 for signing
  pass 1, 1 for signing pass 2, and 3 for the verification pass. In any other State it records the last completed pass:
  0 for none, 1 for signing pass 1, 2 for signing pass 2, and 3 for the verification pass.
* `k'`: `b` bits, the value `H(dom {vvert} R {vvert} A {vvert} M) mod L` computed by signing pass 2 or by the verification pass,
  and zero otherwise. It is not secret: anyone holding `R`, `A` and `M` can compute it.
* `r`: `b` bits, the secret scalar produced by the first signing pass, reduced modulo the
  group order `L`. Like `RndNum` for the ECDSA curves, it never leaves the locker except in
  the encrypted part of an SCC while a signing operation is in progress. It also binds the two
  signing passes: pass 2 recomputes it from its own message and requires the value to match
  (see the State Machine).

There is no stored pre-hash mode selector: the mode is inferred from the path taken, as
described below.

`RndNum` is *not* used: the EdDSA nonce is deterministic by construction, being derived from `prefix` and the message.
Its absence is deliberate; `j` = 0, so Position vii of <<KLEE-ECC>> is always empty.
Bit 3 of _StateExtension_, `HasRndNum` in the other ECC Machines, is instead `HasHashState` (<<KLEE-ECC-StateExtension>>):
it is set on entering State _Msg_Absorb_ and cleared when the open pass is finalized, so that it is set exactly while a pass
is open, including across the same-State re-entry that ends one pass and opens the next.
A _State_ {vvert} _StateExtension_ with `HasHashState` set in a State other than _Msg_Absorb_, or clear in _Msg_Absorb_, is not
supported by the Machine: a PCCC or SCC that carries it is invalid Metadata (<<Zkl-ISA-unpriv.adoc#KLEE-Metadata-validity>>). It does not follow the pattern of
Rule <<KLEE-MGR-load-long-field>>, since it records no loaded field.

The clamped scalar `s` and the 32-byte or 57-byte `prefix`, respectively, are derived from the seed
by hashing it with `H`, as cite:[RFC8032] {sect}5.1.5 and {sect}5.2.5 prescribe. An
implementation may recompute them on each use or cache them in the ADS.
The public key `A` is likewise derived from the seed, or cached in the ADS.

* *Serialized Content*: the serialized content of <<KLEE-ECC>>, with the following fields
  appended.
+
[%autowidth,cols="^1,<3,<5",options="header"]
|===
|  Pos. | Size (Bits)  | Field
| viii  | 8            | `ctxlen`
|   ix  | 2040         | `ctx`
|    x  | `b`          | `r`
|   xi  | `b`          | `k'`
|  xii  | If `HasHashState`: `hs`, else: 0 | The state of `H`
| xiii  | If `HasHashState`: `hs`, else: 0 | The state of `H'`, zero except in signing pass 2
|===

`hs` is the length of the Serialized Content of the hash Machine of `H` as it is serialized under HMAC
(<<KLEE-HMAC>>), that is with `cumul_len` and without a key or MDH: for ed25519 that of SHA-512 (<<KLEE-SHA-2>>), 1664 bits,
and for ed448 that of SHAKE256 (<<KLEE-SHA-3>>), 1792 bits with its padding to a multiple of 128 bits. Both states are present
whenever `HasHashState` is set, so that the length of `Content1` depends only on _StateExtension_
(<<Zkl-ISA-unpriv.adoc#KLEE-length-rule>>).

`r` and `k'` are present unconditionally, and hold zero whenever no signing operation, resp. no signing or verification
operation, is in progress. Making their presence conditional on `msg_pass` would only increase the complexity of the Machine.

The state of an open pass is thus architected: `msg_pass` identifies the pass, and `Content1` carries `r`, `k'` and the
hash states. An export and import, also to a different implementation, resumes the pass where it stopped.
`r` is `b` bits (256 for ed25519 and 456 for ed448) which is a small addition to an SCC
of this size, and it remains confidential in either case, being carried in the encrypted `Content`.
--

State Machine:::

* *States:* those of <<KLEE-ECC>>, and in addition
 ** _Msg_Absorb_ (11), in which message data is absorbed.
 ** _Set_Ctx_ (12), in which the context string is set.

* *Allowed State Transitions:* those of <<KLEE-ECC>>, with the following changes:
 ** _Set_Ctx_ is reachable from, and can transition to, the same states as the _Set_
    states of <<KLEE-ECC>>.
 ** _Msg_Absorb_ is entered from _Ready_, any _Set_ state, or _Msg_Absorb_ itself, by the
    Form B `kl.setst` described below; the re-entry from _Msg_Absorb_ into _Msg_Absorb_
    is an explicitly allowed same-state transition, marking a pass boundary.
 ** _Msg_Absorb_ can be left only for _Msg_Absorb_, _Sign_Generate_, _Sign_Verify_ or _Ready_ (or an Error State);
    a `kl.setst` naming any other State transitions the locker to Error State _Invalid_. Between the two signing passes,
    and between the verification pass and _Sign_Verify_, no _Set_ state can therefore be entered, and `Scalar`, `ctx`,
    `Signature` and `SecondPt` cannot be replaced: a `R` substituted between the passes would yield two signatures with
    the same `r`, which reveal `s`, and a `Signature` substituted after the verification pass could be forged against
    the `k'` already computed.
 ** For `kl.restrict*` (<<Zkl-ISA-unpriv.adoc#KLEE-instruction-restrict>>), _Msg_Absorb_ is a State allowed only while
    performing signature generation during signing passes 1 and 2, and only while performing signature verification during
    the verification pass: clearing _MachinePolicy_[0], resp. _MachinePolicy_[1], in it transitions the locker to Error
    State _Invalid_.
 ** The entry conditions (Rule <<KLEE-MGR-policy-gate>>) for _Sign_Generate_ and _Sign_Verify_ of <<KLEE-ECC>> are
    replaced by the following, in addition to the gating by _MachinePolicy_:
  *** _Sign_Generate_: `Scalar` holds a configured seed, and either `msg_pass` = 2 (pure mode) or `msg_pass` = 0
      and `HasHash` (pre-hash mode).
  *** _Sign_Verify_: `HasSecondPt` and `HasSignature`, and either `msg_pass` = 3 (pure mode) or `msg_pass` = 0
      and `HasHash` (pre-hash mode).

* *Behavior:*

** In State _Point_Mul_, the Behavior of <<KLEE-ECC>> applies, except that its item 1 requires
   `Scalar` to hold a configured seed, and the multiplier is the secret scalar `s` derived from the
   seed (cite:[RFC8032] {sect}5.1.5, resp. {sect}5.2.5, steps 1 to 3) instead of `int(Scalar)`:
   `SecondPt` {leftarrow} `s` {interpunct} `P`. With `HasSecondPt` clear and the default
   `Generator`, `SecondPt` thus receives the public key `A`.

** Signature generation and verification always use the base point `B` of cite:[RFC8032] {sect}5.1, resp. {sect}5.2,
   whatever `Generator` holds: `R` {leftarrow} `r` {interpunct} `B`, the public key `A` derived from the seed is
   `s` {interpunct} `B`, and verification checks its equation over `B`. `Generator` is used only by _Point_Mul_, so
   the check of its validity (<<KLEE-ECC>>) applies only there.

** Signature generation requires *two* passes over the message, and verification one.
   This is inherent to EdDSA, whose second hash takes `R`, which is not known until the
   first pass has completed. `msg_pass` records the open or the completed pass; `msg_pass`, `r` and `k'` are
   cleared upon entering State _Ready_.

** To transition to State _Set_Ctx_, a Form B `kl.setst` is used whose auxiliary
   argument `Xs` sets `ctxlen`. Values greater than 255 cause the locker to transition to
   Error State _Invalid_.
+
If `ctxlen` {ne} 0, the `ctx` value is then loaded with
   (multi-block) Form B `kl.exec` instructions, following Rule <<KLEE-MGR-load-long-field>>
   as the _Set_ states of <<KLEE-ECC>> do, with the progress recorded in `block_base`.
   Leaving _Set_Ctx_ before `ctx` is complete zeroes `ctx` and `ctxlen` (Rule <<KLEE-MGR-load-long-field>>).

** To enter State _Msg_Absorb_ (pure mode only), a Form B `kl.setst` is used whose auxiliary
   argument `Xs` selects the pass. Entering the State requires _AuxInfo_ = 1, and each pass has the entry conditions below (Rule <<KLEE-MGR-policy-gate>>).

  . `Xs` = 0, *signing pass 1*: requires that signature generation be allowed and that
    `Scalar` hold a configured seed; `msg_pass` {leftarrow} 0, and `H` is initialized
    with `dom {vvert} prefix`.
  . `Xs` = 1, *signing pass 2*: requires `msg_pass` = 1; `H` is initialized with
    `dom {vvert} R {vvert} A`, with `R` from `Signature` and `A` derived from the seed.
    A second instance `H'`, initialized with `dom {vvert} prefix` as in pass 1, absorbs the
    same message bytes and recomputes `r`, against which the pass is rebound to pass 1 at
    finalization.
  . `Xs` = 2, *verification pass*: requires that signature verification be allowed and
    that `HasSignature` and `HasSecondPt` hold; `msg_pass` {leftarrow} 3, and `H` is
    initialized with `dom {vvert} R {vvert} A`, with `R` from `Signature` and
    `A` = `SecondPt`.
  . Any other value of `Xs` causes the locker to transition to Error State _Invalid_.

** In State _Msg_Absorb_, Form B ``kl.exec`` instructions absorb message bytes into `H` — and,
   in signing pass 2, into `H'` — through Procedure `process_VLI`
   (<<KLEE-process-VLI>>), invoked as +
   `{fournbsp}` `process_VLI(max_len=0, block, b, state, n, input_base, block_base, 0, cumul_len, process_block(), None, mode)`, +
   where:
  *** `block`, `b`, `state`, `n`, `block_base` and `cumul_len` are the buffer, block size,
   state, state size, and partial-block and cumulative-length counters of the hash instance;
  *** `process_block()` applies its compression function;
  *** `cumul_len` is tracked because the unit
   finalizes the hash itself, appending the padding and length at pass finalization; and
  *** `mode` is
   `assign` for ed25519, whose `H` is `SHA-512` (<<KLEE-SHA-2>>), and `xor_accumulate` for ed448,
   whose `H` is `SHAKE256` (<<KLEE-SHA-3>>).
+
In signing pass 2, `H` and `H'` absorb the same bytes, but their blocks start at different offsets.
The interruption points of _Msg_Absorb_ are those of `H`: 0, and every byte offset at which the `block_base` of `H` is 0.
`H'` may then hold a partial block, which is architected (Position xiii), so a halt there is consistent.

** Leaving State _Msg_Absorb_ — by the same-state re-entry above or by a transition to
   another state — finalizes the current pass:
+
--
   . after pass `Xs` = 0: `r` {leftarrow} `H(dom {vvert} prefix {vvert} M) mod L`,
    `Signature.R` {leftarrow} `r` {interpunct} `B`, `msg_pass` {leftarrow} 1,
    and `HasSignature` is cleared: `Signature.R` holds an intermediate value, and a signature loaded before is discarded;
  . after pass `Xs` = 1: if `H'(dom {vvert} prefix {vvert} M) mod L` {ne} `r`, the pass-2
    message differs from that of pass 1, and the locker transitions to Error State _Invalid_;
    otherwise `k'` {leftarrow} `H(dom {vvert} R {vvert} A {vvert} M)` and `msg_pass` {leftarrow} 2;
  . after pass `Xs` = 2: `k'` as above, and `msg_pass` remains 3.
--
+
The verification pass records 3, both while open and once completed, so that it cannot be confused with signing pass 1,
which also computes a hash but leaves `k'` unset. Were both to record 1, a caller
could run signing pass 1 and then enter _Sign_Verify_, which would verify against a `k'` that was
never computed.

** In State _Sign_Generate_, a single Form D ``kl.exec Kn|K(Xn)`` completes the
   signature per cite:[RFC8032] {sect}5.1.6, resp., {sect}5.2.6:
  . In *pure* mode (`msg_pass` = 2):
    `S` {leftarrow} `(r + k'` {interpunct} `s) mod L`.
  . In *pre-hash* mode (`msg_pass` = 0): both hashes are
    computed internally over the fixed-size inputs, with `Hash` (holding `PH(M)`)
    standing in for the message.
  . `Signature` {leftarrow} (`R`, `S`), `HasSignature` is set, `r` and `k'` are destroyed,
    `msg_pass` {leftarrow} 0, `OutputType` {leftarrow} True, and the state transitions
    to _Output_.

** In State _Sign_Verify_, a single Form D ``kl.exec Kn|K(Xn)`` verifies `Signature`
   per cite:[RFC8032] {sect}5.1.7, resp., {sect}5.2.7, in *pure* mode if `msg_pass` = 3, with the `k'` of the
   verification pass, and in *pre-hash* mode if `msg_pass` = 0.
   All checks those sections require — the range of `S` and the validity of the
   encodings of `R` and `A` — are performed; if any fails, or the verification equation
   does not hold, the state transitions to _Failure_, else to _Success_.

NOTE: Pass 2 recomputes `r` from its own message and requires it to equal the value stored in
pass 1; a mismatch invalidates the locker. This binding prevents manipulation from the caller,
whereby two signatures that share `R` but commit to different messages reveal the private scalar `s`.
The restriction on leaving _Msg_Absorb_ prevents the converse manipulation, a different `R` with the same `r`.
Pre-hash mode is unaffected: `PH(M)` in the `Hash` field feeds both hashes.

[[KLEE-PQC]]
== Post Quantum Public-Key Cryptography

[[KLEE-PQC-ML-KEM]]
=== ML-KEM

The _Module-Lattice-Based Key-Encapsulation Mechanism Standard_ was announced by NIST in August 2024 cite:[nist-fips-203].
The standard defines several procedures, including:

* `ML-KEM.KeyGen`: Generates an encapsulation key `encapsk` and a corresponding decapsulation key `decapsk`.
* `ML-KEM.Encaps`: Uses the encapsulation key `encapsk` to generate a shared secret key `sharedkey` and an associated ciphertext.
* `ML-KEM.Decaps`: Uses the decapsulation key `decapsk` to produce a shared secret key `sharedkey` from a ciphertext.

ML-KEM comes in three versions, ML-KEM-512, ML-KEM-768, and ML-KEM-1024, with increasing cryptographic strength.
They require RBGs of corresponding strength: 128, 192, and 256 bits, respectively.
The sizes of keys and ciphertexts of the three subtypes of ML-KEM are summarized in <<KLEE-ML-KEM-sizes>>.

[[KLEE-ML-KEM-sizes]]
.Sizes (in bytes) of keys and ciphertexts of ML-KEM
[%autowidth,float="center",align="center",cols="^1,^1,^1,^1,^1",options="header"]
|===
| Subtype     | `encapsk` | `decapsk` | `ciphertext` | `sharedkey`
| ML-KEM-512  |       800 |      1632 |          768 |        32
| ML-KEM-768  |      1184 |      2400 |         1088 |        32
| ML-KEM-1024 |      1568 |      3168 |         1568 |        32
|===

The ML-KEM Machines also support the `kl.derive` instruction
(<<Zkl-ISA-unpriv.adoc#KLEE-instruction-derive>>), which takes the `sharedkey` already held in the CC—produced by
`_Encapsulate_` or by `_Decapsulate_`—and moves it into a key field of a second locker, provisioned beforehand
in the ordinary way, or into the `kl.exec` input of a hash function, MAC or XOF in a second locker
(<<KLEE-derive-endpoints>>).

[NOTE]
====
In KLEE's implementation of ML-KEM, the shared key is not treated as an output.
ML-KEM produces key material for a Machine implementing a symmetric algorithm; `kl.derive` moves that
material directly into a second locker, so the shared secret is
handled entirely inside the KLEE unit and never appears in the memory of the process using it.
====

Data Structures:::

* The *Provisioning Input* contains only the MDH.

* *Internal State*:
+
--
 ** `decapsk`: 13056 / 19200 / 25344 bits (1632 / 2400 / 3168 bytes), the string `dk_PKE {vvert} ek {vvert} H(ek) {vvert} z` of cite:[nist-fips-203] Algorithm 16,
 where `dk_PKE` has 384·`k` bytes, `ek` has 384·`k` + 32 bytes, and `H(ek)` and `z` have 32 bytes each (`k` = 2, 3, 4).
 ** `encapsk`: 6400 / 9472 / 12544 bits (800 / 1184 / 1568 bytes). It is not stored separately: it is the `ek` sub-field of `decapsk`,
 at byte offset 384·`k` (768 / 1152 / 1536). When only an encapsulation key is held, the other bytes of `decapsk` are zero.
 ** `HasEncapsk`, `HasDecapsk`: Booleans, recording whether `encapsk`, resp. a complete `decapsk`, holds a configured value.
 They are bits 0 and 1 of _StateExtension_, resp., and follow the pattern of Rule <<KLEE-MGR-load-long-field>>, with the departures stated below. `HasDecapsk` implies `HasEncapsk`.
 ** `HasCiphertext`: Boolean, bit 2 of _StateExtension_, recording whether `ciphertext` holds a complete value, loaded and
 checked, or computed by _Encapsulate_. It follows the pattern of Rule <<KLEE-MGR-load-long-field>>.
 ** `ciphertext`: 6144 / 8704 / 12544 bits (768 / 1088 / 1568 bytes).
 ** `sharedkey` 256 bits.

`encapsk`, `decapsk`, resp. `sharedkey` correspond to `ek`, `dk`, resp. `K` in cite:[nist-fips-203].

The ML-KEM Machines use the _MachineUse_ field of the metadata header to record how many
bytes of a long field have been transferred so far: read from memory in the _encapsk_Input_,
_decapsk_Input_, and _ciphertext_Input_ states, or written to memory in the
_encapsk_Output_ and _ciphertext_Output_ states. This is the transfer counter _W_ of Rule <<KLEE-MGR-load-long-field>>,
which the ECC Machines keep in `block_base` instead (<<KLEE-ECC>>).

The size of the internal state of the three variants is 2432, 3520, and 4768 bytes, excluding metadata.
--

* *Serialized Content*:
+
--
[%autowidth,cols="^1,<3,<3",options="header"]
|===
|  Pos. | Size (Bits) +
for ML-KEM-512/768/1024 | Field
|    i  | 13056 / 19200 / 25344 | `decapsk`, which holds either a complete decapsulation key or only `encapsk` in its `ek` sub-field, according to `HasDecapsk`
|   ii  | 6144 / 8704 / 12544   | `ciphertext`
|  iii  | 256                   | `sharedkey`

These contexts are large: for ML-KEM-512, ML-KEM-768 and ML-KEM-1024 the serialized content is
2432, 3520 and 4768 bytes, that is 152, 220 and 298 blocks of 128 bits; `encapsk` takes no
space of its own, since it is held in the `ek` sub-field of `decapsk`.

Machine-Specific Functions:::
+
--
The procedures implemented by ML-KEM are taken directly from cite:[nist-fips-203]:

* `ML-KEM.KeyGen(d, z)` generates encapsulation key `encapsk` and decapsulation key `decapsk` from random seeds `d, z` (cite:[nist-fips-203] Algorithm 19).
* `ML-KEM.Encaps(encapsk, m)` generates ciphertext `ciphertext` and shared key `sharedkey` from encapsulation key `encapsk` and randomness `m` (cite:[nist-fips-203] Algorithm 20).
* `ML-KEM.Decaps(decapsk, ciphertext)` computes shared key `sharedkey` from decapsulation key `decapsk` and ciphertext `ciphertext` (cite:[nist-fips-203] Algorithm 21).

State Machine:::
+
--
* *States:*
Besides
_Ready_ (1),
_Success_ (46),
_Failure_ (47),
ML-KEM Machines define:
 ** _GenerateKeyPair_ (2)
 ** _Encapsulate_ (3)
 ** _Decapsulate_ (4)
 ** _encapsk_Input_ (5)
 ** _decapsk_Input_ (6)
 ** _encapsk_Output_ (7)
 ** _ciphertext_Input_ (8)
 ** _ciphertext_Output_ (9)
--

* *Allowed State Transitions:*
 ** State transitions are allowed between any two valid states, subject to the restrictions in Rules <<Zkl-ISA-unpriv.adoc#KLEE-GR-setst-in-success-failure>> and <<Zkl-ISA-unpriv.adoc#KLEE-GR-success-failure-cannot-be-set-directly>>.

* *Behavior:*

** Upon provisioning, the fields `decapsk` (and with it `encapsk`), `ciphertext` and `sharedkey` are cleared, and so are `HasEncapsk`, `HasDecapsk` and `HasCiphertext`.

** Upon transitioning to State _Ready_, the field `sharedkey` is cleared, while `decapsk` (and with it `encapsk`), `ciphertext`, `HasEncapsk`, `HasDecapsk` and `HasCiphertext` are kept,
so that a key pair survives a return to _Ready_, in particular from _Success_ and _Failure_ (Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-setst-in-success-failure>>),
and a completely loaded ciphertext (see below) remains available to _Decapsulate_.

** _MachineUse_ is set to zero upon provisioning and upon transitioning to State _Ready_.

** Upon entering State _encapsk_Input_, the whole `decapsk` field is zeroed and `HasEncapsk` and `HasDecapsk` are cleared; the loaded value is written into the `encapsk` sub-field, so that the locker then holds an encapsulation key only.
Upon entering State _decapsk_Input_, `HasEncapsk` and `HasDecapsk` are cleared.
Upon entering State _ciphertext_Input_, `sharedkey` is cleared together with `ciphertext`, since it belongs to the ciphertext being replaced, and `HasCiphertext` is cleared.
When a load completes and passes its check (see below), `HasEncapsk` is set for an `encapsk`, both key flags are set for a `decapsk`, and `HasCiphertext` is set for a `ciphertext`.

 ** No `kl.setst` of this Machine takes an auxiliary parameter.

 ** Apart from `HasEncapsk`, `HasDecapsk` and `HasCiphertext`, the ML-KEM Machines do not carry state information as to whether
 `sharedkey` has been assigned a value.
   The input checks that cite:[nist-fips-203] {sect}7.2 and {sect}7.3 require are
   performed when a field is written (Rule <<KLEE-MGR-check-on-write>>): when its load finishes, and when an import restores a key
   that `HasEncapsk` or `HasDecapsk` marks as configured. They are split according to what a failure means:
+
--
 . Upon completion of State _encapsk_Input_, the *encapsulation key check* of
     cite:[nist-fips-203] {sect}7.2 is performed: the type check (`encapsk` has the length required
     by the parameter set) and the modulus check (`encapsk` re-encodes to itself, i.e. every
     coefficient is reduced modulo `q`).
 . Upon completion of State _decapsk_Input_, the *decapsulation key check* of
     cite:[nist-fips-203] {sect}7.3 is performed: the type check and the hash check (the copy of
     `H(encapsk)` embedded in `decapsk` matches the embedded `encapsk`).
 . A `kl.setst` that leaves State _encapsk_Input_, _decapsk_Input_ or _ciphertext_Input_ before the
     field is complete zeroes the field, as in every Machine (Rule <<KLEE-MGR-load-long-field>>): `HasEncapsk` and
     `HasDecapsk`, resp. `HasCiphertext`, stay clear, so that no partly loaded key or ciphertext can be used
     (Rule <<KLEE-MGR-policy-gate>>).
 . A failure of the decapsulation key check is a *configuration* error: the locker transitions to Error State
     _Invalid_, and the CC must be reconfigured before it can be used.
 . A failure of the encapsulation key check is a *data* error (Rule <<KLEE-MGR-config-data-error>>): `encapsk` is a public key, usually
     a peer's. The whole `decapsk` field is zeroed, `HasEncapsk` and `HasDecapsk` stay clear, and the state machine
     transitions to State _Failure_, which is a valid state.
 . Upon completion of State _ciphertext_Input_, the *ciphertext type check* of
     cite:[nist-fips-203] {sect}7.3 is performed: a completely loaded `ciphertext` has the length that the parameter
     set requires, so it always passes, and the check is stated for conformance with cite:[nist-fips-203] {sect}7.3.
     `HasCiphertext` is then set, and the state machine transitions to State _Ready_ (not _Success_).
--
+
These checks do not affect the implicit rejection of `ML-KEM.Decaps`: a ciphertext that passes the
type check but does not decapsulate correctly still yields the `z`-derived shared key, the state
machine still transitions to _Success_, and the two cases remain indistinguishable to the caller.

 ** In States _GenerateKeyPair_, _Encapsulate_ and _Decapsulate_ the operation is long-running: _MachineUse_ is the field _P_ of Rule <<KLEE-MGR-progress-discard>>, and the `kl.exec` resumes an interrupted operation when it is non-zero.

 ** In State _GenerateKeyPair_, Form D ``kl.exec Kn|K(Xn)`` generates a new key pair using procedure `ML-KEM.KeyGen` of cite:[nist-fips-203] (Algorithm 19).

`ML-KEM.KeyGen` fails only if the random bit generator fails (cite:[nist-fips-203] Algorithm 19); the locker
then transitions to Error State _Invalid_ (Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-rbg-failure>>).
Otherwise `decapsk` (and with it `encapsk`) receives the new key pair,
`HasEncapsk` and `HasDecapsk` are set, and the state machine transitions to State _Ready_, which keeps them.
The caller then transitions to a State that uses the key pair, for instance _encapsk_Output_ or _Decapsulate_.

** In State _Encapsulate_, Form D ``kl.exec Kn|K(Xn)`` executes encapsulation using procedure `ML-KEM.Encaps` of cite:[nist-fips-203] (Algorithm 20), applied to the `encapsk` state field, which must have been set—by `_encapsk_Input_`, `_decapsk_Input_` or `_GenerateKeyPair_`: entering _Encapsulate_ requires `HasEncapsk` (Rule <<KLEE-MGR-policy-gate>>). The procedure draws a random value internally and derives from it *both* the shared key and the ciphertext, which are stored in the `sharedkey` and `ciphertext` state fields, respectively, and `HasCiphertext` is set; the shared key is not drawn independently of the ciphertext.

`ML-KEM.Encaps` fails only if the random bit generator fails (cite:[nist-fips-203] Algorithm 20), since `encapsk` was either
generated by `ML-KEM.KeyGen` or checked when it was loaded; the locker then transitions to Error State _Invalid_
(Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-rbg-failure>>). Otherwise the state machine transitions to state _ciphertext_Output_.

** In State _Decapsulate_, Form D ``kl.exec Kn|K(Xn)`` decapsulates the ciphertext using procedure `ML-KEM.Decaps` of cite:[nist-fips-203] (Algorithm 21).
Entering _Decapsulate_ requires `HasDecapsk` and `HasCiphertext` (Rule <<KLEE-MGR-policy-gate>>), so that `ML-KEM.Decaps` never runs
with a partly loaded key or on a partly loaded or unchecked ciphertext.
`ML-KEM.Decaps` is executed unconditionally. The shared key, either derived from the ciphertext or returned via “implicit rejection” is placed in the `sharedkey` state field, and the state machine transitions to state `_Success_`. The caller cannot distinguish the two cases.

** In States _encapsk_Input_, _decapsk_Input_ and _ciphertext_Input_, the fields `encapsk`,
`decapsk` and `ciphertext` are loaded using (multi-block) `kl.exec` instructions of Form B,
following Rule <<KLEE-MGR-load-long-field>> of <<KLEE-Machine-rules>>, with the progress recorded in
_MachineUse_. The size of each field in bits is 8
times the size in bytes given in <<KLEE-ML-KEM-sizes>>, so it is determined by the KEM variant and
the state and no variable is needed to hold it.

** In States _encapsk_Output_ and _ciphertext_Output_, the fields `encapsk` and `ciphertext` are
emitted using (multi-block) `kl.exec` instructions of Form C, following Rule <<KLEE-MGR-load-long-field>>, with the
progress recorded in _MachineUse_. Both fields are public, so no restriction applies to where they
are written. Once the field has been completely emitted, the state machine transitions to _Success_ (Rule <<KLEE-MGR-load-long-field>>):
after _Encapsulate_, the `sharedkey` is then moved by `kl.derive` from _Success_, as after _Decapsulate_.
Entering _encapsk_Output_ requires `HasEncapsk`, and entering _ciphertext_Output_ requires `HasCiphertext` (Rule <<KLEE-MGR-policy-gate>>).

** `sharedkey` is emitted by no `kl.exec`. It is the only exportable field of an ML-KEM locker, moved by `kl.derive`
(<<Zkl-ISA-unpriv.adoc#KLEE-instruction-derive>>) as Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-shared-secret>> specifies,
in the States given in <<KLEE-derive-endpoints>>. A zero `sharedkey`, as left by _Ready_, is not a source.

[[KLEE-PQC-ML-DSA]]
=== ML-DSA

The _Module-Lattice-Based Digital Signature Standard_ was announced by NIST in August 2024 cite:[nist-fips-204] in three variants: ML-DSA-44, ML-DSA-65, and ML-DSA-87.

[[KLEE-ML-DSA-sizes]]
.Sizes (in bytes) of keys and signatures of ML-DSA
[%autowidth,float="center",align="center",cols="^1,^1,^1,^1",options="header"]
|===
| Subtype   | Private Key | Public Key | Signature Size
| ML-DSA-44 |     2560    |    1312    |     2420
| ML-DSA-65 |     4032    |    1952    |     3309
| ML-DSA-87 |     4896    |    2592    |     4627
|===

The principal functions offered by ML-DSA are:

* `ML-DSA.KeyGen`: Generates a public-private key pair.
* `ML-DSA.Sign`:   Generates a digital signature for a given message.
* `ML-DSA.Verify`: Verifies a digital signature for a given message.
* `HashML-DSA.Sign`:   Generates a digital signature for a given pre-hashed message.
* `HashML-DSA.Verify`: Verifies a digital signature for a given pre-hashed message.

The KLEE ML-DSA Machines execute the core lattice operations of signing and verification, specifically `ML-DSA.Sign_internal` and `ML-DSA.Verify_internal` as defined in cite:[nist-fips-204] (Algorithms 7 and 8), with an _external_ message representative μ:
the caller supplies μ in State _mu_Input_, and the steps of these algorithms that compute μ from `tr` and the formatted message `M'`
are not performed. Consequently the Machine never sees the message, the context string `ctx` or `tr` as separate values.

Message hashing and domain formatting (cite:[nist-fips-204] {sect}5) are structured as follows:

* *Pure ML-DSA:* The caller formats the domain-separated message string `M' = 0x00 {vvert} bin(|ctx|, 8) {vvert} ctx {vvert} M` and computes the 64-byte message representative `mu = SHAKE256(tr {vvert} M', 64)`, which is supplied to the KLEE unit via State _mu_Input_.
* *HashML-DSA (Pre-Hash):* The caller pre-hashes message `M` with the hash function `PH` specified in the _AuxInfo_ field of the MDH, constructs `M' = 0x01 {vvert} bin(|ctx|, 8) {vvert} ctx {vvert} OID(PH) {vvert} PH(M)`, and computes `mu = SHAKE256(tr {vvert} M', 64)` to be loaded into State _mu_Input_.
For FIPS conformance, cite:[nist-fips-204] requires `PH(M)` to be computed within a FIPS-140-validated cryptographic module, which may be the KLEE unit itself if it is required to be FIPS-140-validated.
* *Public Key Hash (`tr`):* `tr = SHAKE256(pubkey, 64)`. It is embedded in `privkey` (cite:[nist-fips-204] Algorithm 24), where `ML-DSA.KeyGen` places it; the caller computes it from the public key.

// `{fournbsp}{fournbsp}` μ = `SHAKE256(tr {vvert} M', 64)`, where `tr` = `SHAKE256(pk, 64)` and
//
// * for pure ML-DSA, `M'` = `0x00 {vvert} bin(|ctx|, 8) {vvert} ctx {vvert} M`;
// * for HashML-DSA, `M'` = `0x01 {vvert} bin(|ctx|, 8) {vvert} ctx {vvert} OID(PH) {vvert} PH(M)`, with `PH` the function that _AuxInfo_ records.

[NOTE]
====
*The caller's duties in forming μ.*
The message representative μ and the string `M'` are formed as stated above, following cite:[nist-fips-204] {sect}5.2 to 5.4 and Algorithms 2 to 5, 7 and 8,
with `PH` the function that _AuxInfo_ records, and `ctx` a context string of at most 255 bytes, chosen by the protocol, `|ctx|` being its length in bytes.
The caller is expected to:

. obtain the public key `pk` of the CC: for verification, the key it has loaded in State _pubkey_Input_; for signing, the key
  emitted in State _pubkey_Output_ after _GenerateKeyPair_ or _compute_pubKey_, or a copy of it from an authenticated source,
  such as a certificate;
. compute `tr` from `pk` once, and keep it with the CC;
. for each message, choose the mode that _AuxInfo_ selects (pure if _AuxInfo_ = 0), form `M'` with the context string that the
  protocol prescribes, compute μ, and load it in State _mu_Input_, before entering _Sign_Generate_ or _Sign_Verify_;
. use, when verifying, the same `ctx` and mode as the signer; and
. compute `PH(M)` for HashML-DSA within a cryptographic module of the required validation level (see above).

The Machine cannot check any of these steps: a μ formed with a wrong `tr`, `ctx` or mode yields a signature that the
intended verifier rejects, or a verification that fails, but it never discloses or weakens the private key.
====


Machine-Specific Functions:::
+
--
The procedures implemented by ML-DSA are taken directly from cite:[nist-fips-204]:

* `ML-DSA.KeyGen(xi)` generates public key `pubkey` and private key `privkey` from random seed `xi` (cite:[nist-fips-204] Algorithm 1).
* `ML-DSA.Sign_internal(privkey, mu, rnd)` generates digital signature `signature` from private key `privkey`, message representative `mu`, and randomness `rnd` (cite:[nist-fips-204] Algorithm 7).
* `ML-DSA.Verify_internal(pubkey, mu, signature)` verifies signature `signature` against public key `pubkey` and message representative `mu` (cite:[nist-fips-204] Algorithm 8).
--

Data Structures:::
+
--
* The *Provisioning Input* consists only of the MDH.
**  The _MachinePolicy_ field in the MDH has the following meaning:

. _MachinePolicy_[0] allows signature generation, and gates _Sign_Generate_;
. _MachinePolicy_[1] allows signature verification, and gates _Sign_Verify_ (Rule <<KLEE-MGR-policy-gate>>).
. A _MachinePolicy_ of 0 is admissible, but makes no sense, since the locker can then neither generate nor verify signatures (<<Zkl-ISA-unpriv.adoc#KLEE-Machine-field>>).

** The _AuxInfo_ field is zero for pure `ML-DSA`. For `HashML-DSA` it records the pre-hash function
`PH`, in the format of bits [15:0] of the MDH (_Machine_, _MachinePolicy_ and _MachineExtension_);
`PH` must be a hash function or XOF that cite:[nist-fips-204] {sect}5.4 admits for the parameter set.
The KLEE unit neither computes `PH` nor enforces its use; the field, which is in the clear in the MDH, informs the
recipients of the CC, which need not implement `PH`. _μ_ is always computed with SHAKE256 (cite:[nist-fips-204] Algorithm 7).
+
_AuxInfo_ is not zeroed by provisioning or by a transition to _Ready_.
At provisioning and at import, a non-zero value of _AuxInfo_ that does not encode a hash function supported by the KLEE implementation
is unsupported Metadata, and raises a KLEE unsupported-Metadata exception (<<Zkl-ISA-unpriv.adoc#KLEE-Metadata-validity>>).
This allows an M-mode handler to emulate the Machine with a hash function that the hardware does not support
(<<Zkl-ISA-unpriv.adoc#KLEE-error-architecture>>).
The hardware does not distinguish whether the value encodes a hash function admitted by cite:[nist-fips-204], by a later revision of it,
or by another national standard: a handler that cannot resolve the exception, including for a value that encodes no
hash function at all, transitions the locker to Error State _Unsupported_.

* *Internal State*:

** In the Metadata Header, the field _MachineUse_ is used to keep track of input and output of long fields in an architecturally defined way and to track
  long-running operations in an implementation-specific way.
 ** `HasPrivKey`, `HasPubKey`: Booleans, recording whether `privkey`, resp. `pubkey`, holds
    a configured value. They are bits 0 and 1 of _StateExtension_, resp., and follow the pattern of Rule <<KLEE-MGR-load-long-field>>, with the departures stated below.
 ** `Hedged`: Boolean, bit 2 of _StateExtension_, recording the signing mode selected on entering _Sign_Generate_.
 ** `privkey`: 2560/4032/4896 bytes (20480/32256/39168 bits) for ML-DSA-44/65/87, resp.
 ** `pubkey` : 1312/1952/2592 bytes (10496/15616/20736 bits) for ML-DSA-44/65/87, resp.
 ** `signature`: 2420/3309/4627  bytes (19360/26472/37016 bits) for ML-DSA-44/65/87, resp.
 ** `mu`: 64 bytes (512 bits), the external message representative μ
 ** `rnd`: 32 bytes (256 bits), the random value of hedged signing; it is non-zero only while a hedged signing operation is interrupted (Rule <<KLEE-MGR-progress-discard>>), and zero otherwise, including for deterministic signing.

[none]
* The ML-DSA Machine does not hash the message: the caller computes μ as described above.

* Besides `rnd`, the internal state may contain several additional variables, for instance intermediate values of the computation of the NTT.
Their definition and their size are implementation-dependent.
An SCC must save them in the ADS, so that an interrupted operation can resume on the same implementation, as Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-long-running-no-data>> prescribes.

* *Serialized Content*:
+

|===
|  Pos. | Size (Bits) +
for ML-DSA-44/65/87 | Field

|  ii   | 10496 / 15616 / 20736            | `pubkey`
|  iii  | 19360 / 26472 / 37016            | `signature`

These contexts are large: for ML-DSA-44, ML-DSA-65 and ML-DSA-87 the serialized content is
6400, 9392 and 12224 bytes, that is 400, 587 and 764 blocks of 128 bits, padding included.

Apart from `HasPrivKey`, `HasPubKey` and `Hedged` (which are stored in _StateExtension_)
the ML-DSA Machines do not carry state information as to whether `signature`
and `mu` have been assigned values.
A `privkey` whose `s1` or `s2` has a coefficient outside [−η, η] (cite:[nist-fips-204] Algorithm 25)
is malformed: this is a configuration error, and the locker transitions to Error State _Invalid_ when `privkey` is written,
that is when its load completes or an import restores it with `HasPrivKey` set (Rule <<KLEE-MGR-check-on-write>>).
Every `pubkey` of the correct length is well formed (cite:[nist-fips-204] Algorithm 23).
A `signature` or `mu` that is malformed or does not verify is a data error and
transitions the state machine to State _Failure_, which is a valid state.

State Machine::: {empty}
+
--
* *States:*
Besides
_Ready_ (1),
_Success_ (46),
_Failure_ (47),
ML-DSA Machines define (States 5 and 7 are not used):
 ** _GenerateKeyPair_ (2)
 ** _pubkey_Output_ (3)
 ** _pubkey_Input_ (4)
 ** _mu_Input_ (6)
 ** _Sign_Generate_ (8)
 ** _Sign_Output_ (9)
 ** _Sign_Verify_ (10)
 ** _Sign_Input_ (11)
 ** _privkey_Input_ (12)
 ** _compute_pubKey_ (13)

* *Allowed State Transitions:*

** State transitions are allowed between any two valid states, subject to the restrictions in Rules <<Zkl-ISA-unpriv.adoc#KLEE-GR-setst-in-success-failure>> and <<Zkl-ISA-unpriv.adoc#KLEE-GR-success-failure-cannot-be-set-directly>>.

* *Behavior:*

** Upon provisioning, fields `privkey` and `pubkey` are cleared, both flags `HasPrivKey` and `HasPubKey` are false, and the state machine transitions to State _Ready_.

** To transition to any one of the states _Ready_, _GenerateKeyPair_, _privkey_Input_, _pubkey_Input_, _mu_Input_, _Sign_Input_, _pubkey_Output_, _compute_pubKey_, _Sign_Verify_, a Form A `kl.setst` instruction must be used.

** Upon transitioning to _Ready_, the fields `signature`, `mu`, and `rnd` are cleared.

** _MachineUse_ is set to zero upon provisioning and upon transitioning to State _Ready_.
   `privkey`, `pubkey`, `HasPrivKey` and `HasPubKey` are not changed.

** In State _GenerateKeyPair_, Form D ``kl.exec Kn|K(Xn)`` generates a new key pair, replacing `privkey` (which embeds `tr`) and `pubkey`, and setting both `HasPrivKey` and `HasPubKey` using procedure `ML-DSA.KeyGen` of cite:[nist-fips-204] (Algorithm 1), with a seed `xi` drawn from the RBG (Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-rbg-failure>>).
On completion the state machine transitions to State _Ready_, which keeps the key pair, as for ML-KEM (<<KLEE-PQC-ML-KEM>>). The caller then transitions to a State that uses it, for instance _pubkey_Output_ or _Sign_Generate_.

** Upon entering State _privkey_Input_, `HasPrivKey` is set to false, and `pubkey` is
erased and `HasPubKey` set to false, so that
the locker never holds a private key and an unrelated public key together.
// CC must be a matching pair, and the incoming private key is in general unrelated to
// the public key that was there before; keeping the latter would leave the CC able to
// verify under one key while signing under another.
When the loaded value is complete, `HasPrivKey` is set to true.

** Upon entering State _pubkey_Input_, `HasPubKey` is set to false; when the loaded value
    is complete, it is set to true. `privkey` and `HasPrivKey` are not affected: loading a
    public key alone is the normal way to configure a CC for verification only.

** In States _privkey_Input_, _pubkey_Input_, _mu_Input_, and _Sign_Input_,
the fields `privkey`, `pubkey`, `mu` and `signature`, respectively, are loaded using
(multi-block) `kl.exec` instructions of Form B, following Rule <<KLEE-MGR-load-long-field>>,
with the progress recorded in _MachineUse_, in bytes.

** Entering State _compute_pubKey_ requires `HasPrivKey` (Rule <<KLEE-MGR-policy-gate>>). In it, a Form D `kl.exec` instruction performs the following operations:

. Derive `pubkey` from `privkey`: decode it with skDecode (cite:[nist-fips-204] Algorithm 25) and apply steps 3, 5, 6 and 8 of Algorithm 6.
. Check whether the public key correctly hashes to `tr` (embedded in `privkey`), and if not, the locker transitions to Error State _Invalid_ (Rule <<KLEE-MGR-check-on-read>>).
. Write the derived public key into `pubkey` and set `HasPubKey`.

On completion the state machine transitions to State _Ready_, which keeps the key pair.

** To transition to State _Sign_Generate_, a Form B `kl.setst` is
   used, and the auxiliary parameter `Xs` selects the signing mode of cite:[nist-fips-204] {sect}3.4

. Entering the State requires `HasPrivKey` (Rule <<KLEE-MGR-policy-gate>>).
. If `Xs` = 0 (for instance, if `Xs = X0`), then _hedged_ signing is selected and `Hedged` is set.
. If `Xs` is non-zero, then *deterministic* signing is selected and `Hedged` is cleared.

** In State _Sign_Generate_, Form D ``kl.exec Kn|K(Xn)`` generates a digital signature using procedure `ML-DSA.Sign_internal` of cite:[nist-fips-204] (Algorithm 7).
The operation is long-running: _MachineUse_ is the field _P_ of Rule <<KLEE-MGR-progress-discard>>. If it is zero, `rnd` is drawn from an approved random bit generator (Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-rbg-failure>>) when `Hedged` is set and is `zeros(256)` otherwise; if it is non-zero, the interrupted operation is resumed with the `rnd` held. On completion `rnd` is destroyed.
The output of `ML-DSA.Sign_internal` is written in `signature`, and the locker transitions to _Sign_Output_.

** Entering State _Sign_Verify_ requires `HasPubKey` (Rule <<KLEE-MGR-policy-gate>>). In it, Form D ``kl.exec Kn|K(Xn)`` verifies a digital signature using procedure `ML-DSA.Verify_internal` of cite:[nist-fips-204] (Algorithm 8):

. If `ML-DSA.Verify_internal` returns `true`, the state machine transitions to State _Success_;
otherwise it transitions to State _Failure_. cite:[nist-fips-204] Algorithm 8 returns a Boolean
only, so nothing is written to `signature` on this path.

** In States _pubkey_Output_ and _Sign_Output_, the fields `pubkey` and `signature` are emitted
using (multi-block) `kl.exec` instructions of Form C, following Rule <<KLEE-MGR-load-long-field>>,
with the progress recorded in _MachineUse_, in bytes. Once the field has been completely emitted, the state machine
transitions to _Success_ (Rule <<KLEE-MGR-load-long-field>>).
Entering _pubkey_Output_ requires `HasPubKey` (Rule <<KLEE-MGR-policy-gate>>).
_Sign_Output_ is entered only from _Sign_Generate_, on completion of its `kl.exec`: a `kl.setst` naming _Sign_Output_ in any other State
transitions the locker to Error State _Invalid_, since no flag records that `signature` holds a generated signature.

** _MachinePolicy_ can be modified using `kl.restrictl`.

`kl.derive` can set the IV of GCM and the nonce of OCB from the `kl.exec` output of another Machine, such as a XOF, without exposing it to software.

The message-hashing State of EdDSA, _Msg_Absorb_ (<<KLEE-EdDSA>>), is not a `kl.derive` endpoint: separating it into transfers using `kl.derive` would not have added flexibility to the protocols using EdDSA, and would only have complicated the software and increased locker pressure.
