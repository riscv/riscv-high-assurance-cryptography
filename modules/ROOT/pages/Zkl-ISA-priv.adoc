//

The KLEE Privileged Architecture is _implemented_ on a hart that implements the `KLS` field and the exception causes of <<KLEE-exceptions>> that apply to its configuration. It is mandatory on every hart that is not M-mode-only, and optional on an M-mode-only hart. Where it is not implemented:

* `KLS` is not present, and is treated as Initial;
* no KLEE exception cause exists, and the behaviors of <<Zkl-ISA-unpriv.adoc#KLEE-exception-error-correspondence>> apply;
* `Smklstatus` and `Ssklvbootscrt` are not implemented; and
* the `mklcsk`, `mklphysbootscrt` and `mkllocality` groups may exist, each where its extension is implemented, with the accessibility that <<KLEE-CSR-mklcsk>> and <<KLEE-CSR-locality-groups>> prescribe.

On an M-mode-only hart, none of the extensions of the table above is mandatory.
`Smklcsk` and `Smklpbootscrt` are allowed in every configuration; with `Smklpbootscrt`, the `mklphysbootscrt`
CSR group sets the Physical Boot Secret Locality.
The requirements for the other extensions are:

.Privileged requirements, per system configuration
[float="center",align="center",cols="<19%,<27%,<27%,<27%",options="header"]

| M-mode only
| Optional: If implemented, `mllockerstatus` is implemented and shadowed in `sllockerstatus`.
| Optional: If implemented, `mkllocality` configures MLocality
| {empty}

| M+U
| Mandatory: `mllockerstatus` is implemented and shadowed in `sllockerstatus`.
| Optional: If implemented, `mkllocality` configures MLocality

| Mandatory: `mllockerstatus` and `sllockerstatus` (`Ssklstatus`) are implemented and are distinct.
| Optional: If implemented, `mkllocality` and `skllocality` (`Sskllclt`) configure MLocality and SLocality
| {empty}

| M+S+U with H
| Mandatory: `mllockerstatus`, `sllockerstatus` and `vsllockerstatus` (the latter two `Ssklstatus`) are implemented and are distinct.
| Optional: If implemented, `mkllocality`, `hkllocality` and `skllocality` (the latter two `Sskllclt`) configure MLocality, HLocality and SLocality
| Optional: If implemented, `hklvirtbootscrt` configures the Virtual Boot Secret Locality
|===

The last two columns give the CSR groups implemented with the extension,
and the Localities they set (<<Zkl-ISA-unpriv.adoc#KLEE-Localities>>); an empty cell means that the extension has no effect in

[[KLEE-exceptions]]
== Exceptions Raised by KLEE

This section describes the error conditions that raise exceptions, as opposed to those that set an Error State (<<Zkl-ISA-unpriv.adoc#KLEE-State-field>>).

When an exception is raised, `*cause` holds the cause, as <<KLEE-exception-codes>> describes; the table lists the causes in decreasing priority order.

The KLEE fatal-error exception precedes every exception that depends on the state of the KLEE unit, including the address-misaligned, access-fault and page-fault exceptions of KLEE memory instructions, whose transfer bounds are computed from that state (<<Zkl-ISA-unpriv.adoc#KLEE-instruction-mv>>); among the KLEE-specific conditions it is preceded only by the illegal-instruction grounds decided without accessing the KLEE unit.

|  3   | Instruction address breakpoint | {empty}
| 12, 1   | Instruction page fault, instruction access fault | As ordered by the Privileged Specification: first during instruction address translation, then on the physical address.
|  2   | Illegal-instruction            | The KLEE grounds decided without accessing the state of the KLEE unit, that is on the basis of defects in the encoding or the operands of the instruction, listed first in <<Zkl-ISA-unpriv.adoc#KLEE-illegal-instruction-grounds>>.
| TBD  | *KLEE fatal-error*             | Fatal system failure in the KLEE unit.
| TBD  | *KLEE missing-CSK*             | Use of the KLEE unit while no CSK is active: either none has been established, or the `mklcsk` group is only partially written (see <<Zkl-ISA-unpriv.adoc#KLEE-CSK-requirements>>, <<KLEE-CSR-mklcsk>>). Only M-mode can establish a CSK.
| TBD  | *KLEE locker-Off*              | Any access, as defined in <<KLEE-CSR-llockerstatus>>, to a locker whose `*llockerstatus` field is _Off_; M-mode forwards it to the mode that owns the _Off_ field.  This exception enables on-demand (lazy) locker loading and trap-and-emulate.

|  3   | Load/store address breakpoint  | On the address of a component access of `kl.load`, `kl.store`, `kl.input` or `kl.output`, when that access is about to be performed; for the first component access, before the address-misaligned check.

// Remark about KLEE locker-Off.:::
// A KLEE unsupported-Metadata exception arises only from a `kl.mgmt` that opens a provisioning or an import, which <<KLEE-CSR-llockerstatus>> exempts from this gate: an unsupported Machine provisioned or imported into an _Off_ locker is reported to the emulator by a KLEE unsupported-Metadata exception, and every later, non-exempt access to the locker by a KLEE locker-Off exception (<<Zkl-ISA-unpriv.adoc#KLEE-error-architecture>>).

The relative order of the standard exceptions is that of the Privileged Specification, reproduced for reference only; the load/store address breakpoint and the load/store faults are evaluated per component access, because the component addresses of a KLEE memory instruction are determined from the state of the KLEE unit.

The `medeleg` and `hedeleg` bits of all KLEE exception causes are read-only zero: KLEE exceptions are never delegated below M-mode.
// Those corresponding to KLEE unsupported-Metadata exception,
// KLEE fatal-error exception, KLEE missing-CSK exception and KLEE locker-Off exception  KLEE out-of-memory exception, KLEE privilege-violation exception and unconfigured-KLIOBUF exception are writable wherever `medeleg`, resp. `hedeleg`, is implemented, so that these causes can be delegated to S-mode and, with the H extension, to VS-mode.

// [NOTE]
// ====
// KLEE memory instructions are allowed to trap so that implementations have more
// flexibility when loading/storing large KLEE contexts, for instance implementing
// by trapping-and-emulating.
// The hardware then raises an illegal-instruction exception for the emulated instruction, before any condition of this table is evaluated (<<KLEE-extensions-overview-unpriv>>). An M-mode emulator of a KLEE instruction reproduces this table in full: it evaluates the `Smstateen` bits, the `KLS` fields, the CSK state and the `*llockerstatus` gates, then the second-group grounds and the remaining conditions, in this order, sets the `*llockerstatus` and `KLS` fields the instruction would set, and raises or forwards the resulting exception as the hardware and the M-mode handler would.
// ====

== CSRs

KLEE extends `*status` and `misa`, and provides three direct CSRs (six on RV32, counting the
high shadows) and up to 14 indirect CSRs (28 on RV32).

[[KLEE-CSRs-priv]]
.KLEE Privileged CSRs.
[cols="^12%,^12%,<26%,<50%"]
[float="center",align="center",options="header"]
|===
| Address     | Privilege  | Field                     | Description
| 0xXXX       | MRW        | `mllockerstatus`              | Per-locker dirtiness and accessibility tracking below M-mode; supports on-demand locker loading
| 0xXXX       | MRW        | `mllockerstatush`             | RV32 only: Shadow of the top 32 bits of `mllockerstatus`
| 0xXXX       | SRW        | `sllockerstatus`              | Per-locker dirtiness and accessibility tracking below S-mode; supports on-demand locker loading
| 0xXXX       | SRW        | `sllockerstatush`             | RV32 only: Shadow of the top 32 bits of `sllockerstatus`
| 0xXXX       | HRW        | `vsllockerstatus`             | Per-locker dirtiness and accessibility tracking below VS-mode; supports on-demand locker loading
| 0xXXX       | HRW        | `vsllockerstatush`            | RV32 only: Shadow of the top 32 bits of `vsllockerstatus`
| (Indirect)  | MRW        | `mklcsk{0..7}`           | KLEE Context Sealing Key.  CSRs "4" to "7" are RV32 only.
| (Indirect)  | MRW        | `mklphysbootscrt{0..3}`  | Locality: Physical (host) Boot Session Secret. CSRs "2" and "3" are RV32 only.
| (Indirect)  | HRW        | `hklvirtbootscrt{0..3}`  | Locality: Virtual (guest) Boot Session Secret. CSRs "2" and "3" are RV32 only.
| (Indirect)  | MRW        | `mkllocality{0..3}`      | Locality: Mutually isolate processes below M-mode. CSRs "2" and "3" are RV32 only.
| (Indirect)  | HRW        | `hkllocality{0..3}`     | Locality: the hypervisor's tag on its virtual machines, separating them from each other. CSRs "2" and "3" are RV32 only.
| (Indirect)  | SRW        | `skllocality{0..3}`      | Locality: Mutually isolate the OS's processes. CSRs "2" and "3" are RV32 only.
|===

On RV32, each of the 64-bit CSRs `mllockerstatus`, `sllockerstatus` and `vsllockerstatus` that is implemented
is accompanied by a 32-bit CSR, `mllockerstatush`, resp. `sllockerstatush`, `vsllockerstatush`,
which accesses bits [63:32]; the CSR itself then accesses bits [31:0].
In this Book, RV32 and RV64 denote an XLEN of 32, resp. 64, in the privilege mode that accesses the CSR; a CSR stated to exist on RV32 only exists for accesses made with an XLEN of 32.

None of these CSRs, the `mklcsk` group included, is available without the KLEE extension, or while a `KLS` field in effect is Off
(<<KLEE-KL-field-in-misa>>, <<KLEE-KLS-field-in-mstatus>>, <<KLEE-KLS-field-VS>>):
an access then raises an illegal-instruction exception, a condition evaluated before the privilege check.
An access from a mode below the privilege of the CSR also raises an illegal-instruction exception.
// and after the `Smstateen` check below, where implemented.
// , except that, as the hypervisor extension prescribes, an access from VS-mode or VU-mode to a CSR that would be accessible in HS-mode, or from VU-mode to a CSR that would be accessible in VS-mode, raises a virtual-instruction exception.
// Where `Smstateen` is implemented, a bit of `mstateen0`, `hstateen0` and `sstateen0` (to be allocated) gates every KLEE instruction and every KLEE CSR, including the identification CSRs, in the modes below the register's own: a clear bit makes the instruction or access raise an illegal-instruction exception (`mstateen0`, `sstateen0`) or a virtual-instruction exception (`hstateen0`), as the `Smstateen` specification prescribes. These exceptions are decided without accessing the KLEE unit, belong to the first group of <<Zkl-ISA-unpriv.adoc#KLEE-illegal-instruction-grounds>>, and are evaluated before every other KLEE condition.

[[KLEE-KL-field-in-misa]]
=== KLEE field in `misa`

{empty}
(((CSR, KLEE field in `misa`)))
Bit `L` (11) of `misa` indicates that the KLEE extension is present; if KLEE is implemented, it must not be read-only zero.

M-mode firmware that provides an emulated KLEE unit can set this bit to 1.
It must not clear `misa.L` without first zeroizing all KLEE state, emulated or in hardware (`kl.clearall` and the CSRs of <<Zkl-ISA-unpriv.adoc#KLEE-out-of-reset-unpriv>>); while `misa.L` is clear, the KLEE state is inaccessible, and need not be retained.

// [WARNING]
// ====
// This allocation is provisional and has not been agreed with the RISC-V Architecture
// Review Committee. Presence of KLEE may instead be discovered by other mechanisms, in
// particular the unified discovery mechanism, which is the direction RISC-V has taken for
// recent extensions and which does not consume a `misa` bit; bit `L` (11) may also be
// allocated to another extension. Implementers should expect this subsection to change, and
// should not treat `misa.L` as a stable interface until the question is settled.
// ====

// ////////////////////////////////////////////////////////////////////

[[KLEE-KLS-field-in-mstatus]]
=== KLEE Context Status in `mstatus` and `sstatus`

{empty}
(((CSR,KLS field in mstatus)))
(((CSR,KLS field in sstatus)))
`mstatus`[26:25] holds a KLEE context status field, `KLS`, shadowed in `sstatus`[26:25].
Defined like the floating-point and vector context status fields `FS` and `VS`,
it tracks the dirtiness of the lockers, of the KLIOBUF and of every writable KLEE-specific CSR other than the `mklcsk` group.
`mstatus.KLS` is always in effect; when V=1, the `vsstatus.KLS` field of <<KLEE-KLS-field-VS>> is
in effect as well.

// [WARNING]
// ====
// The choice of `mstatus`[26:25], and of the corresponding bits of `sstatus` and
// `vsstatus`, is provisional and has not been agreed with the RISC-V Architecture Review
// Committee. Those bit positions are contested by other extensions, and KLS may end up at a
// different offset, in a different register, or be carried by a mechanism other than a
// `*status` context-status field. Nothing in this specification depends on the particular
// offset: only on there being a two-bit context-status field with the semantics of
// <<KLEE-aces-encoding>>, defined analogously to `FS` and `VS`.
// ====

[[KLEE-aces-encoding]]
.Encoding of the `KLS` field
[float="center",align="center",width="100%",cols="^8%,<8%,<84%",options="header"]
|===
|Value |Name |Meaning
|   0   | Off     | KLEE disabled. The KLEE state is inaccessible: KLEE instructions, and KLEE CSR accesses other than reads of the identification CSRs of <<Zkl-ISA-unpriv.adoc#KLEE-CSRs-unpriv>>, raise an illegal-instruction exception.
|   1   | Initial | KLEE enabled. Every locker is _Unconfigured_, and every other state tracked by the field holds its reset value. The hart may issue any KLEE instruction.
|   2   | Clean   | KLEE enabled. The state tracked by the field is potentially different from its reset value, but matches the last context swap.
|   3   | Dirty   | KLEE enabled. At least one locker, KLIOBUF, or KLEE-specific CSR may have changed since the last context swap.
A locker that was configured and is now _Unconfigured_ also makes `KLS` Dirty, since context-switch code must erase its stale saved state.
|===


The following holds for every `KLS` field, in the privilege modes in which it is in effect:

* If a field in effect is Off, every KLEE instruction, and every access to a KLEE CSR other than a read of the identification CSRs (<<Zkl-ISA-unpriv.adoc#KLEE-CSRs-unpriv>>), raises an illegal-instruction exception.
* Where none is Off, an instruction that modifies KLEE state sets every field in effect to Dirty.
  So does a software write to a `*llockerstatus` CSR or to a Locality CSR; context-restoring software therefore writes `KLS` after those CSRs.
* An implementation may set a `KLS` field, or a `*llockerstatus` field, to Dirty from Initial or Clean at any time, even without a state change.
  Setting a field to Dirty is not a change of KLEE state for the state change rule for exceptions of <<Zkl-ISA-unpriv.adoc#KLEE-error-architecture>>.
* The `*llockerstatus` and `KLS` fields that an instruction sets to Dirty are set before any trap is taken on or after that instruction, and before any later instruction executes, including when the instruction continues in the background (Rule <<Zkl-ISA-unpriv.adoc#KLEE-IRR-long-running-no-data>>) or is discarded and restarted (Rule <<Zkl-ISA-unpriv.adoc#KLEE-IRR-uninterruptible-instructions>>).
* While a field is Dirty, the `SD` bit of the register holding it is 1; otherwise that `SD` is set in accordance with the existing specifications.

A hart that implements the KLEE Privileged Architecture, and whose `misa.L` is writable, implements the `KLS` field in every `*status` register it implements.
The field is present and writable while `misa.L` is clear, like `FS` and `VS`; an emulated KLEE unit relies on this.

NOTE: Precise management of `mstatus.KLS` is an optimization that software may use to reduce context-switch overhead.

A write to a `KLS` field modifies no KLEE state:
setting the field to Off, Initial or Clean does not clear the lockers, the KLIOBUF or the KLEE CSRs,
so any such state change must be explicit, and must precede the write.

[[KLEE-KLS-field-VS]]
=== KLEE Context Status in `vsstatus`

{empty}
(((CSR,KLS field in vsstatus)))
With the H extension, `vsstatus`[26:25] also holds a `KLS` field. When V=1, it is in
effect together with `mstatus.KLS`, and <<KLEE-KLS-field-in-mstatus>> governs both.

NOTE: `mstatus.KLS` and `vsstatus.KLS` are not KLEE context state
for the purposes of state tracking, so a write to `vsstatus.KLS` does not set `mstatus.KLS` to Dirty.

[[KLEE-CSR-llockerstatus]]
=== `mllockerstatus`, `sllockerstatus`, and `vsllockerstatus` for Dirtiness Tracking

{empty}
(((CSR, `mllockerstatus`)))
(((CSR, `sllockerstatus`)))
(((CSR, `vsllockerstatus`)))
The 64-bit registers `mllockerstatus`, `sllockerstatus`, and `vsllockerstatus` track per-locker status, including dirtiness, at all levels below M-mode, S-mode, and VS-mode, respectively.

For each of these three CSRs:::
`*llockerstatus`(__i__) = `*llockerstatus`[2{interpunct}__i__+1:2{interpunct}__i__] is a two-bit field that holds the status of ``K(``__i__``)``, encoded as follows.
+
--
[[KLEE-llockerstatus-encoding]]
.Encoding of the `*llockerstatus` bits
[float="center",align="center",width="100%",cols="^8%,<12%,<80%",options="header"]
|===
| Value | Name           | Behavior
|   0   | Off            | The locker is inaccessible.
|   1   | Initial        | The locker is accessible and in an initial state as defined by software.
|   2   | Clean          | The locker is accessible and its state matches the last context swap.
|   3   | Dirty          | The locker is accessible and its state may not match the last context swap.
|===
--
+
`*llockerstatus` is evaluated after the illegal-instruction grounds that do not require KLEE unit state (the first group of <<Zkl-ISA-unpriv.adoc#KLEE-illegal-instruction-grounds>>), and the KLEE fatal-error and missing-CSK exceptions, but before all other conditions, including the second group of <<Zkl-ISA-unpriv.adoc#KLEE-illegal-instruction-grounds>> and <<Zkl-ISA-unpriv.adoc#KLEE-SGR-gate-order>>. The hardware state of a locker with an _Off_ field in effect is never consulted: conditions that depend on its contents are evaluated only after lazy loading or by the M-mode code that emulates the locker.
+
A KLEE instruction _accesses_ ``K(``__i__``)`` if it names the locker as an operand, directly or through a GPR, or if the instruction is `kl.clearall`. An access to a locker with an _Off_ field in effect raises a KLEE locker-Off exception, except for a `kl.mgmt` opening a provisioning or import, `kl.clear`, `kl.clearall`, and `kl.clone` or `kl.rename` as a destination access. These operations do not depend on the contents of the locker, and set every field in effect for it to _Dirty_, even if it was already _Unconfigured_. However, a `kl.clone`, `kl.rename` or `kl.swap` with identical source and destination performs no operation, raises no KLEE locker-Off exception, and sets no field to _Dirty_ (<<Zkl-ISA-unpriv.adoc#KLEE-instruction-clone>>). An exempted instruction that raises an exception before its zeroizing step likewise sets no field: an instruction replaces _Off_ with _Dirty_ only if it has zeroized or overwritten the locker.
+
A mode whose _Off_ mark has been replaced by _Dirty_ treats the hardware locker as authoritative: a mode that held the authoritative image of the locker for lazy loading discards it, and M-mode, which alone emulates a locker, discards the emulated copy it held for it (<<Zkl-ISA-unpriv.adoc#KLEE-error-architecture>>).
+
`kl.getmd*` on a locker with an _Off_ field in effect traps like any other access. An implementation may return the MDH without trapping only if the result matches what the trap and subsequent restore would have produced.
+
A mode marks a locker _Off_ only while it holds the authoritative image or emulates the locker; the hardware contents of an _Off_ locker are never the sole copy of a CC. A handler that has not yet saved a locker leaves its field _Clean_ or _Dirty_.

For `mllockerstatus`:::
+
--
When the privilege mode is (H)S, VS or U/VU:

* an access to ``K(``__i__``)`` while `mllockerstatus`(__i__) is _Off_ raises a KLEE locker-Off exception; and
* an instruction that modifies ``K(``__i__``)`` sets `mllockerstatus`(__i__) to _Dirty_.

A direct write to `mllockerstatus`(__i__) changes neither `sllockerstatus`(__i__) nor `vsllockerstatus`(__i__), where these are distinct registers (<<KLEE-priv-config-requirements>>).
`mstatus.KLS` is also in effect.
--


For `sllockerstatus`:::
+
--
When the privilege mode is VS, U or VU:

* an access to ``K(``__i__``)`` while `mllockerstatus`(__i__) or `sllockerstatus`(__i__) is _Off_ raises a KLEE locker-Off exception; and
* an instruction that modifies ``K(``__i__``)`` sets `sllockerstatus`(__i__) and `mllockerstatus`(__i__) to _Dirty_.

A direct write to `sllockerstatus`(__i__) changes neither `mllockerstatus`(__i__) nor `vsllockerstatus`(__i__) (if defined).
`mstatus.KLS`, `vsstatus.KLS` when V=1, and `mllockerstatus` are also in effect.
--


For `vsllockerstatus`:::
+
--
`vsllockerstatus` exists only with the H extension.
When V=1, it substitutes for `sllockerstatus`: CSR accesses that would target `sllockerstatus` instead access `vsllockerstatus`, as for `vsstatus` and `sstatus`.

When the privilege mode is VU:

* an access to ``K(``__i__``)`` while any of `mllockerstatus`(__i__), `vsllockerstatus`(__i__) or `sllockerstatus`(__i__) is _Off_ raises a KLEE locker-Off exception; and
* an instruction that modifies ``K(``__i__``)`` sets `vsllockerstatus`(__i__), `sllockerstatus`(__i__) and `mllockerstatus`(__i__) to _Dirty_.

A direct write to `vsllockerstatus`(__i__) changes neither `mllockerstatus`(__i__) nor `sllockerstatus`(__i__) (if defined).
`mstatus.KLS`, `vsstatus.KLS`, `sllockerstatus` and `mllockerstatus` are also in effect.
--

The `*llockerstatus` fields that an instruction sets to _Dirty_ are those in effect, that is those owned by the privilege modes above the one in which it executes; an instruction never writes the field owned by its own mode.

The KLEE locker-Off exception is a single exception cause and is not delegable below M-mode, whichever `*llockerstatus` field is _Off_: when raising it, the hardware does not know which mode holds the authoritative copy of the locker. The M-mode handler examines the fields in effect in the order `mllockerstatus`, `sllockerstatus`, `vsllockerstatus`. If `mllockerstatus`(__i__) is _Off_, it resolves the condition itself, and otherwise forwards the exception to the most privileged mode whose field is _Off_, which owns that field and can write it.
A handler therefore never services a KLEE locker-Off exception for a field it cannot write, and an instruction it issues to resolve the condition is not gated by a higher level's field.

[NOTE]
====
The _Off_ value and the KLEE locker-Off exception provide an architectural hook for on-demand (lazy) locker loading. At context restore, a handler may leave a locker unrestored, set its `*llockerstatus` field to _Off_, and retain the authoritative SCC in memory. A subsequent access from a lower-privileged mode traps with a KLEE locker-Off exception to M-mode, which forwards it to the mode that owns the _Off_ field; that handler then imports the SCC before resuming execution. The architecture defines no separate "`lazy`" state: software that marks a locker _Off_ is responsible for ensuring that the authoritative SCC is restored.
====

[[KLEE-CSR-mklcsk]]
=== `mklcsk` Group

{empty}
(((CSR, `mklcsk`)))
The optional `mklcsk` group consists of XLEN-bit M-mode RW CSRs: eight on RV32, four on RV64.

A write to the __i__-th CSR supplies bits [(_i_+1)·XLEN−1 : _i_·XLEN] of the value that becomes the CSK once the group has been written in full.

This CSR group is accessible in M-mode whenever `KLS` is not Off and `misa.L` is set; any other access raises an illegal-instruction exception.
Out of reset `KLS` is Off (<<KLEE-out-of-reset-priv>>), so M-mode firmware enables `KLS` before it establishes the CSK, and until then the KLEE unit is not usable.

A new CSK becomes active only once every CSR of the group has been written since the previous activation; from the first such write until then, the CSK is _partially written_, and the KLEE unit is unavailable (KLEE missing-CSK exception, <<Zkl-ISA-unpriv.adoc#KLEE-CSK-requirements>>).

// A trap or return that changes the privilege mode to M-mode discards a partial write, so that a CSK is never assembled from the writes of two sequences; a trap taken from M-mode to M-mode does not.
// After a discard, the CSK active before the discarded sequence, if any, is active again.
// One mechanism that ensures this is the following (informative):
//
// * The implementation keeps a per-hart flag for each CSR of the group, initially unset.
// * A write by M-mode firmware to a CSR of the group sets its flag, and the implementation keeps the value written so far.
// * Once all flags are set, the values written replace the old CSK atomically, and the flags are cleared; the new CSK can then be used for cryptographic operations.
// * Any mode change to M-mode clears the flags and discards the partially written value, so that M-mode always begins a configuration attempt from a clean state, and a partial key is never activated.
// * A transition out of M-mode does *not* clear the flags, so an incomplete write sequence is not silently lost: the partially written CSK persists, the KLEE unit stays unavailable, and the next KLEE access from any mode traps with a KLEE missing-CSK exception, notifying M-mode, whose handler can then restart the configuration.
// * Any KLEE unit reset clears the flags and discards the partially written value.
// * While any flag is set, that is while a CSK is partially written, the KLEE unit is unavailable: executing a KLEE instruction, or accessing a KLEE CSR other than those named in <<Zkl-ISA-unpriv.adoc#KLEE-CSK-requirements>>, raises a KLEE missing-CSK exception. Since activation clears the flags, the unit becomes available again as soon as the group has been written in full.

Reading a register of the group returns the corresponding part of the active CSK.

A CSK whose value is `zeros(256)` is unconfigured under every model of <<Zkl-ISA-unpriv.adoc#KLEE-CSK-requirements>>: writing that value in full through the `mklcsk` group discards any established CSK and leaves the unit without a CSK; and whenever a CSK is randomly generated, as under the fourth model, an all-zero output of the RBG is discarded and regenerated.

The KLEE unit is unavailable until a CSK is established (<<Zkl-ISA-unpriv.adoc#KLEE-CSK-requirements>>): at once for a hardwired CSK, and as soon as it has been generated for a boot-generated one.

[[KLEE-CSR-locality-groups]]
=== Locality Secret CSR Groups

{empty}
(((CSR, `mklphysbootscrt`)))
(((CSR, `hklvirtbootscrt`)))
(((CSR, `mkllocality`)))
(((CSR, `hkllocality`)))(((CSR, `skllocality`)))
Each group listed in <<KLEE-locality-csr-groups>> holds one 128-bit Locality Secret
(<<Zkl-ISA-unpriv.adoc#KLEE-locality-indexes>>) in XLEN-bit RW CSRs accessed via Indirect CSR Access: four on RV32 and
two on RV64, the CSRs numbered "2" and "3" existing only on RV32.
A write to the __i__-th CSR of a group sets bits [(_i_+1)·XLEN−1 : _i_·XLEN] of its secret.
An access below the privilege of the group, or in unauthenticated Debug mode, raises an
illegal-instruction exception.
The groups are accessible whether or not a CSK has been established (<<Zkl-ISA-unpriv.adoc#KLEE-CSK-requirements>>): no ordering between CSK and Locality configuration is enforced.

[[KLEE-locality-csr-groups]]

|===
| Group | Locality Secret | Privilege | Present when

| [[KLEE-CSR-mklphysbootscrt,mklphysbootscrt]]`mklphysbootscrt{0..3}` | _PhysBootScrt_ |  M   | `Smklpbootscrt` is implemented.
| [[KLEE-CSR-hklvirtbootscrt,hklvirtbootscrt]]`hklvirtbootscrt{0..3}` | _VirtBootScrt_ |  HS  | `Ssklvbootscrt` and the H extension are both implemented.

Software that exports lockers on behalf of a lower privilege level configures every SW Filter Group register it owns before doing so: an export whose CC names an unconfigured entry yields an SCC that no import accepts (<<Zkl-ISA-unpriv.adoc#KLEE-Localities>>). Before running software not entrusted with the CCs of the virtual machine loaded, a hypervisor writes `zeros(128)`, or a value that no virtual machine uses, to `hkllocality` and `hklvirtbootscrt`.

The Locality CSR groups are readable at their respective privilege levels, and
context-switch software saves and restores them like any other CSR.

[NOTE]
====
`skllocality` is the OS's Locality, separating its processes whether the OS runs at S-mode or at VS-mode; a hypervisor uses its own `skllocality` value for its host processes, swaps it with the guest's value when it enters and leaves the guest, and configures its own value before it saves guest KLEE state (<<Zkl-ISA-unpriv.adoc#KLEE-Localities>>).
`hkllocality` is the hypervisor's tag on its virtual machines: it enters the bindings of every export and import a guest performs, and the hypervisor carries it with the virtual machine.
====

[[KLEE-out-of-reset-priv]]
== KLEE Privileged State out of Reset

This section and <<Zkl-ISA-unpriv.adoc#KLEE-out-of-reset-unpriv>> are the authoritative statement of the KLEE state out of
reset:

. bit `L` of `misa` is 1 if the KLEE unit and the KLEE ISA are at least partially implemented in hardware, and 0 for a purely emulated KLEE unit;
 if this bit is writable, M-mode firmware can set it to 1;
. the `KLS` field of `mstatus` (visible in `sstatus`) and, where implemented, of `vsstatus` is Off;
. the CSK is unconfigured, unless it is hardwired, or shared under the fourth model of <<Zkl-ISA-unpriv.adoc#KLEE-CSK-requirements>>, which the reset of one hart neither clears nor regenerates;
. the entire KLF memory is zeroed;
. `mklphysbootscrt` and `hklvirtbootscrt` are zero;
. `mkllocality`, `hkllocality` and `skllocality` are zero; and
. all fields of `mllockerstatus`, `sllockerstatus` and `vsllockerstatus` are _Initial_.

A KLEE unit reset caused by a fatal condition (<<Zkl-ISA-unpriv.adoc#KLEE-error-architecture>>) differs in items 1, 2 and 6: `misa.L` is unchanged, a `KLS` field that is Off stays Off and every other `KLS` field becomes Dirty, and every `*llockerstatus` field is set to _Dirty_.
