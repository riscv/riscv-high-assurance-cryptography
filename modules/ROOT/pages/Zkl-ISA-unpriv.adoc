[[KLEE-unpriv-intro]]
== Introduction

We introduce here the fundamental concepts around which KLEE is designed.

[[KLEE-concepts]]
=== Fundamental Concepts and Definitions

Cryptographic Context:::
(((Cryptographic Context)))
The *Cryptographic Context* (CC) is the foundation of KLEE.
All cryptographic operations performed by KLEE execute within the constraints defined by a CC.
A CC contains secrets, usually keys, but it is more than just a key container:
it is an indivisible structure consisting of a *Metadata Header* (MDH) and *Content*.
The MDH has a fixed format and specifies which Machine can be used with the secrets, and various optional policies associated with the CC.
(((Cryptographic Context, Metadata Header)))
The Content has a Machine-specific format and holds the secrets and other sensitive material, as well as a representation of the Machine's state.
(((Cryptographic Context, Content)))
The Metadata requires integrity, except for explicitly identified non-authoritative format hints such as _ADSDropped_ and layout-preserving fields that the hint makes semantically inactive; the Content requires both integrity and confidentiality.
These requirements are architecturally enforced by KLEE and by the algorithms it implements.

Cryptographic Locker:::
(((Cryptographic Locker)))
To create CCs, KLEE uses *Cryptographic Lockers* (called also simply _locker_ in the following), per-hart architectural containers that safeguard their contents.
A locker is *provisioned* by writing Metadata and Content into it; this operation binds the latter to form a CC.
There is no store-like instruction to extract the Content of the locker in a manner that compromises its confidentiality.
A CC may be used for cryptographic operations only while resident in a locker.
Only the KLEE unit may access or modify a CC residing in a locker, in accordance with the rules set by the architecture and by the Machine bound to the CC.

Sealed Cryptographic Context:::
(((Cryptographic Context, sealed)))
To support context switching while protecting CCs outside architectural state, a CC may be *exported* from a locker as a *Sealed Cryptographic Context* (SCC)—an encrypted and authenticated representation of a CC that can later be *imported* into a locker. Export and import use a _Context Sealing Key_ (CSK), which may be programmable by M-mode. An SCC sealed under one CSK cannot be imported under a different CSK, providing cryptographic domain separation across spatial and temporal domains.

Machine:::
(((Machines)))
(((Cryptographic Context, object-oriented)))
A *Machine* is a state machine that performs cryptographic operations through the interface defined in this specification.
It can implement one or more cryptographic functions (primitives, modes, protocols).
In the metadata of a locker, it is encoded as 16 bits of information.
KLEE provides a small set of instructions for interacting with these state machines.
These instructions take the 16-bit identifier from the locker's metadata, along with standard RISC-V inputs and outputs such as GPRs, vector registers, and memory. Their semantics depend on the selected Machine. Consequently, a CC in a locker encapsulates Machine-specific behavior, allowing different primitives (e.g., AES-128, AES-256, and SM4) to be used interchangeably in the same modes (e.g., ECB, GCM-SIV, and XTS) without changes to the compiled code. Side-channel-attack-resistant variants are supported transparently.

Usage Control Policy:::
(((Cryptographic Context, usage control)))
(((Cryptographic Context, management operations)))
(((Cryptographic Context, usage operations)))
KLEE distinguishes between CC/locker *management* and *usage* operations.
(((Cryptographic Context, export)))
Management operations include *configuration* (e.g., locker provisioning, SCC import, and cloning), *export* of a locker as an SCC, and *clearing* a locker.
Usage operations include cryptographic operations and state changes.
To prevent denial-of-service scenarios, management operations, in particular configuration operations, are less restricted than usage operations. _Usage Control_ policies restrict only certain CC/locker usage operations.

Localities:::
(((Cryptographic Context, Locality)))
KLEE can bind CCs to *Localities*, i.e., restrict usage to specific devices or device classes, hardware configurations, physical or virtual boot cycles, and process domains at various privilege modes. This binding is achieved by using the Localities as _tweaks_ in the encryption and decryption of SCCs.

[[KLEE-architectural-model]]
=== Architectural Model

KLEE is architected as an interface to an _attached_ unit. KLEE instructions are modeled as messages sent over a tightly coupled coprocessor interface. The KLEE unit receives operations from the issuing hart, executes them independently, and returns results.
This model minimizes hart-side implementation complexity: for instance, software implements the logic for locker configuration instructions, while the KLEE unit implements cryptographic operations.
This allows multiple cores to share a KLEE unit, with separate architectural state for each hart, while minimizing the hardware footprint.

The specification only defines the architectural behavior, not implementation.
KLEE may be integrated into a CPU core or implemented as a distinct hardware unit, with separate architectural state for each client hart, and both approaches will be supported by the same code.

KLEE may be partially or completely emulated in M-mode firmware.
For example, an implementation may perform symmetric cipher operations (cf. <<Zkl-ISA-machines.adoc#KLEE-states-symmetric>>) in the KLEE unit while emulating public-key cryptography (cf. <<Zkl-ISA-machines.adoc#KLEE-ECC>> and <<Zkl-ISA-machines.adoc#KLEE-PQC>>).
Public-key primitives may require very large states. Emulating them in M-mode firmware avoids storing those states in the KLEE unit, provided that the relevant lockers reside in secure memory such as on-chip SRAM reserved to M-mode (see <<KLEE-KLF>> for the requirements of this memory).

Locker state must never be accessible in the clear to any privileged mode except M-mode and authenticated Debug mode.
This forbids KLEE implementations in S/VS-mode or HS-mode.
Instructions and Machines may be emulated only in M-mode.
Trap-and-emulate and on-demand (lazy) SCC import rely on the ``*llockerstatus`` CSRs (cf. <<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>>).

* `kl.setst` (<<KLEE-instruction-setst>>) transitions a CC inside a locker between states of a Machine.

== Programmer-Visible Architectural State

[[KLEE-cryptographic-registers]]
=== Cryptographic Lockers

{empty}
(((Cryptographic Context)))
KLEE defines 32 Cryptographic Lockers, numbered 0 to 31 and denoted `K0`–`K31`.

Lockers are per-hart architectural state, like GPRs or vector registers.

Lockers are not separated by privilege mode: when a hart changes mode, it sees the same set of lockers.

Unlike a conventional register, a locker can be _unconfigured_, meaning it does not contain a CC.

If the extension `Zklind` is not implemented,
a locker is addressed like a conventional register, i.e., via a 5-bit immediate.

If the extension `Zklind` is implemented,
a locker can also be addressed indirectly, via a GPR value; an additional instruction-encoding bit selects the mode.

Independently of `Zklind`, indirect locker addressing is always available for
instructions `kl.clone`, `kl.rename`, and `kl.swap` (<<KLEE-instruction-clone>>).

[NOTE]
====
Indirect locker addressing under `Zklind` implies that locker renaming, while still possible, would significantly increase microarchitectural complexity.
We posit that locker renaming is not expected to be necessary, and may even be detrimental, for KLEE.
First, excluding internal state changes, lockers are redefined far less frequently than GPRs or FP registers, and
conditional situations where a locker may take one key or a different one are uncommon.
Second, speculating on the results of cryptographic operations usually leads to security issues.
====

As described in <<KLEE-concepts>>, the CC in each configured locker consists of a Metadata Header (MDH) and `Content`.
The _i_-th locker is denoted `K(i)`, its MDH `K(i).MDH`, and its content `K(i).Content`.
During provisioning and in derived import/export structures, `K(i).Content` is an array of 128-bit blocks.
During import and export, and in an SCC, this array is partitioned into two consecutive arrays of 128-bit blocks:
`Content1`, the architecturally defined content specified for each Machine in <<Zkl-ISA-machines.adoc#KLEE-Machines>>,
and `Content2`, any implementation-defined content.

[[KLEE-KLF]]
=== The Cryptographic Locker File and Authentication Information

Lockers reside in a dedicated, per-hart _cryptographic locker file_ (KLF), a memory accessible only to the KLEE implementation.
If the implementation is (partially) emulated, only M-mode firmware can access the KLF and an implementation-defined mechanism to access the KLF must be provided.
(((Cryptographic Locker File)))

The KLF guarantees the confidentiality and integrity of its contents, including protection against rollback through any access not explicitly permitted by this specification.
KLF accesses do not require hardware-level hardening against physical side-channel attacks.
However, side-channel-protected implementations of the Machines provided by the KLEE unit must also protect the KLF accesses.

It is recommended that `SCC_KeyDeriv`, `SCC_Encrypt`, `SCC_Decrypt`, and every use of the CSK and of the keys derived from it, be implemented with side-channel protection not weaker than the highest _SCProtection_ level, under the implementation's ordering, that it supports for any Machine.

NOTE: While the KLF, as a memory device, must resist rollback attacks, individual lockers do not have to resist rollback via export and import, and cannot.
While re-importing previous CC states may allow multi-time pad attacks on modes such as CTR, XCTR, and GCM, exploiting this would require a level of control over the target software that typically also implies access to plaintext.
Reuse of an internal random value through re-import or cloning is excluded by Rule <<KLEE-GR-atomic-randomness>>.
Re-importing a previous CC state is also desirable, however. For instance, it allows restarting an operation that failed because a payload was corrupted in transit. Adding and enforcing policies to control resumability and cover every legitimate case would overcomplicate the feature.

Architecturally, the KLF contains:

. An array of 32 128-bit blocks, where the _i_-th entry contains the MDH of `K(i)`.
. An implementation-defined amount of memory that can be dynamically allocated to the various registers. This region contains the
   `Content` sections of all configured lockers.

These two types of information are conceptually distinct, regardless of implementation.
The MDH array is always present and is not subject to allocation, so every locker always holds its MDH, even if only to signal that the locker is not configured.
Only the second part is dynamically allocated and capacity-limited; “KLF capacity” refers only to this part.
A locker that holds only its MDH therefore consumes no KLF capacity.

The amount of KLF capacity consumed by each locker depends on the Machine encoded in the MDH, and it may differ from one locker to another.

Insufficient residual KLF capacity may prevent execution of a configuration instruction.

Capacity is freed by unconfiguring other lockers.

The corruption of a hart's KLF is an unrecoverable error condition.
The KLEE architectural state associated with the hart is then reset (<<KLEE-reset-and-m-mode-only>>), and KLEE exception `kl_exc_fatal` is raised (see <<Zkl-ISA-priv.adoc#KLEE-exceptions>> and <<KLEE-error-architecture>> for the behavior when the Privileged Architecture is not implemented).

A hart reset resets the KLEE state of the hart.
The KLEE implementation must zeroize the KLEE state on power up.
The software stack should also explicitly clear all KLEE state at power down, to cause the implementation to zeroize the contents of all lockers.

The KLEE unit holds three 128-bit registers that hold authentication data (the `SIV`, `IMPQUAL`, and `SIV2`) of the locker being currently managed. These registers are accessed using the `kl.load`, `kl.store` and `kl.mv` instructions, as the leading bytes of the image they transfer (<<KLEE-instruction-mv>>).
They are zeroized by a KLEE unit reset, by `kl.clearall`, and by a `kl.mgmt` that opens an import; the `kl.mgmt` that opens an export of a locker in a Valid State writes `SIV` and, when _AuxDataLen_ {ge} 2, `IMPQUAL` and `SIV2`.

[NOTE]
====
The 128 or 384 bits used to hold `SIV`, `IMPQUAL`, and `SIV2` are allocated per hart and not per locker to reduce their hardware cost.
This prevents concurrent non-clearing management operations in the same code: starting a second operation may overwrite the first operation's in-flight `SIV`, `IMPQUAL`, and `SIV2` values.
In a single process space, multiple such operations require careful coordination such as lightweight threads with KLEE context-switching support or serialization using a mutex.
Clearing and provisioning a locker do not touch `SIV`, `IMPQUAL`, and `SIV2` and are thus not subject to these restrictions.
====

=== Providing Inputs and Outputs

[[KLEE-KLV]]
==== RVV/KLV

KLEE inputs and outputs may use vector registers or an architectural input/output buffer (KLIOBUF)
that can be loaded from and stored to external memory. Both mechanisms may be supported simultaneously.

When vector registers are used, the full V extension is not required. KLEE depends only on a minimal subset, termed _KLV_ (KLEE-subset of V)
(((KLV)))
KLV must be fully opcode-compatible with RVV: code written for KLV executes with identical behavior under V together with `Zvbc`.
The current set of features is:

* Vector registers of at least 128 bits.
* Configuration-setting instructions (`vsetvli`/`vsetivli`/`vsetvl`):
** KLEE does not use vector masking and does not define masked versions of its instructions.
Therefore, KLV only requires tail-agnostic and mask-agnostic configurations, and KLEE operations on vector registers always use a tail-agnostic policy;
Bit 25 of the `kl.exec` instruction encoding is reserved for potential future adoption of masked operations, should a compelling use case arise.
** Support for `LMUL` integer values of 1, 2, 4, and 8;
** A `vsetvl`/`vsetvli`/`vsetivli` requesting a configuration that KLV does not support sets `vtype.vill` and `vl` = 0, as in RVV; a KLEE instruction with a vector operand issued while `vtype.vill` is set raises an illegal-instruction exception.
* Unit-strided vector loads and stores;
* `vmv.x.s` and `vmv.s.x` and the slide instructions `vslideup.v[xi]`, `vslidedown.v[xi]`, `vslide1up.vx`, and `vslide1down.vx`, to insert data into and extract data from vector registers;
* Vector logical operations: `vand.v[vxi]`, `vor.v[vxi]`, and `vxor.v[vxi]` (the immediate variants allow obtaining, for instance, a bitwise NOT); and
* `vclmul.v[vx]` and `vclmulh.v[vx]` from `Zvbc`. They may be implemented as trap-and-emulate.

NOTE: KLEE does not depend on a concept of element.
From a logical point of view, the operations are not performed in the vector unit.
A vector register (group) is seen as a bit string of length `KLLEN` = `VL` * `SEW`, where `VL` is the vector length in effect (`vl`).

Floating-point, fixed-point, and general arithmetic vector operations are not required.

When vector registers are used, KLEE determines the lengths of its operands from `VL*SEW`.
The specific choice of `VL` and `SEW` is irrelevant; for example, `VL` = 2, `SEW` = 64 and `VL` = 4, `SEW` = 32 both define a 128-bit input.
The CPU instruction-decoding side of KLEE uses `VL` and `SEW` to determine how much data to send to the KLEE unit proper, but the KLEE unit itself requires only the product `VL*SEW` (or `kliobuftop`).

==== KLIOBUF

KLIOBUF is an optional architectural input/output buffer that may be used in place of vector registers.

KLIOBUF is not part of the KLF.

Two instructions, `kl.input` and `kl.output`, load and store data from/to the KLIOBUF to/from external memory.
When the KLIOBUF is used, `kl.exec`, `kl.setst` and `kl.mgmt` are used in forms with implicit input and output provided by the KLIOBUF, as described in <<KLEE-usage-input-output>>.

The definition of `KLLEN` for KLIOBUF inputs is given in <<KLEE-CSR-kliobuftop>>.

[[KLEE-Metadata]]
=== Metadata

KLEE recognizes two types of metadata that may be contained in a CC or associated with it.

. A 128-bit _MDH_ that determines the Machine, the type of key, and various usage policies associated with the key.
This information is always present in a CC.
The fields are arranged so that the first 64 bits suffice to determine the length of a PI or SCC.

. An optional 128-bit _Implementation Qualifier_ block, denoted by `IMPQUAL`.
It holds copies of three architectural registers that are the KLEE analogues of the hart's `mvendorid`, `marchid`, and `mimpid` CSRs (see <<KLEE-CSR-impl-ids>>).
This qualifier appears when an SCC has _AuxDataLen_ {ge} 2, including when its implementation-specific content segment has been dropped but its header layout is retained.
An implementation uses it to decide whether it can use the implementation-specific content segment when that segment is present. When _ADSDropped_ = 1, the retained `IMPQUAL` and `SIV2` blocks are non-authoritative layout-preserving values and are ignored.

[[KLEE-Machine-field]]
==== _Machine_ and _MachinePolicy_ Fields

Machines are encoded in a 12-bit field.
Values 0–3071 are architecture-defined.
The list of encodings is maintained by RVI (see <<Zkl-ISA-machines.adoc#KLEE-Machines>>).
The remaining values are available for custom Machines.

For encryption/decryption primitives and modes, the _MachinePolicy_ field indicates whether the CC may be used for encryption (lower bit set), decryption (upper bit set), or both. At least one of the bits must be set.

For asymmetric primitives supporting signatures, the lower bit permits signature generation and the upper bit permits verification. In this case, both bits may be zero.
For a Machine that can perform other operations as well, such as the ECC Machines, a zero field still leaves those operations available. For a Machine that can only generate and verify signatures, such as ML-DSA, it makes no sense to clear both bits, since the locker can then perform neither operation; the value is nevertheless not invalid.

For other primitives, the _MachinePolicy_ field may encode additional Machine identifiers to expand the effective encoding space of the _Machine_ field.

[[KLEE-KeyType-field]]
==== _KeyType_ Field

This field takes the value 0 if the key is given by an explicit value, and 1 if the key is given by a system-specific, 64-bit System Key Identifier (SKID).
Values 2 and 3 are currently reserved: a PI or SCC whose _KeyType_ carries one of them is invalid Metadata (see <<KLEE-MVR-open>>). See <<KLEE-system-keys>>.

If the value is 0, keys are provisioned, exported, and imported by value.

If the value is 1, keys are provisioned, exported, and imported as a System Key Identifier (SKID), except for the all-ones (i.e., `ones(64)`) SKID value.

If the SKID is the all-ones value, the key material is randomly generated when provisioning completes, and the locker's _KeyType_ field is then set to 0, so that the key is thereafter exported by value.
Unless otherwise specified, random generation applies to all keys in a Machine at once.

NOTE: A system key identifier may refer to keys with unrelated purposes on different devices; see <<KLEE-system-keys>>.
The SKS supplies an appropriate _Locality_ (see <<KLEE-Localities>>) during locker provisioning to bind the key to the system (<<KLEE-system-keys>>).

[[KLEE-State-field]]
==== _State_ and _StateExtension_ Fields

The _State_ field is used to track the current state of a locker and of the Machine encoded in its MDH.
Examples include whether the locker is _Unconfigured_, encrypting or decrypting data, initializing a hash function, absorbing data in it, and finalizing the digest,
computing elliptic curve point multiples, generating or verifying signatures, or is in an error state.

The _StateExtension_ field can be used by a Machine to store additional state information, usually orthogonal to the _State_ field, such as whether certain values have been provisioned or computed.

State 0 is the _Unconfigured_ state.  It denotes that the locker is unconfigured.
When a locker is in the _Unconfigured_ state, no other field of the MDH has a meaning and it reads zero.
For instance, there are no Usage Policies, Expiration Dates, or Key Types on _Unconfigured_ lockers.

States 1–55 are called _Complete_.
They include States from 1–47, which are called _Valid_, and
(((KLEE, Machine, error states)))
States 48–55, which are termed _Error States_. The latter are used to report KLEE errors.
State 1 is the _Ready_ state.

(((KLEE, Machine, partial states)))
States 56–63, i.e., the states used during management operations, are called the _Partial States_, and are exactly the States that are neither _Unconfigured_ nor Complete.

[[KLEE-Auxiliary-Data-Section]]
==== _AuxDataLen_ and _ADSDropped_ Fields

The _AuxDataLen_ MDH field records the length of the _Auxiliary Data Section_ (ADS) of the content, a variable-size, implementation-dependent part, as a number of 128-bit blocks. When _ADSDropped_ = 1, it retains the length of the ADS before `Content2` was dropped. Zero means that no ADS is present. The value 1 is invalid. The maximum value is 2^14^-1, corresponding to 262,128 bytes.

If _AuxDataLen_ {ge} 2, a copy of the implementation qualifier from the originating implementation

``{fournbsp}{fournbsp}IMPQUAL := zeros(32) @ klmimpid @ klmarchid @ klmvendorid``

(cf. <<KLEE-CSR-impl-ids>>) is included in the SCC.
These 16 bytes, as well as a separate authentication tag for the ADS, are counted within the length recorded by the _AuxDataLen_ field. The importing implementation uses this value to determine whether the ADS can be used.

Since an ADS contains at least an authentication tag (16 bytes) and the originating implementation qualifier (also 16 bytes), the minimum length is 32 bytes, corresponding to an _AuxDataLen_ value of 2.

_ADSDropped_ is an unauthenticated format hint, ignored when _AuxDataLen_ = 0. When _AuxDataLen_ {ge} 2 and _ADSDropped_ = 1, `Content2` is absent, while `IMPQUAL` and `SIV2` remain as non-authoritative padding so that the `Content1` offset does not change. First-segment authentication clears bit 47 only in its local MDH copy.

Toggling _ADSDropped_ cannot affect `Content1` or any policy. Setting it drops optional `Content2`; clearing it requests second-segment processing, whose failure drops `Content2` without rejecting authenticated `Content1` (<<KLEE-SCC-import>>). Manipulation can therefore cause optional ADS loss or an unsuccessful second-segment attempt, but cannot make unauthenticated `Content2` usable or bypass first-segment authentication.

[[KLEE-UsagePolicy]]
==== _UsagePolicy_ Field

The _UsagePolicy_ field determines which modes are allowed to use the locker.

Bits 0, 1, 2, and 3 of the field, when set, disallow CC usage in U-mode, VS-mode, HS-mode, and M-mode, respectively. Bit 4 grants usage in Debug mode only if set. Bit 0 governs both U-mode and VU-mode, and bit 2 governs S-mode whether or not the H extension is implemented. `mstatus.MPRV` is not considered.

Any bit of this field is ignored if the corresponding mode is not supported or not enabled.

[[KLEE-Localities]]
==== _Locality_ Field

The _Locality_ field identifies 128-bit Locality Secrets (LSs) listed in <<KLEE-locality-indexes>>. The LSs are stored in a (possibly virtual) Locality Secrets Table (LST). Some entries are fixed or configurable only through an implementation-specific, authenticated hardware process. These entries are shared by all KLEE units in the same SoC. The remaining entries are software-programmable, per-hart architectural state.

At SCC export and import, any Locality defined by the _Locality_ field cryptographically binds an SCC to the corresponding _current_ hardware and software environments. This binding ends when the SCC is imported into a locker. If a Locality Secret later changes, a subsequent export binds the SCC to the new value. Software is responsible for preventing unauthorized parties from directly accessing lockers.

<<KLEE-locality-indexes>> lists the architected Localities. Eleven LST entries are defined. Entries 0–5 form the _HW Binding Group_, which binds SCCs to the hardware; entries 6–7 form the _Boot Session Group_; and entries 8–10 form the _SW Filter Group_. For each Locality, the table specifies its LST index, domain (SoC-wide, device-wide, VM-wide, or per-process), configurability, bit-field encoding, and value.

because the requested entry is unconfigured and no later entry of its chain is configured
either — then the Metadata is invalid (see <<KLEE-Metadata-validity>>).

Up to six architected Localities may be active concurrently: up to two from the HW Binding Group; at most one of _PhysBootScrt_ or _VirtBootScrt_; and up to three from the SW Filter Group. The SCC generation and import algorithms described in <<KLEE-CC-management>> enforce the policies associated with these Localities.

[[KLEE-Metadata-locality-interoperability]]
==== Interoperability under _Locality_ configurations

_This section is informative and non-normative._

The SW Filter Group binds an SCC to the software that exports it. The register behind each entry depends on the mode:

[float="center",align="center",width="100%",cols="<40%,<30%,<30%",options="header"]
|===
| Mode of the export or import | Entry 9 (_HLocality_) | Entry 10 (_SLocality_)
| S or U, no H extension | unconfigured | `skllocality`
| VS or VU (V=1) | `hkllocality`, set by the hypervisor for the VM | `vskllocality`
| HS or U with the H extension (V=0) | `hkllocality` of the VM loaded | `skllocality` of the hypervisor
| M | `hkllocality` of the VM loaded (unconfigured without the H extension) | `skllocality`
|===

Five scenarios illustrate this:

Migration between hosts with the H extension.::: The guest's _SLocality_ travels with its VS CSRs, and possibly the _HLocality_ with the identity of the machine, for the destination hypervisor to install before the guest runs; each hypervisor keeps its own `skllocality`. The SCCs of the machine then import on any host with the same CSK.

A hypervisor separates its virtual machines.::: The hypervisor may give each virtual machine a distinct `hkllocality`, which the guest can neither read nor write. A guest that names _HLocality_ binds its SCCs to its machine, so the SCCs of two machines differ even when the guests, cloned from one image, hold the same `vskllocality`.

M-mode separates Supervisor Domains.::: Similarly to the previous scenario, M-mode can cryptographically separate Supervisor Domains by giving them a distinct _MLocality_.

An OS becomes a guest.::: An OS runs on a hart without the H extension and sets `skllocality`. The OS's state and SCCs exported in its memory are cloned into a virtual machine, which resumes under a hypervisor. The OS still writes `skllocality`, now reaching `vskllocality`, so entry 10 keeps its value; entry 9 was unconfigured before cloning and cannot have been named. The SCCs exported before cloning therefore import unchanged, whatever the hypervisor holds in (its) _SLocality_ and _HLocality_, provided the new host has the same CSK (<<KLEE-CSK-requirements>>) and the CCs are not bound to the HW Binding Group, _MLocality_ or _PhysBootScrt_, which exist to prevent such migration; _VirtBootScrt_ was unconfigured too.

A hypervisor saves and restores guest lockers, or hands a CC to a guest.::: At V=0, entry 9 is the `hkllocality` of the machine loaded and entry 10 the hypervisor's `skllocality`. A save and its restore are performed at the same level, so their bindings match. Before saving, the hypervisor configures `hkllocality` for the machine and, if a guest CC names _SLocality_, its own `skllocality`, to which that export is bound; an unconfigured entry makes the restore fail as invalid Metadata. To hand a CC to a guest, the hypervisor provisions it naming _HLocality_: the export at V=0 binds it to the tag of the machine, and the import at V=1 uses the same block. A CC naming _SLocality_ cannot cross levels this way, since entry 10 denotes a different register at each level.

In every mode the three entries denote three different registers; no ordering or exclusivity among `mkllocality`, `hkllocality`, `skllocality` and `vskllocality` is required. Host software running under a hypervisor does not name _HLocality_, whose value follows the virtual machine loaded. The same holds for _VirtBootScrt_, whose register the hypervisor sets for the machine loaded.

[[KLEE-Metadata-expiration-date]]
==== _ExpirationDate_ Field

This field is only in effect if extension `Zklexpire` is supported.

If `Zklexpire` is supported, the KLEE implementation must have access to a secure clock.

If `Zklexpire` is not supported, a non-zero _ExpirationDate_ in a PI or SCC is invalid Metadata (see <<KLEE-Metadata-validity>>).

If the secure clock cannot be read, a locker with non-zero _ExpirationDate_ is treated as expired as soon as a usage-controlled instruction is executed on it.

If non-zero, the 20-bit _ExpirationDate_ field specifies the CC's expiration time as whole hours elapsed since 00:00 UTC on 1 January 2027. The maximum representable time span is approximately 119 years and 7 months. The epoch is UTC so that a CC exported on one device and imported on another expires at the same instant regardless of the local time each observes.

[NOTE]
====
This specification cannot enumerate requirements for a secure clock, as
what constitutes adequacy depends on threat models, platforms, and integration
specifics — a challenge common to all time-dependent security features. As a rule
of thumb: *if a clock is adequate for M-mode security features or an on-SoC TPM, it is adequate for KLEE.*
KLEE imposes no stricter requirements. Crucially, software below M-mode must not be able to set the
clock, as that would allow indefinite extension of a CC's lifetime by moving
time backward.
====

This section is the only authoritative statement in this specification of when the _ExpirationDate_ field is evaluated.

The _ExpirationDate_ field is evaluated normatively at the following points:

* At issue of any `kl.exec`, usage-controlled `kl.setst`, or `kl.derive`.
* For `kl.derive`, both endpoints are checked.
* At every architectural resumption point.

The _ExpirationDate_ of a locker that is not in a Valid State is not evaluated.
A transition to Error State `kl_state_expired` is only triggered when an expired locker is being actively used, while still permitting expired contexts to be cleanly evicted, saved, or unconfigured.

The evaluation of _ExpirationDate_ is performed as follows:

. If _ExpirationDate_ is zero, the instruction may proceed.
. The date from the secure clock is converted to the format of the _ExpirationDate_ field; a reading earlier than 00:00 UTC, 1 January 2027 converts to 0.
. The converted date is then compared to the _ExpirationDate_ itself.
. If the converted value is not smaller than the _ExpirationDate_, the KLEE implementation transitions the locker's _State_ field to Error State `kl_state_expired`.
. Otherwise, the instruction may proceed.

[[KLEE-MachineUse]]
==== _MachineUse_ and _AuxInfo_ Fields

The _MachineUse_ and _AuxInfo_ fields can be used by a Machine to store additional information.
If a field is not used by the Machine, the implementation may use it.
An implementation that does so includes an ADS (<<KLEE-Auxiliary-Data-Section>>) in every SCC it exports with such an implementation-specific value, with a possibly empty `Content2`, that is with _AuxDataLen_ {ge} 2, and _AuxDataLen_ = 2 when `Content2` is empty:
this makes the importing implementation check `IMPQUAL`, and so recognize a value that only the originating implementation can interpret.
Neither field may hold any value from which key material or plaintext can be derived: the MDH is not confidential.

These fields are not checked by the validity conditions of <<KLEE-Metadata-validity>>, not even in a PI: a wrong value is reflected in an error of the Machine that uses the field, and a Machine specification may declare a value that the implementation does not implement unsupported Metadata.
It is up to the rules of the Machine to decide what to do with these fields upon provisioning and, in general, when entering State _Ready_.
Machine specifications may use these fields to pass initialization parameters, for instance ML-DSA
<<Zkl-ISA-machines.adoc#KLEE-PQC-ML-DSA>> uses _AuxInfo_ to define the hash function it uses.

// ////////////////////////////////////////////////////////////////////

[[KLEE-Machine-version]]
==== _Version_ Field

This two-bit field denotes the version of the MDH format.

If _Version_ = 0, then the format is the current version.

The value _Version_ = 1 is used to denote newer revisions of the MDH format.
Additional version information must be encoded in other fields of the MDH.

If _Version_ = 3, the format is system-specific.
System-specific formats are allowed only for import operations.
Import of a system-specific format opens with an MDH whose _Version_ is 3 and whose other fields are those of a KLEE-format MDH (the _declared MDH_). At completion the locker's MDH is the declared MDH narrowed, as in <<KLEE-system-keys>>, by any policy the format carries. The format can only narrow the declared MDH, never widen it. _Version_ is then set to 0 (or 1 in a future version of this specification).

Support for loading system-specific formats is optional.
The resulting lockers can be exported only in the KLEE-specified format.
To prevent loading on different implementations, specific localities may be set, or all information may be stored in the ADS to gate it using `IMPQUAL`.

An implementation may support multiple system-specific formats;
the KLEE specification does not specify how to distinguish between them: this is up to the implementation.

The value _Version_ = 2 is reserved.

A PI or SCC with a _Version_ not supported by the implementation
is invalid Metadata (cf. <<KLEE-Metadata-validity>>).

// ////////////////////////////////////////////////////////////////////

[[KLEE-Metadata-validity]]
==== Validity of Metadata

All _reserved_ bits, as well as bits unused by a given Machine, are zero, unless the implementation uses them as stated for _MachineUse_ and _AuxInfo_ (<<KLEE-MachineUse>>).

Metadata is _unsupported_ when the combination of _Machine_, _MachinePolicy_ and _SCProtection_, or a non-zero _MachineExtension_, is not implemented, or when it holds a value that a Machine specification declares unsupported if the implementation does not implement it, such as the _AuxInfo_ of ML-DSA (<<Zkl-ISA-machines.adoc#KLEE-PQC-ML-DSA>>); a _MachinePolicy_ that the conditions below reject makes it invalid, not unsupported.

A supplied MDH is _invalid_ when at least one of the following conditions is satisfied:

* _Version_ is unsupported;
* _KeyType_ is 2 or 3;
* _Locality_[5:4] is 3, or _Locality_ names an unconfigured Locality Secret (<<KLEE-Localities>>);
* The MDH carries any type of custom value without explicitly expressing _ChipFamScrt_ or _ChipScrt_ in _Locality_ (Rule <<KLEE-GR-custom-locality>>);
* _State_ is not _Unconfigured_ at provisioning;
* _State_ is _Unconfigured_ or 61–63 at import (cf. <<KLEE-State-management>>);
* _State_ is 54 or 55, or _State_ {vvert} _StateExtension_ is any value not supported by the Machine encoded in the MDH; for this condition, every Machine supports the Configuration States 56–60 with any _StateExtension_;
* _State_ is _Expired_ in a PI, SCC, or PCCC when `Zklexpire` is not implemented;
* _ExpirationDate_ is non-zero and `Zklexpire` is not implemented;
* _AuxDataLen_ = 1;
* _AuxDataLen_ is non-zero in a PI or in a PCCC whose Configuration State has base type `pi`;
* _ADSDropped_ is non-zero in a PI or in a PCCC whose Configuration State has base type `pi`;
* _MachinePolicy_ is zero for a Machine that requires at least one set bit in it; or
* A Reserved bit is non-zero.

[horizontal]
[[KLEE-MVR-open, Metadata Validity Rule]]Metadata Validity Rule:: A `kl.mgmt` that opens a provisioning or import on unsupported Metadata raises KLEE exception `kl_exc_unsupported`; on invalid Metadata it transitions the locker to Error State _Invalid_.
These checks are not applied to the short import of an Error-State MDH (<<KLEE-error-state-transfer>>).
The locker also transitions to Error State _Invalid_ when, at completion of provisioning, import or export, the System Key Store does not resolve a SKID other than the all-ones value, or the `Content1` of an SCC whose restored _State_ is a Complete State carries the all-ones SKID.

[[KLEE-Memory-Alignment]]
=== Memory Alignment Constraints

All accesses to the `Content` of a locker have a 16-byte granularity: `kl.load`, `kl.store` and `kl.mv` transfer whole 16-byte blocks, and every offset and length they use, `klstart`, `content_size`, `max_admissible`, `image_size` and `image_end` (<<KLEE-instruction-mv>>), is a multiple of 16 bytes.

The effective address of a `kl.load` or a `kl.store` must be a multiple of 16 bytes.
If it is not, no data is transferred and a load, resp. store, address-misaligned exception is
raised on that address.
A PI or an SCC must therefore be held at a 16-byte aligned address.
For `kl.load` and `kl.store` the conditions are evaluated in this order: the illegal-instruction grounds of both groups and the KLEE exceptions, in the order of <<Zkl-ISA-priv.adoc#KLEE-exception-codes>>; the address breakpoint of the first component access, if any; address-misaligned on the effective address; then, per component access in offset order, address breakpoint, and access, page and guest-page faults. The address-misaligned check is performed also when the transfer window is empty.

`kl.input` and `kl.output` are byte-granular and impose no alignment constraint of their own:
a misaligned effective address behaves as it does for an ordinary load or store on the
implementation.

There are no atomicity requirements for any KLEE memory instruction.

[[KLEE-CSR-impl-ids]]
==== `klmvendorid`, `klmarchid`, and `klmimpid`

{empty}
(((CSR, `klmvendorid`)))
(((CSR, `klmarchid`)))
(((CSR, `klmimpid`)))
`klmvendorid`, `klmarchid`, and `klmimpid` identify the version of the KLEE unit, analogously to the `mvendorid`, `marchid`, and `mimpid` CSRs for the hart.

. Their values out of KLEE unit reset identify the version of the KLEE unit. Software cannot modify these values.

. The `klmvendorid` CSR is a 32-bit read-only register providing the JEDEC manufacturer ID of the provider of the KLEE unit (or 0 if not commercial)

Non-commercial IDs are allocated globally by RVI exactly as for the `marchid` values, while commercial IDs are specific to the `klmvendorid`.
It follows the same encoding as `marchid` in the Privileged ISA.
//(<<machine.adoc#norm:marchid_sz_acc_op>>).

. The `klmimpid` CSR is a 32-bit read-only register that provides a unique encoding of the version of the KLEE unit implementation. This register must be readable in any implementation, but a value of 0 can be returned to indicate that the field is not implemented. The implementation value should reflect the design of the KLEE unit itself and not any surrounding system. An implementation that produces an ADS must report a non-zero `klmimpid`.

//(<<machine.adoc#norm:mimpid_op>>).

[[KLEE-CSR-klmaxiobuflen]]
==== `klmaxiobuflen`

{empty}
(((CSR, `klmaxiobuflen`)))
`klmaxiobuflen` is an XLEN-bit RO CSR that reports the maximum configurable length of the KLIOBUF in bytes.
The value is hardwired and specific to the implementation of the KLEE unit.

If `Zklio` is implemented, `klmaxiobuflen` must be at least 16 bytes and at least as large as the largest basic processing unit (granularity) of any implemented Machine.

If `Zklio` is not implemented, the KLIOBUF does not exist: `klmaxiobuflen` reads as zero, and the CSRs `kliobuflen` and `kliobuftop` are not present.

[[KLEE-CSR-kliobuflen]]
==== `kliobuflen`

{empty}
(((CSR, `kliobuflen`)))
`kliobuflen` is an XLEN-bit URW CSR that programs the KLIOBUF length in bytes for use by `kl.input` and `kl.output`.
Writing this register—even when re-writing the current value—also zeroes the buffer and sets `kliobuftop` to the same length.

When `kliobuflen` is zero, the KLIOBUF is _unconfigured_.
Attempting to execute an operation that expects an input or an output in the KLIOBUF while the latter is unconfigured raises exception `kl_exc_unconfigured_buffer`.

The maximum of `kliobuflen` is `klmaxiobuflen`.

Context switching code must save and restore the contents of the KLIOBUF up to `kliobuflen`.

[NOTE]
====
As per the KLEE Privileged Architecture, the dirtiness of the KLIOBUF is not tracked except as part of the entire KLEE state in `*status`.
Software should set `kliobuflen` to zero once the contents of the KLIOBUF are no longer needed.
Context switching code would then not save and restore the contents of the KLIOBUF.
====

// ////////////////////////////////////////////////////////////////////

[[KLEE-CSR-kliobuftop]]
==== `kliobuftop`

{empty}
(((CSR, `kliobuftop`)))
`kliobuftop` is an XLEN-bit URW CSR that sets the upper bound in bytes of the buffer range used by `kl.input` and `kl.output`.

`kliobuftop` plays for the KLIOBUF the role that `VL` plays in the V extension: it defines the operand length `KLLEN` as `kliobuftop` {times} 8 and the transfer window [0, `kliobuftop`).

// For operations involving the KLIOBUF, `klstart` (cf. <<KLEE-CSR-klstart>>) is the position within that window at which processing starts or resumes, analogously to `vstart`; when `klstart` {ne} 0, the bytes processed are those at offsets [`klstart`, `kliobuftop`).
// Shortening an operand is done by lowering `kliobuftop`, never by raising `klstart`.

The maximum of `kliobuftop` is `kliobuflen`.

Modifying `kliobuftop` does not alter buffer contents. It allows per-operation length adjustments without reconfiguring the KLIOBUF via `kliobuflen`, an expensive operation that clears the buffer and may trigger internal garbage collection. This mirrors the use of `VL*SEW` reconfiguration to supply a partial “last block” or a short IV/nonce to Machines.

A value invalid for a given Machine is checked only when an instruction that uses the KLIOBUF is later issued or restarted, with the outcomes of <<KLEE-usage-input-output>>.

[[KLEE-CSR-klstart]]
==== `klstart`

{empty}
(((CSR, `klstart`)))
The XLEN-bit RW CSR `klstart` records, as a byte amount, the progress of the instructions that _honor_ it:

* `kl.load`, `kl.store`, `kl.input` and `kl.output`: the bytes read or written;
* `kl.exec` processing a multi-block operand, which may be interrupted between blocks: the bytes
  processed;
* `kl.derive`, whose `kl.exec` endpoints advance the source and destination lockers in the same way;
* `kl.mv`, vector and non-vector: the locker transfer point. A vector `kl.mv` also tracks, in
  `vstart`, the corresponding position in the vector register when its operand is multi-block.

KLEE has no intrinsic element length and
no counterparts to the vector crypto extension's Element Group Width (EGW), Effective Element Width (EEW), or Element Group Size (EGS).
KLEE instructions such as `kl.exec` are architecturally decoupled from the operations the KLEE unit performs when they are issued.
Therefore `klstart` is defined as a byte count: progress that is not
byte-structured, such as that of the point multiplications and signature operations of <<Zkl-ISA-machines.adoc#KLEE-ECC>>
and <<Zkl-ISA-machines.adoc#KLEE-PQC>>, is recorded in the _MachineUse_ field instead, as Rule
<<KLEE-IRR-long-running-no-data>> prescribes. Every other instruction leaves `klstart` unchanged,
except `kl.mgmt` and `kl.clearall`, which clear it.

`klstart` is the position within the transfer window at which processing starts or resumes,
like `vstart` in the V extension; for a KLIOBUF operand the window is always
[0, `kliobuftop`-1] (<<KLEE-CSR-kliobuftop>>). Software saves and restores `klstart` across
context switches. The KLEE implementation writes it:

. on a precise halt, with a prefix-complete point of the transfer (<<KLEE-Memory-Model>>): the point
  of progress, or 0 for an asynchronous interrupt in an implementation that selects the restart option of Rule
  <<KLEE-IRR-resumability-options>> for `kl.load`, `kl.store`, `kl.input` and `kl.output`, which
  then transfer the prefix again on re-execution;
. with 0 when an instruction that honors it retires, except for `kl.mv`, which by design advances
  `klstart` by the bytes transferred and keeps the result across instructions, to support
  piecewise transfers (<<KLEE-instruction-mv>>); a vector `kl.mv` tracks its progress within the
  vector register in `vstart`, whose value depends on the chosen element size.

For Forms A–C of `kl.exec`, `klstart` {ne} `vstart` {times} `SEW` / 8 at issue raises an
illegal-instruction exception.

The length of the transfer window is `kliobuftop` for a KLIOBUF operand (with `kliobuflen` non-zero), and `VL` {times} `SEW` / 8 for a vector operand.
The following checks are made in order, after the checks of Rule <<KLEE-SGR-gate-order>> (including the Error State and expiration checks) and after those that make the instruction illegal in the locker's _State_ (Rules <<KLEE-SGR-no-exec-in-ready>> and <<Zkl-ISA-machines.adoc#KLEE-MGR-not-allowed-instructions>>); they do not apply to `kl.mv`, whose vector window is [`vstart`, `vl`-1] in elements and whose `klstart` is a locker offset:

. If the length of the transfer window is invalid for the Machine, the locker transitions to Error State _Invalid_.
. If `klstart` {ge} the length of the transfer window, the window is empty: no check is made on the value of `klstart`,
  and the instruction performs no operation other than writing 0 to `klstart`.
. Otherwise, a `klstart` that is not an interruption point the Machine allows transitions the locker to Error State _Invalid_:
  the unwritten part of the output window is zeroed (Rule <<KLEE-SGR-usage-locker-error-state>>).
  This prevents security vulnerabilities such as the use of a locker in an inconsistent state and the release of plaintext in place of ciphertext.

For the locker-directed transfers `kl.load`, `kl.store` and `kl.mv`, `klstart` is bounded above by
the length in bytes of the serialized image `S` (<<KLEE-instruction-mv>>), determined from the
first 8 bytes of the MDH; each of these instructions states the bound it applies.

An _interruption point_ of a Machine in a given State is a `klstart` value that the Machine
can itself produce on a precise halt in that State: unless the Machine states a coarser or a
different set, the whole multiples of its granularity within the transfer window, or 0
for an asynchronous interrupt in an implementation that selects to restart.

Procedure `process_VLI` (<<Zkl-ISA-machines.adoc#KLEE-process-VLI>>) defines its own, at
the boundaries at which its inner loop is allowed to yield.

Software must not write 0 to `klstart` to force a full restart of `kl.exec` or `kl.derive`
once per-block state effects have been committed (Rule
<<KLEE-IRR-block-iterated-instructions>>).

// ////////////////////////////////////////////////////////////////////

[[KLEE-CSR-klmanagedlocker]]
==== `klmanagedlocker`

{empty}
(((CSR, `klmanagedlocker`)))
`klmanagedlocker` is an XLEN-bit RW CSR, but currently only 6 bits are used.

It contains the number of the currently managed locker, or 32 if no locker is currently being managed.

`klmanagedlocker` is set to 32 when the locker it names is cleared (`kl.clear`, `kl.clearall`, or the zeroizing step of a `kl.mgmt` whose opening then fails), is overwritten as the destination of a `kl.clone` or `kl.rename` from another locker, or transitions to an Error State.
When `kl.rename` or `kl.swap` moves the CC of the locker it names, `klmanagedlocker` takes the number of the locker that receives that CC (<<KLEE-instruction-clone>>).

Otherwise, a KLEE exception raised during a management operation that does not transition the locker to an Error State leaves `klmanagedlocker` unchanged: the handler either resolves the condition or sets `klmanagedlocker` to 32 itself.

Internal values of `SIV`, `SIV2` and `IMPQUAL` are associated with this locker.

Values 33 and above are reserved; writing one leaves `klmanagedlocker` unchanged.

NOTE: The `klmanagedlocker` check that `kl.mgmt` performs (<<KLEE-locker-management>>) detects an accidentally
interleaved management operation. A handler that must manage another locker while one is under management
first saves the currently managed locker, writes 32 to `klmanagedlocker`, performs its operations,
and then restores the exported locker (<<KLEE-state-save-and-restore-order>>).
Writing 32 without completing an export loses the in-flight `SIV`, `SIV2` and `IMPQUAL` values, which the next `kl.mgmt` that opens an import or an export overwrites.

[[KLEE-instructions-detailed]]
== Instructions

This section specifies the semantics and encodings of KLEE's unprivileged instructions.

In every encoding, fields shown with fixed values must hold those values. Any deviation from a fixed value or any unlisted combination of field values is a reserved encoding and raises an illegal-instruction exception (first group of <<KLEE-illegal-instruction-grounds>>).

The notation `K(Xd)` denotes the locker whose index is held in GPR `Xd`.
`Kn|K(Xn)` indicates two alternative encodings: a 5-bit immediate locker index (`Kn`) or a locker number supplied by GPR `Xn`.
In every encoding that offers both, bit `r`, the _locker indexing mode selector_, chooses between them:
`r` = 0 makes the 5-bit register field the locker index itself, `r` = 1 makes it the number of the GPR holding the index.
The exceptions are `kl.load` and `kl.store`, which select with `funct3`, and `kl.clone`, `kl.rename`, `kl.swap` and `kl.derive`, which select with field `R` (<<KLEE-instruction-clone>>, <<KLEE-instruction-derive>>).

`%offset` denotes the sign-extended 12-bit immediate of the instruction: bits [31:20] for `kl.load` and `kl.input` (I-type), and bits [31:25] @ [11:7] for `kl.store` and `kl.output` (S-type). The base register is always in bits [19:15] (`rs1`). The effective address of a transfer is `X[rs1] + sext(%offset)`.
For a multi-byte or resumed transfer that value is the address corresponding to the *first* byte of
the transfer, not to the byte at which the transfer resumes: a byte offset of `klstart` is added to
`X[rs1] + sext(%offset)` to form the restart address.
The correspondence between addresses and transfer offsets is given by each instruction.

//

[[KLEE-general-rules-instructions]]
=== General Rules

The following rules apply to all KLEE instructions, unless expressly stated otherwise.

[horizontal]
[[KLEE-GR-multiple-GPRs,GR1]]GR1:: _Use of multiple GPRs for longer inputs:_ A 64-bit operand is one GPR on RV64 and encoded in a pair `(X[s+1],X[s])` as `X[s+1] @ X[s]` on RV32,
and a 128-bit operand is encoded as `X[s+1] @ X[s]` on RV64 and using a GPR quartet on RV32
as `X[s+3] @ X[s+2] @ X[s+1] @ X[s]`. This holds whether the operand is a source or a destination.
The lowest register number of a pair must be even and that of a quartet a multiple of four;
otherwise an illegal-instruction exception is raised.
A pair or quartet is read, resp. written, as a whole.
Here and in every instruction description, RV32 and RV64 denote an XLEN of 32, resp. 64, in the privilege mode that executes the instruction.

GR2:: _If `X0` is used as a destination or source register, but not to index a locker,_ then
anything written to it is discarded, and it reads as zero. When the lowest register of a
pair or quartet is `X0`, no register of the group is written and the group reads as zero.

[[KLEE-GR-klstart-vstart,GR3]]GR3:: KLEE instructions with vector operands that use `klstart` for resumption update `klstart` and `vstart` simultaneously and independently, each according to its own semantics: both denote the same point of progress, `klstart` counting it in bytes and `vstart` in elements of the width in effect. Neither is derived from the other.
This allows the KLEE unit and the vector unit to work in sync while accessing local information more efficiently, but also to explicitly “desync” the two values in certain contexts (such as in the implementation of nested locker management operations).
+
NOTE: For Forms A–C of `kl.exec` the hardware raises an illegal-instruction exception if `klstart` and `vstart` denote different points (<<KLEE-CSR-klstart>>). `kl.mv` keeps the two independent by design, since its `klstart` is a locker offset that accumulates across instructions while `vstart` tracks the vector register.
+
NOTE: The uninterruptible vector-form instructions (`kl.getmdv`, `kl.restrictv`, Form C of `kl.size` and `kl.avail`, `kl.setst`, and `kl.mgmt`) do not produce `vstart` values and therefore do not consume one (Rule <<KLEE-GR-vector-legality>>).

GR4:: The _UsagePolicy_ of the MDH determines whether a certain instruction can be issued, and sometimes when, in a given privilege mode.
Furthermore, certain instructions may modify the state of the locker.
For all instructions, the authoritative table for these two properties is <<KLEE-instruction-properties>>.
No instruction description restates them.
+
[[KLEE-instruction-properties]]
.State modification and usage control, per instruction
[width="100%",cols="<18%,^14%,^14%,^14%,<40%",options="header"]
|===
| Instruction(s)              | May modify KLEE state | May modify other state | Usage-controlled | Notes

| `kl.load`                   | Yes             | No  | No^*^                | Updates `klstart`.
| `kl.store`                  | Only `klstart`  | Yes | No^*^                | Updates `klstart`.

Rule <<KLEE-GR-opening-locker-when>> is not relaxed to obtain this.

[[KLEE-management-operations]]
=== Provisioning, Import, and Export

_This subsection is informative._

Broadly speaking, and setting aside error handling, *Provisioning* consists of the following three steps:

. Use `kl.mgmt` (<<KLEE-instruction-mgmt>>) to prepare a locker to be provisioned, check the validity of the MDH, and load the entire MDH in the locker.
. Use one or more `kl.mv` (<<KLEE-instruction-mv>>) to load the rest of the provisioning information into the locker.
. Use `kl.mgmt` to complete the provisioning process and make the locker available to software.

*Importing* an SCC into a locker is similar:

. Use `kl.mgmt` to prepare a locker to accept an SCC, check the validity of the MDH, and load the entire MDH in the locker.
. Use one or more `kl.mv` to load the rest of the SCC, the authentication data first, into the locker.
. Use `kl.mgmt` to complete the import process by authenticating and decrypting the SCC, and make the locker available to software.

*Exporting* a locker as an SCC consists of the following steps:

. Use `kl.getmd` or `kl.getmdv` (<<KLEE-instruction-getmd>>) to get the MDH of the locker to be exported, in order to determine its size and allocate resources.
. Store the MDH into memory.
. Use `kl.mgmt` to prepare a locker to produce an SCC. This includes encrypting its contents and computing the authentication tag(s).
. Use one or more `kl.mv` to store the rest of the SCC, the authentication data first, to memory.
. Use `kl.mgmt` to complete the export process by restoring the locker in a form available to software.

A locker in an Error State takes shorter paths in both directions, since it is an MDH and nothing else
(<<KLEE-error-state-transfer>>): its export uses no `kl.mgmt` at all, and its import is a single one.

We also anticipate how the _State_ of a configured locker changes under management:

. If it is not being managed, it is in a Valid State.

. If it is being provisioned from a PI, then its _State_ is `kl_cfg_provisioning`.
.. If this provisioning is preempted before it completes, its _State_ is saved by software,
   and upon export the _State_ becomes `kl_cfg_ppi_exporting`. “`ppi`” means “partial provisioning input”.
.. Upon any further preemption and export, the current _State_ is saved by software in its own process space and
   the state remains `kl_cfg_ppi_exporting`.
.. When the export terminates, the value of the _State_ before the export started is restored by software by passing it to the `kl.mgmt` that completes the export operation.
.. If the locker is re-imported, the value of _State_ is first saved and the locker's _State_ becomes `kl_cfg_ppi_importing`.
.. When such a nested management operation is completed, the previous state is restored.
.. Hence, when the last nested management operation is completed, the _State_ is restored to `kl_cfg_provisioning`.

. If an export operation is initiated from a locker in a Valid State, that _State_ is saved by software, and the _State_ becomes `kl_cfg_exporting`.
.. Nested management operations lead to States `kl_cfg_exporting` and `kl_cfg_importing`.

. If an import operation is started on an SCC generated from a locker in a Valid State: the _State_ becomes `kl_cfg_importing`, and the nested management states are `kl_cfg_exporting` and `kl_cfg_importing`.

The values of these States are given in <<KLEE-SC-sealing-status>>.

[[KLEE-instruction-size]]
=== kl.avail and kl.size

_Synopsis_::
`kl.avail` returns 1 if the Machine encoded in the MDH is available in the requested variant, and 0 otherwise.
`kl.size` returns the total size of a memory buffer that would be needed to store the data of a PI or SCC, in bytes, or 0 in case of error (such as unsupported Machine or invalid MDH).

_Mnemonic_::
+
--
There are three Forms of the `kl.avail/kl.size` instructions:
(((KLEE, instruction, kl.size)))
(((KLEE, instruction, kl.avail)))

[upperalpha]
. `kl.{avail,size}  Xd, Ks|K(Xs)` - Size from a context.
. `kl.{avail,size}  Xd, Xs` - Size from MDH[63:0] in one (RV64) or two (RV32) GPRs.
. `kl.{avail,size}  Xd, Vs` - Size from MDH in one vector register.
--

_Encoding_::
+
--
The encoding shares opcode, `funct3`, and `funct2` (the two msbs of `funct7`) with `kl.exec`, but with bit 27 equal to 1.
Bit 25, `q`, selects the instruction: `q` = 0 is `kl.size`, `q` = 1 is `kl.avail`.

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Xd' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'Ks/K(Xs)/Xs/Vs' },
    { bits:  5, name: 0x0 },
    { bits:  1, name: 'q' },
    { bits:  1, name: 'r' },
    { bits:  1, name: 0x1 },
    { bits:  2, name: 'F' },
    { bits:  2, name: 0x0, attr: ['funct2'] },
]}
....

The `F` field and the `r` bit may assume the following values:

* `F` = `0b00`, `r` = `0` {implies} Form A: Size/availability from a context given as `Ks`.
* `F` = `0b00`, `r` = `1` {implies} Form A: Size/availability from a context given indirectly as `K(Xs)`. Only if `Zklind` is present, otherwise this is an illegal instruction.
* `F` = `0b01`, `r` = `0` {implies} Form B: Size/availability from MDH in one (RV64) or two (RV32) GPRs.
* `F` = `0b10`, `r` = `0` {implies} Form C: Size/availability from MDH in a 128-bit vector register.
--

_Description_:: {empty}
+
--
`kl.avail` (`q` = 1 in the encoding) evaluates only the _Machine_, _MachinePolicy_, _MachineExtension_, _KeyType_ and _SCProtection_ fields of the MDH and returns 1 in `Xd` if that combination is implemented (a non-zero _MachineExtension_ never is), 0 otherwise; no other field is examined, so a 1 does not exclude the `kl_exc_unsupported` that a Machine specification attaches to the value of another field, such as the _AuxInfo_ of ML-DSA, and a locker in the _Unconfigured_ State yields 0.

`kl.size` (`q` = 0 in the encoding) returns in GPR `Xd` the total size in bytes of the memory buffer needed to hold the
external image that the MDH describes: a PI, an SCC, or, for a locker in an Error State, the MDH
alone (<<KLEE-data-formats>>, <<KLEE-length-rule>>). For an SCC the size includes the
authentication tag(s) and the ADS; for a PI it is the size of the entire
PI. Knowing this size is necessary for any feature that relies on exporting a locker, including context
switching.

The three Forms for the two instructions differ only in where the MDH is taken from,
as the mnemonics above give:
from the locker itself for Form A, from bits [63:0] supplied in `Xs` (in `X[s+1] @ Xs` on RV32) for Form B,
and from bits [127:0] supplied in `Vs` for Form C.

Let `content1_size` be the length in bytes of the `Content1` of an SCC for the _Machine_,
_MachinePolicy_, _KeyType_ and _StateExtension_ of the MDH, and `pi_content_size` the length in bytes
of the `Content` of a PI for its _Machine_, _MachinePolicy_ and _KeyType_ (<<KLEE-length-rule>>).
These are two distinct quantities and are not interchangeable.
Let `content2_size` = 16 * (_AuxDataLen_ - 2) if _AuxDataLen_ {ge} 2 and _ADSDropped_ = 0, and 0 otherwise.

`kl.size` is computed as follows:

. If the locker (Form A) is _Unconfigured_, then: 0.
. If the supplied MDH (Forms B and C) is not in an Error State and is unsupported or invalid Metadata (see <<KLEE-Metadata-validity>>), or its _State_ is 61–63, then: 0.
  Form B applies only to bits [63:0]: the fields in bits [127:64] are not examined, since none of them affects the size of any structure (<<KLEE-length-rule>>), and the invalidity conditions on them, including Rule <<KLEE-GR-custom-locality>>, are not applied.
. If the MDH._State_ is an Error State, then: 16.
. If the MDH._State_ is a Valid State or `kl_cfg_{importing|exporting}`, then:
  ..  If _AuxDataLen_ = 0, then: 32 + `content1_size`.
  ..  If _AuxDataLen_ {ge} 2, then: 64 + `content1_size` + `content2_size`. The 64-byte fixed part includes `IMPQUAL` and `SIV2` even when _ADSDropped_ = 1.
. If the MDH._State_ is `kl_cfg_provisioning` or `kl_cfg_ppi_{importing|exporting}`, or, for a supplied MDH, _Unconfigured_ (the MDH of a PI), then: 16 + `pi_content_size`.
--

[[KLEE-instruction-exec]]
=== kl.exec

_Synopsis_::
Perform a cryptographic operation in the KLEE unit.

_Mnemonic_::
+
--
The `kl.exec` instruction admits four Forms, namely
(((KLEE, instruction, kl.exec)))

[upperalpha]
. `kl.exec  Vd, Kn|K(Xn), Vs2` {nbsp} takes an input vector and writes to an output vector.
. `kl.exec  {fournbsp} Kn|K(Xn), Vs2` {nbsp} takes an input vector but does not write to an output vector.

. `kl.exec  {fournbsp} Kn|K(Xn) {fournbsp}{nbsp}` {nbsp} does not take an input vector and does not write to an output vector.
--

_Encoding_::
`kl.exec` is an R-type instruction.
+
--
[wavedrom, , svg]
....

{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'rd', attr: ['Vd','—','Vd','—'] },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: "'rs1' (n)", attr: ['Kn|K(Xn)'] },
    { bits:  5, name: 'rs2', attr: ['Vs2','Vs2','—','—'] },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'r' },
    { bits:  1, name: 0x0 },
    { bits:  2, name: 'Form', attr: ['0    0','0    1','1    0','1    1'] },
    { bits:  2, name: 0x0, attr: ['funct2'] },
]}
....

For the four Forms A–D above, the encodings are:

[upperalpha]
. `Form` = `0b00`.
. `Form` = `0b01` and `rd` = `0b00000`.
. `Form` = `0b10` and `rs2` = `0b00000`.
. `Form` = `0b11` and `rd` = `rs2` = `0b00000`.

The locker operand is always encoded in `rs1`. In each Form, unused register fields must be zero: `rd` when there is no output vector, and `rs2` when there is no input vector. Non-zero values in an unused field are reserved, except for encodings assigned to those fields by `Zklmv` (<<KLEE-instruction-mv>>).

`r` is the locker indexing mode selector. Indirect locker addressing is only available when `Zklind` is present. Otherwise, `r` = 1 is an illegal instruction.
--

_Description_::
+
--
Performs a cryptographic operation as defined by the Machine in locker `Kn` or `K(Xn)`.
The instruction may take an input and produce an output.
When it performs no operation on a locker in an Error State or an expired locker, or transitions the locker to an Error State, it zeroes the unwritten part of its output window instead of producing output (Rule <<KLEE-SGR-usage-locker-error-state>>).

In Form A, `Vd` and `Vs2` may be the same register group; any other overlap is reserved.
With `Vd` = `Vs2`, for an operation whose output blocks have the length of its input blocks, each block's output replaces its input at the same offset; for any other operation `Vd` = `Vs2` raises an illegal-instruction exception (<<KLEE-illegal-instruction-grounds>>).

If `Zklv` is not implemented, only Form D `kl.exec`
is supported, Forms A–C raise an illegal-instruction exception, and `kl.input`, `kl.output` are used to provide inputs and
extract outputs from `kl.exec`, as described in <<KLEE-usage-input-output>>.
--

[[KLEE-instruction-mv]]
=== kl.mv

// The `Zklmv` subextension adds dedicated move instructions between scalar/vector registers and a locker.
// The instructions in this extension are encoded as new forms of `kl.exec`:
// `r` is the locker indexing mode selector. Indirect locker addressing is only available when `Zklind` is present. Otherwise, `r` = 1 is an illegal instruction.

_Mnemonics_::
+
--
The `kl.mv` instruction admits the following variants:
(((KLEE, instruction, kl.mv)))

[upperroman]
. `kl.mv  Kd|K(Xd), Xs2` copies 128 bits of content from two or four GPRs into a locker.
. `kl.mv  Kd|K(Xd), Vs2` copies one or more 128-bit blocks of content from a vector register into a locker.
. `kl.mv  Xd,  Ks1|K(Xs1)` extracts 128 bits of content from a locker into two or four GPRs.
. `kl.mv  Vd,  Ks1|K(Xs1)` extracts one or more 128-bit blocks of content from a locker into a vector register.
--

_Encodings_::
+
--
The hart adds the following encodings to the Forms B and C of `kl.exec`. As throughout
`kl.exec`, the locker operand is encoded in `rs1`. The sub-opcode occupies the register field that the
corresponding Form of `kl.exec` leaves unused: `rd` in Form B, `rs2` in Form C.

[upperroman]
. `kl.mv  Kd|K(Xd), Xs2`   is encoded as `Form` = `0b01` and `rd` = `0b00001`.
. `kl.mv  Kd|K(Xd), Vs2`   is encoded as `Form` = `0b01` and `rd` = `0b00010`.
. `kl.mv  Xd,  Ks1|K(Xs1)` is encoded as `Form` = `0b10` and `rs2` = `0b00001`.
. `kl.mv  Vd,  Ks1|K(Xs1)` is encoded as `Form` = `0b10` and `rs2` = `0b00010`.

`rs1` always specifies the source or destination locker. In Forms I and II, `rs2` specifies the source GPR or vector register.
In Forms III and IV, `rd` specifies the destination GPR or vector register.
For Forms II and IV, the vector length must be a multiple of 16 bytes.

`r` is the locker indexing mode selector. Indirect locker addressing is only available when `Zklind` is present. Otherwise, `r` = 1 is an illegal instruction.
--
//
// In the mnemonics of variants A and B the locker is written first because it is the
// destination of the move; it is nonetheless encoded in `rs1`, not in `rd`.

_Description_::
+
--
In each variant of the instruction the locker is the one named by `rs1`.

`kl.mv` is never used on a locker in an Error State (Rule <<KLEE-SGR-error-state-locker-is-only-MDH>>, <<KLEE-error-state-transfer>>).

`kl.mv` does not transfer the MDH, which is carried by `kl.mgmt` and `kl.getmd*`.
The authentication fields `SIV`, `IMPQUAL` and `SIV2` are the leading bytes of the image they transfer, and are held in the three internal per-hart registers of <<KLEE-KLF>> while the locker is under management.

This instruction requires that the locker be ready to accept information (being either provisioned or imported)
or output its contents (being exported).
If the locker's _State_ is not one of the States admitted by Rules <<KLEE-SGR-zkl-load-mv-allowed>> and <<KLEE-SGR-zkl-store-mv-allowed>> — which excludes every Complete State and the _Unconfigured_ State — or `klstart` is not a multiple of 16, an illegal-instruction exception is raised.

For provisioning or import, the instruction also requires that the MDH has already been loaded by the `kl.mgmt` that opened the locker for provisioning or import (<<KLEE-instruction-mgmt>>).

Let `content_size` be the length in bytes of the serialized `Content` of the locker, namely the `Content` of a PI or an SCC,
according to the base type of the image the locker holds (<<KLEE-length-rule>>).
`content_size` is determined by `kl.mv`, from the `MDH` – either the `MDH` of the locker being exported, or the `MDH` provided by the caller for provisioning or import.

The instruction needs to know a _ContentOffset_ value of 0, 16, or 48, to signal the start of the `Content` in the external formats depending on the MDH, the current operation, and the base type of the image the locker holds (<<KLEE-length-rule>>).
Let `content2_size` = 16 * (_AuxDataLen_ - 2) if _AuxDataLen_ {ge} 2 and _ADSDropped_ = 0, and 0 otherwise.

_ContentOffset_ is determined as follows:
// the same case distinction of `kl.size` (<<KLEE-instruction-size>>) but excluding the `Content` and the MDH._ADSDropped_ never affects _ContentOffset_.

. If the MDH._State_ is a Valid State or `kl_cfg_{importing|exporting}`, then:
  ..  If _AuxDataLen_ = 0, then: 16.
  ..  If _AuxDataLen_ {ge} 2, then: 48.
. If the MDH._State_ is `kl_cfg_provisioning` or `kl_cfg_ppi_{importing|exporting}`, then: 0.

The _serialized image_ `S` of the locker is `Content`, `SIV {vvert} Content`, or `SIV {vvert} IMPQUAL {vvert} SIV2 {vvert} Content` for _ContentOffset_ = 0, 16, or 48, respectively, and
`image_size` = _ContentOffset_ + `content_size`, which is the value `kl.size` reports minus 16.

Let `max_admissible` be the length of the longest image of the locker's current base type that the implementation can hold for the Machine: for an image with an SCC base type, `content1_size` plus the largest `content2_size` the implementation supports (<<KLEE-instruction-size>>); for an image with a PI base type, `pi_content_size`. When _ADSDropped_ = 1, `content2_size` is zero, so no `Content2` byte is part of the image. Bytes of an SCC beyond `max_admissible` belong to an ADS that is discarded (<<KLEE-SCC-import>>) and are neither read from memory nor written to the locker.
Let

{fournbsp}{fournbsp}``image_end`` = _ContentOffset_ + `min(content_size, max_admissible)`.

Offsets of `S` at or beyond `image_end` hold no locker data; they read as zero through every architectural access.

`kl.mv` transfers whole 128-bit blocks, never a part of one, and each block the variant would transfer lies either wholly below `image_end` or wholly at or beyond it.

* A block at an offset below `image_end` is transferred.
* A block at an offset at or beyond `image_end` is not: no locker byte is written for it; the destination
  GPR operand, resp. the corresponding elements of `Vd`, are written with zero; and `klstart` does not advance past `image_end`.
* If `klstart` {ge} `image_end`, the locker-writing variants write nothing; the locker-reading variants write their
  destination GPR operand, resp. every element of `Vd` from `vstart` to `vl` − 1, with zero; in all variants
  `klstart` is unchanged.

For each 16-byte block transferred by `kl.mv`, `klstart` advances by 16 bytes.
In vector variants, `vstart` is also used, to track progress in vector elements: for instance each 16-byte block advances `vstart` by 4 for 32-bit elements or by 2 for 64-bit elements.
If a vector transfer is interrupted, `klstart` records the total number of bytes transferred, and `vstart` identifies the first untransferred vector element for resumption.
Element _k_ of the vector operand, for _k_ from `vstart` to `vl` − 1, corresponds to byte offset `klstart` + (_k_ − `vstart`) × `SEW`/8 of the serialized image `S`.
If `vstart` {ge} `vl`, the instruction performs no operation and leaves `klstart` unchanged.
Writes to, resp., reads of, an offset at or beyond `image_end` are ignored, resp., read as zero.

The four variants are displayed in the following table.
For all variants, if the locker's _State_ is not one of the values in the fourth column of its row,
an illegal-instruction exception is raised. A vector variant for which `vl * (SEW/8)` is not a multiple of 16 raises an illegal-instruction exception; the V-enabled check is performed first. `vstart` must likewise point to a multiple of 16 bytes: a vector variant for which `vstart * (SEW/8)` is not a multiple of 16 raises an illegal-instruction exception.

[[KLEE-instruction-setst]]
=== kl.setst

_Synopsis_::

_Mnemonic_::

(((KLEE, instruction, kl.setst)))
+

--
[wavedrom, ,svg]

{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },

[upperalpha]

. `F` = `0b01`.
. `F` = `0b10`.
. `F` = `0b11`.

_Description_::
+
--
The instruction is used to advance the Machine expressed in the locker `Kd` or `K(Xd)`
from one stage to another – for instance, from initializing a hash
function to absorbing data and finalizing the digest. The reached State is normally
the one expressed in `#immed7`, but some States transition automatically to another
State when the instruction completes. The allowed transitions are given in <<KLEE-State-management>> and in the specification of each Machine.

`kl.setst` may also set state information orthogonal to those stages,
possibly as a prerequisite for entering another State.

The following categories of values for `#immed7` apply to all Machines:

* 0 (`kl_state_unconfigured`) clears the locker, in any Form; an auxiliary operand is ignored.
* 1–55 name a _State_ a locker can transition to:
** Values 1–47 are called _Valid_ States.
   Value 1 is called _Ready_ and it is the starting state of any freshly provisioned locker.
   46 and 47 correspond to _Success_ and _Failure_ of the Machine, respectively, and cannot be set directly.
   _Failure_ is an outcome, not an error.
** Values 48–55 are the Error States, used to report KLEE errors (<<KLEE-states-error>>); 54 and 55 are reserved, and so is 53 if `Zklexpire` is not implemented.
   An Error State is accepted as `#immed7` in any State.
   With an Error State as `#immed7`, a locker in a Complete or Partial State transitions to it
   (a reserved one to _Invalid_) _without raising an exception_, even where reaching that State implicitly would
   raise one, and later usage of the locker performs no operation (Rule <<KLEE-SGR-usage-locker-error-state>>).
   On a locker in the _Unconfigured_ State the instruction performs no operation: only the short import
   of <<KLEE-error-state-transfer>> configures a locker directly into an Error State.
* 56–63, i.e., when the top four bits of `#immed7` are `0b0111`, encode `kl.mgmt` (<<KLEE-instruction-mgmt>>).
* 64 encodes `kl_cfg_clear_ads` (<<KLEE-instruction-clearads>>).
* 65–127 are Machine-defined and may change other state information, such as _StateExtension_.

Any other `#immed7` that the architecture or the current Machine does not support transitions the locker to
Error State _Invalid_. Some values require an auxiliary operand of 64 or 128 bits, in one or more
GPRs or in a vector register (group) `Vs`.
--

[[KLEE-instruction-clear]]
==== kl.clear

The instruction `kl.clear Kd` is encoded as `kl.setst` (see <<KLEE-instruction-setst>>) with no auxiliary operands and the `#immed7` equal to `kl_state_unconfigured` (as defined in <<KLEE-State-field>>).
It marks the locker as _Unconfigured_ in its metadata, and releases its resources in the KLF.

Clearing (i.e., unconfiguring) a locker that was not already _Unconfigured_, or whose `*llockerstatus` field in effect is _Off_ (<<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>>), sets the `*llockerstatus` fields in effect for the current privilege mode, and the `KLS` fields in effect, to _Dirty_. The locker's own _State_ field becomes _Unconfigured_.

[[KLEE-instruction-clearall]]
==== kl.clearall

The instruction `kl.clearall` unconfigures all the lockers, as if calling `kl.clear` on each one, and the KLIOBUF, zeroing the buffer and setting
`kliobuflen`, `kliobuftop` and `klstart` to 0, zeroizes the three authentication registers of <<KLEE-KLF>>, and writes 32 to `klmanagedlocker`.

`kl.clearall` is encoded with `r` = `1` and `rs1` = `rd` = `0`.

[[KLEE-instruction-clearads]]
==== kl.clearads

The instruction `kl.clearads Kd|K(Xd)` clears any ADS from the target locker `Kd` or `K(Xd)`.

This instruction is encoded as `kl.setst` (see <<KLEE-instruction-setst>>) with no auxiliary operands and the immediate for _State_ set to `kl_cfg_clear_ads`, i.e., the value 64.

`kl.clearads` deletes any ADS from the target locker.
This instruction is used when exporting a locker for use by some other target, possibly some different implementation.
_AuxDataLen_ and _ADSDropped_ are set to 0. The operation therefore produces a more compact layout without ADS that a destination with a different KLEE unit may have to drop anyway.
Exporting a locker into an SCC in this state will result in an ADS-free SCC being generated.
The first usage instruction that needs to access the ADS regenerates it.

[[KLEE-instruction-mgmt]]
=== kl.mgmt

_Synopsis_::
Open or complete a management operation on a locker.

_Mnemonic_::
The `kl.mgmt` instruction is a separate instruction and admits only Forms A, C, and D of `kl.setst`.
(((KLEE, instruction, kl.mgmt)))

//

_Encoding_::
`kl.mgmt` is an R-type instruction with the encoding of `kl.setst` (<<KLEE-instruction-setst>>) and `#immed7`[6:3] = `0b0111`, that is, `#immed7` in 56–63.

_Description_::
+
--
The instruction brackets the body of a locker management operation (<<KLEE-management-operations>>):
it opens a provisioning, an export or an import on the locker `Kd` or `K(Xd)`,
and completes it.
Like `kl.setst` it changes the _State_ of the locker, but with different semantics,
so it is a separate instruction.
The State reached depends on the previous State of the locker as well as on `#immed7`.

Besides a management command expressed in the `#immed7`,
`kl.mgmt` receives an MDH for two purposes: to decide which variant of the operation to perform,
which may also modify the MDH of the locker, and, when completing an import or an export, to restore
the _State_ the locker had when the operation started from a copy saved by the caller.

The following values of `#immed7` apply (<<KLEE-management-immeds>>):

* 56 (`kl_cfg_provisioning`), 57 (`kl_cfg_exporting`) and 58 (`kl_cfg_importing`) open a
  provisioning, an export and an import, respectively. For 56 and 58 the instruction receives the
  MDH of the locker, as the Forms below supply it, and changes _State_ only after loading it.
* 59–62 are reserved. _State_ takes 59 and 60 only as the result of a `kl.mgmt` with 57 or 58.
* 63 (`kl_cfg_management_end`) completes the current management operation.

The MDH is supplied as follows:

* Form A carries no auxiliary operand. Where the operation requires the MDH, Form A is a
  substitution (<<KLEE-usage-input-output>>) and reads it from bytes [0, 16) of the KLIOBUF,
  ignoring `klstart`. After the `klmanagedlocker` check and before any change to the locker, Rule
  <<KLEE-GR-iobuf-configured>> applies and, with the KLIOBUF configured, `kliobuftop` < 16 raises
  an illegal-instruction exception (Rule <<KLEE-GR-vector-MDH-operand>>).
* Form C carries the MDH in the lowest 128 bits of `Vs`.
* Form D carries the MDH as a 128-bit operand in two or four GPRs starting at `Xs` (Rule
  <<KLEE-GR-multiple-GPRs>>).

Form B is a reserved encoding (<<KLEE-illegal-instruction-grounds>>).

The precise semantics of each operation are given in <<KLEE-locker-management>>.
--

On RV32:

* The destination is the GPR pair `X[d+1] @ X[d]` for `kl.getmdl`, the GPR quartet `X[d+3] @ X[d+2] @ X[d+1] @ X[d]` for `kl.getmd`.

The instruction does not check the validity of the MDH according to the rules in <<KLEE-Metadata-validity>>.

[[KLEE-instruction-getst]]
==== kl.getst, kl.getstx

The pseudo-instructions
(((KLEE, instruction, kl.getst)))
`kl.getst Xd, Ks|K(Xs)`
(((KLEE, instruction, kl.getstx)))
`kl.getstx Xd, Ks|K(Xs)`
return the _State_ field, resp. the _StateExtension_ field, of the metadata of the source locker.
This is useful to determine whether a locker is in an Error State, as defined in <<KLEE-State-field>>.

`kl.getst` is implemented as a read of the source locker's metadata using `kl.getmdl`,
followed by suitable shifting and masking instructions to extract the _State_ field.

As an example, on RV64, `kl.getst` expands to

. `kl.getmdl Xd, Ks` or `K(Xs)`
. `srli  Xd, Xd, 19`
. `andi  Xd, Xd, 0x3F`

and `kl.getstx` to

. `kl.getmdl Xd, Ks` or `K(Xs)`
. `srli  Xd, Xd, 25`
. `andi  Xd, Xd, 0x0F`

On RV32, the assembly code is the same. The instruction `kl.getmdl Xd, Ks` or `K(Xs)` writes the lower 64 bits of the MDH to the register pair `X[d+1] @ X[d]`, and since the _State_ and _StateExtension_ fields lie entirely in the lower 32 bits of the MDH, the shift and masking would be the same.

[[KLEE-instruction-restrict]]
=== kl.restrictl, kl.restricth, and kl.restrictv

_Synopsis_::
Restrict the policies encoded in a CC in a locker.

_Mnemonic_::
+
--
[%hardbreaks]
`kl.restrictl{nbsp}{nbsp}Kd|K(Xd), Xs1`(((KLEE, instruction, kl.restrict)))
`kl.restricth{nbsp}{nbsp}Kd|K(Xd), Xs1`

--

_Encoding_::
+
--
`kl.restrict*` is an R-type instruction.
The encoding shares opcode and `funct3` with `kl.exec`, but `funct2` (i.e., the two msbs of `funct7`) is `0b01`.
[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Kd|K(Xd)' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'Xs1' },
    { bits:  5, name: 0x0 },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'r' },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'h' },
    { bits:  1, name: 'v' },
    { bits:  2, name: 0x1, attr: ['funct2'] },
]}
....

`r` is the locker indexing mode selector. Indirect locker addressing is only available when `Zklind` is present. Otherwise, `r` = 1 is an illegal instruction.

If bit `h` (bit 28) is 0, the instruction is `kl.restrictl`; if `h` is 1, it is `kl.restricth`.

If bit `v` (bit 29) is 0, the input is taken from a GPR (GPR pair for RV32), and the instruction is `kl.restrictl` or `kl.restricth` depending on `h`.
If bit `v` is 1, bit `h` must be 0, and the input is taken from the lowest 128 bits of a vector register (group).
The combination `v` = `h` = 1 is reserved.
--

// comment

_Description_::
+
--
The instructions narrow the policies of the CC in locker `Kd` or `K(Xd)`, with Metadata Header `md`,
as requested by the operand `Xs1` (`Vs1` for `kl.restrictv`), which has the same format as an
MDH. `kl.restrictl` takes bits [63:0] of that format and may change _MachinePolicy_ and
_SCProtection_; `kl.restricth` takes bits [127:64] and may change _Locality_, _UsagePolicy_,
and _ExpirationDate_; `kl.restrictv` takes both halves and applies both sets of
rules as a single instruction.

A zero field of `Xs1` leaves the corresponding field of `md` unchanged, and a non-zero field of `Xs1`
not named above transitions the locker to _Invalid_. Every check, including those that transition the locker to Error State
_Invalid_, is performed before any KLF capacity is allocated for a _SCProtection_ request, as in
`kl.mgmt` (<<KLEE-locker-management>>), and all changes are applied together once every check has
passed. The validity of the changed fields (<<KLEE-Metadata-validity>>) is evaluated on the
resulting MDH, and unchanged fields are not re-examined: a request that would produce an
unsupported or invalid value, such as a non-zero _ExpirationDate_ without `Zklexpire` or a
_Locality_ subfield naming an unconfigured entry, transitions the locker to _Invalid_.

The rules for each non-zero field of `Xs1` are:

* _MachinePolicy_: if the Machine does not use the field, or uses it to extend _Machine_,
  the locker transitions to _Invalid_. Otherwise the new value replaces the old one only if every bit
  it sets was already set, so that a disabled function cannot be enabled; any other value, or one
  invalid for the Machine, transitions the locker to _Invalid_, as does disabling an operation, such
  as encryption or signature generation, while in a State allowed only while performing it.

* _SCProtection_: the value requests that the side-channel protection be raised to that level. A
  request for a weaker level transitions the locker to _Invalid_; the ordering of the custom levels 6
  and 7 relative to the architected ones is implementation-defined. If the stronger level needs
  KLF capacity that cannot be allocated, KLEE exception `kl_exc_out_of_memory` is raised.

* _Locality_: each subfield (<<KLEE-locality-indexes>>) — bits [1:0], [3:2] and [5:4], and each of
  bits 6, 7 and 8 — is treated independently. A subfield of `Xs1` that is zero, or equal to that of
  `md`, requests no change. A zero subfield of `md` takes the value of `Xs1`. A non-zero HW Binding
  subfield may only be replaced by a stricter entry of its chain: _SiPScrt_ by _ChipFamScrt_ or
  _ChipScrt_, _ChipFamScrt_ by _ChipScrt_, _OEMScrt_ by _ProdScrt_ or _DevScrt_, and _ProdScrt_ by
  _DevScrt_. Any other change, including any change of a non-zero Boot Session or SW Filter
  subfield and any weakening, transitions the locker to _Invalid_. A later export binds the SCC to the
  new _Locality_.

* _UsagePolicy_: each set bit removes a permission and each clear bit changes nothing: bits 0–3
  set the corresponding disallow bits of `md`, and bit 4 clears its Debug grant. No request can
  widen the set of modes that may use the CC.

* _ExpirationDate_: if `md`._ExpirationDate_ is zero or `Xs1`._ExpirationDate_ {le}
  `md`._ExpirationDate_, the value in `Xs1` replaces it; otherwise the locker transitions to _Invalid_.

The instructions may be issued in any Complete State; in the _Unconfigured_ State they perform no
operation, and in a Configuration State Rule <<KLEE-SGR-usage-locker-config-state>> applies. They are
not usage-controlled because every change narrows the CC — policies are only removed,
side-channel protection only strengthened, Localities only tightened, and an expiration date only
brought forward — so they cannot give a mode that the _UsagePolicy_ excludes any capability it did
not already have; likewise `kl.clear` (<<KLEE-instruction-clear>>), a strictly stronger denial
primitive, is not usage-controlled.
--

// ////////////////////////////////////////////////////////////////////

[NOTE]
====
Two practical use cases enabled by this instruction are:

*   Allowing privileged code to give a CC to several processes in a
    fine-grained manner, as opposed to all processes.
    This can be achieved by cloning the locker and customizing
    the Localities for each clone.
*   Enabling privileged code to split a CC capable of both
    encryption and decryption into two CCs, one only capable of encryption and
    the other only capable of decryption, thereby creating a one-way channel
    between processes.

The ability to perform such customizations saves both time and computational
resources by avoiding additional round-trips to trusted environments.
====

. `01`{nbsp}{nbsp} encodes `kl.rename`.
. `10`{nbsp}{nbsp} encodes `kl.swap`.

// Comment to ensure proper indentation in the next Description

_Description_::
+
--
`kl.clone`:::
Clones the source locker `Ks` (or the locker indexed by `Xs`) into the destination locker `Kd` (or the locker indexed by `Xd`):

* If source and destination are the same locker the instruction performs no operation, even if the locker is _Unconfigured_, _Off_, or in a Configuration State, which is excepted from Rule <<KLEE-SGR-usage-locker-config-state>>. It sets no `*llockerstatus` or `KLS` field to _Dirty_ (<<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>>).

* If the source locker is _Unconfigured_, an illegal-instruction exception is raised.

* If the source locker is in a Configuration State, KLEE exception `kl_exc_privilege_violation` is raised (Rule <<KLEE-SGR-usage-locker-config-state>>). A source in an Error State is cloned as its MDH alone (Rule <<KLEE-SGR-error-state-locker-is-only-MDH>>).

* Otherwise, the implementation checks whether the KLF capacity that would be available once the destination locker is cleared suffices for a clone of the source locker; if it does not, KLEE exception `kl_exc_out_of_memory` is raised and the destination locker is left unchanged.

* The destination locker is then cleared and the clone is created.

* The destination locker becomes a perfect copy of the source locker: all internal data, including MDH and internal state, are copied verbatim.
The instruction has the same effect on the destination CC as an export and import would, but touches no authentication register.

`kl.rename`:::
If `Ks` = `Kd`, no operation is performed, even if the locker is _Off_, and no field is set to Dirty.
Otherwise the CC of `Ks`, including any Partial or Configuration State, becomes the CC of `Kd`, the previous CC of `Kd` is discarded, and `Ks` becomes _Unconfigured_. If `klmanagedlocker` = `s`, it becomes `d`. Otherwise, if `klmanagedlocker` = `d`, it becomes 32. The source access is not exempt from `kl_exc_locker_off`; the destination access is exempt as for `kl.clone`. The fields in effect for both lockers are set to Dirty.

`kl.swap`:::
If `Ks` = `Kd`, no operation is performed, even if the locker is Off.
Otherwise the CCs of `Ks` and `Kd` are exchanged. If `klmanagedlocker` {in} {`s`,`d`}, it is replaced by the other index. Neither access is exempt from `kl_exc_locker_off`. The fields in effect for both lockers are set to Dirty.

Neither `kl.rename` nor `kl.swap` raises `kl_exc_out_of_memory`, and neither changes the content of any MDH.

See <<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>> for the behavior under emulation, i.e., when the source or destination locker is _Off_ in some `*llockerstatus`.
--

Bits [26:25], i.e., field `R`, are encoded as for `kl.clone` (<<KLEE-instruction-clone>>).
For this instruction, indirect locker addressing is only available when `Zklind` is present. Otherwise, `R` {ne} `00` is an illegal instruction.

The auxiliary input is always a GPR: `kl.derive` has no form without one and no vector form.
--

_Description_::
+
--
`kl.derive` moves up to `length` bytes from an endpoint of the source locker to an endpoint of the
destination locker without making them visible to software: the output of one Machine becomes an
input, possibly a key or some other Content field, of another.

There are two types of such transfer: if the data moved from the source locker to the destination locker
can be also obtained by performing `kl.exec` instructions, or a Rule declares the transfer unrestricted, then we speak of an _unrestricted transfer_;
otherwise it is a _restricted transfer_.

The source and the destination lockers must be different,
otherwise an illegal-instruction exception is raised.

The auxiliary GPR carries `length`.

`kl.derive` is a usage-controlled operation of both source and destination lockers.
Therefore, the _UsagePolicy_ fields of both endpoints are verified
before any state change or transfer operation is performed.
If usage is not allowed in the current privilege mode for either the source or destination locker,
KLEE exception `kl_exc_privilege_violation` is raised per Rule <<KLEE-SGR-usage-policy>>.

Both source and destination lockers must be in specific states, as defined by the
_State_ and _StateExtension_ metadata fields.
The source must be in a state where it can export data, and
the destination must be in a state where it can import data.
These states, and only these states define the fields that are exported or imported,
or the type of the data that would be generated or absorbed by `kl.exec` instructions.
No parameter is passed to `kl.derive` to select the source and destination data.

An _endpoint descriptor_, for both the source and the destination locker, consists of the following information: +
(MDH._Machine_ {vvert} _MachinePolicy_, MDH._State_ {vvert} _StateExtension_, MDH._KeyType_, +
{nbsp}{nbsp}{nbsp}MDH._SCProtection_,  MDH._UsagePolicy_, MDH._Locality_, MDH._ExpirationDate_).

A transfer may occur only if the architecture allows it for the given pair of endpoint descriptors
of the source and destination lockers,
i.e., the Machines and States of both source and destination lockers must be compatible.

An allowed endpoint pair may define a minimum transfer length, an upper limit, and a granularity.

The exact semantics of the transfer, updates to the states of the two lockers as well as
to `klstart`, `vstart`, and any other state of the hart are defined by the architecture
for each endpoint descriptor.

If usage of the instruction is allowed, some Checks, defined below, are performed.
If the transfer is not allowed, the lockers transition as the checks specify.
If a transfer is allowed, then the policies of the destination locker are updated as follows.

In what follows, “DER” means “DErivation Rule”.

[horizontal]
[[KLEE-DER-checks,DER1]]DER1:: The checks of Rule <<KLEE-SGR-gate-order>> apply to both lockers, each check being applied to the source before the destination.
The following checks are then made in order. A check that fails transitions the locker or lockers it names to Error State _Invalid_, and nothing is transferred:

. The _State_ and _StateExtension_ of the source must define a source endpoint (<<Zkl-ISA-machines.adoc#KLEE-derive-endpoints>>). Otherwise the source transitions.
. The _State_ and _StateExtension_ of the destination must define a destination endpoint. A key field, that is a symmetric key or a private key, is a destination endpoint only in State _Ready_ or in a State that the Machine names for loading it, such as _Set_Key_ of HMAC (<<Zkl-ISA-machines.adoc#KLEE-HMAC>>) or _Set_Scalar_ of ECC (<<Zkl-ISA-machines.adoc#KLEE-ECC>>), and never when the destination _KeyType_ is 1 (Rule <<KLEE-DER-SKID-no-export>>). Otherwise the destination transitions.
. The two endpoints must form a pair admitted by Rule <<KLEE-DER-shared-secret>>, <<KLEE-DER-exec-implies-unrestricted>> or <<KLEE-DER-DRBG-implies-unrestricted>>, or explicitly defined in <<Zkl-ISA-machines.adoc#KLEE-Machines>>. Otherwise both lockers transition.
. The effective length (Rule <<KLEE-derive-rule-both-fixed-size>>) must meet the minimum, upper limit and granularity of the pair, and the transferred data any other constraint of the destination. Otherwise the destination transitions.
. A destination key field of `dest_length` bytes requires `length` {ge} `dest_length` and a source field, or remaining `kl.exec` output, of at least `dest_length` bytes. Otherwise the destination transitions. The key field receives exactly `dest_length` bytes, which complete its loading; a key written in State _Ready_ is followed by the initialization that the Machine performs in that State.

[[KLEE-DER-narrowing,DER2]]DER2:: Before any _restricted transfer_ is performed, the policies in the MDH of the destination locker are narrowed by the policies in the MDH of the source locker exactly as a SKID resolution narrows them (<<KLEE-system-keys>>):

* _UsagePolicy_ bits 0–3 of the destination become the OR of both, and bit 4 the AND of both.
* The destination _Locality_ becomes the union of both _Localities_: each HW Binding subfield (bits [1:0] and [3:2]) takes the larger of the two values, that is the stricter entry of its chain (<<KLEE-Localities>>), and bits 6–8 are OR-ed. If the two Boot Session entries are non-zero and differ, or the result names an unconfigured entry (<<KLEE-Localities>>), the destination transitions to Error State _Invalid_ and nothing is transferred.
* If `Zklexpire` is implemented, the destination _ExpirationDate_ becomes the smaller non-zero of the two values, or 0 if both are 0.
* If the destination _SCProtection_ is lower, in the ordering of <<KLEE-SC-protection-levels>>, than that of the source, the destination transitions to Error State _Invalid_ and nothing is transferred.

[[KLEE-DER-unrestricted,DER3]]DER3:: No policy narrowing is applied in case of an _unrestricted transfer_.

The policy narrowing for restricted transfers follows NIST SP 800-57 Part 1 Rev. 5 cite:[nist-SP-800-57-p1-r5], §6.2.1 (key-usage and cryptoperiod metadata protection), and NIST SP 800-108r1 cite:[nist-SP-800-108-r1] §8 (derived keys inherit the security strength and use constraints of the key-derivation key). These Recommendations expect derived material to inherit any constraint of its parent.
Any additional specific transfer defined by the Machines must respect these restrictions.

[horizontal]
[[KLEE-DER-SKID-no-export,DER4]]DER4:: A field configured by a SKID is _never_ exportable, and a key field of a locker whose _KeyType_ is 1 is _never_ importable. No rule may be defined to export or import such a field.

[[KLEE-DER-shared-secret,DER5]]DER5:: Moving a shared secret held by a key-agreement or key-encapsulation Machine, such as the ECC `SecondPt` or the ML-KEM `sharedkey`,
into a key field of a symmetric Machine, into a private key field of a public-key Machine, or into the `kl.exec` input of a hash function, MAC function, or XOF is a _restricted transfer_.
It is admitted whenever both endpoints are defined (Rule <<KLEE-DER-checks>> items 1 and 2); a key field receives the first `dest_length` bytes of the secret (Rule <<KLEE-DER-checks>> item 5).

[[KLEE-DER-exec-implies-unrestricted,DER6]]DER6:: The _`kl.exec` output_ of a source locker, where <<Zkl-ISA-machines.adoc#KLEE-derive-endpoints>> lists it as the source endpoint, is the data that the Form C `kl.exec` instructions permitted in its current _State_ would emit.
The tag of an AEAD Machine is not a `kl.exec` output source, unless that Machine explicitly allows it.
The `kl.exec` output can always be moved, as an _unrestricted transfer_, into a destination endpoint that Form B `kl.exec` instructions load in the current _State_ of the destination, such as the `kl.exec` input of a hash function, MAC or XOF, or the `Scalar` of an ECC Machine in State _Set_Scalar_.
The transfer is a shortcut to `kl.exec` instructions that software could issue on both lockers.
+
NOTE: Such a destination may be a key field, such as the `Scalar` of an ECC Machine or the `K0` of HMAC. Moving any `kl.exec` output into it does not increase the attack surface:
software can always provision a new locker with a key of its choice and any policies, and use it in place of a locker whose key it does not know.
This is the reason such transfers are allowed.
+
_Key derivation._ The `kl.exec` output of a hash function, MAC or XOF can also be moved, as an _unrestricted transfer_, into a key field of a symmetric Machine or into a private key field of a public-key Machine, in a State in which Rule <<KLEE-DER-checks>> item 2 admits that field.
The key field receives the first `dest_length` bytes of the output (Rule <<KLEE-DER-checks>> item 5).

[[KLEE-DER-DRBG-implies-unrestricted,DER7]]DER7:: Using a Machine implementing a DRBG to generate random data
and feed it into a symmetric key field, or into a private key field of a destination Machine
is allowed when the destination is in a State that admits the field (Rule <<KLEE-DER-checks>>).
It is an _unrestricted transfer_, since the output of a DRBG is required to not predictably repeat
the same value twice and not extrapolable from previous or successive outputs.

//

A pair defined in <<Zkl-ISA-machines.adoc#KLEE-Machines>> may further narrow but never relax any policy.

An _exportable field_ is a field that its Machine lists as a source endpoint in <<Zkl-ISA-machines.adoc#KLEE-derive-endpoints>>, an _importable field_ one that it lists as a destination endpoint.
Rules <<KLEE-DER-shared-secret>>, <<KLEE-DER-exec-implies-unrestricted>> and <<KLEE-DER-DRBG-implies-unrestricted>> admit pairs of endpoints; any other pair which is not explicitly defined in <<Zkl-ISA-machines.adoc#KLEE-Machines>> fails Rule <<KLEE-DER-checks>> item 3.

[horizontal]
[[KLEE-derive-rule-both-fixed-size,DER8]]DER8:: *(Transfer Size Rule.)*
A destination field of `dest_length` bytes receives `eff_length` = min(`length`, `dest_length`)
bytes and is zero-filled beyond them (zero-filling does not apply to keys per Rule <<KLEE-DER-checks>>);
any other destination receives `eff_length` = `length`
bytes. `length` = 0 transfers nothing. If the destination is a key field, a `length` of 0 fails the key-length check of Rule <<KLEE-DER-checks>> item 5,
and the destination transitions to Error State _Invalid_; for any other destination the instruction changes no state, provided the other checks of Rule <<KLEE-DER-checks>> pass.
+
The source supplies `eff_length` bytes: the transferred part of a field is truncated to `eff_length` bytes if longer or zero-padded if shorter; a source producing output in blocks of `b` bytes produces the blocks needed to cover
them.
+
The destination consumes the bytes
in its blocks of `b'` bytes, a field being a single block, and a final block shorter than `b'`
is supplied as a `kl.exec` with that shorter input would be. Each endpoint advances as the
`kl.exec` operations producing or consuming these blocks would advance it; a destination
state implemented by `process_VLI` may be left open and continued with `kl.exec`.
+
In all cases, the transfers between the endpoints must have compatible units.
If the source produces data only in multiples of `p` bytes and the destination consumes it
only in multiples of `q` bytes (for instance, a XOF feeding a `process_VLI` state,
<<Zkl-ISA-machines.adoc#KLEE-process-VLI>>), where `p` and `q` are the granularities of the
two States and not their block sizes, then either `p` or `q` must divide the other.
This allows the implementation to internally issue an outputting `kl.exec` operation
and split the output into
`p/q` inputting `kl.exec` operations, or
concatenate the outputs of `q/p` outputting `kl.exec` operations into a single
inputting `kl.exec` operation, without having to keep additional state to be carried
from an internal partial transfer of `max(p,q)` bytes to the next.
+
The interruption points of a `kl.derive` (<<KLEE-CSR-klstart>>) are the `klstart` values that
are interruption points of both endpoints, each in its current State.
--

[[KLEE-instructions-memory]]
=== Memory Instructions

[[KLEE-instruction-load]]
==== kl.load

_Encoding_::
`kl.load` is an I-type instruction.
+
[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x67, attr: ['JALR'] },
    { bits:  5, name: 'context', attr: ['Kd','K(Xd)'] },
    { bits:  3, name: 'kl.load', attr: [0x6,0x7] },
    { bits:  5, name: 'Xs1' },
    { bits: 12, name: 'immed12' },
]}
....
+
`funct3` = 6 selects the immediate locker index in the `context` field and `funct3` = 7 selects the locker indexed by the GPR named by that field.
Indirect locker addressing requires `Zklind`. Otherwise, `funct3` = 0x7 is an illegal instruction.

_Mnemonics_::
`kl.load{fournbsp}{nbsp}{nbsp}{nbsp}Kd|K(Xd), %offset(Xs1)`

_Description_::
+
--
`kl.load` imports the Content of a PI or an SCC into the locker `Kd` or `K(Xd)`.

`kl.load` is never used on a locker in an Error State (Rule <<KLEE-SGR-error-state-locker-is-only-MDH>>, <<KLEE-error-state-transfer>>).

`kl.load` does not transfer the MDH, which is carried by `kl.mgmt`.
The authentication fields `SIV`, `IMPQUAL` and `SIV2` are the leading bytes of the image transferred by `kl.load`, and are loaded in the three internal per-hart registers of <<KLEE-KLF>> while the locker is under management.

Transfers follow the same constraints as those of `kl.mv` (<<KLEE-instruction-mv>>, <<KLEE-Memory-Alignment>>), with `S`, `image_end`, and _ContentOffset_ as defined there.

`kl.load` transfers the offsets `[klstart, image_end)` of `S`: for each _j_ from `klstart` to `image_end` − 1, the byte at memory address ``Xs1 + %offset + ``_j_ is loaded into the _j_-th byte of `S`.
`klstart` tracks a prefix-complete number of bytes loaded.
If `klstart` {ge} `image_end`, nothing is transferred.

Being related to accesses to a locker (<<KLEE-Memory-Alignment>>), `klstart`, `content_size`, `max_admissible`, `image_size` and `image_end` are all multiples of 16 bytes.

When a system-defined format is used, the semantics of `kl.load` are implementation-defined and must be documented; it must satisfy Rules <<KLEE-SGR-zkl-load-mv-allowed>> and <<KLEE-IRR-which-resumable-instructions>>–<<KLEE-IRR-memory-instructions>>.
--

[[KLEE-instruction-store]]
==== kl.store

_Encoding_::
`kl.store` is an S-type instruction.
+
[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x23, attr: ['STORE'] },
    { bits:  5, name: 'immed[4:0]' },
    { bits:  3, name: 'kl.store', attr: [0x6,0x7] },
    { bits:  5, name: 'Xs1' },
    { bits:  5, name: 'context', attr: ['Ks2','K(Xs2)'] },
    { bits:  7, name: 'immed[11:5]' },
]}
....
+
`funct3` = 6 selects the immediate locker index in the `context` field and `funct3` = 7 selects the locker indexed by the GPR named by that field.
Indirect locker addressing requires `Zklind`. Otherwise, `funct3` = 0x7 is an illegal instruction.

_Mnemonic_::
`kl.store %offset(Xs1), Ks2|K(Xs2)`
(((KLEE, instruction, kl.store)))

_Description_::
+
--
`kl.store` exports the serialized image `S` of the locker `Ks2` or `K(Xs2)` to memory.

`kl.store` is never used on a locker in an Error State (Rule <<KLEE-SGR-error-state-locker-is-only-MDH>>, <<KLEE-error-state-transfer>>).

`kl.store` does not transfer the MDH, which is extracted from the locker by `kl.getmd*`.
The authentication fields `SIV`, `IMPQUAL` and `SIV2` are the leading bytes of the image transferred by `kl.store`, and are taken from the three internal per-hart registers of <<KLEE-KLF>> while the locker is under management.

Transfers follow the same constraints as those of `kl.mv` (<<KLEE-instruction-mv>>, <<KLEE-Memory-Alignment>>), with `S`, _ContentOffset_, `image_size` and `image_end` as defined there.
`kl.store` transfers offsets `[klstart, image_size)` of `S`: offsets below `image_end` are stored from the locker, offsets in `[image_end, image_size)` are stored as zero.
That is, for each _j_ from `klstart` to `image_size` − 1, the _j_-th byte of `S` is stored at memory address ``Xs1 + %offset + ``_j_.
`klstart` tracks the prefix-complete number of bytes stored.
If `klstart` {ge} `image_size`, nothing is transferred.

As for `kl.mv`, a _State_ not admitted by Rule <<KLEE-SGR-zkl-store-mv-allowed>>, or a `klstart` that violates those constraints, raises an illegal-instruction exception.

[[KLEE-instruction-input]]
==== kl.input

_Synopsis_::
Load data into the KLIOBUF.

_Mnemonic_::
`kl.input %offset(Xs), Xl`
(((KLEE, instruction, kl.input)))

_Encoding_::
+
--
`kl.input` is an I-type instruction.

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x03, attr: ['LOAD'] },
    { bits:  5, name: 'Xl' },
    { bits:  3, name: 0x7, attr: ['kl.input'] },
    { bits:  5, name: 'Xs' },
    { bits: 12, name: 'immed12' },
]}
....
--

_Description_::
+
--
Without `Zklv`, inputs and outputs are exchanged with memory through the KLIOBUF,
which `kl.input` and `kl.output` fill and drain (<<KLEE-usage-input-output>>).

[[KLEE-iobuf-transfer-window,KLIOBUF transfer window]]
The following holds for `kl.input` and for `kl.output`, and is
stated here once. Both transfer the bytes of the transfer window: for each `j` from `klstart` to
min(`Xl`, `kliobuftop`) − 1,
`kl.input` copies the byte at memory address `%offset(Xs)` + `j` to byte `j` of the KLIOBUF,
whereas
`kl.output` copies byte `j` of the KLIOBUF to the byte at memory address `%offset(Xs)` + `j`.
Bytes below `klstart`,
and bytes at or beyond min(`Xl`, `kliobuftop`), are not accessed on either side.
If `Xl` = 0, or `klstart` {ge} min(`Xl`, `kliobuftop`), the operation transfers nothing and writes 0 to `klstart`.
If `Xl` is greater than `kliobuftop`, only the bytes of the window are transferred; software can
detect this case by comparing `Xl` with `kliobuftop`.

The usage of `kl.input` and `kl.output` is explained in detail in
<<KLEE-usage-input-output>>.
--

[[KLEE-State-management]]
== State Management

For the architected value of the _State_ field, refer to <<KLEE-State-field>>.

(((KLEE, Machine, invalid state)))
(((Cryptographic Locker, invalidation)))
A locker is said to have been _invalidated_ when it has been transitioned to Error State `kl_state_invalid`.
Upon entering an Error State, the locker retains only its MDH (Rule <<KLEE-SGR-error-state-locker-is-only-MDH>>).

Error conditions that lead to exceptions are treated in <<Zkl-ISA-priv.adoc#KLEE-exceptions>>.
See <<KLEE-error-architecture>> for the behavior when the Privileged Architecture is not implemented.

If a Machine defines 47 or fewer valid states (including _Ready_, _Success_, and _Failure_), the current state is stored in the _State_ field.
For Machines with more than 47 valid states, additional state information may reside in the Content section in a Machine-specific format.

When a locker is being provisioned, exported, or imported, it is in one of the following _Configuration_ States:

[[KLEE-SC-sealing-status]]
.Global CC State Numbers: Configuration States
[float="center",align="center",cols="^7%,<33%,<60%",options="header"]
|===
| Value    | Mnemonic                   | Description
|   56     | `kl_cfg_provisioning`     | The locker is being configured.
|   57     | `kl_cfg_exporting`        | The locker, which was in a Valid State, has been placed in exporting mode, i.e., its contents have been encrypted and authenticated for export.
|   58     | `kl_cfg_importing`        | The locker, which was in a Valid State, has been placed in importing mode.
|   59     | `kl_cfg_ppi_exporting`    | The locker, whose base operation is a provisioning, has been placed in exporting mode; its image follows the format of a PI.
|   60     | `kl_cfg_ppi_importing`    | Such an image is being re-imported.
|  61-63   | (Reserved)                 | Reserved.
|===

Nested Management Operations:::
A _nested_ management operation is one opened on a locker that is already under management;
the _base operation_ of a group of nested operations is its outermost management process.
The two Configuration States whose mnemonics contain `ppi` (“partial provisioning input”)
are reached only by a nested management operation whose base operation is a provisioning.
When an import or an export of a locker in a Complete State is interrupted, a nested management operation reuses
`kl_cfg_exporting` and `kl_cfg_importing`, and the base operation is that import or export.
Clearing a locker is an atomic operation that resets the locker to the _Unconfigured_ state, and
as such it is not a nested management operation.

[[KLEE-nested-state-base-types,Nested State Base Types]]
Nested State Base Types:::
The `pi` and `scc` base types of the nested States record whether the image the locker holds originates
from a PI or an SCC, following from the base operation: the base type of a Configuration State is `pi` for
`kl_cfg_provisioning`, `kl_cfg_ppi_exporting` and `kl_cfg_ppi_importing`, and `scc` for
`kl_cfg_exporting` and `kl_cfg_importing`.
They determine its length
(<<KLEE-instruction-size>>), which could not otherwise be recovered once the nested management
operations have overwritten the original _State_.

The immediate in the `kl.setst` instruction (<<KLEE-instruction-setst>>) is a 7-bit value, whereas the _State_ field is only 6 bits long.
This allows `kl.setst` to encode additional operations related to state changes.
The only architected such operation is encoded with the value 64 (`kl_cfg_clear_ads`), which clears any ADS so that the locker can be exported without it; values 65–127 are available to Machines
(see <<KLEE-instruction-clearads>>).

<<KLEE-states-graph>> displays the default state transitions.
The legend for the state transition graph is:

* The double-bordered ellipses represent the _Unconfigured_ State together with the outermost Partial States of a management operation, and the nested Partial States.
* Valid States have single rounded rectangular borders.
* Error States have double rounded rectangular borders.
* Continuous edges denote state transitions induced by usage instructions.
* Dashed edges denote state transitions induced by reaching the expiration date.
* Dotted edges denote state transitions induced by configuration operations.

Completing a provisioning operation leads only to State _Ready_.

Completing an import may result in any admissible value of the _State_ and _StateExtension_ fields, since these are restored to the values at export.

The following rules are generic and apply to all Machines (*SGR* means “State-Specific General Rules”):

[horizontal]
SGR1:: The MDH's _State_ field reflects the current state whenever the CC is in _Ready_, _Success_, _Failure_, or any Error State.
This ensures that these states can be unambiguously determined from the _State_ field alone, without inspecting other fields or the Content.

[[KLEE-SGR-no-exec-in-ready,SGR2]]SGR2:: No `kl.exec` instruction may be executed in State _Ready_ unless the Machine explicitly allows it.
Issuing one otherwise transitions the locker to Error State _Invalid_ (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-not-allowed-instructions>> in <<Zkl-ISA-machines.adoc#KLEE-Machines>>).

SGR3:: Any transition listed in a Machine's specification may be triggered by performing an explicit `kl.setst` operation (<<KLEE-instruction-setst>>), or may be induced by certain conditions specified in the Machine's specification. Transitions to and between _Configuration_ States use `kl.mgmt`; transitions from a Configuration State use `kl.mgmt`, `kl.clear`, `kl.clearall`, an Error State-setting `kl.setst`, a `kl.clone` naming the locker as destination, or a `kl.rename` or `kl.swap` naming it as source or destination.

SGR4:: In a Valid State other than _Success_ and _Failure_, `kl.setst` may be issued with the immediate of the current State.
When the Machine needs to prevent this, it transitions to a different State upon completing the instruction.

[[KLEE-SGR-success-failure,SGR5]]SGR5:: In States _Success_ and _Failure_, only the following KLEE instructions are permitted: `kl.mgmt`, `kl.size`, `kl.avail`, `kl.setst` (subject to Rule <<KLEE-SGR-setst-in-success-failure>> below), `kl.getmd*`, `kl.getst`, `kl.clone`, `kl.rename`, `kl.swap`, `kl.restrict*`, and `kl.derive`.
A `kl.exec` other than those permitted below, or a `kl.setst` not allowed by the architecture or by the Machine in its current _State_ and _StateExtension_, transitions the locker to Error State _Invalid_ (cf. Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-not-allowed-instructions>> in <<Zkl-ISA-machines.adoc#KLEE-Machines>>).
+
In State _Success_ `kl.exec` is also permitted solely to extract further output from a Machine that produces arbitrarily long output, such as a XOF.
Also permitted is `kl.derive` in the following two cases: where the source endpoint is one of its exportable fields (<<KLEE-instruction-derive>>); and under the conditions of use of `kl.exec`.
+
A locker in State _Success_ or _Failure_ may not be the *destination* of a `kl.derive`.
+
NOTE: `ML-KEM.Decaps` (<<Zkl-ISA-machines.adoc#KLEE-PQC-ML-KEM>>) is the motivating case for this `kl.derive` behavior:
it leaves the shared secret in `sharedkey` and
transitions to _Success_, from which the only other exit is _Ready_, and _Ready_ clears
`sharedkey`. Without this provision the shared secret would be unreachable and ML-KEM could not
be used for its stated purpose.

[[KLEE-SGR-setst-in-success-failure,SGR6]]SGR6:: In States _Success_ and _Failure_, `kl.setst` is permitted to transition to _Ready_, to _Unconfigured_ using `#immed7` = `kl_state_unconfigured`, or to an explicitly given Error State.
It is also permitted with `#immed7` = `kl_cfg_clear_ads` (<<KLEE-instruction-clearads>>), which clears any ADS and leaves the _State_ unchanged, when this does not violate usage-control policy.
+
NOTE: Machines such as GCM with a set IV (not GCM-SIV) and Ascon-AEAD128 with a set Nonce could forbid transitions back to _Ready_ to prevent nonce misuse. However, software could bypass this restriction by reloading a saved copy of the original SCC. The architecture therefore does not prohibit transitions back to _Ready_ for simplicity. Returning to _Ready_ may nevertheless erase session-bound internal state, such as randomly generated nonces, as specified in the Machine description.

SGR7:: States _Success_ and _Failure_ cannot be set directly using `kl.setst`: the immediates 46 and 47 are reserved (<<KLEE-illegal-instruction-grounds>>).

SGR8:: A transition from any valid state to _Ready_ using instruction `kl.setst` is always permitted, unless the Machine explicitly forbids it.
// NOTE: Since a locker can always be restored from a backup SCC, preventing transitions to _Ready_--as "GCM with Set IV" (<<KLEE-GCM-with-IV-mode>>) does--is not an effective mitigation against the attacks that would be enabled by transitioning to _Ready_.

SGR9:: The locker state after `kl.setst` completes does not always match the instruction's immediate operand.
Beyond Error State transitions, some operations determine the next state dynamically.
For example, issuing `kl.setst` with a `kl_state_hash_verify` immediate and a verification parameter transitions the locker to either _Success_ or _Failure_.
Instructions such as `kl.exec` may also cause _State_ changes.

[[KLEE-SGR-clear-locker-content-error-state,SGR10]]SGR10:: Upon transitioning to an Error State, the Content of a locker beyond the MDH is cleared:
Internal resources associated with the Content shall also be released,
including any ADS, and the _AuxDataLen_ and _ADSDropped_ fields are set to 0.

[[KLEE-SGR-error-state-locker-is-only-MDH,SGR11]]SGR11::
A locker in an Error State then retains only the MDH.
Requesting its size (<<KLEE-instruction-size>>) returns 16 bytes.

[[KLEE-SGR-transition-to-from-unconfigured,SGR12]]SGR12:: Transitions from _Unconfigured_ to any Complete State may only result from a configuration instruction.
Any usage-controlled instruction (<<KLEE-instruction-properties>>) in State _Unconfigured_ raises an illegal-instruction exception.
Transitions from an Error State to _Unconfigured_ result from explicitly clearing the locker, or from re-opening it for provisioning or import.

SGR13:: The MDH of a locker in the _Unconfigured_ State can be read using `kl.getmd*` (<<KLEE-instruction-getmd>>), returning all zero values.

SGR14:: Exporting a locker in an Error State exports only the MDH (all fields and values), and requires no
`kl.mgmt`:
The MDH of a locker in an Error State is read by software using `kl.getmd*` (<<KLEE-instruction-getmd>>) and stored to memory.
The image can be re-imported with a single `kl.mgmt`, allowing software to take appropriate actions even after a context switch.

SGR15:: If a locker is in any Error State, it can still be reconfigured, cloned, or cleared;
apart from clearing, `kl.setst` can only be used to change the Error State.

[[KLEE-SGR-usage-locker-error-state,SGR16]]SGR16:: Attempts to _use_ a locker in any Error State will not perform any operation, and in particular leave the _State_ field unchanged.
Such an attempt can be considered an operation that would cause a transition to Error State `kl_state_invalid`, so the _State_ field is left unchanged to allow software to address the original error condition. No history of Error States is maintained by the architecture.
+
A usage instruction with an output operand that performs no operation under this Rule or under Rule <<KLEE-SGR-gate-order>> (Error State, expiration), or that transitions its locker to an Error State during execution, writes zeros to every byte of its output window that it has not written: elements `vstart` to `vl` − 1 of `Vd` for a vector output, bytes [`klstart`, `kliobuftop`) for a KLIOBUF output. An in-place operation thus never leaves its input in place of the output it did not produce.

[[KLEE-SGR-usage-policy,SGR17]]SGR17:: Any _usage_ instruction that would violate the Usage Control policies will not perform its operation, and raises KLEE exception `kl_exc_privilege_violation`. See <<KLEE-error-architecture>> for the exact behavior, including when the Privileged Architecture is not implemented.

[[KLEE-SGR-usage-locker-config-state,SGR18]]SGR18:: Usage of a locker in a Configuration State, cloning from it, and restricting it, are not allowed:
Any attempt to do so raises KLEE exception `kl_exc_privilege_violation`.
For a locker in a Configuration State used as the destination of a `kl.clone`, or named as both its source and its destination, see <<KLEE-instruction-clone>>.

[[KLEE-SGR-gate-order,SGR19]]SGR19:: For a usage-controlled instruction (<<KLEE-instruction-properties>>), after the illegal-instruction grounds decided without accessing the state of the KLEE unit (the first group of <<KLEE-illegal-instruction-grounds>>), `kl_exc_fatal`, `kl_exc_no_csk` and `kl_exc_locker_off` (<<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>>), and then the `klstart`/`vstart` check of <<KLEE-CSR-klstart>>, the conditions on a locker are evaluated in this order, and the first that applies decides the outcome:
+
--
. _Unconfigured_: illegal-instruction exception (Rule <<KLEE-SGR-transition-to-from-unconfigured>>);
. Error State: no operation and no exception (Rule <<KLEE-SGR-usage-locker-error-state>>);
. Configuration State: KLEE exception `kl_exc_privilege_violation` (Rule <<KLEE-SGR-usage-locker-config-state>>);
. a forbidden KLIOBUF substitution, or a Form A `kl.exec` with `Vd` = `Vs2` that <<KLEE-instruction-exec>> forbids: illegal-instruction exception (<<KLEE-illegal-instruction-grounds>>);
. _UsagePolicy_: KLEE exception `kl_exc_privilege_violation` (Rule <<KLEE-SGR-usage-policy>>);
. _ExpirationDate_: transition to Error State `kl_state_expired`, then no operation (<<KLEE-Metadata-expiration-date>>);
. A KLIOBUF required by a substitution but unconfigured: KLEE exception `kl_exc_unconfigured_buffer` (Rule <<KLEE-GR-iobuf-configured>>);
. the Machine's own rules.

For `kl.derive`, each condition is evaluated for both endpoints, the source first, before the next; an Error State on either endpoint makes the whole instruction a no-op.
--

[[KLEE-SGR-config-instructions-partial,SGR20]]SGR20:: The following configuration instructions, which are not gated by Usage Control policies, are also allowed when the locker is in a _Partial_ State:
`kl.size`, `kl.avail`, `kl.getmd*`, `kl.getst`,
`kl.setst` with the 7-bit immediate equal to `kl_state_unconfigured` (`kl.clear`) or an Error State,
`kl.clearall`, `kl.clone` naming the locker as destination, and `kl.rename` and `kl.swap`, which move a CC unchanged (<<KLEE-instruction-clone>>).

[[KLEE-SGR-zkl-load-mv-allowed,SGR21]]SGR21:: `kl.load` and `kl.mv` with a destination locker
are allowed in States `kl_cfg_provisioning`, `kl_cfg_importing` and `kl_cfg_ppi_importing`.
In State `kl_cfg_importing` the locker must additionally be the one named by `klmanagedlocker`.

[[KLEE-SGR-zkl-store-mv-allowed,SGR22]]SGR22:: `kl.store` and `kl.mv` with a source locker
are allowed in States `kl_cfg_exporting` and `kl_cfg_ppi_exporting`.
In State `kl_cfg_exporting` the locker must additionally be the one named by `klmanagedlocker`.

[[KLEE-error-architecture]]
== Error Handling Architecture

Without the KLEE Privileged Architecture, which only an M-mode-only hart may omit, the KLEE
exceptions are replaced by the behaviors of <<KLEE-exception-error-correspondence>>, listed in their
natural priority order.

[[KLEE-exception-error-correspondence]]
.Behavior upon exception conditions when the Privileged Architecture is not available.
[float="center",align="center",cols="<1,<2",options="header"]
|===
| KLEE Exception                      | Behavior when the Privileged Architecture is not available.
| `kl_exc_fatal`                    | Implementation and platform defined behavior.
| `kl_exc_no_csk` (See <<KLEE-CSK-requirements>> and <<Zkl-ISA-priv.adoc#KLEE-CSR-mklcsk>>.) | The instruction raises an illegal-instruction exception; on an M-mode-only hart M-mode is both the only mode that can observe it and the only one that can establish a CSK.
| `kl_exc_locker_off` (See <<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>>.)| Does not apply without Privileged Architecture, since the `*llockerstatus` CSRs are not available.
| `kl_exc_unsupported`              | Transition to Error State _Unsupported_.
| `kl_exc_out_of_memory`            | Transition to Error State `kl_state_out_of_memory`.
| `kl_exc_privilege_violation`      | Transition to Error State `kl_state_priv_violation`.
| `kl_exc_unconfigured_buffer`      | The instruction raises an illegal-instruction exception.
|===

For `kl.clone` and `kl.derive`, which name two lockers, the behavior above and the handler's duty
below concern the locker on which the exception is raised: for `kl.clone`, the source for
`kl_exc_privilege_violation` and the destination for `kl_exc_out_of_memory`; for `kl.derive`,
the endpoint on which the failing check is detected, each check being applied to the source before
the destination (Rule <<KLEE-SGR-gate-order>>).

With the Privileged Architecture, the transition is the duty of the exception handler. A handler
that cannot resolve `kl_exc_unsupported`, `kl_exc_out_of_memory` or
`kl_exc_privilege_violation`, cannot forward it to another handler, including an in-process
handler, and does not suppress the process that caused it, must:

. set the _State_ of the locker on which the exception was raised to the corresponding Error State of
  <<KLEE-exception-error-correspondence>>, using the short import of <<KLEE-error-state-transfer>>
  where the instruction left the locker _Unconfigured_, as Rule
  <<KLEE-SGR-transition-to-from-unconfigured>> requires; and
. resume execution at the instruction following the trapping one by advancing `xepc`, since
  otherwise the same exception is raised again. A handler that advances `xepc` past a usage
  instruction should write zeros to its output operand, as the instruction would have done had it
  performed no operation (Rule <<KLEE-SGR-usage-locker-error-state>>).

Elsewhere, including <<Zkl-ISA-machines.adoc#KLEE-Machines>>, <<Zkl-ISA-priv.adoc#KLEE-priv>> and <<Zkl-pseudocode.adoc#KLEE-pseudocode-examples>>, behavior is
described with the Privileged Architecture in effect; without it, the behaviors above replace the
exceptions.

[horizontal]
State change rule for exceptions:: An illegal- or virtual-instruction exception, or a KLEE
exception other than `kl_exc_fatal`, makes no change to KLEE state, except the zeroizing of the
target locker by an opening `kl.mgmt`, which is performed even if the instruction later raises an
exception (<<KLEE-locker-management>>). `kl_exc_fatal` resets the KLEE state (_Fatal Conditions_ below).

=== Categories of Error Conditions

The various categories of error conditions are summarized here for the reader's convenience, since
these are otherwise scattered throughout the specification.

Fatal Conditions:::
+
--
Fatal conditions have the highest priority among the KLEE-specific error categories, and no CPU
state disables their detection. The main one is an integrity failure of the KLF of a hart
(<<KLEE-cryptographic-registers>>); implementations may define others.

A fatal condition causes a KLEE unit reset of the hart (<<KLEE-reset-and-m-mode-only>>).
After the reset completes, KLEE exception `kl_exc_fatal` is raised.
The trap is not delegable below M-mode.
The reset differs from an ordinary one in three ways:

. `misa.L` keeps its value, and every `KLS` field that is not Off becomes Dirty rather than Off.
  This way, `kl_exc_fatal` can be reported, the modes below M-mode are not silently disabled, and
  context-switching code can discard its stale saved state;
. every `*llockerstatus` field becomes _Dirty_ rather than _Initial_, as on entry into unauthenticated
  Debug mode (<<KLEE-interaction-with-debug>>); and
. any masks installed by unauthenticated Debug mode are not lifted.

A CSK generated at boot under the fourth model of <<KLEE-CSK-requirements>> is shared by the harts of
its subsystem and is not regenerated.

Detection and reset may be synchronous or asynchronous, the condition being recorded in the KLEE
unit. The first KLEE instruction or KLEE CSR access issued, or in flight, after detection performs no
operation and raises `kl_exc_fatal`, with `xepc` holding its address. If, at detection, a `KLS`
field in effect is Off or the KLEE bit of an `*stateen0` CSR in effect is clear, the condition is
retained and reported on the first KLEE instruction or KLEE CSR access that is not illegal or virtual
on those grounds; until then such instructions raise an illegal- or virtual-instruction exception,
which <<Zkl-ISA-priv.adoc#KLEE-exception-codes>> ranks above `kl_exc_fatal`.
Detection is thus never disabled; only its reporting is deferred.
--

[[KLEE-illegal-instruction-grounds,Illegal-Instruction Exceptions]]
Illegal-Instruction Exceptions:::
+
--
The grounds for an illegal- or virtual-instruction exception form two groups:

* In the first group, the grounds come from the instruction encoding, the GPRs and the vector
  configuration alone, without accessing the state of the KLEE unit, and therefore take precedence
  over `kl_exc_fatal` (<<Zkl-ISA-priv.adoc#KLEE-exception-codes>>):

. A reserved encoding, including `kl.setst` with `#immed7` 46 or 47, `kl.mgmt` with `#immed7` in 59–62 or in Form B, a reserved `#immed7` of `kl.setst` with `r` = 1 and locker register `X0` (<<KLEE-instruction-setst>>), and a KLEE instruction with a vector operand issued while `vtype.vill` is set (<<KLEE-KLV>>).
. An indirect locker index outside [0..31], or `X0` used as one where not expressly encoded (Rule <<KLEE-GR-GPR-indirect>>), and `kl.derive` with equal locker indices (<<KLEE-instruction-derive>>).
. A GPR pair or quartet not meeting Rule <<KLEE-GR-multiple-GPRs>>.
. A vector operand carrying an MDH with `VL` {times} `SEW` < 128 (Rule <<KLEE-GR-vector-MDH-operand>>), or a vector `kl.mv` whose `vl * (SEW/8)` or `vstart * (SEW/8)` is not a multiple of 16 (<<KLEE-instruction-mv>>).
. An encoding assigned to an extension that is not implemented, for instance as Forms A–C of `kl.exec` without `Zklv`.
. A KLEE instruction or KLEE CSR access gated by a clear `Smstateen` bit (<<Zkl-ISA-priv.adoc#KLEE-CSRs-priv>>), which raises an illegal- or virtual-instruction exception as that extension prescribes; a KLEE instruction issued while `KLS` is Off (see _Fatal_ above), a KLEE instruction issued under big-endian effective data endianness (<<Zkl-notation.adoc#KLEE-Notation>>), and an access to a CSR that <<KLEE-CSRs-unpriv>> declares unavailable or that <<Zkl-ISA-priv.adoc#KLEE-CSRs-priv>> makes inaccessible from the current mode (an illegal- or virtual-instruction exception, as stated there).

* In the second group, the grounds require the state of the KLEE unit: for most of them the
  contents of a locker, which for a locker marked _Off_ (<<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>>) exist only once it has been
  lazily loaded, or in the M-mode code that emulates it. They are evaluated only after
  `kl_exc_no_csk` and the _Off_ gate, once the locker is loaded or by the emulator, and only if no
  fatal condition is pending, `kl_exc_fatal` being raised otherwise:

. A usage-controlled instruction issued on a locker in State _Unconfigured_ (Rule <<KLEE-SGR-transition-to-from-unconfigured>>), including `kl.derive` with an _Unconfigured_ endpoint.
. `kl.load`, `kl.store` or `kl.mv` on a locker whose _State_ does not admit the transfer, or with an inconsistent `klstart` (Rules <<KLEE-SGR-zkl-load-mv-allowed>> and <<KLEE-SGR-zkl-store-mv-allowed>>).
. `kl.mgmt` when `klmanagedlocker` names another locker, when opening an export on an _Unconfigured_ locker, when completing with an `ml`._State_ inconsistent with the locker's Configuration State, or when `kl_cfg_management_end` is issued with no management operation open (<<KLEE-locker-management>>).
. A KLIOBUF substitution that <<KLEE-usage-input-output>> forbids, such as a Form B or C `kl.exec` issued where Form A is expected, including any substitution without `Zklio`, since whether a Form is a substitution depends on the operation the locker's State defines.
. A Form A `kl.mgmt` that must take the MDH from a configured KLIOBUF with `kliobuftop` < 16 (Rule <<KLEE-GR-vector-MDH-operand>>).
. A `kl.clone` whose source is _Unconfigured_ and differs from its destination (<<KLEE-instruction-clone>>).
. A Form A–C `kl.exec` with `klstart` {ne} `vstart` {times} `SEW` / 8 (<<KLEE-CSR-klstart>>).
. A Form A `kl.exec` with `Vd` = `Vs2` for an operation whose output blocks do not have the length of its input blocks (<<KLEE-instruction-exec>>).
. If the Privileged Architecture is not implemented, an instruction issued without a CSK, or one that requires the KLIOBUF while it is unconfigured or absent (<<KLEE-exception-error-correspondence>>).
--

// Exceptions and State Changes::: [[KLEE-exceptions-and-state-changes,Exceptions and State Changes]]
// When a KLEE instruction raises `kl_exc_no_csk`, `kl_exc_locker_off`, `kl_exc_unsupported`, `kl_exc_out_of_memory`, `kl_exc_privilege_violation` or `kl_exc_unconfigured_buffer`, it has changed no KLEE state, unless its description states a change that precedes the exception. `kl.mgmt` is the one instruction that does: it zeroizes the target locker before its checks.

Unsupported Machines:::
+
--
Unsupported Metadata at provisioning or import raises `kl_exc_unsupported` and leaves the locker
_Unconfigured_. A handler below M-mode that receives the delegated exception cannot emulate the
Machine and treats the exception as unresolvable.

An M-mode handler that emulates the Machine instead sets the locker's `*llockerstatus` field to _Off_
(<<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>>). Every later access to the locker that <<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>> does not exempt then traps. At this point, the emulator, holding the locker in its own protected memory, services every operation
on it, including SCC import and export. For this it needs either the inputs of `SCC_Encrypt` and
`SCC_Decrypt` (<<KLEE-SCC-AEAD>>) that it cannot otherwise obtain, namely the CSK and the Locality
Secrets of the HW Binding Group, or access to primitives that compute these functions on its
behalf, provided in an implementation-specific way. An implementation that provides neither cannot
emulate Machines, and reports `kl_exc_unsupported` to software instead.

An emulator keeps one copy per locker slot, and replaces it:

. at the next `kl_exc_unsupported` on that slot; or
. at an emulated `kl.clone` naming the slot as destination, which also clears the hardware locker of
  that slot and marks it _Off_, since the clone of an emulated locker is emulated too.

A copy orphaned by an instruction that <<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>> exempts is never used again but lingers
until replaced, so an emulator that must not retain key material longer than necessary checks
`mllockerstatus` whenever it runs and zeroizes the copies whose _Off_ mark is gone.

`kl_exc_unsupported` is _not_ raised when accessing or using a locker in State `kl_state_unsupported`.
--

Other Exception Conditions:::
+
--
The remaining exceptions, in the order of <<Zkl-ISA-priv.adoc#KLEE-exception-codes>>, are listed below. Without the
Privileged Architecture, the KLEE exceptions among them are replaced as
<<KLEE-exception-error-correspondence>> prescribes.

. *No active CSK.* `kl_exc_no_csk`, on any KLEE instruction or KLEE CSR access that
  <<KLEE-CSK-requirements>> does not exempt, while no CSK is established or the `mklcsk` group is
  only partially written (<<Zkl-ISA-priv.adoc#KLEE-CSR-mklcsk>>).
. *Locker marked _Off_.* `kl_exc_locker_off`, on any access to the locker that <<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>> does not
  exempt, before any condition that depends on its contents. M-mode resolves it or forwards it to
  the mode that owns the _Off_ field.
. *Usage Control.* `kl_exc_privilege_violation`, for a usage-controlled instruction in a mode that
  the _UsagePolicy_ excludes (Rule <<KLEE-SGR-usage-policy>>), and for any use, cloning or
  restriction of a locker in a Configuration State (Rule <<KLEE-SGR-usage-locker-config-state>>).
. *Insufficient KLF capacity.* `kl_exc_out_of_memory`, for a `kl.mgmt` opening a provisioning or
  an import (<<KLEE-locker-management>>), a `kl.clone` (<<KLEE-instruction-clone>>), or an
  `kl.restrict*` raising _SCProtection_ (<<KLEE-instruction-restrict>>).
. *Unconfigured KLIOBUF.* `kl_exc_unconfigured_buffer` (Rule <<KLEE-GR-iobuf-configured>>).
. *Memory exceptions.* The load/store address-breakpoint, address-misaligned, page-fault,
  guest-page-fault and access-fault exceptions of the component accesses of `kl.load`,
  `kl.store`, `kl.input` and `kl.output`, ordered as in <<KLEE-Memory-Alignment>>, with a precise
  halt (<<KLEE-resumability>>); an access to a non-idempotent region is an access fault
  (<<KLEE-Memory-Model>>).
--

Errors Not Raising Exceptions:::
+
--
The following conditions set an Error State, or make the instruction perform no operation, without
an exception; the algorithmic errors below are further cases. Without the Privileged Architecture,
so are the conditions that <<KLEE-exception-error-correspondence>> maps to an Error State.

. *Invalid Metadata or SKID.* _Invalid_, for a `kl.mgmt` opening a provisioning or an import on
  invalid Metadata (<<KLEE-MVR-open>>), for a SKID other than the all-ones value that the System Key
  Store does not or may not resolve (<<KLEE-system-keys>>), and for a `kl.restrict*` request that
  would widen the CC or yield invalid Metadata (<<KLEE-instruction-restrict>>).
. *Instruction not allowed in the current State.* _Invalid_, for a `kl.exec` or `kl.setst` not
  allowed in the current _State_ and _StateExtension_, including an unsupported `#immed7` (Rules
  <<KLEE-SGR-no-exec-in-ready>> and <<KLEE-SGR-success-failure>>, <<KLEE-instruction-setst>>), and for
  a `kl.derive` that fails its checks (<<KLEE-instruction-derive>>).
. *Invalid length.* _Invalid_, for an operand whose transfer-window length (`kliobuftop`, or `VL` {times} `SEW` / 8) the Machine does not accept (<<KLEE-CSR-klstart>>, <<KLEE-usage-input-output>>).
. *Expiration.* _Expired_, for a usage-controlled instruction on an expired locker, which then performs
  no operation (<<KLEE-Metadata-expiration-date>>).
. *Use of a locker in an Error State.* No operation, and the _State_ is unchanged (Rule
  <<KLEE-SGR-usage-locker-error-state>>, <<KLEE-error-state-instructions>>).
. *Explicit Error State.* The Error State that a `kl.setst` immediate names
  (<<KLEE-instruction-setst>>).
. *Unusable ADS.* Dropped at import, without rejecting the SCC (<<KLEE-SCC-import>>).
--

Algorithmic Errors:::
+
--
Algorithmic errors may occur:

. in SCC management, as Error State `kl_state_mgmt_auth` (_Authentication Failed_), when the
  `SIV` check fails at the completion of an import (<<KLEE-SCC-import>>) or of an export
  (<<KLEE-mgmt-completes-export>>); software therefore checks the _State_ after completing an export
  as well as after completing an import;
. in the Machines themselves, which may transition the locker to Error State _Invalid_ or to another
  Error State, as the Machine specifies.

The verification of an authentication tag by an AEAD scheme (_not_ by the SCC export and import
procedures), or of a signature, is _not_ an algorithmic error, whether it succeeds or fails: the
Machine has performed as expected.
--

=== Summary of Behavior of KLEE Instructions in Error States

A locker in an Error State holds only its MDH (Rules <<KLEE-SGR-clear-locker-content-error-state>> and <<KLEE-SGR-error-state-locker-is-only-MDH>>). What an instruction does with it depends on whether the instruction uses the locker or manages it.

The illegal-instruction grounds of the first group (<<KLEE-illegal-instruction-grounds>>), `kl_exc_fatal`, `kl_exc_no_csk`, `kl_exc_locker_off` if a `*llockerstatus` field in effect for the locker is _Off_ (<<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>>), and, for Forms A–C of `kl.exec`, the `klstart`/`vstart` check of <<KLEE-CSR-klstart>> are evaluated before the _State_ of the locker is considered (Rule <<KLEE-SGR-gate-order>>).

An instruction that uses the locker, that is `kl.exec`, `kl.derive`, or a usage-controlled `kl.setst`, performs no operation and raises no exception.
The Error State is the second condition that Rule <<KLEE-SGR-gate-order>> evaluates, right after _Unconfigured_, so the _UsagePolicy_ is not evaluated, and neither is the _ExpirationDate_, which is evaluated only in a Valid State (<<KLEE-Metadata-expiration-date>>).
The _State_ is unchanged: Rule <<KLEE-SGR-usage-locker-error-state>> treats the attempt as one that would cause Error State _Invalid_, and leaves the original Error State visible to software.

[[KLEE-Memory-Model]]
== Memory Model

MMR means “Memory Model Rule.”

[horizontal]
MMR1:: KLEE memory instructions appear to execute in program order on the local hart.

MMR2:: KLEE memory instructions follow RVWMO at the instruction level.
If `Ztso` is implemented, they additionally follow RVTSO at the instruction level.

MMR3:: KLEE memory instructions are supported only for idempotent memory: no component access is made to a non-idempotent or side-effecting PMA region.
If a component access would touch such a region, the instruction halts precisely at the last prefix-complete point before the offending byte (0 is not permitted; see <<KLEE-IRR-resumability-options>>), with the completed prefix committed as in Rule <<KLEE-IRR-which-resumable-instructions>>. It then raises a load, resp. store, access-fault exception with `xepc` at the instruction and `xtval` the offending address; re-execution raises the same exception before any component access unless the offending byte no longer maps to such a region.

MMR4:: KLEE memory instructions may be decomposed into component memory operations of any granularity.
Their issue order is not architecturally constrained beyond the applicable memory model and the semantics of
`kl.exec`, `kl.load`, `kl.store`, `kl.input`, and `kl.output`.
Intra-instruction ordering follows RVWMO, even when `Ztso` is implemented.
Upon precise interruption, `klstart` must record a _prefix-complete_ point of the transfer.

MMR5:: Other harts observe these component memory operations as ordinary memory operations under RVWMO.
No ordering among them is guaranteed before the instruction completes.
Sharing a buffer accessed by a KLEE memory instruction requires the same synchronization as sharing it with an ordinary software loop.

MMR6:: For the purposes of `FENCE`, `FENCE.I`, `SFENCE.VMA` and the `.aq`/`.rl` annotations, the component accesses of a KLEE memory instruction are ordinary loads (`kl.load`, `kl.input`) or stores (`kl.store`, `kl.output`) of the issuing hart.

[[KLEE-resumability]]
== Interruptibility and Resumability of KLEE instructions

IRR means “Interruptibility and Resumability Rule.”

[horizontal]
[[KLEE-IRR-uninterruptible-instructions,IRR1]]IRR1:: Instructions `kl.mgmt`, `kl.getmd*`, `kl.restrict*`, `kl.clone`, `kl.rename`, `kl.swap`, non-vector `kl.mv`, `kl.size` and `kl.avail` are _uninterruptible_: each either completes or has no architecturally visible effect, including no writes to destination vector registers, GPRs, locker bytes, KLIOBUF bytes, or memory.
An implementation realizes this in one of three ways:
+
--
. completing the instruction before taking an asynchronous interrupt;
. completing it in the background where Rule <<KLEE-IRR-long-running-no-data>> permits, subject to Rule <<KLEE-IRR-conflicting-access-rule>>; or
. discarding partial work before taking the trap and restarting upon return.

Software must not rely on whether an uninterruptible instruction has retired when a handler runs and must interact with it only as Rule <<KLEE-IRR-conflicting-access-rule>> prescribes.
--

IRR2:: The architecture specifies no interruption points for `kl.setst`, nor within a single block-processing unit of `kl.exec`. An implementation may nonetheless make a long-running instruction of either interruptible, in the ways Rule <<KLEE-IRR-long-running-no-data>> gives.

[[KLEE-IRR-resumability-options,IRR3]]IRR3:: In general, the following behaviors are allowed when an interrupt or exception handler accesses an input or output of a preempted instruction, the associated locker, or any KLEE state that may be affected by the instruction:

. _Background completion:_ The hart waits for the instruction to complete when the privileged handler accesses affected state. This option is not available for `kl.load`, `kl.store`, `kl.input` and `kl.output`, since these are treated as RISC-V memory instructions.
. _Atomic completion_ of the instruction before any asynchronous interrupt is taken.
. _Precise halt and resumption:_ The instruction halts with `klstart` recording a prefix-complete point (<<KLEE-Memory-Model>>), and resumes from `klstart`, advancing by at least one granule per execution attempt.
. _Timeout followed by precise halt and resumption:_ The system may impose a timeout before halting as described above.
. _Precise halt and restart,_ provided that restart is not the unconditional response to asynchronous
interrupts: repeated interruption of the same instruction must not prevent its eventual completion. This option is available for `kl.load`, `kl.store`, `kl.input`, and `kl.output`, whose transfers are idempotent, and for the long-running instructions of Rule <<KLEE-IRR-long-running-no-data>>; block-iterated `kl.exec`, `kl.derive`, and vector `kl.mv` use option 3 or 4 (Rule <<KLEE-IRR-block-iterated-instructions>> below).
For a synchronous exception raised by a component access, the restart option is not available: the instruction halts precisely with `klstart` at the last prefix-complete point before the faulting byte (this is similar to RVV 1.0 §3.7 (`vstart`) and the "Precise vector traps" subsection of the Exception Handling chapter).

[[KLEE-IRR-long-running-no-data,IRR4]]IRR4:: A Machine's semantics for `kl.exec`, `kl.setst` or `kl.derive` forms that access no vector register or KLIOBUF, and no GPR other than scalar operands captured at issue (Rule <<KLEE-IRR-conflicting-access-rule>>), may perform long-running instructions that access no external memory.
Examples of such long-running instructions include scalar multiplication, key generation, and signature generation or verification.
+
Upon preemption, they may follow any of the behaviors described in <<KLEE-IRR-resumability-options>>, compatibly with the requirements of the interrupt or exception.
The implementation must support at least one of options 3, 4 and 5 of Rule <<KLEE-IRR-resumability-options>> for these operations; under option 5 it guarantees, and documents, a minimum uninterrupted execution quantum or a maximum number of consecutive restarts of one instruction, so that repeated interruption cannot prevent completion.
If an operation continues while the hart is preempted and the hart waits for completion before accessing the affected state, any nested interrupt handler must also wait before accessing that state.
+
If such an operation can advance its recorded progress towards completion of the operation, interrupt at well defined points, and resume from the recorded progress point, the progress must be recorded in the _MachineUse_ field, in an implementation-defined format; `klstart` remains reserved for byte counts (<<KLEE-CSR-klstart>>). An implementation may interrupt such an operation and record its progress only where the recorded state, including the ADS, cannot be consumed against inputs other than those the operation started with; Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-progress-discard>> of <<Zkl-ISA-machines.adoc#KLEE-Machines>> guarantees this by discarding the recorded state on any transition of the locker's _State_ other than the completion of the operation (Rule <<KLEE-GR-atomic-randomness>>). If progress is recorded, the implementation exports the data necessary to support resumption in the ADS. Any importing implementation may discard this Section and restart the operation, and must restart it on an Implementation Qualifier mismatch, or if the ADS is removed from the locker (using `kl.clearads`, cf. <<KLEE-instruction-clearads>>).
+
The architected Content of the locker does not depend on the progress of the operation: an implementation that records progress keeps every intermediate result in the ADS, and if the operation restarts, it does so from the architected Content alone.

[[KLEE-IRR-conflicting-access-rule,IRR5]]IRR5:: All the approaches in Rule <<KLEE-IRR-resumability-options>> are subject to one rule: Before the issuing hart performs a _conflicting access_, the in-flight operation must either have completed or have been precisely halted with `klstart` set per <<KLEE-Memory-Model>>. A conflicting access is any of the following:
+
--
* An ordinary load or store overlapping the memory region of the in-flight KLEE operation.
* An access to a locker used by the operation, including the issue of another KLEE instruction involving a locker used by the operation.
* A read or write of `klstart` or a KLIOBUF CSR.
* A read or write of a GPR or vector register that the operation writes as its destination.
* A write to a vector register or to the KLIOBUF that the operation reads as an operand, including the issue of a `kl.input` targeting it. Scalar operands held in GPRs are captured when the instruction issues, so accessing one is not a conflicting access.

Rules <<KLEE-IRR-resumability-options>> and <<KLEE-IRR-conflicting-access-rule>> make asynchronous execution by the attached KLEE unit invisible to same-hart program order, as <<KLEE-Memory-Model>> requires. Beyond this rule, the architecture specifies only the allowed interruption points for its instructions and Machines.
--

[[KLEE-IRR-which-resumable-instructions,IRR6]]IRR6:: The resumable instructions are `kl.exec`, vector `kl.mv`, `kl.derive`, `kl.load`, `kl.store`, `kl.input`, and `kl.output`. Architecturally, they process input units serially. If an instruction halts precisely, the completed prefix is committed, the failing and subsequent units have no effect, `klstart` records a prefix-complete point, the instruction does not retire, and `xepc` contains its address. If an instruction transitions its locker to an Error State after partial progress, the completed prefix remains committed, the unwritten part of its output window is zeroed (Rule <<KLEE-SGR-usage-locker-error-state>>), and the instruction retires (<<KLEE-CSR-klstart>>).

[[KLEE-IRR-block-iterated-instructions,IRR7]]IRR7:: For block-iterated `kl.exec`, `kl.mv`, and `kl.derive`, fully processed blocks remain written or transferred, and `klstart` records their total byte count. For transfer instructions, bytes below `klstart` remain transferred at both endpoints. A partially executed instruction commits exactly the state that a shorter instruction performing only the completed operations would have committed. This includes the locker, `klstart`, `*llockerstatus`, and effective `KLS` fields, ensuring consistent context save, restore, and resumption. Implementations must honor `klstart` for `kl.exec` and `kl.derive`. Handlers must not reset it to zero to force a restart, as doing so is UNSPECIFIED and may transition the locker to _Invalid_.

[[KLEE-IRR-memory-instructions,IRR8]]IRR8:: KLEE memory instructions (`kl.load`, `kl.store`, `kl.input`, and `kl.output`) are RISC-V memory instructions: such an instruction is complete, and may retire or take a trap with `xepc` past it, only after every component access has passed address translation and permission checks and has been performed.
Otherwise, similarly to vector memory operations, the implementation halts the instruction precisely, with `klstart` at a prefix-complete point allowed by the instruction, and raises the corresponding load/store page-fault, guest-page-fault or access-fault exception synchronously for that execution attempt.
+
NOTE: After each `kl.load` the caller must check whether the locker is _Unconfigured_, in which case the entire configuration operation (not just the `kl.load` instruction, but the software using it) must be restarted: an exception handler may have cleared the locker and advanced `xepc` to force this behavior.
// +
// NOTE: Clearing a locker in an exporting State (<<KLEE-instruction-setst>>) calls for particular care from an
// exception handler, because until the export completes, the ciphertext the locker holds may be the only copy of
// the CC. A handler that intends to clear such a locker must first see the export through to completion — if
// necessary across preemptions of its own by a more privileged mode — and store the resulting image.
// If it clears the locker earlier, by mistake or on an unrecoverable error, the CC is lost: the caller detects
// this by the same check after `kl.store`, must treat the error as unrecoverable, and a further
// `kl.store` on the cleared locker raises an illegal-instruction exception (<<KLEE-instruction-store>>).
// This allows the error to propagate to the outermost caller.
//
// [[KLEE-IRR-algorithms-specific,IRR9]]IRR9:: Machine-specific resumable long-running operations that transfer no data
// in a `kl.setst`, in a (block-processing step of) `kl.exec` operation,
// or in a `kl.derive` operation,
// must either advance its recorded progress towards completion of the operation, or restart.
// The manner in which progress is recorded is implementation-defined, but it cannot use `klstart`
// (for instance, it can use _MachineUse_, as in <<KLEE-ECC>> and <<KLEE-PQC>>).
// Implementations capable of resuming these operations also support their restart.

[[KLEE-usage-input-output]]
== Replacing Vector Inputs and Outputs with kl.input and kl.output

When `Zklio` is available, a Form of `kl.exec`, `kl.setst`, or `kl.mgmt` that reads inputs
from vector registers or writes outputs to them may be replaced by the corresponding Form with no
vector operands.
That Form is the one where the inputs or outputs that would be provided through vector registers
are omitted completely.
That Form is _native_ when the operation requires no input or output.
When issued in a Machine's State where vector inputs or outputs are expected, it is instead
a _substitution_, and it uses the KLIOBUF for the expected inputs or outputs, rather than
raising an illegal-instruction exception.

The instructions `kl.input` and `kl.output` perform no computation and change no state other than the KLIOBUF
and `klstart`; all computation and all other state changes remain in `kl.exec`, `kl.setst`, and `kl.mgmt`.

The substitutions are:

. A Form D `kl.exec` replaces a Form A, B or C `kl.exec`.
. A Form A `kl.setst`, or `kl.mgmt`, replaces the Form C of the same instruction.

// A Form D `kl.exec`, or a Form A `kl.setst` or `kl.mgmt`, is a _substitution_ when the operation
// it performs defines an input or an output, and is _native_ otherwise. A native Form neither reads
// nor writes the KLIOBUF, and ignores `klstart`, which it leaves unchanged; `kl.mgmt`, in every
// Form, and `kl.clearall` nevertheless clear it (<<KLEE-instruction-setst>>, <<KLEE-instruction-clear>>).

A substitution reads its inputs from, and writes its outputs to, the KLIOBUF:

* A substituted Form A `kl.exec` behaves as a Form A with `Vd` = `Vs2` (<<KLEE-instruction-exec>>):
  each block's output replaces its input at the same offset of the window.
* A substituted Form C `kl.exec` writes its output to [`klstart`, `kliobuftop`); bytes of the
  window it does not write are unchanged, and no byte at or beyond `kliobuftop` is written.
* A substituted Form A `kl.setst` reads its auxiliary input from bytes [0, `kliobuftop`) of the
  KLIOBUF, ignoring `klstart`; the truncation to the operand width of
  <<Zkl-ISA-machines.adoc#KLEE-Machines-other-rules>> applies.
* `kl.exec` never modifies `kliobuftop`.

A substitution fails as follows:

* Without `Zklio`, it raises an illegal-instruction exception.
* Mixing vector and KLIOBUF operands is not allowed: a Form B or C `kl.exec` issued where Form A is
  expected raises an illegal-instruction exception.
* An operation whose output blocks do not have the same length as its input blocks may be substituted
  only if its Machine states where its output is written in the KLIOBUF; otherwise the
  substitution raises an illegal-instruction exception.
* If the KLIOBUF is not enabled or `kliobuflen` is zero, KLEE exception
  `kl_exc_unconfigured_buffer` is raised.
* If `kliobuflen` is non-zero but `kliobuftop` is a length invalid for the Machine, the locker transitions to Error State _Invalid_, whether the KLIOBUF is used as an input or only as an output (<<KLEE-CSR-klstart>>).

In <<Zkl-ISA-machines.adoc#KLEE-Machines>>, when a Form of `kl.exec`, `kl.setst`, or `kl.mgmt` is
_expected_ (rather than _required_ or _the only Form allowed_), the substitutions above apply
implicitly and are not repeated for each occurrence.

<<KLEE-replacement-instructions>> gives examples of alternative sequences using `kl.input` and
`kl.output`.

[[KLEE-CC-management]]
== Management of Cryptographic Contexts

In keeping with RISC-V philosophy, KLEE splits complex locker management operations into sequences of simpler instructions rather than implementing them as single instructions driving very large state machines or triggering microcode. Even a trap-and-emulate implementation of complex monolithic instructions would have to support such a splitting by definition.

This has several effects:

. The state machine for managing keys and algorithms, hidden from software in key-protection solutions on other CISC architectures (cf. cite:[IBM-z-arch] “Protection of Cryptographic Keys” or cite:[intel-keylocker]), is exposed to software.
Moving its sequencing out of hardware nevertheless significantly simplifies the hardware. However, the exposure may make the state machine managed by software more complex, and increase the set of rules the hardware must enforce, since management operations must withstand malicious attempts to tamper with them.
. Management sequences can be interrupted between instructions by interrupts and exceptions.
Explicit support is therefore required for context switching, process and virtual machine migration, hibernation, and interoperability between KLEE implementations.
. Dynamic locker management, including lazy context loading, must be supported explicitly rather than relying on implicit caching for repeated key use, as other architectures may do.
The confidentiality and integrity of a CC's MDH and Content must be preserved under these conditions.

KLEE meets these requirements while maintaining binary compatibility across implementations.
However, an implementation need not support resumption of interrupted management operations. In that case, the implementation may force a restart, or a context-switch handler may do so by explicitly clearing partially provisioned or imported lockers during context save or restore. Both the architected instructions and the software that uses them must be able to support both scenarios without requiring code changes.

This section describes how the KLEE ISA supports management of lockers and SCCs for all use cases.

KLEE defines three external CC formats:

. The _Provisioning Input_ (PI), loaded into a locker to create a CC.
. The _Sealed Cryptographic Context_ (SCC), an encrypted and authenticated representation of a CC used when exporting a locker to memory for later import.
. The _Partially Configured Cryptographic Context_ (PCCC), which is used to export a locker when a management operation has been preempted, in order to be able to re-import its contents for a later resumption of the interrupted operation. Its format is identical to that of a PI or an SCC,
depending on the base type of the locker's Configuration State (see <<KLEE-nested-state-base-types>>), except that no additional encryption or authentication is applied.

{empty}
(((Cryptographic Context,Metadata)))
(((Cryptographic Context,Metadata,Header)))
All three formats begin with the 128-bit MDH described in <<KLEE-Metadata>>.

The _AuxDataLen_ field of the MDH gives the size, in 128-bit blocks, of the Implementation-Specific ADS (`IMPQUAL`, `SIV2` and `Content2`), or its size before `Content2` was dropped when _ADSDropped_ = 1. The ADS is empty if _AuxDataLen_ = 0; the value 1 is invalid. KLEE generates an image with _ADSDropped_ = 1 only as an SCC-shaped PCCC: a nested export preserves an interrupted import after `Content2` was dropped. In that image, `IMPQUAL` and `SIV2` remain, `Content2` is absent, and the `Content1` offset is unchanged (<<KLEE-Auxiliary-Data-Section>>). Because _ADSDropped_ is unauthenticated, import also accepts the same layout when the bit was set by modifying an SCC.
A locker in an Error State is its MDH alone (Rule <<KLEE-SGR-error-state-locker-is-only-MDH>>).
--

Encryption during management.:::
While an SCC is imported, or a locker is exported as an SCC, the
`Content` held in the locker is encrypted:

. The `kl.mgmt` that opens an export encrypts it and generates `SIV` and, if _AuxDataLen_ {ge} 2,
  `IMPQUAL` and `SIV2`.
. The `kl.mgmt` that completes an import or an export decrypts and authenticates it. This requires
  the MDH and `Content` to have been loaded, and `SIV`, and if _AuxDataLen_ {ge} 2 also `IMPQUAL`
  and `SIV2`, to be in place. When _ADSDropped_ = 1, no `Content2` is loaded or authenticated. An export completion may instead restore the clear contents from an
  internal copy (<<KLEE-mgmt-completes-export>>).

Partially Configured Cryptographic Context (PCCC).:::
+
--
A locker under management that is exported at a nested level produces a PCCC: its data is exported verbatim, with no
further encryption or authentication, in a shape given by the base type of the locker's Configuration
State (<<KLEE-nested-state-base-types>>):

* `pi` (State `kl_cfg_ppi_exporting`, a partially provisioned locker): a _PI-shaped_ image, the MDH
  followed by the clear `Content` of a PI. This is not a security issue, as the plaintext was
  already available to software, and thus to its more privileged modes.
* `scc` (State `kl_cfg_exporting`, a partially imported SCC, or a locker whose export was itself
  preempted): an _SCC-shaped_ image, the MDH followed by `SIV` and, when present, `IMPQUAL` and
  `SIV2`, as _ContentOffset_ prescribes (<<KLEE-instruction-mv>>), and by the ciphertext `Content`
  already held in the locker.

By saving each MDH in its own local state, software keeps an implicit stack of _State_ values,
whose top belongs to the previous nesting level and is restored by the completing `kl.mgmt`.
To track the progress of `kl.load`, `kl.store` and `kl.mv`, context switching handlers
must save and restore `klstart`.
--

[[KLEE-length-rule]]
=== Determination of the Length of a PI/SCC/PCCC and the KLF Capacity Usage of a Locker

Except when the locker is in an Error State, the MDH fields that determine the length
of a PI, of an SCC and of a PCCC, as well as the KLF capacity occupied by a locker, are all
contained in the lower 64 bits of the MDH:

. The length of a *Provisioning Input* is determined by, and only by, the fields
_Machine_, _MachinePolicy_ and _KeyType_.
It does *not* depend on _AuxDataLen_ or _ADSDropped_: a PI and a PCCC whose Configuration State has base type `pi` carry no ADS, and _AuxDataLen_ and _ADSDropped_ must be zero in their MDH.
It also does not depend on _StateExtension_ or _MachineUse_, whose values are ignored and are
replaced with zero by `kl.mgmt` upon provisioning, nor on _SCProtection_.
During provisioning, the information of a locker reflects the external format of a PI.
The internal representation is finalized into the locker's internal state upon using
`kl.mgmt` to complete the provisioning, which may include the computation of
information such as derived keys, or multiple shares.

. The length of a *Sealed Cryptographic Context*
is determined by, and only by, the
fields _Machine_, _MachinePolicy_, _KeyType_, _StateExtension_, _AuxDataLen_, and _ADSDropped_ (see <<KLEE-Auxiliary-Data-Section>>). _ADSDropped_ can remove only `Content2`; it never changes the presence of `IMPQUAL` or `SIV2`, or the offset or length of `Content1`. Note that this length does not depend on _State_.
It also does *not* depend on _SCProtection_ (see <<KLEE-rules-masked-implementations>>).

. The length of a *Partially Configured Cryptographic Context* is that of a
Provisioning Input if the base type of its Configuration State (<<KLEE-nested-state-base-types>>) is a PI,
and that of a Sealed Cryptographic Context if the base type of its Configuration State is an SCC.
// identifies: the `Content` of a PI for a
// `_pi` State, and `Content1` together with `Content2` for an `_scc` State. Once the image is
// identified, its length is given by the rule above for that format, and depends on no further field.

. The *KLF capacity* occupied by a locker is determined by, and only by, the fields
_Machine_, _MachinePolicy_ and _SCProtection_.
It does not depend on _KeyType_, because a locker holds the expanded key material whether the
key was provisioned by value or retrieved through a System Key Identifier,
nor on _StateExtension_, because a locker is allocated with room for every field the
Machine may come to use.

No other MDH field and no information in the `Content` may affect any of these four quantities. _ADSDropped_ affects the lengths of SCCs and SCC-shaped PCCCs, but does not affect KLF capacity.

A locker in an Error State is its MDH alone (Rule <<KLEE-SGR-error-state-locker-is-only-MDH>>, <<KLEE-error-state-transfer>>).
A PI cannot be in an Error State.

[[KLEE-rules-masked-implementations]]
=== Single-Share Key Export Rule for Masked Implementations

Any multi-share implementation of a Machine will always provision, import and export _all_ its keys and secrets as reconstructed values.
This keeps SCCs compact and ensures interoperability across architectures with different implementations.
(((KLEE, Machine, side-channel protection variants)))
Architecturally, all values are represented as a single share.
Side-channel analysis (SCA)-protected Machines are implementation variants of the same unprotected Machine, not separate specifications.
The only difference is the _SCProtection_ field of the MDH.

NOTE: While reconstructing or re-randomizing a key is in general inexpensive, for instance if the masks are generated
by a block cipher in counter mode,
an implementation that is using a slower method to generate the masks
may include shares or masks in the ADS to accelerate multiple-share reconstruction of a key.

[[KLEE-system-keys]]
=== System Keys and Randomly Generated Key Values

In a PI or SCC, System Keys are encoded as a 64-bit SKID used to retrieve the key from a system-specific SKS.
This replaces the key value itself with a usually smaller field, and may reduce the size of the PI or SCC.

The SKS resolves a SKID different from the all-ones value only as a function of the SKID,
provided it is allowed for the given _Machine_ and _MachinePolicy_.
The value of the key does not depend on _Machine_ and _MachinePolicy_.
For a Machine whose _MachinePolicy_ encodes permissions, a SKID allowed for a _MachinePolicy_ is allowed for every _MachinePolicy_ whose set bits are a subset of it.
The current privilege mode does not affect whether the SKS may resolve a given SKID.

A SKID other than the all-ones value that it does not or is not allowed to resolve transitions the locker to Error State _Invalid_ (see <<KLEE-Metadata-validity>>).

Whenever a SKID is resolved, the _UsagePolicy_ of the locker becomes the intersection of the permissions already encoded in the PI or SCC and those of the key (bits 0–3 or-ed, bit 4 and-ed), and its _Locality_ the union of the Localities in the PI or SCC and those of the key (each HW Binding subfield taking the larger value, bits 6–8 or-ed); if the two Boot Session entries are non-zero and differ, or the resulting _Locality_ names an unconfigured entry (<<KLEE-Localities>>), the locker transitions to Error State _Invalid_, as it does for a supplied MDH at provisioning.

The all-ones SKID (<<KLEE-KeyType-field>>) is not resolved by the SKS.
A SKID carried in an SCC is resolved only after the SCC has been authenticated.

In multi-share implementations, KLEE may copy System Key material from the SKS into the locker and expand it into multiple shares.
The key must still be exported as a SKID.
Any shares or masks included in the ADS (see <<KLEE-rules-masked-implementations>>) must not allow or facilitate recovery of the key's value from those values alone.

[[KLEE-locker-management]]
=== Locker Management Operations

Here we give the values of the `#immed7` field for `kl.mgmt`, and the semantics of the operations that they perform.

[[KLEE-management-immeds]]
.Values (decimal) of `#immed7` to be used for provisioning, importing, and exporting
[float="center",align="center",width="100%",cols="^7%,<27%,<66%",options="header"]
|===
| Value | Mnemonic                  |  Description
|  56   | `kl_cfg_provisioning`    |  Prepare a locker for provisioning.
|  57   | `kl_cfg_exporting`       |  Prepare a locker for export.
|  58   | `kl_cfg_importing`       |  Prepare a locker for import.
|  63   | `kl_cfg_management_end`  |  Complete current management operation.
|===

Depending on the previous state of the locker, the actual _State_ after a non-faulting `kl.mgmt` instruction may be different:

. After `kl.mgmt`, with #immed7 = `kl_cfg_importing`, the locker's _State_ becomes
.. `kl_cfg_ppi_importing` if the data originates from a locker whose provisioning operation had not been completed,
.. `kl_cfg_importing` otherwise, also when the data originates from a locker whose import or export had not been completed.
. After `kl.mgmt`, with #immed7 = `kl_cfg_exporting`, the locker's _State_ becomes
.. `kl_cfg_ppi_exporting` if the locker being exported contains the image of a locker whose provisioning operation had not been completed,
.. `kl_cfg_exporting` otherwise, also when the locker is in `kl_cfg_importing` or `kl_cfg_exporting`.

We now proceed to describe the semantics of `kl.mgmt`.

Three steps are common to every operation below and are not repeated in the description of each of them:

. `kl.mgmt` first checks that `klmanagedlocker` holds either the target locker's number or 32, and raises an illegal-instruction exception if it holds any other value;
. It affects `klmanagedlocker` according to the _State_ in which it leaves the target locker:
.. if that _State_ is a Configuration State, it writes the target locker's number to `klmanagedlocker`;
.. if that _State_ is a Complete State, including any Error State, it writes 32 to `klmanagedlocker`; and
.. if the instruction raises an exception without leaving the target locker in an Error State, `klmanagedlocker` is left unchanged, or set to 32 if the zeroizing step has left the target locker _Unconfigured_: the handler either resolves the condition or sets `klmanagedlocker` to 32 itself (<<KLEE-CSR-klmanagedlocker>>).
. `kl.mgmt` also clears `klstart` (it is the duty of software to restore `klstart` to allow interrupted management operations to be resumed).

Now we consider the specific semantics of `kl.mgmt` for each of the four operations it supports:

* `*kl.mgmt*` *is used to start a provisioning, resp., import process.*
+
--
Before issuing `kl.mgmt`, software must obtain the MDH. Let `ml` be this value.

NOTE: In the case we are starting an import process, `ml` must be first saved by software in its local state.
`ml` is then provided to the `kl.mgmt` operation used to complete the process in order to restore the _State_ the locker was in before the import process started.

A `kl.mgmt` of Form A, C or D is used to start a provisioning, resp., import process and provide `ml`.
It performs the following operations:

.. The target locker is zeroized. Bytes of the serialized `Content` that a management operation has not yet written read as zero through every architectural access (`kl.store`, `kl.mv`, verbatim export).
//.. It checks the validity of the fields of the provided MDH `ml`. If any are invalid according to <<KLEE-Metadata-validity>>, it transitions the locker to Error State _Invalid_.
.. If `#immed7` = `kl_cfg_importing` and `ml`._State_ is an Error State, the locker is immediately
    fully configured in that Error State, with the entire MDH given by the auxiliary input except that _AuxDataLen_ and _ADSDropped_ are set to 0 (Rule <<KLEE-SGR-clear-locker-content-error-state>>). If _State_ is 54 or 55, or 53 when `Zklexpire` is not implemented, then the _State_ is replaced by _Invalid_.
    The steps below are not applied: the locker holds only its MDH (<<KLEE-cryptographic-registers>>), no Machine is selected for execution,
    and no KLF capacity is allocated, so this configuration cannot fail.
    The whole configuration is performed by this one instruction, which is uninterruptible (Rule <<KLEE-IRR-uninterruptible-instructions>>) and opens no management operation, so
    no `kl.mgmt` with `#immed7` = `kl_cfg_management_end` follows.
    This is the _short import path_ of <<KLEE-error-state-transfer>>: we refer to that section for more details.
.. If `ml` is unsupported Metadata (see <<KLEE-MVR-open>>), KLEE exception `kl_exc_unsupported` is raised.
.. In case of *provisioning*:
... `ml`._State_ must be _Unconfigured_, else the Metadata is invalid (<<KLEE-MVR-open>>). _State_ is initially set to _Unconfigured_. This means that during the pre-flight checks described below, _State_ is _Unconfigured_ until it is successfully configured.
... _StateExtension_ and _MachineUse_ are set to 0; the values in the PI are ignored.
... _AuxDataLen_ and _ADSDropped_ must be 0. If either is non-zero in the MDH of a PI,
the locker is transitioned to Error State _Invalid_ (which is a Complete State) and the instruction terminates.
.. If `ml` is invalid Metadata (see <<KLEE-MVR-open>>), the locker is transitioned to Error State _Invalid_.
.. The implementation attempts to allocate KLF capacity according to the requirements of the _Machine_, _MachinePolicy_, and _SCProtection_ fields of the MDH, as prescribed by <<KLEE-length-rule>>. No other field must affect the amount of capacity required.
    If capacity allocation is not possible, KLEE exception `kl_exc_out_of_memory` is raised.
.. If *provisioning*: locker._State_ is set to `kl_cfg_provisioning`;
.. If *importing*: locker._State_ depending on `ml`._State_:
... In every case the opening applies steps 1–5 of <<KLEE-SCC-import>>, determining whether the ADS is retained from the MDH it loads and the implementation's supported maximum.
... If `ml`._State_ is a Valid State, then locker._State_ is set to `kl_cfg_importing`;
... If `ml`._State_ is `kl_cfg_importing` or `kl_cfg_exporting` (the image of an interrupted import or export of a locker in a Complete State), then locker._State_ is set to `kl_cfg_importing`;
... If the base type of `ml`._State_ is `pi`, then locker._State_ is set to `kl_cfg_ppi_importing` (<<KLEE-nested-state-base-types>>);
... If `ml`._State_ is _Unconfigured_, the Metadata is invalid (see <<KLEE-MVR-open>>).
.. In every case above in which a check fails, that is in which a KLEE exception is raised or the locker
transitions to Error State _Unsupported_ or _Invalid_, all fields of the MDH other than _State_ remain
zero and no KLF capacity is allocated; after `kl_exc_out_of_memory` the locker remains _Unconfigured_.
This does not apply to the configuration of a locker directly into an Error State from `ml`, which installs
the entire MDH.
--

* `*kl.mgmt*` *is used to start an export process.*
+
--
Let `ml` <- the MDH of the locker.
Software must first save this value in its local state to restore its _State_ when completing the export process.
`kl.mgmt` can be of Form A, C or D; its auxiliary input is ignored.
`kl.mgmt` performs the following operations:

.. If `ml`._State_ is _Unconfigured_, then: an illegal-instruction exception is raised.

.. If `ml`._State_ is an Error State, then: the locker is left unchanged and no management operation is opened (Rule <<KLEE-SGR-error-state-locker-is-only-MDH>>): the short export path is detailed in <<KLEE-error-state-transfer>>.

.. If `ml`._State_ is a Valid State, then:
The instruction prepares the locker to produce an SCC.
This includes encrypting its contents and computing the authentication tag(s)
as specified in <<KLEE-CC-management>>. Then, locker's _State_ is set to `kl_cfg_exporting`.
The opening `kl.mgmt` causes no changes to any field of the MDH other than _State_: an implementation that creates or changes an ADS, or uses _MachineUse_, keeps _AuxDataLen_ and _MachineUse_ current at all times, so that the MDH software reads before opening the export is the MDH the export authenticates.

.. If `ml`._State_ is a Partial State (we are exporting a not fully configured locker or we are initiating a nested locker export), then:

... No encryption or authentication occurs; the contents of the locker are exported verbatim, in the same order in which they appear in the PI (for a partially provisioned locker) or in the SCC (for a partially imported locker, or a locker previously prepared for export whose export process was itself interrupted).

... The locker's _State_ is set to `kl_cfg_ppi_exporting` or `kl_cfg_exporting` according to its base type (<<KLEE-nested-state-base-types>>).
--

* `*kl.mgmt*` *is issued with `kl_cfg_management_end`*
+
--
`kl.mgmt` with immediate `kl_cfg_management_end` reads first the MDH of the target locker.
Depending on whether MDH._State_ is

* `kl_cfg_provisioning`,
* `kl_cfg_importing`, `kl_cfg_ppi_importing`, resp.
* `kl_cfg_exporting`, `kl_cfg_ppi_exporting`,

the instruction will complete a provisioning, importing, resp., exporting process.

When completing an import or an export, the auxiliary operand `ml` is consumed only for its _State_ field,
which restores the locker's _State_ to the value that field held when the management operation was started.
No other field of the MDH is written from `ml`.

When an SCC import or locker export completes, authentication is checked
only if setting locker.MDH._State_ to `ml`._State_ restores a Complete State.
The probability of accepting an incorrect _State_ is negligible.
A nested completion only checks the base type and does not perform any authentication.

If locker.MDH._State_ is `kl_cfg_importing` or `kl_cfg_exporting`, `ml`._State_ must be a Complete State or a Configuration State of base type `scc`, i.e., `kl_cfg_importing` or `kl_cfg_exporting`;
if it is `kl_cfg_ppi_importing` or `kl_cfg_ppi_exporting`, `ml`._State_ must be a Configuration State of base type `pi`, i.e., `kl_cfg_provisioning`, `kl_cfg_ppi_importing` or `kl_cfg_ppi_exporting` (<<KLEE-nested-state-base-types>>).
Any other `ml`._State_, including a Complete State for a locker of base type `pi` and the values 61–63, raises an illegal-instruction exception.
A Complete `ml`._State_ is accepted only for a locker of base type `scc`, so that the clear `Content` of a partially provisioned locker can become usable only through the completion of its provisioning.
--

** `*kl.mgmt*` *is used to complete a provisioning process.*
+
--
`kl.mgmt` does not need a saved MDH from the start of the provisioning process, hence if a Form C or D was used in place of Form A, the auxiliary input is simply ignored.

Completing a provisioning requires _AuxDataLen_ = 0 and _ADSDropped_ = 0; if locker.MDH._State_ is `kl_cfg_provisioning` and either field is non-zero, the locker transitions to Error State _Invalid_ and the instruction terminates.

The operation makes the provisioned locker available to software by

... For _KeyType_ = 1, generating the key for the all-ones SKID (<<KLEE-KeyType-field>>) or applying the SKID resolution of <<KLEE-system-keys>>;
... Performing any necessary readjustment of the locker's content to turn it into the format internally consumed by the KLEE unit; and
... Setting _State_ to _Ready_, and _StateExtension_ and _MachineUse_ to 0.

A process may be preempted during a locker's provisioning.
Only the information in the original PI is exported by `kl.store` or `kl.mv`,
and it remains unencrypted.
During provisioning, any secret random material required to configure the locker must be generated only by the `kl.mgmt` instruction that completes provisioning. The same restriction applies to retrieving key material from a System Key Store and to deriving, expanding, or re-sharing that material.
This prevents such material from being exposed in an unencrypted export of a partially provisioned locker.
--

** `*kl.mgmt*` *is used to complete an import process.*
+
--
The software uses Form A, C or D of `kl.mgmt` to pass along the value of `ml` saved when the import process was started.
The image authenticated as ``AD[0]`` is the MDH held in the target locker — the image carried in the SCC and loaded when the import was started — with its _State_ field restored from `ml` and _ADSDropped_ cleared in the copy used for authentication (<<KLEE-SCC-import>>). The actual MDH field is not cleared by this computation.

The semantics are:

... If `ml`._State_ is a Complete State (we are importing the export of a fully configured locker)
.... locker.MDH._State_ is set to `ml`._State_.
.... The KLEE unit decrypts and authenticates the locker's content.
.... If authentication fails, the target locker is transitioned to Error State _Authentication Failed_. No exception is raised. Otherwise, if _KeyType_ = 1, the SKID is resolved and the narrowing of <<KLEE-system-keys>> is applied.
.... The KLEE unit performs any necessary readjustment of the locker's content to turn it into the format internally consumed by the KLEE unit.
This makes the locker available to software.
... If `ml`._State_ is not a Complete State (we are either importing the export of a not fully configured locker or a nested locker export):
.... locker.MDH._State_ is set to `ml`._State_.
--

[[KLEE-mgmt-completes-export,Use of kl.mgmt to complete an export process]]
** `*kl.mgmt*` *is used to complete an export process.*
+
--
Software uses Form A, C or D of `kl.mgmt` to supply the MDH value saved when the export process began.

Let `ml` be this auxiliary input.
Then:

.. The locker's _State_ is set to `ml`._State_.
.. If `ml`._State_ is a Complete State (i.e., including Error States), the instruction
restores the internal state of the locker to the clear format it was in when the export process was initiated and allows software to access it:
... The contents are decrypted and authenticated as when completing an import, with the MDH held in the locker as `AD[0]` and _ADSDropped_ cleared in the copy consumed by first-segment authentication.
... If the `SIV` check fails, the locker transitions to Error State _Authentication Failed_ and the instruction terminates; no exception is raised. Otherwise, if _KeyType_ = 1, the SKID is resolved and the narrowing of <<KLEE-system-keys>> is applied.
+
NOTE: An implementation may instead restore the clear contents from an internal copy only if the outcome is identical: the copy is usable only while the locker, its MDH, `SIV` and, when _AuxDataLen_ ≥ 2, `IMPQUAL` and `SIV2` still hold the values written by the opening `kl.mgmt`, and `ml`._State_ equals the _State_ at that time. The specification does not define any internal mechanisms by which an implementation can achieve this.

.. If `ml`._State_ is not a Complete State, no further changes to the locker's contents are made.
--

** *If* `*kl_cfg_management_end*` *is issued when the target locker's _State_ is _Unconfigured_ or a Complete State* (i.e., no management operation open on the target locker), the instruction is an illegal instruction.

[[KLEE-error-state-transfer]]
=== Export and Import of a Locker in an Error State

A locker in an Error State holds only its MDH (Rule <<KLEE-SGR-clear-locker-content-error-state>>), so there is nothing to
encrypt and nothing to authenticate. No SCC and no PCCC are produced, and neither direction opens a
management operation. Both paths are therefore shorter than those of <<KLEE-management-operations>>,
and both are exempt from the resumption machinery, since no `kl.load` or `kl.store` is issued.

When handling a locker in Error State, as well as its exported forms, most MDH fields are ignored and not
checked for validity (as in <<KLEE-Metadata-validity>>). In fact, only the _State_ field is checked.

*Exporting* a locker in an Error State consists of two steps and uses no `kl.mgmt`:
--
. Read the _State_ field with `kl.getst` (<<KLEE-instruction-getst>>) and find it to be an Error State.
. Read the MDH with `kl.getmd` or `kl.getmdv` (<<KLEE-instruction-getmd>>) and store those 16 bytes
  to memory. `kl.size` reports 16.

Issuing `kl.mgmt` with `#immed7` = `kl_cfg_exporting` on a locker in an Error State is permitted but
useless: it leaves the locker unchanged and opens no management operation
(<<KLEE-locker-management>>).
--

*Importing* such an image consists of one step:
--
. Issue `kl.mgmt` with `#immed7` = `kl_cfg_importing` and the 16-byte MDH
  as the auxiliary operand. The instruction performs the following steps:
  .. It zeroizes the locker named by the instruction and copies the MDH into it, with _AuxDataLen_ and _ADSDropped_ set to 0 (Rule <<KLEE-SGR-clear-locker-content-error-state>>).
  .. If _State_ is 54 or 55, or 53 when `Zklexpire` is not implemented, the _State_ is replaced by _Invalid_.

This operation is uninterruptible
  (Rule <<KLEE-IRR-uninterruptible-instructions>>), so the locker is never observed.
  Form C or D carries the whole MDH, as does a Form A taking it from the KLIOBUF.

No `kl.mgmt` with `#immed7` = `kl_cfg_management_end` follows, and issuing one is an illegal
instruction. The `SIV`, `SIV2` and `IMPQUAL` registers take no part in either path and need not be saved
for it.
--

[[KLEE-SCC-AEAD]]
=== The SCC Authenticated Encryption Scheme

The cryptographic scheme used in the export and import of SCCs is
a variant of AES-GCM-SIV cite:[DBLP-journals-iacr-GueronLL17,RFC8452].
The differences with respect to AES-GCM-SIV are:

. The block containing the lengths of Associated Data and Plaintext is not included in the evaluation of POLYVAL.
This is intentional: the information needed to fully determine the lengths of
all sections is already included in the MDH, and thus in the POLYVAL.
. The optional Nonce is omitted.
. A domain separation bit, `sep`, has been added to distinguish the two segments of the content that are sealed in an SCC: the fixed architecture-defined content (`sep` = 0) and the optional implementation-dependent content (`sep` = 1).
. For `sep` = 0, bit 47 of `AD[0]`, the unauthenticated _ADSDropped_ bit of the MDH (<<KLEE-Auxiliary-Data-Section>>), is cleared before `POLYVAL` is evaluated.

We define the Key Derivation (<<KLEE-SCC-key-derivation>>) and POLYVAL (<<KLEE-SCC-POLYVAL>>) functions first.
The generation of an SCC from a locker (<<KLEE-SCC-export>>) and the import of an SCC into a locker (<<KLEE-SCC-import>>) are defined next.

In the pseudocode of this section, `AESE256(K, B)` denotes the AES-256 encryption of the
128-bit block `B` under the 256-bit key `K`, as specified in FIPS 197 cite:[nist-fips-197].

[[KLEE-SCC-key-derivation]]
.RFC8452 Key Derivation
[]
----
function SCC_KeyDeriv(key : bits(256), nonce : bits(96))
    → struct{enc_key : bits(256), auth_key : bits(128)} =
{
  local A : array [0..5] of bits(128);
  local i : int;

  foreach(i from 0 to 5) do:
    A[i] ← AESE256(key, nonce @ bin(i,32));

  return struct {
    enc_key  = A[5][63:0] @ A[4][63:0] @ A[3][63:0] @ A[2][63:0],
    auth_key = A[1][63:0] @ A[0][63:0]
  }
}
----

NOTE: Due to the computational cost of the key derivation function, implementations may cache the derived keys.

[NOTE]
====
To reduce payload size, the AES-GCM-SIV-derived construction used for SCC import and export omits the nonce.
It relies instead on AES-GCM-SIV's resistance to nonce reuse and misuse. The construction remains secure for up to 2^64^ 128-bit blocks observed by an adversary.

This provides practical protection for client applications. On cloud servers, each virtual machine and supervisor domain should use a unique CSK. To transfer CCs between domains, M-mode firmware can import an SCC using the source domain's CSK and re-export it using the target domain's CSK.

The `SIV` (Synthetic IV), which is also the GCM-SIV authentication tag, is the encryption of the `POLYVAL` hash of the MDH with _ADSDropped_ cleared in the authentication copy, the Locality Secrets, and Content, concatenated in that order. In the `POLYVAL` pseudocode below, the input is represented as an array of 128-bit blocks, which are absorbed in increasing index order.
====

[[KLEE-SCC-POLYVAL]]
.Polyval Hashing Function
[]
----
function POLYVAL(auth_key : bits(128), blocks[0..n-1] : bits(128), n : int)
    → bits(128) =
{
  local tmp : bits(128) ← zeros(128);
  local i : int;

  foreach(i from 0 to n-1) do:
    tmp ← tmp xor blocks[i];
    tmp ← Montmul(tmp, auth_key);

  return tmp;
}
----

We now define `Montmul(a, b)`, the Montgomery multiplication operation used in POLYVAL.

The field F is GF(2)[`x`] modulo `x^128^ + x^127^ + x^126^ + x^121^ + 1`.

A 128-bit value `V` represents the element whose coefficient of `x^k^` is `V[k]`.
Both the byte order and the bit order run forward; this is the representation of
cite:[RFC8452] {sect}3, under which `x^0^` is the byte string `0x01` followed by
fifteen zero bytes, i.e., the value `1`.

`Montmul(a, b)` is not plain multiplication but Montgomery multiplication; it is: +
 +
`{fournbsp}{fournbsp}` `Montmul(a, b)` = `a` {interpunct} `b` {interpunct} `x^-128^` `{nbsp}{nbsp}` in the field F.

We now give the notation used for the inputs and outputs of the SCC encryption and decryption functions,
i.e., <<KLEE-SCC-GCM-SIV-enc>> and <<KLEE-SCC-GCM-SIV-dec>>:

* `AD[]` denotes the Associated Data as an array of `len_AD` 128-bit blocks, that is
  `AD[0] {vvert} AD[1] {vvert} {ellipsis} {vvert} AD[len_AD-1]`, in that order;
* `P[]`, resp., `C[]`, denotes a Plaintext, resp., a Ciphertext, as arrays of `len_PC`
  128-bit blocks, that is `P[0] {vvert} P[1] {vvert} {ellipsis} {vvert} P[len_PC-1]`,
  resp. `C[0] {vvert} C[1] {vvert} {ellipsis} {vvert} C[len_PC-1]`, in that order;
* `K` is a 256-bit Key;
* `N` is a 96-bit Nonce; and
* `SIV` is a 128-bit SIV/tag.

[NOTE]
====
As in AES-GCM-SIV, we use bit 127 to distinguish tag inputs (bit 127 takes the value 0) from
keystream inputs (1). This construction adds a second domain separation bit, `sep`, in bit
126 to distinguish architecture-defined content (`sep` = 0) from the ADS (`sep` = 1).
The security reduction is just one bit: the tag input carries 126 bits of the `POLYVAL`
result rather than 127, and the keystream counter block carries 94 bits of the `SIV` rather than
95.
====

// Both segments derive their keys from the same CSK and all-zero nonce.
// Without `sep`,
// only their Associated Data and SIV values would distinguish them. This does not imply an
// attack: a collision between `SIV` and `SIV2` has negligible probability. However, separation
// would then depend on those values rather than on the construction itself.
// Placing `sep` in bit 126 of both AES inputs makes the separation unconditional.
//
// * in the *tag* computation, `0 @ sep @ POLYVAL({ellipsis})[125:0]`, so that the same
//   Associated Data and plaintext yield different tags in the two segments; and
// * in the *keystream* counter block, `1 @ sep @ SIV[125:32] @` counter, so that the two segments
//   cannot share a keystream even if their SIVs were to collide.

[[KLEE-SCC-GCM-SIV-enc]]
.AES-GCM-SIV Encryption for SCC Generation
[]
----
function SCC_Encrypt(AD[] : array of bits(128), N : bits(96), sep: bits(1),
    P[] : array of bits(128), K : bits(256), len_AD : int, len_PC : int)
  → {SIV : bits(128), C[] : array of bits(128)} =
{
  local AD_auth : array [0..len_AD-1] of bits(128) ← AD[];

  enc_key, auth_key ← SCC_KeyDeriv(K,N);
  if (sep = 0) then:
    AD_auth[0][47] ← 0;
  SIV ← POLYVAL(auth_key, AD_auth || P, len_AD + len_PC);
  SIV[95:0] ← SIV[95:0] xor N;
  SIV ← AESE256(enc_key, 0 @ sep @ SIV[125:0]);

  foreach(i from 0 to len_PC - 1) do:
    C[i] ← P[i] xor AESE256(enc_key,
             1 @ sep @ SIV[125:32] @ bin((int(SIV[31:0]) + i) mod 2**32, 32));

  return ( SIV, C[] );
}
----

`len_PC` never exceeds `max_admissible` / 16 (<<KLEE-instruction-mv>>), and `len_AD` never exceeds 7.

[[KLEE-SCC-GCM-SIV-dec]]
.AES-GCM-SIV Decryption for SCC Import
[]
----
function SCC_Decrypt(AD[] : array of bits(128), N : bits(96), sep: bits(1),
    SIV : bits(128), C[] : array of bits(128), K : bits(256),
    len_AD : int, len_PC : int)
  → {correct : bool, P[] : array of bits(128)} =
{
  local AD_auth : array [0..len_AD-1] of bits(128) ← AD[];

  enc_key, auth_key ← SCC_KeyDeriv(K,N);
  if (sep = 0) then:
    AD_auth[0][47] ← 0;

  foreach(i from 0 to len_PC - 1) do:
    P[i] ← C[i] xor AESE256(enc_key,
             1 @ sep @ SIV[125:32] @ bin((int(SIV[31:0]) + i) mod 2**32, 32));

  s ← POLYVAL(auth_key, AD_auth || P, len_AD + len_PC);
  tmp ← s;
  tmp[95:0] ← tmp[95:0] xor N;
  tmp ← AESE256(enc_key, 0 @ sep @ tmp[125:0]);

  if (tmp != SIV) then:
    foreach(i from 0 to len_PC - 1)
      P[i] ← zeros(128);
    return ( false, P[] );

  return ( true, P[] );
}
----

NOTE: *Design Rationale for the Sealing Construction.*
The Locality Secrets are supplied to the AEAD as _associated data_ rather than mixed into the
Context Sealing Key through a KDF. Both approaches bind the SCC to the Locality set, but
using associated data is computationally less expensive. POLYVAL requires one `Montmul`
per 128-bit block and is thus significantly faster than most KDFs. This approach also
avoids re-deriving `enc_key` and `auth_key` when the Locality set changes.
Distinct Locality sets lead to the same SIV with collision probability 2^-126^.

[[KLEE-SCC-export]]
=== Generation of an SCC from a Fully Configured Locker

If the _State_ field is set to a Valid State, then ``K(i)`` is fully provisioned,
and opening the locker for export (`kl.mgmt Kd|K(Xd), #kl_cfg_exporting`) performs the following steps
to create the serialized, encrypted and authenticated SCC from the locker.

Regarding the Localities, the substitution rules in <<KLEE-Localities>> and <<KLEE-interaction-with-debug>> apply.
We define `LST_eff[j]` as the value of `LST` entry j after applying these substitution rules;
a non-implemented entry with no configured replacement contributes `zeros(128)` and makes the Metadata invalid at provisioning/import; an export is not refused on this ground, the resulting SCC being rejected at import. Entry 9 of `LST` is `hkllocality`, and entry 10 the effective register of <<KLEE-Localities>>: `skllocality`, or `vskllocality` when V=1.
In the export and import algorithms we then replace `LST[j]` with `LST_eff[j]`.

After `kl.clearads`, a fully configured locker has _AuxDataLen_ = 0 and _ADSDropped_ = 0 (<<KLEE-instruction-clearads>>). An SCC-shaped PCCC may instead carry _ADSDropped_ = 1 to preserve an interrupted import after `Content2` was dropped.

.Exporting a Fully Configured Locker ``K(i)``
--
. First, the Machine-dependent data is processed:
.. `saved_MDH` <- the MDH of ``K(i)`` immediately before its _State_ is set to `kl_cfg_exporting` (the image software saved beforehand), ``len_AD`` <- 1
.. ``AD[0]`` <- `saved_MDH`. `SCC_Encrypt` clears _ADSDropped_ in its local copy of this block before computing `SIV`; the `saved_MDH` returned in the SCC is unchanged.
.. foreach(_j_ from 0 to 10) do:
... If `saved_MDH`._Locality_ includes Locality #j, then ``AD[len_AD]`` <-  ``LST_eff[``_j_``]``, ``len_AD`` <- ``len_AD`` + 1
.. `len_PC` <- the number of 128-bit blocks of `Content1` (Section 5.a of <<KLEE-SCC>>).
.. `SIV`, `Content1~CT~[]` <- `SCC_Encrypt(AD, zeros(96), 0, K(i).Content1~PT~[], CSK, len_AD, len_PC)`
. Second, if _AuxDataLen_ {ge} 2 then: the implementation-dependent data is processed:
.. `len_AD2` <- 2, ``AD2[0]`` <- ``K(i)``.`IMPQUAL`, ``AD2[1]`` <- `SIV`.
.. `len_PC2` <- the number of 128-bit blocks of `Content2` (Section 5.b of <<KLEE-SCC>>), that is _AuxDataLen_ − 2.
.. `SIV2`, `Content2~CT~[]` <- `SCC_Encrypt(AD2, zeros(96), 1, K(i).Content2~PT~[], CSK, len_AD2, len_PC2)`
. Finally, if _AuxDataLen_ = 0, then:
.. return(`saved_MDH`, `SIV`, `Content1~CT~[]`)
. else:
.. return(`saved_MDH`, `SIV`, `IMPQUAL`, `SIV2`, `Content1~CT~[]` and `Content2~CT~[]`) (note that `Content2~CT~[]` may be empty)
--

// Of the returned values, `SIV`, `SIV2` and `IMPQUAL` are placed in the CSRs `acesivl`/`acesivh`,
// `acesiv2l`/`acesiv2h` and `aceiql`/`aceiqh`, from which software stores them to memory; the ciphertext
// remains in the locker, whence `kl.store` (<<KLEE-instruction-store>>) transfers it; and `saved_MDH` is the
// image software already holds, which `kl.getmd*` (<<KLEE-instruction-getmd>>) also returns.
//
// If _AuxDataLen_ = 0, then `SIV2` and `IMPQUAL` are not generated, and therefore
// `acesiv2l`/`acesiv2h` and `aceiql`/`aceiqh` are not written to.
// They may contain stale values, but this is not an issue as they are not exported to memory in this case.

[NOTE]
====
A locker in an Error State is not exported by this procedure (Rule <<KLEE-SGR-error-state-locker-is-only-MDH>>).
====

[IMPORTANT]
====
Taking `SIV` as ``AD2[1]`` binds the two payloads together, so that `SIV2` and
the keystream of the second segment change whenever the
first payload changes; an attacker cannot graft the Implementation-Specific ADS of one SCC onto the architecture-dependent part of another.
====

[NOTE]
====
If an export operation is completed prematurely, an authentication error results upon import (see next section).
If an import operation is completed prematurely, an authentication error results.
If any of the two operations is not completed, various types of error conditions will occur because _State_ is a Configuration State.
====

[[KLEE-SCC-import]]
=== Decryption and Authentication of a Complete SCC into a Locker

The following algorithm describes the import of the SCC of a fully configured locker as a whole.
Steps 1 to 5 are performed by the `kl.mgmt Kd|K(Xd), #kl_cfg_importing` that opens the import
(<<KLEE-locker-management>>), step 6 by the `kl.load` or locker-writing `kl.mv` instructions that follow it
(<<KLEE-instruction-load>>, <<KLEE-instruction-mv>>), and the remaining steps by
`kl.mgmt Kd|K(Xd), #kl_cfg_management_end`, which decrypts and authenticates the SCC.

.Importing a Fully Configured Locker ``K(i)``
--
 . Clear ``K(i)``.
 . Load `M`, the MDH from the SCC, into ``K(i)``.MDH.
 . Check correctness of `M`, and whether the Machine is supported.
 . Determine the SCC layout from `M`.
 . If `M`._AuxDataLen_ {ge} 2 and either `M`._ADSDropped_ = 1 or `M`._AuxDataLen_ exceeds the implementation's maximum for the given Machine, set ``K(i)``.MDH._ADSDropped_ to 1. Otherwise set it to 0. This changes only the length of `Content2`: when _AuxDataLen_ {ge} 2, `IMPQUAL` and `SIV2` remain present and _ContentOffset_ remains 48.
 . Load the rest of the SCC up to the length described by the resulting working MDH. If _ADSDropped_ = 1, this includes `SIV`, `IMPQUAL`, `SIV2`, and `Content1`, but no `Content2`.
 . `saved_MDH` <- the MDH image held in ``K(i)``, that is `M` with the working value of _ADSDropped_ and with its _State_ field restored from the auxiliary operand of the completing `kl.mgmt`.
 . ``AD[0]`` <- `saved_MDH`, ``len_AD`` <- 1. `SCC_Decrypt` clears _ADSDropped_ in its local copy of `AD[0]` before authenticating it; the MDH held in ``K(i)`` is unchanged by that computation.
 . foreach (`j` from 0 to 10) do:
 .. If `saved_MDH`._Locality_ includes Locality #j, then ``AD[len_AD]`` <-  ``LST_eff[j]``, ``len_AD`` <- ``len_AD`` + 1
 . `len_PC` <- the number of 128-bit blocks of `Content1` (Section 5.a of <<KLEE-SCC>>).
 . `correct`, ``K(i)``.`Content1` <- `SCC_Decrypt(AD, zeros(96), 0, SIV, K(i).Content1, CSK, len_AD, len_PC)`.
 . If `correct` {ne} `true`, the SCC is rejected: ``K(i)`` transitions to Error State `kl_state_mgmt_auth` (Rule <<KLEE-SGR-clear-locker-content-error-state>>).
 . Second, if ``K(i)``.MDH._AuxDataLen_ {ge} 2 and ``K(i)``.MDH._ADSDropped_ = 0, the implementation-dependent data is processed:
.. `len_AD2` <- 2, ``AD2[0]`` <- ``K(i)``.`IMPQUAL`, ``AD2[1]`` <- `SIV`.
.. If ``K(i)``.`IMPQUAL` = `zeros(32) @ klmimpid @ klmarchid @ klmvendorid` then:
... `len_PC2` <- the number of 128-bit blocks of `Content2` (Section 5.b of <<KLEE-SCC>>), that is ``K(i)``.MDH._AuxDataLen_ − 2.
... `correct`, ``K(i)``.`Content2` <- `SCC_Decrypt(AD2, zeros(96), 1, SIV2, K(i).Content2, CSK, len_AD2, len_PC2)`.
.. else:
... `correct` <- `false`.
 . If second-segment processing was attempted and `correct` {ne} `true`, drop `Content2` and set ``K(i)``.MDH._ADSDropped_ to 1.
 . If ``K(i)``.MDH._AuxDataLen_ = 0 or ``K(i)``.MDH._ADSDropped_ = 1, import completes using only the architecture-dependent content. The state machine must establish a consistent internal state and set _ADSDropped_ to 0. If no replacement ADS is generated, it sets _AuxDataLen_ to 0; if it generates replacement ADS, during completion or later, it sets _AuxDataLen_ to the appropriate value, which is at least 2. Otherwise the successfully imported ADS is retained, _AuxDataLen_ is preserved, and _ADSDropped_ is set to 0. A later export uses these current values: it emits no ADS when _AuxDataLen_ = 0, or emits the newly generated or retained ADS when _AuxDataLen_ {ge} 2.
--

[NOTE]
====
This procedure ensures that if the SCC's optional implementation-specific ADS makes the SCC too large to fit in a locker, or if that ADS is incompatible, the implementation ignores the optional data, but keeps the architecture-dependent content: Only a failure of the first authentication (SIV) rejects the entire SCC.
====

[[KLEE-import-and-DIEL]]
=== Import and Data-Independent Execution Latency

_This section is informative and non-normative._

In KLEE, Data-Independent Execution Latency (DIEL) applies only to the cryptographic operations it performs, including the decryption and authentication of SCC contents.

All locker management instructions are split into three phases: An initial `kl.mgmt`, load/store instructions, and a final `kl.mgmt`.
The two `kl.mgmt` instructions perform no memory accesses.

The dependencies of the `kl.mgmt` instructions' timing are limited to very few factors:

. Actual size of the SCC to export, including the implementation-dependent part.
. `SIV` or `SIV2` authentication failures on import;
. `IMPQUAL` mismatches on import; and
. Attempts to import SCCs whose total length exceeds what the target implementation supports for the given Machine.
  In this case, the implementation-dependent part is necessarily unsupported and `Content2` is not loaded (<<KLEE-SCC-import>>); only the architecture-dependent part is authenticated and decrypted (if the resulting _State_ is a Complete State) and used.

Apart from these factors, only the number of blocks to process may affect the timing of the `kl.mgmt` instructions.
The timing of the processing of each block is independent of the actual data being processed.

[[KLEE-state-save-and-restore-order]]
== Context Switching, KLEE State Save and Restore Order

Lower-privileged modes may save, restore, or overwrite lockers configured by higher-privileged modes.
Hence, higher-privileged software must clear any lockers it uses before relinquishing control to lower-privileged modes.
If it uses the KLIOBUF, `klstart`, `klmanagedlocker` or the authentication registers while a lower-privileged context's KLEE state is live, it must save that state beforehand and restore it afterwards, as at a context switch (below), so that the lower-privileged context observes its own values and none of the higher-privileged mode's data; on return to a different context the KLIOBUF holds that context's saved contents or, with `kliobuflen` = 0, nothing.
When switching to a lower-privileged component, only lockers previously saved for that same component may be restored, and lockers that are not part of that component's KLEE state must be erased.

_The remainder of this section is informative and non-normative._

This aligns with standard context-switching hygiene.

// ////////////////////////////////////////////////////////////////////

This is the recommended order for saving and restoring the KLEE state.

* Save order:

. Save `klstart` first, since every later step may clear it.
. Save the raw value of `klmanagedlocker`.
. If `Zklio` is present:
.. Save `kliobuflen` and `kliobuftop`.
.. If `kliobuflen` is nonzero, save the buffer contents using `kl.output` with `klstart` = 0 and `kliobuftop` raised to `kliobuflen`, since the `kl.mgmt` of a locker export may take `ml` from the KLIOBUF (<<KLEE-usage-input-output>>).
. If the saved `klmanagedlocker` is in [0..31], read the MDH of the locker it indexes using `kl.getmd*` and select the State-appropriate save path:
.. If the locker is _Unconfigured_, save no locker image.
.. If the locker is in an Error State, save its MDH using the short Error-State path (<<KLEE-error-state-transfer>>).
.. Otherwise, export the locker using the applicable Complete- or Configuration-State path. This export precedes every other `kl.mgmt` that could overwrite the authentication registers.
. Save every other non-Unconfigured locker using the path appropriate to its State, with the working value of `klmanagedlocker` set to 32 before and after each export.

* Restore order:

. Restore the lockers other than the locker indexed by the saved `klmanagedlocker`, with the working value of `klmanagedlocker` set to 32 before and after each import.
. If the saved `klmanagedlocker` is in [0..31] and an image was saved for the locker it indexes, restore that locker using the path appropriate to its saved State, with the working value of `klmanagedlocker` set to 32 before opening its import.
. If `Zklio` is present:
.. Restore `kliobuflen`, which zeroes the buffer and sets `kliobuftop`.
.. Restore the buffer contents, if saved, using `kl.input` with `klstart` = 0 and `kliobuftop` = `kliobuflen`.
.. Restore `kliobuftop`.
. Restore the raw saved value of `klmanagedlocker`.
. Restore `klstart` last, since every earlier step may clear it.

A handler that passes `ml` through the KLIOBUF configures `kliobuflen` {ge} 16 for the locker exports and imports and restores the saved value afterwards.

A handler must treat `klmanagedlocker` as a hint and check the MDH of the locker it names before selecting a save path. For example, user software may clear `K0`, write `klmanagedlocker` = 0, and then enter a handler. Reading the all-zero MDH identifies `K0` as _Unconfigured_, so the handler saves no image for it and does not attempt an export that would raise an illegal-instruction exception.

[[KLEE-CSK-requirements]]
== Architectural Requirements on the Context Sealing Key

The KLEE unit must have a configured Context Sealing Key (CSK) before it can operate. Without an active CSK, every KLEE instruction and every KLEE CSR access raises `kl_exc_no_csk`, except access to the `mklcsk` CSR group, to the Locality Secret CSR groups (<<Zkl-ISA-priv.adoc#KLEE-CSR-locality-groups>>), which are configured independently of the CSK, and to the read-only identification CSRs `klmvendorid`, `klmarchid`, `klmimpid`, and `klmaxiobuflen` (<<KLEE-CSR-impl-ids>>, <<KLEE-CSR-klmaxiobuflen>>). The latter CSRs remain readable to allow firmware to identify the KLEE unit without having to configure it.

A CSK can be set in one of four mutually exclusive ways:

. A value programmed by M-mode through the `mklcsk` CSR group (see <<Zkl-ISA-priv.adoc#KLEE-CSR-mklcsk>>).
. A separate secure HW block (e.g., Caliptra cite:[caliptra]), or a port to a secure HW block, which is exclusive to M-mode, is used to configure CSK values and export them using a dedicated interface based on public key encryption.
. A fixed, hardwired value, generated at manufacturing time (either per die or shared across batches).
. A value generated by a secure RBG (see <<KLEE-RBG>>) at boot and not accessible to any software.

The third and fourth models are primarily suited to specialized embedded deployments: a hardwired CSK cannot be reconfigured or revoked, while a boot-generated CSK cannot preserve SCCs across power loss.
Under the fourth model, all harts in a well-defined subsystem of a SoC share a CSK and cannot exchange SCCs with other subsystems. The CSK survives a single hart's reset or fatal condition and is regenerated only at subsystem power-on reset.

In the second model, only M-mode may request that the secure hardware block configure its hart's CSK, using a handle or wrapped key. The clear key must not be exposed to any software, including M-mode.
Addressing and key transport are platform-specific and outside the scope of this specification.

The KLEE unit is immediately available under the third model; under the other models, it becomes available only after a CSK has been established. A hart reset resets the associated KLEE state (<<KLEE-reset-and-m-mode-only>>). In the first and second models, this includes the configurable CSK, leaving the unit unavailable until the CSK is re-established.

NOTE: When the CSK is shared across devices, CCs intended to be device-bound must set _Locality_ to include _ChipScrt_ or _DevScrt_.

Except for in M-mode and in the first model, CSK values must _never_ be readable by software in clear.
//An implementation that permits CSK reprogramming via the `mklcsk` CSR group must follow the activation rules in <<Zkl-ISA-priv.adoc#KLEE-CSR-mklcsk>>.

[IMPORTANT]
====
When a process migrates between harts, its SCCs should remain importable, requiring the destination hart to use the same CSK as the source. The OS and hypervisor should ensure that M-mode establishes this CSK on the destination hart. The mechanism for supervisor software to request this operation is platform-dependent and outside the scope of this specification.
Under the fourth model, this requirement can be met only within the subsystem sharing the CSK, not across subsystems.
Unless software handles the differences, it may migrate a process only between harts whose KLEE units have identical values for `klmvendorid`, `klmarchid`, `klmimpid`, and `klmaxiobuflen` and implement the same extensions and Machines.
====

M-mode firmware must account for the configuration model used for the CSK. Persistence mechanisms for configurable CSKs are implementation-specific. Transferring a CSK to another endpoint—such as the M-mode firmware of another device, a local TPM (for example, to preserve the CSK across suspension or host hibernation), or a cloud-based HSM—*requires* an authenticated public-key wrapping mechanism. Such a mechanism is outside the scope of this specification.

[[KLEE-reset-and-m-mode-only]]
== KLEE Unit Reset and M-mode-only Harts

A _KLEE unit reset_ of a hart resets that hart's KLEE architectural state
(cf. <<KLEE-out-of-reset-unpriv>> and <<Zkl-ISA-priv.adoc#KLEE-out-of-reset-priv>>);
in a KLEE unit shared by several harts it affects only that hart's state, any shared Locality Secrets excepted.
A hart reset implies a KLEE unit reset of that hart, and so does a fatal condition, with the differences stated in <<KLEE-error-architecture>>.
A hardwired CSK is not affected by reset.

On a hart without the KLEE Privileged Architecture (<<KLEE-error-architecture>>), the CSK is established by M-mode through a model of <<KLEE-CSK-requirements>>, every software-programmable Locality Secret whose CSR group is not implemented is unconfigured (<<KLEE-Localities>>), and `KLS` is treated as Initial; which CSRs of <<Zkl-ISA-priv.adoc#KLEE-priv>> may exist on such a hart is stated there.

[[KLEE-out-of-reset-unpriv]]
== KLEE Unprivileged State out of Reset

This section and <<Zkl-ISA-priv.adoc#KLEE-out-of-reset-priv>> are the authoritative statement of KLEE state out of
reset. Out of KLEE unit reset:

. All lockers are in State _Unconfigured_ with zeroized contents.
. If `Zklio` is available, `kliobuflen` = 0 (i.e., the KLIOBUF unconfigured), `kliobuftop` = 0, and the KLIOBUF is zeroized;
. `klstart` = 0;
. The value of `klmanagedlocker` is 32;
. The three authentication registers of <<KLEE-KLF>> are zero.

[[KLEE-interaction-with-debug]]
== Interaction with Debug Mode

All KLEE state is inaccessible in Debug mode, and no KLEE instruction may be
executed in it, unless an implementation-defined _authenticated-debug_ signal
is asserted.

[NOTE]
====
The natural source for the authenticated-debug signal is the authentication
interface of the Debug Module defined by the RISC-V Debug specification
(`dmstatus.authenticated`); the mapping is implementation-defined.
====

In authenticated Debug mode:

. KLEE instructions and CSRs are accessible with M-mode privilege, subject to the exceptions below.
. The `mklcsk` CSR group is inaccessible for both reads and writes. Entering authenticated Debug mode neither zeroizes nor replaces the CSK; the active CSK remains available to management instructions.
. A CC may be _used_ only if bit 4 of its _UsagePolicy_ field (<<KLEE-Metadata>>) is set; bits 0–3 are not evaluated in Debug mode. Debug code is otherwise limited to management operations. It may export existing contexts as SCCs, provision and use contexts created for Debug mode, and restore the saved state before exiting. An existing CC may be used only if its _UsagePolicy_ explicitly authorizes Debug-mode use.

Upon entering Debug mode while the authenticated-debug signal is _deasserted_:

. All lockers are zeroized and set to _Unconfigured_.
. The KLIOBUF is zeroized, and `kliobuflen`, `kliobuftop`, and `klstart` are set to zero.
. All applicable `*llockerstatus` fields are set to _Dirty_; every `KLS` field that is not Off is set to _Dirty_.
. The software-configurable Locality Secrets — _PhysBootScrt_, _VirtBootScrt_, _MLocality_, _HLocality_, and _SLocality_ (`mklphysbootscrt`, `hklvirtbootscrt`, `mkllocality`, `hkllocality`, `skllocality`, `vskllocality`) — are zeroized. Their CSRs subsequently read as zero.
. The HW Binding Group entries cannot be zeroized and are therefore _masked_: until the next hart reset each such entry is _unconfigured_ for this hart (<<KLEE-Localities>>). A PI or SCC whose _Locality_ names a masked entry is invalid Metadata, and chain substitution does not substitute a masked entry.
. The CSK is zeroized _and_ thus is essentially unconfigured. If the CSK is hardwired, or shared under the fourth model of <<KLEE-CSK-requirements>>, the KLEE unit of the hart has no active CSK until the next hart reset, and every access that <<KLEE-CSK-requirements>> does not exempt raises `kl_exc_no_csk`. A shared CSK itself is not modified. At no time does the KLEE unit use an all-zero CSK or an all-zero HW Binding entry as key material.

[NOTE]
====
Normal execution cannot resume after entry into unauthenticated Debug mode because the KLEE state has been destroyed.

Debugging that preserves KLEE state therefore requires authenticated Debug mode. Recovery requires a hart reset, which restores access to the hardwired HW Binding values and, under the third CSK model, the hardwired CSK, followed by re-establishment of the CSK and Locality Secrets by the privileged software stack and re-provisioning of the contexts.

Under the programmable CSK models, if M-mode re-establishes the same CSK, SCCs exported before entry into Debug mode become importable again, providing a complete recovery path through the ordinary context-saving mechanisms.
====
