[[KLEE-unpriv-intro]]
== Introduction

KLEE lets software perform high-performance cryptographic operations without giving it direct access to
the keys or to other critical derived value. The fundamental features it provides are:

* *Atomic operations.* Each cryptographic operation is atomic, so no intermediate value can leak through memory read exploits.
If an instruction performs several distinct cryptographic operations,
such an instruction can only be interrupted between these operations.

* *Splitting of complex algorithms into smaller atomic operations.* As opposed to some CISC architectures and instead
aligning with RISC-V philosophy, KLEE does not offer instructions that perform the operations of complex modes of operation on inputs of arbitrary length.

* *Hidden cryptographic state.* KLEE operations do not reveal keys and other critical values.

* *A single interface for many primitives*, instead of separate instructions per primitive:
 ** Primitives alone do not suffice for modes such as AES-GCM-SIV, XTS, and OCB, where leaked derived keys or intermediate values compromise security. KLEE therefore also defines modes of operation, among them CTR, GCM, and CMAC, and secure key derivation.
 ** Encrypt-only and decrypt-only versions reduce misuse, and versions with a preset IV or nonce keep it confidential.
 The modes work with AES-128, -192, -256, and other block ciphers such as SM4.
 ** The interface also supports hash functions, public-key and post-quantum algorithms, and SCA-resistant implementations.
 ** When side-channel protected implementations of cryptographic operations are available, they are simply variants of the standard algorithms, and they can be used in place of the latter without changes to the code.
 ** Implementations need not support every algorithm and variant thereof: following RISC-V practice, KLEE defines subextensions and leaves requirements to the RISC-V profiles.

* *Support for context switch, persistence, sleep, hibernation, and VM migration.*

* *Scalability.* One ISA and ABI serve embedded to server cores.

We next introduce the concepts on which KLEE realizes these features.

[[KLEE-concepts]]
=== Fundamental Concepts and Definitions

Cryptographic Context:::
(((Cryptographic Context)))
Every KLEE instruction runs within the contraints set by a *Cryptographic Context* (CC).
A CC is an indivisible structure consisting of a *Metadata Header* (MDH) and *Content*.
(((Cryptographic Context, Content)))
The Content holds the secrets, usually keys, and other sensitive material.
(((Cryptographic Context, Metadata Header)))
The MDH has a fixed-format, and it restricts the use of the secrets to one set of cryptographic algorithms and can enforce usage
constraints by process, VM, security state, boot cycle, expiration date, or other policies
The Metadata requires integrity, except for explicitly identified format hints, and the layout-preserving fields that hints make inactive; the Content requires integrity and confidentiality.
KLEE and the algorithms it implements enforce these requirements architecturally.

Cryptographic Locker:::
(((Cryptographic Locker)))
CCs are created in *Cryptographic Lockers* (_lockers_ for short), per-hart architectural containers that safeguard their contents.
*Provisioning* a locker writes Metadata and Content into it and binds them into a CC.
A CC is usable only while it resides in a locker, where only the KLEE unit accesses or modifies it, under the rules of the architecture and of its Machine; no instruction extracts the Content in a way that compromises its confidentiality.

KLEE Machine:::
(((Machines)))
(((Cryptographic Context, object-oriented)))
A *KLEE Machine* (short: _Machine_) is a state machine that implements one or more cryptographic functions (primitives, modes, protocols) through the interface of this specification.
The metadata of a locker encodes it in a 16-bit identifier.
A small set of KLEE instructions operates the Machines: they take this identifier from the metadata and standard RISC-V inputs and outputs, such as GPRs, vector registers and memory, and their semantics depend on the Machine.
A CC thus encapsulates Machine-specific behavior, so that different primitives (e.g., AES-128, AES-256 and SM4) can be used in the same modes (e.g., ECB, GCM-SIV and XTS) without changing the compiled code. Side-channel-resistant variants are supported transparently.

Sealed Cryptographic Context:::
(((Cryptographic Context, sealed)))
For context switching, a CC can be *exported* from a locker as a *Sealed Cryptographic Context* (SCC), an encrypted and authenticated representation that can later be *imported* into a locker. Export and import use a _Context Sealing Key_ (CSK), which M-mode may be able to program. An SCC sealed under one CSK cannot be imported under another, which separates spatial and temporal domains cryptographically.

Usage Control Policy:::
+
--
(((Cryptographic Context, usage control)))
(((Cryptographic Context, management operations)))
(((Cryptographic Context, usage operations)))
KLEE distinguishes *management* operations from *usage* operations on CCs and lockers.
(((Cryptographic Context, export)))
Management operations are classified as

* *configuration* (e.g., *provisioning*, SCC *import*, and *cloning*, *renaming* and *swapping* lockers),
* *export* of a locker as an SCC, and
* *clearing* a locker, i.e., freeing it, deleting any secret it contains.

Usage operations are cryptographic operations and state changes.

To prevent denial of service, management operations are less restricted than usage operations: _Usage Control_ policies restrict only usage operations.
--

Localities:::
(((Cryptographic Context, Locality)))
KLEE can bind a CC to *Localities*, which restrict its use to specific devices or device classes, hardware configurations, physical or virtual boot cycles, and process domains at various privilege modes.
// The Localities act as _tweaks_ in the encryption and decryption of SCCs.

[[KLEE-architectural-model]]
=== Architectural Model

KLEE is architected as an interface to an _attached_ unit: its instructions are messages over a tightly coupled coprocessor interface, and the KLEE unit executes them independently of the issuing hart and returns the results.
This keeps the hart side simple: software implements the logic of locker configuration, the KLEE unit the cryptography, and several cores may share one KLEE unit.

The specification defines architectural behavior only, not implementation:
KLEE may be integrated into a CPU core or be a distinct hardware unit, with separate architectural state per client hart, and the same code runs on both.

KLEE may be emulated, partly or completely, in M-mode firmware: an implementation may, for example, perform symmetric operations (<<Zkl-ISA-machines.adoc#KLEE-states-symmetric>>) in the KLEE unit and emulate public-key cryptography (<<Zkl-ISA-machines.adoc#KLEE-ECC>>, <<Zkl-ISA-machines.adoc#KLEE-PQC>>), whose very large states then reside in secure memory that meets the requirements of <<KLEE-KLF>>, such as on-chip SRAM reserved to M-mode.

Locker state must never be accessible in the clear to any privileged mode except M-mode and authenticated Debug mode.
KLEE implementations in S/VS-mode or HS-mode are therefore forbidden: instructions and Machines may be emulated only in M-mode.
Trap-and-emulate and on-demand (lazy) SCC import rely on the ``*llockerstatus`` CSRs (<<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>>).

[[KLEE-Prerequisites]]
=== Prerequisites

A conformant implementation of KLEE requires the RISC-V External Debug Security extension.

It also requires that the KLEE exceptions defined in <Zkl-ISA-priv.adoc#KLEE-exceptions>>> be implemented and raised as the unprivileged architecture mandates.

Where the KLEE unit or its Machines need an RBG, it must use an entropy source that meets the requirements of the `Zkr` specification cite:[RISCV-ISA-Unpriv], conditioned by a DRBG compliant with NIST SP 800-90A cite:[nist-SP-800-90-r1] or an equivalent standard.
Rule <<KLEE-GR-rbg-failure>> states what happens when the RBG fails.

`Zkl` conformance requires:

. at least one of `Zklv` and `Zklio`;
. AES128, AES192 and AES256 in ECB and GCM modes, AES128 and AES256 in GCM-SIV mode, and SHA2,
as defined in <<Zkl-ISA-machines.adoc#KLEE-Machines>>; and
. `Zklmem`, in hardware or by trap-and-emulate (<<KLEE-error-architecture>>).

KLEE instructions may raise various exceptions.
Besides the standard RISC-V exception types, KLEE also has a few own exception types, listed in <<Zkl-ISA-priv.adoc#KLEE-priv-extensions>>.

With trap-and-emulate, the hardware raises an illegal-instruction exception for the instructions it does not implement, which the platform must deliver to M-mode (`medeleg` bit 2 zero); the encodings are assigned, not reserved (<<KLEE-illegal-instruction-grounds>>).
`Zklmv` must then be in hardware, since the emulating code moves data between memory and the locker with it.
`kl.load` and `kl.store` are thus always present; `Zklmv` and `Zklexpire` are otherwise optional.

`Zklv` requires the KLV subset of the vector extension (<<KLEE-KLV>>) with `VLEN` {ge} 128, that is `Zvl128b` or a larger `Zvl*b`, on which every vector Form that carries an MDH or a 128-bit block depends.

The principal KLEE instructions, defined in full below, are:

* `kl.mgmt` (<<KLEE-instruction-mgmt>>) moves a locker through the stages of its management lifecycle, and,
with the KLEE memory operations `kl.load` (<<KLEE-instruction-load>>), `kl.store` (<<KLEE-instruction-store>>), `kl.mvin` and `kl.mvout` (<<KLEE-instruction-mv>>),
performs the management operations (<<KLEE-management-operations>>):
 ** *provisioning* loads metadata and clear Content into a locker, binding them;
 ** *export* writes a locker to memory as an SCC;
 ** *import* loads an SCC into a locker; and
 ** each takes several instructions, except on a locker in an Error State (<<KLEE-error-state-transfer>>).
* `kl.clear` (<<KLEE-instruction-clear>>) unconfigures and clears a locker. It is a management instruction, but never part of a multi-instruction management operation.
* `kl.exec` (<<KLEE-instruction-exec>>) performs the cryptographic operations that the Machine configured in a locker defines for the current state of the locker.
* `kl.setst` (<<KLEE-instruction-setst>>) moves the CC in a locker between the states of its Machine.
* `kl.getmd*` (<<KLEE-instruction-getmd>>) reads the metadata of a locker. The pseudo-instruction `kl.getst` (<<KLEE-instruction-getst>>), built on `kl.getmdl`, extracts the state of a locker from its MDH, and thus also reports errors.

[[KLEE-cryptographic-registers]]
== Cryptographic Lockers

{empty}
(((Cryptographic Context)))
KLEE defines 32 Cryptographic Lockers, `K0`–`K31`.
Like GPRs or vector registers, lockers are per-hart architectural state, and they are not separated by privilege mode: a hart sees the same lockers in every mode.
Unlike a conventional register, a locker can be _unconfigured_, that is hold no CC.

A locker is addressed like a conventional register, by a 5-bit immediate.
With `Zklind`, a locker can also be addressed indirectly, by a GPR value, and an encoding bit selects the mode: the full specification of `Zklind` is given in <<KLEE-indirect-lockers>>.
Some management instructions may also name the locker under management, written `KM` (Rule <<KLEE-GR-klmanagedlocker-override>>).

The CC in a configured locker consists of a Metadata Header (MDH) and `Content` (<<KLEE-concepts>>).
The _i_-th locker is denoted `K(i)`, its MDH `K(i).MDH`, and its content `K(i).Content`.
During import and export, and in an SCC, the content consists of two consecutive arrays of 128-bit blocks:
`Content1`, the architected content that <<Zkl-ISA-machines.adoc#KLEE-Machines>> specifies for each Machine,
and `Content2`, any implementation-specific content.

[[KLEE-KLF]]
== The Cryptographic Locker File and Authentication Information

(((Cryptographic Locker File)))Lockers reside in a per-hart _cryptographic locker file_ (KLF), a memory that only the KLEE implementation can access.
If the implementation is partly or fully emulated, only M-mode firmware can access the KLF, through an implementation-defined mechanism that must be provided.

The KLF guarantees the confidentiality and integrity of its contents, including against rollback through any access this specification does not permit.
KLF accesses need no hardware hardening against physical side-channel attacks, except that side-channel-protected implementations of the Machines of the KLEE unit must protect them too.

It is recommended that `SCC_KeyDeriv`, `SCC_Encrypt`, `SCC_Decrypt`, and every use of the CSK and of the keys derived from it have side-channel protection not weaker than the highest _SCProtection_ level, in the implementation's ordering, that the implementation supports for any Machine.

NOTE: The KLF, as a memory device, must resist rollback, but individual lockers need not, and cannot, resist rollback through export and import.
Re-importing an earlier CC state may enable multi-time-pad attacks on modes such as CTR, XCTR and GCM (<<Zkl-ISA-machines.adoc#KLEE-nonce-reuse>>), but exploiting them needs a control of the target software that usually also exposes the plaintext.
Re-import is also a useful feature, for instance to restart an operation whose payload was corrupted in transit, and policies covering every legitimate case would overcomplicate the feature.

Architecturally, the KLF contains:

. an array of 32 128-bit blocks, whose _i_-th entry holds the MDH of `K(i)`; and
. an implementation-defined amount of memory, allocated dynamically to the lockers, which holds the `Content` of every configured locker.

The two parts are conceptually distinct, whatever the implementation.
The MDH array is always present, so every locker holds its MDH, if only to show that it is unconfigured.
Only the second part is allocated and capacity-limited: "`KLF capacity`" refers to it alone, a locker that holds only its MDH consumes none, and the capacity a locker consumes depends on its MDH (<<KLEE-length-rule>>).
Insufficient capacity may prevent a configuration instruction from executing; unconfiguring other lockers frees it.

The corruption of a hart's KLF is unrecoverable: the KLEE architectural state of the hart is reset (<<KLEE-reset-and-m-mode-only>>), and a KLEE fatal-error exception is raised–see <<Zkl-ISA-priv.adoc#KLEE-exceptions>> for the definitions of exceptions raised by KLEE.

The KLEE unit holds three 128-bit _authentication registers_, with the authentication and identification data of the locker being managed: `SIV`, `IMPQUAL` and `SIV2`. `kl.load`, `kl.store`, `kl.mvin` and `kl.mvout` access them as the leading bytes of the image they transfer (<<KLEE-instruction-mv>>).
The `kl.mgmt` that opens an export of a locker in a Valid State writes `SIV` and, when _AuxDataLen_ {ge} 2, `IMPQUAL` and `SIV2`. A `kl.mgmt` that opens an import leaves them unchanged: the `kl.load` or `kl.mvin` that follows writes them.

[NOTE]
====
The 128 or 384 bits of `SIV`, `IMPQUAL` and `SIV2` are allocated per hart, not per locker, to reduce hardware cost.
Code therefore cannot run concurrent non-clearing management operations: a second operation may overwrite the in-flight `SIV`, `IMPQUAL` and `SIV2` of the first.
<<KLEE-CSR-klmanagedlocker>> recommends how software avoids such interleaving.
`kl.clear` and provisioning do not touch these registers and `kl.clear` is not restricted.
====

== Providing Inputs and Outputs

[[KLEE-KLV]]
=== RVV/KLV

KLEE takes its inputs and outputs from vector registers, from an architectural input/output buffer (KLIOBUF) loaded from and stored to memory, or from both.

(((KLV)))Vector registers do not require the full V extension, only a minimal subset, _KLV_ (KLEE-subset of V).
KLV must be fully opcode-compatible with RVV: code written for KLV behaves identically under V with `Zvbc`.
KLV comprises:

* vector registers of at least 128 bits;
* the configuration-setting instructions `vsetvli`, `vsetivli` and `vsetvl`, with:
** tail-agnostic and mask-agnostic configurations only, since KLEE neither uses vector masking nor defines masked instructions, and always applies a tail-agnostic policy (bit 25 of the `kl.exec` encoding is reserved for masked operations, should a compelling use case arise);
** `LMUL` values 1, 2, 4 and 8; and
** for a configuration that KLV does not support, `vtype.vill` is set and `vl` = 0, as in RVV, and a KLEE instruction with a vector operand issued while `vtype.vill` is set raises an illegal-instruction exception;
* unit-strided vector loads and stores;
* `vmv.x.s`, `vmv.s.x`, and the slides `vslideup.v[xi]`, `vslidedown.v[xi]`, `vslide1up.vx` and `vslide1down.vx`, to move data into and out of vector registers;
* the logical operations `vand.v[vxi]`, `vor.v[vxi]` and `vxor.v[vxi]` (the immediate forms give, for instance, a bitwise NOT); and
* `vclmul.v[vx]` and `vclmulh.v[vx]` of `Zvbc`, which may be trap-and-emulated.

Floating-point, fixed-point and general arithmetic vector operations are not required.

NOTE: KLEE has no concept of element, and logically does not operate in the vector unit: it sees a vector register (group) as a bit string of length `KLLEN` = `VL` * `SEW`, where `VL` is the vector length in effect (`vl`).

KLEE takes the length of a vector operand from `VL*SEW` alone (`VL` = 2 with `SEW` = 64 and `VL` = 4 with `SEW` = 32, for example, both give 128 bits): the decode side of the CPU uses `VL` and `SEW` to determine how much data to send to the KLEE unit, which needs only their product, or `kliobuftop`.

=== KLIOBUF

The KLIOBUF is an optional architectural input/output buffer that may replace vector registers; it is not part of the KLF.

The instructions `kl.input` and `kl.output` transfer data between the KLIOBUF and memory, and `kl.exec`, `kl.setst` and `kl.mgmt` then use Forms whose inputs and outputs are implicitly in the KLIOBUF (<<KLEE-usage-input-output>>).
<<KLEE-CSR-kliobuftop>> defines `KLLEN` for KLIOBUF operands.

[[KLEE-Metadata]]
== Metadata

A CC carries two kinds of metadata:

. the 128-bit _MDH_, always present, which determines the Machine, the type of key, and the usage policies of the key; its fields are arranged so that its first 64 bits determine the length of a PI or SCC; and
. the optional 128-bit _Implementation Qualifier_ `IMPQUAL`, which copies the three KLEE analogues of the hart's `mvendorid`, `marchid` and `mimpid` CSRs (<<KLEE-CSR-impl-ids>>).
It is present when an SCC has _AuxDataLen_ {ge} 2, and tells an implementation whether it can use the implementation-specific content of the SCC (<<KLEE-Auxiliary-Data-Section>>).

<<KLEE-metadata-header>> summarizes the fields of the MDH, which the following subsections describe.

[[KLEE-Machine-field]]
=== _Machine_ and _MachinePolicy_ Fields

_Machine_ is a 12-bit field. Values 0–3071 are architecture-defined, with encodings maintained by RVI (<<Zkl-ISA-machines.adoc#KLEE-Machines>>); the remaining values are for custom Machines.

The meaning of _MachinePolicy_ depends on the Machine:

* For encryption/decryption primitives and modes, the lower bit permits encryption and the upper bit decryption. At least one bit must be set.
* For a MAC that verifies a tag internally, the lower bit permits the output of the tag and the upper bit its verification.
* For asymmetric primitives that support signatures, the lower bit permits signature generation and the upper bit verification. For a Machine with other operations as well, a zero field leaves those operations available.
* For other primitives, _MachinePolicy_ may encode further Machine identifiers, extending the encoding space of _Machine_.

For a MAC, or a Machine that only signs and verifies, a zero _MachinePolicy_ leaves the locker able to perform none of its operations, but is not invalid.
Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-policy-gate>> states how _MachinePolicy_ gates the States of a Machine.

[[KLEE-KeyType-field]]
=== _KeyType_ Field

_KeyType_ is 0 if the key is provisioned by value, in which case it is also exported and imported by value.
_KeyType_ is 1 if the key is indicated via a system-specific, 64-bit System Key Identifier (SKID) (<<KLEE-system-keys>>).

Values 2 and 3 are reserved: a PI or SCC that carries one of them is invalid Metadata (<<KLEE-MVR-open>>).
The all-ones SKID (`ones(64)`) is the exception: the key material is generated randomly when provisioning completes, all keys of the Machine at once unless otherwise specified, and _KeyType_ is then set to 0, so that the key is thereafter exported by value. If the RBG fails, Rule <<KLEE-GR-rbg-failure>> applies.

NOTE: A SKID may refer to keys with unrelated purposes on different devices;
the _System Key Store_ (SKS) supplies an appropriate _Locality_ (<<KLEE-Localities>>) during provisioning, to bind the key to the system (<<KLEE-system-keys>>).

[[KLEE-State-field]]
=== _State_ and _StateExtension_ Fields

_State_ tracks the state of a locker and its Machine: _Unconfigured_, encrypting or decrypting, initializing, absorbing into or finalizing a hash, computing point multiples, signing or verifying, or in an error state, for instance.
_StateExtension_ lets a Machine keep further state information, usually orthogonal to _State_, such as whether certain values have been provisioned or computed.

States 1–55 are the _Complete_ States: the _Valid_ States 1–47, State 1 being _Ready_, and
(((KLEE, Machine, error states)))

[[KLEE-Auxiliary-Data-Section]]
=== _AuxDataLen_ and _ADSDropped_ Fields

_AuxDataLen_ gives the length, in 128-bit blocks, of the _Auxiliary Data Section_ (ADS), the variable-size, implementation-specific part of the content; with _ADSDropped_ = 1, it keeps the length before `Content2` was dropped. Zero means no ADS, and 1 is invalid; the maximum, 2^14^-1, is 262,128 bytes.

If _AuxDataLen_ {ge} 2, the SCC includes a copy of the implementation qualifier of the originating implementation (<<KLEE-CSR-impl-ids>>),

``{fournbsp}{fournbsp}IMPQUAL := zeros(32) @ klmimpid @ klmarchid @ klmvendorid``,

which the importing implementation uses to decide whether it can use the ADS.
_AuxDataLen_ counts these 16 bytes and the separate 16-byte authentication tag of the ADS, so its minimum is 2 (32 bytes).

_ADSDropped_ is an unauthenticated format hint, ignored when _AuxDataLen_ = 0. When _AuxDataLen_ {ge} 2 and _ADSDropped_ = 1, `Content2` is absent, and `IMPQUAL` and `SIV2` remain as non-authoritative padding, so that the offset of `Content1` does not change. First-segment authentication clears bit 47 only in its local copy of the MDH.

Toggling _ADSDropped_ cannot affect `Content1` or any policy: setting it drops the optional `Content2`, and clearing it requests second-segment processing, whose failure drops `Content2` without rejecting the authenticated `Content1` (<<KLEE-SCC-import>>). Manipulating it can therefore lose the optional ADS or cause an unsuccessful second-segment attempt, but cannot make an unauthenticated `Content2` usable or bypass first-segment authentication.

[[KLEE-UsagePolicy]]
=== _UsagePolicy_ Field

_UsagePolicy_ determines which modes may use the locker.
A _usage instruction_ is an instruction that uses the Machine in a locker to perform operations on the internal state of the locker, or to expose that state, as a `kl.exec` that produces output does.
Usage Control applies only to the usage instructions; <<KLEE-instruction-properties>> lists them.
Bits 0–3, when set, disallow usage in U-mode, VS-mode, HS-mode and M-mode, respectively; bit 0 also governs VU-mode, and bit 2 governs S-mode whether or not the H extension is implemented. Bit 4, when set, grants usage in Debug mode.
`mstatus.MPRV` is not considered, and the bit of a mode that is not supported or not enabled is ignored.

[[KLEE-Localities]]
=== _Locality_ Field

_Locality_ names 128-bit Locality Secrets (LSs), listed in <<KLEE-locality-indexes>> and stored in a, possibly virtual, Locality Secrets Table (LST). Some entries are fixed, or configurable only through an implementation-specific, authenticated hardware process, and are shared by all KLEE units of an SoC; the others are software-programmable, per-hart architectural state.

At SCC export and import, the Localities named in _Locality_ cryptographically bind the SCC to the _current_ hardware and software environments. The binding ends when the SCC is imported; if a Locality Secret changes later, the next export binds the SCC to the new value. Software must prevent unauthorized parties from accessing the lockers directly.

Eleven LST entries are architected: entries 0–5 form the _HW Binding Group_, which binds SCCs to the hardware; entries 6–7 the _Boot Session Group_; and entries 8–10 the _SW Filter Group_. <<KLEE-locality-indexes>> gives, for each, its LST index, domain (SoC, device, VM or process), configurability, bit field and value.

[[KLEE-Metadata-locality-interoperability]]
=== Interoperability under _Locality_ configurations

_This section is informative and non-normative._

The SW Filter Group binds an SCC to the software that exports it, through a register that depends on the mode:

[float="center",align="center",width="100%",cols="<35%,<35%,<30%",options="header"]
|===
| Mode of the export or import | Entry 9 (_HLocality_) | Entry 10 (_SLocality_)
| S or U, no H extension | unconfigured | `skllocality`
| VS or VU (V=1) | `hkllocality`, set by the hypervisor for the VM | `skllocality`
| HS or U with the H extension (V=0) | `hkllocality` of the VM loaded | `skllocality` of the hypervisor
| M | `hkllocality` of the VM loaded (unconfigured without the H extension) | `skllocality`
|===

Five scenarios illustrate this:

Migration between hosts with the H extension.::: The guest's `skllocality` value travels with the saved state of the guest, and possibly its _HLocality_ with the identity of the machine, for the destination hypervisor to install before the guest runs; each hypervisor keeps its own `skllocality` value. The SCCs of the machine then import on any host with the same CSK.

A hypervisor separates its virtual machines.::: The hypervisor may give each virtual machine a distinct `hkllocality`, which the guest can neither read nor write. A guest that names _HLocality_ binds its SCCs to its machine, so the SCCs of two machines differ even when their guests, cloned from one image, hold the same `skllocality`.

M-mode separates Supervisor Domains.::: Likewise, M-mode can separate Supervisor Domains cryptographically by giving them distinct _MLocality_ values.

An OS becomes a guest.::: An OS on a hart without the H extension sets `skllocality`. Its state, and the SCCs exported in its memory, are cloned into a virtual machine that resumes under a hypervisor. The OS still writes `skllocality`. The SCCs exported before cloning therefore import unchanged, whatever the hypervisor's _SLocality_ and _HLocality_, provided that the new host has the same CSK (<<KLEE-CSK-requirements>>) and that the CCs are not bound to the HW Binding Group, _MLocality_ or _PhysBootScrt_, which exist to prevent such migration; _VirtBootScrt_ was unconfigured too.

A hypervisor saves and restores guest lockers, or hands a CC to a guest.::: At V=0, entry 9 is the `hkllocality` of the machine loaded, and entry 10 the hypervisor's own value of `skllocality`. A save and its restore happen at the same level, so their bindings match. Before saving, the hypervisor configures `hkllocality` for the machine and, if a guest CC names _SLocality_, its own value of `skllocality`, to which that export is bound; an unconfigured entry makes the restore fail as invalid Metadata. To hand a CC to a guest, the hypervisor provisions it naming _HLocality_: the export at V=0 binds it to the tag of the machine, and the import at V=1 uses the same block. A CC naming _SLocality_ cannot cross levels this way, since `skllocality` holds a different value at each level: the hypervisor's own at V=0, and at V=1 the guest's, which the hypervisor installs before the guest runs.

In every mode the three entries denote three different registers, and no ordering or exclusivity among `mkllocality`, `hkllocality`, and `skllocality` is required. Host software under a hypervisor does not name _HLocality_ or _VirtBootScrt_, whose values the hypervisor sets for the machine loaded.

[[KLEE-Metadata-expiration-date]]
=== _ExpirationDate_ Field

_ExpirationDate_ is in effect only with `Zklexpire`, which requires the KLEE implementation to have access to a secure clock.
Without `Zklexpire`, a non-zero _ExpirationDate_ in a PI or SCC is invalid Metadata (<<KLEE-Metadata-validity>>).

A non-zero 20-bit _ExpirationDate_ gives the expiration time of the CC in whole hours since 00:00 UTC, 1 January 2027, a span of about 119 years and 7 months. The epoch is in UTC, so that a CC exported on one device and imported on another expires at the same instant, whatever the local time of each.
If the secure clock cannot be read, a usage instruction on a locker with a non-zero _ExpirationDate_ performs no operation and zeroes its output (Rule <<KLEE-GR-usage-locker-error-state>>), and the _State_ is unchanged: the CC can be used again once the clock can be read, while a transition to _Expired_ would destroy its Content.

[NOTE]
====
This specification cannot enumerate the requirements on a secure clock: what is adequate depends on threat models, platforms and integration, as for every time-dependent security feature. As a rule of thumb, *a clock adequate for M-mode security features or an on-SoC TPM is adequate for KLEE*; KLEE imposes no stricter requirement.
Software below M-mode, however, must not be able to set the clock, since moving time backward would extend the lifetime of a CC indefinitely.
====

_ExpirationDate_ is evaluated only:

* at the issue of any usage instruction, for `kl.derive` at both endpoints; and
* at every architectural resumption point of a usage instruction.

The _ExpirationDate_ of a locker that is not in a Valid State is not evaluated: only an expired locker in active use transitions to Error State `kl_state_expired`, and expired contexts can still be evicted, saved or unconfigured cleanly.

The evaluation proceeds as follows:

. If _ExpirationDate_ is zero, the instruction proceeds.
. The date of the secure clock is converted to the format of _ExpirationDate_; a reading earlier than 00:00 UTC, 1 January 2027, converts to 0.
. If the converted value is not smaller than _ExpirationDate_, the locker transitions to Error State `kl_state_expired`; otherwise the instruction proceeds.

A Machine may use these fields to pass initialization parameters at provisioning: ML-DSA (<<Zkl-ISA-machines.adoc#KLEE-PQC-ML-DSA>>), for instance, records its pre-hash function in _AuxInfo_.

[[KLEE-Machine-version]]
=== _Version_ Field

_Version_ gives the version of the MDH format:

* 0: the current format;
* 1: newer revisions of the format, whose further version information is encoded in other MDH fields;
* 2: reserved; and
* 3: a system-specific format.

A PI or SCC with a _Version_ that the implementation does not support is invalid Metadata (<<KLEE-Metadata-validity>>).

System-specific formats are optional and allowed only for import.
The import opens with a KLEE-format MDH whose _Version_ is 3, the _declared MDH_;
at completion, the MDH of the locker is the declared MDH narrowed by any policy the format carries (per the <<KLEE-MNR>>), never widened, with _Version_ set to 0 (or 1 in a future version of this specification).
Such lockers can be exported only in the KLEE format. To prevent loading on other implementations, specific Localities may be set, or all information may be kept in the ADS, gated by `IMPQUAL`. An implementation may support several system-specific formats and distinguishes them in an implementation-defined way.

[[KLEE-Metadata-validity]]
=== Validity of Metadata

Software keeps all _reserved_ bits, and all bits that the Machine does not use, zero. A non-zero value is handled as follows:

* in a Reserved bit, it makes the Metadata invalid (see below);
* in _MachinePolicy_ or _MachineExtension_, a value that the implementation does not implement for the Machine makes it unsupported;
* the _StateExtension_ and _MachineUse_ of a PI are ignored, and zeroed upon provisioning (<<KLEE-locker-management>>);
* outside a PI, a _State_ {vvert} _StateExtension_ value that the Machine does not support makes it invalid (see below); and
* otherwise, _MachineUse_ and _AuxInfo_ are not checked by the conditions below, but by the rules of the Machine and by their use in the implementation (<<KLEE-MachineUse>>).

Metadata is _unsupported_ when the combination of _Machine_, _MachinePolicy_ and _SCProtection_, or a non-zero _MachineExtension_, is not implemented; when _KeyType_ is 1 and the implementation does not support System Key Identifiers, including the all-ones SKID, for the Machine (<<KLEE-KeyType-field>>, <<KLEE-system-keys>>); or when it holds a value that a Machine specification declares unsupported if not implemented, such as the _AuxInfo_ of ML-DSA (<<Zkl-ISA-machines.adoc#KLEE-PQC-ML-DSA>>) or of EdDSA (<<Zkl-ISA-machines.adoc#KLEE-EdDSA>>). A _MachinePolicy_ that the conditions below reject makes it invalid, not unsupported.

A supplied MDH is _invalid_ when at least one of the following holds:

* _Version_ is unsupported;
* _KeyType_ is 1 for a Machine whose Provisioning Input has no key field, for instance the unkeyed hash functions and XOFs, the ECC, ML-KEM and ML-DSA Machines, and the NIK variants of HMAC;
* _KeyType_ is 2 or 3;
* _Locality_[5:4] is 3, or _Locality_ names an unconfigured Locality Secret (<<KLEE-Localities>>);
* the MDH carries any custom value without naming _ChipFamScrt_ or _ChipScrt_ in _Locality_ (Rule <<KLEE-GR-custom-locality>>);
* _State_ is not _Unconfigured_ at provisioning;
* _State_ is _Unconfigured_ or 61–63 at import (<<KLEE-State-management>>);
* _State_ is 54 or 55, or _State_ {vvert} _StateExtension_ is a value that the Machine does not support; for this condition, every Machine supports the Configuration States 56–60 with any _StateExtension_, and the _StateExtension_ in a PI is ignored and zeroed upon provisioning;
* _State_ is _Expired_ in a PI, SCC or PCCC when `Zklexpire` is not implemented;
* _ExpirationDate_ is non-zero and `Zklexpire` is not implemented;
* _AuxDataLen_ = 1;
* _AuxDataLen_ or _ADSDropped_ is non-zero in a PI, or in a PCCC with base type `pi` (<<KLEE-nested-state-base-types>>);
* _MachinePolicy_ is zero for a Machine that requires at least one set bit in it; or
* a Reserved bit is non-zero.

[[KLEE-MVR-open, Metadata Validity Rule]]Metadata Validity Rule:: A `kl.mgmt` that opens a provisioning or import on unsupported Metadata raises a KLEE unsupported-Metadata exception; on invalid Metadata it transitions the locker to Error State _Invalid_.
These checks are not applied to the short import of an Error-State MDH (<<KLEE-error-state-transfer>>).
The locker also transitions to Error State _Invalid_ when, at the completion of a provisioning, import or export, the SKS does not resolve a SKID other than the all-ones value, or when the `Content1` of an SCC whose restored _State_ is a Complete State carries the all-ones SKID.

[[KLEE-Metadata-narrowing]]
=== Narrowing of Metadata

Several operations narrow the policies of a CC by those of another source, all by the same rule: the resolution of a SKID (<<KLEE-system-keys>>),
a restricted `kl.derive` (Rule <<KLEE-GR-narrowing>>), the import of a system-specific format (<<KLEE-Machine-version>>),
and `kl.restrict*`, at the request of software (<<KLEE-instruction-restrict>>).

[[KLEE-MNR, Metadata Narrowing Rule]]Metadata Narrowing Rule:: The _narrowing_ of an MDH _A_ by the policies of a source _B_ (an MDH, the
policies that the SKS associates with a key, or those that a system-specific format carries) is _A_ with the following
fields replaced; a policy field that _B_ does not carry leaves that field of _A_ unchanged, and no other field changes:
+
--
* _UsagePolicy_: bits 0–3 become the OR of both, and bit 4 the AND of both, so that the modes that may use the CC are those that both allow.
* _Locality_ (<<KLEE-locality-indexes>>): each HW Binding subfield (bits [1:0] and [3:2]) takes the larger value, that is the stricter entry of its chain, zero meaning no binding; the Boot Session subfield (bits [5:4]) takes the non-zero value if only one is non-zero; and bits 6–8 are OR-ed.
* _ExpirationDate_, with `Zklexpire`: the smaller non-zero value, or 0 if both are 0.

The narrowing fails, and the locker transitions to Error State _Invalid_, if both Boot Session subfields are non-zero and differ,
or if the resulting _Locality_ names an unconfigured entry (<<KLEE-Localities>>).
Narrowing never changes _SCProtection_; an operation that must also compare side-channel protection levels must explicitly state so.
--

[[KLEE-CSR-klmaxiobuflen]]
=== `klmaxiobuflen`

(((CSR, `klmaxiobuflen`)))`klmaxiobuflen` is an XLEN-bit CSR that reports the maximum configurable length of the KLIOBUF, in bytes.
It is writable in the same modes and for the same purpose as the CSRs of <<KLEE-CSR-impl-ids>>; its hardwired value out of KLEE unit reset is its maximum.
M-mode should write it only while the KLEE unit is in its state out of reset (<<KLEE-out-of-reset-unpriv>>), before any write to `kliobuflen`, and should never reduce it below the current `kliobuflen`: after such a write, the values of `kliobuflen` and `kliobuftop` and the contents of the KLIOBUF are UNSPECIFIED, and no other state is affected.

With `Zklio`, `klmaxiobuflen` must be at least 16 bytes, and at least the largest basic processing unit (granularity) of any implemented Machine.
Without `Zklio`, the KLIOBUF does not exist, `klmaxiobuflen` reads as zero, and `kliobuflen` and `kliobuftop` are not present.

[[KLEE-CSR-kliobuflen]]
=== `kliobuflen`

(((CSR, `kliobuflen`)))`kliobuflen` is an XLEN-bit URW CSR that programs the length of the KLIOBUF, in bytes, for `kl.input` and `kl.output`; its maximum is `klmaxiobuflen`.
Every write, even of the current value, zeroes the buffer and sets `kliobuftop` to the same length.

A zero `kliobuflen` leaves the KLIOBUF _unconfigured_: an operation that expects an input or an output in it then raises an unconfigured-KLIOBUF exception.

[NOTE]
====
The KLEE Privileged Architecture tracks the dirtiness of the KLIOBUF only as part of the entire KLEE state in `*status`.
Software should therefore set `kliobuflen` to zero once it no longer needs the KLIOBUF contents, which context-switch code must otherwise save and restore.
====

// ////////////////////////////////////////////////////////////////////

[[KLEE-CSR-kliobuftop]]
=== `kliobuftop`

(((CSR, `kliobuftop`)))`kliobuftop` is an XLEN-bit URW CSR that sets the upper bound, in bytes, of the buffer range that `kl.input` and `kl.output` use; its maximum is `kliobuflen`.
It plays for the KLIOBUF the role of `VL` in the V extension: it defines the operand length `KLLEN` as `kliobuftop` {times} 8, and the transfer window [0, `kliobuftop`-1].

// For operations involving the KLIOBUF, `klstart` (<<KLEE-CSR-klstart>>) is the position within that window at which processing starts or resumes, analogously to `vstart`; when `klstart` {ne} 0, the bytes processed are those at offsets [`klstart`, `kliobuftop`).
// Shortening an operand is done by lowering `kliobuftop`, never by raising `klstart`.

Writing `kliobuftop` leaves the buffer unchanged, so software can set the length per operation without a write to `kliobuflen`, which clears the buffer; this mirrors the use of `VL*SEW` to supply a partial last block, or a short IV or nonce, to a Machine.

A value invalid for a Machine is detected only when an instruction that uses the KLIOBUF is later issued or restarted, with the outcomes of <<KLEE-usage-input-output>>.

[[KLEE-CSR-klstart]]
=== `klstart`

(((CSR, `klstart`)))`klstart` is an XLEN-bit RW CSR that records, in bytes, the progress of the instructions that _honor_ it:

* `kl.load`, `kl.store`, `kl.input` and `kl.output`: the bytes read or written;
* `kl.exec` on a multi-block operand, which may be interrupted between blocks: the bytes processed;
* `kl.derive`, whose `kl.exec` endpoints advance the source and destination lockers in the same way; and
* `kl.mvin` and `kl.mvout`, vector or not: the locker transfer point. A vector variant with a multi-block operand also tracks the corresponding position in the vector register in `vstart`.

Every other instruction leaves `klstart` unchanged, except `kl.clearall`, and `kl.mgmt` after its check of `klmanagedlocker` (<<KLEE-locker-management>>), which clear it.

KLEE has no intrinsic element length, and no counterpart of the Element Group Width (EGW), Effective Element Width (EEW) or Element Group Size (EGS) of the vector crypto extension; its instructions, such as `kl.exec`, are architecturally decoupled from the operations the KLEE unit performs for them. Hence, `klstart` is a byte count; progress that is not byte-structured, such as that of the point multiplications and signature operations of <<Zkl-ISA-machines.adoc#KLEE-ECC>> and <<Zkl-ISA-machines.adoc#KLEE-PQC>>, is recorded by Machines or their implementations in _MachineUse_ (Rule <<KLEE-GR-long-running-no-data>>).

Like `vstart` in the V extension, `klstart` is the position within the transfer window at which processing starts or resumes; for a KLIOBUF operand the window is [0, `kliobuftop`-1] (<<KLEE-CSR-kliobuftop>>).
The KLEE implementation writes it:

. on a precise exception, with a prefix-complete point of the transfer (more precise statement in <<KLEE-rule-memory-instruction-decomposed>>): the point of progress, or 0 for an  interrupt in an implementation that selects the restart option of Rule <<KLEE-GR-resumability-options>> for `kl.load`, `kl.store`, `kl.input` and `kl.output`, which then transfer the prefix again when re-executed; and
. with 0 when an instruction that honors `klstart` retires, except `kl.mvin` and `kl.mvout`, which advance `klstart` by the bytes transferred and keep it across instructions, to support piecewise transfers (<<KLEE-instruction-mv>>); their vector variants track their progress within the vector register in `vstart`, whose value depends on the element size chosen.

Issuing Form A, B or C of `kl.exec` with `klstart` {ne} `vstart` {times} `SEW` / 8 raises an illegal-instruction exception.

The transfer window is `kliobuftop` bytes long for a KLIOBUF operand (with `kliobuflen` non-zero), and `VL` {times} `SEW` / 8 bytes long for a vector operand.
The following checks are made in order, after those of <<KLEE-GR-gate-order>> (including the Error State and expiration checks) and after those that make the instruction illegal in the locker's _State_ (Rules <<KLEE-GR-no-exec-in-ready>> and <<Zkl-ISA-machines.adoc#KLEE-MGR-not-allowed-instructions>>).
They do not apply to `kl.mvin` and `kl.mvout`, whose vector window is [`vstart`, `vl`-1] in elements and whose `klstart` is a locker offset.

. If the length of the transfer window is invalid for the Machine, the locker transitions to Error State _Invalid_.
. If `klstart` {ge} the length of the transfer window, the window is empty: `klstart` is not checked, and the instruction only writes 0 to `klstart`.
. Otherwise, a `klstart` that is not an interruption point of the Machine transitions the locker to Error State _Invalid_, and the unwritten part of the output window is zeroed (Rule <<KLEE-GR-usage-locker-error-state>>).
  This prevents, for instance, the use of a locker in an inconsistent state and the release of plaintext in place of ciphertext.

An _interruption point_ of a Machine in a given State is a `klstart` value that the Machine can itself produce on a precise halt in that State: unless the Machine states a coarser or a different set, the whole multiples of its granularity within the transfer window, or 0 for an asynchronous interrupt in an implementation that selects to restart.
Procedure `process_VLI` (<<Zkl-ISA-machines.adoc#KLEE-process-VLI>>) defines its own, at the boundaries at which its inner loop may yield.

For the locker-directed transfers `kl.load`, `kl.store`, `kl.mvin` and `kl.mvout`, `klstart` is bounded above by the length in bytes of the serialized image `S` (<<KLEE-instruction-mv>>), determined from the first 8 bytes of the MDH; each of these instructions states the bound it applies.

Software should not write 0 to `klstart` to force a full restart of `kl.exec` or `kl.derive`
once per-block state effects have been committed; Rule
<<KLEE-GR-block-iterated-instructions>> states the consequence.

[[KLEE-CSR-klmanagedlocker]]
=== `klmanagedlocker`

(((CSR, `klmanagedlocker`)))`klmanagedlocker` is an XLEN-bit RW CSR, of which only 6 bits are currently used.
It holds the number of the locker most recently placed under management, or 32 if none. Values 33 and above are reserved; writing one leaves `klmanagedlocker` unchanged.
The locker it names is under management while it is in a Configuration State, and the internal values `SIV`, `SIV2` and `IMPQUAL` then belong to it.

`klmanagedlocker` becomes 32 when the locker it names is cleared (`kl.clear`, `kl.clearall`, or the zeroizing step of a `kl.mgmt` whose opening then fails), or is overwritten as the destination of a `kl.clone` or `kl.rename` from another locker.
A `kl.mgmt` that performs no operation on an _Unconfigured_ locker also sets it to 32 (Rule <<KLEE-GR-cleared-under-management>>).
It keeps its value when the management operation completes, and when the locker it names enters an Error State, so that software checking the _State_ of the locker through `KM` (Rule <<KLEE-GR-klmanagedlocker-override>>) reads the outcome of the operation, not an _Unconfigured_ locker.
When `kl.rename` or `kl.swap` moves the CC of the locker it names, `klmanagedlocker` takes the number of the locker that receives that CC (<<KLEE-instruction-clone>>).
Otherwise, a KLEE exception raised during a management operation that does not transition the locker to an Error State leaves `klmanagedlocker` unchanged: the handler either resolves the condition or writes 32 itself.

[[KLEE-klmanagedlocker-software-check,Software Requirement on klmanagedlocker]]
Software that issues `kl.load`, `kl.store`, `kl.mvin`, `kl.mvout`, or an instruction naming `KM` (Rule <<KLEE-GR-klmanagedlocker-override>>), must first read `klmanagedlocker`.
If the value is not the number of the locker on which the software intends to act, or 32 where it intends a transfer to or from the KLIOBUF, the software must save it and write the intended value before issuing the instruction, and must restore the saved value before control returns to the code that set it.
In particular, it binds every exception handler, whether it runs at a higher privilege than the interrupted code or in the same mode, such as a U-mode signal handler, and any other code that runs at a higher privilege than the code that last wrote `klmanagedlocker`.
Software that completes or abandons a management operation must then write 32 to `klmanagedlocker`, or restore the value that it saved.
The architecture does not enforce these requirements: an instruction issued in violation of them acts on the locker that `klmanagedlocker` names.

Software should not interleave cryptographic operations, or the management of other lockers, with the steps of a management operation: it should complete the operation, or abandon it, first.
`klmanagedlocker` and the authentication registers (<<KLEE-KLF>>) exist once per hart: managing another locker between the steps requires `klmanagedlocker` to be saved, set and restored, and may overwrite the in-flight `SIV`, `IMPQUAL` and `SIV2` of the first operation; and an instruction naming `KM` between the steps acts on whichever locker `klmanagedlocker` then names. Each is an opportunity for a defect that silently acts on the wrong locker.
Code that must nevertheless interleave them, for instance in several threads of one process, needs coordination, such as lightweight threads with KLEE context-switching support, or a mutex.

NOTE: The check of `klmanagedlocker` by `kl.mgmt` (<<KLEE-locker-management>>) detects an accidentally interleaved management operation, and also software that has not written 32 after finishing a management operation.
A handler that must manage another locker meanwhile first saves the managed locker, writes 32 to `klmanagedlocker`, performs its operations, and then restores the exported locker (<<KLEE-state-save-and-restore-order>>).
Writing 32 without completing an export loses the in-flight `SIV`, `SIV2` and `IMPQUAL`, which the next export opening of a Valid-State locker, or the first `kl.load` or `kl.mvin` of the next import, overwrites.

[[KLEE-instructions-detailed]]
== Instructions

_This section specifies the semantics and encodings of the unprivileged KLEE instructions.
Only the semantics and encoding are described here and not the behavior of the instructions in various States of the Machines,
how they respect usage policies, how they use randomness, how they access memory and whether they are interruptible.
The rules governing all these aspects are grouped in <<KLEE-ISA-rules>>._

When mentioning rules is necessary to describe the behavior of an instruction, the behavior is explicitly given in the description of the instruction together with the reference to the rule.

[[KLEE-general-rules-instructions]]
=== General Rules Governing Encoding and Arguments

In every encoding, fields shown with fixed values must hold them. Any other value of such a field, and any unlisted combination of field values, is a reserved encoding and raises an illegal-instruction exception (first group of <<KLEE-illegal-instruction-grounds>>).

`%offset` denotes the sign-extended 12-bit immediate of the instruction: bits [31:20] for `kl.load` and `kl.input` (I-type), and bits [31:25] @ [11:7] for `kl.store` and `kl.output` (S-type). The base register is always in bits [19:15] (`rs1`), and the effective address of a transfer is `X[rs1] + sext(%offset)`.
This is the address of the *first* byte of the transfer, even for a multi-byte or resumed transfer; a resumed transfer restarts at that address plus a byte offset of `klstart`.
Each instruction gives the correspondence between addresses and transfer offsets.

The following rules apply to all KLEE instructions, unless stated otherwise.

[horizontal]
[[KLEE-GR-multiple-GPRs,GR1]]GR1:: _Use of multiple GPRs for longer inputs:_ A 64-bit operand is one GPR on RV64, and the pair `(X[s+1],X[s])`, as `X[s+1] @ X[s]`, on RV32.
A 128-bit operand is the pair `X[s+1] @ X[s]` on RV64, and the quartet `X[s+3] @ X[s+2] @ X[s+1] @ X[s]` on RV32.
This holds for sources and destinations alike.
The lowest register number of a pair must be even, and that of a quartet a multiple of four; otherwise an illegal-instruction exception is raised.
A pair or quartet is read, resp. written, as a whole.
Here and in every instruction description, RV32 and RV64 denote an XLEN of 32, resp. 64, in the privilege mode that executes the instruction.

GR2:: _`X0` as a destination or source register, but not as a locker index:_ writes to it are discarded, and it reads as zero.
When the lowest register of a
pair or quartet is `X0`, no register of the group is written, and the group reads as zero.

[[KLEE-GR-GPR-indirect,GR3]]GR3:: The fields 'r' and 'R' in the encodings are reserved for `Zklind` and their function is described in <<KLEE-indirect-lockers>>. If `Zklind` is not available, these fields must be equal to zero and a non-zero value raise an illegal-instruction exception, except `r` = 1 with `X0` in the locker register field, which encodes `KM` where Rule <<KLEE-GR-klmanagedlocker-override>> allows it.

[[KLEE-GR-klmanagedlocker-override,GR4]]GR4:: _The managed locker:_ `klmanagedlocker` determines the locker on which some management instructions operate, as follows:

* `kl.load`, `kl.store`, `kl.mvin` and `kl.mvout` have no locker operand, and always operate on the locker that `klmanagedlocker` names.
* `kl.mgmt`, `kl.setst` (including `kl.clear` and `kl.clearads`), `kl.getmd*` (and so `kl.getst` and `kl.getstx`), and Form A of `kl.size` and `kl.avail` may name the _managed locker_, written `KM`, in place of a locker operand.
`KM` is encoded with `r` = 1 and `X0` in the locker register field, with or without `Zklind`, and denotes the locker that `klmanagedlocker` names.
When `klmanagedlocker` = 32, `KM` denotes no locker, and the instruction behaves as on an _Unconfigured_ locker: `kl.getmd*` returns zeros, `kl.size` and `kl.avail` return 0, and `kl.setst`, `kl.mgmt` with `kl_cfg_exporting` and `kl.mgmt` with `kl_cfg_management_end` perform no operation (Rule <<KLEE-GR-cleared-under-management>>).
A `kl.mgmt` that opens a provisioning or an import on `KM` while `klmanagedlocker` = 32 raises an illegal-instruction exception, since there is no locker to open.
* A locker named in the encoding, directly or indirectly, is never replaced by the value of `klmanagedlocker`.
+
NOTE: The transfer instructions have no locker operand because the opening `kl.mgmt` already names the locker in `klmanagedlocker`: repeating the index would add a second source of error and nothing else.
The freed encoding fields let `kl.load` and `kl.store` share their encodings with `kl.input` and `kl.output`, and `kl.mvin` and `kl.mvout` name GPRs, a vector register or the KLIOBUF.
`KM` lets one routine per management operation complete and query whichever locker it manages, without carrying its index in a GPR and without `Zklind`.
Once a clear has reset `klmanagedlocker` to 32, `KM` reads as an _Unconfigured_ locker, so the check that follows each step of such a routine detects the clear (Rule <<KLEE-GR-cleared-under-management>>); after the completion of the operation, or an Error State, `KM` still names the locker, and the check reads its _State_.
An explicit operand is never redirected, so a value of `klmanagedlocker` left by other software cannot make such an instruction act on a locker other than the one it names, and the check of `klmanagedlocker` by `kl.mgmt` (<<KLEE-locker-management>>) detects an interleaved management operation.

[[KLEE-GR-vector-MDH-operand,GR5]]GR5:: Where a KLEE instruction carries the whole 128-bit MDH in a vector register or group, such as the MDH-formatted operand of `kl.restrictv` and the destination of `kl.getmdv`, the operand must satisfy `VL` {times} `SEW` {ge} 128; otherwise an illegal-instruction exception is raised.
<<KLEE-extensions-overview-unpriv>> records which vector extensions provide such a register.
The same requirement applies to an MDH taken from the KLIOBUF: `kliobuftop` {ge} 16.

[[KLEE-GR-vector-legality,GR6]]GR6:: A vector register (group) operand whose register number is not a multiple of the LMUL in effect is a reserved encoding and raises an illegal-instruction exception, as in RVV 1.0.
Every KLEE instruction with a vector operand sets `vstart` to 0 when it retires, and on a precise halt sets it as <<KLEE-CSR-klstart>> and Rule <<KLEE-GR-klstart-vstart>> prescribe. An instruction with a vector operand that produces no `vstart` value (`kl.getmdv`, `kl.restrictv`, Form C of `kl.size` and `kl.avail`, `kl.setst` and `kl.mgmt`), issued with `vstart` {ne} 0, either raises an illegal-instruction exception, as RVV 1.0 {sect}3.7 permits for a `vstart` value that the instruction can never produce, or ignores `vstart`; which of the two is implementation-defined.

[[KLEE-GR-klstart-vstart,GR7]]GR7:: KLEE instructions with vector operands that use `klstart` for resumption update `klstart` and `vstart` simultaneously and independently, each by its own semantics: both denote the same point of progress, `klstart` in bytes and `vstart` in elements of the width in effect, and neither is derived from the other.
Each unit thus keeps its own information, and the two values can still be explicitly "`desynced`", as in locker management operations.
+
NOTE: For Forms A–C of `kl.exec`, an illegal-instruction exception is raised if `klstart` and `vstart` denote different points (<<KLEE-CSR-klstart>>). `kl.mvin` and `kl.mvout` keep the two independent by design: their `klstart` is a locker offset that accumulates across instructions, while `vstart` tracks the vector register.
+
NOTE: The uninterruptible vector-form instructions, which Rule <<KLEE-GR-vector-legality>> lists, produce no `vstart` value, and therefore consume none.

[[KLEE-management-operations]]
=== Provisioning, Import, and Export

_This section is informative and non-normative._

Setting error handling aside, *management* operations consists of the following three steps, where the first and the last one consist of a single KLEE  instruction, and the second step consists of one or more `kl.mvin` or `kl.mvout` (alternatively, `kl.load` or `kl.store`) instructions:

. `kl.mgmt` (<<KLEE-instruction-mgmt>>) prepares the locker for the management operation.
. One or more `kl.mvin` (<<KLEE-instruction-mv>>) load the rest of the information to be read into the locker, or one or more `kl.mvout` move the information in the locker out.
. `kl.mgmt` completes the management operation and makes the locker available to software.

// Setting error handling aside, *provisioning* consists of the following three steps:
//
// . `kl.mgmt` (<<KLEE-instruction-mgmt>>) prepares the locker, checks the validity of the MDH, and loads the whole MDH into the locker.
// . One or more `kl.mvin` (<<KLEE-instruction-mv>>) load the rest of the provisioning information.
// . `kl.mgmt` completes the provisioning and makes the locker available to software.
//
//
// *Importing* an SCC is similar:
//
// . `kl.mgmt` prepares the locker to accept an SCC, checks the validity of the MDH, and loads the whole MDH into the locker.
// . One or more `kl.mvin` load the rest of the SCC, authentication data first, into the locker.
// . `kl.mgmt` authenticates and decrypts the SCC, and makes the locker available to software.
//
// *Exporting* a locker as an SCC takes five steps:
//
// . `kl.getmd` or `kl.getmdv` (<<KLEE-instruction-getmd>>) exports the MDH out of the locker, and `kl.size` (<<KLEE-instruction-size>>) gives the size of the SCC, for which software allocates resources.
// . Software stores the MDH to memory.
// . `kl.mgmt` prepares the locker to produce an SCC, encrypting its contents and computing the authentication tag(s).
// . One or more `kl.mvout` move the rest of the SCC, authentication data first, out of the locker.
// . `kl.mgmt` completes the export and restores the locker to a form available to software.

[[KLEE-instruction-size]]
=== kl.avail and kl.size

_Synopsis_::
`kl.avail` returns 1 if the Machine encoded in the MDH is available in the requested variant, and 0 otherwise.
`kl.size` returns the size in bytes of the memory buffer needed for the data of a PI or SCC, or 0 on error, such as an unsupported Machine or an invalid MDH.

_Mnemonic_::
+
--
`kl.avail` and `kl.size` have three Forms:
(((KLEE, instruction, kl.size)))
(((KLEE, instruction, kl.avail)))

[upperalpha]
. `kl.{avail,size}  Xd, Ks` - Size from a context.
. `kl.{avail,size}  Xd, Xs` - Size from MDH[63:0] in one (RV64) or two (RV32) GPRs.
. `kl.{avail,size}  Xd, Vs` - Size from MDH in one vector register.
--

_Encoding_::
+
--
The encoding shares the opcode, `funct3` and `funct2` (the two msbs of `funct7`) of `kl.exec`, with bit 27 set.
Bit 25, `q`, selects `kl.size` (`q` = 0) or `kl.avail` (`q` = 1).

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Xd' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'Ks/Xs/Vs' },
    { bits:  5, name: 0x0 },
    { bits:  1, name: 'q' },
    { bits:  1, name: 'r', attr: ['Zklind'] },
    { bits:  1, name: 0x1 },
    { bits:  2, name: 'F' },
    { bits:  2, name: 0x0, attr: ['funct2'] },
]}
....

Field `F` selects the Form:

* `F` = `0b00` {implies} Form A, from a context `Ks`.
* `F` = `0b01` {implies} Form B, from an MDH in one (RV64) or two (RV32) GPRs.
* `F` = `0b10` {implies} Form C, from an MDH in a 128-bit vector register.
--

_Description_:: {empty}
+
--
`kl.avail` (`q` = 1) examines only the _Machine_, _MachinePolicy_, _MachineExtension_, _KeyType_ and _SCProtection_ fields of the MDH, and writes 1 to `Xd` if that combination is implemented (a non-zero _MachineExtension_ never is), and 0 otherwise.
Since it examines no other field, a 1 does not exclude a KLEE unsupported-Metadata exception that a Machine specification attaches to the value of another field, such as the _AuxInfo_ of ML-DSA. An _Unconfigured_ locker yields 0.

`kl.size` (`q` = 0) writes to `Xd` the size in bytes of the memory buffer needed for the
external image that the MDH describes: a PI, an SCC, or, for a locker in an Error State, the MDH
alone (<<KLEE-data-formats>>, <<KLEE-length-rule>>). For an SCC the size includes the
authentication tag(s) and the ADS; for a PI it is the size of the entire PI.

The Forms differ only in the source of the MDH: the locker itself (Form A), bits [63:0] in `Xs`, or in `X[s+1] @ Xs` on RV32 (Form B), or bits [127:0] in `Vs` (Form C).
In Form A, `Ks` may be `KM` (Rule <<KLEE-GR-klmanagedlocker-override>>).

Let `content1_size` be the length in bytes of the `Content1` of an SCC for the _Machine_,
_MachinePolicy_, _KeyType_ and _StateExtension_ of the MDH, and `pi_content_size` the length in bytes
of the `Content` of a PI for its _Machine_, _MachinePolicy_ and _KeyType_ (<<KLEE-length-rule>>); the two are distinct and not interchangeable.
Let `content2_size` be 16 * (_AuxDataLen_ - 2) if _AuxDataLen_ {ge} 2 and _ADSDropped_ = 0, and 0 otherwise.

`kl.size` returns:

. Form A: 0 if the locker is _Unconfigured_;
. Forms B and C: 0 if the supplied MDH is not in an Error State and is unsupported or invalid Metadata (<<KLEE-Metadata-validity>>), or its _State_ is 61–63.
. Form B examines only bits [63:0]: none of the fields in bits [127:64] affects the size of any structure (<<KLEE-length-rule>>), so the invalidity and unsupported-Metadata conditions on them, including Rule <<KLEE-GR-custom-locality>> and the _AuxInfo_ of a Machine, are not applied;
. 16 if MDH._State_ is an Error State;
. if MDH._State_ is a Valid State or `kl_cfg_{importing|exporting}`:
  .. 32 + `content1_size` if _AuxDataLen_ = 0;
  .. 64 + `content1_size` + `content2_size` if _AuxDataLen_ {ge} 2, the 64-byte fixed part including `IMPQUAL` and `SIV2` even when _ADSDropped_ = 1;
. 16 + `pi_content_size` if MDH._State_ is `kl_cfg_provisioning`, `kl_cfg_ppi_importing`, or `kl_cfg_ppi_exporting`, or, for a supplied MDH, _Unconfigured_ (the MDH of a PI).
--

[[KLEE-instruction-exec]]
=== kl.exec

_Synopsis_::
Perform a cryptographic operation in the KLEE unit.

_Mnemonic_::
+
--
`kl.exec` has four Forms:
(((KLEE, instruction, kl.exec)))

[upperalpha]
. `kl.exec  Vd, Kn, Vs2` {nbsp} reads an input vector and writes an output vector.
. `kl.exec  {fournbsp} Kn, Vs2` {nbsp} reads an input vector and writes no output vector.
. `kl.exec  Vd, Kn {fournbsp}{nbsp}` {nbsp} reads no input vector and writes an output vector.
. `kl.exec  {fournbsp} Kn {fournbsp}{nbsp}` {nbsp} reads no input vector and writes no output vector.
--

_Encoding_::
`kl.exec` is an R-type instruction.
+
--
[wavedrom, , svg]
....

{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'rd', attr: ['Vd','—','Vd','—'] },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: "'rs1' (n)", attr: ['Kn'] },
    { bits:  5, name: 'rs2', attr: ['Vs2','Vs2','—','—'] },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'r', attr: ['Zklind'] },
    { bits:  1, name: 0x0 },
    { bits:  2, name: 'Form', attr: ['0    0','0    1','1    0','1    1'] },
    { bits:  2, name: 0x0, attr: ['funct2'] },
]}
....

The encodings of Forms A–D are:

[upperalpha]
. `Form` = `0b00`.
. `Form` = `0b01` and `rd` = `0b00000`.
. `Form` = `0b10` and `rs2` = `0b00000`.
. `Form` = `0b11` and `rd` = `rs2` = `0b00000`.

The locker operand is always in `rs1`. An unused register field, `rd` without an output vector and `rs2` without an input vector, must be zero; non-zero values in it are reserved, except for encodings that `Zklmv` assigns to it (<<KLEE-instruction-mv>>).
--

_Description_::
+
--
Performs the cryptographic operation that the Machine in locker `Kn` defines, possibly taking an input and producing an output.
When it performs no operation, on an _Unconfigured_, Error-State or expired locker, or when it transitions the locker to an Error State, it zeroes the unwritten part of its output window instead of producing output (Rule <<KLEE-GR-usage-locker-error-state>>).

In Form A, `Vd` and `Vs2` may be the same register group; any other overlap is reserved.
`Vd` = `Vs2` is allowed only for an operation whose output blocks have the length of its input blocks, each block's output then replacing its input at the same offset; for any other operation it raises an illegal-instruction exception (<<KLEE-illegal-instruction-grounds>>).

Without `Zklv`, only Form D is supported, Forms A–C raise an illegal-instruction exception, and `kl.input` and `kl.output` supply the inputs of `kl.exec` and extract its outputs (<<KLEE-usage-input-output>>).
--

[[KLEE-instruction-mv]]
=== kl.mvin and kl.mvout

// The `Zklmv` subextension adds dedicated move instructions between scalar/vector registers and a locker.
// The instructions in this extension are encoded as new forms of `kl.exec`:

_Synopsis_::
  Move content between scalar/vector registers, or the KLIOBUF, and the locker under management, which is in a Configuration State.

_Mnemonics_::
+
--
`kl.mvin` and `kl.mvout` are one instruction with six variants:
(((KLEE, instruction, kl.mvin)))(((KLEE, instruction, kl.mvout)))

[upperroman]
. `kl.mvin Xs2` copies 128 bits of content from two or four GPRs into the locker.
. `kl.mvin Vs2` copies one or more 128-bit blocks of content from a vector register into the locker.
. `kl.mvin KLIOBUF` copies one or more 128-bit blocks of content from the KLIOBUF into the locker.
. `kl.mvout Xs1` moves 128 bits of content from the locker into two or four GPRs.
. `kl.mvout Vs1` moves one or more 128-bit blocks of content from the locker into a vector register.
. `kl.mvout KLIOBUF` moves one or more 128-bit blocks of content from the locker into the KLIOBUF.

The locker is not an operand: the instruction acts on the locker that `klmanagedlocker` names (Rule <<KLEE-GR-klmanagedlocker-override>>).
--

_Encodings_::
+
--
The encodings are variants of `kl.exec` Form D (`Form` = `0b11`): the field `rd`, which is zero in `kl.exec`, is non-zero and selects the variant. Since no locker is encoded, `r` = 0; a non-zero `r` is reserved.

[upperroman]
. `kl.mvin Xs2` is encoded with       `rd` = `0b00001`, `rs1` = `0`, and `rs2` holds the source GPR.
. `kl.mvin Vs2` is encoded with       `rd` = `0b00010`, `rs1` = `0`, and `rs2` holds the source vector register.
. `kl.mvin KLIOBUF` is encoded with   `rd` = `0b00011`, `rs1` = `0`, and `rs2` = `0b00000`.
. `kl.mvout Xs1` is encoded with      `rd` = `0b00101`, `rs2` = `0`, and `rs1` holds the destination GPR.
. `kl.mvout Vs1` is encoded with      `rd` = `0b00110`, `rs2` = `0`, and `rs1` holds the destination vector register.
. `kl.mvout KLIOBUF` is encoded with  `rd` = `0b00111`, `rs2` = `0`, and `rs1` = `0b00000`.

Any other non-zero value of `rd` in Form D is reserved and raises an illegal-instruction exception.
--

_Description_::
+
--
`kl.mvin` and `kl.mvout` transfer the `Content` of the locker that `klmanagedlocker` names, which must be in a Configuration State.
`kl.mvin` fills a locker being provisioned or imported (States `kl_cfg_provisioning`, `kl_cfg_importing` and `kl_cfg_ppi_importing`, Rule <<KLEE-GR-zkl-load-mv-allowed>>); `kl.mvout` drains a locker being exported (States `kl_cfg_exporting` and `kl_cfg_ppi_exporting`, Rule <<KLEE-GR-zkl-store-mv-allowed>>).
They do not transfer the MDH, which `kl.mgmt` and `kl.getmd*` carry; for provisioning or import, the `kl.mgmt` that opened the locker (<<KLEE-instruction-mgmt>>) must already have loaded it.
The authentication fields `SIV`, `IMPQUAL` and `SIV2` are the leading bytes of the image they transfer; while the locker is under management, they are held in the three authentication registers of <<KLEE-KLF>>.

An illegal-instruction exception is raised in any Valid State or in a Configuration State that does not admit the variant, if `klstart` is not a multiple of 16, or, for a vector variant, if `vl * (SEW/8)` or `vstart * (SEW/8)` is not a multiple of 16; the V-enabled check is performed first.
On an _Unconfigured_ or Error-State locker, however, every variant performs no operation, whatever the value of `klstart`, and `kl.mvout` writes zeros to its destination (Rule <<KLEE-GR-cleared-under-management>>).
The same holds when `klmanagedlocker` = 32, that is when no locker is under management.

Let `content_size` be the length in bytes of the serialized `Content` of the locker, that of a PI or of an SCC according to the base type of the image the locker holds (<<KLEE-length-rule>>).
The instruction determines it from the MDH of the locker being exported, or from the one the caller supplied for provisioning or import.

In the external formats, the `Content` starts at a _ContentOffset_ that depends on the MDH, the current operation and the base type of the image:
// the same case distinction of `kl.size` (<<KLEE-instruction-size>>) but excluding the `Content` and the MDH._ADSDropped_ never affects _ContentOffset_.

. if MDH._State_ is a Valid State, `kl_cfg_importing` or `kl_cfg_exporting`: 16 if _AuxDataLen_ = 0, and 48 if _AuxDataLen_ {ge} 2;
. if MDH._State_ is `kl_cfg_provisioning`, `kl_cfg_ppi_importing`, or `kl_cfg_ppi_exporting`: 0.

The _serialized image_ `S` of the locker is `Content`, `SIV {vvert} Content`, or `SIV {vvert} IMPQUAL {vvert} SIV2 {vvert} Content` for _ContentOffset_ = 0, 16 or 48, respectively.
Its size is `image_size` = _ContentOffset_ + `content_size`, the value that `kl.size` reports minus 16.

Let `max_admissible` be the length of the longest image of the locker's current base type that the implementation can hold for the Machine: `pi_content_size` for a PI base type, and `content1_size` plus the largest supported `content2_size` for an SCC base type (<<KLEE-instruction-size>>).
With _ADSDropped_ = 1, `content2_size` is replaced by zero, so the image contains no `Content2` byte.
Bytes of an SCC beyond `max_admissible` belong to a discarded ADS (<<KLEE-SCC-import>>), and are neither read from memory nor written to the locker.
Let

{fournbsp}{fournbsp}``image_end`` = _ContentOffset_ + `min(content_size, max_admissible)`.

`kl.mvin` and `kl.mvout` transfer only 16-byte blocks, at 16-byte aligned offsets below `image_end`: the block at offset `klstart` is transferred if `klstart` < `image_end`, and `klstart` then advances by 16.
If `klstart` {ge} `image_end`, `klstart` is unchanged, `kl.mvin` writes nothing, and `kl.mvout` writes zero to its
destination GPRs, resp. to every element of `Vs1` from `vstart` to `vl` − 1.

The vector variants also track progress in `vstart`, in vector elements: each 16-byte block advances it by 128/`SEW`, for instance by 4 for 32-bit elements or by 2 for 64-bit elements.
Element _k_ of the vector operand, for _k_ from `vstart` to `vl` − 1, corresponds to byte offset `klstart` + (_k_ − `vstart`) × `SEW`/8 of `S`.
If a vector transfer is interrupted, `klstart` records the total number of bytes transferred, and `vstart` the first untransferred element; if `vstart` {ge} `vl`, the instruction performs no operation and leaves `klstart` unchanged.

The KLIOBUF variants (III and VI) use the KLIOBUF in place of a vector register: they transfer bytes 0 to `kliobuftop` − 1 of the KLIOBUF to or from offsets `klstart` to `klstart` + `kliobuftop` − 1 of `S`, as the vector variants do with `vstart` = 0 and `vl` × `SEW`/8 = `kliobuftop`.
They require a configured KLIOBUF (Rule <<KLEE-GR-iobuf-configured>>) and a `kliobuftop` that is a multiple of 16, raising an illegal-instruction exception otherwise, and, like the GPR variants, are architecturally uninterruptible (Rule <<KLEE-GR-uninterruptible-instructions>>).

NOTE: The KLIOBUF variants give an implementation without `Zklv` a multi-block transfer: `kl.input` fills the KLIOBUF from memory and `kl.mvin KLIOBUF` moves it into the locker, as `kl.input` and `kl.exec` cooperate for the inputs of a Machine (<<KLEE-usage-input-output>>).
Their window is the KLIOBUF up to `kliobuftop`, so they need no element position, and a transfer of at most `klmaxiobuflen` bytes can be uninterruptible.

If one management operation combines `kl.mvin` or `kl.mvout` with `kl.load` or `kl.store`, each byte of
`Content` holds the value last written to its offset, by whichever instruction.
--

[[KLEE-instruction-setst]]
=== kl.setst

_Synopsis_::
Change the state of the Machine encoded in the CC in a locker.

_Mnemonic_::
`kl.setst` has four Forms:
(((KLEE, instruction, kl.setst)))
+
[upperalpha]
. `kl.setst Kd, #immed7{fournbsp}{nbsp}{nbsp}` with no auxiliary input.
. `kl.setst Kd, #immed7, Xs{nbsp}` with auxiliary input in one or two GPRs (RV64/RV32).
. `kl.setst Kd, #immed7, Vs{nbsp}` — in a vector register.
. `kl.setst Kd, #immed7, Xs{nbsp}` — in two or four GPRs (RV64/RV32).

//

_Encoding_::
`kl.setst` is an R-type instruction.
The encodings with `#immed7`[6:3] = `0b0111` belong to `kl.mgmt` (<<KLEE-instruction-mgmt>>), a separate instruction; all others are `kl.setst`.
+
--
[wavedrom, ,svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Kd' },
    { bits:  3, name: 0x3, attr: ['kl.setst'] },
    { bits:  5, name: 'rs1' },
    { bits:  1, name: 'r', attr: ['Zklind']   },
    { bits:  2, name: 'F' },
    { bits:  2, name: 0x0 },
    { bits:  7, name: 'immed7' },
]}
....

`#immed7` = `kl_cfg_clearall` (65) is valid only in Form A, with `Kd` = 0 and `r` = 0, where it encodes `kl.clearall` (<<KLEE-instruction-clearall>>); every other encoding with `#immed7` = 65 is reserved.

The encodings of the four Forms are:
[upperalpha]
. `F` = `0b00`. `rs1` = `0b00000`.
. `F` = `0b01`.
. `F` = `0b10`.
. `F` = `0b11`.
--

// ////////////////////////////////////////////////////////////////////

_Description_::
+
--
`kl.setst` advances the Machine of locker `Kd` from one stage to another, for instance from initializing a hash
function to absorbing data and finalizing the digest. It normally reaches the State that `#immed7` names, but some States transition automatically to another
State when the instruction completes. <<KLEE-State-management>> and the specification of each Machine give the allowed transitions.
`kl.setst` may also set state information orthogonal to these stages, possibly as a prerequisite for entering another State.

For all Machines, `#immed7` takes the following values:

* 0 (`kl_state_unconfigured`) clears the locker, in any Form, ignoring any auxiliary operand.
* 1–55 name a _State_:
** 1–47 are the _Valid_ States (<<KLEE-states-valid>>). 46 and 47, _Success_ and _Failure_ of the Machine, cannot be set directly; _Failure_ is an outcome, not an error.
** 48–55 are the Error States (<<KLEE-states-error>>); 54 and 55 are reserved, and so is 53 without `Zklexpire`.
   An Error State is accepted as `#immed7` in any State: a locker in a Complete or Configuration State transitions to it
   (to _Invalid_ for a reserved one) _without raising an exception_, even where reaching that State implicitly would
   raise one, and later usage of the locker performs no operation (Rule <<KLEE-GR-usage-locker-error-state>>).
   On an _Unconfigured_ locker the instruction performs no operation: only the short import
   of <<KLEE-error-state-transfer>> configures a locker directly into an Error State.
* 56–63, whose top four bits are `0b0111`, encode `kl.mgmt` (<<KLEE-instruction-mgmt>>).
* 64 encodes `kl_cfg_clear_ads` (<<KLEE-instruction-clearads>>).
* 65 encodes `kl_cfg_clearall` (<<KLEE-instruction-clearall>>), in Form A with locker 0 and `r` = 0 only.
* 66–127 are Machine-defined, and may change other state information, such as _StateExtension_.

Any other value that the architecture or the current Machine does not support transitions the locker to
Error State _Invalid_; on an _Unconfigured_ locker, every immediate other than `kl_state_unconfigured` and `kl_cfg_clearall` performs no operation (Rule <<KLEE-GR-transition-to-from-unconfigured>>). Some values require a 64- or 128-bit auxiliary operand, in one or more
GPRs or in a vector register (group) `Vs`.

For this instruction and its variants, Rule <<KLEE-GR-klmanagedlocker-override>> applies.
--

[[KLEE-instruction-clear]]
==== kl.clear

`kl.clear Kd` is `kl.setst` (<<KLEE-instruction-setst>>) with no auxiliary operand and `#immed7` = `kl_state_unconfigured` (<<KLEE-State-field>>).
It sets the _State_ of the locker to _Unconfigured_, and releases its resources in the KLF.

Clearing a locker not already _Unconfigured_, or whose `*llockerstatus` field in effect is _Off_ (<<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>>), sets to _Dirty_ the `*llockerstatus` fields in effect for the current privilege mode and the `KLS` fields in effect.

// ////////////////////////////////////////////////////////////////////

[[KLEE-instruction-clearall]]
==== kl.clearall

`kl.clearall` is `kl.setst` with no auxiliary operand and `#immed7` = `kl_cfg_clearall`,
the locker number equal to 0 and `r` = 0.
The locker field names no locker: `kl.clearall` acts on every locker whatever the _State_ of `K0`, and is not a usage instruction.

It unconfigures every locker, as `kl.clear` on each would.
It also unconfigures the KLIOBUF, zeroing the buffer and setting `kliobuflen`, `kliobuftop` and `klstart` to 0; zeroizes the three authentication registers of <<KLEE-KLF>>; and writes 32 to `klmanagedlocker`.

// ////////////////////////////////////////////////////////////////////

[[KLEE-instruction-clearads]]
==== kl.clearads

`kl.clearads Kd` deletes any ADS from locker `Kd`, and sets _AuxDataLen_ and _ADSDropped_ to 0.
It is `kl.setst` (<<KLEE-instruction-setst>>) with no auxiliary operand and `#immed7` = `kl_cfg_clear_ads` (64).

Software uses it before exporting a locker for another target, possibly a different implementation: the export then produces a more compact, ADS-free SCC, whose ADS a destination with a different KLEE unit might have to drop anyway.
The first usage instruction that needs the ADS regenerates it.
`kl.clearads` is permitted in every Valid State, and may cause an interrupted operation to restart (Rule <<KLEE-GR-clearads>>).

[[KLEE-instruction-mgmt]]
=== kl.mgmt

_Synopsis_::
Open or complete a management operation on a locker.

_Mnemonic_::
`kl.mgmt` is a separate instruction, with only Forms A, C and D of `kl.setst`.
(((KLEE, instruction, kl.mgmt)))

//

_Encoding_::
`kl.mgmt` is an R-type instruction with the encoding of `kl.setst` (<<KLEE-instruction-setst>>) and `#immed7`[6:3] = `0b0111`, that is, `#immed7` in 56–63.

_Description_::
+
--
For this instruction, Rule <<KLEE-GR-klmanagedlocker-override>> applies.

`kl.mgmt` brackets the body of a locker management operation (<<KLEE-management-operations>>):
it opens a provisioning, an export or an import on locker `Kd`, and completes it.
Like `kl.setst` it changes the _State_ of the locker, but with different semantics, hence a separate instruction.
The State reached depends on both the previous State of the locker and `#immed7`.
Besides the command in `#immed7`, `kl.mgmt` receives an MDH: when opening, it selects the variant of the operation and may become the MDH of the locker; when completing an import or an export, it restores, from the copy the caller saved, the _State_ the locker had when the operation started.

The valued that `#immed7` can take are given in <<KLEE-management-immeds>>.

The Forms supply the MDH as follows:

* Form A carries no auxiliary operand. Where the operation requires the MDH, Form A is a
  substitution (<<KLEE-usage-input-output>>), and reads it from bytes [0, 15] of the KLIOBUF,
  ignoring `klstart`. After the `klmanagedlocker` check and before any change to the locker, Rule
  <<KLEE-GR-iobuf-configured>> applies, and, with the KLIOBUF configured, `kliobuftop` < 16 raises
  an illegal-instruction exception (Rule <<KLEE-GR-vector-MDH-operand>>).
* Form C carries it in the lowest 128 bits of `Vs`.
* Form D carries it as a 128-bit operand in two or four GPRs starting at `Xs` (Rule
  <<KLEE-GR-multiple-GPRs>>).
* Form B is a reserved encoding (<<KLEE-illegal-instruction-grounds>>).

<<KLEE-locker-management>> gives the precise semantics of each operation.
--

[[KLEE-instruction-getmd]]
=== kl.getmd, kl.getmdl, and kl.getmdv

_Synopsis_::
Export the MDH of a locker.

_Mnemonics_::
+
--
[%hardbreaks]
`kl.getmdl{nbsp}Xd, Ks`(((KLEE, instruction, kl.getmdl)))
`kl.getmd{nbsp}{nbsp}Xd, Ks`(((KLEE, instruction, kl.getmd)))
`kl.getmdv{nbsp}Vd, Ks`(((KLEE, instruction, kl.getmdv)))
--


_Encoding_::
+
--
`kl.getmd*` are R-type instructions that share the opcode and `funct3` of `kl.exec`, with `funct2` = `0b11`.

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Xd' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'rs1', attr: ['Ks'] },
    { bits:  5, name: 0x00  },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'r', attr: ['Zklind']   },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'h' },
    { bits:  1, name: 'v' },
    { bits:  2, name: 0x3, attr: ['funct2'] },
]}
....

`r` is the locker indexing mode selector (Rule <<KLEE-GR-GPR-indirect>>).

With bit `v` (bit 29) = 0, bit `h` (bit 28) selects `kl.getmdl` (`h` = 0) or `kl.getmd` (`h` = 1), and the result goes to GPRs: one GPR on RV64 and a pair on RV32 for `kl.getmdl`, a pair on RV64 and a quartet on RV32 for `kl.getmd` (Rule <<KLEE-GR-multiple-GPRs>>).
With `v` = 1, the instruction is `kl.getmdv`, which writes the entire MDH to the lowest 128 bits of a vector register (group); `h` must then be 0, and `v` = `h` = 1 is reserved.
--

_Description_::
+
--
These instructions copy the MDH of locker `Ks`, which is all-zero for an _Unconfigured_ locker:

* `kl.getmdl` copies bits [63:0] to GPR `Xd` on RV64, and to the pair `X[d+1] @ X[d]` on RV32.
* `kl.getmd` copies bits [127:0]: on RV64, bits [63:0] to `Xd` and bits [127:64] to `X[d+1]`; on RV32, to the quartet `X[d+3] @ X[d+2] @ X[d+1] @ X[d]`.
* `kl.getmdv` copies bits [127:0] to vector register `Vd`, on RV32 as on RV64. Bits above 127 follow the tail-agnostic policy (<<KLEE-KLV>>).

The instructions do not check the validity of the MDH (<<KLEE-Metadata-validity>>).
`Ks` may be `KM` (Rule <<KLEE-GR-klmanagedlocker-override>>).
--

[[KLEE-instruction-getst]]
==== kl.getst, kl.getstx

The pseudo-instructions
(((KLEE, instruction, kl.getst)))
`kl.getst Xd, Ks`
(((KLEE, instruction, kl.getstx)))
`kl.getstx Xd, Ks`
return the _State_, resp. _StateExtension_, field of the MDH of the source locker, for instance to determine whether it is in an Error State (<<KLEE-State-field>>).
They read the MDH with `kl.getmdl`, and extract the field by shifting and masking.

On RV64, `kl.getst` expands to

. `kl.getmdl Xd, Ks`
. `srli  Xd, Xd, 19`
. `andi  Xd, Xd, 0x3F`

and `kl.getstx` to

. `kl.getmdl Xd, Ks`
. `srli  Xd, Xd, 25`
. `andi  Xd, Xd, 0x0F`

On RV32 the code is the same: `kl.getmdl` writes the lower 64 bits of the MDH to the pair `X[d+1] @ X[d]`, and _State_ and _StateExtension_ lie entirely in the lower 32 bits, in `X[d]`.

[[KLEE-instruction-restrict]]
=== kl.restrictl, kl.restricth, and kl.restrictv

_Synopsis_::
Restrict the policies encoded in a CC in a locker.

_Mnemonic_::
+
--
[%hardbreaks]
`kl.restrictl{nbsp}{nbsp}Kd, Xs1`(((KLEE, instruction, kl.restrict)))
`kl.restricth{nbsp}{nbsp}Kd, Xs1`
`kl.restrictv{nbsp}{nbsp}Kd, Vs1`
--

_Encoding_::
+
--
`kl.restrict*` are R-type instructions that share the opcode and `funct3` of `kl.exec`, with `funct2` (the two msbs of `funct7`) = `0b01`.
[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Kd' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'Xs1' },
    { bits:  5, name: 0x0 },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'r', attr: ['Zklind']   },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'h' },
    { bits:  1, name: 'v' },
    { bits:  2, name: 0x1, attr: ['funct2'] },
]}
....

`r` is the locker indexing mode selector (Rule <<KLEE-GR-GPR-indirect>>).

With bit `v` (bit 29) = 0, bit `h` (bit 28) selects `kl.restrictl` (`h` = 0) or `kl.restricth` (`h` = 1), and the input comes from a GPR (a GPR pair on RV32).
With `v` = 1, the instruction is `kl.restrictv`, `h` must be 0, and the input comes from the lowest 128 bits of a vector register (group); `v` = `h` = 1 is reserved.
--

// comment

_Description_::
+
--
These instructions narrow the policies of the CC in locker `Kd`, whose MDH is `md`,
as the operand `Xs1` (`Vs1` for `kl.restrictv`), in the format of an MDH, requests.
For _Locality_, _UsagePolicy_ and _ExpirationDate_ the result is the narrowing of `md` by `Xs1`
(Metadata Narrowing Rule <<KLEE-MNR>>), except that a request weaker than `md`, which a narrowing would silently override,
transitions the locker to _Invalid_, as the rules below state field by field.
`kl.restrictl` takes bits [63:0] of the operand and may change _MachinePolicy_ and _SCProtection_; `kl.restricth` takes bits [127:64] and may change _Locality_, _UsagePolicy_
and _ExpirationDate_; `kl.restrictv` takes both halves and applies both sets of rules in one instruction.

A zero field of `Xs1` leaves the corresponding field of `md` unchanged, and a non-zero field not named above transitions the locker to _Invalid_.
Every check, including those that transition the locker to Error State _Invalid_, precedes any allocation of KLF capacity for a _SCProtection_ request, as in
`kl.mgmt` (<<KLEE-locker-management>>), and all changes are applied together once every check has passed.
Validity (<<KLEE-Metadata-validity>>) is evaluated on the changed fields of the resulting MDH, without re-examining the unchanged ones: a request that would produce an
unsupported or invalid value, such as a non-zero _ExpirationDate_ without `Zklexpire` or a
_Locality_ subfield naming an unconfigured entry, transitions the locker to _Invalid_.

The rules for each non-zero field of `Xs1` are:

* _MachinePolicy_: if the Machine does not use the field, or uses it to extend _Machine_,
  the locker transitions to _Invalid_. Otherwise the new value replaces the old one only if every bit
  it sets was already set, so that no disabled function can be enabled. Any other value
  transitions the locker to _Invalid_. A Machine
  with fields that exist only for some values of _MachinePolicy_, such as the ECC Machines
  (<<Zkl-ISA-machines.adoc#KLEE-ECC>>), states what a narrowing does to them.

* _SCProtection_: requests raising the side-channel protection to that level. A
  request for a weaker level transitions the locker to _Invalid_. If the stronger level needs
  KLF capacity that cannot be allocated, a KLEE out-of-memory exception is raised.

* _Locality_: each subfield (<<KLEE-locality-indexes>>), bits [1:0], [3:2] and [5:4] and each of
  bits 6, 7 and 8, is treated independently. A subfield of `Xs1` that is zero or equal to that of
  `md` requests no change, and a zero subfield of `md` takes the value of `Xs1`. A non-zero HW Binding
  subfield may be replaced only by a stricter entry of its chain: _SiPScrt_ by _ChipFamScrt_ or
  _ChipScrt_, _ChipFamScrt_ by _ChipScrt_, _OEMScrt_ by _ProdScrt_ or _DevScrt_, and _ProdScrt_ by
  _DevScrt_. Any other change, including any change of a non-zero Boot Session or SW Filter
  subfield and any weakening, transitions the locker to _Invalid_. A later export binds the SCC to the
  new _Locality_.

* _UsagePolicy_: each set bit removes a permission, and each clear bit changes nothing: bits 0–3
  set the corresponding disallow bits of `md`, and bit 4 clears its Debug grant. No request can
  widen the set of modes that may use the CC.

* _ExpirationDate_: if `md`._ExpirationDate_ is zero or `Xs1`._ExpirationDate_ {le}
  `md`._ExpirationDate_, the value in `Xs1` replaces it; otherwise the locker transitions to _Invalid_.

The instructions may be issued in any Complete State, but in an Error State a request that would transition
the locker to _Invalid_ instead performs no operation, leaving the Error State unchanged. In the _Unconfigured_ State they perform no
operation, and in a Configuration State Rule <<KLEE-GR-usage-locker-config-state>> applies.
They are not usage instructions (Rule <<KLEE-GR-usage-policy>>): every change narrows the CC, so a mode that the _UsagePolicy_ excludes gains no capability; the same holds for `kl.clear` (<<KLEE-instruction-clear>>), a stronger denial primitive.
--

// ////////////////////////////////////////////////////////////////////

[NOTE]
====
These instructions enable two practical use cases:
privileged code can give a CC to some processes rather than to all, by cloning the locker and customizing the Localities of each clone; and
split a CC capable of encryption and decryption into two CCs, one able only to encrypt and the other only to decrypt, creating a one-way channel between processes.
Such customizations save time and computation by avoiding round-trips to trusted environments.
====

[[KLEE-instruction-clone]]
=== kl.clone, kl.rename, and kl.swap

_Synopsis_::
Copy, move or exchange the CCs of lockers.

_Mnemonic_::
`kl.{clone, rename, swap} Kd, Ks`
(((KLEE, instruction, kl.clone)))
(((KLEE, instruction, kl.rename)))
(((KLEE, instruction, kl.swap)))

_Encoding_::
These are R-type instructions that share the opcode and `funct3` of `kl.exec`, with `funct2` = 2.
+
[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Kd' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'Ks' },
    { bits:  5, name: 0x0 },
    { bits:  2, name: 'R', attr: ['Zklind']   },
    { bits:  2, name: 'T' },
    { bits:  1, name: 0x0 },
    { bits:  2, name: 0x2, attr: ['funct2'] },
]}
....
+
--
Field `T` (bits [28:27]) selects the instruction:

. `00`{nbsp}{nbsp} encodes `kl.clone`.
. `01`{nbsp}{nbsp} encodes `kl.rename`.
. `10`{nbsp}{nbsp} encodes `kl.swap`.
--

// Comment to ensure proper indentation in the next Description

_Description_::
+
--
`kl.clone`:::
Clones the source locker `Ks` (or the locker indexed by `Xs`) into the destination locker `Kd` (or the locker indexed by `Xd`):

* If source and destination are the same locker, the instruction performs no operation, even if the locker is _Unconfigured_, _Off_, or in a Configuration State, which is excepted from Rule <<KLEE-GR-usage-locker-config-state>>, and sets no `*llockerstatus` or `KLS` field to _Dirty_ (<<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>>).
* An _Unconfigured_ source makes the destination _Unconfigured_ too, as `kl.clear Kd` would (<<KLEE-instruction-clear>>): the clone of an unconfigured locker is an unconfigured locker.
* A source in a Configuration State raises a KLEE privilege-violation exception (Rule <<KLEE-GR-usage-locker-config-state>>). A source in an Error State is cloned as its MDH alone (Rule <<KLEE-GR-error-state-locker-is-only-MDH>>).
* Otherwise, if the KLF capacity available once the destination is cleared does not suffice for a clone of the source, a KLEE out-of-memory exception is raised, and the destination is left unchanged.
* Otherwise the destination is cleared and becomes a perfect copy of the source: all internal data, MDH and internal state included, are copied verbatim.
If `klmanagedlocker` named the destination, it becomes 32 (<<KLEE-CSR-klmanagedlocker>>).
The effect is that of an export from the source followed by an import into the destination, except that no authentication register is touched.

`kl.rename`:::
If `Ks` = `Kd`, no operation is performed, even if the locker is _Off_, and no field is set to Dirty.
Otherwise the CC of `Ks`, Configuration State included, becomes the CC of `Kd`, the previous CC of `Kd` is discarded, `Ks` becomes _Unconfigured_, and the fields in effect for both lockers are set to Dirty. With an _Unconfigured_ source, `kl.rename` thus acts as `kl.clear Kd` and also clears `Ks`, except for this setting to Dirty.
If `klmanagedlocker` = `s`, it becomes `d`; otherwise, if it is `d`, it becomes 32. The source access is not exempt from the KLEE locker-Off exception; the destination access is exempt, as for `kl.clone`.

`kl.swap`:::
If `Ks` = `Kd`, no operation is performed, even if the locker is _Off_.
Otherwise the CCs of `Ks` and `Kd` are exchanged, and if `klmanagedlocker` {in} {`s`,`d`}, it takes the other index. Neither access is exempt from the KLEE locker-Off exception. The fields in effect for both lockers are set to Dirty.

Neither `kl.rename` nor `kl.swap` raises a KLEE out-of-memory exception or changes the content of any MDH.
<<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>> gives the behavior under emulation, when the source or destination locker is _Off_ in some `*llockerstatus`.
--

[[KLEE-instruction-derive]]
=== kl.derive

_Synopsis_::
Transfer data from one locker into another without exposing it to software.

_Mnemonic_::
`kl.derive Kd, Ks1, Xs2`
(((KLEE, instruction, kl.derive)))

_Encoding_::
+
--
`kl.derive` is an R-type instruction.

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Kd' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'Ks1' },
    { bits:  5, name: 'Xs2' },
    { bits:  2, name: 'R', attr: ['Zklind']   },
    { bits:  2, name: 0x3 },
    { bits:  1, name: 0x0 },
    { bits:  2, name: 0x2, attr: ['funct2'] },
]}
....

The auxiliary input is always a GPR: `kl.derive` has no form without one, and no vector form.
--

_Description_::
+
--
`kl.derive` moves up to `length` bytes, which the auxiliary GPR carries, from an endpoint of the source locker to an endpoint of the
destination locker, without making them visible to software: the output of one Machine becomes an
input, possibly a key or another Content field, of another.

A transfer is _unrestricted_ if software could also obtain the data moved by issuing `kl.exec` instructions, or if a Rule declares it unrestricted; otherwise it is _restricted_.

Source and destination must be different lockers; otherwise an illegal-instruction exception is raised.
Usage Control applies to both lockers (Rule <<KLEE-GR-usage-policy>>), and both are checked
before any state change or transfer, in the order of Rule <<KLEE-GR-checks>>.

The _State_ and _StateExtension_ of each locker determine its endpoint: the source must be in a State in which it can export data, and
the destination in one in which it can import data.
These States alone define the fields exported or imported, or the type of the data that `kl.exec` instructions would generate or absorb; no parameter of `kl.derive` selects them.

An _endpoint descriptor_, of the source or of the destination, consists of: +
(MDH._Machine_ {vvert} _MachinePolicy_, MDH._State_ {vvert} _StateExtension_, MDH._KeyType_, +
{nbsp}{nbsp}{nbsp}MDH._SCProtection_,  MDH._UsagePolicy_, MDH._Locality_, MDH._ExpirationDate_).

A transfer may occur only if the architecture allows the pair of endpoint descriptors.
An allowed pair may define a minimum length, an upper limit and a granularity; the architecture defines, per pair, the semantics of the transfer and its updates to the States of the two lockers, to `klstart` and `vstart`, and to any other state of the hart.
The checks below then decide: a disallowed transfer transitions the lockers as they specify, and an allowed one updates the policies of the destination as follows.
--

[[KLEE-instructions-memory]]
=== Memory Instructions

[[KLEE-Memory-Alignment,Memory Alignment Constraints]]
Accesses to the serialized, user-visible representation of the `Content` of a locker are 16-byte granular: `kl.load`, `kl.store`, `kl.mvin` and `kl.mvout` transfer whole 16-byte blocks, and all their offsets and lengths, `klstart`, `content_size`, `max_admissible`, `image_size` and `image_end` (<<KLEE-instruction-mv>>), are multiples of 16 bytes.

The effective address of a `kl.load` or `kl.store` must be 16-byte aligned, so a PI or SCC must be held at a 16-byte aligned address.
A misaligned address transfers no data and raises a load or store address-misaligned exception on that address; the check applies even when the transfer window is empty.
`kl.load` and `kl.store` evaluate their conditions in this order:

. the illegal-instruction grounds of both groups and the KLEE exceptions, in the order of <<Zkl-ISA-priv.adoc#KLEE-exception-codes>>;
. the address breakpoint of the first component access, if any;
. address-misaligned, on the effective address; and
. for each component access, in offset order, the address breakpoint, then access, page and guest-page faults.

`kl.input` and `kl.output` are byte-granular and impose no alignment constraint: a misaligned effective address behaves as for an ordinary load or store on the implementation.

[[KLEE-instruction-load]]
==== kl.load and kl.input

(((KLEE, instruction, kl.load)))(((KLEE, instruction, kl.input)))_Mnemonics_::
`kl.load %offset(Xs1)` +
`kl.input %offset(Xs1)`

_Encoding_::
--
`kl.load`/`kl.input` is an I-type instruction.

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x03, attr: ['LOAD'] },
    { bits:  5, name: 'Xl' },
    { bits:  3, name: 0x7, attr: ['kl.input'] },
    { bits:  5, name: 'Xs' },
    { bits: 12, name: 'immed12' },
]}
....
--

_Description_::
+
--
The locker number is not an argument of this instruction.
The locker to which data is copied to is determined by the `klmanagedlocker` CSR, if `klmanagedlocker` < 32.
If `klmanagedlocker` = 32, the operation addresses the KLIOBUF: with `Xl` = 0 it performs no operation and writes 0 to `klstart`, whether or not `Zklio` is in effect and the KLIOBUF configured (Rule <<KLEE-GR-cleared-under-management>>); otherwise it writes to the KLIOBUF, if `Zklio` is in effect, and raises an illegal-instruction exception if not.

NOTE: `kl.input` is an alias for `kl.load`, to be used in source code when it is clear that `klmanagedlocker` = 32.

For `klmanagedlocker` < 32:::
`kl.load` imports the Content of a PI or an SCC into the locker. The length argument `Xl` must be 0; a non-zero `Xl` raises an illegal-instruction exception.
+
NOTE: `Xl` has a meaning only for the KLIOBUF. A non-zero value while a locker is under management reveals a `kl.input` or `kl.output` issued at the wrong time, and is reported rather than ignored.
It is never used on a locker in an Error State (Rule <<KLEE-GR-error-state-locker-is-only-MDH>>, <<KLEE-error-state-transfer>>), and does not transfer the MDH, which `kl.mgmt` carries.
As for `kl.mvin`, the leading bytes of the image are the authentication fields `SIV`, `IMPQUAL` and `SIV2`, which `kl.load` writes to the authentication registers of <<KLEE-KLF>>.
+
Transfers follow the constraints of `kl.mvin` (<<KLEE-instruction-mv>>, <<KLEE-Memory-Alignment>>), with `S`, `image_end` and _ContentOffset_ as defined there.
`kl.load` transfers the offsets `[klstart, image_end-1]` of `S`: for each _j_ from `klstart` to `image_end` − 1, it loads the byte at memory address ``Xs1 + %offset + ``_j_ into byte _j_ of `S`.
`klstart` tracks a prefix-complete number of bytes loaded; if `klstart` {ge} `image_end`, nothing is transferred.
On an _Unconfigured_ locker, or one in an Error State, `kl.load` has an empty transfer window, and accesses no memory (Rule <<KLEE-GR-cleared-under-management>>).
+
With a system-specific format, the semantics of `kl.load` are implementation-defined and must be documented, and must satisfy Rules <<KLEE-GR-zkl-load-mv-allowed>> and <<KLEE-GR-which-resumable-instructions>>–<<KLEE-GR-memory-instructions>>.

For `klmanagedlocker` = 32:::
[[KLEE-iobuf-transfer-window,KLIOBUF transfer window]]
`kl.input` and `kl.output` both transfer the bytes of the transfer window: for each `j` from `klstart` to
min(`Xl`, `kliobuftop`) − 1,
`kl.input` copies the byte at memory address `%offset(Xs)` + `j` to byte `j` of the KLIOBUF,
and `kl.output` copies byte `j` of the KLIOBUF to memory address `%offset(Xs)` + `j`.
Bytes below `klstart`, and at or beyond min(`Xl`, `kliobuftop`), are accessed on neither side.
With `Xl` = 0, the operation transfers nothing and writes 0 to `klstart`, before Rule <<KLEE-GR-iobuf-configured>> is evaluated; with `klstart` {ge} min(`Xl`, `kliobuftop`), it does the same after that Rule.
If `Xl` exceeds `kliobuftop`, only the bytes of the window are transferred.
--

(((KLEE, instruction, kl.store)))(((KLEE, instruction, kl.output)))_Mnemonics_::

| `kl.load`                   | Yes             | No  | No^*^                | Updates `klstart`.

[[KLEE-GR-iobuf-configured,GR9]]GR9:: Instructions that access the KLIOBUF, such as `kl.input` and `kl.output`, require the KLIOBUF to be enabled and `kliobuflen` to be non-zero; otherwise they raise an unconfigured-KLIOBUF exception.

=== Randomness

[horizontal]
[[KLEE-GR-rbg-failure,GR11]]GR11:: _Failure of the random bit generator:_
If an operation needs random bits from the RBG (<<KLEE-Prerequisites>>), for instance for a key, a key pair, a signing
nonce, the per-encapsulation randomness of a KEM, or the key of an all-ones SKID when provisioning completes, and the RBG
fails to supply them, the operation is not performed, and the locker transitions to Error State _Invalid_, which clears its
Content (Rule <<KLEE-GR-clear-locker-content-error-state>>).
An _RBG failure_ is a permanent failure that the entropy source reports (for `Zkr`, the DEAD state), or a failed health test.
While random bits are only temporarily unavailable, the instruction does not complete and changes no state: it waits, or is interrupted and restarted as option 3 of Rule <<KLEE-GR-uninterruptible-instructions>> or option 5 of Rule <<KLEE-GR-resumability-options>> allows.
An implementation that cannot obtain the bits within an implementation-defined bound treats the condition as an RBG failure, so that the instruction always terminates. An RBG failure is never reported as _Failure_, which is reserved
for the outcome of an operation that a Machine has performed.

The following _State-Specific General Rules_ (*SGR*) apply to all Machines:

[horizontal]
GR12:: Whenever the CC is in _Ready_, _Success_, _Failure_ or an Error State, the _State_ field of the MDH holds that State, so that _State_ alone identifies it, without inspecting other fields or the Content.

GR13:: A transition listed in the specification of a Machine is triggered by an explicit `kl.setst` (<<KLEE-instruction-setst>>), or by conditions stated by the specification. Transitions to and between Configuration States use `kl.mgmt`; transitions out of a Configuration State use `kl.mgmt`, `kl.clear`, `kl.clearall`, a `kl.setst` to an Error State, a `kl.clone` naming the locker as destination, or a `kl.rename` or `kl.swap` naming it as source or destination.

[[KLEE-GR-state-after-setst,GR14]]GR14:: The State reached upon completion of a `kl.setst` need not be the one its immediate names: besides Error State transitions, some operations determine the next State dynamically.
For example, `kl.setst` with immediate `kl_state_hash_verify` and a verification parameter transitions the locker to _Success_ or _Failure_.
Other instructions, such as `kl.exec`, may also change the _State_, under conditions that the Machine specifies.

=== Rules Governing Valid States

[horizontal]
[[KLEE-GR-to-ready,GR15]]GR15:: `kl.setst` may always transition a locker from a Valid State to _Ready_, unless the Machine explicitly forbids it.
// NOTE: Since a locker can always be restored from a backup SCC, preventing transitions to _Ready_--as "GCM with Set IV" (<<KLEE-GCM-with-IV-mode>>) does--is not an effective mitigation against the attacks that would be enabled by transitioning to _Ready_.

[[KLEE-GR-same-state,GR16]]GR16:: In a Valid State other than _Success_ and _Failure_, `kl.setst` may be issued with the immediate of the current State.
Unless the Machine states otherwise, it repeats the operations of entering that State; in a State that loads a field, this restarts the load (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-load-long-field>>).
Where repeating them would produce an internal state that the referenced standard does not allow or does not define, the Machine forbids the same-State `kl.setst`, which then transitions the locker to Error State _Invalid_ (for instance Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-no-hash-output-repeat>>).

[[KLEE-GR-no-exec-in-ready,GR17]]GR17:: A `kl.exec` in State _Ready_ that the Machine does not explicitly allow transitions the locker to Error State _Invalid_ (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-not-allowed-instructions>> in <<Zkl-ISA-machines.adoc#KLEE-Machines>>).

[[KLEE-GR-clearads,GR18]]GR18:: `kl.clearads` (<<KLEE-instruction-clearads>>) is permitted in every Valid State.
It leaves _State_ and _StateExtension_ unchanged, and is subject to Usage Control (<<KLEE-instruction-properties>> in Rule <<KLEE-GR-usage-policy>>).
Removing the ADS discards any intermediate state of an interrupted long-running operation that the implementation keeps there:
in a State of Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-progress-discard>> it zeroes the progress field _P_, and the operation restarts
when its instruction is next issued, exactly as if the SCC exported before the `kl.clearads` had been imported on a different
KLEE implementation (Rule <<KLEE-GR-long-running-no-data>>).

[[KLEE-GR-success-failure-cannot-be-set-directly,GR19]]GR19:: `kl.setst` cannot set States _Success_ and _Failure_ directly: the immediates 46 and 47 are reserved (<<KLEE-illegal-instruction-grounds>>).

[[KLEE-GR-setst-in-success-failure,GR20]]GR20:: In States _Success_ and _Failure_, `kl.setst` may transition the locker to _Ready_, to _Unconfigured_, or to an explicitly given Error State.
It is also permitted with `#immed7` = `kl_cfg_clear_ads` (<<KLEE-instruction-clearads>>), which clears any ADS and leaves the _State_ unchanged, when the Usage Control policies allow it (Rule <<KLEE-GR-clearads>>).
+
NOTE: Machines such as GCM with a set IV (not GCM-SIV) and Ascon-AEAD128 with a set Nonce could forbid the return to _Ready_ to prevent nonce misuse, but software could bypass this by reloading a saved copy of the original SCC. For simplicity, the architecture therefore allows the return to _Ready_ (<<Zkl-ISA-machines.adoc#KLEE-nonce-reuse>>). The return may nevertheless erase session-bound internal state, such as randomly generated nonces, as the Machine specifies.

[[KLEE-GR-success-failure,GR21]]GR21:: In States _Success_ and _Failure_, the only KLEE instructions permitted are `kl.mgmt`, `kl.size`, `kl.avail`, `kl.setst` (subject to Rule <<KLEE-GR-setst-in-success-failure>>), `kl.getmd*`, `kl.getst`, `kl.clone`, `kl.rename`, `kl.swap`, `kl.restrict*` and `kl.derive`.
+
In State _Success_, `kl.exec` is also permitted, solely to extract further output from a Machine that produces arbitrarily long output without consuming further input, such as a XOF.
`kl.derive` is permitted only where the source endpoint is one of the exportable fields of the locker (<<KLEE-instruction-derive>>), or under the conditions on `kl.exec`; a locker in State _Success_ or _Failure_ may not be the *destination* of a `kl.derive`.
Any other `kl.exec`, or a `kl.setst` that the architecture or the Machine does not allow in the current _State_ and _StateExtension_, transitions the locker to Error State _Invalid_ (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-not-allowed-instructions>> in <<Zkl-ISA-machines.adoc#KLEE-Machines>>).
+
NOTE: ML-KEM (<<Zkl-ISA-machines.adoc#KLEE-PQC-ML-KEM>>) is the motivating case for this `kl.derive` behavior:
`ML-KEM.Decaps`, and `ML-KEM.Encaps` once its ciphertext has been emitted, leave the shared secret in `sharedkey` and
transition to _Success_, from which the only other exit is _Ready_, and _Ready_ clears
`sharedkey`. Without this provision the shared secret would be unreachable, and ML-KEM useless for its stated purpose.

=== Rules governing Error States and the _Unconfigured_ State

[horizontal]
[[KLEE-GR-clear-locker-content-error-state,GR22]]GR22:: On transitioning to an Error State, a locker clears its Content beyond the MDH, and releases the internal resources associated with it, any ADS included; _AuxDataLen_ and _ADSDropped_ are set to 0.

[[KLEE-GR-error-state-locker-is-only-MDH,GR23]]GR23::
A locker in an Error State holds only its MDH, and its size (<<KLEE-instruction-size>>) is 16 bytes.

[[KLEE-GR-error-state-can-be-reconfigured,GR24]]GR24:: A locker in an Error State can still be reconfigured, cloned or cleared;
apart from clearing it, `kl.setst` can only change its Error State.

[[KLEE-GR-error-state-exported-as-MDH,GR25]]GR25:: A locker in an Error State is exported as its MDH alone, with all its fields and without `kl.mgmt`, and a single `kl.mgmt` re-imports the image (<<KLEE-error-state-transfer>>), so that software can handle the error even after a context switch.

[[KLEE-GR-usage-locker-error-state,GR26]]GR26:: An attempt to _use_ a locker in an Error State performs no operation, and in particular leaves the _State_ unchanged.
Although such an attempt is an error that would otherwise transition the locker to _Invalid_, the _State_ is kept, so that software can address the original error condition; the architecture keeps no history of Error States.
+
A usage instruction with an output operand that performs no operation under this Rule or under <<KLEE-GR-gate-order>> (_Unconfigured_, Error State, expiration, unreadable secure clock), or that transitions its locker to an Error State during execution, writes zeros to every byte of its output window that it has not written: elements `vstart` to `vl` − 1 of `Vd` for a vector output, bytes [`klstart`, `kliobuftop`-1] for a KLIOBUF output. An in-place operation thus never leaves its input in place of the output it did not produce.

[[KLEE-GR-transition-to-from-unconfigured,GR27]]GR27:: Only a configuration instruction can transition a locker from _Unconfigured_ to a Complete State.
Any usage instruction (<<KLEE-instruction-properties>> in Rule <<KLEE-GR-usage-policy>>) in State _Unconfigured_ performs no operation and raises no exception: the locker stays _Unconfigured_, and an output operand is zeroed as Rule <<KLEE-GR-usage-locker-error-state>> prescribes; `kl.derive` has no output operand, and performs no operation if either endpoint is _Unconfigured_.
A locker leaves an Error State for _Unconfigured_ through `kl.clear` or `kl.clearall`, through a `kl.rename` naming it as source, through a `kl.clone` or `kl.rename` naming it as destination with an _Unconfigured_ source (<<KLEE-instruction-clone>>), or by being re-opened for provisioning or import.

[[KLEE-GR-getmdto-from-unconfigured,GR28]]GR28:: `kl.getmd*` (<<KLEE-instruction-getmd>>) reads the MDH of an _Unconfigured_ locker as all zeros.

[[KLEE-GR-cleared-under-management,GR29]]GR29:: On a locker that is _Unconfigured_ or in an Error State, `kl.load`, `kl.store`, `kl.mvin`, `kl.mvout` and `kl.mgmt` with `kl_cfg_management_end` perform no operation and raise no exception; so does `kl.mgmt` with `kl_cfg_exporting`, since the short export path of an Error-State locker uses no `kl.mgmt` (<<KLEE-error-state-transfer>>).
When `klmanagedlocker` = 32, the value a clear leaves (<<KLEE-CSR-klmanagedlocker>>), `kl.mvin`, `kl.mvout`, and `kl.load` and `kl.store` with `Xl` = 0 likewise perform no operation and raise no exception, before any check of `Zklio` or of the KLIOBUF.
These outcomes follow the checks that do not depend on the _State_: the first group of <<KLEE-illegal-instruction-grounds>>, the KLEE fatal-error, missing-CSK and locker-Off exceptions and, for `kl.mgmt`, the check of `klmanagedlocker`. In detail:
+
--
* `kl.load` and `kl.store` have an empty transfer window, whatever the value of `klstart`: they access no memory, retire with `klstart` = 0, but can still raise the address-misaligned exception (<<KLEE-Memory-Alignment>>). With `klmanagedlocker` = 32 the address is not checked for alignment, as for `kl.input` and `kl.output`.
* `kl.mvin` and `kl.mvout` leave `klstart` unchanged, whatever its value; `kl.mvout` writes zeros, as when `klstart` {ge} `image_end` (<<KLEE-instruction-mv>>).
* `kl.mgmt` reads neither its auxiliary operand nor the KLIOBUF, so that Rules <<KLEE-GR-vector-MDH-operand>> and <<KLEE-GR-iobuf-configured>> do not apply; it leaves the authentication registers unchanged, and performs only its common steps (<<KLEE-locker-management>>), which leave `klstart` = 0, and `klmanagedlocker` = 32 on an _Unconfigured_ locker and the number of the locker on an Error-State one. On a locker in a Valid State, `kl_cfg_management_end` still raises an illegal-instruction exception.

Software that exports a locker must rely on the image only if the _State_ read after the last instruction of the export, or in the MDH that `kl.getmd*` returned when the image is the MDH alone, is not _Unconfigured_.
--

[NOTE]
====
Rule <<KLEE-GR-cleared-under-management>> prevents a _check-then-use race_ in management procedures, and also simplifies them.
A handler may clear a partially provisioned or imported locker instead of saving it, which forces the interrupted operation to restart (<<KLEE-CC-management>>, which also obliges system software to let the operation complete).
The interrupted software detects the clear by reading the _State_ after each management instruction (<<Zkl-pseudocode.adoc#KLEE-management-code-snippets>>).
If the clear occurs after such a check, the instructions that follow perform no operation, and the software simply falls through to its next check, where it detects the clear and restarts: no trap is needed, and no handler has to deal with one.
The Rule covers `klmanagedlocker` = 32 for the same reason: a clear writes 32 to `klmanagedlocker` (<<KLEE-CSR-klmanagedlocker>>), so a transfer issued in the race window no longer addresses a locker (Rule <<KLEE-GR-klmanagedlocker-override>>).
For the same reason an instruction naming `KM` then behaves as on an _Unconfigured_ locker: the `kl.getst` that follows reads zero, and the software restarts.
Without the no-op, `kl.load` would act as `kl.input` and write memory into the KLIOBUF, `kl.store` as `kl.output` and write the KLIOBUF into the buffer meant for the SCC, and `kl.mvin` or `kl.mvout` would trap, each for a benign race.
The no-op costs nothing: a locker transfer always has `Xl` = 0, and `kl.input` or `kl.output` with `Xl` = 0 transfers nothing in any case.
The same holds for an Error State that a handler sets on a locker under management, for instance _Out of Memory_ when a context restore cannot re-import it: software detects the Error State at its next check and abandons the operation.

An export cannot be restarted, since the clear destroys what was being exported. Its instructions, the opening `kl.mgmt` included, nevertheless perform no operation, so that the exporting software learns of the loss from its own checks rather than from a trap.
// Layered system software then composes: a guest OS saving a partially provisioned locker when the hypervisor clears it finds the locker _Unconfigured_, saves no image, and passes the restart on to the provisioning software.
Once cleared, a locker stays _Unconfigured_ until software reopens it, so the check after the last instruction of an export alone decides whether the image is complete; earlier checks only end the export sooner.
====

=== Rules governing Configuration States

[horizontal]
[[KLEE-GR-opening-locker-when,GR30]]GR30:: _When a locker can be opened for import or export:_
Opening a locker for provisioning or import, and executing `kl.clear`, is allowed in every State, since the
locker is zeroized first; opening it for export is allowed in every Complete or Configuration State, and performs no operation on an _Unconfigured_ locker (Rule <<KLEE-GR-cleared-under-management>>).
No Machine may set conditions under which a locker can be opened for export or import, or cleared.

[[KLEE-GR-config-instructions-config-state,GR31]]GR31:: The following configuration instructions, which Usage Control policies do not gate, are also allowed on a locker in a Configuration State:
`kl.size`, `kl.avail`, `kl.getmd*`, `kl.getst`,
`kl.setst` with the immediate `kl_state_unconfigured` (`kl.clear`) or an Error State,
`kl.clearall`, `kl.clone` naming the locker as destination, and `kl.rename` and `kl.swap`, which move a CC unchanged (<<KLEE-instruction-clone>>).

[[KLEE-GR-zkl-load-mv-allowed,GR32]]GR32:: `kl.load` and `kl.mvin`
are allowed in States `kl_cfg_provisioning`, `kl_cfg_importing` and `kl_cfg_ppi_importing`, on the locker that `klmanagedlocker` names (Rule <<KLEE-GR-klmanagedlocker-override>>).

[[KLEE-GR-zkl-store-mv-allowed,GR33]]GR33:: `kl.store` and `kl.mvout`
are allowed in States `kl_cfg_exporting` and `kl_cfg_ppi_exporting`, on the locker that `klmanagedlocker` names (Rule <<KLEE-GR-klmanagedlocker-override>>).

[[KLEE-GR-usage-locker-config-state,GR34]]GR34:: Using a locker in a Configuration State, cloning from it, or restricting it raises a KLEE privilege-violation exception.
<<KLEE-instruction-clone>> covers such a locker as the destination of a `kl.clone`, or as both its source and its destination.

[[KLEE-GR-completion-state,GR35]]GR35:: The `kl.mgmt` that completes a management operation (<<KLEE-locker-management>>) leaves the locker:
+
--
* after a provisioning, in State _Ready_, with _StateExtension_ and _MachineUse_ zero;
* after an import or an export, in the _State_ supplied in `ml`, that is the one the locker had when it was exported, resp. when the export was opened, and which may itself be a Configuration State; an import thus restores the _State_ and the _StateExtension_ that the locker had at export, the latter carried in the SCC; or
* in an Error State, or in _Failure_, if a check made at completion fails: _Authentication Failed_ for the `SIV` check, and otherwise the outcome that the failing check prescribes.
--

=== Derivation Rules

[horizontal]
[[KLEE-GR-checks,GR36]]GR36:: The checks of <<KLEE-GR-gate-order>> apply to both lockers, each to the source before the destination.
The following checks are then made in order; a failed check transitions the failing locker or lockers to Error State _Invalid_, and nothing is transferred:

. The _State_ and _StateExtension_ of the source must define a source endpoint (<<Zkl-ISA-machines.adoc#KLEE-derive-endpoints>>); otherwise the source transitions.
. The _State_ and _StateExtension_ of the destination must define a destination endpoint. A key field, that is a symmetric or a private key, is a destination endpoint only in State _Ready_ or in a State that the Machine names for loading it, such as _Set_Key_ of HMAC (<<Zkl-ISA-machines.adoc#KLEE-HMAC>>) or _Set_Scalar_ of ECC (<<Zkl-ISA-machines.adoc#KLEE-ECC>>), and never when the destination _KeyType_ is 1 (Rule <<KLEE-GR-SKID-no-export>>). Otherwise the destination transitions.
. The two endpoints must form a pair that Rule <<KLEE-GR-shared-secret>>, <<KLEE-GR-exec-implies-unrestricted>> or <<KLEE-GR-DRBG-implies-unrestricted>> admits, or that <<Zkl-ISA-machines.adoc#KLEE-Machines>> explicitly defines; otherwise both lockers transition.
. The effective length (Rule <<KLEE-GR-derive-rule-both-fixed-size>>) must meet the minimum, upper limit and granularity of the pair, and the transferred data any other constraint of the destination; otherwise the destination transitions.
. A destination key field of `dest_length` bytes requires `length` {ge} `dest_length`, and a source field, or remaining `kl.exec` output, of at least `dest_length` bytes; otherwise the destination transitions. The key field receives exactly `dest_length` bytes, which complete its loading; a key written in State _Ready_ is followed by the initialization that the Machine performs in that State.

[[KLEE-GR-narrowing,GR37]]GR37:: Before any _restricted transfer_, the MDH of the destination locker is narrowed by that of the source locker (Metadata Narrowing Rule <<KLEE-MNR>>).
If the narrowing fails, or if the destination _SCProtection_ is lower than that of the source in the ordering of <<KLEE-SC-protection-levels>>, the destination transitions to Error State _Invalid_, and nothing is transferred.

[[KLEE-GR-unrestricted,GR38]]GR38:: An _unrestricted transfer_ applies no policy narrowing.

The narrowing of restricted transfers follows NIST SP 800-57 Part 1 Rev. 5 cite:[nist-SP-800-57-p1-r5], §6.2.1 (key-usage and cryptoperiod metadata protection), and NIST SP 800-108r1 cite:[nist-SP-800-108-r1] §8 (derived keys inherit the security strength and use constraints of the key-derivation key): these Recommendations expect derived material to inherit every constraint of its parent.
Any further transfer that a Machine defines must respect these restrictions.

[horizontal]
[[KLEE-GR-SKID-no-export,GR39]]GR39:: A field configured by a SKID is _never_ exportable, and a key field of a locker whose _KeyType_ is 1 is _never_ importable. No rule may be defined to export or import such a field.

[[KLEE-GR-shared-secret,GR40]]GR40:: Moving a shared secret from a key-agreement or key-encapsulation Machine, such as the ECC `SecondPt` or the ML-KEM `sharedkey`,
into a key field of a symmetric Machine, a private key field of a public-key Machine, or the `kl.exec` input of a hash, MAC or XOF is a _restricted transfer_.
It is admitted whenever both endpoints are defined (Rule <<KLEE-GR-checks>> items 1 and 2); a key field receives the first `dest_length` bytes of the secret (Rule <<KLEE-GR-checks>> item 5).

[[KLEE-GR-exec-implies-unrestricted,GR41]]GR41:: The `kl.exec` _output_ of a source locker, listed in <<Zkl-ISA-machines.adoc#KLEE-derive-endpoints>> as a source endpoint, is the data that the Form C `kl.exec` instructions permitted in its current _State_ would emit; the tag of an AEAD Machine is not such output, unless that Machine explicitly allows it.
The `kl.exec` output can always be moved, as an _unrestricted transfer_, into a destination endpoint that Form B `kl.exec` instructions load in the current _State_ of the destination, such as the `kl.exec` input of a hash function, MAC or XOF, or the `Scalar` of an ECC Machine in State _Set_Scalar_: the transfer is a shortcut for `kl.exec` instructions that software could issue on both lockers.
+
NOTE: Such transfers are allowed and unrestricted because in these cases the source data can be obtained
and the destination fields can be freely written by the caller, so no attack surface is increased.
// NOTE: Such a destination may be a key field, such as the `Scalar` of an ECC Machine or the `K0` of HMAC. Moving any `kl.exec` output into it does not increase the attack surface, which is why
// software can always provision a new locker with a key of its choice and any policies, and use it in place of a locker whose key it does not know.
+
_Key derivation._ The `kl.exec` output of a hash function, MAC or XOF can also be moved, as an _unrestricted transfer_, into a key field of a symmetric Machine or a private key field of a public-key Machine, in a State in which Rule <<KLEE-GR-checks>> item 2 admits that field; the key field receives the first `dest_length` bytes of the output (Rule <<KLEE-GR-checks>> item 5).

[[KLEE-GR-DRBG-implies-unrestricted,GR42]]GR42:: A Machine implementing a DRBG (none is currently architected) may generate random data
into a symmetric key field, or a private key field, of a destination Machine in a State that admits the field (Rule <<KLEE-GR-checks>>).
This is an _unrestricted transfer_, since the output of a DRBG must neither predictably repeat a value
nor be extrapolable from previous or later outputs.

//

A pair defined in <<Zkl-ISA-machines.adoc#KLEE-Machines>> may further narrow, but never relax, any policy.

An _exportable field_ is one that its Machine lists as a source endpoint in <<Zkl-ISA-machines.adoc#KLEE-derive-endpoints>>, and an _importable field_ one that it lists as a destination endpoint.
Rules <<KLEE-GR-shared-secret>>, <<KLEE-GR-exec-implies-unrestricted>> and <<KLEE-GR-DRBG-implies-unrestricted>> admit pairs of endpoints; any other pair not explicitly defined in <<Zkl-ISA-machines.adoc#KLEE-Machines>> fails Rule <<KLEE-GR-checks>> item 3.

[horizontal]
[[KLEE-GR-derive-rule-both-fixed-size,GR43]]GR43:: _Transfer Size Rule:_
A destination field of `dest_length` bytes receives `eff_length` = min(`length`, `dest_length`)
bytes, zero-filled beyond them (zero-filling does not apply to keys, per Rule <<KLEE-GR-checks>>);
any other destination receives `eff_length` = `length` bytes.
`length` = 0 transfers nothing: for a key field it fails the key-length check of Rule <<KLEE-GR-checks>> item 5,
and the destination transitions to Error State _Invalid_; for any other destination the instruction changes no state, provided the other checks of Rule <<KLEE-GR-checks>> pass.
+
The source supplies `eff_length` bytes: the transferred part of a field is truncated to `eff_length` bytes if longer, or zero-padded if shorter, and a source producing output in blocks of `b` bytes produces the blocks needed to cover them.
+
The destination consumes the bytes it received in equal-sized blocks,
where a shorter final block is supplied by a `kl.exec` with a corresponding shorter input.
Each endpoint advances by the amount of data being transferred like the
`kl.exec` operations producing or consuming these blocks would advance it; a destination
State implemented by `process_VLI` may be left open and continued with `kl.exec`.
+
The units of the endpoints must be compatible: if the source produces data as `p`-byte blocks and the destination consumes it
only in `q`-byte block, where `p` and `q` are the granularities of the
two States and not necessarily their block sizes, either `p` or `q` must divide the other.
The implementation can then internally split the output of one outputting `kl.exec` into `p/q` inputting `kl.exec` operations,
or concatenate the outputs of `q/p` outputting `kl.exec` operations into one inputting `kl.exec`,
without carrying state from an internal partial transfer of `max(p,q)` bytes to the next.
+
The interruption points of a `kl.derive` (<<KLEE-CSR-klstart>>) are the `klstart` values that
are interruption points of both endpoints, each in its current State.

[[KLEE-Memory-Model]]
=== Memory Model Rules

In these rules, a _KLEE memory instruction_ is `kl.load`, `kl.store`, `kl.input` or `kl.output`.

[horizontal]
GR44:: KLEE memory instructions appear to execute in program order on the local hart.

GR45:: At the instruction level, KLEE memory instructions follow RVWMO, and, with `Ztso`, also RVTSO.

GR46:: KLEE memory instructions support only idempotent memory: they make no component access to a non-idempotent or side-effecting PMA region.
An instruction whose component access would touch such a region halts precisely at the last prefix-complete point before the offending byte, which may not be 0 (<<KLEE-GR-resumability-options>>), with the completed prefix committed (Rule <<KLEE-GR-which-resumable-instructions>>), and raises a load, resp. store, access-fault exception, with `xepc` at the instruction and `xtval` holding the offending address. Re-execution raises the same exception before any component access, unless the offending byte no longer maps to such a region.

[[KLEE-rule-memory-instruction-decomposed,GR47]]GR47:: A KLEE memory instruction may be decomposed into component memory operations of any granularity, issued in any order that the memory model and the semantics of
`kl.exec`, `kl.load`, `kl.store`, `kl.input` and `kl.output` allow, and none is required to be atomic; ordering within one instruction follows RVWMO, even with `Ztso`.
On a precise interruption, `klstart` records a _prefix-complete_ point of the transfer: an offset below which every component access has been performed, and at or beyond which none has had an architecturally visible effect.

GR48:: Other harts observe the component memory operations as ordinary memory operations under RVWMO, with no ordering among them guaranteed before the instruction completes.
A buffer that a KLEE memory instruction accesses therefore needs the same synchronization to be shared as one that an ordinary software loop accesses.

GR49:: For `FENCE`, `FENCE.I`, `SFENCE.VMA` and the `.aq`/`.rl` annotations, the component accesses of a KLEE memory instruction are ordinary loads (`kl.load`, `kl.input`) or stores (`kl.store`, `kl.output`) of the issuing hart.

=== State change rule for exceptions

[horizontal]
[[KLEE-exception-state-change,GR50]]GR50:: An illegal-instruction exception, or a KLEE
exception other than the fatal-error one, leaves the KLEE state unchanged, except for two changes that `kl.mgmt`
makes even if it later raises an exception (<<KLEE-locker-management>>):
a `kl.mgmt` that opens a provisioning or an import zeroizes the target locker and writes 32 to `klmanagedlocker`, and any `kl.mgmt` that
passes the check of `klmanagedlocker` (<<KLEE-locker-management>>) clears `klstart`.
A KLEE fatal-error exception resets the KLEE state (_Fatal Conditions_ below).


[[KLEE-resumability]]
=== Interruptibility and Resumability of KLEE instructions

[horizontal]
[[KLEE-GR-uninterruptible-instructions,GR51]]GR51:: `kl.mgmt`, `kl.getmd*`, `kl.restrict*`, `kl.clone`, `kl.rename`, `kl.swap`, non-vector `kl.mvin` and `kl.mvout`, `kl.size` and `kl.avail` are architecturally _uninterruptible_: each either completes, raises an exception with only the effects that <<KLEE-exception-state-change>> allows, or has no architecturally visible effect, writing no vector register, GPR, locker byte, KLIOBUF byte or memory.
An implementation achieves this by:
+
--
. completing the instruction before taking an asynchronous interrupt;
. completing it in the background, where Rule <<KLEE-GR-long-running-no-data>> permits, subject to Rule <<KLEE-GR-conflicting-access-rule>>; or
. discarding partial work before taking the trap, and restarting on return.

Software must not rely on whether an uninterruptible instruction has retired when a handler runs, and interacts with it only as Rule <<KLEE-GR-conflicting-access-rule>> prescribes.
--

GR52:: The architecture specifies no interruption point within `kl.setst`, nor within a single block-processing unit of `kl.exec`; an implementation may nevertheless make a long-running instance of either interruptible, as Rule <<KLEE-GR-long-running-no-data>> allows.

[[KLEE-GR-resumability-options,GR53]]GR53:: When an interrupt or exception handler accesses an input or output of a preempted instruction, its locker, or any KLEE state that the instruction may affect, the implementation may choose among:

. _Background completion:_ the hart waits for the instruction to complete when the handler accesses affected state. Not available for `kl.load`, `kl.store`, `kl.input` and `kl.output`, which are RISC-V memory instructions.
. _Atomic completion_ of the instruction before any asynchronous interrupt is taken.
. _Precise halt and resumption:_ the instruction halts with `klstart` at a prefix-complete point (<<KLEE-Memory-Model>>), and resumes from `klstart`, advancing by at least one granule per execution attempt.
. _Timeout, then precise halt and resumption:_ as option 3, after a timeout that the system may impose.
. _Precise halt and restart,_ provided that restart is not the unconditional response to asynchronous
interrupts, so that repeated interruption cannot prevent completion. Available for `kl.load`, `kl.store`, `kl.input` and `kl.output`, whose transfers are idempotent, and for the long-running instructions of Rule <<KLEE-GR-long-running-no-data>>; block-iterated `kl.exec`, `kl.derive` and vector `kl.mvin` and `kl.mvout` use option 3 or 4 (Rule <<KLEE-GR-block-iterated-instructions>>).
On a synchronous exception raised by a component access, restart is not available: the instruction halts precisely, with `klstart` at the last prefix-complete point before the faulting byte, as in RVV 1.0 §3.7 (`vstart`) and the "`Precise vector traps`" subsection of the Exception Handling chapter.

[[KLEE-GR-long-running-no-data,GR54]]GR54:: A `kl.exec`, `kl.setst` or `kl.derive` whose Machine semantics access no external memory, no vector register, no KLIOBUF, and no GPR other than scalar operands captured at issue (Rule <<KLEE-GR-conflicting-access-rule>>), may be long-running, for instance a scalar multiplication, a key generation, or a signature generation or verification.
+
On preemption, it may follow any behavior of <<KLEE-GR-resumability-options>> compatible with the requirements of the interrupt or exception.
The implementation supports at least one of options 3, 4 and 5 of Rule <<KLEE-GR-resumability-options>>; under option 5 it guarantees and documents a minimum uninterrupted execution quantum, or a maximum number of consecutive restarts of one instruction, to avoid livelocks.
If the operation continues while the hart is preempted, and the hart waits for completion before accessing the affected state, any nested interrupt handler must wait too.
+
An operation that can record its progress, halt at well-defined points and resume from the recorded point records that progress in _MachineUse_, in an implementation-defined format; `klstart` remains reserved for byte counts (<<KLEE-CSR-klstart>>). The implementation may halt such an operation and record its progress only where the recorded state, ADS included, cannot be consumed against inputs other than those the operation started with; Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-progress-discard>> of <<Zkl-ISA-machines.adoc#KLEE-Machines>> ensures this by discarding the recorded state on every transition of the _State_ of the locker other than the completion of the operation.
+
The implementation keeps every intermediate result needed for resumption in the ADS, which it exports; the architected Content of the locker thus does not depend on the progress of the operation, and a restarted operation starts from the architected Content alone. An importing implementation may discard the ADS and restart the operation, and must restart it on an Implementation Qualifier mismatch, or if `kl.clearads` (<<KLEE-instruction-clearads>>) has removed the ADS.
+
A Machine may nevertheless keep in the architected Content a value that the algorithm draws, such as the `RndNum` of the ECC Machines (<<Zkl-ISA-machines.adoc#KLEE-ECC>>) or the `rnd` of ML-DSA (<<Zkl-ISA-machines.adoc#KLEE-PQC-ML-DSA>>), only because such a value depends on the architected state of the algorithm alone, not on the implementation; such a value is meaningful only while the progress field is non-zero (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-progress-discard>>), and is likewise discarded if the operation is restarted.

[[KLEE-GR-conflicting-access-rule,GR55]]GR55:: Every option of Rule <<KLEE-GR-resumability-options>> obeys one rule: before the issuing hart performs a _conflicting access_, the in-flight operation must have completed, or have halted precisely with `klstart` set as <<KLEE-Memory-Model>> requires. A conflicting access is:
+
--
* an ordinary load or store overlapping the memory region of the in-flight KLEE operation;
* an access to a locker that the operation uses, including the issue of another KLEE instruction involving it;
* a read or write of `klstart` or of a KLIOBUF CSR;
* a read or write of a GPR or vector register that the operation writes; or
* a write to a vector register or to the KLIOBUF that the operation reads, including the issue of a `kl.input` targeting it. Scalar operands in GPRs are captured at issue, so accessing them is not a conflicting access.

This Rule and Rule <<KLEE-GR-resumability-options>> make asynchronous execution by the KLEE unit invisible to same-hart program order, as <<KLEE-Memory-Model>> requires. Beyond them, the architecture specifies only the allowed interruption points of its instructions and Machines.
--

[[KLEE-GR-which-resumable-instructions,GR56]]GR56:: The resumable instructions are `kl.exec`, vector `kl.mvin` and `kl.mvout`, `kl.derive`, `kl.load`, `kl.store`, `kl.input` and `kl.output`, which architecturally process their input units serially. On a precise halt, the completed prefix is committed, the failing and subsequent units have no effect, `klstart` records a prefix-complete point, and the instruction does not retire, `xepc` holding its address. If the instruction transitions its locker to an Error State after partial progress, the completed prefix remains committed, the unwritten part of its output window is zeroed (Rule <<KLEE-GR-usage-locker-error-state>>), and the instruction retires (<<KLEE-CSR-klstart>>).

[[KLEE-GR-block-iterated-instructions,GR57]]GR57:: For a block-iterated `kl.exec`, `kl.mvin`, `kl.mvout` or `kl.derive`, the fully processed blocks remain written or transferred, at both endpoints of a transfer, and `klstart` records their total byte count. A partially executed instruction commits exactly the state that a shorter instruction performing only the completed operations would commit, including the locker, `klstart`, and the `*llockerstatus` and effective `KLS` fields, so that context save, restore and resumption remain consistent. Implementations must honor `klstart` for `kl.exec` and `kl.derive`. A handler that resets `klstart` to 0 causes the instruction to execute as a new instruction over its whole window, from the state that the completed prefix committed; its output then differs from that of an uninterrupted execution.
No Machine shall define intra-instruction state outside this model: the state that a halted instruction leaves is described entirely by the locker, `klstart`, `vstart` and, for the long-running operations of Rule <<KLEE-GR-long-running-no-data>>, the progress recorded in _MachineUse_ and the ADS.

[[KLEE-GR-memory-instructions,GR58]]GR58:: KLEE memory instructions are RISC-V memory instructions: one completes, and may retire or take a trap with `xepc` past it, only after every component access has passed address translation and permission checks and have been performed.
Otherwise, as for vector memory operations, the implementation triggers a precise load/store page-fault, guest-page-fault or access-fault exception for that execution attempt, with `klstart` at a prefix-complete point that the instruction permits.

NOTE: After each `kl.load`, `kl.store`, `kl.mvin` or `kl.mvout`, the caller checks whether the locker is _Unconfigured_. With `kl.getst Xd, KM` (Rule <<KLEE-GR-klmanagedlocker-override>>) the check needs no locker number, and reads zero once a clear has reset `klmanagedlocker` to 32.
If the locker is _Unconfigured_, a handler has cleared it, and the software restarts the entire configuration operation, not only the memory operation.
A memory operation issued or resumed after the locker was cleared performs no operation, so the caller always reaches this check (Rule <<KLEE-GR-cleared-under-management>>).
// +
// NOTE: Clearing a locker in an exporting State (<<KLEE-instruction-setst>>) calls for particular care from an
// exception handler, because until the export completes, the ciphertext the locker holds may be the only copy of
// the CC. A handler that intends to clear such a locker must first see the export through to completion — if
// necessary across preemptions of its own by a more privileged mode — and store the resulting image.
// If it clears the locker earlier, by mistake or on an unrecoverable error, the CC is lost: the caller detects
// this by the same check after `kl.store`, must treat the error as unrecoverable, and a further
// `kl.store` on the cleared locker raises an illegal-instruction exception (<<KLEE-instruction-store>>).
// This allows the error to propagate to the outermost caller.
//
// [[KLEE-GR-algorithms-specific,IRR9]]IRR9:: Machine-specific resumable long-running operations that transfer no data
// in a `kl.setst`, in a (block-processing step of) `kl.exec` operation,
// or in a `kl.derive` operation,
// must either advance its recorded progress towards completion of the operation, or restart.
// The manner in which progress is recorded is implementation-defined, but it cannot use `klstart`
// (for instance, it can use _MachineUse_, as in <<KLEE-ECC>> and <<KLEE-PQC>>).
// Implementations capable of resuming these operations also support their restart.

  where the instruction left the locker _Unconfigured_, as Rule

. advance `xepc` past the trapping instruction, since re-executing it raises the same exception again.
  A handler that advances `xepc` past a usage instruction must write zeros to its output operand,
  as the instruction would have done had it performed no operation (Rule <<KLEE-GR-usage-locker-error-state>>).

We now collect the error conditions, which the rest of the specification states where they arise.

Fatal Conditions:::
+
--
Fatal conditions have the highest priority among the KLEE-specific error categories, and no CPU
state disables their detection. The main one is an integrity failure of the KLF of a hart
(<<KLEE-cryptographic-registers>>); implementations may define others.

A fatal condition causes a KLEE unit reset of the hart (<<KLEE-reset-and-m-mode-only>>), after which
a KLEE fatal-error exception is raised.
The reset differs from an ordinary one in three ways:

. `misa.L` keeps its value, and every `KLS` field that is not Off becomes Dirty rather than Off,
  so that the KLEE fatal-error exception can be reported, the modes below M-mode are not silently disabled, and
  context switching code can discard its stale saved state;
. every `*llockerstatus` field becomes _Dirty_ rather than _Initial_; and
. masks installed by unauthenticated Debug mode stay in place.

A CSK generated at boot under the fourth model of <<KLEE-CSK-requirements>> is shared by the harts of
its subsystem, and is not regenerated.

Detection and reset may be synchronous or asynchronous; the KLEE unit records the condition.
The first KLEE instruction or KLEE CSR access issued, or in flight, after detection performs no
operation and raises a KLEE fatal-error exception, with `xepc` holding its address. If, at detection, a `KLS`
field in effect is Off or the KLEE bit of an `*stateen0` CSR in effect is clear, the condition is
retained, and reported on the first KLEE instruction or KLEE CSR access that is not illegal or virtual
on those grounds; until then, such instructions raise an illegal-instruction exception,
which <<Zkl-ISA-priv.adoc#KLEE-exception-codes>> ranks above the KLEE fatal-error exception.
Detection is thus never disabled; only its reporting is deferred.
--

[[KLEE-illegal-instruction-grounds,Illegal-Instruction Exceptions]]
Illegal-Instruction Exceptions:::
+
--
The grounds for an illegal-instruction exception form two groups:

* The grounds of the first group depend only on the instruction encoding, the GPRs and the vector
  configuration, not on the state of the KLEE unit, and therefore take precedence
  over the KLEE fatal-error exception (<<Zkl-ISA-priv.adoc#KLEE-exception-codes>>):

. A reserved encoding, including `kl.setst` with `#immed7` 46 or 47, `kl.mgmt` with `#immed7` in 59–62 or in Form B, `KM` on an instruction that Rule <<KLEE-GR-klmanagedlocker-override>> does not list, or on `kl.setst` with `#immed7` = `kl_cfg_clearall`, and a KLEE instruction with a vector operand issued while `vtype.vill` is set (<<KLEE-KLV>>).
. An indirect locker index outside [0..31], `X0` as an indirect locker index register where it does not encode `KM` (Rules <<KLEE-GR-GPR-indirect>> and <<KLEE-GR-klmanagedlocker-override>>), or a `kl.derive` with equal locker indices (<<KLEE-instruction-derive>>).
. A GPR pair or quartet not meeting Rule <<KLEE-GR-multiple-GPRs>>.
. A vector operand carrying an MDH with `VL` {times} `SEW` < 128 (Rule <<KLEE-GR-vector-MDH-operand>>), or a vector `kl.mvin` or `kl.mvout` whose `vl * (SEW/8)` or `vstart * (SEW/8)` is not a multiple of 16 (<<KLEE-instruction-mv>>).
. An encoding of an extension that is not implemented, such as Forms A–C of `kl.exec` without `Zklv`.
. A KLEE instruction or KLEE CSR access gated by a clear `Smstateen` bit (<<Zkl-ISA-priv.adoc#KLEE-CSRs-priv>>), with an illegal-instruction exception as that extension prescribes; a KLEE instruction issued while `KLS` is Off (see _Fatal_ above) or under big-endian effective data endianness (<<Zkl-notation.adoc#KLEE-Notation>>); or an access to a CSR that <<KLEE-CSRs-unpriv>> declares unavailable, or that <<Zkl-ISA-priv.adoc#KLEE-CSRs-priv>> makes inaccessible from the current mode, with an illegal-instruction exception as stated there.

* The grounds of the second group depend on the state of the KLEE unit, mostly on the
  contents of a locker, which, for a locker marked _Off_ (<<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>>), exist only once it has been
  lazily loaded, or in the M-mode code that emulates it. They are evaluated after
  the KLEE missing-CSK exception and the _Off_ gate, once the locker is loaded or by the emulator, and only if no
  fatal condition is pending; otherwise a KLEE fatal-error exception is raised. For a usage instruction they follow the
  order of <<KLEE-GR-gate-order>>, so items 3 and 6 below are evaluated only after the _Unconfigured_, Error-State and
  Configuration-State conditions:

. `kl.load`, `kl.store`, `kl.mvin` or `kl.mvout` on a locker whose _State_ does not admit the transfer, or with an inconsistent `klstart` (Rules <<KLEE-GR-zkl-load-mv-allowed>> and <<KLEE-GR-zkl-store-mv-allowed>>), except on a locker that is _Unconfigured_ or in an Error State, where the instruction performs no operation (Rule <<KLEE-GR-cleared-under-management>>).
. `kl.mgmt` when `klmanagedlocker` names another locker, when opening a provisioning or an import on `KM` while `klmanagedlocker` = 32 (Rule <<KLEE-GR-klmanagedlocker-override>>), when completing with an `ml`._State_ inconsistent with the locker's Configuration State, or when `kl_cfg_management_end` is issued on a locker in a Valid State (<<KLEE-locker-management>>); on a locker that is _Unconfigured_ or in an Error State, `kl_cfg_management_end` performs no operation, as does the opening of an export on an _Unconfigured_ locker (Rule <<KLEE-GR-cleared-under-management>>).
. A KLIOBUF substitution that <<KLEE-usage-input-output>> forbids, such as a Form B or C `kl.exec` issued where Form A is expected, or any substitution without `Zklio`. This ground depends on the State, which defines the operation and thus whether a Form is a substitution.
. A Form A `kl.mgmt` that must take the MDH from a configured KLIOBUF with `kliobuftop` < 16 (Rule <<KLEE-GR-vector-MDH-operand>>).
. A Form A–C `kl.exec` with `klstart` {ne} `vstart` {times} `SEW` / 8 (<<KLEE-CSR-klstart>>).
. A Form A `kl.exec` with `Vd` = `Vs2` for an operation whose output blocks do not have the length of its input blocks (<<KLEE-instruction-exec>>).
. `kl.load` or `kl.store` with `Xl` {ne} 0: with `klmanagedlocker` < 32, always (<<KLEE-instruction-load>>, <<KLEE-instruction-store>>); with `klmanagedlocker` = 32, that is as `kl.input` or `kl.output`, on an implementation without `Zklio`. With `Xl` = 0 and `klmanagedlocker` = 32 both perform no operation (Rule <<KLEE-GR-cleared-under-management>>). A missing CSK and an unconfigured KLIOBUF raise the KLEE missing-CSK and unconfigured-KLIOBUF exceptions instead (<<KLEE-CSK-requirements>>, Rule <<KLEE-GR-iobuf-configured>>).
--

// Exceptions and State Changes::: [[KLEE-exceptions-and-state-changes,Exceptions and State Changes]]
// When a KLEE instruction raises a KLEE missing-CSK exception, KLEE locker-Off exception, KLEE unsupported-Metadata exception, KLEE out-of-memory exception, KLEE privilege-violation exception or unconfigured-KLIOBUF exception, it has changed no KLEE state, unless its description states a change that precedes the exception. `kl.mgmt` is the one instruction that does: it zeroizes the target locker before its checks.

[[KLEE-unsupported-handling,Unsupported Metadata]]
Unsupported Metadata:::
+
--
Unsupported Metadata at provisioning or import raises a KLEE unsupported-Metadata exception, and leaves the locker
_Unconfigured_. A handler below M-mode, to which M-mode forwards the exception, cannot emulate the
Machine, and treats the exception as unresolvable.

An M-mode handler that emulates the Machine instead sets the `*llockerstatus` field of the locker to _Off_
(<<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>>), so that every later access to the locker (that <<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>> does not exempt) traps.
The emulator then holds the locker in its own protected memory, and services every operation
on it, SCC import and export included. For these it needs either the inputs of `SCC_Encrypt` and
`SCC_Decrypt` (<<KLEE-SCC-AEAD>>) that it cannot otherwise obtain, namely the CSK and the Locality
Secrets of the HW Binding Group, or primitives that compute these functions on its
behalf, provided in an implementation-specific way. An implementation that provides neither cannot
emulate Machines, and reports a KLEE unsupported-Metadata exception to software instead.

An emulator keeps one copy per locker slot, and replaces it:

. at the next KLEE unsupported-Metadata exception on that slot; or
. at an emulated `kl.clone` naming the slot as destination, which also clears the hardware locker of
  that slot and marks it _Off_, since the clone of an emulated locker is emulated too.

A copy orphaned by an instruction that <<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>> exempts is never used again, but lingers
until replaced. An emulator that must not retain key material longer than necessary therefore checks
`mllockerstatus` whenever it runs, and zeroizes the copies whose _Off_ mark is gone.

Accessing or using a locker in State `kl_state_unsupported` does _not_ raise a KLEE unsupported-Metadata exception.
--

Other Exception Conditions:::
+
--
The remaining exceptions are, in the order of <<Zkl-ISA-priv.adoc#KLEE-exception-codes>>, as follows.

. *No active CSK.* A KLEE missing-CSK exception, on any KLEE instruction or KLEE CSR access that
  <<KLEE-CSK-requirements>> does not exempt, while no CSK is established or the `mklcsk` group is
  only partially written (<<Zkl-ISA-priv.adoc#KLEE-CSR-mklcsk>>).
. *Locker marked _Off_.* A KLEE locker-Off exception, on any access to the locker that <<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>> does not
  exempt, before any condition that depends on its contents. M-mode resolves it or forwards it to
  the mode that owns the _Off_ field.
. *Usage Control.* A KLEE privilege-violation exception, for a usage instruction (<<KLEE-instruction-properties>> in Rule <<KLEE-GR-usage-policy>>) in a mode that
  the _UsagePolicy_ excludes (Rule <<KLEE-GR-usage-policy>>), and for any use, cloning or
  restriction of a locker in a Configuration State (Rule <<KLEE-GR-usage-locker-config-state>>).
. *Insufficient KLF capacity.* A KLEE out-of-memory exception, for a `kl.mgmt` opening a provisioning or
  an import (<<KLEE-locker-management>>), a `kl.clone` (<<KLEE-instruction-clone>>), or a
  `kl.restrict*` raising _SCProtection_ (<<KLEE-instruction-restrict>>).
. *Unconfigured KLIOBUF.* An unconfigured-KLIOBUF exception (Rule <<KLEE-GR-iobuf-configured>>).
. *Memory exceptions.* The load/store address-breakpoint, address-misaligned, page-fault,
  guest-page-fault and access-fault exceptions of the component accesses of `kl.load`,
  `kl.store`, `kl.input` and `kl.output`, ordered as in <<KLEE-Memory-Alignment>>, with a precise
  halt (<<KLEE-resumability>>); an access to a non-idempotent region is an access fault
  (<<KLEE-Memory-Model>>).
--

Errors Not Raising Exceptions:::
+
--
The following conditions set an Error State, or make the instruction perform no operation, without
an exception, as do the algorithmic errors below.

. *Invalid Metadata or SKID.* _Invalid_, for a `kl.mgmt` opening a provisioning or an import on
  invalid Metadata (<<KLEE-MVR-open>>), for a SKID other than the all-ones value that the SKS
  does not or may not resolve (<<KLEE-system-keys>>), and for a `kl.restrict*` request that
  would widen the CC or yield invalid Metadata (<<KLEE-instruction-restrict>>); in an Error State, such a request instead performs
  no operation, and the Error State is kept.
. *Instruction not allowed in the current State.* _Invalid_, for a `kl.exec` or `kl.setst` not
  allowed in the current _State_ and _StateExtension_, including an unsupported `#immed7` (Rules
  <<KLEE-GR-no-exec-in-ready>>, <<KLEE-GR-success-failure>>, <<Zkl-ISA-machines.adoc#KLEE-MGR-not-allowed-instructions>> and
  <<Zkl-ISA-machines.adoc#KLEE-MGR-policy-gate>>, <<KLEE-instruction-setst>>), and for
  a `kl.derive` that fails its checks (<<KLEE-instruction-derive>>).
. *Invalid length.* _Invalid_, for an operand whose transfer-window length (`kliobuftop`, or `VL` {times} `SEW` / 8) the Machine does not accept (<<KLEE-CSR-klstart>>, <<KLEE-usage-input-output>>).
. *Expiration.* _Expired_, for a usage instruction (<<KLEE-instruction-properties>> in Rule <<KLEE-GR-usage-policy>>) on an expired locker, which then performs
  no operation; no operation, with the _State_ unchanged, if the secure clock cannot be read (<<KLEE-Metadata-expiration-date>>).
. *Use of an _Unconfigured_ or Error-State locker.* No operation, and the _State_ is unchanged (Rules
  <<KLEE-GR-transition-to-from-unconfigured>> and <<KLEE-GR-usage-locker-error-state>>, <<KLEE-insns-on-unconf-or-error-locker>>, <<KLEE-insns-on-unconf-or-error-locker>>).
. *Explicit Error State.* The Error State that a `kl.setst` immediate names
  (<<KLEE-instruction-setst>>).
. *RBG failure.* _Invalid_, for an operation that cannot obtain the random bits it needs (Rule <<KLEE-GR-rbg-failure>>).
. *Unusable ADS.* Dropped at import, without rejecting the SCC (<<KLEE-SCC-import>>).
--

Algorithmic Errors:::
+
--
Algorithmic errors occur:

. in SCC management, as Error State `kl_state_mgmt_auth` (_Authentication Failed_), when the
  `SIV` check fails at the completion of an import (<<KLEE-SCC-import>>) or of an export
  (<<KLEE-mgmt-completes-export>>); software therefore checks the _State_ after completing an export,
  as after completing an import; and
. in the Machines, which may transition the locker to Error State _Invalid_ or to another
  Error State, as each specifies. Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-config-data-error>> distinguishes
  configuration errors, which transition the locker to Error State _Invalid_, from data errors, which transition
  it to _Failure_. Other Machine errors also lead to _Invalid_: a further `kl.exec` in
  a final-block State (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-single-last-block>>), a violated policy gate or entry
  condition (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-policy-gate>>), and an RBG failure
  (Rule <<KLEE-GR-rbg-failure>>).

Neither the verification of an authentication tag by an AEAD scheme (_not_ by the SCC export and import
procedures) nor that of a signature is an algorithmic error, whether it succeeds or fails: the
Machine has performed as expected.

[[KLEE-GR-gate-order]]
=== Order of Evaluation for Usage Instructions

Priority Order Error Handling Rules:::
+
--
For a usage instruction (<<KLEE-instruction-properties>> in Rule <<KLEE-GR-usage-policy>>), the following are evaluated first: the illegal-instruction grounds decided without accessing the state of the KLEE unit (the first group of <<KLEE-illegal-instruction-grounds>>), then the KLEE fatal-error, missing-CSK and locker-Off exceptions (<<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>>), and then the `klstart`/`vstart` check of <<KLEE-CSR-klstart>>.
The conditions on the locker follow in this order, and the first that applies decides the outcome:

. _Unconfigured_: no operation and no exception (Rule <<KLEE-GR-transition-to-from-unconfigured>>);
. Error State: no operation and no exception (Rule <<KLEE-GR-usage-locker-error-state>>);
. Configuration State: KLEE privilege-violation exception (Rule <<KLEE-GR-usage-locker-config-state>>);
. a forbidden KLIOBUF substitution, or a Form A `kl.exec` with `Vd` = `Vs2` that <<KLEE-instruction-exec>> forbids: illegal-instruction exception (<<KLEE-illegal-instruction-grounds>>);
. _UsagePolicy_: KLEE privilege-violation exception (Rule <<KLEE-GR-usage-policy>>);
. _ExpirationDate_: transition to Error State `kl_state_expired`, then no operation; if the secure clock cannot be read, no operation, the _State_ unchanged (<<KLEE-Metadata-expiration-date>>);
. a KLIOBUF required by a substitution but unconfigured: unconfigured-KLIOBUF exception (Rule <<KLEE-GR-iobuf-configured>>);
. the Machine's own rules.

For `kl.derive`, each condition is evaluated for both endpoints, the source first, before the next condition; an _Unconfigured_ or Error-State endpoint makes the whole instruction a no-op.
--

=== Summary of Behavior of KLEE Instructions on Unconfigured or Error State Lockers

A locker in an Error State is inert: it holds only its MDH (Rules <<KLEE-GR-clear-locker-content-error-state>> and <<KLEE-GR-error-state-locker-is-only-MDH>>), and what an instruction does with it depends on whether the instruction _uses_ the locker or _manages_ it.
Usage instructions on such a locker fall through, as no-ops or zero writes, and so do usage instructions on an _Unconfigured_ locker.
The caller can thus detect the condition and act on it without checking after every single instruction, and no time is spent in trap handlers that could not resolve it.
Configuration instructions, on the other hand, perform as expected.

The checks that <<KLEE-GR-gate-order>> places before the conditions on the locker, the first group of <<KLEE-illegal-instruction-grounds>> among them, come first; only then is the _State_ considered, _Unconfigured_ before Error State.
A usage instruction on such a locker performs no cryptographic operation and leaves the MDH untouched: the _State_ is unchanged, so that the original error condition is preserved, and for the same reason neither the _UsagePolicy_ nor the _ExpirationDate_ is checked.

[[KLEE-usage-input-output]]
== Replacing Vector Inputs and Outputs with kl.input and kl.output

With `Zklio`, a Form of `kl.exec`, `kl.setst` or `kl.mgmt` that reads inputs from vector registers, or writes outputs to them, may be replaced by the corresponding Form without vector operands.
That Form is _native_ where the operation has no input or output. Issued in a State of a Machine that expects vector inputs or outputs, it is instead a _substitution_: it uses the KLIOBUF for them, rather than raising an illegal-instruction exception.

`kl.input` and `kl.output` perform no computation, and change no state other than the KLIOBUF
and `klstart`; all computation and other state changes remain in `kl.exec`, `kl.setst` and `kl.mgmt`.

The substitutions are:

. a Form D `kl.exec` for a Form A, B or C `kl.exec`; and
. a Form A `kl.setst`, or `kl.mgmt`, for the Form C of the same instruction.

// A Form D `kl.exec`, or a Form A `kl.setst` or `kl.mgmt`, is a _substitution_ when the operation
// it performs defines an input or an output, and is _native_ otherwise. A native Form neither reads
// nor writes the KLIOBUF, and ignores `klstart`, which it leaves unchanged; `kl.mgmt`, in every
// Form, and `kl.clearall` nevertheless clear it (<<KLEE-instruction-setst>>, <<KLEE-instruction-clear>>).

A substitution reads its inputs from, and writes its outputs to, the KLIOBUF:

* A substituted Form A `kl.exec` behaves as a Form A with `Vd` = `Vs2` (<<KLEE-instruction-exec>>):
  each block's output replaces its input at the same offset of the window.
* A substituted Form C `kl.exec` writes its output to [`klstart`, `kliobuftop`-1], clearing the bits it
  does not produce (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-clear-output>>); bytes below `klstart`, and at or beyond `kliobuftop`, are not written.
* A substituted Form A `kl.setst` reads its auxiliary input from bytes [0, `kliobuftop`-1] of the
  KLIOBUF, ignoring `klstart`, truncated to the operand width as
  Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-fixed-width-input>> prescribes.
* `kl.exec` never modifies `kliobuftop`.

A substitution fails as follows:

* Without `Zklio`, it raises an illegal-instruction exception.
* Vector and KLIOBUF operands cannot be mixed: a Form B or C `kl.exec` issued where Form A is
  expected raises an illegal-instruction exception.
* An operation whose output blocks differ in length from its input blocks may be substituted
  only if its Machine states where the output is written in the KLIOBUF; otherwise the
  substitution raises an illegal-instruction exception.
* If the KLIOBUF is not enabled, or `kliobuflen` is zero, an unconfigured-KLIOBUF exception is raised.
* If `kliobuflen` is non-zero but `kliobuftop` is a length invalid for the Machine, the locker transitions to Error State _Invalid_, whether the KLIOBUF serves as input or only as output (<<KLEE-CSR-klstart>>); for an MDH operand, however, `kliobuftop` < 16 raises an illegal-instruction exception (Rule <<KLEE-GR-vector-MDH-operand>>).

Where <<Zkl-ISA-machines.adoc#KLEE-Machines>> says that a Form of `kl.exec`, `kl.setst` or `kl.mgmt` is
_expected_, rather than _required_ or _the only Form allowed_, the substitutions above apply
implicitly. <<KLEE-replacement-instructions>> gives examples of equivalent sequences using `kl.input` and `kl.output`.

[[KLEE-CC-management]]
== Management of Cryptographic Contexts

In keeping with the RISC-V philosophy, KLEE splits locker management into sequences of simple instructions, rather than single instructions that drive large state machines or microcode.
Three consequences follow:

. The state machines managing keys and algorithms, which the key-protection solutions of CISC architectures hide (cite:[IBM-z-arch] "`Protection of Cryptographic Keys`" or cite:[intel-keylocker]), is now exposed to software. The hardware becomes simpler, even if it must enforce several rules to prevent misuse, but the software using it becomes more complex.
. Interrupts and exceptions can separate the instructions of a management sequence, so context switching, process and virtual machine migration, hibernation, and interoperability between KLEE implementations need explicit support.
. Dynamic locker management, lazy context loading included, needs explicit support too, where other architectures cache repeated key uses implicitly.

Throughout, the confidentiality and integrity of the MDH and Content of a CC are preserved, and binary compatibility holds across implementations that support the same sub-extensions.

A context-switch handler need not save a partially provisioned or imported locker: it may clear it instead, during context save or restore, which forces the interrupted management operation to restart.
Software handles resumption and restart alike, without code changes: it reads the _State_ of the locker after each management instruction, and restarts the operation if it finds the locker _Unconfigured_ (Rule <<KLEE-GR-cleared-under-management>>).
Two obligations bind system software:

* Clearing must not be its unconditional response at every context switch, since repeated restarts would prevent completion, for instance while a debugger single-steps the interrupted software.
* A locker in State `kl_cfg_exporting` holds the only copy of its CC: unless system software terminates the interrupted software, it saves such a locker by a nested export (<<KLEE-nested-mgmt>>), and never clears it.

KLEE defines three external CC formats, each beginning with the 128-bit MDH of <<KLEE-Metadata>>:

. the _Provisioning Input_ (PI), loaded into a locker to create a CC;
. the _Sealed Cryptographic Context_ (SCC), an encrypted and authenticated representation of a CC, used to export a locker to memory for later import; and
. the _Partially Configured Cryptographic Context_ (PCCC), used to export a locker whose management operation has been preempted, and to re-import it later to resume that operation. It has the format of a PI or of an SCC, according to the base type of the Configuration State of the locker (<<KLEE-nested-state-base-types>>), without further encryption or authentication.

A locker in an Error State consists only of an MDH, so
its export is a read of the MDH, which uses no `kl.mgmt`, and its import uses a single one (<<KLEE-error-state-transfer>>).

Under management, the _State_ of a configured locker changes as follows:

. A locker that is not being managed is in a Valid State.

. A locker being provisioned from a PI is in State `kl_cfg_provisioning`.
.. If the provisioning is preempted, software saves the _State_ and the export changes it to `kl_cfg_ppi_exporting` ("`ppi`" for "`partial provisioning input`"); further preemptions and exports save the current _State_ and leave `kl_cfg_ppi_exporting`.
.. When the export terminates, software restores the _State_ it had before the export, by passing it to the `kl.mgmt` that completes the export.
.. If the locker is re-imported, its _State_ is first saved, and then becomes `kl_cfg_ppi_importing`.
.. Completing a nested management operation restores the previous _State_:
completing the last nested one restores `kl_cfg_provisioning`;
completing the outermost one brings the locker to State _Ready_.

. An export from a Valid State: software saves the _State_, which becomes `kl_cfg_exporting`; nested management operations lead to States `kl_cfg_exporting` and `kl_cfg_importing`.

. An import of an SCC generated from a locker in a Valid State: the _State_ becomes `kl_cfg_importing`, and nested management operations lead to States `kl_cfg_exporting` and `kl_cfg_importing`.

<<KLEE-SC-sealing-status>> gives the values of these States.

Management operations may be nested, i.e., an exception may interrupt the sequence of operations to provision, import, or export a locker.
The exception handler may initiate an export operation on the same locker, which we call a _nested export_, which is now in a Configuration State, generating a PCCC.
Such a nested export may itself be interrupted.
Later, an exception handler may initiate the restore of the same locker, resulting in a _nested import_, which may also be itself interrupted.
We have following definitions:

[[KLEE-nested-mgmt,Nested Management Operations]]
Nested Management Operations:::
A _nested_ management operation is one opened on a locker already under management;
the _base operation_ of a group of nested operations is the outermost one, that is
the last management operation opened on the locker while it was _not_ in a Configuration State.
The two Configuration States whose mnemonics contain `ppi` ("`partial provisioning input`")
are reached only by a nested operation whose base operation is a provisioning.
A nested operation on an interrupted import or export of a locker in a Complete State reuses
`kl_cfg_exporting` and `kl_cfg_importing`, and its base operation is that import or export.
Clearing a locker undoes any nested management operation by resetting a locker to _Unconfigured_.

[[KLEE-nested-state-base-types,Nested State Base Types]]
Nested State Base Types:::
The base type of a Configuration State, `pi` or `scc`, records whether the image the locker holds derives
from a PI or an SCC, as the base operation determines: it is `pi` for
`kl_cfg_provisioning`, `kl_cfg_ppi_exporting` and `kl_cfg_ppi_importing`, and `scc` for
`kl_cfg_exporting` and `kl_cfg_importing`.
It determines the length of the image
(<<KLEE-instruction-size>>), which could not otherwise be recovered once nested management
operations have overwritten the original _State_.

[[KLEE-data-formats]]
=== Formats of PIs, SCCs, and Partially Configured Cryptographic Contexts

Provisioning Input (PI).:::
The MDH, with _State_ = _Unconfigured_, followed by `Content`. The
`kl.mgmt` that completes the provisioning sets _State_ to _Ready_.

Sealed Cryptographic Context (SCC).:::
+
--
Up to five sections, in this order:

[[KLEE-SCC]]
.Plaintext of the Sealed Cryptographic Context (SCC) Format, all Sections in Order
[width="100%",cols="^8%,14%,21%,57%",options="header"]
|===
| Section | Section Name | Size                 | Description
| 1       | `MDH`        | 128 bits             | See <<KLEE-Metadata>>.
| 2       | `SIV`        | 128 bits             | Authentication tag for `MDH`, the Locality Secrets its _Locality_ names, and `Content1` (<<KLEE-SCC-export>>).
| 3       | `IMPQUAL`    | 128 bits, if present | Identifies the implementation of the KLEE unit. Non-authoritative, and ignored when _ADSDropped_ = 1.
| 4       | `SIV2`       | 128 bits, if present | Authentication tag for `IMPQUAL`, `SIV` and `Content2`. Non-authoritative, and not verified when _ADSDropped_ = 1.
//
| 5.a
| `Content1`
| A multiple of 128 bits. See <<KLEE-length-rule>>.
| Keys and other Machine-specific information, necessary for the correct functioning of the Machine. Encrypted in memory, and also inside the KLEE unit during partial import.
//
| 5.b
| `Content2`
| A multiple of 128 bits.
| ADS: data _not_ necessary for the correct functioning of the Machine.
  Encrypted in memory and during partial import.
|===

Sections 3, 4 and 5.b form the implementation-specific ADS, whose size _AuxDataLen_ gives (<<KLEE-Auxiliary-Data-Section>>).
KLEE generates an image with _ADSDropped_ = 1 only as an SCC-shaped PCCC, when a nested export preserves an interrupted import after `Content2` was dropped; since _ADSDropped_ is unauthenticated, import also accepts this layout when the bit was set by modifying an SCC.
A locker in an Error State is its MDH alone (Rule <<KLEE-GR-error-state-locker-is-only-MDH>>).
--

Encryption during management.:::
While an SCC is imported, or a locker is exported as an SCC, the locker holds its
`Content` encrypted:

. The `kl.mgmt` that opens an export encrypts it, and generates `SIV` and, if _AuxDataLen_ {ge} 2,
  `IMPQUAL` and `SIV2`.
. The `kl.mgmt` that completes an import or an export decrypts and authenticates it, once
  the MDH and `Content`, `SIV`, and, if _AuxDataLen_ {ge} 2, `IMPQUAL`
  and `SIV2` are in place. With _ADSDropped_ = 1, no `Content2` is loaded or authenticated. An export completion may instead restore the clear contents from an
  internal copy (<<KLEE-mgmt-completes-export>>).

Partially Configured Cryptographic Context (PCCC).:::
+
--
Exporting a locker under management at a nested level produces a PCCC: its data is exported verbatim, without
further encryption or authentication, in the shape that the base type of the Configuration
State of the locker gives (<<KLEE-nested-state-base-types>>):

* `pi` (State `kl_cfg_ppi_exporting`, a partially provisioned locker): a _PI-shaped_ image, the MDH
  followed by the clear `Content` of a PI. This is not a security issue: the plaintext was
  already available to software, and thus to its more privileged modes.
* `scc` (State `kl_cfg_exporting`, a partially imported SCC, or a locker whose export was itself
  preempted): an _SCC-shaped_ image, the MDH followed by `SIV` and, when present, `IMPQUAL` and
  `SIV2`, as _ContentOffset_ prescribes (<<KLEE-instruction-mv>>), and by the ciphertext `Content`
  already in the locker.

By saving each MDH in its own local state, software keeps an implicit stack of _State_ values,
whose top belongs to the previous nesting level, and which the completing `kl.mgmt` restores.
--

[[KLEE-length-rule]]
=== Length of a PI/SCC/PCCC and KLF Capacity Usage of a Locker

Except for a locker in an Error State, which is its MDH alone (Rule <<KLEE-GR-error-state-locker-is-only-MDH>>, <<KLEE-error-state-transfer>>), the MDH fields that determine the length
of a PI, an SCC and a PCCC, and the KLF capacity that a locker occupies, all
lie in the lower 64 bits of the MDH:

. The length of a *Provisioning Input* depends only on
_Machine_, _MachinePolicy_ and _KeyType_.
It does *not* depend on _AuxDataLen_ or _ADSDropped_, which must be zero in the MDH of a PI, and of a PCCC whose Configuration State has base type `pi`, since these carry no ADS;
nor on _StateExtension_ or _MachineUse_, which are ignored and zeroed by `kl.mgmt` upon provisioning; nor on _SCProtection_.
During provisioning, the locker holds the information in the external format of a PI.
The `kl.mgmt` that completes the provisioning converts it into the internal state of the locker, possibly computing
information such as derived keys, or multiple shares.

. The length of a *Sealed Cryptographic Context*
depends only on _Machine_, _MachinePolicy_, _KeyType_, _StateExtension_, _AuxDataLen_ and _ADSDropped_ (<<KLEE-Auxiliary-Data-Section>>), not on _State_. _ADSDropped_ can remove only `Content2`; it never changes the presence of `IMPQUAL` or `SIV2`, nor the offset or length of `Content1`.
It does *not* depend on _SCProtection_ either (<<KLEE-rules-masked-implementations>>).

. The length of a *Partially Configured Cryptographic Context* is that of a
PI if the base type of its Configuration State (<<KLEE-nested-state-base-types>>) is `pi`,
and that of an SCC if it is `scc`.
// identifies: the `Content` of a PI for a
// `_pi` State, and `Content1` together with `Content2` for an `_scc` State. Once the image is
// identified, its length is given by the rule above for that format, and depends on no further field.

. The *KLF capacity* that a locker occupies depends only on
_Machine_, _MachinePolicy_, _SCProtection_ and _KeyType_.
It depends on _KeyType_ because a SKID policy may forbid the export of a key value even to the KLF, so that the Machines using the key forward their operations to another environment; it does not depend on _StateExtension_, since a locker is allocated with room for every field its Machine may use.
The capacity a locker uses once provisioned does not change later: dropping the ADS, for instance, shortens SCCs and SCC-shaped PCCCs, but not the KLF capacity.

// No other MDH field, and no information in the `Content`, may affect any of these four quantities.

A PI cannot be in an Error State.

[[KLEE-rules-masked-implementations]]
=== Single-Share Key Export Rule for Masked Implementations

A multi-share implementation of a Machine always provisions, imports and exports _all_ its keys and secrets as reconstructed values,
which keeps SCCs compact and interoperable across implementations.
(((KLEE, Machine, side-channel protection variants)))
Architecturally, every value is a single share:
side-channel analysis (SCA)-protected Machines are implementation variants of the unprotected Machine, not separate specifications,
and differ from it only in the _SCProtection_ field of the MDH.

NOTE: Reconstructing or re-randomizing a key is usually inexpensive, for instance when a block cipher in counter mode generates the masks;
an implementation with a slower mask generator may include shares or masks in the ADS to accelerate the generation of the multiple shares.

[[KLEE-system-keys]]
=== System Keys and Randomly Generated Key Values

A PI or SCC encodes a System Key as a 64-bit SKID, from which a system-specific SKS retrieves the key.
The SKID also replaces the key value in a PI, SCC, or PCCC:

[horizontal]
[[KLEE-SKR-skid-field,SKR1]]SKR1:: In a PI, an SCC, or PCCC, the key field of a System Key holds its SKID in place of the key value,
and is thereby reduced from the key size to 64 bits.

("SKR" means "System Key Rule".)

Furthermore:

[horizontal]
[[KLEE-SKR-single-skid,SKR2]]SKR2:: For a Machine with more than one key, such as XEX/XTS, a single SKID retrieves all its keys from the SKS.

The SKS resolves a SKID other than the all-ones value as a function of the SKID alone,
if the SKID is allowed for the _Machine_ and _MachinePolicy_; the key value depends on neither.
For a key for which the SKS also encodes policies, these are used to narrow the policies of the locker
as described in <<KLEE-Metadata-narrowing>>.
The current privilege mode does not affect whether the SKS may resolve a SKID.

A SKID other than the all-ones value that the SKS does not, or may not, resolve transitions the locker to Error State _Invalid_ (<<KLEE-Metadata-validity>>).
Whenever a SKID is resolved, the MDH of the locker is narrowed by the policies that the SKS associates with the key (Metadata Narrowing Rule <<KLEE-MNR>>); if the narrowing fails, the locker transitions to Error State _Invalid_, as for a supplied MDH at provisioning.

The SKS does not resolve the all-ones SKID, which is instead randomly generated (<<KLEE-KeyType-field>>).

A SKID carried in an SCC is resolved only after the SCC has been authenticated.

A multi-share implementation may copy System Key material from the SKS into the locker and expand it into multiple shares, but
must still export the key as a SKID.
Shares or masks included in the ADS (<<KLEE-rules-masked-implementations>>) must not allow or facilitate the recovery of the key value from those values alone.

[[KLEE-locker-management]]
=== Locker Management Operations

This section defines the operations performed by `kl.mgmt` for the `#immed7` values given by the table below.

[[KLEE-management-immeds]]
.Values (decimal) of `#immed7` to be used for provisioning, importing, and exporting
[float="center",align="center",width="100%",cols="^7%,<27%,<66%",options="header"]
|===
| Value | Mnemonic                 |  Description
|  56   | `kl_cfg_provisioning`    |  Prepare a locker for provisioning.
|  57   | `kl_cfg_exporting`       |  Prepare a locker for export.
|  58   | `kl_cfg_importing`       |  Prepare a locker for import.
|  63   | `kl_cfg_management_end`  |  Complete the current management operation.
|===

These values correspond to State values as per <<KLEE-SC-sealing-status>>, however, as a `#immed7` values passed to `kl.mgmt`,
values 59–62 are reserved; _State_ takes Value 59 and 60 only as the result of a `kl.mgmt` with 57 or 58, depending on the
previous State of the CC:
A `kl.mgmt` with `kl_cfg_importing` or `kl_cfg_exporting` leaves the locker in `kl_cfg_ppi_importing`, resp. `kl_cfg_ppi_exporting`, when the image derives from a provisioning that had not completed (<<KLEE-nested-state-base-types>>), as the operations below specify.

Three steps are common to every operation below, and are not repeated in their descriptions:

. `kl.mgmt` first checks that `klmanagedlocker` holds the number of the target locker or 32, and raises an illegal-instruction exception otherwise; for `KM` (Rule <<KLEE-GR-klmanagedlocker-override>>) the check always passes.
. It updates `klmanagedlocker` according to the _State_ in which it leaves the target locker:
.. a Configuration State or a Complete State, Error States included: the number of the target locker, which software replaces by 32, or by the value it saved, once the management operation is finished (<<KLEE-CSR-klmanagedlocker>>);
.. _Unconfigured_ (Rule <<KLEE-GR-cleared-under-management>>): 32;
.. if it raises an exception without leaving the target locker in an Error State, `klmanagedlocker` is unchanged, or 32 if the zeroizing step has left the target locker _Unconfigured_ (<<KLEE-CSR-klmanagedlocker>>).
. It clears `klstart` once it has passed the checks that precede the conditions on the locker (the first group of <<KLEE-illegal-instruction-grounds>>, and the KLEE fatal-error, missing-CSK and locker-Off exceptions) and the check of `klmanagedlocker` above, even if it then raises an exception; rejected by one of those checks, it leaves `klstart` unchanged, so that an accidentally interleaved `kl.mgmt` does not destroy the progress of the operation under way. Software restores `klstart` to resume interrupted management operations.

The four operations of `kl.mgmt` are:

* `*kl.mgmt*` *opens a provisioning or an import.*
+
--
Software first obtains the MDH, `ml`, and supplies it with a Form A, C or D `kl.mgmt`.

NOTE: For an import, software first saves `ml` in its local state, and supplies it to the `kl.mgmt` that completes the import, to restore the _State_ that the locker had before the import started.

The instruction:

.. zeroizes the target locker; bytes of the serialized `Content` that the management operation has not yet written read as zero through every architectural access (`kl.store`, `kl.mvout`, verbatim export);
//.. It checks the validity of the fields of the provided MDH `ml`. If any are invalid according to <<KLEE-Metadata-validity>>, it transitions the locker to Error State _Invalid_.

// .. if `#immed7` = `kl_cfg_importing` and `ml`._State_ is an Error State, configures the locker immediately and
//     fully in that Error State, with the entire MDH from the auxiliary input, except that _AuxDataLen_ and _ADSDropped_ are set to 0 (Rule <<KLEE-GR-clear-locker-content-error-state>>); a _State_ of 54 or 55, or of 53 without `Zklexpire`, is replaced by _Invalid_.
//     The steps below are skipped: the locker holds only its MDH (<<KLEE-cryptographic-registers>>), no Machine is selected for execution,
//     and no KLF capacity is allocated, so this configuration cannot fail.
//     This one uninterruptible instruction (Rule <<KLEE-GR-uninterruptible-instructions>>) performs the whole configuration and opens no management operation, so
//     no `kl.mgmt` with `#immed7` = `kl_cfg_management_end` follows.
//     This is the _short import path_ of <<KLEE-error-state-transfer>>;

.. if `#immed7` = `kl_cfg_importing` and `ml`._State_ is an Error State, takes instead the _short import path_ of <<KLEE-error-state-transfer>>:
    it configures the locker immediately and fully in that Error State, skips the steps below, and opens no management operation;
.. raises a KLEE unsupported-Metadata exception if `ml` is unsupported Metadata (<<KLEE-MVR-open>>);
.. for a *provisioning*:
... requires `ml`._State_ to be _Unconfigured_, the Metadata being invalid otherwise (<<KLEE-MVR-open>>); the _State_ of the locker stays _Unconfigured_ during the checks below, until the locker is successfully configured;
... sets _StateExtension_ and _MachineUse_ to 0, ignoring the values in the PI;
... requires _AuxDataLen_ and _ADSDropped_ to be 0: if either is non-zero in the MDH of the PI,
the locker transitions to Error State _Invalid_, a Complete State, and the instruction terminates;
.. transitions the locker to Error State _Invalid_ if `ml` is invalid Metadata (<<KLEE-MVR-open>>), an _Unconfigured_ `ml`._State_ being invalid for an import;
.. attempts to allocate the KLF capacity that the MDH fields _Machine_, _MachinePolicy_, _SCProtection_, and _KeyType_ require (<<KLEE-length-rule>>),
    and raises a KLEE out-of-memory exception if it cannot;
.. for a *provisioning*, sets the _State_ of the locker to `kl_cfg_provisioning`;
.. for an *import*:
... applies steps 1–5 of <<KLEE-SCC-import>>, which decide, from the MDH loaded and the maximum that the implementation supports, whether the ADS is retained;
... sets the _State_ of the locker to `kl_cfg_importing` if `ml`._State_ is a Valid State,
or `kl_cfg_importing` or `kl_cfg_exporting` (the image of an interrupted import or export of a locker in a Complete State);
... sets it to `kl_cfg_ppi_importing` if the base type of `ml`._State_ is `pi` (<<KLEE-nested-state-base-types>>).

Wherever a check above fails, raising a KLEE exception or transitioning the locker to Error State _Unsupported_ or _Invalid_, every
MDH field other than _State_ remains zero, and no KLF capacity is allocated; after a KLEE out-of-memory exception, the locker remains _Unconfigured_.
This does not apply to the configuration of a locker directly into an Error State from `ml`, which installs the entire MDH.
--

* `*kl.mgmt*` *opens an export.*
+
--
Let `ml` be the MDH of the locker, which software first saves in its local state, to restore the _State_ when completing the export.
`kl.mgmt` can be of Form A, C or D, and ignores its auxiliary input. Depending on `ml`._State_:

.. _Unconfigured_: no operation and no exception. No management operation is opened, the authentication registers are unchanged, and only the common steps above take effect (Rule <<KLEE-GR-cleared-under-management>>).

.. An Error State: the locker is left unchanged, and no management operation is opened (Rule <<KLEE-GR-error-state-locker-is-only-MDH>>); <<KLEE-error-state-transfer>> details this short export path.

.. A Valid State: the instruction prepares the locker to produce an SCC, encrypting its contents and computing the authentication tag(s)
as <<KLEE-CC-management>> specifies, and sets its _State_ to `kl_cfg_exporting`.
The opening `kl.mgmt` changes no MDH field other than _State_: an implementation that creates or changes an ADS, or uses _MachineUse_, keeps _AuxDataLen_ and _MachineUse_ current at all times, so that the MDH that software reads before opening the export is the MDH that the export authenticates.

.. A Configuration State (the export of a partially configured locker, or a nested export):

... no encryption or authentication occurs: the contents of the locker are exported verbatim, in their order in the PI (for a partially provisioned locker) or in the SCC (for a partially imported locker, or a locker whose own export was interrupted);

... the _State_ of the locker is set to `kl_cfg_ppi_exporting` or `kl_cfg_exporting`, according to its base type (<<KLEE-nested-state-base-types>>).
--

* `*kl.mgmt*` *with `kl_cfg_management_end` completes a management operation.*
+
--
It first reads the MDH of the target locker, and completes a provisioning if its _State_ is `kl_cfg_provisioning`,
an import if it is `kl_cfg_importing` or `kl_cfg_ppi_importing`, and an export if it is `kl_cfg_exporting` or `kl_cfg_ppi_exporting`.

When completing an import or an export, it consumes only the _State_ field of the auxiliary operand `ml`,
which restores the _State_ of the locker to the value it had when the management operation started;
no other MDH field is written from `ml`.

At the completion of an SCC import or a locker export, authentication is checked
only if setting locker.MDH._State_ to `ml`._State_ restores a Complete State; the probability of accepting an incorrect _State_ is negligible.
A nested completion only checks the base type, without authentication.

If locker.MDH._State_ is `kl_cfg_importing` or `kl_cfg_exporting`, `ml`._State_ must be a Complete State or a Configuration State of base type `scc`, i.e., `kl_cfg_importing` or `kl_cfg_exporting`;
if it is `kl_cfg_ppi_importing` or `kl_cfg_ppi_exporting`, `ml`._State_ must be a Configuration State of base type `pi`, i.e., `kl_cfg_provisioning`, `kl_cfg_ppi_importing` or `kl_cfg_ppi_exporting` (<<KLEE-nested-state-base-types>>).
Any other `ml`._State_, including a Complete State for a locker of base type `pi` and the values 61–63, raises an illegal-instruction exception.
A Complete `ml`._State_ is accepted only for a locker of base type `scc`, so that the clear `Content` of a partially provisioned locker can become usable only by completing its provisioning.
--

** `*kl.mgmt*` *completes a provisioning.*
+
--
No MDH saved at provisioning start is needed: Form A is native, and Forms C and D ignore their auxiliary input.

Completing a provisioning requires _AuxDataLen_ = 0 and _ADSDropped_ = 0; if locker.MDH._State_ is `kl_cfg_provisioning` and either field is non-zero, the locker transitions to Error State _Invalid_, and the instruction terminates.

The operation makes the provisioned locker available to software by:

... for _KeyType_ = 1, generating the key of the all-ones SKID (<<KLEE-KeyType-field>>, Rule <<KLEE-GR-rbg-failure>>), or applying the SKID resolution of <<KLEE-system-keys>>;
... converting the content of the locker into the format that the KLEE unit uses internally;
... performing the checks that the Machine attaches to the fields of the PI (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-check-on-write>>); a failed check transitions the
    locker as Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-config-data-error>> classifies it, to Error State _Invalid_ for a configuration error or to _Failure_ for a data
    error, in place of the step below; and
... setting _State_ to _Ready_, and _StateExtension_ and _MachineUse_ to 0.

If a process is preempted during provisioning, `kl.store` or `kl.mvout` exports only the information of the original PI, unencrypted.
Only the `kl.mgmt` that completes the provisioning may therefore generate secret random material needed to configure the locker, retrieve key material from the SKS, or derive, expand or re-share that material,
so that no such material is exposed in an unencrypted export of a partially provisioned locker.
--

** `*kl.mgmt*` *completes an import.*
+
--
Software uses Form A, C or D of `kl.mgmt` to supply the value `ml` saved when the import started.
The image authenticated as ``AD[0]`` is the MDH held in the target locker, that is the one carried in the SCC and loaded when the import started, with its _State_ restored from `ml`, and _ADSDropped_ cleared in the copy used for authentication only (<<KLEE-SCC-import>>).

... If `ml`._State_ is a Complete State (the import of the export of a fully configured locker):
.... locker.MDH._State_ is set to `ml`._State_.
.... The KLEE unit decrypts and authenticates the content of the locker.
.... If authentication fails, the target locker transitions to Error State _Authentication Failed_, without an exception. Otherwise, if _KeyType_ = 1, the SKID is resolved, and the narrowing of <<KLEE-system-keys>> is applied.
.... The KLEE unit converts the content of the locker into the format that it uses internally.
.... The KLEE unit performs the checks that the Machine attaches to the fields that the import restores (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-check-on-write>>); a failed
check transitions the locker as at the completion of a provisioning (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-config-data-error>>).
This makes the locker available to software.
... Otherwise (the import of the export of a partially configured locker, or of a nested export), locker.MDH._State_ is set to `ml`._State_.
--

[[KLEE-mgmt-completes-export,Use of kl.mgmt to complete an export process]]
** `*kl.mgmt*` *completes an export.*
+
--
Software uses Form A, C or D of `kl.mgmt` to supply the MDH value `ml` saved when the export began. Then:

.. The _State_ of the locker is set to `ml`._State_.
.. If `ml`._State_ is a Complete State, Error States included, the instruction
restores the locker to the clear format it had when the export began, and makes it accessible to software:
... it decrypts and authenticates the contents as when completing an import, with the MDH held in the locker as `AD[0]`, and _ADSDropped_ cleared in the copy that first-segment authentication consumes;
... if the `SIV` check fails, the locker transitions to Error State _Authentication Failed_, and the instruction terminates without an exception; otherwise, if _KeyType_ = 1, the SKID is resolved, and the narrowing of <<KLEE-system-keys>> is applied.
+
NOTE: An implementation may instead restore the clear contents from an internal copy, but only if the outcome is identical: the copy is usable only while the locker, its MDH, `SIV` and, when _AuxDataLen_ ≥ 2, `IMPQUAL` and `SIV2` still hold the values that the opening `kl.mgmt` wrote, and `ml`._State_ equals the _State_ at that time. The specification defines no internal mechanism for this.

.. If `ml`._State_ is not a Complete State, the contents of the locker are not changed further.
--

** `*kl_cfg_management_end*` *issued on a locker in a Valid State*, with no management operation open on it, raises an illegal-instruction exception.

** `*kl_cfg_management_end*` *issued on a locker that is _Unconfigured_ or in an Error State* performs no operation and raises no exception: it ignores `ml`, and only the common steps above take effect (Rule <<KLEE-GR-cleared-under-management>>).

=== SCC Export and Import Algorithms

Section <<KLEE-SCC-AEAD>> describes the algorithms of SCC export and import, starting with the authenticated encryption scheme they use.

[[KLEE-SCC-AEAD]]
=== The SCC Authenticated Encryption Scheme

SCC export and import use a variant of AES-GCM-SIV cite:[DBLP-journals-iacr-GueronLL17,RFC8452], which differs from it as follows:

. The POLYVAL input omits the lengths of the AD and PT, since the MDH already determines the lengths of all sections.
. The optional Nonce is omitted.
. A domain separation bit, `sep`, distinguishes the two segments of the content sealed in an SCC: the architected content (`sep` = 0) and the optional implementation-specific content (`sep` = 1).
. For `sep` = 0, bit 47 of `AD[0]`, the unauthenticated _ADSDropped_ bit of the MDH (<<KLEE-Auxiliary-Data-Section>>), is cleared before `POLYVAL` is evaluated.

The Key Derivation (<<KLEE-SCC-key-derivation>>) and POLYVAL (<<KLEE-SCC-POLYVAL>>) functions are defined first,
then the generation of an SCC from a locker (<<KLEE-SCC-export>>) and the import of an SCC into a locker (<<KLEE-SCC-import>>).

In the pseudocode, `AESE256(K, B)` denotes the AES-256 encryption of the
128-bit block `B` under the 256-bit key `K` (FIPS 197 cite:[nist-fips-197]).

[[KLEE-SCC-key-derivation]]
.RFC8452 Key Derivation
[]
----
function SCC_KeyDeriv(key : bits(256), nonce : bits(96))
    → struct{enc_key : bits(256), auth_key : bits(128)} =
{
  local A : array [0..5] of bits(128);
  local i : int;

  foreach(i from 0 to 5) do:
    A[i] ← AESE256(key, nonce @ bin(i,32));

  return struct { enc_key  = A[5][63:0] @ A[4][63:0] @ A[3][63:0] @ A[2][63:0],
                  auth_key = A[1][63:0] @ A[0][63:0] }
}
----

// NOTE: Since key derivation is costly, implementations may cache the derived keys.

[[KLEE-SCC-POLYVAL]]
.Polyval Hashing Function
[]
----
function POLYVAL(auth_key : bits(128), blocks[0..n-1] : bits(128), n : int)
    → bits(128) =
{
  local tmp : bits(128) ← zeros(128);
  local i : int;

  foreach(i from 0 to n-1) do:
    tmp ← tmp xor blocks[i];
    tmp ← Montmul(tmp, auth_key);

  return tmp;
}
----

POLYVAL uses Montgomery multiplication, `Montmul(a, b)`, in the field F = GF(2)[`x`] modulo `x^128^ + x^127^ + x^126^ + x^121^ + 1`.
A 128-bit value `V` represents the element whose coefficient of `x^k^` is `V[k]`;
byte order and bit order both run forward, as in
cite:[RFC8452] {sect}3, under which `x^0^` is the byte string `0x01` followed by
fifteen zero bytes, i.e., the value `1`. Then: +
 +
`{fournbsp}{fournbsp}` `Montmul(a, b)` = `a` {interpunct} `b` {interpunct} `x^-128^` `{nbsp}{nbsp}` in the field F.

The SCC encryption and decryption functions, <<KLEE-SCC-GCM-SIV-enc>> and <<KLEE-SCC-GCM-SIV-dec>>, use the following notation:

* `AD[]` denotes the Associated Data as an array of `len_AD` 128-bit blocks, that is
  `AD[0] {vvert} AD[1] {vvert} {ellipsis} {vvert} AD[len_AD-1]`, in that order;
* `P[]`, resp., `C[]`, denotes a Plaintext, resp., a Ciphertext, as arrays of `len_PC`
  128-bit blocks, that is `P[0] {vvert} P[1] {vvert} {ellipsis} {vvert} P[len_PC-1]`,
  resp. `C[0] {vvert} C[1] {vvert} {ellipsis} {vvert} C[len_PC-1]`, in that order;
* `K` is a 256-bit Key;
* `N` is a 96-bit Nonce; and
* `SIV` is a 128-bit SIV/tag.

//

[[KLEE-SCC-GCM-SIV-enc]]
.AES-GCM-SIV Encryption for SCC Generation
[]
----
function SCC_Encrypt(AD[] : array of bits(128), N : bits(96), sep: bits(1),
    P[] : array of bits(128), K : bits(256), len_AD : int, len_PC : int)
  → {SIV : bits(128), C[] : array of bits(128)} =
{
  local AD_auth : array [0..len_AD-1] of bits(128) ← AD[];

  enc_key, auth_key ← SCC_KeyDeriv(K,N);
  if (sep = 0) then:
    AD_auth[0][47] ← 0;
  SIV ← POLYVAL(auth_key, AD_auth || P, len_AD + len_PC);
  SIV[95:0] ← SIV[95:0] xor N;
  SIV ← AESE256(enc_key, 0 @ sep @ SIV[125:0]);

  foreach(i from 0 to len_PC - 1) do:
    C[i] ← P[i] xor AESE256(enc_key,
             1 @ sep @ SIV[125:32] @ bin((int(SIV[31:0]) + i) mod 2**32, 32));

  return ( SIV, C[] );
}
----

`len_PC` never exceeds `max_admissible` / 16 (<<KLEE-instruction-mv>>), and `len_AD` never exceeds 7.

[[KLEE-SCC-GCM-SIV-dec]]
.AES-GCM-SIV Decryption for SCC Import
[]
----
function SCC_Decrypt(AD[] : array of bits(128), N : bits(96), sep: bits(1),
    SIV : bits(128), C[] : array of bits(128), K : bits(256),
    len_AD : int, len_PC : int)
  → {correct : bool, P[] : array of bits(128)} =
{
  local AD_auth : array [0..len_AD-1] of bits(128) ← AD[];

  enc_key, auth_key ← SCC_KeyDeriv(K,N);
  if (sep = 0) then:
    AD_auth[0][47] ← 0;

  foreach(i from 0 to len_PC - 1) do:
    P[i] ← C[i] xor AESE256(enc_key,
             1 @ sep @ SIV[125:32] @ bin((int(SIV[31:0]) + i) mod 2**32, 32));

  s ← POLYVAL(auth_key, AD_auth || P, len_AD + len_PC);
  tmp ← s;
  tmp[95:0] ← tmp[95:0] xor N;
  tmp ← AESE256(enc_key, 0 @ sep @ tmp[125:0]);

  if (tmp != SIV) then:
    foreach(i from 0 to len_PC - 1)
      P[i] ← zeros(128);
    return ( false, P[] );

  return ( true, P[] );
}
----

[[KLEE-SCC-export]]
=== Generation of an SCC from a Fully Configured Locker

If the locker is in an Error State, use the method in <<KLEE-error-state-transfer>>.

A locker ``K(i)`` in a Valid State is fully provisioned, and opening it for export (`kl.mgmt Kd, #kl_cfg_exporting`) creates the serialized, encrypted and authenticated SCC by the steps below.

The Locality substitution rules of <<KLEE-Localities>> apply: `LST_eff[j]` is the value of `LST` entry _j_ after substitution, and replaces `LST[j]` in the export and import algorithms.
An entry not implemented and with no configured replacement contributes `zeros(128)`, and makes the Metadata invalid at provisioning or import; an export is not refused on this ground, but the resulting SCC is rejected at import. Entry 9 of `LST` is `hkllocality`, and entry 10 is `skllocality`.

After `kl.clearads`, a fully configured locker has _AuxDataLen_ = 0 and _ADSDropped_ = 0 (<<KLEE-instruction-clearads>>); only an SCC-shaped PCCC may carry _ADSDropped_ = 1, to preserve an interrupted import after `Content2` was dropped.

.Exporting a Fully Configured Locker ``K(i)``
--
. First, process the architected content:
.. `saved_MDH` <- the MDH of ``K(i)`` immediately before its _State_ is set to `kl_cfg_exporting` (the image software saved beforehand), ``len_AD`` <- 1
.. ``AD[0]`` <- `saved_MDH`. `SCC_Encrypt` clears _ADSDropped_ in its local copy of this block before computing `SIV`; the `saved_MDH` returned in the SCC is unchanged.
.. foreach(_j_ from 0 to 10) do:
... If `saved_MDH`._Locality_ includes Locality #j, then ``AD[len_AD]`` <-  ``LST_eff[``_j_``]``, ``len_AD`` <- ``len_AD`` + 1
.. `len_PC` <- the number of 128-bit blocks of `Content1` (Section 5.a of <<KLEE-SCC>>).
.. `SIV`, `Content1~CT~[]` <- `SCC_Encrypt(AD, zeros(96), 0, K(i).Content1~PT~[], CSK, len_AD, len_PC)`
. Second, if _AuxDataLen_ {ge} 2, process the implementation-specific content:
.. `len_AD2` <- 2, ``AD2[0]`` <- ``K(i)``.`IMPQUAL`, ``AD2[1]`` <- `SIV`.
.. `len_PC2` <- the number of 128-bit blocks of `Content2` (Section 5.b of <<KLEE-SCC>>), i.e., _AuxDataLen_ − 2.
.. `SIV2`, `Content2~CT~[]` <- `SCC_Encrypt(AD2, zeros(96), 1, K(i).Content2~PT~[], CSK, len_AD2, len_PC2)`
. Finally, if _AuxDataLen_ = 0, then:
.. return(`saved_MDH`, `SIV`, `Content1~CT~[]`)
. else:
.. return(`saved_MDH`, `SIV`, `IMPQUAL`, `SIV2`, `Content1~CT~[]` and `Content2~CT~[]`) (`Content2~CT~[]` may be empty)
--

// Of the returned values, `SIV`, `SIV2` and `IMPQUAL` are placed in the CSRs `§acesivl`/`acesivh`,
// `acesiv2l`/`acesiv2h` and `aceiql`/`aceiqh`, from which software stores them to memory; the ciphertext
// remains in the locker, whence `kl.store` (<<KLEE-instruction-store>>) transfers it; and `saved_MDH` is the
// image software already holds, which `kl.getmd*` (<<KLEE-instruction-getmd>>) also returns.
//
// If _AuxDataLen_ = 0, then `SIV2` and `IMPQUAL` are not generated, and therefore
// `acesiv2l`/`acesiv2h` and `aceiql`/`aceiqh` are not written to.
// They may contain stale values, but this is not an issue as they are not exported to memory in this case.

[NOTE]
====
Completing an export prematurely causes an authentication error at import (next section), and completing an import prematurely an authentication error at once.
Leaving either operation uncompleted leaves the _State_ a Configuration State, in which most instructions fail.
====

[[KLEE-SCC-import]]
=== Decryption and Authentication of a Complete SCC into a Locker

If the SCC's MDH is in an Error State, use the method in <<KLEE-error-state-transfer>>.

The following algorithm imports the SCC of a fully configured locker.
The `kl.mgmt Kd, #kl_cfg_importing` opening the import performs steps 1 to 5
(<<KLEE-locker-management>>), the `kl.load` or `kl.mvin` instructions that follow perform step 6
(<<KLEE-instruction-load>>, <<KLEE-instruction-mv>>), and
`kl.mgmt Kd, #kl_cfg_management_end` decrypts and authenticates the SCC, makes it available to software.

.Importing a Fully Configured Locker ``K(i)``
--
 . Clear ``K(i)``.
 . Load `M`, the MDH from the SCC, into ``K(i)``.MDH.
 . Check the validity of `M`, and whether the Machine is supported.
 . Determine the SCC layout from `M`.
 . If `M`._AuxDataLen_ {ge} 2, and either `M`._ADSDropped_ = 1 or `M`._AuxDataLen_ exceeds the maximum of the implementation for the Machine, set ``K(i)``.MDH._ADSDropped_ to 1; otherwise set it to 0. This changes only the length of `Content2`: when _AuxDataLen_ {ge} 2, `IMPQUAL` and `SIV2` remain present and _ContentOffset_ remains 48.
 . Load the rest of the SCC, up to the length that the resulting working MDH gives: with _ADSDropped_ = 1, `SIV`, `IMPQUAL`, `SIV2` and `Content1`, but no `Content2`.
 . `saved_MDH` <- the MDH image held in ``K(i)``, that is `M` with the working value of _ADSDropped_ and with its _State_ field restored from the auxiliary operand of the completing `kl.mgmt`.
 . ``AD[0]`` <- `saved_MDH`, ``len_AD`` <- 1. `SCC_Decrypt` clears _ADSDropped_ in its local copy of `AD[0]` before authenticating it; the MDH held in ``K(i)`` is unchanged by that computation.
 . foreach (`j` from 0 to 10) do:
 .. If `saved_MDH`._Locality_ includes Locality #j, then ``AD[len_AD]`` <-  ``LST_eff[j]``, ``len_AD`` <- ``len_AD`` + 1
 . `len_PC` <- the number of 128-bit blocks of `Content1` (Section 5.a of <<KLEE-SCC>>).
 . `correct`, ``K(i)``.`Content1` <- `SCC_Decrypt(AD, zeros(96), 0, SIV, K(i).Content1, CSK, len_AD, len_PC)`.
 . If `correct` {ne} `true`, the SCC is rejected: ``K(i)`` transitions to Error State `kl_state_mgmt_auth` (Rule <<KLEE-GR-clear-locker-content-error-state>>).
 . If ``K(i)``.MDH._AuxDataLen_ {ge} 2 and ``K(i)``.MDH._ADSDropped_ = 0, process the implementation-specific content:
.. `len_AD2` <- 2, ``AD2[0]`` <- ``K(i)``.`IMPQUAL`, ``AD2[1]`` <- `SIV`.
.. If ``K(i)``.`IMPQUAL` = `zeros(32) @ klmimpid @ klmarchid @ klmvendorid` then:
... `len_PC2` <- the number of 128-bit blocks of `Content2` (Section 5.b of <<KLEE-SCC>>), that is ``K(i)``.MDH._AuxDataLen_ − 2.
... `correct`, ``K(i)``.`Content2` <- `SCC_Decrypt(AD2, zeros(96), 1, SIV2, K(i).Content2, CSK, len_AD2, len_PC2)`.
.. else:
... `correct` <- `false`.
 . If second-segment processing was attempted and `correct` {ne} `true`, drop `Content2` and set ``K(i)``.MDH._ADSDropped_ to 1.
 . If ``K(i)``.MDH._AuxDataLen_ = 0 or ``K(i)``.MDH._ADSDropped_ = 1, the import completes with the architected content alone: the Machine establishes a consistent internal state, sets _ADSDropped_ to 0, and sets _AuxDataLen_ to 0, or, if it generates a replacement ADS, during completion or later, to the appropriate value, at least 2. Otherwise the successfully imported ADS is retained, _AuxDataLen_ is preserved, and _ADSDropped_ is set to 0. A later export uses these current values, emitting no ADS when _AuxDataLen_ = 0, and the generated or retained ADS when _AuxDataLen_ {ge} 2.
--

[NOTE]
====
If the optional implementation-specific ADS makes the SCC too large for a locker, or is incompatible, the implementation ignores it and keeps the architected content: only a failure of the first authentication (`SIV`) rejects the entire SCC.
====

=== Design Rationale for the Sealing Construction

_This section is informative and non-normative._

To reduce the size of the payload and allow the system to cache the encryption and authentication keys, the construction omits the nonce and relies on the resistance of AES-GCM-SIV to nonce reuse and misuse. It remains secure for up to O(2^64^) 128-bit blocks observed by an adversary, which suffices for client applications. On cloud servers, each virtual machine and supervisor domain should use its own CSK; to transfer a CC between domains, M-mode firmware imports the SCC under the CSK of the source domain and re-exports it under that of the target domain.

The `SIV` (Synthetic IV), which is also the GCM-SIV authentication tag, is the encryption of the `POLYVAL` hash (<<KLEE-SCC-POLYVAL>>) of the MDH, with _ADSDropped_ cleared in the authenticated copy, of the Locality Secrets, and of the Content, in that order.
The Locality Secrets thus enter the AEAD as _associated data_ rather than being mixed into the Context Sealing Key by a KDF. Both approaches bind the SCC to the Locality set, but associated data is cheaper: POLYVAL costs one `Montmul` per 128-bit block, far less than most KDFs, and a change of Locality set requires no re-derivation of `enc_key` and `auth_key`. Distinct Locality sets yield the same SIV with probability 2^-126^.

Taking `SIV` as ``AD2[1]`` binds the two payloads: `SIV2` and the keystream of the second segment change whenever the first payload changes, so an attacker cannot graft the implementation-specific ADS of one SCC onto the architected part of another.

As in AES-GCM-SIV, bit 127 separates tag inputs (0) from keystream inputs (1). The additional domain separation bit `sep` (bit 126) costs one bit of security: the tag input carries 126 bits of the `POLYVAL` result instead of 127, and the keystream generator 94 bits of the `SIV` instead of 95. Without it, the keystreams of the two segments would coincide only with vanishing probability, so the construction would still be secure; with it, they differ by design.

[[KLEE-error-state-transfer]]
=== Export and Import of a Locker in an Error State

A locker in an Error State holds only its MDH (Rule <<KLEE-GR-clear-locker-content-error-state>>).
No KLF capacity is allocated for the locker, and the Machine definition fields are ignored.
There is nothing to encrypt and KLEE also does not authenticate it, since it would be easy to forge
a valid authenticated MDH in the current environment.
Neither direction produces an SCC or a PCCC, or opens a management operation.
Both paths are thus shorter than those of <<KLEE-management-operations>>,
and, since they issue no `kl.load` or `kl.store`, take no part in resumption.

For such a locker and its exported image, only the _State_ field of the MDH is checked; the other fields are not checked for validity (<<KLEE-Metadata-validity>>).

*Exporting* a locker in an Error State takes two steps, and no `kl.mgmt`:

. Read the _State_ field with `kl.getst` (<<KLEE-instruction-getst>>), and find an Error State.
. Read the MDH with `kl.getmd` or `kl.getmdv` (<<KLEE-instruction-getmd>>), and store its 16 bytes
  to memory; `kl.size` reports 16.

A `kl.mgmt` with `#immed7` = `kl_cfg_exporting` on a locker in an Error State is permitted but
useless: it leaves the locker unchanged and opens no management operation; only its common steps take effect, `klmanagedlocker` naming the locker and `klstart` becoming 0
(<<KLEE-locker-management>>).

*Importing* such an image takes one step:

. Issue `kl.mgmt` with `#immed7` = `kl_cfg_importing` and the 16-byte MDH
  as the auxiliary operand, carried whole by Form C or D, or by a Form A from the KLIOBUF. The instruction:
  .. zeroizes the locker it names, and copies the MDH into it, with _AuxDataLen_ and _ADSDropped_ set to 0 (Rule <<KLEE-GR-clear-locker-content-error-state>>);
  .. replaces a _State_ of 54 or 55, or of 53 without `Zklexpire`, by _Invalid_.

The instruction is uninterruptible (Rule <<KLEE-GR-uninterruptible-instructions>>), so no intermediate state of the locker is ever observable.
No `kl.mgmt` with `#immed7` = `kl_cfg_management_end` follows; issuing one performs no operation (Rule <<KLEE-GR-cleared-under-management>>).
The `SIV`, `SIV2` and `IMPQUAL` registers take no part in either path, and need not be saved for it.

[[KLEE-state-save-and-restore-order]]
== Context Switching, KLEE State Save and Restore Order

_This section is informative and non-normative._

Lower-privileged modes may save, restore or overwrite lockers that higher-privileged modes configure,
so higher-privileged software must clear the lockers it uses before giving control to lower-privileged modes.
If higher-privileged software uses the KLIOBUF, `klstart`, `klmanagedlocker` or the authentication registers while the KLEE state of a lower-privileged context is live, it must save and restore them as at a context switch (below), so that the lower-privileged context observes its own values and no data of the higher-privileged mode.
When switching to a lower-privileged component, software restores only the lockers previously saved for that component, and erases those that are not part of its KLEE state.
The same applies to `kliobuflen` and to the KLIOBUF when `kliobuflen` {ne} 0.

[WARNING]
====
`klmanagedlocker` is writable in every mode, and it alone determines the locker of `kl.load`, `kl.store`, `kl.mvin` and `kl.mvout`, and of every instruction naming `KM` (Rule <<KLEE-GR-klmanagedlocker-override>>).
Privileged code, and every exception handler, including one that runs in the same mode as the interrupted code, therefore follows the software requirement of <<KLEE-CSR-klmanagedlocker>>: before issuing any of these instructions it reads `klmanagedlocker` and, unless it is acting on the locker under management, saves the value and writes the number of the locker it intends, or 32 for a KLIOBUF transfer, and restores the saved value before returning to the interrupted context.
Otherwise a value left by the interrupted or less privileged software redirects these instructions to another locker: a `kl.store` would export a different locker, and a `kl.clear KM` would clear a different locker and leave the intended one in place.
Instructions that name their locker in the encoding are not affected.
====

The recommended order for saving and restoring the KLEE state is:

* Save order:

. Save `klstart` first, since every later step may clear it.
. Save the raw value of `klmanagedlocker`.
. With `Zklio`:
.. save `kliobuflen` and `kliobuftop`;
.. if `kliobuflen` is non-zero, save the buffer contents with `kl.output`, with `klmanagedlocker` = 32 (otherwise `kl.output` would store the managed locker's image, Rule <<KLEE-GR-klmanagedlocker-override>>), `klstart` = 0 and `kliobuftop` raised to `kliobuflen`, since the `kl.mgmt` of a locker export may take `ml` from the KLIOBUF (<<KLEE-usage-input-output>>).
. If the saved `klmanagedlocker` is in [0..31], read the MDH of the locker it indexes with `kl.getmd*`, and choose the save path by State:
.. _Unconfigured_: save no locker image;
.. an Error State: save its MDH by the short Error-State path (<<KLEE-error-state-transfer>>);
.. otherwise, export the locker by the applicable Complete- or Configuration-State path, before any other `kl.mgmt` that could overwrite the authentication registers.
. Save every other locker that is not _Unconfigured_ by the path appropriate to its State, with the working value of `klmanagedlocker` set to 32 before and after each export.

* Restore order:

. Restore the lockers other than the one that the saved `klmanagedlocker` indexes, with the working value of `klmanagedlocker` set to 32 before and after each import.
. If the saved `klmanagedlocker` is in [0..31] and an image was saved for the locker it indexes, restore that locker by the path appropriate to its saved State, with the working value of `klmanagedlocker` set to 32 before opening its import.
. With `Zklio`:
.. restore `kliobuflen`, which zeroes the buffer and sets `kliobuftop`;
.. restore the buffer contents, if saved, with `kl.input`, with `klmanagedlocker` = 32, `klstart` = 0 and `kliobuftop` = `kliobuflen`;
.. restore `kliobuftop`.
. Restore the raw saved value of `klmanagedlocker`, or 32 if the handler has cleared the locker it named instead of saving it.
. Restore `klstart` last, since every earlier step may clear it.

A handler that passes `ml` through the KLIOBUF configures `kliobuflen` {ge} 16 for the locker exports and imports, and restores the saved value afterwards.

A handler treats `klmanagedlocker` as a hint, and checks the MDH of the locker it names before choosing a save path.
User software may, for example, clear `K0`, write 0 to `klmanagedlocker`, and enter a handler: the all-zero MDH identifies `K0` as _Unconfigured_, so the handler knows it must not save an image for it.
// an export attempted on it would perform no operation (Rule <<KLEE-GR-cleared-under-management>>).
Likewise, a handler saves no image for a locker that it finds _Unconfigured_ at the end of an export, because more privileged software has cleared it in the meantime.

A handler that clears a partially provisioned or imported locker that `klmanagedlocker` names, instead of saving it, restores 32 in place of the saved `klmanagedlocker`, the value that the clear has set; it restores `klstart` as saved.
The interrupted software then finds the locker _Unconfigured_ at its next check, and restarts the provisioning or import (Rule <<KLEE-GR-cleared-under-management>>).

[[KLEE-CSK-requirements]]
== Architectural Requirements on the Context Sealing Key

The KLEE unit operates only with a configured Context Sealing Key (CSK). Without an active CSK, every KLEE instruction and KLEE CSR access raises a KLEE missing-CSK exception, with two exceptions: accesses to the `mklcsk` CSR group and to the Locality Secret CSR groups (<<Zkl-ISA-priv.adoc#KLEE-CSR-locality-groups>>), which are configured independently of the CSK; and reads of the identification CSRs `klmvendorid`, `klmarchid`, `klmimpid` and `klmaxiobuflen` (<<KLEE-CSR-impl-ids>>, <<KLEE-CSR-klmaxiobuflen>>), so that firmware can identify the KLEE unit before configuring it.

A CSK is set in one of four mutually exclusive ways:

. a value that M-mode programs through the `mklcsk` CSR group (<<Zkl-ISA-priv.adoc#KLEE-CSR-mklcsk>>);
. a value configured by a secure hardware block exclusive to M-mode (e.g., Caliptra cite:[caliptra]), or a port to one, which exports CSK values through a dedicated interface based on public-key encryption.
  Only M-mode may request the block to configure the CSK of its hart, by a handle or a wrapped key; the clear key must not be exposed to any software, M-mode included.
  Addressing and key transport are platform-specific and outside the scope of this specification;
. a fixed, hardwired value, generated at manufacturing time, per die or shared across batches; or
. a value generated at boot by a secure RBG (<<KLEE-Prerequisites>>), and accessible to no software.
  All harts of a well-defined subsystem of an SoC share it, and cannot exchange SCCs with other subsystems; it survives the reset or fatal condition of a single hart, and is regenerated only at the power-on reset of the subsystem.

The third and fourth models suit mainly specialized embedded deployments: a hardwired CSK cannot be reconfigured or revoked, and a boot-generated CSK cannot preserve SCCs across power loss.

Under the third model the KLEE unit is available at once; under the others, only after a CSK has been established. A hart reset resets the associated KLEE state (<<KLEE-reset-and-m-mode-only>>), under the first and second models including the configurable CSK, which leaves the unit unavailable until the CSK is re-established.

No software may read a CSK value in clear, except M-mode under the first model.
//An implementation that permits CSK reprogramming via the `mklcsk` CSR group must follow the activation rules in <<Zkl-ISA-priv.adoc#KLEE-CSR-mklcsk>>.

NOTE: When the CSK is shared across devices, CCs meant to be device-bound must name _ChipScrt_ or _DevScrt_ in their _Locality_.

[IMPORTANT]
====
For the SCCs of a process to remain importable when it migrates between harts, the destination hart must use the CSK of the source; the OS and hypervisor should ensure that M-mode establishes it there, by a platform-dependent mechanism outside the scope of this specification.
Under the fourth model, this is possible only within the subsystem that shares the CSK.
Unless software handles the differences, it may migrate a process only between harts whose KLEE units have identical `klmvendorid`, `klmarchid`, `klmimpid` and `klmaxiobuflen`, and implement the same extensions and Machines.
====

M-mode firmware must account for the configuration model of the CSK. Persistence mechanisms for configurable CSKs are implementation-specific. Transferring a CSK to another endpoint, such as the M-mode firmware of another device, a local TPM (for instance to preserve the CSK across suspension or host hibernation), or a cloud-based HSM, *requires* an authenticated public-key wrapping mechanism, outside the scope of this specification.

[[KLEE-reset-and-m-mode-only]]
== KLEE Unit Reset and M-mode-only Harts

A _KLEE unit reset_ of a hart resets the KLEE architectural state of that hart
(<<KLEE-out-of-reset-unpriv>>, <<Zkl-ISA-priv.adoc#KLEE-out-of-reset-priv>>);
in a KLEE unit shared by several harts, it affects only the state of that hart, shared Locality Secrets excepted.
A hart reset implies a KLEE unit reset of that hart, and so does a fatal condition, with the differences stated in <<KLEE-error-architecture>>.
Reset does not affect a hardwired CSK.

M-mode establishes the CSK by one of the models of <<KLEE-CSK-requirements>>, every software-programmable Locality Secret whose CSR group is not implemented is unconfigured (<<KLEE-Localities>>), and `KLS` is treated as Initial; <<Zkl-ISA-priv.adoc#KLEE-priv>> states which of its CSRs may exist on such a hart.

[[KLEE-indirect-lockers]]
== Zklind: Indirect Locker Naming

In this section we assume throughout that `Zklind` is available.

This means that, in all places where a locker is named in an encoding, the locker can also be named _indirectly_:
the 5-bit immediate locker index names a GPR instead of a locker, and the value in the GPR names the locker.
Indirect addressing is written as `K(Xd)`, `K(Xs1)`, and `K(Xs2)` whenever direct addressing is written as `Kd`, `Ks1`, and `Ks2`.
The managed locker `KM` (Rule <<KLEE-GR-klmanagedlocker-override>>) is not an indirect operand, although it is encoded with `r` = 1 and `X0`, and is available without `Zklind`.

[NOTE]
====
Register renaming of lockers remains possible with indirect addressing, but would add much microarchitectural complexity for little benefit: lockers are redefined far less often than GPRs or FP registers, rarely take one key or another conditionally, and speculation on cryptographic results usually creates security issues.
====

Where an encoding offers both, bit `r`, called the _locker indexing mode selector_, chooses between them: with `r` = 0 the 5-bit register field is the locker index, and with `r` = 1 it is the number of the GPR holding the index.

In instructions `kl.clone`, `kl.rename`, `kl.swap` (<<KLEE-instruction-clone>>), and `kl.derive` (<<KLEE-instruction-derive>>) Field `R` (bits [26:25]) selects how the lockers are given:

[upperalpha]
. `00`{nbsp}{nbsp} source and destination both as immediates;
. `01`{nbsp}{nbsp} source as an immediate, destination through a GPR;
. `10`{nbsp}{nbsp} source through a GPR, destination as an immediate;
. `11`{nbsp}{nbsp} source and destination both through GPRs.

`kl.avail` and `kl.size` (<<KLEE-instruction-size>>) have an additional variant of Form A:

* `F` = `0b00`, `r` = `1` {implies} Form A, from a context given indirectly as `K(Xs)` (Rule <<KLEE-GR-GPR-indirect>>).

An indirect locker index outside [0..31] raises an illegal-instruction exception, and so does `X0` as the indirect locker index register, except where it encodes `KM` (Rule <<KLEE-GR-klmanagedlocker-override>>).
