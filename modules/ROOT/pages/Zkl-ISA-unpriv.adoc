[[KLEE-unpriv-intro]]
== Introduction

KLEE lets software perform high-performance cryptographic operations without direct access to the keys or other critical derived values.
Its fundamental features are:

* *Atomic operations.* Each cryptographic operation is atomic, so no intermediate value can leak through memory read exploits.
An instruction that performs several distinct cryptographic operations can be interrupted only between them.

* *Splitting of complex algorithms into smaller atomic operations.* Unlike some CISC architectures, and in line with RISC-V philosophy, KLEE offers no instructions that perform complex modes of operation on inputs of arbitrary length.

* *Hidden cryptographic state.* KLEE operations do not reveal keys and other critical values.

* *A single interface for many primitives*, instead of separate instructions per primitive:
 ** Primitives alone do not suffice for modes such as AES-GCM-SIV, XTS, and OCB, where leaked derived keys or intermediate values compromise security. KLEE therefore also defines modes of operation, among them CTR, GCM, and CMAC, and secure key derivation.
 ** Encrypt-only and decrypt-only versions reduce misuse, and versions with a preset IV or nonce keep it confidential.
 The modes work with AES-128, -192, -256, and other block ciphers such as SM4.
 ** The interface also supports hash functions, public-key and post-quantum algorithms, and SCA-resistant implementations.
 ** Side-channel-protected implementations, when available, are simply variants of the standard algorithms and can replace them without code changes.
 ** Implementations need not support every algorithm and variant: following RISC-V practice, KLEE defines subextensions and leaves requirements to the RISC-V profiles.

* *Support for context switch, persistence, sleep, hibernation, and VM migration.*

* *Scalability.* One ISA and ABI serve embedded to server cores.

KLEE realizes these features through the following concepts.

[[KLEE-concepts]]
=== Fundamental Concepts and Definitions

Cryptographic Context:::
(((Cryptographic Context)))
Most KLEE instructions run within the constraints set by a *Cryptographic Context* (CC).
A CC is an indivisible structure consisting of a *Metadata Header* (MDH) and *Content*.
(((Cryptographic Context, Content)))
The Content holds the secrets, usually keys, and other sensitive material.
(((Cryptographic Context, Metadata Header)))
The MDH has a fixed format, restricts the use of the secrets to one set of cryptographic algorithms, and can enforce usage constraints by process, VM, security state, boot cycle, expiration date, or other policies.
The Metadata requires integrity, except for explicitly identified format hints and the layout-preserving fields they make inactive; the Content requires integrity and confidentiality.
KLEE and the algorithms it implements enforce these requirements architecturally.

Cryptographic Locker:::
(((Cryptographic Locker)))
CCs are created in *Cryptographic Lockers* (_lockers_ for short), per-hart architectural containers that safeguard their contents.
*Provisioning* a locker writes Metadata and Content into it and binds them into a CC.
A CC is usable only while in a locker, where only the KLEE unit accesses or modifies it, under the rules of the architecture and its Machine; no instruction extracts the Content in a way that compromises its confidentiality.

KLEE Machine:::
(((Machines)))
(((Cryptographic Context, object-oriented)))
A *KLEE Machine* (short: _Machine_) is a state machine that implements one or more cryptographic functions (primitives, modes, protocols) through the interface of this specification.
The metadata of a locker identifies its Machine by the 12-bit _Machine_ field, which _MachinePolicy_ and _MachineExtension_ extend to 16 bits (<<KLEE-metadata-header>>).
A small set of KLEE instructions operates the Machines: they take this identifier from the metadata and standard RISC-V inputs and outputs, such as GPRs, vector registers and memory, and their semantics depend on the Machine.
A CC thus encapsulates Machine-specific behavior, so that different primitives (e.g., AES-128, AES-256 and SM4) can be used in the same modes (e.g., ECB, GCM-SIV and XTS) without changing the compiled code. Side-channel-resistant variants are supported transparently.

Sealed Cryptographic Context:::
(((Cryptographic Context, sealed)))
For context switching, a CC can be *exported* from a locker as a *Sealed Cryptographic Context* (SCC), an encrypted and authenticated representation that can later be *imported* into a locker. Export and import use a _Context Sealing Key_ (CSK), which M-mode may be able to program. An SCC sealed under one CSK cannot be imported under another, which separates spatial and temporal domains cryptographically.

Usage Control Policy:::
+
--
(((Cryptographic Context, usage control)))
(((Cryptographic Context, management operations)))
(((Cryptographic Context, usage operations)))
KLEE distinguishes *management* operations from *usage* operations on CCs and lockers.
(((Cryptographic Context, export)))
Management operations are classified as

* *configuration* (e.g., *provisioning*, SCC *import*, and *cloning*, *renaming* and *swapping* lockers),
* *export* of a locker as an SCC, and
* *clearing* a locker, i.e., freeing it, deleting any secret it contains.

Usage operations are cryptographic operations and state changes.

To prevent denial of service, management operations are less restricted than usage operations: _Usage Control_ policies restrict only usage operations.
--

Localities:::
(((Cryptographic Context, Locality)))
KLEE can bind a CC to *Localities*, which restrict where its exported SCCs can be imported, and thus where it can be restored and used: specific devices or device classes, hardware configurations, physical or virtual boot cycles, and process domains at various privilege modes.
// The Localities act as _tweaks_ in the encryption and decryption of SCCs.

[[KLEE-architectural-model]]
=== Architectural Model

KLEE is architected as an interface to an _attached_ unit: its instructions are messages over a tightly coupled coprocessor interface, and the KLEE unit executes them independently of the issuing hart and returns the results.
This keeps the hart side simple: software implements the locker-configuration logic, the KLEE unit the cryptography, and several cores may share one KLEE unit.

The specification defines only architectural behavior, not implementation: KLEE may be integrated into a CPU core or be a distinct hardware unit; either way each client hart has separate KLEE architectural state, and the same code runs on both.

KLEE may be emulated, partly or completely, in M-mode firmware: an implementation may, for example, perform symmetric operations (<<Zkl-ISA-machines.adoc#KLEE-states-symmetric>>) in the KLEE unit and emulate public-key cryptography (<<Zkl-ISA-machines.adoc#KLEE-ECC>>, <<Zkl-ISA-machines.adoc#KLEE-PQC>>), whose very large states then reside in secure memory that meets the requirements of <<KLEE-KLF>>, such as on-chip SRAM reserved to M-mode.

Locker state must never be accessible in the clear to any privileged mode except M-mode and authenticated Debug mode.
The only locker state exported in the clear is the `Content` of a partial provisioning, which software has itself supplied (<<KLEE-data-formats>>).
KLEE implementations in S/VS-mode or HS-mode are therefore forbidden: instructions and Machines may be emulated only in M-mode.
Trap-and-emulate and on-demand (lazy) SCC import rely on the ``*llockerstatus`` CSRs (<<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>>).

[[KLEE-Prerequisites]]
=== Prerequisites

A conformant KLEE implementation requires the RISC-V External Debug Security extension cite:[riscvExternalDebugSecurity].

It also requires the KLEE exceptions of <<Zkl-ISA-priv.adoc#KLEE-exceptions>> to be implemented and raised as the unprivileged architecture mandates, whether or not the KLEE Privileged Architecture is implemented.

Where the KLEE unit or its Machines need an RBG, it must use an entropy source that meets the requirements of the `Zkr` specification cite:[RISCV-ISA-Unpriv], used to seed a DRBG compliant with NIST SP 800-90A cite:[nist-SP-800-90-r1] or an equivalent standard.
Rule <<KLEE-GR-rbg-failure>> covers RBG failure.

`Zkl` conformance requires:

. at least one of `Zklv` and `Zklio`;
. AES128, AES192 and AES256 in ECB and GCM modes, AES128 and AES256 in GCM-SIV mode, and SHA2-224, SHA2-256, SHA2-384, SHA2-512, SHA2-512/224 and SHA2-512/256,
as defined in <<Zkl-ISA-machines.adoc#KLEE-Machines>>; and
. `Zklmem`, in hardware or by trap-and-emulate (<<KLEE-error-architecture>>).

KLEE instructions may raise the standard RISC-V exceptions and a few KLEE-specific exception types, listed in <<Zkl-ISA-priv.adoc#KLEE-exception-codes>>.

With trap-and-emulate, the hardware raises an illegal-instruction exception for instructions it does not implement, which the platform must deliver to M-mode (`medeleg` bit 2 zero); the encodings are assigned, not reserved (<<KLEE-illegal-instruction-grounds>>).
`Zklmv` must then be in hardware, since the emulating code moves data between memory and the locker with it.
`kl.load` and `kl.store` are thus always present; `Zklmv` and `Zklexpire` are otherwise optional.

`Zklv` requires the KLV subset of the vector extension (<<KLEE-KLV>>) with `VLEN` {ge} 128, that is `Zvl128b` or a larger `Zvl*b`, on which every vector Form that carries an MDH or a 128-bit block depends.

The principal KLEE instructions, defined in full below, are:

* `kl.mgmt` (<<KLEE-instruction-mgmt>>) moves a locker through its management lifecycle, and,
with the KLEE memory operations `kl.load` (<<KLEE-instruction-load>>), `kl.store` (<<KLEE-instruction-store>>), `kl.mvin` and `kl.mvout` (<<KLEE-instruction-mv>>),
performs the management operations (<<KLEE-management-operations>>):
 ** *provisioning* loads metadata and clear Content into a locker, binding them;
 ** *export* writes a locker to memory as an SCC;
 ** *import* loads an SCC into a locker; and
 ** each takes several instructions, except on a locker in an Error State (<<KLEE-error-state-transfer>>).
* `kl.clear` (<<KLEE-instruction-clear>>) unconfigures and clears a locker. It is a pseudo-instruction of `kl.setst`, and never part of a management operation.
* `kl.exec` (<<KLEE-instruction-exec>>) performs the cryptographic operations that the Machine configured in a locker defines for the locker's current state.
* `kl.setst` (<<KLEE-instruction-setst>>) moves the CC in a locker between the states of its Machine.
* `kl.getmd*` (<<KLEE-instruction-getmd>>) reads the metadata of a locker. The pseudo-instruction `kl.getst` (<<KLEE-instruction-getst>>), built on `kl.getmdl`, extracts the state of a locker from its MDH, and thus also reports errors.

[[KLEE-cryptographic-registers]]
== Cryptographic Lockers

{empty}
(((Cryptographic Context)))
KLEE defines 32 Cryptographic Lockers, `K0`–`K31`.
Like GPRs or vector registers, lockers are per-hart architectural state, not separated by privilege mode: a hart sees the same lockers in every mode.
Unlike a conventional register, a locker can be _unconfigured_, that is hold no CC.

A locker is addressed like a conventional register, by a 5-bit immediate.
With `Zklind` (<<KLEE-indirect-lockers>>), a locker can also be addressed indirectly, by a GPR value, and an encoding bit selects the mode.
Some management instructions may also name the locker under management, written `KLML` (Rule <<KLEE-GR-klmanagedlocker-override>>).

The CC in a configured locker consists of a Metadata Header (MDH) and `Content` (<<KLEE-concepts>>).
The _i_-th locker is denoted `K(i)`, its MDH `K(i).MDH`, and its content `K(i).Content`.
During import and export, and in an SCC, the content consists of two consecutive arrays of 128-bit blocks:
`Content1`, the architected content that <<Zkl-ISA-machines.adoc#KLEE-Machines>> specifies for each Machine,
and `Content2`, any implementation-specific content.

[[KLEE-KLF]]
== The Cryptographic Locker File and Authentication Information

(((Cryptographic Locker File)))Lockers reside in a per-hart _cryptographic locker file_ (KLF), a memory that only the KLEE implementation can access.
If the implementation is partly or fully emulated, only M-mode firmware can access the KLF, through an implementation-defined mechanism that must be provided.

The KLF guarantees the confidentiality and integrity of its contents, including against rollback through any access this specification does not permit.
KLF accesses need no hardware hardening against physical side-channel attacks, except that side-channel-protected implementations of the KLEE unit's Machines must protect them too.

It is recommended that the side-channel and fault-injection protection of `SCC_KeyDeriv`, `SCC_Encrypt`, `SCC_Decrypt`, and every use of the CSK and its derived keys be no weaker than the highest side-channel protection level the implementation supports for any Machine.

NOTE: The KLF, as a memory device, must resist rollback, but individual lockers need not, and cannot, resist rollback through export and import.
Re-importing an earlier CC state may enable multi-time-pad attacks on modes such as CTR, XCTR and GCM (<<Zkl-ISA-machines.adoc#KLEE-nonce-reuse>>), but exploiting them needs control of the target software, which usually also exposes the plaintext.
Re-import is also useful, for instance to restart an operation whose payload was corrupted in transit, and policies covering every legitimate case would overcomplicate it.

Architecturally, the KLF contains:

. an array of 32 128-bit blocks, whose _i_-th entry holds the MDH of `K(i)`; and
. an implementation-defined amount of memory, allocated dynamically to the lockers, which holds the `Content` of every configured locker.

The two parts are conceptually distinct, whatever the implementation.
The MDH array is always present, so every locker holds its MDH, if only to show that it is unconfigured.
Only the second part is allocated and capacity-limited: "`KLF capacity`" refers to it alone, a locker that holds only its MDH consumes none, and the capacity a locker consumes depends on its MDH (<<KLEE-length-rule>>).
Insufficient capacity may prevent a configuration instruction from executing; unconfiguring other lockers frees it.

Corruption of a hart's KLF is unrecoverable: the hart's KLEE architectural state is reset (<<KLEE-reset-and-m-mode-only>>), and a KLEE fatal-error exception (<<Zkl-ISA-priv.adoc#KLEE-exceptions>>) is raised.

The KLEE unit holds three 128-bit _authentication registers_, with the authentication and identification data of the locker under management: `SIV`, `IMPQUAL` and `SIV2`. `kl.load`, `kl.store`, `kl.mvin` and `kl.mvout` access them as the leading bytes of the image they transfer (<<KLEE-instruction-mv>>).
The `kl.mgmt` that opens an export of a locker in a Valid State writes `SIV` and, when _AuxDataLen_ {ge} 2, `IMPQUAL` and `SIV2`. A `kl.mgmt` that opens an import, other than the short import of a locker in an Error State (<<KLEE-error-state-transfer>>), zeroizes them, and the `kl.load` or `kl.mvin` that follows writes them, so that no value of an earlier management operation can be read back through the import image.

[NOTE]
====
The 128 or 384 bits of `SIV`, `IMPQUAL` and `SIV2` are allocated per hart, not per locker, to reduce hardware cost.
This restricts, and imposes software discipline on, running multiple management operations:
a second operation may overwrite the in-flight `SIV`, `IMPQUAL` and `SIV2` of the first.
<<KLEE-CSR-klmanagedlocker>>, <<KLEE-managed-locker-rules>> and <<KLEE-SR-management>> explain how software should manage management operations.
====

== Providing Inputs and Outputs

[[KLEE-KLV]]
=== RVV/KLV

KLEE takes its inputs and outputs from vector registers, from an architectural input/output buffer (KLIOBUF) loaded from and stored to memory, or from both.

(((KLV)))Vector registers do not require the full V extension, only a minimal subset, _KLV_ (KLEE-subset of V).
KLV must be fully opcode-compatible with RVV: code written for KLV behaves identically under V with `Zvbc`.
KLV comprises:

* vector registers of at least 128 bits;
* the configuration-setting instructions `vsetvli`, `vsetivli` and `vsetvl`, with:
** tail-agnostic and mask-agnostic configurations only, since KLEE neither uses vector masking nor defines masked instructions, and always applies a tail-agnostic policy (bit 25 of the `kl.exec` encoding is reserved for masked operations, should a compelling use case arise);
** `SEW` values 8, 16, 32 and 64, with `ELEN` = 64;
** `LMUL` values 1, 2, 4 and 8; and
** for a configuration that KLV does not support, `vtype.vill` is set and `vl` = 0, as in RVV, and a KLEE instruction with a vector operand issued while `vtype.vill` is set raises an illegal-instruction exception;
* unit-stride vector loads and stores of element widths 8, 16, 32 and 64;
* `vmv.x.s`, `vmv.s.x`, and the slides `vslideup.v[xi]`, `vslidedown.v[xi]`, `vslide1up.vx` and `vslide1down.vx`, to move data into and out of vector registers;
* the logical operations `vand.v[vxi]`, `vor.v[vxi]` and `vxor.v[vxi]` (the immediate forms give, for instance, a bitwise NOT); and
* `vclmul.v[vx]` and `vclmulh.v[vx]` of `Zvbc`, which may be trap-and-emulated.

Floating-point, fixed-point and general arithmetic vector operations are not required.

NOTE: KLEE has no concept of element, and logically does not operate in the vector unit: it sees a vector register (group) as a bit string of length `KLLEN` = `VL` * `SEW`, where `VL` is the vector length in effect (`vl`).

KLEE takes the length of a vector operand from `VL*SEW` alone (`VL` = 2 with `SEW` = 64 and `VL` = 4 with `SEW` = 32, for example, both give 128 bits): the CPU decode side uses `VL` and `SEW` to determine how much data to send to the KLEE unit, which needs only their product.

=== KLIOBUF

The KLIOBUF is an optional architectural input/output buffer that may replace vector registers; it is not part of the KLF.

`kl.input` and `kl.output` transfer data between the KLIOBUF and memory, and `kl.exec`, `kl.setst` and `kl.mgmt` then use Forms whose inputs and outputs are implicitly in the KLIOBUF (<<KLEE-usage-input-output>>).
<<KLEE-CSR-kliobuftop>> defines `KLLEN` for KLIOBUF operands.

[[KLEE-Metadata]]
== Metadata

A CC carries two kinds of metadata:

. the 128-bit _MDH_, always present, which determines the Machine, the key type and the key's usage policies; its first 64 bits determine the length of a PI or SCC; and
. the optional 128-bit _Implementation Qualifier_ `IMPQUAL`, which copies the three KLEE analogues of the hart's `mvendorid`, `marchid` and `mimpid` CSRs (<<KLEE-CSR-impl-ids>>).
It is present when an SCC has _AuxDataLen_ {ge} 2, and tells an implementation whether it can use the implementation-specific content of the SCC (<<KLEE-Auxiliary-Data-Section>>).

<<KLEE-metadata-header>> summarizes the MDH fields, which the following subsections describe.

[[KLEE-Machine-field]]
=== _Machine_ and _MachinePolicy_ Fields

_Machine_ is a 12-bit field. Values 0–3071 are architecture-defined, with encodings maintained by RVI (<<Zkl-ISA-machines.adoc#KLEE-Machines>>); the remaining values are for custom Machines.

The meaning of _MachinePolicy_ depends on the Machine:

* For encryption/decryption primitives and modes, bit 0 of _MachinePolicy_ permits encryption and bit 1 decryption. At least one bit must be set.
* For asymmetric primitives that support signatures, bit 0 permits signature generation and bit 1 verification. For a Machine with other operations as well, a zero field leaves those operations available.
* For other primitives, _MachinePolicy_ may encode further Machine identifiers, extending the encoding space of _Machine_.

For a Machine that only signs and verifies, a zero _MachinePolicy_ disables all the locker's operations but is not invalid.
Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-policy-gate>> states how _MachinePolicy_ gates the States of a Machine.

[[KLEE-SCProtection-field]]
=== _SCProtection_ Field

KLEE defines three side-channel protection levels, Levels A, B and C, encoded in _SCProtection_ as the values 0, 1 and 2.
Value 3 is reserved, and makes the Metadata invalid (<<KLEE-Metadata-validity>>).
cite:[riscvPlatformSecurityModel] defines the security concepts and requirements.

[[KLEE-SC-protection-levels]]
.Encoding of Side-Channel Protection levels
[float="center",align="center",cols="^7%,^7%,<86%",options="header"]
|===
| Value  | Level | Description
|   0    | A     | No timing leakage: the same cryptographic operation on the same number of input units takes the same time in the KLEE unit, whatever the input data.
|   1    | B     | No timing leakage; differential side-channel protection.
|   2    | C     | No timing leakage; side-channel protection;
detection of injected faults, followed either by completion with the correct result and no other physical leakage, or by
a transition to a fatal error condition (see <<KLEE-error-architecture>>).
|===

An implementation documents, for each level it supports, the standard, security level and test metrics it meets; Level B, resp. C, must offer at least the guarantees documented for Level A, resp. B.

NOTE: This specification gives no precise definitions or profiles for these values.
Implementations will likely be expected to follow ISO/IEC 19790:2025 cite:[ISOIEC-19790-2025], Clauses 7.8.2–7.8.4 and Annex F, that is, ISO/IEC 17825:2024 cite:[ISOIEC-17825-2024], Clause 7.3.4, tested and documented per ISO/IEC 24759:2025 cite:[ISOIEC-24759-2025], Clauses 6.7 and 6.8.1–6.8.3, or equivalently FIPS 140-3 cite:[nist-fips-140-3], which adopts ISO/IEC 19790:2012 and ISO/IEC 24759:2017, with the CMVP metrics of NIST SP 800-140F cite:[nist-SP-800-140F].
A CC provider that sends its keys to a secure receiver, such as a TEE applet that forwards the CC to the software consuming it, negotiates the protection level with it by a system-specific mechanism, including the choice between FIPS 140-3 security levels 1–3 (resisting about one day of analysis) and 4 (several days).

[[KLEE-KeyType-field]]
=== _KeyType_ Field

_KeyType_ is 0 if the key is provisioned by value; it is then also exported and imported by value.
_KeyType_ is 1 if the key is identified by a system-specific, 64-bit System Key Identifier (SKID) (<<KLEE-system-keys>>).
The all-ones SKID (`ones(64)`) is the exception: the key material is generated randomly when provisioning completes, all keys of the Machine at once unless otherwise specified, and _KeyType_ is then set to 0, so the key is thereafter exported by value. If the RBG fails, Rule <<KLEE-GR-rbg-failure>> applies.

Values 2 and 3 are reserved: a PI or SCC that carries one of them is invalid Metadata (<<KLEE-Metadata-validity>>).

NOTE: A SKID may refer to keys with unrelated purposes on different devices;
the _System Key Store_ (SKS) supplies an appropriate _Locality_ (<<KLEE-Localities>>) during provisioning, to bind the key to the system (<<KLEE-system-keys>>).

[[KLEE-State-field]]
=== _State_ and _StateExtension_ Fields

_State_ tracks the state of a locker and its Machine: _Unconfigured_, encrypting or decrypting, initializing, absorbing into or finalizing a hash, computing point multiples, signing or verifying, or in an error state, for instance.
_StateExtension_ lets a Machine keep further state information, usually orthogonal to _State_, such as whether certain values have been provisioned or computed.

State 0 is _Unconfigured_: every other field of the MDH then reads zero and has no meaning, and the locker has no Usage Policy, Expiration Date or Key Type.

States 1–55 are the _Complete_ States: the _Valid_ States 1–47, State 1 being _Ready_, and
(((KLEE, Machine, error states)))

[[KLEE-Auxiliary-Data-Section]]
=== _AuxDataLen_ and _ADSDropped_ Fields

_AuxDataLen_ gives the length, in 128-bit blocks, of the _Auxiliary Data Section_ (ADS), the variable-size, implementation-specific part of the content; with _ADSDropped_ = 1, it keeps the length before `Content2` was dropped.
Zero means no ADS; the maximum, 2^14^-1, is 262,128 bytes.

If _AuxDataLen_ {ge} 2, the SCC includes a copy of the implementation qualifier of the originating implementation (<<KLEE-CSR-impl-ids>>),

``{fournbsp}{fournbsp}IMPQUAL := zeros(32) @ klmimpid @ klmarchid @ klmvendorid``,

which the importing implementation uses to decide whether it can use the ADS.
_AuxDataLen_ counts these 16 bytes and the 16-byte authentication tag of the ADS, so its minimum is 2, and 1 is invalid.

_ADSDropped_, bit 47 of the MDH, is an unauthenticated format hint, ignored when _AuxDataLen_ = 0; first-segment authentication clears it only in its local copy of the MDH.
With _AuxDataLen_ {ge} 2 and _ADSDropped_ = 1, `Content2` is absent, and `IMPQUAL` and `SIV2` remain as non-authoritative padding that keeps the offset of `Content1` unchanged.
Setting _ADSDropped_ drops the optional `Content2`; clearing it requests second-segment processing, whose failure drops `Content2` without rejecting the authenticated `Content1` (<<KLEE-SCC-import>>).
Toggling it therefore cannot affect `Content1` or any policy, make an unauthenticated `Content2` usable, or bypass first-segment authentication; dropping `Content2` can at most make an interrupted long-running operation restart (Rule <<KLEE-GR-long-running-progress>>).

// The format of the ADS is described in <<KLEE-data-formats>>.

[[KLEE-UsagePolicy]]
=== _UsagePolicy_ Field

_UsagePolicy_ determines which modes may use the locker.
A _usage instruction_ uses the Machine in a locker to operate on the locker's internal state, or to expose it, as a `kl.exec` that produces output does; Usage Control applies only to these instructions, listed in <<KLEE-instruction-properties>>.
Bits 0–3, when set, disallow usage in U-mode (VU-mode included), VS-mode, S-mode (HS-mode with the H extension) and M-mode, respectively; bit 4, when set, grants usage in Debug mode.
`mstatus.MPRV` is not considered, and the bit of a mode that is unsupported or not enabled is ignored.

[[KLEE-Localities]]
=== _Locality_ Field

_Locality_ names 128-bit Locality Secrets (LSs), listed in <<KLEE-locality-indexes>> and stored in a possibly virtual Locality Secrets Table (LST).
Some entries are fixed, or configurable only by an implementation-specific, authenticated hardware process, and shared by all KLEE units of an SoC; the others are software-programmable, per-hart architectural state.

At SCC export and import, the Localities named in _Locality_ cryptographically bind the SCC to the _current_ hardware and software environments.
The binding ends at import: if a Locality Secret changes later, the next export binds its SCC to the new value.
Software must prevent unauthorized parties from accessing the lockers directly (Rule <<KLEE-SR-clear-before-lower-mode>>).

Eleven LST entries are architected: entries 0–5 form the _HW Binding Group_, which binds SCCs to the hardware; entries 6–7 the _Boot Session Group_; and entries 8–10 the _SW Filter Group_.

[[KLEE-Metadata-expiration-date]]
=== _ExpirationDate_ Field

_ExpirationDate_ is in effect only with `Zklexpire`, which requires the KLEE implementation to access a secure clock.
Without `Zklexpire`, a non-zero _ExpirationDate_ in a PI or SCC is invalid Metadata (<<KLEE-Metadata-validity>>).

A non-zero 20-bit _ExpirationDate_ gives the expiration time of the CC in whole hours since 00:00 UTC, 1 January 2027, a span of about 119 years and 7 months. The epoch is in UTC, so a CC exported on one device and imported on another expires at the same instant, whatever their local times.

[NOTE]
====
This specification cannot set requirements on a secure clock, as what is adequate depends on threat models, platforms and integration.
As a rule of thumb, *a clock adequate for M-mode security features or an on-SoC TPM is adequate for KLEE*.
Software below M-mode, however, must not be able to set the clock.
====

_ExpirationDate_ is evaluated only:

* at the issue of any usage instruction, for `kl.derive` at both endpoints; and
* at every architectural resumption point of a usage instruction.

The _ExpirationDate_ of a locker that is not in a Valid State is not evaluated: only an expired locker in active use transitions to Error State `kl_state_expired`, and expired contexts can still be managed cleanly.

The evaluation proceeds as follows:

. If _ExpirationDate_ is zero, the instruction proceeds.
. If the secure clock cannot be read, the instruction raises a KLEE clock-unavailable exception (<<Zkl-ISA-priv.adoc#KLEE-exception-codes>>) and leaves the _State_ unchanged.
. The secure clock's date is converted to the _ExpirationDate_ format; a reading earlier than 00:00 UTC, 1 January 2027, converts to 0, and one at or after 2^20^ − 1 hours converts to 2^20^ − 1.
. If the converted value is at least _ExpirationDate_, the locker transitions to Error State `kl_state_expired`; otherwise the instruction proceeds.

An unreadable secure clock traps, rather than making the instruction a silent no-op, so that M-mode can handle the failure, which may also be induced by glitching the clock.
The instruction keeps the _State_, so that a handler that restores the clock can re-execute it; otherwise Rule <<KLEE-SR-handler-duty>> applies, with _Expired_ as the Error State.

[[KLEE-MachineUse]]
=== _MachineUse_ and _AuxInfo_ Fields

A Machine may use _MachineUse_ and _AuxInfo_ to store additional information.

An implementation may use a field, or a subfield, that its Machine does not use. It then includes an ADS (<<KLEE-Auxiliary-Data-Section>>) in every SCC it exports with such a value: _AuxDataLen_ {ge} 2, and exactly 2 when `Content2` is empty.
The importing implementation thus checks `IMPQUAL`, and recognizes a value that only the originating implementation can interpret.
Neither field may hold any value from which key material or plaintext can be derived, since the MDH is not confidential.

The validity conditions of <<KLEE-Metadata-validity>> do not check these fields, not even in a PI: a wrong value causes an error of the Machine that uses it, and a Machine specification may declare a value unsupported Metadata where the implementation does not implement it.
The _MachineUse_ of a PI is ignored and zeroed upon provisioning (<<KLEE-Metadata-validity>>). Otherwise, the rules of the Machine decide what happens to _AuxInfo_ upon provisioning, and to both fields on entering State _Ready_.
A Machine may use these fields to pass initialization parameters at provisioning: ML-DSA (<<Zkl-ISA-machines.adoc#KLEE-PQC-ML-DSA>>), for instance, records its pre-hash function in _AuxInfo_.

// ////////////////////////////////////////////////////////////////////

[[KLEE-Machine-version]]
=== _Version_ Field

_Version_ gives the version of the MDH format:

* 0: the current format;
* 1: newer revisions of the format, whose further version information is encoded in other MDH fields;
* 2: reserved; and
* 3: a system-specific format.

A PI or SCC with a _Version_ that the implementation does not support is invalid Metadata (<<KLEE-Metadata-validity>>).

System-specific formats are optional and allowed only for import.
The import opens with a KLEE-format MDH whose _Version_ is 3, and whose policies apply as in any other import.
The format may carry further policies, which apply in addition to those of the declared MDH, never in their place: at completion, the MDH of the locker is the declared MDH narrowed by the policies the format carries (<<KLEE-Metadata-narrowing>>), with _Version_ set to 0 (or 1 in a future version of this specification); if the narrowing fails, the locker transitions to Error State _Privilege Violation_.
How a format encodes its policies, and how the implementation converts them into KLEE policies, is implementation-defined; the converted policies are never weaker than those the format carries.
The format of the data that follows the KLEE-format MDH defines whether, and how, that input data is protected: this specification does not require a system-specific format to be encrypted or authenticated, since some systems import encrypted keys without authenticating them.

Lockers provisioned with a system-specific format can be exported only in the KLEE format, as SCCs.
An implementation may support several system-specific formats and distinguishes them in an implementation-defined way.

KLEE deliberately defines no system-specific export.
To prevent loading on other implementations, specific Localities may be set, or all information may be kept in the ADS, gated by `IMPQUAL`.

[[KLEE-Metadata-validity]]
=== Validity of Metadata

Software keeps all _reserved_ bits, and all bits that the Machine does not use, zero. A non-zero value is handled as follows:

* in a Reserved bit, it makes the Metadata invalid (see below);
* in _MachinePolicy_ or _MachineExtension_, a value that the implementation does not implement for the Machine makes it unsupported;
* the _StateExtension_ and _MachineUse_ of a PI are ignored, and zeroed upon provisioning (<<KLEE-locker-management>>);
* outside a PI, a _State_ {vvert} _StateExtension_ value that the Machine does not support makes it invalid (see below); and
* otherwise, _MachineUse_ and _AuxInfo_ are not checked by the conditions below, but by the rules of the Machine and by their use in the implementation (<<KLEE-MachineUse>>).

Metadata is _unsupported_ when the combination of _Machine_, _MachinePolicy_, _MachineExtension_ and an _SCProtection_ value of 0 to 2 (Levels A to C) is not implemented; when _KeyType_ is 1 and the implementation does not support System Key Identifiers, including the all-ones SKID, for the Machine (<<KLEE-KeyType-field>>, <<KLEE-system-keys>>); or when it holds a value that a Machine specification declares unsupported if not implemented, such as the _AuxInfo_ of ML-DSA (<<Zkl-ISA-machines.adoc#KLEE-PQC-ML-DSA>>) or of EdDSA (<<Zkl-ISA-machines.adoc#KLEE-EdDSA>>). A _MachinePolicy_ that the conditions below reject makes it invalid, not unsupported.

A supplied MDH is _invalid_ when any of the following holds:

* _Version_ is unsupported;
* _KeyType_ is 1 for a Machine whose Provisioning Input has no key field, for instance the unkeyed hash functions and XOFs, the ECC, ML-KEM and ML-DSA Machines, and the NIK variants of HMAC;
* _KeyType_ is 2 or 3;
* _SCProtection_ is 3, a reserved value (<<KLEE-SCProtection-field>>);
* _Locality_[5:4] is 3, or _Locality_ names an unconfigured Locality Secret without a configured substitute (<<KLEE-Localities>>);
* the MDH carries a custom _Machine_ or a system-specific _Version_ without naming _ChipFamScrt_ or _ChipScrt_ in _Locality_ (Rule <<KLEE-GR-custom-locality>>);
* _State_ is not _Unconfigured_ at provisioning;
* _State_ is _Unconfigured_ or 61–63 at import (<<KLEE-State-management>>);
* _State_ is 54 or 55, or _State_ {vvert} _StateExtension_ is a value that the Machine does not support; for this condition, every Machine supports the Configuration States 56–60 with any _StateExtension_, and the _StateExtension_ in a PI is ignored and zeroed upon provisioning;
* _State_ is _Expired_ in a PI, SCC or PCCC when `Zklexpire` is not implemented;
* _ExpirationDate_ is non-zero and `Zklexpire` is not implemented;
* _AuxDataLen_ = 1;
* _AuxDataLen_ or _ADSDropped_ is non-zero in a PI, or in a PCCC with base type `pi` (<<KLEE-nested-mgmt>>);
* _MachinePolicy_ is zero for a Machine that requires at least one set bit in it; or
* a Reserved bit is non-zero.

[[KLEE-Metadata-narrowing]]
=== Narrowing of Metadata

Several operations narrow the policies of a CC by those of another source, all in the same way: the resolution of a SKID (<<KLEE-system-keys>>),
a restricted `kl.derive` (Rule <<KLEE-GR-narrowing>>), the import of a system-specific format (<<KLEE-Machine-version>>),
and `kl.restrict*`, at the request of software (<<KLEE-instruction-restrict>>).

The _narrowing_ of an MDH _A_ by the policies of a source _B_ (an MDH, the
policies that the SKS associates with a key, or those that a system-specific format carries) is _A_ with the following
fields replaced; a policy field that _B_ does not carry leaves that field of _A_ unchanged, and no other field changes:

* _UsagePolicy_: bits 0–3 become the OR of both, and bit 4 the AND of both, so that the modes that may use the CC are those that both allow.
* _Locality_ (<<KLEE-locality-indexes>>): each HW Binding subfield (bits [1:0] and [3:2]) takes the larger value, that is the stricter entry of its chain, zero meaning no binding; the Boot Session subfield (bits [5:4]) takes the non-zero value if only one is non-zero; and bits 6–8 are OR-ed.
* _ExpirationDate_, with `Zklexpire`: the smaller non-zero value, or 0 if both are 0.

If both Boot Session subfields are non-zero and differ, or if the resulting _Locality_ names an unconfigured entry without a configured substitute (<<KLEE-Localities>>), the policies cannot be met, and the narrowing _fails_; each operation that narrows states the outcome.
Narrowing changes neither _SCProtection_ nor _MachinePolicy_; only `kl.restrictl` and `kl.restrictv` narrow _MachinePolicy_, under Rule <<KLEE-GR-policy-narrowing-state>>.

=== klmvendorid, klmarchid, and klmimpid

{empty}
(((CSR, `klmvendorid`)))(((CSR, `klmarchid`)))(((CSR, `klmimpid`)))`klmvendorid`, `klmarchid` and `klmimpid` identify the version of the KLEE unit, as `mvendorid`, `marchid` and `mimpid` do for the hart.

. Their values out of KLEE unit reset identify the KLEE unit.
They are read-only in every mode other than M-mode, HS-mode included.
M-mode may write them only to present an emulated KLEE unit to lower privilege modes; `IMPQUAL` (<<KLEE-Auxiliary-Data-Section>>) then reports the written values.

. `klmvendorid` is a 32-bit register holding the JEDEC manufacturer ID of the KLEE unit provider, or 0 if non-commercial, in the JEDEC bank/offset encoding of `mvendorid` in the Privileged ISA.
//(<<machine.adoc#norm:mvendorid_enc>>).

. `klmarchid` is a 32-bit register encoding the base microarchitecture of the KLEE unit, as `marchid` does in the Privileged ISA.
RVI allocates non-commercial IDs globally, as for `marchid`; commercial IDs are specific to the `klmvendorid`.
//(<<machine.adoc#norm:marchid_sz_acc_op>>).

. `klmimpid` is a 32-bit register that uniquely encodes the version of the KLEE unit implementation, as `mimpid` does for the hart in the Privileged ISA; it reads 0 if not implemented, which an implementation that produces an ADS must not do.
Its value reflects the design of the KLEE unit itself, not of the surrounding system.
//(<<machine.adoc#norm:mimpid_op>>).

Together, these three CSRs form the _Implementation Qualifier_ (<<KLEE-Auxiliary-Data-Section>>).

[[KLEE-CSR-klmaxiobuflen]]
=== klmaxiobuflen

(((CSR, `klmaxiobuflen`)))`klmaxiobuflen` is an XLEN-bit CSR that reports the maximum configurable length of the KLIOBUF, in bytes.
It is writable in the same modes and for the same purpose as the CSRs of <<KLEE-CSR-impl-ids>>; its hardwired value out of KLEE unit reset is its maximum.
M-mode should write it only while the KLEE unit is in its state out of reset (<<KLEE-out-of-reset-unpriv>>), before any write to `kliobuflen`, and should never reduce it below the current `kliobuflen`: after a write that does, `kliobuflen` and `kliobuftop` become 0 and the KLIOBUF is zeroed, as after a write of 0 to `kliobuflen`, and no other state is affected.

With `Zklio`, `klmaxiobuflen` must be at least 16 bytes and at least the largest basic processing unit (granularity) of any implemented Machine.
Without `Zklio`, the KLIOBUF does not exist, `klmaxiobuflen` reads as zero, and `kliobuflen` and `kliobuftop` are not present.

// ////////////////////////////////////////////////////////////////////

[[KLEE-CSR-kliobuflen]]
=== kliobuflen

(((CSR, `kliobuflen`)))`kliobuflen` is an XLEN-bit URW CSR that programs the length of the KLIOBUF, in bytes, for `kl.input` and `kl.output`; its maximum is `klmaxiobuflen`.
Every write, even of the current value, zeroes the buffer up to the new value of `kliobuflen`, and sets `kliobuftop` to the same length.

A zero `kliobuflen` leaves the KLIOBUF _unconfigured_: an operation that expects an input or an output in it raises an unconfigured-KLIOBUF exception.

Rule <<KLEE-SR-kliobuflen-zero>> recommends writing 0 once the contents are no longer needed.

// ////////////////////////////////////////////////////////////////////

[[KLEE-CSR-kliobuftop]]
=== kliobuftop

(((CSR, `kliobuftop`)))`kliobuftop` is an XLEN-bit URW CSR that sets the upper bound, in bytes, of the buffer range that `kl.input` and `kl.output` use; its maximum is `kliobuflen`.
It is the KLIOBUF counterpart of `VL` in the V extension: it defines the operand length `KLLEN` as `kliobuftop` {times} 8 and the transfer window [0, `kliobuftop`-1].

Writing `kliobuftop` leaves the buffer unchanged, so software can set the length per operation without writing `kliobuflen`, which clears the buffer; this mirrors the use of `VL*SEW` to supply a partial last block, or a short IV or nonce, to a Machine.

A value invalid for a Machine is detected only when an instruction that uses the KLIOBUF is later issued or restarted, with the outcomes given in <<KLEE-usage-input-output>>.

// ////////////////////////////////////////////////////////////////////

[[KLEE-CSR-klstart]]
=== klstart

(((CSR, `klstart`)))`klstart` is an XLEN-bit RW CSR that records, in bytes, the progress of the instructions that _honor_ it:

* `kl.load`, `kl.store`, `kl.input` and `kl.output`: the bytes read or written;
* `kl.exec` on a multi-block operand, which may be interrupted between blocks: the bytes processed;
* `kl.derive`, whose `kl.exec` endpoints advance the source and destination lockers in the same way; and
* `kl.mvin` and `kl.mvout`, vector or not: the locker transfer point.
A vector variant with a multi-block operand also tracks the corresponding position in the vector register in `vstart`.

Every other instruction leaves `klstart` unchanged, except `kl.clearall`, and `kl.mgmt` after its check of `klmanagedlocker` (<<KLEE-locker-management>>), which clear it.

KLEE has no intrinsic element length and no counterpart of the Element Group Width (EGW), Effective Element Width (EEW) or Element Group Size (EGS) of the vector crypto extension; its instructions, such as `kl.exec`, are architecturally decoupled from the operations the KLEE unit performs for them.
Hence `klstart` is a byte count; Machines or their implementations record progress that is not byte-structured, such as that of the point multiplications and signature operations of <<Zkl-ISA-machines.adoc#KLEE-ECC>> and <<Zkl-ISA-machines.adoc#KLEE-PQC>>, in _MachineUse_ (Rule <<KLEE-GR-long-running-progress>>).

Like `vstart` in the V extension, `klstart` is the position within the transfer window at which processing starts or resumes; for a KLIOBUF operand the window is [0, `kliobuftop`-1] (<<KLEE-CSR-kliobuftop>>).
The KLEE implementation writes it:

. on a precise exception, with a prefix-complete point of the transfer (stated precisely in <<KLEE-rule-memory-instruction-decomposed>>): the point of progress, or 0 for an interrupt in an implementation that selects the restart option of Rule <<KLEE-GR-resumability-options>> for `kl.load`, `kl.store`, `kl.input` and `kl.output`, within the bound of option 5 of Rule <<KLEE-GR-resumability-options>>, which then transfer the prefix again when re-executed; and
. with 0 when an instruction that honors `klstart` retires, except `kl.mvin` and `kl.mvout`, which advance `klstart` by the bytes transferred and keep it across instructions to support piecewise transfers (<<KLEE-instruction-mv>>); their vector variants track their progress within the vector register in `vstart`, whose value depends on the chosen element size.

Issuing Form A, B or C of `kl.exec` with `klstart` {ne} `vstart` {times} `SEW` / 8 raises an illegal-instruction exception.

The transfer window is `kliobuftop` bytes long for a KLIOBUF operand (with `kliobuflen` non-zero) and `VL` {times} `SEW` / 8 bytes long for a vector operand.
The following checks are made in order, after those of <<KLEE-GR-gate-order>> (including the Error State and expiration checks) and those that make the instruction illegal in the locker's _State_ (Rules <<KLEE-GR-no-exec-in-ready>> and <<Zkl-ISA-machines.adoc#KLEE-MGR-not-allowed-instructions>>).
They do not apply to `kl.mvin` and `kl.mvout`, whose vector window is [`vstart`, `vl`-1] in elements and whose `klstart` is a locker offset.
Nor do they apply to a `kl.exec` whose native Form in its Machine and State is Form D, or to Form A `kl.setst`, which leave `klstart` unchanged, or to `kl.mgmt`, which clears it in every Form (<<KLEE-locker-management>>).
A Form D `kl.exec` that substitutes for Form A, B or C (<<KLEE-usage-input-output>>) makes these checks on its KLIOBUF transfer window.

. If the length of the transfer window is invalid for the Machine, the locker transitions to Error State _Invalid_.
. If `klstart` {ge} the length of the transfer window, the window is empty: `klstart` is not checked, and the instruction only writes 0 to `klstart`.
  A window of length 0 that is valid for the Machine (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-granularity>>) is also empty: the instruction does not reach the Machine, so it does not count as the `kl.exec` that a State admits (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-single-last-block>>), just as a vector instruction with `vl` = 0 updates no element.
  There is no need to issue a `kl.exec` to feed an empty input to a Machine (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-single-last-block>>).
. Otherwise, a `klstart` that is not an interruption point of the instruction transitions the locker to Error State _Invalid_, and the unwritten part of the output window is zeroed (Rule <<KLEE-GR-usage-locker-error-state>>).
  This prevents, for instance, using a locker in an inconsistent state and releasing plaintext in place of ciphertext.

An _interruption point_ of a KLEE instruction in a given State of a Machine is a `klstart` value that the instruction can itself produce on a precise halt in that State: unless the Machine states a coarser or different set, the whole multiples of the Machine's granularity within the transfer window.
Procedure `process_VLI` (<<Zkl-ISA-machines.adoc#KLEE-process-VLI>>) defines its own: 0, and any multiple of its granularity at which the locker's `block_base` is 0, as it is after every halt of its inner loop.

For the locker-directed transfers `kl.load`, `kl.store`, `kl.mvin` and `kl.mvout`, `klstart` is bounded above by the length in bytes of the <<KLEE-serialized-image,serialized image>> `S`, determined from the first 8 bytes of the MDH; each of these instructions states the bound it applies.

<<KLEE-interposed-software,Interposed software>> follows Rules <<KLEE-SR-klstart-save>> to <<KLEE-SR-klstart-restore>>, and all software follows Rule <<KLEE-SR-klstart-no-reset>> (<<KLEE-klstart-software-check>>).

[[KLEE-CSR-klmanagedlocker]]
=== klmanagedlocker

(((CSR, `klmanagedlocker`)))`klmanagedlocker` is an XLEN-bit RW CSR; only 6 of its bits are currently used.
It holds the number of the locker most recently placed under management, the value surviving certain error conditions to allow for error recovery, or 32 if none, such as after a management operation has been completed without errors.
Values 33 and above are reserved; writing one leaves `klmanagedlocker` unchanged.
While the locker it names is in a Configuration State, that locker is under management and owns the internal values `SIV`, `SIV2` and `IMPQUAL`.

Rule <<KLEE-GR-klmanagedlocker-updates>> lists the events that change `klmanagedlocker`.
Rules <<KLEE-GR-locker-less-transfers>> to <<KLEE-GR-mgmt-klmanagedlocker-check>> state how instructions use it.

Software that uses `klmanagedlocker` follows Rules <<KLEE-SR-klmanagedlocker-write>> to <<KLEE-SR-no-interleaving>> (<<KLEE-SR-management>>).

[[KLEE-instructions-detailed]]
== Instructions

_This section specifies only the semantics and encodings of the unprivileged KLEE instructions, not their behavior in the various States of the Machines, how they respect usage policies, how they use randomness, how they access memory, or whether they are interruptible.
The rules governing these aspects are grouped in <<KLEE-ISA-rules>>._

When describing an instruction's behavior requires a rule, the instruction's description states that behavior explicitly, with a reference to the rule.

[[KLEE-no-operation]]No Operation:::
(((no operation)))
An instruction that *performs no operation* performs none of the operations of the KLEE unit, such as cryptographic operations, but may still have the effects that its description or a rule states, such as writing zeros to its output, writing 0 to `klstart`, setting `klmanagedlocker`, or raising an exception.

[[KLEE-general-rules-instructions]]
=== General Rules Governing Encoding and Arguments

In every encoding, fields shown with fixed values must hold them.
Any other value of such a field, and any unlisted combination of field values, is a reserved encoding and raises an illegal-instruction exception (first group of <<KLEE-illegal-instruction-grounds>>).

`%offset` denotes the instruction's sign-extended 12-bit immediate: bits [31:20] for `kl.load` and `kl.input` (I-type), and bits [31:25] @ [11:7] for `kl.store` and `kl.output` (S-type).
The base register is always in bits [19:15] (`rs1`), and the effective address of a transfer is `X[rs1] + sext(%offset)`.
This is the address of the *first* byte of the transfer, even for a multi-byte or resumed transfer; a resumed transfer restarts at that address plus `klstart` bytes.
Each instruction gives the correspondence between addresses and transfer offsets.

The following rules apply to all KLEE instructions, unless stated otherwise.

[horizontal]
[[KLEE-GR-multiple-GPRs,GR1]]GR1:: _Use of multiple GPRs for longer inputs:_ A 64-bit operand is one GPR on RV64 and the pair `(X[s+1],X[s])`, as `X[s+1] @ X[s]`, on RV32.
A 128-bit operand is the pair `X[s+1] @ X[s]` on RV64 and the quartet `X[s+3] @ X[s+2] @ X[s+1] @ X[s]` on RV32.
This holds for sources and destinations alike.
The lowest register number of a pair must be even, and that of a quartet a multiple of four; otherwise an illegal-instruction exception is raised.
A pair or quartet is read or written as a whole.
Here and in every instruction description, RV32 and RV64 denote an XLEN of 32, resp. 64, in the privilege mode executing the instruction.

[[KLEE-GR-x0-operand,GR2]]GR2:: If `X0` is used as a destination or source register, writes to it are discarded, and it reads as zero.
When the lowest register of a pair or quartet is `X0`, no register of the group is written, and the group reads as zero.

[[KLEE-GR-GPR-indirect,GR3]]GR3:: The encoding fields 'r' and 'R' are reserved for `Zklind`; <<KLEE-indirect-lockers>> describes their function.
If `Zklind` is not available, these fields must be zero and a non-zero value raises an illegal-instruction exception, except `r` = 1 with `X0` in the locker register field, which encodes `KLML` where Rule <<KLEE-GR-klmanagedlocker-override>> allows it.

[[KLEE-GR-vector-MDH-operand,GR4]]GR4:: Where a KLEE instruction carries the whole 128-bit MDH in a vector register or group, such as the MDH-formatted operand of `kl.restrictv` and the destination of `kl.getmdv`, the operand must satisfy `VL` {times} `SEW` {ge} 128; otherwise an illegal-instruction exception is raised.
<<KLEE-extensions-overview-unpriv>> lists the vector extensions that provide such a register.
The same requirement applies to an MDH taken from the KLIOBUF: `kliobuftop` {ge} 16.
`kl.mgmt` reads its MDH only where its operation needs one, which depends on the locker's _State_ (Rule <<KLEE-GR-cleared-under-management>>), so for `kl.mgmt` this check is a ground of the second group (<<KLEE-illegal-instruction-grounds>>), made after the `klmanagedlocker` check and before any change to the locker.

[[KLEE-GR-vector-legality,GR5]]GR5:: A vector register (group) operand whose register number is not a multiple of the LMUL in effect is a reserved encoding and raises an illegal-instruction exception, as in RVV 1.0.
Every KLEE instruction with a vector operand sets `vstart` to 0 when it retires, and on a precise halt sets it as <<KLEE-CSR-klstart>> and Rule <<KLEE-GR-klstart-vstart>> prescribe.
An instruction with a vector operand that produces no `vstart` value (`kl.getmdv`, `kl.restrictv`, Form C of `kl.size` and `kl.avail`, `kl.setst` and `kl.mgmt`) raises an illegal-instruction exception if issued with `vstart` {ne} 0, as RVV 1.0 {sect}3.7 permits for a `vstart` value that the instruction can never produce.

[[KLEE-GR-klstart-vstart,GR6]]GR6:: KLEE instructions with vector operands that use `klstart` for resumption update `klstart` and `vstart` simultaneously and independently, each by its own semantics, and neither is derived from the other; except for `kl.mvin` and `kl.mvout`, both denote the same point of progress, `klstart` in bytes and `vstart` in elements of the width in effect.
Each unit thus keeps its own information, and the two values can still be explicitly "`desynced`", as in locker management operations.
+
NOTE: For Forms A–C of `kl.exec`, an illegal-instruction exception is raised if `klstart` and `vstart` denote different points (<<KLEE-CSR-klstart>>).
`kl.mvin` and `kl.mvout` keep the two independent by design: their `klstart` is a locker offset that accumulates across instructions, while `vstart` tracks the vector register.
+
NOTE: The uninterruptible vector-form instructions listed in Rule <<KLEE-GR-vector-legality>> produce no `vstart` value and therefore consume none.

[[KLEE-management-operations]]
=== Provisioning, Import, and Export

_This section is informative and non-normative. It serves to place the management operations in their context._

Setting aside the handling of lockers in an Error State, a *management* operation takes three steps: the first and the last are a single KLEE instruction each, and the second is one or more `kl.mvin` or `kl.mvout` (alternatively, `kl.load` or `kl.store`) instructions:

. `kl.mgmt` (<<KLEE-instruction-mgmt>>) prepares the locker for the management operation.
. One or more `kl.mvin` (<<KLEE-instruction-mv>>) load the rest of the information into the locker, or one or more `kl.mvout` move the locker's information out.
. `kl.mgmt` completes the management operation and makes the locker available to software.

// Setting error handling aside, *provisioning* consists of the following three steps:
//
// . `kl.mgmt` (<<KLEE-instruction-mgmt>>) prepares the locker, checks the validity of the MDH, and loads the whole MDH into the locker.
// . One or more `kl.mvin` (<<KLEE-instruction-mv>>) load the rest of the provisioning information.
// . `kl.mgmt` completes the provisioning and makes the locker available to software.
//
//
// *Importing* an SCC is similar:
//
// . `kl.mgmt` prepares the locker to accept an SCC, checks the validity of the MDH, and loads the whole MDH into the locker.
// . One or more `kl.mvin` load the rest of the SCC, authentication data first, into the locker.
// . `kl.mgmt` authenticates and decrypts the SCC, and makes the locker available to software.
//
// *Exporting* a locker as an SCC takes five steps:
//
// . `kl.getmd` or `kl.getmdv` (<<KLEE-instruction-getmd>>) exports the MDH out of the locker, and `kl.size` (<<KLEE-instruction-size>>) gives the size of the SCC, for which software allocates resources.
// . Software stores the MDH to memory.
// . `kl.mgmt` prepares the locker to produce an SCC, encrypting its contents and computing the authentication tag(s).
// . One or more `kl.mvout` move the rest of the SCC, authentication data first, out of the locker.
// . `kl.mgmt` completes the export and restores the locker to a form available to software.

[[KLEE-instruction-size]]
=== kl.avail and kl.size

_Synopsis_::
`kl.avail` returns 1 if the Machine encoded in the MDH is available in the requested variant, and 0 otherwise.
`kl.size` returns the size in bytes of the memory buffer needed for the data of a PI or SCC, or 0 on error, such as an unsupported Machine or an invalid MDH.

_Mnemonic_::
+
--
`kl.avail` and `kl.size` have three Forms:
(((KLEE, instruction, kl.size)))
(((KLEE, instruction, kl.avail)))

[upperalpha]
. `kl.{avail,size}  Xd, Ks` - Size from a context.
. `kl.{avail,size}  Xd, Xs` - Size from MDH[63:0] in one (RV64) or two (RV32) GPRs.
. `kl.{avail,size}  Xd, Vs` - Size from MDH in one vector register.
--

_Encoding_::
+
--
The encoding shares the opcode, `funct3` and `funct2` (the two msbs of `funct7`) of `kl.exec`, with bit 27 set.
Bit 25, `q`, selects `kl.size` (`q` = 0) or `kl.avail` (`q` = 1).

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Xd' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'Ks/Xs/Vs' },
    { bits:  5, name: 0x0 },
    { bits:  1, name: 'q' },
    { bits:  1, name: 'r', attr: ['Zklind'] },
    { bits:  1, name: 0x1 },
    { bits:  2, name: 'F' },
    { bits:  2, name: 0x0, attr: ['funct2'] },
]}
....

Field `F` selects the Form:

* `F` = `0b00` {implies} Form A, from a context `Ks`.
* `F` = `0b01` {implies} Form B, from an MDH in one (RV64) or two (RV32) GPRs.
* `F` = `0b10` {implies} Form C, from an MDH in a 128-bit vector register.
--

_Description_:: {empty}
+
--
`kl.avail` (`q` = 1) examines only the _Machine_, _MachinePolicy_, _MachineExtension_, _KeyType_ and _SCProtection_ fields of the MDH, and writes 1 to `Xd` if that combination is implemented (no non-zero _MachineExtension_ is currently defined), and 0 otherwise.
A 1 therefore does not exclude a KLEE unsupported-Metadata exception that a Machine specification attaches to the value of another field, such as the _AuxInfo_ of ML-DSA.
In Form A, an _Unconfigured_ locker yields 0 whatever these fields hold.

`kl.size` (`q` = 0) writes to `Xd` the size in bytes of the memory buffer needed for the external image that the MDH describes: a PI, an SCC, or, for a locker in an Error State, the MDH alone (<<KLEE-data-formats>>, <<KLEE-length-rule>>).
For an SCC the size includes the authentication tag(s) and the ADS; for a PI it covers the entire PI.

The Forms differ only in the source of the MDH: the locker itself (Form A), bits [63:0] in `Xs`, or in `X[s+1] @ Xs` on RV32 (Form B), or bits [127:0] in `Vs` (Form C).
In Form A, `Ks` may be `KLML` (Rule <<KLEE-GR-klmanagedlocker-override>>).

Let `content1_size` be the length in bytes of the `Content1` of an SCC for the _Machine_, _MachinePolicy_, _KeyType_ and _StateExtension_ of the MDH, and `pi_content_size` the length in bytes of the `Content` of a PI for its _Machine_, _MachinePolicy_ and _KeyType_ (<<KLEE-length-rule>>); the two are not interchangeable.
Let `content2_size` be 16 * (_AuxDataLen_ - 2) if _AuxDataLen_ {ge} 2 and _ADSDropped_ = 0, and 0 otherwise.

Form B examines only bits [63:0]: no field in bits [127:64] affects the size of any structure (<<KLEE-length-rule>>), so the invalidity and unsupported-Metadata conditions on those fields, including Rule <<KLEE-GR-custom-locality>> and the _AuxInfo_ of a Machine, are not applied.

`kl.size` returns:

. Form A: 0 if the locker is _Unconfigured_;
. Forms B and C: 0 if the supplied MDH is not in an Error State and is unsupported or invalid Metadata (<<KLEE-Metadata-validity>>), or its _State_ is 61–63; validity is evaluated as at provisioning when the supplied _State_ is _Unconfigured_, and as at import otherwise.
. 16 if MDH._State_ is an Error State;
. if MDH._State_ is a Valid State or `kl_cfg_{importing|exporting}`:
  .. 32 + `content1_size` if _AuxDataLen_ = 0;
  .. 64 + `content1_size` + `content2_size` if _AuxDataLen_ {ge} 2, the 64-byte fixed part including `IMPQUAL` and `SIV2` even when _ADSDropped_ = 1;
. 16 + `pi_content_size` if MDH._State_ is `kl_cfg_provisioning`, `kl_cfg_ppi_importing`, or `kl_cfg_ppi_exporting`, or, for a supplied MDH, _Unconfigured_ (the MDH of a PI).
--

[[KLEE-instruction-exec]]
=== kl.exec

_Synopsis_::
Perform a cryptographic operation in the KLEE unit.

_Mnemonic_::
+
--
`kl.exec` has four Forms:
(((KLEE, instruction, kl.exec)))

[upperalpha]
. `kl.exec  Vd, Kn, Vs2` {nbsp} reads an input vector and writes an output vector.
. `kl.exec  {fournbsp} Kn, Vs2` {nbsp} reads an input vector and writes no output vector.
. `kl.exec  Vd, Kn {fournbsp}{nbsp}` {nbsp} reads no input vector and writes an output vector.
. `kl.exec  {fournbsp} Kn {fournbsp}{nbsp}` {nbsp} reads no input vector and writes no output vector.
--

_Encoding_::
`kl.exec` is an R-type instruction.
+
--
[wavedrom, , svg]
....

{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'rd', attr: ['Vd','—','Vd','—'] },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: "'rs1' (n)", attr: ['Kn'] },
    { bits:  5, name: 'rs2', attr: ['Vs2','Vs2','—','—'] },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'r', attr: ['Zklind'] },
    { bits:  1, name: 0x0 },
    { bits:  2, name: 'Form', attr: ['0    0','0    1','1    0','1    1'] },
    { bits:  2, name: 0x0, attr: ['funct2'] },
]}
....

The encodings of Forms A–D are:

[upperalpha]
. `Form` = `0b00`.
. `Form` = `0b01` and `rd` = `0b00000`.
. `Form` = `0b10` and `rs2` = `0b00000`.
. `Form` = `0b11` and `rd` = `rs2` = `0b00000`.

The locker operand is always in `rs1`.
An unused register field (`rd` without an output vector, `rs2` without an input vector) must be zero, except in the encodings that `Zklmv` assigns (<<KLEE-instruction-mv>>); other non-zero values in it are reserved.
--

_Description_::
+
--
Performs the cryptographic operation that the Machine in locker `Kn` defines, possibly taking an input and producing an output.
When it performs no operation (on an _Unconfigured_, Error-State or expired locker) or transitions the locker to an Error State, it zeroes the unwritten part of its output window instead of producing output (Rule <<KLEE-GR-usage-locker-error-state>>).

In Form A, each output block has the length of its input block and is written at the same window offset, so `Vd` and `Vs2` may always be the same register group, each block's output replacing its input; any other overlap is reserved.

NOTE: A future version of this specification may define, with their semantics, _expanding_ or _narrowing_ multi-block `kl.exec` operations, whose output blocks are longer, resp. shorter, than their input blocks.
No current Machine needs them.

Without `Zklv`, only Form D is supported: Forms A–C raise an illegal-instruction exception, and `kl.input` and `kl.output` supply the inputs of `kl.exec` and extract its outputs (<<KLEE-usage-input-output>>).
--

[[KLEE-instruction-mv]]
=== kl.mvin and kl.mvout

The `Zklmv` subextension adds dedicated move instructions between scalar/vector registers and a locker.
The instructions in this extension are encoded as new forms of `kl.exec`.

_Synopsis_::
  Move content between scalar/vector registers or the KLIOBUF and the locker under management, which is in a Configuration State.

_Mnemonics_::
+
--
`kl.mvin` and `kl.mvout` are one instruction with six variants:
(((KLEE, instruction, kl.mvin)))(((KLEE, instruction, kl.mvout)))

[upperroman]
. `kl.mvin Xs2` copies 128 bits from two or four GPRs into the locker.
. `kl.mvin Vs2` copies one or more 128-bit blocks from a vector register into the locker.
. `kl.mvin KLIOBUF` copies one or more 128-bit blocks from the KLIOBUF into the locker.
. `kl.mvout Xs1` copies 128 bits from the locker into two or four GPRs at `Xs1`.
. `kl.mvout Vs1` copies one or more 128-bit blocks from the locker into a vector register `Vs1`.
. `kl.mvout KLIOBUF` copies one or more 128-bit blocks from the locker into the KLIOBUF.

The locker is not an operand: the instruction acts on the locker that `klmanagedlocker` names (Rule <<KLEE-GR-locker-less-transfers>>).
--

_Encodings_::
+
--
The encodings are variants of `kl.exec` Form D (`Form` = `0b11`) in which `rd`, zero in `kl.exec`, is non-zero and selects the variant. Since no locker is encoded, `r` = 0; a non-zero `r` is reserved.

[upperroman]
. `kl.mvin Xs2`:       `rd` = `0b00001`, `rs1` = `0`, and `rs2` holds the source GPR.
. `kl.mvin Vs2`:       `rd` = `0b00010`, `rs1` = `0`, and `rs2` holds the source vector register.
. `kl.mvin KLIOBUF`:   `rd` = `0b00011`, `rs1` = `0`, and `rs2` = `0b00000`.
. `kl.mvout Xs1`:      `rd` = `0b00101`, `rs2` = `0`, and `rs1` names the destination GPR.
. `kl.mvout Vs1`:      `rd` = `0b00110`, `rs2` = `0`, and `rs1` names the destination vector register.
. `kl.mvout KLIOBUF`:  `rd` = `0b00111`, `rs2` = `0`, and `rs1` = `0b00000`.

Any other non-zero value of `rd` in Form D is reserved and raises an illegal-instruction exception.
--

_Description_::
+
--
`kl.mvin` moves `Content` into, and `kl.mvout` out of, the managed locker (Rule <<KLEE-GR-locker-less-transfers>>).
Neither transfers the MDH: for a provisioning or an import, the opening `kl.mgmt` has already loaded it (<<KLEE-instruction-mgmt>>), and `kl.getmd*` reads it.

[[KLEE-mv-locker-checks,locker checks]]Locker checks:::
The managed locker must be in a Configuration State that admits the instruction, and `klstart` must be a multiple of 16:
+
* `kl.mvin`, a locker being provisioned or imported: `kl_cfg_provisioning`, `kl_cfg_importing` or `kl_cfg_ppi_importing` (Rule <<KLEE-GR-zkl-load-mv-allowed>>);
* `kl.mvout`, a locker being exported: `kl_cfg_exporting` or `kl_cfg_ppi_exporting` (Rule <<KLEE-GR-zkl-store-mv-allowed>>).
+
Otherwise an illegal-instruction exception is raised, except on an _Unconfigured_ or Error-State locker, on which the instruction performs no operation, whatever `klstart` is (Rule <<KLEE-GR-cleared-under-management>>).

[[KLEE-serialized-image,serialized image]]Serialized image:::
`content_size` is the length in bytes of the serialized `Content` of the locker, as a PI or an SCC according to the base type of its image (<<KLEE-length-rule>>), as given by the locker's MDH.
In the external formats, the `Content` starts at a _ContentOffset_ that depends on that MDH:
// the same case distinction of `kl.size` (<<KLEE-instruction-size>>) but excluding the `Content` and the MDH._ADSDropped_ never affects _ContentOffset_.
+
. 16 if _AuxDataLen_ = 0, and 48 if _AuxDataLen_ {ge} 2, if MDH._State_ is a Valid State, `kl_cfg_importing` or `kl_cfg_exporting`;
. 0 if MDH._State_ is `kl_cfg_provisioning`, `kl_cfg_ppi_importing` or `kl_cfg_ppi_exporting`.
+
The _serialized image_ `S` of the locker is `Content`, `SIV {vvert} Content`, or `SIV {vvert} IMPQUAL {vvert} SIV2 {vvert} Content` for _ContentOffset_ = 0, 16 or 48, respectively; while the locker is under management, the authentication registers (<<KLEE-KLF>>) hold its leading fields.
Its size is `image_size` = _ContentOffset_ + `content_size`, the value that `kl.size` reports minus 16.
+
`max_admissible` is the length of the longest image of the locker's base type that the implementation can hold for the Machine: `pi_content_size` for base type `pi`, and `content1_size` plus the largest supported `content2_size` for base type `scc` (<<KLEE-instruction-size>>); with _ADSDropped_ = 1, `content2_size` counts as zero.
Bytes of an SCC beyond `max_admissible` belong to a discarded ADS (<<KLEE-SCC-import>>), and are not transferred.
The transferred part of `S` ends at `image_end` = _ContentOffset_ + min(`content_size`, `max_admissible`).

Transfer:::
`kl.mvin` and `kl.mvout` transfer only whole 16-byte blocks, at 16-byte-aligned offsets of `S`: the block at offset `klstart` is transferred if `klstart` < `image_end`, and `klstart` then advances by 16.
If `klstart` {ge} `image_end`, `klstart` is unchanged, `kl.mvin` writes nothing, and `kl.mvout` writes zeros to its destination GPRs, resp. to every element of `Vs1` from `vstart` to `vl` − 1.
If one management operation combines `kl.mvin` or `kl.mvout` with `kl.load` or `kl.store`, each byte of `Content` holds the value last written to its offset, by whichever instruction.

Vector variants (II and V):::
They also track progress in `vstart`: each 16-byte block advances it by 128/`SEW` elements, for instance by 4 for 32-bit and by 2 for 64-bit elements.
Element _k_ of the vector operand, for _k_ from `vstart` to `vl` − 1, corresponds to byte offset `klstart` + (_k_ − `vstart`) × `SEW`/8 of `S`.
If the transfer is interrupted, `klstart` holds the total number of bytes transferred, and `vstart` the first untransferred element; if `vstart` {ge} `vl`, the instruction performs no operation and leaves `klstart` unchanged.

KLIOBUF variants (III and VI):::
They use the KLIOBUF in place of a vector register: they transfer bytes 0 to `kliobuftop` − 1 of the KLIOBUF to or from offsets `klstart` to `klstart` + `kliobuftop` − 1 of `S`, as a vector variant with `vstart` = 0 and `vl` × `SEW`/8 = `kliobuftop` does.
Like the GPR variants (I and IV), they are architecturally uninterruptible (Rule <<KLEE-GR-uninterruptible-instructions>>).
+
NOTE: The KLIOBUF variants give an implementation without `Zklv` multi-block transfers: `kl.input` fills the KLIOBUF from memory, with `klmanagedlocker` = 32, and `kl.mvin KLIOBUF` moves it into the locker, with `klmanagedlocker` naming that locker (Rule <<KLEE-SR-klmanagedlocker-write>>), as `kl.input` and `kl.exec` cooperate for the inputs of a Machine (<<KLEE-usage-input-output>>).
Their window is the KLIOBUF up to `kliobuftop`, so they need no element position, and a transfer of at most `klmaxiobuflen` bytes can be uninterruptible.

Exceptions and no-operation cases:::
Besides the <<KLEE-mv-locker-checks>>, an illegal-instruction exception is raised if:
+
* for a vector variant, `vl` × `SEW`/8 or `vstart` × `SEW`/8 is not a multiple of 16; or
* for a KLIOBUF variant, `Zklio` is not implemented, or `kliobuftop` is not a multiple of 16.
+
For a vector variant, the check that the vector extension is enabled precedes all of these and the locker checks.
+
A KLIOBUF variant raises an unconfigured-KLIOBUF exception if the KLIOBUF is unconfigured (Rule <<KLEE-GR-iobuf-configured>>).
+
When `klmanagedlocker` = 32, every variant performs no operation, whatever `klstart` is, as on an _Unconfigured_ or Error-State locker; in both cases `kl.mvout` writes zeros to its destination (Rule <<KLEE-GR-cleared-under-management>>).
With `klmanagedlocker` = 32, a KLIOBUF variant performs no operation before checking the KLIOBUF and `kliobuftop`, but after checking for `Zklio`.
--

[[KLEE-instruction-setst]]
=== kl.setst

_Synopsis_::
Change the state of the Machine encoded in the CC in a locker.

_Mnemonic_::
`kl.setst` has four Forms:
(((KLEE, instruction, kl.setst)))
+
[upperalpha]
. `kl.setst Kd, #immed7{fournbsp}{nbsp}{nbsp}` with no auxiliary input.
. `kl.setst Kd, #immed7, Xs{nbsp}` with auxiliary input in one or two GPRs (RV64/RV32).
. `kl.setst Kd, #immed7, Vs{nbsp}` — in a vector register.
. `kl.setst Kd, #immed7, Xs{nbsp}` — in two or four GPRs (RV64/RV32).

//

_Encoding_::
`kl.setst` is an R-type instruction.
The encodings with bit 24 = 1 belong to `kl.setml` and `kl.setmli` (<<KLEE-instruction-get-set-ml>>); of the others, those with `#immed7`[6:3] = `0b0111` belong to `kl.mgmt` (<<KLEE-instruction-mgmt>>); these are separate instructions, and all remaining encodings are `kl.setst`.
+
--
[wavedrom, ,svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Kd' },
    { bits:  3, name: 0x3, attr: ['kl.setst'] },
    { bits:  5, name: 'rs1' },
    { bits:  1, name: 'r', attr: ['Zklind']   },
    { bits:  2, name: 'F' },
    { bits:  2, name: 0x0 },
    { bits:  7, name: 'immed7' },
]}
....

`#immed7` = `kl_cfg_clearall` (65) is valid only in Form A, with `Kd` = 0 and `r` = 0, where it encodes `kl.clearall` (<<KLEE-instruction-clearall>>); every other encoding with `#immed7` = 65 is reserved.

The encodings of the four Forms are:
[upperalpha]
. `F` = `0b00`. `rs1` = `0b00000`.
. `F` = `0b01`.
. `F` = `0b10`.
. `F` = `0b11`.
--

// ////////////////////////////////////////////////////////////////////

_Description_::
+
--
`kl.setst` advances the Machine of locker `Kd` from one stage to another, for instance from initializing a hash function to absorbing data and finalizing the digest.
It normally reaches the State that `#immed7` names, but some States transition automatically to another State when the instruction completes.
<<KLEE-State-management>> and each Machine's specification give the allowed transitions.
`kl.setst` may also set state information orthogonal to these stages, possibly as a prerequisite for entering another State.

For all Machines, `#immed7` takes these values:

* 0 (`kl_state_unconfigured`) clears the locker, in any Form, ignoring any auxiliary operand.
* 1–55 name a _State_:
** 1–47 are the _Valid_ States (<<KLEE-states-valid>>). 46 and 47, _Success_ and _Failure_ of the Machine, cannot be set directly; _Failure_ is an outcome, not an error.
** 48–55 are the Error States (<<KLEE-states-error>>); 54 and 55 are reserved, and so is 53 without `Zklexpire`.
   An Error State is accepted as `#immed7` in any State: a locker in a Complete or Configuration State transitions to it _without raising an exception_, even where reaching that State implicitly would raise one, and later usage of the locker performs no operation (Rule <<KLEE-GR-usage-locker-error-state>>).
   On an _Unconfigured_ locker the instruction performs no operation: only the short import of <<KLEE-error-state-transfer>> configures a locker directly into an Error State.
* 56–63, whose top four bits are `0b0111`, encode `kl.mgmt` (<<KLEE-instruction-mgmt>>).
* 64 encodes `kl_cfg_clear_ads` (<<KLEE-instruction-clearads>>).
* 65 encodes `kl_cfg_clearall` (<<KLEE-instruction-clearall>>), in Form A with locker 0 and `r` = 0 only.
* 66–127 are Machine-defined, and may change other state information, such as _StateExtension_.

A value in 1–45 or 66–127 that the current Machine does not support transitions the locker to Error State _Invalid_.
On an _Unconfigured_ locker, every immediate in 1–45, 48–53, 64 and 66–127 performs no operation (Rule <<KLEE-GR-transition-to-from-unconfigured>>).
The immediates 46, 47, 54 and 55, and 53 without `Zklexpire`, are reserved in every State (Rule <<KLEE-GR-success-failure-cannot-be-set-directly>>, <<KLEE-illegal-instruction-grounds>>); 0 and 65 encode `kl.clear` and `kl.clearall`, and 56–63 encode `kl.mgmt`.
Some values require a 64- or 128-bit auxiliary operand, in one or more GPRs or in a vector register (group) `Vs`.

For this instruction and its variants, Rules <<KLEE-GR-klmanagedlocker-override>> and <<KLEE-GR-klml-no-managed-locker>> apply.
--

[[KLEE-instruction-clear]]
==== kl.clear

`kl.clear Kd` is `kl.setst` (<<KLEE-instruction-setst>>) with no auxiliary operand and `#immed7` = `kl_state_unconfigured` (<<KLEE-State-field>>).
It sets the locker's _State_ to _Unconfigured_ and releases its KLF resources.
As a robustness recommendation, clearing should also zeroize the Content and any ADS that the locker held: the zeroization at provisioning and import already prevents a new CC from reading them, but no secret then remains in the KLF.

Clearing a locker not already _Unconfigured_, or whose `*llockerstatus` field in effect is _Off_ (<<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>>), sets to Dirty the `*llockerstatus` fields in effect for the current privilege mode and the `KLS` fields in effect.

// ////////////////////////////////////////////////////////////////////

[[KLEE-instruction-clearall]]
==== kl.clearall

`kl.clearall` is `kl.setst` with no auxiliary operand, `#immed7` = `kl_cfg_clearall`, locker number 0 and `r` = 0.
The locker field names no locker: `kl.clearall` acts on every locker whatever the _State_ of `K0`, and is not a usage instruction.

It unconfigures every locker, as `kl.clear` on each would.
It also unconfigures the KLIOBUF, zeroing the buffer and setting `kliobuflen`, `kliobuftop` and `klstart` to 0; zeroizes the three authentication registers of <<KLEE-KLF>>; and writes 32 to `klmanagedlocker`.

// ////////////////////////////////////////////////////////////////////

[[KLEE-instruction-clearads]]
==== kl.clearads

`kl.clearads Kd` deletes any ADS from locker `Kd`, and sets _AuxDataLen_ and _ADSDropped_ to 0.
It is `kl.setst` (<<KLEE-instruction-setst>>) with no auxiliary operand and `#immed7` = `kl_cfg_clear_ads` (64).

Software uses it before exporting a locker for another target to make the SCC smaller.
A destination with a different KLEE unit would drop the ADS anyway.
// The first usage instruction that needs the ADS regenerates it.
`kl.clearads` is permitted in every Valid State, and may cause an interrupted operation to restart (Rule <<KLEE-GR-clearads>>).

[[KLEE-instruction-mgmt]]
=== kl.mgmt

_Synopsis_::
Open or complete a management operation on a locker.

_Mnemonic_::
While `kl.mgmt` uses the same encoding as Forms A, C and D only of `kl.setst`,
it is a distinct instruction.
(((KLEE, instruction, kl.mgmt)))

//

_Encoding_::
`kl.mgmt` is an R-type instruction with the encoding of `kl.setst` (<<KLEE-instruction-setst>>) and `#immed7`[6:3] = `0b0111`, that is, `#immed7` in 56–63.

_Description_::
+
--
For this instruction, Rules <<KLEE-GR-klmanagedlocker-override>> to <<KLEE-GR-mgmt-klmanagedlocker-check>> apply.

`kl.mgmt` brackets the body of a locker management operation (<<KLEE-management-operations>>): it opens a provisioning, an export or an import on locker `Kd`, and completes it.
Like `kl.setst` it changes the locker's _State_, but with different semantics, hence a separate instruction.
The State reached depends on both the locker's previous State and `#immed7`.
Besides the command in `#immed7`, `kl.mgmt` receives an MDH: when opening, it selects the variant of the operation and may become the locker's MDH; when completing an import or an export, it restores, from the copy the caller saved, the _State_ the locker had when the operation started.

<<KLEE-management-immeds>> gives the values of `#immed7`.

The Forms supply the MDH as follows:

* Form A carries no auxiliary operand. Where the operation needs the MDH, Form A is a
  substitution (<<KLEE-usage-input-output>>) and reads it from bytes [0, 15] of the KLIOBUF,
  ignoring `klstart`. After the `klmanagedlocker` check and before any change to the locker, Rule
  <<KLEE-GR-iobuf-configured>> applies and, with the KLIOBUF configured, `kliobuftop` < 16 raises
  an illegal-instruction exception (Rule <<KLEE-GR-vector-MDH-operand>>).
* Form C carries it in the lowest 128 bits of `Vs`. Where the operation needs it, `VL` {times} `SEW` < 128 raises an illegal-instruction exception at the same point as for Form A (Rule <<KLEE-GR-vector-MDH-operand>>).
* Form D carries it as a 128-bit operand in two or four GPRs starting at `Xs` (Rule
  <<KLEE-GR-multiple-GPRs>>).
* Form B is a reserved encoding (<<KLEE-illegal-instruction-grounds>>).

<<KLEE-locker-management>> gives the precise semantics of each operation.
--

[[KLEE-instruction-getmd]]
=== kl.getmd, kl.getmdl, and kl.getmdv

_Synopsis_::
Export the MDH of a locker.

_Mnemonics_::
+
--
[%hardbreaks]
`kl.getmdl{nbsp}Xd, Ks`(((KLEE, instruction, kl.getmdl)))
`kl.getmd{nbsp}{nbsp}Xd, Ks`(((KLEE, instruction, kl.getmd)))
`kl.getmdv{nbsp}Vd, Ks`(((KLEE, instruction, kl.getmdv)))
--


_Encoding_::
+
--
`kl.getmd*` are R-type instructions that share the opcode and `funct3` of `kl.exec`, with `funct2` = `0b11`.

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Xd' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'rs1', attr: ['Ks'] },
    { bits:  5, name: 0x00  },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'r', attr: ['Zklind']   },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'h' },
    { bits:  1, name: 'v' },
    { bits:  2, name: 0x3, attr: ['funct2'] },
]}
....

`r` is the locker indexing mode selector (Rule <<KLEE-GR-GPR-indirect>>).

With bit `v` (bit 29) = 0, bit `h` (bit 28) selects `kl.getmdl` (`h` = 0) or `kl.getmd` (`h` = 1), and the result goes to GPRs: one GPR on RV64 and a pair on RV32 for `kl.getmdl`, a pair on RV64 and a quartet on RV32 for `kl.getmd` (Rule <<KLEE-GR-multiple-GPRs>>).
With `v` = 1, the instruction is `kl.getmdv`, which writes the entire MDH to the lowest 128 bits of a vector register (group); `h` must then be 0.
`v` = `h` = 1 is used to encode `kl.getml` (<<KLEE-instruction-get-set-ml>>).
--

_Description_::
+
--
These instructions copy the MDH of locker `Ks`, which is all-zero for an _Unconfigured_ locker:

* `kl.getmdl` copies bits [63:0] to GPR `Xd` on RV64, and to the pair `X[d+1] @ X[d]` on RV32.
* `kl.getmd` copies bits [127:0]: on RV64, bits [63:0] to `Xd` and bits [127:64] to `X[d+1]`; on RV32, to the quartet `X[d+3] @ X[d+2] @ X[d+1] @ X[d]`.
* `kl.getmdv` copies bits [127:0] to vector register `Vd`, on RV32 as on RV64. Bits [`VL` {times} `SEW` − 1 : 128] are written with zeros, and the tail follows the tail-agnostic policy (<<KLEE-KLV>>).

They do not check MDH validity (<<KLEE-Metadata-validity>>).
`Ks` may be `KLML` (Rule <<KLEE-GR-klmanagedlocker-override>>).
--

[[KLEE-instruction-getst]]
==== kl.getst and kl.getstx

The pseudo-instructions
(((KLEE, instruction, kl.getst)))
`kl.getst Xd, Ks`
(((KLEE, instruction, kl.getstx)))
`kl.getstx Xd, Ks`
return the _State_, resp. _StateExtension_, field of the MDH of the source locker, for instance to determine whether it is in an Error State (<<KLEE-State-field>>).
They read the MDH with `kl.getmdl` and extract the field by shifting and masking.

On RV64, `kl.getst` expands to

. `kl.getmdl Xd, Ks`
. `srli  Xd, Xd, 18`
. `andi  Xd, Xd, 0x3F`

and `kl.getstx` to

. `kl.getmdl Xd, Ks`
. `srli  Xd, Xd, 24`
. `andi  Xd, Xd, 0x0F`

On RV32 the code is the same: `kl.getmdl` writes the lower 64 bits of the MDH to the pair `X[d+1] @ X[d]`, so `d` must be even (Rule <<KLEE-GR-multiple-GPRs>>) and `X[d+1]` is overwritten; _State_ and _StateExtension_ lie entirely in the lower 32 bits, in `X[d]`.

[[KLEE-instruction-get-set-ml]]
=== kl.getml, kl.setml, and kl.setmli

_Synopsis_::
Get, resp. set, the value of `klmanagedlocker`.

_Mnemonics_::
+
--
[%hardbreaks]
`kl.getml{nbsp}{nbsp}Xd`(((KLEE, instruction, kl.getml)))
`kl.setml{nbsp}{nbsp}Xs1`(((KLEE, instruction, kl.setml)))
`kl.setmli{nbsp}#uimm7`(((KLEE, instruction, kl.setmli)))
--

_Encodings_::
+
--
The encodings are variants of those of `kl.getmd*` (<<KLEE-instruction-getmd>>) and `kl.setst` (<<KLEE-instruction-setst>>):

* `kl.getml Xd`: the `kl.getmd*` encoding with `v` = `h` = 1, `r` = 0 and `rs1` = 0; `rd` holds `Xd`.
* `kl.setmli #uimm7`: the `kl.setst` encoding with bit 24 = 1, `Kd` = 0, `r` = 0, `F` = `0b00` and `rs1` = 0; `#immed7` holds `#uimm7`.
* `kl.setml Xs1`: the `kl.setst` encoding with bit 24 = 1, `Kd` = 0, `r` = 0, `F` = `0b01` and `#immed7` = 0; `rs1` holds `Xs1`.

Every other encoding with `v` = `h` = 1 in the `kl.getmd*` encoding, or with bit 24 = 1 in the `kl.setst` encoding, is reserved.
--

_Description_::
+
--
`kl.getml` writes `klmanagedlocker`, zero-extended, to `Xd`.
`kl.setml` and `kl.setmli` write `X[rs1]`, resp. the zero-extended `#uimm7`, to `klmanagedlocker`, with the effect of a CSR write (<<KLEE-CSR-klmanagedlocker>>): a value of 33 or more leaves `klmanagedlocker` unchanged.

These instructions are part of `Zkl` common and are gated as accesses to `klmanagedlocker` (<<KLEE-CSR-unpriv>>).
They are non-destructive configuration instructions, not usage instructions: Usage Control does not gate them.
They are uninterruptible (Rule <<KLEE-GR-uninterruptible-instructions>>), and Rules <<KLEE-SR-klmanagedlocker-write>> and <<KLEE-SR-klmanagedlocker-finish>> apply to their writes as to CSR writes.

NOTE: Since in many implementations CSR accesses are slow, we provide, similarly to the Vector extensions, instructions to quickly set and get the value of `klmanagedlocker` without incurring CSR access penalties and without requiring implementations to selectively use a different implementation for these accesses. Therefore, internally, the value of `klmanagedlocker` may be used as a prefix for the KLEE instructions that need it.
--

_Mnemonic_::

_Encoding_::
+

`kl.restrict*` are R-type instructions that share the opcode and `funct3` of `kl.exec`, with `funct2` (the two msbs of `funct7`) = `0b01`.
[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Kd' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'Xs1' },

    { bits:  1, name: 'h' },
    { bits:  1, name: 'v' },
    { bits:  2, name: 0x1, attr: ['funct2'] },
]}
....

`r` is the locker indexing mode selector (Rule <<KLEE-GR-GPR-indirect>>).

With bit `v` (bit 29) = 0, bit `h` (bit 28) selects `kl.restrictl` (`h` = 0) or `kl.restricth` (`h` = 1), and the input comes from a GPR (a GPR pair on RV32).
With `v` = 1, the instruction is `kl.restrictv`, `h` must be 0, and the input comes from the lowest 128 bits of a vector register (group); `v` = `h` = 1 is reserved.
--

// comment

_Description_::
+
--
These instructions narrow the policies of the CC in locker `Kd`, whose MDH is `md`, as their operand requests: `Xs1`, or `Vs1` for `kl.restrictv`, formatted as an MDH.

Operand:::
* `kl.restrictl` takes bits [63:0] of the operand, and may change _MachinePolicy_;
* `kl.restricth` takes bits [127:64], supplied in `Xs1`[63:0], and may change _Locality_, _UsagePolicy_ and _ExpirationDate_;
* `kl.restrictv` takes both halves, and applies both sets of rules.
+
A zero field of `Xs1` leaves the corresponding field of `md` unchanged; a non-zero field other than these four transitions the locker to _Invalid_.

Field rules:::
For _Locality_ and _ExpirationDate_, the result is the narrowing of `md` by `Xs1` (<<KLEE-Metadata-narrowing>>), except that a _Locality_ request weaker than `md` transitions the locker to _Privilege Violation_ instead of being overridden.
_UsagePolicy_ follows its own field rule below: `Xs1` is a request, not an MDH policy, so a clear bit 4 does not withdraw the Debug grant.
Each non-zero field of `Xs1` is handled as follows:
+
* _MachinePolicy_: the new value replaces the old one only if every bit it sets was already set, so that no disabled function can be enabled.
  Any other value, a value that disables the operation of the current State (Rule <<KLEE-GR-policy-narrowing-state>>), and any value for a Machine that does not use the field or uses it to extend _Machine_, transitions the locker to _Invalid_.
  A Machine with fields that exist only for some values of _MachinePolicy_, such as the ECC Machines (<<Zkl-ISA-machines.adoc#KLEE-ECC>>), states what a narrowing does to them.
* _Locality_: each subfield (<<KLEE-locality-indexes>>), bits [1:0], [3:2] and [5:4] and each of bits 6, 7 and 8, is treated independently.
  A subfield of `Xs1` that is zero or equal to that of `md` requests no change, and a zero subfield of `md` takes the value of `Xs1`.
  A non-zero HW Binding subfield may be replaced only by a stricter entry of its chain: _SiPScrt_ by _ChipFamScrt_ or _ChipScrt_, _ChipFamScrt_ by _ChipScrt_, _OEMScrt_ by _ProdScrt_ or _DevScrt_, and _ProdScrt_ by _DevScrt_.
  Any other change, a weakening or a change of a non-zero Boot Session or SW Filter subfield included, transitions the locker to _Privilege Violation_.
  A later export binds its SCC to the new _Locality_.
* _UsagePolicy_: each set bit removes a permission, and each clear bit changes nothing: bits 0–3 set the corresponding disallow bits of `md`, and bit 4 clears its Debug grant, so no request can widen the set of modes that may use the CC.
* _ExpirationDate_: if `md`._ExpirationDate_ is zero or `Xs1`._ExpirationDate_ {le} `md`._ExpirationDate_, the value in `Xs1` replaces it; otherwise the field is unchanged, without error.

Validity of the result:::
Validity (<<KLEE-Metadata-validity>>) is evaluated on the changed fields only.
A request that would produce an unsupported or invalid value, such as a non-zero _ExpirationDate_ without `Zklexpire`, transitions the locker to _Invalid_; one that would make _Locality_ name an unconfigured entry without a configured substitute, to _Privilege Violation_; one that does both, to _Invalid_.

States:::
The instructions may be issued in any Complete State; in an Error State, a request that would transition the locker to an Error State performs no operation instead.
In the _Unconfigured_ State they perform no operation, and in a Configuration State Rule <<KLEE-GR-usage-locker-config-state>> applies.
+
They are not usage instructions (Rule <<KLEE-GR-usage-policy>>): every change narrows the CC, so a mode that the _UsagePolicy_ excludes gains no capability; the same holds for `kl.clear` (<<KLEE-instruction-clear>>), a stronger denial primitive.
--

[[KLEE-instruction-clone]]
=== kl.clone, kl.rename, and kl.swap

_Synopsis_::
Copy, move or exchange the CCs of lockers.

_Mnemonic_::
`kl.{clone, rename, swap} Kd, Ks`
(((KLEE, instruction, kl.clone)))
(((KLEE, instruction, kl.rename)))
(((KLEE, instruction, kl.swap)))

_Encoding_::
These are R-type instructions that share the opcode and `funct3` of `kl.exec`, with `funct2` = 2.
+
[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Kd' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'Ks' },
    { bits:  5, name: 0x0 },
    { bits:  2, name: 'R', attr: ['Zklind']   },
    { bits:  2, name: 'T' },
    { bits:  1, name: 0x0 },
    { bits:  2, name: 0x2, attr: ['funct2'] },
]}
....
+
--
Field `T` (bits [28:27]) selects the instruction:

. `00`{nbsp}{nbsp} encodes `kl.clone`.
. `01`{nbsp}{nbsp} encodes `kl.rename`.
. `10`{nbsp}{nbsp} encodes `kl.swap`.
--

// Comment to ensure proper indentation in the next Description

_Description_::
+
--
`kl.clone`:::
Clones the source locker `Ks` (or the locker indexed by `Xs`) into the destination locker `Kd` (or the locker indexed by `Xd`):

* If source and destination are the same locker, the instruction performs no operation and sets no `*llockerstatus` or `KLS` field to Dirty (<<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>>), even if the locker is _Unconfigured_, _Off_, or in a Configuration State; in the last case, Rule <<KLEE-GR-usage-locker-config-state>> does not apply.
* An _Unconfigured_ source makes the destination _Unconfigured_ too, i.e., clears it.
* A source in a Configuration State raises a KLEE privilege-violation exception (Rule <<KLEE-GR-usage-locker-config-state>>). A source in an Error State is cloned as its MDH alone (Rule <<KLEE-GR-error-state-locker-is-only-MDH>>).
* Otherwise, if the KLF capacity available once the destination is cleared cannot hold a clone of the source, a KLEE out-of-memory exception is raised and the destination is left unchanged.
* Otherwise the destination is cleared and becomes a verbatim copy of the source, including all internal data, the MDH and the internal state.
As the one exception, if the source has an interrupted long-running operation (Rule <<KLEE-GR-long-running-progress>>), the copy restarts it: its progress is zeroed and the values drawn or computed for the operation are discarded, as at an import that completes without `Content2`.
If `klmanagedlocker` named the destination, it becomes 32 (<<KLEE-CSR-klmanagedlocker>>).
The effect is that of an export from the source followed by an import into the destination, except that no authentication register is touched.

`kl.rename`:::
If `Ks` = `Kd`, no operation is performed, even if the locker is _Off_, and no field is set to Dirty.
Otherwise the CC of `Ks`, Configuration State included, becomes the CC of `Kd`, the previous CC of `Kd` is discarded, `Ks` becomes _Unconfigured_, and the fields in effect for both lockers are set to Dirty. With an _Unconfigured_ source, `kl.rename` thus acts as `kl.clear Kd`, except that it always sets the fields in effect for both lockers to Dirty.
If `klmanagedlocker` = `s`, it becomes `d`; otherwise, if it is `d`, it becomes 32. The source access is not exempt from the KLEE locker-Off exception; the destination access is exempt, as for `kl.clone`.

`kl.swap`:::
If `Ks` = `Kd`, no operation is performed, even if the locker is _Off_.
Otherwise the CCs of `Ks` and `Kd` are exchanged, and if `klmanagedlocker` {in} {`s`,`d`}, it takes the other index. Neither access is exempt from the KLEE locker-Off exception. The fields in effect for both lockers are set to Dirty.

Neither `kl.rename` nor `kl.swap` raises a KLEE out-of-memory exception or changes the content of any MDH.
<<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>> gives the behavior under emulation, when the source or destination locker is _Off_ in some `*llockerstatus`.
--

[[KLEE-instruction-derive]]
=== kl.derive

_Synopsis_::
Transfer data from one locker into another without exposing it to software.

_Mnemonic_::
`kl.derive Kd, Ks1, Xs2`
(((KLEE, instruction, kl.derive)))

_Encoding_::
+
--
`kl.derive` is an R-type instruction.

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Kd' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'Ks1' },
    { bits:  5, name: 'Xs2' },
    { bits:  2, name: 'R', attr: ['Zklind']   },
    { bits:  2, name: 0x3 },
    { bits:  1, name: 0x0 },
    { bits:  2, name: 0x2, attr: ['funct2'] },
]}
....

The auxiliary input is always a GPR: `kl.derive` has no form without one, and no vector form.
--

_Description_::
+
--
`kl.derive` moves up to `length` bytes, `length` being the value of the auxiliary GPR, from an endpoint of the source locker to an endpoint of the destination locker without exposing them to software: the output of one Machine becomes an input of another, possibly a key or another Content field.

A transfer is _unrestricted_ if software could also obtain the data moved by issuing `kl.exec` instructions, or if a Rule declares it unrestricted; otherwise it is _restricted_.

Source and destination must be different lockers; otherwise an illegal-instruction exception is raised.
Usage Control applies to both lockers (Rule <<KLEE-GR-usage-policy>>), and both are checked before any state change or transfer, in the order of Rule <<KLEE-GR-checks>>.

The _State_ and _StateExtension_ of each locker determine its endpoint: the source must be in a State in which it can export data, and the destination in one in which it can import data.
These States alone define the fields exported or imported, or the type of the data that `kl.exec` instructions would generate or absorb; no parameter of `kl.derive` selects them.

The _endpoint descriptor_ of the source or of the destination is: +
(MDH._Machine_ {vvert} _MachinePolicy_, MDH._State_ {vvert} _StateExtension_, MDH._KeyType_, +
{nbsp}{nbsp}{nbsp}MDH._UsagePolicy_, MDH._Locality_, MDH._ExpirationDate_).

A transfer may occur only if the architecture allows the pair of endpoint descriptors.
An allowed pair may define a minimum length, an upper limit and a granularity; the architecture defines, per pair, the semantics of the transfer and its updates to the States of the two lockers and to `klstart`; `kl.derive` changes no other state of the hart (<<KLEE-instruction-properties>>).
The checks of the Derivation Rules then decide: a disallowed transfer transitions the lockers as they specify, and an allowed one updates the policies of the destination as Rules <<KLEE-GR-narrowing>> and <<KLEE-GR-unrestricted>> state.
--

[[KLEE-instructions-memory]]
=== Memory Instructions

Accesses to the serialized, user-visible representation of a locker's `Content` are 16-byte granular: `kl.load`, `kl.store`, `kl.mvin` and `kl.mvout` transfer whole 16-byte blocks, and all their offsets and lengths, `klstart`, `content_size`, `max_admissible`, `image_size` and `image_end` (<<KLEE-instruction-mv>>), are multiples of 16.

The effective address of a `kl.load` or `kl.store` must be 16-byte aligned, so a PI or SCC must be held at a 16-byte aligned address.
A misaligned address transfers no data and raises a load or store address-misaligned exception on that address; the check applies even when the transfer window is empty.
`kl.load` and `kl.store` evaluate their conditions in this order:

. the illegal-instruction grounds of both groups and the KLEE exceptions, in the order of <<Zkl-ISA-priv.adoc#KLEE-exception-codes>>;
. the address breakpoint of the first component access, if any;
. address-misaligned, on the effective address; and
. for each component access, in offset order, the address breakpoint, then page, guest-page and access faults, as ordered by the Privileged Specification.

`kl.input` and `kl.output` are byte-granular and impose no alignment constraint: a misaligned effective address behaves as for an ordinary load or store on the implementation.

[[KLEE-instruction-load]]
==== kl.load and kl.input

(((KLEE, instruction, kl.load)))(((KLEE, instruction, kl.input)))_Mnemonics_::
`kl.load %offset(Xs), Xl` +
`kl.input %offset(Xs), Xl`

_Encoding_::
--
`kl.load`/`kl.input` is an I-type instruction.

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x03, attr: ['LOAD'] },
    { bits:  5, name: 'Xl' },
    { bits:  3, name: 0x7, attr: ['kl.load','kl.input'] },
    { bits:  5, name: 'Xs' },
    { bits: 12, name: 'immed12' },
]}
....
--

_Description_::
+
--
The locker is not an operand: with `klmanagedlocker` < 32, `kl.load` copies data into the locker that `klmanagedlocker` names; with `klmanagedlocker` = 32, into the KLIOBUF.

NOTE: `kl.input` is an alias for `kl.load`, for source code in which `klmanagedlocker` is known to be 32.

For `klmanagedlocker` < 32:::
`kl.load` imports the Content of a PI or an SCC into the locker, but not its MDH, which `kl.mgmt` carries.
A non-zero `Xl` raises an illegal-instruction exception; otherwise, `kl.load` makes the <<KLEE-mv-locker-checks,locker checks>> of `kl.mvin`.
+
NOTE: `Xl` is meaningful only for the KLIOBUF. A non-zero value while a locker is under management reveals a `kl.input` or `kl.output` issued at the wrong time, and is reported rather than ignored.
+
For each _j_ in `[klstart, image_end-1]`, `kl.load` loads the byte at memory address ``Xs + %offset + ``_j_ into byte _j_ of the <<KLEE-serialized-image,serialized image>> `S`, in 16-byte blocks from a 16-byte aligned address (<<KLEE-instructions-memory>>).
`klstart` tracks a prefix-complete number of bytes loaded; if `klstart` {ge} `image_end`, nothing is transferred.
On an _Unconfigured_ or Error-State locker, `kl.load` has an empty transfer window and accesses no memory (Rules <<KLEE-GR-cleared-under-management>> and <<KLEE-GR-error-state-locker-is-only-MDH>>); software does not use it on an Error-State locker (<<KLEE-error-state-transfer>>).
+
With a system-specific format, the semantics of `kl.load` are implementation-defined, must be documented, and must satisfy Rules <<KLEE-GR-zkl-load-mv-allowed>> and <<KLEE-GR-which-resumable-instructions>>–<<KLEE-GR-memory-instructions>>.

For `klmanagedlocker` = 32:::
With `Xl` = 0, `kl.input` and `kl.output` perform no operation and write 0 to `klstart`, before any check of `Zklio` or of the KLIOBUF (Rules <<KLEE-GR-cleared-under-management>> and <<KLEE-GR-iobuf-configured>>).
Otherwise, they raise an illegal-instruction exception if `Zklio` is not in effect; if it is, they transfer the bytes of the <<KLEE-iobuf-transfer-window>> below.

[[KLEE-iobuf-transfer-window,KLIOBUF transfer window]]KLIOBUF transfer window:::
The KLIOBUF transfer window of `kl.input` and `kl.output` is the offsets _j_ from `klstart` to min(`Xl`, `kliobuftop`) − 1.
For each such _j_, `kl.input` copies the byte at memory address ``Xs + %offset + ``_j_ to byte _j_ of the KLIOBUF, and `kl.output` copies byte _j_ of the KLIOBUF to that address.
Bytes outside the window are accessed on neither side, so an `Xl` beyond `kliobuftop` transfers only the window.
If `klstart` {ge} min(`Xl`, `kliobuftop`), the window is empty: after Rule <<KLEE-GR-iobuf-configured>> is evaluated, nothing is transferred and `klstart` is set to 0.
--

For `klmanagedlocker` < 32:::

[[KLEE-ISA-rules]]
== Rules

[[KLEE-managed-locker-rules]]
=== Rules Governing the Managed Locker

`klmanagedlocker` (<<KLEE-CSR-klmanagedlocker>>) names the _managed locker_ used by some management instructions.

[horizontal]
[[KLEE-GR-locker-less-transfers,GR7]]GR7:: `kl.load`, `kl.store`, `kl.mvin` and `kl.mvout` have no locker operand and act on the locker whose number is provided by `klmanagedlocker`.

[[KLEE-GR-klmanagedlocker-override,GR8]]GR8:: `kl.mgmt`, `kl.setst` (including `kl.clear` and `kl.clearads`), `kl.getmd*` (hence `kl.getst` and `kl.getstx`), and Form A of `kl.size` and `kl.avail` may name the _managed locker_, written `KLML`, in place of a locker operand.
`KLML` is encoded with `r` = 1 and `X0` in the locker register field, with or without `Zklind`, and denotes the locker that `klmanagedlocker` names.

[[KLEE-GR-klml-openings,GR9]]GR9:: A `kl.mgmt` that opens a provisioning, an import or an export on `KLML` raises an illegal-instruction exception when `klmanagedlocker` = 32. Otherwise, it opens that locker, and `klmanagedlocker` is not changed, except that an export opening on an _Unconfigured_ locker performs no operation and sets it to 32 (Rules <<KLEE-GR-cleared-under-management>> and <<KLEE-GR-klmanagedlocker-updates>>).

[[KLEE-GR-klml-no-managed-locker,GR10]]GR10:: When `klmanagedlocker` = 32, an instruction naming `KLML`, other than the openings of Rule <<KLEE-GR-klml-openings>>, behaves as on an _Unconfigured_ locker: `kl.getmd*` returns zeros, `kl.size` and `kl.avail` return 0, and `kl.setst`, and `kl.mgmt` with `kl_cfg_management_end`, perform no operation (Rule <<KLEE-GR-cleared-under-management>>).

[[KLEE-GR-mgmt-klmanagedlocker-check,GR11]]GR11:: A `kl.mgmt` that names its locker explicitly raises an illegal-instruction exception unless `klmanagedlocker` holds the number of that locker or 32.

[[KLEE-GR-klmanagedlocker-updates,GR12]]GR12:: Besides writes by software, through the CSR or `kl.setml` and `kl.setmli` (<<KLEE-instruction-get-set-ml>>), only the following change `klmanagedlocker`:

* a `kl.mgmt` that leaves its target locker in a Configuration State or a Complete State sets it to, or leaves it at, that locker's number;
* a `kl.mgmt` that performs no operation on an _Unconfigured_ locker sets `klmanagedlocker` to 32 (Rule <<KLEE-GR-cleared-under-management>>);
* a `kl.mgmt` that opens a provisioning or an import and raises an exception after its zeroizing step sets it to the target locker's number;
* a `kl.clear` or `kl.clearall` that clears the managed locker sets `klmanagedlocker` to 32;
* a `kl.clone` or `kl.rename` that overwrites the managed locker, as destination, from another locker, sets `klmanagedlocker` to 32; and
* a `kl.rename` or `kl.swap` that moves the CC of the managed locker sets `klmanagedlocker` to the receiving locker's number (<<KLEE-instruction-clone>>).

[[KLEE-managed-locker-rationale]]
==== Rationale for the Rules Governing the Managed Locker

_This subsection is informative and non-normative._

The design allows locker management software subroutines independent of the locker number.:::
//  By Rules <<KLEE-GR-locker-less-transfers>> and <<KLEE-GR-klmanagedlocker-override>>,
  The opening `kl.mgmt` either records its named locker in `klmanagedlocker`, or uses the `klmanagedlocker` set by software.
  The transfers that follow and the closing `kl.mgmt` need no locker number.

A clear inserted into a management operation has a software-visible effect.:::
//  By Rules <<KLEE-GR-klml-no-managed-locker>> and <<KLEE-GR-klmanagedlocker-updates>>.
  clearing the managed locker resets `klmanagedlocker` to 32, where `KLML` reads as an _Unconfigured_ locker, so the check after each step of a management routine detects the clear (Rule <<KLEE-GR-cleared-under-management>>).

The outcome of an operation is preserved and stays readable.:::
// By Rule <<KLEE-GR-klmanagedlocker-updates>>,
  `klmanagedlocker` keeps its value when the operation completes, when its locker enters an Error State, and on any other KLEE exception.
  A check through `KLML` therefore reads the outcome, not an _Unconfigured_ locker, and after a failed opening a handler can find the zeroized locker even for `KLML`.
  After any other KLEE exception, the handler resolves the condition or writes 32.

Missing writes to `klmanagedlocker` cause a trap downstream.:::
// By Rules <<KLEE-GR-klml-openings>> and <<KLEE-GR-mgmt-klmanagedlocker-check>>,
  A `KLML` opening with `klmanagedlocker` = 32 traps, since there is no locker to open.
  Software that writes 32 after completing a management operation (Rule <<KLEE-SR-klmanagedlocker-finish>>)
  prevents other code from opening the last locker it managed, which may lose information, since the opening `kl.mgmt` traps instead.
  This also reveals an interleaved management operation, or a missing write of 32 after one.

| `kl.store`                  | Only `klstart`  | Yes | No^*^                | Updates `klstart`.
| `kl.input`                  | Yes             | No  | No                   | Modifies the KLIOBUF and `klstart`, but no locker.
| `kl.output`                 | Only `klstart`  | Yes | No                   | Modifies `klstart`, but no locker.
5+| ^*^ Usable only in the States admitted by Rule <<KLEE-GR-zkl-load-mv-allowed>>, resp. Rule <<KLEE-GR-zkl-store-mv-allowed>>; on an _Unconfigured_ or Error-State locker they perform no operation (Rule <<KLEE-GR-cleared-under-management>>).
|===

[[KLEE-destructive-config]]
The *destructive configuration instructions* are the configuration instructions that zeroize or overwrite a locker without reading what it held before: a `kl.mgmt` that opens a provisioning or an import, `kl.clear`, `kl.clearall`, and `kl.clone` and `kl.rename` for their destination locker.

[horizontal]
[[KLEE-GR-iobuf-configured,GR14]]GR14:: KLIOBUF instructions such as `kl.input` and `kl.output` require `Zklio` and a non-zero `kliobuflen`; with `Zklio` and `kliobuflen` = 0 they raise an unconfigured-KLIOBUF exception.

=== Custom Metadata

[horizontal]
[[KLEE-GR-custom-locality,GR15]]GR15:: A CC whose MDH carries a custom _Machine_ or a system-specific _Version_ must name _ChipFamScrt_, or the stricter _ChipScrt_, in its _Locality_; otherwise the Metadata is invalid.
Implementation-specific values of _MachineUse_ and _AuxInfo_ are exempt from this Rule: the ADS and `IMPQUAL` bind them to the implementation (<<KLEE-MachineUse>>).

=== Randomness

[horizontal]
[[KLEE-GR-rbg-failure,GR16]]GR16:: _RBG failure:_ if the entropy source has failed permanently (for `Zkr`, the DEAD state), then an operation that needs random bits is not performed, and its locker transitions to _Invalid_, not _Failure_.
If the bits are only temporarily unavailable, the instruction waits, or is interrupted and then resumed or restarted, as Rules <<KLEE-GR-uninterruptible-instructions>> and <<KLEE-GR-resumability-options>> allow for it; past an implementation-defined bound, it raises a KLEE RBG-unavailable exception and leaves the _State_ unchanged.
A health-test failure from which the entropy source can recover makes the bits temporarily unavailable.
+
NOTE: Such an event should be extremely rare, since for most applications Machines will need fresh bits from a DRBG and not directly from a conditioned entropy source.

The following rules apply to all Machines:

[horizontal]
[[KLEE-GR-state-identifies-cc,GR17]]GR17:: When the CC is in _Ready_, _Success_, _Failure_ or an Error State, the _State_ field of the MDH holds that State, so that _State_ identifies it without inspecting other fields or the Content.

[[KLEE-GR-transition-triggers,GR18]]GR18:: A transition that a Machine specification lists is triggered by an explicit `kl.setst` (<<KLEE-instruction-setst>>), or by conditions that the specification states.
Transitions to and between Configuration States use `kl.mgmt`; transitions out of a Configuration State use `kl.mgmt`, `kl.clear`, `kl.clearall`, a `kl.setst` to an Error State, a `kl.clone` naming the locker as destination, or a `kl.rename` or `kl.swap` naming it as source or destination.

[[KLEE-GR-state-after-setst,GR19]]GR19:: The State that a `kl.setst` reaches on completion need not be the one its immediate names: besides Error State transitions, some operations determine the next State dynamically.
For example, `kl.setst` with immediate `kl_state_hash_verify` and a verification parameter transitions the locker to _Success_ or _Failure_.
Other instructions, such as `kl.exec`, may also change the _State_, under conditions that the Machine specifies.

=== Rules Governing Valid States

[horizontal]
[[KLEE-GR-to-ready,GR20]]GR20:: `kl.setst` may always transition a locker from a Valid State to _Ready_, unless the Machine explicitly forbids it.
// NOTE: Since a locker can always be restored from a backup SCC, preventing transitions to _Ready_--as "GCM with Set IV" (<<KLEE-GCM-with-IV-mode>>) does--is not an effective mitigation against the attacks that would be enabled by transitioning to _Ready_.

[[KLEE-GR-same-state,GR21]]GR21:: In a Valid State other than _Success_ and _Failure_, `kl.setst` may be issued with the immediate of the current State.
Unless the Machine states otherwise, it repeats the operations of entering that State; in a State that loads a field, this restarts the load (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-load-long-field>>).
Where repeating them would produce an internal state that the referenced standard does not allow or define, the Machine forbids the same-State `kl.setst`, which then transitions the locker to Error State _Invalid_ (for instance Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-no-hash-output-repeat>>).

[[KLEE-GR-no-exec-in-ready,GR22]]GR22:: A `kl.exec` in State _Ready_ that the Machine does not explicitly allow transitions the locker to Error State _Invalid_ (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-not-allowed-instructions>> in <<Zkl-ISA-machines.adoc#KLEE-Machines>>).

[[KLEE-GR-clearads,GR23]]GR23:: `kl.clearads` (<<KLEE-instruction-clearads>>) is permitted in every Valid State.
It leaves _State_ and _StateExtension_ unchanged, and is subject to Usage Control (<<KLEE-instruction-properties>> in Rule <<KLEE-GR-usage-policy>>).
Removing the ADS discards any intermediate state that the implementation keeps there for an interrupted long-running operation: in a State of Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-progress-discard>> it zeroes the progress field _P_, and the operation restarts when its instruction is next issued, exactly as if the SCC exported before the `kl.clearads` had been imported on a different KLEE implementation (Rule <<KLEE-GR-long-running-progress>>).

[[KLEE-GR-success-failure-cannot-be-set-directly,GR24]]GR24:: `kl.setst` cannot set States _Success_ and _Failure_ directly: the immediates 46 and 47 are reserved (<<KLEE-illegal-instruction-grounds>>).

[[KLEE-GR-setst-in-success-failure,GR25]]GR25:: In States _Success_ and _Failure_, `kl.setst` may transition the locker to _Ready_, to _Unconfigured_, or to an explicitly given Error State.
It is also permitted with `#immed7` = `kl_cfg_clear_ads` (<<KLEE-instruction-clearads>>), which clears any ADS and leaves the _State_ unchanged, when the Usage Control policies allow it (Rule <<KLEE-GR-clearads>>).
+
NOTE: In theory, some Machines could forbid the return to _Ready_ to prevent nonce misuse, but software could bypass this by reloading a saved copy of the original SCC. Hence, the architecture chooses to allow the return to _Ready_ unconditionally for simplicity.
The return may nevertheless erase session-bound internal state, such as randomly generated nonces, as the Machine specifies.

[[KLEE-GR-success-failure,GR26]]GR26:: In States _Success_ and _Failure_, the only KLEE instructions permitted are `kl.mgmt`, `kl.size`, `kl.avail`, `kl.setst` (subject to Rule <<KLEE-GR-setst-in-success-failure>>), `kl.getmd*`, `kl.getst`, `kl.clone`, `kl.rename`, `kl.swap`, `kl.restrict*` and `kl.derive`.
+
`kl.derive` is permitted only where the source endpoint is one of the locker's exportable fields (<<KLEE-instruction-derive>>); a locker in State _Success_ or _Failure_ cannot be the *destination* of a `kl.derive`.
A `kl.exec`, or a `kl.setst` that the architecture or the Machine does not allow in the current _State_ and _StateExtension_, transitions the locker to Error State _Invalid_ (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-not-allowed-instructions>> in <<Zkl-ISA-machines.adoc#KLEE-Machines>>).
+
NOTE: ML-KEM (<<Zkl-ISA-machines.adoc#KLEE-PQC-ML-KEM>>) motivates this `kl.derive` behavior: `ML-KEM.Decaps`, and `ML-KEM.Encaps` once its ciphertext has been emitted, leave the shared secret in `sharedkey` and transition to _Success_, whose only other exit is _Ready_, which clears `sharedkey`.
Without this provision the shared secret would be unreachable, and ML-KEM useless for its stated purpose.

[[KLEE-GR-policy-narrowing-state,GR27]]GR27:: A narrowing of _MachinePolicy_ by `kl.restrictl` or `kl.restrictv` (<<KLEE-instruction-restrict>>) that disables the operation of the current Valid State, or violates an entry condition of that State that depends on _MachinePolicy_ (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-policy-gate>>), transitions the locker to Error State _Invalid_, as a `kl.setst` into that State would.
Metadata narrowing never changes _MachinePolicy_ (<<KLEE-Metadata-narrowing>>), so this Rule applies only to `kl.restrictl` and `kl.restrictv`.

=== Rules governing Error States and the _Unconfigured_ State

[horizontal]
[[KLEE-GR-clear-locker-content-error-state,GR28]]GR28:: On transitioning to an Error State, a locker clears its Content beyond the MDH, and releases the internal resources that held that Content, any ADS included; _AuxDataLen_ and _ADSDropped_ are set to 0.

[[KLEE-GR-error-state-locker-is-only-MDH,GR29]]GR29::
A locker in an Error State holds only its MDH, and its size (<<KLEE-instruction-size>>) is 16 bytes.

[[KLEE-GR-error-state-can-be-reconfigured,GR30]]GR30:: A locker in an Error State can still be reconfigured, cloned or cleared; apart from clearing it, `kl.setst` can only change its Error State.

[[KLEE-GR-error-state-exported-as-MDH,GR31]]GR31:: A locker in an Error State is exported as its MDH alone, with all its fields and without `kl.mgmt`, and a single `kl.mgmt` re-imports the image (<<KLEE-error-state-transfer>>), so that software can handle the error even after a context switch.

[[KLEE-GR-usage-locker-error-state,GR32]]GR32:: An attempt to _use_ a locker in an Error State performs no operation, and in particular leaves the _State_ unchanged.
Although such an attempt is an error that would otherwise transition the locker to _Invalid_, keeping the _State_ lets software address the original error condition; the architecture keeps no history of Error States.
+
A usage instruction with an output operand that performs no operation under this Rule or under <<KLEE-GR-gate-order>> (_Unconfigured_, Error State, or expiration), or that transitions its locker to an Error State during execution, writes zeros to every byte of its output window that it has not written: elements [`vstart`, `vl`-1] of `Vd` for a vector output, bytes [`klstart`, `kliobuftop`-1] for a KLIOBUF output.
An in-place operation thus never leaves its input in place of the output it did not produce.

[[KLEE-GR-transition-to-from-unconfigured,GR33]]GR33:: Only a configuration instruction can transition a locker from _Unconfigured_ to a Complete State.
Any usage instruction (<<KLEE-instruction-properties>> in Rule <<KLEE-GR-usage-policy>>) in State _Unconfigured_ performs no operation and raises no exception: the locker stays _Unconfigured_, and an output operand is zeroed as Rule <<KLEE-GR-usage-locker-error-state>> prescribes; `kl.derive` has no output operand, and performs no operation if either endpoint is _Unconfigured_.
A locker leaves an Error State for _Unconfigured_ through `kl.clear` or `kl.clearall`, a `kl.rename` naming it as source, a `kl.clone` or `kl.rename` naming it as destination with an _Unconfigured_ source, a `kl.swap` with an _Unconfigured_ locker (<<KLEE-instruction-clone>>), or a re-opening for provisioning or import.

[[KLEE-GR-getmdto-from-unconfigured,GR34]]GR34:: `kl.getmd*` (<<KLEE-instruction-getmd>>) reads the MDH of an _Unconfigured_ locker as all zeros.

[[KLEE-GR-cleared-under-management,GR35]]GR35:: On a locker that is _Unconfigured_ or in an Error State, `kl.load`, `kl.store`, `kl.mvin`, `kl.mvout` and `kl.mgmt` with `kl_cfg_management_end` perform no operation and raise no exception; so does `kl.mgmt` with `kl_cfg_exporting`, since the short export path of an Error-State locker uses no `kl.mgmt` (<<KLEE-error-state-transfer>>).
When `klmanagedlocker` = 32, the value a clear leaves (<<KLEE-CSR-klmanagedlocker>>), `kl.mvin` and `kl.mvout` likewise perform no operation and raise no exception; so do `kl.load` and `kl.store` with `Xl` = 0, before any check of `Zklio` or of the KLIOBUF.
These outcomes follow the checks that do not depend on the _State_: the first group of <<KLEE-illegal-instruction-grounds>>, the KLEE fatal-error, missing-CSK and locker-Off exceptions, for `kl.mgmt` the check of `klmanagedlocker`, and for `kl.load` and `kl.store` with `klmanagedlocker` < 32 the check that `Xl` is 0 (<<KLEE-illegal-instruction-grounds>>).
In detail:
+
--
* `kl.load` and `kl.store` have an empty transfer window, whatever `klstart` holds: they access no memory and retire with `klstart` = 0, but can still raise the address-misaligned exception (<<KLEE-instructions-memory>>).
With `klmanagedlocker` = 32 the address is not checked for alignment, as for `kl.input` and `kl.output`.
* `kl.mvin` and `kl.mvout` leave `klstart` unchanged, whatever its value; `kl.mvout` writes zeros, as when `klstart` {ge} `image_end` (<<KLEE-instruction-mv>>).
* `kl.mgmt` reads neither its auxiliary operand nor the KLIOBUF, so Rules <<KLEE-GR-vector-MDH-operand>> and <<KLEE-GR-iobuf-configured>> do not apply; it leaves the authentication registers unchanged and performs only its common steps (<<KLEE-locker-management>>), which leave `klstart` = 0, and `klmanagedlocker` = 32 on an _Unconfigured_ locker and the locker's number on an Error-State one.
On a locker in a Valid State, `kl_cfg_management_end` still raises an illegal-instruction exception.

Software that exports a locker must rely on the image only if the _State_ read after the last instruction of the export, or in the MDH that `kl.getmd*` returned when the image is the MDH alone, is not _Unconfigured_.
--

[NOTE]
====
The Rule closes a _check-then-use race_: between a _State_ check and the next instruction, a handler may clear a locker being provisioned or imported, which sets `klmanagedlocker` to 32 and forces a restart (<<KLEE-CC-management>>), or set an Error State.
The instructions that follow then perform no operation, instead of acting on the KLIOBUF or trapping, and the next check detects the change; only a `KLML` opening traps, with `klmanagedlocker` = 32 (Rule <<KLEE-GR-klml-openings>>).
Only the check after the last instruction is therefore required; earlier checks only react sooner.
An export cannot restart, since the clear destroys its CC.
====

=== Rules governing Configuration States

[horizontal]
[[KLEE-GR-opening-locker-when,GR36]]GR36:: _When a locker can be opened for import or export:_
Opening a locker for provisioning or import, and executing `kl.clear`, is allowed in every State, since the locker is zeroized first; opening it for export is allowed in every Complete or Configuration State, and performs no operation on an _Unconfigured_ locker (Rule <<KLEE-GR-cleared-under-management>>).
No Machine may set conditions under which a locker can be opened for export or import, or cleared.

[[KLEE-GR-config-instructions-config-state,GR37]]GR37:: The following configuration instructions, which Usage Control policies do not gate, are also allowed on a locker in a Configuration State: `kl.size`, `kl.avail`, `kl.getmd*`, `kl.getst`, `kl.setst` with the immediate `kl_state_unconfigured` (`kl.clear`) or an Error State, `kl.clearall`, `kl.clone` naming the locker as destination, and `kl.rename` and `kl.swap`, which move a CC unchanged (<<KLEE-instruction-clone>>).

[[KLEE-GR-zkl-load-mv-allowed,GR38]]GR38:: `kl.load` and `kl.mvin` are allowed in States `kl_cfg_provisioning`, `kl_cfg_importing` and `kl_cfg_ppi_importing`, on the locker that `klmanagedlocker` names (Rule <<KLEE-GR-locker-less-transfers>>).

[[KLEE-GR-zkl-store-mv-allowed,GR39]]GR39:: `kl.store` and `kl.mvout` are allowed in States `kl_cfg_exporting` and `kl_cfg_ppi_exporting`, on the locker that `klmanagedlocker` names (Rule <<KLEE-GR-locker-less-transfers>>).

[[KLEE-GR-usage-locker-config-state,GR40]]GR40:: Using a locker in a Configuration State, cloning from it, or restricting it raises a KLEE privilege-violation exception.
The locker's _State_ is unchanged so that the management operation under way can complete: a handler must not set an Error State on such a locker (<<KLEE-error-architecture>>).
A locker in State `kl_cfg_exporting` holds the only copy of its CC (<<KLEE-CC-management>>), which an Error State would destroy.
<<KLEE-instruction-clone>> covers such a locker as the destination of a `kl.clone`, or as both its source and destination.

[[KLEE-GR-completion-state,GR41]]GR41:: The `kl.mgmt` that completes a management operation (<<KLEE-locker-management>>) leaves the locker:
+
--
* after a provisioning, in State _Ready_, with _StateExtension_ and _MachineUse_ zero;
* after an import or an export, in the _State_ supplied in `ml`, that is, the one the locker had when it was exported, resp. when the export was opened, which may itself be a Configuration State; an import thus restores the _State_ and _StateExtension_ that the locker had at export, the latter carried in the SCC; or
* in an Error State, or in _Failure_, if a check made at completion fails: _Authentication Failed_ for the `SIV` check, and otherwise the outcome that the failing check prescribes.
--

=== Derivation Rules

[horizontal]
[[KLEE-GR-checks,GR42]]GR42:: The checks of <<KLEE-GR-gate-order>> apply to both lockers, in the order that <<KLEE-GR-gate-order>> gives for `kl.derive`.
The following checks are then made in order; a failed check transitions the failing locker or lockers to Error State _Invalid_, and nothing is transferred:

. The _State_ and _StateExtension_ of the source must define a source endpoint (<<Zkl-ISA-machines.adoc#KLEE-derive-endpoints>>); otherwise the source transitions.
. The _State_ and _StateExtension_ of the destination must define a destination endpoint. A key field, that is, a symmetric or private key, is a destination endpoint only in State _Ready_ or in a State that the Machine names for loading it, such as _Set_Key_ of HMAC (<<Zkl-ISA-machines.adoc#KLEE-HMAC>>) or _Set_Scalar_ of ECC (<<Zkl-ISA-machines.adoc#KLEE-ECC>>), and never when the destination _KeyType_ is 1 (Rule <<KLEE-GR-SKID-no-export>>). Otherwise the destination transitions.
. The two endpoints must form a pair that Rule <<KLEE-GR-shared-secret>>, <<KLEE-GR-exec-implies-unrestricted>> or <<KLEE-GR-DRBG-implies-unrestricted>> admits, or that <<Zkl-ISA-machines.adoc#KLEE-Machines>> explicitly defines; otherwise both lockers transition.
. The effective length (Rule <<KLEE-GR-derive-rule-both-fixed-size>>) must meet the minimum, upper limit and granularity of the pair, and the transferred data any other constraint of the destination; otherwise the destination transitions.
. A destination key field of `dest_length` bytes requires `length` {ge} `dest_length`, and a source field, or remaining `kl.exec` output, of at least `dest_length` bytes; otherwise the destination transitions. The key field receives exactly `dest_length` bytes, which complete its loading; a key written in State _Ready_ is followed by the initialization that the Machine performs in that State.

[[KLEE-GR-narrowing,GR43]]GR43:: Before any _restricted transfer_, the _SCProtection_ of the destination locker is compared with that of the source.
If it is lower, the destination transitions to Error State _Privilege Violation_ and nothing is transferred: a narrowing never raises the level of the destination (<<KLEE-Metadata-narrowing>>), and the secret would otherwise be used with weaker side-channel protection than its source requires.
Otherwise the MDH of the source narrows that of the destination (<<KLEE-Metadata-narrowing>>).
If the narrowing fails, the destination transitions to Error State _Privilege Violation_ and nothing is transferred.

[[KLEE-GR-unrestricted,GR44]]GR44:: An _unrestricted transfer_ applies no policy narrowing.

The narrowing of restricted transfers follows NIST SP 800-57 Part 1 Rev. 5 cite:[nist-SP-800-57-p1-r5], §6.2.1 (key-usage and cryptoperiod metadata protection), and NIST SP 800-108r1 cite:[nist-SP-800-108-r1] §8 (derived keys inherit the security strength and use constraints of the key-derivation key): these Recommendations expect derived material to inherit every constraint of its parent.
Any further transfer that a Machine defines must respect these restrictions.

[horizontal]
[[KLEE-GR-SKID-no-export,GR45]]GR45:: A field configured by a SKID is _never_ exportable, and a key field of a locker whose _KeyType_ is 1 is _never_ importable. No rule may be defined to export or import such a field.

[[KLEE-GR-shared-secret,GR46]]GR46:: Moving a shared secret from a key-agreement or key-encapsulation Machine, such as the ECC `SecondPt` or the ML-KEM `sharedkey`, into a key field of a symmetric Machine, a private key field of a public-key Machine, or the `kl.exec` input of a hash, MAC or XOF is a _restricted transfer_.
It is admitted whenever both endpoints are defined (Rule <<KLEE-GR-checks>> items 1 and 2); a key field receives the first `dest_length` bytes of the secret (Rule <<KLEE-GR-checks>> item 5).
A hash, MAC or XOF that receives a shared secret this way may output its digest, tag or output stream through `kl.exec`, within the policies of its narrowed MDH: the one-way function protects the secret, and its output is the derived value that a key derivation would otherwise produce.

[[KLEE-GR-exec-implies-unrestricted,GR47]]GR47:: The `kl.exec` _output_ of a source locker, listed in <<Zkl-ISA-machines.adoc#KLEE-derive-endpoints>> as a source endpoint, is the data that the Form C `kl.exec` instructions permitted in its current _State_ would emit; the tag of an AEAD Machine is not such output, unless that Machine explicitly allows it.
The `kl.exec` output can always be moved, as an _unrestricted transfer_, into a destination endpoint that Form B `kl.exec` instructions load in the current _State_ of the destination, such as the `kl.exec` input of a hash function, MAC or XOF, or the `Scalar` of an ECC Machine in State _Set_Scalar_: the transfer is a shortcut for `kl.exec` instructions that software could issue on both lockers.
+
NOTE: Such transfers are allowed and unrestricted because the caller can obtain the source data and freely write the destination fields, so the attack surface does not increase.
// NOTE: Such a destination may be a key field, such as the `Scalar` of an ECC Machine or the `K0` of HMAC. Moving any `kl.exec` output into it does not increase the attack surface, which is why
// software can always provision a new locker with a key of its choice and any policies, and use it in place of a locker whose key it does not know.
+
_Key derivation._ The `kl.exec` output of a hash function, MAC or XOF can also be moved, as an _unrestricted transfer_, into a key field of a symmetric Machine or a private key field of a public-key Machine, in a State where Rule <<KLEE-GR-checks>> item 2 admits that field; the key field receives the first `dest_length` bytes of the output (Rule <<KLEE-GR-checks>> item 5).

[[KLEE-GR-DRBG-implies-unrestricted,GR48]]GR48:: A Machine implementing a DRBG (none is currently architected) may generate random data into a symmetric or private key field of a destination Machine in a State that admits the field (Rule <<KLEE-GR-checks>>).
This is an _unrestricted transfer_, since the output of a DRBG must neither predictably repeat a value nor be extrapolable from previous or later outputs.

//

A pair defined in <<Zkl-ISA-machines.adoc#KLEE-Machines>> may further narrow, but never relax, any policy.

An _exportable field_ is one that its Machine lists as a source endpoint in <<Zkl-ISA-machines.adoc#KLEE-derive-endpoints>>, and an _importable field_ one that it lists as a destination endpoint.
Rules <<KLEE-GR-shared-secret>>, <<KLEE-GR-exec-implies-unrestricted>> and <<KLEE-GR-DRBG-implies-unrestricted>> admit pairs of endpoints; any other pair not explicitly defined in <<Zkl-ISA-machines.adoc#KLEE-Machines>> fails Rule <<KLEE-GR-checks>> item 3.

[horizontal]
[[KLEE-GR-derive-rule-both-fixed-size,GR49]]GR49:: _Transfer Size Rule:_
A destination field of `dest_length` bytes receives `eff_length` = min(`length`, `dest_length`) bytes, zero-filled beyond them except for a key (Rule <<KLEE-GR-checks>>); any other destination receives `eff_length` = `length` bytes.
With `length` = 0 nothing is transferred: a key field fails the key-length check of Rule <<KLEE-GR-checks>> item 5, and its locker transitions to Error State _Invalid_; for any other destination the instruction changes no state, if the other checks of that Rule pass.
+
The source supplies `eff_length` bytes: a field is truncated or zero-padded to that length, and a source that produces `b`-byte blocks produces as many as needed.
The destination consumes them in equal-sized blocks, a shorter final block as a `kl.exec` with a shorter input would.
Each endpoint advances as the `kl.exec` operations producing or consuming these blocks would; a destination State implemented by `process_VLI` may be left open and continued with `kl.exec`.
+
If the source produces `p`-byte units and the destination consumes `q`-byte units, `p` and `q` being the granularities of the two States, one must divide the other, so that the implementation can split one output into `p/q` inputs, or join `q/p` outputs into one input, without carrying partial state from one internal transfer of `max(p,q)` bytes to the next.
+
The interruption points of a `kl.derive` (<<KLEE-CSR-klstart>>) are the `klstart` values that are interruption points in the current States of both endpoints.
A `kl.derive` into a key field is uninterruptible (Rule <<KLEE-GR-uninterruptible-instructions>>): its only interruption point is 0, so the key, and the initialization that the Machine performs in _Ready_, complete in one execution, and no locker is ever usable with a partly written key.

[[KLEE-Memory-Model]]
=== Memory Model Rules

In these rules, a _KLEE memory instruction_ is `kl.load`, `kl.store`, `kl.input` or `kl.output`.

[horizontal]
[[KLEE-GR-memory-program-order,GR50]]GR50:: KLEE memory instructions appear to execute in program order on the local hart.

[[KLEE-GR-memory-rvwmo,GR51]]GR51:: At the instruction level, KLEE memory instructions follow RVWMO, and, with `Ztso`, also RVTSO.

[[KLEE-GR-idempotent-memory,GR52]]GR52:: KLEE memory instructions support only idempotent memory: they make no component access to a non-idempotent or side-effecting PMA region.
An instruction whose component access would touch such a region halts precisely at the last prefix-complete point before the offending byte, with the completed prefix committed (Rule <<KLEE-GR-which-resumable-instructions>>), and raises a load, resp. store, access-fault exception, with `xepc` at the instruction and `xtval` holding the offending address.
Re-execution raises the same exception before any component access, unless the offending byte no longer maps to such a region.

[[KLEE-rule-memory-instruction-decomposed,GR53]]GR53:: A KLEE memory instruction may be decomposed into component memory operations of any granularity, issued in any order that the memory model and the semantics of `kl.exec`, `kl.load`, `kl.store`, `kl.input` and `kl.output` allow, and none is required to be atomic; ordering within one instruction follows RVWMO, even with `Ztso`.
On a precise interruption, `klstart` records a _prefix-complete_ point of the transfer: an offset below which every component access has been performed, and at or beyond which none has had an architecturally visible effect.

[[KLEE-GR-memory-observation,GR54]]GR54:: Other harts observe the component memory operations as ordinary memory operations under RVWMO, with no ordering among them guaranteed before the instruction completes.
A buffer that a KLEE memory instruction accesses therefore needs the same synchronization to be shared as one that an ordinary software loop accesses.

[[KLEE-GR-memory-fences,GR55]]GR55:: For `FENCE`, `FENCE.I`, `SFENCE.VMA` and the `.aq`/`.rl` annotations, the component accesses of a KLEE memory instruction are ordinary loads (`kl.load`, `kl.input`) or stores (`kl.store`, `kl.output`) of the issuing hart.

=== State change rule for exceptions

[horizontal]
[[KLEE-exception-state-change,GR56]]GR56:: An illegal-instruction exception, or a KLEE exception other than the fatal-error one, leaves the KLEE state unchanged, except for two changes that `kl.mgmt` makes even if it later raises an exception (<<KLEE-locker-management>>): a `kl.mgmt` that opens a provisioning or an import zeroizes the target locker and writes its number to `klmanagedlocker`, and any `kl.mgmt` that passes the check of `klmanagedlocker` (<<KLEE-locker-management>>) clears `klstart`.
A KLEE fatal-error exception resets the KLEE state (_Fatal Conditions_ below).


[[KLEE-resumability]]
=== Interruptibility and Resumability of KLEE instructions

[horizontal]
[[KLEE-GR-uninterruptible-instructions,GR57]]GR57:: `kl.mgmt`, `kl.getmd*`, `kl.getml`, `kl.setml`, `kl.setmli`, `kl.restrict*`, `kl.clone`, `kl.rename`, `kl.swap`, non-vector `kl.mvin` and `kl.mvout`, `kl.size`, `kl.avail`, and a `kl.derive` into a key field (Rule <<KLEE-GR-checks>> item 5) are architecturally _uninterruptible_: each completes, raises an exception with only the effects of <<KLEE-exception-state-change>>, or has no architecturally visible effect.
An implementation achieves this by:
+
--
. completing the instruction before taking an asynchronous interrupt;
. completing it in the background, where Rule <<KLEE-GR-long-running-no-data>> permits, subject to Rule <<KLEE-GR-conflicting-access-rule>>; or
. discarding partial work before taking the trap and restarting on return, with a documented minimum uninterrupted progress, or maximum number of consecutive restarts, that prevents livelock.

Software interacts with an uninterruptible instruction as Rule <<KLEE-SR-uninterruptible>> states.
--

[[KLEE-GR-no-intra-interruption-points,GR58]]GR58:: The architecture specifies no interruption point within `kl.setst` or within a single block-processing unit of `kl.exec`; an implementation may nevertheless make a long-running instance of either interruptible, as Rule <<KLEE-GR-long-running-no-data>> allows.

[[KLEE-GR-resumability-options,GR59]]GR59:: When a handler accesses an input, output or locker of a preempted instruction, or other KLEE state it may affect, the implementation chooses one of:
+
--
. _Background completion:_ the hart waits for the instruction to complete; not available for `kl.load`, `kl.store`, `kl.input` and `kl.output`, which are memory instructions.
. _Atomic completion_ before any asynchronous interrupt is taken.
. _Precise halt and resumption:_ the instruction halts with `klstart` at a prefix-complete point (<<KLEE-Memory-Model>>) and resumes from it, advancing by at least one granule per attempt.
. _Timeout, then precise halt and resumption:_ as option 3, after a timeout that the system may impose.
. _Precise halt and restart,_ for `kl.load`, `kl.store`, `kl.input` and `kl.output` only with a documented maximum number of consecutive restarts of one execution, after which that execution uses option 3; available only for `kl.load`, `kl.store`, `kl.input` and `kl.output`, whose transfers are idempotent, and for the operations of Rule <<KLEE-GR-long-running-no-data>>.

Block-iterated `kl.exec`, `kl.derive` and vector `kl.mvin` and `kl.mvout` use option 3 or 4 (Rule <<KLEE-GR-block-iterated-instructions>>).
A synchronous exception raised by a component access always halts the instruction precisely, with `klstart` at the last prefix-complete point before the faulting byte, as RVV 1.0 §3.7 prescribes for `vstart`.
--

[[KLEE-GR-long-running-no-data,GR60]]GR60:: A `kl.exec`, `kl.setst` or `kl.derive` whose Machine semantics access no memory, vector register or KLIOBUF, and no GPR other than scalar operands captured at issue (Rule <<KLEE-GR-conflicting-access-rule>>), may be _long-running_. Examples are scalar multiplication, key generation or signing.
+
On preemption it may behave as any option of Rule <<KLEE-GR-resumability-options>> that the interrupt or exception allows; the implementation supports at least one of options 3, 4 and 5, and under option 5 documents a minimum uninterrupted progress, or maximum number of consecutive restarts, that prevents livelock.
If the operation continues in the background while the hart is preempted, any instruction that wants to access the affected state will wait for it to be available, even if in a handler, nested ones included.

[[KLEE-GR-long-running-progress,GR61]]GR61:: A long-running operation (Rule <<KLEE-GR-long-running-no-data>>) that halts and resumes records its progress in _MachineUse_ (not in `klstart`), in an implementation-defined format, and keeps its intermediate results in the ADS, updating the architected Content only at completion; _MachineUse_, which records the progress, is part of the MDH.
Hence the architected Content does not depend on its progress and a restart starts from that Content alone.
It may halt only where the recorded state cannot be consumed against other inputs, which Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-progress-discard>> ensures by discarding that state on every transition of the locker's _State_ other than completion.
+
An import may discard the ADS and restart the operation, and must restart it whenever it completes without `Content2`, for any reason, such as an Implementation Qualifier mismatch, a failed `SIV2` check or _ADSDropped_ = 1 (<<KLEE-SCC-import>>), for instance as a result of an intervening `kl.clearads` (<<KLEE-instruction-clearads>>).
`kl.clone` likewise restarts the operation in the copy (<<KLEE-instruction-clone>>).
A restart zeroes the progress and destroys every value drawn or computed for the operation (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-progress-discard>>).
+
A Machine may nevertheless keep in the architected Content a value the algorithm draws, such as the `RndNum` of the ECC Machines (<<Zkl-ISA-machines.adoc#KLEE-ECC>>) or the `rnd` of ML-DSA (<<Zkl-ISA-machines.adoc#KLEE-PQC-ML-DSA>>), since it is architected state.
Even though it is meaningful only while the progress is non-zero, and is discarded on restart, this does not make it implementation-specific.

[[KLEE-GR-conflicting-access-rule,GR62]]GR62:: Every option of Rule <<KLEE-GR-resumability-options>> obeys one rule: before the issuing hart performs a _conflicting access_, the in-flight operation must have completed, or have halted precisely with `klstart` set as <<KLEE-Memory-Model>> requires.
A conflicting access is:
+
--
* an ordinary load or store overlapping the memory region of the in-flight KLEE operation;
* an access to a locker that the operation uses, including the issue of another KLEE instruction involving it;
* a read or write of `klstart`, `vstart`, `klmanagedlocker` or a KLIOBUF CSR, including by `kl.getml`, `kl.setml` and `kl.setmli`, since the operation may still update them (Rule <<KLEE-GR-klstart-vstart>>, <<KLEE-locker-management>>);
* the issue of a KLEE instruction that reads or writes the authentication registers `SIV`, `IMPQUAL` and `SIV2` (<<KLEE-KLF>>), such as a `kl.mgmt` that opens an export or an import, while the operation reads or writes them;
* a read or write of a GPR or vector register that the operation writes; or
* a write to a vector register or to the KLIOBUF that the operation reads, including the issue of a `kl.input` targeting it.
Scalar operands in GPRs are captured at issue, so accessing them is not a conflicting access.

This Rule and Rule <<KLEE-GR-resumability-options>> make asynchronous execution by the KLEE unit invisible to same-hart program order, as <<KLEE-Memory-Model>> requires.
Beyond them, the architecture specifies only the allowed interruption points of its instructions and Machines.
--

[[KLEE-GR-which-resumable-instructions,GR63]]GR63:: The resumable instructions are `kl.exec`, vector `kl.mvin` and `kl.mvout`, `kl.derive` other than into a key field (Rule <<KLEE-GR-uninterruptible-instructions>>), `kl.load`, `kl.store`, `kl.input` and `kl.output`, which architecturally process their input units serially.
On a precise halt, the completed prefix is committed, the failing and subsequent units have no effect, `klstart` records a prefix-complete point, and the instruction does not retire, `xepc` holding its address.
If the instruction transitions its locker to an Error State after partial progress, the completed prefix remains committed, the unwritten part of its output window is zeroed (Rule <<KLEE-GR-usage-locker-error-state>>), and the instruction retires (<<KLEE-CSR-klstart>>).

[[KLEE-GR-block-iterated-instructions,GR64]]GR64:: For a block-iterated `kl.exec`, `kl.mvin`, `kl.mvout` or `kl.derive`, the fully processed blocks remain written or transferred, at both endpoints of a transfer, and `klstart` records their total byte count.
A partially executed instruction commits exactly the state that a shorter instruction performing only the completed operations would commit, including the locker, `klstart`, and the `*llockerstatus` and effective `KLS` fields, so that context save, restore and resumption remain consistent.
Implementations must honor `klstart` for `kl.exec` and `kl.derive`.
A handler that resets `klstart` to 0 to make the instruction execute anew over its whole window, but from the state that the completed prefix committed, may lead to partial plaintext leakage, or multi-use pads.
This is the rationale for Rule <<KLEE-SR-klstart-no-reset>>.
The state that a halted instruction leaves is described entirely by the locker, `klstart`, `vstart` and, for the long-running operations of Rule <<KLEE-GR-long-running-no-data>>, the progress recorded in _MachineUse_ and the ADS.

[[KLEE-GR-memory-instructions,GR65]]GR65:: KLEE memory instructions are RISC-V memory instructions: one completes, and may retire or take a trap with `xepc` past it, only after every component access has passed address translation and permission checks and has been performed.
Otherwise, as for vector memory operations, the implementation triggers a precise load/store page-fault, guest-page-fault or access-fault exception for that execution attempt, with `klstart` at a prefix-complete point that the instruction permits.

NOTE: After the last `kl.load`, `kl.store`, `kl.mvin` or `kl.mvout` of a management operation, the caller checks whether the locker is _Unconfigured_; checking after each one only reacts sooner.
With `kl.getst Xd, KLML` (Rule <<KLEE-GR-klmanagedlocker-override>>) the check needs no locker number, and reads zero once a clear has reset `klmanagedlocker` to 32.
If the locker is _Unconfigured_, a handler has cleared it, and the software restarts the entire configuration operation, not only the memory operation.
A memory operation issued or resumed after the locker was cleared performs no operation, so the caller always reaches this check (Rule <<KLEE-GR-cleared-under-management>>).

The items below collect the error conditions that the specification states where they arise.

Fatal Conditions:::
+
--
Fatal conditions have the highest priority among the KLEE-specific error categories.
The main one is an integrity failure of a hart's KLF (<<KLEE-KLF>>); implementations may define others.

A fatal condition causes a KLEE unit reset of the hart (<<KLEE-reset-and-m-mode-only>>), followed by a KLEE fatal-error exception.
The reset differs from an ordinary one in two ways:

. `misa.L` keeps its value, and every `KLS` field not Off becomes Dirty rather than Off, so that the KLEE fatal-error exception can be reported, the modes below M-mode are not silently disabled, and context-switching code can discard its stale saved state; and
. every `*llockerstatus` field becomes _Dirty_ rather than _Initial_.

A CSK generated at boot under the fourth model of <<KLEE-CSK-requirements>> is shared by the harts of its subsystem and is not regenerated.

Detection and reset may be synchronous or asynchronous; the KLEE unit records the condition.
The first KLEE instruction or KLEE CSR access issued, or in flight, after detection performs no operation and raises a KLEE fatal-error exception, with `xepc` holding its address.
If, at detection, a `KLS` field in effect is Off or the KLEE bit of an `*stateen0` CSR in effect is clear, the condition is retained and reported on the first KLEE instruction or KLEE CSR access not illegal on those grounds; until then, such instructions raise an illegal-instruction exception, which <<Zkl-ISA-priv.adoc#KLEE-exception-codes>> ranks above the KLEE fatal-error exception.
No CPU state thus disables detection; it only defers reporting.
--

[[KLEE-illegal-instruction-grounds,Illegal-Instruction Exceptions]]
Illegal-Instruction Exceptions:::
+
--
The grounds for an illegal-instruction exception form two groups:

* The first group depends only on the instruction encoding, the GPRs and the vector configuration, not on the state of the KLEE unit, and therefore takes precedence over the KLEE fatal-error exception (<<Zkl-ISA-priv.adoc#KLEE-exception-codes>>):

. A reserved encoding, including `kl.setst` with `#immed7` 46, 47, 54 or 55, or 53 without `Zklexpire`, `kl.mgmt` with `#immed7` in 59–62 or in Form B, `KLML` on an instruction that Rule <<KLEE-GR-klmanagedlocker-override>> does not list, or on `kl.setst` with `#immed7` = `kl_cfg_clearall`, and a KLEE instruction with a vector operand issued while `vtype.vill` is set (<<KLEE-KLV>>).
. An indirect locker index outside [0..31], `X0` as an indirect locker index register where it does not encode `KLML` (Rules <<KLEE-GR-GPR-indirect>> and <<KLEE-GR-klmanagedlocker-override>>), or a `kl.derive` with equal locker indices (<<KLEE-instruction-derive>>).
. A GPR pair or quartet not meeting Rule <<KLEE-GR-multiple-GPRs>>.
. A vector operand carrying an MDH with `VL` {times} `SEW` < 128 (Rule <<KLEE-GR-vector-MDH-operand>>), other than that of `kl.mgmt`, an instruction with a vector operand that produces no `vstart` value issued with `vstart` {ne} 0 (Rule <<KLEE-GR-vector-legality>>), or a vector `kl.mvin` or `kl.mvout` whose `vl * (SEW/8)` or `vstart * (SEW/8)` is not a multiple of 16 (<<KLEE-instruction-mv>>).
. An encoding of an unimplemented extension, such as Forms A–C of `kl.exec` without `Zklv`.
. A KLEE instruction or KLEE CSR access gated by a clear `Smstateen` bit (<<Zkl-ISA-priv.adoc#KLEE-CSRs-priv>>), with an illegal-instruction exception as that extension prescribes; a KLEE instruction issued while `KLS` is Off (see _Fatal_ above) or under big-endian effective data endianness (<<Zkl-notation.adoc#KLEE-Notation>>); or an access to a CSR that <<KLEE-CSRs-unpriv>> declares unavailable, or that <<Zkl-ISA-priv.adoc#KLEE-CSRs-priv>> makes inaccessible from the current mode, with an illegal-instruction exception as stated there.

* The second group depends on the state of the KLEE unit, mostly on a locker's contents.
  Its grounds are evaluated after the KLEE missing-CSK exception and the _Off_ gate, for a locker marked _Off_ (<<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>>) once it is lazily loaded or by the M-mode code that emulates it; a pending fatal condition raises a KLEE fatal-error exception instead.
  For a usage instruction they follow the order of <<KLEE-GR-gate-order>>:

. `kl.load`, `kl.store`, `kl.mvin` or `kl.mvout` on a locker whose _State_ does not admit the transfer, or with a `klstart` that is not a multiple of 16 (<<KLEE-mv-locker-checks>>), other than an _Unconfigured_ or Error-State locker, on which the instruction performs no operation.
. `kl.mgmt` when `klmanagedlocker` names another locker, when opening a provisioning, an import or an export on `KLML` while `klmanagedlocker` = 32 (Rule <<KLEE-GR-klml-openings>>), when completing with an `ml`._State_ inconsistent with the locker's Configuration State, or when issuing `kl_cfg_management_end` on a locker in a Valid State (<<KLEE-locker-management>>).
. A KLIOBUF substitution that <<KLEE-usage-input-output>> forbids, such as a Form B or C `kl.exec` where Form A is expected, or any substitution without `Zklio`. This ground depends on the _State_, which defines the operation and thus whether a Form is a substitution.
. A `kl.mgmt` that must read its MDH from a vector operand with `VL` {times} `SEW` < 128, or, in Form A, from a configured KLIOBUF with `kliobuftop` < 16 (Rule <<KLEE-GR-vector-MDH-operand>>).
. A Form A–C `kl.exec` with `klstart` {ne} `vstart` {times} `SEW` / 8 (<<KLEE-CSR-klstart>>).
. `kl.load` or `kl.store` with `Xl` {ne} 0: with `klmanagedlocker` < 32, always (<<KLEE-instruction-load>>, <<KLEE-instruction-store>>); with `klmanagedlocker` = 32, that is, as `kl.input` or `kl.output`, on an implementation without `Zklio`. A missing CSK and an unconfigured KLIOBUF raise the KLEE missing-CSK and unconfigured-KLIOBUF exceptions instead (<<KLEE-CSK-requirements>>, Rule <<KLEE-GR-iobuf-configured>>).
--

// Exceptions and State Changes::: [[KLEE-exceptions-and-state-changes,Exceptions and State Changes]]
// When a KLEE instruction raises a KLEE missing-CSK exception, KLEE locker-Off exception, KLEE unsupported-Metadata exception, KLEE out-of-memory exception, KLEE privilege-violation exception or unconfigured-KLIOBUF exception, it has changed no KLEE state, unless its description states a change that precedes the exception. `kl.mgmt` is the one instruction that does: it zeroizes the target locker before its checks.

[[KLEE-unsupported-handling,Unsupported Metadata]]
Unsupported Metadata:::
+
--
Unsupported Metadata at provisioning or import raises a KLEE unsupported-Metadata exception and leaves the locker _Unconfigured_, with `klmanagedlocker` naming it (<<KLEE-CSR-klmanagedlocker>>).

A handler below M-mode cannot emulate the Machine and treats the exception as unresolvable.

An M-mode handler that emulates the Machine instead sets the locker's `*llockerstatus` field to _Off_ (<<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>>), so that every later access to the locker, except by a <<KLEE-destructive-config,destructive configuration instruction>>, traps.
The emulator then holds the locker in its own protected memory and services every operation on it, including SCC import and export.
For these, it needs either (a) the CSK and the Locality Secrets of the HW Binding Group, inputs of `SCC_Encrypt` and `SCC_Decrypt` (<<KLEE-SCC-AEAD>>) that it cannot otherwise obtain, or (b) implementation-specific primitives that compute these functions for it.

An emulator keeps one copy per locker slot and replaces it:

. at the next KLEE unsupported-Metadata exception on that slot; or
. at an emulated `kl.clone` naming the slot as destination, which also clears the slot's hardware locker and marks it _Off_, since the clone of an emulated locker is emulated too.

A copy orphaned by a <<KLEE-destructive-config,destructive configuration instruction>> is never used again but lingers until replaced.
As a robustness recommendation, as for a cleared locker (<<KLEE-instruction-clear>>), an emulator should zeroize a copy whose _Off_ mark is gone before M-mode next returns control to a less privileged mode; checking `mllockerstatus` whenever it runs finds such copies.

Accessing or using a locker in State `kl_state_unsupported` does _not_ raise a KLEE unsupported-Metadata exception.
--

Other Exception Conditions:::
+
--
The remaining exceptions, in the order of <<Zkl-ISA-priv.adoc#KLEE-exception-codes>>, are:

. *No active CSK.* A KLEE missing-CSK exception on any KLEE instruction or KLEE CSR access that <<KLEE-CSK-requirements>> does not exempt, while no CSK is established or the `mklcsk` group is only partially written (<<Zkl-ISA-priv.adoc#KLEE-CSR-mklcsk>>).
. *Locker marked _Off_.* A KLEE locker-Off exception on any access to the locker other than by a <<KLEE-destructive-config,destructive configuration instruction>> (<<Zkl-ISA-priv.adoc#KLEE-CSR-llockerstatus>>), before any condition that depends on its contents.
  M-mode resolves it or forwards it to the mode that owns the _Off_ field.
. *Usage Control.* A KLEE privilege-violation exception for a usage instruction (<<KLEE-instruction-properties>> in Rule <<KLEE-GR-usage-policy>>) in a mode that the _UsagePolicy_ excludes, and for any use, cloning or restriction of a locker in a Configuration State (Rule <<KLEE-GR-usage-locker-config-state>>).
. *Unreadable secure clock.* A KLEE clock-unavailable exception for a usage instruction on a locker with a non-zero _ExpirationDate_ while the secure clock cannot be read, raised while leaving the _State_ unchanged (<<KLEE-Metadata-expiration-date>>).
. *Insufficient KLF capacity.* A KLEE out-of-memory exception for a `kl.mgmt` opening a provisioning or an import (<<KLEE-locker-management>>) or for `kl.clone` (<<KLEE-instruction-clone>>).
. *Unconfigured KLIOBUF.* An unconfigured-KLIOBUF exception (Rule <<KLEE-GR-iobuf-configured>>).
. *Random bits unavailable.* A KLEE RBG-unavailable exception for an operation whose random bits remain unavailable past the implementation-defined bound of Rule <<KLEE-GR-rbg-failure>>, raised while leaving the _State_ unchanged.
. *Memory exceptions.* The load/store address-breakpoint, address-misaligned, page-fault, guest-page-fault and access-fault exceptions of the component accesses of `kl.load`, `kl.store`, `kl.input` and `kl.output`, ordered as in <<KLEE-instructions-memory>>, with a precise halt (<<KLEE-resumability>>); an access to a non-idempotent region is an access fault (<<KLEE-Memory-Model>>).
--

Errors Not Raising Exceptions:::
+
--
The following conditions set an Error State, or make the instruction perform no operation (<<KLEE-no-operation>>), without an exception, as do the algorithmic errors below.

. *Invalid Metadata or SKID.* _Invalid_, for a `kl.mgmt` opening a provisioning or an import on invalid Metadata (<<KLEE-MVR-open>>), for a SKID other than the all-ones value that the SKS does not or may not resolve (<<KLEE-system-keys>>), and for a `kl.restrict*` request that would widen _MachinePolicy_ or yield invalid Metadata (<<KLEE-instruction-restrict>>).
. *Instruction not allowed in the current State.* _Invalid_, for a `kl.exec` or `kl.setst` not allowed in the current _State_ and _StateExtension_, including an unsupported `#immed7` (Rules <<KLEE-GR-no-exec-in-ready>>, <<KLEE-GR-success-failure>>, <<Zkl-ISA-machines.adoc#KLEE-MGR-not-allowed-instructions>> and <<Zkl-ISA-machines.adoc#KLEE-MGR-policy-gate>>, <<KLEE-instruction-setst>>), and for a `kl.derive` that fails its checks (<<KLEE-instruction-derive>>).
. *Invalid length.* _Invalid_, for an operand whose transfer-window length (`kliobuftop`, or `VL` {times} `SEW` / 8) the Machine does not accept (<<KLEE-CSR-klstart>>, <<KLEE-usage-input-output>>).
. *Expiration.* A usage instruction (Rule <<KLEE-GR-usage-policy>>) on an expired locker, if it can read the secure clock, sets State to _Expired_ and performs no operation.
//; no operation, with _State_ unchanged, if the secure clock cannot be read (<<KLEE-Metadata-expiration-date>>).
. *Policy violation without an exception.* _Privilege Violation_, for a failed narrowing of the Usage Control policies (<<KLEE-Metadata-narrowing>>), whether by the policies of an SKS (<<KLEE-system-keys>>), of a system-specific format (<<KLEE-Machine-version>>) or of the source of a restricted transfer (Rule <<KLEE-GR-narrowing>>); for a `kl.restrict*` request that would widen _Locality_, or make it name an unconfigured entry without a configured substitute (<<KLEE-instruction-restrict>>); and for a restricted `kl.derive` into a locker whose _SCProtection_ is lower than that of its source (Rule <<KLEE-GR-narrowing>>).
. *Use of an _Unconfigured_ or Error-State locker.* No operation, and the _State_ is unchanged (Rules <<KLEE-GR-transition-to-from-unconfigured>> and <<KLEE-GR-usage-locker-error-state>>, <<KLEE-insns-on-unconf-or-error-locker>>).
. *Explicit Error State.* The Error State that a `kl.setst` immediate names (<<KLEE-instruction-setst>>).
. *RBG failure.* _Invalid_, for an operation whose entropy source has failed permanently (Rule <<KLEE-GR-rbg-failure>>).
. *Unusable ADS.* Dropped at import, without rejecting the SCC (<<KLEE-SCC-import>>).

On a locker in an Error State, a `kl.restrict*` request that would set an Error State performs no operation instead, and the Error State is kept (<<KLEE-instruction-restrict>>).
--

Algorithmic Errors:::
+
--
Algorithmic errors occur:

. in SCC management, as Error State `kl_state_mgmt_auth` (_Authentication Failed_), when the `SIV` check fails at the completion of an import (<<KLEE-SCC-import>>) or of an export (<<KLEE-mgmt-completes-export>>); software should therefore check the _State_ after completing an export, as after an import; and
. in the Machines, which may transition the locker to an Error State, as each specifies.
  Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-config-data-error>> distinguishes configuration errors, which lead to _Invalid_, from data errors, which lead to _Failure_.
  Other Machine errors also lead to _Invalid_: a further `kl.exec` in a final-block State (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-single-last-block>>), a violated policy gate or entry condition (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-policy-gate>>), and an RBG failure (Rule <<KLEE-GR-rbg-failure>>).

The verification of an AEAD tag or of a signature in a Machine is not an algorithmic error, even when it fails: the Machine has performed as expected.
--

[[KLEE-GR-gate-order]]
=== Order of Evaluation for Usage Instructions

Priority Order Error Handling Rules:::
+
--
For a usage instruction (<<KLEE-instruction-properties>> in Rule <<KLEE-GR-usage-policy>>), the first group of <<KLEE-illegal-instruction-grounds>> is evaluated first, then the KLEE fatal-error, missing-CSK and locker-Off exceptions (<<Zkl-ISA-priv.adoc#KLEE-exception-codes>>), then the `klstart`/`vstart` check of <<KLEE-CSR-klstart>>.
The conditions on the locker follow in this order, and the first that applies decides the outcome:

. _Unconfigured_: no operation and no exception (Rule <<KLEE-GR-transition-to-from-unconfigured>>);
. Error State: no operation and no exception (Rule <<KLEE-GR-usage-locker-error-state>>);
. Configuration State: KLEE privilege-violation exception, the _State_ unchanged (Rule <<KLEE-GR-usage-locker-config-state>>);
. a forbidden KLIOBUF substitution: illegal-instruction exception (<<KLEE-illegal-instruction-grounds>>);
. _UsagePolicy_: KLEE privilege-violation exception (Rule <<KLEE-GR-usage-policy>>);
. _ExpirationDate_: transition to Error State `kl_state_expired`, then no operation; if the secure clock cannot be read, KLEE clock-unavailable exception, the _State_ unchanged (<<KLEE-Metadata-expiration-date>>);
. a KLIOBUF required by a substitution but unconfigured: unconfigured-KLIOBUF exception (Rule <<KLEE-GR-iobuf-configured>>);
. the Machine's own rules.

For `kl.derive`, each condition is evaluated for both endpoints, the source first, before the next condition; an _Unconfigured_ or Error-State endpoint makes the whole instruction a no-op.
--

[[KLEE-fall-through-summary]]
=== Summary of Behavior of KLEE Instructions on Unconfigured or Error State Lockers

A locker in an Error State is inert: it holds only its MDH (Rules <<KLEE-GR-clear-locker-content-error-state>> and <<KLEE-GR-error-state-locker-is-only-MDH>>).
Usage instructions on such a locker, or on an _Unconfigured_ one, fall through as no-ops or zero writes, so the caller can detect and handle the condition without checking after every instruction, and no time is spent in trap handlers that could not resolve it.

[[KLEE-usage-input-output]]
== Replacing Vector Inputs and Outputs with kl.input and kl.output

With `Zklio`, a Form of `kl.exec`, `kl.setst` or `kl.mgmt` that reads inputs from, or writes outputs to, vector registers, which we call the _native_ form in its Machine and State, may be replaced by the corresponding Form without vector operands, _substitution_, that uses the KLIOBUF for them rather than raising an illegal-instruction exception.

`kl.input` and `kl.output` perform no computation and change only the KLIOBUF and `klstart`; all computation and other state changes remain in `kl.exec`, `kl.setst` and `kl.mgmt`.

The substitutions are:

. a Form D `kl.exec` for a Form A, B or C `kl.exec`; and
. a Form A `kl.setst`, or `kl.mgmt`, for the Form C of the same instruction.

A substitution reads its inputs from, and writes its outputs to, the KLIOBUF:

* A substituted Form A `kl.exec` behaves as a Form A with `Vd` = `Vs2` (<<KLEE-instruction-exec>>):
  each block's output replaces its input at the same offset of the window.
* A substituted Form C `kl.exec` writes its output to [`klstart`, `kliobuftop`-1], clearing the bits it does not produce (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-clear-output>>), and writes no byte outside that range.
* A substituted Form A `kl.setst` reads its auxiliary input from KLIOBUF bytes [0, `kliobuftop`-1], ignoring `klstart`, truncated to the operand width as Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-fixed-width-input>> prescribes.
* `kl.exec` never modifies `kliobuftop`.

A substitution fails as follows:

* Without `Zklio`, it raises an illegal-instruction exception.
* Vector and KLIOBUF operands cannot be mixed: a Form B or C `kl.exec` issued where Form A is
  expected raises an illegal-instruction exception.
* If `kliobuflen` is zero, it raises an unconfigured-KLIOBUF exception.
* If `kliobuflen` is non-zero but `kliobuftop` is an invalid length for the Machine, the locker transitions to Error State _Invalid_, whether the KLIOBUF serves as input or only as output (<<KLEE-CSR-klstart>>); for an MDH operand, however, `kliobuftop` < 16 raises an illegal-instruction exception (Rule <<KLEE-GR-vector-MDH-operand>>).

Where <<Zkl-ISA-machines.adoc#KLEE-Machines>> says that a Form of `kl.exec`, `kl.setst` or `kl.mgmt` is _expected_, rather than _required_ or _the only Form allowed_, the substitutions above apply implicitly.
<<KLEE-replacement-instructions>> gives examples of equivalent sequences using `kl.input` and `kl.output`.

[[KLEE-CC-management]]
== Management of Cryptographic Contexts

Following the RISC-V philosophy, KLEE splits locker management into sequences of simple instructions, not single instructions that drive large state machines or microcode.
As a consequence:

. the state machines that manage keys and algorithms, which CISC key-protection solutions hide (cite:[IBM-z-arch] "`Protection of Cryptographic Keys`" or cite:[intel-keylocker]), are exposed to software: the hardware is simpler, though it enforces rules against misuse, and the software more complex;
. interrupts and exceptions can separate the instructions of a management sequence, so context switching, process and virtual machine migration, hibernation, and interoperability between KLEE implementations need explicit support; and
. so does dynamic locker management, lazy context loading included, where other architectures cache repeated key uses implicitly.

Throughout, the confidentiality and integrity of the MDH and Content of a CC are preserved, and binary compatibility holds across implementations that support the same sub-extensions.

A context-switch handler may clear a partially provisioned or imported locker instead of saving it, which makes the interrupted operation restart.
It must nevertheless be able to save such a locker, for instance to avoid livelock.
The same software code must handle both resumption and restart (Rule <<KLEE-GR-cleared-under-management>>).
Rules <<KLEE-SR-no-unconditional-clear>> and <<KLEE-SR-never-clear-exporting>> bind system software.

[[KLEE-nested-mgmt]]
=== Management Operation Types

KLEE defines various external CC formats, each starting with the 128-bit MDH of <<KLEE-Metadata>>.
The first two have been mentioned earlier:

. the _Provisioning Input_ (PI), loaded into a locker to create a CC; and
. the _Sealed Cryptographic Context_ (SCC), an encrypted and authenticated representation of a CC, exported to memory for later import.

These and two other formats are used by management operations, each consisting of one or more KLEE management instructions.

A management operation is *open* from its opening `kl.mgmt` until its completing `kl.mgmt`, or until the locker is cleared; while it is open, the locker is in a Configuration State.
`kl.mgmt` opens or completes a management operation according to its `#immed7`:

[[KLEE-management-immeds]]
.Values (decimal) of `#immed7` for provisioning, importing, and exporting
[float="center",align="center",width="100%",cols="^7%,<27%,<66%",options="header"]
|===
| Value | Mnemonic                 |  Description
|  56   | `kl_cfg_provisioning`    |  Prepare a locker for provisioning.
|  57   | `kl_cfg_exporting`       |  Prepare a locker for export.
|  58   | `kl_cfg_importing`       |  Prepare a locker for import.
|  63   | `kl_cfg_management_end`  |  Complete the current management operation.
|===

Not every Configuration State of <<KLEE-SC-sealing-status>> is an `#immed7` value: `kl_cfg_ppi_exporting` and `kl_cfg_ppi_importing` cannot be set directly, and result only from nested operations, described below.

A *base (management) operation* (also called the outermost operation) is opened on a locker in no Configuration State:

* a (base) _provisioning_ from a PI, in State `kl_cfg_provisioning`;
* a (base) _export_ of a locker in a Valid State, in State `kl_cfg_exporting`; or
* a (base) _import_ of an SCC, in State `kl_cfg_importing`.

Before opening an export, software saves the locker's MDH as `ml`; an import takes `ml` from the saved image.
The `kl.mgmt` that completes an export or an import receives `ml` and restores its _State_; completing a base operation leaves the locker in a Complete State (Rule <<KLEE-GR-completion-state>>).

An exception may interrupt an open operation.
The handler may then save the locker by a *nested export*, an export opened on a locker in a Configuration State, and restore it later by a *nested import* of the resulting image; nested operations may themselves be interrupted and nested.

Each Configuration State encodes a *base type* `pi` if the base operation is a provisioning and `scc` otherwise, which determines the format and length of the locker's image at any nesting depth (<<KLEE-instruction-size>>):

* `pi`: `kl_cfg_provisioning`, with `kl_cfg_ppi_exporting` and `kl_cfg_ppi_importing` ("`ppi`" for "`partial provisioning input`") for nested exports and imports;
* `scc`: `kl_cfg_exporting` and `kl_cfg_importing`, for base and nested operations alike.

<<KLEE-SC-sealing-status>> gives the values of these States.
Nested exports and imports use a third format:

[start=3]
. the *Partially Configured Cryptographic Context* (PCCC), whose MDH holds a Configuration State, and which has the format of a PI or an SCC, according to its base type, without further encryption or authentication.

A locker in an Error State has a fourth format, its MDH alone: its export reads the MDH, without `kl.mgmt`, and its import is a single `kl.mgmt` (<<KLEE-error-state-transfer>>).

Clearing a locker ends all its open operations and leaves it _Unconfigured_.

[[KLEE-data-formats]]
=== Formats of PIs, SCCs, and Partially Configured Cryptographic Contexts

Provisioning Input (PI).:::
The MDH, with _State_ = _Unconfigured_, followed by `Content`; the completing `kl.mgmt` sets _State_ to _Ready_.

Sealed Cryptographic Context (SCC).:::
+
--
Up to five sections, in this order:

[[KLEE-SCC]]
.Plaintext of the Sealed Cryptographic Context (SCC) Format, all Sections in Order
[width="100%",cols="^8%,14%,21%,57%",options="header"]
|===
| Section | Section Name | Size                 | Description
| 1       | `MDH`        | 128 bits             | See <<KLEE-Metadata>>.
| 2       | `SIV`        | 128 bits             | Authentication tag for `MDH`, the Locality Secrets its _Locality_ names, and `Content1` (<<KLEE-SCC-export>>).
| 3       | `IMPQUAL`    | 128 bits, if present | Identifies the implementation of the KLEE unit. Non-authoritative, and ignored when _ADSDropped_ = 1.
| 4       | `SIV2`       | 128 bits, if present | Authentication tag for `IMPQUAL`, `SIV` and `Content2`. Non-authoritative, and not verified when _ADSDropped_ = 1.
//
| 5.a
| `Content1`
| A multiple of 128 bits. See <<KLEE-length-rule>>.
| Keys and other Machine-specific information that the Machine needs to function correctly. Encrypted in memory, and inside the KLEE unit during partial import.
//
| 5.b
| `Content2`
| A multiple of 128 bits.
| ADS: data that the Machine does _not_ need to function correctly.
  Encrypted in memory and during partial import.
|===

Sections 3, 4 and 5.b form the implementation-specific ADS, whose size _AuxDataLen_ gives (<<KLEE-Auxiliary-Data-Section>>).
KLEE generates an image with _ADSDropped_ = 1 only as an SCC-shaped PCCC, when a nested export preserves an interrupted import after `Content2` was dropped; since _ADSDropped_ is unauthenticated, import also accepts this layout in an SCC modified to set the bit.
--

Encryption during management.:::
While an SCC is imported, or a locker is exported as an SCC, the locker holds its `Content` encrypted:

. an export opening `kl.mgmt` encrypts the locker, generates `SIV` and, if _AuxDataLen_ {ge} 2, `IMPQUAL` and `SIV2`;
. the `kl.mgmt` that completes the base import or export decrypts and authenticates it, once the MDH, `Content`, `SIV` and, if _AuxDataLen_ {ge} 2, `IMPQUAL` and `SIV2` are in place; with _ADSDropped_ = 1, no `Content2` is loaded or authenticated.
  An export completion may instead restore the clear contents from an internal copy (<<KLEE-mgmt-completes-export>>).

Partially Configured Cryptographic Context (PCCC).:::
+
--
A PCCC (<<KLEE-nested-mgmt>>) has one of two shapes:

* base type `pi`: a _PI-shaped_ image, the MDH followed by the clear `Content` of the PI.
  This exposes nothing new, since software supplied that `Content`; software that provisions a locker clears it before giving control to a less privileged mode, which could otherwise export it (<<KLEE-isolation-between-modes>>).
* base type `scc`: an _SCC-shaped_ image, the MDH followed by `SIV` and, when present, `IMPQUAL` and `SIV2`, as _ContentOffset_ prescribes (<<KLEE-instruction-mv>>), and by the ciphertext `Content` already in the locker.

Since each export saves its own `ml`, software keeps an implicit stack of _State_ values, one per nesting level.
--

[[KLEE-length-rule]]
=== Length of External Formats and KLF Capacity Usage of a Locker

The lengths of a PI, an SCC or a PCCC, and the KLF capacity of a locker are determined by fields contained in bits [63:0] of the MDH.
The following items do not apply to a locker in an Error State (<<KLEE-error-state-transfer>>):

. The length of a *Provisioning Input* depends only on _Machine_, _MachinePolicy_ and _KeyType_.
_AuxDataLen_ and _ADSDropped_ must be zero in a PI, and in a PI-shaped PCCC, since these carry no ADS; `kl.mgmt` ignores and zeroes _StateExtension_ and _MachineUse_ upon provisioning.

. The length of a *Sealed Cryptographic Context* depends only on _Machine_, _MachinePolicy_, _KeyType_, _StateExtension_, _AuxDataLen_ and _ADSDropped_ (<<KLEE-Auxiliary-Data-Section>>), not on _State_ or _SCProtection_ (<<KLEE-rules-masked-implementations>>).
_ADSDropped_ removes only `Content2`: the presence of `IMPQUAL` and `SIV2`, and the offset and length of `Content1`, do not change.

. The length of a *Partially Configured Cryptographic Context* is that of the format corresponding to its base type, i.e.,
that of a PI if its base type is `pi` and that of an SCC if its base type is `scc`.

. The *KLF capacity* of a locker depends only on _Machine_, _MachinePolicy_, _SCProtection_ and _KeyType_, and does not change once the locker is provisioned: dropping the ADS shortens its SCCs but not its capacity.
A locker is allocated room for every field its Machine may use; the capacity depends on _KeyType_ because a SKID may denote a key that never enters the KLF.

// No other MDH field, and no information in the `Content`, may affect any of these four quantities.

A PI cannot be in an Error State.

[[KLEE-rules-masked-implementations]]
==== Single-Share Key Export Rule for Masked Implementations

A multi-share implementation of a Machine provisions, imports and exports all its keys and secrets as reconstructed values, so that SCCs stay compact and interoperable.
(((KLEE, Machine, side-channel protection variants)))
Architecturally every value is a single share: a side-channel-protected Machine is an implementation variant of the unprotected one, distinguished only by the _SCProtection_ field of the MDH.

NOTE: Reconstructing or re-randomizing a key is usually cheap, for instance when a block cipher in counter mode generates the masks; an implementation with a slower mask generator may keep shares or masks in the ADS.

[[KLEE-system-keys]]
==== System Keys and Randomly Generated Key Values

A PI or SCC encodes a System Key as a 64-bit SKID, from which a system-specific SKS retrieves the key.
Hence:

[horizontal]
[[KLEE-GR-skid-field,GR66]]GR66:: In a PI, an SCC, or a PCCC, the key field of a System Key holds its SKID instead of the key value, and so shrinks from the key size to 64 bits.

[[KLEE-GR-single-skid,GR67]]GR67:: For a Machine with more than one key, such as XEX/XTS, a single SKID retrieves all its keys from the SKS.

The SKS resolves a SKID other than the all-ones value as a function of the SKID alone, if the SKID is allowed for the _Machine_ and _MachinePolicy_; the key value depends on neither.
If the SKS also encodes policies for a key, they narrow the policies of the locker as <<KLEE-Metadata-narrowing>> describes.
For a key that the system intends to protect, the SKS associates at least a _UsagePolicy_ with its SKID, since the SKS policies are the only architectural control on which modes may use it; a _UsagePolicy_ that admits every mode, for instance for a public signature-verification key, is a deliberate choice and the responsibility of the system's architects.
The current privilege mode does not affect whether the SKS may resolve a SKID.

A SKID other than the all-ones value that the SKS does not resolve transitions the locker to Error State _Invalid_ (<<KLEE-Metadata-validity>>).
Whenever a SKID is resolved, the policies that the SKS associates with the key narrow the MDH of the locker (<<KLEE-Metadata-narrowing>>); if the narrowing fails, the locker transitions to Error State _Privilege Violation_.
The all-ones SKID generates a new random key (<<KLEE-KeyType-field>>).

A SKID carried in an SCC is resolved only after the SCC is authenticated.

A multi-share implementation may copy System Key material from the SKS into the locker and expand it into multiple shares, but must still export the key as a SKID.
Shares or masks included in the ADS (<<KLEE-rules-masked-implementations>>) must not allow or facilitate recovering the key value from those values alone.

[[KLEE-locker-management]]
=== Locker Management Operations

This section defines the operations that `kl.mgmt` performs for the `#immed7` values of <<KLEE-management-immeds>>.

Three steps are common to every operation below and are not repeated in their descriptions:

. `kl.mgmt` first performs the check of Rules <<KLEE-GR-klml-openings>> and <<KLEE-GR-mgmt-klmanagedlocker-check>>, and raises an illegal-instruction exception if it fails.
. It updates `klmanagedlocker` as Rule <<KLEE-GR-klmanagedlocker-updates>> states.
. It clears `klstart` once it has passed the checks that precede the conditions on the locker (the first group of <<KLEE-illegal-instruction-grounds>>, and the KLEE fatal-error, missing-CSK and locker-Off exceptions) and the `klmanagedlocker` check above, even if it then raises an exception; if one of those checks rejects it, it leaves `klstart` unchanged, so an accidentally interleaved `kl.mgmt` does not destroy the progress of the ongoing operation. Software restores `klstart` to resume interrupted management operations.

The four operations of `kl.mgmt` are described in the next four sections:

[[KLEE-MVR-open]]
==== kl.mgmt opens a provisioning or an import

Software first obtains the MDH, `ml`, and supplies it with a Form A, C or D `kl.mgmt`.

NOTE: For an import, software first saves `ml` in its local state and supplies it to the `kl.mgmt` that completes the import, to restore the _State_ the locker had before the import started.

The instruction:

.. zeroizes the target locker; bytes of the <<KLEE-serialized-image,serialized image>> `S`, authentication fields included, not yet written by the management operation read as zero through every architectural access (`kl.store`, `kl.mvout`, verbatim export);
//.. It checks the validity of the fields of the provided MDH `ml`. If any are invalid according to <<KLEE-Metadata-validity>>, it transitions the locker to Error State _Invalid_.

// .. if `#immed7` = `kl_cfg_importing` and `ml`._State_ is an Error State, configures the locker immediately and
//     fully in that Error State, with the entire MDH from the auxiliary input, except that _AuxDataLen_ and _ADSDropped_ are set to 0 (Rule <<KLEE-GR-clear-locker-content-error-state>>); a _State_ of 54 or 55, or of 53 without `Zklexpire`, is replaced by _Invalid_.
//     The steps below are skipped: the locker holds only its MDH (<<KLEE-cryptographic-registers>>), no Machine is selected for execution,
//     and no KLF capacity is allocated, so this configuration cannot fail.
//     This one uninterruptible instruction (Rule <<KLEE-GR-uninterruptible-instructions>>) performs the whole configuration and opens no management operation, so
//     no `kl.mgmt` with `#immed7` = `kl_cfg_management_end` follows.
//     This is the _short import path_ of <<KLEE-error-state-transfer>>;

.. if `#immed7` = `kl_cfg_importing` and `ml`._State_ is an Error State, instead takes the _short import path_ of <<KLEE-error-state-transfer>>: it configures the locker immediately and fully in that Error State, skips the steps below, and opens no management operation;
.. for an import, zeroizes the authentication registers `SIV`, `IMPQUAL` and `SIV2` (<<KLEE-KLF>>);
.. raises a KLEE unsupported-Metadata exception if `ml` is unsupported Metadata (<<KLEE-Metadata-validity>>);
.. for a *provisioning*:
... requires `ml`._State_ to be _Unconfigured_, else the Metadata is invalid; the locker's _State_ stays _Unconfigured_ during the checks below, until successful configuration;
... sets _StateExtension_ and _MachineUse_ to 0, ignoring the values in the PI;
... requires _AuxDataLen_ and _ADSDropped_ to be 0: if either is non-zero in the MDH of the PI, the locker transitions to Error State _Invalid_, a Complete State, and the instruction terminates;
.. transitions the locker to Error State _Invalid_ if `ml` is invalid Metadata (<<KLEE-Metadata-validity>>), an _Unconfigured_ `ml`._State_ being invalid for an import;
.. attempts to allocate the KLF capacity that the MDH fields _Machine_, _MachinePolicy_, _SCProtection_, and _KeyType_ require (<<KLEE-length-rule>>), and raises a KLEE out-of-memory exception if it cannot;
.. for a *provisioning*, sets the locker's _State_ to `kl_cfg_provisioning`;
.. for an *import*:
... decide, from the loaded MDH and the maximum the implementation supports, whether the ADS is retained (this is realized as
Steps 1–5 of the import routine of <<KLEE-SCC-import>>);
... sets the locker's _State_ to `kl_cfg_importing` if `ml`._State_ is a Valid State, `kl_cfg_importing` or `kl_cfg_exporting`;
... sets it to `kl_cfg_ppi_importing` if the base type of `ml`._State_ is `pi` (<<KLEE-nested-mgmt>>).

Whenever a check above fails, raising a KLEE exception or transitioning the locker to Error State _Unsupported_ or _Invalid_, every MDH field other than _State_ remains zero and no KLF capacity is allocated; after a KLEE out-of-memory exception, the locker remains _Unconfigured_.
This does not apply to configuring a locker directly into an Error State from `ml`, which installs the entire MDH.

==== kl.mgmt opens an export

Software first saves a copy, `ml`, of the locker's MDH, to restore the _State_ when completing the export.
`kl.mgmt` can be of Form A, C or D, and ignores its auxiliary input. Depending on `ml`._State_:

.. _Unconfigured_: no operation and no exception. No management operation is opened, the authentication registers are unchanged, and only the common steps above take effect (Rule <<KLEE-GR-cleared-under-management>>).

.. An Error State: the locker is unchanged, and no management operation is opened (Rule <<KLEE-GR-error-state-locker-is-only-MDH>>); <<KLEE-error-state-transfer>> details this short export path.

.. A Valid State: the instruction prepares the locker to produce an SCC, encrypting its contents and computing the authentication tag(s) as <<KLEE-CC-management>> specifies, and sets its _State_ to `kl_cfg_exporting`.
The opening `kl.mgmt` changes no MDH field other than _State_: an implementation that creates or changes an ADS, or uses _MachineUse_, always keeps _AuxDataLen_ and _MachineUse_ current, so that the MDH software reads before opening the export is the one the export authenticates.

.. A Configuration State (the export of a partially configured locker, or a nested export):

... no encryption or authentication occurs: the locker's contents are exported verbatim, in their order in the PI (for a partially provisioned locker) or in the SCC (for a partially imported locker, or a locker whose own export was interrupted);

... the locker's _State_ is set to `kl_cfg_ppi_exporting` or `kl_cfg_exporting`, according to its base type (<<KLEE-nested-mgmt>>).

==== kl.mgmt completes a management operation

First, note that:

. `kl_cfg_management_end` issued on a locker in a Valid State raises an illegal-instruction exception, since there is no management operation open on it.

. `kl_cfg_management_end` issued on a locker that is _Unconfigured_ or in an Error State performs no operation, raises no exception, ignores `ml`, and only the common steps above take effect (Rule <<KLEE-GR-cleared-under-management>>).

These two special cases aside, a `kl.mgmt` issued to complete a management operation
first reads the target locker's MDH, and completes a provisioning if its _State_ is `kl_cfg_provisioning`, an import if it is `kl_cfg_importing` or `kl_cfg_ppi_importing`, and an export if it is `kl_cfg_exporting` or `kl_cfg_ppi_exporting`.

When completing an import or an export, it consumes only the _State_ field of the auxiliary operand `ml`, which restores the locker's _State_ to its value when the management operation started; no other MDH field is written from `ml`.

On completing an SCC import or a locker export, authentication is checked only if setting locker.MDH._State_ to `ml`._State_ restores a Complete State; the probability of accepting an incorrect _State_ is negligible.
A nested completion checks only the base type, without authentication.

If locker.MDH._State_ is `kl_cfg_importing` or `kl_cfg_exporting`, `ml`._State_ must be a Complete State or a Configuration State of base type `scc`, i.e., `kl_cfg_importing` or `kl_cfg_exporting`; if it is `kl_cfg_ppi_importing` or `kl_cfg_ppi_exporting`, `ml`._State_ must be a Configuration State of base type `pi`, i.e., `kl_cfg_provisioning`, `kl_cfg_ppi_importing` or `kl_cfg_ppi_exporting` (<<KLEE-nested-mgmt>>).
Any other `ml`._State_, including a Complete State for a locker of base type `pi` and the values 61–63, raises an illegal-instruction exception.
A Complete `ml`._State_ is accepted only for a locker of base type `scc`, so the clear `Content` of a partially provisioned locker becomes usable only by completing its provisioning.

* `*kl.mgmt*` *completes a provisioning.*
+
--
No MDH saved at provisioning start is needed: Forms C and D of `kl.mgmt` ignore their auxiliary input.

Completing a provisioning requires _AuxDataLen_ = 0 and _ADSDropped_ = 0; if locker.MDH._State_ is `kl_cfg_provisioning` and either field is non-zero, the locker transitions to Error State _Invalid_, and the instruction terminates.

The operation makes the provisioned locker available to software by:

... for _KeyType_ = 1, generating the key of the all-ones SKID (<<KLEE-KeyType-field>>, Rule <<KLEE-GR-rbg-failure>>), or applying the SKID resolution of <<KLEE-system-keys>>;
... converting the locker's content into the internal format of the KLEE unit;
... performing any check required by the Machine on the fields of the PI (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-check-on-write>>); a failed check transitions the locker as Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-config-data-error>> classifies it, to Error State _Invalid_ for a configuration error or to _Failure_ for a data error, in place of the step below; and
... setting _State_ to _Ready_, and _StateExtension_ and _MachineUse_ to 0.

If a process is preempted during provisioning, `kl.store` or `kl.mvout` exports only the original PI information, unencrypted.
Only the `kl.mgmt` that completes the provisioning may therefore generate secret random material needed to configure the locker, retrieve key material from the SKS, or derive, expand or re-share that material, so that no such material is exposed in an unencrypted export of a partially provisioned locker.
--

* `*kl.mgmt*` *completes an import.*
+
--
Software uses Form A, C or D of `kl.mgmt` to supply the value `ml` saved when the import started.
The image authenticated as ``AD[0]`` is the MDH held in the target locker, i.e., the one carried in the SCC and loaded when the import started, with its _State_ restored from `ml` and _ADSDropped_ cleared only in the copy used for authentication (<<KLEE-SCC-import>>).

... If `ml`._State_ is a Complete State (the import of the export of a fully configured locker):
.... locker.MDH._State_ is set to `ml`._State_.
.... The KLEE unit decrypts and authenticates the locker's content.
.... If authentication fails, the target locker transitions to Error State _Authentication Failed_, without an exception. Otherwise, if _KeyType_ = 1, the SKID is resolved, and the narrowing of <<KLEE-system-keys>> is applied; an all-ones SKID, which only a PI may carry, transitions the locker to Error State _Invalid_.
.... The KLEE unit converts the locker's content into its internal format.
.... The KLEE unit performs the checks that the Machine attaches to the fields that the import restores (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-check-on-write>>); a failed check transitions the locker as when completing a provisioning (Rule <<Zkl-ISA-machines.adoc#KLEE-MGR-config-data-error>>).
This makes the locker available to software.
... Otherwise (the import of the export of a partially configured locker, or of a nested export), locker.MDH._State_ is set to `ml`._State_.
--

[[KLEE-mgmt-completes-export]]
==== kl.mgmt completes an export

Software uses Form A, C or D of `kl.mgmt` to supply the MDH value `ml` saved when the export began. Then:

. The _State_ of the locker is set to `ml`._State_.
. If `ml`._State_ is a Complete State, the instruction restores the locker to the clear format it had when the export began, and makes it accessible to software:
.. it decrypts and authenticates the contents as when completing an import, with the MDH held in the locker as `AD[0]`, and _ADSDropped_ cleared in the copy that first-segment authentication consumes;
.. if the `SIV` check fails, the locker transitions to Error State _Authentication Failed_, and the instruction terminates without an exception; otherwise, if _KeyType_ = 1, the SKID is resolved, and the narrowing of <<KLEE-system-keys>> is applied.
. If `ml`._State_ is not a Complete State, the locker's contents are not changed further.

NOTE: In place of decrypting and authenticating the locker's contents in Step 2.a, implementation may instead restore the clear contents from an internal copy, if it can guarantee that the outcome is identical. The specification defines no mechanism for this.

=== SCC Export and Import Algorithms

Section <<KLEE-SCC-AEAD>> describes the SCC export and import algorithms, starting with the authenticated encryption scheme they use.

[[KLEE-SCC-AEAD]]
=== The SCC Authenticated Encryption Scheme

SCC export and import use a variant of AES-GCM-SIV cite:[DBLP-journals-iacr-GueronLL17,RFC8452] that differs as follows:

. The POLYVAL input omits the lengths of the associated data and plaintext, since they are already implied by the MDH.
. The optional Nonce is omitted.
. A domain separation bit, `sep`, distinguishes the two segments of the content sealed in an SCC: the architected content (`sep` = 0) and the optional implementation-specific content (`sep` = 1); `sep` replaces bit 126 of the tag input and of every counter block.
. For `sep` = 0, bit 47 of `AD[0]`, the unauthenticated _ADSDropped_ bit of the MDH (<<KLEE-Auxiliary-Data-Section>>), is cleared before `POLYVAL` is evaluated.

The Key Derivation (<<KLEE-SCC-key-derivation>>) and POLYVAL (<<KLEE-SCC-POLYVAL>>) functions are defined first, then SCC generation from a locker (<<KLEE-SCC-export>>) and SCC import into a locker (<<KLEE-SCC-import>>).

In the pseudocode, `AESE256(K, B)` denotes the AES-256 encryption of the 128-bit block `B` under the 256-bit key `K` (FIPS 197 cite:[nist-fips-197]).

[[KLEE-SCC-key-derivation]]
.RFC8452 Key Derivation
[]
----
function SCC_KeyDeriv(key : bits(256), nonce : bits(96))
    → struct{enc_key : bits(256), auth_key : bits(128)} =
{
  local A : array [0..5] of bits(128);
  local i : int;

  foreach(i from 0 to 5) do:
    A[i] ← AESE256(key, nonce @ bin(i,32));

  return struct { enc_key  = A[5][63:0] @ A[4][63:0] @ A[3][63:0] @ A[2][63:0],
                  auth_key = A[1][63:0] @ A[0][63:0] }
}
----

// NOTE: Since key derivation is costly, implementations may cache the derived keys.

[[KLEE-SCC-POLYVAL]]
.Polyval Hashing Function
[]
----
function POLYVAL(auth_key : bits(128), blocks[0..n-1] : bits(128), n : int)
    → bits(128) =
{
  local tmp : bits(128) ← zeros(128);
  local i : int;

  foreach(i from 0 to n-1) do:
    tmp ← tmp xor blocks[i];
    tmp ← Montmul(tmp, auth_key);

  return tmp;
}
----

POLYVAL uses Montgomery multiplication, `Montmul(a, b)`, in the field F = GF(2)[`x`] modulo `x^128^ + x^127^ + x^126^ + x^121^ + 1`.
A 128-bit value `V` represents the element whose coefficient of `x^k^` is `V[k]`;
byte order and bit order both run forward, as in
cite:[RFC8452] {sect}3, under which `x^0^` is the byte string `0x01` followed by
fifteen zero bytes, i.e., the value `1`. Then: +
 +
`{fournbsp}{fournbsp}` `Montmul(a, b)` = `a` {interpunct} `b` {interpunct} `x^-128^` `{nbsp}{nbsp}` in the field F.

The SCC encryption and decryption functions, <<KLEE-SCC-GCM-SIV-enc>> and <<KLEE-SCC-GCM-SIV-dec>>, use this notation:

* `AD[]` denotes the Associated Data as an array of `len_AD` 128-bit blocks, that is
  `AD[0] {vvert} AD[1] {vvert} {ellipsis} {vvert} AD[len_AD-1]`, in that order;
* `P[]`, resp., `C[]`, denotes a Plaintext, resp., a Ciphertext, as arrays of `len_PC`
  128-bit blocks, that is `P[0] {vvert} P[1] {vvert} {ellipsis} {vvert} P[len_PC-1]`,
  resp. `C[0] {vvert} C[1] {vvert} {ellipsis} {vvert} C[len_PC-1]`, in that order;
* `K` is a 256-bit Key;
* `N` is a 96-bit Nonce; and
* `SIV` is a 128-bit SIV/tag.

//

[[KLEE-SCC-GCM-SIV-enc]]
.AES-GCM-SIV Encryption for SCC Generation
[]
----
function SCC_Encrypt(AD[] : array of bits(128), N : bits(96), sep: bits(1),
    P[] : array of bits(128), K : bits(256), len_AD : int, len_PC : int)
  → {SIV : bits(128), C[] : array of bits(128)} =
{
  local AD_auth : array [0..len_AD-1] of bits(128) ← AD[];

  enc_key, auth_key ← SCC_KeyDeriv(K,N);
  if (sep = 0) then:
    AD_auth[0][47] ← 0;
  SIV ← POLYVAL(auth_key, AD_auth || P, len_AD + len_PC);
  SIV[95:0] ← SIV[95:0] xor N;
  SIV ← AESE256(enc_key, 0 @ sep @ SIV[125:0]);

  foreach(i from 0 to len_PC - 1) do:
    C[i] ← P[i] xor AESE256(enc_key,
             1 @ sep @ SIV[125:32] @ bin((int(SIV[31:0]) + i) mod 2**32, 32));

  return ( SIV, C[] );
}
----

`len_PC` never exceeds `max_admissible` / 16 (<<KLEE-instruction-mv>>), and `len_AD` never exceeds 7.

[[KLEE-SCC-GCM-SIV-dec]]
.AES-GCM-SIV Decryption for SCC Import
[]
----
function SCC_Decrypt(AD[] : array of bits(128), N : bits(96), sep: bits(1),
    SIV : bits(128), C[] : array of bits(128), K : bits(256),
    len_AD : int, len_PC : int)
  → {correct : bool, P[] : array of bits(128)} =
{
  local AD_auth : array [0..len_AD-1] of bits(128) ← AD[];

  enc_key, auth_key ← SCC_KeyDeriv(K,N);
  if (sep = 0) then:
    AD_auth[0][47] ← 0;

  foreach(i from 0 to len_PC - 1) do:
    P[i] ← C[i] xor AESE256(enc_key,
             1 @ sep @ SIV[125:32] @ bin((int(SIV[31:0]) + i) mod 2**32, 32));

  s ← POLYVAL(auth_key, AD_auth || P, len_AD + len_PC);
  tmp ← s;
  tmp[95:0] ← tmp[95:0] xor N;
  tmp ← AESE256(enc_key, 0 @ sep @ tmp[125:0]);

  if (tmp != SIV) then:
    foreach(i from 0 to len_PC - 1)
      P[i] ← zeros(128);
    return ( false, P[] );

  return ( true, P[] );
}
----

[[KLEE-SCC-export]]
=== Generation of an SCC from a Fully Configured Locker

For a locker in an Error State, use the method of <<KLEE-error-state-transfer>>.

A locker ``K(i)`` in a Valid State is fully provisioned, and opening it for export (`kl.mgmt Kd, #kl_cfg_exporting`) creates the serialized, encrypted and authenticated SCC by the steps below.

The Locality substitution rules of <<KLEE-Localities>> apply: `LST_eff[j]` is the value of `LST` entry _j_ after substitution, and replaces `LST[j]` in the export and import algorithms.
An unimplemented entry with no configured replacement contributes `zeros(128)` and makes the Metadata invalid at provisioning or import; an export is not refused on this ground, but the resulting SCC is rejected at import (Rule <<KLEE-SR-locality-unconfigure>>). Entry 9 of `LST` is `hkllocality`, and entry 10 is `skllocality`.

After `kl.clearads`, a fully configured locker has _AuxDataLen_ = 0 and _ADSDropped_ = 0 (<<KLEE-instruction-clearads>>); only an SCC-shaped PCCC may carry _ADSDropped_ = 1, to preserve an interrupted import after `Content2` was dropped.

.Exporting a Fully Configured Locker ``K(i)``
--
. First, process the architected content:
.. `saved_MDH` <- the MDH of ``K(i)`` immediately before its _State_ is set to `kl_cfg_exporting` (the image software saved beforehand), ``len_AD`` <- 1
.. ``AD[0]`` <- `saved_MDH`. `SCC_Encrypt` clears _ADSDropped_ in its local copy of this block before computing `SIV`; the `saved_MDH` returned in the SCC is unchanged.
.. foreach(_j_ from 0 to 10) do:
... If `saved_MDH`._Locality_ includes Locality #j, then ``AD[len_AD]`` <-  ``LST_eff[``_j_``]``, ``len_AD`` <- ``len_AD`` + 1
.. `len_PC` <- the number of 128-bit blocks of `Content1` (Section 5.a of <<KLEE-SCC>>).
.. `SIV`, `Content1~CT~[]` <- `SCC_Encrypt(AD, zeros(96), 0, K(i).Content1~PT~[], CSK, len_AD, len_PC)`
. Second, if _AuxDataLen_ {ge} 2, process the implementation-specific content:
.. `len_AD2` <- 2, ``AD2[0]`` <- ``K(i)``.`IMPQUAL`, ``AD2[1]`` <- `SIV`.
.. `len_PC2` <- the number of 128-bit blocks of `Content2` (Section 5.b of <<KLEE-SCC>>), i.e., _AuxDataLen_ − 2.
.. `SIV2`, `Content2~CT~[]` <- `SCC_Encrypt(AD2, zeros(96), 1, K(i).Content2~PT~[], CSK, len_AD2, len_PC2)`
. Finally, if _AuxDataLen_ = 0, then:
.. return(`saved_MDH`, `SIV`, `Content1~CT~[]`)
. else:
.. return(`saved_MDH`, `SIV`, `IMPQUAL`, `SIV2`, `Content1~CT~[]` and `Content2~CT~[]`) (`Content2~CT~[]` may be empty)
--

// Of the returned values, `SIV`, `SIV2` and `IMPQUAL` are placed in the CSRs `§acesivl`/`acesivh`,
// `acesiv2l`/`acesiv2h` and `aceiql`/`aceiqh`, from which software stores them to memory; the ciphertext
// remains in the locker, whence `kl.store` (<<KLEE-instruction-store>>) transfers it; and `saved_MDH` is the
// image software already holds, which `kl.getmd*` (<<KLEE-instruction-getmd>>) also returns.
//
// If _AuxDataLen_ = 0, then `SIV2` and `IMPQUAL` are not generated, and therefore
// `acesiv2l`/`acesiv2h` and `aceiql`/`aceiqh` are not written to.
// They may contain stale values, but this is not an issue as they are not exported to memory in this case.

[NOTE]
====
Completing an export prematurely causes an authentication error at import (next section), and completing an import prematurely causes one at once.
Leaving either operation incomplete leaves the _State_ a Configuration State, in which most instructions fail.
====

[[KLEE-SCC-import]]
=== Decryption and Authentication of a Complete SCC into a Locker

For an SCC whose MDH is in an Error State, use the method of <<KLEE-error-state-transfer>>.

The following algorithm imports the SCC of a fully configured locker.
The `kl.mgmt Kd, #kl_cfg_importing` opening the import performs steps 1 to 5 (<<KLEE-locker-management>>), the subsequent `kl.load` or `kl.mvin` instructions perform step 6, and `kl.mgmt Kd, #kl_cfg_management_end` performs steps 7 to 15, which decrypt and authenticate the SCC and make it available to software.

.Importing a Fully Configured Locker ``K(i)``
--
 . Clear ``K(i)``.
 . Load `M`, the MDH from the SCC, into ``K(i)``.MDH.
 . Check the validity of `M`, and whether the Machine is supported.
 . Determine the SCC layout from `M`.
 . If `M`._AuxDataLen_ {ge} 2, and either `M`._ADSDropped_ = 1 or `M`._AuxDataLen_ exceeds the maximum of the implementation for the Machine, set ``K(i)``.MDH._ADSDropped_ to 1; otherwise set it to 0. This changes only the length of `Content2`: when _AuxDataLen_ {ge} 2, `IMPQUAL` and `SIV2` remain present and _ContentOffset_ remains 48.
 . Load the rest of the SCC, up to the length that the resulting working MDH gives: with _ADSDropped_ = 1, `SIV`, `IMPQUAL`, `SIV2` and `Content1`, but no `Content2`.
 . `saved_MDH` <- the MDH image held in ``K(i)``, that is `M` with the working value of _ADSDropped_ and with its _State_ field restored from the auxiliary operand of the completing `kl.mgmt`.
 . ``AD[0]`` <- `saved_MDH`, ``len_AD`` <- 1. `SCC_Decrypt` clears _ADSDropped_ in its local copy of `AD[0]` before authenticating it; the MDH held in ``K(i)`` is unchanged by that computation.
 . foreach (`j` from 0 to 10) do:
 .. If `saved_MDH`._Locality_ includes Locality #j, then ``AD[len_AD]`` <-  ``LST_eff[j]``, ``len_AD`` <- ``len_AD`` + 1
 . `len_PC` <- the number of 128-bit blocks of `Content1` (Section 5.a of <<KLEE-SCC>>).
 . `correct`, ``K(i)``.`Content1` <- `SCC_Decrypt(AD, zeros(96), 0, SIV, K(i).Content1, CSK, len_AD, len_PC)`.
 . If `correct` {ne} `true`, the SCC is rejected: ``K(i)`` transitions to Error State `kl_state_mgmt_auth` (_Authentication Failed_, Rule <<KLEE-GR-clear-locker-content-error-state>>), and the remaining steps are skipped.
 . If ``K(i)``.MDH._AuxDataLen_ {ge} 2 and ``K(i)``.MDH._ADSDropped_ = 0, process the implementation-specific content:
.. `len_AD2` <- 2, ``AD2[0]`` <- ``K(i)``.`IMPQUAL`, ``AD2[1]`` <- `SIV`.
.. If ``K(i)``.`IMPQUAL` = `zeros(32) @ klmimpid @ klmarchid @ klmvendorid` then:
... `len_PC2` <- the number of 128-bit blocks of `Content2` (Section 5.b of <<KLEE-SCC>>), that is ``K(i)``.MDH._AuxDataLen_ − 2.
... `correct`, ``K(i)``.`Content2` <- `SCC_Decrypt(AD2, zeros(96), 1, SIV2, K(i).Content2, CSK, len_AD2, len_PC2)`.
.. else:
... `correct` <- `false`.
 . If second-segment processing was attempted and `correct` {ne} `true`, drop `Content2` and set ``K(i)``.MDH._ADSDropped_ to 1.
 . If ``K(i)``.MDH._AuxDataLen_ = 0 or ``K(i)``.MDH._ADSDropped_ = 1, the import completes with the architected content alone: the Machine establishes a consistent internal state, restarting any interrupted long-running operation (Rule <<KLEE-GR-long-running-progress>>), sets _ADSDropped_ to 0, and sets _AuxDataLen_ to 0, or, if it generates a replacement ADS, during completion or later, to the appropriate value, at least 2. Otherwise the successfully imported ADS is retained, _AuxDataLen_ is preserved, and _ADSDropped_ is set to 0. A later export uses these current values, emitting no ADS when _AuxDataLen_ = 0, and the generated or retained ADS when _AuxDataLen_ {ge} 2.
--

[NOTE]
====
If the optional implementation-specific ADS makes the SCC too large for a locker, or is incompatible, the implementation ignores it and keeps the architected content: only a failed first authentication (`SIV`) rejects the entire SCC.
====

=== Design Rationale for the Sealing Construction

_This section is informative and non-normative._

Omitting the nonce reduces the size of the payload and lets the system cache the encryption and authentication keys; the nonce-misuse resistance of AES-GCM-SIV keeps the construction secure for up to O(2^64^) 128-bit blocks observed by an adversary, enough for client applications.
On cloud servers, each virtual machine and supervisor domain should use its own CSK;
M-mode firmware moves a CC between domains by importing its SCC under the source CSK and exporting it under the target CSK.

The `SIV`, the GCM-SIV tag, encrypts the `POLYVAL` hash (<<KLEE-SCC-POLYVAL>>) of the MDH with _ADSDropped_ cleared, the Locality Secrets and the Content.
Hashing the Locality Secrets as associated data, rather than deriving the keys from them, binds the SCC to the Locality set for one `Montmul` per block, with no new `enc_key` or `auth_key` when the set changes; distinct sets give the same `SIV` with probability at most (`len_AD` + `len_PC`) {times} 2^-126^.

Taking `SIV` as ``AD2[1]`` binds the two payloads: `SIV2` and the second segment's keystream depend on the first payload, so the ADS of one SCC cannot be grafted onto another.

As in AES-GCM-SIV, bit 127 separates tag inputs from keystream inputs; the extra bit `sep` (bit 126) costs one bit of security, and makes the keystreams of the two segments differ by design rather than with overwhelming probability.

[[KLEE-error-state-transfer]]
=== Export and Import of a Locker in an Error State

A locker in an Error State is its MDH alone (Rule <<KLEE-GR-clear-locker-content-error-state>>), and uses no KLF capacity.
Of that MDH, in the locker and in its exported image, only the _State_ field is checked; the other fields, those that define the Machine included, are not validated (<<KLEE-Metadata-validity>>).
There is no Content to encrypt, and KLEE does not authenticate the MDH: any software in the current environment can produce a locker in an Error State with Metadata of its choice, by provisioning it and issuing `kl.setst` with an Error-State immediate, so authentication would prove nothing.
Neither direction produces an SCC or a PCCC, opens a management operation, or takes part in resumption.

*Exporting* a locker in an Error State takes two steps, and no `kl.mgmt`:

. Read the _State_ field with `kl.getst` (<<KLEE-instruction-getst>>), and find an Error State.
. Read the MDH with `kl.getmd` or `kl.getmdv` (<<KLEE-instruction-getmd>>), and store it to memory; `kl.size` reports 16.

A `kl.mgmt` with `#immed7` = `kl_cfg_exporting` on a locker in an Error State is permitted but useless: it leaves the locker unchanged and opens no management operation; only its common steps take effect: `klmanagedlocker` naming the locker and `klstart` becoming 0 (<<KLEE-locker-management>>).
The `SIV`, `SIV2` and `IMPQUAL` registers take no part in this export and in the corresponding import.

*Importing* such an image takes one step:

. Issue `kl.mgmt` with `#immed7` = `kl_cfg_importing` and the 16-byte MDH as the auxiliary operand, carried whole by Form C or D, or by a Form A from the KLIOBUF. The instruction:
  .. zeroizes the locker it names and copies the MDH into it, with _AuxDataLen_ and _ADSDropped_ set to 0 (Rule <<KLEE-GR-clear-locker-content-error-state>>);
  .. replaces a _State_ of 54 or 55, or of 53 without `Zklexpire`, by _Invalid_.

The instruction is uninterruptible since it only transfers the MDH, and it opens no management operation.
Hence, no `kl.mgmt` with `#immed7` = `kl_cfg_management_end` follows; issuing one performs no operation (Rule <<KLEE-GR-cleared-under-management>>).

[[KLEE-software-requirements]]
== Software Requirements

This section's rules bind software; the architecture does not enforce them.
Software that violates them may act on the wrong locker, lose the only copy of a CC, or expose one context's data to another.
<<KLEE-state-save-and-restore-order>> shows how privileged software and exception handlers meet them.

[[KLEE-interposed-software,interposed software]]
(((interposed software)))
_Interposed software_ is code that runs while other software may have a halted instruction, or a management operation in progress, in the live KLEE state of the hart.
It includes every trap handler, for an exception or an interrupt, in any mode, even that of the interrupted code (for instance a U-mode signal handler), and any other code that shares that KLEE state, such as another thread of the same process.

[[KLEE-SR-isolation]]
=== Isolation of Contexts

[horizontal]
[[KLEE-SR-clear-before-lower-mode,SR1]]SR1:: Software must prevent unauthorized parties from accessing its lockers directly.
In particular, before giving control to a less privileged mode, software must (save and) clear every locker containing a CC it owns.
// +
// NOTE: _UsagePolicy_ does not protect a resident locker from management by any mode: a less privileged mode could export a partially provisioned locker as a clear PI-shaped PCCC (<<KLEE-data-formats>>), or clear a locker and reconfigure it with the same MDH and a key it knows, which the more privileged software could not tell apart through `kl.getmd`.

[[KLEE-SR-restore-own-lockers,SR2]]SR2:: When switching to a less privileged component, software must restore only the lockers saved for that component, and clear the others; the same holds for `kliobuflen`, and for the KLIOBUF when `kliobuflen` {ne} 0.

[[KLEE-SR-save-shared-state,SR3]]SR3:: Software that uses the KLIOBUF, `klstart` or `klmanagedlocker`, or performs a management operation, while the KLEE state of a less privileged context is live, must first save the state it uses and restore it before returning, so that the less privileged context observes its own values and no data of the more privileged mode.

[[KLEE-SR-kliobuf]]
=== Requirements on the KLIOBUF

[horizontal]
[[KLEE-SR-kliobuflen-zero,SR4]]SR4:: Software should set `kliobuflen` to zero once it no longer needs the KLIOBUF contents, which context-switch code must otherwise save and restore. Setting `kliobuflen` to zero in place of `kliobuftop` ensures the contents are erased when `kliobuflen` is reconfigured later.
// +
// NOTE: The KLEE Privileged Architecture tracks KLIOBUF dirtiness only as part of the whole KLEE state in `*status`.

[[KLEE-klstart-software-check]]
=== Requirements on `klstart`

`klstart` exists once per hart, and nothing resets it before other software uses it: an instruction that honors `klstart` starts at the value it finds, and `kl.mgmt`, `kl.clearall` and every instruction that honors `klstart` write it.
Rules <<KLEE-SR-klstart-save>> to <<KLEE-SR-klstart-restore>> bind <<KLEE-interposed-software,interposed software>>.

[horizontal]
[[KLEE-SR-klstart-save,SR5]]SR5:: Such software must save `klstart` before its first KLEE instruction.

[[KLEE-SR-klstart-zero,SR6]]SR6:: Such software must write 0 to `klstart` before its first instruction that honors it, which would otherwise skip the prefix of its own operand that the interrupted software has processed.

[[KLEE-SR-klstart-restore,SR7]]SR7:: Such software must restore the saved `klstart` before control returns to the interrupted software, which would otherwise resume from another point, or restart.

[[KLEE-SR-klstart-no-reset,SR8]]SR8:: Software should not write 0 to `klstart` to force a full restart of `kl.exec` or `kl.derive` once per-block state effects have been committed.
// For the Machines that Rule <<KLEE-GR-block-iterated-instructions>> names, it must not let the interrupted instruction resume with `klstart` = 0, whether it writes the 0 or leaves one that another KLEE instruction has written; that Rule states the consequence.

[[KLEE-SR-management]]
=== Requirements on Management Operations

Rules <<KLEE-SR-klmanagedlocker-write>> and <<KLEE-SR-nested-export-first>> bind <<KLEE-interposed-software,interposed software>>, and Rule <<KLEE-SR-klmanagedlocker-finish>> all software; an instruction issued in violation of these three Rules acts on whatever locker `klmanagedlocker` names (<<KLEE-managed-locker-rules>>).

[horizontal]
[[KLEE-SR-klmanagedlocker-write,SR9]]SR9:: Before `kl.load`, `kl.store`, `kl.mvin`, `kl.mvout`, an instruction naming `KLML` (Rule <<KLEE-GR-klmanagedlocker-override>>), or a `kl.mgmt` that names its locker explicitly, software must read `klmanagedlocker`; if it does not hold the intended value, software must save it, write the intended value, and restore the saved one before control returns to the code that set it.
The intended value is the number of the target locker, 32 for a transfer to or from the KLIOBUF, and either for a `kl.mgmt` that names its locker explicitly.

[[KLEE-SR-klmanagedlocker-finish,SR10]]SR10:: Software that completes or abandons a management operation must then write 32 to `klmanagedlocker`, or restore the value it saved.

[[KLEE-SR-nested-export-first,SR11]]SR11:: Before opening, on another locker, an export from a Valid State or an import other than the short import of an Error-State image (<<KLEE-error-state-transfer>>), while the locker that `klmanagedlocker` names is in State `kl_cfg_exporting` or `kl_cfg_importing`, software must save that locker by a nested export and restore it before returning to the code that opened its operation, or terminate that code.
Software may instead clear a locker in State `kl_cfg_importing`, whose import then restarts (<<KLEE-CC-management>>).
// +
// NOTE: Without the nested export, the opening overwrites the in-flight `SIV`, `IMPQUAL` and `SIV2` (<<KLEE-KLF>>), and a pending export fails its authentication, losing the only copy of its CC.

[[KLEE-SR-no-interleaving,SR12]]SR12:: Software should complete or discard a management operation before it performs cryptographic operations or manages other lockers.
Code that must interleave them, for instance in several threads of one process, needs coordination, such as lightweight threads with KLEE context-switching support, or a mutex.
// +
// NOTE: `klmanagedlocker` and the authentication registers (<<KLEE-KLF>>) exist once per hart, so interleaving needs extra saves and writes of `klmanagedlocker`, risks overwriting the in-flight `SIV`, `IMPQUAL` and `SIV2`, and redirects every instruction naming `KLML`; each is a chance to act silently on the wrong locker.

[[KLEE-SR-no-unconditional-clear,SR13]]SR13:: System software must not clear a locker under management unconditionally at every context switch, since repeated restarts may prevent completion.

[[KLEE-SR-never-clear-exporting,SR14]]SR14:: A locker in State `kl_cfg_exporting` holds the only copy of its CC: unless system software terminates the interrupted software, it must save such a locker by a nested export (<<KLEE-nested-mgmt>>) and never clear it.

[[KLEE-SR-handlers]]
=== Requirements on Exception Handlers

[horizontal]
[[KLEE-SR-handler-duty,SR15]]SR15:: A handler that can neither resolve nor forward to another handler, an in-process one included, a KLEE unsupported-Metadata, out-of-memory, privilege-violation, clock-unavailable or RBG-unavailable exception, or any exception that a `kl.mgmt` opening a provisioning or an import raises once it has zeroized the locker, and does not terminate the process that caused it, must:
+
--
. unless the locker on which the exception was raised is in a Configuration State, which it keeps so that the management operation under way can complete (Rule <<KLEE-GR-usage-locker-config-state>>), set the _State_ of that locker to the corresponding Error State of <<KLEE-exception-error-correspondence>>, or to _Invalid_ where that table gives none, by the short import of <<KLEE-error-state-transfer>> where the instruction left the locker _Unconfigured_, as Rule <<KLEE-GR-transition-to-from-unconfigured>> requires; a locker left _Unconfigured_ would make software restart the operation (Rule <<KLEE-GR-cleared-under-management>>) and trap again without end.
  For an instruction naming `KLML`, that locker is the one `klmanagedlocker` names, which a failed opening leaves set (Rule <<KLEE-GR-klmanagedlocker-updates>>); and
. advance `xepc` past the trapping instruction, since re-executing it raises the same exception.
  A handler that advances `xepc` past a usage instruction must write zeros to its output operand, as the instruction does when it performs no operation (Rule <<KLEE-GR-usage-locker-error-state>>).
--

[[KLEE-SR-uninterruptible,SR16]]SR16:: Software must not rely on whether an uninterruptible instruction (Rule <<KLEE-GR-uninterruptible-instructions>>) has retired when a handler runs, and must interact with it only as Rule <<KLEE-GR-conflicting-access-rule>> prescribes.

[[KLEE-SR-localities]]
=== Requirements on Localities

[horizontal]
[[KLEE-SR-locality-unconfigure,SR17]]SR17:: Software must not unconfigure a Locality Secret while a locker bound to it may still be exported: an export made after that binds `zeros(128)` in its place, and no import accepts the resulting SCC (<<KLEE-SCC-export>>).

[[KLEE-state-save-and-restore-order]]
== Context Switching, KLEE State Save and Restore Order

_While this section is architecturally informative and non-normative, it provides guidelines for privileged software writers that must be followed in order to avoid security defects._

This section collects the duties that the KLEE state places on privileged software and exception handlers, in the order software meets them.
An item that cites a rule SR__n__ restates a normative requirement of <<KLEE-software-requirements>>, which takes precedence.

[[KLEE-shared-hart-state]]
=== KLEE State Shared by All Modes

The following KLEE state exists once per hart, and every mode can read and change it:

* the lockers;
* `klstart` (<<KLEE-CSR-klstart>>);
* `klmanagedlocker` (<<KLEE-CSR-klmanagedlocker>>, <<KLEE-managed-locker-rules>>);
* with `Zklio`, `kliobuflen`, `kliobuftop` and the KLIOBUF; and
* the authentication registers `SIV`, `IMPQUAL` and `SIV2` (<<KLEE-KLF>>).

[[KLEE-isolation-between-modes]]
=== Isolation Between Privilege Modes

* Before giving control to a less privileged mode, clear, or save and clear, every locker you have configured, and leave none in a Configuration State (Rule <<KLEE-SR-clear-before-lower-mode>>).
* When switching to a less privileged component, restore only its own lockers and clear the others, together with `kliobuflen` and, when it is non-zero, the KLIOBUF (Rule <<KLEE-SR-restore-own-lockers>>).
* While the KLEE state of a less privileged context is live, first save the state you use and restore it before returning (Rule <<KLEE-SR-save-shared-state>>, <<KLEE-save-order>>, <<KLEE-restore-order>>).

[[KLEE-handler-duties]]
=== Duties of Every Exception Handler

Every trap handler, and any other code that shares the KLEE state of the interrupted software, is <<KLEE-interposed-software,interposed software>>, bound by Rules <<KLEE-SR-klstart-save>> to <<KLEE-SR-klstart-restore>>, <<KLEE-SR-klmanagedlocker-write>> and <<KLEE-SR-nested-export-first>>.

On entry, before its first KLEE instruction, the handler:

. saves `klstart`, whose value other KLEE instructions may overwrite (Rule <<KLEE-SR-klstart-save>>);
. saves `klmanagedlocker` (Rule <<KLEE-SR-klmanagedlocker-write>>);
. writes 0 to `klstart` before its first instruction that honors it (Rule <<KLEE-SR-klstart-zero>>); and
. saves the vector state, and writes 0 to `vstart`, before its first vector KLEE instruction (Rule <<KLEE-GR-vector-legality>>).

Before each instruction whose locker `klmanagedlocker` determines, the handler:

* writes to `klmanagedlocker` the number of the locker it intends to act on, or 32 for a transfer to or from the KLIOBUF (Rule <<KLEE-SR-klmanagedlocker-write>>); and
* writes 32, or the number of the target locker, before a `kl.mgmt` that names its locker explicitly (Rules <<KLEE-GR-mgmt-klmanagedlocker-check>> and <<KLEE-SR-klmanagedlocker-write>>).

On exit, the handler:

. restores `klmanagedlocker` to its saved value, or to 32 if it has cleared, instead of saving, the locker that value named (<<KLEE-clearing-instead-of-saving>>);
. restores `klstart` last, exactly as saved (Rules <<KLEE-SR-klstart-restore>> and <<KLEE-SR-klstart-no-reset>>); and

. restores the vector state, `vstart` included.

[[KLEE-reading-locker-state]]
=== Reading the _State_ of a Locker

* `kl.getst Xd, KLML` reads the _State_ of the locker that `klmanagedlocker` names; with `klmanagedlocker` = 32 it returns 0 (Rule <<KLEE-GR-klml-no-managed-locker>>).
* To inspect lockers whose numbers it holds in registers, software writes each number in turn to `klmanagedlocker` and names `KLML`.
* `kl.getst` reads the _State_, `kl.getstx` the _StateExtension_, and `kl.getmd` the whole MDH, which an export passes to its completing `kl.mgmt` and which is the entire locker in an Error State (<<KLEE-error-state-transfer>>).
* A handler prefers the forms without a vector operand: `kl.getst`, `kl.getmd`, Forms A and B of `kl.size`, and Form D of `kl.mgmt`.
* On RV32, `kl.getst` and `kl.getstx` expand to `kl.getmdl`, which writes the pair `X[d+1] @ X[d]`, so `d` must be even; `kl.getmd` writes a pair on RV64 and, on RV32, a quartet whose first register number is a multiple of four (Rule <<KLEE-GR-multiple-GPRs>>).
* A _State_ in 48–55, that is, with `(State & 0x38) = 0x30`, is an Error State (<<KLEE-states-error>>).
* Since usage instructions fall through _Unconfigured_ and Error-State lockers, and, through their handlers, Configuration-State ones, as no-ops or at most with zeros as output and the _State_ unchanged (Rules <<KLEE-GR-transition-to-from-unconfigured>>, <<KLEE-GR-usage-locker-error-state>>, <<KLEE-GR-usage-locker-config-state>> and <<KLEE-SR-handler-duty>>), software that relies on the output must check that the locker is in a Valid State before using the output.
  Checking immediately after the instruction also protects against a reconfiguration of the locker in between, which only improper software performs, ignoring the coordination that Rule <<KLEE-SR-no-interleaving>> calls for.
* `klmanagedlocker` need not name a locker under management: a handler checks the _State_ of the locker it names before choosing a save path, and saves no image for an _Unconfigured_ locker.

[[KLEE-management-routines]]
=== Management Routines

* A management routine takes the locker number as a parameter.
  On entry it saves `klmanagedlocker` and writes the parameter to it;
  it names the locker `KLML` in every KLEE instruction;
  it writes the parameter again before every opening, a restart included (Rule <<KLEE-GR-klml-openings>>); and
  on exit it restores the saved value (<<Zkl-pseudocode.adoc#KLEE-management-code-snippets>>).
  A handler can thus call it, also for a nested export or import of the locker that the interrupted operation manages.
* Software that completes or abandons a management operation writes 32 to `klmanagedlocker`, or restores the value it saved (Rule <<KLEE-SR-klmanagedlocker-finish>>).
* After each management instruction, the routine reads the _State_ of the locker: _Unconfigured_ means the locker has been cleared, so a provisioning or an import restarts and an export has lost its CC (Rule <<KLEE-GR-cleared-under-management>>); an Error State means the operation has failed.
* An export sizes its buffer with `kl.size`, and reads the size again after its opening `kl.mgmt`.
* Software does not interleave cryptographic operations, or the management of other lockers, with the steps of a management operation.
Code that must coordinates them applies Rule <<KLEE-SR-no-interleaving>>.

[[KLEE-save-order]]
=== Context Save Order

. Save `klstart`.
. Save `klmanagedlocker`.
. With `Zklio`:
.. save `kliobuflen` and `kliobuftop`;
.. if `kliobuflen` is non-zero, save the buffer contents with `kl.output`, with `klmanagedlocker` = 32, `klstart` = 0 and `kliobuftop` = `kliobuflen`.
. If the saved `klmanagedlocker` is in [0..31], write it back to `klmanagedlocker`, read the _State_ of the locker with `kl.getst` on `KLML`, and choose the save path by State:
.. _Unconfigured_: save no locker image;
.. an Error State: save its MDH by the short Error-State path (<<KLEE-error-state-transfer>>);
.. otherwise, export the locker before any other `kl.mgmt`.
. Save every other locker that is not _Unconfigured_, with `klmanagedlocker` = 32 between exports.

A handler that passes `ml` through the KLIOBUF configures `kliobuflen` {ge} 16 for the locker exports and imports, and restores the saved value afterwards.

[[KLEE-restore-order]]
=== Context Restore Order

. Restore the lockers other than the one that the saved `klmanagedlocker` indexes, with `klmanagedlocker` = 32 between imports.
. If the saved `klmanagedlocker` is in [0..31] and an image was saved for the locker it indexes, restore that locker last among the lockers.
. With `Zklio`:
.. restore `kliobuflen`;
.. restore the buffer contents, if saved, with `kl.input`, with `klmanagedlocker` = 32, `klstart` = 0 and `kliobuftop` = `kliobuflen`;
.. restore `kliobuftop`.
. Restore the saved value of `klmanagedlocker`, or 32 if the handler has cleared the locker it named instead of saving it.
. Restore `klstart` last.

[[KLEE-clearing-instead-of-saving]]
=== Clearing a Locker Instead of Saving it

Under the conditions of Rules <<KLEE-SR-no-unconditional-clear>> and <<KLEE-SR-never-clear-exporting>>,
a handler may clear a locker being provisioned or imported instead of saving it; the interrupted software then restarts the operation (Rule <<KLEE-GR-cleared-under-management>>).
The handler restores 32 in place of the saved `klmanagedlocker`, and `klstart` as saved.


[[KLEE-managing-another-locker]]
=== Managing Another Locker During a Management Operation

While the managed locker is in State `kl_cfg_exporting` or `kl_cfg_importing`, a handler that must open an export or an import on another locker must:
//
// that overwrites the authentication registers (<<KLEE-KLF>>, Rule <<KLEE-SR-nested-export-first>>):

. first save the managed locker by a nested export, and write 32 to `klmanagedlocker`; and
. restore that locker before returning.

It may instead clear a managed locker in State `kl_cfg_importing`, or terminate the interrupted software.

[[KLEE-handling-klee-exceptions]]
=== Handling a KLEE Exception

A handler that can neither resolve nor forward a KLEE exception covered by Rule <<KLEE-SR-handler-duty>>, nor terminate the process:

. unless the locker is in a Configuration State, sets its Error State from <<KLEE-exception-error-correspondence>>, or _Invalid_ where that table gives none, by the short import of <<KLEE-error-state-transfer>> if the locker is _Unconfigured_; and
. zeroes the output of a usage instruction, and advances `xepc` past the instruction.
// For an instruction naming `KLML`, the locker is the one `klmanagedlocker` names.

[[KLEE-CSK-requirements]]
== Architectural Requirements on the Context Sealing Key

The KLEE unit operates only with an active Context Sealing Key (CSK).
Without one, every KLEE instruction and KLEE CSR access raises a KLEE missing-CSK exception, except accesses to the `mklcsk` and Locality Secret CSR groups (<<Zkl-ISA-priv.adoc#KLEE-CSR-locality-groups>>), which are configured independently of the CSK, and reads of the identification CSRs `klmvendorid`, `klmarchid`, `klmimpid` and `klmaxiobuflen` (<<KLEE-CSR-impl-ids>>, <<KLEE-CSR-klmaxiobuflen>>), so that firmware can identify the KLEE unit before a CSK exists.

The CSK is established in exactly one of four ways:

. M-mode programs it through the `mklcsk` CSR group (<<Zkl-ISA-priv.adoc#KLEE-CSR-mklcsk>>).
. A secure hardware block exclusive to M-mode, such as Caliptra cite:[caliptra], or a port to one, configures it through a dedicated interface based on public-key encryption.
  Only M-mode may request this, by a handle or a wrapped key, and no software, M-mode included, ever sees the clear key; addressing and key transport are platform-specific and outside the scope of this specification.
. It is hardwired at manufacturing time, per die or shared across batches.
. A secure RBG (<<KLEE-Prerequisites>>) generates it at boot, accessible to no software.

// All harts of a well-defined subsystem of an SoC share it, and cannot exchange SCCs with other subsystems; it survives the reset or fatal condition of a single hart, and is regenerated only at the power-on reset of the subsystem.

Only M-mode, under the first way, can read the CSK in clear.
The third and fourth ways suit mainly specialized embedded deployments: a hardwired CSK cannot be reconfigured or revoked, and a boot-generated one cannot preserve SCCs across power loss.
With a hardwired CSK, the KLEE unit is available from reset; otherwise, only once the CSK is established.
A hart reset resets its KLEE state (<<KLEE-reset-and-m-mode-only>>) and, under the first and second ways, its CSK, which must then be established again.

NOTE: When the CSK is shared across devices, CCs meant to be device-bound must name _ChipScrt_ or _DevScrt_ in their _Locality_.

Persistence of a configurable CSK is implementation-specific.
Transferring a CSK to another endpoint, such as the M-mode firmware of another device, a local TPM (for instance across suspension or host hibernation), or a cloud-based HSM, requires an authenticated public-key wrapping mechanism, outside the scope of this specification.

[[KLEE-reset-and-m-mode-only]]
== KLEE Unit Reset and M-mode-only Harts

A _KLEE unit reset_ of a hart resets that hart's KLEE architectural state (<<KLEE-out-of-reset-unpriv>>, <<Zkl-ISA-priv.adoc#KLEE-out-of-reset-priv>>); in a KLEE unit shared by several harts, it affects only that hart's state, shared Locality Secrets excepted.
A hart reset implies a KLEE unit reset of that hart, and so does a fatal condition, with the differences stated in <<KLEE-error-architecture>>.
Reset does not affect a hardwired CSK.

On an M-mode-only hart, every software-programmable Locality Secret whose CSR group is not implemented is unconfigured (<<KLEE-Localities>>), and, where the KLEE Privileged Architecture is not implemented, `KLS` is treated as Initial; <<Zkl-ISA-priv.adoc#KLEE-priv>> states which of its CSRs may exist on such a hart.

[[KLEE-indirect-lockers]]
== Zklind: Indirect Locker Naming

This section applies when `Zklind` is implemented.

Wherever an encoding names a locker, the locker can also be named _indirectly_: the 5-bit immediate locker index names a GPR instead of a locker, and the value in the GPR names the locker.
Indirect addressing is written `K(Xd)`, `K(Xs1)`, and `K(Xs2)` where direct addressing is written `Kd`, `Ks1`, and `Ks2`.
The managed locker `KLML` (Rule <<KLEE-GR-klmanagedlocker-override>>) is not an indirect operand, although it is encoded with `r` = 1 and `X0`, and is available without `Zklind`.
It is written `KLML`: `K(x0)` names no locker, and assemblers reject it.

// [NOTE]
// ====
// Register renaming of lockers remains possible with indirect addressing, but would add much microarchitectural complexity for little benefit: lockers are redefined far less often than GPRs or FP registers, rarely take one key or another conditionally, and speculation on cryptographic results usually creates security issues.
// ====

Where an encoding offers both, bit `r`, called the _locker indexing mode selector_, chooses between them: with `r` = 0 the 5-bit register field is the locker index, and with `r` = 1 it is the number of the GPR holding the index.

In instructions `kl.clone`, `kl.rename`, `kl.swap` (<<KLEE-instruction-clone>>), and `kl.derive` (<<KLEE-instruction-derive>>) Field `R` (bits [26:25]) selects how the lockers are given:

[upperalpha]
. `00`{nbsp}{nbsp} source and destination both as immediates;
. `01`{nbsp}{nbsp} source as an immediate, destination through a GPR;
. `10`{nbsp}{nbsp} source through a GPR, destination as an immediate;
. `11`{nbsp}{nbsp} source and destination both through GPRs.

`kl.avail` and `kl.size` (<<KLEE-instruction-size>>) have an additional variant of Form A:

* `F` = `0b00`, `r` = `1` {implies} Form A, from a context given indirectly as `K(Xs)` (Rule <<KLEE-GR-GPR-indirect>>).

An indirect locker index outside [0..31] raises an illegal-instruction exception, and so does `X0` as the indirect locker index register, except where it encodes `KLML` (Rule <<KLEE-GR-klmanagedlocker-override>>).
