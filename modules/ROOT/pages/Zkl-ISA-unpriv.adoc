[[KLE-unpriv-intro]]
== Introduction

KLE lets software perform high-performance cryptographic operations without direct access to the keys or other critical derived values.
KLE achieves this through the concepts explained next.

[[KLE-concepts]]
=== Foundational Principles and Definitions

Principles are labeled P__n__, where __n__ is a sequential number.
The most important ones define what the KLE architecture is about:

[horizontal]
[[KLE-ISA-Principle-hidden-keys,P1]]P1:: _KLE allows software to use keys that are not exposed to software. It also hides the internal state of the cryptographic algorithms it performs._
[[KLE-ISA-Principle-key-binding,P2]]P2:: _KLE associates each key with an algorithm, and with policies that limit its use to certain privilege modes and bind it to software and hardware environments_.
[[KLE-ISA-Principle-prefix-complete,P3]]P3:: _Every cryptographic operation is atomic. +
If an instruction performs multiple cryptographic operations, it reports prefix-complete progress._
[[KLE-ISA-Principle-multiple-algorithms,P4]]P4:: _Multiple keys can be in use at the same time, and their algorithms composed_.

//

These four Principles prompt the definition of a _Cryptographic Context_:

Definition: _Cryptographic Context_.::
(((Cryptographic Context)))
Most KLE instructions run within the constraints set by a *Cryptographic Context* (CC).
A CC is an indivisible structure consisting of a *Metadata Header* (MDH), with a fixed format and length, and a *Content*, whose size depends on the MDH.
(((Cryptographic Context, Content)))
The Content holds the secrets, such as keys, and other sensitive material.
(((Cryptographic Context, Metadata Header)))
The MDH binds the use of the secrets in the Content to one set of cryptographic algorithms, and, optionally, to a process, VM, security state, boot cycle, expiration date, or other policies.
The MDH requires integrity, except for _ADSDropped_, an unauthenticated format hint (<<KLE-Auxiliary-Data-Section>>); the Content requires integrity and confidentiality.
KLE and the algorithms it implements enforce these requirements architecturally.

[horizontal]
[[KLE-ISA-Principle-contexts-stateful,P5]]P5:: _Cryptographic Contexts are stateful, and record and manage the progress of the algorithm._

Multiple CCs can be active at the same time; a caller must be able to configure them as they need.
This requires an architectural place for them.

[horizontal]
[[KLE-ISA-Principle-management-architectural,P6]]P6:: _Resource management is architectural: resources are managed by software, and their exhaustion is reported by the architecture so that software can take the necessary actions_.

//

KLE applies this Principle by defining Cryptographic Lockers.

Definition: _Cryptographic Locker_.::
(((Cryptographic Locker)))
*Cryptographic Lockers* (_lockers_ for short) are per-hart architectural containers that safeguard their contents.
CCs are created by writing Metadata and Content into a locker, a process called *Provisioning*, which also binds them to each other.
A CC is usable only while in a locker, where only the KLE unit accesses or modifies it, under the rules of the architecture and its Machine; no instruction returns its secrets in clear, except as Rule <<KLE-GR-no-extraction>> allows.

//

A KLE implementation supports 32 lockers.

[horizontal]
[[KLE-ISA-Principle-scalable,P7]]P7:: _KLE is scalable: it works on small and larger cores, with and without vector registers._
[[KLE-ISA-Principle-small-instructions-code,P8]]P8:: _Instructions are as simple as possible, in accord with the RISC-V philosophy, while code sequences stay short._
[[KLE-ISA-Principle-encoding-pressure,P9]]P9:: _Minimize the pressure on the instruction encoding space._

//

Embedding the algorithm's encoding in the MDH is the main mechanism implementing <<KLE-ISA-Principle-encoding-pressure>>.

[horizontal]
[[KLE-ISA-Principle-small-architectural-state,P10]]P10:: _Architectural state beyond the lockers is minimal, and exists once per hart._

Algorithms are implemented by KLE Machines:

Definition: _KLE Machine_.::
(((Machines)))
(((Cryptographic Context, object-oriented)))
A *KLE Machine* (short: _Machine_) is a state machine that implements one or more cryptographic functions (primitives, modes, protocols) through the interface of this specification.
It is fully identified by fields in the MDH.
A small set of KLE instructions operates all Machines: their inputs and outputs come from vector registers, GPRs, and memory, and their semantics depend on the Machine.

Encapsulating Machine-specific behavior in the MDH rather than the instructions lets different primitives (e.g., AES-128, AES-256 and SM4) be used in the same modes (e.g., ECB, GCM-SIV and XTS) without changing the compiled code, and supports side-channel-resistant variants transparently.

[horizontal]
[[KLE-ISA-Principle-no-misuse,P11]]P11:: _A Machine admits only the sequences of operations that its specification defines._
[[KLE-ISA-Principle-cia-inside,P12]]P12:: _Inside a locker, a CC is accessed only through its Machine and the instructions managing it._
[[KLE-ISA-Principle-availability,P13]]P13:: _Software can always configure a new CC, after clearing other lockers if necessary._
[[KLE-ISA-Principle-persistence,P14]]P14:: _A CC can be saved and restored, also into a different locker or on a different implementation, to support features such as context switching, sleep, hibernation and VM migration._
[[KLE-ISA-Principle-confidentiality-integrity,P15]]P15:: _Outside a locker, a CC is sealed: it reveals nothing, and cannot be altered undetected._

The mechanism for saving and restoring CCs is the generation of Sealed Cryptographic Contexts:

Definition: _Sealed Cryptographic Context_.::
(((Cryptographic Context, sealed)))
For context switching, a CC can be *exported* from a locker as a *Sealed Cryptographic Context* (SCC), an encrypted and authenticated representation that can later be *imported* into a locker. Export and import use a _Context Sealing Key_ (CSK), which M-mode may be able to program. An SCC sealed under one CSK cannot be imported under another, which separates spatial and temporal domains cryptographically.

[horizontal]
[[KLE-ISA-Principle-no-privilege-elevation,P16]]P16:: _No operation yields a key or widens a policy: secrets flow only downhill._

<<KLE-ISA-Principle-no-privilege-elevation>> is the same principle behind NIST's key-management recommendations on the associations of a key with its usage and related information (NIST SP 800-57 Part 1 Rev. 5 cite:[nist-SP-800-57-p1-r5], §§6.2.1.4 and 6.2.1.6) and on the cryptographic strength, separation and context binding of derived keys (NIST SP 800-108 Rev. 1, Update 1 cite:[nist-SP-800-108-r1], “Security Considerations”).

Finally, KLE instructions are subdivided into classes, each usable only in certain contexts. Instructions that use the secrets in CCs are bounded by usage policies, whereas those that, for instance, save and restore SCCs can be used at any time. Principles <<KLE-ISA-Principle-availability>> and <<KLE-ISA-Principle-persistence>> exist to prevent denial of service on the resources of the KLE implementation.

Definition: _Instruction Classes and Usage Control_.::
+
--
(((Cryptographic Context, usage control)))
(((Cryptographic Context, management operations)))
(((Cryptographic Context, usage operations)))
KLE distinguishes between *management* operations and *usage* operations on CCs and lockers.
(((Cryptographic Context, export)))
The management operations are *provisioning*, SCC *import*, and *export* of a locker as an SCC; *clearing* a locker, i.e., freeing it and deleting any secret it contains, is a separate configuration instruction.
None of these uses the secrets of a locker for the operations of its Machine. None changes the Machine or the Usage Control policies of a Valid locker, except through the narrowing, provisioning and import defined for it.
Usage operations are cryptographic operations and state changes.
To prevent denial of service, management operations and clearing are less restricted than usage operations: _Usage Control_ policies restrict only usage operations.
--

Definition: _Localities_.::
(((Cryptographic Context, Locality)))
KLE can bind a CC to *Localities*, which restrict where its exported SCCs can be imported and so where it can be restored and used: specific devices or device classes, hardware configurations, physical or virtual boot cycles, and process domains at various privilege modes.
// The Localities act as _tweaks_ in the encryption and decryption of SCCs.

The entire architecture follows from these Principles and Definitions.

[[KLE-architectural-model]]
=== Architectural Model

KLE is architected as an interface to an _attached_ unit: its instructions are messages over a tightly coupled coprocessor interface, and the KLE unit executes them independently of the issuing hart and returns the results.

This keeps the hart side simple: software implements the locker-configuration logic, the KLE unit the cryptography, and several cores may share one KLE unit.

The specification defines only architectural behavior, not implementation: KLE may be integrated into a CPU core or be a distinct hardware unit; either way each client hart has separate KLE architectural state, and the same code runs on both.

KLE may be emulated, partly or completely, in M-mode firmware: an implementation may, for example, perform symmetric operations (<<Zkl-ISA-machines.adoc#KLE-states-symmetric>>) in the KLE unit and emulate public-key cryptography (<<Zkl-ISA-machines.adoc#KLE-ECC>>, <<Zkl-ISA-machines.adoc#KLE-PQC>>), whose very large states then reside in secure memory that meets the requirements of <<KLE-KLF>>, such as on-chip SRAM reserved to M-mode.

No instruction may make key material or other locker state that the KLE holds accessible in the clear to any privileged mode except M-mode and _authenticated Debug mode_, which is Debug mode while the External Debug Security extension (<<KLE-Prerequisites>>) authorizes external debugging of M-mode.
The only locker state exported in the clear is what the software that opened the operation supplied: the `Content` of a partial provisioning (<<KLE-management-formats-and-states>>), and the data loaded by an unfinished system-specific import (Rule <<KLE-GR-sysfmt-as-received>>); since any mode can export it, that software clears or completes the operation before another software context runs (Rule <<Zkl-software.adoc#KLE-SR-clear-before-lower-mode>>).
A misuse that Rule <<Zkl-ISA-machines.adoc#KLE-MGR-caller-limits>> leaves to the caller, such as the reuse of an IV, can still reveal locker state derived from the key, such as the GHASH key of GCM (<<Zkl-ISA-machines.adoc#KLE-accepted-risks>>).
KLE implementations in S/VS-mode or HS-mode are forbidden: instructions and Machines may be emulated only in M-mode.
Trap-and-emulate and on-demand (lazy) SCC import rely on the `*llockerstatus` CSRs (<<Zkl-ISA-priv.adoc#KLE-CSR-llockerstatus>>).

[[KLE-Prerequisites]]
=== Prerequisites

A conformant KLE implementation requires the RISC-V External Debug Security extension cite:[riscvExternalDebugSecurity].

It also requires the KLE exceptions of <<Zkl-ISA-priv.adoc#KLE-exceptions>> to be implemented and raised as the unprivileged architecture mandates, whether or not the other parts of the KLE Privileged Architecture are implemented.

Where the KLE unit or its Machines need an RBG, they must use an entropy source that meets the requirements of the `Zkr` extension (chapter “Cryptography Extensions: Scalar & Entropy Source Instructions”, section “Entropy Source” cite:[RISCV-ISA-Unpriv]), used to seed a DRBG compliant with NIST SP 800-90A cite:[nist-SP-800-90-r1] or with another standard that the implementation documents.
The DRBG must be instantiated with a security strength of at least 256 bits and reseeded from that entropy source at the interval its standard prescribes; another standard may replace SP 800-90A only if it provides at least this strength.
Rule <<KLE-GR-rbg-failure>> covers RBG failure.

[[KLE-Notation-endianness]]
=== Endianness

As defined in <<Zkl-notation.adoc#KLE-Notation-values>>, a PI, an SCC and a PCCC (cf. <<KLE-management-formats-and-states>>) are byte strings: a value `V` of `8n` bits in them, the MDH (cf. <<KLE-Metadata>>) included, occupies `n` consecutive bytes, byte `i` holding `V[8i+7:8i]`, whatever the data endianness (`mstatus.MBE`, `SBE` and `UBE`, and with the H extension `hstatus.VSBE` and `vsstatus.UBE`) of the hart.
KLE memory instructions follow this mapping, and those bits do not affect them.
Software on a hart with big-endian data accesses that moves an MDH between memory and GPRs, or vector elements wider than 8 bits, converts its byte order, for instance with `rev8`, or uses byte accesses.
This convention lets CCs migrate between harts of different endianness.

[[KLE-extensions-overview-unpriv]]
== Extensions Overview

KLE comprises several sub-extensions. Those that define ISA features follow; those that define cryptographic algorithms are listed in <<Zkl-ISA-machines.adoc#KLE-exec-encodings>>.

.Extensions defining KLE ISA features
[,%header,cols="<14%,<56%,<30%"]
|===
| Extension       | Features                                                                | Defined in:
| `Zklv`          | Support for vector registers.                                           | <<KLE-instructions-detailed>>
| `Zklio`         | Support for streaming instructions and the KLIOBUF.                     | <<KLE-KLIOBUF>>, <<KLE-usage-input-output>>
| `Zklmem`        | Dedicated memory instructions.                                          | <<KLE-instructions-memory>>
| `Zklmv`         | Dedicated move instructions.                                            | <<KLE-instruction-mv>>
| `Zklexpire`     | Support for the _ExpirationDate_ metadata field.                        | <<KLE-Metadata-expiration-date>>
|===

`Zkl` conformance requires:

. at least one of `Zklv` and `Zklio`;
. AES-128, AES-192 and AES-256 in ECB and GCM modes, AES-128 and AES-256 in GCM-SIV mode, and SHA2-224, SHA2-256, SHA2-384, SHA2-512, SHA2-512/224 and SHA2-512/256, as defined in <<Zkl-ISA-machines.adoc#KLE-Machines>>; and
. `Zklmem`, in hardware or by trap-and-emulate (<<Zkl-ISA-priv.adoc#KLE-kleemulation>>); in the latter case `Zklmv` in hardware.

KLE instructions may raise the standard RISC-V exceptions and a few KLE-specific exception types, listed in <<Zkl-ISA-priv.adoc#KLE-exception-codes>>.

With trap-and-emulate, the hardware raises an illegal-instruction exception for instructions it does not implement, which the platform must deliver to M-mode (`medeleg` bit 2 zero); the encodings are assigned, not reserved (<<KLE-second-group-ILL-grounds>>).
The emulating code moves data between memory and the locker with `Zklmv` (item 3).
`kl.load` and `kl.store` are always present; `Zklmv` and `Zklexpire` are otherwise optional.

`Zklv` requires the KLV subset of the vector extension (<<KLE-KLV>>) with `VLEN` {ge} 128, that is, `Zvl128b` or a larger `Zvl*b`, which every vector Form that carries an MDH or a 128-bit block needs.

The principal KLE instructions, defined in full below, are:

* `kl.mgmt` (<<KLE-instruction-mgmt>>) moves a locker through its management lifecycle, and,
with the management transfer instructions `kl.load` and `kl.store` (<<KLE-instructions-memory>>), `kl.mvin` and `kl.mvout` (<<KLE-instruction-mv>>),
performs the management operations (<<KLE-management-operations>>), each in several instructions, except on a locker in an Error State (<<KLE-error-state-transfer>>):
 ** *provisioning* loads metadata and clear Content into a locker, binding them;
 ** *export* writes a locker to memory as an SCC;
 ** *import* loads an SCC into a locker.
* `kl.clear` (<<KLE-instruction-clear>>) unconfigures and clears a locker. It is a pseudo-instruction of `kl.setst`, and never part of a management operation.
* `kl.exec` (<<KLE-instruction-exec>>) performs the cryptographic operations that the Machine configured in a locker defines for the locker's current state.
* `kl.setst` (<<KLE-instruction-setst>>) moves the CC in a locker between the states of its Machine.
* `kl.getmd*` (<<KLE-instruction-getmd>>) reads the metadata of a locker. The pseudo-instruction `kl.getst` (<<KLE-instruction-getst>>), built on `kl.getmdl`, extracts the state of a locker from its MDH and also reports errors.

== Architectural State and Operand Sources

[[KLE-cryptographic-registers]]
=== Cryptographic Lockers

{empty}
(((Cryptographic Context)))
KLE defines 32 Cryptographic Lockers, `K0`–`K31`.
Like GPRs or vector registers, lockers are per-hart architectural state, not separated by privilege mode: a hart sees the same lockers in every mode.
Unlike a conventional register, a locker can be _unconfigured_; that is, it holds no CC.
A locker is addressed by a 5-bit immediate in instruction encodings.
Some instructions may also name the named locker, written `KLNL`, whose number is taken from a CSR.

The CC in a configured locker consists of a Metadata Header (MDH) and `Content` (<<KLE-concepts>>).
The _i_-th locker is denoted `K(i)`, its MDH `K(i).MDH`, and its content `K(i).Content`.
During import and export, and in an SCC, the content consists of two consecutive arrays of 128-bit blocks:
`Content1`, the architected content that <<Zkl-ISA-machines.adoc#KLE-Machines>> specifies for each Machine,
and `Content2`, any implementation-specific content.

[[KLE-KLF]]
=== The Cryptographic Locker File and Authentication Information

(((Cryptographic Locker File)))Lockers reside in a per-hart _cryptographic locker file_ (KLF), a memory that only the KLE implementation can access.
Where the implementation is emulated, in part or in full, only M-mode firmware accesses it, through an implementation-defined mechanism that the implementation must provide.

The KLF guarantees the confidentiality and integrity of its contents, also against rollback through any access this specification does not permit.
This specification can only recommend side-channel resistance, not require it.
It *strongly recommends* that every path that handles a locker's secrets (reconstruction, re-sharing, KLF access, `SCC_KeyDeriv`, `SCC_Encrypt`, `SCC_Decrypt`, and every use of the CSK and its derived keys) resist timing, other side-channel and fault-injection attacks at least as well as the locker's Machine at its _SCProtection_ level (<<KLE-SCProtection-field>>), and that a path serving several Machines do so at the highest level among them.
What an implementation achieves is established only by the certifications that its implementer provides, if any.

NOTE: Side-channel resistance depends on how a path is implemented, for instance on the core that runs an emulated path, and this specification defines only architectural behavior, so it accepts the risk of timing leakage.
If `SCC_KeyDeriv`, `SCC_Encrypt` or `SCC_Decrypt` leaks timing, software below M-mode, which chooses the SCCs that an import decrypts and can time each `kl.mgmt`, may recover the keys derived from the CSK, and then decrypt and forge every SCC sealed under that CSK.
Every _SCProtection_ level, Level A included, is likewise a target: a locker has the protection that the implementation documents for its level (<<KLE-SC-protection-levels>>).

NOTE: The KLF resists rollback, but an SCC does not: it can be imported again, under the same CSK and Localities, as long as it exists.
Any party that holds an SCC can replay an earlier CC state: the software that stores it, and any mode that could export the locker.
This may enable multi-time-pad or nonce-reuse attacks on every Machine whose security rests on a fresh IV, nonce or counter: CBC, CFB, OFB, CTR, XCTR, GCM, OCB, Ascon-AEAD128 and, for message equality only, GCM-SIV.
A CC owner must trust the party that stores its SCCs for freshness, clear its lockers before another software context runs (Rule <<Zkl-software.adoc#KLE-SR-clear-before-lower-mode>>), use a Machine whose security survives replay, or accept the risk.
Re-import also has legitimate uses, such as retrying an operation after payload corruption, that policies cannot readily distinguish from misuse.


Architecturally, the KLF holds two distinct parts, whatever the implementation:

. an array of 32 128-bit blocks, whose _i_-th entry holds the MDH of `K(i)`, so that every locker holds its MDH, if only to show that it is unconfigured; and
. an implementation-defined amount of memory, allocated dynamically, which holds the `Content` of every configured locker.

"`KLF capacity`" refers only to the second part: a locker that holds only its MDH consumes none, and the capacity a locker consumes depends on its MDH (<<KLE-length-rule>>).
Insufficient capacity may prevent a configuration instruction from executing; unconfiguring other lockers frees capacity.
The number of lockers, 32, comes from the 5-bit register fields of the encoding, not from the capacity.
An implementation need not hold 32 configured lockers at once.
The KLF capacity must suffice for two fully configured CCs of the largest Machine that the implementation supports, each with the largest ADS that the implementation keeps for it, together with any state that the implementation needs while it operates on them.
If system-specific formats (that is, formats other than those that KLE defines) are supported,
the capacity must also include the largest difference between the memory required by the import of a system-specific format and the memory required by the import of a KLE format of the same Machine.
Any further capacity is desirable, but not required.

Corruption of a hart's KLF is unrecoverable: it resets the hart's KLE architectural state (<<KLE-reset-and-m-mode-only>>) and raises a KLE fatal-error exception (<<Zkl-ISA-priv.adoc#KLE-exceptions>>).

The KLE unit holds three 128-bit _authentication registers_, `SIV`, `IMPQUAL` and `SIV2`, with the authentication and identification data of the locker that owns them (<<KLE-auth-reg-association>>); `kl.load`, `kl.store`, `kl.mvin` and `kl.mvout` access them as the leading bytes of the image (<<KLE-instruction-mv>>).
The export-opening `kl.mgmt` of a Valid locker writes `SIV`, and `IMPQUAL` and `SIV2` when the _AuxDataLen_ of the locker's MDH is at least 2.
An import-opening `kl.mgmt`, other than the short import of an Error-State locker (<<KLE-error-state-transfer>>), zeroizes them before the `kl.load` or `kl.mvin` that writes them.

NOTE: The authentication registers exist once per hart, not per locker, to reduce hardware cost, so a second management operation may overwrite those of the first while it is in flight.
Rules <<Zkl-software.adoc#KLE-SR-nested-export-first>> and <<Zkl-software.adoc#KLE-SR-no-interleaving>> state what software must do.

[[KLE-KLV]]
=== RVV/KLV

KLE takes its inputs and outputs from vector registers, from an architectural input/output buffer (KLIOBUF) loaded from and stored to memory, or from both.

(((KLV)))Vector registers need only a minimal subset of the V extension, _KLV_ (KLE-subset of V).
KLV must be fully opcode-compatible with RVV: code written for KLV behaves identically under V with `Zvbc`, for the vector configurations that KLV supports.
KLV comprises:

* vector registers of at least 128 bits;
* the CSRs `vstart`, `vl`, `vtype` and `vlenb`, with their RVV 1.0 semantics;
* the configuration-setting instructions `vsetvli`, `vsetivli` and `vsetvl`, with:
** tail-agnostic and mask-agnostic configurations only, since KLE neither uses vector masking nor defines masked instructions, and always applies a tail-agnostic policy (bit 25 of the `kl.exec` encoding is reserved for masked operations, should a compelling use case arise);
** `SEW` values 8, 16, 32 and 64, with `ELEN` = 64;
** `LMUL` values 1, 2, 4 and 8; and
** for a configuration that KLV does not support, `vtype.vill` is set and `vl` = 0, as in RVV;
a KLE instruction with a vector operand raises an illegal-instruction exception if `vtype.vill` is set;
* the unit-stride loads and stores `vle<eew>.v` and `vse<eew>.v` of element widths 8, 16, 32 and 64 whose `EMUL` is 1, 2, 4 or 8;
* the whole-register loads, stores and moves `vl<n>re<eew>.v`, `vs<n>r.v` and `vmv<n>r.v`, for context switches;
* `vmv.x.s`, `vmv.s.x`, and the slides `vslideup.v[xi]`, `vslidedown.v[xi]`, `vslide1up.vx` and `vslide1down.vx`, to move data into and out of vector registers;
* the logical operations `vand.v[vxi]`, `vor.v[vxi]` and `vxor.v[vxi]` (the immediate forms give, for instance, a bitwise NOT); and
* `vclmul.v[vx]` and `vclmulh.v[vx]` of `Zvbc`, for `SEW` = 64 only, as in `Zvbc`; they may be trap-and-emulated.

KLV requires the listed instructions only with `vm` = 1; their masked encodings are reserved.

Floating-point, fixed-point and general arithmetic vector operations are not required.

NOTE: KLE has no concept of an element, and it is not part of the vector unit: it sees a vector register (including a vector register group if `LMUL` > 1) as a bit string of length `KLLEN` = `VL` {times} `SEW`, where `VL` is the vector length in effect (`vl`).

KLE takes the length of a vector operand from `VL` {times} `SEW` alone (`VL` = 2 with `SEW` = 64 and `VL` = 4 with `SEW` = 32, for example, both give 128 bits): the CPU decode side uses `VL` and `SEW` to determine how much data to send to the KLE unit, which needs only their product.

[[KLE-KLIOBUF]]
=== KLIOBUF

When `Zklio` is implemented, the architectural input/output buffer KLIOBUF may replace vector registers.
The KLIOBUF is per-hart architectural state, not separated by privilege mode, but it is not part of the KLF.

The `Zklio` instructions `kl.input` and `kl.output` transfer data between the KLIOBUF and memory, and the base extension `kl.exec` then uses Forms whose inputs and outputs are implicitly in the KLIOBUF (<<KLE-usage-input-output>>).
<<KLE-CSR-kliobuftop>> defines `KLLEN` for KLIOBUF operands.

[[KLE-Metadata]]
== Metadata

An SCC carries two kinds of metadata:

. the 128-bit _MDH_, always present, which determines the Machine, the key type and the key's usage policies; its first 64 bits determine the length of a PI or SCC; and
. the optional 128-bit _Implementation Qualifier_ `IMPQUAL`, which copies the three KLE analogues of the hart's `mvendorid`, `marchid` and `mimpid` CSRs, namely `mklvendorid`, `mklarchid` and `mklimpid` (<<KLE-Auxiliary-Data-Section>> gives the format of `IMPQUAL`).
It is present when an SCC has _AuxDataLen_ {ge} 2, and lets an implementation determine whether it can use the implementation-specific content of the SCC (<<KLE-Auxiliary-Data-Section>>).

In the rest of the document, “metadata” refers to the first type. The implementation qualifier is always called `IMPQUAL`.

<<KLE-metadata-header>> summarizes the MDH fields, which the following subsections describe.

[[KLE-Machine-field]]
=== _Machine_ and _MachinePolicy_ Fields

_Machine_ is a 12-bit field. Values 0–3071 are architecture-defined, with encodings maintained by RVI (<<Zkl-ISA-machines.adoc#KLE-Machines>>); the remaining values are for custom Machines.

The meaning of _MachinePolicy_ depends on the Machine:

* For encryption/decryption primitives and modes, bit 0 of _MachinePolicy_ permits encryption and bit 1 decryption.
* For asymmetric primitives that support signatures, bit 0 permits their generation and bit 1 verification.
* For MACs that generate and verify tags, bit 0 permits generation and bit 1 verification.

In the future, _MachineExtension_ may be used to encode more Machines.

Rule <<Zkl-ISA-machines.adoc#KLE-MGR-policy-gate>> states how _MachinePolicy_ gates the States of a Machine, and which values are valid.

[[KLE-SCProtection-field]]
=== _SCProtection_ Field

KLE defines three side-channel protection levels, Levels A, B and C, encoded in _SCProtection_ as the values 0, 1 and 2.
Value 3 is reserved, and makes the Metadata invalid (<<KLE-Metadata-validity>>).
cite:[riscvPlatformSecurityModel] gives the threat model and security concepts in which these levels are used.

[[KLE-SC-protection-levels]]
.Encoding of Side-Channel Protection levels
[float="center",align="center",cols="^7%,^7%,<86%",options="header"]
|===
| Value  | Level | Description
|   0    | A     | No timing leakage: the same cryptographic operation on the same number of input units takes the same time in the KLE unit, whatever the values of the key, of the internal state, of the input data and of any random value drawn for the operation, except for the dependence that the cryptographic method itself requires (below).
|   1    | B     | No timing leakage; differential side-channel protection.
|   2    | C     | The protection of Level B;
detection of injected faults, followed either by completion with the correct result and no other physical leakage, or by
a transition to a fatal error condition (see <<KLE-error-architecture>>).
|===

A level applies to the operations that need it for security, such as signature generation but not signature verification, and only as far as the cryptographic method of the Machine needs it: the execution time of ML-DSA, for instance, may depend on the number of iterations of its rejection loops (<<Zkl-ISA-machines.adoc#KLE-PQC-ML-DSA>>).

An implementation must document, for each level it supports, the standard and edition, assessment profile, security level and test metrics it meets, such as acquisition-time limits and trace sample sizes; Level B, resp. C, must offer at least the guarantees documented for Level A, resp. B.

[NOTE]
====
This specification gives no assurance profiles for these levels.
A CC provider that sends its keys to a secure receiver, such as a TEE applet that forwards the CC to the software consuming it, negotiates the protection level and its assessment profile with it by a system-specific mechanism.
Relevant references are ISO/IEC 19790:2025 cite:[ISOIEC-19790-2025] for the security requirements of cryptographic modules, ISO/IEC 24759:2025 cite:[ISOIEC-24759-2025] for their testing, ISO/IEC 17825:2024 cite:[ISOIEC-17825-2024] for testing the mitigation of non-invasive attacks, and FIPS 140-3 cite:[nist-fips-140-3], which adopts ISO/IEC 19790:2012 and ISO/IEC 24759:2017 with CMVP modifications; and NIST SP 800-140F cite:[nist-SP-800-140F].
====
// , where the CMVP lists approved non-invasive test metrics, currently specifies none.
// Acquisition-time limits and trace sample sizes measure the effort of a test, not how long an attack is resisted; nor does a FIPS level number state such a duration, or make an assessment equivalent to one under the later ISO/IEC editions.

[[KLE-State-field]]
=== _State_ and _StateExtension_ Fields

_State_ tracks the state of a locker and its Machine: _Unconfigured_, encrypting or decrypting, initializing, absorbing into or finalizing a hash, computing point multiples, signing or verifying, or in an error state, for instance.
_StateExtension_ is used to keep further state information, usually orthogonal or additional to _State_.
The tables in this section give the values of _State_ and _StateExtension_ common to all Machines, including that of a locker with no Machine, and the States used for CC management.

[[KLE-def-unconfigured]]Definition: _Unconfigured Locker_.::
A locker is _Unconfigured_ when _State_ and _StateExtension_ are 0: every other field of the MDH then reads zero and has no meaning, and the locker has no Usage Policy, Expiration Date or Key Type.
An _Unconfigured_ locker holds no Content beyond the MDH.

[[KLE-locker-in-error-state]]Definition: _Error State_.::
(((KLE, Machine, error states)))
A locker is in an _Error State_, which reports a KLE error, when _State_ is 0 and _StateExtension_ is 1–6: _StateExtension_ holds the code of the Error State (<<KLE-stateexts-error>>).
A locker in an Error State holds no Content beyond the MDH, whose other fields keep their values except as Rule <<KLE-GR-clear-locker-content-error-state>> states. Entering an Error State overwrites _StateExtension_ with its code, and no Machine defines a _StateExtension_ @ _State_ 0.
The Error-State image of such a locker (<<KLE-error-state-transfer>>) also consists only of the MDH.

[[KLE-def-inert]]Definition: _Inert Locker_.::
An _Inert_ locker is a locker that is either _Unconfigured_ or in an Error State, or the named locker `KLNL` while `klnamedlocker` = 32.

(((KLE, Machine, invalid state)))
(((Cryptographic Locker, invalidation)))
A locker is said to be _invalidated_ when it transitions to Error State _Invalid_ (i.e., _State_ = 0 and _StateExtension_ = `kl_stateext_invalid`).

Without `Zklexpire`, no locker can be in Error State _Expired_, and a PI, SCC or PCCC whose MDH carries _StateExtension_ 6 at _State_ 0 is invalid.

A locker being provisioned, exported or imported is in one of the following _Configuration_ States:

[[KLE-KeyType-field]]
=== _KeyType_ Field

_KeyType_ states how the keys of a CC are supplied:

* 0: by value; the keys are provisioned, exported and imported as values.
* 1: by a system-specific, 64-bit System Key Identifier (SKID) (<<KLE-system-keys>>).
* 2: generated randomly by the `kl.mgmt` that completes a base (non-nested) provisioning, all keys of the Machine at once unless the Machine states otherwise; an RBG failure follows Rule <<KLE-GR-rbg-failure>>.
The PI has the layout of one with _KeyType_ = 0, and the generated values replace its key values.
_KeyType_ then becomes 0, so the keys are exported by value; _KeyType_ = 2 occurs only in a PI, in a PCCC of base type `pi` and in a locker being provisioned from them (<<KLE-management-formats-and-states>>).
* 3: reserved; a PI or SCC that carries it is invalid Metadata (<<KLE-Metadata-validity>>).

NOTE: A SKID may refer to keys with unrelated purposes on different devices; the _System Key Store_ (SKS) therefore supplies a _Locality_ for it (Rule <<KLE-GR-skid-policies>>).

[[KLE-Auxiliary-Data-Section]]
=== _AuxDataLen_ and _ADSDropped_ Fields

_AuxDataLen_ gives the length, in 128-bit blocks, of the _Auxiliary Data Section_ (ADS), the variable-size, implementation-specific part of the content; with _ADSDropped_ = 1, it keeps the length before `Content2` was dropped.
With _Version_ = 3, it instead gives the length of the data of a system-specific format (<<KLE-system-specific-import>>), and no rule that reads it as the length of an ADS applies: such an MDH has no ADS, `IMPQUAL` or `SIV2`, and its _ADSDropped_ stays 0.
Zero means no ADS; the maximum, 2^14^ − 1, is 262,128 bytes.

If _AuxDataLen_ {ge} 2, the SCC includes a copy of the implementation qualifier of the originating implementation (<<Zkl-ISA-priv.adoc#KLE-CSR-impl-ids>>),
the 128-bit `IMPQUAL`:

``{fournbsp}{fournbsp}IMPQUAL := zeros(32) @ mklimpid[31:0] @ mklarchid[31:0] @ mklvendorid[31:0]``.

The importing implementation compares the whole 128 bits with its own `IMPQUAL`, and uses the ADS only if the two are equal; an implementation has no other compatibility rule.
An implementation that produces an ADS must have values of `mklvendorid`, `mklarchid` and `mklimpid` out of KLE unit reset that no implementation with a different ADS format has, and `mklvendorid` and `mklarchid` not both 0.
An M-mode handler that emulates a Machine and writes an ADS for the lockers it holds (<<Zkl-ISA-priv.adoc#KLE-unsupported-handling>>) qualifies that ADS itself, for instance with an `IMPQUAL` of its own, which must also be unique per ADS format, as for the KLE unit.
_AuxDataLen_ counts these 16 bytes and the 16-byte authentication tag of the ADS, so, unless it is the length of the payload of a system-specific format, it is 0 or at least 2, and 1 is invalid.
Outside a system-specific format, _AuxDataLen_ is implementation-dependent, and its value never depends on key material, a secret field, plaintext or ciphertext, or a value drawn for an operation: it depends only on the other fields of the MDH and on the progress that Rule <<KLE-GR-long-running-progress>> allows, since `kl.getmd*` returns it in every mode and State.

_ADSDropped_, bit 47 of the MDH, is an unauthenticated format hint, ignored in an SCC whose _AuxDataLen_ is 0 and subject to the validity conditions of <<KLE-Metadata-validity>>; first-segment authentication clears it only in its local copy of the MDH.
After an import, `K(i).MDH` holds _ADSDropped_ = 0, and an absent or dropped `Content2` leaves _AuxDataLen_ = 0 (<<KLE-SCC-import>>); an export uses the _AuxDataLen_ of the MDH, which the implementation keeps up to date (<<KLE-SCC-export>>).
With _AuxDataLen_ {ge} 2 and _ADSDropped_ = 1, `Content2` is absent, and `IMPQUAL` and `SIV2` remain as non-authoritative padding that keeps the offset of `Content1` unchanged.
Setting _ADSDropped_ in an SCC tells the import to drop the optional `Content2`, and the import then zeroes the implementation-defined subfields of _MachineUse_ and _AuxInfo_ (<<KLE-MachineUse>>).
Clearing it requests second-segment processing; if that fails, the import drops `Content2`, but it still accepts the authenticated `Content1` (<<KLE-SCC-import>>).
Toggling it cannot affect `Content1` or any policy, make an unauthenticated `Content2` usable, or bypass first-segment authentication; dropping `Content2` can at most force a restart of an interrupted long-running operation (Rule <<KLE-GR-long-running-restart>>).

[[KLE-UsagePolicy]]
=== _UsagePolicy_ Field

_UsagePolicy_ determines which modes may use the locker.
A _usage instruction_ uses the Machine in a locker to operate on the locker's internal state, or to expose it, as a `kl.exec` that produces output does; Usage Control applies only to these instructions, listed in <<KLE-instruction-properties>>.
Bits 0–4, when set, allow usage in U-mode (VU-mode included), VS-mode, S-mode (HS-mode with the H extension), M-mode, and Debug mode, respectively.
Usage in Debug mode requires bit 4 and, outside authenticated Debug mode (<<KLE-architectural-model>>), also that bits 0–3 allow the debug access privilege of the External Debug Security extension, which is the most privileged mode for which it allows external debug, and every mode below it, so that a debugger authorized only for lower privilege modes gains no usage that those modes lack.

WARNING: The Debug-mode rule above is based on a draft of the External Debug Security extension (the debug access privilege). It must be revisited when that extension is ratified.

A clear bit denies its mode, so a zero _UsagePolicy_ admits no mode: software sets each permission deliberately.
`mstatus.MPRV` is not considered, and the bit of a mode that is unsupported or not enabled has no effect, because it is never checked.

[[KLE-Localities]]
=== _Locality_ Field

_Locality_ names 128-bit Locality Secrets (LSs), listed in <<KLE-locality-indexes>> and stored in a possibly virtual Locality Secrets Table (LST).
Some entries are fixed, or configurable only by an implementation-specific, authenticated hardware process, and shared by all KLE units of an SoC; the others are software-programmable, per-hart architectural state.

At SCC export and import, the Localities named in _Locality_ cryptographically bind the SCC to the _current_ hardware and software environments.
The binding ends at import: if a Locality Secret changes later, the next export binds its SCC to the new value.
// Software must prevent unauthorized parties from accessing the lockers directly (Rule <<Zkl-software.adoc#KLE-SR-clear-before-lower-mode>>).

[[KLE-Metadata-expiration-date]]
=== _ExpirationDate_ Field

_ExpirationDate_ is in effect only with `Zklexpire`, which requires the KLE implementation to access a secure clock.
Without `Zklexpire`, a non-zero _ExpirationDate_ in a PI or SCC is invalid Metadata (<<KLE-Metadata-validity>>).

A non-zero 20-bit _ExpirationDate_ gives the CC's expiration in whole hours since 00:00 UTC, 1 January 2027, spanning about 119 years and 7 months, independent of time zones.
Software below M-mode must not be able to set the clock.
A secure clock reports monotonically non-decreasing time, even under attempts to roll it back.

[NOTE]
====
The assurance of the clock, like that of the _SCProtection_ levels (<<KLE-SCProtection-field>>), is set by security standards and platform profiles, not by this specification.
It is *strongly recommended* that a platform with `Zklexpire` document its clock, and that the clock:

* map to UTC with a documented resolution, maximum error and drift;
* keep advancing, or be trustworthily resynchronized, across suspension, reset, power loss and the restore of a saved platform or VM state;
* be protected against unauthorized setting, rollback and stoppage, or detect them; and
* report itself unavailable, never as zero or a pre-epoch date, while its UTC mapping, progress or error bounds cannot be trusted, until a trusted recovery.
====

_ExpirationDate_ is evaluated only:

* at the issue of any usage instruction, for `kl.derive` at both endpoints; and
* when a usage instruction resumes after a halt, but not between the blocks or component operations of one execution.

Each execution reads the clock at most once, before any component operation, and a passed check covers the rest of it, even if the date passes meanwhile.
An unavailable clock on resumption leaves the prefix committed before the halt in place (Rule <<KLE-exception-state-change>>).

The _ExpirationDate_ of a locker that is not in a Valid State is not evaluated: only an expired locker in active use transitions to Error State _Expired_, and expired contexts can still be managed cleanly.

The evaluation proceeds as follows:

. If _ExpirationDate_ is zero, the instruction proceeds.
. If the secure clock cannot be read, the instruction raises a KLE clock-unavailable exception (<<Zkl-ISA-priv.adoc#KLE-exception-codes>>) and leaves the _State_ unchanged.
. The secure clock's date is converted to the _ExpirationDate_ format, in whole hours rounded down; a reading before the epoch converts to 0, and one at or after 2^20^ − 1 hours converts to 2^20^ − 1.
. If the converted value is at least _ExpirationDate_, the locker transitions to Error State _Expired_; otherwise the instruction proceeds.

An unreadable secure clock traps, rather than making the instruction a silent no-op, so that M-mode can handle the failure, which may also be induced by glitching the clock.
The instruction keeps the _State_, so that a handler that restores the clock can re-execute it; a handler that cannot restore the clock can put the locker in Error State _Expired_ with `kl.setste` (<<KLE-instruction-setste>>).

[[KLE-MachineUse]]
=== _MachineUse_ and _AuxInfo_ Fields

A Machine may use _MachineUse_ and _AuxInfo_ to store additional information.

An implementation may use a field, or a subfield, that its Machine does not use: each Machine specification identifies the bits it defines, and the others, including progress in an implementation-defined format (Rule <<KLE-GR-long-running-progress>>), are _implementation-defined_.
Their values are disposable: ignoring them preserves the architected semantics, policies and parameters of the Machine, at the cost of a restart at most.
An implementation that uses such a value keeps _AuxDataLen_ {ge} 2 in the MDH, exactly 2 when `Content2` is empty, so that every SCC it exports includes an ADS (<<KLE-Auxiliary-Data-Section>>).
An import, or an export completion that restores a Valid State, interprets them only if both segments authenticate, even with an empty `Content2`, and the authenticated `IMPQUAL` equals that of the importing implementation.
Otherwise, if the ADS is absent or discarded (_ADSDropped_ = 1 included), that operation zeroes them after first-segment authentication and before the locker becomes Valid; the Machine then proceeds from the architected fields alone, restarting as Rule <<KLE-GR-long-running-restart>> requires.
`kl.clearads` zeroes them likewise in a resident locker, so that `kl.getmd*` and a later export observe zeros; later computation may set new values, but never restore the discarded ones.

Neither field may hold a value that depends on key material, a secret field, plaintext or a value drawn for the operation, other than the progress that Rule <<KLE-GR-long-running-progress>> allows, since the MDH is not confidential and `kl.getmd*` returns it in every mode and State.

<<KLE-Metadata-validity>> checks these fields only through the unsupported condition on values that a Machine specification declares, and by requiring _MachineUse_ to be zero at a system-specific import (Rule <<KLE-GR-sysfmt-mdh>>).
Otherwise a wrong value causes an error of the Machine that uses it; a discarded implementation-defined value causes none.
Provisioning ignores and zeroes the _MachineUse_ of a PI and the implementation-defined subfields of its _AuxInfo_ (<<KLE-locker-management>>); the completion of a system-specific import (Rule <<KLE-GR-sysfmt-completion>>) zeroes the implementation-defined subfields of _AuxInfo_ that the declared MDH supplies.
The rules of the Machine decide what happens to the subfields of _AuxInfo_ that it defines upon provisioning, and to both fields on entering State _Ready_.
A Machine may use _AuxInfo_ to pass initialization parameters at provisioning: EdDSA (<<Zkl-ISA-machines.adoc#KLE-EdDSA>>), for instance, records in _AuxInfo_ the modes a CC may use.

// ////////////////////////////////////////////////////////////////////

[[KLE-Machine-version]]
=== _Version_ Field

_Version_ gives the version of the MDH format:

* 0: the current format;
* 1: reserved for newer revisions of the format, whose further version information is encoded in other MDH fields; unsupported in this revision;
* 2: reserved; and
* 3: a system-specific format, used only for import (<<KLE-system-specific-import>>).

A PI, SCC or PCCC with a _Version_ that the implementation does not support is invalid Metadata (<<KLE-Metadata-validity>>).
It is invalid, not _Unsupported_: the version fixes the layout of the MDH, so no other field can be interpreted.

[[KLE-Metadata-validity]]
=== Validity of Metadata

In a PI, software keeps all _reserved_ bits, and all bits that the Machine does not use, zero; elsewhere, software passes unchanged the MDH bits that the implementation wrote.

Valid Metadata is _unsupported_ when any of the following holds:

* the combination of _Machine_, _MachinePolicy_, _MachineExtension_ and an _SCProtection_ value of 0 to 2 (Levels A to C) is not implemented;
* _KeyType_ is 1, resp. 2, and the implementation does not support System Key Identifiers, resp. random key generation, for the Machine (<<KLE-KeyType-field>>, <<KLE-system-keys>>); or
* it holds a value that a Machine specification declares unsupported if not implemented, such as the _AuxInfo_ of EdDSA (<<Zkl-ISA-machines.adoc#KLE-EdDSA>>).

A supplied MDH is _invalid_ when any of the following holds:

* _Version_ is unsupported, or is 3 in a PI or in a PCCC of base type `pi`;
* _Version_ is 3 at import and any of the following holds: _State_ is not _Unconfigured_, `kl_cfg_importing` or `kl_cfg_exporting`; _AuxDataLen_ is zero; or one of _StateExtension_, _KeyType_, _ADSDropped_ and _MachineUse_ is non-zero (<<KLE-system-specific-import>>);
* _KeyType_ is 1 or 2 for a Machine whose Provisioning Input has no key field, for instance the unkeyed hash functions and XOFs, the ECC, ML-KEM and ML-DSA Machines, and the NIK variants of HMAC;
* _KeyType_ is 3, or 2 outside a PI and a PCCC of base type `pi`;
* _SCProtection_ is 3, a reserved value (<<KLE-SCProtection-field>>);
* _Locality_[5:4] is 3, or _Locality_ names an unconfigured Locality Secret without a configured substitute (<<KLE-Localities>>);
* the MDH carries a custom _Machine_ or a system-specific _Version_ without the _Locality_ binding that Rule <<KLE-GR-custom-locality>> requires;
* _State_ is not 0, or _StateExtension_ is non-zero (an Error State), at provisioning, or _State_ is 0 and _StateExtension_ is 7–15 at import;
* _State_ is 61–63 at import, or _Unconfigured_ at an import whose _Version_ is not 3 (<<KLE-State-management>>);
* in an SCC or PCCC, _StateExtension_ @ _State_ is a value that the Machine does not support; for this condition, every Machine supports _State_ 0 with a _StateExtension_ of 1–5, and of 6 with `Zklexpire`, and the Configuration States 56–60 with any _StateExtension_;
* _StateExtension_ is 6 (_Expired_) at _State_ 0 in an SCC or PCCC when `Zklexpire` is not implemented;
* _ExpirationDate_ is non-zero and `Zklexpire` is not implemented;
* _AuxDataLen_ = 1 and _Version_ is not 3;
* _AuxDataLen_ or _ADSDropped_ is non-zero in a PI, or in a PCCC with base type `pi` (<<KLE-management-formats-and-states>>);
* _MachinePolicy_ has a value that Rule <<Zkl-ISA-machines.adoc#KLE-MGR-policy-gate>> does not admit for the Machine, such as zero for a Machine that requires at least one set bit in it; or
* a Reserved bit is non-zero.

Invalid Metadata takes precedence over unsupported Metadata: the test for _unsupported_ applies only to valid Metadata, as only a valid _Version_ fixes the layout of the fields it reads.

[[KLE-Metadata-narrowing]]
=== Narrowing of Metadata

Several operations narrow the policies of a CC by those of another source, by the narrowing defined below: the resolution of a SKID (<<KLE-system-keys>>),
a restricted `kl.derive` (Rule <<KLE-GR-narrowing>>), the import of a system-specific format (<<KLE-system-specific-import>>),
and `kl.rstr*`, at the request of software (<<KLE-instruction-restrict>>).

The _narrowing_ of an MDH _A_ by the policies of a source _B_ (an MDH, the
policies that the SKS associates with a key, or those that a system-specific format carries) is _A_ with the following
fields replaced; a policy field that _B_ does not carry leaves that field of _A_ unchanged, and no other field changes:

* _MachinePolicy_: for `kl.rstrl` and `kl.rstrv` only, the AND of both, so that the functions enabled are those that both enable (Rule <<KLE-GR-policy-narrowing-state>>); every other narrowing leaves it unchanged, even when _B_ is an MDH.
* _UsagePolicy_: the AND of both, so that the modes that may use the CC are those that both allow.
* _Locality_ (<<KLE-locality-indexes>>): each HW Binding subfield (bits [1:0] and [3:2]) takes the larger value, that is, the stricter entry of its chain, zero meaning no binding; the Boot Session subfield (bits [5:4]) takes the non-zero value if only one is non-zero, and their common value if they are equal; and bits 6–8 are OR-ed.
* _ExpirationDate_, with `Zklexpire`: the smaller non-zero value, or 0 if both are 0.
Without `Zklexpire`, an expiration among the policies of the SKS or of a system-specific format makes the narrowing fail.

If both Boot Session subfields are non-zero and differ, or if the resulting _Locality_ names an unconfigured entry without a configured substitute (<<KLE-Localities>>), the policies cannot be met, and the narrowing _fails_; each operation that narrows states the outcome.
Narrowing never changes _SCProtection_.

KLE provides the following unprivileged CSRs.
Like `vstart` and `vl`, they are unprivileged; the getter and setter instructions are nevertheless the recommended way for software to access them (<<KLE-instruction-getter-setter>>).

The `KLS` field in effect controls access to these CSRs: while it is Off, every access, a read of a CSR that M-mode emulates included, raises an illegal-instruction exception (<<Zkl-ISA-priv.adoc#KLE-KLS-field-in-mstatus>>).

A CSR whose description gives a maximum is WARL: writing a larger value sets the maximum, so software must read it back (for software below M-mode, by means of the getter instructions of <<KLE-instruction-getter-setter>>).
Writing a reserved value to `klnamedlocker`, which has no maximum, leaves it unchanged (<<KLE-CSR-klnamedlocker>>).

[[KLE-CSR-kliobuflen]]
=== kliobuflen

(((CSR, `kliobuflen`)))`kliobuflen` is an XLEN-bit URW CSR that programs the length of the KLIOBUF, in bytes, for `kl.input` and `kl.output`; its maximum is the maximum length of the KLIOBUF (<<Zkl-ISA-priv.adoc#KLE-CSR-mklmaxiobuflen>>).
Every write, even of the current value, zeroes the buffer below the new length before it completes, and sets `kliobuftop` to that length.
Bytes beyond the new length need not be erased, since they stay inaccessible until a later write zeroes them: a write of zero makes the contents inaccessible without erasing them, unless the implementation supports Level C (<<KLE-destructive-config>>).

A zero `kliobuflen` leaves the KLIOBUF _unconfigured_: an operation that expects an input or an output in it raises an illegal-instruction exception (Rule <<KLE-GR-iobuf-configured>>).

// <<Zkl-software.adoc#KLE-pseudocode-examples>> provides the necessary guidelines for software.

// ////////////////////////////////////////////////////////////////////

[[KLE-CSR-kliobuftop]]
=== kliobuftop

(((CSR, `kliobuftop`)))`kliobuftop` is an XLEN-bit URW CSR that sets the upper bound, in bytes, of the buffer range that `kl.input` and `kl.output` use; its maximum is `kliobuflen`, and `kl.exec` never modifies it.
It is the KLIOBUF counterpart of `VL` in the V extension: it defines the operand length `KLLEN` as `kliobuftop` {times} 8 and the transfer window [0, `kliobuftop`-1].

Writing `kliobuftop` leaves the buffer unchanged, so software can set the length per operation without writing `kliobuflen`, which clears the buffer; this mirrors the use of `VL` {times} `SEW` to supply a partial last block, or a short IV or nonce, to a Machine.

A value invalid for a Machine is detected only when an instruction that uses the KLIOBUF is later issued or restarted, with the outcomes given in <<KLE-usage-input-output>>.

// ////////////////////////////////////////////////////////////////////

[[KLE-CSR-klstart]]
=== klstart

(((CSR, `klstart`)))`klstart` is an XLEN-bit URW CSR that records, in bytes, the progress of the instructions that _honor_ it:

* `kl.load`, `kl.store`, `kl.input` and `kl.output`: the bytes read or written;
* `kl.exec` with a vector or KLIOBUF operand, which may be interrupted at its interruption points (Rule <<KLE-GR-interruption-point>>): the bytes processed;
* `kl.derive`, which is uninterruptible, requires `klstart` = 0 (Rule <<KLE-GR-checks>>) and leaves it 0; and
* `kl.mvin` and `kl.mvout`, vector or not: the locker transfer point.

KLE has no intrinsic element length and no counterpart of the Element Group Width (EGW) or Element Group Size (EGS) of the vector crypto extension, or the Effective Element Width (EEW) of the vector extension; its instructions, such as `kl.exec`, are architecturally decoupled from the operations the KLE unit performs for them.
`klstart` is a byte count; Machines or their implementations record progress that is not byte-structured, such as that of the point multiplications and signature operations of <<Zkl-ISA-machines.adoc#KLE-ECC>> and <<Zkl-ISA-machines.adoc#KLE-PQC>>, in their progress field, in _MachineUse_ (Rule <<KLE-GR-long-running-progress>>).

Like `vstart` in the V extension, `klstart` is the position within the _transfer window_ of `kl.exec` at which processing starts or resumes: bytes [0, `kliobuftop`-1] for a KLIOBUF operand, with `kliobuflen` non-zero, and [0, `VL` {times} `SEW`/8 - 1] for a vector operand.
The memory instructions and `kl.mvin` and `kl.mvout` define their own windows (<<KLE-iobuf-transfer-window>>, <<KLE-serialized-image>>).

Rule <<KLE-GR-klstart-updates>> lists the events that change `klstart`, Rules <<KLE-GR-interruption-point>> and <<KLE-GR-transfer-window-checks>> state how `kl.exec` checks it, and <<Zkl-software.adoc#KLE-pseudocode-examples>> provides guidelines for software.

// ////////////////////////////////////////////////////////////////////

[[KLE-CSR-klnamedlocker]]
=== klnamedlocker

(((CSR, `klnamedlocker`)))`klnamedlocker` is an XLEN-bit URW CSR; only 6 of its bits are currently used.
It holds the number of the locker named for management transfers and `KLNL`, or 32 if none.
Completing a management operation, even with an error, keeps the number, so that software can inspect the outcome through `KLNL` before writing 32 or restoring a saved value.
Values 33 and above are reserved; writing one leaves `klnamedlocker` unchanged.
While the locker it names is in a Configuration State, that locker is under management; software keeps the authentication registers `SIV`, `IMPQUAL` and `SIV2` associated with the locker under management (<<KLE-auth-reg-association>>).

The named locker serves two purposes:

. a single management routine using the named locker can manage any locker, which reduces code size; and
. a clear of the named locker sets `klnamedlocker` to 32 (Rule <<KLE-GR-klnamedlocker-updates>>), which code that does not rewrite `klnamedlocker` during a management operation detects; other code checks the outcome with `kl.getst`.
// . the outcome stays readable: `klnamedlocker` keeps its value on completion, on entry into an Error State and on any other KLE exception, so a check through `KLNL` reads the outcome.

Addressing the named locker when `klnamedlocker` is 32 causes the instruction to fall through: Rule <<KLE-GR-outcome-inert>>.

Rule <<KLE-GR-klnamedlocker-updates>> lists the events that change `klnamedlocker`, Rules <<KLE-GR-klnamedlocker-override>>, <<KLE-GR-locker-less-transfers>> and <<KLE-GR-outcome-inert>> state how instructions use it, and <<Zkl-software.adoc#KLE-pseudocode-examples>> provides guidelines for software writers.

[[KLE-instructions-detailed]]
== Instructions

_This section specifies only the semantics and encodings of the unprivileged KLE instructions, not their behavior in the various States of the Machines, how they respect usage policies, how they use randomness, how they access memory, or whether they are interruptible.
The rules governing these aspects are grouped in <<KLE-ISA-rules>>._

Where an instruction's behavior depends on a rule, its description states that behavior and references the rule.

[[KLE-no-operation]]Definition: _No Operation_.::
(((no operation)))
An instruction that *performs no operation* performs none of the operations of the KLE unit, such as cryptographic operations, but may still have the effects that its description or a rule states, such as writing zeros to its output, writing 0 to `klstart`, setting `klnamedlocker`, or raising an exception.

[[KLE-general-rules-instructions]]
=== General Rules Governing Encoding and Arguments

// `%offset` denotes the instruction's sign-extended 12-bit immediate: bits [31:20] for `kl.load` and `kl.input` (I-type), and bits [31:25] @ [11:7] for `kl.store` and `kl.output` (S-type).
// The base register is always in bits [19:15] (`rs1`), and the effective address of a transfer is `X[rs1] + %offset`, modulo 2^XLEN^.
// This is the address of the *first* byte of the transfer, even for a multi-byte or resumed transfer; a resumed transfer restarts at that address plus `klstart` bytes.
// Each instruction gives the correspondence between addresses and transfer offsets.

The following rules apply to all KLE instructions, unless stated otherwise.

[horizontal]
[[KLE-GR-reserved-encodings,GR1]]GR1:: In every encoding, fields shown with fixed values must hold them.
Any other value of such a field, and any unlisted combination of field values, is a reserved encoding and raises an illegal-instruction exception (<<KLE-second-group-ILL-grounds>>).

[[KLE-GR-multiple-GPRs,GR2]]GR2:: _Use of multiple GPRs for longer inputs:_ A 64-bit operand is one GPR on RV64 and the pair `(X[s+1],X[s])`, as `X[s+1] @ X[s]`, on RV32.
A 128-bit operand is the pair `X[s+1] @ X[s]` on RV64 and the quartet `X[s+3] @ X[s+2] @ X[s+1] @ X[s]` on RV32.
This holds for sources and destinations alike.
The lowest register number of a pair must be even, and that of a quartet a multiple of four; otherwise an illegal-instruction exception is raised.
A pair or quartet is read or written as a whole.
Here and in every instruction description, RV32 and RV64 denote an XLEN of 32, resp. 64, in the privilege mode executing the instruction.

[[KLE-GR-x0-operand,GR3]]GR3:: If `X0` is used as a destination or source register, writes to it are discarded, and it reads as zero.
When the lowest register of a pair or quartet is `X0`, no register of the group is written, and the group reads as zero.

[[KLE-GR-klnamedlocker-override,GR4]]GR4:: Every instruction that can encode a locker number may encode instead the named locker, written `KLNL`: the locker that `klnamedlocker` names when the instruction issues, or no locker if `klnamedlocker` = 32 (Rule <<KLE-GR-outcome-inert>>).
The encoding fields `r` and `R` serve only to encode `KLNL`, in place of a locker register field, which must then hold `X0`: `r` = 1 for the single locker operand; in `kl.clone`, `kl.rename`, `kl.swap` and `kl.derive`, `R` = `01` for the first operand, the destination, and `R` = `10` for the second, the source; `R` = `11` is reserved.
A non-zero locker register field that `r` or `R` replaces is a reserved encoding.

[[KLE-GR-locker-less-transfers,GR5]]GR5:: The management transfer instructions, `kl.load`, `kl.store`, `kl.mvin` and `kl.mvout`, have no locker operand: they act on the locker that `klnamedlocker` names.

[[KLE-GR-vector-MDH-operand,GR6]]GR6:: Where a KLE instruction carries the whole 128-bit MDH in a vector register or group, such as the MDH-formatted operand of `kl.rstrv` and the destination of `kl.getmdv`, the operand must satisfy `VL` {times} `SEW` {ge} 128; otherwise an illegal-instruction exception is raised.
<<KLE-extensions-overview-unpriv>> lists the vector extensions that provide such a register.

[[KLE-GR-vector-legality,GR7]]GR7:: A vector register operand whose register number is not a multiple of the LMUL in effect is a reserved encoding and raises an illegal-instruction exception, as in RVV 1.0.
Every KLE instruction with a vector operand sets `vstart` to 0 when it retires, and on a precise halt sets it as Rules <<KLE-GR-precise-halt>> and <<KLE-GR-klstart-vstart>> prescribe.
An instruction with a vector operand that produces no `vstart` value (`kl.getmdv`, `kl.rstrv`, Form C of `kl.size`, `kl.avail`, `kl.setst` and `kl.mgmt`) raises an illegal-instruction exception if issued with `vstart` {ne} 0, as RVV 1.0 {sect}3.7 permits for a `vstart` value that the instruction can never produce.

[[KLE-GR-klstart-vstart,GR8]]GR8:: KLE instructions with vector operands that use `klstart` for resumption update `klstart` and `vstart` simultaneously and independently, each by its own semantics; except for `kl.mvin` and `kl.mvout`, both denote the same point of progress, `klstart` in bytes and `vstart` in elements of the width in effect.
Issuing a Form A–C `kl.exec` with `klstart` {ne} `vstart` {times} `SEW`/8 raises an illegal-instruction exception.
Each unit keeps its own information, and the two values can still be explicitly "`desynced`", as in locker management operations.
A Machine whose interruption points are not multiples of `SEW`/8, such as CFB with `u` not a multiple of 8, is resumable at all of them only with `SEW` = 8 (Rule <<KLE-GR-interruption-point>>).
+
`kl.mvin` and `kl.mvout` keep the two independent by design: their `klstart` is a locker offset that accumulates across instructions, while `vstart` tracks the vector register.

[[KLE-management-operations]]
=== Provisioning, Import, and Export

// _This section is informative and non-normative. It serves to place the management operations in their context._

Setting aside the handling of lockers in an Error State, a *management* operation takes three steps: the first and the last are one KLE instruction each, and the second is one or more `kl.mvin` or `kl.mvout` (alternatively, `kl.load` or `kl.store`) instructions:

. An opening `kl.mgmt` (<<KLE-instruction-mgmt>>) prepares the locker for the management operation.
. One or more `kl.mvin` (<<KLE-instruction-mv>>) load the rest of the information into the locker, or one or more `kl.mvout` move the locker's information out.
. A completing `kl.mgmt` ends the management operation and makes the locker available to software.

// Setting error handling aside, *provisioning* consists of the following three steps:
//
// . `kl.mgmt` (<<KLE-instruction-mgmt>>) prepares the locker, checks the validity of the MDH, and loads the whole MDH into the locker.
// . One or more `kl.mvin` (<<KLE-instruction-mv>>) load the rest of the provisioning information.
// . `kl.mgmt` completes the provisioning and makes the locker available to software.
//
//
// *Importing* an SCC is similar:
//
// . `kl.mgmt` prepares the locker to accept an SCC, checks the validity of the MDH, and loads the whole MDH into the locker.
// . One or more `kl.mvin` load the rest of the SCC, authentication data first, into the locker.
// . `kl.mgmt` authenticates and decrypts the SCC, and makes the locker available to software.
//
// *Exporting* a locker as an SCC takes five steps:
//
// . `kl.getmd` or `kl.getmdv` (<<KLE-instruction-getmd>>) exports the MDH out of the locker, and `kl.size` (<<KLE-instruction-size>>) gives the size of the SCC, for which software allocates resources.
// . Software stores the MDH to memory.
// . `kl.mgmt` prepares the locker to produce an SCC, encrypting its contents and computing the authentication tag(s).
// . One or more `kl.mvout` move the rest of the SCC, authentication data first, out of the locker.
// . `kl.mgmt` completes the export and restores the locker to a form available to software.

// ////////////////////////////////////////////////////////////////////

[[KLE-instruction-size]]
=== kl.avail and kl.size

`kl.avail` and `kl.size`, together with `kl.getmd`, `kl.getmdl`, and `kl.getmdv` (<<KLE-instruction-getmd>>), are the _inspection_ instructions, i.e., those that examine the MDH but do not change any state.

Synopsis::
`kl.avail` returns 1 if the Machine encoded in the MDH is available in the requested variant, and 0 otherwise.
`kl.size` returns the size in bytes of the memory buffer needed for the data of a PI, an SCC or a system-specific format, or 0 on error, such as an unsupported Machine or an invalid MDH, or raises an illegal-instruction exception for M-mode emulation (item <<KLE-size-avail-lookup>>).

Mnemonic::
+
--
`kl.avail` and `kl.size` have three Forms:
(((KLE, instruction, kl.size)))
(((KLE, instruction, kl.avail)))

[upperalpha]
. `kl.{avail,size}  Xd, Ks` - Size from a context.
. `kl.{avail,size}  Xd, Xs` - Size from MDH[63:0] in one (RV64) or two (RV32) GPRs.
. `kl.{avail,size}  Xd, Vs` - Size from MDH in one vector register.
--

Encoding::
+
--
The encoding shares the opcode, `funct3` and `funct2` (the two msbs of `funct7`) of `kl.exec`, with bit 27 set.
Bit 25, `q`, selects `kl.size` (`q` = 0) or `kl.avail` (`q` = 1).

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Xd' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'Ks/Xs/Vs' },
    { bits:  5, name: 0x0 },
    { bits:  1, name: 'q' },
    { bits:  1, name: 'r', attr: ['KLNL'] },
    { bits:  1, name: 0x1 },
    { bits:  2, name: 'F' },
    { bits:  2, name: 0x0, attr: ['funct2'] },
]}
....

Field `F` selects the Form:

* `F` = `0b00` {implies} Form A, from a context `Ks`.
* `F` = `0b01` {implies} Form B, from an MDH in one (RV64) or two (RV32) GPRs.
* `F` = `0b10` {implies} Form C, from an MDH in a 128-bit vector register.

`r` must be 0 in Forms B and C; `r` = 1 there is a reserved encoding.
--

Description:: {empty}
+
--
`kl.avail` (`q` = 1) tells whether the KLE unit implements the _Machine fields_ of an MDH: its _Machine_, _MachinePolicy_, _MachineExtension_, _KeyType_ and _SCProtection_ (no non-zero _MachineExtension_ is currently defined).
`kl.size` (`q` = 0) gives the size in bytes of the external image that an MDH describes: a PI, an SCC with its tag(s) and ADS, the MDH of a system-specific format followed by its appended data (Rule <<KLE-GR-sysfmt-mdh>>), or, for an Error State, the MDH alone (<<KLE-management-formats-and-states>>, <<KLE-length-rule>>).

The MDH is that of locker `Ks` in Form A, where `Ks` may be `KLNL` (Rule <<KLE-GR-klnamedlocker-override>>); bits [63:0] in `Xs`, or `X[s+1] @ Xs` on RV32, in Form B; and bits [127:0] in `Vs` in Form C.
Form B examines only bits [63:0], since no field in bits [127:64] affects the size of any structure (<<KLE-length-rule>>); conditions on those fields, such as Rule <<KLE-GR-custom-locality>> and the _AuxInfo_ of a Machine, are not applied.

`content1_size` is the length in bytes of the `Content1` of an SCC for the given MDH, and `pi_content_size` that of the `Content` of a PI, both determined according to <<KLE-length-rule>>.
`content2_size` is 16 * (_AuxDataLen_ - 2) if _AuxDataLen_ {ge} 2 and _ADSDropped_ = 0, and 0 otherwise.

For both instructions, the checks of Rule <<KLE-GR-management-check-order>> come first; among them are `r` = 1 in Form B or C (a reserved encoding), `vstart` {ne} 0 in Form C (Rule <<KLE-GR-vector-legality>>) and, in Form A, a locker that is _Off_.
The instruction then writes to `Xd` the value of the first item of its list that applies.

`kl.size` returns or raises, evaluated in order:

. Form A: 0 if `Ks` is `KLNL` while `klnamedlocker` = 32 or the locker is _Unconfigured_, 16 if the locker is in an Error State, and otherwise the size of item 7;
. Forms B and C: 0 if _State_ is 61–63, or is 0 with a _StateExtension_ of 7–15 (reserved);
. 16 if _State_ is 0 with a _StateExtension_ of 1–5, or 6 with `Zklexpire` (an Error State) (<<KLE-error-state-transfer>>);
. 0 if _Version_ is 1 or 2, or if _SCProtection_ or _KeyType_ holds a reserved value;
. [[KLE-size-avail-lookup,5]]if the KLE unit does not natively implement the Machine fields: an illegal-instruction exception if `mstatus.kleemulation` = 1 (<<Zkl-ISA-priv.adoc#KLE-kleemulation>>), so that M-mode can supply the value, and 0 otherwise;
. 0 if the MDH is unsupported or invalid Metadata (<<KLE-Metadata-validity>>), evaluated as at provisioning when _State_ is 0 and _Version_ is not 3, and as at import otherwise;
. the size:
.. 16 + 16 {times} _AuxDataLen_ if _Version_ is 3, whatever the _State_;
//: _Version_ 3 becomes 0 only when the base import concludes (<<KLE-system-specific-import>>);
.. if _State_ is a Valid State or `kl_cfg_{importing|exporting}`: 32 + `content1_size` if _AuxDataLen_ = 0, and 64 + `content1_size` + `content2_size` if _AuxDataLen_ {ge} 2, the 64-byte fixed part including `IMPQUAL` and `SIV2` even when _ADSDropped_ = 1;
.. 16 + `pi_content_size` if _State_ is `kl_cfg_provisioning`, `kl_cfg_ppi_importing` or `kl_cfg_ppi_exporting`, or if a supplied MDH has _State_ 0 (the MDH of a PI).

`kl.avail` returns or raises, evaluated in order:

. Form A: 0 if `Ks` is `KLNL` while `klnamedlocker` = 32 or the locker is _Unconfigured_, and otherwise 1 if the KLE unit implements the Machine fields of the MDH, and 0 if not;
. Forms B and C: 0 if _Version_ is 1 or 2, or if _SCProtection_ or _KeyType_ holds a reserved value;
. if the KLE unit does not natively implement the Machine fields: same as item <<KLE-size-avail-lookup>> of `kl.size`;
. 1 otherwise, whatever the other fields hold: a 1 does not exclude a KLE unsupported-Metadata exception that a Machine specification attaches to another field, such as the _AuxInfo_ of EdDSA.

Every item before the lookup is independent of which Machines are implemented, so the lookup traps only when the KLE unit does not natively implement the Machine fields; M-mode then supplies the value of the remaining items.
--

[[KLE-instruction-exec]]
=== kl.exec

Synopsis::
Perform a cryptographic operation in the KLE unit.

Mnemonic::
+
--
`kl.exec` has four Forms:
(((KLE, instruction, kl.exec)))

[upperalpha]
. `kl.exec  Vd, Kn, Vs2` {nbsp} reads an input vector and writes an output vector.
. `kl.exec  {fournbsp} Kn, Vs2` {nbsp} reads an input vector and writes no output vector.
. `kl.exec  Vd, Kn {fournbsp}{nbsp}` {nbsp} reads no input vector and writes an output vector.
. `kl.exec  {fournbsp} Kn {fournbsp}{nbsp}` {nbsp} reads no input vector and writes no output vector.
--

Encoding::
`kl.exec` is an R-type instruction.
+
--
[wavedrom, , svg]
....

{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'rd', attr: ['Vd','—','Vd','—'] },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: "'rs1' (n)", attr: ['Kn'] },
    { bits:  5, name: 'rs2', attr: ['Vs2','Vs2','—','—'] },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'r', attr: ['KLNL'] },
    { bits:  1, name: 0x0 },
    { bits:  2, name: 'Form', attr: ['0    0','0    1','1    0','1    1'] },
    { bits:  2, name: 0x0, attr: ['funct2'] },
]}
....

The encodings of Forms A–D are:

[upperalpha]
. `Form` = `0b00`.
. `Form` = `0b01` and `rd` = `0b00000`.
. `Form` = `0b10` and `rs2` = `0b00000`.
. `Form` = `0b11` and `rd` = `rs2` = `0b00000`.

The locker operand is always in `rs1`.
An unused register field (`rd` without an output vector, `rs2` without an input vector) must be zero, except in the encodings that `Zklmv` assigns (<<KLE-instruction-mv>>); other non-zero values in it are reserved.
--

Description::
+
--
Performs a cryptographic operation defined by the Machine in locker `Kn` and its state, possibly taking an input and producing an output; `Kn` may be `KLNL` (Rule <<KLE-GR-klnamedlocker-override>>).
When it performs no operation (under Rule <<KLE-GR-outcome-inert>>) or transitions the locker to an Error State, it zeroes the unwritten part of its output window instead of producing further output (Rule <<KLE-GR-zero-unwritten-output>>).

In Form A, each output block has the length of its input block and is written at the same window offset, so `Vd` and `Vs2` may always be the same register group, each block's output replacing its input; any other overlap of `Vd` with `Vs2` raises an illegal-instruction exception.

NOTE: A future version of this specification may define the semantics of _expanding_ or _narrowing_ multi-block `kl.exec` operations, whose output blocks are longer, respectively shorter, than their input blocks. No current Machine defines such operations.

Without `Zklv`, only Form D is supported: Forms A–C raise an illegal-instruction exception, and `kl.input` and `kl.output` supply the inputs of `kl.exec` and extract its outputs (<<KLE-usage-input-output>>).
--

[[KLE-instruction-mv]]
=== kl.mvin and kl.mvout

The `Zklmv` subextension adds dedicated move instructions between scalar/vector registers and a locker.
The instructions in this extension are encoded as new forms of `kl.exec`.

Synopsis::
  Move content between scalar/vector registers or the KLIOBUF and the locker under management, which is in a Configuration State.

Mnemonics::
+
--
`kl.mvin` and `kl.mvout` have three variants each:
(((KLE, instruction, kl.mvin)))(((KLE, instruction, kl.mvout)))

[upperroman]
. `kl.mvin Xs2` copies 128 bits from two or four GPRs into the locker.
. `kl.mvin Vs2` copies one or more 128-bit blocks from a vector register into the locker.
. `kl.mvin KLIOBUF` copies one or more 128-bit blocks from the KLIOBUF into the locker.
. `kl.mvout Xs1` copies 128 bits from the locker into two or four GPRs at `Xs1`.
. `kl.mvout Vs1` copies one or more 128-bit blocks from the locker into a vector register `Vs1`.
. `kl.mvout KLIOBUF` copies one or more 128-bit blocks from the locker into the KLIOBUF.

The locker is not an operand: the instruction acts on the locker that `klnamedlocker` names (Rule <<KLE-GR-locker-less-transfers>>).
--

Encodings::
+
--
The encodings are variants of `kl.exec` Form D (`Form` = `0b11`) in which `rd`, zero in `kl.exec`, is non-zero and selects the variant. No locker is encoded, so `r` = 0; a non-zero `r` is reserved.

[upperroman]
. `kl.mvin Xs2`:       `rd` = `0b00001`, `rs1` = `0`, and `rs2` holds the source GPR.
. `kl.mvin Vs2`:       `rd` = `0b00010`, `rs1` = `0`, and `rs2` holds the source vector register.
. `kl.mvin KLIOBUF`:   `rd` = `0b00011`, `rs1` = `0`, and `rs2` = `0b00000`.
. `kl.mvout Xs1`:      `rd` = `0b00101`, `rs2` = `0`, and `rs1` names the destination GPR.
. `kl.mvout Vs1`:      `rd` = `0b00110`, `rs2` = `0`, and `rs1` names the destination vector register.
. `kl.mvout KLIOBUF`:  `rd` = `0b00111`, `rs2` = `0`, and `rs1` = `0b00000`.

Any other non-zero value of `rd` in Form D is reserved and raises an illegal-instruction exception.
A non-zero `rs1` in variants I–III or VI, or a non-zero `rs2` in variants III–VI, is likewise reserved and raises an illegal-instruction exception.
--

Description::
+
--
`kl.mvin` moves the <<KLE-serialized-image,serialized image>> `S` into, and `kl.mvout` out of, the named locker (Rule <<KLE-GR-locker-less-transfers>>).
Neither transfers the MDH: for a provisioning or an import, the opening `kl.mgmt` has already loaded it (<<KLE-instruction-mgmt>>), and `kl.getmd*` reads it.

[[KLE-mv-locker-checks,locker checks]]Locker checks::
The named locker must be in a Configuration State that admits the instruction, and `klstart` must be a multiple of 16:
+
* `kl.mvin`, a locker being provisioned or imported: `kl_cfg_provisioning`, `kl_cfg_importing` or `kl_cfg_ppi_importing` (Rule <<KLE-GR-zkl-load-mv-allowed>>);
* `kl.mvout`, a locker being exported: `kl_cfg_exporting` or `kl_cfg_ppi_exporting` (Rule <<KLE-GR-zkl-load-mv-allowed>>).
+
Otherwise an illegal-instruction exception is raised, except on an _Unconfigured_ or Error-State locker, on which the instruction performs no operation, whatever `klstart` is (Rule <<KLE-GR-outcome-inert>>).

Transfer::
`kl.mvin` and `kl.mvout` process the operand window in 16-byte blocks, in order: if `klstart` < `image_end`, the block of the <<KLE-serialized-image,serialized image>> `S` at offset `klstart` is transferred and `klstart` advances by 16; otherwise `kl.mvin` ignores the block, `kl.mvout` writes zeros to it, and `klstart` is unchanged. `klstart` is kept across instructions; a sequence of them transfers `S` piecewise.
A GPR variant transfers exactly one block and is uninterruptible; a vector variant transfers one block per 128/`SEW` elements and can be interrupted at a block boundary (Rule <<KLE-GR-interruptibility-classes>>).
If one management operation combines `kl.mvin` or `kl.mvout` with `kl.load` or `kl.store`, each byte of `S` holds the value last written to its offset, by whichever instruction.

Vector variants (II and V)::
They also track progress in `vstart`: each 16-byte block advances it by 128/`SEW` elements, for instance by 4 for 32-bit and by 2 for 64-bit elements.
Element _k_ of the vector operand, for _k_ from `vstart` to `vl` − 1, corresponds to byte offset `klstart` + (_k_ − `vstart`) {times} `SEW`/8 of `S`.
The transfer can halt only at a block boundary: `klstart` then holds the image offset reached, and `vstart` the first unprocessed element; if `vstart` {ge} `vl`, the instruction, after the checks of Rule <<KLE-GR-management-check-order>> and the Locker Checks above, transfers nothing and leaves `klstart` unchanged.

KLIOBUF variants (III and VI)::
They use the KLIOBUF in place of a vector register: they transfer bytes 0 to `kliobuftop` − 1 of the KLIOBUF to or from offsets `klstart` to `klstart` + `kliobuftop` − 1 of `S`, as a vector variant with `vstart` = 0 and `vl` {times} `SEW`/8 = `kliobuftop` does.
Like the GPR variants (I and IV), they are architecturally uninterruptible (Rule <<KLE-GR-interruptibility-classes>>), although they may transfer several blocks: their length is bounded by the maximum length of the KLIOBUF.
+
NOTE: The KLIOBUF variants give an implementation without `Zklv` multi-block transfers: `kl.input` fills the KLIOBUF from memory, with `klnamedlocker` = 32, and `kl.mvin KLIOBUF` moves it into the locker, with `klnamedlocker` naming that locker, as `kl.input` and `kl.exec` cooperate for the inputs of a Machine (<<KLE-usage-input-output>>).
Their window is the KLIOBUF up to `kliobuftop`, so they need no element position, and a transfer of at most that maximum length can be uninterruptible.
`kl.input` and `kl.mvin KLIOBUF` share `klstart`: the first reads it as its resume point and writes 0 to it, while the second reads and advances it as the offset in the image.
`kl.output` and `kl.mvout KLIOBUF` share it likewise, so software saves and restores it around each `kl.input` or `kl.output` (Rule <<Zkl-software.adoc#KLE-SR-klstart-iobuf>>).

Exceptions and no-operation cases::
The checks are made in the order of Rule <<KLE-GR-management-check-order>>.
A vector variant whose vector extension is not enabled, or whose `vl` {times} `SEW`/8 or `vstart` {times} `SEW`/8 is not a multiple of 16, raises an illegal-instruction exception (<<KLE-second-group-ILL-grounds>>), on any locker.
So does a KLIOBUF variant if `kliobuftop` is not a multiple of 16.
+
After the locker-state-independent checks, on an _Unconfigured_ or Error-State locker, or when `klnamedlocker` = 32, every variant performs no operation, whatever `klstart` is, and raises no exception (Rules <<KLE-GR-outcome-inert>>, <<KLE-GR-fall-through-operands>>); `kl.mvout` writes zeros to its destination.
+
Otherwise, besides the Locker Checks above, a KLIOBUF variant raises an illegal-instruction exception if the KLIOBUF is unconfigured; without `Zklio` it always is (Rule <<KLE-GR-iobuf-configured>>).
+
On a locker or `klnamedlocker` that makes the variant perform no operation, a KLIOBUF `kl.mvout` writes zeros to `[0, kliobuftop-1]` of a configured buffer and accesses none otherwise; both directions keep `klstart`.
On such a locker a vector `kl.mvout` writes zeros to elements [`vstart`, `vl`-1] of its destination, the tail following the tail-agnostic policy and the elements below `vstart` unchanged.
--

[[KLE-instruction-setst]]
=== kl.setst and kl.setstq

Synopsis::
Change the state of the Machine encoded in the CC in a locker.

Mnemonic::
`kl.setst` has four Forms:
(((KLE, instruction, kl.setst)))
+
[upperalpha]
. `kl.setst{nbsp}{nbsp}Kd, #immed7{fournbsp}{nbsp}{nbsp}` with no auxiliary input.
. `kl.setst{nbsp}{nbsp}Kd, #immed7, Xs{nbsp}` with auxiliary input in one or two GPRs (RV64/RV32).
. `kl.setst{nbsp}{nbsp}Kd, #immed7, Vs{nbsp}` with auxiliary input in a vector register.
. `kl.setstq{nbsp}Kd, #immed7, Xs{nbsp}` with auxiliary input in two or four GPRs (RV64/RV32).

//

Encoding::
`kl.setst` is an R-type instruction.
+
--
[wavedrom, ,svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Kd' },
    { bits:  3, name: 0x3, attr: ['kl.setst'] },
    { bits:  5, name: 'rs1' },
    { bits:  1, name: 'r', attr: ['KLNL'] },
    { bits:  2, name: 'F' },
    { bits:  2, name: 'G' },
    { bits:  7, name: 'immed7' },
]}
....

The following are separate instructions that share the encoding space of `kl.setst`:

* The encodings with `G` = `0b01` define the instruction `kl.setste` (<<KLE-instruction-setste>>). +
* The encodings with `G` = `0b10` belong to `kl.set*` (<<KLE-instruction-getter-setter>>). +
* The encodings with `G` = `0b11` belong to `kl.mgmt` (<<KLE-instruction-mgmt>>).

`#immed7` = `kl_cfg_clearall` (65) is valid only in Form A, with `Kd` = 0 and `r` = 0, where it encodes `kl.clearall` (<<KLE-instruction-clearall>>); every other encoding with `G` = `0b00` and `#immed7` = 65 is reserved.

The encodings of the four Forms are:

* `F` = `0b00`, `rs1` = `0b00000`: Form A, whose auxiliary operand reads as zero (Rule <<KLE-GR-x0-operand>>).
* `F` = `0b00`, `rs1` {ne} `0b00000`: Form B, with a 64-bit auxiliary operand in `Xs` = `rs1` (RV64) or in `X[s+1] @ Xs` (RV32, Rule <<KLE-GR-multiple-GPRs>>).
* `F` = `0b01`: Form C.
* `F` = `0b10`: Form D, with a 128-bit auxiliary operand in two (RV64) or four (RV32) GPRs starting at `Xs` = `rs1` (Rule <<KLE-GR-multiple-GPRs>>).
* `F` = `0b11` is reserved (Rule <<KLE-GR-reserved-encodings>>).

Form A is Form B with `X0`: where a Machine expects Form B or D, a Form A supplies an operand of zero; where it expects Form A, a Form B or D is a wrong Form (Rule <<KLE-GR-form-mismatch>>).
Where a Machine expects Form C, Rule <<Zkl-ISA-machines.adoc#KLE-MGR-form-D-where-C>> says which other Forms are admitted.
--

// ////////////////////////////////////////////////////////////////////

Description::
+
--
`kl.setst` advances the Machine of locker `Kd` from one stage to another, for instance from initializing a hash function to absorbing data and finalizing the digest.
It normally reaches the State that `#immed7` names, but some States transition automatically to another State when the instruction completes.
<<KLE-State-management>> and each Machine's specification give the allowed transitions.
`kl.setst` may also set state information orthogonal to these stages, possibly as a prerequisite for entering another State.

For all Machines, `#immed7` takes these values:

* 0 (`kl_state_inert`) encodes `kl.clear` (<<KLE-instruction-clear>>), which clears the locker in any Form without reading any auxiliary operand, the locker-state-independent checks of Rule <<KLE-GR-management-check-order>> still applying.
* 1–53 name the _Valid_ States that _Ready_ and the Machine define (<<KLE-states-valid>>).
* 54 and 55 name _Success_ and _Failure_ of the Machine, that cannot be set directly (Rule <<KLE-GR-success-failure-cannot-be-set-directly>>); _Failure_ is an outcome, not an error.
* 56–63 are reserved encodings (Rule <<KLE-GR-reserved-encodings>>); with `G` = `0b11` instead of `0b00`, the values 56–58 and 63 encode `kl.mgmt` (<<KLE-instruction-mgmt>>), and 59–62 are reserved encodings.
* 64 encodes `kl_cfg_clear_ads` (<<KLE-instruction-clearads>>).
* 65 encodes `kl_cfg_clearall` (<<KLE-instruction-clearall>>), in Form A with locker 0 and `r` = 0 only.
* 66–127 are Machine-defined, and may change other state information, such as _StateExtension_.

The State class of the locker decides the outcome of an immediate in 1–55, 64 or 66–127:

* in a Valid State, Rule <<KLE-GR-outcome-valid-state>> applies: unless one of its items 1–3 applies first, an immediate that neither the architecture nor the Machine admits in the current State (Rule <<KLE-GR-setst-not-admitted>>), 54 and 55 included, or a wrong Form, transitions the locker to Error State _Invalid_;
* in a Configuration State, Rule <<KLE-GR-outcome-config-state>> applies: a usage instruction raises a KLE privilege-violation exception and leaves the _State_ unchanged;
* on an _inert locker_ (Unconfigured, in an Error State or `KLNL` while `klnamedlocker` = 32), the instruction performs no operation (Rule <<KLE-GR-outcome-inert>>).

Some values require an auxiliary operand, in GPRs (Forms B and D) or in a vector register `Vs` (Form C).

`Kd` may be `KLNL`, except for `kl.clearall` (Rules <<KLE-GR-klnamedlocker-override>> and <<KLE-GR-outcome-inert>>).
--

[[KLE-instruction-setste]]
==== kl.setste

Synopsis::
Set a locker to an Error State.

Mnemonic::
(((KLE, instruction, kl.setste)))
`kl.setste Kd, #immed7`

Encoding::
`kl.setste` is the encoding of `kl.setst` (<<KLE-instruction-setst>>) with `G` = `0b01`, valid only with `F` = `0b00`, `rs1` = `0b00000` and `#immed7` in 1–6.
Every other encoding with `G` = `0b01` is reserved, and so is `#immed7` = 6 without `Zklexpire`.

Description::
`kl.setste` sets _State_ to 0 (_Inert_) and _StateExtension_ to `#immed7`, the code of an Error State (<<KLE-stateexts-error>>).
The "e" stands for empty and error.
It sets _State_ to 0 in every State.
It is a configuration instruction, admitted in every State (Rule <<KLE-GR-error-state-can-be-reconfigured>>).

[[KLE-instruction-clear]]
==== kl.clear

(((KLE, instruction, kl.clear)))`kl.clear Kd` is `kl.setst` (<<KLE-instruction-setst>>) with `#immed7` = `kl_state_inert` (<<KLE-State-field>>), in any Form; it does not read any auxiliary operand, the locker-state-independent checks of Rule <<KLE-GR-management-check-order>> still applying.
It sets the locker's _State_ to _Unconfigured_ and releases its KLF resources.
It is a configuration instruction, not a usage instruction: the _UsagePolicy_ does not restrict it, nor can the Machine (<<KLE-instruction-properties>>).
Rule <<KLE-GR-klnamedlocker-updates>> also applies.

A `kl.clear` sets to Dirty the `*llockerstatus` field in effect for the current privilege mode of its locker if it changes the locker or that field is _Off_ (<<Zkl-ISA-priv.adoc#KLE-CSR-llockerstatus>>), and the `KLS` fields in effect if it changes the locker or `klnamedlocker`, or that field is _Off_.

[[KLE-instruction-clearall]]
==== kl.clearall

(((KLE, instruction, kl.clearall)))`kl.clearall` is `kl.setst` with no auxiliary operand, `#immed7` = `kl_cfg_clearall`, locker number 0 and `r` = 0.
The locker field names no locker: `kl.clearall` acts on every locker whatever the _State_ of `K0`, and is not a usage instruction.

It unconfigures every locker, as `kl.clear` on each would.
With `Zklio`, it also unconfigures the KLIOBUF by setting `kliobuflen` and `kliobuftop` to 0; the contents become inaccessible and are erased only as <<KLE-destructive-config>> requires; in every case it sets `klstart` to 0; zeroizes the three authentication registers of <<KLE-KLF>>; and writes 32 to `klnamedlocker` (Rule <<KLE-GR-klnamedlocker-updates>>).
It sets to Dirty the `*llockerstatus` fields in effect for the current privilege mode, for every locker that it changes or whose field in effect is _Off_, as `kl.clear` does, and the `KLS` fields in effect if it changes a locker, `kliobuflen`, `kliobuftop`, `klstart`, `klnamedlocker` or an authentication register, or if the field in effect of any locker is _Off_.

[[KLE-instruction-clearads]]
==== kl.clearads

(((KLE, instruction, kl.clearads)))`kl.clearads Kd` deletes any ADS from locker `Kd`, sets _AuxDataLen_ and _ADSDropped_ to 0, and zeroes the implementation-defined subfields of _MachineUse_ and _AuxInfo_ (<<KLE-MachineUse>>).
It is encoded as `kl.setst` (<<KLE-instruction-setst>>) with no auxiliary operand and `#immed7` = `kl_cfg_clear_ads` (64). Any other Form of `kl.setst` with `#immed7` = 64 is a wrong Form (Rule <<KLE-GR-form-mismatch>>).

// The first usage instruction that needs the ADS regenerates it.
`kl.clearads` is a usage instruction, admitted in every Valid State (Rule <<KLE-GR-to-ready>>).
It leaves _State_ unchanged, and _StateExtension_ too, except that it clears the flag of any material that Rule <<KLE-GR-progress-discard>> destroys, such as `HasRndNum` of the ECC Machines.
It discards the implementation-defined state, in the ADS and in _MachineUse_ and _AuxInfo_ (<<KLE-MachineUse>>), including any that an interrupted long-running operation keeps: in a State of Rule <<KLE-GR-progress-discard>> it zeroes the progress field _P_, and the operation restarts when its instruction is next issued, exactly as if the SCC exported before the `kl.clearads` had been imported on a different KLE implementation (Rule <<KLE-GR-long-running-restart>>).

NOTE: Software uses `kl.clearads` to make the SCC smaller before exporting a locker for another target. A destination with a different KLE unit would drop the ADS anyway.

[[KLE-destructive-config]]
=== Destructive Configuration Instructions

`kl.clear` and `kl.clearall` (<<KLE-instruction-clear>> and <<KLE-instruction-clearall>>) are two of the
_destructive configuration instructions_, the configuration instructions that discard the CC in a locker without reading it, other than `kl.setste`.
`kl.setste` also discards the Content of its locker (Rule <<KLE-GR-clear-locker-content-error-state>>), but it is not one of them: it leaves `klnamedlocker` unchanged (Rule <<KLE-GR-klnamedlocker-updates>>), and it is not exempt from the KLE locker-Off exception.
The other destructive configuration instructions are:

* a provisioning- or import-opening `kl.mgmt` (defined in the next section, <<KLE-instruction-mgmt>>), which zeroizes the locker before configuring it;
* `kl.clone` and `kl.rename` (defined later in <<KLE-instruction-clone>>), which replace the CC of their destination locker with that of the source; and
* `kl.swap` (same section), a special case that overwrites both its lockers, each with the CC of the other, so nothing is lost.

A destructive configuration instruction destroys the CC it replaces right after the locker-state-independent checks of Rule <<KLE-GR-management-check-order>>, the check of the MDH operand of `kl.mgmt` included, whatever the outcome, unless it names `KLNL` while `klnamedlocker` = 32, when it finds no locker and performs no operation (Rule <<KLE-GR-outcome-inert>>), or it is a `kl.clone`, `kl.rename` or `kl.swap` whose source and destination are the same locker, which performs no operation (<<KLE-instruction-clone>>).

Only the destination accesses of the destructive configuration instructions other than `kl.swap` are exempt from the KLE locker-Off exception (<<Zkl-ISA-priv.adoc#KLE-CSR-llockerstatus>>): a provisioning- or import-opening `kl.mgmt`, `kl.clear`, `kl.clearall`, and `kl.clone` or `kl.rename` into the locker.
So is any access of a `kl.clone`, `kl.rename` or `kl.swap` whose source and destination are the same locker, which performs no operation (<<KLE-instruction-clone>>).
Every other access raises it: the source access of `kl.clone` and `kl.rename`, either access of `kl.swap`, and every access by another instruction, such as `kl.load`, `kl.mvin` or `kl.setste`, even one that writes the locker without reading it.

KLF capacity that `kl.mgmt` or `kl.clone` allocates to a locker reads as zero, to the locker's Machine and to every architectural access, until written.
An implementation that supports Level C (<<KLE-SC-protection-levels>>) must also zeroize at once the Content and any ADS of every locker whose CC is discarded by `kl.clear`, `kl.clearall` or as the previous CC of the destination of `kl.rename` or `kl.clone`, or that transitions to an Error State (Rule <<KLE-GR-clear-locker-content-error-state>>), and the KLIOBUF bytes that a write of `kliobuflen` or a `kl.clearall` makes inaccessible (<<KLE-CSR-kliobuflen>>); any other implementation need only release them.

[[KLE-instruction-mgmt]]
=== kl.mgmt

Synopsis::
Open or complete a management operation on a locker.

Mnemonics::
+
--
(((KLE, instruction, kl.mgmt)))`kl.mgmt` uses the encoding of only Forms A, C and D of `kl.setst`, but is a distinct instruction.

[upperalpha]
. `kl.mgmt  Kd, #immed7{fournbsp}{nbsp}{nbsp}` with no auxiliary input.
. Reserved.
. `kl.mgmt  Kd, #immed7, Vs{nbsp}` with auxiliary input in a vector register.
. `kl.mgmt  Kd, #immed7, Xs{nbsp}` with auxiliary input in two or four GPRs (RV64/RV32).
--

//

Encoding::
`kl.mgmt` is an R-type instruction with the encoding of `kl.setst` (<<KLE-instruction-setst>>), `G` = `0b11` and `#immed7`[6:3] = `0b0111`, that is, `#immed7` in 56–63.

Description::
+
--
For this instruction, Rules <<KLE-GR-multiple-GPRs>>, <<KLE-GR-x0-operand>>, <<KLE-GR-klnamedlocker-override>>, <<KLE-GR-vector-MDH-operand>>, <<KLE-GR-vector-legality>> and <<KLE-GR-klnamedlocker-updates>> apply.

`kl.mgmt` brackets the body of a locker management operation (<<KLE-management-operations>>): it opens a provisioning, an export or an import on locker `Kd`, and completes it.
A `kl.mgmt` that opens, resp. completes, a management operation is an _opening_, resp. _completing_, `kl.mgmt`, named after its operation: a provisioning-opening `kl.mgmt`, an export-completing `kl.mgmt`, and so on.

A provisioning- or import-opening `kl.mgmt` is allowed in every _State_ (<<KLE-instruction-properties>>).
It is a <<KLE-destructive-config,destructive configuration instruction>>, which erases the memory of the locker before using it:
this prevents any previous content from leaking into a nested management operation.

Like `kl.setst`, `kl.mgmt` changes the locker's _State_, but with different semantics.
The State reached depends on both the locker's previous State and `#immed7`.
Besides the command in `#immed7`, a `kl.mgmt` that needs it receives an MDH: when opening a provisioning or an import, it selects the variant of the operation and may become the locker's MDH; when completing an import or an export, it restores the _State_ recorded in `ml`, the copy of the MDH that the caller saved (<<KLE-management-formats-and-states>>).

<<KLE-management-immeds>> gives the values of `#immed7`; every other value is reserved (Rule <<KLE-GR-reserved-encodings>>).

The Forms supply the MDH as follows:

* Form A carries no auxiliary operand, and supplies an all-zero MDH (Rule <<KLE-GR-x0-operand>>).
* Form C carries it in the lowest 128 bits of `Vs`. `VL` {times} `SEW` < 128 raises an illegal-instruction exception
  (Rule <<KLE-GR-vector-MDH-operand>>) at its place in the order of Rule <<KLE-GR-management-check-order>>, whatever the operation and the _State_ and even if the instruction would fall through; the _State_ is kept.
* Form D carries it as a 128-bit operand in two or four GPRs starting at `Xs` (Rule
  <<KLE-GR-multiple-GPRs>>).

<<KLE-locker-management>> gives the precise semantics of each operation.
--

[[KLE-instruction-getmd]]
=== kl.getmd, kl.getmdl, and kl.getmdv

Synopsis::
Export the MDH of a locker.

Mnemonics::
+
--
[%hardbreaks]
`kl.getmdl{nbsp}Xd, Ks`(((KLE, instruction, kl.getmdl)))
`kl.getmd{nbsp}{nbsp}Xd, Ks`(((KLE, instruction, kl.getmd)))
`kl.getmdv{nbsp}Vd, Ks`(((KLE, instruction, kl.getmdv)))
--


Encoding::
+
--
`kl.getmd*` are R-type instructions that share the opcode and `funct3` of `kl.exec`, with `funct2` = `0b11`.

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Xd' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'rs1', attr: ['Ks'] },
    { bits:  5, name: 0x00  },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'r', attr: ['KLNL']   },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'h' },
    { bits:  1, name: 'v' },
    { bits:  2, name: 0x3, attr: ['funct2'] },
]}
....

`r` names `KLNL` as Rule <<KLE-GR-klnamedlocker-override>> specifies.

With bit `v` (bit 29) = 0, bit `h` (bit 28) selects `kl.getmdl` (`h` = 0) or `kl.getmd` (`h` = 1), and the result goes to GPRs: one GPR on RV64 and a pair on RV32 for `kl.getmdl`, a pair on RV64 and a quartet on RV32 for `kl.getmd` (Rule <<KLE-GR-multiple-GPRs>>).
With `v` = 1, the instruction is `kl.getmdv`, which writes the entire MDH to the lowest 128 bits of a vector register; `h` must then be 0.
`v` = `h` = 1 encodes `kl.getnl` (<<KLE-instruction-getter-setter>>).
--

Description::
+
--
These instructions copy the MDH of locker `Ks`, which is all-zero for an _Unconfigured_ locker:

* `kl.getmdl` copies bits [63:0] to GPR `Xd` on RV64, and to the pair `X[d+1] @ X[d]` on RV32.
* `kl.getmd` copies bits [127:0]: on RV64, bits [63:0] to `Xd` and bits [127:64] to `X[d+1]`; on RV32, to the quartet `X[d+3] @ X[d+2] @ X[d+1] @ X[d]`.
* `kl.getmdv` copies bits [127:0] to vector register `Vd`, on RV32 as on RV64. Bits [`VL` {times} `SEW` − 1 : 128] are written with zeros, and the tail follows the tail-agnostic policy (<<KLE-KLV>>).

They do not check MDH validity (<<KLE-Metadata-validity>>).
`Ks` may be `KLNL` (Rule <<KLE-GR-klnamedlocker-override>>).
--

[[KLE-instruction-getst]]
=== kl.getst and kl.getstx

The pseudo-instructions
(((KLE, instruction, kl.getst)))
`kl.getst Xd, Ks`
(((KLE, instruction, kl.getstx)))
`kl.getstx Xd, Ks`
return the _State_, resp. _StateExtension_, field of the MDH of the source locker, for instance to determine whether it is in an Error State (<<KLE-State-field>>).
They read the MDH with `kl.getmdl` and extract the field by shifting and masking.
`Ks` may be `KLNL`; the expansion then uses `kl.getmdl` with `r` = 1. With `Xd` = `X0` the instruction writes nothing (Rule <<KLE-GR-x0-operand>>).

On RV64, `kl.getst` expands to

. `kl.getmdl Xd, Ks`
. `srli  Xd, Xd, 18`
. `andi  Xd, Xd, 0x3F`

and `kl.getstx` by the same code, with the constants in Steps 2 and 3 changed to 24 and `0x0F`, respectively.
//
// . `kl.getmdl Xd, Ks`
// . `srli  Xd, Xd, 24`
// . `andi  Xd, Xd, 0x0F`

On RV32 the code is the same, but `Xd` must be even (Rule <<KLE-GR-multiple-GPRs>>) and `X[d+1]` is also overwritten with MDH bits [63:32].
// `kl.getmdl` writes the lower 64 bits of the MDH to the pair `X[d+1] @ X[d]`, and _State_ and _StateExtension_ lie entirely in `X[d]`.

[[KLE-instruction-getter-setter]]
=== CSR Getters and Setters: kl.get*, kl.set*, and kl.set*i

Like `vsetvl` and related instructions of the vector extension, these instructions set and get certain CSR values without a CSR access, which is slow in many implementations.

Synopsis::
Get, resp. set, the value of `klnamedlocker`, `kliobuflen`, `kliobuftop`, and `klstart`.

Mnemonics::
+
--
`kl.getnl/getbl/getbt/getks{fournbsp}{nbsp}{nbsp}Xd`(((KLE, instruction, kl.getnl)))(((KLE, instruction, kl.getbl)))(((KLE, instruction, kl.getbt)))(((KLE, instruction, kl.getks))) +
`kl.setnl/setbl/setbt/setks{fournbsp}{nbsp}{nbsp}Xs1`(((KLE, instruction, kl.setnl)))(((KLE, instruction, kl.setbl)))(((KLE, instruction, kl.setbt)))(((KLE, instruction, kl.setks))) +
`kl.setnli/setbli/setbti/setksi{nbsp}#uimm7`(((KLE, instruction, kl.setnli)))(((KLE, instruction, kl.setbli)))(((KLE, instruction, kl.setbti)))(((KLE, instruction, kl.setksi)))
--

Encodings::
+
--
The encodings are variants of those of `kl.getmd*` (<<KLE-instruction-getmd>>) and `kl.setst` (<<KLE-instruction-setst>>):

* `kl.getnl Xd`, `kl.getbl Xd`, `kl.getbt Xd`, `kl.getks Xd`:
these instructions use the `kl.getmd*` encoding with `v` = `h` = 1, `r` = 0 and `rs1` = 1, 2, 3, and 4, respectively; `rd` holds `Xd`.

* `kl.setnl Xs1`, `kl.setbl Xs1`, `kl.setbt Xs1`, `kl.setks Xs1`:
the `kl.setst` encoding with `G` = `0b10`, `r` = 0, `F` = `0b00`, `#immed7` = 0, and `rd` = 1, 2, 3, and 4, respectively; `rs1` holds `Xs1`.

* `kl.setnli #uimm7`, `kl.setbli #uimm7`, `kl.setbti #uimm7`, `kl.setksi #uimm7`:
the `kl.setst` encoding with `G` = `0b10`, `r` = 0, `F` = `0b01`, `rs1` = 0, and `rd` = 1, 2, 3, and 4, respectively; `#immed7` holds `#uimm7`.

Every other encoding with `v` = `h` = 1 in the `kl.getmd*` encoding, or with `G` = `0b10` in the `kl.setst` encoding, is reserved.
--

Description::
+
--
`kl.getnl`, `kl.getbl`, `kl.getbt`, and `kl.getks` write
`klnamedlocker`, `kliobuflen`, `kliobuftop`, and `klstart`, respectively, zero-extended, to `Xd`.

`kl.setnl`, `kl.setbl`, `kl.setbt`, and `kl.setks` write `X[rs1]` to
`klnamedlocker`, `kliobuflen`, `kliobuftop`, and `klstart`, respectively,
with the effect of a CSR write.

`kl.setnli`, `kl.setbli`, `kl.setbti`, and `kl.setksi` write zero-extended `#uimm7` to
`klnamedlocker`, `kliobuflen`, `kliobuftop`, and `klstart`, respectively,
with the effect of a CSR write.

`kl.getnl`, `kl.setnl`, `kl.setnli`, `kl.getks`, `kl.setks` and `kl.setksi` are part of `Zkl` common; the ones on `kliobuflen` and `kliobuftop` are part of `Zklio` and reserved (Rule <<KLE-GR-reserved-encodings>>) without it. They are not gated as accesses to the CSRs: the privilege of the CSR is not checked, and software should use them to read or write `klnamedlocker`, `kliobuflen`, `kliobuftop` and `klstart`.
They behave as reads and writes of the CSRs: the CSRs are WARL: a written value above the maximum of the CSR is replaced by that maximum (a reserved value leaves `klnamedlocker` unchanged), and `mklmaxiobuflen` {ge} `kliobuflen` {ge} `kliobuftop` is enforced (<<Zkl-ISA-priv.adoc#KLE-CSR-mklmaxiobuflen>>, <<KLE-CSR-kliobuflen>>, <<KLE-CSR-kliobuftop>>).

They are configuration instructions, not usage instructions: Usage Control does not gate them.
--

[[KLE-instruction-restrict]]
=== kl.rstrl, kl.rstrh, and kl.rstrv

Synopsis::
Restrict the policies encoded in a CC in a locker.

Mnemonics::
+
--
[%hardbreaks]
`kl.rstrl{nbsp}{nbsp}Kd, Xs1`(((KLE, instruction, kl.rstr)))(((KLE, instruction, kl.rstrl)))
`kl.rstrh{nbsp}{nbsp}Kd, Xs1`(((KLE, instruction, kl.rstrh)))
`kl.rstrv{nbsp}{nbsp}Kd, Vs1`(((KLE, instruction, kl.rstrv)))
--

Encoding::
+
--
`kl.rstr*` are R-type instructions that share the opcode and `funct3` of `kl.exec`, with `funct2` (the two msbs of `funct7`) = `0b01`.
[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Kd' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'Xs1/Vs1' },
    { bits:  5, name: 0x0 },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'r', attr: ['KLNL']   },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'h' },
    { bits:  1, name: 'v' },
    { bits:  2, name: 0x1, attr: ['funct2'] },
]}
....

`r` names `KLNL` as Rule <<KLE-GR-klnamedlocker-override>> specifies.

With bit `v` (bit 29) = 0, bit `h` (bit 28) selects `kl.rstrl` (`h` = 0) or `kl.rstrh` (`h` = 1), and the input comes from a GPR (a GPR pair on RV32).
With `v` = 1, the instruction is `kl.rstrv`, `h` must be 0, and the input comes from the lowest 128 bits of a vector register; `v` = `h` = 1 is reserved.
--

// comment

Description::
+
--
These instructions narrow the policies of the CC in locker `Kd`, whose MDH is `md`, as their operand requests: `Xs1`, or `Vs1` for `kl.rstrv`, formatted as an MDH.

Operand::
* `kl.rstrl` takes bits [63:0] of the operand, and may change _MachinePolicy_;
* `kl.rstrh` takes bits [127:64], supplied in `Xs1`[63:0], and may change _Locality_, _UsagePolicy_ and _ExpirationDate_;
* `kl.rstrv` takes both halves, and applies both sets of rules.
+
The _request_ `rq` is the 128-bit MDH image that these halves form; the fields of a half that the instruction does not take are not requested and stay unchanged.
In a half that the instruction takes, a non-zero field other than these four transitions the locker to _Invalid_.
A _MachinePolicy_ or _UsagePolicy_ of `rq` with all bits set, and a zero _Locality_ or _ExpirationDate_ of `rq`, leave the corresponding field of `md` unchanged.

Per-field behavior::
Each field of `rq` narrows the matching field of `md` (<<KLE-Metadata-narrowing>>), except as stated below for _Locality_.
A set _MachinePolicy_ or _UsagePolicy_ bit, or an _ExpirationDate_ later than a non-zero `md`._ExpirationDate_, changes nothing and is not an error.
A non-zero _Locality_ subfield of `rq` that differs from that of `md` and is not a permitted replacement below transitions the locker to _Privilege Violation_.
+
* _MachinePolicy_: no disabled function can be enabled again.
  A request that disables the operation of the current State takes effect as Rule <<KLE-GR-policy-narrowing-state>> states.
  A Machine with fields that exist only for some values of _MachinePolicy_, such as the ECC Machines (<<Zkl-ISA-machines.adoc#KLE-ECC>>), states what a narrowing does to them.
* _Locality_: each subfield (<<KLE-locality-indexes>>), bits [1:0], [3:2], [5:4], 6, 7 and 8, is treated independently.
  A subfield of `rq` that is zero or equal to that of `md` changes nothing, and a zero subfield of `md` takes the value of `rq`.
  A non-zero HW Binding subfield may be replaced only by a stricter entry of its chain: _SiPScrt_ by _ChipFamScrt_ or _ChipScrt_, _ChipFamScrt_ by _ChipScrt_, _OEMScrt_ by _ProdScrt_ or _DevScrt_, and _ProdScrt_ by _DevScrt_.
  Any other change, including a weakening or a change of a non-zero Boot Session or SW Filter subfield, transitions the locker to _Privilege Violation_ instead of overriding the field.
  A later export binds its SCC to the new _Locality_.
* _UsagePolicy_: each clear bit removes a permission from the corresponding bit of `md`, and each set bit changes nothing.
* _ExpirationDate_: a non-zero value of `rq` replaces that of `md` if `md`._ExpirationDate_ is zero or `rq`._ExpirationDate_ {le} `md`._ExpirationDate_; otherwise the field is unchanged, without error.

Validity of the result::
Validity (<<KLE-Metadata-validity>>) is evaluated first, on the changed fields only.
A request that would produce an unsupported or invalid value, such as a reserved _Locality_ subfield or a non-zero _ExpirationDate_ without `Zklexpire`, transitions the locker to _Invalid_, even if it also asks for a change that gives _Privilege Violation_, such as a _Locality_ that names an unconfigured entry without a configured substitute.
Only a request with valid values can give _Privilege Violation_.
A request that transitions the locker to an Error State changes no other field of `md` beyond those of Rule <<KLE-GR-clear-locker-content-error-state>>.

States::
The `kl.rstr` instructions are not usage instructions (Rule <<KLE-GR-usage-policy>>).
They act only in a Valid State: on an _Unconfigured_ or Error-State locker they perform no operation (Rule <<KLE-GR-outcome-inert>>), and in a Configuration State Rule <<KLE-GR-outcome-config-state>> applies.
--

NOTE: A `kl.rstr` narrows only the CC in `Kd`. Copies of the same secret made earlier, such as SCCs exported before the narrowing or clones in other lockers, keep their wider policies (<<KLE-KLF>>).
// Memory carries no attributes that could track such copies, so making a narrowing effective everywhere is up to the discipline of the software that holds them.

// ////////////////////////////////////////////////////////////////////

[NOTE]
====
These instructions let privileged code give different processes customized copies of a CC, bound to per-process
Localities or limited to a subset of its functions, such as separate encryption-only and decryption-only copies, which some modes do not keep apart (<<Zkl-ISA-machines.adoc#KLE-accepted-risks>>).
This may avoid repeated expensive round-trips to trusted environments.
====

[[KLE-instruction-clone]]
=== kl.clone, kl.rename, and kl.swap

Synopsis::
Copy, move or exchange the CCs of lockers.

Mnemonics::
`kl.{clone, rename, swap} Kd, Ks`
+
Either `Kd` or `Ks`, not both, may be `KLNL` (Rule <<KLE-GR-klnamedlocker-override>>).
(((KLE, instruction, kl.clone)))
(((KLE, instruction, kl.rename)))
(((KLE, instruction, kl.swap)))

Encoding::
These are R-type instructions that share the opcode and `funct3` of `kl.exec`, with `funct2` = `0b10`.
+
[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Kd' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'Ks' },
    { bits:  5, name: 0x0 },
    { bits:  2, name: 'R', attr: ['KLNL']   },
    { bits:  2, name: 'T' },
    { bits:  1, name: 0x0 },
    { bits:  2, name: 0x2, attr: ['funct2'] },
]}
....
+
--
Field `T` (bits [28:27]) selects the instruction:

. `00`{nbsp}{nbsp} encodes `kl.clone`.
. `01`{nbsp}{nbsp} encodes `kl.rename`.
. `10`{nbsp}{nbsp} encodes `kl.swap`.
. `11`{nbsp}{nbsp} encodes `kl.derive` (<<KLE-instruction-derive>>).
--

// Comment to ensure proper indentation in the next Description

Description::
+
--
`kl.clone`::
Clones source locker `Ks` into destination locker `Kd`, either of which, not both, may be `KLNL` (Rule <<KLE-GR-klnamedlocker-override>>):

* If source and destination are the same locker, the instruction performs no operation and sets no `*llockerstatus` or `KLS` field to Dirty (<<Zkl-ISA-priv.adoc#KLE-CSR-llockerstatus>>), even if the locker is _Unconfigured_, _Off_, or in a Configuration State; in the last case, Rule <<KLE-GR-outcome-config-state>> does not apply.
* If they are different lockers and neither of them is `KLNL` while `klnamedlocker` = 32, the instruction first clears the destination, as `kl.clear` would, even if it then raises an exception (<<KLE-destructive-config>>); if `klnamedlocker` named the destination, it becomes 32. The `*llockerstatus` field in effect for the destination and the `KLS` field in effect are set to Dirty, whatever the outcome. The source then decides the result:
** An _Unconfigured_ source leaves the destination _Unconfigured_.
** A source in a Configuration State raises a KLE privilege-violation exception (Rule <<KLE-GR-outcome-config-state>>).
** A source in an Error State is cloned as its MDH alone (Rule <<KLE-GR-clear-locker-content-error-state>>).
** Any other source is copied verbatim, with its internal data, MDH and internal state, unless the available KLF capacity cannot hold the clone, in which case the instruction raises a KLE out-of-memory exception.
As the one exception, if the source has an interrupted long-running operation, the copy restarts it (Rule <<KLE-GR-long-running-restart>>): its progress is zeroed and the values drawn or computed for the operation are discarded, as at an import that completes without `Content2`.
Like the source, the copy stays usable whatever the current Locality Secrets. `kl.clone` is not a usage instruction, so no _UsagePolicy_ restricts it (Rule <<KLE-GR-usage-policy>>).

`kl.rename`::
If `Ks` and `Kd` name the same locker, through `KLNL` too, no operation is performed, even if the locker is _Off_, and no `*llockerstatus` or `KLS` field is set to Dirty.
Otherwise the CC of `Ks`, Configuration State included, becomes the CC of `Kd`, the previous CC of `Kd` is discarded, as `kl.clear` would, `Ks` becomes _Unconfigured_, and the `*llockerstatus` fields in effect for both lockers and the `KLS` fields in effect are set to Dirty. With an _Unconfigured_ source, `kl.rename` acts as `kl.clear Kd`, except that it always sets these fields to Dirty.
If `klnamedlocker` = `s`, it becomes `d`; otherwise, if it is `d`, it becomes 32. The source access is not exempt from the KLE locker-Off exception; the destination access is exempt, as for `kl.clone`.

`kl.swap`::
If `Ks` and `Kd` name the same locker, through `KLNL` too, no operation is performed, even if the locker is _Off_, and no `*llockerstatus` or `KLS` field is set to Dirty.
Otherwise the CCs of `Ks` and `Kd` are exchanged, and if `klnamedlocker` {in} {`s`,`d`}, it takes the other index. Neither access is exempt from the KLE locker-Off exception. The `*llockerstatus` fields in effect for both lockers and the `KLS` fields in effect are set to Dirty.

With `klnamedlocker` = 32, a `kl.clone`, `kl.rename` or `kl.swap` with a `KLNL` operand finds no locker and performs no operation, its other locker untouched (Rule <<KLE-GR-outcome-inert>>).

Neither `kl.rename` nor `kl.swap` raises a KLE out-of-memory exception or edits the content of any MDH: they move or exchange entire lockers.
When `Ks` and `Kd` name the same locker, `kl.clone`, `kl.rename` and `kl.swap` still make the checks of Rule <<KLE-GR-management-check-order>>, except that of a locker whose `*llockerstatus` field is _Off_.
<<Zkl-ISA-priv.adoc#KLE-CSR-llockerstatus>> and <<Zkl-ISA-priv.adoc#KLE-unsupported-handling>> give the behavior under lazy loading and emulation, when the source or destination locker is _Off_ in some `*llockerstatus`.
--

[[KLE-instruction-derive]]
=== kl.derive

Synopsis::
Transfer data from one locker into another without exposing it to software.

Mnemonic::
`kl.derive Kd, Ks1, Xs2`
+
Either `Kd` or `Ks1`, not both, may be `KLNL` (Rule <<KLE-GR-klnamedlocker-override>>).
(((KLE, instruction, kl.derive)))

Encoding::
+
--
`kl.derive` is an R-type instruction.

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Kd' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'Ks1' },
    { bits:  5, name: 'Xs2' },
    { bits:  2, name: 'R', attr: ['KLNL']   },
    { bits:  2, name: 0x3 },
    { bits:  1, name: 0x0 },
    { bits:  2, name: 0x2, attr: ['funct2'] },
]}
....

The auxiliary input is always a GPR: `kl.derive` has no form without one, and no vector form.
--

Description::
+
--
A `kl.derive` transfers data from a _source endpoint_ to a _destination endpoint_; the architecture decides which pairs of endpoints are admitted.

[[KLE-source-endpoint,Source Endpoint]]Definition: _Source endpoint_.::
A source endpoint is what a Machine lists as a source for a _State_ in <<Zkl-ISA-machines.adoc#KLE-derive-endpoints>>: an _exportable field_, whose availability may depend on _StateExtension_ or on an MDH field that the Machine names, such as `OutputType` of ECC (<<Zkl-ISA-machines.adoc#KLE-ECC-MachineUse>>); otherwise the `kl.exec` _output_, the data that a Form C `kl.exec` permitted in that State would emit.
A field configured by a SKID is never exportable (Rule <<KLE-GR-skid-field>>).

[[KLE-destination-endpoint,Destination Endpoint]]Definition: _Destination endpoint_.::
A destination endpoint is what a Machine lists as a destination for a _State_ in <<Zkl-ISA-machines.adoc#KLE-derive-endpoints>>: an _importable field_ that an admitted pair names; or the `kl.exec` _input_, the data that a Form B `kl.exec` of that State would absorb. It fixes the minimum, upper limit and granularity of the transfer.
A key field is a destination only in _Ready_ or in a State that the Machine names for loading it, such as _Set_Key_ of HMAC (<<Zkl-ISA-machines.adoc#KLE-HMAC>>), and never when _KeyType_ is 1 (Rule <<KLE-GR-skid-field>>).

[[KLE-admitted-pairs,Admitted Pairs]]Definition: _Admitted pairs_.::
An _admitted pair_ consists of a source and a destination endpoint; the MDH of each locker, not an operand of `kl.derive`, determines its endpoint.
Rules <<KLE-GR-shared-secret>> and <<KLE-GR-exec-implies-unrestricted>> admit two families of pairs, and state for each whether the transfer is restricted or unrestricted. Any other pair is not admitted.
// Before the simplification of the admissible pairs, the sentence above continued:
// a Machine may define further pairs, which narrow but never relax any policy and respect Rule <<KLE-GR-shared-secret>>.
An admitted pair fixes the semantics of the transfer and its updates to the two States and to `klstart` (Rules <<KLE-GR-derive-rule-both-fixed-size>>–<<KLE-GR-exec-implies-unrestricted>>); `kl.derive` changes no other state of the hart (<<KLE-instruction-properties>>).

Let `length` be the value provided by the auxiliary GPR, and `eff_length` the number of bytes transferred (Rule <<KLE-GR-derive-rule-both-fixed-size>>): min(`length`, `dest_length`) for a destination field of `dest_length` bytes, and `length` otherwise.
`kl.derive` moves `eff_length` bytes from an endpoint of the source locker to an endpoint of the destination locker without exposing them to software: the output of one Machine becomes an input of another, possibly into a key field or a `kl.exec` input, as the admitted pairs allow.
`Xs2` = `X0` gives `length` = 0, and Rule <<KLE-GR-checks>> gives the outcome when `length` is zero or short.

A transfer is _unrestricted_ only where software could also obtain the moved data by issuing `kl.exec` instructions, as for the block cipher outputs of Rule <<KLE-GR-exec-implies-unrestricted>> and a shared secret that its Machine allows to export through `kl.exec`; otherwise it is _restricted_, as for any other shared secret (Rule <<KLE-GR-shared-secret>>).

Source and destination must be different lockers, else an illegal-instruction exception is raised.
Usage Control applies to both lockers (Rule <<KLE-GR-outcome-valid-state>>), and both are checked before any state change or transfer: first the conditions of Rule <<KLE-GR-outcome-valid-state>>, in the order of Rule <<KLE-GR-derive-check-order>>, then those of Rules <<KLE-GR-checks>> and <<KLE-GR-narrowing>>.
--

=== KLE Memory Instructions

The checks of the KLE memory instructions and their behavior in the memory model are defined in <<KLE-Memory-Model>>.

[[KLE-instruction-load]]
==== kl.load and kl.input

(((KLE, instruction, kl.load)))(((KLE, instruction, kl.input)))Mnemonics::
`kl.load %offset(Xs), Xl` +
`kl.input %offset(Xs), Xl` +
`kl.input` is an alias for `kl.load`, for source code in which `klnamedlocker` is known to be 32.

Encoding::
--
`kl.load`/`kl.input` is an I-type instruction.
`%offset` is `immed12`, sign-extended to XLEN bits.

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x03, attr: ['LOAD'] },
    { bits:  5, name: 'Xl' },
    { bits:  3, name: 0x7, attr: ['kl.load','kl.input'] },
    { bits:  5, name: 'Xs' },
    { bits: 12, name: 'immed12' },
]}
....
--

Description::
+
--
The locker is not an operand: with `klnamedlocker` < 32, `kl.load` copies data into the locker that `klnamedlocker` names; with `klnamedlocker` = 32, into the KLIOBUF.

For `klnamedlocker` < 32::
`kl.load` imports the Content of a PI or an SCC into the locker, but not its MDH, which `kl.mgmt` carries.
A non-zero `Xl` raises an illegal-instruction exception; otherwise, `kl.load` makes the Locker Checks in <<KLE-instruction-mv>> of `kl.mvin`.
+
For each _j_ in `[klstart, image_end-1]`, `kl.load` loads the byte at memory address (``Xs + %offset + ``_j_) mod 2^XLEN^ into byte _j_ of the <<KLE-serialized-image,serialized image>> `S` of the locker's Content, in 16-byte blocks from a 16-byte aligned address (Rule <<KLE-GR-management-check-order>>).
`klstart` tracks the prefix-complete number of bytes loaded; if `klstart` {ge} `image_end`, nothing is transferred.
On an _Unconfigured_ or Error-State locker, `kl.load` accesses no memory and writes nothing (Rule <<KLE-GR-fall-through-operands>>).
// ; software does not use it on an Error-State locker (<<KLE-error-state-transfer>>).
+
With a system-specific format, `kl.load` transfers the data that follows the MDH unchanged, as the serialized image `S` (<<KLE-system-specific-import>>).

For `klnamedlocker` = 32::
With `Xl` = 0, after items 1–6 of Rule <<KLE-GR-management-check-order>>, `kl.input` and `kl.output` perform no operation and write 0 to `klstart`, before any check of `Zklio` or of the KLIOBUF (Rules <<KLE-GR-fall-through-operands>> and <<KLE-GR-iobuf-configured>>).
If `Zklio` is in effect, they transfer the bytes of the <<KLE-iobuf-transfer-window>>;
otherwise, they raise an illegal-instruction exception (item 7 of Rule <<KLE-GR-management-check-order>>).

[[KLE-iobuf-transfer-window,KLIOBUF transfer window]]Definition: _KLIOBUF transfer window_.::
Let _n_ = min(`Xl`, `kliobuftop`).
The *KLIOBUF transfer window* of `kl.input` and `kl.output` consists of the offsets _j_ with `klstart` {le} _j_ < _n_.
For each _j_ in the window, `kl.input` copies the byte at address (``Xs + %offset + ``_j_) mod 2^XLEN^ to KLIOBUF byte _j_, and `kl.output` copies KLIOBUF byte _j_ to that address.
No other byte is accessed, in memory or in the KLIOBUF; in particular, bytes from `kliobuftop` on are never transferred, whatever `Xl`.
If `klstart` {ge} _n_, the window is *empty*: the checks of Rule <<KLE-GR-iobuf-configured>> are still made, then nothing is transferred and `klstart` is set to 0.
--

[[KLE-instruction-store]]
==== kl.store and kl.output

(((KLE, instruction, kl.store)))(((KLE, instruction, kl.output)))Mnemonics::
`kl.store %offset(Xs), Xl` +
`kl.output %offset(Xs), Xl` +
`kl.output` is an alias for `kl.store`, for source code in which `klnamedlocker` is known to be 32.

Encoding::
`kl.store`/`kl.output` is an S-type instruction.
`%offset` is `immed[11:5]` @ `immed[4:0]`, sign-extended to XLEN bits.
+
[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x23, attr: ['STORE'] },
    { bits:  5, name: 'immed[4:0]' },
    { bits:  3, name: 0x5, attr: ['kl.store','kl.output'] },
    { bits:  5, name: 'Xs' },
    { bits:  5, name: 'Xl' },
    { bits:  7, name: 'immed[11:5]' },
]}
....

Description::
+
--
The locker is not an operand: with `klnamedlocker` < 32, `kl.store` copies data out of the locker that `klnamedlocker` names; with `klnamedlocker` = 32, out of the KLIOBUF.

For `klnamedlocker` < 32::
`kl.store` exports the <<KLE-serialized-image,serialized image>> `S` of the locker to memory, but not its MDH, which `kl.getmd*` extracts.
A non-zero `Xl` raises an illegal-instruction exception; otherwise, `kl.store` makes the Locker Checks in <<KLE-instruction-mv>> of `kl.mvout`.
+
For each _j_ in `[klstart, image_size-1]`, `kl.store` stores byte _j_ of `S` at memory address (``Xs + %offset + ``_j_) mod 2^XLEN^, in 16-byte blocks to a 16-byte aligned address (Rule <<KLE-GR-management-check-order>>); the bytes from `image_end` on are stored as zero.
`klstart` tracks the prefix-complete number of bytes stored; if `klstart` {ge} `image_size`, nothing is transferred.
On an _Unconfigured_ or Error-State locker, `kl.store` accesses no memory (Rules <<KLE-GR-fall-through-operands>> and <<KLE-GR-clear-locker-content-error-state>>); software does not use it on an Error-State locker (<<KLE-error-state-transfer>>).

For `klnamedlocker` = 32::
`kl.output` is described with `kl.input` (<<KLE-instruction-load>>): it copies the bytes of the <<KLE-iobuf-transfer-window>> from the KLIOBUF to memory.
--

[[KLE-ISA-rules]]
== Rules

This section collects several Rules that govern the behavior of the KLE ISA.
Many of these Rules only deal with classes of States, namely _Unconfigured_, _Valid_, _Error_, _Configuration_, _Complete_, and _Inert_; and
of instructions, that is _Usage_, _Memory_ and _Configuration_.
_Configuration_ instructions may be further specified into _inspection_, _destructive_, _transfer_ and _narrowing_.
// Note that `kl.load` and `kl.store` are both transfer and memory instructions.
Other Rules are instruction-specific.

[[KLE-content-confidentiality]]
=== Content Confidentiality

// The following Rules protect the Content of a CC in two ways: it leaves a locker only sealed, and CCs that pertain only to certain chip families or devices cannot be disclosed to other chip families or devices.

[horizontal]
[[KLE-GR-no-extraction,GR9]]GR9:: Once the provisioning, or the base import of a system-specific format (<<KLE-system-specific-import>>), that binds a key to its Metadata completes, no instruction returns in clear the value of the key, or of any other secret field of the Content, except as an output defined by the Machine for `kl.exec` (Rule <<KLE-GR-exec-implies-unrestricted>>).

[[KLE-GR-custom-locality,GR10]]GR10:: A CC whose MDH carries a custom _Machine_ or a system-specific _Version_ must include at least one of _SiPScrt_, _ChipFamScrt_, _ChipScrt_, _OEMScrt_, _ProdScrt_, or _DevScrt_ in its _Locality_, to bind the information in the CC to its allowed consumers; otherwise the Metadata is invalid.

[[KLE-usage-input-output]]
=== Zklio

With `Zklio`, the KLIOBUF can replace the vector operands of `kl.exec`, so that code runs on cores without vector registers; `kl.setst` and `kl.mgmt` use Form D instead of Form C.

[horizontal]
[[KLE-GR-substitution,GR11]]GR11:: With `Zklio`, every Form of `kl.exec` that reads inputs from or writes outputs to vector registers, the _native_ Form in its Machine and State, admits a _substitution_: a Form D `kl.exec`, using the KLIOBUF in their place, however the Machine describes the use of the native Form.

[[KLE-GR-substitution-operands,GR12]]GR12:: Where a Form A or B `kl.exec` expects a vector input, its substitution takes the input from [`klstart`, `kliobuftop`-1] instead of a vector register, and where a Form A or C `kl.exec` expects a vector output, its substitution writes it to [`klstart`, `kliobuftop`-1] (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-clear-output>>), a Form A substitution writing each block's output over its input.

[[KLE-GR-form-mismatch,GR13]]GR13:: A _wrong Form_ of a usage instruction is a Form that is none of: a native Form of the instruction expected in the locker's State (for `kl.setst`, as determined by its immediate); a Form that <<KLE-instruction-setst>> admits in place of a native Form of `kl.setst`; with `Zklio`, the substitution of that native Form (Rule <<KLE-GR-substitution>>).

[[KLE-GR-iobuf-configured,GR14]]GR14:: These instructions access the KLIOBUF and require it to be configured, with a non-zero `kliobuflen`, even for an empty transfer window:
+
--
* a `kl.input` or `kl.output` with `Xl` {ne} 0, which names no locker and never falls through;
* the KLIOBUF variants of `kl.mvin` and `kl.mvout`; and
* a substitution that is not a wrong Form (Rule <<KLE-GR-form-mismatch>>).
--
+
A `kl.input` or `kl.output` with `Xl` = 0 is not one of them: it is the encoding of a locker transfer, which falls through as described in Rule <<KLE-GR-outcome-inert>> below.
//, so it performs no operation and writes 0 to `klstart`, whatever `Zklio` and the KLIOBUF (<<KLE-instruction-load>>).
+
If the KLIOBUF is not configured, such an instruction is a ground of the <<KLE-third-group-ILL-grounds>>: a usage instruction at item 1 of Rule <<KLE-GR-outcome-valid-state>>, and any other instruction right after the checks of Rule <<KLE-GR-management-check-order>>, unless it falls through (Rule <<KLE-GR-fall-through-operands>>).

[[KLE-GR-substitution-failures,GR15]]GR15:: For a substitution of `kl.exec` (Rule <<KLE-GR-substitution>>) that is not a wrong Form (Rule <<KLE-GR-form-mismatch>>), a non-zero `kliobuflen` with a `kliobuftop` invalid for the Machine transitions the locker to Error State _Invalid_, whether the KLIOBUF is used as input or only as output (Rule <<KLE-GR-transfer-window-checks>>).

[[KLE-issue-checks]]
=== Checks at Instruction Issue

[horizontal]
[[KLE-GR-management-check-order,GR16]]GR16:: The _locker-state-independent checks_ of an instruction, those that precede the state-dependent ones, are made first, in this order, the first that fails deciding the outcome:
+
--
. a `KLS` field in effect that is Off, or a `*stateen0` denial: illegal-instruction exception, or virtual-instruction exception for an `hstateen0` denial while V=1 (<<KLE-first-group-ILL-grounds>>);
. a pending fatal condition: KLE fatal-error exception;
. the <<KLE-second-group-ILL-grounds>>: illegal/virtual-instruction exception;
. no active CSK: KLE missing-CSK exception (<<KLE-CSK-requirements>>);
. for an instruction that names `KLNL`, and for `kl.load`, `kl.store`, `kl.mvin` and `kl.mvout`, which act on the locker that `klnamedlocker` names (Rule <<KLE-GR-locker-less-transfers>>), except a `kl.input` or `kl.output` with `Xl` {ne} 0, which names no locker and never falls through, the _klnamedlocker check_: the locker is the one named by `klnamedlocker`, or none if it is 32 (Rule <<KLE-GR-klnamedlocker-override>>), and with none, item 6 does not apply, the remaining items are still checked, and the instruction falls through (Rule <<KLE-GR-outcome-inert>>);
. an access to a locker whose `*llockerstatus` field in effect is _Off_, other than the destination access of a destructive configuration instruction other than `kl.swap` (<<KLE-destructive-config>>) and any access of a `kl.clone`, `kl.rename` or `kl.swap` whose source and destination are the same locker (<<KLE-instruction-clone>>), so that `kl.load`, `kl.mvin` and `kl.setste` are not exempt: KLE locker-Off exception (<<Zkl-ISA-priv.adoc#KLE-CSR-llockerstatus>>);
. the <<KLE-third-group-ILL-grounds>> that do not depend on the locker's _State_, its items 3–5, 7 and 8, and its item 6 for a `kl.input` or `kl.output` with a non-zero `Xl`: illegal-instruction exception; the MDH-operand check of `kl.mgmt` is always made, even if the instruction then falls through;
. for `kl.load` and `kl.store` with `klnamedlocker` < 32:
first, the address breakpoint of the first component access (<<KLE-GR-memory-instructions>>), then
load, resp. store, address-misaligned exception if the effective address is not 16-byte aligned, even for an empty transfer window.
The address breakpoint is checked only if the transfer window is not empty and the locker is not inert; the alignment check is always made.
The breakpoint is checked for the first component access only; Rule <<KLE-GR-memory-instructions>> governs the later ones.
The first component access is at the effective address plus `klstart`, with a size of 16 bytes, and both exceptions write that address to `xtval`; a `klstart` that is not a multiple of 16 is left to the Locker Checks (<<KLE-third-group-ILL-grounds>>).
--

[[KLE-GR-state-dependent-checks,GR17]]GR17:: The _locker-state-dependent checks_ follow those of Rule <<KLE-GR-management-check-order>>. The class of the locker's State selects them, and the cited Rule or section states them and their order:
+
--
. an inert locker: none; the instruction has the outcome of Rule <<KLE-GR-outcome-inert>>;
. a Configuration State: Rule <<KLE-GR-outcome-config-state>>, with the <<KLE-mv-locker-checks,locker checks>> for a management transfer and the sequence of the operation under way for a `kl.mgmt` (<<KLE-locker-management>>);
. a Valid State, for a configuration instruction: Rule <<KLE-GR-config-valid-state>>, with the <<KLE-mv-locker-checks,locker checks>> for a management transfer, Rule <<KLE-GR-policy-narrowing-state>> for `kl.rstr*`, and Rule <<KLE-GR-error-state-can-be-reconfigured>> for `kl.setste`;
. a Valid State, for a usage instruction: Rule <<KLE-GR-outcome-valid-state>>, then, for a `kl.exec`, the transfer-window checks of Rule <<KLE-GR-transfer-window-checks>> and, after them, the Rules of its Machine (<<Zkl-ISA-machines.adoc#KLE-MGR-granularity>>, <<Zkl-ISA-machines.adoc#KLE-MGR-single-last-block>>), and, for a `kl.derive`, Rules <<KLE-GR-derive-check-order>>, <<KLE-GR-checks>> and <<KLE-GR-narrowing>>, in this order.
--

[[KLE-GR-config-valid-state,GR19]]GR19:: In a Valid State, in which no management operation is under way, every configuration instruction is admitted except a management transfer instruction or a completing `kl.mgmt`, which raise an illegal-instruction exception (Locker Checks in <<KLE-instruction-mv>>).

+
--
. a substitution (Rule <<KLE-GR-substitution>>) with an unconfigured KLIOBUF raises an illegal-instruction exception (Rule <<KLE-GR-iobuf-configured>>);
. a _UsagePolicy_ that forbids the instruction raises a KLE privilege-violation exception according to Rule <<KLE-GR-usage-policy>>;
. a non-zero _ExpirationDate_ is evaluated as <<KLE-Metadata-expiration-date>> states: a secure clock that cannot be read raises a KLE clock-unavailable exception and leaves the _State_ unchanged, and a passed _ExpirationDate_ transitions the affected locker to Error State _Expired_;

. otherwise, the instruction performs its operation.
--
+
For `kl.derive`, see Rule <<KLE-GR-derive-check-order>>.

[[KLE-GR-same-state,GR21]]GR21:: Unless the Machine explicitly allows it and defines what it does, a Valid State does not admit:
+
--
. a `kl.exec` in _Ready_;
. a `kl.setst` naming the current State, except in _Ready_ (Rule <<KLE-GR-to-ready>>) and in a State that loads a field, where it restarts the load (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-load-long-field>>).
--

[[KLE-GR-to-ready,GR22]]GR22:: A `kl.setst` naming _Ready_ and `kl.clearads` (<<KLE-instruction-clearads>>) are admitted in every Valid State, whatever the _MachinePolicy_ of the locker, subject to items 1–3 of Rule <<KLE-GR-outcome-valid-state>>; a wrong Form of either is not admitted (Rule <<KLE-GR-form-mismatch>>).

[[KLE-GR-policy-narrowing-state,GR25]]GR25:: A `kl.rstrl` or `kl.rstrv` (<<KLE-instruction-restrict>>) that narrows _MachinePolicy_ to a value that the Machine forbids transitions the locker to Error State _Invalid_.
Any other narrowing changes no State; from the next instruction on, Rule <<Zkl-ISA-machines.adoc#KLE-MGR-policy-gate>> checks each `kl.exec`, `kl.derive` and usage `kl.setst` against the narrowed _MachinePolicy_, at issue and on entering a State.

[[KLE-inert-locker-rules]]
=== Rules Governing Inert Lockers

Recall from <<KLE-def-inert>> that an _inert_ locker is an _Unconfigured_ locker, a locker in an Error State, or `KLNL` while `klnamedlocker` = 32.
// , which a `kl.mvin` or `kl.mvout` also names then (Rule <<KLE-GR-locker-less-transfers>>).

[horizontal]
[[KLE-GR-outcome-inert,GR32]]GR32:: After the locker-state-independent checks of Rule <<KLE-GR-management-check-order>>, an instruction on an inert locker has only the outcome that <<KLE-insn-outcomes-inert>> gives.
It _falls through_, performing no operation, leaving the _State_ unchanged and raising no exception, unless it is:
+
--
* a destructive configuration instruction on an _Unconfigured_ or Error-State locker, which acts as on any locker and may raise an exception only after its destructive step (Rule <<KLE-exception-state-change>>);

* a `kl.input` or `kl.output` with `Xl` {ne} 0, which transfers, or raises the exceptions, of Rule <<KLE-GR-iobuf-configured>>.

[[KLE-derivation-rules]]
=== Derivation Rules

The Rules of this section apply to `kl.derive`.

[horizontal]
[[KLE-GR-derive-check-order,GR37]]GR37:: Each condition of Rule <<KLE-GR-outcome-valid-state>>, starting with the State class (Rule <<KLE-GR-state-dependent-checks>>), is checked first on the source of a `kl.derive` and then on its destination, before the next condition.
A condition that applies to both lockers takes effect on both; one that applies to the source only leaves the destination unchanged.

[[KLE-GR-derive-rule-both-fixed-size,GR38]]GR38:: _Transfer size and progress:_
A destination field of `dest_length` bytes receives `eff_length` = min(`length`, `dest_length`) bytes and is zero-filled beyond them; any other destination receives `eff_length` = `length` bytes.
Each endpoint advances as the `kl.exec` instructions producing or consuming the bytes would, except a field source, which does not advance: byte `i` of the transfer is byte `i` of the field, and zero in the unused part of a final partial output unit.
+
Every check that can raise an exception precedes the first unit.
If a field fails a check when its transfer completes (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-check-on-write>>), its locker takes the outcome that its Machine specifies, or else _Invalid_, and the instruction retires; the source keeps the effects of the units already transferred.

[[KLE-GR-checks,GR39]]GR39:: After the checks of Rule <<KLE-GR-outcome-valid-state>>, the following checks are made in order; a failed check transitions the locker named to Error State _Invalid_ (Rule <<KLE-GR-clear-locker-content-error-state>>), and nothing more is transferred:

. `klstart` must be 0; otherwise the destination transitions.
. The source must be a source endpoint; otherwise the source transitions.
. The destination must be a destination endpoint; otherwise the destination transitions.
. The pair must be admitted; otherwise both transition.
. The effective length (Rule <<KLE-GR-derive-rule-both-fixed-size>>) must meet the length constraints of the destination, a final partial input unit included, and the `eff_length` bytes must fit its remaining capacity; otherwise the destination transitions.
. A destination that receives a whole value has the following length conditions; otherwise the destination transitions:
** A destination key field of `dest_length` bytes is loaded in full: it requires `length` {ge} `dest_length` and a source field, or remaining `kl.exec` output, of at least `dest_length` bytes, unless its Machine admits a shorter key under conditions that it states, as <<Zkl-ISA-machines.adoc#KLE-HMAC,HMAC>> does; a key field that receives a shared secret (Rule <<KLE-GR-shared-secret>>) is never zero-padded by it: the secret has at least `dest_length` bytes, and the field receives the first `dest_length` of them. The `eff_length` bytes it receives (Rule <<KLE-GR-derive-rule-both-fixed-size>>) replace whatever a `kl.exec` loaded into it and complete its loading; a key written in State _Ready_ is followed by the initialization that the Machine performs in that State.
** A message input receiving a shared secret (Rule <<KLE-GR-shared-secret>>) requires a `length` equal to the length of the secret.
// Before byte-granular hash inputs:
// A message input receiving a shared secret (Rule <<KLE-GR-shared-secret>>) requires `klstart` = 0 and a `length` at least the length of the secret and at most that length rounded up to a multiple of the granularity of the destination; otherwise the destination transitions.
. The source must be able to supply the `eff_length` bytes, a final partial output unit included (Rule <<KLE-GR-derive-rule-both-fixed-size>>); otherwise the source transitions.
+
Apart from their failure outcomes, these checks change nothing; the checks on the transferred values are made per unit (Rule <<KLE-GR-derive-rule-both-fixed-size>>).

[[KLE-GR-narrowing,GR40]]GR40:: Before a nonempty _restricted transfer_ that Rule <<KLE-GR-checks>> admits begins, the destination transitions to Error State _Privilege Violation_, and nothing is transferred, if its _SCProtection_ is lower than that of the source, or else if the narrowing of its MDH by that of the source (<<KLE-Metadata-narrowing>>) fails.
Otherwise the narrowed policies govern the transfer, but are written only with its first committed unit (Rule <<KLE-GR-derive-rule-both-fixed-size>>).

[[KLE-GR-unrestricted-no-narrowing,GR41]]GR41:: An _unrestricted transfer_ applies no policy narrowing.

[[KLE-GR-shared-secret,GR42]]GR42:: A shared secret of a key-agreement or key-encapsulation Machine moves into a key field of a symmetric Machine that <<Zkl-ISA-machines.adoc#KLE-derive-endpoints>> lists as a destination, or into the `kl.exec` input of a hash function, MAC or XOF that <<Zkl-ISA-machines.adoc#KLE-derive-endpoints>> lists for it.
If its Machine explicitly allows it to export through `kl.exec`, it moves as an unrestricted transfer of its field.
Otherwise, as the ML-KEM `sharedkey`, it moves only as a _restricted transfer_ and only to these destinations: no other message input receives it, not even one that a Machine defines.

[[KLE-GR-exec-implies-unrestricted,GR43]]GR43:: The `kl.exec` output of a block cipher Machine that <<Zkl-ISA-machines.adoc#KLE-derive-endpoints>> lists as a source can be moved, as an _unrestricted transfer_, into a key field of a symmetric Machine that <<Zkl-ISA-machines.adoc#KLE-derive-endpoints>> lists as a destination. No other `kl.exec` output is a source.

=== State Changes Under Exceptions

[horizontal]
[[KLE-exception-state-change,GR44]]GR44:: A KLE fatal-error exception resets the KLE state (KLE fatal-error in <<Zkl-ISA-priv.adoc#KLE-exception-codes>>). Any other exception leaves the KLE state unchanged, except for these changes, made even when the instruction then raises an exception:
+
--
* the destructive step (<<KLE-destructive-config>>) of a provisioning- or import-opening `kl.mgmt`, which zeroizes the locker and sets `klnamedlocker` (Rule <<KLE-GR-klnamedlocker-updates>>), and of a `kl.clone`, which clears its destination as `kl.clear` would, with the same effect on `klnamedlocker` (<<KLE-instruction-clone>>) and on the `*llockerstatus` and `KLS` fields it sets to Dirty;
* the zeroization of `SIV`, `IMPQUAL` and `SIV2` by an import-opening `kl.mgmt` (<<KLE-MVR-open>>);
* the clearing of `klstart` by any `kl.mgmt` that passes items 1–6 of the locker-state-independent checks (<<KLE-locker-management>>); and
* the completed prefix, and the `klstart` that records it, that a memory instruction commits when one of its component accesses raises a memory exception (Rules <<KLE-GR-memory-instructions>> and <<KLE-GR-resumability-options>>).
--
+
For a resumed instruction, "`unchanged`" refers to the state when it is issued again, not at the halt; the prefix committed by earlier attempts is part of that state and is not undone.

[[KLE-resumability]]
=== Interruptibility and Resumability of KLE Instructions

[horizontal]
[[KLE-GR-halted-state,GR45]]GR45:: The state that a halted instruction leaves is described entirely by the locker, `klstart`, `vstart`, the committed output prefix (Rule <<KLE-GR-precise-halt>>), the identity of the halted instruction, held in the hart state that software saves and restores and not in the KLE (Rule <<KLE-GR-long-running-progress>>) and, for a <<KLE-GR-long-running-no-data>>, the progress field _P_ (Rule <<KLE-GR-long-running-progress>>) and the ADS, and, under option 5 of Rule <<KLE-GR-resumability-options>>, the restart count.

[[KLE-GR-interruptibility-classes,GR46]]GR46:: The architecturally _resumable_ instructions are `kl.exec`, which halts only at an interruption point of its Machine and State (Rule <<KLE-GR-interruption-point>>); the vector `kl.mvin` and `kl.mvout`, which transfer several 128-bit blocks and halt only at a block boundary; and `kl.load`, `kl.store`, `kl.input` and `kl.output`, which commit their input units as a prefix in offset order (Rule <<KLE-GR-prefix-complete>>), whatever the order of their component accesses (Rule <<KLE-GR-memory-instructions>>).
Every other KLE instruction is _uninterruptible_ (Rule <<KLE-GR-uninterruptible-instructions>>).
A `kl.derive` is never <<KLE-GR-long-running-no-data,long-running>> and requires `klstart` = 0 (Rule <<KLE-GR-checks>>).

[[KLE-GR-resumability-options,GR47]]GR47:: When a handler accesses an input, output or locker of a preempted instruction, or other KLE state the instruction may affect, the implementation chooses one of:
+
--
. _Background completion:_ the hart waits for the instruction to complete; not for the memory instructions `kl.load`, `kl.store`, `kl.input` and `kl.output`.
A KLE fatal error detected before such an instruction completes makes every conflicting access (Rule <<KLE-GR-conflicting-access-rule>>) wait for the KLE unit reset, and the outputs of that instruction are then zero.
. _Atomic completion_ before the interrupt is taken.
. _Precise halt and resumption_ at the prefix-complete point that `klstart` records (Rule <<KLE-GR-prefix-complete>>); as for `vstart` in RVV 1.0, forward progress must eventually be guaranteed for the granule that `klstart` reports.
. _Timeout, then precise halt and resumption:_ option 3, after a system-imposed timeout.
. _Precise halt and restart_ at the `klstart` and `vstart` with which the instruction was issued, discarding the partial work of the attempt, at most _R_ consecutive times for the same locker and instruction, against livelock; _R_ is a choice of the implementation, documented for each instruction that uses this option, and the KLE unit keeps the count with the halted state of the locker (Rule <<KLE-GR-halted-state>>), which any completion or State transition resets.
A `kl.input` or `kl.output` names no locker and does not use this option.
Past that bound, it is not restarted: a memory instruction continues under option 3, as it does once a component access of any attempt has had a visible effect; any other instruction, uninterruptible ones (Rule <<KLE-GR-uninterruptible-instructions>>) and a long-running `kl.setst` included, completes before any interrupt is taken, or halts under option 3 or 4 if it supports one.
An internal computation of a <<KLE-GR-long-running-no-data>> restarts under its own rules within the same bound, keeping the committed prefix of the enclosing instruction.

`kl.exec` and the vector `kl.mvin` and `kl.mvout` use option 3 or 4 (Rule <<KLE-GR-precise-halt>>); a long-running operation (<<KLE-GR-long-running-no-data>>) may also use option 5 (Rule <<KLE-GR-long-running-preemption>>).
A synchronous exception raised by a component access halts the instruction precisely, with `klstart` at the last prefix-complete point, among those that the instruction permits, before the faulting byte (RVV 1.0 §3.7).
--

[[KLE-GR-uninterruptible-instructions,GR48]]GR48:: An uninterruptible instruction (Rule <<KLE-GR-interruptibility-classes>>) completes, raises an exception with only the effects of Rule <<KLE-exception-state-change>>, or has no architecturally visible effect, except that a long-running operation (<<KLE-GR-long-running-no-data>>) halts as Rule <<KLE-GR-long-running-preemption>> states.
An implementation achieves this with option 1, 2 or 5 of Rule <<KLE-GR-resumability-options>>, option 1 subject to Rule <<KLE-GR-conflicting-access-rule>>.

[[KLE-GR-precise-halt,GR49]]GR49:: On a precise halt of a resumable instruction (Rule <<KLE-GR-interruptibility-classes>>), the completed prefix is committed at both endpoints of the transfer, and `klstart` records its byte count or, for `kl.mvin` and `kl.mvout`, the image offset that <<KLE-instruction-mv>> specifies.
The failing and subsequent units have no effect, except as Rule <<KLE-GR-prefix-complete>> permits for a memory instruction, and the instruction does not retire, `xepc` holding its address.
If the instruction transitions its locker to an Error State after partial progress, the completed prefix stays committed, the unwritten part of its output window is zeroed (Rule <<KLE-GR-zero-unwritten-output>>), and the instruction retires (Rule <<KLE-GR-klstart-updates>>).

[[KLE-GR-interruption-point,GR50]]GR50:: An _interruption point_ of a KLE instruction in a State of a Machine is a `klstart` value at which the instruction may halt precisely: a multiple of the Machine's granularity within the transfer window, unless the Machine, or a macro such as `PROCESS_VLI` (<<Zkl-ISA-machines.adoc#KLE-process-VLI>>), defines another set.
For a `kl.exec` with a vector operand it is also a multiple of `SEW`/8; if no non-zero point of the set is one, the only interruption point is 0.

[[KLE-GR-klstart-updates,GR51]]GR51:: Apart from a precise halt (Rule <<KLE-GR-precise-halt>>), <<KLE-CSR-klstart,an instruction that honors `klstart`>> writes 0 to it when it retires, whether it performs its operation or falls through (Rule <<KLE-GR-outcome-inert>>), except `kl.mvin` and `kl.mvout`, which keep it (<<KLE-instruction-mv>>).
`kl.clearall` and a `kl.mgmt` that passes items 1–6 of the locker-state-independent checks (<<KLE-locker-management>>) also write 0 to it; every other instruction leaves it unchanged.

[[KLE-GR-transfer-window-checks,GR52]]GR52:: A Form A–C `kl.exec`, or a Form D `kl.exec` that substitutes for one (<<KLE-usage-input-output>>), checks its transfer window after the conditions of Rule <<KLE-GR-outcome-valid-state>>, in this order:
+
. A `klstart` {ge} the length, which includes a length of 0, makes the window _empty_: the instruction writes 0 to `klstart` and does not reach the Machine, which keeps its State.
. Otherwise, a length invalid for the Machine transitions the locker to Error State _Invalid_.
. Any other `klstart` that is not an interruption point (Rule <<KLE-GR-interruption-point>>) transitions the locker to Error State _Invalid_.

[[KLE-GR-conflicting-access-rule,GR53]]GR53:: Under every option of Rule <<KLE-GR-resumability-options>>, before the issuing hart performs a _conflicting access_, the in-flight operation must have completed, or have halted precisely with `klstart` set as Rule <<KLE-GR-prefix-complete>> requires.
A conflicting access is:
+
--
* an ordinary load or store overlapping the memory region of the in-flight KLE operation;
* an access to a locker that the operation uses, including the issue of another KLE instruction involving it;
* a read or write of `klstart`, `vstart`, `klnamedlocker`, `kliobuflen` or `kliobuftop`, including by the getter and setter instructions (<<KLE-instruction-getter-setter>>);
* a write to a privileged CSR that governs the operation: the `mklcsk` group (<<Zkl-ISA-priv.adoc#KLE-CSR-mklcsk>>), `mklmaxiobuflen` (<<Zkl-ISA-priv.adoc#KLE-CSR-mklmaxiobuflen>>), a Locality CSR (<<Zkl-ISA-priv.adoc#KLE-CSR-locality-groups>>), a `*llockerstatus` CSR (<<Zkl-ISA-priv.adoc#KLE-CSR-llockerstatus>>), a `*stateen0` CSR, or a write to `mstatus`, `sstatus` or `vsstatus` that changes `KLS`;
* the issue of a KLE instruction that reads or writes the authentication registers `SIV`, `IMPQUAL` and `SIV2`, such as an export- or import-opening `kl.mgmt`, while the operation reads or writes them;
* a read or write of a GPR, a vector register or a KLIOBUF byte that the operation writes, including the issue of a `kl.output`, of `kl.mvin KLIOBUF`, or of any other instruction that reads or writes the KLIOBUF; or
* a write to a vector register or to the KLIOBUF that the operation reads, including the issue of a `kl.input` targeting it.

Scalar operands in GPRs, `vl` and `vtype` are captured at issue; accessing them is not a conflicting access.
A KLE instruction sets to Dirty the `*llockerstatus` and `KLS` fields that it affects when it is issued.
// Done before any later instruction of the hart can read them, so a read of these fields is not a conflicting access.
--

NOTE: Together, the last Rule and Rule <<KLE-GR-resumability-options>> make asynchronous execution by the KLE unit invisible to same-hart program order, as <<KLE-Memory-Model>> requires.
Beyond them, the architecture specifies only the allowed interruption points of its instructions and Machines.
An implementation may also preempt a <<KLE-GR-long-running-no-data>> at points that it defines itself.
These operations are defined in the next section.

=== Implementation-Defined Interruption of Long-Running Operations

[[KLE-GR-long-running-no-data,Long-Running Operation]]Definition: _Long-running operation_.::
A `kl.exec` or `kl.setst` that accesses only its lockers and the values of the operands captured at issue may be _long-running_, such as a scalar multiplication, a key generation or a signature; so may a _component operation_ of one, a computation on state already in its lockers between the reading of its inputs and the writing of its outputs, such as the completion of the load of a field.

//

[horizontal]
[[KLE-GR-long-running-preemption,GR54]]GR54:: On preemption, a long-running operation behaves as an option of Rule <<KLE-GR-resumability-options>> that the interrupt or exception allows; the implementation supports at least one of options 3, 4 and 5.
Whether a long-running `kl.setst` is resumable under option 3 or 4 is implementation-defined; one that is makes its State transition only at completion, and until then its State admits only that `kl.setst`, a `kl.setst` naming _Ready_ (Rule <<KLE-GR-to-ready>>), `kl.clearads` and configuration instructions.

[[KLE-GR-long-running-progress,GR55]]GR55:: A long-running operation that halts at implementation-defined points records its progress in a _progress field_ _P_ of the MDH, which is _MachineUse_ or a subfield of it.
_P_ is non-zero and monotonically increasing from the first precise halt of the operation until its completion, and zero otherwise; its format is implementation-defined.
+
The set of the interruption points, and the progress recorded at each,
never depends on key material, a secret field, plaintext or ciphertext, or the value of any ephemeral random value drawn for the operation, with one exception: where the Machine's standard allows the execution time to reveal the number of iterations of a loop, such as a rejection loop (<<Zkl-ISA-machines.adoc#KLE-PQC-ML-DSA>>), they may depend on that number.
Only the timing of the halt determines the interruption point.
+
The operation keeps its intermediate results in the ADS and updates architected Content only at completion.
Apart from changes in the MDH at issue or at retirement of the instruction as its semantics define, no other changes are made to the MDH during the operation except for _P_ and _AuxDataLen_; _AuxDataLen_ depends only on the State and on the halt point.
+
A long-running operation takes no input after it starts: all its inputs are those in its lockers and its scalar or vector operands when the instruction that starts it is issued.
It keeps copies of these initial inputs in the ADS, and a resumed instruction does not re-read the operands.
The resuming instruction, a `kl.exec` or a `kl.setst`, must be the halted one with the same operand registers, immediate and, for a vector operand, `vtype` and `vl`, and, for a KLIOBUF operand, `kliobuftop`; otherwise the locker transitions to Error State _Invalid_.
A re-issue with an empty window (item 1 of Rule <<KLE-GR-transfer-window-checks>>) is not a resumption and leaves the operation halted.
+
The random and intermediate values that the operation keeps in a state field or in the ADS are its _material_, meaningful only while _P_ is non-zero.
A Machine may nevertheless write such a random value, an _ephemeral random value_, and its flag to architected Content before completion, such as ECC's `RndNum` and `HasRndNum` (<<Zkl-ISA-machines.adoc#KLE-ECC>>) or ML-DSA's `rnd` (<<Zkl-ISA-machines.adoc#KLE-PQC-ML-DSA>>); a restart discards it (Rule <<KLE-GR-long-running-restart>>).

[[KLE-GR-progress-discard,GR56]]GR56:: A State in which a `kl.exec` may be interrupted under Rule <<KLE-GR-long-running-preemption>> admits only that instruction and Form, the `kl.setst` instructions that its Machine allows in the State, `kl.clearads` (Rule <<KLE-GR-to-ready>>) and configuration instructions.
For the progress field _P_ and the material of its operation (Rule <<KLE-GR-long-running-progress>>):
+
--
. If _P_ is non-zero, the instruction resumes the operation, or restarts it after zeroing _P_ within the bound of option 5 of Rule <<KLE-GR-resumability-options>>, and a restart generates the material anew.
. An interrupt leaves _P_ and the material unchanged.
. If _P_ is non-zero, `kl.clearads` and every transition of the locker's _State_, a same-State `kl.setst` included, zero _P_ and destroy the material.
The moves of a management operation into and out of a Configuration State are not such transitions (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-management-no-state-operations>>).
. When the operation completes, _P_ is zeroed, and the algorithm of the Machine determines whether the material is kept.
--

[[KLE-GR-long-running-restart,GR57]]GR57:: An import, or an export completion that restores a Valid State, may restart a halted long-running operation, discarding the ADS. It must restart anyway if the ADS is not retained, such as on an `IMPQUAL` mismatch, a failed `SIV2` check or _ADSDropped_ = 1 (<<KLE-SCC-import>>).
// For the reviewer: a restart on an `IMPQUAL` mismatch needs no bound of its own. Privileged software that migrates a locker to a unit with a different `IMPQUAL` can call `kl.clearads` first, so that the operation restarts by the mechanism of the target platform once the locker is imported. Requiring the same `IMPQUAL` across the units of a migration would defeat the flexibility of locker migration and of implementation-defined halting points.
An export or an import zeroes _P_ and destroys the material only where it restarts the operation.
`kl.clone` always restarts it in the copy (<<KLE-instruction-clone>>), zeroing the copy's _P_ and destroying its material; the source keeps both.
A restart zeroes _P_ and destroys the material, every intermediate value computed or randomly drawn for the operation (Rule <<KLE-GR-progress-discard>>).

[[KLE-Memory-Model]]
=== Memory Instructions and Memory Model

The _KLE memory instructions_ are `kl.load`, `kl.store`, `kl.input` and `kl.output`; they are RISC-V memory instructions.
`kl.mvin` and `kl.mvout` access no memory and are not memory instructions.

[horizontal]
[[KLE-rule-memory-instruction-decomposed,GR58]]GR58:: A KLE memory instruction may be decomposed into component accesses of any granularity, none of them required to be atomic, performed in any order that the semantics of the instruction and the memory model allow; among the component accesses of one instruction, ordering follows RVWMO, even with `Ztso`.

[[KLE-GR-memory-rvwmo,GR59]]GR59:: KLE memory instructions appear to execute in program order on the local hart.
Their component accesses are ordinary loads (`kl.load`, `kl.input`) or stores (`kl.store`, `kl.output`) of the issuing hart: between instructions they follow RVWMO, and with `Ztso` RVTSO; `FENCE` and the `.aq`/`.rl` annotations order them as they order ordinary loads and stores, and `FENCE.I` and `SFENCE.VMA` affect them as they affect ordinary loads and stores; other harts observe them as ordinary memory operations under RVWMO, or under RVTSO with `Ztso`, with no order among those of one instruction guaranteed before it completes.

[[KLE-GR-memory-instructions,GR60]]GR60:: After the checks of Rules <<KLE-GR-management-check-order>> and <<KLE-GR-state-dependent-checks>>, each component access of a KLE memory instruction checks, in offset order, the address breakpoint, then the page, guest-page and access faults, as per the Privileged Specification.
Only the checks are in offset order: the accesses themselves are performed in any order that Rule <<KLE-rule-memory-instruction-decomposed>> allows.
A KLE memory instruction completes, and may retire or take a trap with `xepc` past it, only after every component access has passed address translation and permission checks and has been performed.
Otherwise a component access raises the corresponding precise exception for that execution attempt, and the instruction halts as Rules <<KLE-GR-resumability-options>> and <<KLE-GR-precise-halt>> state.

[[KLE-GR-memory-dependencies,GR61]]GR61:: For the syntactic dependencies of RVWMO, each locker, as one unit, and each byte of the KLIOBUF is a register, and a KLE memory instruction has these registers:
+
--
* _Source registers:_ `Xs` and `Xl`, the CSRs `klstart`, `kliobuflen`, `kliobuftop` and `klnamedlocker`, and the data source registers below. `Xs`, `Xl` and `klstart` are address source registers.
* _Data source registers:_ for `kl.store`, the locker it reads; for `kl.output`, the KLIOBUF bytes it reads; none for `kl.load` and `kl.input`.
* _Destination registers:_ `klstart`, an accumulating CSR, tracked as one unit; for `kl.load`, the locker it writes; for `kl.input`, the KLIOBUF bytes it writes. The instruction carries a dependency from each source register to `klstart`.
--
+
Every other KLE instruction carries a dependency from each register, locker and KLIOBUF byte that it reads to each that it writes, so that a dependency passes from a `kl.load` or `kl.input` through lockers and the KLIOBUF to a later `kl.store` or `kl.output`.

[[KLE-GR-prefix-complete,GR62]]GR62:: On a precise halt, `klstart` records a _prefix-complete_ point of the transfer, that is, an offset below which every component access has been performed.
A component access at or beyond it may already have had an architecturally visible effect; re-executing the instruction from that point produces the correct final state. The recorded point never moves back over a prefix committed in this or an earlier attempt.

[[KLE-GR-idempotent-memory,GR63]]GR63:: KLE memory instructions support only idempotent memory: a component access whose effective memory attributes (the PMAs, as modified by the page-based memory type where `Svpbmt` is implemented) are non-idempotent or have side effects is not made, and raises a load, resp. store, access-fault exception (cf. Rule <<KLE-GR-memory-instructions>>), with `xtval` holding the offending address.
Re-execution raises the same exception at the same offending byte, unless that byte no longer has such attributes.

[[KLE-GR-memory-no-random-no-clock,GR64]]GR64:: No component operation of a KLE memory instruction draws random bits (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-atomic-randomness>>) or reads the clock (<<KLE-Metadata-expiration-date>>).

[[KLE-randomness]]
=== Randomness

[horizontal]
[[KLE-GR-rbg-failure,GR65]]GR65:: _RBG/DRBG failures._ If the entropy source has failed permanently (for `Zkr`, the DEAD state), an operation that needs random bits is not performed and its locker transitions to _Invalid_; for `kl.clone` and `kl.derive`, that locker is the destination.
If the bits are only temporarily unavailable, as after a health-test failure from which the source can recover, the instruction waits and, past a documented, implementation-defined bound, raises a KLE RBG-unavailable exception (Rule <<KLE-exception-state-change>>); while the instruction has written nothing beyond the prefix that `klstart` records, an interrupt ends the wait and the instruction is re-executed after it (Rule <<KLE-GR-uninterruptible-instructions>>); otherwise an interrupt ends the wait early only where Rules <<KLE-GR-resumability-options>> and <<KLE-GR-long-running-preemption>> allow it.
An instruction draws all the random bits that it needs before it writes any of its output beyond the prefix that `klstart` records, to `Vd` or the KLIOBUF, so that a KLE RBG-unavailable exception leaves its output unchanged and an in-place `kl.exec` can be re-executed on its intact input; after a permanent failure the locker is _Invalid_ and Rule <<KLE-GR-zero-unwritten-output>> zeroes the part of the output window not yet written.

[[KLE-system-specific-import]]
=== Rules for the Import of a System-Specific Format

[horizontal]
[[KLE-GR-sysfmt-import-only,GR66]]GR66:: System-specific formats are optional and only imported: a PI, or a PCCC of base type `pi`, with _Version_ = 3 is invalid Metadata (<<KLE-Metadata-validity>>).
Such an import replaces a provisioning and is never a snapshot of a running Machine: the format supplies every field that the Machine needs and cannot set itself; for an MDH field such as _AuxInfo_, the value of the MDH is used unless the format supplies one (Rule <<KLE-GR-sysfmt-mdh>>).
_Version_ = 3 appears only during such an import, base or nested, and in the PCCC of a nested export taken during it.
An implementation may support several such formats and distinguishes them in an implementation-defined way.

NOTE: A system-specific format is imported and not provisioned because it may authenticate its data: SCC import code already handles an _Authentication Failed_ error, whereas provisioning code does not, since completing a provisioning authenticates nothing.
Software normally _imports_ CCs (as SCCs) provided by other environments, and since system-specific formats are external to the caller and come from external sources, import is also conceptually the right operation.
However, as after a provisioning of a KLE format, a successful import of a system-specific format ends in _Ready_ with no ADS, and the MDH fields that describe a started Machine are zero (Rule <<KLE-GR-sysfmt-mdh>>).

[horizontal]
[[KLE-GR-sysfmt-mdh,GR67]]GR67:: The base import of a system-specific format opens with a KLE-format MDH:
+
--
* _Version_: 3.
* _AuxDataLen_: the length, in 128-bit blocks, of the data after the MDH, zero-padded to a whole number of blocks.
  Software records it before the import, and `kl.size` and `kl.load` read it (<<KLE-instruction-size>>, <<KLE-serialized-image>>). The format carries no ADS.
* _Machine_, _MachinePolicy_ and _MachineExtension_: the Machine that the import configures.
  The opening `kl.mgmt` checks them and allocates capacity as for any import, or the capacity that holds the 16 {times} _AuxDataLen_ bytes of data while the import lasts (Rules <<KLE-GR-sysfmt-as-received>>, <<KLE-GR-klf-capacity>>), whichever is larger; no `kl.mgmt` rewrites them.
  The format determines this Machine, by naming it or by its own definition.
  Before converting the data, the import-completing `kl.mgmt` checks that the _Machine_ and _MachineExtension_ of the MDH equal those that the format determines, and that the _MachinePolicy_ of the MDH enables only operations that the format allows; if not, the locker transitions to Error State _Invalid_.
* _SCProtection_, _UsagePolicy_, _Locality_ and _ExpirationDate_: the policies, applied as in any import. The format may supply values for _UsagePolicy_, _Locality_ and _ExpirationDate_, which narrow those of the MDH, and a minimum _SCProtection_, which the MDH must meet (Rule <<KLE-GR-sysfmt-completion>>).
* _AuxInfo_: as in a PI of the Machine. The MDH may carry a value, which the import uses unless the format supplies one; the value then comes from the format.
* _State_, _StateExtension_, _KeyType_, _ADSDropped_ and _MachineUse_: zero.
--

[[KLE-GR-sysfmt-policies,GR68]]GR68:: A system-specific format may carry policies beyond those of the declared MDH; the implementation converts them, in an implementation-defined way, into KLE policies at least as strong, which apply in addition to those of the MDH, never in their place.
A policy that cannot be so converted is a failed translation (Rule <<KLE-GR-sysfmt-completion>>).
The format defines whether and how its data is protected: this specification requires neither encryption nor authentication.
The format and the implementer of its import either prevent the import from producing an inconsistent state or reject the data that would produce one (Rule <<KLE-GR-sysfmt-diligence>>).

[[KLE-GR-sysfmt-diligence,GR69]]GR69:: A system-specific format and its import circumvent no requirement of this specification or of the referenced standard of the Machine; the architect of the format and the implementer of its import ensure this.
The base import leaves a locker whose MDH and Content the following sequence could also have produced:
+
--
. a provisioning of the same Machine;
. the usage instructions that load each field that the converted Content configures and the PI does not carry, or that set it by an operation (Rule <<Zkl-ISA-machines.adoc#KLE-operation-immediates>>), then a `kl.setst` naming _Ready_; and
. the narrowing of step 3 of Rule <<KLE-GR-sysfmt-completion>>.

No initialization operation of the format leaves a field in a value that the operations of the Machine could not produce, and no conversion bypasses a check or a derivation of the Machine (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-sysfmt-standard>>).
--

[[KLE-GR-sysfmt-as-received,GR70]]GR70:: Until the import completes, the locker holds the loaded data as received: authentication, decryption, conversion and policy translation take place only in the completing `kl.mgmt`.
A nested export taken during the import (<<KLE-management-formats-and-states>>) is a PCCC that carries only what software supplied: the MDH, which keeps _Version_ 3 and _AuxDataLen_, followed by the data loaded, at _ContentOffset_ 0; its nested import opens with that MDH and restores the locker.

[[KLE-GR-sysfmt-completion,GR71]]GR71:: The `kl.mgmt` that completes a system-specific import receives an `ml` whose _State_ is 0 and proceeds in four steps; a step that leaves the locker in an Error State ends the import.
+
--
. It authenticates and/or decrypts the data, if the format is authenticated and/or encrypted. A failed authentication gives Error State _Authentication Failed_.
It then makes the check of Rule <<KLE-GR-sysfmt-mdh>>, converts the data to the internal representation expected by KLE, translates the policies of the format and takes _AuxInfo_ from the format where it supplies a value. A failure here invalidates the locker.
. The converted Content undergoes every check that the Machine makes on a provisioning or an import of the same fields, with the same outcomes (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-check-on-write>>); each field that it configures is then in the same status, its flag included, as after a complete load of that field by `kl.exec` (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-load-long-field>>).
. It narrows the declared MDH by the translated policies (<<KLE-Metadata-narrowing>>); a failed narrowing, or a format that requires a higher side-channel protection level than the declared _SCProtection_, gives Error State _Privilege Violation_.
. It sets _Version_ and _AuxDataLen_ to 0, zeroes the implementation-defined subfields of _AuxInfo_ (<<KLE-MachineUse>>) and, unless a Machine check left the locker in _Failure_, enters _Ready_ performing the operations of entering it (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-management-no-state-operations>>) or, at this completion only, with initialization operations of the format instead. The other provisioning actions of the Machine, such as setting a default or clearing a field or its flag, apply only to the fields that the converted Content does not configure, and to their flags; none clears a flag set in step 2.
--

NOTE: A CC imported from a system-specific format can be bound by its _Locality_ to the implementations meant to use it.
Code examples (<<Zkl-software.adoc#KLE-pseudocode-examples>>) include no such import.

[[KLE-error-architecture]]
== Error Handling Architecture

An error condition has one of three outcomes:
it raises an exception; it is recorded in the locker as an Error State, which travels with the CC and stays readable until the locker is reconfigured; or on an inert locker, it lets instructions have only the outcome described in <<KLE-insn-outcomes-inert>>, i.e., most fall through and raise no exception.
This Section describes when exceptions are raised and when Error States are set.

// This section lists the error conditions by outcome, as a checklist for implementers and a reference for handler writers; the referenced sections specify them, and Rules <<KLE-GR-management-check-order>> and <<KLE-GR-outcome-valid-state>> give the order in which they are checked.

[[KLE-exceptions-grounds]]
=== Exceptions

A summary of the grounds of each exception that KLE may raise is given here.
The grounds are given in the same descending priority order as in <<Zkl-ISA-priv.adoc#KLE-priv-extensions>>: the address breakpoint and address-misaligned grounds of the first component access of a KLE memory instruction precede the locker-state-dependent grounds (Rule <<KLE-GR-management-check-order>>, item 8), and its page, guest-page and access faults follow them.

[[KLE-first-group-ILL-grounds,First Group of Illegal-Instruction Exception Grounds]]First Group of Illegal-Instruction Exception Grounds::
+
--
These grounds depend only on the presence of a KLE unit and of its features; they raise an illegal-instruction exception, except as item 2 states:

. An access denied by `KLS` = Off or by a `*stateen0` gate;
. an `hstateen0` denial while V=1, or a guest access for which <<Zkl-ISA-priv.adoc#KLE-privileged-CSRs>> prescribes one, raises a virtual-instruction exception instead.
--

KLE fatal-error::
+
--
The main fatal condition is an integrity failure of a hart's KLF (<<KLE-KLF>>); implementations may define others.
Detection and the resulting KLE unit reset (<<KLE-reset-and-m-mode-only>>) may be synchronous or asynchronous; the KLE unit records the condition, and the first KLE instruction or KLE CSR access issued, or in flight, after detection performs no further operation and raises the exception (in the order of Rule <<KLE-GR-management-check-order>>), with `xepc` holding its address; a prefix that an in-flight instruction has already committed stays (Rule <<KLE-GR-precise-halt>>).
The reset takes effect as early as the detection, and at the latest when that instruction or access is issued.
If it takes effect earlier, the KLE unit retains only the internal state needed to raise this exception, and no other exception, and clears that state when it raises it.
Meanwhile no instruction accesses the KLF.
--

[[KLE-second-group-ILL-grounds,Second Group of Illegal-Instruction Exception Grounds]]Second Group of Illegal-Instruction Exception Grounds::
+
--
These grounds depend only on the instruction encoding, the GPR numbers, the vector configuration, `kliobuftop` and the current privilege mode; they raise an illegal-instruction exception, except as item 6 states:

. A reserved encoding, including also `KLNL` where Rule <<KLE-GR-klnamedlocker-override>> does not admit it, or a vector operand while `vtype.vill` is set (<<KLE-KLV>>).
. A reserved value of `r` or `R`, or a non-zero locker register field that they replace (Rule <<KLE-GR-klnamedlocker-override>>), or, in a `kl.derive` with `R` = `00`, equal locker indices (<<KLE-instruction-derive>>).
. A GPR pair or quartet not meeting Rule <<KLE-GR-multiple-GPRs>>.
. A vector operand that Rules <<KLE-GR-vector-MDH-operand>> and <<KLE-GR-vector-legality>>, <<KLE-instruction-exec>> or <<KLE-instruction-mv>> exclude, other than the MDH operand of `kl.mgmt`, or a KLIOBUF variant of `kl.mvin` or `kl.mvout` with `kliobuftop` not a multiple of 16 (<<KLE-instruction-mv>>).
. An encoding of an unimplemented extension.
. An access to a KLE CSR unavailable in the current mode (<<KLE-CSRs-unpriv>>, <<Zkl-ISA-priv.adoc#KLE-privileged-CSRs>>); in VS-mode or VU-mode, where the Privileged Specification prescribes it, a virtual-instruction exception instead.
--

KLE missing-CSK:: No CSK is active (<<Zkl-ISA-priv.adoc#KLE-CSR-mklcsk>>); raised by every KLE instruction and KLE CSR access, except as <<KLE-CSK-requirements>> states.

KLE locker-Off:: An access to a locker marked _Off_, except the destination access of a destructive configuration instruction other than `kl.swap`, and any access of a `kl.clone`, `kl.rename` or `kl.swap` whose source and destination are the same locker (<<KLE-destructive-config>>, <<KLE-instruction-clone>>, <<Zkl-ISA-priv.adoc#KLE-CSR-llockerstatus>>).

[[KLE-third-group-ILL-grounds,Third Group of Illegal-Instruction Exception Grounds]]Third Group of Illegal-Instruction Exception Grounds::
+
--
These grounds depend on the state of the KLE unit:

. A transfer that the locker's _State_ does not admit, or a misaligned `klstart` (Locker Checks in <<KLE-instruction-mv>>).
. A `kl.mgmt` out of sequence (<<KLE-locker-management>>).
. An MDH operand of `kl.mgmt` in `Vs` shorter than 128 bits, whatever the operation (Rules <<KLE-GR-vector-MDH-operand>>, <<KLE-GR-management-check-order>>, <<KLE-instruction-mgmt>>).
. A Form A–C `kl.exec` with `klstart` {ne} `vstart` {times} `SEW` / 8 (Rule <<KLE-GR-klstart-vstart>>).
. A non-zero `Xl` where <<KLE-instructions-memory>> forbids it.
. `kl.input` or `kl.output` with a non-zero `Xl`, without `Zklio`, and any of these instructions with an unconfigured KLIOBUF (Rule <<KLE-GR-iobuf-configured>>).
. A `kl.derive` whose `KLNL` operand names its other locker (<<KLE-instruction-derive>>).
. A `kl.avail` or `kl.size` of Form B or C while `mstatus.kleemulation` is 1, that reaches the lookup of <<KLE-size-avail-lookup,item 5 of `kl.size`>> with an MDH whose combination of Machine fields the KLE unit does not natively implement (<<Zkl-ISA-priv.adoc#KLE-kleemulation>>).
--

KLE unsupported-Metadata:: Unsupported Metadata at a provisioning- or import-opening `kl.mgmt`, which leaves the locker _Unconfigured_ (<<KLE-MVR-open>>); only an M-mode handler can resolve it, by emulating the Machine (<<Zkl-ISA-priv.adoc#KLE-unsupported-handling>>).
Accessing or using a locker in State `kl_stateext_unsupported` raises no such exception.

KLE privilege-violation:: A usage instruction that the _UsagePolicy_ denies (Rule <<KLE-GR-usage-policy>>), or any use, clone or restriction of a locker in a Configuration State (Rule <<KLE-GR-outcome-config-state>>).

KLE clock-unavailable:: The secure clock cannot be read to check a non-zero _ExpirationDate_ (<<KLE-Metadata-expiration-date>>).

KLE out-of-memory:: Insufficient KLF capacity for provisioning, import, or cloning (<<KLE-locker-management>>, <<KLE-instruction-clone>>).

KLE RBG-unavailable:: Random bits that an operation needs remain unavailable past the bound of Rule <<KLE-GR-rbg-failure>>.

Memory exceptions:: The load/store address breakpoint, address-misaligned, and page, guest-page and access-fault exceptions of a KLE memory instruction (<<KLE-GR-memory-instructions>>, <<KLE-Memory-Model>>).

[[KLE-error-states]]
=== Error States

These conditions set an Error State without an exception:

* _Invalid_:
** invalid Metadata or SKID (<<KLE-Metadata-validity>>, <<KLE-system-keys>>);
** an instruction that the Machine, its State or _MachinePolicy_ does not admit, a wrong Form and a `kl.setst` with a non-allowed immediate included (Rules <<KLE-GR-form-mismatch>>, <<KLE-GR-same-state>>, <<KLE-GR-to-ready>>, <<KLE-GR-setst-not-admitted>>, <<KLE-GR-success-failure-cannot-be-set-directly>>, <<KLE-GR-checks>> and <<Zkl-ISA-machines.adoc#KLE-MGR-policy-gate>>);
** a transfer window of a length that the Machine does not admit, or a `klstart` inside it that is not an interruption point (Rule <<KLE-GR-transfer-window-checks>>);
** a permanent RBG failure (Rule <<KLE-GR-rbg-failure>>);
** a configuration error of the Machine (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-config-data-error>>);
** a field that fails its check when a `kl.derive` transfer completes, unless its Machine specifies another outcome (Rule <<KLE-GR-derive-rule-both-fixed-size>>);
** a provisioning completion with a non-zero _AuxDataLen_ or _ADSDropped_ (<<KLE-locker-management>>);
** a system-specific import whose MDH does not match its format, or whose format check fails when the format does not authenticate its data, or whose conversion or policy translation fails (Rules <<KLE-GR-sysfmt-mdh>> and <<KLE-GR-sysfmt-completion>>).
* _Expired_: an _ExpirationDate_ that has passed (<<KLE-Metadata-expiration-date>>).
* _Privilege Violation_: a failed narrowing (<<KLE-Metadata-narrowing>>, <<KLE-instruction-restrict>>, Rule <<KLE-GR-narrowing>>), a SKID resolution below the minimum _SCProtection_ that the SKS associates with the SKID (Rule <<KLE-GR-skid-resolution>>), a restricted `kl.derive` into a destination of lower _SCProtection_ (Rule <<KLE-GR-narrowing>>), or a system-specific import whose format requires a higher side-channel protection level than the declared _SCProtection_ (Rule <<KLE-GR-sysfmt-completion>>).
* _Authentication Failed_: a failed SCC authentication, at the completion of an import (<<KLE-SCC-import>>) or of an export (<<KLE-mgmt-completes-export>>), so software checks the _State_ after both; and a failed check that a system-specific format defines, when the format authenticates its data (Rule <<KLE-GR-sysfmt-completion>>).
* Any Error State: the one that a `kl.setste` names (Rule <<KLE-GR-error-state-can-be-reconfigured>>).

Two outcomes are not Error States: a Machine enters _Failure_ on a data error (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-config-data-error>>) or on a failed verification of an AEAD tag or a signature, which is a result, not an error; and an ADS that fails its check at import is dropped, the SCC accepted (<<KLE-SCC-import>>).

[[KLE-CC-management]]
== Management of Cryptographic Contexts

Following the RISC-V philosophy, KLE splits locker management into sequences of simple instructions, not single instructions that drive large state machines or microcode.
As a consequence:

. the state machines that manage keys and algorithms, which CISC key-protection solutions hide (cite:[IBM-z-arch] "`Protection of Cryptographic Keys`" or cite:[intel-keylocker]), are exposed to software: the hardware is simpler, though it enforces rules against misuse, and the software more complex;
. interrupts and exceptions can separate the instructions of a management sequence, so context switching, process and virtual machine migration, hibernation, and interoperability between KLE implementations need explicit support; and
. so does dynamic locker management, lazy context loading included, where other architectures cache repeated key uses implicitly.

Throughout, KLE preserves the integrity of the MDH and the confidentiality and integrity of the Content of a CC, and binary compatibility holds across implementations that support the same sub-extensions.

<<Zkl-software.adoc#KLE-pseudocode-examples>> provides guidelines for system software.

// ////////////////////////////////////////////////////////////////////

[[KLE-management-formats-and-states]]
=== Management States and Formats

A management operation is *open* from its opening `kl.mgmt` until its *completing* `kl.mgmt`, or until a destructive configuration instruction (<<KLE-destructive-config>>) or a transition to an Error State discards the locker's CC, which ends every open operation on it; `kl.rename` and `kl.swap` carry an open operation with the CC they move.
While it is open, the locker is in a Configuration State.
`kl.mgmt` opens or completes an operation according to its `#immed7`:

[[KLE-management-immeds]]
.Values (decimal) of #immed7 for provisioning, importing, and exporting
[float="center",align="center",width="100%",cols="^7%,<27%,<66%",options="header"]
|===
| Value | Mnemonic                 |  Description
|  56   | `kl_cfg_provisioning`    |  Prepare a locker for provisioning.
|  57   | `kl_cfg_exporting`       |  Prepare a locker for export.
|  58   | `kl_cfg_importing`       |  Prepare a locker for import.
|  63   | `kl_cfg_management_end`  |  Complete the current management operation.
|===

Management operations use various formats to move a CC.
The first two are the Provisioning Input (PI) and the Sealed Cryptographic Context (SCC):

Definition: _Provisioning Input (PI)_.::
The MDH, with _State_ and _StateExtension_ zero, followed by the clear `Content`. A PI is not a locker, so it is never _Unconfigured_.

Definition: _Sealed Cryptographic Context (SCC)_.::
+
--
Up to five sections, in this order, section 5 consisting of `Content1` followed by `Content2`:

[[KLE-SCC]]
.Plaintext of the Sealed Cryptographic Context (SCC) Format, all Sections in Order
[width="100%",cols="^8%,14%,21%,57%",options="header"]
|===
| Section | Section Name | Size                 | Description
| 1       | `MDH`        | 128 bits             | See <<KLE-Metadata>>.
| 2       | `SIV`        | 128 bits             | Authentication tag for `MDH`, the Locality Secrets its _Locality_ names, and `Content1` (<<KLE-SCC-export>>).
| 3       | `IMPQUAL`    | 128 bits, if present | Identifies the implementation of the KLE unit. Non-authoritative, and ignored when _ADSDropped_ = 1.
| 4       | `SIV2`       | 128 bits, if present | Authentication tag for `IMPQUAL`, `SIV` and `Content2`. Non-authoritative, and not verified when _ADSDropped_ = 1.
//
| 5.a
| `Content1`
| A multiple of 128 bits. See <<KLE-length-rule>>.
| Keys and other Machine-specific information that the Machine needs to function correctly. Encrypted in memory, and inside the KLE unit while the SCC is imported or exported.
//
| 5.b
| `Content2`
| A multiple of 128 bits.
| ADS: data that the Machine does _not_ need to function correctly.
  Encrypted in memory, and inside the KLE unit while the SCC is imported or exported.
|===

Sections 3, 4 and 5.b form the implementation-specific ADS, of size _AuxDataLen_ (<<KLE-Auxiliary-Data-Section>>).
KLE generates an image with _ADSDropped_ = 1 only as an SCC-shaped PCCC, when a nested export preserves an interrupted import after `Content2` was dropped; since _ADSDropped_ is unauthenticated, import also accepts this layout in an SCC modified to set the bit.
--

Definition: _Base (Management) Operation_.::
A base management operation is a _provisioning_ from a PI, in State `kl_cfg_provisioning`; an _import_ of an SCC or of a system-specific format (<<KLE-system-specific-import>>), in `kl_cfg_importing`; or an _export_ of a locker in a Valid State, in `kl_cfg_exporting`.
A provisioning or an import is base when `ml`._State_ is not a Configuration State, whatever the State of the locker it opens on; an export is base when it is opened on a locker in a Valid State.

Definition: _Nested Management Operation and Base Type_.::
+
--
An exception may interrupt an open operation. A handler then saves the locker by a *nested export*, an export opened on a locker in a Configuration State, and restores it by a *nested import* of the resulting image, opened whatever the State of the locker; the image is the Partially Configured Cryptographic Context (PCCC) defined below. Nested operations may themselves be interrupted and nested.
States `kl_cfg_ppi_exporting` and `kl_cfg_ppi_importing` result only from nested operations, and are not `#immed7` values.
Each Configuration State (<<KLE-SC-sealing-status>>) encodes the *base type* of its operation, which fixes the format and length of the locker's image at every nesting depth (<<KLE-instruction-size>>):

* `pi`, for a provisioning: `kl_cfg_provisioning`, and `kl_cfg_ppi_exporting` and `kl_cfg_ppi_importing` ("`ppi`" means "`partial provisioning input`") for nested operations;
* `scc` otherwise: `kl_cfg_exporting` and `kl_cfg_importing`, for base and nested operations alike.
--

[[KLE-definition-PCCC]]
Definition: _Partially Configured Cryptographic Context (PCCC)_.::
The third format is the image that an export produces on a locker already in a Configuration State: an MDH holding a Configuration State, in the format of its *base type*, without further encryption or authentication:
+
* base type `pi`: a _PI-shaped_ image, the MDH followed by the clear `Content` that software supplied in the PI; software clears such a locker before giving control to another software context, of the same or a lower privilege, which could otherwise export it (Rule <<Zkl-software.adoc#KLE-SR-clear-before-lower-mode>>);
* base type `scc`: an _SCC-shaped_ image, in the format of an SCC: the MDH followed by `SIV` and, when present, `IMPQUAL` and `SIV2`, as _ContentOffset_ prescribes (<<KLE-serialized-image>>), and by the `Content` already in the locker, as ciphertext; with _Version_ = 3, the MDH followed only by the `Content` as software supplied it (<<KLE-system-specific-import>>).

The fourth format is used for CCs in an Error State.

Definition: _Error-State image_.::
The exported image of an Error-State locker is the MDH alone: its export reads the MDH from the locker and writes it to memory; its import is a single `kl.mgmt` (<<KLE-error-state-transfer>>).

Software saves the locker's MDH as `ml` before opening an export, and an import takes `ml` from the image. The completing `kl.mgmt` restores _State_ from `ml`, so each nesting level keeps its own _State_; completing a base operation leaves the locker in a Valid or Error State, and completing a nested operation restores the Configuration State that `ml` carries (Rule <<KLE-GR-completion-state>>).

Encryption during management::
While an SCC is imported, or a locker exported as one, the locker holds its `Content` encrypted: the base export-opening `kl.mgmt` encrypts it and generates `SIV` and, if _AuxDataLen_ {ge} 2, `IMPQUAL` and `SIV2`; the base import- or export-completing `kl.mgmt` decrypts and authenticates it once the whole image is in place, or restores it from an internal copy (<<KLE-mgmt-completes-export>>); with _ADSDropped_ = 1, no `Content2` is loaded or authenticated.

[[KLE-serialized-image,serialized image]]Definition: _Serialized image_.::
`content_size` is the length in bytes of the serialized `Content` of the locker, as a PI or an SCC according to the base type of its image (<<KLE-length-rule>>), as given by the locker's MDH.
In a PI, an SCC or a PCCC, the `Content` starts at a _ContentOffset_ that depends on that MDH:
// the same case distinction of `kl.size` (<<KLE-instruction-size>>) but excluding the `Content` and the MDH._ADSDropped_ never affects _ContentOffset_.
+
. 0 if MDH._Version_ is 3 (<<KLE-system-specific-import>>), `content_size` and `max_admissible` then both being 16 {times} _AuxDataLen_;
. otherwise, 16 if _AuxDataLen_ = 0, and 48 if _AuxDataLen_ {ge} 2, if MDH._State_ is a Valid State, `kl_cfg_importing` or `kl_cfg_exporting`;
. 0 if MDH._State_ is 0 (the MDH of a PI), `kl_cfg_provisioning`, `kl_cfg_ppi_importing` or `kl_cfg_ppi_exporting`.
+
The _serialized image_ `S` of the locker is `Content`, `SIV {vvert} Content`, or `SIV {vvert} IMPQUAL {vvert} SIV2 {vvert} Content` for _ContentOffset_ = 0, 16 or 48, respectively; while the locker is under management, the authentication registers (<<KLE-KLF>>) hold its leading fields.
Its size is `image_size` = _ContentOffset_ + `content_size`, the value that `kl.size` reports minus 16.
+
`max_admissible` is the length in bytes of the longest `Content` of the locker's base type that the implementation can hold for the Machine: `pi_content_size` for base type `pi`, and `content1_size` plus the largest supported `content2_size` for base type `scc` (<<KLE-instruction-size>>); with _ADSDropped_ = 1, `content2_size` counts as zero.
Bytes of `Content` beyond `max_admissible` belong to a discarded ADS (<<KLE-SCC-import>>), and are not transferred.
The transferred part of `S` ends at `image_end` = _ContentOffset_ + min(`content_size`, `max_admissible`).
Accesses to `S` are 16-byte granular: the management transfer instructions (Rule <<KLE-GR-locker-less-transfers>>) transfer whole 16-byte blocks, and all their offsets and lengths, `klstart`, `content_size`, `max_admissible`, `image_size` and `image_end`, are multiples of 16.

[[KLE-length-rule]]
=== Length of External Formats and KLF Capacity Usage of a Locker

[horizontal]
[[KLE-GR-image-length,GR72]]GR72:: The length of an external image depends only on fields in bits [63:0] of its MDH, as follows, where the bullets are considered in order:
+
* an Error State image, _State_ 0 with a _StateExtension_ of 1–5, or 6 with `Zklexpire`, whatever its other fields hold: the length is 16 bytes (see <<KLE-locker-in-error-state>>);
* any other image with _Version_ = 3: the length is 16 + 16 {times} _AuxDataLen_ bytes (Rule <<KLE-GR-sysfmt-mdh>>);
* a PI: the length depends on _Machine_, _MachinePolicy_, _MachineExtension_ and _KeyType_;
* an SCC: the length depends on _Machine_, _MachinePolicy_, _MachineExtension_, _KeyType_, _StateExtension_, _AuxDataLen_ and _ADSDropped_;
* a PCCC: as the format of its base type (<<KLE-management-formats-and-states>>).

[[KLE-GR-klf-capacity,GR73]]GR73:: The KLF capacity used by a locker is fixed when the opening `kl.mgmt` or the `kl.clone` that configures it allocates it, and depends only on the _Machine_, _MachinePolicy_, _MachineExtension_, _SCProtection_ and _KeyType_ of the MDH it installs and, during a system-specific import, on _AuxDataLen_.
It covers every field that its Machine may use in every State it can reach and the largest ADS that the implementation keeps for the Machine.
It also covers, during a system-specific import, the 16 {times} _AuxDataLen_ bytes that the locker holds as received (Rule <<KLE-GR-sysfmt-as-received>>), even where they exceed what the Machine normally occupies; upon base import completion the implementation may release any excess capacity beyond what the converted CC occupies.
A later change of _State_ or _MachinePolicy_ does not change it; it is released only as stated above at a base import completion, when the locker enters an Error State (Rule <<KLE-GR-clear-locker-content-error-state>>), or when it is destructively configured; with _KeyType_ = 2 it is that of _KeyType_ = 0.

[[KLE-rules-masked-implementations]]
=== Single-Share Key Export Rule for Masked Implementations

[horizontal]
[[KLE-GR-single-share,GR74]]GR74:: _Single-share export:_ A multi-share implementation of a Machine provisions, imports and exports all its keys and secrets as reconstructed values.
(((KLE, Machine, side-channel protection variants)))
A side-channel-protected Machine is an implementation variant of the unprotected one, distinguished architecturally only by the _SCProtection_ field of the MDH.
// The reconstruction may be only conceptual, and is protected as <<KLE-KLF>> recommends.
Such an implementation may copy System Key material from the SKS into the locker and expand it into shares, but exports the key only as its SKID (Rule <<KLE-GR-skid-field>>); no ADS, alone or combined with any other data that KLE exports, including other SCCs of the same CC, may allow or facilitate recovering a key value configured by a SKID.

NOTE: Reconstructing or re-randomizing a key is usually an inexpensive operation, for instance when a block cipher in counter mode generates the masks; an implementation with a slower share generator may keep shares or masks in the ADS.

[[KLE-system-keys]]
=== System Keys

A System Key is identified by a 64-bit SKID, from which a system-specific SKS retrieves the key:

[horizontal]
[[KLE-GR-skid-field,GR75]]GR75:: In a PI, an SCC or a PCCC, the key fields of a System Key together hold its SKID, 64 bits, instead of the key values; for a Machine with several keys, the SKS retrieves all of them from that single SKID.
A field configured by a SKID is _never_ exportable, and a key field of a locker whose _KeyType_ is 1 is _never_ importable, by `kl.derive`; no instruction outputs the key value of such a field, which a PI, an SCC or a PCCC replaces by the SKID.

[[KLE-GR-skid-resolution,GR76]]GR76:: _SKID resolution:_ The SKS resolves a SKID that is allowed for the _Machine_ and _MachinePolicy_, whatever the current privilege mode, into a key value that depends on the SKID alone; it resolves a SKID carried in an SCC only after the SCC is authenticated.
A SKID that the SKS does not resolve transitions the locker to Error State _Invalid_ (<<KLE-Metadata-validity>>); the policies that the SKS associates with a resolved key (Rule <<KLE-GR-skid-policies>>) narrow the MDH of the locker (<<KLE-Metadata-narrowing>>), and a failed narrowing transitions the locker to Error State _Privilege Violation_.
The SKS may also associate a minimum _SCProtection_ with a SKID; a resolution whose MDH has an _SCProtection_ lower than that minimum transitions the locker to Error State _Privilege Violation_.

[[KLE-GR-skid-policies,GR77]]GR77:: The SKS associates a _Locality_ (<<KLE-Localities>>) with every SKID, and may associate further policies, such as a _UsagePolicy_, with some SKIDs only.
A policy that it does not associate leaves the corresponding field unchanged when the MDH is narrowed (<<KLE-Metadata-narrowing>>).

[[KLE-locker-management]]
=== Locker Management Operations

This section defines the operations that `kl.mgmt` performs for the `#immed7` values of <<KLE-management-immeds>>.

Two steps are common to every operation below and are not repeated in their descriptions; after the checks of Rule <<KLE-GR-management-check-order>>, a `kl.mgmt` with `KLNL` and `klnamedlocker` = 32 performs only these two (Rule <<KLE-GR-outcome-inert>>):

. It updates `klnamedlocker` as Rule <<KLE-GR-klnamedlocker-updates>> states.
. It clears `klstart` once it has passed items 1–6 of the locker-state-independent checks (Rule <<KLE-GR-management-check-order>>), even if it then raises an exception; if one of those checks rejects it, it leaves `klstart` unchanged, so such a `kl.mgmt` does not destroy the progress of the ongoing operation. Software restores `klstart` to resume interrupted management operations.

The next six subsections describe the semantics of `kl.mgmt`:

[[KLE-MVR-open]]
==== Provisioning- and Import-Opening kl.mgmt

Software first obtains the MDH, `ml`, and supplies it with a Form C or D `kl.mgmt`.
For an import, software first saves `ml` in its local state and supplies it to the import-completing `kl.mgmt`, to restore the _State_ the locker had when it was exported (Rule <<KLE-GR-completion-state>>).

The `kl.mgmt` instruction:

.. zeroizes the target locker, as a <<KLE-destructive-config,destructive configuration instruction>>; bytes of the `Content` of the <<KLE-serialized-image,serialized image>> `S` not yet written since this opening read as zero through every architectural access (`kl.store`, `kl.mvout`, verbatim export); its authentication fields read the current values of the authentication registers (<<KLE-KLF>>), which an import opening zeroizes;
//.. It checks the validity of the fields of the provided MDH `ml`. If any are invalid according to <<KLE-Metadata-validity>>, it transitions the locker to Error State _Invalid_.

// .. if `#immed7` = `kl_cfg_importing` and `ml`._State_ is an Error State, configures the locker immediately and
//     fully in that Error State, with the entire MDH from the auxiliary input, except that _AuxDataLen_ and _ADSDropped_ are set to 0 (Rule <<KLE-GR-clear-locker-content-error-state>>); a _State_ of 54 or 55, or of 53 without `Zklexpire`, is replaced by _Invalid_.
//     The steps below are skipped: the locker holds only its MDH (<<KLE-cryptographic-registers>>), no Machine is selected for execution,
//     and no KLF capacity is allocated, so this configuration cannot fail.
//     This one uninterruptible instruction (Rule <<KLE-GR-uninterruptible-instructions>>) performs the whole configuration and opens no management operation, so
//     no `kl.mgmt` with `#immed7` = `kl_cfg_management_end` follows.
//     This is the _short import path_ of <<KLE-error-state-transfer>>;

.. if `#immed7` = `kl_cfg_importing` and `ml` is in an Error State (_State_ 0, _StateExtension_ 1–6), instead takes the _short import path_ of <<KLE-error-state-transfer>>: it configures the locker immediately in that Error State, or in _Invalid_ if the MDH is invalid, skips the steps below, and opens no management operation;
.. for an import, zeroizes the authentication registers `SIV`, `IMPQUAL` and `SIV2` (<<KLE-KLF>>);
.. copies `ml` into `M`, zeroing _MachineUse_ and the implementation-defined subfields of _AuxInfo_ (<<KLE-MachineUse>>) for a provisioning; the checks below are made on `M`, the locker's MDH staying zero;
.. for a *provisioning*:
... requires `ml`._State_ to be 0, else the Metadata is invalid; the locker's _State_ stays _Unconfigured_ during the checks below, until successful configuration;
... requires `M`._AuxDataLen_ and `M`._ADSDropped_ to be 0: if either is non-zero, the locker transitions to Error State _Invalid_ and the instruction terminates;
.. transitions the locker to Error State _Invalid_ if `M` is invalid Metadata (<<KLE-Metadata-validity>>), an _Unconfigured_ `ml` being invalid for an import unless `ml`._Version_ is 3, and skips the steps below;
.. raises a KLE unsupported-Metadata exception if `M` is unsupported Metadata (<<KLE-Metadata-validity>>);
.. attempts to allocate the KLF capacity that the fields _Machine_, _MachinePolicy_, _MachineExtension_, _SCProtection_ and _KeyType_ of `M` require (<<KLE-length-rule>>) and, if `M`._Version_ is 3, the capacity for 16 {times} `M`._AuxDataLen_ bytes of data (Rule <<KLE-GR-sysfmt-as-received>>), and raises a KLE out-of-memory exception if it cannot;
.. for a *provisioning*, installs `M` as the locker's MDH, with _State_ `kl_cfg_provisioning`;
.. for an *import*:
... installs `M` as the locker's MDH, with _ADSDropped_ = 1 if `M`._Version_ is not 3, `M`._AuxDataLen_ {ge} 2, and either `M`._ADSDropped_ = 1 or `M`._AuxDataLen_ exceeds the maximum of the implementation for the Machine, and with _ADSDropped_ = 0 otherwise (Step 4 of <<KLE-SCC-import>>);
... sets the locker's _State_ to `kl_cfg_importing` if `ml`._State_ is a Valid State, `kl_cfg_importing` or `kl_cfg_exporting`, or `ml`._Version_ is 3;
... sets it to `kl_cfg_ppi_importing` if the base type of `ml`._State_ is `pi` (<<KLE-management-formats-and-states>>).

Whenever a check above fails, raising a KLE exception or transitioning the locker to Error State _Invalid_, every MDH field other than _State_ and _StateExtension_ remains zero and no KLF capacity is allocated; after a KLE out-of-memory exception, the locker remains _Unconfigured_ until a handler sets Error State _Out of Memory_ (<<Zkl-software.adoc#KLE-SR-handler-duty>>).
This does not apply to configuring a locker directly into an Error State from `ml`, which installs the MDH as <<KLE-error-state-transfer>> states.

[NOTE]
====
Clearing the locker right after the locker-state-independent checks of Rule <<KLE-GR-management-check-order>>, before any check of the opening itself, guarantees that any later failure has the same effect: the old content is destroyed and `klnamedlocker` names the locker (Rules <<KLE-GR-klnamedlocker-updates>> and <<KLE-exception-state-change>>).
The capacity check then counts the locker's own allocation as free.
====

==== Export-Opening kl.mgmt

Software first saves a copy, `ml`, of the locker's MDH, to restore the _State_ when completing the export.
`kl.mgmt` can be of Form A, C or D, and ignores its auxiliary input. Depending on `ml`._State_:

.. _Unconfigured_: no operation and no exception. No management operation is opened, the authentication registers are unchanged, and only the common steps above take effect (Rule <<KLE-GR-outcome-inert>>).

.. An Error State: the locker is unchanged, and no management operation is opened (Rule <<KLE-GR-error-state-can-be-reconfigured>>); <<KLE-error-state-transfer>> details this short export path.

.. A Valid State: if the _Locality_ of the MDH names an unconfigured entry without a configured substitute (<<KLE-Localities>>), no operation and no exception: no management operation is opened, the _State_ and the authentication registers are unchanged, and only the common steps above take effect.
Otherwise the instruction prepares the locker to produce an SCC, encrypting its contents and computing the authentication tag(s) as <<KLE-SCC-export>> specifies, and sets its _State_ to `kl_cfg_exporting`.
The opening `kl.mgmt` changes no MDH field other than _State_: an implementation that creates or changes an ADS, or uses _MachineUse_, always keeps _AuxDataLen_ and _MachineUse_ current, so that the MDH software reads before opening the export is the one the export authenticates.

.. A Configuration State (the export of a partially configured locker, or a nested export):

... no encryption or authentication occurs: the locker's contents are exported verbatim, in their order in the PI (for a partially provisioned locker) or in the SCC (for a partially imported locker, or a locker whose own export was interrupted);

... the locker's _State_ is set to `kl_cfg_ppi_exporting` or `kl_cfg_exporting`, according to its base type (<<KLE-management-formats-and-states>>).

==== Common Properties of Completing kl.mgmt

Two special cases:

. `kl_cfg_management_end` issued on a locker in a Valid State raises an illegal-instruction exception: no management operation is open on it.

. `kl_cfg_management_end` issued on an _Unconfigured_ or Error-State locker performs no operation, raises no exception and ignores `ml`; only the common steps above take effect (Rule <<KLE-GR-outcome-inert>>).

These two special cases aside, a `kl.mgmt` issued to complete a management operation
first reads the target locker's MDH, and completes a provisioning if its _State_ is `kl_cfg_provisioning`, an import if it is `kl_cfg_importing` or `kl_cfg_ppi_importing`, and an export if it is `kl_cfg_exporting` or `kl_cfg_ppi_exporting`.

When completing an import or an export, it consumes only the _State_ field of the auxiliary operand `ml`, which restores the locker's _State_ to the value that `ml` records; no other MDH field is written from `ml`.
The locker keeps the _StateExtension_ that it holds during the operation: for an export, the one that it had when the export was opened; for an import, the one carried in the image (<<KLE-SCC-import>>). The completion restores _StateExtension_ @ _State_ without reading `ml`._StateExtension_.
An Error State never reaches a completion: its image is the MDH alone, imported by the short import path, and an export opened on an Error-State locker opens no operation (<<KLE-error-state-transfer>>).

On completing an SCC import or a locker export, authentication is checked only if setting locker.MDH._State_ to `ml`._State_ restores a Valid State; the probability of accepting an incorrect _State_ is negligible.
A nested completion checks only the base type, without authentication.

The `kl.mgmt` completing an import or an export admits these values of `ml`._State_ (<<KLE-management-formats-and-states>>); any other, 61–63 included, raises an illegal-instruction exception:

* a locker whose MDH has _Version_ = 3: `kl_cfg_importing` or `kl_cfg_exporting`, and, for a locker in `kl_cfg_importing`, also _State_ 0, which completes the system-specific import (Rule <<KLE-GR-sysfmt-completion>>);
* otherwise, a locker of base type `scc` (`kl_cfg_importing` or `kl_cfg_exporting`): a Valid State (1–55), `kl_cfg_importing` or `kl_cfg_exporting`;
* a locker of base type `pi` (`kl_cfg_ppi_importing` or `kl_cfg_ppi_exporting`): `kl_cfg_provisioning`, `kl_cfg_ppi_importing` or `kl_cfg_ppi_exporting`, never a Valid State, so the clear `Content` of a partially provisioned locker becomes usable only by completing its provisioning.

==== Provisioning-Completing kl.mgmt

No MDH saved at provisioning start is needed: `kl.mgmt` can be of Form A, C or D, and ignores its auxiliary input.
It transfers no data to or from memory, vector registers, the KLIOBUF or another locker, so the random generation of keys for _KeyType_ = 2 never waits on, or delays, a data transfer (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-atomic-randomness>>).

Completing a provisioning requires _AuxDataLen_ = 0 and _ADSDropped_ = 0; if locker.MDH._State_ is `kl_cfg_provisioning` and either field is non-zero, the locker transitions to Error State _Invalid_, and the instruction terminates.

The operation makes the provisioned locker available to software by:

... for _KeyType_ = 2, generating the key and setting _KeyType_ to 0 (<<KLE-KeyType-field>>, Rule <<KLE-GR-rbg-failure>>), and for _KeyType_ = 1, applying the SKID resolution of <<KLE-system-keys>>;
... converting the locker's content into the internal format of the KLE unit;
... performing any check required by the Machine on the fields of the PI (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-check-on-write>>); a failed check transitions the locker as Rule <<Zkl-ISA-machines.adoc#KLE-MGR-config-data-error>> classifies it, to Error State _Invalid_ for a configuration error or to _Failure_ for a data error, in place of the step below; and
... setting _State_ to _Ready_, with the operations of entering it (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-management-no-state-operations>>), and _StateExtension_, _MachineUse_ and the implementation-defined subfields of _AuxInfo_ to 0.

If a process is preempted during provisioning, `kl.store` or `kl.mvout` exports only the original PI information, unencrypted.
Within a provisioning, only its completing `kl.mgmt` may generate secret random material needed to configure the locker, retrieve key material from the SKS, or derive, expand or re-share that material, so that no such material is exposed in an unencrypted export of a partially provisioned locker.

==== Import-Completing kl.mgmt

Software uses Form C or D of `kl.mgmt` to supply the value `ml` saved when the import started.
The image authenticated as ``AD[0]`` is the MDH held in the target locker, i.e., the one carried in the SCC and loaded when the import started, with its _State_ restored from `ml` and _ADSDropped_ cleared only in the copy used for authentication (<<KLE-SCC-import>>).

... If locker.MDH._Version_ is 3 and `ml`._State_ is 0, the instruction completes the system-specific import as <<KLE-system-specific-import>> states.
... If `ml`._State_ is a Valid State (the import of the export of a fully configured locker):
.... locker.MDH._State_ is set to `ml`._State_.
.... The KLE unit decrypts and authenticates the locker's content.
.... If authentication fails, the target locker transitions to Error State _Authentication Failed_, without an exception. Otherwise, the ADS is processed, or dropped, as <<KLE-SCC-import>> states; then, if _KeyType_ = 1, the SKID is resolved, and the narrowing of <<KLE-system-keys>> is applied.
.... The KLE unit converts the locker's content into its internal format.
.... The KLE unit performs the checks that the Machine attaches to the fields that the import restores (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-check-on-write>>); a failed check transitions the locker as when completing a provisioning (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-config-data-error>>).
This makes the locker available to software.
... Otherwise (the import of the export of a partially configured locker, or of a nested export), locker.MDH._State_ is set to `ml`._State_.

[[KLE-mgmt-completes-export]]
==== Export-Completing kl.mgmt

Software uses Form C or D of `kl.mgmt` to supply the MDH value `ml` saved when the export began. Then:

. The _State_ of the locker is set to `ml`._State_.
. If `ml`._State_ is a Valid State, the instruction restores the locker to the clear format it had when the export began, and makes it accessible to software:
.. it decrypts and authenticates the contents as when completing an import, with the MDH held in the locker as `AD[0]`, and _ADSDropped_ cleared in the copy that first-segment authentication consumes;
.. if the `SIV` check fails, the locker transitions to Error State _Authentication Failed_, and the instruction terminates without an exception; otherwise it performs Steps 14–15 of <<KLE-SCC-import>>, and then the steps that follow authentication in the import-completing `kl.mgmt` (<<KLE-locker-management>>): SKID resolution and narrowing for _KeyType_ = 1, conversion into the internal format, and the checks of Rule <<Zkl-ISA-machines.adoc#KLE-MGR-check-on-write>>, with the same outcomes.
. If `ml`._State_ is not a Valid State, the locker's contents are not changed further.

Instead of decrypting and authenticating the locker's contents in Step 2.a, an implementation may restore the clear contents from an internal copy, made when the export was opened, if the outcome is identical; the specification defines no mechanism for this, and Step 2.b then follows as after a successful `SIV` check.
The copy is valid only if, since the export was opened:

* no instruction has written the locker's MDH or contents, moved its CC, or opened or completed a management operation on it other than this export, so that a nested export or import, a destructive configuration instruction, `kl.setste`, `kl.rename` or `kl.swap` on the locker invalidates the copy;
* `SIV` and, if the image carries them, `IMPQUAL` and `SIV2` still hold the values that the opening generated; and
* the CSK and the `LST_eff` entry of every Locality that the MDH names (<<KLE-Localities>>), which the decryption and authentication use, are unchanged.

With a valid copy, Step 2.b still performs SKID resolution and narrowing for _KeyType_ = 1 against the current SKS state, so a revoked SKID or a changed SKS policy has the same outcome as on the full path.

Without a valid copy, the instruction decrypts and authenticates as Step 2.a states.
With one, it uses the copy only if `ml`._State_ equals the _State_ that the locker had when the export was opened; otherwise it transitions the locker to Error State _Authentication Failed_, as the failing `SIV` check would.

=== SCC Export and Import Algorithms

Section <<KLE-SCC-AEAD>> defines the authenticated encryption scheme, and <<KLE-SCC-export>> and <<KLE-SCC-import>> the SCC export and import algorithms.

[[KLE-SCC-AEAD]]
==== The SCC Authenticated Encryption Scheme

SCC export and import use a variant of AES-GCM-SIV cite:[DBLP-journals-iacr-GueronLL17,RFC8452] that differs from the standard as follows:
the POLYVAL input does not contain the lengths of the associated data and plaintext, since they are already implied by the MDH;
the optional nonce is omitted;
a domain separation bit, `sep`, distinguishes the two segments of the content sealed in an SCC: the architected content (`sep` = 0) and the optional implementation-specific content (`sep` = 1); `sep` replaces bit 126 of the tag input and of every counter block; and
for `sep` = 0, bit 47 of `MDH` (the first block of the associated data), i.e.,
the unauthenticated _ADSDropped_ bit of the MDH (<<KLE-Auxiliary-Data-Section>>), is cleared before `POLYVAL` is evaluated.

The Key Derivation (<<KLE-SCC-key-derivation>>) and POLYVAL (<<KLE-SCC-POLYVAL>>) functions are defined first, then SCC generation from a locker (<<KLE-SCC-export>>) and SCC import into a locker (<<KLE-SCC-import>>).

In the pseudocode, `AESE256(K, B)` denotes the AES-256 encryption of the 128-bit block `B` under the 256-bit key `K` (FIPS 197 cite:[nist-fips-197]).

[[KLE-SCC-key-derivation]]
.RFC 8452 Key Derivation
[]
----
function SCC_KeyDeriv(key : bits(256), nonce : bits(96))
    → struct{enc_key : bits(256), auth_key : bits(128)} =
{
  local A : array [0..5] of bits(128);
  local i : int;

  foreach(i from 0 to 5) do:
    A[i] ← AESE256(key, nonce @ bin(i,32));

  return struct { enc_key  = A[5][63:0] @ A[4][63:0] @ A[3][63:0] @ A[2][63:0],
                  auth_key = A[1][63:0] @ A[0][63:0] }
}
----

// NOTE: Since key derivation is costly, implementations may cache the derived keys.

[[KLE-SCC-POLYVAL]]
.POLYVAL Hashing Function
[]
----
function POLYVAL(auth_key : bits(128), blocks[] : array of bits(128), n : int)
    → bits(128) =
{
  local tmp : bits(128) ← zeros(128);
  local i : int;

  foreach(i from 0 to n-1) do:
    tmp ← tmp xor blocks[i];
    tmp ← Montmul(tmp, auth_key);

  return tmp;
}
----

POLYVAL uses Montgomery multiplication, `Montmul(a, b)`, in the field F = GF(2)[`x`] modulo `x^128^ + x^127^ + x^126^ + x^121^ + 1`.
A 128-bit value `V` represents the element whose coefficient of `x^k^` is `V[k]`;
byte order and bit order both run forward, as in
cite:[RFC8452] {sect}3, under which `x^0^` is the byte string `0x01` followed by
fifteen zero bytes, i.e., the value `1`. Then: +
 +
`{fournbsp}{fournbsp}` `Montmul(a, b)` = `a` {interpunct} `b` {interpunct} `x^-128^` `{nbsp}{nbsp}` in the field F.

The SCC encryption and decryption functions, <<KLE-SCC-GCM-SIV-enc>> and <<KLE-SCC-GCM-SIV-dec>>, use this notation:

* `AD[]` denotes the Associated Data as an array of `len_AD` 128-bit blocks, that is
  `AD[0] {vvert} AD[1] {vvert} {ellipsis} {vvert} AD[len_AD-1]`, in that order;
* `P[]`, resp. `C[]`, denotes a Plaintext, resp. a Ciphertext, as arrays of `len_PC`
  128-bit blocks, that is `P[0] {vvert} P[1] {vvert} {ellipsis} {vvert} P[len_PC-1]`,
  resp. `C[0] {vvert} C[1] {vvert} {ellipsis} {vvert} C[len_PC-1]`, in that order;
* `K` is a 256-bit Key;
* `N` is a 96-bit Nonce; and
* `SIV` is a 128-bit SIV/tag.

//

[[KLE-SCC-GCM-SIV-enc]]
.AES-GCM-SIV Encryption for SCC Generation
[]
----
function SCC_Encrypt(AD[] : array of bits(128), N : bits(96), sep: bits(1),
    P[] : array of bits(128), K : bits(256), len_AD : int, len_PC : int)
  → {SIV : bits(128), C[] : array of bits(128)} =
{
  local AD_auth : array [0..len_AD-1] of bits(128) ← AD[];
  local keys : struct{enc_key : bits(256), auth_key : bits(128)};
  local i : int;

  keys ← SCC_KeyDeriv(K,N);
  if (sep = 0) then:
    AD_auth[0][47] ← 0;
  SIV ← POLYVAL(keys.auth_key, AD_auth[] ‖ P[], len_AD + len_PC);
  SIV[95:0] ← SIV[95:0] xor N;
  SIV ← AESE256(keys.enc_key, zeros(1) @ sep @ SIV[125:0]);

  foreach(i from 0 to len_PC - 1) do:
    C[i] ← P[i] xor AESE256(keys.enc_key,
             ones(1) @ sep @ SIV[125:32]
               @ bin((int(SIV[31:0]) + i) mod 2**32, 32));

  return ( SIV, C[] );
}
----

`len_PC` never exceeds `max_admissible` / 16 (<<KLE-serialized-image>>), and `len_AD` never exceeds 7.

[[KLE-SCC-GCM-SIV-dec]]
.AES-GCM-SIV Decryption for SCC Import
[]
----
function SCC_Decrypt(AD[] : array of bits(128), N : bits(96), sep: bits(1),
    SIV : bits(128), C[] : array of bits(128), K : bits(256),
    len_AD : int, len_PC : int)
  → {correct : bool, P[] : array of bits(128)} =
{
  local AD_auth : array [0..len_AD-1] of bits(128) ← AD[];
  local keys : struct{enc_key : bits(256), auth_key : bits(128)};
  local s, tmp : bits(128);
  local i : int;

  keys ← SCC_KeyDeriv(K,N);
  if (sep = 0) then:
    AD_auth[0][47] ← 0;

  foreach(i from 0 to len_PC - 1) do:
    P[i] ← C[i] xor AESE256(keys.enc_key,
             ones(1) @ sep @ SIV[125:32]
               @ bin((int(SIV[31:0]) + i) mod 2**32, 32));

  s ← POLYVAL(keys.auth_key, AD_auth[] ‖ P[], len_AD + len_PC);
  tmp ← s;
  tmp[95:0] ← tmp[95:0] xor N;
  tmp ← AESE256(keys.enc_key, zeros(1) @ sep @ tmp[125:0]);

  if (tmp ≠ SIV) then:
    foreach(i from 0 to len_PC - 1) do:
      P[i] ← zeros(128);
    return ( false, P[] );

  return ( true, P[] );
}
----

The comparison `tmp {ne} SIV` is performed in constant time.
It is strongly recommended that `SCC_KeyDeriv`, `SCC_Encrypt` and `SCC_Decrypt` also take a time, and make memory accesses, independent of the CSK, the derived keys, the Locality Secrets and the plaintext, as the KLF paths are recommended to (<<KLE-KLF>>).

[[KLE-SCC-export]]
==== Generation of an SCC from a Fully Configured Locker

A locker ``K(i)`` in a Valid State is fully provisioned, and opening it for export creates the serialized, encrypted and authenticated SCC by the steps below.

The Locality substitution rules of <<KLE-Localities>> apply: `LST_eff[j]` is the value of `LST` entry _j_ after substitution, and replaces `LST[j]` in the export and import algorithms.
An unconfigured entry (<<KLE-Localities>>) with no configured substitute makes the Metadata invalid at provisioning or import, and makes the export-opening `kl.mgmt` of a locker in a Valid State perform no operation (Rule <<Zkl-software.adoc#KLE-SR-locality-unconfigure>>). Entry 9 of `LST` is `hkllocality`, and entry 10 is `skllocality`.

After `kl.clearads`, a fully configured locker has _AuxDataLen_ = 0 and _ADSDropped_ = 0 (<<KLE-instruction-clearads>>); KLE sets _ADSDropped_ = 1 only in an SCC-shaped PCCC, to preserve an interrupted import after `Content2` was dropped (<<KLE-management-formats-and-states>>).

.Exporting a Fully Configured Locker ``K(i)``
--
* Step 1: Read the MDH with `kl.getmd`; if it is in an Error State, use the method of <<KLE-error-state-transfer>> instead.
* Step 2: Store the MDH at offset 0 of the SCC buffer, in the byte order of <<KLE-Notation-endianness>>.
* The export-opening `kl.mgmt Kd/KLNL, #kl_cfg_exporting` performs Steps 3 and 4:
[start=3]
. Process the architected content:
.. `saved_MDH` <- ``K(i).MDH``, ``len_AD`` <- 1
.. ``K(i).MDH``._State_ <- `kl_cfg_exporting`
.. ``AD[0]`` <- `saved_MDH` (no need to mask _ADSDropped_: it is zero in a fully configured locker).
.. foreach(_j_ from 0 to 10) do:
... If `saved_MDH`._Locality_ names Locality #j (<<KLE-locality-indexes>>), then
.... ``AD[len_AD]`` <-  ``LST_eff[``_j_``]``, ``len_AD`` <- ``len_AD`` + 1
.. `len_PC` <- the number of 128-bit blocks of `Content1`.
.. `SIV`, `Content1~CT~[]` <- +
`{fournbsp}{fournbsp}SCC_Encrypt(AD, zeros(96), 0, K(i).Content1~PT~[], CSK, len_AD, len_PC)`
. If _AuxDataLen_ {ge} 2, process the implementation-specific content:
.. `len_AD2` <- 2, +
``AD2[0]`` <- `IMPQUAL` <- the `IMPQUAL` of the implementation (<<KLE-Auxiliary-Data-Section>>), formed from the values of `mklvendorid`, `mklarchid` and `mklimpid` out of KLE unit reset, ``AD2[1]`` <- `SIV`.
.. `len_PC2` <- _AuxDataLen_ − 2, the number of 128-bit blocks of `Content2`.
.. `SIV2`, `Content2~CT~[]` <- +
`{fournbsp}{fournbsp}SCC_Encrypt(AD2, zeros(96), 1, K(i).Content2~PT~[], CSK, len_AD2, len_PC2)`
* A loop of `kl.store` or `kl.mvout` instructions saves the serialized image `S` (<<KLE-serialized-image>>) at offset 16 of the SCC buffer:
[start=5]
. If _AuxDataLen_ = 0, `S` = `SIV` {vvert} `Content1~CT~`.
. Otherwise, `S` = `SIV` {vvert} `IMPQUAL` {vvert} `SIV2` {vvert} `Content1~CT~` {vvert} `Content2~CT~`, where `Content2~CT~` may be empty.
. Store `S` to memory.
* The completing `kl.mgmt` restores the locker as <<KLE-mgmt-completes-export>> specifies.
--

[NOTE]
====
An export completed prematurely fails authentication at import (<<KLE-SCC-import>>) with overwhelming probability, and an import completed prematurely fails it at once; an operation left incomplete keeps the locker in a Configuration State, in which most instructions fail.
====

[[KLE-SCC-import]]
==== Decryption and Authentication of a Complete SCC into a Locker

The following algorithm imports the SCC of a fully configured locker.
For an SCC whose MDH is in an Error State, use the method of <<KLE-error-state-transfer>>.

.Importing a Fully Configured Locker ``K(i)``
--
* Step 1: Read `M`, the MDH of the SCC, from memory, in the byte order of <<KLE-Notation-endianness>>.
* The import-opening `kl.mgmt Kd/KLNL, #kl_cfg_importing, Vs/Xs`, with `M` in `Vs` or `Xs`, performs the following Steps:
[start=2]
. Clear and deallocate ``K(i)``, and zeroize `SIV`, `IMPQUAL` and `SIV2`.
. Make the opening checks of <<KLE-MVR-open>> on `M`, stopping with their outcome if one fails.
. ``K(i)``.MDH <- `M`, with ``K(i)``.MDH._ADSDropped_ <- 1 if `M`._Version_ is not 3, `M`._AuxDataLen_ {ge} 2, and either `M`._ADSDropped_ = 1 or `M`._AuxDataLen_ exceeds the implementation's maximum for the Machine, and <- 0 otherwise.
. Determine the SCC layout from ``K(i)``.MDH.
// This changes only the length of `Content2`: when _AuxDataLen_ {ge} 2, `IMPQUAL` and `SIV2` remain present and _ContentOffset_ remains 48. The opening `kl.mgmt` then
. Set the appropriate Configuration State according to <<KLE-MVR-open>>.
* A loop around `kl.load`/`kl.mvin` instructions performs the following step:
[start=7]
. Load the rest of the SCC from its offset 16, to the length that the working MDH gives: with _ADSDropped_ = 1, `SIV`, `IMPQUAL`, `SIV2` and `Content1`, but no `Content2`.
* The completing `kl.mgmt` decrypts and authenticates the SCC and makes it available to software:
[start=8]
. `saved_MDH` <- the MDH image held in ``K(i)``, that is `M` with the working _ADSDropped_ and its _State_ field restored from the auxiliary operand of the completing `kl.mgmt`.
. ``AD[0]`` <- `saved_MDH`, ``len_AD`` <- 1. `SCC_Decrypt` clears _ADSDropped_ in its local copy of `AD[0]` before authenticating it; the MDH held in ``K(i)`` is unchanged by that computation.
. foreach (`j` from 0 to 10) do:
.. If `saved_MDH`._Locality_ names Locality #j (<<KLE-locality-indexes>>), then ``AD[len_AD]`` <-  ``LST_eff[j]``, ``len_AD`` <- ``len_AD`` + 1
. `len_PC` <- the number of 128-bit blocks of `Content1`.
. `correct`, ``K(i)``.`Content1` <- +
`SCC_Decrypt(AD, zeros(96), 0, SIV, K(i).Content1, CSK, len_AD, len_PC)`.
. If `correct` {ne} `true`, the SCC is rejected: ``K(i)`` transitions to Error State `kl_stateext_mgmt_auth` (_Authentication Failed_, Rule <<KLE-GR-clear-locker-content-error-state>>), and the remaining steps are skipped.
. If ``K(i)``.MDH._AuxDataLen_ {ge} 2 and ``K(i)``.MDH._ADSDropped_ = 0, process the implementation-specific content:
.. `len_AD2` <- 2, ``AD2[0]`` <- ``K(i)``.`IMPQUAL`, ``AD2[1]`` <- `SIV`.
.. If ``K(i)``.`IMPQUAL` = the `IMPQUAL` of the implementation (<<KLE-Auxiliary-Data-Section>>), formed from the values of `mklvendorid`, `mklarchid` and `mklimpid` out of KLE unit reset, then:
... `len_PC2` <- the number of 128-bit blocks of `Content2`, that is ``K(i)``.MDH._AuxDataLen_ − 2.
... `correct`, ``K(i)``.`Content2` <- `SCC_Decrypt(AD2, zeros(96), 1, SIV2, K(i).Content2, CSK, len_AD2, len_PC2)`.
.. else:
... `correct` <- `false`.
.. If `correct` {ne} `true`, then:
... drop `Content2` and set ``K(i)``.MDH._ADSDropped_ to 1.
. If ``K(i)``.MDH._AuxDataLen_ = 0 or ``K(i)``.MDH._ADSDropped_ = 1:
.. Zero the implementation-defined subfields of the MDH (<<KLE-MachineUse>>);
.. _ADSDropped_ <- 0; and
.. _AuxDataLen_ <- 0 (it may be set to at least 2 again if the implementation generates a replacement ADS right away).
// otherwise it keeps the ADS and sets _ADSDropped_ to 0. Either way, any restart that Rule <<KLE-GR-long-running-restart>> requires is made before the locker becomes Valid, and a later export emits the ADS that _AuxDataLen_ then describes.
--

==== Design Rationale for the Sealing Construction

_This section is informative and non-normative._

Omitting the nonce shrinks the payload and lets the derived keys be cached; the nonce-misuse resistance of AES-GCM-SIV keeps the construction secure for up to O(2^64^) blocks observed by an adversary.
On cloud servers, each virtual machine and supervisor domain should have its own CSK; M-mode firmware moves a CC between them by importing its SCC under the source CSK and exporting it under the target CSK.

The `SIV`, the GCM-SIV tag, is the encryption of the `POLYVAL` hash (<<KLE-SCC-POLYVAL>>) of the MDH with _ADSDropped_ cleared, the Locality Secrets and the Content. Including the Locality Secrets in the `SIV`, instead of deriving keys from them, binds the SCC to the Localities for one `Montmul` per block, far less than most KDFs, and keeps the keys cacheable, since a change of the set derives no new keys.
Distinct sets give the same `SIV` with probability at most max(`len_AD` + `len_PC`) {times} 2^-126^, the maximum taken over the two sets.
Taking `SIV` as ``AD2[1]`` makes `SIV2` and the second keystream depend on the first payload, so an ADS cannot be grafted onto another SCC.
As in AES-GCM-SIV, bit 127 separates tag inputs from keystream inputs; bit 126 separates the keystreams of the two segments, at the cost of one bit of security.

[[KLE-error-state-transfer]]
==== Export and Import of a Locker in an Error State

A locker in an Error State is only an MDH (Rule <<KLE-GR-clear-locker-content-error-state>>) and uses no KLF capacity.
Its import checks the MDH as any supplied MDH (<<KLE-Metadata-validity>>).
There is no Content to encrypt, and KLE does not authenticate the MDH: any software in the current environment can produce any Error State by issuing `kl.setste`, so authentication would prove nothing.
Neither direction produces an SCC or a PCCC, opens a management operation, uses `SIV`, `SIV2` or `IMPQUAL`, or takes part in resumption.

*Exporting* such a locker needs no `kl.mgmt`: `kl.getst` (<<KLE-instruction-getst>>) finds an Error State, and `kl.getmd` or `kl.getmdv` (<<KLE-instruction-getmd>>) reads the MDH, which software stores; `kl.size` reports 16.
A `kl.mgmt` with `#immed7` = `kl_cfg_exporting` on such a locker is permitted but useless: it leaves the locker unchanged and opens no management operation, and only its common steps take effect, `klnamedlocker` naming the locker and `klstart` becoming 0 (<<KLE-locker-management>>).

*Importing* the image takes one uninterruptible `kl.mgmt` with `#immed7` = `kl_cfg_importing` and the 16-byte MDH as the auxiliary operand, carried whole by Form C or D.
It zeroizes the locker that it names; if the MDH is invalid Metadata (<<KLE-Metadata-validity>>), it transitions the locker to Error State _Invalid_, as any import does; otherwise the MDH is installed as is, with only _AuxDataLen_ and _ADSDropped_ set to 0 (Rule <<KLE-GR-clear-locker-content-error-state>>), and nothing else is transferred.
A `kl.mgmt` with `#immed7` = `kl_cfg_management_end` is not needed after it, and performs no operation (Rule <<KLE-GR-outcome-inert>>).

[[KLE-CSK-requirements]]
== Architectural Requirements on the Context Sealing Key

The KLE unit operates only with an active Context Sealing Key (CSK): with a hardwired CSK it is available from reset, otherwise once the CSK is established.
Without an active CSK, every KLE instruction and KLE CSR access raises a KLE missing-CSK exception, except writes to the `mklcsk` group and accesses to the Locality Secret CSR groups (<<Zkl-ISA-priv.adoc#KLE-CSR-locality-groups>>), which are configured independently of the CSK.

Each hart holds a CSK, established in exactly one of four ways:

. M-mode programs it through the `mklcsk` CSR group (<<Zkl-ISA-priv.adoc#KLE-CSR-mklcsk>>); M-mode can then read it in clear, and no software can read it in any other way.
. A secure hardware block exclusive to M-mode, such as Caliptra cite:[caliptra], or a port to one, configures it through a dedicated interface based on public-key encryption, at the request of M-mode only, by a handle or a wrapped key; addressing and key transport are platform-specific and outside the scope of this specification.
. It is hardwired at manufacturing time and cannot be reconfigured or revoked.
. A secure RBG (<<KLE-Prerequisites>>) generates it at boot.
  All harts of a subsystem of an SoC that the platform defines and documents hold the same such CSK, so that processes can migrate among them, and cannot exchange SCCs with other subsystems; the CSK survives the reset or fatal condition of a single hart and is regenerated only at the power-on reset of the subsystem, so the SCCs sealed under it cannot be imported after a power loss.

The third and fourth ways suit mainly specialized embedded deployments.
Harts among which processes or CCs migrate must hold the same CSK: under the first and second ways, M-mode establishes it on each.
A hart reset or a KLE fatal condition (<<KLE-error-architecture>>) resets the hart's KLE state (<<KLE-reset-and-m-mode-only>>) and, under the first and second ways only, its CSK, which must then be established again.

NOTE: When the CSK is shared across devices, CCs meant to be device-bound need to name _ChipScrt_ or _DevScrt_ in their _Locality_.

Persistence of a configurable CSK is implementation-specific.
Transferring a CSK to another endpoint, such as the M-mode firmware of another device, a local TPM (for instance across suspension or host hibernation), or a cloud-based HSM, requires an authenticated public-key wrapping mechanism, which this specification does not define.

[[KLE-reset-and-m-mode-only]]
== KLE Unit Reset and M-mode-only Harts

A _KLE unit reset_ of a hart resets that hart's KLE architectural state (<<KLE-out-of-reset-unpriv>>, <<Zkl-ISA-priv.adoc#KLE-out-of-reset-priv>>); in a KLE unit shared by several harts, it affects only that hart's state, shared Locality Secrets excepted.
A hart reset implies a KLE unit reset of that hart, and so does a fatal condition (<<KLE-error-architecture>>), with the differences of <<Zkl-ISA-priv.adoc#KLE-out-of-reset-priv>>.
A KLE unit reset of a hart also unconfigures a CSK established under the first or second way (<<KLE-CSK-requirements>>), and affects neither a hardwired CSK nor a boot-generated one, which it neither clears nor regenerates.

A non-retentive hart suspend is not a hart reset: whether the KLE state of the hart (lockers, KLIOBUF, CSRs and authentication registers) is retained across it is implementation-defined, and retention is strongly recommended.
An implementation documents whether and how it retains that state; software that cannot rely on retention exports its lockers before the suspend (<<Zkl-software.adoc#KLE-state-save-and-restore-order>>).

On an M-mode-only hart, every software-programmable Locality Secret whose CSR group is not implemented is unconfigured (<<KLE-Localities>>), and, where the KLE Privileged Architecture is not implemented, `KLS` is treated as Initial; <<Zkl-ISA-priv.adoc#KLE-priv>> states which of its CSRs may exist on such a hart.
