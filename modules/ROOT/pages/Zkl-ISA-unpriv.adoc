[[KLE-unpriv-intro]]
== Introduction

KLE lets software perform high-performance cryptographic operations without direct access to the keys or other critical derived values.
KLE achieves this feature through the concepts explained next.

[[KLE-concepts]]
=== Foundational Principles and Definitions

Principles are labeled P__n__, where __n__ is a progressive number.

[horizontal]
[[KLE-ISA-Principle-hidden-keys,P1]]P1:: _KLE allows software to use keys that are hidden from it._
[[KLE-ISA-Principle-key-binding,P2]]P2:: _KLE associates each key with an algorithm, and with policies that limit its use to certain privilege modes and bind it to software and hardware environments_.
[[KLE-ISA-Principle-prefix-complete,P3]]P3:: _Every cryptographic operation is atomic. +
(f an instruction performs multiple cryptographic operations, it must be prefix-complete.)_
[[KLE-ISA-Principle-multiple-algorithms,P4]]P4:: _Multiple keys can be in use at the same time, and their algorithms composed_.

//

These four Principles prompt the definition of a _Cryptographic Context_:

Definition: _Cryptographic Context_::
(((Cryptographic Context)))
Most KLE instructions run within the constraints set by a *Cryptographic Context* (CC).
A CC is an indivisible structure consisting of a *Metadata Header* (MDH), with a fixed format and length, and a *Content*, whose size depends on the MDH.
(((Cryptographic Context, Content)))
The Content holds the secrets, usually keys, and other sensitive material.
(((Cryptographic Context, Metadata Header)))
The MDH binds the use of the secrets in the Content to one set of cryptographic algorithms, and, optionally, to a process, VM, security state, boot cycle, expiration date, or other policies.
The MDH requires integrity (except for hint bits); the Content requires integrity and confidentiality.
KLE and the algorithms it implements enforce these requirements architecturally.

[horizontal]
[[KLE-ISA-Principle-contexts-stateful,P5]]P5:: _Cryptographic Contexts are stateful, and record and manage the progress of the algorithm._

Multiple CCs can be active at the same time, a caller must be able to configure them as they need.
This requires an architectural place for them.

[horizontal]
[[KLE-ISA-Principle-management-architectural,P6]]P6:: _Resource management is architectural: resources are managed by software, and their exhaustion is reported by the architecture so that software can take the necessary actions_.

//

KLE applies this Principle by defining Cryptographic Lockers.

Definition: _Cryptographic Locker_::
(((Cryptographic Locker)))
CCs are created in *Cryptographic Lockers* (_lockers_ for short), per-hart architectural containers that safeguard their contents.
*Provisioning* a locker writes Metadata and Content into it and binds them into a CC.
A CC is usable only while in a locker, where only the KLE unit accesses or modifies it, under the rules of the architecture and its Machine; no instruction extracts the Content in a way that compromises its confidentiality.

//

A KLE implementation offers support for multiple lockers (in fact, 32).

[horizontal]
[[KLE-ISA-Principle-scalable,P7]]P7:: _KLE is scalable: it works on small and larger cores, with and without vector registers._
[[KLE-ISA-Principle-small-instructions-code,P8]]P8:: _Instructions are as simple as possible, in accord with common RISC-V philosophy, and despite this code sequences must be kept short._
[[KLE-ISA-Principle-encoding-pressure,P9]]P9:: _Minimize the pressure on the instruction encoding space._

//

Embedding the encoding of the algorithm in the MDH is the main mechanism to implement <<KLE-ISA-Principle-encoding-pressure>>.

[horizontal]
[[KLE-ISA-Principle-small-architectural-state,P10]]P10:: _Architectural state beyond the lockers is minimal, and exists once per hart._

Algorithms are implemented by KLE Machines:

Definition: _KLE Machine_::
(((Machines)))
(((Cryptographic Context, object-oriented)))
A *KLE Machine* (short: _Machine_) is a state machine that implements one or more cryptographic functions (primitives, modes, protocols) through the interface of this specification.
It is identified by fields in the MDH.
A small set of KLE instructions operates all Machines: their inputs and outputs come from vector registers, GPRs, and memory, and their semantics depend on the Machine.
Encapsulating Machine-specific behavior in the MDH rather than the instructions lets different primitives (e.g., AES-128, AES-256 and SM4) be used in the same modes (e.g., ECB, GCM-SIV and XTS) without changing the compiled code, and supports side-channel-resistant variants transparently.

[horizontal]
[[KLE-ISA-Principle-no-misuse,P11]]P11:: _A Machine admits only the sequences of operations that its specification defines._
[[KLE-ISA-Principle-cia-inside,P12]]P12:: _Inside a locker, a CC is accessed only through its Machine and the instructions managing it._
[[KLE-ISA-Principle-availability,P13]]P13:: _Software can always configure a new CC._
[[KLE-ISA-Principle-persistence,P14]]P14:: _A CC can be saved and restored, also into a different locker or on an different implementation, in order to support features such as context switching, sleep, hibernation, VM migration._
[[KLE-ISA-Principle-confidentiality-integrity,P15]]P15:: _Outside a locker, a CC is sealed: it reveals nothing, and cannot be altered undetected._

The mechanism for saving and restoring CCs is the generation of Sealed Cryptographic Contexts:

Definition: _Sealed Cryptographic Context_::
(((Cryptographic Context, sealed)))
For context switching, a CC can be *exported* from a locker as a *Sealed Cryptographic Context* (SCC), an encrypted and authenticated representation that can later be *imported* into a locker. Export and import use a _Context Sealing Key_ (CSK), which M-mode may be able to program. An SCC sealed under one CSK cannot be imported under another, which separates spatial and temporal domains cryptographically.

[horizontal]
[[KLE-ISA-Principle-no-privilege-elevation,P16]]P16:: _No operation yields a key or widens a policy: secrets flow only downhill._

<<KLE-ISA-Principle-no-privilege-elevation>> is the same principle behind NIST's key-management recommendations on the associations of a key with its usage and related information (NIST SP 800-57 Part 1 Rev. 5 cite:[nist-SP-800-57-p1-r5], §§6.2.1.4 and 6.2.1.6) and on the cryptographic strength, separation and context binding of derived keys (NIST SP 800-108 Rev. 1, Update 1 cite:[nist-SP-800-108-r1], "Security Considerations").

Finally, as a consequence of Principle <<KLE-ISA-Principle-key-binding>>, KLE instructions are subdivided into classes which can only be used in various contexts. Instructions that use the secrets in CCs are bounded by usage policies, whereas those that, for instance, save and restore SCCs can be used anytime. Principles <<KLE-ISA-Principle-availability>> and <<KLE-ISA-Principle-persistence>> exist to prevent denial of service on the resources of the KLE implementation.

Definition: _Instruction Classes and Usage Control_::
+
--
(((Cryptographic Context, usage control)))
(((Cryptographic Context, management operations)))
(((Cryptographic Context, usage operations)))
KLE distinguishes between *management* operations and *usage* operations on CCs and lockers.
(((Cryptographic Context, export)))
Management operations perform

* *configuration* (e.g., *provisioning* and SCC *import*),
* *export* of a locker as an SCC, and
* *clearing* a locker, i.e., freeing it, deleting any secret it contains.

Management operations, while they may be destroying the contents of lockers, do not use their contents, nor do they modify any cryptographic information in them, including any that may affect how this information is used.
Usage operations are cryptographic operations and state changes.
To prevent denial of service, management operations are less restricted than usage operations: _Usage Control_ policies restrict only usage operations.
--

Definition: _Localities_::
(((Cryptographic Context, Locality)))
KLE can bind a CC to *Localities*, which restrict where its exported SCCs can be imported, and thus where it can be restored and used: specific devices or device classes, hardware configurations, physical or virtual boot cycles, and process domains at various privilege modes.
// The Localities act as _tweaks_ in the encryption and decryption of SCCs.

The entire architecture follows from these Principles and Definitions.

// [horizontal]
// [[KLE-ISA-Decision-metadata,D1]]D1:: One fixed-size Metadata Header alone says what a locker is, what it admits and how large it is (<<KLE-ISA-Principle-management-architectural>>, <<KLE-ISA-Principle-encoding-pressure>>, <<KLE-ISA-Principle-small-architectural-state>>).
// [[KLE-ISA-Decision-machine-protocol,D2]]D2:: Every Machine follows one protocol: `kl.setst` names the next State, and `kl.exec` performs its operation (<<KLE-ISA-Principle-contexts-stateful>>, <<KLE-ISA-Principle-encoding-pressure>>).
// [[KLE-ISA-Decision-error-architecture,D3]]D3:: Each CC records its own errors (<<KLE-ISA-Principle-multiple-algorithms>>, <<KLE-ISA-Principle-persistence>>):
// [[KLE-ISA-Decision-error-states,D3(a)]]D3(a)::: as an Error State of its locker;
// [[KLE-ISA-Decision-exceptions,D3(b)]]D3(b)::: with an exception only where falling through would misreport the error (<<KLE-ISA-Principle-no-privilege-elevation>>).
// [[KLE-ISA-Decision-instruction-outcome,D4]]D4:: The outcome of an instruction depends only on the State group of its locker and on its class (<<KLE-ISA-Principle-availability>>, <<KLE-ISA-Principle-prefix-complete>>):
// [[KLE-ISA-Decision-misuse,D4(a)]]D4(a)::: misuse invalidates a Valid locker (<<KLE-ISA-Principle-no-misuse>>);
// [[KLE-ISA-Decision-fall-through,D4(b)]]D4(b)::: on an inert locker, instructions fall through, so that one check at the end of a sequence suffices (<<KLE-ISA-Principle-small-instructions-code>>).
// [[KLE-ISA-Decision-management-protocol,D5]]D5:: A management operation runs from an opening to a completing `kl.mgmt`, the locker being in a Configuration State in between (<<KLE-ISA-Principle-availability>>, <<KLE-ISA-Principle-prefix-complete>>).
// [[KLE-ISA-Decision-named-locker,D6]]D6:: `klnamedlocker` names the locker of the CC in transit, so management routines need no locker number (<<KLE-ISA-Principle-small-instructions-code>>, <<KLE-ISA-Principle-small-architectural-state>>).
// [[KLE-ISA-Decision-resumption,D7]]D7:: `klstart` records the prefix-complete point of an interrupted instruction, and a long-running operation keeps its progress in its locker (<<KLE-ISA-Principle-persistence>>, <<KLE-ISA-Principle-prefix-complete>>).
// [[KLE-ISA-Decision-derivation,D8]]D8:: `kl.derive` moves material between lockers inside the unit, so combined algorithms expose no key (<<KLE-ISA-Principle-multiple-algorithms>>, <<KLE-ISA-Principle-no-privilege-elevation>>).
// [[KLE-ISA-Decision-attached-unit,D9]]D9:: KLE instructions are messages to an attached unit that alone accesses the lockers (<<KLE-ISA-Principle-scalable>>, <<KLE-ISA-Principle-no-privilege-elevation>>, <<KLE-ISA-Principle-cia-inside>>):
// [[KLE-ISA-Decision-invisible-asynchrony,D9(a)]]D9(a)::: its asynchrony is invisible to the hart (<<KLE-ISA-Principle-cia-inside>>);
// [[KLE-ISA-Decision-riscv-operands,D9(b)]]D9(b)::: its operands follow the RISC-V conventions (<<KLE-ISA-Principle-scalable>>, <<KLE-ISA-Principle-small-instructions-code>>).

[[KLE-architectural-model]]
=== Architectural Model

KLE is architected as an interface to an _attached_ unit: its instructions are messages over a tightly coupled coprocessor interface, and the KLE unit executes them independently of the issuing hart and returns the results.

This keeps the hart side simple: software implements the locker-configuration logic, the KLE unit the cryptography, and several cores may share one KLE unit.

The specification defines only architectural behavior, not implementation: KLE may be integrated into a CPU core or be a distinct hardware unit; either way each client hart has separate KLE architectural state, and the same code runs on both.

KLE may be emulated, partly or completely, in M-mode firmware: an implementation may, for example, perform symmetric operations (<<Zkl-ISA-machines.adoc#KLE-states-symmetric>>) in the KLE unit and emulate public-key cryptography (<<Zkl-ISA-machines.adoc#KLE-ECC>>, <<Zkl-ISA-machines.adoc#KLE-PQC>>), whose very large states then reside in secure memory that meets the requirements of <<KLE-KLF>>, such as on-chip SRAM reserved to M-mode.

Locker state must never be accessible in the clear to any privileged mode except M-mode and authenticated Debug mode.
The only locker state exported in the clear is the `Content` of a partial provisioning, which software has itself supplied (<<KLE-data-formats>>).
KLE implementations in S/VS-mode or HS-mode are therefore forbidden: instructions and Machines may be emulated only in M-mode.
Trap-and-emulate and on-demand (lazy) SCC import rely on the ``*llockerstatus`` CSRs (<<Zkl-ISA-priv.adoc#KLE-CSR-llockerstatus>>).

// ////////////////////////////////////////////////////////////////////

[[KLE-Prerequisites]]
=== Prerequisites

A conformant KLE implementation requires the RISC-V External Debug Security extension cite:[riscvExternalDebugSecurity].

It also requires the KLE exceptions of <<Zkl-ISA-priv.adoc#KLE-exceptions>> to be implemented and raised as the unprivileged architecture mandates, whether or not the other parts of the KLE Privileged Architecture are implemented.

Where the KLE unit or its Machines need an RBG, it must use an entropy source that meets the requirements of the `Zkr` specification cite:[RISCV-ISA-Unpriv], used to seed a DRBG compliant with NIST SP 800-90A cite:[nist-SP-800-90-r1] or an equivalent standard.
Rule <<KLE-GR-rbg-failure>> covers RBG failure.

[[KLE-extensions-overview-unpriv]]
== Extensions Overview

KLE comprises several sub-extensions. Those that define ISA features follow; those that define cryptographic algorithms are listed in <<Zkl-ISA-machines.adoc#KLE-exec-encodings>>.

.Extensions defining KLE ISA features
[,%header,cols="<18%,<64%,<18%"]
|===
| Extension       | Features                                                                | Defined in:
| `Zklv`          | Support for vector registers.                                           | <<KLE-instructions-detailed>>
| `Zklio`         | Support for streaming instructions and the KLIOBUF input/output buffer. | <<KLE-KLIOBUF>>, <<KLE-usage-input-output>>
| `Zklmem`        | Dedicated memory instructions.                                          | <<KLE-instruction-load>>, <<KLE-instruction-store>>
| `Zklmv`         | Dedicated move instructions.                                            | <<KLE-instruction-mv>>
| `Zklexpire`     | Support for the _ExpirationDate_ metadata field.                        | <<KLE-Metadata-expiration-date>>
|===

`Zkl` conformance requires:

. at least one of `Zklv` and `Zklio`;
. AES-128, -192 and -256 in ECB and GCM modes, AES-128 and -256 in GCM-SIV mode, and SHA2-224, -256, -384, -512, -512/224 and -512/256,
as defined in <<Zkl-ISA-machines.adoc#KLE-Machines>>; and
. `Zklmem`, in hardware or by trap-and-emulate (<<KLE-error-architecture>>).

KLE instructions may raise the standard RISC-V exceptions and a few KLE-specific exception types, listed in <<Zkl-ISA-priv.adoc#KLE-exception-codes>>.

With trap-and-emulate, the hardware raises an illegal-instruction exception for instructions it does not implement, which the platform must deliver to M-mode (`medeleg` bit 2 zero); the encodings are assigned, not reserved (<<KLE-illegal-instruction-grounds>>).
`Zklmv` must then be in hardware, since the emulating code moves data between memory and the locker with it.
`kl.load` and `kl.store` are thus always present; `Zklmv` and `Zklexpire` are otherwise optional.

`Zklv` requires the KLV subset of the vector extension (<<KLE-KLV>>) with `VLEN` {ge} 128, that is `Zvl128b` or a larger `Zvl*b`, on which every vector Form that carries an MDH or a 128-bit block depends.

The principal KLE instructions, defined in full below, are:

* `kl.mgmt` (<<KLE-instruction-mgmt>>) moves a locker through its management lifecycle, and,
with the KLE memory operations `kl.load` (<<KLE-instruction-load>>), `kl.store` (<<KLE-instruction-store>>), `kl.mvin` and `kl.mvout` (<<KLE-instruction-mv>>),
performs the management operations (<<KLE-management-operations>>):
 ** *provisioning* loads metadata and clear Content into a locker, binding them;
 ** *export* writes a locker to memory as an SCC;
 ** *import* loads an SCC into a locker; and
 ** each takes several instructions, except on a locker in an Error State (<<KLE-error-state-transfer>>).
* `kl.clear` (<<KLE-instruction-clear>>) unconfigures and clears a locker. It is a pseudo-instruction of `kl.setst`, and never part of a management operation.
* `kl.exec` (<<KLE-instruction-exec>>) performs the cryptographic operations that the Machine configured in a locker defines for the locker's current state.
* `kl.setst` (<<KLE-instruction-setst>>) moves the CC in a locker between the states of its Machine.
* `kl.getmd*` (<<KLE-instruction-getmd>>) reads the metadata of a locker. The pseudo-instruction `kl.getst` (<<KLE-instruction-getst>>), built on `kl.getmdl`, extracts the state of a locker from its MDH, and thus also reports errors.

== Inputs and Outputs

[[KLE-cryptographic-registers]]
=== Cryptographic Lockers

{empty}
(((Cryptographic Context)))
KLE defines 32 Cryptographic Lockers, `K0`–`K31`.
Like GPRs or vector registers, lockers are per-hart architectural state, not separated by privilege mode: a hart sees the same lockers in every mode.
Unlike a conventional register, a locker can be _unconfigured_; that is, it holds no CC.

A locker is addressed like a conventional register, by a 5-bit immediate.
Some instructions may also name the named locker, written `KLNL` (Rule <<KLE-GR-klnamedlocker-override>>).

The CC in a configured locker consists of a Metadata Header (MDH) and `Content` (<<KLE-concepts>>).
The _i_-th locker is denoted `K(i)`, its MDH `K(i).MDH`, and its content `K(i).Content`.
During import and export, and in an SCC, the content consists of two consecutive arrays of 128-bit blocks:
`Content1`, the architected content that <<Zkl-ISA-machines.adoc#KLE-Machines>> specifies for each Machine,
and `Content2`, any implementation-specific content.

[[KLE-KLF]]
=== The Cryptographic Locker File and Authentication Information

(((Cryptographic Locker File)))Lockers reside in a per-hart _cryptographic locker file_ (KLF), a memory that only the KLE implementation can access.
Where the implementation is emulated, in part or in full, only M-mode firmware accesses it, through an implementation-defined mechanism that must be provided by the implementation.

The KLF guarantees the confidentiality and integrity of its contents, also against rollback through any access this specification does not permit.
Its accesses need no hardening against physical side channels, except in side-channel-protected implementations of the Machines.
It is strongly recommended that every path that handles a locker's secrets (reconstruction, re-sharing, KLF access, `SCC_KeyDeriv`, `SCC_Encrypt`, `SCC_Decrypt`, and every use of the CSK and its derived keys) resist side-channel and fault-injection attacks as well as the locker's Machine at its _SCProtection_ level (<<KLE-SCProtection-field>>), and that a path serving several Machines do so at the highest level among them.

NOTE: The KLF resists rollback, but individual lockers need not, and cannot, resist it through export and import.
Re-importing an earlier CC state may enable multi-time-pad attacks on modes such as CTR, XCTR and GCM (Rule <<Zkl-ISA-machines.adoc#KLE-nonce-reuse>>), but exploiting them needs control of the target software, which usually exposes the plaintext anyway; and re-import has legitimate uses, such as restarting an operation whose payload was corrupted in transit, that policies could hardly all cover.

Architecturally, the KLF holds two distinct parts, whatever the implementation:

. an array of 32 128-bit blocks, whose _i_-th entry holds the MDH of `K(i)`, so that every locker holds its MDH, if only to show that it is unconfigured; and
. an implementation-defined amount of memory, allocated dynamically, which holds the `Content` of every configured locker.

"`KLF capacity`" refers only to the second part: a locker that holds only its MDH consumes none, and the capacity a locker consumes depends on its MDH (<<KLE-length-rule>>).
Insufficient capacity may prevent a configuration instruction from executing; unconfiguring other lockers frees capacity.

Corruption of a hart's KLF is unrecoverable: it resets the hart's KLE architectural state (<<KLE-reset-and-m-mode-only>>) and raises a KLE fatal-error exception (<<Zkl-ISA-priv.adoc#KLE-exceptions>>).

The KLE unit holds three 128-bit _authentication registers_, `SIV`, `IMPQUAL` and `SIV2`, with the authentication and identification data of the locker under management; `kl.load`, `kl.store`, `kl.mvin` and `kl.mvout` access them as the leading bytes of the image (<<KLE-instruction-mv>>).
The export-opening `kl.mgmt` of a Valid locker writes `SIV`, and `IMPQUAL` and `SIV2` when _AuxDataLen_ {ge} 2.
An import-opening `kl.mgmt`, other than the short import of an Error-State locker (<<KLE-error-state-transfer>>), zeroizes them before the `kl.load` or `kl.mvin` that writes them, so that no value of an earlier management operation can be read back through the import image.

NOTE: The authentication registers exist once per hart, not per locker, to reduce hardware cost, so a second management operation may overwrite those of the first while it is in flight; <<KLE-CSR-klnamedlocker>>, <<KLE-named-locker-rules>> and <<KLE-SR-management>> explain how software handles multiple management operations.

[[KLE-KLV]]
=== RVV/KLV

KLE takes its inputs and outputs from vector registers, from an architectural input/output buffer (KLIOBUF) loaded from and stored to memory, or from both.

(((KLV)))Vector registers do not require the full V extension, only a minimal subset, _KLV_ (KLE-subset of V).
KLV must be fully opcode-compatible with RVV: code written for KLV behaves identically under V with `Zvbc`.
KLV comprises:

* vector registers of at least 128 bits;
* the configuration-setting instructions `vsetvli`, `vsetivli` and `vsetvl`, with:
** tail-agnostic and mask-agnostic configurations only, since KLE neither uses vector masking nor defines masked instructions, and always applies a tail-agnostic policy (bit 25 of the `kl.exec` encoding is reserved for masked operations, should a compelling use case arise);
** `SEW` values 8, 16, 32 and 64, with `ELEN` = 64;
** `LMUL` values 1, 2, 4 and 8; and
** for a configuration that KLV does not support, `vtype.vill` is set and `vl` = 0, as in RVV, and a KLE instruction with a vector operand issued while `vtype.vill` is set raises an illegal-instruction exception;
* unit-stride vector loads and stores of element widths 8, 16, 32 and 64;
* `vmv.x.s`, `vmv.s.x`, and the slides `vslideup.v[xi]`, `vslidedown.v[xi]`, `vslide1up.vx` and `vslide1down.vx`, to move data into and out of vector registers;
* the logical operations `vand.v[vxi]`, `vor.v[vxi]` and `vxor.v[vxi]` (the immediate forms give, for instance, a bitwise NOT); and
* `vclmul.v[vx]` and `vclmulh.v[vx]` of `Zvbc`, which may be trap-and-emulated.

Floating-point, fixed-point and general arithmetic vector operations are not required.

NOTE: KLE has no concept of element, and logically does not operate in the vector unit: it sees a vector register (group) as a bit string of length `KLLEN` = `VL` * `SEW`, where `VL` is the vector length in effect (`vl`).

KLE takes the length of a vector operand from `VL*SEW` alone (`VL` = 2 with `SEW` = 64 and `VL` = 4 with `SEW` = 32, for example, both give 128 bits): the CPU decode side uses `VL` and `SEW` to determine how much data to send to the KLE unit, which needs only their product.

[[KLE-KLIOBUF]]
=== KLIOBUF

When the extension `Zklio` is in effect, an optional architectural input/output buffer, the KLIOBUF, may replace vector registers; like the lockers, it is per-hart architectural state, not separated by privilege mode, but it is not part of the KLF.

The `Zklio` instructions `kl.input` and `kl.output` transfer data between the KLIOBUF and memory, and the base extension `kl.exec`, `kl.setst` and `kl.mgmt` then use Forms whose inputs and outputs are implicitly in the KLIOBUF (<<KLE-usage-input-output>>).
<<KLE-CSR-kliobuftop>> defines `KLLEN` for KLIOBUF operands.

[[KLE-Metadata]]
== Metadata

A CC carries two kinds of metadata:

. the 128-bit _MDH_, always present, which determines the Machine, the key type and the key's usage policies; its first 64 bits determine the length of a PI or SCC; and
. the optional 128-bit _Implementation Qualifier_ `IMPQUAL`, which copies the three KLE analogues of the hart's `mvendorid`, `marchid` and `mimpid` CSRs (<<KLE-CSR-impl-ids>>).
It is present when an SCC has _AuxDataLen_ {ge} 2, and tells an implementation whether it can use the implementation-specific content of the SCC (<<KLE-Auxiliary-Data-Section>>).

In the rest of the document, "medatata" refers to the first type. The implementation qualifier is always deferred as `IMPQUAL`.

<<KLE-metadata-header>> summarizes the MDH fields, which the following subsections describe.

[[KLE-metadata-header]]
.Format of the 128-bit Metadata Header

[[KLE-Machine-field]]
=== _Machine_ and _MachinePolicy_ Fields

_Machine_ is a 12-bit field. Values 0–3071 are architecture-defined, with encodings maintained by RVI (<<Zkl-ISA-machines.adoc#KLE-Machines>>); the remaining values are for custom Machines.

The meaning of _MachinePolicy_ depends on the Machine:

* For encryption/decryption primitives and modes, bit 0 of _MachinePolicy_ permits encryption and bit 1 decryption. At least one bit must be set.
* For asymmetric primitives that support signatures, bit 0 permits signature generation and bit 1 verification. For a Machine with other operations as well, a zero field leaves those operations available.
* For other primitives, _MachinePolicy_ may encode further Machine identifiers, extending the encoding space of _Machine_.

For a Machine that only signs and verifies, a zero _MachinePolicy_ disables all the locker's operations but is not invalid.
Rule <<Zkl-ISA-machines.adoc#KLE-MGR-policy-gate>> states how _MachinePolicy_ gates the States of a Machine.

// ////////////////////////////////////////////////////////////////////

[[KLE-SCProtection-field]]
=== _SCProtection_ Field

KLE defines three side-channel protection levels, Levels A, B and C, encoded in _SCProtection_ as the values 0, 1 and 2.
Value 3 is reserved, and makes the Metadata invalid (<<KLE-Metadata-validity>>).
cite:[riscvPlatformSecurityModel] defines the security concepts and requirements.

[[KLE-SC-protection-levels]]
.Encoding of Side-Channel Protection levels
[float="center",align="center",cols="^7%,^7%,<86%",options="header"]
|===
| Value  | Level | Description
|   0    | A     | No timing leakage: the same cryptographic operation on the same number of input units takes the same time in the KLE unit, whatever the input data.
|   1    | B     | No timing leakage; differential side-channel protection.
|   2    | C     | No timing leakage; side-channel protection;
detection of injected faults, followed either by completion with the correct result and no other physical leakage, or by
a transition to a fatal error condition (see <<KLE-error-architecture>>).
|===

A level applies to the operations that need it for security, such as signature generation but not signature verification, and only as far as the cryptographic method of the Machine needs it: the execution time of ML-DSA, for instance, may depend on the number of iterations of its rejection loops (<<Zkl-ISA-machines.adoc#KLE-PQC-ML-DSA>>).

An implementation documents, for each level it supports, the standard and edition, assessment profile, security level and test metrics it meets, such as acquisition-time limits and trace sample sizes; Level B, resp. C, must offer at least the guarantees documented for Level A, resp. B.

[NOTE]
====
This specification gives no assurance profiles for these levels. Relevant references are ISO/IEC 19790:2025 cite:[ISOIEC-19790-2025] for the security requirements of cryptographic modules, ISO/IEC 24759:2025 cite:[ISOIEC-24759-2025] for their testing, ISO/IEC 17825:2024 cite:[ISOIEC-17825-2024] for testing the mitigation of non-invasive attacks, and FIPS 140-3 cite:[nist-fips-140-3], which adopts ISO/IEC 19790:2012 and ISO/IEC 24759:2017 with CMVP modifications; NIST SP 800-140F (March 2020) cite:[nist-SP-800-140F], where the CMVP lists approved non-invasive test metrics, currently specifies none.
Acquisition-time limits and trace sample sizes measure the effort of a test, not how long an attack is resisted; nor does a FIPS level number state such a duration, or make an assessment equivalent to one under the later ISO/IEC editions.

A CC provider that sends its keys to a secure receiver, such as a TEE applet that forwards the CC to the software consuming it, negotiates the protection level and its assessment profile with it by a system-specific mechanism.
====

[[KLE-KeyType-field]]
=== _KeyType_ Field

_KeyType_ is 0 for a key provisioned by value, and 1 for a key identified by a system-specific, 64-bit System Key Identifier (SKID) (<<KLE-system-keys>>).
A _KeyType_ 0 key is also exported and imported by value.
_KeyType_ is 2 for keys that the non-nested provisioning-completing `kl.mgmt` generates randomly, all keys of the Machine at once unless the Machine specifies otherwise: the PI has the layout of one with _KeyType_ = 0, whose key values are replaced, and _KeyType_ becomes 0, so the keys are then exported by value; an RBG failure follows Rule <<KLE-GR-rbg-failure>>.
_KeyType_ = 2 thus occurs only in a PI and in a PCCC of base type `pi`.
_KeyType_ Value 3 is reserved: a PI or SCC that carries it is invalid Metadata (<<KLE-Metadata-validity>>).

NOTE: A SKID may refer to keys with unrelated purposes on different devices;
the _System Key Store_ (SKS) supplies an appropriate _Locality_ (<<KLE-Localities>>) during provisioning, to bind the key to the system (<<KLE-system-keys>>).

[[KLE-State-field]]
=== _State_ and _StateExtension_ Fields

_State_ tracks the state of a locker and its Machine: _Unconfigured_, encrypting or decrypting, initializing, absorbing into or finalizing a hash, computing point multiples, signing or verifying, or in an error state, for instance.
_StateExtension_ lets a Machine keep further state information, usually orthogonal to _State_, such as whether certain values have been provisioned or computed.

State 0 is _Unconfigured_: every other field of the MDH then reads zero and has no meaning, and the locker has no Usage Policy, Expiration Date or Key Type.

States 1–55 are the _Complete_ States: the _Valid_ States 1–47, State 1 being _Ready_, and
(((KLE, Machine, error states)))
the _Error States_ 48–55, which report KLE errors.

(((KLE, Machine, configuration states)))States 56–63, used during management operations, are the _Configuration States_, exactly the States that are neither _Unconfigured_ nor Complete; 61–63 are reserved (<<KLE-SC-sealing-status>>).

[[KLE-Auxiliary-Data-Section]]
=== _AuxDataLen_ and _ADSDropped_ Fields

_AuxDataLen_ gives the length, in 128-bit blocks, of the _Auxiliary Data Section_ (ADS), the variable-size, implementation-specific part of the content; with _ADSDropped_ = 1, it keeps the length before `Content2` was dropped.
Zero means no ADS; the maximum, 2^14^-1, is 262,128 bytes.

If _AuxDataLen_ {ge} 2, the SCC includes a copy of the implementation qualifier of the originating implementation (<<KLE-CSR-impl-ids>>),

``{fournbsp}{fournbsp}IMPQUAL := zeros(32) @ klmimpid @ klmarchid @ klmvendorid``,

which the importing implementation uses to decide whether it can use the ADS.
_AuxDataLen_ counts these 16 bytes and the 16-byte authentication tag of the ADS, so its minimum is 2, and 1 is invalid.

_ADSDropped_, bit 47 of the MDH, is an unauthenticated format hint, ignored when _AuxDataLen_ = 0; first-segment authentication clears it only in its local copy of the MDH.
With _AuxDataLen_ {ge} 2 and _ADSDropped_ = 1, `Content2` is absent, and `IMPQUAL` and `SIV2` remain as non-authoritative padding that keeps the offset of `Content1` unchanged.
Setting _ADSDropped_ drops the optional `Content2`; clearing it requests second-segment processing, whose failure drops `Content2` without rejecting the authenticated `Content1` (<<KLE-SCC-import>>).
Setting it also makes the import zero the implementation-defined subfields of _MachineUse_ and _AuxInfo_ (<<KLE-MachineUse>>).
Toggling it therefore cannot affect `Content1` or any policy, make an unauthenticated `Content2` usable, or bypass first-segment authentication; dropping `Content2` can at most make an interrupted long-running operation restart (Rule <<KLE-GR-long-running-restart>>).

// The format of the ADS is described in <<KLE-data-formats>>.

[[KLE-UsagePolicy]]
=== _UsagePolicy_ Field

_UsagePolicy_ determines which modes may use the locker.
A _usage instruction_ uses the Machine in a locker to operate on the locker's internal state, or to expose it, as a `kl.exec` that produces output does; Usage Control applies only to these instructions, listed in <<KLE-instruction-properties>>.
Bits 0–3, when set, disallow usage in U-mode (VU-mode included), VS-mode, S-mode (HS-mode with the H extension) and M-mode, respectively; bit 4, when set, grants usage in Debug mode.
`mstatus.MPRV` is not considered, and the bit of a mode that is unsupported or not enabled is ignored.

[[KLE-Localities]]
=== _Locality_ Field

_Locality_ names 128-bit Locality Secrets (LSs), listed in <<KLE-locality-indexes>> and stored in a possibly virtual Locality Secrets Table (LST).
Some entries are fixed, or configurable only by an implementation-specific, authenticated hardware process, and shared by all KLE units of an SoC; the others are software-programmable, per-hart architectural state.

At SCC export and import, the Localities named in _Locality_ cryptographically bind the SCC to the _current_ hardware and software environments.
The binding ends at import: if a Locality Secret changes later, the next export binds its SCC to the new value.
Software must prevent unauthorized parties from accessing the lockers directly (Rule <<KLE-SR-clear-before-lower-mode>>).

Eleven LST entries are architected: entries 0–5 form the _HW Binding Group_, which binds SCCs to the hardware; entries 6–7 the _Boot Session Group_; and entries 8–10 the _SW Filter Group_.

[[KLE-Metadata-expiration-date]]
=== _ExpirationDate_ Field

_ExpirationDate_ is in effect only with `Zklexpire`, which requires the KLE implementation to access a secure clock.
Without `Zklexpire`, a non-zero _ExpirationDate_ in a PI or SCC is invalid Metadata (<<KLE-Metadata-validity>>).

A non-zero 20-bit _ExpirationDate_ gives the expiration time of the CC in whole hours since 00:00 UTC, 1 January 2027, a span of about 119 years and 7 months: the same instant on every device, whatever its time zone.
Software below M-mode must not be able to set the clock.

[NOTE]
====
The assurance of the clock, like that of the _SCProtection_ levels (<<KLE-SCProtection-field>>), is set by security standards and platform profiles, not by this specification.
It is *strongly recommended* that a platform with `Zklexpire` document its clock, and that the clock:

* map to UTC with a documented resolution, maximum error and drift, which a boot-relative counter alone does not;
* keep advancing, or be trustworthily resynchronized, across suspension, reset, power loss and the restore of a saved platform or VM state;
* be protected against unauthorized setting, rollback and stoppage, or detect them; and
* report itself unavailable, never as zero or a pre-epoch date, while its UTC mapping, progress or error bounds cannot be trusted, until a trusted recovery.
====

_ExpirationDate_ is evaluated only:

* at the issue of any usage instruction, for `kl.derive` at both endpoints; and
* when a usage instruction resumes after a halt, but not between the blocks or component operations of one execution.

Each execution reads the clock once, before any component operation, and a passed check covers the rest of it, even if the date passes meanwhile.
An unavailable clock on resumption leaves the prefix committed before the halt in place (Rule <<KLE-exception-state-change>>).

The _ExpirationDate_ of a locker that is not in a Valid State is not evaluated: only an expired locker in active use transitions to Error State `kl_state_expired`, and expired contexts can still be managed cleanly.

The evaluation proceeds as follows:

. If _ExpirationDate_ is zero, the instruction proceeds.
. If the secure clock cannot be read, the instruction raises a KLE clock-unavailable exception (<<Zkl-ISA-priv.adoc#KLE-exception-codes>>) and leaves the _State_ unchanged.
. The secure clock's date is converted to the _ExpirationDate_ format, in whole hours rounded down; a reading before the epoch converts to 0, and one at or after 2^20^ − 1 hours converts to 2^20^ − 1.
. If the converted value is at least _ExpirationDate_, the locker transitions to Error State `kl_state_expired`; otherwise the instruction proceeds.

An unreadable secure clock traps, rather than making the instruction a silent no-op, so that M-mode can handle the failure, which may also be induced by glitching the clock.
The instruction keeps the _State_, so that a handler that restores the clock can re-execute it; otherwise Rule <<KLE-SR-handler-duty>> applies, with _Expired_ as the Error State.

[[KLE-MachineUse]]
=== _MachineUse_ and _AuxInfo_ Fields

A Machine may use _MachineUse_ and _AuxInfo_ to store additional information.

An implementation may use a field, or a subfield, that its Machine does not use: each Machine specification identifies the bits it defines, and the others, including progress in an implementation-defined format (Rule <<KLE-GR-long-running-progress>>), are _implementation-defined_.
Their values are disposable: ignoring them preserves the architected semantics, policies and parameters of the Machine, at the cost of a restart at most.
An implementation includes an ADS (<<KLE-Auxiliary-Data-Section>>) in every SCC it exports with such a value: _AuxDataLen_ {ge} 2, and exactly 2 when `Content2` is empty.
An import interprets them only if both segments authenticate, even with an empty `Content2`, and the authenticated `IMPQUAL` matches the importing implementation.
If the ADS is absent or discarded instead, _ADSDropped_ = 1 included, the import zeroes them after first-segment authentication, which covers them as received, and before the locker becomes Valid; the Machine then proceeds from the architected fields alone, restarting as Rule <<KLE-GR-long-running-restart>> requires.
`kl.clearads` zeroes them in the same way in a resident locker, so that `kl.getmd*` and a later export observe zeros; later computation may set new values, but never restore the discarded ones.

Neither field may hold any value from which key material or plaintext can be derived, since the MDH is not confidential.

The validity conditions of <<KLE-Metadata-validity>> do not check these fields, not even in a PI: a wrong value causes an error of the Machine that uses it, and a Machine specification may declare a value unsupported Metadata where the implementation does not implement it. A discarded implementation-defined value causes no such error.
The _MachineUse_ of a PI is ignored and zeroed upon provisioning (<<KLE-Metadata-validity>>). Otherwise, the rules of the Machine decide what happens to _AuxInfo_ upon provisioning, and to both fields on entering State _Ready_.
A Machine may use these fields to pass initialization parameters at provisioning: EdDSA (<<Zkl-ISA-machines.adoc#KLE-EdDSA>>), for instance, records in _AuxInfo_ the modes a CC may use.

[[KLE-Machine-version]]
=== _Version_ Field

_Version_ gives the version of the MDH format:

* 0: the current format;
* 1: newer revisions of the format, whose further version information is encoded in other MDH fields;
* 2: reserved; and
* 3: a system-specific format.

A PI or SCC with a _Version_ that the implementation does not support is invalid Metadata (<<KLE-Metadata-validity>>).

System-specific formats are optional and allowed only for import.
The import opens with a KLE-format MDH whose _Version_ is 3, and whose policies apply as in any other import.
The format may carry further policies, which apply in addition to those of the declared MDH, never in their place: at completion, the MDH of the locker is the declared MDH narrowed by the policies the format carries (<<KLE-Metadata-narrowing>>), with _Version_ set to 0 (or 1 in a future version of this specification); if the narrowing fails, the locker transitions to Error State _Privilege Violation_.
How a format encodes its policies, and how the implementation converts them into KLE policies, is implementation-defined; the converted policies are never weaker than those the format carries.
The format of the data that follows the KLE-format MDH defines whether, and how, that input data is protected: this specification does not require a system-specific format to be encrypted or authenticated, since some systems import encrypted keys without authenticating them.

Lockers provisioned with a system-specific format can be exported only in the KLE format, as SCCs.
An implementation may support several system-specific formats and distinguishes them in an implementation-defined way.

KLE deliberately defines no system-specific export.
To prevent loading on other implementations, specific Localities may be set, or all information may be kept in the ADS, gated by `IMPQUAL`.

[[KLE-Metadata-validity]]
=== Validity of Metadata

Software keeps all _reserved_ bits, and all bits that the Machine does not use, zero. A non-zero value is handled as follows:

* in a Reserved bit, it makes the Metadata invalid (see below);
* in _MachinePolicy_ or _MachineExtension_, a value that the implementation does not implement for the Machine makes it unsupported;
* the _StateExtension_ and _MachineUse_ of a PI are ignored, and zeroed upon provisioning (<<KLE-locker-management>>);
* outside a PI, a _State_ {vvert} _StateExtension_ value that the Machine does not support makes it invalid (see below); and
* otherwise, _MachineUse_ and _AuxInfo_ are not checked by the conditions below, but by the rules of the Machine and by their use in the implementation (<<KLE-MachineUse>>).

Metadata is _unsupported_ when the combination of _Machine_, _MachinePolicy_, _MachineExtension_ and an _SCProtection_ value of 0 to 2 (Levels A to C) is not implemented; when _KeyType_ is 1, resp. 2, and the implementation does not support System Key Identifiers, resp. random key generation, for the Machine (<<KLE-KeyType-field>>, <<KLE-system-keys>>); or when it holds a value that a Machine specification declares unsupported if not implemented, such as the _AuxInfo_ of EdDSA (<<Zkl-ISA-machines.adoc#KLE-EdDSA>>). A _MachinePolicy_ that the conditions below reject makes it invalid, not unsupported.

A supplied MDH is _invalid_ when any of the following holds:

* _Version_ is unsupported;
* _KeyType_ is 1 or 2 for a Machine whose Provisioning Input has no key field, for instance the unkeyed hash functions and XOFs, the ECC, ML-KEM and ML-DSA Machines, and the NIK variants of HMAC;
* _KeyType_ is 3, or 2 outside a PI and a PCCC of base type `pi`;
* _SCProtection_ is 3, a reserved value (<<KLE-SCProtection-field>>);
* _Locality_[5:4] is 3, or _Locality_ names an unconfigured Locality Secret without a configured substitute (<<KLE-Localities>>);
* the MDH carries a custom _Machine_ or a system-specific _Version_ without naming _ChipFamScrt_ or _ChipScrt_ in _Locality_ (Rule <<KLE-GR-custom-locality>>);
* _State_ is not _Unconfigured_ at provisioning;
* _State_ is _Unconfigured_ or 61–63 at import (<<KLE-State-management>>);
* _State_ is 54 or 55, or _State_ {vvert} _StateExtension_ is a value that the Machine does not support; for this condition, every Machine supports the Configuration States 56–60 with any _StateExtension_, and the _StateExtension_ in a PI is ignored and zeroed upon provisioning;
* _State_ is _Expired_ in a PI, SCC or PCCC when `Zklexpire` is not implemented;
* _ExpirationDate_ is non-zero and `Zklexpire` is not implemented;
* _AuxDataLen_ = 1;
* _AuxDataLen_ or _ADSDropped_ is non-zero in a PI, or in a PCCC with base type `pi` (<<KLE-nested-mgmt>>);
* _MachinePolicy_ is zero for a Machine that requires at least one set bit in it; or
* a Reserved bit is non-zero.

[[KLE-Metadata-narrowing]]
=== Narrowing of Metadata

Several operations narrow the policies of a CC by those of another source, all in the same way: the resolution of a SKID (<<KLE-system-keys>>),
a restricted `kl.derive` (Rule <<KLE-GR-narrowing>>), the import of a system-specific format (<<KLE-Machine-version>>),
and `kl.restrict*`, at the request of software (<<KLE-instruction-restrict>>).

The _narrowing_ of an MDH _A_ by the policies of a source _B_ (an MDH, the
policies that the SKS associates with a key, or those that a system-specific format carries) is _A_ with the following
fields replaced; a policy field that _B_ does not carry leaves that field of _A_ unchanged, and no other field changes:

* _UsagePolicy_: bits 0–3 become the OR of both, and bit 4 the AND of both, so that the modes that may use the CC are those that both allow.
* _Locality_ (<<KLE-locality-indexes>>): each HW Binding subfield (bits [1:0] and [3:2]) takes the larger value, that is the stricter entry of its chain, zero meaning no binding; the Boot Session subfield (bits [5:4]) takes the non-zero value if only one is non-zero; and bits 6–8 are OR-ed.
* _ExpirationDate_, with `Zklexpire`: the smaller non-zero value, or 0 if both are 0.

If both Boot Session subfields are non-zero and differ, or if the resulting _Locality_ names an unconfigured entry without a configured substitute (<<KLE-Localities>>), the policies cannot be met, and the narrowing _fails_; each operation that narrows states the outcome.
Narrowing changes neither _SCProtection_ nor _MachinePolicy_; only `kl.restrictl` and `kl.restrictv` narrow _MachinePolicy_, under Rule <<KLE-GR-policy-narrowing-state>>.

[[KLE-CSR-impl-ids]]
=== klmvendorid, klmarchid, and klmimpid

{empty}
(((CSR, `klmvendorid`)))(((CSR, `klmarchid`)))(((CSR, `klmimpid`)))`klmvendorid`, `klmarchid` and `klmimpid` identify the version of the KLE unit, as `mvendorid`, `marchid` and `mimpid` do for the hart.

[[KLE-CSR-klmaxiobuflen]]
=== klmaxiobuflen

(((CSR, `klmaxiobuflen`)))`klmaxiobuflen` is an XLEN-bit CSR that reports the maximum configurable length of the KLIOBUF, in bytes.
It is writable in the same modes and for the same purpose as the CSRs of <<KLE-CSR-impl-ids>>; its hardwired value out of KLE unit reset is its maximum.
M-mode should write it only while the KLE unit is in its state out of reset (<<KLE-out-of-reset-unpriv>>), before any write to `kliobuflen`, and should never reduce it below the current `kliobuflen`: after a write that does, `kliobuflen` and `kliobuftop` become 0 and the whole KLIOBUF is zeroized; no other state is affected.

With `Zklio`, `klmaxiobuflen` must be at least 16 bytes and at least the largest basic processing unit (granularity) of any implemented Machine.
Without `Zklio`, the KLIOBUF does not exist, `klmaxiobuflen` reads as zero, and `kliobuflen` and `kliobuftop` are not present.

// ////////////////////////////////////////////////////////////////////

[[KLE-CSR-kliobuflen]]
=== kliobuflen

(((CSR, `kliobuflen`)))`kliobuflen` is an XLEN-bit URW CSR that programs the length of the KLIOBUF, in bytes, for `kl.input` and `kl.output`; its maximum is `klmaxiobuflen`.
Every write, even of the current value, zeroes the buffer below the new length before it completes, and sets `kliobuftop` to that length.
Bytes beyond the new length need not be erased, since they stay inaccessible until a later write zeroes them: a write of zero makes the contents inaccessible without erasing them.

A zero `kliobuflen` leaves the KLIOBUF _unconfigured_: an operation that expects an input or an output in it raises an illegal-instruction exception (Rule <<KLE-GR-iobuf-configured>>).

Rule <<KLE-SR-kliobuflen-zero>> recommends writing 0 once the contents are no longer needed.

// ////////////////////////////////////////////////////////////////////

[[KLE-CSR-kliobuftop]]
=== kliobuftop

(((CSR, `kliobuftop`)))`kliobuftop` is an XLEN-bit URW CSR that sets the upper bound, in bytes, of the buffer range that `kl.input` and `kl.output` use; its maximum is `kliobuflen`.
It is the KLIOBUF counterpart of `VL` in the V extension: it defines the operand length `KLLEN` as `kliobuftop` {times} 8 and the transfer window [0, `kliobuftop`-1].

Writing `kliobuftop` leaves the buffer unchanged, so software can set the length per operation without writing `kliobuflen`, which clears the buffer; this mirrors the use of `VL*SEW` to supply a partial last block, or a short IV or nonce, to a Machine.

A value invalid for a Machine is detected only when an instruction that uses the KLIOBUF is later issued or restarted, with the outcomes given in <<KLE-usage-input-output>>.

// ////////////////////////////////////////////////////////////////////

[[KLE-CSR-klstart]]
=== klstart

(((CSR, `klstart`)))`klstart` is an XLEN-bit RW CSR that records, in bytes, the progress of the instructions that _honor_ it:

* `kl.load`, `kl.store`, `kl.input` and `kl.output`: the bytes read or written;
* `kl.exec` with a vector or KLIOBUF operand, which may be interrupted between blocks: the bytes processed;
* `kl.derive`, whose `kl.exec` endpoints advance the source and destination lockers in the same way; and
* `kl.mvin` and `kl.mvout`, vector or not: the locker transfer point.

KLE has no intrinsic element length and no counterpart of the Element Group Width (EGW), Effective Element Width (EEW) or Element Group Size (EGS) of the vector crypto extension; its instructions, such as `kl.exec`, are architecturally decoupled from the operations the KLE unit performs for them.
Hence `klstart` is a byte count; Machines or their implementations record progress that is not byte-structured, such as that of the point multiplications and signature operations of <<Zkl-ISA-machines.adoc#KLE-ECC>> and <<Zkl-ISA-machines.adoc#KLE-PQC>>, in _MachineUse_ (Rule <<KLE-GR-long-running-progress>>).

Like `vstart` in the V extension, `klstart` is the position within the _transfer window_ of `kl.exec` at which processing starts or resumes: bytes [0, `kliobuftop`-1] for a KLIOBUF operand, with `kliobuflen` non-zero, and [0, `VL` {times} `SEW`/8 - 1] for a vector operand.
The memory instructions and `kl.mvin` and `kl.mvout` define their own windows (<<KLE-iobuf-transfer-window>>, <<KLE-serialized-image>>).

Rule <<KLE-GR-klstart-updates>> lists the events that change `klstart`, Rules <<KLE-GR-interruption-point>> and <<KLE-GR-transfer-window-checks>> state how `kl.exec` checks it, and <<KLE-klstart-software-check>> states what software must do with it.

// ////////////////////////////////////////////////////////////////////

[[KLE-CSR-klnamedlocker]]
=== klnamedlocker

(((CSR, `klnamedlocker`)))`klnamedlocker` is an XLEN-bit RW CSR; only 6 of its bits are currently used.
It holds the number of the locker most recently placed under management, or 32 if none.
Completing a management operation, even with an error, keeps the number, so that software can inspect the outcome through `KLNL` before writing 32 or restoring a saved value (Rule <<KLE-SR-klnamedlocker-finish>>).
Values 33 and above are reserved; writing one leaves `klnamedlocker` unchanged.
While the locker it names is in a Configuration State, that locker is under management and owns the internal values `SIV`, `SIV2` and `IMPQUAL`.

Rule <<KLE-GR-klnamedlocker-updates>> lists the events that change `klnamedlocker`, Rules <<KLE-GR-locker-less-transfers>> to <<KLE-GR-mgmt-klnamedlocker-check>> state how instructions use it, and <<KLE-SR-management>> states what software must do with it.

[[KLE-instructions-detailed]]
== Instructions

_This section specifies only the semantics and encodings of the unprivileged KLE instructions, not their behavior in the various States of the Machines, how they respect usage policies, how they use randomness, how they access memory, or whether they are interruptible.
The rules governing these aspects are grouped in <<KLE-ISA-rules>>._

When describing an instruction's behavior requires a rule, the instruction's description states that behavior explicitly, with a reference to the rule.

[[KLE-no-operation]]Definition: _No Operation_::
(((no operation)))
An instruction that *performs no operation* performs none of the operations of the KLE unit, such as cryptographic operations, but may still have the effects that its description or a rule states, such as writing zeros to its output, writing 0 to `klstart`, setting `klnamedlocker`, or raising an exception.

[[KLE-general-rules-instructions]]
=== General Rules Governing Encoding and Arguments

In every encoding, fields shown with fixed values must hold them.
Any other value of such a field, and any unlisted combination of field values, is a reserved encoding and raises an illegal-instruction exception (first group of <<KLE-illegal-instruction-grounds>>).

`%offset` denotes the instruction's sign-extended 12-bit immediate: bits [31:20] for `kl.load` and `kl.input` (I-type), and bits [31:25] @ [11:7] for `kl.store` and `kl.output` (S-type).
The base register is always in bits [19:15] (`rs1`), and the effective address of a transfer is `X[rs1] + sext(%offset)`.
This is the address of the *first* byte of the transfer, even for a multi-byte or resumed transfer; a resumed transfer restarts at that address plus `klstart` bytes.
Each instruction gives the correspondence between addresses and transfer offsets.

The following rules apply to all KLE instructions, unless stated otherwise.

[horizontal]
[[KLE-GR-multiple-GPRs,GR1]]GR1:: _Use of multiple GPRs for longer inputs:_ A 64-bit operand is one GPR on RV64 and the pair `(X[s+1],X[s])`, as `X[s+1] @ X[s]`, on RV32.
A 128-bit operand is the pair `X[s+1] @ X[s]` on RV64 and the quartet `X[s+3] @ X[s+2] @ X[s+1] @ X[s]` on RV32.
This holds for sources and destinations alike.
The lowest register number of a pair must be even, and that of a quartet a multiple of four; otherwise an illegal-instruction exception is raised.
A pair or quartet is read or written as a whole.
Here and in every instruction description, RV32 and RV64 denote an XLEN of 32, resp. 64, in the privilege mode executing the instruction.

[[KLE-GR-x0-operand,GR2]]GR2:: If `X0` is used as a destination or source register, writes to it are discarded, and it reads as zero.
When the lowest register of a pair or quartet is `X0`, no register of the group is written, and the group reads as zero.

[[KLE-GR-r-R-fields,GR3]]GR3:: The encoding fields `r` and `R` serve only to name the named locker `KLNL` in place of a locker register field, which must then hold `X0`, where Rule <<KLE-GR-klnamedlocker-override>> admits it.
`r` = 1 applies to the single locker operand; in `kl.clone`, `kl.rename`, `kl.swap` and `kl.derive`, `R` = `01` applies to the first operand, the destination, and `R` = `10` to the second, the source.
`R` = `11`, and any other non-zero value of these fields, is reserved.

[[KLE-GR-vector-MDH-operand,GR4]]GR4:: Where a KLE instruction carries the whole 128-bit MDH in a vector register or group, such as the MDH-formatted operand of `kl.restrictv` and the destination of `kl.getmdv`, the operand must satisfy `VL` {times} `SEW` {ge} 128; otherwise an illegal-instruction exception is raised.
<<KLE-extensions-overview-unpriv>> lists the vector extensions that provide such a register.
The same requirement applies to an MDH taken from the KLIOBUF: `kliobuftop` {ge} 16.
`kl.mgmt` reads its MDH only where its operation needs one, which depends on the locker's _State_ (Rule <<KLE-GR-fall-through-mgmt>>), so for `kl.mgmt` this check is a ground of the second group (<<KLE-illegal-instruction-grounds>>), made after the `klnamedlocker` check and before any change to the locker.

[[KLE-GR-vector-legality,GR5]]GR5:: A vector register (group) operand whose register number is not a multiple of the LMUL in effect is a reserved encoding and raises an illegal-instruction exception, as in RVV 1.0.
Every KLE instruction with a vector operand sets `vstart` to 0 when it retires, and on a precise halt sets it as Rules <<KLE-GR-klstart-updates>> and <<KLE-GR-klstart-vstart>> prescribe.
An instruction with a vector operand that produces no `vstart` value (`kl.getmdv`, `kl.restrictv`, Form C of `kl.size` and `kl.avail`, `kl.setst` and `kl.mgmt`) raises an illegal-instruction exception if issued with `vstart` {ne} 0, as RVV 1.0 {sect}3.7 permits for a `vstart` value that the instruction can never produce.

[[KLE-GR-klstart-vstart,GR6]]GR6:: KLE instructions with vector operands that use `klstart` for resumption update `klstart` and `vstart` simultaneously and independently, each by its own semantics; except for `kl.mvin` and `kl.mvout`, both denote the same point of progress, `klstart` in bytes and `vstart` in elements of the width in effect.
Issuing a Form A–C `kl.exec` with `klstart` {ne} `vstart` {times} `SEW`/8 raises an illegal-instruction exception.
Each unit thus keeps its own information, and the two values can still be explicitly "`desynced`", as in locker management operations.
+
NOTE: `kl.mvin` and `kl.mvout` keep the two independent by design: their `klstart` is a locker offset that accumulates across instructions, while `vstart` tracks the vector register.
+
NOTE: The uninterruptible vector-form instructions listed in Rule <<KLE-GR-vector-legality>> produce no `vstart` value and therefore consume none.

[[KLE-management-operations]]
=== Provisioning, Import, and Export

_This section is informative and non-normative. It serves to place the management operations in their context._

Setting aside the handling of lockers in an Error State, a *management* operation takes three steps: the first and the last are a single KLE instruction each, and the second is one or more `kl.mvin` or `kl.mvout` (alternatively, `kl.load` or `kl.store`) instructions:

. An opening `kl.mgmt` (<<KLE-instruction-mgmt>>) prepares the locker for the management operation.
. One or more `kl.mvin` (<<KLE-instruction-mv>>) load the rest of the information into the locker, or one or more `kl.mvout` move the locker's information out.
. A completing `kl.mgmt` ends the management operation and makes the locker available to software.

// Setting error handling aside, *provisioning* consists of the following three steps:
//
// . `kl.mgmt` (<<KLE-instruction-mgmt>>) prepares the locker, checks the validity of the MDH, and loads the whole MDH into the locker.
// . One or more `kl.mvin` (<<KLE-instruction-mv>>) load the rest of the provisioning information.
// . `kl.mgmt` completes the provisioning and makes the locker available to software.
//
//
// *Importing* an SCC is similar:
//
// . `kl.mgmt` prepares the locker to accept an SCC, checks the validity of the MDH, and loads the whole MDH into the locker.
// . One or more `kl.mvin` load the rest of the SCC, authentication data first, into the locker.
// . `kl.mgmt` authenticates and decrypts the SCC, and makes the locker available to software.
//
// *Exporting* a locker as an SCC takes five steps:
//
// . `kl.getmd` or `kl.getmdv` (<<KLE-instruction-getmd>>) exports the MDH out of the locker, and `kl.size` (<<KLE-instruction-size>>) gives the size of the SCC, for which software allocates resources.
// . Software stores the MDH to memory.
// . `kl.mgmt` prepares the locker to produce an SCC, encrypting its contents and computing the authentication tag(s).
// . One or more `kl.mvout` move the rest of the SCC, authentication data first, out of the locker.
// . `kl.mgmt` completes the export and restores the locker to a form available to software.

// ////////////////////////////////////////////////////////////////////

[[KLE-instruction-size]]
=== kl.avail and kl.size

_Synopsis_::
`kl.avail` returns 1 if the Machine encoded in the MDH is available in the requested variant, and 0 otherwise.
`kl.size` returns the size in bytes of the memory buffer needed for the data of a PI or SCC, or 0 on error, such as an unsupported Machine or an invalid MDH.

_Mnemonic_::
+
--
`kl.avail` and `kl.size` have three Forms:
(((KLE, instruction, kl.size)))
(((KLE, instruction, kl.avail)))

[upperalpha]
. `kl.{avail,size}  Xd, Ks` - Size from a context.
. `kl.{avail,size}  Xd, Xs` - Size from MDH[63:0] in one (RV64) or two (RV32) GPRs.
. `kl.{avail,size}  Xd, Vs` - Size from MDH in one vector register.
--

_Encoding_::
+
--
The encoding shares the opcode, `funct3` and `funct2` (the two msbs of `funct7`) of `kl.exec`, with bit 27 set.
Bit 25, `q`, selects `kl.size` (`q` = 0) or `kl.avail` (`q` = 1).

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Xd' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'Ks/Xs/Vs' },
    { bits:  5, name: 0x0 },
    { bits:  1, name: 'q' },
    { bits:  1, name: 'r', attr: ['KLNL'] },
    { bits:  1, name: 0x1 },
    { bits:  2, name: 'F' },
    { bits:  2, name: 0x0, attr: ['funct2'] },
]}
....

Field `F` selects the Form:

* `F` = `0b00` {implies} Form A, from a context `Ks`.
* `F` = `0b01` {implies} Form B, from an MDH in one (RV64) or two (RV32) GPRs.
* `F` = `0b10` {implies} Form C, from an MDH in a 128-bit vector register.
--

_Description_:: {empty}
+
--
`kl.avail` (`q` = 1) examines only the _Machine_, _MachinePolicy_, _MachineExtension_, _KeyType_ and _SCProtection_ fields of the MDH, and writes 1 to `Xd` if that combination is implemented (no non-zero _MachineExtension_ is currently defined), and 0 otherwise.
A 1 therefore does not exclude a KLE unsupported-Metadata exception that a Machine specification attaches to the value of another field, such as the _AuxInfo_ of EdDSA.
In Form A, an _Unconfigured_ locker yields 0 whatever these fields hold.

`kl.size` (`q` = 0) writes to `Xd` the size in bytes of the memory buffer needed for the external image that the MDH describes: a PI, an SCC, or, for a locker in an Error State, the MDH alone (<<KLE-data-formats>>, <<KLE-length-rule>>).
For an SCC the size includes the authentication tag(s) and the ADS; for a PI it covers the entire PI.

The Forms differ only in the source of the MDH: the locker itself (Form A), bits [63:0] in `Xs`, or in `X[s+1] @ Xs` on RV32 (Form B), or bits [127:0] in `Vs` (Form C).
In Form A, `Ks` may be `KLNL` (Rule <<KLE-GR-klnamedlocker-override>>).

Let `content1_size` be the length in bytes of the `Content1` of an SCC for the _Machine_, _MachinePolicy_, _KeyType_ and _StateExtension_ of the MDH, and `pi_content_size` the length in bytes of the `Content` of a PI for its _Machine_, _MachinePolicy_ and _KeyType_ (<<KLE-length-rule>>); the two are not interchangeable.
Let `content2_size` be 16 * (_AuxDataLen_ - 2) if _AuxDataLen_ {ge} 2 and _ADSDropped_ = 0, and 0 otherwise.

Form B examines only bits [63:0]: no field in bits [127:64] affects the size of any structure (<<KLE-length-rule>>), so the invalidity and unsupported-Metadata conditions on those fields, including Rule <<KLE-GR-custom-locality>> and the _AuxInfo_ of a Machine, are not applied.

`kl.size` returns:

. Form A: 0 if the locker is _Unconfigured_;
. Forms B and C: 0 if the supplied MDH is not in an Error State and is unsupported or invalid Metadata (<<KLE-Metadata-validity>>), or its _State_ is 61–63; validity is evaluated as at provisioning when the supplied _State_ is _Unconfigured_, and as at import otherwise.
. 16 if MDH._State_ is an Error State;
. if MDH._State_ is a Valid State or `kl_cfg_{importing|exporting}`:
  .. 32 + `content1_size` if _AuxDataLen_ = 0;
  .. 64 + `content1_size` + `content2_size` if _AuxDataLen_ {ge} 2, the 64-byte fixed part including `IMPQUAL` and `SIV2` even when _ADSDropped_ = 1;
. 16 + `pi_content_size` if MDH._State_ is `kl_cfg_provisioning`, `kl_cfg_ppi_importing`, or `kl_cfg_ppi_exporting`, or, for a supplied MDH, _Unconfigured_ (the MDH of a PI).
--

[[KLE-instruction-exec]]
=== kl.exec

_Synopsis_::
Perform a cryptographic operation in the KLE unit.

_Mnemonic_::
+
--
`kl.exec` has four Forms:
(((KLE, instruction, kl.exec)))

[upperalpha]
. `kl.exec  Vd, Kn, Vs2` {nbsp} reads an input vector and writes an output vector.
. `kl.exec  {fournbsp} Kn, Vs2` {nbsp} reads an input vector and writes no output vector.
. `kl.exec  Vd, Kn {fournbsp}{nbsp}` {nbsp} reads no input vector and writes an output vector.
. `kl.exec  {fournbsp} Kn {fournbsp}{nbsp}` {nbsp} reads no input vector and writes no output vector.
--

_Encoding_::
`kl.exec` is an R-type instruction.
+
--
[wavedrom, , svg]
....

{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'rd', attr: ['Vd','—','Vd','—'] },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: "'rs1' (n)", attr: ['Kn'] },
    { bits:  5, name: 'rs2', attr: ['Vs2','Vs2','—','—'] },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'r', attr: ['KLNL'] },
    { bits:  1, name: 0x0 },
    { bits:  2, name: 'Form', attr: ['0    0','0    1','1    0','1    1'] },
    { bits:  2, name: 0x0, attr: ['funct2'] },
]}
....

The encodings of Forms A–D are:

[upperalpha]
. `Form` = `0b00`.
. `Form` = `0b01` and `rd` = `0b00000`.
. `Form` = `0b10` and `rs2` = `0b00000`.
. `Form` = `0b11` and `rd` = `rs2` = `0b00000`.

The locker operand is always in `rs1`.
An unused register field (`rd` without an output vector, `rs2` without an input vector) must be zero, except in the encodings that `Zklmv` assigns (<<KLE-instruction-mv>>); other non-zero values in it are reserved.
--

_Description_::
+
--
Performs the cryptographic operation that the Machine in locker `Kn` defines, possibly taking an input and producing an output; `Kn` may be `KLNL` (Rule <<KLE-GR-klnamedlocker-override>>).
When it performs no operation (on an _Unconfigured_, Error-State or expired locker) or transitions the locker to an Error State, it zeroes the unwritten part of its output window instead of producing output (Rule <<KLE-GR-zero-unwritten-output>>).

In Form A, each output block has the length of its input block and is written at the same window offset, so `Vd` and `Vs2` may always be the same register group, each block's output replacing its input; any other overlap is reserved.

NOTE: A future version of this specification may define the semantics of _expanding_ or _narrowing_ multi-block `kl.exec` operations, whose output blocks are longer, resp. shorter, than their input blocks. No current Machine defines such operations.

Without `Zklv`, only Form D is supported: Forms A–C raise an illegal-instruction exception, and `kl.input` and `kl.output` supply the inputs of `kl.exec` and extract its outputs (<<KLE-usage-input-output>>).
--

[[KLE-instruction-mv]]
=== kl.mvin and kl.mvout

The `Zklmv` subextension adds dedicated move instructions between scalar/vector registers and a locker.
The instructions in this extension are encoded as new forms of `kl.exec`.

_Synopsis_::
  Move content between scalar/vector registers or the KLIOBUF and the locker under management, which is in a Configuration State.

_Mnemonics_::
+
--
`kl.mvin` and `kl.mvout` are one instruction with six variants:
(((KLE, instruction, kl.mvin)))(((KLE, instruction, kl.mvout)))

[upperroman]
. `kl.mvin Xs2` copies 128 bits from two or four GPRs into the locker.
. `kl.mvin Vs2` copies one or more 128-bit blocks from a vector register into the locker.
. `kl.mvin KLIOBUF` copies one or more 128-bit blocks from the KLIOBUF into the locker.
. `kl.mvout Xs1` copies 128 bits from the locker into two or four GPRs at `Xs1`.
. `kl.mvout Vs1` copies one or more 128-bit blocks from the locker into a vector register `Vs1`.
. `kl.mvout KLIOBUF` copies one or more 128-bit blocks from the locker into the KLIOBUF.

The locker is not an operand: the instruction acts on the locker that `klnamedlocker` names (Rule <<KLE-GR-locker-less-transfers>>).
--

_Encodings_::
+
--
The encodings are variants of `kl.exec` Form D (`Form` = `0b11`) in which `rd`, zero in `kl.exec`, is non-zero and selects the variant. Since no locker is encoded, `r` = 0; a non-zero `r` is reserved.

[upperroman]
. `kl.mvin Xs2`:       `rd` = `0b00001`, `rs1` = `0`, and `rs2` holds the source GPR.
. `kl.mvin Vs2`:       `rd` = `0b00010`, `rs1` = `0`, and `rs2` holds the source vector register.
. `kl.mvin KLIOBUF`:   `rd` = `0b00011`, `rs1` = `0`, and `rs2` = `0b00000`.
. `kl.mvout Xs1`:      `rd` = `0b00101`, `rs2` = `0`, and `rs1` names the destination GPR.
. `kl.mvout Vs1`:      `rd` = `0b00110`, `rs2` = `0`, and `rs1` names the destination vector register.
. `kl.mvout KLIOBUF`:  `rd` = `0b00111`, `rs2` = `0`, and `rs1` = `0b00000`.

Any other non-zero value of `rd` in Form D is reserved and raises an illegal-instruction exception.
--

_Description_::
+
--
`kl.mvin` moves `Content` into, and `kl.mvout` out of, the named locker (Rule <<KLE-GR-locker-less-transfers>>).
Neither transfers the MDH: for a provisioning or an import, the opening `kl.mgmt` has already loaded it (<<KLE-instruction-mgmt>>), and `kl.getmd*` reads it.

[[KLE-mv-locker-checks,locker checks]]Locker checks::
The named locker must be in a Configuration State that admits the instruction, and `klstart` must be a multiple of 16:
+
* `kl.mvin`, a locker being provisioned or imported: `kl_cfg_provisioning`, `kl_cfg_importing` or `kl_cfg_ppi_importing` (Rule <<KLE-GR-zkl-load-mv-allowed>>);
* `kl.mvout`, a locker being exported: `kl_cfg_exporting` or `kl_cfg_ppi_exporting` (Rule <<KLE-GR-zkl-store-mv-allowed>>).
+
Otherwise an illegal-instruction exception is raised, except on an _Unconfigured_ or Error-State locker, on which the instruction performs no operation, whatever `klstart` is (Rule <<KLE-GR-fall-through-mv>>).

Transfer::
`kl.mvin` and `kl.mvout` transfer whole 16-byte blocks of the <<KLE-serialized-image,serialized image>> `S` of the locker, a byte string, at 16-byte-aligned offsets: the block at offset `klstart` is transferred if `klstart` < `image_end`, and `klstart` then advances by 16; it is kept across instructions, so that a sequence of them transfers `S` piecewise.
A GPR variant transfers exactly one block, so there is nothing to interrupt and it is uninterruptible; a vector variant transfers one block per 128/`SEW` elements and can be interrupted at a block boundary (Rule <<KLE-GR-interruptibility-classes>>).
If `klstart` {ge} `image_end`, `klstart` is unchanged, `kl.mvin` writes nothing, and `kl.mvout` writes zeros to its destination GPRs, resp. to every element of `Vs1` from `vstart` to `vl` − 1.
If one management operation combines `kl.mvin` or `kl.mvout` with `kl.load` or `kl.store`, each byte of `Content` holds the value last written to its offset, by whichever instruction.

Vector variants (II and V)::
They also track progress in `vstart`: each 16-byte block advances it by 128/`SEW` elements, for instance by 4 for 32-bit and by 2 for 64-bit elements.
Element _k_ of the vector operand, for _k_ from `vstart` to `vl` − 1, corresponds to byte offset `klstart` + (_k_ − `vstart`) × `SEW`/8 of `S`.
The transfer can halt only at a block boundary: `klstart` then holds the total number of bytes transferred, and `vstart` the first untransferred element; if `vstart` {ge} `vl`, the instruction performs no operation and leaves `klstart` unchanged.

KLIOBUF variants (III and VI)::
They use the KLIOBUF in place of a vector register: they transfer bytes 0 to `kliobuftop` − 1 of the KLIOBUF to or from offsets `klstart` to `klstart` + `kliobuftop` − 1 of `S`, as a vector variant with `vstart` = 0 and `vl` × `SEW`/8 = `kliobuftop` does.
Like the GPR variants (I and IV), they are architecturally uninterruptible (Rule <<KLE-GR-uninterruptible-class>>), although they may transfer several blocks: their length is bounded by `klmaxiobuflen`.
+
NOTE: The KLIOBUF variants give an implementation without `Zklv` multi-block transfers: `kl.input` fills the KLIOBUF from memory, with `klnamedlocker` = 32, and `kl.mvin KLIOBUF` moves it into the locker, with `klnamedlocker` naming that locker (Rule <<KLE-SR-klnamedlocker-write>>), as `kl.input` and `kl.exec` cooperate for the inputs of a Machine (<<KLE-usage-input-output>>).
Their window is the KLIOBUF up to `kliobuftop`, so they need no element position, and a transfer of at most `klmaxiobuflen` bytes can be uninterruptible.

Exceptions and no-operation cases::
Besides the <<KLE-mv-locker-checks>>, an illegal-instruction exception is raised if:
+
* for a vector variant, `vl` × `SEW`/8 or `vstart` × `SEW`/8 is not a multiple of 16; or
* for a KLIOBUF variant, `Zklio` is not implemented, or, unless the variant performs no operation, the KLIOBUF is unconfigured (Rule <<KLE-GR-iobuf-configured>>) or `kliobuftop` is not a multiple of 16.
+
For a vector variant, the check that the vector extension is enabled precedes all of these and the locker checks.
+
When `klnamedlocker` = 32, every variant performs no operation, whatever `klstart` is, as on an _Unconfigured_ or Error-State locker; in both cases `kl.mvout` writes zeros to its destination (Rule <<KLE-GR-fall-through-mv>>).
A KLIOBUF `kl.mvout` writes them to `[0, kliobuftop)` of a configured buffer, and accesses none otherwise; both directions keep `klstart`.
--

[[KLE-instruction-setst]]
=== kl.setst

_Synopsis_::
Change the state of the Machine encoded in the CC in a locker.

_Mnemonic_::
`kl.setst` has four Forms:
(((KLE, instruction, kl.setst)))
+
[upperalpha]
. `kl.setst Kd, #immed7{fournbsp}{nbsp}{nbsp}` with no auxiliary input.
. `kl.setst Kd, #immed7, Xs{nbsp}` with auxiliary input in one or two GPRs (RV64/RV32).
. `kl.setst Kd, #immed7, Vs{nbsp}` — in a vector register.
. `kl.setst Kd, #immed7, Xs{nbsp}` — in two or four GPRs (RV64/RV32).

//

_Encoding_::
`kl.setst` is an R-type instruction.
The encodings with bit 24 = 1 belong to `kl.setnl` and `kl.setnli` (<<KLE-instruction-get-set-nl>>); of the others, those with `#immed7`[6:3] = `0b0111` belong to `kl.mgmt` (<<KLE-instruction-mgmt>>); these are separate instructions, and all remaining encodings are `kl.setst`.
+
--
[wavedrom, ,svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Kd' },
    { bits:  3, name: 0x3, attr: ['kl.setst'] },
    { bits:  5, name: 'rs1' },
    { bits:  1, name: 'r', attr: ['KLNL']   },
    { bits:  2, name: 'F' },
    { bits:  2, name: 0x0 },
    { bits:  7, name: 'immed7' },
]}
....

`#immed7` = `kl_cfg_clearall` (65) is valid only in Form A, with `Kd` = 0 and `r` = 0, where it encodes `kl.clearall` (<<KLE-instruction-clearall>>); every other encoding with `#immed7` = 65 is reserved.

The encodings of the four Forms are:
[upperalpha]
. `F` = `0b00`. `rs1` = `0b00000`.
. `F` = `0b01`.
. `F` = `0b10`.
. `F` = `0b11`.
--

// ////////////////////////////////////////////////////////////////////

_Description_::
+
--
`kl.setst` advances the Machine of locker `Kd` from one stage to another, for instance from initializing a hash function to absorbing data and finalizing the digest.
It normally reaches the State that `#immed7` names, but some States transition automatically to another State when the instruction completes.
<<KLE-State-management>> and each Machine's specification give the allowed transitions.
`kl.setst` may also set state information orthogonal to these stages, possibly as a prerequisite for entering another State.

For all Machines, `#immed7` takes these values:

* 0 (`kl_state_unconfigured`) clears the locker, in any Form, ignoring any auxiliary operand.
* 1–47 name the _Valid_ States (<<KLE-states-valid>>). 46 and 47, _Success_ and _Failure_ of the Machine, cannot be set directly; _Failure_ is an outcome, not an error.
* 48–55 name the Error States (<<KLE-states-error>>); 54 and 55 are reserved, and so is 53 without `Zklexpire`.
   An Error State is accepted as `#immed7` in any State: a locker in a Complete or Configuration State transitions to it _without raising an exception_, even where reaching that State implicitly would raise one, and later usage of the locker performs no operation (Rule <<KLE-GR-usage-locker-error-state>>).
   On an _Unconfigured_ locker the instruction performs no operation: only the short import of <<KLE-error-state-transfer>> configures a locker directly into an Error State.
* 56–63, whose top four bits are `0b0111`, encode `kl.mgmt` (<<KLE-instruction-mgmt>>).
* 64 encodes `kl_cfg_clear_ads` (<<KLE-instruction-clearads>>).
* 65 encodes `kl_cfg_clearall` (<<KLE-instruction-clearall>>), in Form A with locker 0 and `r` = 0 only.
* 66–127 are Machine-defined, and may change other state information, such as _StateExtension_.

A value in 1–45 or 66–127 that the current Machine does not support transitions the locker to Error State _Invalid_.
On an _Unconfigured_ locker, every immediate in 1–45, 48–53, 64 and 66–127 performs no operation (Rule <<KLE-GR-transition-to-from-unconfigured>>).
The immediates 46, 47, 54 and 55, and 53 without `Zklexpire`, are reserved in every State (Rule <<KLE-GR-success-failure-cannot-be-set-directly>>, <<KLE-illegal-instruction-grounds>>); 0 and 65 encode `kl.clear` and `kl.clearall`, and 56–63 encode `kl.mgmt`.
Some values require a 64- or 128-bit auxiliary operand, in one or more GPRs or in a vector register (group) `Vs`.

`Kd` may be `KLNL`, except for `kl.clearall` (Rules <<KLE-GR-klnamedlocker-override>> and <<KLE-GR-klnl-no-named-locker>>).
--

[[KLE-instruction-clear]]
==== kl.clear

`kl.clear Kd` is `kl.setst` (<<KLE-instruction-setst>>) with no auxiliary operand and `#immed7` = `kl_state_unconfigured` (<<KLE-State-field>>).
It sets the locker's _State_ to _Unconfigured_ and releases its KLF resources.
It is a configuration instruction, not a usage instruction (<<KLE-instruction-properties>>): neither the _UsagePolicy_ nor the Machine restricts it (Rule <<KLE-GR-opening-locker-when>>).

Clearing a locker not already _Unconfigured_, or whose `*llockerstatus` field in effect is _Off_ (<<Zkl-ISA-priv.adoc#KLE-CSR-llockerstatus>>), sets to Dirty the `*llockerstatus` fields in effect for the current privilege mode and the `KLS` fields in effect.

// ////////////////////////////////////////////////////////////////////

[[KLE-instruction-clearall]]
==== kl.clearall

`kl.clearall` is `kl.setst` with no auxiliary operand, `#immed7` = `kl_cfg_clearall`, locker number 0 and `r` = 0.
The locker field names no locker: `kl.clearall` acts on every locker whatever the _State_ of `K0`, and is not a usage instruction.

It unconfigures every locker, as `kl.clear` on each would.
It also unconfigures the KLIOBUF, zeroing the buffer and setting `kliobuflen`, `kliobuftop` and `klstart` to 0; zeroizes the three authentication registers of <<KLE-KLF>>; and writes 32 to `klnamedlocker`.

// ////////////////////////////////////////////////////////////////////

[[KLE-instruction-clearads]]
==== kl.clearads

`kl.clearads Kd` deletes any ADS from locker `Kd`, sets _AuxDataLen_ and _ADSDropped_ to 0, and zeroes the implementation-defined subfields of _MachineUse_ and _AuxInfo_ (<<KLE-MachineUse>>).
It is encoded as `kl.setst` (<<KLE-instruction-setst>>) with no auxiliary operand and `#immed7` = `kl_cfg_clear_ads` (64).

Software uses it before exporting a locker for another target to make the SCC smaller.
A destination with a different KLE unit would drop the ADS anyway.
// The first usage instruction that needs the ADS regenerates it.
`kl.clearads` is permitted in every Valid State, and may cause an interrupted operation to restart (Rule <<KLE-GR-clearads>>).

[[KLE-destructive-config]]
=== Destructive Configuration Instructions

`kl.clear` and `kl.clearall` (<<KLE-instruction-clear>> and <<KLE-instruction-clearall>>) are two of the
_destructive configuration instructions_, the configuration instructions that discard the CC in a locker without reading it.
The other destructive configuration instructions are:

* a provisioning- or import-opening `kl.mgmt` (defined in the next section, <<KLE-instruction-mgmt>>), which zeroizes the locker before configuring it;
* `kl.clone` and `kl.rename` (defined later in <<KLE-instruction-clone>>), which replace the CC of their destination locker with that of the source; and
* `kl.swap` (same section), a special case that overwrites both its lockers, each with the CC of the other, so nothing is lost.

A destructive configuration instruction destroys the CC it replaces right after the state-independent checks of Rule <<KLE-GR-management-check-order>> and, for `kl.mgmt`, the check of its MDH operand (Rule <<KLE-GR-vector-MDH-operand>>), whatever the outcome.

Only the accesses that overwrite a locker without reading it are exempt from the KLE locker-Off exception (<<Zkl-ISA-priv.adoc#KLE-CSR-llockerstatus>>): not the source access of `kl.clone` and `kl.rename`, nor either access of `kl.swap`.

The zeroization by `kl.mgmt` already keeps a new CC from reading the old contents.
As a robustness recommendation, `kl.clear` and `kl.clearall` should also zeroize the Content and any ADS, to erase stale secrets from the KLF sooner.

[[KLE-instruction-mgmt]]
=== kl.mgmt

_Synopsis_::
Open or complete a management operation on a locker.

_Mnemonic_::
While `kl.mgmt` uses the same encoding as Forms A, C and D only of `kl.setst`,
it is a distinct instruction.
(((KLE, instruction, kl.mgmt)))

//

_Encoding_::
`kl.mgmt` is an R-type instruction with the encoding of `kl.setst` (<<KLE-instruction-setst>>) and `#immed7`[6:3] = `0b0111`, that is, `#immed7` in 56–63.

_Description_::
+
--
For this instruction, Rules <<KLE-GR-klnamedlocker-override>> to <<KLE-GR-mgmt-klnamedlocker-check>> apply.

`kl.mgmt` brackets the body of a locker management operation (<<KLE-management-operations>>): it opens a provisioning, an export or an import on locker `Kd`, and completes it.
A `kl.mgmt` that opens, resp. completes, a management operation is an _opening_, resp. _completing_, `kl.mgmt`, named after its operation: a provisioning-opening `kl.mgmt`, an export-completing `kl.mgmt`, and so on.

A provisioning- or import-opening `kl.mgmt` is allowed in every _State_ (Rule <<KLE-GR-opening-locker-when>>).
It is a <<KLE-destructive-config,destructive configuration instruction>>, which erases the memory of the locker before using it:
this prevents any previous content from leaking into a nested management operation.

Like `kl.setst`, `kl.mgmt` changes the locker's _State_, but with different semantics, hence a separate instruction.
The State reached depends on both the locker's previous State and `#immed7`.
Besides the command in `#immed7`, `kl.mgmt` receives an MDH: when opening, it selects the variant of the operation and may become the locker's MDH; when completing an import or an export, it restores, from the copy the caller saved, the _State_ the locker had when the operation started.

<<KLE-management-immeds>> gives the values of `#immed7`.

The Forms supply the MDH as follows:

* Form A carries no auxiliary operand. Where the operation needs the MDH, Form A is a
  substitution (<<KLE-usage-input-output>>) and reads it from bytes [0, 15] of the KLIOBUF,
  ignoring `klstart`. After the `klnamedlocker` check and before any change to the locker, Rule
  <<KLE-GR-iobuf-configured>> applies and, with the KLIOBUF configured, `kliobuftop` < 16 raises
  an illegal-instruction exception (Rule <<KLE-GR-vector-MDH-operand>>).
* Form C carries it in the lowest 128 bits of `Vs`. Where the operation needs it, `VL` {times} `SEW` < 128 raises an illegal-instruction exception at the same point as for Form A (Rule <<KLE-GR-vector-MDH-operand>>).
* Form D carries it as a 128-bit operand in two or four GPRs starting at `Xs` (Rule
  <<KLE-GR-multiple-GPRs>>).
* Form B is a reserved encoding (<<KLE-illegal-instruction-grounds>>).

<<KLE-locker-management>> gives the precise semantics of each operation.
--

[[KLE-instruction-getmd]]
=== kl.getmd, kl.getmdl, and kl.getmdv

_Synopsis_::
Export the MDH of a locker.

_Mnemonics_::
+
--
[%hardbreaks]
`kl.getmdl{nbsp}Xd, Ks`(((KLE, instruction, kl.getmdl)))
`kl.getmd{nbsp}{nbsp}Xd, Ks`(((KLE, instruction, kl.getmd)))
`kl.getmdv{nbsp}Vd, Ks`(((KLE, instruction, kl.getmdv)))
--


_Encoding_::
+
--
`kl.getmd*` are R-type instructions that share the opcode and `funct3` of `kl.exec`, with `funct2` = `0b11`.

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Xd' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'rs1', attr: ['Ks'] },
    { bits:  5, name: 0x00  },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'r', attr: ['KLNL']   },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'h' },
    { bits:  1, name: 'v' },
    { bits:  2, name: 0x3, attr: ['funct2'] },
]}
....

`r` names `KLNL` as Rule <<KLE-GR-r-R-fields>> specifies.

With bit `v` (bit 29) = 0, bit `h` (bit 28) selects `kl.getmdl` (`h` = 0) or `kl.getmd` (`h` = 1), and the result goes to GPRs: one GPR on RV64 and a pair on RV32 for `kl.getmdl`, a pair on RV64 and a quartet on RV32 for `kl.getmd` (Rule <<KLE-GR-multiple-GPRs>>).
With `v` = 1, the instruction is `kl.getmdv`, which writes the entire MDH to the lowest 128 bits of a vector register (group); `h` must then be 0.
`v` = `h` = 1 is used to encode `kl.getnl` (<<KLE-instruction-get-set-nl>>).
--

_Description_::
+
--
These instructions copy the MDH of locker `Ks`, which is all-zero for an _Unconfigured_ locker:

* `kl.getmdl` copies bits [63:0] to GPR `Xd` on RV64, and to the pair `X[d+1] @ X[d]` on RV32.
* `kl.getmd` copies bits [127:0]: on RV64, bits [63:0] to `Xd` and bits [127:64] to `X[d+1]`; on RV32, to the quartet `X[d+3] @ X[d+2] @ X[d+1] @ X[d]`.
* `kl.getmdv` copies bits [127:0] to vector register `Vd`, on RV32 as on RV64. Bits [`VL` {times} `SEW` − 1 : 128] are written with zeros, and the tail follows the tail-agnostic policy (<<KLE-KLV>>).

They do not check MDH validity (<<KLE-Metadata-validity>>).
`Ks` may be `KLNL` (Rule <<KLE-GR-klnamedlocker-override>>).
--

[[KLE-instruction-getst]]
==== kl.getst and kl.getstx

The pseudo-instructions
(((KLE, instruction, kl.getst)))
`kl.getst Xd, Ks`
(((KLE, instruction, kl.getstx)))
`kl.getstx Xd, Ks`
return the _State_, resp. _StateExtension_, field of the MDH of the source locker, for instance to determine whether it is in an Error State (<<KLE-State-field>>).
They read the MDH with `kl.getmdl` and extract the field by shifting and masking.

On RV64, `kl.getst` expands to

. `kl.getmdl Xd, Ks`
. `srli  Xd, Xd, 18`
. `andi  Xd, Xd, 0x3F`

and `kl.getstx` to

. `kl.getmdl Xd, Ks`
. `srli  Xd, Xd, 24`
. `andi  Xd, Xd, 0x0F`

On RV32 the code is the same: `kl.getmdl` writes the lower 64 bits of the MDH to the pair `X[d+1] @ X[d]` but _State_ and _StateExtension_ lie entirely in the lower 32 bits, i.e., in `X[d]`.

[[KLE-instruction-get-set-nl]]
=== kl.getnl, kl.setnl, and kl.setnli

Since in many implementations CSR accesses are slow, we provide, similarly to the Vector extensions, instructions to quickly set and get the value of `klnamedlocker` without incurring CSR access penalties and without requiring implementations to selectively use a different implementation path for these accesses. Internally, the value of `klnamedlocker` may be used as a prefix for the KLE instructions that need it.

_Synopsis_::
Get, resp. set, the value of `klnamedlocker`.

_Mnemonics_::
+
--
[%hardbreaks]
`kl.getnl{nbsp}{nbsp}Xd`(((KLE, instruction, kl.getnl)))
`kl.setnl{nbsp}{nbsp}Xs1`(((KLE, instruction, kl.setnl)))
`kl.setnli{nbsp}#uimm7`(((KLE, instruction, kl.setnli)))
--

_Encodings_::
+
--
The encodings are variants of those of `kl.getmd*` (<<KLE-instruction-getmd>>) and `kl.setst` (<<KLE-instruction-setst>>):

* `kl.getnl Xd`: the `kl.getmd*` encoding with `v` = `h` = 1, `r` = 0 and `rs1` = 0; `rd` holds `Xd`.
* `kl.setnli #uimm7`: the `kl.setst` encoding with bit 24 = 1, `Kd` = 0, `r` = 0, `F` = `0b00` and `rs1` = 0; `#immed7` holds `#uimm7`.
* `kl.setnl Xs1`: the `kl.setst` encoding with bit 24 = 1, `Kd` = 0, `r` = 0, `F` = `0b01` and `#immed7` = 0; `rs1` holds `Xs1`.

Every other encoding with `v` = `h` = 1 in the `kl.getmd*` encoding, or with bit 24 = 1 in the `kl.setst` encoding, is reserved.
--

_Description_::
+
--
`kl.getnl` writes `klnamedlocker`, zero-extended, to `Xd`.
`kl.setnl` and `kl.setnli` write `X[rs1]`, resp. the zero-extended `#uimm7`, to `klnamedlocker`, with the effect of a CSR write (<<KLE-CSR-klnamedlocker>>): a value of 33 or more leaves `klnamedlocker` unchanged.

These instructions are part of `Zkl` common and are gated as accesses to `klnamedlocker` (<<KLE-CSR-unpriv>>).
They are configuration instructions, not usage instructions: Usage Control does not gate them.
They are uninterruptible (Rule <<KLE-GR-uninterruptible-class>>), and Rules <<KLE-SR-klnamedlocker-write>> and <<KLE-SR-klnamedlocker-finish>> apply to their writes as to CSR writes.
--

[[KLE-instruction-restrict]]
=== kl.restrictl, kl.restricth, and kl.restrictv

_Synopsis_::
Restrict the policies encoded in a CC in a locker.

_Mnemonic_::
+
--
[%hardbreaks]
`kl.restrictl{nbsp}{nbsp}Kd, Xs1`(((KLE, instruction, kl.restrict)))
`kl.restricth{nbsp}{nbsp}Kd, Xs1`
`kl.restrictv{nbsp}{nbsp}Kd, Vs1`
--

_Encoding_::
+
--
`kl.restrict*` are R-type instructions that share the opcode and `funct3` of `kl.exec`, with `funct2` (the two msbs of `funct7`) = `0b01`.
[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Kd' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'Xs1' },
    { bits:  5, name: 0x0 },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'r', attr: ['KLNL']   },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'h' },
    { bits:  1, name: 'v' },
    { bits:  2, name: 0x1, attr: ['funct2'] },
]}
....

`r` names `KLNL` as Rule <<KLE-GR-r-R-fields>> specifies.

With bit `v` (bit 29) = 0, bit `h` (bit 28) selects `kl.restrictl` (`h` = 0) or `kl.restricth` (`h` = 1), and the input comes from a GPR (a GPR pair on RV32).
With `v` = 1, the instruction is `kl.restrictv`, `h` must be 0, and the input comes from the lowest 128 bits of a vector register (group); `v` = `h` = 1 is reserved.
--

// comment

_Description_::
+
--
These instructions narrow the policies of the CC in locker `Kd`, whose MDH is `md`, as their operand requests: `Xs1`, or `Vs1` for `kl.restrictv`, formatted as an MDH.

Operand::
* `kl.restrictl` takes bits [63:0] of the operand, and may change _MachinePolicy_;
* `kl.restricth` takes bits [127:64], supplied in `Xs1`[63:0], and may change _Locality_, _UsagePolicy_ and _ExpirationDate_;
* `kl.restrictv` takes both halves, and applies both sets of rules.
+
A zero field of `Xs1` leaves the corresponding field of `md` unchanged; a non-zero field other than these four transitions the locker to _Invalid_.

Per-field behavior::
For _Locality_ and _ExpirationDate_, the result is the narrowing of `md` by `Xs1` (<<KLE-Metadata-narrowing>>), except that a _Locality_ request weaker than `md` transitions the locker to _Privilege Violation_ instead of being overridden.
_UsagePolicy_ follows its own field rule below: `Xs1` is a request, not an MDH policy, so a clear bit 4 does not withdraw the Debug grant.
Each non-zero field of `Xs1` is handled as follows:
+
* _MachinePolicy_: each set bit clears the corresponding bit of `md`, disabling that function, and each clear bit changes nothing, so that no disabled function can be enabled.
  A request that the current State forbids (Rule <<KLE-GR-policy-narrowing-state>>), or one for a Machine that does not use the field or uses it to extend _Machine_, transitions the locker to _Invalid_.
  A Machine with fields that exist only for some values of _MachinePolicy_, such as the ECC Machines (<<Zkl-ISA-machines.adoc#KLE-ECC>>), states what a narrowing does to them.
* _Locality_: each subfield (<<KLE-locality-indexes>>), bits [1:0], [3:2] and [5:4] and each of bits 6, 7 and 8, is treated independently.
  A subfield of `Xs1` that is zero or equal to that of `md` requests no change, and a zero subfield of `md` takes the value of `Xs1`.
  A non-zero HW Binding subfield may be replaced only by a stricter entry of its chain: _SiPScrt_ by _ChipFamScrt_ or _ChipScrt_, _ChipFamScrt_ by _ChipScrt_, _OEMScrt_ by _ProdScrt_ or _DevScrt_, and _ProdScrt_ by _DevScrt_.
  Any other change, a weakening or a change of a non-zero Boot Session or SW Filter subfield included, transitions the locker to _Privilege Violation_.
  A later export binds its SCC to the new _Locality_.
* _UsagePolicy_: each set bit removes a permission, and each clear bit changes nothing: bits 0–3 set the corresponding disallow bits of `md`, and bit 4 clears its Debug grant, so no request can widen the set of modes that may use the CC.
* _ExpirationDate_: if `md`._ExpirationDate_ is zero or `Xs1`._ExpirationDate_ {le} `md`._ExpirationDate_, the value in `Xs1` replaces it; otherwise the field is unchanged, without error.

Validity of the result::
Validity (<<KLE-Metadata-validity>>) is evaluated on the changed fields only.
A request that would produce an unsupported or invalid value, such as a non-zero _ExpirationDate_ without `Zklexpire`, transitions the locker to _Invalid_; one that would make _Locality_ name an unconfigured entry without a configured substitute, to _Privilege Violation_; one that does both, to _Invalid_.

States::
The instructions act only in a Valid State: on an _Unconfigured_ or Error-State locker they perform no operation (Rule <<KLE-GR-outcome-inert>>), and in a Configuration State Rule <<KLE-GR-usage-locker-config-state>> applies.
+
They are not usage instructions (Rule <<KLE-GR-usage-policy>>): every change narrows the CC, so a mode that the _UsagePolicy_ excludes gains no capability; the same holds for `kl.clear` (<<KLE-instruction-clear>>), a stronger denial primitive.
--

Localities or limiting them to a subset of their functionalities, such as creating separate encryption-only and decryption-only versions.

[[KLE-instruction-clone]]
=== kl.clone, kl.rename, and kl.swap

_Synopsis_::
Copy, move or exchange the CCs of lockers.

_Mnemonic_::
`kl.{clone, rename, swap} Kd, Ks`
+
Either `Kd` or `Ks`, not both, may be `KLNL` (Rule <<KLE-GR-r-R-fields>>).
(((KLE, instruction, kl.clone)))
(((KLE, instruction, kl.rename)))
(((KLE, instruction, kl.swap)))

_Encoding_::
These are R-type instructions that share the opcode and `funct3` of `kl.exec`, with `funct2` = 2.
+
[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Kd' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'Ks' },
    { bits:  5, name: 0x0 },
    { bits:  2, name: 'R', attr: ['KLNL']   },
    { bits:  2, name: 'T' },
    { bits:  1, name: 0x0 },
    { bits:  2, name: 0x2, attr: ['funct2'] },
]}
....
+
--
Field `T` (bits [28:27]) selects the instruction:

. `00`{nbsp}{nbsp} encodes `kl.clone`.
. `01`{nbsp}{nbsp} encodes `kl.rename`.
. `10`{nbsp}{nbsp} encodes `kl.swap`.
--

// Comment to ensure proper indentation in the next Description

_Description_::
+
--
`kl.clone`::
Clones the source locker `Ks` into the destination locker `Kd`, either of which, not both, may be `KLNL` (Rule <<KLE-GR-r-R-fields>>):

* If source and destination are the same locker, the instruction performs no operation and sets no `*llockerstatus` or `KLS` field to Dirty (<<Zkl-ISA-priv.adoc#KLE-CSR-llockerstatus>>), even if the locker is _Unconfigured_, _Off_, or in a Configuration State; in the last case, Rule <<KLE-GR-usage-locker-config-state>> does not apply.
* Otherwise it first clears the destination, as `kl.clear` would, even if it then raises an exception (<<KLE-destructive-config>>); if `klnamedlocker` named the destination, it becomes 32.
* An _Unconfigured_ source leaves the destination _Unconfigured_.
* A source in a Configuration State raises a KLE privilege-violation exception (Rule <<KLE-GR-usage-locker-config-state>>). A source in an Error State is cloned as its MDH alone (Rule <<KLE-GR-error-state-locker-is-only-MDH>>).
* Otherwise, if the available KLF capacity cannot hold a clone of the source, a KLE out-of-memory exception is raised.
* Otherwise the destination becomes a verbatim copy of the source, including all internal data, the MDH and the internal state.
As the one exception, if the source has an interrupted long-running operation, the copy restarts it (Rule <<KLE-GR-long-running-restart>>): its progress is zeroed and the values drawn or computed for the operation are discarded, as at an import that completes without `Content2`.
The effect is that of an export from the source followed by an import into the destination, except that no authentication register is touched.

`kl.rename`::
If `Ks` and `Kd` name the same locker, through `KLNL` too, no operation is performed, even if the locker is _Off_, and no field is set to Dirty.
Otherwise the CC of `Ks`, Configuration State included, becomes the CC of `Kd`, the previous CC of `Kd` is discarded, `Ks` becomes _Unconfigured_, and the fields in effect for both lockers are set to Dirty. With an _Unconfigured_ source, `kl.rename` thus acts as `kl.clear Kd`, except that it always sets the fields in effect for both lockers to Dirty.
If `klnamedlocker` = `s`, it becomes `d`; otherwise, if it is `d`, it becomes 32. The source access is not exempt from the KLE locker-Off exception; the destination access is exempt, as for `kl.clone`.

`kl.swap`::
If `Ks` and `Kd` name the same locker, through `KLNL` too, no operation is performed, even if the locker is _Off_.
Otherwise the CCs of `Ks` and `Kd` are exchanged, and if `klnamedlocker` {in} {`s`,`d`}, it takes the other index. Neither access is exempt from the KLE locker-Off exception. The fields in effect for both lockers are set to Dirty.

Neither `kl.rename` nor `kl.swap` raises a KLE out-of-memory exception or changes the content of any MDH.
<<Zkl-ISA-priv.adoc#KLE-CSR-llockerstatus>> gives the behavior under emulation, when the source or destination locker is _Off_ in some `*llockerstatus`.
--

[[KLE-instruction-derive]]
=== kl.derive

_Synopsis_::
Transfer data from one locker into another without exposing it to software.

_Mnemonic_::
`kl.derive Kd, Ks1, Xs2`
+
Either `Kd` or `Ks1`, not both, may be `KLNL` (Rule <<KLE-GR-r-R-fields>>).
(((KLE, instruction, kl.derive)))

_Encoding_::
+
--
`kl.derive` is an R-type instruction.

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'Kd' },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: 'Ks1' },
    { bits:  5, name: 'Xs2' },
    { bits:  2, name: 'R', attr: ['KLNL']   },
    { bits:  2, name: 0x3 },
    { bits:  1, name: 0x0 },
    { bits:  2, name: 0x2, attr: ['funct2'] },
]}
....

The auxiliary input is always a GPR: `kl.derive` has no form without one, and no vector form.
--

_Description_::
+
--
A `kl.derive` transfers data from a _source endpoint_ to a _destination endpoint_; the architecture decides which pairs of endpoints are admitted.

[[KLE-source-endpoint,Source Endpoint]]Definition: _Source endpoint:_::
A source endpoint is a field or a value of _State_ and _StateExtension_ that a Machine lists as a source in <<Zkl-ISA-machines.adoc#KLE-derive-endpoints>>.
It exports the _exportable field_ that its Machine lists for that State, whose availability _StateExtension_, or an MDH field that the Machine names, such as `OutputType` of ECC (<<Zkl-ISA-machines.adoc#KLE-ECC-MachineUse>>), may determine; if the Machine lists none, it exports its `kl.exec` _output_, the data that the Form C `kl.exec` instructions permitted in that State would emit. A field configured by a SKID is never exportable (Rule <<KLE-GR-SKID-no-export>>).

[[KLE-destination-endpoint,Destination Endpoint]]Definition: _Destination endpoint:_::
A destination endpoint is a field or a value of _State_ and _StateExtension_ that a Machine lists as a destination in <<Zkl-ISA-machines.adoc#KLE-derive-endpoints>>.
It imports data either in an _importable field_, or consumes it as an `kl.exec` _input_, the data that the Form B `kl.exec` instructions of that State would absorb. A key field, that is, a symmetric or private key, is a destination only in State _Ready_ or in a State that the Machine names for loading it, such as _Set_Key_ of HMAC (<<Zkl-ISA-machines.adoc#KLE-HMAC>>) or _Set_Scalar_ of ECC (<<Zkl-ISA-machines.adoc#KLE-ECC>>), and never when _KeyType_ is 1 (Rule <<KLE-GR-SKID-no-export>>). The destination fixes the minimum, upper limit and granularity of the transfer.

[[KLE-admitted-pairs,Admitted Pairs]]Definition: _Admitted pairs:_::
An _admitted pair_ consists of a source endpoint and of a destination endpoint; the MDH of each locker, not an operand of `kl.derive`, determines its endpoint.
Rules <<KLE-GR-shared-secret>>, <<KLE-GR-exec-implies-unrestricted>> and <<KLE-GR-DRBG-implies-unrestricted>> admit three families of pairs, and state for each whether the transfer is restricted or unrestricted; a Machine may define further pairs, which narrow but never relax any policy and respect Rule <<KLE-GR-shared-secret>>. Any other pair is not admitted.
An admitted pair fixes the semantics of the transfer and its updates to the two States and to `klstart` (Rules <<KLE-GR-checks>>–<<KLE-GR-derive-rule-both-fixed-size>>); `kl.derive` changes no other state of the hart (<<KLE-instruction-properties>>).

`kl.derive` moves up to `length` bytes, `length` being the value of the auxiliary GPR, from an endpoint of the source locker to an endpoint of the destination locker without exposing them to software: the output of one Machine becomes an input of another, possibly a key or another Content field.
`length` is that of the whole transfer, also when it resumes from byte `klstart` (Rule <<KLE-GR-derive-rule-both-fixed-size>>).

A transfer is _unrestricted_ if software could also obtain the data moved by issuing `kl.exec` instructions, or if a Rule declares it unrestricted; otherwise, and for a shared secret in every case (Rule <<KLE-GR-shared-secret>>), it is _restricted_.

Source and destination must be different lockers; otherwise an illegal-instruction exception is raised, also when a `KLNL` operand names the other locker.
Usage Control applies to both lockers (Rule <<KLE-GR-outcome-valid-state>>), and both are checked before any state change or transfer, in the order of Rule <<KLE-GR-checks>>.
--

[[KLE-instructions-memory]]
=== Memory Instructions

Accesses to the serialized, user-visible representation of a locker's `Content` are 16-byte granular: `kl.load`, `kl.store`, `kl.mvin` and `kl.mvout` transfer whole 16-byte blocks, and all their offsets and lengths, `klstart`, `content_size`, `max_admissible`, `image_size` and `image_end` (<<KLE-serialized-image>>), are multiples of 16.

The effective address of a `kl.load` or `kl.store` must be 16-byte aligned, so a PI or SCC must be held at a 16-byte aligned address.
A misaligned address transfers no data and raises a load, resp. store, address-misaligned exception on that address; the check applies even when the transfer window is empty.
`kl.load` and `kl.store` evaluate their conditions in this order:

. the illegal-instruction grounds of both groups and the KLE exceptions, in the order of <<Zkl-ISA-priv.adoc#KLE-exception-codes>>;
. the address breakpoint of the first component access, if any;
. address-misaligned, on the effective address; and
. for each component access, in offset order, the address breakpoint, then page, guest-page and access faults, as ordered by the Privileged Specification.

`kl.input` and `kl.output` are byte-granular and impose no alignment constraint: a misaligned effective address behaves as for an ordinary load, resp. store, on the implementation.

[[KLE-instruction-load]]
==== kl.load and kl.input

(((KLE, instruction, kl.load)))(((KLE, instruction, kl.input)))_Mnemonics_::
`kl.load %offset(Xs), Xl` +
`kl.input %offset(Xs), Xl` +
`kl.input` is an alias for `kl.load`, for source code in which `klnamedlocker` is known to be 32.

_Encoding_::
--
`kl.load`/`kl.input` is an I-type instruction.

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x03, attr: ['LOAD'] },
    { bits:  5, name: 'Xl' },
    { bits:  3, name: 0x7, attr: ['kl.load','kl.input'] },
    { bits:  5, name: 'Xs' },
    { bits: 12, name: 'immed12' },
]}
....
--

_Description_::
+
--
The locker is not an operand: with `klnamedlocker` < 32, `kl.load` copies data into the locker that `klnamedlocker` names; with `klnamedlocker` = 32, into the KLIOBUF.

For `klnamedlocker` < 32::
`kl.load` imports the Content of a PI or an SCC into the locker, but not its MDH, which `kl.mgmt` carries.
A non-zero `Xl` raises an illegal-instruction exception; otherwise, `kl.load` makes the <<KLE-mv-locker-checks,locker checks>> of `kl.mvin`.
+
For each _j_ in `[klstart, image_end-1]`, `kl.load` loads the byte at memory address ``Xs + %offset + ``_j_ into byte _j_ of the <<KLE-serialized-image,serialized image>> `S`, in 16-byte blocks from a 16-byte aligned address (<<KLE-instructions-memory>>).
`klstart` tracks a prefix-complete number of bytes loaded; if `klstart` {ge} `image_end`, nothing is transferred.
On an _Unconfigured_ or Error-State locker, `kl.load` has an empty transfer window and accesses no memory (Rules <<KLE-GR-fall-through-load-store>> and <<KLE-GR-error-state-locker-is-only-MDH>>); software does not use it on an Error-State locker (<<KLE-error-state-transfer>>).
+
With a system-specific format, the semantics of `kl.load` are implementation-defined, must be documented, and must satisfy Rules <<KLE-GR-zkl-load-mv-allowed>>, <<KLE-GR-resumable-class>>, <<KLE-GR-precise-halt>>, <<KLE-GR-block-iterated-instructions>> and <<KLE-GR-memory-instructions>>.

For `klnamedlocker` = 32::
With `Xl` = 0, `kl.input` and `kl.output` perform no operation and write 0 to `klstart`, before any check of `Zklio` or of the KLIOBUF (Rules <<KLE-GR-fall-through-load-store>> and <<KLE-GR-iobuf-configured>>).
Otherwise, they raise an illegal-instruction exception if `Zklio` is not in effect; if it is, they transfer the bytes of the <<KLE-iobuf-transfer-window>> below.

[[KLE-iobuf-transfer-window,KLIOBUF transfer window]]Definition: _KLIOBUF transfer window_::
The KLIOBUF transfer window of `kl.input` and `kl.output` is the offsets _j_ from `klstart` to min(`Xl`, `kliobuftop`) − 1.
For each such _j_, `kl.input` copies the byte at memory address ``Xs + %offset + ``_j_ to byte _j_ of the KLIOBUF, and `kl.output` copies byte _j_ of the KLIOBUF to that address.
Bytes outside the window are accessed on neither side, so an `Xl` beyond `kliobuftop` transfers only the window.
If `klstart` {ge} min(`Xl`, `kliobuftop`), the window is empty: after Rule <<KLE-GR-iobuf-configured>> is evaluated, nothing is transferred and `klstart` is set to 0.
--

==== kl.store and kl.output

(((KLE, instruction, kl.store)))(((KLE, instruction, kl.output)))_Mnemonics_::

{reg:[

_Description_::

The locker is not an operand: with `klnamedlocker` < 32, `kl.store` copies data out of the locker that `klnamedlocker` names; with `klnamedlocker` = 32, out of the KLIOBUF.

For `klnamedlocker` < 32::

For `klnamedlocker` = 32::

5+| ^*^ Usable only in the States admitted by Rule <<KLE-GR-zkl-load-mv-allowed>>, resp. Rule <<KLE-GR-zkl-store-mv-allowed>>; on an _Unconfigured_ or Error-State locker they perform no operation (Rule <<KLE-GR-cleared-under-management>>).
|===

[horizontal]
[[KLE-GR-iobuf-configured,GR8]]GR8:: The KLIOBUF instructions, `kl.input`, `kl.output` and the KLIOBUF variants of `kl.mvin` and `kl.mvout`, and the usage instructions that substitute the KLIOBUF for a vector operand (<<KLE-usage-input-output>>), require: `Zklio` and a configured KLIOBUF, with a non-zero `kliobuflen`, even for an empty transfer window. Otherwise, they raise an illegal-instruction exception, after the checks of Rule <<KLE-GR-gate-order>> or <<KLE-GR-management-check-order>>.
An unconfigured KLIOBUF is a ground of the second group of <<KLE-illegal-instruction-grounds>>.
// the issuing mode configures the KLIOBUF itself, so no handler can resolve it.
+
An instruction that performs no operation needs no configured KLIOBUF: `kl.mvin` and `kl.mvout` with no named locker, or an _Unconfigured_ or Error-State one (<<KLE-instruction-mv>>), a Form D `kl.exec` on such a locker (Rule <<KLE-GR-zero-unwritten-output>>), and `kl.input` and `kl.output` with `Xl` = 0, which need no `Zklio` either (<<KLE-instruction-load>>).

[[KLE-named-locker-rules]]
=== Rules Governing the Named Locker

[horizontal]
[[KLE-GR-locker-less-transfers,GR9]]GR9:: `kl.load`, `kl.store`, `kl.mvin` and `kl.mvout` are the only instructions that have no locker operand.
Hence, they can only act on the locker named by `klnamedlocker`.

[[KLE-GR-klnamedlocker-override,GR10]]GR10:: Every instruction that names a locker may name the named locker, written `KLNL`, instead; `kl.clone`, `kl.rename`, `kl.swap` and `kl.derive` may do so for one of their two lockers only.
`KLNL` is encoded as Rule <<KLE-GR-r-R-fields>> specifies, and denotes the locker that `klnamedlocker` names when the instruction issues.

[[KLE-GR-klnl-openings,GR11]]GR11:: An opening `kl.mgmt` on `KLNL` performs no operation when `klnamedlocker` = 32, which stays 32 (Rule <<KLE-GR-klnl-no-named-locker>>). Otherwise, it opens that locker, and `klnamedlocker` is not changed, except that an export opening on an _Unconfigured_ locker performs no operation and sets it to 32 (cf. Rules <<KLE-GR-fall-through-mgmt>> and <<KLE-GR-klnamedlocker-updates>>).

[[KLE-GR-klnl-no-named-locker,GR12]]GR12:: When `klnamedlocker` = 32, an instruction naming `KLNL`, an opening `kl.mgmt` included, falls through as on an _Unconfigured_ locker (Rule <<KLE-GR-outcome-inert>>): `kl.getmd*` returns zeros, `kl.size` and `kl.avail` return 0, and `kl.exec`, `kl.setst`, `kl.restrict*`, `kl.clone`, `kl.rename`, `kl.swap`, `kl.derive` and `kl.mgmt` perform no operation, `kl.exec` zeroing its output (cf. Rule <<KLE-GR-zero-unwritten-output>>).

[[KLE-GR-mgmt-klnamedlocker-check,GR13]]GR13:: A `kl.mgmt` that names a locker explicitly raises an illegal-instruction exception unless `klnamedlocker` holds the number of the same locker or 32.

[[KLE-GR-klnamedlocker-updates,GR14]]GR14:: Besides writes by software, through the CSR or `kl.setnl` and `kl.setnli` (<<KLE-instruction-get-set-nl>>), only the following change `klnamedlocker`:

. a `kl.mgmt` that leaves its target locker in a Configuration State or a Complete State sets it to, or leaves it at, that locker's number;
. a `kl.mgmt` that performs no operation on an _Unconfigured_ locker sets `klnamedlocker` to 32 (Rule <<KLE-GR-fall-through-mgmt>>);
. a provisioning- or import-opening `kl.mgmt` that raises an exception after its zeroizing step sets it to the target locker's number;
. a `kl.clear` or `kl.clearall` that clears the named locker sets `klnamedlocker` to 32;
. a `kl.clone` or `kl.rename` from another locker into the named locker sets `klnamedlocker` to 32, a `kl.clone` even if it then traps; and
. a `kl.rename` or `kl.swap` that moves the CC of the named locker sets `klnamedlocker` to the receiving locker's number (<<KLE-instruction-clone>>).

[NOTE]
====
The named locker serves three purposes:

. a single management routine using the named locker can manage any locker, with significant code savings;
. a clear inserted into a management operation, for instance by a handler, is detectable: it sets `klnamedlocker` to 32 (Rule <<KLE-GR-cleared-under-management>>);
. the outcome stays readable: `klnamedlocker` keeps its value on completion, on entry into an Error State and on any other KLE exception, so a check through `KLNL` reads the outcome until software writes 32 to it.
====

[[KLE-content-confidentiality]]
=== Content Confidentiality

Rule <<KLE-GR-no-extraction>> protects the Content of a CC: it leaves a locker only sealed. Rule <<KLE-GR-custom-locality>> protects the Metadata that gives the Content its meaning: Metadata that only one chip can interpret leaves only to that chip.

[horizontal]
[[KLE-GR-no-extraction,GR15]]GR15:: _No extraction:_ Once a key has been sealed in a CC, that is, once the provisioning that bound it has completed, no instruction returns the value of the key, or of any other secret field of the Content, in clear:
+
--
. `kl.getmd*` returns only the MDH;
. `kl.exec` returns only the output of the Machine's operation, and no Machine may define an operation whose output is a key field;
. `kl.derive` moves material only into another locker, under Rules <<KLE-GR-checks>>–<<KLE-GR-derive-rule-both-fixed-size>>, where it is again subject to this Rule;
. every image of the locker, an SCC or an SCC-shaped PCCC, carries the Content encrypted and authenticated under a CSK (<<KLE-SCC>>, <<KLE-data-formats>>); a locker in an Error State has no Content to carry (Rule <<KLE-GR-error-state-locker-is-only-MDH>>).

Before sealing, a PI-shaped PCCC returns the clear Content of a provisioning still in progress, which the exporting software supplied itself; Rule <<KLE-SR-clear-before-lower-mode>> keeps it from a less privileged mode.
--

[[KLE-GR-custom-locality,GR16]]GR16:: A CC whose MDH carries a custom _Machine_ or a system-specific _Version_ must name _ChipFamScrt_, or the stricter _ChipScrt_, in its _Locality_; otherwise the Metadata is invalid.
The implementation-defined subfields of _MachineUse_ and _AuxInfo_ are exempt from this Rule: they are interpreted only with a matching, authenticated `IMPQUAL`, and zeroed otherwise (<<KLE-MachineUse>>).

[[KLE-State-management]]
=== Rules Governing the _State_ Field and its Transitions

<<KLE-State-field>> gives the architected values of the _State_ field, including the _Configuration_ States that a locker takes while being provisioned, exported or imported (<<KLE-SC-sealing-status>>).

(((KLE, Machine, invalid state)))
(((Cryptographic Locker, invalidation)))
A locker is _invalidated_ when it transitions to Error State `kl_state_invalid`.
<<Zkl-ISA-priv.adoc#KLE-exceptions>> treats the error conditions that raise exceptions.

[[KLE-GR-state-identifies-cc,GR17]]GR17:: When the CC is in _Ready_, _Success_, _Failure_ or an Error State, the _State_ field of the MDH holds that State, so that _State_ identifies it without inspecting other fields or the Content.

Other instructions, such as `kl.exec`, may also change the _State_, under conditions that the Machine specifies.

[[KLE-outcome-rules]]
=== Outcome of an Instruction on a Locker

[horizontal]
[[KLE-GR-outcome-by-state,GR20]]GR20:: After the checks that do not depend on the locker's _State_ (Rule <<KLE-GR-management-check-order>>), the outcome of a KLE instruction is determined by the State of the locker and the instruction class (<<KLE-instruction-properties>>), as described in the next three Rules.

[horizontal]
[[KLE-GR-outcome-inert,GR20.a]]GR20.a::: _Unconfigured_ locker, locker in an Error State, or, for an instruction that acts on the named locker, no named locker (`klnamedlocker` = 32): every instruction other than a <<KLE-destructive-config,destructive configuration instruction>> performs no operation and raises no exception; the _State_ is unchanged, an output operand is zeroed, and an inspection instruction returns zeros or the MDH (Rules <<KLE-GR-klnl-no-named-locker>>, <<KLE-GR-usage-locker-error-state>>–<<KLE-GR-fall-through-mgmt>>).
A `kl.setst` that replaces an Error State is no exception: it overwrites essentially all the locker holds (Rule <<KLE-GR-error-state-locker-is-only-MDH>>).
With no named locker, the destructive configuration instructions also perform no operation, an opening `kl.mgmt` included (Rules <<KLE-GR-klnl-no-named-locker>> and <<KLE-GR-klnl-openings>>).

[[KLE-GR-outcome-config-state,GR20.b]]GR20.b::: Locker in a Configuration State: the configuration instructions that the operation under way admits are admitted (Rules <<KLE-GR-config-instructions-config-state>>–<<KLE-GR-zkl-store-mv-allowed>>, <<KLE-locker-management>>), and every other instruction traps:
a transfer of the other direction, or a completing `kl.mgmt` with an inconsistent `ml`._State_, with an illegal-instruction exception (<<KLE-mv-locker-checks>>, <<KLE-locker-management>>); a usage instruction, a `kl.clone` from the locker or a `kl.restrict*` on it, with a KLE privilege-violation exception (Rule <<KLE-GR-usage-locker-config-state>>).

[[KLE-GR-outcome-valid-state,GR20.c]]GR20.c::: Locker in a Valid State: every configuration instruction is admitted (Rule <<KLE-GR-opening-locker-when>> for an opening `kl.mgmt`), except a transfer or a completing `kl.mgmt`, which raises an illegal-instruction exception, no management operation being under way (<<KLE-mv-locker-checks>>, Rule <<KLE-GR-fall-through-mgmt>>).
A usage instruction that the _UsagePolicy_ forbids raises a KLE privilege-violation exception (Rule <<KLE-GR-usage-policy>>); one that the Machine, the State or _MachinePolicy_ does not admit performs no operation and transitions the locker to Error State _Invalid_ (Rules <<KLE-GR-no-exec-in-ready>>, <<KLE-GR-success-failure>>, <<Zkl-ISA-machines.adoc#KLE-MGR-policy-gate>>); any other performs its operation, after the checks of Rule <<KLE-GR-gate-order>>.

=== Rules Governing Valid States

[horizontal]
[[KLE-GR-to-ready,GR21]]GR21:: `kl.setst` may always transition a locker from a Valid State to _Ready_.
//; no Machine may forbid it.
// NOTE: Since a locker can always be restored from a backup SCC, preventing transitions to _Ready_--as "GCM with Set IV" (<<KLE-GCM-with-IV-mode>>) does--is not an effective mitigation against the attacks that would be enabled by transitioning to _Ready_.

[[KLE-GR-same-state,GR22]]GR22:: In a Valid State other than _Success_ and _Failure_, `kl.setst` may be issued with the immediate of the current State.
Unless the Machine states otherwise, it repeats the operations of entering that State; in a State that loads a field, this restarts the load (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-load-long-field>>).
Where repeating them would produce an internal state that the referenced standard does not allow or define, the Machine either forbids the same-State `kl.setst`, which then transitions the locker to Error State _Invalid_ (for instance Rule <<Zkl-ISA-machines.adoc#KLE-MGR-no-hash-output-repeat>>), or defines a specific behavior.

[[KLE-GR-no-exec-in-ready,GR23]]GR23:: A `kl.exec` in State _Ready_ is admitted only where the Machine explicitly allows it (Rule <<KLE-GR-outcome-valid-state>>, Rule <<Zkl-ISA-machines.adoc#KLE-MGR-not-allowed-instructions>> in <<Zkl-ISA-machines.adoc#KLE-Machines>>).

[[KLE-GR-clearads,GR24]]GR24:: `kl.clearads` (<<KLE-instruction-clearads>>) is permitted in every Valid State.
It leaves _State_ unchanged, and _StateExtension_ too, except that it clears the flag of any material that Rule <<Zkl-ISA-machines.adoc#KLE-MGR-progress-discard>> destroys, such as `HasRndNum` of the ECC Machines; it is subject to Usage Control (Rule <<KLE-GR-outcome-valid-state>>).
It discards the implementation-defined state, in the ADS and in _MachineUse_ and _AuxInfo_ (<<KLE-MachineUse>>), including any that an interrupted long-running operation keeps: in a State of Rule <<Zkl-ISA-machines.adoc#KLE-MGR-progress-discard>> it zeroes the progress field _P_, and the operation restarts when its instruction is next issued, exactly as if the SCC exported before the `kl.clearads` had been imported on a different KLE implementation (Rule <<KLE-GR-long-running-restart>>).

[[KLE-GR-success-failure-cannot-be-set-directly,GR25]]GR25:: `kl.setst` cannot set States _Success_ and _Failure_ directly: the immediates 46 and 47 are reserved (<<KLE-illegal-instruction-grounds>>).

[[KLE-GR-setst-in-success-failure,GR26]]GR26:: In States _Success_ and _Failure_, `kl.setst` may be used to transition the locker to State _Unconfigured_, or to a given Error State, besides the options given by Rules <<KLE-GR-to-ready>> and <<KLE-GR-clearads>>.
// +
// NOTE: A Machines could try forbidding the return to _Ready_ to prevent nonce misuse, but software could bypass this by reloading a saved copy of the original SCC. Hence, the architecture chooses to allow the return to _Ready_ unconditionally for simplicity.
// The return may nevertheless erase session-bound internal state, such as randomly generated nonces, as the Machine specifies.

[[KLE-GR-success-failure,GR27]]GR27:: In States _Success_ and _Failure_, the only KLE instructions permitted are `kl.mgmt`, `kl.size`, `kl.avail`, `kl.setst` (subject to Rule <<KLE-GR-setst-in-success-failure>>), `kl.getmd*`, `kl.getst`, `kl.clone`, `kl.rename`, `kl.swap` and `kl.restrict*`.
No other usage instruction is admitted (Rule <<KLE-GR-outcome-valid-state>>, Rule <<Zkl-ISA-machines.adoc#KLE-MGR-not-allowed-instructions>> in <<Zkl-ISA-machines.adoc#KLE-Machines>>), `kl.derive` included (cf. definitions of <<KLE-source-endpoint>> and <<KLE-destination-endpoint>>).

[[KLE-GR-policy-narrowing-state,GR28]]GR28:: In a Valid State, _MachinePolicy_ enables the operation of the State and satisfies its entry conditions (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-policy-gate>>): a `kl.restrictl` or `kl.restrictv` (<<KLE-instruction-restrict>>) that would break this transitions the locker to Error State _Invalid_ instead.
To narrow a locker during an operation, software first returns it to _Ready_ (Rule <<KLE-GR-to-ready>>).
Metadata narrowing never changes _MachinePolicy_ (<<KLE-Metadata-narrowing>>), so this Rule applies only to `kl.restrictl` and `kl.restrictv`.

=== Rules governing Error States and the _Unconfigured_ State

[horizontal]
[[KLE-GR-clear-locker-content-error-state,GR29]]GR29:: On transitioning to an Error State, a locker clears its Content beyond the MDH, and releases the internal resources that held that Content, any ADS included; _AuxDataLen_ and _ADSDropped_ are set to 0.

[[KLE-GR-error-state-locker-is-only-MDH,GR30]]GR30::
A locker in an Error State holds only its MDH, and its size (<<KLE-instruction-size>>) is 16 bytes.

[[KLE-GR-error-state-can-be-reconfigured,GR31]]GR31:: A locker in an Error State can still be reconfigured, cloned or cleared; apart from clearing it, `kl.setst` can only change its Error State.

[[KLE-GR-error-state-exported-as-MDH,GR32]]GR32:: A locker in an Error State is exported as its MDH alone, with all its fields and without `kl.mgmt`, and a single `kl.mgmt` re-imports the image (<<KLE-error-state-transfer>>), so that software can handle the error even after a context switch.

[[KLE-GR-usage-locker-error-state,GR33]]GR33:: The architecture keeps no history of Error States: an attempt to _use_ a locker in an Error State, although an error that would otherwise transition the locker to _Invalid_, leaves the _State_ unchanged (Rule <<KLE-GR-outcome-inert>>), so that software can address the original error condition.

[[KLE-GR-zero-unwritten-output,GR34]]GR34:: A usage instruction with an output operand that performs no operation under Rule <<KLE-GR-usage-locker-error-state>> or <<KLE-GR-gate-order>> (_Unconfigured_, Error State, or expiration), or that transitions its locker to an Error State during execution, writes zeros to every byte of its output window that it has not written: elements [`vstart`, `vl`-1] of `Vd` for a vector output, bytes [`klstart`, `kliobuftop`-1] for a KLIOBUF output.
An in-place operation thus never leaves its input in place of the output it did not produce.
A Form D `kl.exec` that performs no operation takes a configured KLIOBUF as its output window, whatever its former native Form and with no length or granularity check, accesses no buffer if none is configured, and clears `klstart`.

[[KLE-GR-transition-to-from-unconfigured,GR35]]GR35:: Only a configuration instruction can transition a locker from _Unconfigured_ to a Complete State; a usage instruction falls through (Rule <<KLE-GR-outcome-inert>>), `kl.derive` if either endpoint is _Unconfigured_.
A locker leaves an Error State for _Unconfigured_ through `kl.clear` or `kl.clearall`, a `kl.rename` naming it as source, a `kl.clone` or `kl.rename` naming it as destination with an _Unconfigured_ source, a `kl.clone` naming it as destination that then traps, a `kl.swap` with an _Unconfigured_ locker (<<KLE-instruction-clone>>), or a provisioning- or import-opening `kl.mgmt`, which is a <<KLE-destructive-config,destructive configuration instruction>>.

[[KLE-GR-getmd-to-from-unconfigured,GR36]]GR36:: `kl.getmd*` (<<KLE-instruction-getmd>>) reads the MDH of an _Unconfigured_ locker as all zeros.

[[KLE-GR-cleared-under-management,GR37]]GR37:: The fall-through of Rule <<KLE-GR-outcome-inert>> applies to `kl.load`, `kl.store`, `kl.mvin` and `kl.mvout`, and to `kl.mgmt` with `kl_cfg_exporting` or `kl_cfg_management_end`, the short export path of an Error-State locker using no `kl.mgmt` (<<KLE-error-state-transfer>>); `klnamedlocker` = 32 is the value a clear leaves (<<KLE-CSR-klnamedlocker>>), as detailed in the next three Rules.

[horizontal]
[[KLE-GR-fall-through-load-store,GR37.a]]GR37.a::: Falling through, `kl.load` and `kl.store` access no memory, whatever `klstart` holds, and retire with `klstart` = 0. They can still raise the address-misaligned exception (<<KLE-instructions-memory>>), unless `klnamedlocker` = 32: they then fall through only with `Xl` = 0, before any check of `Zklio` or of the KLIOBUF.

[[KLE-GR-fall-through-mv,GR37.b]]GR37.b::: Falling through, `kl.mvin` and `kl.mvout` leave `klstart` unchanged, `kl.mvout` writes zeros, as when `klstart` {ge} `image_end` (<<KLE-instruction-mv>>), and the KLIOBUF variants check neither the KLIOBUF nor its alignment.

[[KLE-GR-fall-through-mgmt,GR37.c]]GR37.c::: Falling through, `kl.mgmt` reads neither its auxiliary operand nor the KLIOBUF (Rules <<KLE-GR-vector-MDH-operand>> and <<KLE-GR-iobuf-configured>> do not apply), keeps the authentication registers, and performs only its common steps (<<KLE-locker-management>>): `klstart` becomes 0, and `klnamedlocker` 32 on an _Unconfigured_ locker, or the locker's number on an Error-State one.
On a Valid locker, `kl_cfg_management_end` still raises an illegal-instruction exception.

[[KLE-GR-management-check-order,GR38]]GR38:: The checks that do not depend on the locker's _State_ precede the outcomes of Rules <<KLE-GR-outcome-inert>>–<<KLE-GR-outcome-valid-state>> and <<KLE-GR-cleared-under-management>>–<<KLE-GR-fall-through-mgmt>>: the first group of <<KLE-illegal-instruction-grounds>>, the KLE fatal-error, missing-CSK and locker-Off exceptions, for `kl.mgmt` the check of `klnamedlocker`, for `kl.load` and `kl.store` with `klnamedlocker` < 32 the check that `Xl` is 0, and for a Form A–C `kl.exec` the check of `klstart` against `vstart` (Rule <<KLE-GR-klstart-vstart>>).

[NOTE]
====
The Rule closes a _check-then-use race_: between a _State_ check and the next instruction, a handler may clear a locker being provisioned or imported, which sets `klnamedlocker` to 32 and forces a restart (<<KLE-CC-management>>), or set an Error State.
The instructions that follow then perform no operation, a `KLNL` opening with `klnamedlocker` = 32 included (Rule <<KLE-GR-klnl-openings>>), instead of acting on the KLIOBUF or trapping, and the next check detects the change.
Only the check after the last instruction is therefore required; earlier checks only react sooner.
An export cannot restart, since the clear destroys its CC.
====

[horizontal]
[[KLE-GR-gate-order,GR39]]GR39:: For a usage instruction (<<KLE-instruction-properties>> in Rule <<KLE-GR-usage-policy>>), the checks of Rule <<KLE-GR-management-check-order>> are followed by the conditions on the locker, in this order, the first that applies deciding the outcome:
+
--
. _Unconfigured_: no operation and no exception (Rule <<KLE-GR-transition-to-from-unconfigured>>);
. Error State: no operation and no exception (Rule <<KLE-GR-usage-locker-error-state>>);
. Configuration State: KLE privilege-violation exception, the _State_ unchanged (Rule <<KLE-GR-usage-locker-config-state>>);
. a forbidden KLIOBUF substitution: illegal-instruction exception (<<KLE-illegal-instruction-grounds>>);
. a KLIOBUF required by a substitution but unconfigured: illegal-instruction exception (Rule <<KLE-GR-iobuf-configured>>);
. _UsagePolicy_: KLE privilege-violation exception (Rule <<KLE-GR-outcome-valid-state>>);
. _ExpirationDate_: transition to Error State `kl_state_expired`, then no operation; if the secure clock cannot be read, KLE clock-unavailable exception, the _State_ unchanged (<<KLE-Metadata-expiration-date>>);
. the Machine's own rules.

For `kl.derive`, each condition is evaluated for both endpoints, the source first, before the next condition; an _Unconfigured_ or Error-State endpoint makes the instruction a no-op.
--

// [[KLE-fall-through-summary]]
// ==== Summary of Behavior of KLE Instructions on Unconfigured or Error State Lockers

<<KLE-insns-on-unconf-or-error-locker>> summarizes the outcome of every instruction on an _Unconfigured_ or Error-State locker.
Usage instructions fall through after the checks that precede the conditions on the locker (Rule <<KLE-GR-gate-order>>): they perform no operation and leave the MDH, hence the original error condition, unchanged, so that neither the _UsagePolicy_ nor the _ExpirationDate_ is evaluated.
Configuration instructions perform as expected.

[[KLE-insns-on-unconf-or-error-locker]]
.Behavior of instructions on an _Unconfigured_ or Error State locker
[float="center",align="center",width="100%",cols="<1,<1,<1",options="header"]
|===
| Instruction                                  | Outcome on an _Unconfigured_ locker | Outcome in an Error State
| <<KLE-instruction-size,kl.size Form A>>      | Returns 0. | Returns 16.
| <<KLE-instruction-size,kl.avail Form A>>     | Returns 0. | Evaluates the MDH fields that identify the Machine.

| <<KLE-instruction-load,kl.load>>, <<KLE-instruction-store,kl.store>>, +
<<KLE-instruction-mv,kl.mvin and kl.mvout>>
2+| `kl.load` and `kl.store` perform no operation and retire with `klstart` = 0. `kl.mvin` writes nothing into the locker, `kl.mvout` reads zeros from it, and both leave `klstart` unchanged. The _State_ causes no exception.

| Usage instructions +

=== Rules governing Configuration States

A locker can always be reconfigured: a management operation can be opened in every State that Rule <<KLE-GR-opening-locker-when>> lists, a destructive configuration instruction is admitted in every State, and neither a Machine nor a _UsagePolicy_ may restrict them, so that a new CC can always be placed, even when every locker is in use, and the exits from an Error State (Rule <<KLE-GR-error-state-can-be-reconfigured>>) are always open.
A saved SCC can always be reloaded, so refusing a configuration transition would protect nothing and only deny a resource.

[horizontal]
[[KLE-GR-opening-locker-when,GR40]]GR40:: _When a locker can be opened:_
Opening a locker for provisioning or import, and executing `kl.clear`, is allowed in every State, since these are <<KLE-destructive-config,destructive configuration instructions>>; opening it for export is allowed in every Complete or Configuration State.
No Machine may set conditions under which a locker can be opened for export or import, or cleared.

[[KLE-GR-config-instructions-config-state,GR41]]GR41:: The following configuration instructions, which Usage Control policies do not gate, are also allowed on a locker in a Configuration State: `kl.size`, `kl.avail`, `kl.getmd*`, `kl.getst`, `kl.setst` with the immediate `kl_state_unconfigured` (`kl.clear`) or an Error State, `kl.clearall`, `kl.clone` naming the locker as destination, and `kl.rename` and `kl.swap`, which move a CC unchanged (<<KLE-instruction-clone>>).

[[KLE-GR-zkl-load-mv-allowed,GR42]]GR42:: `kl.load` and `kl.mvin` are allowed in States `kl_cfg_provisioning`, `kl_cfg_importing` and `kl_cfg_ppi_importing`, on the locker that `klnamedlocker` names (Rule <<KLE-GR-locker-less-transfers>>).

[[KLE-GR-zkl-store-mv-allowed,GR43]]GR43:: `kl.store` and `kl.mvout` are allowed in States `kl_cfg_exporting` and `kl_cfg_ppi_exporting`, on the locker that `klnamedlocker` names (Rule <<KLE-GR-locker-less-transfers>>).

[[KLE-GR-usage-locker-config-state,GR44]]GR44:: On a locker in a Configuration State, a usage instruction, a `kl.clone` into another locker, and a `kl.restrict*` raise a KLE privilege-violation exception and leave the _State_ unchanged.

[[KLE-GR-completion-state,GR45]]GR45:: The completing `kl.mgmt` (<<KLE-locker-management>>) leaves the locker:
+
--
* after a provisioning, in State _Ready_, with _StateExtension_ and _MachineUse_ zero;
* after an import or an export, in the _State_ supplied in `ml`, that is, the one the locker had when it was exported, resp. when the export was opened, which may itself be a Configuration State; an import thus restores the _State_ and _StateExtension_ that the locker had at export, the latter carried in the SCC; or
* in an Error State, or in _Failure_, if a check made at completion fails: _Authentication Failed_ for the `SIV` check, and otherwise the outcome that the failing check prescribes.
--

[[KLE-derivation-rules]]
=== Derivation Rules

The Rules of this section apply Principle <<KLE-ISA-Principle-no-privilege-elevation>> to `kl.derive`, with the transfer classes that <<KLE-instruction-derive>> defines.

[horizontal]
[[KLE-GR-checks,GR46]]GR46:: The checks of Rule <<KLE-GR-gate-order>> apply to both lockers, in the order it gives for `kl.derive`.
The following checks are then made in order, at issue and on resumption; a failed check transitions the locker named to Error State _Invalid_ (Rule <<KLE-GR-clear-locker-content-error-state>>), and nothing more is transferred:

. The source must be a source endpoint; otherwise the source.
. The destination must be a destination endpoint; otherwise the destination.
. The pair must be admitted; otherwise both.
. The effective length (Rule <<KLE-GR-derive-rule-both-fixed-size>>) must meet the length constraints of the destination, a final partial input unit included, and the untransferred suffix must fit its remaining capacity; otherwise the destination.
. A destination key field of `dest_length` bytes is always loaded in full: it requires `length` {ge} `dest_length`, `klstart` = 0, and a source field, or remaining `kl.exec` output, of at least `dest_length` bytes; otherwise the destination. The key field receives exactly `dest_length` bytes, which complete its loading; a key written in State _Ready_ is followed by the initialization that the Machine performs in that State.
A message input receiving a shared secret (Rule <<KLE-GR-shared-secret>>) requires `length` at least the length of the secret, and `klstart` = 0; otherwise the destination.
. The endpoint granularities must be compatible as Rule <<KLE-GR-derive-rule-both-fixed-size>> specifies; otherwise both.
. For any other destination, if `klstart` {ge} `eff_length`, `length` = 0 included, the instruction retires with `klstart` = 0, skipping the remaining checks and changing nothing else.
. An interior non-zero `klstart` must be an admitted common interruption point of the two endpoints (Rule <<KLE-GR-derive-rule-both-fixed-size>>); otherwise both.
. The source must be able to supply the untransferred suffix, a final partial output unit included (Rule <<KLE-GR-derive-rule-both-fixed-size>>); otherwise the source.
+
Apart from their failure outcomes, these checks change nothing; the checks on the transferred values are made per unit (Rule <<KLE-GR-derive-rule-both-fixed-size>>).

[[KLE-GR-narrowing,GR47]]GR47:: Before a nonempty _restricted transfer_ that Rule <<KLE-GR-checks>> admits, the _SCProtection_ of the destination locker is compared with that of the source.
If it is lower, the destination transitions to Error State _Privilege Violation_ and nothing is transferred: a narrowing never raises the level of the destination (<<KLE-Metadata-narrowing>>), and the secret would otherwise be used with weaker side-channel protection than its source requires.
Otherwise the MDH of the source narrows that of the destination (<<KLE-Metadata-narrowing>>); if the narrowing fails, the destination transitions to Error State _Privilege Violation_ and nothing more is transferred.
The narrowed policies govern the transfer, but are written only with its first committed unit (Rule <<KLE-GR-derive-rule-both-fixed-size>>), so that a transfer that commits nothing leaves them unchanged; a resumed transfer narrows again, against the current MDHs.

[[KLE-GR-unrestricted,GR48]]GR48:: An _unrestricted transfer_ applies no policy narrowing.

[[KLE-GR-SKID-no-export,GR49]]GR49:: A field configured by a SKID is _never_ exportable, and a key field of a locker whose _KeyType_ is 1 is _never_ importable. No rule may be defined to export or import such a field.

[[KLE-GR-shared-secret,GR50]]GR50:: Moving a shared secret from a key-agreement or key-encapsulation Machine, such as the shared secret of an ECC Machine in _Output_ or the ML-KEM `sharedkey`, is a _restricted transfer_ into a key field of a symmetric Machine or a private key field of a public-key Machine, which receives the first `dest_length` bytes of the secret, and into the `kl.exec` input of a hash function, MAC or XOF that <<Zkl-ISA-machines.adoc#KLE-derive-endpoints>> lists for it, which receives the whole secret.
Rule <<KLE-GR-checks>> item 5 checks the length and `klstart` of both, and Rule <<KLE-GR-uninterruptible-class>> makes both uninterruptible.
No other message input receives a shared secret, not even one that a Machine defines (<<Zkl-rules-explanation.adoc#KLE-residue-GR>>).

[[KLE-GR-exec-implies-unrestricted,GR51]]GR51:: The `kl.exec` output of a source can always be moved, as an _unrestricted transfer_, into the `kl.exec` input of a destination, such as that of a hash function, MAC or XOF, or into a key field of a symmetric Machine or a private key field of a public-key Machine, which receives the first `dest_length` bytes of the output (Rule <<KLE-GR-checks>> item 5).
The transfer is a shortcut for instructions that software could issue anyway: `kl.exec` on the source, and on the destination `kl.exec` or a provisioning with a key of its choice.
Some pairs are unusual, such as keystream or a signature into a key field, and no protocol would use them, but none is an attack vector: software could read the output and provision a locker with it as its key.
// +
// NOTE: Such transfers are allowed and unrestricted because the caller can obtain the same data and write the destination fields.
// NOTE: Such a destination may be a key field, such as the `Scalar` of an ECC Machine or the `K0` of HMAC. Moving any `kl.exec` output into it does not increase the attack surface, which is why
// software can always provision a new locker with a key of its choice and any policies, and use it in place of a locker whose key it does not know.

[[KLE-GR-DRBG-implies-unrestricted,GR52]]GR52:: A Machine implementing a DRBG (none is currently architected) may generate random data into a symmetric or private key field of a destination Machine in a State that admits the field as a destination.
This is an _unrestricted transfer_, since the output of a DRBG must neither predictably repeat a value nor be extrapolable from previous or later outputs.

[[KLE-GR-derive-rule-both-fixed-size,GR53]]GR53:: _Transfer size and progress:_
A destination field of `dest_length` bytes receives `eff_length` = min(`length`, `dest_length`) bytes and is zero-filled beyond them, any other destination `eff_length` = `length` bytes.
Each endpoint advances as the `kl.exec` instructions producing or consuming the bytes would, except that a field source does not advance: byte `i` of the transfer, counted across resumptions, is byte `i` of the field, or zero beyond its end, so that the field can be derived any number of times.
+
The granularities of the two endpoints must divide one another, and the bytes move in _units_ of the larger one, the last possibly shorter, each committed at both endpoints at once, with any narrowing (Rule <<KLE-GR-narrowing>>).
The interruption points are the unit boundaries that both endpoints admit, from which a halted transfer resumes at `klstart`.
A field that fails a check when its transfer completes (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-check-on-write>>) leaves its locker in the outcome its Machine specifies, or _Invalid_, and the instruction retires, the source keeping the effects of the units already transferred; every check that can raise an exception precedes the first unit.

////
[[KLE-GR-derive-rule-both-fixed-size,GR53]]GR53:: _Transfer size and progress:_
A destination field of `dest_length` bytes receives `eff_length` = min(`length`, `dest_length`) bytes, any other destination `eff_length` = `length` bytes: the byte window is `[0, eff_length)`, and a resumed transfer continues from byte `klstart` of it.
With `length` = 0 nothing is transferred: a key field fails Rule <<KLE-GR-checks>> item 5; for any other destination the instruction only clears `klstart`, if the other checks of that Rule pass.
+
The source supplies `eff_length` bytes: a field is truncated or zero-padded to that length, and a source that produces `b`-byte blocks produces as many as needed.
The destination consumes them in equal-sized blocks, a shorter final block as a `kl.exec` with a shorter input would.
Each endpoint advances as the `kl.exec` operations producing or consuming these blocks would; a destination State implemented by `process_VLI` may be left open and continued with `kl.exec`.
A field source does not advance: every `kl.derive` transfers the whole field from its beginning, as a complete emission by `kl.exec` would, but without using or changing the transfer counter of the State, so that the field can be derived any number of times.
+
If the source produces `p`-byte units and the destination consumes `q`-byte units, `p` and `q` being the granularities of the two States, one must divide the other, so that the implementation can split one output into `p/q` inputs, or join `q/p` outputs into one input, without carrying partial state from one internal transfer of `max(p,q)` bytes to the next.
+
The interruption points of a `kl.derive` (Rule <<KLE-GR-interruption-point>>) are the `klstart` values that are interruption points in the current States of both endpoints.
A `kl.derive` into a key field, or of a shared secret into a message input (Rule <<KLE-GR-shared-secret>>), is uninterruptible (Rule <<KLE-GR-uninterruptible-class>>): its only interruption point is 0, so that the key, with the initialization that the Machine performs in _Ready_, or the whole secret, enters the destination in one execution, and no locker ever holds a partly written key or a part of a secret.
////

[[KLE-Memory-Model]]
=== Memory Model Rules

In these rules, a _KLE memory instruction_ is `kl.load`, `kl.store`, `kl.input` or `kl.output`.

[horizontal]
[[KLE-GR-memory-program-order,GR54]]GR54:: KLE memory instructions appear to execute in program order on the local hart.

[[KLE-GR-memory-rvwmo,GR55]]GR55:: At the instruction level, KLE memory instructions follow RVWMO, and, with `Ztso`, also RVTSO.

[[KLE-GR-idempotent-memory,GR56]]GR56:: KLE memory instructions support only idempotent memory: they make no component access to a non-idempotent or side-effecting PMA region.
An instruction whose component access would touch such a region halts precisely at the last prefix-complete point before the offending byte, with the completed prefix committed (Rule <<KLE-GR-precise-halt>>), and raises a load, resp. store, access-fault exception, with `xepc` at the instruction and `xtval` holding the offending address.
Re-execution raises the same exception before any component access, unless the offending byte no longer maps to such a region.

[[KLE-rule-memory-instruction-decomposed,GR57]]GR57:: A KLE memory instruction may be decomposed into component memory operations of any granularity, issued in any order that the memory model and the semantics of `kl.exec`, `kl.load`, `kl.store`, `kl.input` and `kl.output` allow, and none is required to be atomic; ordering within one instruction follows RVWMO, even with `Ztso`.

[[KLE-GR-prefix-complete,GR58]]GR58:: On a precise halt, `klstart` records a _prefix-complete_ point of the transfer: an offset below which every component access has been performed.
As RVV 1.0 permits for `vstart` ("Precise vector traps"), a component access at or beyond it may already have had an architecturally visible effect, since re-executing the instruction from that point produces the correct final state: the source and the destination of a KLE memory instruction never overlap.
The recorded point never moves back over a prefix committed in this or an earlier attempt.

[[KLE-GR-memory-no-random-no-clock,GR59]]GR59:: No component operation of a KLE memory instruction draws random bits (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-atomic-randomness>>) or reads the clock (<<KLE-Metadata-expiration-date>>).

[[KLE-GR-memory-observation,GR60]]GR60:: Other harts observe the component memory operations as ordinary memory operations under RVWMO, with no ordering among them guaranteed before the instruction completes.
A buffer that a KLE memory instruction accesses therefore needs the same synchronization to be shared as one that an ordinary software loop accesses.

[[KLE-GR-memory-fences,GR61]]GR61:: For `FENCE`, `FENCE.I`, `SFENCE.VMA` and the `.aq`/`.rl` annotations, the component accesses of a KLE memory instruction are ordinary loads (`kl.load`, `kl.input`) or stores (`kl.store`, `kl.output`) of the issuing hart.

[[KLE-GR-memory-instructions,GR62]]GR62:: KLE memory instructions are RISC-V memory instructions: one completes, and may retire or take a trap with `xepc` past it, only after every component access has passed address translation and permission checks and has been performed.
Otherwise, as for vector memory operations, the implementation triggers a precise load/store page-fault, guest-page-fault or access-fault exception for that execution attempt, with `klstart` at a prefix-complete point that the instruction permits.

NOTE: After the last `kl.load`, `kl.store`, `kl.mvin` or `kl.mvout` of a management operation, the caller checks whether the locker is _Unconfigured_; checking after each one only reacts sooner.
With `kl.getst Xd, KLNL` (Rule <<KLE-GR-klnamedlocker-override>>) the check needs no locker number, and reads zero once a clear has reset `klnamedlocker` to 32.
If the locker is _Unconfigured_, a handler has cleared it, and the software restarts the entire configuration operation, not only the memory operation.
A memory operation issued or resumed after the locker was cleared performs no operation, so the caller always reaches this check (Rule <<KLE-GR-fall-through-load-store>>).

=== State changes under exceptions

[horizontal]
[[KLE-exception-state-change,GR63]]GR63:: A KLE fatal-error exception resets the KLE state (KLE fatal-error in <<KLE-exception-error-correspondence>>). Any other exception leaves the KLE state unchanged, except for these changes, made even when the instruction then raises an exception:
+
--
* the destructive step (<<KLE-destructive-config>>) of a provisioning- or import-opening `kl.mgmt`, which zeroizes the locker and writes its number to `klnamedlocker` (<<KLE-locker-management>>), and of a `kl.clone`, which clears its destination as `kl.clear` would (<<KLE-instruction-clone>>);
* the clearing of `klstart` by any `kl.mgmt` that passes its `klnamedlocker` check (<<KLE-locker-management>>); and
* the completed prefix, and the `klstart` that records it, that a memory instruction commits when one of its component accesses raises a memory exception (Rules <<KLE-GR-memory-instructions>> and <<KLE-GR-resumability-options>>).
--
+
For a resumed instruction, the unchanged state is that at its resumption, with the prefix committed before it.

[[KLE-klstart-rules]]
=== Rules Governing `klstart`

[horizontal]
[[KLE-GR-klstart-updates,GR64]]GR64:: An instruction that honors `klstart` (<<KLE-CSR-klstart>>) records in it a prefix-complete point on a precise halt (Rule <<KLE-GR-precise-halt>>) and writes 0 to it when it retires, except `kl.mvin` and `kl.mvout`, which keep it (<<KLE-instruction-mv>>).
`kl.clearall`, `kl.mgmt` after its check of `klnamedlocker` (<<KLE-locker-management>>), and a Form D `kl.exec` that performs no operation (Rule <<KLE-GR-zero-unwritten-output>>) write 0 to it; every other instruction leaves it unchanged.

[[KLE-GR-interruption-point,GR65]]GR65:: An _interruption point_ of a KLE instruction in a State of a Machine is a `klstart` value that the instruction can itself produce on a precise halt in that State: the whole multiples of the Machine's granularity within the transfer window, unless the Machine, or a procedure such as `process_VLI` (<<Zkl-ISA-machines.adoc#KLE-process-VLI>>), defines another set.

[[KLE-GR-transfer-window-checks,GR66]]GR66:: A Form A–C `kl.exec`, or a Form D `kl.exec` that substitutes for one (<<KLE-usage-input-output>>), checks its transfer window after the checks of Rule <<KLE-GR-gate-order>> and those that make it illegal in the locker's _State_ (Rules <<KLE-GR-no-exec-in-ready>> and <<Zkl-ISA-machines.adoc#KLE-MGR-not-allowed-instructions>>), in this order:
+
. A length invalid for the Machine transitions the locker to Error State _Invalid_ (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-granularity>>).
. A `klstart` {ge} the length, which includes a valid length 0, makes the window _empty_: the instruction writes 0 to `klstart` and does not reach the Machine, so it is not the `kl.exec` that a State admits (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-single-last-block>>).
. Any other `klstart` that is not an interruption point (Rule <<KLE-GR-interruption-point>>) transitions the locker to Error State _Invalid_, and the unwritten part of the output window is zeroed (Rule <<KLE-GR-zero-unwritten-output>>).

[[KLE-resumability]]
=== Interruptibility and Resumability of KLE instructions

[horizontal]
[[KLE-GR-halted-state,GR67]]GR67:: The state that a halted instruction leaves is described entirely by the locker, `klstart`, `vstart` and, for the long-running operations of Rule <<KLE-GR-long-running-no-data>>, the progress recorded in _MachineUse_ and the ADS.

[[KLE-GR-interruptibility-classes,GR68]]GR68:: Every KLE instruction is either uninterruptible or resumable, as the next two Rules list.

[horizontal]
[[KLE-GR-uninterruptible-class,GR68.a]]GR68.a::: The _uninterruptible_ instructions are `kl.mgmt`, `kl.setst`, with `kl.clear`, `kl.clearall` and `kl.clearads`, `kl.getmd*`, `kl.getnl`, `kl.setnl`, `kl.setnli`, `kl.restrict*`, `kl.clone`, `kl.rename`, `kl.swap`, `kl.size`, `kl.avail`, the GPR and KLIOBUF variants of `kl.mvin` and `kl.mvout`, and a `kl.derive` into a key field or of a shared secret (Rule <<KLE-GR-shared-secret>>).

[[KLE-GR-resumable-class,GR68.b]]GR68.b::: The _resumable_ instructions are `kl.exec`, vector `kl.mvin` and `kl.mvout`, which transfer several 128-bit blocks and halt only at a block boundary, any `kl.derive` that Rule <<KLE-GR-uninterruptible-class>> does not list, and `kl.load`, `kl.store`, `kl.input` and `kl.output`, which architecturally process their input units serially.

[[KLE-GR-uninterruptible-instructions,GR69]]GR69:: An uninterruptible instruction (Rule <<KLE-GR-uninterruptible-class>>) completes, raises an exception with only the effects of Rule <<KLE-exception-state-change>>, or has no architecturally visible effect, except that a long-running operation (Rule <<KLE-GR-long-running-no-data>>) halts as Rule <<KLE-GR-long-running-preemption>> states, with its progress recorded in _MachineUse_, a field of the MDH (Rule <<KLE-GR-long-running-progress>>).
For `kl.derive`, this ensures that no locker ever holds a partly written key or a part of a shared secret.
An implementation achieves this by:
+
--
. completing the instruction before taking an asynchronous interrupt;
. completing it in the background, where Rule <<KLE-GR-long-running-preemption>> permits, subject to Rule <<KLE-GR-conflicting-access-rule>>; or
. discarding partial work before taking the trap and restarting on return, with a documented minimum uninterrupted progress, or maximum number of consecutive restarts, that prevents livelock.

Software interacts with an uninterruptible instruction as Rule <<KLE-SR-uninterruptible>> states.
--

[[KLE-GR-no-intra-interruption-points,GR70]]GR70:: The architecture specifies no interruption point within `kl.setst` or within a single block-processing unit of `kl.exec`; an implementation may nevertheless make a long-running instance of either interruptible, as Rule <<KLE-GR-long-running-preemption>> allows.

[[KLE-GR-resumability-options,GR71]]GR71:: When a handler accesses an input, output or locker of a preempted instruction, or other KLE state the instruction may affect, the implementation chooses one of:
+
--
. _Background completion:_ the hart waits for the instruction to complete; not for the memory instructions `kl.load`, `kl.store`, `kl.input` and `kl.output`.
. _Atomic completion_ before the interrupt is taken.
. _Precise halt and resumption_ at the prefix-complete point that `klstart` records (Rule <<KLE-GR-prefix-complete>>); as for `vstart` in RVV 1.0, forward progress must eventually be guaranteed for the granule that `klstart` reports.
. _Timeout, then precise halt and resumption:_ option 3, after a system-imposed timeout.
. _Precise halt and restart_ at `klstart` = 0, discarding all partial work: for a memory instruction, only while none of its component accesses, in this or an earlier attempt, has had a visible effect, and at most a documented number of consecutive times, after which option 3 applies; for an internal computation of Rule <<KLE-GR-long-running-no-data>>, under its own restart rules, keeping the committed prefix of the enclosing instruction.

Block-iterated instructions, `kl.exec`, `kl.derive` and vector `kl.mvin` and `kl.mvout`, use option 3 or 4 (Rule <<KLE-GR-block-iterated-instructions>>).
A synchronous exception raised by a component access halts the instruction precisely, with `klstart` at the last prefix-complete point before the faulting byte (RVV 1.0 §3.7).
--

[[KLE-GR-precise-halt,GR72]]GR72:: On a precise halt of a resumable instruction (Rule <<KLE-GR-resumable-class>>), the completed prefix is committed, the failing and subsequent units have no effect, except as Rule <<KLE-GR-prefix-complete>> permits for a memory instruction, `klstart` records a prefix-complete point, and the instruction does not retire, `xepc` holding its address.
If the instruction transitions its locker to an Error State after partial progress, the completed prefix remains committed, the unwritten part of its output window is zeroed (Rule <<KLE-GR-zero-unwritten-output>>), and the instruction retires (Rule <<KLE-GR-klstart-updates>>).

[[KLE-GR-block-iterated-instructions,GR73]]GR73:: For a block-iterated `kl.exec`, `kl.mvin`, `kl.mvout` or `kl.derive`, the fully processed blocks remain written or transferred, at both endpoints of a transfer, and `klstart` records their total byte count.
Implementations must honor `klstart` for `kl.exec` and `kl.derive`: a handler that resets `klstart` to 0 to make the instruction execute anew over its whole window, but from the state that the completed prefix committed, may cause partial plaintext leakage or multi-use pads, which is the rationale for Rule <<KLE-SR-klstart-no-reset>>.

[[KLE-GR-conflicting-access-rule,GR74]]GR74:: Every option of Rule <<KLE-GR-resumability-options>> obeys one rule: before the issuing hart performs a _conflicting access_, the in-flight operation must have completed, or have halted precisely with `klstart` set as Rule <<KLE-GR-prefix-complete>> requires.
A conflicting access is:
+
--
* an ordinary load or store overlapping the memory region of the in-flight KLE operation;
* an access to a locker that the operation uses, including the issue of another KLE instruction involving it;
* a read or write of `klstart`, `vstart`, `klnamedlocker` or a KLIOBUF CSR, including by `kl.getnl`, `kl.setnl` and `kl.setnli`, since the operation may still update them (Rule <<KLE-GR-klstart-vstart>>, <<KLE-locker-management>>);
* the issue of a KLE instruction that reads or writes the authentication registers `SIV`, `IMPQUAL` and `SIV2` (<<KLE-KLF>>), such as an export- or import-opening `kl.mgmt`, while the operation reads or writes them;
* a read or write of a GPR or vector register that the operation writes; or
* a write to a vector register or to the KLIOBUF that the operation reads, including the issue of a `kl.input` targeting it.
Scalar operands in GPRs are captured at issue, so accessing them is not a conflicting access.

NOTE: This Rule and Rule <<KLE-GR-resumability-options>> make asynchronous execution by the KLE unit invisible to same-hart program order, as <<KLE-Memory-Model>> requires.
Beyond them, the architecture specifies only the allowed interruption points of its instructions and Machines.
--

[[KLE-GR-long-running-no-data,GR75]]GR75:: A `kl.exec`, `kl.setst` or `kl.derive` that accesses only its lockers and the scalar operands captured at issue may be _long-running_, such as a scalar multiplication, a key generation or a signature; so may a _component operation_ of one, a computation on state already in its lockers between the reading of its inputs and the writing of its outputs, such as the completion of the load of a field.
The next four Rules govern such an operation.

[horizontal]
[[KLE-GR-long-running-preemption,GR75.a]]GR75.a::: On preemption, a long-running operation behaves as an option of Rule <<KLE-GR-resumability-options>> that the interrupt or exception allows; the implementation supports option 3, 4 or 5, under option 5 with a documented minimum uninterrupted progress, or maximum number of consecutive restarts, against livelock.
A conflicting access, even by a nested handler, waits for an operation that continues in the background (Rule <<KLE-GR-conflicting-access-rule>>).

[[KLE-GR-long-running-progress,GR75.b]]GR75.b::: A long-running operation that halts records its progress in _MachineUse_, part of the MDH, not in `klstart`, in an implementation-defined format, and keeps its intermediate results in the ADS, updating the architected Content only at completion, so that a restart starts from the Content alone.
It may halt only where the recorded state cannot be consumed against other inputs, which Rule <<Zkl-ISA-machines.adoc#KLE-MGR-progress-discard>> ensures by discarding that state on every transition of the locker's _State_ other than completion.

[[KLE-GR-long-running-restart,GR75.c]]GR75.c::: An import may restart a halted long-running operation, discarding the ADS, and must restart it when the import completes without `Content2`, for any reason, such as an Implementation Qualifier mismatch, a failed `SIV2` check or _ADSDropped_ = 1 (<<KLE-SCC-import>>), for instance after a `kl.clearads` (<<KLE-instruction-clearads>>); `kl.clone` restarts it in the copy (<<KLE-instruction-clone>>).
A restart zeroes the progress and destroys every value drawn or computed for the operation (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-progress-discard>>).

[[KLE-GR-long-running-drawn-values,GR75.d]]GR75.d::: A Machine may keep a drawn value in the architected Content, such as the `RndNum` of the ECC Machines (<<Zkl-ISA-machines.adoc#KLE-ECC>>) or the `rnd` of ML-DSA (<<Zkl-ISA-machines.adoc#KLE-PQC-ML-DSA>>), although Rule <<KLE-GR-long-running-progress>> updates the Content only at completion: the value is architected state, even though it is meaningful only while the progress is non-zero, and a restart discards it (Rule <<KLE-GR-long-running-restart>>).

[[KLE-randomness]]
=== Randomness

Instructions that draw random bits transfer no data, and instructions that transfer data never wait for random bits, also when resumed (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-atomic-randomness>>): a nonce, for instance, is generated in the locker by one instruction and used by later ones.

[horizontal]
[[KLE-GR-rbg-failure,GR76]]GR76:: _RBG failure:_ if the entropy source has failed permanently (for `Zkr`, the DEAD state), then an operation that needs random bits is not performed, and its locker transitions to _Invalid_, not _Failure_.
If the bits are only temporarily unavailable, the instruction waits, or is interrupted and then resumed or restarted, as Rules <<KLE-GR-uninterruptible-instructions>> and <<KLE-GR-resumability-options>> allow for it; past an implementation-defined bound, it raises a KLE RBG-unavailable exception and leaves the _State_ unchanged.
A health-test failure from which the entropy source can recover makes the bits temporarily unavailable.
+
NOTE: Such an event should be rare, since for most applications Machines will need fresh bits from a DRBG and not directly from a conditioned entropy source.

[[KLE-error-architecture]]
== Error Handling Architecture

An error condition has one of three outcomes:

* it raises an exception, which a handler may resolve, with only the effects of Rule <<KLE-exception-state-change>>;
* it is recorded in the locker as an Error State, which travels with the CC and stays readable until the locker is reconfigured; or
* on an inert locker, _Unconfigured_ or in an Error State, or with no named locker, the instruction performs no operation and raises no exception, so that software checks the _State_ once, after its last step.

This section lists the error conditions by outcome, as a checklist for implementers and a reference for handler writers; the referenced sections specify them, and Rules <<KLE-GR-management-check-order>> and <<KLE-GR-gate-order>> give the order in which they are checked.

[[KLE-exception-error-correspondence]]
=== Exceptions

The exceptions are listed in the priority order of <<Zkl-ISA-priv.adoc#KLE-exception-codes>>, except that the two groups of illegal-instruction grounds are listed one after the other.
For a KLE exception, _Handler_ gives the Error State that a handler which neither resolves nor forwards it sets under Rule <<KLE-SR-handler-duty>>; the exception itself sets none.
For `kl.clone` and `kl.derive`, which name two lockers, that State is set on the locker on which the exception is raised: for `kl.clone`, the destination of a KLE out-of-memory exception; for `kl.derive`, the endpoint where the failing check is detected, the source being checked first (Rule <<KLE-GR-gate-order>>).

[[KLE-illegal-instruction-grounds,Illegal-Instruction Exceptions]]Illegal-instruction::
+
--
The first group of grounds depends only on the instruction encoding, the GPRs and the vector configuration:

. A reserved encoding: of `kl.setst` (<<KLE-instruction-setst>>) or `kl.mgmt` (<<KLE-management-immeds>>), `KLNL` where Rule <<KLE-GR-klnamedlocker-override>> does not admit it, or a vector operand while `vtype.vill` is set (<<KLE-KLV>>).
. A reserved value of `r` or `R` (Rule <<KLE-GR-r-R-fields>>), or, in a `kl.derive` with `R` = `00`, equal locker indices (<<KLE-instruction-derive>>).
. A GPR pair or quartet not meeting Rule <<KLE-GR-multiple-GPRs>>.
. A vector operand that Rules <<KLE-GR-vector-MDH-operand>> and <<KLE-GR-vector-legality>>, or <<KLE-instruction-mv>>, exclude.
. An encoding of an unimplemented extension.
. An access denied by `KLS` = Off or by a `*stateen0` gate, or to a CSR unavailable in the current mode (<<KLE-CSRs-unpriv>>, <<Zkl-ISA-priv.adoc#KLE-privileged-CSRs>>); an `hstateen0` denial while V=1 raises a virtual-instruction exception instead.

The second group depends on the state of the KLE unit:

. A transfer that the locker's _State_ does not admit, or a misaligned `klstart` (<<KLE-mv-locker-checks>>).
. A `kl.mgmt` out of sequence (Rule <<KLE-GR-mgmt-klnamedlocker-check>>, <<KLE-locker-management>>).
. A KLIOBUF substitution that <<KLE-usage-input-output>> forbids.
. An MDH operand of `kl.mgmt` shorter than 128 bits (Rule <<KLE-GR-vector-MDH-operand>>).
. A Form A–C `kl.exec` with `klstart` {ne} `vstart` {times} `SEW` / 8 (Rule <<KLE-GR-klstart-vstart>>).
. A non-zero `Xl` where <<KLE-instruction-load>> or <<KLE-instruction-store>> forbids it.
. An unconfigured KLIOBUF (Rule <<KLE-GR-iobuf-configured>>).
. A `kl.derive` whose `KLNL` operand names its other locker (<<KLE-instruction-derive>>).
--

KLE fatal-error::
+
--
The main fatal condition is an integrity failure of a hart's KLF (<<KLE-KLF>>); implementations may define others.
Detection and the resulting KLE unit reset (<<KLE-reset-and-m-mode-only>>) may be synchronous or asynchronous; the KLE unit records the condition, and the first KLE instruction or KLE CSR access issued, or in flight, after detection performs no operation and raises the exception, with `xepc` holding its address.
While a `KLS` field in effect is Off, or the KLE bit of an `*stateen0` CSR in effect is clear, the condition is retained and the exception of that denial (<<KLE-CSRs-unpriv>>) is raised instead: these states defer the report, never the detection.
_Handler_: none; the condition is not recoverable.
--

KLE missing-CSK:: No CSK is active (<<Zkl-ISA-priv.adoc#KLE-CSR-mklcsk>>); raised by every KLE instruction and KLE CSR access, except as <<KLE-CSK-requirements>> states.
_Handler_: none, Rule <<KLE-SR-handler-duty>> does not apply.

KLE locker-Off:: An access to a locker marked _Off_ (<<Zkl-ISA-priv.adoc#KLE-CSR-llockerstatus>>).
_Handler_: none, Rule <<KLE-SR-handler-duty>> does not apply.

KLE unsupported-Metadata:: Unsupported Metadata at a provisioning- or import-opening `kl.mgmt`, which leaves the locker _Unconfigured_ (<<KLE-MVR-open>>); only an M-mode handler can resolve it, by emulating the Machine (<<Zkl-ISA-priv.adoc#KLE-unsupported-handling>>).
Accessing or using a locker in State `kl_state_unsupported` raises no such exception.
_Handler_: _Unsupported_.

KLE privilege-violation:: A usage instruction that the _UsagePolicy_ denies (Rule <<KLE-GR-outcome-valid-state>>), or any use, clone or restriction of a locker in a Configuration State (Rule <<KLE-GR-usage-locker-config-state>>).
_Handler_: _Privilege Violation_; none for a locker in a Configuration State, which keeps its _State_.

KLE clock-unavailable:: The secure clock cannot be read to check a non-zero _ExpirationDate_ (<<KLE-Metadata-expiration-date>>).
_Handler_: _Expired_.

KLE out-of-memory:: Insufficient KLF capacity when opening a provisioning or import, or cloning (<<KLE-locker-management>>, <<KLE-instruction-clone>>).
_Handler_: _Out of Memory_.

KLE RBG-unavailable:: Random bits that an operation needs remain unavailable past the bound of Rule <<KLE-GR-rbg-failure>>.
_Handler_: _Invalid_.

Memory exceptions:: The exceptions of the component accesses of a KLE memory instruction (<<KLE-instructions-memory>>, <<KLE-Memory-Model>>).

[[KLE-error-states]]
=== Error States

These conditions set an Error State without an exception:

* _Invalid_:
** invalid Metadata or SKID (<<KLE-MVR-open>>, <<KLE-system-keys>>, <<KLE-instruction-restrict>>);
** an instruction that the Machine, its State or _MachinePolicy_ does not admit (Rules <<KLE-GR-no-exec-in-ready>>, <<KLE-GR-success-failure>>, <<KLE-GR-checks>>, <<Zkl-ISA-machines.adoc#KLE-MGR-not-allowed-instructions>> and <<Zkl-ISA-machines.adoc#KLE-MGR-policy-gate>>);
** a transfer window of a length that the Machine does not admit, or a `klstart` inside it that is not an interruption point (Rule <<KLE-GR-transfer-window-checks>>);
** a permanent RBG failure (Rule <<KLE-GR-rbg-failure>>);
** a configuration error of the Machine (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-config-data-error>>).
* _Expired_: an _ExpirationDate_ that has passed (<<KLE-Metadata-expiration-date>>).
* _Privilege Violation_: a failed narrowing (<<KLE-Metadata-narrowing>>, <<KLE-instruction-restrict>>, Rule <<KLE-GR-narrowing>>).
* _Authentication Failed_: a failed SCC authentication, at the completion of an import (<<KLE-SCC-import>>) or of an export (<<KLE-mgmt-completes-export>>), so software checks the _State_ after both.
* Any Error State: the one that a `kl.setst` names (<<KLE-instruction-setst>>).

Two outcomes are not Error States: a Machine enters _Failure_ on a data error (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-config-data-error>>) or on a failed verification of an AEAD tag or a signature, which is a result, not an error; and an ADS that fails its check at import is dropped, the SCC accepted (<<KLE-SCC-import>>).

=== No Operation

On an _Unconfigured_ or Error-State locker, every instruction other than a destructive configuration instruction performs no operation and raises no exception: the _State_ is unchanged, an output operand is zeroed, and an inspection instruction returns zeros or the MDH (Rule <<KLE-GR-outcome-inert>>).
On `KLNL` while `klnamedlocker` = 32, every instruction falls through likewise, `kl.clone`, `kl.rename`, `kl.swap` and the openings of `kl.mgmt` included (Rules <<KLE-GR-klnl-no-named-locker>> and <<KLE-GR-klnl-openings>>).
<<KLE-insns-on-unconf-or-error-locker>> gives the outcome of each instruction.

[[KLE-usage-input-output]]
== Replacing Vector Inputs and Outputs with kl.input and kl.output

With `Zklio`, a Form of `kl.exec`, `kl.setst` or `kl.mgmt` that reads inputs from, or writes outputs to, vector registers, which we call the _native_ form in its Machine and State, may be replaced by the corresponding Form without vector operands, _substitution_, that uses the KLIOBUF for them rather than raising an illegal-instruction exception.

`kl.input` and `kl.output` perform no computation and change only the KLIOBUF and `klstart`; all computation and other state changes remain in `kl.exec`, `kl.setst` and `kl.mgmt`.

The substitutions are:

. a Form D `kl.exec` for a Form A, B or C `kl.exec`; and
. a Form A `kl.setst`, or `kl.mgmt`, for the Form C of the same instruction.

A substitution reads its inputs from, and writes its outputs to, the KLIOBUF:

* A substituted Form A `kl.exec` behaves as a Form A with `Vd` = `Vs2` (<<KLE-instruction-exec>>):
  each block's output replaces its input at the same offset of the window.
* A substituted Form C `kl.exec` writes its output to [`klstart`, `kliobuftop`-1], clearing the bits it does not produce (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-clear-output>>), and writes no byte outside that range.
* A substituted Form A `kl.setst` reads its auxiliary input from KLIOBUF bytes [0, `kliobuftop`-1], ignoring `klstart`, truncated to the operand width as Rule <<Zkl-ISA-machines.adoc#KLE-MGR-fixed-width-input>> prescribes.
* `kl.exec` never modifies `kliobuftop`.

A substitution fails as follows:

* Without `Zklio`, it raises an illegal-instruction exception.
* Vector and KLIOBUF operands cannot be mixed: a Form B or C `kl.exec` issued where Form A is
  expected raises an illegal-instruction exception.
* If `kliobuflen` is zero, it raises an illegal-instruction exception (Rule <<KLE-GR-iobuf-configured>>).
* If `kliobuflen` is non-zero but `kliobuftop` is an invalid length for the Machine, the locker transitions to Error State _Invalid_, whether the KLIOBUF serves as input or only as output (Rule <<KLE-GR-transfer-window-checks>>); for an MDH operand, however, `kliobuftop` < 16 raises an illegal-instruction exception (Rule <<KLE-GR-vector-MDH-operand>>).

Where <<Zkl-ISA-machines.adoc#KLE-Machines>> says that a Form of `kl.exec`, `kl.setst` or `kl.mgmt` is _expected_, rather than _required_ or _the only Form allowed_, the substitutions above apply implicitly.
<<KLE-replacement-instructions>> gives examples of equivalent sequences using `kl.input` and `kl.output`.

[[KLE-CC-management]]
== Management of Cryptographic Contexts

Following the RISC-V philosophy, KLE splits locker management into sequences of simple instructions, not single instructions that drive large state machines or microcode.
As a consequence:

. the state machines that manage keys and algorithms, which CISC key-protection solutions hide (cite:[IBM-z-arch] "`Protection of Cryptographic Keys`" or cite:[intel-keylocker]), are exposed to software: the hardware is simpler, though it enforces rules against misuse, and the software more complex;
. interrupts and exceptions can separate the instructions of a management sequence, so context switching, process and virtual machine migration, hibernation, and interoperability between KLE implementations need explicit support; and
. so does dynamic locker management, lazy context loading included, where other architectures cache repeated key uses implicitly.

Throughout, the integrity of the MDH, and the confidentiality and integrity of the Content, of a CC are preserved, and binary compatibility holds across implementations that support the same sub-extensions.

A context-switch handler may clear a partially provisioned or imported locker instead of saving it, which makes the interrupted operation restart.
It must nevertheless be able to save such a locker, for instance to avoid livelock.
The same software code must handle both resumption and restart (Rule <<KLE-GR-cleared-under-management>>).
Rules <<KLE-SR-no-unconditional-clear>> and <<KLE-SR-never-clear-exporting>> bind system software.

[[KLE-nested-mgmt]]
=== Management Operation Types

KLE defines various external CC formats, each starting with the 128-bit MDH of <<KLE-Metadata>>.
The first two have been mentioned earlier:

. the _Provisioning Input_ (PI), loaded into a locker to create a CC; and
. the _Sealed Cryptographic Context_ (SCC), an encrypted and authenticated representation of a CC, exported to memory for later import.

These and two other formats are used by management operations, each consisting of one or more KLE management instructions.

A management operation is *open* from its opening `kl.mgmt` until its completing `kl.mgmt`, or until the locker is cleared; while it is open, the locker is in a Configuration State.
`kl.mgmt` opens or completes a management operation according to its `#immed7`:

[[KLE-management-immeds]]
.Values (decimal) of #immed7 for provisioning, importing, and exporting
[float="center",align="center",width="100%",cols="^7%,<27%,<66%",options="header"]
|===
| Value | Mnemonic                 |  Description
|  56   | `kl_cfg_provisioning`    |  Prepare a locker for provisioning.
|  57   | `kl_cfg_exporting`       |  Prepare a locker for export.
|  58   | `kl_cfg_importing`       |  Prepare a locker for import.
|  63   | `kl_cfg_management_end`  |  Complete the current management operation.
|===

Not every Configuration State of <<KLE-SC-sealing-status>> is an `#immed7` value: `kl_cfg_ppi_exporting` and `kl_cfg_ppi_importing` cannot be set directly, and result only from nested operations, described below.

A *base (management) operation* (also called the outermost operation) is opened on a locker in no Configuration State:

* a (base) _provisioning_ from a PI, in State `kl_cfg_provisioning`;
* a (base) _export_ of a locker in a Valid State, in State `kl_cfg_exporting`; or
* a (base) _import_ of an SCC, in State `kl_cfg_importing`.

Before opening an export, software saves the locker's MDH as `ml`; an import takes `ml` from the saved image.
The export- or import-completing `kl.mgmt` receives `ml` and restores its _State_; completing a base operation leaves the locker in a Complete State (Rule <<KLE-GR-completion-state>>).

An exception may interrupt an open operation.
The handler may then save the locker by a *nested export*, an export opened on a locker in a Configuration State, and restore it later by a *nested import* of the resulting image; nested operations may themselves be interrupted and nested.

Each Configuration State encodes a *base type* `pi` if the base operation is a provisioning and `scc` otherwise, which determines the format and length of the locker's image at any nesting depth (<<KLE-instruction-size>>):

* `pi`: `kl_cfg_provisioning`, with `kl_cfg_ppi_exporting` and `kl_cfg_ppi_importing` ("`ppi`" for "`partial provisioning input`") for nested exports and imports;
* `scc`: `kl_cfg_exporting` and `kl_cfg_importing`, for base and nested operations alike.

<<KLE-SC-sealing-status>> gives the values of these States.
Nested exports and imports use a third format:

[start=3]
. the *Partially Configured Cryptographic Context* (PCCC), whose MDH holds a Configuration State, and which has the format of a PI or an SCC, according to its base type, without further encryption or authentication.

A locker in an Error State has a fourth format, its MDH alone: its export reads the MDH, without `kl.mgmt`, and its import is a single `kl.mgmt` (<<KLE-error-state-transfer>>).

Clearing a locker ends all its open operations and leaves it _Unconfigured_.

[[KLE-data-formats]]
=== Formats of PIs, SCCs, and Partially Configured Cryptographic Contexts

Provisioning Input (PI)::
The MDH, with _State_ = _Unconfigured_, followed by `Content`; the provisioning-completing `kl.mgmt` sets _State_ to _Ready_.

Sealed Cryptographic Context (SCC)::
+
--
Up to five sections, in this order:

[[KLE-SCC]]
.Plaintext of the Sealed Cryptographic Context (SCC) Format, all Sections in Order
[width="100%",cols="^8%,14%,21%,57%",options="header"]
|===
| Section | Section Name | Size                 | Description
| 1       | `MDH`        | 128 bits             | See <<KLE-Metadata>>.
| 2       | `SIV`        | 128 bits             | Authentication tag for `MDH`, the Locality Secrets its _Locality_ names, and `Content1` (<<KLE-SCC-export>>).
| 3       | `IMPQUAL`    | 128 bits, if present | Identifies the implementation of the KLE unit. Non-authoritative, and ignored when _ADSDropped_ = 1.
| 4       | `SIV2`       | 128 bits, if present | Authentication tag for `IMPQUAL`, `SIV` and `Content2`. Non-authoritative, and not verified when _ADSDropped_ = 1.
//
| 5.a
| `Content1`
| A multiple of 128 bits. See <<KLE-length-rule>>.
| Keys and other Machine-specific information that the Machine needs to function correctly. Encrypted in memory, and inside the KLE unit during partial import.
//
| 5.b
| `Content2`
| A multiple of 128 bits.
| ADS: data that the Machine does _not_ need to function correctly.
  Encrypted in memory and during partial import.
|===

Sections 3, 4 and 5.b form the implementation-specific ADS, whose size _AuxDataLen_ gives (<<KLE-Auxiliary-Data-Section>>).
KLE generates an image with _ADSDropped_ = 1 only as an SCC-shaped PCCC, when a nested export preserves an interrupted import after `Content2` was dropped; since _ADSDropped_ is unauthenticated, import also accepts this layout in an SCC modified to set the bit.
--

Encryption during management::
While an SCC is imported, or a locker is exported as an SCC, the locker holds its `Content` encrypted:

. an export-opening `kl.mgmt` encrypts the locker, generates `SIV` and, if _AuxDataLen_ {ge} 2, `IMPQUAL` and `SIV2`;
. the base import- or export-completing `kl.mgmt` decrypts and authenticates it, once the MDH, `Content`, `SIV` and, if _AuxDataLen_ {ge} 2, `IMPQUAL` and `SIV2` are in place; with _ADSDropped_ = 1, no `Content2` is loaded or authenticated.
  An export completion may instead restore the clear contents from an internal copy (<<KLE-mgmt-completes-export>>).

Partially Configured Cryptographic Context (PCCC)::
+
--
A PCCC (<<KLE-nested-mgmt>>) has one of two shapes:

* base type `pi`: a _PI-shaped_ image, the MDH followed by the clear `Content` of the PI.
  This exposes nothing new, since software supplied that `Content`; software that provisions a locker clears it before giving control to a less privileged mode, which could otherwise export it (Rule <<KLE-SR-clear-before-lower-mode>>).
* base type `scc`: an _SCC-shaped_ image, the MDH followed by `SIV` and, when present, `IMPQUAL` and `SIV2`, as _ContentOffset_ prescribes (<<KLE-serialized-image>>), and by the ciphertext `Content` already in the locker.

Since each export saves its own `ml`, software keeps an implicit stack of _State_ values, one per nesting level.
--

[[KLE-serialized-image,serialized image]]Definition: _Serialized image_::
`content_size` is the length in bytes of the serialized `Content` of the locker, as a PI or an SCC according to the base type of its image (<<KLE-length-rule>>), as given by the locker's MDH.
In a PI, an SCC or a PCCC, the `Content` starts at a _ContentOffset_ that depends on that MDH:
// the same case distinction of `kl.size` (<<KLE-instruction-size>>) but excluding the `Content` and the MDH._ADSDropped_ never affects _ContentOffset_.
+
. 16 if _AuxDataLen_ = 0, and 48 if _AuxDataLen_ {ge} 2, if MDH._State_ is a Valid State, `kl_cfg_importing` or `kl_cfg_exporting`;
. 0 if MDH._State_ is `kl_cfg_provisioning`, `kl_cfg_ppi_importing` or `kl_cfg_ppi_exporting`.
+
The _serialized image_ `S` of the locker is `Content`, `SIV {vvert} Content`, or `SIV {vvert} IMPQUAL {vvert} SIV2 {vvert} Content` for _ContentOffset_ = 0, 16 or 48, respectively; while the locker is under management, the authentication registers (<<KLE-KLF>>) hold its leading fields.
Its size is `image_size` = _ContentOffset_ + `content_size`, the value that `kl.size` reports minus 16.
+
`max_admissible` is the length of the longest image of the locker's base type that the implementation can hold for the Machine: `pi_content_size` for base type `pi`, and `content1_size` plus the largest supported `content2_size` for base type `scc` (<<KLE-instruction-size>>); with _ADSDropped_ = 1, `content2_size` counts as zero.
Bytes of an SCC beyond `max_admissible` belong to a discarded ADS (<<KLE-SCC-import>>), and are not transferred.
The transferred part of `S` ends at `image_end` = _ContentOffset_ + min(`content_size`, `max_admissible`).

// ////////////////////////////////////////////////////////////////////

[[KLE-length-rule]]
=== Length of External Formats and KLF Capacity Usage of a Locker

The lengths of a PI, an SCC or a PCCC, and the KLF capacity of a locker are determined by fields contained in bits [63:0] of the MDH.
The following items do not apply to a locker in an Error State (<<KLE-error-state-transfer>>):

. The length of a *Provisioning Input* depends only on _Machine_, _MachinePolicy_ and _KeyType_.
_AuxDataLen_ and _ADSDropped_ must be zero in a PI, and in a PI-shaped PCCC, since these carry no ADS; `kl.mgmt` ignores and zeroes _StateExtension_ and _MachineUse_ upon provisioning.

. The length of a *Sealed Cryptographic Context* depends only on _Machine_, _MachinePolicy_, _KeyType_, _StateExtension_, _AuxDataLen_ and _ADSDropped_ (<<KLE-Auxiliary-Data-Section>>), not on _State_ or _SCProtection_ (<<KLE-rules-masked-implementations>>).
_ADSDropped_ removes only `Content2`: the presence of `IMPQUAL` and `SIV2`, and the offset and length of `Content1`, do not change.

. The length of a *Partially Configured Cryptographic Context* is that of the format corresponding to its base type, i.e.,
that of a PI if its base type is `pi` and that of an SCC if its base type is `scc`.

. The *KLF capacity* of a locker depends only on _Machine_, _MachinePolicy_, _SCProtection_ and _KeyType_, and does not change once the locker is provisioned: dropping the ADS shortens its SCCs but not its capacity.
A locker is allocated room for every field its Machine may use; the capacity depends on _KeyType_ because a SKID may denote a key that never enters the KLF.
With _KeyType_ = 2 it is that of _KeyType_ = 0, so the provisioning-completing `kl.mgmt` allocates nothing more.

// No other MDH field, and no information in the `Content`, may affect any of these four quantities.

A PI cannot be in an Error State.

// ////////////////////////////////////////////////////////////////////

[[KLE-rules-masked-implementations]]
==== Single-Share Key Export Rule for Masked Implementations

A multi-share implementation of a Machine provisions, imports and exports all its keys and secrets as reconstructed values, so that SCCs stay compact and interoperable.
(((KLE, Machine, side-channel protection variants)))
Architecturally every value is a single share: a side-channel-protected Machine is an implementation variant of the unprotected one, distinguished only by the _SCProtection_ field of the MDH.
The reconstruction may be only conceptual, and is protected as <<KLE-KLF>> recommends.

NOTE: Reconstructing or re-randomizing a key is usually cheap, for instance when a block cipher in counter mode generates the masks; an implementation with a slower mask generator may keep shares or masks in the ADS.

// ////////////////////////////////////////////////////////////////////

[[KLE-system-keys]]
==== System Keys

A PI or SCC encodes a System Key as a 64-bit SKID, from which a system-specific SKS retrieves the key.
Hence:

[horizontal]
[[KLE-GR-skid-field,GR77]]GR77:: In a PI, an SCC, or a PCCC, the key field of a System Key holds its SKID instead of the key value, and so shrinks from the key size to 64 bits.

[[KLE-GR-single-skid,GR78]]GR78:: For a Machine with more than one key, such as XEX/XTS, a single SKID retrieves all its keys from the SKS.

The SKS resolves a SKID as a function of the SKID alone, if the SKID is allowed for the _Machine_ and _MachinePolicy_; the key value depends on neither.
If the SKS also encodes policies for a key, they narrow the policies of the locker as <<KLE-Metadata-narrowing>> describes.
For a key that the system intends to protect, the SKS associates at least a _UsagePolicy_ with its SKID, since the SKS policies are the only architectural control on which modes may use it; a _UsagePolicy_ that admits every mode, for instance for a public signature-verification key, is a deliberate choice and the responsibility of the system's architects.
The current privilege mode does not affect whether the SKS may resolve a SKID.

A SKID that the SKS does not resolve transitions the locker to Error State _Invalid_ (<<KLE-Metadata-validity>>).
Whenever a SKID is resolved, the policies that the SKS associates with the key narrow the MDH of the locker (<<KLE-Metadata-narrowing>>); if the narrowing fails, the locker transitions to Error State _Privilege Violation_.

A SKID carried in an SCC is resolved only after the SCC is authenticated.

A multi-share implementation may copy System Key material from the SKS into the locker and expand it into multiple shares, but must still export the key as a SKID.
Shares or masks included in the ADS (<<KLE-rules-masked-implementations>>) must not allow or facilitate recovering the key value from those values alone.

[[KLE-locker-management]]
=== Locker Management Operations

This section defines the operations that `kl.mgmt` performs for the `#immed7` values of <<KLE-management-immeds>>.

Three steps are common to every operation below and are not repeated in their descriptions:

. `kl.mgmt` first performs the check of Rule <<KLE-GR-mgmt-klnamedlocker-check>>, and raises an illegal-instruction exception if it fails; with `KLNL` and `klnamedlocker` = 32 it performs only these common steps (Rules <<KLE-GR-klnl-openings>> and <<KLE-GR-klnl-no-named-locker>>).
. It updates `klnamedlocker` as Rule <<KLE-GR-klnamedlocker-updates>> states.
. It clears `klstart` once it has passed the checks that precede the conditions on the locker (the first group of <<KLE-illegal-instruction-grounds>>, and the KLE fatal-error, missing-CSK and locker-Off exceptions) and the `klnamedlocker` check above, even if it then raises an exception; if one of those checks rejects it, it leaves `klstart` unchanged, so an accidentally interleaved `kl.mgmt` does not destroy the progress of the ongoing operation. Software restores `klstart` to resume interrupted management operations.

The four operations of `kl.mgmt` are described in the next four sections:

[[KLE-MVR-open]]
==== Provisioning- and import-opening kl.mgmt

Software first obtains the MDH, `ml`, and supplies it with a Form A, C or D `kl.mgmt`.

NOTE: For an import, software first saves `ml` in its local state and supplies it to the import-completing `kl.mgmt`, to restore the _State_ the locker had before the import started.

The instruction:

.. zeroizes the target locker, as a <<KLE-destructive-config,destructive configuration instruction>>; bytes of the <<KLE-serialized-image,serialized image>> `S`, authentication fields included, not yet written by the management operation read as zero through every architectural access (`kl.store`, `kl.mvout`, verbatim export);
//.. It checks the validity of the fields of the provided MDH `ml`. If any are invalid according to <<KLE-Metadata-validity>>, it transitions the locker to Error State _Invalid_.

// .. if `#immed7` = `kl_cfg_importing` and `ml`._State_ is an Error State, configures the locker immediately and
//     fully in that Error State, with the entire MDH from the auxiliary input, except that _AuxDataLen_ and _ADSDropped_ are set to 0 (Rule <<KLE-GR-clear-locker-content-error-state>>); a _State_ of 54 or 55, or of 53 without `Zklexpire`, is replaced by _Invalid_.
//     The steps below are skipped: the locker holds only its MDH (<<KLE-cryptographic-registers>>), no Machine is selected for execution,
//     and no KLF capacity is allocated, so this configuration cannot fail.
//     This one uninterruptible instruction (Rule <<KLE-GR-uninterruptible-instructions>>) performs the whole configuration and opens no management operation, so
//     no `kl.mgmt` with `#immed7` = `kl_cfg_management_end` follows.
//     This is the _short import path_ of <<KLE-error-state-transfer>>;

.. if `#immed7` = `kl_cfg_importing` and `ml`._State_ is an Error State, instead takes the _short import path_ of <<KLE-error-state-transfer>>: it configures the locker immediately and fully in that Error State, skips the steps below, and opens no management operation;
.. for an import, zeroizes the authentication registers `SIV`, `IMPQUAL` and `SIV2` (<<KLE-KLF>>);
.. copies `ml` into `M`, zeroing _StateExtension_ and _MachineUse_ for a provisioning; the checks below are made on `M`, the locker's MDH staying zero;
.. raises a KLE unsupported-Metadata exception if `M` is unsupported Metadata (<<KLE-Metadata-validity>>);
.. for a *provisioning*:
... requires `ml`._State_ to be _Unconfigured_, else the Metadata is invalid; the locker's _State_ stays _Unconfigured_ during the checks below, until successful configuration;
... requires `M`._AuxDataLen_ and `M`._ADSDropped_ to be 0: if either is non-zero, the locker transitions to Error State _Invalid_, a Complete State, and the instruction terminates;
.. transitions the locker to Error State _Invalid_ if `M` is invalid Metadata (<<KLE-Metadata-validity>>), an _Unconfigured_ `ml`._State_ being invalid for an import;
.. attempts to allocate the KLF capacity that the fields _Machine_, _MachinePolicy_, _SCProtection_ and _KeyType_ of `M` require (<<KLE-length-rule>>), and raises a KLE out-of-memory exception if it cannot;
.. for a *provisioning*, installs `M` as the locker's MDH, with _State_ `kl_cfg_provisioning`;
.. for an *import*:
... installs `M` as the locker's MDH, with the _ADSDropped_ bit that Steps 1–5 of <<KLE-SCC-import>>, which describe this same opening, derive from it and from the maximum the implementation supports;
... sets the locker's _State_ to `kl_cfg_importing` if `ml`._State_ is a Valid State, `kl_cfg_importing` or `kl_cfg_exporting`;
... sets it to `kl_cfg_ppi_importing` if the base type of `ml`._State_ is `pi` (<<KLE-nested-mgmt>>).

Whenever a check above fails, raising a KLE exception or transitioning the locker to Error State _Invalid_, every MDH field other than _State_ remains zero and no KLF capacity is allocated; after a KLE out-of-memory exception, the locker remains _Unconfigured_.
This does not apply to configuring a locker directly into an Error State from `ml`, which installs the entire MDH.

[NOTE]
====
The locker is zeroized and its Content deallocated before any check that can cause the operation to fail. Zeroizing first gives every way the instruction can end, success, Error State or exception, the same outcome: the old content is destroyed and `klnamedlocker` names the locker (Rules <<KLE-GR-klnamedlocker-updates>> and <<KLE-exception-state-change>>).
It also lets the capacity check count the locker's own allocation as free, so that a CC can be reconfigured in place, and lets a handler that emulates an unsupported Machine (<<Zkl-ISA-priv.adoc#KLE-unsupported-handling>>) find its target zeroized and named, even for `KLNL`.
====

==== Export-opening kl.mgmt

Software first saves a copy, `ml`, of the locker's MDH, to restore the _State_ when completing the export.
`kl.mgmt` can be of Form A, C or D, and ignores its auxiliary input. Depending on `ml`._State_:

.. _Unconfigured_: no operation and no exception. No management operation is opened, the authentication registers are unchanged, and only the common steps above take effect (Rule <<KLE-GR-fall-through-mgmt>>).

.. An Error State: the locker is unchanged, and no management operation is opened (Rule <<KLE-GR-error-state-locker-is-only-MDH>>); <<KLE-error-state-transfer>> details this short export path.

.. A Valid State: the instruction prepares the locker to produce an SCC, encrypting its contents and computing the authentication tag(s) as <<KLE-CC-management>> specifies, and sets its _State_ to `kl_cfg_exporting`.
The opening `kl.mgmt` changes no MDH field other than _State_: an implementation that creates or changes an ADS, or uses _MachineUse_, always keeps _AuxDataLen_ and _MachineUse_ current, so that the MDH software reads before opening the export is the one the export authenticates.

.. A Configuration State (the export of a partially configured locker, or a nested export):

... no encryption or authentication occurs: the locker's contents are exported verbatim, in their order in the PI (for a partially provisioned locker) or in the SCC (for a partially imported locker, or a locker whose own export was interrupted);

... the locker's _State_ is set to `kl_cfg_ppi_exporting` or `kl_cfg_exporting`, according to its base type (<<KLE-nested-mgmt>>).

==== Completing kl.mgmt

First, note that:

. `kl_cfg_management_end` issued on a locker in a Valid State raises an illegal-instruction exception, since there is no management operation open on it.

. `kl_cfg_management_end` issued on a locker that is _Unconfigured_ or in an Error State performs no operation, raises no exception, ignores `ml`, and only the common steps above take effect (Rule <<KLE-GR-fall-through-mgmt>>).

These two special cases aside, a `kl.mgmt` issued to complete a management operation
first reads the target locker's MDH, and completes a provisioning if its _State_ is `kl_cfg_provisioning`, an import if it is `kl_cfg_importing` or `kl_cfg_ppi_importing`, and an export if it is `kl_cfg_exporting` or `kl_cfg_ppi_exporting`.

When completing an import or an export, it consumes only the _State_ field of the auxiliary operand `ml`, which restores the locker's _State_ to its value when the management operation started; no other MDH field is written from `ml`.

On completing an SCC import or a locker export, authentication is checked only if setting locker.MDH._State_ to `ml`._State_ restores a Complete State; the probability of accepting an incorrect _State_ is negligible.
A nested completion checks only the base type, without authentication.

If locker.MDH._State_ is `kl_cfg_importing` or `kl_cfg_exporting`, `ml`._State_ must be a Complete State or a Configuration State of base type `scc`, i.e., `kl_cfg_importing` or `kl_cfg_exporting`; if it is `kl_cfg_ppi_importing` or `kl_cfg_ppi_exporting`, `ml`._State_ must be a Configuration State of base type `pi`, i.e., `kl_cfg_provisioning`, `kl_cfg_ppi_importing` or `kl_cfg_ppi_exporting` (<<KLE-nested-mgmt>>).
Any other `ml`._State_, including a Complete State for a locker of base type `pi` and the values 61–63, raises an illegal-instruction exception.
A Complete `ml`._State_ is accepted only for a locker of base type `scc`, so the clear `Content` of a partially provisioned locker becomes usable only by completing its provisioning.

* *Provisioning-completing kl.mgmt.*
+
--
No MDH saved at provisioning start is needed: Forms C and D of `kl.mgmt` ignore their auxiliary input.

Completing a provisioning requires _AuxDataLen_ = 0 and _ADSDropped_ = 0; if locker.MDH._State_ is `kl_cfg_provisioning` and either field is non-zero, the locker transitions to Error State _Invalid_, and the instruction terminates.

The operation makes the provisioned locker available to software by:

... for _KeyType_ = 2, generating the key and setting _KeyType_ to 0 (<<KLE-KeyType-field>>, Rule <<KLE-GR-rbg-failure>>), and for _KeyType_ = 1, applying the SKID resolution of <<KLE-system-keys>>;
... converting the locker's content into the internal format of the KLE unit;
... performing any check required by the Machine on the fields of the PI (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-check-on-write>>); a failed check transitions the locker as Rule <<Zkl-ISA-machines.adoc#KLE-MGR-config-data-error>> classifies it, to Error State _Invalid_ for a configuration error or to _Failure_ for a data error, in place of the step below; and
... setting _State_ to _Ready_, and _StateExtension_ and _MachineUse_ to 0.

If a process is preempted during provisioning, `kl.store` or `kl.mvout` exports only the original PI information, unencrypted.
Only the provisioning-completing `kl.mgmt` may therefore generate secret random material needed to configure the locker, retrieve key material from the SKS, or derive, expand or re-share that material, so that no such material is exposed in an unencrypted export of a partially provisioned locker.
--

* *Import-completing kl.mgmt.*
+
--
Software uses Form A, C or D of `kl.mgmt` to supply the value `ml` saved when the import started.
The image authenticated as ``AD[0]`` is the MDH held in the target locker, i.e., the one carried in the SCC and loaded when the import started, with its _State_ restored from `ml` and _ADSDropped_ cleared only in the copy used for authentication (<<KLE-SCC-import>>).

... If `ml`._State_ is a Complete State (the import of the export of a fully configured locker):
.... locker.MDH._State_ is set to `ml`._State_.
.... The KLE unit decrypts and authenticates the locker's content.
.... If authentication fails, the target locker transitions to Error State _Authentication Failed_, without an exception. Otherwise, if _KeyType_ = 1, the SKID is resolved, and the narrowing of <<KLE-system-keys>> is applied.
.... The KLE unit converts the locker's content into its internal format.
.... The KLE unit performs the checks that the Machine attaches to the fields that the import restores (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-check-on-write>>); a failed check transitions the locker as when completing a provisioning (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-config-data-error>>).
This makes the locker available to software.
... Otherwise (the import of the export of a partially configured locker, or of a nested export), locker.MDH._State_ is set to `ml`._State_.
--

[[KLE-mgmt-completes-export]]
==== Export-completing kl.mgmt

Software uses Form A, C or D of `kl.mgmt` to supply the MDH value `ml` saved when the export began. Then:

. The _State_ of the locker is set to `ml`._State_.
. If `ml`._State_ is a Complete State, the instruction restores the locker to the clear format it had when the export began, and makes it accessible to software:
.. it decrypts and authenticates the contents as when completing an import, with the MDH held in the locker as `AD[0]`, and _ADSDropped_ cleared in the copy that first-segment authentication consumes;
.. if the `SIV` check fails, the locker transitions to Error State _Authentication Failed_, and the instruction terminates without an exception; otherwise, if _KeyType_ = 1, the SKID is resolved, and the narrowing of <<KLE-system-keys>> is applied.
. If `ml`._State_ is not a Complete State, the locker's contents are not changed further.

NOTE: In place of decrypting and authenticating the locker's contents in Step 2.a, an implementation may instead restore the clear contents from an internal copy, if it can guarantee that the outcome is identical. The specification defines no mechanism for this.

=== SCC Export and Import Algorithms

Section <<KLE-SCC-AEAD>> describes the SCC export and import algorithms, starting with the authenticated encryption scheme they use.

[[KLE-SCC-AEAD]]
=== The SCC Authenticated Encryption Scheme

SCC export and import use a variant of AES-GCM-SIV cite:[DBLP-journals-iacr-GueronLL17,RFC8452] that differs as follows:

. The POLYVAL input omits the lengths of the associated data and plaintext, since they are already implied by the MDH.
. The optional Nonce is omitted.
. A domain separation bit, `sep`, distinguishes the two segments of the content sealed in an SCC: the architected content (`sep` = 0) and the optional implementation-specific content (`sep` = 1); `sep` replaces bit 126 of the tag input and of every counter block.
. For `sep` = 0, bit 47 of `AD[0]`, the unauthenticated _ADSDropped_ bit of the MDH (<<KLE-Auxiliary-Data-Section>>), is cleared before `POLYVAL` is evaluated.

The Key Derivation (<<KLE-SCC-key-derivation>>) and POLYVAL (<<KLE-SCC-POLYVAL>>) functions are defined first, then SCC generation from a locker (<<KLE-SCC-export>>) and SCC import into a locker (<<KLE-SCC-import>>).

In the pseudocode, `AESE256(K, B)` denotes the AES-256 encryption of the 128-bit block `B` under the 256-bit key `K` (FIPS 197 cite:[nist-fips-197]).

[[KLE-SCC-key-derivation]]
.RFC8452 Key Derivation
[]
----
function SCC_KeyDeriv(key : bits(256), nonce : bits(96))
    → struct{enc_key : bits(256), auth_key : bits(128)} =
{
  local A : array [0..5] of bits(128);
  local i : int;

  foreach(i from 0 to 5) do:
    A[i] ← AESE256(key, nonce @ bin(i,32));

  return struct { enc_key  = A[5][63:0] @ A[4][63:0] @ A[3][63:0] @ A[2][63:0],
                  auth_key = A[1][63:0] @ A[0][63:0] }
}
----

// NOTE: Since key derivation is costly, implementations may cache the derived keys.

[[KLE-SCC-POLYVAL]]
.Polyval Hashing Function
[]
----
function POLYVAL(auth_key : bits(128), blocks[0..n-1] : bits(128), n : int)
    → bits(128) =
{
  local tmp : bits(128) ← zeros(128);
  local i : int;

  foreach(i from 0 to n-1) do:
    tmp ← tmp xor blocks[i];
    tmp ← Montmul(tmp, auth_key);

  return tmp;
}
----

POLYVAL uses Montgomery multiplication, `Montmul(a, b)`, in the field F = GF(2)[`x`] modulo `x^128^ + x^127^ + x^126^ + x^121^ + 1`.
A 128-bit value `V` represents the element whose coefficient of `x^k^` is `V[k]`;
byte order and bit order both run forward, as in
cite:[RFC8452] {sect}3, under which `x^0^` is the byte string `0x01` followed by
fifteen zero bytes, i.e., the value `1`. Then: +
 +
`{fournbsp}{fournbsp}` `Montmul(a, b)` = `a` {interpunct} `b` {interpunct} `x^-128^` `{nbsp}{nbsp}` in the field F.

The SCC encryption and decryption functions, <<KLE-SCC-GCM-SIV-enc>> and <<KLE-SCC-GCM-SIV-dec>>, use this notation:

* `AD[]` denotes the Associated Data as an array of `len_AD` 128-bit blocks, that is
  `AD[0] {vvert} AD[1] {vvert} {ellipsis} {vvert} AD[len_AD-1]`, in that order;
* `P[]`, resp., `C[]`, denotes a Plaintext, resp., a Ciphertext, as arrays of `len_PC`
  128-bit blocks, that is `P[0] {vvert} P[1] {vvert} {ellipsis} {vvert} P[len_PC-1]`,
  resp. `C[0] {vvert} C[1] {vvert} {ellipsis} {vvert} C[len_PC-1]`, in that order;
* `K` is a 256-bit Key;
* `N` is a 96-bit Nonce; and
* `SIV` is a 128-bit SIV/tag.

//

[[KLE-SCC-GCM-SIV-enc]]
.AES-GCM-SIV Encryption for SCC Generation
[]
----
function SCC_Encrypt(AD[] : array of bits(128), N : bits(96), sep: bits(1),
    P[] : array of bits(128), K : bits(256), len_AD : int, len_PC : int)
  → {SIV : bits(128), C[] : array of bits(128)} =
{
  local AD_auth : array [0..len_AD-1] of bits(128) ← AD[];

  enc_key, auth_key ← SCC_KeyDeriv(K,N);
  if (sep = 0) then:
    AD_auth[0][47] ← 0;
  SIV ← POLYVAL(auth_key, AD_auth || P, len_AD + len_PC);
  SIV[95:0] ← SIV[95:0] xor N;
  SIV ← AESE256(enc_key, 0 @ sep @ SIV[125:0]);

  foreach(i from 0 to len_PC - 1) do:
    C[i] ← P[i] xor AESE256(enc_key,
             1 @ sep @ SIV[125:32] @ bin\((int(SIV[31:0]) + i) mod 2**32, 32));

  return ( SIV, C[] );
}
----

`len_PC` never exceeds `max_admissible` / 16 (<<KLE-serialized-image>>), and `len_AD` never exceeds 7.

[[KLE-SCC-GCM-SIV-dec]]
.AES-GCM-SIV Decryption for SCC Import
[]
----
function SCC_Decrypt(AD[] : array of bits(128), N : bits(96), sep: bits(1),
    SIV : bits(128), C[] : array of bits(128), K : bits(256),
    len_AD : int, len_PC : int)
  → {correct : bool, P[] : array of bits(128)} =
{
  local AD_auth : array [0..len_AD-1] of bits(128) ← AD[];

  enc_key, auth_key ← SCC_KeyDeriv(K,N);
  if (sep = 0) then:
    AD_auth[0][47] ← 0;

  foreach(i from 0 to len_PC - 1) do:
    P[i] ← C[i] xor AESE256(enc_key,
             1 @ sep @ SIV[125:32] @ bin\((int(SIV[31:0]) + i) mod 2**32, 32));

  s ← POLYVAL(auth_key, AD_auth || P, len_AD + len_PC);
  tmp ← s;
  tmp[95:0] ← tmp[95:0] xor N;
  tmp ← AESE256(enc_key, 0 @ sep @ tmp[125:0]);

  if (tmp != SIV) then:
    foreach(i from 0 to len_PC - 1)
      P[i] ← zeros(128);
    return ( false, P[] );

  return ( true, P[] );
}
----

[[KLE-SCC-export]]
=== Generation of an SCC from a Fully Configured Locker

A locker ``K(i)`` in a Valid State is fully provisioned, and opening it for export creates the serialized, encrypted and authenticated SCC by the steps below.

The Locality substitution rules of <<KLE-Localities>> apply: `LST_eff[j]` is the value of `LST` entry _j_ after substitution, and replaces `LST[j]` in the export and import algorithms.
An unimplemented entry with no configured replacement contributes `zeros(128)` and makes the Metadata invalid at provisioning or import; an export is not refused on this ground, but the resulting SCC is rejected at import (Rule <<KLE-SR-locality-unconfigure>>). Entry 9 of `LST` is `hkllocality`, and entry 10 is `skllocality`.

After `kl.clearads`, a fully configured locker has _AuxDataLen_ = 0 and _ADSDropped_ = 0 (<<KLE-instruction-clearads>>); only an SCC-shaped PCCC may carry _ADSDropped_ = 1, to preserve an interrupted import after `Content2` was dropped.

.Exporting a Fully Configured Locker ``K(i)``
--
* Use `kl.getmd` to get the MDH
. If MDH is in an Error State, use the method of <<KLE-error-state-transfer>>.
* Step 2: Use `sl`/`sd`/`vls*` to store the MDH to memory
* The export-opening `kl.mgmt Kd/KLNL, #kl_cfg_exporting` performs the following Steps:
[start=3]
. Process the architected content:
.. `saved_MDH` <- ``K(i).MDH``, ``len_AD`` <- 1
.. ``K(i).MDH``._State_ <- `kl_cfg_exporting`
.. ``AD[0]`` <- `saved_MDH` (no need to mask _ADSDropped_: it is zero in a fully configured locker).
.. foreach(_j_ from 0 to 10) do:
... If `saved_MDH`._Locality_ includes Locality #j, then
.... ``AD[len_AD]`` <-  ``LST_eff[``_j_``]``, ``len_AD`` <- ``len_AD`` + 1
.. `len_PC` <- the number of 128-bit blocks of `Content1` (Section 5.a of <<KLE-SCC>>).
.. `SIV`, `Content1~CT~[]` <- +
`{fournbsp}{fournbsp}SCC_Encrypt(AD, zeros(96), 0, K(i).Content1~PT~[], CSK, len_AD, len_PC)`
. If _AuxDataLen_ {ge} 2, process the implementation-specific content:
.. `len_AD2` <- 2, ``AD2[0]`` <- ``K(i)``.`IMPQUAL`, ``AD2[1]`` <- `SIV`.
.. `len_PC2` <- _AuxDataLen_ − 2 (i.e., the number of 128-bit blocks of `Content2`, Section 5.b of <<KLE-SCC>>).
.. `SIV2`, `Content2~CT~[]` <- +
`{fournbsp}{fournbsp}SCC_Encrypt(AD2, zeros(96), 1, K(i).Content2~PT~[], CSK, len_AD2, len_PC2)`
* A loop around `kl.store`/`kl.mvout` instructions is used to save the rest of the SCC to memory
[start=5]
. If _AuxDataLen_ = 0, then:
.. `S` <- `saved_MDH` {vvert} `SIV` {vvert} `Content1~CT~`
. else:
.. `S` <- `saved_MDH` {vvert} `SIV` {vvert} `IMPQUAL` {vvert} `SIV2` {vvert} `Content1~CT~` {vvert} `Content2~CT~` (`Content2~CT~` may be empty)
. Store `S` to memory
* The closing `kl.mgmt Kd/KLNL, #kl_cfg_management_end` restores the locker to the unencrypted state and makes it available to software:
[start=8]
. The steps are described in <<KLE-SCC-import>>
--

[NOTE]
====
An export completed prematurely fails authentication at import (<<KLE-SCC-import>>) with overwhelming probability, and an import completed prematurely fails it at once; an operation left incomplete keeps the locker in a Configuration State, in which most instructions fail.
====

[[KLE-SCC-import]]
=== Decryption and Authentication of a Complete SCC into a Locker

The following algorithm imports the SCC of a fully configured locker.
For an SCC whose MDH is in an Error State, use the method of <<KLE-error-state-transfer>>.

.Importing a Fully Configured Locker ``K(i)``
--
* Step 1: Read `M`, the MDH from the SCC from memory.
* The import-opening `kl.mgmt Kd/KLNL, #kl_cfg_importing, M` performs the following Steps:
[start=8]
. Clear and deallocate ``K(i)``.
. Make the opening checks of <<KLE-MVR-open>> on `M`, stopping with their outcome if one fails.
. Determine the SCC layout from `M`.
. ``K(i)``.MDH. <- `M`
. If `M`._AuxDataLen_ {ge} 2, and either `M`._ADSDropped_ = 1 or `M`._AuxDataLen_ exceeds the maximum of the implementation for the Machine:
.. ``K(i)``.MDH._ADSDropped_ <- 1
. else
.. ``K(i)``.MDH._ADSDropped_ <- 10
// This changes only the length of `Content2`: when _AuxDataLen_ {ge} 2, `IMPQUAL` and `SIV2` remain present and _ContentOffset_ remains 48. The opening `kl.mgmt` then
. Set the appropriate Configuration State according to <<KLE-MVR-open>>.
* A loop around `kl.load`/`kl.mvin` instructions performs the following step:
[start=9]
. Load the rest of the SCC, up to the length that the resulting working MDH gives: with _ADSDropped_ = 1, `SIV`, `IMPQUAL`, `SIV2` and `Content1`, but no `Content2`.
* The closing `kl.mgmt Kd/KLNL, #kl_cfg_management_end` decrypts and authenticates the SCC and make it available to software:
[start=10]
. `saved_MDH` <- the MDH image held in ``K(i)``, that is `M` with the working value of _ADSDropped_ and with its _State_ field restored from the auxiliary operand of the completing `kl.mgmt`.
. ``AD[0]`` <- `saved_MDH`, ``len_AD`` <- 1. `SCC_Decrypt` clears _ADSDropped_ in its local copy of `AD[0]` before authenticating it; the MDH held in ``K(i)`` is unchanged by that computation.
. foreach (`j` from 0 to 10) do:
.. If `saved_MDH`._Locality_ includes Locality #j, then ``AD[len_AD]`` <-  ``LST_eff[j]``, ``len_AD`` <- ``len_AD`` + 1
. `len_PC` <- the number of 128-bit blocks of `Content1` (Section 5.a of <<KLE-SCC>>).
. `correct`, ``K(i)``.`Content1` <- `SCC_Decrypt(AD, zeros(96), 0, SIV, K(i).Content1, CSK, len_AD, len_PC)`.
. If `correct` {ne} `true`, the SCC is rejected: ``K(i)`` transitions to Error State `kl_state_mgmt_auth` (_Authentication Failed_, Rule <<KLE-GR-clear-locker-content-error-state>>), and the remaining steps are skipped.
. If ``K(i)``.MDH._AuxDataLen_ {ge} 2 and ``K(i)``.MDH._ADSDropped_ = 0, process the implementation-specific content:
.. `len_AD2` <- 2, ``AD2[0]`` <- ``K(i)``.`IMPQUAL`, ``AD2[1]`` <- `SIV`.
.. If ``K(i)``.`IMPQUAL` = `zeros(32) @ klmimpid @ klmarchid @ klmvendorid` then:
... `len_PC2` <- the number of 128-bit blocks of `Content2` (Section 5.b of <<KLE-SCC>>), that is ``K(i)``.MDH._AuxDataLen_ − 2.
... `correct`, ``K(i)``.`Content2` <- `SCC_Decrypt(AD2, zeros(96), 1, SIV2, K(i).Content2, CSK, len_AD2, len_PC2)`.
.. else:
... `correct` <- `false`.
. If second-segment processing was attempted and `correct` {ne} `true`, drop `Content2` and set ``K(i)``.MDH._ADSDropped_ to 1.
. If ``K(i)``.MDH._AuxDataLen_ = 0 or ``K(i)``.MDH._ADSDropped_ = 1:
.. Zero the implementation-defined subfields of the MDH (<<KLE-MachineUse>>);
.. _ADSDropped_ <- 0; and
.. _AuxDataLen_ <- 0 (may be then set to at least 2 again if the implementation generates a replacement ADS right away).
// otherwise it keeps the ADS and sets _ADSDropped_ to 0. Either way, any restart that Rule <<KLE-GR-long-running-restart>> requires is made before the locker becomes Valid, and a later export emits the ADS that _AuxDataLen_ then describes.
--

=== Design Rationale for the Sealing Construction

_This section is informative and non-normative._

Omitting the nonce shrinks the payload and lets the derived keys be cached; the nonce-misuse resistance of AES-GCM-SIV keeps the construction secure for up to O(2^64^) blocks observed by an adversary.
On cloud servers, each virtual machine and supervisor domain should have its own CSK; M-mode firmware moves a CC between them by importing its SCC under the source CSK and exporting it under the target CSK.

The `SIV`, the GCM-SIV tag, is the encryption of the `POLYVAL` hash (<<KLE-SCC-POLYVAL>>) of the MDH with _ADSDropped_ cleared, the Locality Secrets and the Content.
Hashing the Locality Secrets, rather than deriving the keys from them, binds the SCC to the Localities for the cost of one `Montmul` per block.
This is much faster than most KDFs and, like omitting the nonce, with no new derived keys when the set changes, it allows the keys to be cached.
Distinct sets give the same `SIV` with probability at most (`len_AD` + `len_PC`) {times} 2^-126^.
Taking `SIV` as ``AD2[1]`` makes `SIV2` and the second keystream depend on the first payload, so an ADS cannot be grafted onto another SCC.
Bit 127 separates tag inputs from keystream inputs, as in AES-GCM-SIV; bit 126 makes the keystreams of the two segments differ by design, at the cost of one bit of security.

[[KLE-error-state-transfer]]
=== Export and Import of a Locker in an Error State

A locker in an Error State consists only of an MDH (Rule <<KLE-GR-clear-locker-content-error-state>>), and uses no KLF capacity.
Of that MDH, in the locker and in its exported image, only the _State_ field is checked; the other fields are not validated (<<KLE-Metadata-validity>>).
There is no Content to encrypt, and KLE does not authenticate the MDH: any software in the current environment can produce a locker in an arbitrary Error State, by provisioning it and issuing `kl.setst` with an Error-State immediate, so authentication would prove nothing.
Neither direction produces an SCC or a PCCC, opens a management operation, or takes part in resumption.

*Exporting* a locker in an Error State takes two steps, and no `kl.mgmt`:

. Read the _State_ field with `kl.getst` (<<KLE-instruction-getst>>), and find an Error State.
. Read the MDH with `kl.getmd` or `kl.getmdv` (<<KLE-instruction-getmd>>), and store it to memory; `kl.size` reports 16.

A `kl.mgmt` with `#immed7` = `kl_cfg_exporting` on a locker in an Error State is permitted but useless: it leaves the locker unchanged and opens no management operation; only its common steps take effect: `klnamedlocker` naming the locker and `klstart` becoming 0 (<<KLE-locker-management>>).
The `SIV`, `SIV2` and `IMPQUAL` registers take no part in this export and in the corresponding import.

*Importing* such an image takes one step:

. Issue `kl.mgmt` with `#immed7` = `kl_cfg_importing` and the 16-byte MDH as the auxiliary operand, carried whole by Form C or D, or by a Form A from the KLIOBUF. The instruction:
.. zeroizes the locker it names and copies the MDH into it, with _AuxDataLen_ and _ADSDropped_ set to 0 (Rule <<KLE-GR-clear-locker-content-error-state>>);
.. replaces a _State_ of 54 or 55, or of 53 without `Zklexpire`, by _Invalid_.

The instruction is uninterruptible. It only transfers the MDH.
No `kl.mgmt` with `#immed7` = `kl_cfg_management_end` needs to follows: issuing one performs no operation (Rule <<KLE-GR-fall-through-mgmt>>).

[[KLE-CSK-requirements]]
== Architectural Requirements on the Context Sealing Key

The KLE unit operates only with an active Context Sealing Key (CSK).
Without one, every KLE instruction and KLE CSR access raises a KLE missing-CSK exception, except accesses to the `mklcsk` and Locality Secret CSR groups (<<Zkl-ISA-priv.adoc#KLE-CSR-locality-groups>>), which are configured independently of the CSK, and reads of the identification CSRs `klmvendorid`, `klmarchid`, `klmimpid` and `klmaxiobuflen` (<<KLE-CSR-impl-ids>>, <<KLE-CSR-klmaxiobuflen>>), so that firmware can identify the KLE unit before a CSK exists.

The CSK is established in exactly one of four ways:

. M-mode programs it through the `mklcsk` CSR group (<<Zkl-ISA-priv.adoc#KLE-CSR-mklcsk>>).
. A secure hardware block exclusive to M-mode, such as Caliptra cite:[caliptra], or a port to one, configures it through a dedicated interface based on public-key encryption.
  Only M-mode may request this, by a handle or a wrapped key, and no software, M-mode included, ever sees the clear key; addressing and key transport are platform-specific and outside the scope of this specification.
. It is hardwired at manufacturing time, per die or shared across batches.
. A secure RBG (<<KLE-Prerequisites>>) generates it at boot, accessible to no software.
+
All harts of a well-defined subsystem of an SoC share it, and cannot exchange SCCs with other subsystems; it survives the reset or fatal condition of a single hart, and is regenerated only at the power-on reset of the subsystem.

Only M-mode, under the first way, can read the CSK in clear.
The third and fourth ways suit mainly specialized embedded deployments: a hardwired CSK cannot be reconfigured or revoked, and a boot-generated one cannot preserve SCCs across power loss.
With a hardwired CSK, the KLE unit is available from reset; otherwise, only once the CSK is established.
A hart reset resets its KLE state (<<KLE-reset-and-m-mode-only>>) and, under the first and second ways, its CSK, which must then be established again.

NOTE: When the CSK is shared across devices, CCs meant to be device-bound must name _ChipScrt_ or _DevScrt_ in their _Locality_.

Persistence of a configurable CSK is implementation-specific.
Transferring a CSK to another endpoint, such as the M-mode firmware of another device, a local TPM (for instance across suspension or host hibernation), or a cloud-based HSM, requires an authenticated public-key wrapping mechanism, outside the scope of this specification.

[[KLE-reset-and-m-mode-only]]
== KLE Unit Reset and M-mode-only Harts

A _KLE unit reset_ of a hart resets that hart's KLE architectural state (<<KLE-out-of-reset-unpriv>>, <<Zkl-ISA-priv.adoc#KLE-out-of-reset-priv>>); in a KLE unit shared by several harts, it affects only that hart's state, shared Locality Secrets excepted.
A hart reset implies a KLE unit reset of that hart, and so does a fatal condition (<<KLE-error-architecture>>), with the differences of <<Zkl-ISA-priv.adoc#KLE-out-of-reset-priv>>.
Reset does not affect a hardwired CSK.

On an M-mode-only hart, every software-programmable Locality Secret whose CSR group is not implemented is unconfigured (<<KLE-Localities>>), and, where the KLE Privileged Architecture is not implemented, `KLS` is treated as Initial; <<Zkl-ISA-priv.adoc#KLE-priv>> states which of its CSRs may exist on such a hart.

[[KLE-software-requirements]]
== Software Requirements

_This section is architecturally informative and non-normative.
This section's rules bind software; the architecture does not enforce them._

KLE splits complex operations into small instructions, and relies on software to use them as intended.
This is normal for a RISC architecture, however the discipline involved is all the more critical because KLE is a security feature.
Software, privileged or not, that ignores these Rules may lose functionality and cause security breached: it may compromise the integrity of cryptographic state and, through the checks of the KLE architecture, its availability, or reveal a CC to peer- or lower-privileged software environments not meant to receive it.

[[KLE-interposed-software,interposed software]]Definition: _Interposed software_::
(((interposed software)))
_Interposed software_ is code that runs while other software may have a halted instruction, or a management operation in progress, in the live KLE state of the hart.
It includes every trap handler, for an exception or an interrupt, in any mode, even that of the interrupted code (for instance a U-mode signal handler), and any other code that shares that KLE state, such as another thread of the same process.

[[KLE-SR-isolation]]
=== Isolation of Contexts

[horizontal]
[[KLE-SR-clear-before-lower-mode,SR1]]SR1:: Software must prevent unauthorized parties from accessing its lockers directly.
In particular, before giving control to a less privileged mode, software must (save and) clear every locker that holds a CC it owns or that it has placed in a Configuration State, completing any export first (Rule <<KLE-SR-never-clear-exporting>>).

[[KLE-SR-restore-own-lockers,SR2]]SR2:: When switching to a less privileged component, software must restore only the lockers saved for that component, and clear the others; the same holds for `kliobuflen`, and for the KLIOBUF when `kliobuflen` {ne} 0.

[[KLE-SR-save-shared-state,SR3]]SR3:: Software that uses the KLIOBUF, `klstart` or `klnamedlocker`, or performs a management operation, while the KLE state of a less privileged context is live, must first save the state it uses and restore it before returning, so that the less privileged context observes its own values and no data of the more privileged mode.

[[KLE-SR-kliobuf]]
=== Requirements on the KLIOBUF

[horizontal]
[[KLE-SR-kliobuflen-zero,SR4]]SR4:: Software should set `kliobuflen` to zero once it no longer needs the KLIOBUF contents, which context-switch code must otherwise save and restore (<<KLE-save-order>>, <<KLE-restore-order>>); setting `kliobuftop` to zero instead keeps them accessible.

[[KLE-klstart-software-check]]
=== Requirements on `klstart`

`klstart` exists once per hart, and nothing resets it before other software uses it: an instruction that honors `klstart` starts at the value it finds, and `kl.mgmt`, `kl.clearall` and every instruction that honors `klstart` write it.
Rules <<KLE-SR-klstart-save>> to <<KLE-SR-klstart-restore>> bind <<KLE-interposed-software,interposed software>>.

[horizontal]
[[KLE-SR-klstart-save,SR5]]SR5:: Such software must save `klstart` before its first KLE instruction.

[[KLE-SR-klstart-zero,SR6]]SR6:: Such software must write 0 to `klstart` before its first instruction that honors it, which would otherwise skip the prefix of its own operand that the interrupted software has processed.

[[KLE-SR-klstart-restore,SR7]]SR7:: Such software must restore the saved `klstart` before control returns to the interrupted software, which would otherwise resume from another point, or restart.
A handler that skips the instruction retires it instead (Rule <<KLE-SR-handler-duty>>).

[[KLE-SR-klstart-no-reset,SR8]]SR8:: Software should not write 0 to `klstart` to force a full restart of `kl.exec` or `kl.derive` once per-block state effects have been committed.

[[KLE-SR-management]]
=== Requirements on Management Operations

Rules <<KLE-SR-klnamedlocker-write>> and <<KLE-SR-nested-export-first>> bind <<KLE-interposed-software,interposed software>>, and Rule <<KLE-SR-klnamedlocker-finish>> all software; an instruction issued in violation of these three Rules acts on whatever locker `klnamedlocker` names (<<KLE-named-locker-rules>>).

[horizontal]
[[KLE-SR-klnamedlocker-write,SR9]]SR9:: Before `kl.load`, `kl.store`, `kl.mvin`, `kl.mvout`, an instruction naming `KLNL` (Rule <<KLE-GR-klnamedlocker-override>>), or a `kl.mgmt` that names its locker explicitly, software must read `klnamedlocker`; if it does not hold the intended value, software must save it, write the intended value, and restore the saved one before control returns to the code that set it.
The intended value is the number of the target locker, 32 for a transfer to or from the KLIOBUF, and 32 or the number of the target locker for a `kl.mgmt` that names its locker explicitly.

[[KLE-SR-klnamedlocker-finish,SR10]]SR10:: Software that completes or abandons a management operation must then write 32 to `klnamedlocker`, or restore the value it saved.

[[KLE-SR-nested-export-first,SR11]]SR11:: Before opening, on another locker, an export from a Valid State or an import other than the short import of an Error-State image (<<KLE-error-state-transfer>>), while the locker that `klnamedlocker` names is in State `kl_cfg_exporting` or `kl_cfg_importing`, software must save that locker by a nested export and restore it before returning to the code that opened its operation, or terminate that code.
While that locker is in such a State, software must not write another value to `klnamedlocker` before saving it this way, so that `klnamedlocker` names the owner of the authentication registers at every trap.
Software may instead clear a locker in State `kl_cfg_importing`, whose import then restarts (<<KLE-CC-management>>).

[[KLE-SR-no-interleaving,SR12]]SR12:: Software should complete or discard a management operation before it performs cryptographic operations or manages other lockers.
Code that must interleave them, for instance in several threads of one process, needs coordination, such as lightweight threads with KLE context-switching support, or a mutex.

[[KLE-SR-no-unconditional-clear,SR13]]SR13:: System software must not clear a locker under management unconditionally at every context switch, since repeated restarts may prevent completion.

[[KLE-SR-never-clear-exporting,SR14]]SR14:: Unless it terminates the owner, software must not clear a locker during an export, base or nested, since a clear is not deferred and destroys the CC.
It first completes the export and saves the image, with its MDH and any resumption state, in storage protected for the owner; it may then clear the locker, whose image preserves any outer export, and restores the image before the owner resumes.

[[KLE-SR-uninterruptible,SR16]]SR16:: Software must not rely on whether an uninterruptible instruction (Rule <<KLE-GR-uninterruptible-class>>) has retired when a handler runs, and must interact with it only as Rule <<KLE-GR-conflicting-access-rule>> prescribes.

[[KLE-handler-duties]]
=== Duties of Every Exception Handler

<<KLE-interposed-software,Interposed software>> is bound by Rules <<KLE-SR-klstart-save>> to <<KLE-SR-klstart-restore>>, <<KLE-SR-klnamedlocker-write>> and <<KLE-SR-nested-export-first>>.

On entry, before its first KLE instruction, the handler:

. saves `klstart` (Rule <<KLE-SR-klstart-save>>);
. saves `klnamedlocker` (Rule <<KLE-SR-klnamedlocker-write>>);
. writes 0 to `klstart` before its first instruction that honors it (Rule <<KLE-SR-klstart-zero>>); and
. saves the vector state, and writes 0 to `vstart`, before its first vector KLE instruction (Rule <<KLE-GR-vector-legality>>).

Before each instruction that Rule <<KLE-SR-klnamedlocker-write>> lists, it sets `klnamedlocker` as that Rule requires.

On exit, the handler:

. restores `klnamedlocker` to its saved value, or to 32 if it has cleared, instead of saving, the locker that value named (<<KLE-save-order>>);
. restores the vector state, `vstart` included; and
. restores `klstart` last, exactly as saved (Rules <<KLE-SR-klstart-restore>> and <<KLE-SR-klstart-no-reset>>).

A handler that skips the trapping instruction applies its retirement effects to `klstart` and `vstart` instead of restoring them (Rule <<KLE-SR-handler-duty>>).

[[KLE-reading-locker-state]]
=== Reading the _State_ of a Locker

* `kl.getst Xd, KLNL` reads the _State_ of the locker that `klnamedlocker` names; with `klnamedlocker` = 32 it returns 0 (Rule <<KLE-GR-klnl-no-named-locker>>).
* To inspect lockers whose numbers it holds in registers, software writes each number in turn to `klnamedlocker` and names `KLNL`.
* `kl.getst` reads the _State_, `kl.getstx` the _StateExtension_, and `kl.getmd` the whole MDH.
* On RV32, `kl.getst` and `kl.getstx` write the GPR pair `X[d+1] @ X[d]`, and `kl.getmd` a quartet (<<KLE-instruction-getst>>, <<KLE-instruction-getmd>>).
* A _State_ in 48–55, that is, with `(State & 0x38) = 0x30`, is an Error State (<<KLE-states-error>>).
* Software that relies on the output of a usage instruction checks, immediately after the instruction, that the locker is in a Valid State before using the output.

[[KLE-management-routines]]
=== Management Routines

* The recommended approach is that a management routine takes the locker number as a parameter, 32 meaning the locker indexed by `klnamedlocker`. It saves `klnamedlocker`, and on entry and at every restart writes the number to it or, for 32, keeps its value, returning an error to its caller if that is 32 too (Rule <<KLE-GR-klnl-openings>>); it names the locker `KLNL` throughout, and restores the saved value on exit, also when it abandons the operation (Rule <<KLE-SR-klnamedlocker-finish>>, <<Zkl-pseudocode.adoc#KLE-management-code-snippets>>).
//  A handler can thus call it, also for a nested export or import of the locker that the interrupted operation manages.
* After each management instruction, the routine reads the _State_ of the locker: _Unconfigured_ means the locker has been cleared, so a provisioning or an import restarts and an export has lost its CC (Rule <<KLE-GR-cleared-under-management>>); an Error State means the operation has failed.
* An export sizes its buffer with `kl.size`, and reads the size again after its opening `kl.mgmt`.
* Software does not interleave cryptographic operations, or the management of other lockers, with the steps of a management operation (Rule <<KLE-SR-no-interleaving>>).

[[KLE-save-order]]
=== Context Save Order

. Save `klstart`.
. Save `klnamedlocker`.
. If the saved `klnamedlocker` is in [0..31], save that locker first, with Form C or D `kl.mgmt` and no KLIOBUF transfer (Rule <<KLE-SR-nested-export-first>>), choosing the path by its _State_, read with `kl.getst` on `KLNL`:
.. _Unconfigured_: save no locker image;
.. an Error State: save its MDH by the short Error-State path (<<KLE-error-state-transfer>>);
.. otherwise, export the locker, by nested export if it is under management.
. With `Zklio`:
.. save `kliobuflen` and `kliobuftop`;
.. if `kliobuflen` is non-zero, save the buffer contents with `kl.output`, with `klnamedlocker` = 32, `klstart` = 0 and `kliobuftop` = `kliobuflen`, then write 0 to `kliobuflen`.
. Save every other locker that is not _Unconfigured_, with `klnamedlocker` = 32 between exports.

Each export completes, with its completing `kl.mgmt` and outcome check, before its locker is cleared (Rule <<KLE-SR-never-clear-exporting>>).

Instead of saving a locker being provisioned or imported, the handler may clear it, subject to Rules <<KLE-SR-no-unconditional-clear>> and <<KLE-SR-never-clear-exporting>>; the interrupted software then restarts the operation (Rule <<KLE-GR-cleared-under-management>>), and the handler restores 32 in place of a saved `klnamedlocker` that named that locker (<<KLE-restore-order>>).

A handler that passes `ml` through the KLIOBUF for the other lockers configures `kliobuflen` {ge} 16 for their exports and imports, and restores the saved value afterwards.

// ////////////////////////////////////////////////////////////////////

[[KLE-restore-order]]
=== Context Restore Order

. Clear the lockers for which no image is restored below, or all of them with `kl.clearall` (Rule <<KLE-SR-restore-own-lockers>>).
. Restore the lockers other than the one that the saved `klnamedlocker` indexes, with `klnamedlocker` = 32 between imports.
. With `Zklio`:
.. restore `kliobuflen`;
.. restore the buffer contents, if saved, with `kl.input`, with `klnamedlocker` = 32, `klstart` = 0 and `kliobuftop` = `kliobuflen`;
.. restore `kliobuftop`.
. If the saved `klnamedlocker` is in [0..31] and an image was saved for the locker it indexes, restore that locker last, with Form C or D `kl.mgmt` and no KLIOBUF transfer.
. Restore the saved value of `klnamedlocker`, or 32 if the handler has cleared the locker it named instead of saving it.
. Restore `klstart` last.

[[KLE-handling-kle-exceptions]]
=== Handling a KLE Exception

A handler that can neither resolve nor forward a KLE exception covered by Rule <<KLE-SR-handler-duty>>, nor terminate the process:

. unless the locker is in a Configuration State, sets it to the Error State that <<KLE-exception-error-correspondence>> gives, or to _Invalid_ where it gives none: with `kl.setst` and that Error State as immediate (<<KLE-instruction-setst>>), or, if the locker is _Unconfigured_, by the short import of an MDH holding that State (<<KLE-error-state-transfer>>); and
. advances `xepc` past the instruction, retiring a usage instruction as Rule <<KLE-SR-handler-duty>> states.
