[[KLEE-separation]]
= Structure of the KLEE Specification: Separation of Architecture and Data Formats
ifdef::env-site[]
// On the site each page stands alone; the PDF gets these from src/Zkl.adoc.
include::partial$Zkl-symbols.adoc[]
endif::[]

The KLEE ISA is split into three normative chapters and one non-normative chapter.

* <<Zkl-ISA-unpriv.adoc#KLEE-unpriv>> defines the fixed part of the Unprivileged Architecture.
The instructions and architectural state are specified independently of the exact data formats they operate on.
It should be a chapter in the Unprivileged Architecture Part of the complete RISC-V specification document.

* {empty}
+
--
<<Zkl-ISA-machines.adoc#KLEE-Machines>> defines the Data Structures and Machines of the Unprivileged Architecture.

Within the RISC-V architecture, conformance to <<Zkl-ISA-unpriv.adoc#KLEE-unpriv>> requires full conformance to <<Zkl-ISA-machines.adoc#KLEE-Machines>>.
In other words, each implemented non-custom algorithm must fully exhibit the behavior specified there.

The Machines are kept separate from the instructions because the data formats used to manage keys are intended to be interoperable across different ISAs that implement KLEE or equivalent functionality. These formats are therefore not specific to RISC-V, and such ISAs must also support the Metadata Header format and the semantics of its fields verbatim. We envision that it could later be expunged and made into an independent industry standard accepted by other architecture designers.
--

* <<Zkl-ISA-priv.adoc#KLEE-priv>> defines the Privileged Architecture.
It should be a chapter in the Privileged Architecture Part of the complete RISC-V specification document.

* <<Zkl-pseudocode.adoc#KLEE-pseudocode-examples>> provides non-normative pseudocode examples illustrating the intended use of the algorithms defined in <<Zkl-ISA-machines.adoc#KLEE-Machines>>.
Its rightful place would be in an appendix of the complete specification document.
