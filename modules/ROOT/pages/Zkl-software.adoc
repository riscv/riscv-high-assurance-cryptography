_This chapter is informative, except the Rules of <<KLE-software-requirements>>, which are normative for software._
The examples follow <<Zkl-notation.adoc#KLE-Notation>>: a vector register loaded from memory holds the lowest-addressed byte in its least significant bits.
They assume RV64, where a 64-bit operand is one GPR; on RV32 it is a GPR pair (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-multiple-GPRs>>).

// ///////////////////////////////////////////////////////////////////

[[KLE-software-requirements]]
== Software Requirements

These Rules bind privileged and unprivileged software; the architecture does not enforce them.
Violations may corrupt cryptographic state, make it unavailable, or reveal a CC to peer or less privileged software.

[[KLE-interposed-software,interposed software]]Definition: _Interposed software_.::
(((interposed software)))
_Interposed software_ runs while the hart's live KLE state may hold a halted instruction or open management operation for other software.
It includes every exception and interrupt handler in any mode, even those of the interrupted code, and other code sharing that state, such as another thread of the same process.

// ////////////////////////////////////////////////////////////////////

[[KLE-SR-isolation]]
=== Isolation and the KLIOBUF

[horizontal]
[[KLE-SR-clear-before-lower-mode,SR1]]SR1:: Software must keep its lockers from unauthorized parties.
Before giving control to a less privileged mode, it must:
* clear every locker that holds its CC or that it has placed in a Configuration State, completing any export first (Rule <<KLE-SR-no-unconditional-clear>>);
* if the KLIOBUF holds its data, write to `kliobuflen` either the value saved for the less privileged mode (<<KLE-save-order>>), which zeroes the buffer below that length, or 0, which makes the buffer inaccessible (<<Zkl-ISA-unpriv.adoc#KLE-CSR-kliobuflen>>).

[[KLE-SR-kliobuflen-zero,SR2]]SR2:: Software should zero `kliobuflen` once it no longer needs the KLIOBUF contents, which context-switch code must otherwise save and restore (<<KLE-save-order>>, <<KLE-restore-order>>); zeroing `kliobuftop` instead keeps them accessible.

// ////////////////////////////////////////////////////////////////////

[[KLE-klstart-software-check]]
=== Requirements on `klstart`

Each hart has one `klstart`, which persists between programs; an instruction that honors it starts at its current value.
Without these Rules, interposed software could skip its operand prefix or use the wrong KLIOBUF offset, and the interrupted instruction could resume at the wrong position, without an exception.

[horizontal]
[[KLE-SR-klstart-save,SR3]]SR3:: <<KLE-interposed-software,Interposed software>> must save `klstart` (`kl.getks` or a CSR read) before any other KLE instruction, write 0 to it before its first instruction that honors it, and restore it before returning to the interrupted software.
A handler that skips the trapping instruction applies the retirement effects to `klstart` instead (Rule <<KLE-SR-handler-duty>>).

[[KLE-SR-klstart-no-reset,SR4]]SR4:: Software should not write 0 to `klstart` to restart a `kl.exec` that has committed per-block state effects.

[[KLE-SR-klstart-iobuf,SR5]]SR5:: Software that transfers an image through the KLIOBUF must save `klstart` after each `kl.mvin KLIOBUF` or `kl.mvout KLIOBUF`, write 0 to it before the `kl.input` or `kl.output` that next fills or drains the KLIOBUF, and restore it before the next `kl.mvin KLIOBUF` or `kl.mvout KLIOBUF`.

// ////////////////////////////////////////////////////////////////////

[[KLE-SR-management]]
=== Requirements on Management Operations

The KLE implementation does not enforce Rules <<KLE-SR-klnamedlocker-write>> and <<KLE-SR-nested-export-first>>: instructions use the current `klnamedlocker`, and a `kl.mgmt` naming its locker explicitly overwrites it regardless of an open operation (<<Zkl-ISA-unpriv.adoc#KLE-named-locker-rules>>).

[horizontal]
[[KLE-SR-klnamedlocker-write,SR6]]SR6:: Before `kl.load`, `kl.store`, `kl.mvin`, `kl.mvout`, an instruction naming `KLNL` (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-klnamedlocker-override>>), or a `kl.mgmt` naming its locker explicitly, interposed software must, if `klnamedlocker` differs from the intended value, save it, write that value, and restore the saved value before returning to the code that set it.
The intended value is the target locker number, or 32 for a KLIOBUF transfer; a `kl.mgmt` naming its locker explicitly permits either.
On completing or abandoning a management operation, any software must write 32 to `klnamedlocker` or restore its saved value.

[[KLE-SR-nested-export-first,SR7]]SR7:: Before a `kl.mgmt` on another locker, all software must save any locker in `kl_cfg_exporting` or `kl_cfg_importing` by nested export, whether or not `klnamedlocker` names it.
It must restore the locker before returning to the code that opened the operation, or terminate that code; it may instead clear a locker in `kl_cfg_importing`, whose import then restarts (<<Zkl-ISA-unpriv.adoc#KLE-CC-management>>).
While such a locker is open and no nested export has saved it, software must write only that locker number or 32 to `klnamedlocker`: context-switch code uses it to identify the owner of the hart's single set of authentication registers (<<Zkl-ISA-unpriv.adoc#KLE-auth-reg-association>>, <<Zkl-ISA-unpriv.adoc#KLE-KLF>>).

[[KLE-SR-no-interleaving,SR8]]SR8:: Software should complete or discard a management operation before it performs cryptographic operations or manages other lockers; code that must interleave them, such as threads of one process, needs coordination, such as a mutex or lightweight threads with KLE context-switching support.
Software that writes 32 to `klnamedlocker` while its own import or export is open, for instance for a transfer through the KLIOBUF (<<Zkl-ISA-unpriv.adoc#KLE-instruction-mv>>), must have no other locker in State `kl_cfg_importing` or `kl_cfg_exporting`, even one that a nested export has saved: context-switch code then finds the open operation by its State (<<KLE-save-order>>).

[[KLE-SR-no-unconditional-clear,SR9]]SR9:: At a context switch, system software may clear a locker being provisioned or imported instead of saving it; the operation then restarts.
It must also support saving such a locker and must not clear it unconditionally at every context switch, which may prevent completion.
Unless it terminates the owner, software must complete a base or nested export before clearing its locker: clearing destroys the CC.

[[KLE-SR-handlers]]
=== Requirements on Exception Handlers

[horizontal]
[[KLE-SR-handler-duty,SR10]]SR10:: A handler that neither resolves nor forwards an exception, even to an in-process handler, and does not terminate the process must do the following if <<Zkl-ISA-unpriv.adoc#KLE-exception-error-correspondence>> gives an Error State:
+
--
. set the locker on which the exception was raised, for `KLNL` the one that `klnamedlocker` names (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-klnamedlocker-updates>>), to the _State_ that the same table gives, with a `kl.setste` (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-error-state-can-be-reconfigured>>), even if the locker is _Unconfigured_; and
. advance `xepc` past the trapping instruction, which would otherwise trap again, and, for a usage instruction, keep the output prefix that `klstart` and `vstart` record, zero the rest of the output window, and apply the retirement effects on `klstart` and `vstart` (Rules <<Zkl-ISA-unpriv.adoc#KLE-GR-outcomes>> and <<Zkl-ISA-unpriv.adoc#KLE-GR-klstart-vstart>>); for a `kl.mgmt`, also write to `klnamedlocker` the number of the locker it names, as its retirement would (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-klnamedlocker-updates>>).
--

[[KLE-SR-uninterruptible,SR11]]SR11:: Software must not rely on whether an uninterruptible instruction (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-interruptibility-classes>>) has retired when a handler runs, and must interact with it only as Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-conflicting-access-rule>> prescribes.

// ////////////////////////////////////////////////////////////////////

[[KLE-SR-localities]]
=== Requirements on Localities

[horizontal]
[[KLE-SR-locality-unconfigure,SR12]]SR12:: Software must not unconfigure a Locality Secret while a locker bound to it may still be exported: the export of such a locker in a Valid State is refused (<<Zkl-ISA-unpriv.adoc#KLE-SCC-export>>) until the Locality Secret is configured again.

[[KLE-SR-hypervisor-locality-clear,SR13]]SR13:: Before running software not entrusted with the CCs of the loaded virtual machine, a hypervisor must write `zeros(128)`, or a value that no virtual machine uses, to `hkllocality` and `hklvirtbootscrt` (<<Zkl-ISA-priv.adoc#KLE-CSR-hkllocality>>, <<Zkl-ISA-priv.adoc#KLE-CSR-hklvirtbootscrt>>).

// ////////////////////////////////////////////////////////////////////

[[KLE-SR-transfer-loops]]
=== Requirements on Transfers, Keys and Outputs

[horizontal]
[[KLE-SR-no-klstart-loop,SR14]]SR14:: Software must bound a `kl.mvin` or `kl.mvout` sequence by a length fixed beforehand, the image size read with `kl.size` or, for a provisioning, the length of the PI that it built, and check the _State_ afterward.
`klstart` is not a loop bound (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>, NOTE after Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-error-state-can-be-reconfigured>>).

[[KLE-SR-export-final-check,SR15]]SR15:: Software must rely on an exported image only if the _State_ read after the last instruction of the export is neither _Unconfigured_ nor an Error State or, when the image is the MDH alone, if the MDH that `kl.getmd*` returned is not _Unconfigured_ (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>).
After a `kl.mgmt` that opens an export from a Valid State, software must continue only if the _State_ is `kl_cfg_exporting`; a Valid State means a refusal (<<Zkl-ISA-unpriv.adoc#KLE-SCC-export>>).

[[KLE-SR-csk-change,SR16]]SR16:: M-mode must not change the value of a CSK (<<Zkl-ISA-unpriv.adoc#KLE-CSK-requirements>>), or erase it without keeping what re-establishes the same value, until every export open on the hart under it, base or nested, has completed and its image has been saved.
With trapped selection, M-mode may replace the CSK held at a KLE missing-CSK exception, keeping what re-establishes it (<<KLE-handling-kle-exceptions>>).
Software should complete the exports and imports open on a hart before it opens one at another _SCProtection_ level, since each switch of the CSK held traps to M-mode.
Breaking this recommendation never makes an export or import use the CSK of another level: each `kl.mgmt` that uses a CSK checks its level, and traps on a mismatch.

[[KLE-SR-skid-usage-policy,SR17]]SR17:: A system that intends to protect a System Key (<<Zkl-ISA-unpriv.adoc#KLE-system-keys>>) must associate at least a _UsagePolicy_ with its SKID in the SKS.

[[KLE-SR-unverified-plaintext,SR18]]SR18:: Software must not use plaintext that an AEAD Machine outputs before the locker reaches _Success_ for that message, and must discard it if the locker does not.

[[KLE-SR-scc-clear-unauthenticated,SR19]]SR19:: Software must not rely on a value read from the clear blocks of an SCC in memory (<<Zkl-ISA-unpriv.adoc#KLE-GR-scc-clear-blocks>>) as authentic until an import of the SCC, or other means, has authenticated it.

[[KLE-state-save-and-restore-order]]
== Software Guidelines

The guidelines of this section are for privileged software.

// Here we collect the duties that the KLE state places on privileged software and exception handlers, in the order software meets them.

For context switches or other use while a less privileged context's KLE state is live, follow <<KLE-save-order>> and <<KLE-restore-order>> to preserve its values and isolate more privileged data (Rule <<KLE-SR-clear-before-lower-mode>>).
The normative Rules of <<KLE-software-requirements>> take precedence over these guidelines.

// ////////////////////////////////////////////////////////////////////

[[KLE-reading-locker-state]]
=== Reading the _State_ of a Locker

To inspect lockers by number, software writes each number in turn to `klnamedlocker` and names `KLNL` in the following instructions. While an import or export is open, it first saves that locker by a nested export (Rule <<KLE-SR-nested-export-first>>). To find an open locker, as step 3 of <<KLE-save-order>> requires, software issues `kl.getst` with the explicit operands `K0` to `K31`, which leaves `klnamedlocker` unchanged.

To inspect a locker so named, it then uses the instructions `kl.getst`, `kl.getstx` (<<Zkl-ISA-unpriv.adoc#KLE-instruction-getst>>) and `kl.getmd` (<<Zkl-ISA-unpriv.adoc#KLE-instruction-getmd>>).

Immediately after a usage instruction, check for a Valid State before using its output; for AEAD plaintext, also follow Rule <<KLE-SR-unverified-plaintext>>.

// ////////////////////////////////////////////////////////////////////

[[KLE-iobuf-length-probe]]
=== Probing the Maximum KLIOBUF Length

As with `vsetvl`, the getter and setter instructions give the maximum KLIOBUF length: write a large value with `kl.setbl`, then read it back with `kl.getbl`.
The probe destroys the buffer contents and sets `kliobuftop` to `kliobuflen`; software that needs its `kliobuftop` saves it with `kl.getbt` and restores it with `kl.setbt` after the last `kl.setbl`.
A context restore does not probe: each OS, or other execution environment, probes once and keeps the value, which only an M-mode write to `mklmaxiobuflen` changes (<<Zkl-ISA-priv.adoc#KLE-CSR-mklmaxiobuflen>>).

[source,asm]
----
  li        a0, -1  # a0 ← all ones, above any maximum
  kl.getbl  t1      # save the current length
  kl.setbl  a0      # zeroes the buffer, clamps to the maximum
  kl.getbl  t0      # t0 ← length granted
  kl.setbl  t1      # restore the length; the contents stay zero
----

// ////////////////////////////////////////////////////////////////////

[[KLE-management-routines]]
=== Management Routines

* A management routine should take the locker number as a parameter, 32 meaning the locker that `klnamedlocker` names.
It saves `klnamedlocker`, then, on entry and at every restart, writes the number to it; for 32 it keeps the value, and returns an error to its caller if that value is also 32 (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>).
It names the locker `KLNL` throughout.
On exit, even when it abandons the operation, it restores the saved value, or writes 32 if that value names a locker that a clear has destroyed (Rule <<KLE-SR-klnamedlocker-write>>, <<KLE-management-code-snippets>>).
//  A handler can thus call it, also for a nested export or import of the locker that the interrupted operation manages.
* After each management instruction, the routine reads the _State_ of the locker, in one code path for resumption and restart:
** _Unconfigured_: the locker has been cleared, so a provisioning or an import restarts and an export has lost its CC (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>);
** an Error State: the operation has failed;
** a Valid State after an export-opening `kl.mgmt`: the export was refused, and the routine reports an error and leaves the locker in place.
* An export sizes its buffer with `kl.size`, and reads the size again after its opening `kl.mgmt`.
* Follow Rule <<KLE-SR-no-interleaving>> when coordinating management and cryptographic operations.

// ////////////////////////////////////////////////////////////////////

[[KLE-handler-duties]]
=== Duties of Every Exception Handler

<<KLE-interposed-software,Interposed software>> is bound by Rules <<KLE-SR-klstart-save>>, <<KLE-SR-klnamedlocker-write>> and <<KLE-SR-nested-export-first>>.

On entry, the handler performs these steps, using the getter and setter instructions for `klstart` and `klnamedlocker` (<<Zkl-ISA-unpriv.adoc#KLE-instruction-getter-setter>>):

. save `klstart` before any other KLE instruction (`kl.getks`, Rule <<KLE-SR-klstart-save>>);
. save `klnamedlocker` (`kl.getnl`, Rule <<KLE-SR-klnamedlocker-write>>);
. write 0 to `klstart` (`kl.setksi 0`) before its first instruction that honors it (Rule <<KLE-SR-klstart-save>>); and
. save the vector state, and write 0 to `vstart`, before its first vector KLE instruction (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-vector-legality>>).

Before each instruction that Rule <<KLE-SR-klnamedlocker-write>> lists, it sets `klnamedlocker` as that Rule requires.

On exit, the handler:

. restores `klnamedlocker` (`kl.setnl`) to its saved value, or to the value that item 2 of Rule <<KLE-SR-handler-duty>> writes, or to 32 if it has cleared, instead of saving, the locker that value named (<<KLE-save-order>>);
. restores the vector state, including `vstart`; and
. restores `klstart` last (`kl.setks`), exactly as saved (Rules <<KLE-SR-klstart-save>> and <<KLE-SR-klstart-no-reset>>).

A handler that skips the trapping instruction applies its retirement effects to `klstart` and `vstart` instead of restoring them (Rule <<KLE-SR-handler-duty>>).

// ////////////////////////////////////////////////////////////////////

[[KLE-save-order]]
=== Context Save Order

Before any export, the saving mode saves the Locality Secret CSR values of the context, unless it holds them, and sets the Locality Secret CSRs that it owns to the values under which the images are to be restored; a hypervisor writes its own value to `skllocality` (<<Zkl-ISA-priv.adoc#KLE-CSR-locality-groups>>).

. Save `klstart` (`kl.getks`).
. Save `klnamedlocker` (`kl.getnl`).
. Let the _managed locker_ be the locker that the saved `klnamedlocker` indexes, if it is in [0..31]; otherwise, the locker in State `kl_cfg_importing` or `kl_cfg_exporting`, if there is one; for a locker whose field that the saving mode owns is _Off_, its saved image gives that State (Rules <<KLE-SR-nested-export-first>> and <<KLE-SR-no-interleaving>>).
These Rules make it the owner of the authentication registers, if a locker owns them (<<Zkl-ISA-unpriv.adoc#KLE-auth-reg-association>>).
If the field of the managed locker that the saving mode owns is _Off_, keep its saved image: it remains the managed locker, which <<KLE-restore-order>> restores last or defers again.
Otherwise, if there is a managed locker, save it first, with Form C or D `kl.mgmt` (Rule <<KLE-SR-nested-export-first>>). How depends on its _State_, read with `kl.getst`; transfer directly to memory (`kl.store` with `Xl` = `x0`) or through GPRs or vector registers, not through the KLIOBUF, which step 4 has yet to save:
.. _Unconfigured_: save no locker image;
.. an Error State: export only its MDH (<<Zkl-ISA-unpriv.adoc#KLE-error-state-transfer>>);
.. otherwise, export the locker, by nested export if it is in a Configuration State.
. With `Zklio`:
.. save `kliobuflen` and `kliobuftop` (`kl.getbl`, `kl.getbt`);
.. if `kliobuflen` is non-zero, save the buffer contents with a `kl.output` whose `Xl` holds the saved `kliobuflen`, with `klnamedlocker` = 32, `klstart` = 0 and `kliobuftop` = `kliobuflen` (`kl.setnli 32`, `kl.setksi 0`, `kl.setbt` of the saved length), then write 0 to `kliobuflen` (`kl.setbli 0`).
. For every locker other than the managed locker, act by its `*llockerstatus` field that the saving mode owns (<<Zkl-ISA-priv.adoc#KLE-CSR-llockerstatus>>); a locker without such a field counts as Dirty. Keep `klnamedlocker` = 32 between exports.
** Clean or _Off_: keep its saved image;
** Dirty and _Unconfigured_: erase its saved image;
** otherwise: save it as step 3 saves the managed locker.

Complete each export with `kl.mgmt` and an outcome check before clearing its locker (Rules <<KLE-SR-no-unconditional-clear>> and <<KLE-SR-export-final-check>>).

An export-opening `kl.mgmt` that leaves a Valid locker in its Valid State was refused (Rule <<KLE-SR-export-final-check>>): the handler saves no image for that locker and reports the error to the code that owns it, and the restore order clears the locker, whose CC is lost.
Software that complies with Rule <<KLE-SR-locality-unconfigure>> and configures the Locality Secret CSRs before it exports (<<Zkl-ISA-priv.adoc#KLE-CSR-locality-groups>>) encounters no refused export.


Software does not read or compare `IMPQUAL`: the unit does, on import.
An image restored on a unit whose `IMPQUAL` differs has its ADS dropped (_AuxDataLen_ reads 0 in `kl.getmd` after the import, unless the implementation has already written a new ADS), and a halted checkpointable operation restarts; software whose mode the _UsagePolicy_ of the locker admits may call `kl.clearads` before the export, which shortens the image; otherwise the import on the target drops the ADS.

If the handler clears a locker being provisioned or imported under Rule <<KLE-SR-no-unconditional-clear>>, the interrupted operation restarts (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>); restore 32 instead of a saved `klnamedlocker` that named it (<<KLE-restore-order>>).

// ////////////////////////////////////////////////////////////////////

[[KLE-restore-order]]
=== Context Restore Order

. Clear every locker for which no image is restored below, a locker whose restoration is deferred included, or all of them with `kl.clearall` (Rule <<KLE-SR-clear-before-lower-mode>>).
. Set the Locality Secret CSRs to the values in force when the images were saved (<<KLE-save-order>>, <<Zkl-ISA-priv.adoc#KLE-CSR-locality-groups>>) before any import; restore a value of the context that differs from them, such as the `skllocality` of a guest, after the last import and before `KLS`. A later import of a deferred locker needs the same values around it.
. Restore the lockers other than the managed locker (<<KLE-save-order>>), with `klnamedlocker` = 32 between imports.
. With `Zklio`:
.. restore `kliobuflen` (`kl.setbl`), which zeroes the buffer and sets `kliobuftop` to it;
.. restore the buffer contents, if saved, with a `kl.input` whose `Xl` holds the saved `kliobuflen`, with `klnamedlocker` = 32, `klstart` = 0 and `kliobuftop` = `kliobuflen`;
.. restore `kliobuftop` (`kl.setbt`), after the buffer, since a write of `kliobuflen` resets it.
. If an image was saved for the managed locker, restore it last, with Form C or D `kl.mgmt`, transferring directly from memory (`kl.load` with `Xl` = `x0`) or through GPRs or vector registers, not through the KLIOBUF, which step 4 has restored.
. Restore the saved value of `klnamedlocker`, or 32 if the handler has cleared the locker it named instead of saving it.
. Restore `klstart` after every other KLE instruction (`kl.setks`).
. Write the `*llockerstatus` fields that the restoring mode owns: Clean for a restored locker, _Off_ for a locker whose restoration is deferred, and Initial for a cleared locker. Then write `KLS`, after those CSRs (<<Zkl-ISA-priv.adoc#KLE-KLS-field-in-mstatus>>).

The getter and setter instructions are the recommended way for software to access `klnamedlocker`, `kliobuflen`, `kliobuftop` and `klstart` (<<Zkl-ISA-unpriv.adoc#KLE-instruction-getter-setter>>).

[[KLE-handling-kle-exceptions]]
=== Handling a KLE Exception

A handler that can neither resolve nor forward a KLE exception for which <<Zkl-ISA-unpriv.adoc#KLE-exception-error-correspondence>> gives an Error State, nor terminate the process, follows Rule <<KLE-SR-handler-duty>>.

For KLE missing-CSK and locker-Off, which have no Error State, a handler issues no `kl.setste`: it resolves the exception, forwards it (for locker-Off, see <<Zkl-ISA-priv.adoc#KLE-CSR-llockerstatus>>), or terminates the process.
A KLE fatal-error exception has no Error State either and cannot be resolved: the M-mode handler re-establishes the M-mode KLE state that the hart KLE state reset cleared (<<Zkl-ISA-priv.adoc#KLE-out-of-reset-priv>>) and reports the loss of their KLE state to the contexts that held it.
If the condition persists (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-rbg-failure>>), its first KLE instruction or KLE CSR access raises the exception again, so it saves `mepc`, `mcause` and `mstatus` first; it then makes none until a KLE unit reset.
A KLE RBG-unavailable exception is resolved by re-executing the instruction after a delay that the handler chooses: the architecture does not report the recovery of the entropy source, and until then the instruction traps again (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-rbg-failure>>).
A handler follows Rule <<KLE-SR-handler-duty>> for it only when it gives up.

An M-mode handler resolves a KLE missing-CSK exception by establishing a CSK and re-executing the instruction (<<Zkl-ISA-priv.adoc#KLE-CSR-mklcfg>>).
With `mtval` = 0, it establishes the CSK of the level that the platform uses most or, with `Smklmultcsk`, every CSK that it holds; an export or import at another level then traps again with 8 + L.
With `mtval` = 8 + L, it establishes CSK~L~, through the `mklcsk` group under the first way or the secure hardware block under the second.
With trapped selection it first writes L to `mklcfg`; with `Smklmultcsk` the exception has already selected L.
It keeps what re-establishes each CSK, one per level, in memory that only M-mode can access: the value under the first way, a handle or wrapped key under the second.

[[KLE-management-code-snippets]]
== Code for Locker Configuration and Export Operations

These provisioning, import and export sequences provide a starting point for libraries or OS APIs, showing operations and error detection; application-specific error handling is omitted.

Registers::
GPR `t0` holds the number of the locker to be provisioned, imported or exported, or 32 for the locker that `klnamedlocker` names, and GPR `t6` points to the 16-byte aligned memory location of the PI or SCC (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-management-check-order>>).
The MDH is loaded and stored with `ld` and `sd`, and passed in the GPR pair `s5:s4`; on RV32 it takes a GPR quartet (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-multiple-GPRs>>).

Selecting the locker::
The routines save `klnamedlocker` on entry and use `select_locker` below on entry and every `restart`.
Their KLE instructions encode no locker number: `kl.load`, `kl.store`, `kl.mvin` and `kl.mvout` have no locker operand; `kl.mgmt`, `kl.getst`, `kl.getmd` and `kl.size` name `KLNL` (Rules <<Zkl-ISA-unpriv.adoc#KLE-GR-klnamedlocker-override>> and <<Zkl-ISA-unpriv.adoc#KLE-GR-locker-less-transfers>>).
A clear resets `klnamedlocker` to 32. A `KLNL` opening then performs no operation (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>), whereas an opening on a named locker opens it, even a Valid one.
The next _State_ check reads 0. The preamble at `restart` then names locker `t0` again or, if `t0` = 32, branches to `no_locker`: the clear destroyed the locker.
On exit, restore the saved value or 32 if it names a cleared locker (Rule <<KLE-SR-klnamedlocker-write>>, Error handling below).
A handler that has saved the interrupted operation may call these routines, including for nested export or import of that operation's locker (<<KLE-state-save-and-restore-order>>).
+
----
.macro select_locker              # t0 = p: 0-31, or 32 for the named locker
  li        t1, 32
  bgeu      t0, t1, 1f            # p = 32: keep the named locker
  kl.setnl  t0                    # p in 0-31: name locker p
  j         2f
1:
  kl.getnl  t2
  bgeu      t2, t1, no_locker     # none named, or cleared: error to caller
2:
.endm
----

Checking the _State_::
+
--
After each management instruction, the code reads the _State_ with `kl.getst` and, if it is 0, the _StateExtension_ with `kl.getstx`.
If a handler has meanwhile cleared the locker or set an Error State, every following `kl.mvin`, `kl.mvout`, `kl.load`, `kl.store` or `kl.mgmt`, including a `KLNL` opening or completion after a clear, performs no operation (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>), and the check detects the change:

* after a clear, `KLNL` reads as _Unconfigured_, with _State_ and _StateExtension_ 0: a provisioning or an import restarts at its preamble, and an export, whose CC is destroyed, branches to `handle_errors`;
* after an Error State, or after the completing `kl.mgmt`, `KLNL` still names the locker, so the check reads its final _State_ and _StateExtension_; an Error State abandons the operation.

`kl.load` and `kl.store` take `Xl` = `x0`, so after a clear, with `klnamedlocker` = 32, they designate no locker and fall through (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-management-check-order>>, item 5).
The macro `check_state` makes this check for provisioning and import; an export branches to `handle_errors` on _State_ 0 alone.
----
.macro check_state on_clear       # after a management instruction
  kl.getst  t2, KLNL
  bnez      t2, 1f                # State not 0: no clear, no Error State
  kl.getstx t2, KLNL
  beqz      t2, \on_clear         # Unconfigured: the locker was cleared
  j         handle_errors         # Error State
1:
.endm
----

Only the check after the last instruction is required; the earlier ones react sooner.
The code may bound the restarts and then branch to its error handling, for robustness only: system software must let the operation complete (Rule <<KLE-SR-no-unconditional-clear>>).
--

Error handling::
The code at `handle_errors` and `no_locker` is not shown; `no_locker` returns an error to the caller, since with `t0` = 32 no locker is named, or a clear has destroyed the named one.
If the saved value of `klnamedlocker` names the locker that a clear has destroyed, both write 32 to `klnamedlocker` instead of restoring it, as does a handler that clears a locker instead of saving it (<<KLE-restore-order>>).
This is always the case for `no_locker` reached after a clear with `t0` = 32, and for `handle_errors` reached on an export whose locker the caller had named and that has been cleared.
`handle_errors` writes 0 to `klstart`, which a `kl.mvin` or `kl.mvout` loop leaves at its last transfer point, and restores `klnamedlocker` as the routines do on exit.
If the locker is still in a Configuration State, `handle_errors` clears it if it is being provisioned or imported and, if it is being exported, completes the export with the saved MDH, which restores the locker.

[[KLE-provisioning-code]]
=== Provisioning

The provisioning code assumes that the Content immediately follows the MDH in memory.
The MDH of the PI carries _State_ = 0; the completing `kl.mgmt` sets _Ready_.

*Provisioning Code (`Zklmv`)*
----
# t5 holds the length of the PI's Content (hence, excluding the MDH) in bytes.
# t5 can be zero. The caller constructed the PI and so knows this length.
# t5 is never modified, so the working count and pointer can be re-derived
# from it whenever the operation is restarted.

  ld        s4, 0(t6)             # load MDH[63:0] from memory
  ld        s5, 8(t6)             # load MDH[127:64] from memory
  kl.getnl  s8                    # save the caller's value: the routine may
                                  # run inside another management operation

restart:
  select_locker                   # name the locker: every KLE instruction
                                  # below acts on it; a clear resets it to 32
  kl.mgmt   KLNL, #kl_cfg_provisioning, s5:s4 # start provisioning, load MDH
  check_state restart             # Error State: provisioning ended

  addi      t4, t6, 16            # source pointer: first byte after MDH
  mv        s1, t5                # working byte count, re-derived from t5
                                  # on restart

  vsetvli   s6, zero, e8, m2, ta, ma # s6 = VLMAX
vloop:
  mv        s2, s1
  bleu      s2, s6, 1f
  mv        s2, s6
1:
  vsetvli   s2, s2, e8, m2, ta, ma # AVL <= VLMAX, so vl = AVL, multiple of 16
  vle8.v    v2, (t4)              # load a chunk of the PI
  kl.mvin   v2                    # move it into the locker
  add       t4, t4, s2            # bump the source pointer
  sub       s1, s1, s2            # decrement the bytes still to load
  check_state restart             # *new* Error State
  bnez      s1, vloop

  kl.mgmt   KLNL, #kl_cfg_management_end # complete provisioning
                                  # and possibly reconstruct data
  check_state restart             # catches errors at completion (e.g., SKS)

finished:
  kl.setnl  s8                    # restore the caller's value
# The locker is Ready, or in Failure after a data error at completion. Any
# Error State met above is new, since the PI carried State = 0:
# handle_errors decides the course of action.
----

*Provisioning Code (`Zklmem`)*
----
  ld        s4, 0(t6)             # load MDH[63:0] from memory
  ld        s5, 8(t6)             # load MDH[127:64] from memory
  kl.getnl  s8                    # save the caller's value

restart:
  select_locker                   # name the locker (a clear resets it to 32)
  kl.mgmt   KLNL, #kl_cfg_provisioning, s5:s4 # start prov. and load MDH
  check_state restart             # Error State?

  # Assume that the Content directly follows the MDH in memory.
  kl.load   16(t6), x0            # load rest of PI into the locker
  check_state restart
  kl.mgmt   KLNL, #kl_cfg_management_end # complete provisioning
                                  # and possibly reconstruct data
  check_state restart             # catches errors at completion (e.g., SKS)
finished:
  kl.setnl  s8                    # restore the caller's value
----

[[KLE-export-code]]
=== Export

*Export Code (`Zklmv`)*
----
  kl.getnl   s8                   # save the caller's value
  select_locker                   # name the locker for all that follows
  kl.size    s1, KLNL             # TOTAL size to export
  beqz       s1, handle_errors    # 0 means the locker is unconfigured

  {...}  # here code that allocates the buffer to store the exported data

  kl.getmd   s5:s4, KLNL          # get MDH, including its _State_
  beqz       s4, handle_errors    # all zero: locker cleared since kl.size
  sd         s4, 0(t6)            # store MDH[63:0] to memory
  sd         s5, 8(t6)            # store MDH[127:64] to memory

  addi       t6, t6, 16           # point to next memory region
  li         s3, 16               # s3 = 16 (size of MDH)
  beq        s1, s3, done         # only the MDH to store (e.g., Error State)

  kl.mgmt    KLNL, #kl_cfg_exporting  # start exporting
  kl.getst   t2, KLNL
  beqz       t2, handle_errors    # cleared, or Error State set meanwhile
  li         t3, kl_cfg_provisioning # 56, the lowest Configuration State
  bltu       t2, t3, export_refused # Valid State: export refused
  kl.size    t2, KLNL             # size now that the export is open
  bne        t2, s1, handle_errors # ADS changed since the buffer was sized
  addi       s1, s1, -16          # adjust size to remove the MDH
  mv         t4, t6               # destination: first byte after stored MDH
  vsetvli    s6, zero, e8, m2, ta, ma # s6 = VLMAX
store_loop:
  mv         s2, s1
  bleu       s2, s6, 1f
  mv         s2, s6
1:
  vsetvli    s2, s2, e8, m2, ta, ma # AVL <= VLMAX, so vl = AVL, multiple of 16
  kl.mvout   v2                   # move chunk out of the locker,
                                  # advance klstart
  vse8.v     v2, (t4)             # store it
  add        t4, t4, s2           # bump the destination pointer
  sub        s1, s1, s2           # decrement the bytes still to store
  kl.getst   t2, KLNL
  beqz       t2, handle_errors    # cleared (CC lost), or Error State
  bnez       s1, store_loop

finished:
  # Restore _State_ from the saved MDH.
  kl.mgmt    KLNL, #kl_cfg_management_end, s5:s4
  kl.getst   t2, KLNL
  beqz       t2, handle_errors    # cleared, or `kl_stateext_mgmt_auth`
done:
  kl.setnl   s8                   # restore the caller's value
----

[WARNING]
====
This is an incomplete procedure, like the other management listings.
A locker in an Error State is covered: only its MDH is stored.
`export_refused` reports a refused export and leaves the locker in place (<<KLE-management-routines>>).
A locker under management is exported by the same sequence, but the caller must also save `klstart` before the opening `kl.mgmt`, which clears it, and restore it after the re-import (<<KLE-state-save-and-restore-order>>); this is not shown.
====

*Export Code (`Zklmem`)*
----
# Up to the size check after the opening kl.mgmt, and from finished on, the
# code is that of the Zklmv version.
  kl.store  0(t6), x0             # store SIV, IMPQUAL, SIV2 and Content
                                  # of the locker (Xl = x0)
  kl.getst  t2, KLNL
  beqz      t2, handle_errors     # cleared (CC lost), or Error State
----

[[KLE-import-code]]
=== Import

*Import Code (`Zklmv`)*
----
  ld         s4, 0(t6)            # load MDH[63:0] from memory
  ld         s5, 8(t6)            # load MDH[127:64] from memory
  srli       s7, s4, 20           # bits [29:20] of the saved MDH:
  andi       s7, s7, 0x3ff        # _StateExtension_ @ _State_
  kl.getnl   s8                   # save the caller's value

restart:
  select_locker                   # name the locker (a clear resets it to 32)
  kl.mgmt   KLNL, #kl_cfg_importing, s5:s4    # open locker for import, load MDH
  kl.getst  t2, KLNL
  bnez      t2, 2f                # State not 0: the import is open
  kl.getstx t2, KLNL
  beqz      t2, restart           # Unconfigured: locker cleared, restart
  slli      t2, t2, 6             # Error State: if as saved, the short import
  beq       t2, s7, success       # is complete, with this one kl.mgmt
  j         handle_errors         # new Error State (e.g., invalid Metadata)
2:
  kl.size   s1, KLNL              # size of the image the locker accepts,
                                  # without a dropped ADS
  beqz      s1, restart           # 0: locker cleared since the check
  addi      t4, t6, 16            # first byte after the MDH
  addi      s1, s1, -16           # image size to load, without the MDH

  vsetvli   s6, zero, e8, m2, ta, ma # s6 = VLMAX
vloop:
  mv        s2, s1
  bleu      s2, s6, 1f
  mv        s2, s6
1:
  vsetvli   s2, s2, e8, m2, ta, ma # AVL <= VLMAX, so vl = AVL, multiple of 16
  vle8.v    v2, (t4)              # load a chunk of the SCC
  kl.mvin   v2                    # move it into the locker, advance klstart
  add       t4, t4, s2
  sub       s1, s1, s2
  check_state restart
  bnez      s1, vloop

  kl.mgmt   KLNL, #kl_cfg_management_end, s5:s4 # decrypt and auth SCC
                                  # and restore _State_ from the saved MDH
  check_state restart             # catches "Authentication Failed"

success:
  kl.setnl  s8                    # restore the caller's value
----

*Import Code (`Zklmem`)*
----
  ld        s4, 0(t6)             # load MDH[63:0] from memory
  ld        s5, 8(t6)             # load MDH[127:64] from memory
  srli      s7, s4, 20            # bits [29:20] of the saved MDH:
  andi      s7, s7, 0x3ff         # _StateExtension_ @ _State_
  kl.getnl  s8                    # save the caller's value

restart:
  select_locker                   # name the locker (a clear resets it to 32)
  kl.mgmt   KLNL, #kl_cfg_importing, s5:s4    # open locker for import, load MDH
  kl.getst  t2, KLNL
  bnez      t2, 2f                # State not 0: the import is open
  kl.getstx t2, KLNL
  beqz      t2, restart           # Unconfigured: locker cleared, restart
  slli      t2, t2, 6             # Error State: if as saved, the short import
  beq       t2, s7, success       # is complete, with this one kl.mgmt
  j         handle_errors         # new Error State (e.g., invalid Metadata)
2:
  addi      t4, t6, 16            # first byte after the MDH

  kl.load   0(t4), x0             # load rest of SCC into the locker
  check_state restart
  kl.mgmt   KLNL, #kl_cfg_management_end, s5:s4 # decrypt and auth locker,
                                  # if necessary complete it
  check_state restart             # catches `kl_stateext_mgmt_auth`

success:
  kl.setnl  s8                    # restore the caller's value
----

The opening `kl.mgmt` of provisioning and import receives the MDH in Form D (<<Zkl-ISA-unpriv.adoc#KLE-MVR-open>>) and checks all of it, even for the image of a locker in an Error State (<<Zkl-ISA-unpriv.adoc#KLE-error-state-transfer>>).
The completing `kl.mgmt KLNL, #kl_cfg_management_end` can still transition the locker to an Error State (<<Zkl-ISA-unpriv.adoc#KLE-instruction-mgmt>>), for instance at SKS resolution, at a Machine check on the PI or at key generation (provisioning), or at Locality resolution or authentication (import); with _KeyType_ = 2 it can also raise a KLE RBG-unavailable exception (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-rbg-failure>>).
The `kl.getst` after it detects this, as well as a clear or an Error State set earlier.
A data error found by a Machine check on a field of the PI or SCC leaves the locker in _Failure_ instead (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-completion-state>>); these listings do not test for it.

[[KLE-routines-after-clear]]
=== Behavior of Routines Whose Locker is Cleared by a Handler

This section traces a handler clearing the locker of <<KLE-provisioning-code>>, <<KLE-export-code>> or <<KLE-import-code>>, for both `Zklmv` and `Zklmem`.
Rule <<KLE-SR-no-unconditional-clear>> permits this during provisioning or import, and during export only if the owner is terminated.
If defective privileged software nevertheless resumes an export, its first _State_ check detects the loss; the routine must terminate because the CC is irrecoverable.

The handler::
The handler saves `klnamedlocker` on entry; clearing its named locker sets it to 32 (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-klnamedlocker-updates>>).
On exit, it writes 32 to `klnamedlocker` instead of restoring the cleared locker's saved number, so the routine resumes with `klnamedlocker` = 32 (<<KLE-handler-duties>>, <<KLE-save-order>> and <<KLE-restore-order>>).

The instructions of the routine::
+
--
With `klnamedlocker` = 32, the routine's instructions find no locker (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>):

* `kl.mvin` and every `kl.mgmt` naming `KLNL`, including the completing one, do nothing;
* `kl.mvout` writes zeros to its vector destination, which the export routine may store to memory before its next check;
* `kl.load` and `kl.store`, with `Xl` = `x0`, designate no locker and fall through (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-management-check-order>>, item 5);
* the next check reads _State_ 0: `check_state` in a provisioning or an import, which also reads _StateExtension_ 0, and `kl.getst` in an export.
--

The next step of the routine::
+
--
* A provisioning or an import with `t0` in 0–31 branches to `restart`. There `select_locker` names locker `t0` again, the opening `kl.mgmt` zeroizes and reopens it, and the operation starts over.
* A provisioning or an import with `t0` = 32 branches to `restart`, where `select_locker` reads 32 and branches to `no_locker`. The caller gets an error, because nothing records which locker it meant.
* An export branches to `handle_errors` at its first check, because the clear has destroyed the CC; the memory image it has written so far is incomplete and must be discarded.
--

Why a clear resets `klnamedlocker`::
+
--
Suppose a clear left `klnamedlocker` unchanged. `KLNL` would then still name the cleared locker:

* While the locker stays _Unconfigured_, instructions fall through and the next check reads _State_ 0. Export takes `handle_errors`; provisioning or import with `t0` in 0–31 restarts. With `t0` = 32, `select_locker` would instead recover the cleared locker's number at `restart` and reopen it, missing the loss and defeating the handler's intent to free it.
* Once another context receives the locker, any routine, including export, would act on that context's CC through `KLNL` and read its _State_.

Resetting `klnamedlocker` to 32 lets a routine using only the named locker detect a clear, which therefore counts as reconfiguration.
--

[[KLE-machine-code-examples]]
== Code for the Machines

The listings of <<KLE-machine-code-examples>> are RV64 code for the V extension (`VLEN` {ge} 128) and Zbb; locker `K0` is the target, and <<KLE-pseudocode-ECDH-KDF>> also uses `K1` and `K2`.
On a hart with `VLEN` = 64 (<<Zkl-ISA-unpriv.adoc#KLE-unpriv-exts-overview>>), a 128-bit operand needs a register group: code selects `LMUL` {ge} 2 and vector register numbers that are multiples of it (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-vector-legality>>), and checks the `vl` that `vsetvli` grants before it issues a KLE instruction.
Arguments arrive in `a0`–`a6`; `error` is the caller's error handling, not shown, which erases the output buffer of a decryption before it reports (Rule <<KLE-SR-unverified-plaintext>>).
`import_scc n, rs` stands for the import code of <<KLE-import-code>> with `t0` = `n` and `t6` = `rs`. It changes `vtype`, but no `a` register.
Most examples have `b` = 128: a 16-byte block is processed with `vl` = 16 and SEW = 8, so `KLLEN` = 128, and a shorter piece of `p` bytes with `vl` = `p`, so `KLLEN` = 8 {times} `p`.
Most listings omit the `kl.getst` that checks, before an output is used, that the locker is still in a Valid State (<<KLE-reading-locker-state>>). A usage instruction on a locker that a handler has cleared or invalidated performs no operation and writes zeros.

[[KLE-ECB-mode-example]]
=== Electronic Codebook Mode

The following listing encrypts data with an ECB CC.

[[KLE-pseudocode-ECB-encryption]]
.Simple Example: Encryption with no Authentication
----
# a0 = SCC, a1 = plaintext, a2 = ciphertext buffer, a3 = length in bytes,
# a multiple of 16

  import_scc 0, a0                # import the SCC into locker K0
  kl.getst  t1, K0
  beqz      t1, error             # State 0: the import failed

  kl.setst  K0, #kl_state_encrypt # configure the locker to encrypt
  kl.getst  t1, K0
  li        t2, kl_state_encrypt
  bne       t1, t2, error

  vsetivli  zero, 16, e8, m1, ta, ma # one block: KLLEN = 128
  beqz      a3, 2f
1:
  vle8.v    v0, (a1)              # one block of plaintext
  kl.exec   v0, K0, v0            # encrypt it
  vse8.v    v0, (a2)
  addi      a1, a1, 16
  addi      a2, a2, 16
  addi      a3, a3, -16
  bnez      a3, 1b
2:
----

In _Encrypt_ and _Decrypt_ a Form A `kl.exec` processes every block of its operand (<<Zkl-ISA-machines.adoc#KLE-ECB-mode>>), so one instruction can encrypt several blocks inside the KLE unit.
The following listing encrypts eight blocks per `kl.exec`, with `KLLEN` = 1024, and the last group with a smaller multiple of 128 bits.
With LMUL = 8 and `VLEN` {ge} 128, a register group holds at least 128 bytes.
An interrupt may halt such a `kl.exec` after some blocks; on return, the same instruction resumes from `klstart` (<<Zkl-ISA-unpriv.adoc#KLE-CSR-klstart>>), so the loop needs no code for it.

[[KLE-pseudocode-ECB-encryption-multi-block]]
.ECB Encryption, Eight Blocks per Instruction
----
# a0 = SCC, a1 = plaintext, a2 = ciphertext buffer, a3 = length in bytes,
# a multiple of 16

  import_scc 0, a0                # import the SCC into locker K0
  kl.setst  K0, #kl_state_encrypt # configure the locker to encrypt
  kl.getst  t1, K0
  li        t2, kl_state_encrypt
  bne       t1, t2, error         # the import failed

  li        t3, 128               # eight blocks
  beqz      a3, 2f
1:
  minu      t4, a3, t3            # this group: 16 to 128 bytes
  vsetvli   zero, t4, e8, m8, ta, ma # KLLEN = 8 * t4
  vle8.v    v8, (a1)              # up to eight blocks of plaintext
  kl.exec   v8, K0, v8            # encrypt them all
  vse8.v    v8, (a2)
  add       a1, a1, t4
  add       a2, a2, t4
  sub       a3, a3, t4
  bnez      a3, 1b
2:
----

[[KLE-chaining-example]]
=== Chaining/Feedback Modes (CBC, CFB, and OFB)

The `kl.setst` into _Encrypt_ or _Decrypt_ of a CBC or CFB CC takes the IV as a Form C operand (<<Zkl-ISA-machines.adoc#KLE-chaining>>), and the CC keeps the chaining value across `kl.exec` instructions, so the loop needs no code for it.
An interrupt may halt a `kl.exec` after some blocks, with the chaining value of the last completed block; on return, the same instruction resumes from `klstart` (<<Zkl-ISA-unpriv.adoc#KLE-CSR-klstart>>).
The following listing encrypts with a CBC CC, one block per `kl.exec`.

[[KLE-pseudocode-CBC-encryption]]
.CBC Encryption
----
# a0 = SCC, a1 = plaintext, a2 = ciphertext buffer, a3 = number of blocks,
# a5 = the 16-byte IV

  import_scc 0, a0                # import the SCC into locker K0
  vsetivli  zero, 16, e8, m1, ta, ma # one block: KLLEN = 128
  vle8.v    v1, (a5)
  kl.setst  K0, #kl_state_encrypt, v1  # IV ← v1
  kl.getst  t1, K0
  li        t2, kl_state_encrypt
  bne       t1, t2, error         # the import failed

  beqz      a3, 2f
1:
  vle8.v    v0, (a1)
  kl.exec   v0, K0, v0            # chained to the previous block
  vse8.v    v0, (a2)
  addi      a1, a1, 16
  addi      a2, a2, 16
  addi      a3, a3, -1
  bnez      a3, 1b
2:
----

With `VLEN` {ge} 128 and LMUL = 8, a register group holds at least eight blocks, and one `kl.exec` chains them in order inside the KLE unit.
The following listing takes the number of blocks as a parameter; for the last group, of fewer than eight blocks, it reduces `vl`.

[[KLE-pseudocode-CBC-encryption-multi-block]]
.CBC Encryption, Eight Blocks per Instruction
----
# a0 = SCC, a1 = plaintext, a2 = ciphertext buffer, a3 = number of blocks,
# a5 = the 16-byte IV; LMUL = 8 holds at least 8 blocks

  import_scc 0, a0
  vsetivli  zero, 16, e8, m1, ta, ma
  vle8.v    v1, (a5)
  kl.setst  K0, #kl_state_encrypt, v1  # IV ← v1
  kl.getst  t1, K0
  li        t2, kl_state_encrypt
  bne       t1, t2, error         # the import failed

  li        t3, 8                 # blocks per group
  beqz      a3, 2f
1:
  minu      t4, a3, t3            # blocks in this group: 8, then the rest
  slli      t5, t4, 4             # bytes: 16 * blocks
  vsetvli   zero, t5, e8, m8, ta, ma # KLLEN = 128 * blocks
  vle8.v    v8, (a1)
  kl.exec   v8, K0, v8            # each block chained to the last
  vse8.v    v8, (a2)
  add       a1, a1, t5
  add       a2, a2, t5
  sub       a3, a3, t4
  bnez      a3, 1b
2:
----

A CFB CC takes its segment size `u` from the _AuxInfo_ field of its MDH, which is fixed at provisioning.
The following listing encrypts any number of bytes with CFB8, that is, with an SCC whose `u` = 8.

[[KLE-pseudocode-CFB8-encryption]]
.CFB8 Encryption
----
# a0 = SCC, a1 = plaintext, a2 = ciphertext buffer, a3 = length in bytes,
# a5 = the 16-byte IV

  import_scc 0, a0                # u = 8, from the MDH
  vsetivli  zero, 16, e8, m1, ta, ma
  vle8.v    v1, (a5)
  kl.setst  K0, #kl_state_encrypt, v1       # IV ← v1
  kl.getst  t1, K0
  li        t2, kl_state_encrypt
  bne       t1, t2, error         # the import failed

  li        t3, 128               # a full register group
  beqz      a3, 2f
1:
  minu      t4, a3, t3            # whole segments: one byte each
  vsetvli   zero, t4, e8, m8, ta, ma
  vle8.v    v8, (a1)
  kl.exec   v8, K0, v8
  vse8.v    v8, (a2)
  add       a1, a1, t4
  add       a2, a2, t4
  sub       a3, a3, t4
  bnez      a3, 1b
2:
----

CBC and CFB8 decryption differ from the listings above only in the State: `kl_state_decrypt` replaces `kl_state_encrypt`.

=== XEX/XTS Modes

The listings below encrypt and decrypt a data unit of `n` blocks, `b` = `KLLEN` = 128.
The parameter `last_len` is the length of the last block in bytes: if it is 16, the data unit consists of whole blocks;
otherwise the last block is partial, and the data unit is completed by <<Zkl-ISA-machines.adoc#KLE-XTS-from-XEX>>.

[[KLE-pseudocode-basic-IV-mode]]
.XEX Encryption
----
# a0 = SCC, a1 = PT, a2 = CT (may equal a1), a3 = n blocks, the last of
# a4 = last_len bytes, 1 <= last_len <= 16, n >= 1, n >= 2 if last_len < 16,
# a5 = the 16-byte tweak

  import_scc 0, a0
  vsetivli  zero, 16, e8, m1, ta, ma # one block: KLLEN = 128
  vle8.v    v0, (a5)
  kl.setst  K0, #kl_state_encrypt, v0 # configure to encrypt, set the tweak

  li        t1, 16
  mv        t2, a3                # m = n full blocks if last_len = 16,
  beq       a4, t1, 1f
  addi      t2, a3, -1            # n-1 otherwise
1:
  vle8.v    v0, (a1)
  kl.exec   v0, K0, v0            # encrypt one block of plaintext
  vse8.v    v0, (a2)
  addi      a1, a1, 16
  addi      a2, a2, 16
  addi      t2, t2, -1
  bnez      t2, 1b
  beq       a4, t1, 2f            # whole blocks: done

  # Ciphertext stealing: a1 points to P_m, a2 to C_m, s = last_len
  addi      t3, a2, -16           # C_{m-1}
  vle8.v    v0, (t3)              # CC, at mask index m-1
  vmv.v.v   v1, v0
  vsetvli   zero, a4, e8, m1, tu, ma # s bytes, the rest of v1 kept
  vle8.v    v1, (a1)              # v1 = CP @ P_m
  vse8.v    v0, (a2)              # C_m: the first s bytes of CC
  vsetivli  zero, 16, e8, m1, ta, ma
  kl.exec   v1, K0, v1            # C_{m-1}, at mask index m
  vse8.v    v1, (t3)
2:
----

P~m~ is read before C~m~ is written, so CT may be the same buffer as PT.

[[KLE-pseudocode-XEX-decryption]]
.XEX Decryption
----
# a0 = SCC, a1 = CT, a2 = PT (may equal a1), a3 = n blocks, the last of
# a4 = last_len bytes, 1 <= last_len <= 16, n >= 2 if last_len < 16,
# a5 = the 16-byte tweak

  import_scc 0, a0
  vsetivli  zero, 16, e8, m1, ta, ma # one block: KLLEN = 128
  vle8.v    v0, (a5)
  kl.setst  K0, #kl_state_decrypt, v0 # configure to decrypt, set the tweak

  li        t1, 16
  mv        t2, a3                # n plain blocks if last_len = 16,
  beq       a4, t1, 1f
  addi      t2, a3, -2            # m-1 = n-2 otherwise
1:
  beqz      t2, 3f
2:
  vle8.v    v0, (a1)
  kl.exec   v0, K0, v0            # decrypt one block of ciphertext
  vse8.v    v0, (a2)
  addi      a1, a1, 16
  addi      a2, a2, 16
  addi      t2, t2, -1
  bnez      t2, 2b
3:
  beq       a4, t1, 4f            # whole blocks: done

  # Ciphertext stealing: a1 points to C_{m-1}, a2 to P_{m-1}, s = last_len
  kl.setst  K0, #kl_xex_state_steal # skip mask index m-1
  vle8.v    v0, (a1)              # C_{m-1}
  kl.exec   v0, K0, v0            # PP, at mask index m
  vmv.v.v   v1, v0
  addi      t3, a1, 16            # C_m
  addi      t4, a2, 16            # P_m
  vsetvli   zero, a4, e8, m1, tu, ma # s bytes, the rest of v1 kept
  vle8.v    v1, (t3)              # v1 = CP @ C_m
  vse8.v    v0, (t4)              # P_m: the first s bytes of PP
  vsetivli  zero, 16, e8, m1, ta, ma
  kl.exec   v1, K0, v1            # P_{m-1}, at mask index m-1
  vse8.v    v1, (a2)              # the locker is now in Success
4:
----

As in encryption, C~m~ is read before P~m~ is written.
With stealing, the locker ends in _Success_, and a `kl.setst` into _Ready_ precedes the next tweak.

[[KLE-unified-AEAD-examples]]
=== Unified AEAD Algorithm Interface

The following pseudocode drives every AEAD Machine.
It reads `glog` and the pass flags with `kl.getinfo`; the MDH supplies `tag_len_p` as usual.
`AD_FINAL`, `DATA_FINAL` and `PREPASS_FINAL` set the corresponding final-block State with the meaningful bit length of the remaining piece, then issue its one `kl.exec` if the length is non-zero.
The final piece is the last 1 to 128 bits, a full block included, and is empty only for an empty AD, PT or CT (<<Zkl-ISA-machines.adoc#KLE-unified-AEAD>>).
<<KLE-pseudocode-unified-AEAD-final>> gives them; the Machine ignores the bits of the final transport byte above that length.

[[KLE-pseudocode-unified-AEAD]]
.Unified AEAD Processing
----
# K is a configured unified AEAD locker.  setup_nonce(K, N) enters
# Hash_Absorb.  A preset-nonce Machine needs only "kl.setst K,
# #kl_state_hash_absorb".  tag_len_p comes from the MDH.

  kl.getinfo t0, K
  andi       t1, t0, 0xf          # glog
  srli       t2, t0, 4
  andi       t2, t2, 1            # TwoPTPasses

  setup_nonce(K, N)
  if decrypt:
      kl.setst K, #kl_state_set_tag_value, tag_len_p
      kl.exec  K, tag              # Form B: the Machine retains the tag

  absorb_full_blocks(K, AD)
  AD_FINAL(K, AD_tail, AD_bits - full_bits(AD))

  if encrypt and t2:
      kl.setst K, #kl_state_aead_prepass
      absorb_full_blocks(K, PT)
      PREPASS_FINAL(K, PT_tail, PT_bits - full_bits(PT))
      kl.exec  siv, K              # Form C: the SIV; enters Encrypt
  else:
      kl.setst K, decrypt ? #kl_state_decrypt : #kl_state_encrypt

  crypt_full_blocks(K, decrypt ? CT : PT, decrypt ? PT : CT)
  DATA_FINAL(K, decrypt ? CT_tail : PT_tail,
             decrypt ? CT_bits - full_bits(CT) : PT_bits - full_bits(PT))

  if decrypt:
      kl.exec  K                   # Form D: verifies the retained tag
      require(kl.getst(K) == kl_state_success)
  else:
      kl.exec  tag, K              # Form C: the tag; Success, or Failure
                                   # with a zero tag if a replayed PT changed
      require(kl.getst(K) == kl_state_success)
----

[[KLE-pseudocode-unified-AEAD-final]]
.Routines of Unified AEAD Processing
----
# K is K0.  Each routine takes a0 = input and a1 = its length in bits,
# and changes only t5, t6, v0-v15 and the registers it returns.  The
# full-block routines process up to eight blocks per kl.exec and return
# a0 = the final piece and a1 = its length, 1 to 128 bits for nonempty
# input; full_bits(X) is 0 for an empty X, else X_bits - 1 with its low
# 7 bits cleared.  crypt_full_blocks and DATA_FINAL also take
# a2 = output buffer (advanced), and DATA_FINAL a3 = 1 to decrypt.
# The final pieces are a multiple of 2^glog bits, at most b = 128.

setup_nonce:                      # a supplied nonce, any length
  kl.setst  K0, #kl_state_set_aux_value, a1 # Form B: Xs = nonce_len
  addi      t5, a1, 7
  srli      t5, t5, 3             # ceil(nonce_len / 8) bytes
  j         1f                    # the last kl.exec enters Hash_Absorb

absorb_full_blocks:               # in Hash_Absorb or a prepass State
  beqz      a1, 2f                # empty input: empty final piece
  addi      t5, a1, -1
  andi      t5, t5, -128          # bits before the final piece
  sub       a1, a1, t5            # final piece: 1 to 128 bits
  srli      t5, t5, 3             # their bytes
  beqz      t5, 2f
1:
  li        t6, 128
  minu      t6, t5, t6            # up to eight blocks: KLLEN <= 1024
  vsetvli   zero, t6, e8, m8, ta, ma
  vle8.v    v8, (a0)
  kl.exec   K0, v8                # Form B: absorbs them all
  add       a0, a0, t6
  sub       t5, t5, t6
  bnez      t5, 1b
2:
  ret

crypt_full_blocks:                # in Encrypt or Decrypt
  beqz      a1, 3f
  addi      t5, a1, -1
  andi      t5, t5, -128
  sub       a1, a1, t5
  srli      t5, t5, 3
  beqz      t5, 3f
2:
  li        t6, 128
  minu      t6, t5, t6
  vsetvli   zero, t6, e8, m8, ta, ma
  vle8.v    v8, (a0)
  kl.exec   v8, K0, v8            # Form A: up to eight blocks
  vse8.v    v8, (a2)
  add       a0, a0, t6
  add       a2, a2, t6
  sub       t5, t5, t6
  bnez      t5, 2b
3:
  ret

AD_FINAL:
  kl.setst  K0, #kl_state_hash_last_block, a1
  j         1f
PREPASS_FINAL:
  kl.setst  K0, #kl_state_aead_prepass_last, a1
1:
  beqz      a1, 2f                # n = 0: the kl.setst completed the piece
  addi      t5, a1, 7
  srli      t5, t5, 3             # ceil(n/8) bytes
  vsetvli   zero, t5, e8, m1, ta, ma # KLLEN = 8 * ceil(n/8) >= n
  vle8.v    v0, (a0)
  kl.exec   K0, v0                # Form B: absorbs the piece
2:
  ret

DATA_FINAL:
  bnez      a3, 1f
  kl.setst  K0, #kl_state_enc_last_block, a1
  j         2f
1:
  kl.setst  K0, #kl_state_dec_last_block, a1
2:
  beqz      a1, 3f                # n = 0: the locker is in *_Tag_Finalize
  addi      t5, a1, 7
  srli      t5, t5, 3             # ceil(n/8) bytes
  vsetvli   zero, t5, e8, m1, ta, ma # KLLEN = 8 * ceil(n/8) >= n
  vle8.v    v0, (a0)
  kl.exec   v2, K0, v0            # Form A; enters *_Tag_Finalize
  vse8.v    v2, (a2)
3:
  ret
----

The caller does not pad AD, PT or CT, compute their length block, or maintain their per-message lengths.
It must retain the PT buffer through the GCM-SIV prepass and obey Rule <<KLE-SR-unverified-plaintext>> on decryption.

[[KLE-hash-example]]
=== Hash Functions, MACs and XOFs

The following sequence hashes a message with any Machine of <<Zkl-ISA-machines.adoc#KLE-hash-functions-MACs-XOFs>>; only the SCC and `out_bytes`, the number of output bytes, differ.

* *Message.* The caller passes `M` unpadded; the `kl.setst` that ends it pads it.
The final piece, of `M_bits` mod 64 bits, fits every Machine, since `b` {ge} 64; for BLAKE2 it is a whole number of bytes.
A partial final byte holds the final bits as the standard orders them: in its most significant positions for SHA-2 and SM3, in its least significant ones for SHA-3, KMAC and Ascon, and as its `H` does for HMAC.
* *Output length.* `Xs` = 8 {times} `out_bytes` in the `kl.setst` into _Hash_Output_ makes the Machine emit exactly `out_bytes` bytes, then enter _Success_.
For KMAC128 and KMAC256 it is also the `L` that the MAC encodes, while KMACXOF128 and KMACXOF256 encode `L` = 0; for every other Machine it only truncates the output.
`Xs` = 0 requests the full digest, or an unbounded XOF, and is invalid for KMAC128 and KMAC256.
`out_bytes` is at least 1 (8 for HMAC, 4 for KMAC128 and KMAC256), at most the digest length for a fixed-output Machine, and below 2^29^ for an XOF, KMAC128 or KMAC256.
* *BLAKE2.* A digest of `nn` {ne} `nn~max~` bytes, such as BLAKE2b-256, needs an SCC whose `nn`, which enters the IV, was set by the _Set_Aux_Value_ operation of <<Zkl-ISA-machines.adoc#KLE-BLAKE2>> or by a system-specific import.
With `kk` {ne} 0 and no system key, `M` starts with the key zero-padded to `b` bits (cite:[RFC7693] {sect}3.3), which alone forms the message for an empty `M`; a system key needs no such block.
* *The SCC* is in _Ready_, or in _Hash_Absorb_ if it was exported after a prefix of the message, such as secret content (NOTE of <<Zkl-ISA-machines.adoc#KLE-Ascon-Hash256>>); it then takes no first `kl.setst`, and `M` is the rest of the message.
An SCC of the NIK variant of <<Zkl-ISA-machines.adoc#KLE-HMAC>> must already hold its key.
An SCC of HMAC, KMAC128, KMAC256, or BLAKE2 with a system key must enable _Hash_Output_ (_MachinePolicy_[0]); for the MAC verification below, one of HMAC, KMAC128 or KMAC256 must enable _Hash_Verify_ (_MachinePolicy_[1]) instead.

[[KLE-pseudocode-hash]]
.Hashing a Message
----
# a0 = SCC of any hash, MAC or XOF, a1 = message M, a2 = M_bits,
# a3 = output buffer OUT, a4 = out_bytes

  import_scc 0, a0
  kl.setst  K0, #kl_state_hash_absorb

  andi      t3, a2, 63            # r: the final piece, 0 to 63 bits
  sub       t4, a2, t3
  srli      t4, t4, 3             # h: the bytes before it
  li        t2, 16
  beqz      t4, 2f
1:
  minu      t1, t4, t2            # the last chunk may be shorter
  vsetvli   zero, t1, e8, m1, ta, ma # KLLEN = 8 * t1
  vle8.v    v0, (a1)
  kl.exec   K0, v0                # absorb t1 bytes, unpadded
  add       a1, a1, t1
  sub       t4, t4, t1
  bnez      t4, 1b
2:
  kl.setst  K0, #kl_state_hash_last_block, t3 # r = 0: does nothing
  beqz      t3, 3f
  addi      t1, t3, 7
  srli      t1, t1, 3             # ceil(r/8) bytes
  vsetvli   zero, t1, e8, m1, ta, ma
  vle8.v    v0, (a1)
  kl.exec   K0, v0                # absorb the final r bits
3:
  slli      t1, a4, 3
  kl.setst  K0, #kl_state_hash_output, t1 # end the message: the Machine
                                  # pads
4:
  minu      t1, a4, t2
  vsetvli   zero, t1, e8, m1, ta, ma
  kl.exec   v0, K0                # emit the next t1 bytes
  vse8.v    v0, (a3)
  add       a3, a3, t1
  sub       a4, a4, t1
  bnez      a4, 4b
  kl.getst  t1, K0                # _Success_
----

To verify a MAC `T` of `T_len` bits with HMAC, KMAC128 or KMAC256 instead, the
code from label `3` on is replaced by the listing below.
For HMAC, min(`T_len`, `t`) must equal the locker's `tag_len_p`; KMAC128 and KMAC256 bind `L` = `tag_len_p` into the MAC, so `T_len` must equal `tag_len_p` (Rule <<Zkl-ISA-machines.adoc#KLE-MGR-tag-verify>>).
The listing compares `tag_len_p` bits.
For KMAC128 and KMAC256, it takes `T_len` {le} 8 {times} `VLEN`, since a register group with LMUL = 8 holds 8 {times} `VLEN` bits.

.MAC Verification
----

3:
  kl.setst  K0, #kl_state_hash_verify, a6
  srli      t1, a6, 3
  vsetvli   zero, t1, e8, m8, ta, ma # KLLEN = T_len
  vle8.v    v0, (a5)
  kl.exec   K0, v0                # compares tag_len_p bits
  kl.getst  t1, K0                # _Success_ if T matches,
                                  # _Failure_ otherwise
----

[[KLE-ECDH-KDF-example]]
=== Key Agreement and Key Derivation

The following sequence runs an ephemeral P-256 key agreement, derives an AES-256 key `K` = SHA-256(`00000001` {vvert} `Z` {vvert} `FixedInfo`) from its shared secret `Z` with the one-step key-derivation function of cite:[NIST-SP-800-56Cr2] {sect}4.1, and places `K` in a GCM locker. Software sees neither `Z` nor `K`.

* *Lockers.* `K1` holds an ECC Machine for secp256r1, `K0` a SHA-256 Machine and `K2` a GCM Machine with AES-256 and the full `tag_len_p`, each in _Ready_.
The ECC States have no named constants, so the listing writes them by number (<<Zkl-ISA-machines.adoc#KLE-ECC>>).
* *Points.* The listing returns the ephemeral public key for the peer.
The peer's public key `Q` arrives encoded as <<Zkl-ISA-machines.adoc#KLE-ECC>> specifies: its X coordinate, then its Y coordinate, each 32 bytes little-endian.
_Point_Mul_ validates `Q`, and transitions to _Failure_ if it is not a valid point.
* *The check after the first `kl.derive`.* A `kl.derive` from a locker in _Failure_ makes that locker _Invalid_ and leaves `K0` unchanged, so `K` would be derived without `Z`; the `kl.getst` that follows rejects that case.
* *FixedInfo* takes at most 16 bytes here; a longer one is absorbed in chunks, as in <<KLE-pseudocode-hash>>.

[[KLE-pseudocode-ECDH-KDF]]
.ECDH and One-Step Key Derivation into an AES-256 Key
----
# a0 = SCC of ECC secp256r1, a1 = SCC of SHA-256, a2 = SCC of GCM with AES-256,
# a3 = peer public key Q, 64 bytes, a4 = buffer for the ephemeral public key,
# 64 bytes, a5 = FixedInfo, a6 = its length in bytes, 1 to 16

  import_scc 1, a0
  import_scc 0, a1
  import_scc 2, a2
  li        t2, 1
  kl.setst  K1, #3, t2            # Set_Scalar, Xs != 0: a random scalar d
  kl.setst  K1, #4                # Point_Mul
  kl.exec   K1                    # Form D: SecondPt ← [d]G, to Output
  li        t1, 64                # one point
1:
  vsetvli   t5, t1, e8, m1, ta, ma # vl <= min(t1, VLEN/8)
  kl.exec   v0, K1                # emit the next vl bytes of [d]G; the
                                  # last to Success
  vse8.v    v0, (a4)              # the ephemeral public key, for the peer
  add       a4, a4, t5
  sub       t1, t1, t5
  bnez      t1, 1b
  kl.setst  K1, #kl_state_ready   # Form A keeps d
  kl.setst  K1, #8                # Set_SecondPt
  li        t1, 64
2:
  vsetvli   t5, t1, e8, m1, ta, ma
  vle8.v    v0, (a3)
  kl.exec   K1, v0                # load the next vl bytes of Q; the last
                                  # sets HasSecondPt
  add       a3, a3, t5
  sub       t1, t1, t5
  bnez      t1, 2b
  kl.setst  K1, #4                # Point_Mul
  kl.exec   K1                    # SecondPt ← [d]Q, to Output with a
                                  # shared secret, or Failure for a bad Q
  kl.setst  K0, #kl_state_hash_absorb
  lui       t1, 0x01000           # the counter 00000001, big-endian
  vsetivli  zero, 1, e32, m1, ta, ma # KLLEN = 32
  vmv.s.x   v0, t1
  kl.exec   K0, v0                # absorb the counter
  li        t1, 32
  kl.derive K0, K1, t1            # absorb Z, 32 bytes; K1 to Success
  kl.getst  t3, K1
  li        t4, kl_state_success
  bne       t3, t4, error         # K1 not in Success: Z did not enter K0
  vsetvli   zero, a6, e8, m1, ta, ma
  vle8.v    v0, (a5)
  kl.exec   K0, v0                # absorb FixedInfo
  kl.setst  K0, #kl_state_hash_output # pad: the digest is K
  kl.derive K2, K0, t1            # K into the AES-256 key; K0 to Success
----

*Sealed variant.* With _MachineExtension_ = 2 in the ECC SCC, the same listing also keeps `Z` and `K` from software that controls the lockers (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-sealed>>).
The public key stays readable, but a Form C `kl.exec` of `Z` makes `K1` _Invalid_, and `Z` seals `K0` when it enters it, so a Form C `kl.exec` of the digest makes `K0` _Invalid_.
Both `kl.derive` instructions are then restricted: each moves at least 16 bytes and narrows the Metadata of its destination (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-narrowing>>).
So `K2` ends with no wider a _UsagePolicy_, _Locality_ or _ExpirationDate_ than `K1`.
`K0` and `K2` therefore need an _SCProtection_ that includes that of `K1` (<<Zkl-ISA-unpriv.adoc#KLE-SC-ordering>>).

*Longer keys.* `Z` feeds one `kl.derive` (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-derive-rule-both-fixed-size>>), sealed or not, so the counter cannot advance to `00000002`.
A key longer than the digest, or several keys, need a longer output from one hash locker:

* SHA-512; or
* KMAC256 with `L` set to the total length, `S` = "KDF" and an agreed salt of at most 131 bytes as `K` (Option 3 of cite:[NIST-SP-800-56Cr2] {sect}4.1); the 132-byte `default_salt` spans two `key_block` blocks.

Each `kl.derive` from that output takes its next bytes.

[[KLE-SampleNTT-example]]
=== Rejection Sampling from an XOF

_Hash_Output_Bits_ reads an XOF output a set number of bits at a time, which suits rejection sampling.
The following sequence computes SampleNTT of cite:[nist-fips-203] Algorithm 7, with which ML-KEM expands its matrix from a seed.
It reads the SHAKE128 output for `B` = `ρ` {vvert} `j` {vvert} `i` in 12-bit pieces, and keeps each value below `q` = 3329 until it has 256 coefficients.

* SHAKE128 emits each output byte from its least significant bit, so consecutive 12-bit pieces are the values `d~1~`, `d~2~` that Algorithm 7 forms from each 3 bytes, in order.
* Each `kl.setst` sets `read_len` to 12. The first also ends the message, as a Form A `kl.setst` naming _Hash_Output_ would, for an unbounded output.
* `B` is absorbed in as many pieces as `vsetvli` grants, each of at most `VLEN`/8 bytes: one from `VLEN` = 512, where `vl` = 34.
* The Form C `kl.exec` that follows, with `KLLEN` = 16, emits those 12 bits and clears the 4 above them, so `vmv.x.s` returns the value itself.
* SampleNTT runs on public data, since `ρ` is part of the encapsulation key, so its variable number of reads reveals nothing secret.

[[KLE-pseudocode-SampleNTT]]
.SampleNTT from SHAKE128
----
# a0 = SCC of SHAKE128, a1 = B = rho || j || i, 34 bytes,
# a2 = output, 256 coefficients of 16 bits

  import_scc 0, a0
  kl.setst  K0, #kl_state_hash_absorb
  li        t1, 34
1:
  vsetvli   t5, t1, e8, m1, ta, ma # vl <= min(t1, VLEN/8)
  vle8.v    v0, (a1)
  kl.exec   K0, v0                # absorb the next vl bytes of B
  add       a1, a1, t5
  sub       t1, t1, t5
  bnez      t1, 1b
  vsetivli  zero, 1, e16, m1, ta, ma # KLLEN = 16
  li        t2, 12
  li        t3, 3329              # q
  addi      t4, a2, 512           # the end of the output
2:
  kl.setst  K0, #kl_state_hash_output_bits, t2 # read_len = 12; the first pads
  kl.exec   v0, K0                # the next 12 bits, zero-extended
  vmv.x.s   t1, v0
  bgeu      t1, t3, 2b            # reject a value >= q
  sh        t1, 0(a2)
  addi      a2, a2, 2
  bne       a2, t4, 2b
----
