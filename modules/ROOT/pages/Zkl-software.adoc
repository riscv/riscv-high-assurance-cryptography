_This chapter is informative._ It gives requirements, guidelines and code examples for software that uses KLE.
The examples follow <<Zkl-notation.adoc#KLE-Notation>>: a vector register loaded from memory holds the
byte at the lowest address in its least significant bits.
The example listings assume RV64.

// ///////////////////////////////////////////////////////////////////

[[KLE-software-requirements]]
== Software Requirements

_This section is informative for the architecture, which does not enforce its Rules; software must follow them._

KLE splits complex operations into small instructions, which software must use as intended.
Software, privileged or not, that ignores these Rules may corrupt cryptographic state, make it unavailable through the checks of the architecture, or reveal a CC to peer or less privileged software not meant to receive it.

[[KLE-interposed-software,interposed software]]Definition: _Interposed software_.::
(((interposed software)))
_Interposed software_ is code that runs while the live KLE state of the hart may hold a halted instruction, or a management operation in progress, of other software.
It includes every exception and interrupt handler, in any mode, that of the interrupted code included, and any other code sharing that KLE state, such as another thread of the same process.

// ////////////////////////////////////////////////////////////////////

[[KLE-SR-isolation]]
=== Isolation of Contexts

[horizontal]
[[KLE-SR-clear-before-lower-mode,SR1]]SR1:: Software must keep its lockers from unauthorized parties; before giving control to a less privileged mode, it must clear every locker that holds its CC or that it has placed in a Configuration State, completing any export first (Rule <<KLE-SR-no-unconditional-clear>>).

[[KLE-SR-restore-own-lockers,SR2]]SR2:: When switching to a less privileged component, software must restore only the lockers saved for that component, and clear the others; the same holds for `kliobuflen`, and for the KLIOBUF when `kliobuflen` {ne} 0.

[[KLE-SR-save-shared-state,SR3]]SR3:: Software that uses the KLIOBUF, `klstart` or `klnamedlocker`, or performs a management operation, while the KLE state of a less privileged context is live, must first save the state it uses and restore it before returning, so that the less privileged context sees its own values and no data of the more privileged mode.

// ////////////////////////////////////////////////////////////////////

[[KLE-SR-kliobuf]]
=== Requirements on the KLIOBUF

[horizontal]
[[KLE-SR-kliobuflen-zero,SR4]]SR4:: Software should set `kliobuflen` to zero once it no longer needs the KLIOBUF contents, which context-switch code must otherwise save and restore (<<Zkl-software.adoc#KLE-save-order>>, <<Zkl-software.adoc#KLE-restore-order>>); setting `kliobuftop` to zero instead keeps them accessible.

// ////////////////////////////////////////////////////////////////////

[[KLE-klstart-software-check]]
=== Requirements on `klstart`

`klstart` is one per hart, and nothing resets it automatically between programs: an instruction that honors it starts at the value it finds, and `kl.mgmt`, `kl.clearall` and every instruction that honors it write it.
Without Rule <<KLE-SR-klstart-save>>, interposed software would start where the interrupted instruction halted, skipping a prefix of its own operand, and the interrupted instruction would then resume elsewhere, or restart.

[horizontal]
[[KLE-SR-klstart-save,SR5]]SR5:: <<KLE-interposed-software,Interposed software>> must save `klstart` before its first KLE instruction, write 0 to it before its first instruction that honors it, and restore the saved value before control returns to the interrupted software.
A handler that skips the trapping instruction applies its retirement effects to `klstart` instead (Rule <<KLE-SR-handler-duty>>).

[[KLE-SR-klstart-no-reset,SR6]]SR6:: Software should not write 0 to `klstart` to force a full restart of `kl.exec` or `kl.derive` once per-block state effects have been committed.

// ////////////////////////////////////////////////////////////////////

[[KLE-SR-management]]
=== Requirements on Management Operations

Rule <<KLE-SR-nested-export-first>> binds <<KLE-interposed-software,interposed software>>.
An instruction issued in violation of Rule <<KLE-SR-klnamedlocker-write>> or <<KLE-SR-nested-export-first>> acts on whatever locker `klnamedlocker` names (<<Zkl-ISA-unpriv.adoc#KLE-named-locker-rules>>).

[horizontal]
[[KLE-SR-klnamedlocker-write,SR7]]SR7:: Before `kl.load`, `kl.store`, `kl.mvin`, `kl.mvout`, an instruction naming `KLNL` (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-klnamedlocker-override>>), or a `kl.mgmt` that names its locker explicitly, interposed software must read `klnamedlocker` and, if `klnamedlocker` does not hold the intended value, save it, write the intended value, and restore the saved one before control returns to the code that set it.
The intended value is the number of the target locker; 32 for a transfer to or from the KLIOBUF; and 32 or the target locker's number for a `kl.mgmt` that names its locker explicitly.
Any software that completes or abandons a management operation must then write 32 to `klnamedlocker`, or restore the value it saved.

[[KLE-SR-nested-export-first,SR8]]SR8:: Before opening, on another locker, an export from a Valid State or an import other than the short import of an Error-State image (<<Zkl-ISA-unpriv.adoc#KLE-error-state-transfer>>), while the locker that `klnamedlocker` names is in State `kl_cfg_exporting` or `kl_cfg_importing`, software must save that locker by a nested export and restore it before returning to the code that opened its operation, or terminate that code.
While that locker is in such a State, software must not write another value to `klnamedlocker` before saving it this way, so that `klnamedlocker` names the owner of the authentication registers at every trap.
Software may instead clear a locker in State `kl_cfg_importing`, whose import then restarts (<<Zkl-ISA-unpriv.adoc#KLE-CC-management>>).

[[KLE-SR-no-interleaving,SR9]]SR9:: Software should complete or discard a management operation before it performs cryptographic operations or manages other lockers.
Code that must interleave them, such as several threads of one process, needs coordination: a mutex, or lightweight threads with KLE context-switching support.
Software that writes 32 to `klnamedlocker` while its own import or export is open, for instance to transfer data through the KLIOBUF (<<Zkl-ISA-unpriv.adoc#KLE-instruction-mv>>), must have no other import or export open that a nested export has not saved.

[[KLE-SR-no-unconditional-clear,SR10]]SR10:: At a context switch, system software may clear a locker under a provisioning or an import instead of saving it, which restarts the operation; it must, however, be able to save such a locker, and must not clear it unconditionally at every context switch.
Unless it terminates the owner, software must not clear a locker under an export, base or nested, before completing that export.
+
NOTE: Repeated restarts may prevent a provisioning or an import from completing, and a clear destroys the CC of a locker under an export.

// ////////////////////////////////////////////////////////////////////

[[KLE-SR-handlers]]
=== Requirements on Exception Handlers

[horizontal]
[[KLE-SR-handler-duty,SR11]]SR11:: A handler that neither resolves nor forwards, to another handler, in-process handlers included, an exception for which <<Zkl-ISA-unpriv.adoc#KLE-exception-error-correspondence>> gives an Error State, and that does not terminate the process, must:
+
--
. set the _State_ of the locker on which the exception was raised, for `KLNL` the one that `klnamedlocker` names (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-klnamedlocker-updates>>), to that Error State, through the short import of <<Zkl-ISA-unpriv.adoc#KLE-error-state-transfer>> if the locker is _Unconfigured_ (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>); a locker in a Configuration State keeps its _State_ (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-config-state>>); and
. advance `xepc` past the trapping instruction, which would otherwise trap again; for a usage instruction, keep the output prefix that `klstart` and `vstart` record, zero the rest of the output window (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-zero-unwritten-output>>), and apply the retirement effects on `klstart` and `vstart` (Rules <<Zkl-ISA-unpriv.adoc#KLE-GR-klstart-updates>> and <<Zkl-ISA-unpriv.adoc#KLE-GR-klstart-vstart>>).
--

[[KLE-SR-uninterruptible,SR12]]SR12:: Software must not rely on whether an uninterruptible instruction (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-interruptibility-classes>>) has retired when a handler runs, and must interact with it only as Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-conflicting-access-rule>> prescribes.

// ////////////////////////////////////////////////////////////////////

[[KLE-SR-localities]]
=== Requirements on Localities

[horizontal]
[[KLE-SR-locality-unconfigure,SR13]]SR13:: Software must not unconfigure a Locality Secret while a locker bound to it may still be exported: an export made after that binds `zeros(128)` in its place, and no import accepts the resulting SCC (<<Zkl-ISA-unpriv.adoc#KLE-SCC-export>>).

// ////////////////////////////////////////////////////////////////////

[[KLE-SR-transfer-loops]]
=== Requirements on Transfer Sequences

[horizontal]
[[KLE-SR-no-klstart-loop,SR14]]SR14:: Software must not use `klstart` as the termination condition of a sequence of `kl.mvin` or `kl.mvout`, since `klstart` does not advance on a locker that has become _Unconfigured_ or entered an Error State (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>). The sequence is bounded by the image size read with `kl.size` before it, and the _State_ is checked after it (<<Zkl-software.adoc#KLE-pseudocode-examples>>, NOTE after Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-memory-instructions>>).

[[KLE-SR-export-final-check,SR15]]SR15:: Software that exports a locker must rely on the image only if the _State_ read after the last instruction of the export, or in the MDH that `kl.getmd*` returned when the image is the MDH alone, is not _Unconfigured_ (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>).

// ////////////////////////////////////////////////////////////////////

[[KLE-SR-csk]]
=== Requirements on the Context Sealing Key

[horizontal]
[[KLE-SR-csk-change,SR16]]SR16:: The architecture does not block a change of the CSK (<<Zkl-ISA-unpriv.adoc#KLE-CSK-requirements>>) while an export is open.
M-mode must not change the CSK of a hart until every export open on it, base or nested, has completed and its image has been saved.

// ////////////////////////////////////////////////////////////////////

[[KLE-SR-system-keys]]
=== Requirements on System Keys

[horizontal]
[[KLE-SR-skid-usage-policy,SR17]]SR17:: A system that intends to protect a System Key (<<Zkl-ISA-unpriv.adoc#KLE-system-keys>>) associates at least a _UsagePolicy_ with its SKID in the SKS; a _UsagePolicy_ that admits every mode, as for a public signature-verification key, is a deliberate choice.

[[KLE-state-save-and-restore-order]]
== Software Guidelines

The guidelines of this section are for privileged software.

// Here we collect the duties that the KLE state places on privileged software and exception handlers, in the order software meets them.

A context switch meets Rules <<KLE-SR-clear-before-lower-mode>> to <<KLE-SR-save-shared-state>> by following <<KLE-save-order>> and <<KLE-restore-order>>.
Where an item cites a Rule SR__n__ (<<KLE-software-requirements>>), that Rule takes precedence.

// ////////////////////////////////////////////////////////////////////

[[KLE-handler-duties]]
=== Duties of Every Exception Handler

<<KLE-interposed-software,Interposed software>> is bound by Rules <<KLE-SR-klstart-save>>, <<KLE-SR-klnamedlocker-write>> and <<KLE-SR-nested-export-first>>.

On entry, before its first KLE instruction, the handler:

. saves `klstart` (Rule <<KLE-SR-klstart-save>>);
. saves `klnamedlocker` (Rule <<KLE-SR-klnamedlocker-write>>);
. writes 0 to `klstart` before its first instruction that honors it (Rule <<KLE-SR-klstart-save>>); and
. saves the vector state, and writes 0 to `vstart`, before its first vector KLE instruction (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-vector-legality>>).

Before each instruction that Rule <<KLE-SR-klnamedlocker-write>> lists, it sets `klnamedlocker` as that Rule requires.

On exit, the handler:

. restores `klnamedlocker` to its saved value, or to 32 if it has cleared, instead of saving, the locker that value named (<<KLE-save-order>>);
. restores the vector state, `vstart` included; and
. restores `klstart` last, exactly as saved (Rules <<KLE-SR-klstart-save>> and <<KLE-SR-klstart-no-reset>>).

A handler that skips the trapping instruction applies its retirement effects to `klstart` and `vstart` instead of restoring them (Rule <<KLE-SR-handler-duty>>).

// ////////////////////////////////////////////////////////////////////

[[KLE-reading-locker-state]]
=== Reading the _State_ of a Locker

* `kl.getst Xd, KLNL` reads the _State_ of the locker that `klnamedlocker` names; with `klnamedlocker` = 32 it returns 0 (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>).
* To inspect lockers by number, software writes each number in turn to `klnamedlocker` and names `KLNL` in the following instructions.
* `kl.getst` reads the _State_, `kl.getstx` the _StateExtension_, and `kl.getmd` the whole MDH.
* On RV32, `kl.getst` and `kl.getstx` write the GPR pair `X[d+1] @ X[d]`, and `kl.getmd` a quartet (<<Zkl-ISA-unpriv.adoc#KLE-instruction-getst>>, <<Zkl-ISA-unpriv.adoc#KLE-instruction-getmd>>).
* A _State_ in 48–55, that is, with `(State & 0x38) = 0x30`, is an Error State (<<Zkl-ISA-unpriv.adoc#KLE-states-error>>).
* Before using the output of a usage instruction, software checks, immediately after the instruction, that the locker is in a Valid State.

// ////////////////////////////////////////////////////////////////////

[[KLE-management-routines]]
=== Management Routines

* A management routine should take the locker number as a parameter, 32 meaning the locker that `klnamedlocker` names. It saves `klnamedlocker`; on entry and at every restart, it writes the number to it, or, for 32, keeps its value and returns an error to its caller if that value is also 32 (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>). It names the locker `KLNL` throughout, and restores the saved value on exit, also when it abandons the operation (Rules <<KLE-SR-klnamedlocker-write>>, <<Zkl-software.adoc#KLE-management-code-snippets>>).
//  A handler can thus call it, also for a nested export or import of the locker that the interrupted operation manages.
* After each management instruction, the routine reads the _State_ of the locker: _Unconfigured_ means it has been cleared, so a provisioning or an import restarts and an export has lost its CC (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>); an Error State means the operation has failed. One code path handles resumption and restart.
* An export sizes its buffer with `kl.size`, and reads the size again after its opening `kl.mgmt`.
* Software does not interleave cryptographic operations, or the management of other lockers, with the steps of a management operation (Rule <<KLE-SR-no-interleaving>>).

// ////////////////////////////////////////////////////////////////////

[[KLE-save-order]]
=== Context Save Order

. Save `klstart`.
. Save `klnamedlocker`.
. Let the _owner_ be the locker that the saved `klnamedlocker` indexes, if it is in [0..31]; otherwise, the locker in State `kl_cfg_importing` or `kl_cfg_exporting`, if there is one (Rule <<KLE-SR-no-interleaving>>).
If there is an owner, save it first, with Form C or D `kl.mgmt` and no KLIOBUF transfer (Rule <<KLE-SR-nested-export-first>>), choosing the path by its _State_, read with `kl.getst`:
.. _Unconfigured_: save no locker image;
.. an Error State: save its MDH by the short Error-State path (<<Zkl-ISA-unpriv.adoc#KLE-error-state-transfer>>);
.. otherwise, export the locker, by nested export if it is under management.
. With `Zklio`:
.. save `kliobuflen` and `kliobuftop`;
.. if `kliobuflen` is non-zero, save the buffer contents with `kl.output`, with `klnamedlocker` = 32, `klstart` = 0 and `kliobuftop` = `kliobuflen`, then write 0 to `kliobuflen`.
. Save every locker other than the owner that is not _Unconfigured_, with `klnamedlocker` = 32 between exports.

Each export completes, with its completing `kl.mgmt` and outcome check, before its locker is cleared (Rule <<KLE-SR-no-unconditional-clear>>).

The handler may clear a locker being provisioned or imported instead of saving it (Rule <<KLE-SR-no-unconditional-clear>>); the interrupted software then restarts the operation (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>), and the handler restores 32 in place of a saved `klnamedlocker` that named that locker (<<KLE-restore-order>>).

A handler that passes `ml` through the KLIOBUF for the other lockers configures `kliobuflen` {ge} 16 for their exports and imports, and restores the saved value afterwards.

// ////////////////////////////////////////////////////////////////////

[[KLE-restore-order]]
=== Context Restore Order

. Clear the lockers for which no image is restored below, or all of them with `kl.clearall` (Rule <<KLE-SR-restore-own-lockers>>).
. Restore the lockers other than the owner (<<KLE-save-order>>), with `klnamedlocker` = 32 between imports.
. With `Zklio`:
.. restore `kliobuflen`;
.. restore the buffer contents, if saved, with `kl.input`, with `klnamedlocker` = 32, `klstart` = 0 and `kliobuftop` = `kliobuflen`;
.. restore `kliobuftop`.
. If an image was saved for the owner, restore it last, with Form C or D `kl.mgmt` and no KLIOBUF transfer.
. Restore the saved value of `klnamedlocker`, or 32 if the handler has cleared the locker it named instead of saving it.
. Restore `klstart` last.

// ////////////////////////////////////////////////////////////////////

[[KLE-handling-kle-exceptions]]
=== Handling a KLE Exception

A handler that can neither resolve nor forward a KLE exception covered by Rule <<KLE-SR-handler-duty>>, nor terminate the process:

. unless the locker is in a Configuration State, sets it to the Error State that <<Zkl-ISA-unpriv.adoc#KLE-exception-error-correspondence>> gives, or to _Invalid_ where it gives none: with `kl.setst` and that Error State as immediate (<<Zkl-ISA-unpriv.adoc#KLE-instruction-setst>>), or, if the locker is _Unconfigured_, by the short import of an MDH holding that State (<<Zkl-ISA-unpriv.adoc#KLE-error-state-transfer>>); and
. advances `xepc` past the instruction, retiring a usage instruction as Rule <<KLE-SR-handler-duty>> states.

[[KLE-management-code-snippets]]
== Code for Locker Configuration and Export Operations

[WARNING]
====
These examples are being rewritten. They are not yet definitive.
====

This section gives the instruction sequences for provisioning, import and export.
They show the operation and its error detection, not application-specific error handling, and can be packaged into libraries or OS APIs.

Registers::
GPR `t0` holds the number of the locker to be provisioned, imported or exported, or 32 for the locker that `klnamedlocker` names, and GPR `t6` points to the 16-byte aligned memory location of the PI or SCC (<<Zkl-ISA-unpriv.adoc#KLE-instructions-memory>>).
The MDH is loaded and stored with `ld` and `sd`, and passed in the GPR pair `s5:s4`; on RV32 it takes a GPR quartet (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-multiple-GPRs>>).

Selecting the locker::
No instruction of the routines directly encodes a locker number: the routines save `klnamedlocker` on entry, select the locker with the preamble `select_locker` below on entry and at every `restart`, and every KLE instruction then acts on that locker (Rules <<Zkl-ISA-unpriv.adoc#KLE-GR-locker-less-transfers>> and <<Zkl-ISA-unpriv.adoc#KLE-GR-klnamedlocker-override>>).
`kl.load`, `kl.store`, `kl.mvin` and `kl.mvout` have no locker operand; `kl.mgmt`, `kl.getst`, `kl.getmd` and `kl.size` name `KLNL`.
A clear resets `klnamedlocker` to 32, after which a `KLNL` opening performs no operation (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>): the next _State_ check reads 0, and the preamble at `restart` names locker `t0` again or, if `t0` = 32, branches to `no_locker`, since the clear has destroyed the locker. An opening on a named locker opens it, even a Valid one.
On exit the routines restore the saved value (Rule <<KLE-SR-klnamedlocker-write>>), so a handler that has saved the interrupted operation (<<KLE-state-save-and-restore-order>>) can call them, also for a nested export or import of the locker that operation manages.
+
----
.macro select_locker              # t0 = p: 0-31, or 32 for the named locker
  li        t1, 32
  bgeu      t0, t1, 1f            # p = 32: keep the named locker
  kl.setnl  t0                    # p in 0-31: name locker p
  j         2f
1:
  kl.getnl  t2
  bgeu      t2, t1, no_locker     # none named, or cleared: error to caller
2:
.endm
----

Checking the _State_::
+
--
After each management instruction, the code reads the _State_ of the locker with `kl.getst`.
If a handler has meanwhile cleared the locker or set it to an Error State, every following `kl.mvin`, `kl.mvout`, `kl.load`, `kl.store` or `kl.mgmt`, including a `KLNL` opening after a clear, performs no operation (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>), and the check detects the change:

* after a clear, `KLNL` reads as an _Unconfigured_ locker, so the check finds _State_ 0: a provisioning or an import restarts at its preamble, and an export, whose CC the clear has destroyed, branches to `handle_errors`;
* after an Error State, or after the completing `kl.mgmt`, `KLNL` still names the locker, so the check reads its final _State_; an Error State abandons the operation.

Only the check after the last instruction is required; the earlier ones react sooner.
The code may bound the number of restarts and then branch to its error handling, for robustness only: system software must let the operation complete (Rule <<KLE-SR-no-unconditional-clear>>).
--

Error handling::
The code at `handle_errors` and `no_locker` is not shown; `no_locker` restores `klnamedlocker` and returns an error to the caller, since with `t0` = 32 no locker is named, or a clear has destroyed the named one.
`handle_errors` writes 0 to `klstart`, which a `kl.mvin` or `kl.mvout` loop leaves at its last transfer point, and restores `klnamedlocker` as the routines do on exit.
If the locker is still in a Configuration State, `handle_errors` clears it if it is being provisioned or imported, and completes its export with the saved MDH, which restores the locker, if it is being exported.

=== Provisioning

The provisioning code assumes that the Content immediately follows the MDH in memory.
The MDH of the PI carries _State_ = _Unconfigured_ (0); the completing `kl.mgmt` sets _Ready_.

*Provisioning Code (`Zklmv`)*
----
# t5 holds the length of the PI's Content (hence, excluding the MDH) in bytes.
# t5 can be zero. The caller constructed the PI and so knows this length.
# t5 is never modified, so the working count and pointer can be re-derived
# from it whenever the operation is restarted.

  ld        s4, 0(t6)             # load MDH[63:0] from memory
  ld        s5, 8(t6)             # load MDH[127:64] from memory
  li        t3, 0x30              # const useful to determine Error States
  kl.getnl  s8                    # save the caller's value: the routine may
                                  # run inside another management operation

restart:
  select_locker                   # name the locker: every KLE instruction
                                  # below acts on it; a clear resets it to 32
  kl.mgmt   KLNL, #kl_cfg_provisioning, s5:s4 # start provisioning, load MDH
  kl.getst  t2, KLNL              # get _State_ field from MDH
  beqz      t2, restart           # locker cleared: must restart
  andi      t2, t2, 0x38          # Check the three top bits of State
  beq       t3, t2, handle_errors # Error State: provisioning ended

  addi      t4, t6, 16            # source pointer: first byte after MDH
  mv        s1, t5                # working byte count, re-derived from t5
                                  # on restart

  vsetvli   s6, zero, e8, m1, ta, ma # s6 = VLMAX
vloop:
  mv        s2, s1
  bleu      s2, s6, 1f
  mv        s2, s6
1:
  vsetvli   s2, s2, e8, m1, ta, ma # AVL <= VLMAX, so vl = AVL, multiple of 16
  vle8.v    v1, (t4)              # load a chunk of the PI
  kl.mvin   v1                    # move it into the locker
  add       t4, t4, s2            # bump the source pointer
  sub       s1, s1, s2            # decrement the bytes still to load
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared: must restart
  andi      t2, t2, 0x38          # Three top bits -> Error or Management
  beq       t3, t2, handle_errors # *new* Error State
  bnez      s1, vloop

  kl.mgmt   KLNL, #kl_cfg_management_end # complete provisioning
                                  # and possibly reconstruct data
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared: must restart
  andi      t2, t2, 0x38
  beq       t3, t2, handle_errors # catches errors at completion (e.g., SKS)

finished:
  kl.setnl  s8                    # restore the caller's value
# The locker is Ready, or in Failure after a data error at completion. Any
# Error State met above is new, since the PI carried State = Unconfigured:
# handle_errors decides the course of action.
----

*Provisioning Code (`Zklmem`)*
----
  ld        s4, 0(t6)             # load MDH[63:0] from memory
  ld        s5, 8(t6)             # load MDH[127:64] from memory
  li        t3, 0x30              # const useful to determine Error States
  kl.getnl  s8                    # save the caller's value

restart:
  select_locker                   # name the locker (a clear resets it to 32)
  kl.mgmt   KLNL, #kl_cfg_provisioning, s5:s4 # start prov. and load MDH
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared: must restart
  andi      t2, t2, 0x38          # Check the three top bits of State
  beq       t3, t2, handle_errors # Error State?

  # Assume that the Content directly follows the MDH in memory.
  kl.load   16(t6), x0            # load rest of PI into the locker
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared means force restart
  andi      t2, t2, 0x38
  beq       t3, t2, handle_errors
  kl.mgmt   KLNL, #kl_cfg_management_end # complete provisioning
                                  # and possibly reconstruct data
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared: must restart
  andi      t2, t2, 0x38
  beq       t3, t2, handle_errors # catches errors at completion (e.g., SKS)
finished:
  kl.setnl  s8                    # restore the caller's value
----

=== Export

*Export Code (`Zklmv`)*
----
  li         t3, 0x30             # to determine Error States
  kl.getnl   s8                   # save the caller's value
  select_locker                   # name the locker for all that follows
  kl.size    s1, KLNL             # TOTAL size to export
  beqz       s1, handle_errors    # 0 means the locker is unconfigured

  {...}  # here code that allocates the buffer to store the exported data

  kl.getmd   s5:s4, KLNL          # get MDH, including its _State_
  srli       t2, s4, 18           # _State_ of that MDH, bits [23:18]
  andi       t2, t2, 0x3f
  beqz       t2, handle_errors    # locker cleared since kl.size
  sd         s4, 0(t6)            # store MDH[63:0] to memory
  sd         s5, 8(t6)            # store MDH[127:64] to memory

  addi       t6, t6, 16           # point to next memory region
  li         s3, 16               # s3 = 16 (size of MDH)
  beq        s1, s3, done         # only the MDH to store (e.g., Error State)

  kl.mgmt    KLNL, #kl_cfg_exporting  # start exporting
  kl.getst   t2, KLNL
  beqz       t2, handle_errors    # locker cleared: the CC is lost
  andi       t2, t2, 0x38
  beq        t3, t2, handle_errors # Error State set meanwhile
  kl.size    t2, KLNL             # size now that the export is open
  bne        t2, s1, handle_errors # ADS changed since the buffer was sized
  addi       s1, s1, -16          # adjust size to remove the MDH
  mv         t4, t6               # destination: first byte after stored MDH
  vsetvli    s6, zero, e8, m1, ta, ma # s6 = VLMAX
store_loop:
  mv         s2, s1
  bleu       s2, s6, 1f
  mv         s2, s6
1:
  vsetvli    s2, s2, e8, m1, ta, ma # AVL <= VLMAX, so vl = AVL, multiple of 16
  kl.mvout   v2                   # move chunk out of the locker,
                                  # advance klstart
  vse8.v     v2, (t4)             # store it
  add        t4, t4, s2           # bump the destination pointer
  sub        s1, s1, s2           # decrement the bytes still to store
  kl.getst   t2, KLNL
  beqz       t2, handle_errors    # locker cleared: the CC is lost
  andi       t2, t2, 0x38
  beq        t3, t2, handle_errors
  bnez       s1, store_loop

finished:
  # Restore _State_ from the saved MDH.
  kl.mgmt    KLNL, #kl_cfg_management_end, s5:s4
  kl.getst   t2, KLNL
  beqz       t2, handle_errors    # locker cleared: the CC is lost
  andi       t2, t2, 0x38
  beq        t3, t2, handle_errors # catches `kl_state_mgmt_auth`
done:
  kl.setnl   s8                   # restore the caller's value
----

[WARNING]
====
Incomplete procedure, like all the others in management.
A locker in an Error State is covered: only its MDH is stored.
A locker under management (partially provisioned, imported or exported) is exported by the same sequence;
the caller must also save `klstart` before the opening `kl.mgmt`, which clears it, and restore it after the re-import
(<<KLE-state-save-and-restore-order>>), which is not shown.
====

*Export Code (`Zklmem`)*
----
# Up to the size check after the opening kl.mgmt, and from finished on, the
# code is that of the Zklmv version.
  kl.store  0(t6), x0             # store SIV, IMPQUAL, SIV2 and Content
                                  # of the locker (Xl = x0)
  kl.getst  t2, KLNL
  beqz      t2, handle_errors     # locker cleared: the CC is lost
  andi      t2, t2, 0x38
  beq       t3, t2, handle_errors
----

[[KLE-import-code]]
=== Import

*Import Code (`Zklmv`)*
----
  ld         s4, 0(t6)            # load MDH[63:0] from memory
  ld         s5, 8(t6)            # load MDH[127:64] from memory
  li         t3, 0x30             # to determine Error States
  srli       s7, s4, 18           # _State_ of the saved MDH, bits [23:18]
  andi       s7, s7, 0x38         # s7 = 0x30: image of an Error-State locker
  kl.getnl   s8                   # save the caller's value

restart:
  select_locker                   # name the locker (a clear resets it to 32)
  kl.mgmt   KLNL, #kl_cfg_importing, s5:s4    # open locker for import, load MDH
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared means force restart
  andi      t2, t2, 0x38
  bne       t3, t2, 2f            # three top bits of _State_ = 110 ?
  beq       t3, s7, success       # yes, as saved: the short import is complete,
                                  # with this one kl.mgmt and no load
  j         handle_errors         # yes, but new (e.g., invalid Metadata)
2:
  kl.size   s1, KLNL              # size of the image the locker accepts,
                                  # without a dropped ADS
  beqz      s1, restart           # 0: locker cleared since the check
  addi      t4, t6, 16            # first byte after the MDH
  addi      s1, s1, -16           # image size to load, without the MDH

  vsetvli   s6, zero, e8, m1, ta, ma # s6 = VLMAX
vloop:
  mv        s2, s1
  bleu      s2, s6, 1f
  mv        s2, s6
1:
  vsetvli   s2, s2, e8, m1, ta, ma # AVL <= VLMAX, so vl = AVL, multiple of 16
  vle8.v    v2, (t4)              # load a chunk of the SCC
  kl.mvin   v2                    # move it into the locker, advance klstart
  add       t4, t4, s2
  sub       s1, s1, s2
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared means force restart
  andi      t2, t2, 0x38
  beq       t3, t2, handle_errors
  bnez      s1, vloop

  kl.mgmt   KLNL, #kl_cfg_management_end, s5:s4 # decrypt and auth SCC
                                  # and restore _State_ from the saved MDH
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared means force restart
  andi      t2, t2, 0x38
  beq       t3, t2, handle_errors # catches "Authentication Failed"

success:
  kl.setnl  s8                    # restore the caller's value
----

*Import Code (`Zklmem`)*
----
  ld        s4, 0(t6)             # load MDH[63:0] from memory
  ld        s5, 8(t6)             # load MDH[127:64] from memory
  li        t3, 0x30              # to determine Error States
  srli      s7, s4, 18            # _State_ of the saved MDH, bits [23:18]
  andi      s7, s7, 0x38          # s7 = 0x30: image of an Error-State locker
  kl.getnl  s8                    # save the caller's value

restart:
  select_locker                   # name the locker (a clear resets it to 32)
  kl.mgmt   KLNL, #kl_cfg_importing, s5:s4    # open locker for import, load MDH
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared means force restart
  andi      t2, t2, 0x38
  bne       t3, t2, 2f            # three top bits of _State_ = 110 ?
  beq       t3, s7, success       # yes, as saved: the short import is complete
  j         handle_errors         # yes, but new (e.g., invalid Metadata)
2:
  addi      t4, t6, 16            # first byte after the MDH

  kl.load   0(t4), x0             # load rest of SCC into the locker
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared means force restart
  andi      t2, t2, 0x38
  beq       t3, t2, handle_errors
  kl.mgmt   KLNL, #kl_cfg_management_end, s5:s4 # decrypt and auth locker,
                                  # if necessary complete it
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared means force restart
  andi      t2, t2, 0x38
  beq       t3, t2, handle_errors # catches `kl_state_mgmt_auth`

success:
  kl.setnl  s8                    # restore the caller's value
----

In provisioning and import, the opening `kl.mgmt` checks the whole MDH, which it receives in Form D (<<Zkl-ISA-unpriv.adoc#KLE-MVR-open>>); for the image of a locker in an Error State it checks only the _State_ (<<Zkl-ISA-unpriv.adoc#KLE-error-state-transfer>>).
The checks at completion, SKS resolution at provisioning and authentication at import, can still transition the locker to an Error State at `kl.mgmt KLNL, #kl_cfg_management_end`; the `kl.getst` after it detects this, as well as a clear or an Error State set earlier.
A data error found by a check that the Machine attaches to a field of the PI or SCC leaves the locker in _Failure_ instead (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-completion-state>>), which these listings do not test.

[[KLE-ECB-mode-example]]
=== Electronic Codebook Modes (Direct Encryption/Decryption)

The listings of this section are RV64 code for the V extension (`VLEN` {ge} 128) and Zbb; locker `K0` is the target throughout, and the following one encrypts data with an ECB CC.
Arguments arrive in `a0`–`a7`, `s9` and `s10`; `error` is the caller's error handling, not shown.
`import_scc n, rs` stands for the import code of <<KLE-import-code>> with `t0` = `n` and `t6` = `rs`; it changes no `a` register, `s9` or `s10`, but it changes `vtype`.
A 16-byte block is processed with `vl` = 16 and SEW = 8, so `KLLEN` = 128, as in most examples, where `b` = 128; a shorter piece of `n` bytes is processed with `vl` = `n`, so `KLLEN` = 8 {times} `n`.
Most listings omit the `kl.getst` that checks, before an output is used, that the locker is still in a Valid State (<<KLE-reading-locker-state>>): a usage instruction on a locker that a handler has cleared or invalidated performs no operation and writes zeros.

[[KLE-pseudocode-ECB-encryption]]
.Simple Example: Encryption with no Authentication
----
# a0 = SCC, a1 = plaintext, a2 = ciphertext buffer, a3 = length in bytes,
# a multiple of 16

  import_scc 0, a0                # import the SCC into locker K0
  li        t3, 0x30              # to determine Error States
  kl.getst  t1, K0
  andi      t2, t1, 0x38
  beq       t2, t3, error         # Error State: the import failed

  kl.setst  K0, #kl_state_encrypt # configure the locker to encrypt
  kl.getst  t1, K0
  li        t2, kl_state_encrypt
  bne       t1, t2, error

  vsetivli  zero, 16, e8, m1, ta, ma # one block: KLLEN = 128
  beqz      a3, 2f
1:
  vle8.v    v0, (a1)              # one block of plaintext
  kl.exec   v0, K0, v0            # encrypt it
  vse8.v    v0, (a2)
  addi      a1, a1, 16
  addi      a2, a2, 16
  addi      a3, a3, -16
  bnez      a3, 1b
2:
----

In _Encrypt_ and _Decrypt_ a Form A `kl.exec` processes every block of its operand (<<Zkl-ISA-machines.adoc#KLE-ECB-mode>>), so one instruction can encrypt several blocks inside the KLE unit.
The following listing encrypts eight blocks per `kl.exec`, with `KLLEN` = 1024, and the last group with a smaller multiple of 128 bits.
With LMUL = 8 and `VLEN` {ge} 128, a register group holds at least 128 bytes.
An interrupt may halt such a `kl.exec` after some blocks; on return, the same instruction resumes from `klstart` (<<Zkl-ISA-unpriv.adoc#KLE-CSR-klstart>>), so the loop needs no code for it.

[[KLE-pseudocode-ECB-encryption-multi-block]]
.ECB Encryption, Eight Blocks per Instruction
----
# a0 = SCC, a1 = plaintext, a2 = ciphertext buffer, a3 = length in bytes,
# a multiple of 16

  import_scc 0, a0                # import the SCC into locker K0
  kl.setst  K0, #kl_state_encrypt # configure the locker to encrypt
  kl.getst  t1, K0
  li        t2, kl_state_encrypt
  bne       t1, t2, error         # the import failed

  li        t3, 128               # eight blocks
  beqz      a3, 2f
1:
  minu      t4, a3, t3            # this group: 16 to 128 bytes
  vsetvli   zero, t4, e8, m8, ta, ma # KLLEN = 8 * t4
  vle8.v    v8, (a1)              # up to eight blocks of plaintext
  kl.exec   v8, K0, v8            # encrypt them all
  vse8.v    v8, (a2)
  add       a1, a1, t4
  add       a2, a2, t4
  sub       a3, a3, t4
  bnez      a3, 1b
2:
----

.Encrypt with Keystream Generation

# a0 = SCC, a1 = PT, a2 = CT (may equal a1), a3 = length of PT in bytes,
# a4 = initial counter value, a5 = the 16-byte nonce

  import_scc 0, a0

=== XEX/XTS Modes

The listings below encrypt and decrypt a data unit of `n` blocks, `b` = `KLLEN` = 128.
The parameter `last_len` is the length of the last block in bytes: if it is 16, the data unit is in whole blocks;
otherwise the last block is partial, and the data unit is completed by <<Zkl-ISA-machines.adoc#KLE-XTS-from-XEX>>.

[[KLE-pseudocode-basic-IV-mode]]
.XEX Encryption
----
# a0 = SCC, a1 = PT, a2 = CT (may equal a1), a3 = n blocks, the last of
# a4 = last_len bytes, 1 <= last_len <= 16, n >= 2 if last_len < 16,
# a5 = the 16-byte tweak

  import_scc 0, a0
  vsetivli  zero, 16, e8, m1, ta, ma # one block: KLLEN = 128
  vle8.v    v0, (a5)
  kl.setst  K0, #kl_state_encrypt, v0 # configure to encrypt, set the tweak

  li        t1, 16
  mv        t2, a3                # m = n full blocks if last_len = 16,
  beq       a4, t1, 1f
  addi      t2, a3, -1            # n-1 otherwise
1:
  vle8.v    v0, (a1)
  kl.exec   v0, K0, v0            # encrypt one block of plaintext
  vse8.v    v0, (a2)
  addi      a1, a1, 16
  addi      a2, a2, 16
  addi      t2, t2, -1
  bnez      t2, 1b
  beq       a4, t1, 2f            # whole blocks: done

  # Ciphertext stealing: a1 points to P_m, a2 to C_m, s = last_len
  addi      t3, a2, -16           # C_{m-1}
  vle8.v    v0, (t3)              # CC, at mask index m-1
  vmv.v.v   v1, v0
  vsetvli   zero, a4, e8, m1, tu, ma # s bytes, the rest of v1 kept
  vle8.v    v1, (a1)              # v1 = CP @ P_m
  vse8.v    v0, (a2)              # C_m: the first s bytes of CC
  vsetivli  zero, 16, e8, m1, ta, ma
  kl.exec   v1, K0, v1            # C_{m-1}, at mask index m
  vse8.v    v1, (t3)
2:
----

P~m~ is read before C~m~ is written, so CT may be the same buffer as PT.

[[KLE-pseudocode-XEX-decryption]]
.XEX Decryption
----
# a0 = SCC, a1 = CT, a2 = PT (may equal a1), a3 = n blocks, the last of
# a4 = last_len bytes, 1 <= last_len <= 16, n >= 2 if last_len < 16,
# a5 = the 16-byte tweak

  import_scc 0, a0
  vsetivli  zero, 16, e8, m1, ta, ma # one block: KLLEN = 128
  vle8.v    v0, (a5)
  kl.setst  K0, #kl_state_decrypt, v0 # configure to decrypt, set the tweak

  li        t1, 16
  mv        t2, a3                # w = n plain blocks if last_len = 16,
  beq       a4, t1, 1f
  addi      t2, a3, -2            # m-1 = n-2 otherwise
1:
  beqz      t2, 3f
2:
  vle8.v    v0, (a1)
  kl.exec   v0, K0, v0            # decrypt one block of ciphertext
  vse8.v    v0, (a2)
  addi      a1, a1, 16
  addi      a2, a2, 16
  addi      t2, t2, -1
  bnez      t2, 2b
3:
  beq       a4, t1, 4f            # whole blocks: done

  # Ciphertext stealing: a1 points to C_{m-1}, a2 to P_{m-1}, s = last_len
  kl.setst  K0, #kl_xex_state_steal # skip mask index m-1
  vle8.v    v0, (a1)              # C_{m-1}
  kl.exec   v0, K0, v0            # PP, at mask index m
  vmv.v.v   v1, v0
  addi      t3, a1, 16            # C_m
  addi      t4, a2, 16            # P_m
  vsetvli   zero, a4, e8, m1, tu, ma # s bytes, the rest of v1 kept
  vle8.v    v1, (t3)              # v1 = CP @ C_m
  vse8.v    v0, (t4)              # P_m: the first s bytes of PP
  vsetivli  zero, 16, e8, m1, ta, ma
  kl.exec   v1, K0, v1            # P_{m-1}, at mask index m-1
  vse8.v    v1, (a2)              # the locker is now in Success
4:
----

As in encryption, C~m~ is read before P~m~ is written.
With stealing, the locker ends in _Success_, and a `kl.setst` into _Ready_ precedes the next tweak.

[[KLE-GCM-mode-examples]]
=== GCM Mode

<<KLE-pseudocode-GCM-encryption>> encrypts with GCM, with
`b` = `KLLEN` = 128 and `c` = 32.

Associated data and plaintext/ciphertext are treated differently, as <<Zkl-ISA-machines.adoc#KLE-GCM-mode>> requires.
The caller zero-fills the final block of the AD beyond its actual end, and `GHASH` absorbs that block whole.
The PT and CT are not zero-padded: a final block shorter than `b` goes through State _Enc_Last_Block_ (or _Dec_Last_Block_), so that no keystream bit past the end of the message is absorbed into `GHASH` or written out.
The Machine takes the PT and the CT in whole bytes (each last-block `Xs` is a multiple of 8); these listings also take the AD in whole bytes, so `len_in_bits` is always 8 times a byte count.

[[KLE-pseudocode-GCM-encryption]]
.GCM Encryption
----
# a0 = CC, a1 = AD, a2 = length of AD in bytes, a3 = PT, a4 = CT (may
# equal a3), a5 = length of PT in bytes, a6 = IV, a7 = length of IV in
# bytes, at least 1.  The caller has zero-filled the last block of the AD.

  import_scc 0, a0                # also computes the derived hash key

  # Set the IV.  The Form B kl.setst carries its length in bits; kl.exec
  # then absorbs the IV in chunks of 16 bytes, the last one possibly
  # shorter.  After the last byte the Machine computes J0 and moves to
  # _Hash_Absorb_ by itself, so no kl.setst is issued for that transition.
  slli      t1, a7, 3
  kl.setst  K0, #kl_state_set_aux_value, t1 # len_in_bits(IV)
  li        t2, 16
1:
  minu      t1, a7, t2
  vsetvli   zero, t1, e8, m1, ta, ma # KLLEN = 8 * bytes in this chunk
  vle8.v    v0, (a6)
  kl.exec   K0, v0                # absorb a chunk of the IV
  add       a6, a6, t1
  sub       a7, a7, t1
  bnez      a7, 1b

  # The AD contribution to the tag
  vsetivli  zero, 16, e8, m1, ta, ma # one block: KLLEN = 128
  addi      t1, a2, 15
  srli      t1, t1, 4             # ceil(len_in_bytes(AD)/16) blocks
  mv        t3, a1
  beqz      t1, 3f
2:
  vle8.v    v0, (t3)
  kl.exec   K0, v0                # absorb it into GHASH
  addi      t3, t3, 16
  addi      t1, t1, -1
  bnez      t1, 2b
3:
  # Encrypt the whole blocks of the plaintext
  kl.setst  K0, #kl_state_encrypt
  srli      t1, a5, 4             # whole blocks of PT
  mv        t3, a3
  mv        t4, a4
  beqz      t1, 5f
4:
  vle8.v    v0, (t3)
  kl.exec   v1, K0, v0
  vse8.v    v1, (t4)
  addi      t3, t3, 16
  addi      t4, t4, 16
  addi      t1, t1, -1
  bnez      t1, 4b
5:
  # Final partial block, if any.  The plaintext is not zero-padded here.
  andi      t1, a5, 15            # its length in bytes
  beqz      t1, 6f
  slli      t2, t1, 3
  kl.setst  K0, #kl_state_enc_last_block, t2 # its length in bits
  vsetvli   zero, t1, e8, m1, ta, ma
  vle8.v    v0, (t3)
  kl.exec   v1, K0, v0
  vse8.v    v1, (t4)
6:
  # Absorb the lengths, finalize the tag, and read it out
  slli      t1, a5, 3
  rev8      t1, t1                # bswap(bin(len_in_bits(PT), 64))
  slli      t2, a2, 3
  rev8      t2, t2                # bswap(bin(len_in_bits(AD), 64))
  vsetivli  zero, 2, e64, m1, tu, ma # KLLEN = 128
  vmv.v.x   v1, t1                # bits [127:64]
  vmv.s.x   v1, t2                # bits [63:0]
  kl.setst  K0, #kl_state_enc_tag_finalize, v1
  kl.exec   v2, K0                # v2 holds the tag
----

<<KLE-pseudocode-GCM-decryption>> decrypts with GCM from the point where the AD has been absorbed; up to there, it is <<KLE-pseudocode-GCM-encryption>>.
// Decryption differs from encryption in three ways: the roles of `PT` and `CT` are
// reversed; States _Encrypt_ and _Enc_Last_Block_ are replaced by _Decrypt_ and
// _Dec_Last_Block_; and the tag is finalized and verified instead of being emitted, as shown
// below.
No `kl.exec` is issued in State _Dec_Tag_Finalize_: the recomputed tag
stays inside the locker.

[[KLE-pseudocode-GCM-decryption]]
.GCM Decryption
----
# As GCM Encryption up to label 3, with a3 = CT, a4 = PT (may equal a3),
# a5 = length of CT in bytes, and s9 = the 16-byte received tag

  # Decrypt the whole blocks of the ciphertext
  kl.setst  K0, #kl_state_decrypt
  srli      t1, a5, 4             # whole blocks of CT
  mv        t3, a3
  mv        t4, a4
  beqz      t1, 5f
4:
  vle8.v    v0, (t3)
  kl.exec   v1, K0, v0
  vse8.v    v1, (t4)
  addi      t3, t3, 16
  addi      t4, t4, 16
  addi      t1, t1, -1
  bnez      t1, 4b
5:
  # Final partial block, if any.  The ciphertext is not zero-padded here.
  andi      t1, a5, 15
  beqz      t1, 6f
  slli      t2, t1, 3
  kl.setst  K0, #kl_state_dec_last_block, t2
  vsetvli   zero, t1, e8, m1, ta, ma
  vle8.v    v0, (t3)
  kl.exec   v1, K0, v0
  vse8.v    v1, (t4)
6:
  # Absorb the lengths.  The tag is computed and kept inside the locker.
  slli      t1, a5, 3
  rev8      t1, t1                # bswap(bin(len_in_bits(CT), 64))
  slli      t2, a2, 3
  rev8      t2, t2                # bswap(bin(len_in_bits(AD), 64))
  vsetivli  zero, 2, e64, m1, tu, ma
  vmv.v.x   v1, t1
  vmv.s.x   v1, t2
  kl.setst  K0, #kl_state_dec_tag_finalize, v1

  # Supply the received tag; the comparison sets _Success_ or _Failure_
  vsetivli  zero, 16, e8, m1, ta, ma
  vle8.v    v1, (s9)
  kl.setst  K0, #kl_state_hash_verify, v1
  kl.getst  t1, K0
  li        t2, kl_state_success
  bne       t1, t2, error         # do not use the plaintext
----

GCM encryption can also use an ECB CC, if the vector ISA
has carry-less multiplication, here the `vghsh.vv` of Zvkg. Under the threat model of KLE, however, this exposes
the hashing key, which may lead to forgeries, though not to a loss of confidentiality.

[[KLE-pseudocode-GCM-encryption-alternate]]
.Implementing GCM encryption using an ECB CC
----
# a0 = ECB encryption CC, a1 = AD, a2 = length of AD in bytes, a3 = PT,
# a4 = CT (may equal a3), a5 = length of PT in bytes, a6 = the 12-byte IV.
# The caller has zero-filled the last block of the AD.  vghsh.vv (Zvkg)
# computes vd <- (vd xor vs1) * vs2 in GF(2^128), as GHASH does.

  import_scc 0, a0
  kl.setst  K0, #kl_state_encrypt # kl.exec encrypts only in _Encrypt_
  vsetivli  zero, 4, e32, m1, ta, ma # one block: KLLEN = 128
  vmv.v.i   v0, 0
  vsetivli  zero, 3, e32, m1, tu, ma
  vle32.v   v0, (a6)              # v0[95:0] = IV, in bytes 0..11
  vsetivli  zero, 4, e32, m1, ta, ma
  vmv.v.i   v3, 0                 # zeros(b), "Auth Data 1"
  kl.exec   v4, K0, v3            # compute H

  addi      t1, a2, 15
  srli      t1, t1, 4             # ceil(len_in_bytes(AD)/16) blocks
  mv        t3, a1
  beqz      t1, 2f
1:
  vle32.v   v1, (t3)
  vghsh.vv  v3, v4, v1            # v3 <- (v3 xor v1) * H
  addi      t3, t3, 16
  addi      t1, t1, -1
  bnez      t1, 1b
2:
  # Counter 1 gives E(K, J0), the tag mask: with a 96-bit IV, the counter
  # of the text starts at 2.
  li        t5, 2
  srli      t1, a5, 4             # whole blocks of PT
  mv        t3, a3
  mv        t4, a4
  beqz      t1, 4f
3:
  rev8      t2, t5
  srli      t2, t2, 32            # bswap(bin(counter, 32))
  vmv.v.v   v5, v0
  vmv.s.x   v6, t2
  vslideup.vi v5, v6, 3           # v5 = bswap(bin(counter, 32)) @ IV
  vle32.v   v1, (t3)
  kl.exec   v2, K0, v5            # the mask: the encrypted counter
  vxor.vv   v1, v1, v2            # CTR encryption
  vghsh.vv  v3, v4, v1
  vse32.v   v1, (t4)
  addi      t3, t3, 16
  addi      t4, t4, 16
  addi      t5, t5, 1
  addi      t1, t1, -1
  bnez      t1, 3b
4:
  # Final partial block of r bytes, if any.  The ciphertext is truncated
  # to r bytes before it is absorbed and stored: GHASH absorbs the
  # zero-padded ciphertext, which is what SP 800-38D specifies.
  andi      t6, a5, 15            # r
  beqz      t6, 5f
  rev8      t2, t5
  srli      t2, t2, 32
  vmv.v.v   v5, v0
  vmv.s.x   v6, t2
  vslideup.vi v5, v6, 3
  kl.exec   v2, K0, v5
  vmv.v.i   v1, 0
  vsetvli   zero, t6, e8, m1, tu, ma # r bytes, the rest of v1 kept zero
  vle8.v    v1, (t3)
  vxor.vv   v1, v1, v2            # the keystream past the end is discarded
  vse8.v    v1, (t4)
  vsetivli  zero, 4, e32, m1, ta, ma
  vghsh.vv  v3, v4, v1
5:
  slli      t1, a5, 3
  rev8      t1, t1                # bswap(bin(len_in_bits(PT), 64))
  slli      t2, a2, 3
  rev8      t2, t2                # bswap(bin(len_in_bits(AD), 64))
  vsetivli  zero, 2, e64, m1, tu, ma
  vmv.v.x   v1, t1
  vmv.s.x   v1, t2
  vsetivli  zero, 4, e32, m1, ta, ma
  vghsh.vv  v3, v4, v1
  li        t2, 0x01000000        # bswap(bin(1, 32))
  vmv.v.v   v5, v0
  vmv.s.x   v6, t2
  vslideup.vi v5, v6, 3           # J0 (counter 1), for the tag mask
  kl.exec   v2, K0, v5
  vxor.vv   v3, v3, v2            # v3 holds the tag
----

[[KLE-GCM-SIV-mode-examples]]
=== GCM-SIV Mode

<<KLE-pseudocode-GCM-SIV-encryption>> encrypts with a GCM-SIV CC (`b` = `KLLEN` = 128), for AD and plaintext in whole bytes, as the Machine requires;
<<KLE-pseudocode-GCM-SIV-decryption>> decrypts.

[[KLE-pseudocode-GCM-SIV-encryption]]
.GCM-SIV Encryption
----
# a0 = SCC, a1 = AD, a2 = length of AD in bytes, a3 = PT, a4 = CT (may
# equal a3), a5 = length of PT in bytes, a6 = the 12-byte nonce.  The
# caller has zero-padded the last block of the AD and of the PT.

  import_scc 0, a0

  # Set the nonce, which also derives enc_key and auth_key.  The nonce is
  # the vector operand of a Form C kl.setst; no kl.exec is issued in this
  # State.
  vsetivli  zero, 12, e8, m1, ta, ma # KLLEN = 96
  vle8.v    v0, (a6)
  kl.setst  K0, #kl_state_set_aux_value, v0

  # Absorb the AD and then the plaintext into POLYVAL
  vsetivli  zero, 16, e8, m1, ta, ma # one block: KLLEN = 128
  kl.setst  K0, #kl_state_hash_absorb
  addi      t1, a2, 15
  srli      t1, t1, 4             # ceil(len_in_bytes(AD)/16) blocks
  mv        t3, a1
  beqz      t1, 2f
1:
  vle8.v    v0, (t3)              # a block of associated data
  kl.exec   K0, v0                # absorb it into POLYVAL
  addi      t3, t3, 16
  addi      t1, t1, -1
  bnez      t1, 1b
2:
  addi      t1, a5, 15
  srli      t1, t1, 4             # ceil(len_in_bytes(PT)/16) blocks
  mv        t3, a3
  beqz      t1, 4f
3:
  vle8.v    v0, (t3)              # a block of plaintext
  kl.exec   K0, v0                # absorb it into POLYVAL
  addi      t3, t3, 16
  addi      t1, t1, -1
  bnez      t1, 3b
4:
  # Finalize the SIV.  The lengths are the *input* of a Form A kl.exec in
  # State _Enc_Tag_Finalize_, and the SIV is its output; they are not
  # absorbed by a further kl.exec in _Hash_Absorb_.
  kl.setst  K0, #kl_state_enc_tag_finalize
  slli      t1, a5, 3
  slli      t2, a2, 3
  vsetivli  zero, 2, e64, m1, tu, ma # KLLEN = 128
  vmv.v.x   v0, t1                # bin(len_in_bits(PT), 64)
  vmv.s.x   v0, t2                # @ bin(len_in_bits(AD), 64)
  kl.exec   v2, K0, v0            # v2 holds the tag

  # Second pass: encrypt the whole blocks of the plaintext, with the SIV
  # as IV.  The kl.exec above has already moved the locker to _Encrypt_;
  # a kl.setst naming _Encrypt_ would invalidate it.
  vsetivli  zero, 16, e8, m1, ta, ma
  srli      t1, a5, 4             # whole blocks of PT
  mv        t3, a3
  mv        t4, a4
  beqz      t1, 6f
5:
  vle8.v    v0, (t3)              # a block of plaintext
  kl.exec   v1, K0, v0            # encrypt it
  vse8.v    v1, (t4)              # a block of ciphertext
  addi      t3, t3, 16
  addi      t4, t4, 16
  addi      t1, t1, -1
  bnez      t1, 5b
6:
  # Final partial block, if any.  Unlike in the first pass, it must not
  # go through as a zero-padded whole block: _Enc_Last_Block_ writes no
  # keystream bit past the end of PT to CT.
  andi      t1, a5, 15
  beqz      t1, 7f
  slli      t2, t1, 3
  kl.setst  K0, #kl_state_enc_last_block, t2
  vsetvli   zero, t1, e8, m1, ta, ma
  vle8.v    v0, (t3)
  kl.exec   v1, K0, v0
  vse8.v    v1, (t4)
7:
----

[[KLE-pseudocode-GCM-SIV-decryption]]
.GCM-SIV Decryption
----
# a0 = SCC, a1 = AD, a2 = length of AD in bytes, a3 = CT, a4 = PT (may
# equal a3), a5 = length of CT in bytes, a6 = the 12-byte nonce, a7 = the
# 16-byte received SIV.  The caller has zero-padded the last block of AD.

  import_scc 0, a0

  # Set the nonce
  vsetivli  zero, 12, e8, m1, ta, ma # KLLEN = 96
  vle8.v    v0, (a6)
  kl.setst  K0, #kl_state_set_aux_value, v0

  # Set the received SIV, which serves as the IV of the decryption
  vsetivli  zero, 16, e8, m1, ta, ma # one block: KLLEN = 128
  vle8.v    v0, (a7)
  kl.setst  K0, #kl_state_set_aux_value_2, v0

  # Absorb the AD
  kl.setst  K0, #kl_state_hash_absorb
  addi      t1, a2, 15
  srli      t1, t1, 4             # ceil(len_in_bytes(AD)/16) blocks
  mv        t3, a1
  beqz      t1, 2f
1:
  vle8.v    v0, (t3)
  kl.exec   K0, v0                # absorb it into POLYVAL
  addi      t3, t3, 16
  addi      t1, t1, -1
  bnez      t1, 1b
2:
  # Decrypt the whole blocks; each recovered block is absorbed into POLYVAL
  kl.setst  K0, #kl_state_decrypt
  srli      t1, a5, 4             # whole blocks of CT
  mv        t3, a3
  mv        t4, a4
  beqz      t1, 4f
3:
  vle8.v    v0, (t3)
  kl.exec   v1, K0, v0
  vse8.v    v1, (t4)
  addi      t3, t3, 16
  addi      t4, t4, 16
  addi      t1, t1, -1
  bnez      t1, 3b
4:
  # Final partial block, if any
  andi      t1, a5, 15
  beqz      t1, 5f
  slli      t2, t1, 3
  kl.setst  K0, #kl_state_dec_last_block, t2
  vsetvli   zero, t1, e8, m1, ta, ma
  vle8.v    v0, (t3)
  kl.exec   v1, K0, v0
  vse8.v    v1, (t4)
5:
  # Absorb the lengths and verify, with a Form B kl.exec: the recomputed
  # SIV is compared internally against the one supplied above
  kl.setst  K0, #kl_state_dec_tag_finalize
  slli      t1, a5, 3
  slli      t2, a2, 3
  vsetivli  zero, 2, e64, m1, tu, ma # KLLEN = 128
  vmv.v.x   v0, t1                # bin(len_in_bits(PT), 64)
  vmv.s.x   v0, t2                # @ bin(len_in_bits(AD), 64)
  kl.exec   K0, v0
  kl.getst  t1, K0
  li        t2, kl_state_success
  bne       t1, t2, error         # do not use the plaintext
----

[[KLE-OCB-mode-examples]]
=== OCB Mode

This section gives OCB encryption and decryption (`b` = `KLLEN` = 128).

[[KLE-pseudocode-OCB-encryption]]
.OCB Encryption
----
# a0 = CC, a1 = AD, a2 = AD_len in bits, a3 = PT, a4 = CT (may equal a3),
# a5 = PT_len in bits, a6 = nonce N, a7 = N_len in bits, s9 = tag_len.
# AD_len and PT_len are multiples of 8.

  import_scc 0, a0

  # Set the nonce
  kl.setst  K0, #kl_state_set_aux_value, a7
  addi      t1, a7, 7
  srli      t1, t1, 3             # ceil(N_len/8) bytes
  vsetvli   zero, t1, e8, m1, ta, ma
  vle8.v    v0, (a6)
  kl.exec   K0, v0

  # The next state change also sets the tag length
  kl.setst  K0, #kl_state_hash_absorb, s9

  # Compute the AD contribution to the tag
  vsetivli  zero, 16, e8, m1, ta, ma # one block: KLLEN = 128
  srli      t1, a2, 7             # whole blocks of AD
  mv        t3, a1
  beqz      t1, 2f
1:
  vle8.v    v0, (t3)
  kl.exec   K0, v0                # absorb it into the hash
  addi      t3, t3, 16
  addi      t1, t1, -1
  bnez      t1, 1b
2:
  andi      t2, a2, 127           # can be zero
  kl.setst  K0, #kl_state_hash_last_block, t2
  beqz      t2, 3f
  srli      t1, t2, 3
  vsetvli   zero, t1, e8, m1, ta, ma
  vle8.v    v0, (t3)
  kl.exec   K0, v0                # absorb the last AD block
3:
  # Encrypt the plaintext and continue the computation of the tag
  kl.setst  K0, #kl_state_encrypt
  vsetivli  zero, 16, e8, m1, ta, ma
  srli      t1, a5, 7             # whole blocks of PT
  mv        t3, a3
  mv        t4, a4
  beqz      t1, 5f
4:
  vle8.v    v0, (t3)
  kl.exec   v1, K0, v0
  vse8.v    v1, (t4)
  addi      t3, t3, 16
  addi      t4, t4, 16
  addi      t1, t1, -1
  bnez      t1, 4b
5:
  andi      t2, a5, 127           # can be zero
  kl.setst  K0, #kl_state_enc_last_block, t2
  beqz      t2, 6f
  srli      t1, t2, 3
  vsetvli   zero, t1, e8, m1, ta, ma
  vle8.v    v0, (t3)
  kl.exec   v1, K0, v0            # encrypt it and absorb it into the tag
  vse8.v    v1, (t4)
  j         7f
6:
  kl.exec   K0                    # Form D: finalize the tag only
7:
  # _Enc_Last_Block_ transitions to _Enc_Tag_Finalize_ on its own, so no
  # kl.setst is issued here.
  vsetivli  zero, 16, e8, m1, ta, ma
  kl.exec   v1, K0                # output the tag
----

OCB decryption follows <<KLE-pseudocode-OCB-encryption>> up to the final block, with the roles of `PT` and `CT` exchanged, and States _Decrypt_ and _Dec_Last_Block_ in place of _Encrypt_ and _Enc_Last_Block_;
<<KLE-pseudocode-OCB-decryption-difference>> gives only the last step, which differs:
OCB has no _Dec_Tag_Finalize_ State, and after the last block _Dec_Last_Block_ transitions directly to
_Hash_Verify_, where a Form B `kl.exec` supplies the received tag.

[[KLE-pseudocode-OCB-decryption-difference]]
.OCB Decryption
----
# s10 = the received tag, of tag_len bits
  srli      t1, s9, 3
  vsetvli   zero, t1, e8, m1, ta, ma # KLLEN = tag_len
  vle8.v    v1, (s10)
  kl.exec   K0, v1                # Form B: compares it with checksum_P
  kl.getst  t1, K0
  li        t2, kl_state_success
  bne       t1, t2, error         # do not use the plaintext
----

[[KLE-pseudocode-CMAC]]
.CMAC Computation
----
# a0 = CC, a1 = CMAC input M, a2 = M_len in bits, a multiple of 8

  import_scc 0, a0
  vsetivli  zero, 16, e8, m1, ta, ma # one block: KLLEN = 128

  kl.setst  K0, #kl_state_hash_absorb

[[KLE-hash-example]]
=== Hash Functions, MACs and XOFs

The following sequence hashes a message with any Machine of <<Zkl-ISA-machines.adoc#KLE-hash-functions-MACs-XOFs>>; only the SCC and the number `out_bytes` of output bytes differ.

* *Message.* The caller passes `M` unpadded; the `kl.setst` into _Hash_Output_ pads it.
The final piece, of `M_bits` mod 64 bits, fits every Machine, since `b` {ge} 64; for BLAKE2 it must be a whole number of bytes.
A partial final byte holds the final bits in the order of the standard: in its most significant positions for SHA-2 and SM3,
in its least significant positions for SHA-3, KMAC and Ascon, and as for its `H` for HMAC.
* *Output length.* An `Xs` = 8 {times} `out_bytes` in the `kl.setst` into _Hash_Output_ makes the Machine emit exactly `out_bytes` bytes and then enter _Success_.
For KMAC128 and KMAC256 it is also the `L` that the MAC encodes; KMACXOF128 and KMACXOF256 encode `L` = 0.
For every other Machine, `out_bytes` only truncates the output.
`out_bytes` is:
** at least 1; at least 8 for HMAC, and at least 4 for KMAC128 and KMAC256;
** at most the digest length for a fixed-output Machine;
** below 2^29^ for an XOF, KMAC128 or KMAC256.
+
`Xs` = 0 asks instead for the full digest, or for an unbounded XOF; it is invalid for KMAC128 and KMAC256.
* *BLAKE2.* A digest of `nn` {ne} `nn~max~` bytes, such as BLAKE2b-256, needs an SCC whose `nn` was set by the _Set_Aux_Value_ operation of <<Zkl-ISA-machines.adoc#KLE-BLAKE2>> or by a system-specific import, since `nn` enters the IV.
With `kk` {ne} 0 and no system key, the caller keys the hash: `M` starts with the key zero-padded to `b` bits (cite:[RFC7693] {sect}3.3), which alone forms the message for an empty `M`; a system key needs no such block.
* *The SCC.*
** It is in _Ready_; one exported in _Hash_Absorb_ after a prefix of the message, as in the NOTE of <<Zkl-ISA-machines.adoc#KLE-Ascon-Hash256>>, takes no first `kl.setst`, and `M` is then the rest of the message.
** An SCC of the NIK variant of <<Zkl-ISA-machines.adoc#KLE-HMAC>> must already hold its key.
** The SCC of HMAC, KMAC128 or KMAC256, or of BLAKE2 with a system key, must enable _Hash_Output_ (_MachinePolicy_[0]);
for the MAC verification below, that of HMAC, KMAC128 or KMAC256 must enable _Hash_Verify_ (_MachinePolicy_[1]) instead.

[[KLE-pseudocode-hash]]
.Hashing a Message
----
# a0 = SCC of any hash, MAC or XOF, a1 = message M, a2 = M_bits,
# a3 = output buffer OUT, a4 = out_bytes

  import_scc 0, a0
  kl.setst  K0, #kl_state_hash_absorb

  andi      t3, a2, 63            # r: the final piece, 0 to 63 bits
  sub       t4, a2, t3
  srli      t4, t4, 3             # h: the bytes before it
  li        t2, 16
  beqz      t4, 2f
1:
  minu      t1, t4, t2            # the last chunk may be shorter
  vsetvli   zero, t1, e8, m1, ta, ma # KLLEN = 8 * t1
  vle8.v    v0, (a1)
  kl.exec   K0, v0                # absorb t1 bytes, unpadded
  add       a1, a1, t1
  sub       t4, t4, t1
  bnez      t4, 1b
2:
  kl.setst  K0, #kl_state_hash_last_block, t3 # r = 0: does nothing
  beqz      t3, 3f
  addi      t1, t3, 7
  srli      t1, t1, 3             # ceil(r/8) bytes
  vsetvli   zero, t1, e8, m1, ta, ma
  vle8.v    v0, (a1)
  kl.exec   K0, v0                # absorb the final r bits
3:
  slli      t1, a4, 3
  kl.setst  K0, #kl_state_hash_output, t1 # end the message: the Machine
                                  # pads
4:
  minu      t1, a4, t2
  vsetvli   zero, t1, e8, m1, ta, ma
  kl.exec   v0, K0                # emit the next t1 bytes
  vse8.v    v0, (a3)
  add       a3, a3, t1
  sub       a4, a4, t1
  bnez      a4, 4b
  kl.getst  t1, K0                # _Success_
----

To verify a MAC `T` of `T_len` bits with HMAC, KMAC128 or KMAC256 instead, the
code from label `3` on is replaced by the listing below.
The listing takes `T_len` at most `t` for HMAC and at most `b` for KMAC128 and KMAC256.
HMAC also admits a longer `T`, but compares only its first `t` bits; KMAC128 and KMAC256 do not admit one.
With 128-bit vectors, LMUL = 8 holds a tag of up to 1024 bits: every HMAC tag, and a KMAC
tag up to that length.

[[KLE-pseudocode-hash-verify]]
.MAC Verification
----
# a5 = T, a6 = T_len in bits, a multiple of 8, >= 64 (KMAC: 32)
  kl.setst  K0, #kl_state_hash_verify, a6
  srli      t1, a6, 3
  vsetvli   zero, t1, e8, m8, ta, ma # KLLEN = T_len
  vle8.v    v0, (a5)
  kl.exec   K0, v0                # compares the first T_len bits
  kl.getst  t1, K0                # _Success_ if T matches,
                                  # _Failure_ otherwise
----

With Ascon-CXOF128 and a customization string `Z` of `Z_bits` bits, the first `kl.setst`
is replaced by:

[[KLE-pseudocode-cxof-customization]]
.Ascon-CXOF128 Customization
----
# a5 = Z, a6 = Z_bits, 0 to 2048
  kl.setst  K0, #kl_state_set_aux_value, a6 # absorbs bin(Z_bits, 64)
  addi      t4, a6, 7
  srli      t4, t4, 3             # ceil(Z_bits/8) bytes of Z
  li        t2, 16
  beqz      t4, 2f
1:
  minu      t1, t4, t2            # chunks of up to 16 bytes, as for M
  vsetvli   zero, t1, e8, m1, ta, ma
  vle8.v    v0, (a5)
  kl.exec   K0, v0
  add       a5, a5, t1
  sub       t4, t4, t1
  bnez      t4, 1b
2:
  kl.setst  K0, #kl_state_hash_absorb # pad Z; M follows as above
----
