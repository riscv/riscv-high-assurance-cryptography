_This chapter is informative._ It gives the requirements and guidelines for software that uses KLE, and code examples.
The examples follow the conventions of
<<Zkl-notation.adoc#KLE-Notation>>; in particular, a value loaded into a vector register holds the
byte at the lowest address in its least significant bits.
The listings assume RV64, on which a 64-bit operand, such as the destination of `kl.getst` or the auxiliary input of a Form B `kl.setst`, is one GPR; on RV32 it is a GPR pair whose first register number is even (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-multiple-GPRs>>).

// ///////////////////////////////////////////////////////////////////

[[KLE-software-requirements]]
== Software Requirements

_This section is informative for the architecture, which does not enforce its Rules; software must follow them._

KLE splits complex operations into small instructions and relies on software to use them as intended.
Software, privileged or not, that ignores these Rules may lose functionality and breach security: it may corrupt cryptographic state, make it unavailable through the checks of the architecture, or reveal a CC to peer or less privileged software not meant to receive it.

[[KLE-interposed-software,interposed software]]Definition: _Interposed software_.::
(((interposed software)))
_Interposed software_ is code that runs while other software may have a halted instruction, or a management operation in progress, in the live KLE state of the hart.
It includes every trap handler, for an exception or an interrupt, in any mode, even the same mode of the interrupted code, and any other code that shares that KLE state, such as another thread of the same process.

// ////////////////////////////////////////////////////////////////////

[[KLE-SR-isolation]]
=== Isolation of Contexts

[horizontal]
[[KLE-SR-clear-before-lower-mode,SR1]]SR1:: Software must keep its lockers from unauthorized parties; before giving control to a less privileged mode, it must clear every locker that holds its CC or that it has placed in a Configuration State, completing any export first (Rule <<KLE-SR-no-unconditional-clear>>).

[[KLE-SR-restore-own-lockers,SR2]]SR2:: When switching to a less privileged component, software must restore only the lockers saved for that component, and clear the others; the same holds for `kliobuflen`, and for the KLIOBUF when `kliobuflen` {ne} 0.

[[KLE-SR-save-shared-state,SR3]]SR3:: Software that uses the KLIOBUF, `klstart` or `klnamedlocker`, or performs a management operation, while the KLE state of a less privileged context is live, must first save the state it uses and restore it before returning, so that the less privileged context observes its own values and no data of the more privileged mode.

// ////////////////////////////////////////////////////////////////////

[[KLE-SR-kliobuf]]
=== Requirements on the KLIOBUF

[horizontal]
[[KLE-SR-kliobuflen-zero,SR4]]SR4:: Software should set `kliobuflen` to zero once it no longer needs the KLIOBUF contents, which context-switch code must otherwise save and restore (<<Zkl-software.adoc#KLE-save-order>>, <<Zkl-software.adoc#KLE-restore-order>>); setting `kliobuftop` to zero instead keeps them accessible.

// ////////////////////////////////////////////////////////////////////

[[KLE-klstart-software-check]]
=== Requirements on `klstart`

`klstart` exists once per hart, and nothing resets it before other software uses it: an instruction that honors `klstart` starts at the value it finds, and `kl.mgmt`, `kl.clearall` and every instruction that honors `klstart` write it.
Without Rule <<KLE-SR-klstart-save>>, an instruction of interposed software would start where the interrupted instruction halted, skipping a prefix of its own operand, and the interrupted instruction would resume at another position, or restart.

[horizontal]
[[KLE-SR-klstart-save,SR5]]SR5:: <<KLE-interposed-software,Interposed software>> must save `klstart` before its first KLE instruction, write 0 to it before its first instruction that honors it, and restore the saved value before control returns to the interrupted software.
A handler that skips the trapping instruction applies its retirement effects to `klstart` instead (Rule <<KLE-SR-handler-duty>>).

[[KLE-SR-klstart-no-reset,SR6]]SR6:: Software should not write 0 to `klstart` to force a full restart of `kl.exec` or `kl.derive` once per-block state effects have been committed.

// ////////////////////////////////////////////////////////////////////

[[KLE-SR-management]]
=== Requirements on Management Operations

Rule <<KLE-SR-nested-export-first>> binds <<KLE-interposed-software,interposed software>>.
An instruction issued in violation of Rule <<KLE-SR-klnamedlocker-write>> or <<KLE-SR-nested-export-first>> acts on whatever locker `klnamedlocker` names (<<Zkl-ISA-unpriv.adoc#KLE-named-locker-rules>>).

[horizontal]
[[KLE-SR-klnamedlocker-write,SR7]]SR7:: Before `kl.load`, `kl.store`, `kl.mvin`, `kl.mvout`, an instruction naming `KLNL` (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-klnamedlocker-override>>), or a `kl.mgmt` that names its locker explicitly, interposed software must read `klnamedlocker` and, if `klnamedlocker` does not hold the intended value, save it, write the intended value, and restore the saved one before control returns to the code that set it.
The intended value is the number of the target locker, 32 for a transfer to or from the KLIOBUF, and 32 or the number of the target locker for a `kl.mgmt` that names its locker explicitly.
Any software that completes or abandons a management operation must then write 32 to `klnamedlocker`, or restore the value it saved.

[[KLE-SR-nested-export-first,SR8]]SR8:: Before opening, on another locker, an export from a Valid State or an import other than the short import of an Error-State image (<<Zkl-ISA-unpriv.adoc#KLE-error-state-transfer>>), while the locker that `klnamedlocker` names is in State `kl_cfg_exporting` or `kl_cfg_importing`, software must save that locker by a nested export and restore it before returning to the code that opened its operation, or terminate that code.
While that locker is in such a State, software must not write another value to `klnamedlocker` before saving it this way, so that `klnamedlocker` names the owner of the authentication registers at every trap.
Software may instead clear a locker in State `kl_cfg_importing`, whose import then restarts (<<Zkl-ISA-unpriv.adoc#KLE-CC-management>>).

[[KLE-SR-no-interleaving,SR9]]SR9:: Software should complete or discard a management operation before it performs cryptographic operations or manages other lockers.
Code that must interleave them, for instance in several threads of one process, needs coordination, such as lightweight threads with KLE context-switching support, or a mutex.
Software that writes 32 to `klnamedlocker` while its own import or export is open, for instance to transfer data through the KLIOBUF (<<Zkl-ISA-unpriv.adoc#KLE-instruction-mv>>), must have no other import or export open that a nested export has not saved.

[[KLE-SR-no-unconditional-clear,SR10]]SR10:: At a context switch, system software may clear a locker under a provisioning or an import instead of saving it, which forces the operation to restart, but it must be able to save such a locker and must not clear it unconditionally at every context switch.
Unless it terminates the owner, software must not clear a locker under an export, base or nested, before completing that export.
+
NOTE: Repeated restarts may prevent a provisioning or an import from completing, and a clear destroys the CC of a locker under an export.

// ////////////////////////////////////////////////////////////////////

[[KLE-SR-handlers]]
=== Requirements on Exception Handlers

[horizontal]
[[KLE-SR-handler-duty,SR11]]SR11:: A handler that neither resolves nor forwards, to another handler, in-process handlers included, an exception for which <<Zkl-ISA-unpriv.adoc#KLE-exception-error-correspondence>> gives an Error State, and that does not terminate the process, must:
+
--
. set the _State_ of the locker on which the exception was raised, for `KLNL` the one that `klnamedlocker` names (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-klnamedlocker-updates>>), to that Error State, through the short import of <<Zkl-ISA-unpriv.adoc#KLE-error-state-transfer>> if the locker is _Unconfigured_ (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>); a locker in a Configuration State keeps its _State_ (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-config-state>>); and
. advance `xepc` past the trapping instruction, which would otherwise trap again; for a usage instruction, keep the output prefix that `klstart` and `vstart` record, zero the rest of the output window (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-zero-unwritten-output>>), and apply the retirement effects on `klstart` and `vstart` (Rules <<Zkl-ISA-unpriv.adoc#KLE-GR-klstart-updates>> and <<Zkl-ISA-unpriv.adoc#KLE-GR-klstart-vstart>>).
--

[[KLE-SR-uninterruptible,SR12]]SR12:: Software must not rely on whether an uninterruptible instruction (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-interruptibility-classes>>) has retired when a handler runs, and must interact with it only as Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-conflicting-access-rule>> prescribes.

// ////////////////////////////////////////////////////////////////////

[[KLE-SR-localities]]
=== Requirements on Localities

[horizontal]
[[KLE-SR-locality-unconfigure,SR13]]SR13:: Software must not unconfigure a Locality Secret while a locker bound to it may still be exported: an export made after that binds `zeros(128)` in its place, and no import accepts the resulting SCC (<<Zkl-ISA-unpriv.adoc#KLE-SCC-export>>).

// ////////////////////////////////////////////////////////////////////

[[KLE-SR-transfer-loops]]
=== Requirements on Transfer Sequences

[horizontal]
[[KLE-SR-no-klstart-loop,SR14]]SR14:: Software must not use `klstart` as the termination condition of a sequence of `kl.mvin` or `kl.mvout`, since `klstart` does not advance on a locker that has become _Unconfigured_ or entered an Error State (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>). The sequence is bounded by the image size read with `kl.size` before it, and the _State_ is checked after it (<<Zkl-software.adoc#KLE-pseudocode-examples>>, NOTE after Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-memory-instructions>>).

[[KLE-SR-export-final-check,SR15]]SR15:: Software that exports a locker must rely on the image only if the _State_ read after the last instruction of the export, or in the MDH that `kl.getmd*` returned when the image is the MDH alone, is not _Unconfigured_ (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>).

// ////////////////////////////////////////////////////////////////////

[[KLE-SR-csk]]
=== Requirements on the Context Sealing Key

[horizontal]
[[KLE-SR-csk-change,SR16]]SR16:: The architecture does not block a change of the CSK (<<Zkl-ISA-unpriv.adoc#KLE-CSK-requirements>>) while an export is open.
M-mode must not change the CSK of a hart until every export open on it, base or nested, has completed and its image has been saved.

[[KLE-SR-system-keys]]
=== Requirements on System Keys

[horizontal]
[[KLE-SR-skid-usage-policy,SR17]]SR17:: A system that intends to protect a System Key (<<Zkl-ISA-unpriv.adoc#KLE-system-keys>>) associates at least a _UsagePolicy_ with its SKID in the SKS; a _UsagePolicy_ that admits every mode, as for a public signature-verification key, is a deliberate choice.

[[KLE-state-save-and-restore-order]]
== Software Guidelines

The guidelines of this section are for privileged software.

// Here we collect the duties that the KLE state places on privileged software and exception handlers, in the order software meets them.

A context switch meets Rules <<KLE-SR-clear-before-lower-mode>> to <<KLE-SR-save-shared-state>> by following <<KLE-save-order>> and <<KLE-restore-order>>.
Where an item cites a Rule SR__n__ (<<KLE-software-requirements>>), that Rule takes precedence.

// ////////////////////////////////////////////////////////////////////

[[KLE-handler-duties]]
=== Duties of Every Exception Handler

<<KLE-interposed-software,Interposed software>> is bound by Rules <<KLE-SR-klstart-save>>, <<KLE-SR-klnamedlocker-write>> and <<KLE-SR-nested-export-first>>.

On entry, before its first KLE instruction, the handler:

. saves `klstart` (Rule <<KLE-SR-klstart-save>>);
. saves `klnamedlocker` (Rule <<KLE-SR-klnamedlocker-write>>);
. writes 0 to `klstart` before its first instruction that honors it (Rule <<KLE-SR-klstart-save>>); and
. saves the vector state, and writes 0 to `vstart`, before its first vector KLE instruction (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-vector-legality>>).

Before each instruction that Rule <<KLE-SR-klnamedlocker-write>> lists, it sets `klnamedlocker` as that Rule requires.

On exit, the handler:

. restores `klnamedlocker` to its saved value, or to 32 if it has cleared, instead of saving, the locker that value named (<<KLE-save-order>>);
. restores the vector state, `vstart` included; and
. restores `klstart` last, exactly as saved (Rules <<KLE-SR-klstart-save>> and <<KLE-SR-klstart-no-reset>>).

A handler that skips the trapping instruction applies its retirement effects to `klstart` and `vstart` instead of restoring them (Rule <<KLE-SR-handler-duty>>).

// ////////////////////////////////////////////////////////////////////

[[KLE-reading-locker-state]]
=== Reading the _State_ of a Locker

* `kl.getst Xd, KLNL` reads the _State_ of the locker that `klnamedlocker` names; with `klnamedlocker` = 32 it returns 0 (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>).
* To inspect lockers whose numbers it holds in registers, software writes each number in turn to `klnamedlocker` and names `KLNL`.
* `kl.getst` reads the _State_, `kl.getstx` the _StateExtension_, and `kl.getmd` the whole MDH.
* On RV32, `kl.getst` and `kl.getstx` write the GPR pair `X[d+1] @ X[d]`, and `kl.getmd` a quartet (<<Zkl-ISA-unpriv.adoc#KLE-instruction-getst>>, <<Zkl-ISA-unpriv.adoc#KLE-instruction-getmd>>).
* A _State_ in 48–55, that is, with `(State & 0x38) = 0x30`, is an Error State (<<Zkl-ISA-unpriv.adoc#KLE-states-error>>).
* Software that relies on the output of a usage instruction checks, immediately after the instruction, that the locker is in a Valid State before using the output.

// ////////////////////////////////////////////////////////////////////

[[KLE-management-routines]]
=== Management Routines

* The recommended approach is that a management routine takes the locker number as a parameter, 32 meaning the locker indexed by `klnamedlocker`. It saves `klnamedlocker`, and on entry and at every restart writes the number to it or, for 32, keeps its value, returning an error to its caller if that is 32 too (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>); it names the locker `KLNL` throughout, and restores the saved value on exit, also when it abandons the operation (Rules <<KLE-SR-klnamedlocker-write>>, <<Zkl-software.adoc#KLE-management-code-snippets>>).
//  A handler can thus call it, also for a nested export or import of the locker that the interrupted operation manages.
* After each management instruction, the routine reads the _State_ of the locker: _Unconfigured_ means the locker has been cleared, so a provisioning or an import restarts and an export has lost its CC (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>); an Error State means the operation has failed. The same code handles resumption and restart.
* An export sizes its buffer with `kl.size`, and reads the size again after its opening `kl.mgmt`.
* Software does not interleave cryptographic operations, or the management of other lockers, with the steps of a management operation (Rule <<KLE-SR-no-interleaving>>).

// ////////////////////////////////////////////////////////////////////

[[KLE-save-order]]
=== Context Save Order

. Save `klstart`.
. Save `klnamedlocker`.
. Let the _owner_ be the locker that the saved `klnamedlocker` indexes, if it is in [0..31]; otherwise, the locker in State `kl_cfg_importing` or `kl_cfg_exporting`, if there is one (Rule <<KLE-SR-no-interleaving>>).
If there is an owner, save it first, with Form C or D `kl.mgmt` and no KLIOBUF transfer (Rule <<KLE-SR-nested-export-first>>), choosing the path by its _State_, read with `kl.getst`:
.. _Unconfigured_: save no locker image;
.. an Error State: save its MDH by the short Error-State path (<<Zkl-ISA-unpriv.adoc#KLE-error-state-transfer>>);
.. otherwise, export the locker, by nested export if it is under management.
. With `Zklio`:
.. save `kliobuflen` and `kliobuftop`;
.. if `kliobuflen` is non-zero, save the buffer contents with `kl.output`, with `klnamedlocker` = 32, `klstart` = 0 and `kliobuftop` = `kliobuflen`, then write 0 to `kliobuflen`.
. Save every locker other than the owner that is not _Unconfigured_, with `klnamedlocker` = 32 between exports.

Each export completes, with its completing `kl.mgmt` and outcome check, before its locker is cleared (Rule <<KLE-SR-no-unconditional-clear>>).

Instead of saving a locker being provisioned or imported, the handler may clear it, subject to Rule <<KLE-SR-no-unconditional-clear>>; the interrupted software then restarts the operation (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>), and the handler restores 32 in place of a saved `klnamedlocker` that named that locker (<<KLE-restore-order>>).

A handler that passes `ml` through the KLIOBUF for the other lockers configures `kliobuflen` {ge} 16 for their exports and imports, and restores the saved value afterwards.

// ////////////////////////////////////////////////////////////////////

[[KLE-restore-order]]
=== Context Restore Order

. Clear the lockers for which no image is restored below, or all of them with `kl.clearall` (Rule <<KLE-SR-restore-own-lockers>>).
. Restore the lockers other than the owner (<<KLE-save-order>>), with `klnamedlocker` = 32 between imports.
. With `Zklio`:
.. restore `kliobuflen`;
.. restore the buffer contents, if saved, with `kl.input`, with `klnamedlocker` = 32, `klstart` = 0 and `kliobuftop` = `kliobuflen`;
.. restore `kliobuftop`.
. If an image was saved for the owner, restore it last, with Form C or D `kl.mgmt` and no KLIOBUF transfer.
. Restore the saved value of `klnamedlocker`, or 32 if the handler has cleared the locker it named instead of saving it.
. Restore `klstart` last.

// ////////////////////////////////////////////////////////////////////

[[KLE-handling-kle-exceptions]]
=== Handling a KLE Exception

A handler that can neither resolve nor forward a KLE exception covered by Rule <<KLE-SR-handler-duty>>, nor terminate the process:

. unless the locker is in a Configuration State, sets it to the Error State that <<Zkl-ISA-unpriv.adoc#KLE-exception-error-correspondence>> gives, or to _Invalid_ where it gives none: with `kl.setst` and that Error State as immediate (<<Zkl-ISA-unpriv.adoc#KLE-instruction-setst>>), or, if the locker is _Unconfigured_, by the short import of an MDH holding that State (<<Zkl-ISA-unpriv.adoc#KLE-error-state-transfer>>); and
. advances `xepc` past the instruction, retiring a usage instruction as Rule <<KLE-SR-handler-duty>> states.

[[KLE-management-code-snippets]]
== Code for Locker Configuration and Export Operations

[WARNING]
====
These examples are being rewritten. They are not yet definitive.
====

This subsection illustrates the intended instruction sequences for locker configuration and export operations.
They show the main operation logic and error detection, but not application-specific error management, and can be packaged into libraries or OS APIs to avoid increasing application code size.

Registers::
GPR `t0` holds the number of the locker to be provisioned, imported or exported, or 32 for the locker that `klnamedlocker` names, and GPR `t6` points to the 16-byte aligned memory location of the PI or SCC (<<Zkl-ISA-unpriv.adoc#KLE-instructions-memory>>).
The MDH is loaded and stored with `ld` and `sd`, and passed in the GPR pair `s5:s4`; on RV32 it takes a GPR quartet (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-multiple-GPRs>>).

Selecting the locker::
The routines never use explicit locker numbers in the instructions: they save `klnamedlocker` on entry and select the locker with the preamble `select_locker` below, on entry and at every `restart`, and every KLE instruction then acts on that locker (Rules <<Zkl-ISA-unpriv.adoc#KLE-GR-locker-less-transfers>> and <<Zkl-ISA-unpriv.adoc#KLE-GR-klnamedlocker-override>>).
`kl.load`, `kl.store`, `kl.mvin` and `kl.mvout` have no locker operand, and `kl.mgmt`, `kl.getst`, `kl.getmd` and `kl.size` name the named locker `KLNL`.
A clear resets `klnamedlocker` to 32, after which a `KLNL` opening performs no operation (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>): the next _State_ check reads 0, and the preamble at `restart` names locker `t0` again or, when `t0` = 32, whose locker the clear has destroyed, branches to `no_locker`. An opening on a named locker opens it, a Valid one included.
On exit they restore the saved value, as Rule <<KLE-SR-klnamedlocker-write>> requires of software that has finished a management operation; a routine can thus be called from a handler that has saved the interrupted operation (<<KLE-state-save-and-restore-order>>), including for a nested export or import of the locker that operation manages.
+
----
.macro select_locker              # t0 = p: 0-31, or 32 for the named locker
  li        t1, 32
  bgeu      t0, t1, 1f            # p = 32: keep the named locker
  kl.setnl  t0                    # p in 0-31: name locker p
  j         2f
1:
  kl.getnl  t2
  bgeu      t2, t1, no_locker     # none named, or cleared: error to caller
2:
.endm
----

Checking the _State_::
+
--
After each management instruction, the code reads the _State_ of the locker with `kl.getst`.
If a handler has meanwhile cleared the locker or set it to an Error State, a following `kl.mvin`, `kl.mvout`, `kl.load`, `kl.store` or `kl.mgmt`, a `KLNL` opening after a clear included, performs no operation (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-outcome-inert>>), and the check detects the change:

* after a clear, `KLNL` reads as an _Unconfigured_ locker, so the check finds _State_ 0: a provisioning or an import restarts, its preamble naming locker `t0` again or branching to `no_locker` when `t0` = 32, and an export, whose CC the clear has destroyed, branches to `handle_errors`;
* after an Error State, or the completing `kl.mgmt`, `KLNL` still names the locker, so the check reads its final _State_, and an Error State abandons the operation.

Only the check after the last instruction is required; the earlier checks only react sooner.
The code may bound the number of restarts and branch to its error handling once the bound is reached; this is a matter of robustness only, since system software must let the operation complete (Rule <<KLE-SR-no-unconditional-clear>>).
--

Error handling::
The code at `handle_errors` and `no_locker` is not shown; `no_locker` restores `klnamedlocker` and returns an error to the caller, since with `t0` = 32 no locker is named, or a clear has destroyed the named one.
It writes 0 to `klstart`, which a `kl.mvin` or `kl.mvout` loop leaves at its last transfer point, and restores `klnamedlocker` as the routines do on exit.
If the locker is still in a Configuration State, it clears a locker being provisioned or imported, and completes the export of a locker being exported with the saved MDH, which restores the locker.

=== Provisioning

The provisioning code assumes that the Content immediately follows the MDH in memory.
The MDH of the PI carries _State_ = _Unconfigured_ (0); the completing `kl.mgmt` sets _Ready_.

*Provisioning Code (`Zklmv`)*
----
# t5 holds the length of the PI's Content (hence, excluding the MDH) in bytes.
# t5 can be zero. The caller constructed the PI and so knows this length.
# t5 is never modified, so the working count and pointer can be re-derived
# from it whenever the operation is restarted.

  ld        s4, 0(t6)             # load MDH[63:0] from memory
  ld        s5, 8(t6)             # load MDH[127:64] from memory
  li        t3, 0x30              # const useful to determine Error States
  kl.getnl  s8                    # save the caller's value: the routine may
                                  # run inside another management operation

restart:
  select_locker                   # name the locker: every KLE instruction
                                  # below acts on it; a clear resets it to 32
  kl.mgmt   KLNL, #kl_cfg_provisioning, s5:s4 # start provisioning, load MDH
  kl.getst  t2, KLNL              # get _State_ field from MDH
  beqz      t2, restart           # locker cleared: must restart
  andi      t2, t2, 0x38          # Check the three top bits of State
  beq       t3, t2, handle_errors # Error State: provisioning ended

  addi      t4, t6, 16            # source pointer: first byte after MDH
  mv        s1, t5                # working byte count, re-derived from t5
                                  # on restart

  vsetvli   s6, zero, e8, m1, ta, ma # s6 = VLMAX
vloop:
  mv        s2, s1
  bleu      s2, s6, 1f
  mv        s2, s6
1:
  vsetvli   s2, s2, e8, m1, ta, ma # AVL <= VLMAX, so vl = AVL, multiple of 16
  vle8.v    v1, (t4)              # load a chunk of the PI
  kl.mvin   v1                    # move it into the locker
  add       t4, t4, s2            # bump the source pointer
  sub       s1, s1, s2            # decrement the bytes still to load
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared: must restart
  andi      t2, t2, 0x38          # Three top bits -> Error or Management
  beq       t3, t2, handle_errors # *new* Error State
  bnez      s1, vloop

  kl.mgmt   KLNL, #kl_cfg_management_end # complete provisioning
                                  # and possibly reconstruct data
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared: must restart
  andi      t2, t2, 0x38
  beq       t3, t2, handle_errors # catches errors at completion (e.g., SKS)

finished:
  kl.setnl  s8                    # restore the caller's value
# The locker is Ready, or in Failure after a data error at completion. Any
# Error State met above is new, since the PI carried State = Unconfigured:
# handle_errors decides the course of action.
----

*Provisioning Code (`Zklmem`)*
----
  ld        s4, 0(t6)             # load MDH[63:0] from memory
  ld        s5, 8(t6)             # load MDH[127:64] from memory
  li        t3, 0x30              # const useful to determine Error States
  kl.getnl  s8                    # save the caller's value

restart:
  select_locker                   # name the locker (a clear resets it to 32)
  kl.mgmt   KLNL, #kl_cfg_provisioning, s5:s4 # start prov. and load MDH
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared: must restart
  andi      t2, t2, 0x38          # Check the three top bits of State
  beq       t3, t2, handle_errors # Error State?

  # Assume that the Content directly follows the MDH in memory.
  kl.load   16(t6), x0            # load rest of PI into the locker
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared means force restart
  andi      t2, t2, 0x38
  beq       t3, t2, handle_errors
  kl.mgmt   KLNL, #kl_cfg_management_end # complete provisioning
                                  # and possibly reconstruct data
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared: must restart
  andi      t2, t2, 0x38
  beq       t3, t2, handle_errors # catches errors at completion (e.g., SKS)
finished:
  kl.setnl  s8                    # restore the caller's value
----

=== Export

*Export Code (`Zklmv`)*
----
  li         t3, 0x30             # to determine Error States
  kl.getnl   s8                   # save the caller's value
  select_locker                   # name the locker for all that follows
  kl.size    s1, KLNL             # TOTAL size to export
  beqz       s1, handle_errors    # 0 means the locker is unconfigured

  {...}  # here code that allocates the buffer to store the exported data

  kl.getmd   s5:s4, KLNL          # get MDH, including its _State_
  srli       t2, s4, 18           # _State_ of that MDH, bits [23:18]
  andi       t2, t2, 0x3f
  beqz       t2, handle_errors    # locker cleared since kl.size
  sd         s4, 0(t6)            # store MDH[63:0] to memory
  sd         s5, 8(t6)            # store MDH[127:64] to memory

  addi       t6, t6, 16           # point to next memory region
  li         s3, 16               # s3 = 16 (size of MDH)
  beq        s1, s3, done         # only the MDH to store (e.g., Error State)

  kl.mgmt    KLNL, #kl_cfg_exporting  # start exporting
  kl.getst   t2, KLNL
  beqz       t2, handle_errors    # locker cleared: the CC is lost
  andi       t2, t2, 0x38
  beq        t3, t2, handle_errors # Error State set meanwhile
  kl.size    t2, KLNL             # size now that the export is open
  bne        t2, s1, handle_errors # ADS changed since the buffer was sized
  addi       s1, s1, -16          # adjust size to remove the MDH
  mv         t4, t6               # destination: first byte after stored MDH
  vsetvli    s6, zero, e8, m1, ta, ma # s6 = VLMAX
store_loop:
  mv         s2, s1
  bleu       s2, s6, 1f
  mv         s2, s6
1:
  vsetvli    s2, s2, e8, m1, ta, ma # AVL <= VLMAX, so vl = AVL, multiple of 16
  kl.mvout   v2                   # move chunk out of the locker,
                                  # advance klstart
  vse8.v     v2, (t4)             # store it
  add        t4, t4, s2           # bump the destination pointer
  sub        s1, s1, s2           # decrement the bytes still to store
  kl.getst   t2, KLNL
  beqz       t2, handle_errors    # locker cleared: the CC is lost
  andi       t2, t2, 0x38
  beq        t3, t2, handle_errors
  bnez       s1, store_loop

finished:
  # Restore _State_ from the saved MDH.
  kl.mgmt    KLNL, #kl_cfg_management_end, s5:s4
  kl.getst   t2, KLNL
  beqz       t2, handle_errors    # locker cleared: the CC is lost
  andi       t2, t2, 0x38
  beq        t3, t2, handle_errors # catches `kl_state_mgmt_auth`
done:
  kl.setnl   s8                   # restore the caller's value
----

[WARNING]
====
Incomplete procedure, like all the others in management.
A locker in an Error State is covered: only its MDH is stored.
A locker under management (partially provisioned, imported or exported) is exported by the same sequence,
but the caller must also save `klstart` before the opening `kl.mgmt`, which clears it, and restore it after the re-import
(<<KLE-state-save-and-restore-order>>); this is not shown.
====

*Export Code (`Zklmem`)*
----
# Up to the size check after the opening kl.mgmt, and from finished on, the
# code is that of the Zklmv version.
  kl.store  0(t6), x0             # store SIV, IMPQUAL, SIV2 and Content
                                  # of the locker (Xl = x0)
  kl.getst  t2, KLNL
  beqz      t2, handle_errors     # locker cleared: the CC is lost
  andi      t2, t2, 0x38
  beq       t3, t2, handle_errors
----

=== Import

*Import Code (`Zklmv`)*
----
  ld         s4, 0(t6)            # load MDH[63:0] from memory
  ld         s5, 8(t6)            # load MDH[127:64] from memory
  li         t3, 0x30             # to determine Error States
  srli       s7, s4, 18           # _State_ of the saved MDH, bits [23:18]
  andi       s7, s7, 0x38         # s7 = 0x30: image of an Error-State locker
  kl.getnl   s8                   # save the caller's value

restart:
  select_locker                   # name the locker (a clear resets it to 32)
  kl.mgmt   KLNL, #kl_cfg_importing, s5:s4    # open locker for import, load MDH
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared means force restart
  andi      t2, t2, 0x38
  bne       t3, t2, 2f            # three top bits of _State_ = 110 ?
  beq       t3, s7, success       # yes, as saved: the short import is complete,
                                  # with this one kl.mgmt and no load
  j         handle_errors         # yes, but new (e.g., invalid Metadata)
2:
  kl.size   s1, KLNL              # size of the image the locker accepts,
                                  # without a dropped ADS
  beqz      s1, restart           # 0: locker cleared since the check
  addi      t4, t6, 16            # first byte after the MDH
  addi      s1, s1, -16           # image size to load, without the MDH

  vsetvli   s6, zero, e8, m1, ta, ma # s6 = VLMAX
vloop:
  mv        s2, s1
  bleu      s2, s6, 1f
  mv        s2, s6
1:
  vsetvli   s2, s2, e8, m1, ta, ma # AVL <= VLMAX, so vl = AVL, multiple of 16
  vle8.v    v2, (t4)              # load a chunk of the SCC
  kl.mvin   v2                    # move it into the locker, advance klstart
  add       t4, t4, s2
  sub       s1, s1, s2
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared means force restart
  andi      t2, t2, 0x38
  beq       t3, t2, handle_errors
  bnez      s1, vloop

  kl.mgmt   KLNL, #kl_cfg_management_end, s5:s4 # decrypt and auth SCC
                                  # and restore _State_ from the saved MDH
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared means force restart
  andi      t2, t2, 0x38
  beq       t3, t2, handle_errors # catches "Authentication Failed"

success:
  kl.setnl  s8                    # restore the caller's value
----

*Import Code (`Zklmem`)*
----
  ld        s4, 0(t6)             # load MDH[63:0] from memory
  ld        s5, 8(t6)             # load MDH[127:64] from memory
  li        t3, 0x30              # to determine Error States
  srli      s7, s4, 18            # _State_ of the saved MDH, bits [23:18]
  andi      s7, s7, 0x38          # s7 = 0x30: image of an Error-State locker
  kl.getnl  s8                    # save the caller's value

restart:
  select_locker                   # name the locker (a clear resets it to 32)
  kl.mgmt   KLNL, #kl_cfg_importing, s5:s4    # open locker for import, load MDH
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared means force restart
  andi      t2, t2, 0x38
  bne       t3, t2, 2f            # three top bits of _State_ = 110 ?
  beq       t3, s7, success       # yes, as saved: the short import is complete
  j         handle_errors         # yes, but new (e.g., invalid Metadata)
2:
  addi      t4, t6, 16            # first byte after the MDH

  kl.load   0(t4), x0             # load rest of SCC into the locker
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared means force restart
  andi      t2, t2, 0x38
  beq       t3, t2, handle_errors
  kl.mgmt   KLNL, #kl_cfg_management_end, s5:s4 # decrypt and auth locker,
                                  # if necessary complete it
  kl.getst  t2, KLNL
  beqz      t2, restart           # locker cleared means force restart
  andi      t2, t2, 0x38
  beq       t3, t2, handle_errors # catches `kl_state_mgmt_auth`

success:
  kl.setnl  s8                    # restore the caller's value
----

During the provisioning and import procedures, the validity of the whole MDH is checked by the opening `kl.mgmt`, which receives it in Form D (<<Zkl-ISA-unpriv.adoc#KLE-MVR-open>>), except for the image of a locker in an Error State, of which only the _State_ is checked (<<Zkl-ISA-unpriv.adoc#KLE-error-state-transfer>>).
The conditions evaluated at completion — SKS resolution at provisioning, authentication at import — can still transition the locker to an Error State upon executing `kl.mgmt KLNL, #kl_cfg_management_end`, which the `kl.getst` after that instruction detects, as it detects a clear or an Error State set at any earlier point.
A data error found by a check that the Machine attaches to a field of the PI or SCC leaves the locker in _Failure_ instead (Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-completion-state>>), which these listings do not test.

[[KLE-ECB-mode-example]]
=== Electronic Codebook Modes (Direct Encryption/Decryption)

The following pseudocode illustrates how to use an ECB CC to encrypt data with a block cipher.
Here, as in most other examples, we assume the block cipher has a width of 128 bits (`KLLEN` is also 128).
The uppercase `IMPORT` instruction is a placeholder for an import code snippet, library, or API call.
Most listings omit the `kl.getst` with which software checks, before it uses an output, that the locker is still in a Valid State (<<KLE-reading-locker-state>>): a usage instruction on a locker that a handler has cleared or invalidated performs no operation and writes zeros.

[[KLE-pseudocode-ECB-encryption]]
.Simple Example: Encryption with no Authentication
----
- Call OS API to get the necessary SCC. Assume X5 points to the SCC.
- Allocate memory for ciphertext buffer.

  vsetivli zero, 4, e32, m1, ta, ma        // Use 128-bit vectors
  IMPORT K0, (X5)                          // Import the SCC into locker K0
  kl.getst X1, K0
  if (48 <= X1 <= 55) then: handle error

  kl.setst K0, #kl_state_encrypt         // Configure locker to encrypt
  kl.getst X1, K0
  if (X1 != kl_state_encrypt) then: handle error

  // assume plaintext in whole blocks
  foreach(i from 0 to len_in_bytes(plaintext)/16-1) do:
    V0 ← plaintext[16*i .. 16*i+15]
    kl.exec V0, K0, V0                   // Encrypt one block of plaintext
    ciphertext[16*i .. 16*i+15] ← V0
----

[[KLE-keystream-modes-example]]
=== CTR/XCTR Keystream Generation

[[KLE-pseudocode-keystream-modes]]
.Encrypt with Keystream Generation
----
// Acquire payload, initialize
- Info: plaintext = *PT
- Process gets a Keystream Generation SCC from an API. X5 = pointer to it.
- Info: X6 = initial counter value.
- Allocate memory for ciphertext buffer CT (if not same as PT).

  vsetivli zero, 4, e32, m1, ta, ma         // Use 128-bit vectors
  IMPORT K0, (X5)

  // The next operations set the nonce and the initial counter
  V1 ← nonce
  kl.setst K0, #kl_state_operate, V1
  kl.setst K0, #kl_state_set_aux_value, X6  // ctr ← bin(X6, j)

  // Compute keystream, use it to encrypt plaintext.  A final partial block
  // still takes a whole keystream block; the caller discards the bytes past
  // the end of PT.
  foreach(i from 0 to ceil(len_in_bytes(PT)/16)-1) do:
    V0 ← PT[16*i .. min(16*i+15, len_in_bytes(PT)-1)]
    kl.exec V1, K0
    V1 ← V1 xor V0
    CT[16*i .. min(16*i+15, len_in_bytes(PT)-1)] ← V1
----

=== XEX/XTS Modes

Only XEX encryption pseudocode is provided; decryption is similar
(here it is also assumed `b` = `KLLEN` = 128).

[[KLE-pseudocode-basic-IV-mode]]
.Pseudocode for XEX encryption
----
// Acquire payload and SCC, initialize
- Info: plaintext = *PT
- Call an API to get the corresponding SCC.  X5 = pointer to it.
- Allocate memory for ciphertext buffer CT (if not same as PT).

  vsetivli zero, 4, e32, m1, ta, ma      // Use 128-bit vectors
  IMPORT K0, (X5)

  V0 ← tweak
  kl.setst K0, #kl_state_encrypt, V0 // Configure locker to encrypt, set tweak

  foreach(i from 0 to floor(len_in_bytes(PT)/16)-1) do:
    V0 ← PT[16*i .. 16*i+15]

    CT[16*i .. 16*i+15] ← V0

The loop covers whole blocks only: XEX has no partial-block state.

[[KLE-GCM-mode-examples]]
=== GCM Mode

In <<KLE-pseudocode-GCM-encryption>> we show pseudocode for GCM encryption, again with
`b` = `KLLEN` = 128 and `c` = 32.

Associated data and plaintext/ciphertext are treated differently, as <<Zkl-ISA-machines.adoc#KLE-GCM-mode>> requires.
The caller zero-fills the final block of the AD beyond its actual end, and `GHASH` absorbs that block whole.
For the PT and CT the caller must not rely on zero-padding: a final block shorter than `b` goes through State _Enc_Last_Block_ (or _Dec_Last_Block_ for decryption), so that no keystream bit past the end of the message is absorbed into `GHASH` or written out.
The Machine takes the PT and the CT in whole bytes (each last-block `Xs` is a multiple of 8). These listings also take the AD in whole bytes, so `len_in_bits` is always 8 times a byte count.

[[KLE-pseudocode-GCM-encryption]]
.GCM Encryption
----
// Acquire payload, initialize
- Info: authenticated data = *AD, plaintext = *PT
- Process gets a GCM encryption CC from an API.  X5 = pointer to the CC.
- Allocate memory for ciphertext buffer CT (if not same as PT).

  vsetivli zero, 4, e32, m1, ta, ma         // Use 128-bit vectors
  IMPORT K0, (X5)               // Import (also computes the derived Auth Key)

  // Set the IV.  The Form B kl.setst carries its length in bits; the IV
  // itself is then absorbed by kl.exec.  This example assumes that the IV fits
  // in V0; a longer one is supplied by several kl.exec, each a multiple of
  // 16 bytes except the last.  When the last byte has been absorbed the
  // Machine computes J0 and moves to _Hash_Absorb_ by itself, so no kl.setst
  // is issued for that transition.

  X1 ← len_in_bits(IV)

  kl.setst K0, #kl_state_set_aux_value, X1
  X2 ← X1/8                                // len_in_bytes(IV)
  vsetvli  zero, X2, e8, m1, ta, ma        // KLLEN = 8*len_in_bytes(IV)
  V0 ← IV
  kl.exec K0, V0
  vsetivli zero, 4, e32, m1, ta, ma        // back to 128-bit vectors

  // Compute the AD contribution to the tag.
  // The caller has zero-filled the last block beyond the end of the AD.
  foreach(i from 0 to ceil(len_in_bytes(AD)/16)-1) do:
    V0 ← AD[16*i .. 16*i+15]
    kl.exec K0, V0                       // Absorb it into GHASH

  // Encrypt the whole blocks of the plaintext
  kl.setst K0, #kl_state_encrypt
  PT_fullblocks ← floor(len_in_bits(PT)/128)

  foreach(i from 0 to PT_fullblocks-1) do:
    V0 ← PT[16*i .. 16*i+15]
    kl.exec V1, K0, V0
    CT[16*i .. 16*i+15] ← V1

  // Fractional final block, if any. The plaintext is not zero-padded here.
  X1 ← len_in_bits(PT) mod 128
  if (X1 != 0) then:
    kl.setst K0, #kl_state_enc_last_block, X1
    V0 ← PT[16*PT_fullblocks .. 16*PT_fullblocks+ceil(X1/8)-1]
    kl.exec V1, K0, V0
    CT[16*PT_fullblocks .. 16*PT_fullblocks+ceil(X1/8)-1] ← V1

  // Absorb the lengths, finalize the tag, and read it out
  V1 ← bswap(bin(len_in_bits(PT), 64)) @ bswap(bin(len_in_bits(AD), 64))
  kl.setst K0, #kl_state_enc_tag_finalize, V1
  kl.exec V2, K0                          // V2 contains the tag
----

<<KLE-pseudocode-GCM-decryption>> gives the code for GCM decryption, from the point where the AD has been absorbed; up to there, the code is that of <<KLE-pseudocode-GCM-encryption>>.
// Decryption differs from encryption in three ways: the roles of `PT` and `CT` are
// reversed; States _Encrypt_ and _Enc_Last_Block_ are replaced by _Decrypt_ and
// _Dec_Last_Block_; and the tag is finalized and verified instead of being emitted, as shown
// below.
Note that no `kl.exec` is issued in State _Dec_Tag_Finalize_: the recomputed tag
stays inside the locker and is never made available to software on this path.

[[KLE-pseudocode-GCM-decryption]]
.GCM Decryption
----
  // Decrypt the whole blocks of the ciphertext
  kl.setst K0, #kl_state_decrypt
  CT_fullblocks ← floor(len_in_bits(CT)/128)
  foreach(i from 0 to CT_fullblocks-1) do:
    V0 ← CT[16*i .. 16*i+15]
    kl.exec V1, K0, V0
    PT[16*i .. 16*i+15] ← V1

  // Fractional final block, if any.  The ciphertext is not zero-padded here.
  X1 ← len_in_bits(CT) mod 128
  if (X1 != 0) then:
    kl.setst K0, #kl_state_dec_last_block, X1
    V0 ← CT[16*CT_fullblocks .. 16*CT_fullblocks+ceil(X1/8)-1]
    kl.exec V1, K0, V0
    PT[16*CT_fullblocks .. 16*CT_fullblocks+ceil(X1/8)-1] ← V1

  // Absorb the lengths.  The tag is computed and retained inside the locker.
  V1 ← bswap(bin(len_in_bits(CT), 64)) @ bswap(bin(len_in_bits(AD), 64))
  kl.setst K0, #kl_state_dec_tag_finalize, V1

  // Supply the received tag; the comparison sets _Success_ or _Failure_
  V1 ← tag_from_payload
  kl.setst K0, #kl_state_hash_verify, V1
  kl.getst X1, K0
  if (X1 != kl_state_success) then:
     handle error     // Do not use the plaintext in case of error
----

//

We also show how to implement GCM encryption using an ECB CC, provided the vector ISA
supports carry-less binary multiplication.  However, under the threat model that prompted
the KLE design, this risks exposing the hashing key, which may lead to forgeries,
even though confidentiality would not be compromised.

[[KLE-pseudocode-GCM-encryption-alternate]]
.Implementing GCM encryption using an ECB CC
----
// Acquire payload, initialize
- Info: authenticated data = *AD, plaintext = *PT
- Process gets an ECB encryption CC from an API.  X5 = pointer to the CC.
- Allocate memory for ciphertext buffer CT (if not same as PT).

  vsetivli zero, 4, e32, m1, ta, ma
  IMPORT K0, (X5)
  kl.setst K0, #kl_state_encrypt      // kl.exec encrypts only in _Encrypt_
  V0[95:0] ← IV                       // 96-bit IV in bytes 0..11
  V3 ← zeros(b)                       // "Auth Data 1"
  kl.exec V4, K0, V3                  // compute H

  // The caller has zero-filled the last block beyond the end of the AD.
  foreach(i from 0 to ceil(len_in_bytes(AD)/16)-1) do:
    V1 ← AD[16*i .. 16*i+15]
    V3 ← V3 xor V1
    V3 ← Galoismul(V4, V3)

  // Counter = 1 is used for E(K,J0), which is the tag mask: in this 96-bit
  // nonce version, the counter for the text starts at 2.

  counter ← 2
  PT_fullblocks ← floor(len_in_bytes(PT)/16)
  foreach(i from 0 to PT_fullblocks-1) do:
    V5 ← bswap(bin(counter,32)) @ V0[95:0]
    V1 ← PT[16*i .. 16*i+15]
    kl.exec V2, K0, V5                // create mask by encrypting the counter
    V1 ← V1 xor V2                    // CTR encrypt
    V3 ← V3 xor V1
    V3 ← Galoismul(V4, V3)
    CT[16*i .. 16*i+15] ← V1
    counter ← counter + 1

  // Fractional final block of r bytes, if any.  The ciphertext is truncated
  // to r bytes before it is absorbed and stored: GHASH absorbs the
  // zero-padded ciphertext, which is what SP 800-38D specifies.
  r ← len_in_bytes(PT) mod 16
  if (r != 0) then:
    V5 ← bswap(bin(counter,32)) @ V0[95:0]
    V1 ← PT[16*PT_fullblocks .. 16*PT_fullblocks+r-1]
    kl.exec V2, K0, V5
    V1 ← V1 xor V2
    V1 ← zeros(128-8*r) @ V1[8*r-1:0] // discard the keystream past the end
    V3 ← V3 xor V1
    V3 ← Galoismul(V4, V3)
    CT[16*PT_fullblocks .. 16*PT_fullblocks+r-1] ← V1

  V3 ← V3 xor (bswap(bin(len_in_bits(PT),64)) @ bswap(bin(len_in_bits(AD),64)))
  V3 ← Galoismul(V4, V3)
  V5 ← bswap(bin(1,32)) @ V0[95:0]    // J0 (counter 1), for the tag mask
  kl.exec V2, K0, V5
  tag ← V3 xor V2
----

[[KLE-GCM-SIV-mode-examples]]
=== GCM-SIV Mode

We show in <<KLE-pseudocode-GCM-SIV-encryption>> how to perform AEAD encryption with a GCM-SIV CC (with `b` = `KLLEN` = 128), for AD and plaintext in whole bytes, as the Machine requires.
<<KLE-pseudocode-GCM-SIV-decryption>> is the corresponding pseudocode for decryption.

[[KLE-pseudocode-GCM-SIV-encryption]]
.GCM-SIV Encryption
----
// Acquire payload, initialize
- Info: authenticated data = *AD
- Info: plaintext = *PT
- Call API to get the key from a key management applet or HW block.
- The API returns the SCC. Assume X5 is the pointer to it.
- Allocate memory for ciphertext buffer CT (if not same as PT).

  vsetivli zero, 4, e32, m1, ta, ma   // Use 128-bit vectors
  IMPORT K0, (X5)

  // Set the nonce, which also derives enc_key and auth_key.
  // Form C kl.setst: the nonce is the vector input of kl.setst.
  //  No kl.exec is issued in this state.

  V0 ← nonce
  kl.setst K0, #kl_state_set_aux_value, V0

  // Absorb the AD and then the plaintext into POLYVAL.
  // The caller has zero-padded the last block of each.

  kl.setst K0, #kl_state_hash_absorb
  foreach(i from 0 to ceil(len_in_bytes(AD)/16)-1) do:
    V0 ← AD[16*i .. 16*i+15]             // Load a block of associated data
    kl.exec K0, V0                       // Absorb it into POLYVAL

  foreach(i from 0 to ceil(len_in_bytes(PT)/16)-1) do:
    V0 ← PT[16*i .. 16*i+15]             // Load a block of plaintext
    kl.exec K0, V0                       // Absorb it into POLYVAL

  // Finalize the SIV.  The lengths are the *input* of a Form A kl.exec in
  // State _Enc_Tag_Finalize_, and the SIV is its output; they are not
  // absorbed by a further kl.exec in _Hash_Absorb_.
  kl.setst K0, #kl_state_enc_tag_finalize
  V0 ← bin(len_in_bits(PT), 64) @ bin(len_in_bits(AD), 64)
  kl.exec V2, K0, V0
  tag ← V2

  // Second pass: encrypt the whole blocks of the plaintext, with the SIV
  // as IV. The kl.exec above has already moved the locker to _Encrypt_;
  // a kl.setst naming _Encrypt_ would invalidate it.
  PT_fullblocks ← floor(len_in_bits(PT)/128)

  foreach(i from 0 to PT_fullblocks-1) do:
    V0 ← PT[16*i .. 16*i+15]             // Load a block of plaintext
    kl.exec V1, K0, V0                   // Encrypt the block
    CT[16*i .. 16*i+15] ← V1             // Store a block of ciphertext

  // Fractional final block, if any.  Unlike in the first pass, it must not
  // go through as a zero-padded whole block: _Enc_Last_Block_ writes no
  // keystream bit past the end of PT to CT.
  X1 ← len_in_bits(PT) mod 128
  if (X1 != 0) then:
    kl.setst K0, #kl_state_enc_last_block, X1
    V0 ← PT[16*PT_fullblocks .. 16*PT_fullblocks+ceil(X1/8)-1]
    kl.exec V1, K0, V0
    CT[16*PT_fullblocks .. 16*PT_fullblocks+ceil(X1/8)-1] ← V1
----

[[KLE-pseudocode-GCM-SIV-decryption]]
.GCM-SIV Decryption
----
// Acquire payload, initialize
- Info: authenticated data = *AD
- Info: ciphertext = *CT
- Call an API to get the corresponding key from a key management entity.
- The API returns the SCC. Assume X5 is the pointer to it.
- Allocate memory for plaintext buffer PT (if not same as CT).

  vsetivli zero, 4, e32, m1, ta, ma      // Use 128-bit vectors
  IMPORT K0, (X5)

  // Set the nonce
  V0 ← nonce
  kl.setst K0, #kl_state_set_aux_value, V0

  // Set the received SIV, which serves as the IV of the decryption.
  V0 ← SIV
  kl.setst K0, #kl_state_set_aux_value_2, V0

  // Absorb the AD.  The caller has zero-padded the last block.
  kl.setst K0, #kl_state_hash_absorb
  foreach(i from 0 to ceil(len_in_bytes(AD)/16)-1) do:
    V0 ← AD[16*i .. 16*i+15]
    kl.exec K0, V0                       // Absorb it into POLYVAL

  // Decrypt the whole blocks; each recovered block is absorbed into POLYVAL
  kl.setst K0, #kl_state_decrypt
  CT_fullblocks ← floor(len_in_bits(CT)/128)
  foreach(i from 0 to CT_fullblocks-1) do:
    V0 ← CT[16*i .. 16*i+15]
    kl.exec V1, K0, V0
    PT[16*i .. 16*i+15] ← V1

  // Fractional final block, if any
  X1 ← len_in_bits(CT) mod 128
  if (X1 != 0) then:
    kl.setst K0, #kl_state_dec_last_block, X1
    V0 ← CT[16*CT_fullblocks .. 16*CT_fullblocks+ceil(X1/8)-1]
    kl.exec V1, K0, V0
    PT[16*CT_fullblocks .. 16*CT_fullblocks+ceil(X1/8)-1] ← V1

  // Absorb the lengths and verify, with a Form B kl.exec: the recomputed
  // SIV is compared internally against the one supplied above
  kl.setst K0, #kl_state_dec_tag_finalize
  V0 ← bin(len_in_bits(PT), 64) @ bin(len_in_bits(AD), 64)
  kl.exec K0, V0
  kl.getst X1, K0
  if (X1 != kl_state_success) then:
    handle error     // Do not use the plaintext if error
----

[[KLE-OCB-mode-examples]]
=== OCB Mode

In this section we show pseudocode for OCB encryption and decryption (`b` = `KLLEN` = 128).

[[KLE-pseudocode-OCB-encryption]]
.OCB Encryption
----
// Acquire payload, initialize
- Info:
- authenticated data = *AD with bit length AD_len, a multiple of 8
- plaintext = *PT with bit length PT_len, a multiple of 8
- nonce N with bit length N_len
- tag length tag_len

- Process gets an OCB encryption CC from an API.  X5 = pointer to the CC.
- Allocate memory for ciphertext buffer CT (if not same as PT).

  vsetivli zero,4,e32,m1,ta,ma              // Use 128-bit vectors
  IMPORT K0, (X5)

  // The next operations set the nonce
  X1 ← N_len
  kl.setst K0, #kl_state_set_aux_value, X1
  V0 ← N
  kl.exec K0, V0

  // The next state change also sets the tag length
  X1 ← tag_len
  kl.setst K0, #kl_state_hash_absorb, X1

  AD_fullblocks ← floor(AD_len/128)
  PT_fullblocks ← floor(PT_len/128)

  // Compute AD contribution to tag
  foreach(i from 0 to AD_fullblocks-1) do:
    V0 ← AD[16*i .. 16*i+15]
    kl.exec K0, V0                       // Absorb it into hash

  X1 ← AD_len mod 128                    // Can be zero
  kl.setst K0, #kl_state_hash_last_block, X1

  if (X1 != 0) then:
    V0 ← AD[AD_fullblocks*16 .. AD_fullblocks*16+ceil(X1/8)-1]
    kl.exec K0, V0                       // Absorb the last AD block

  // Encrypt plaintext and continue computation of tag
  kl.setst K0, #kl_state_encrypt
  foreach(i from 0 to PT_fullblocks-1) do:
    V0 ← PT[16*i .. 16*i+15]
    kl.exec V1, K0, V0
    CT[16*i .. 16*i+15] ← V1

  X1 ← PT_len mod 128                    // Can be zero
  kl.setst K0, #kl_state_enc_last_block, X1

  if (X1 != 0) then:
    V0 ← PT[PT_fullblocks*16 .. PT_fullblocks*16+ceil(X1/8)-1]
    kl.exec V1, K0, V0              // Encrypt it and absorb it into the tag
    CT[PT_fullblocks*16 .. PT_fullblocks*16+ceil(X1/8)-1] ← V1
  else:
    kl.exec K0                           // Form D: finalize the tag only

  // _Enc_Last_Block_ transitions to _Enc_Tag_Finalize_ on its own, so no
  // kl.setst is issued here.
  kl.exec V1, K0                         // output tag
----

OCB decryption follows <<KLE-pseudocode-OCB-encryption>> up to the final block, with the roles of `PT` and `CT` exchanged, and States _Decrypt_ and _Dec_Last_Block_ in place of _Encrypt_ and _Enc_Last_Block_;
<<KLE-pseudocode-OCB-decryption-difference>> gives only the last step, which differs.
OCB has no _Dec_Tag_Finalize_ state: after the last block, _Dec_Last_Block_ transitions directly to
_Hash_Verify_, where a Form B `kl.exec` supplies the received tag, as shown below.

[[KLE-pseudocode-OCB-decryption-difference]]
.OCB Decryption
----
  V1 ← tag                               // the tag received with the message
  kl.exec K0, V1                         // Form B: compares it with checksum_P
  kl.getst X1, K0
  if (X1 != kl_state_success) then:      // do not use the plaintext if error
     handle error
----

[[KLE-CMAC-mode-example]]
=== CMAC Functions

[[KLE-pseudocode-CMAC]]
.CMAC Computation
----
- Info: CMAC input = *M with bit length M_len, a multiple of 8
- Process gets a CMAC CC from an API. Assume X5 is the pointer to the CC.

  vsetivli zero, 4, e32, m1, ta, ma      // Use 128-bit vectors
  IMPORT K0, (X5)

  kl.setst K0, #kl_state_hash_absorb
  blocks    ← floor(M_len/128)
  remainder ← M_len mod 128
  if (remainder = 0 and blocks > 0) then: // a whole number of full blocks:
    blocks    ← blocks - 1               // the last one is the "last block"
    remainder ← 128                  // a full last block takes no 10* padding

  foreach(i from 0 to blocks-1) do:
    V0 ← M[16*i .. 16*i+15]
    kl.exec K0, V0

  X1 ← remainder
  kl.setst K0, #kl_state_hash_last_block, X1
                                         // with X1 = 0 (empty message),
                                         // the padded block is absorbed here
  if (remainder != 0) then:
    V0 ← M[16*blocks .. 16*blocks+ceil(remainder/8)-1]
    kl.exec K0, V0                       // absorbs the last block

  kl.setst K0, #kl_state_hash_output
  kl.exec V0, K0                         // this is the CMAC value
----

To verify a CMAC `T` of `T_len` bits instead, the last two instructions are replaced by:

[[KLE-pseudocode-CMAC-verify]]
.CMAC Verification
----
  X1 ← T_len                             // a multiple of 8, at least 64
  kl.setst K0, #kl_state_hash_verify, X1
  V0 ← T
  kl.exec K0, V0                         // compares the first T_len bits
  kl.getst X2, K0                        // _Success_ if T matches,
                                         // _Failure_ otherwise
----

[[KLE-hash-example]]
=== Hash Functions, MACs and XOFs

The following sequence hashes a message with any Machine of
<<Zkl-ISA-machines.adoc#KLE-hash-functions-MACs-XOFs>>: only the SCC, and the number
`out_bytes` of output bytes, differ.
The caller passes the message unpadded; the `kl.setst` into _Hash_Output_ pads it.
The final piece of `M_bits` mod 64 bits fits every Machine, whose `b` is at least 64; it
must be a whole number of bytes for BLAKE2. For SHA-2 and SM3 its partial last byte holds
the final bits in its most significant positions, for SHA-3, KMAC and Ascon in its least
significant ones, and for HMAC as for its `H`, each as its standard orders bits.
`X1` = 8 {times} `out_bytes` makes the Machine emit exactly `out_bytes` bytes and then enter
_Success_; for KMAC128 and KMAC256 it is also the output length `L` that the MAC encodes,
while KMACXOF128 and KMACXOF256 encode `L` = 0 and only stop after `out_bytes` bytes.
`out_bytes` is at least 1, at least 8 for HMAC, and at least 4 for KMAC128 and KMAC256; it is at most the digest length for a fixed-output Machine, and below 2^29^ for an XOF, KMAC128 or KMAC256.
`X1` = 0 would instead ask for the full digest, or for an unbounded XOF; it is invalid for KMAC128 and KMAC256.
Except for KMAC128 and KMAC256, `out_bytes` only truncates the output of the Machine: a BLAKE2 digest of `nn` bytes other
than `nn~max~`, such as BLAKE2b-256, comes from an SCC whose `nn` was set by the _Set_Aux_Value_
operation of <<Zkl-ISA-machines.adoc#KLE-BLAKE2>> or by a system-specific import, since `nn` enters the IV.
An SCC with `kk` {ne} 0 and no system key is keyed by the caller: `M` then starts with the key,
zero-padded to `b` bits (cite:[RFC7693] {sect}3.3), which alone forms the message for an
empty `M`; a system key needs no such block.
An SCC of the NIK variant of <<Zkl-ISA-machines.adoc#KLE-HMAC>> must already hold its key.
The SCC of HMAC, KMAC128 or KMAC256, and that of BLAKE2 with a system key, must enable
_Hash_Output_ (_MachinePolicy_[0]); for the MAC verification below, that of HMAC,
KMAC128 or KMAC256 must enable _Hash_Verify_ (_MachinePolicy_[1]) instead.
The SCC is in _Ready_; an SCC exported in _Hash_Absorb_ after a prefix of the message, as
in the NOTE of <<Zkl-ISA-machines.adoc#KLE-Ascon-Hash256>>, takes no first `kl.setst`, and
`M` is then the rest of the message.

[[KLE-pseudocode-hash]]
.Hashing a Message
----
- Info: message = *M of M_bits bits; out_bytes bytes of output wanted.
- Process gets the SCC of any hash, MAC or XOF from an API. X5 = pointer.

  IMPORT K0, (X5)
  kl.setst K0, #kl_state_hash_absorb

  r ← M_bits mod 64                      // the final piece, 0 to 63 bits
  h ← (M_bits - r)/8                     // the bytes before it
  foreach(i from 0 to ceil(h/16)-1) do:
    n ← min(16, h - 16*i)                // the last chunk may be shorter
    vsetvli zero, n, e8, m1, ta, ma      // KLLEN = 8n
    V0 ← M[16*i .. 16*i+n-1]
    kl.exec K0, V0                       // absorbs n bytes, unpadded

  X1 ← r
  kl.setst K0, #kl_state_hash_last_block, X1  // r = 0: does nothing
  if (r != 0) then:
    n ← ceil(r/8)
    vsetvli zero, n, e8, m1, ta, ma
    V0 ← M[h .. h+n-1]
    kl.exec K0, V0                       // absorbs the final r bits

  X1 ← 8*out_bytes
  kl.setst K0, #kl_state_hash_output, X1 // ends the message: Machine pads

  foreach(j from 0 to ceil(out_bytes/16)-1) do:
    n ← min(16, out_bytes - 16*j)
    vsetvli zero, n, e8, m1, ta, ma
    kl.exec V0, K0                       // emits the next n bytes
    OUT[16*j .. 16*j+n-1] ← V0
  kl.getst X2, K0                        // _Success_
----

To verify a MAC `T` of `T_len` bits with HMAC, KMAC128 or KMAC256 instead, the
instructions from the
`kl.setst` into _Hash_Output_ on are replaced by the listing below.
The listing takes `T_len` at most `t` for HMAC and at most `b` for KMAC128 and KMAC256.
HMAC also admits a longer `T`, but compares only its first `t` bits; KMAC128 and KMAC256 do not admit one.
With 128-bit vectors, LMUL = 8 holds a tag of up to 1024 bits: every HMAC tag, and a KMAC
tag up to that length.

[[KLE-pseudocode-hash-verify]]
.MAC Verification
----
  X1 ← T_len                             // multiple of 8, >= 64 (KMAC: 32)
  kl.setst K0, #kl_state_hash_verify, X1
  vsetvli zero, T_len/8, e8, m8, ta, ma  // KLLEN = T_len
  V0 ← T
  kl.exec K0, V0                         // compares the first T_len bits
  kl.getst X2, K0                        // _Success_ if T matches,
                                         // _Failure_ otherwise
----

With Ascon-CXOF128 and a customization string `Z` of `Z_bits` bits, the first `kl.setst`
is replaced by:

[[KLE-pseudocode-cxof-customization]]
.Ascon-CXOF128 Customization
----
  X1 ← Z_bits                            // 0 to 2048
  kl.setst K0, #kl_state_set_aux_value, X1  // absorbs bin(Z_bits, 64)
  // the ceil(Z_bits/8) bytes of Z, in kl.exec of up to 16 bytes, as for M
  kl.setst K0, #kl_state_hash_absorb     // pads Z; M follows as above
----
