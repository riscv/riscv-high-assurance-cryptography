This introduction to the _Cryptographic Lockers Extension_ (KLE), formerly the _Atomic Cryptography Extension_ (ACE),
is not part of the specification and, in particular, is not normative.
When KLE is ratified, parts of this introduction, for instance the Threat Model, may be incorporated into the specification.
Expect repetitions of material written here in various places of the specification: It is not a mistake.

The ratification plan is
https://riscv.atlassian.net/wiki/spaces/HACX/pages/484966423/High+Assurance+Crypto+Ratification+Plan[here].

== Features

KLE lets software perform high-performance cryptographic operations without giving it direct access to the keys or to other critical derived value.
The use cases that motivated its development include content protection (including both media and local LLM decryption), link and storage encryption, secure boot, and attestation.

We now list the main features of KLE:

* *Atomic operations.* Each cryptographic operation is atomic, so keys cannot be recovered from data before and after processing
obtained through memory read exploits.
//  An instruction can be interrupted only between operations, if it performs multiple cryptographic operations in a single call,
//  or at the points an algorithm defines for its long-running operations.
//+
//_Rationale for atomic operations._
//  If the primitive is secure, its key cannot be recovered from the inputs and outputs of the complete operation. ISAs that take the key between rounds or MAC stages would not have this property, even if the key came from a hidden register. For instance, an attacker with access to an instruction computing only 4 or 5 rounds of AES can efficiently recover the key cite:[Rijndael-revised]. Hence, even splitting the AES, say, into two calls (for AES-128) or three (for AES-192 and AES-256) is not an option if the goal is preventing exposure of the key.

* *Cryptographic Lockers* are architectural containers that hide their secrets from software.
They contain Content consisting of the keys and other state information, and Metadata that binds the Content to algorithms, and optionally to usage policies, hardware and software environments, and an expiration date.
Software _provisions_ (writes) Content and Metadata into a locker to bind them into a *Cryptographic Context*.
KLE instructions reference lockers instead of key values, and they must respect a strict set of rules governing their management:
they cannot reveal keys and other critical values.
The cryptographic context in a locker an be exported using an authenticated encryption algorithm to memory and reimported into a locker.



* *A single interface for many primitives*, instead of separate instructions per primitive:
 ** Primitives alone do not suffice for modes such as AES-GCM-SIV, XTS, and OCB, where leaked derived keys or intermediate values compromise security. KLE therefore also defines modes of operation, among them CTR, GCM, and CMAC, and secure key derivation.
 ** Encrypt-only and decrypt-only versions reduce misuse, and versions with a preset IV or nonce keep it confidential.
 The modes work with AES-128, -192, -256, and other block ciphers such as SM4.
 ** The interface also supports hash functions, public-key and post-quantum algorithms, and SCA-resistant implementations.
 ** When side-channel protected implementations of cryptographic operations are available, they are simply variants of the standard algorithms, and they can be used in place of the latter without changes to the code.
 ** Implementations need not support every algorithm and variant thereof: following RISC-V practice, KLE defines subextensions; `Zkl` requires a baseline set of algorithms (<<Zkl-ISA-unpriv.adoc#KLE-extensions-overview-unpriv>>) and leaves the others to the RISC-V profiles.

* *Scalability.* One ISA and ABI serve embedded to server cores, and KLE supports persistence, sleep, hibernation, and VM migration.

[[KLE-introduction-non-features]]
== Non-Goals

KLE intentionally does not provide the following features.

* **Variable-length inputs:** plaintexts, ciphertexts, and hash inputs are processed in fixed-size blocks.

* **Full key management:** KLE provides only building blocks; the key-management logic resides in trusted software, such as TEE applets. External schemes do not provision keys directly: a local trusted software or hardware component obtains keys and policies and configures the CCs.

* **Key revocation**, because:

. it would cost significant implementation effort and performance, against KLE's goals of simplicity and speed;
. a universal mechanism is impractical: protocols are numerous, revocation data may be unbounded, and the KLE unit would need dynamic access to secure memory, whereas isolated software components can provide revocation with strong guarantees;
. revocation applies mainly to root keys, which the trusted entity managing them can revoke, while expiration dates and _Localities_ limit the lifetime and scope of derived keys; and
. applications that access root keys directly, such as link or storage encryption, usually run in protected environments with their own revocation mechanisms.

* **Full prevention of misuse by compromised processes:** a compromised process keeps access to its own CCs, so KLE complements, but does not replace, vulnerability mitigations and process isolation. Modes that use one operation for both encryption and decryption, such as counter mode, remain open to such abuse.

[[KLE-threat-model]]
== Threat Model

**Assets** are _keys_ and any information that helps an adversary recover plaintext or forge ciphertexts or MACs, such as the masks of tweakable XEX modes and the derived keys of AES-GCM-SIV.
Their _confidentiality_ and _integrity_ are protected; their _availability_ is not an architectural goal, but the _availability of resources_ is: a caller can always configure a locker, and the KLE unit never evicts a CC on its own.

**Adversaries** can compromise processes through software vulnerabilities, and can access memory, for example by abusing hardware interfaces or interposing between the SoC and memory. Sophisticated hardware attacks, such as tampering with a focused ion beam or scanning electron microscope (FIB/SEM), are excluded.
// Every implementation is free of timing leakage (Level A of <<Zkl-ISA-unpriv.adoc#KLE-SCProtection-field>>); protection against other side-channel analysis (SCA), Levels B and C, is optional, and KLE provides interfaces to implementations with and without it.
//
// Where it can, KLE neither accepts risks nor removes useful features. It _controls_ threats through its own mechanisms and _transfers_ the residual risk, key extraction, to the privileged or trusted software and hardware that manage keys. Trusted software can use control-flow integrity, memory encryption with integrity protection, and anti-replay mechanisms; hardware key-management blocks can be hardened.

Direct plaintext leakage, memory-corruption attacks against the process using KLE, and Release of Unverified Plaintext (RUP) attacks are _accepted_: the processed data resides in the user's execution context, where KLE cannot protect it.

[[KLE-open-points]]
== Discussion Points

These items are neither known defects nor a measure of the specification's maturity. They fall into two groups.

Group A — items requiring closure by the RISC-V Architecture Review Committee (ARC).::

. *Opcode allocation.* The encodings are provisional, and the final allocation is the ARC's responsibility.
  The _core instructions_ use the MISC-MEM opcode, which currently has several unused `funct3` values; similar gaps elsewhere
  would serve as well. The _memory instructions_ are harder, since their offsets take all remaining bits once `opcode`,
  `funct3`, and source and destination registers are fixed: `kl.input` uses the only unused `funct3` value of LOAD, 0x7, and `kl.output` the value 0x5 of STORE;
  these instructions are encoded together with `kl.load` and `kl.store`, respectively.
+
`kl.size`, `kl.avail`, `kl.getmd*`, `kl.restrict*`, and `kl.clone` could move encoding bits [29:25] to [24:20] and fix
bits [29:25] to zero, freeing significant space in `funct7`.

. *`misa.L` and `mstatus[26:25]` (KLS).* Provisional and contested. `misa.L` may give way to another mechanism, such as
  Unified Discovery, and KLS may move to another offset or register, or to a mechanism other than a `*status`
  context-status field; the same holds for the corresponding bits of `sstatus` and `vsstatus`. The specification depends
  only on a two-bit context-status field with the semantics of <<Zkl-ISA-priv.adoc#KLE-aces-encoding>>, analogous to
  `FS` and `VS`.

. *`mstatus`[27] (`kleemulation`).* The bit that makes `kl.avail` and `kl.size` of Form B or C trap on a Machine, or a
  combination of its MDH fields, that the KLE unit does not implement natively, so that M-mode can emulate it (<<Zkl-ISA-priv.adoc#KLE-kleemulation>>), is placed in
  `mstatus` only provisionally. The ARC needs to relocate it to a position that is actually available, in `mstatus` or in another M-mode CSR.

. *KLE CSR addresses.* All addresses are placeholders, to be assigned by
  the ARC, as is the `Smstateen` bit of <<Zkl-ISA-priv.adoc#KLE-privileged-CSRs>>.

. *Exception cause codes.* The ARC must allocate `mcause` values: individual causes, or a single
  KLE cause with a subcause register. Some form of reporting "`mtval`" the locker number is also
  needed; it would spare handlers from decoding locker references, `KLNL` included.
.. *specific* `*mtval*` *or KLE Emulation Trap.* Currently we are using the illegal-instruction exception for the purpose of
  trap-and-emulate. It would be a good idea to define a new exception type for this purpose, especially
  since we are currently _not_ delegating emulation to any mode below M. Or getting a special `mtval`
  for the purpose.
  With `kleemulation`, the illegal-instruction exception must also stay undelegated (<<Zkl-ISA-priv.adoc#KLE-kleemulation>>); a dedicated cause would remove that constraint.

. *KLV scope.* <<Zkl-ISA-unpriv.adoc#KLE-KLV>> defines the vector subset KLE requires, which we consider complete.
  These questions do not block candidacy but need ARC feedback:

  .. Should KLV vector instructions be gated by `*status.VS` or by another mechanism?
  .. How should KLV be discovered?
  .. How to define `kl.exec` element widths? `EGW`/`SEW` cannot represent sizes that are not powers of two; one
     option is to allow any power of two that divides the size, with `EGW`/`SEW` and the `vstart` increment
     defined per iteration.

. *Discoverability of cipher/mode combinations.*
  We propose that software discover Machines with the `kl.avail` instruction rather than by extension names, since subextensions could proliferate beyond manageability.
  <<Zkl-ISA-machines.adoc#KLE-exec-encodings>> nonetheless lists suggested extension names, formed by concatenating `Zkl`, the primitive name ending in `p`, and the mode name ending in `m` (e.g., `Zklaes192p` and `Zklaes192pgcmm`).

//. *Cross-hart CSR access.* Is there, or should there be, an architected way for M-mode on one hart to read or configure
//  another hart's CSRs? <<Zkl-ISA-unpriv.adoc#KLE-CSK-requirements>> and <<Zkl-ISA-priv.adoc#KLE-CSR-mklcsk>> could
//  then use it instead of platform-specific channels.

Group B — open design questions owned by this task group.::

//. *`kl.mgmt` interruptibility.* `kl.mgmt` can run relatively long, though much less than an ECC scalar multiplication or a
//  signature verification. It is uninterruptible because preempting and resuming it may open new attack vectors: an
//  interrupted encryption or decryption leaves a locker with both encrypted and unencrypted content, and unencrypted
//  content cannot be exported as such. A precise interruption seems secure only if the KLE unit works on an internal copy.

. *Nonces for SCC export and import.* An RFC 8452 nonce costs six AES-256 encryptions per export or import, whereas the
  current design recomputes the derived keys only when the CSK changes. A competing architecture also omits nonces from
  key export and import, probably for the same reason. We welcome input on this choice.
// One alternative is to encrypt `nonce @ constant1` and `nonce @ constant2` under the _derived encryption key_, producing `A` and `B`. The algorithms could then use `enc_key xor (B @ A)` and `auth_key xor B xor A` instead of `enc_key` and `auth_key`. This construction is non-standard, but it is secure and faster: it requires only two additional AES-256 encryptions.

. *Additional inputs for random key generation.* KDFs with arbitrary inputs and unlimited outputs could easily be defined
  as Machines that feed a locker's key field through `kl.derive`. Should standard KDFs be defined?

. *`SCC_Encrypt` security claim.* Substantiate the claim “secure for up to 2^64^ 128-bit blocks.”

. *Emulated Machines.* TODO: define how software discovers which instructions and Machines are emulated, and decide
  whether an emulated Machine may override a natively implemented one with a fixed emulated version
  (<<Zkl-ISA-priv.adoc#KLE-kleemulation>>).

. *Memory-instruction check order.* Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-management-check-order>> makes the address-misaligned check of `kl.load` and `kl.store` a locker-state-independent check, so a misaligned address traps even on an inert locker.
  Hardware implementers should confirm that this order is practical, and that M-mode trap-and-emulate (<<Zkl-ISA-priv.adoc#KLE-kleemulation>>) can reproduce it.
