This introduction to the _Cryptographic Lockers Extension_ (KLE), formerly the _Atomic Cryptography Extension_ (ACE), is not normative and repeats material from the specification on purpose.
Parts of it, such as the Threat Model, may enter the specification at ratification.

// https://riscv.atlassian.net/wiki/spaces/HACX/pages/484966423/High+Assurance+Crypto+Ratification+Plan[here].

== Features

KLE lets software perform fast cryptographic operations without access to the keys or other critical values, for uses such as content protection (media and local LLM decryption), link and storage encryption, secure boot, and attestation.
Its main features are:

* *Atomic operations.* Each cryptographic operation is atomic, so keys cannot be recovered from the data before and after it, even by a memory-read exploit.
//  An instruction can be interrupted only between operations, if it performs multiple cryptographic operations in a single call,
//  or at the points an algorithm defines for its long-running operations.
//+
//_Rationale for atomic operations._
//  If the primitive is secure, its key cannot be recovered from the inputs and outputs of the complete operation. ISAs that take the key between rounds or MAC stages would not have this property, even if the key came from a hidden register. For instance, an attacker with access to an instruction computing only 4 or 5 rounds of AES can efficiently recover the key cite:[Rijndael-revised]. Hence, even splitting the AES, say, into two calls (for AES-128) or three (for AES-192 and AES-256) is not an option if the goal is preventing exposure of the key.

* *Cryptographic Lockers* are architectural containers that hide their secrets from software.
Software _provisions_ a locker with Content (keys and other state) and Metadata that binds the Content to algorithms and, optionally, to usage policies, hardware and software environments, and an expiration date, forming a *Cryptographic Context*.
KLE instructions reference lockers, not key values; strict management rules keep lockers from revealing critical values; and a context can be exported to memory under authenticated encryption and later reimported.

* *One interface for many primitives*, instead of separate instructions per primitive:
 ** Leaked derived keys or intermediate values break modes such as AES-GCM-SIV, XTS, and OCB, so KLE defines modes of operation (among them CTR, GCM, and CMAC) and secure key derivation, for AES-128, -192, -256 and other block ciphers such as SM4.
 ** Encrypt-only and decrypt-only versions reduce misuse, and versions with a preset IV or nonce keep it confidential.
 ** The interface also covers hash functions and public-key and post-quantum algorithms. Side-channel protected implementations, where available, are variants of the standard algorithms and replace them without code changes.
 ** Implementations need not support every algorithm: KLE defines subextensions, and `Zkl` requires a baseline set (<<Zkl-ISA-unpriv.adoc#KLE-unpriv-exts-overview>>), leaving the others to the RISC-V profiles.

* *Scalability.* One ISA and ABI serve cores from embedded to server, with support for persistence, sleep, hibernation, and VM migration.

[[KLE-introduction-non-features]]
== Non-Goals

KLE intentionally does not provide:

* **Variable-length inputs:** data is processed in fixed-size blocks.

* **Full key management:** KLE provides building blocks, and the key-management logic resides in trusted software, such as TEE applets. External schemes provision keys only through a local trusted component that obtains keys and policies and configures the CCs.

* **Key revocation**, because:

. it would cost implementation effort and performance, against KLE's goals of simplicity and speed;
. no universal mechanism is practical: protocols are numerous, revocation data may be unbounded, and the KLE unit would need dynamic access to secure memory, whereas isolated software components can revoke keys with strong guarantees;
. revocation applies mainly to root keys, which their trusted manager can revoke, while expiration dates and _Localities_ limit the lifetime and scope of derived keys; and
. applications that use root keys directly, such as link or storage encryption, usually run in protected environments with their own revocation.

* **Full prevention of misuse by compromised processes:** a compromised process keeps access to its CCs, so KLE complements, but does not replace, vulnerability mitigations and process isolation. Modes that use one operation to encrypt and decrypt, such as counter modes, stay open to such abuse.

[[KLE-threat-model]]
== Threat Model

**Assets** are _keys_ and any information that helps an adversary recover plaintext or forge ciphertexts or MACs, such as the masks of tweakable XEX modes and the derived keys of AES-GCM-SIV.
Their _confidentiality_ and _integrity_ are protected. Their _availability_ is not an architectural goal, but the _availability of resources_ is: a caller can always configure a locker, and the KLE unit never evicts a CC on its own.

**Adversaries** can compromise processes through software vulnerabilities, and access memory, for example by abusing hardware interfaces or interposing between the SoC and memory. Sophisticated hardware attacks, such as tampering with a focused ion beam or scanning electron microscope (FIB/SEM), are excluded.
// Every implementation is free of timing leakage (Level A of <<Zkl-ISA-unpriv.adoc#KLE-SCProtection-field>>); protection against other side-channel analysis (SCA), Levels B and C, is optional, and KLE provides interfaces to implementations with and without it.
//
// Where it can, KLE neither accepts risks nor removes useful features. It _controls_ threats through its own mechanisms and _transfers_ the residual risk, key extraction, to the privileged or trusted software and hardware that manage keys. Trusted software can use control-flow integrity, memory encryption with integrity protection, and anti-replay mechanisms; hardware key-management blocks can be hardened.

Direct plaintext leakage, memory-corruption attacks against the process using KLE, and Release of Unverified Plaintext (RUP) attacks are _accepted_: the processed data resides in the user's execution context, where KLE cannot protect it.

[[KLE-open-points]]
== Discussion Points

These items are neither known defects nor a measure of the specification's maturity.

Group A: items requiring closure by the RISC-V Architecture Review Committee (ARC).::

. *Opcode allocation.* The encodings are provisional; the ARC allocates the final ones.
  The _core instructions_ use the MISC-MEM opcode, which has several unused `funct3` values; similar gaps elsewhere would serve as well.
  The _memory instructions_ are harder, since their offsets take every bit that `opcode`, `funct3` and the registers leave: `kl.input` uses the only unused `funct3` value of LOAD, 0x7, and `kl.output` the value 0x5 of STORE, encoded together with `kl.load` and `kl.store`, respectively.
+
Moving encoding bits [29:25] of `kl.size`, `kl.avail`, `kl.getmd*`, `kl.rstr*`, and `kl.clone` to [24:20], with [29:25] fixed to zero, would free significant space in `funct7`.

. *Naming of instructions.* Should the instructions that use vector registers take a `v` prefix, as `vkl.mgmt` for the version that takes the `MDH` from a vector register, and those that take 128 bits from GPRs a `q` suffix, as `kl.mgmtq`?

. *`misa.L` and `mstatus[26:25]` (KLS).* Provisional and contested. `misa.L` may give way to another mechanism, such as Unified Discovery, and KLS, with the corresponding bits of `sstatus` and `vsstatus`, may move to another offset or register, or to a mechanism other than a `*status` context-status field.
  The specification depends only on a two-bit context-status field with the semantics of <<Zkl-ISA-priv.adoc#KLE-aces-encoding>>, like `FS` and `VS`.

. *`mstatus`[27] (`kleemulation`).* The bit that makes `kl.avail` and `kl.size` of Form B or C trap on a Machine, or a combination of its MDH fields, that the KLE unit does not implement natively, so that M-mode can emulate it (<<Zkl-ISA-priv.adoc#KLE-kleemulation>>), sits in `mstatus` only provisionally. The ARC must move it to a free position, in `mstatus` or another M-mode CSR.

. *KLE CSR addresses.* All addresses, and the `Smstateen` bit of <<Zkl-ISA-priv.adoc#KLE-privileged-CSRs>>, are placeholders for the ARC to assign.

. *Exception cause codes.* The ARC must allocate `mcause` values: individual causes, or a single KLE cause with a subcause register.
  A way to report the locker number, for instance in `mtval`, is also needed; it would spare handlers from decoding locker references, `KLNL` included.
.. *specific* `*mtval*` *or KLE Emulation Trap.* Trap-and-emulate uses the illegal-instruction exception, which, with `kleemulation`, must stay undelegated (<<Zkl-ISA-priv.adoc#KLE-kleemulation>>).
  A dedicated exception type would be better, especially since no mode below M emulates, and would remove that constraint; a special `mtval` could serve instead.

. *KLV scope.* <<Zkl-ISA-unpriv.adoc#KLE-KLV>> defines the vector subset KLE requires, which we consider complete.
  These questions do not block candidacy but need ARC feedback:

  .. Should `*status.VS` or another mechanism gate KLV vector instructions?
  .. How should KLV be discovered?
  .. How should `kl.exec` element widths be defined? `EGW`/`SEW` cannot represent sizes that are not powers of two; one
     option allows any power of two that divides the size, with `EGW`/`SEW` and the `vstart` increment defined per iteration.

. *Discoverability of cipher/mode combinations.*
  We propose that software discover Machines with `kl.avail` rather than by extension names, which could proliferate beyond manageability.
  <<Zkl-ISA-machines.adoc#KLE-exec-encodings>> still suggests names: `Zkl`, the primitive name ending in `p`, and the mode name ending in `m` (e.g., `Zklaes192p` and `Zklaes192pgcmm`).

//. *Cross-hart CSR access.* Is there, or should there be, an architected way for M-mode on one hart to read or configure
//  another hart's CSRs? <<Zkl-ISA-unpriv.adoc#KLE-CSK-requirements>> and <<Zkl-ISA-priv.adoc#KLE-CSR-mklcsk>> could
//  then use it instead of platform-specific channels.

Group B: open design questions owned by this task group.::

//. *`kl.mgmt` interruptibility.* `kl.mgmt` can run relatively long, though much less than an ECC scalar multiplication or a
//  signature verification. It is uninterruptible because preempting and resuming it may open new attack vectors: an
//  interrupted encryption or decryption leaves a locker with both encrypted and unencrypted content, and unencrypted
//  content cannot be exported as such. A precise interruption seems secure only if the KLE unit works on an internal copy.

. *Nonces for SCC export and import.* An RFC 8452 nonce costs six AES-256 encryptions per export or import, whereas this
  design recomputes the derived keys only when the CSK changes. A competing architecture also omits nonces from
  key export and import, probably for the same reason. We welcome input on this choice.

. *Additional inputs for random key generation.* Should standard KDFs be defined?

. *`SCC_Encrypt` security claim.* Substantiate the claim “secure for up to 2^64^ 128-bit blocks.”

. *Emulated Machines.* TODO: define how software discovers emulated instructions and Machines, and whether an emulated Machine may override a native one with a fixed emulated version (<<Zkl-ISA-priv.adoc#KLE-kleemulation>>).

. *Memory-instruction check order.* Rule <<Zkl-ISA-unpriv.adoc#KLE-GR-management-check-order>> checks the address alignment of `kl.load` and `kl.store` independently of the locker State, so a misaligned address traps even on an inert locker.
  Hardware implementers should confirm that this order is practical, and that M-mode trap-and-emulate (<<Zkl-ISA-priv.adoc#KLE-kleemulation>>) can reproduce it.
