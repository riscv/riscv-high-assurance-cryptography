This introduction to the _Cryptographic Lockers Extensions_ (KLEE), formerly the _Atomic Cryptography Extension_ (ACE),
is not part of the specification.
The ratification plan is
https://riscv.atlassian.net/wiki/spaces/HACX/pages/484966423/High+Assurance+Crypto+Ratification+Plan[here].

== Features

KLEE lets software perform high-performance cryptographic operations without having direct access to the keys.
(((design, high performance)))
Its use cases include content protection (including local LLM decryption), link and storage encryption, secure boot, and attestation.

Its main features are:

* *Cryptographic Contexts.* KLEE binds secrets, such as keys, and metadata into an indivisible _Cryptographic Context_ (CC). The metadata restricts each secret to one algorithm and can enforce usage constraints by process, VM, security state, boot cycle, expiration date, or other policies.

* *Cryptographic Lockers.* CCs reside in _Cryptographic Lockers_, architectural containers that hide their secrets from software. Software _provisions_ (writes) secrets and metadata into a locker, and KLEE instructions name lockers instead of key values. Keys thus never sit in process memory, and implementations can be faster and side-channel protected.

* *Atomic operations.* Each cryptographic operation is atomic, so no intermediate value leaks through architectural side channels.
  An instruction can be interrupted only between operations, or at the points an algorithm defines for its long-running operations.

* *One interface for many primitives*, instead of separate instructions per primitive:
 ** Primitives alone do not suffice for modes such as AES-GCM-SIV, XTS, and OCB, where leaked derived keys or intermediate values compromise security. KLEE therefore also defines modes of operation, among them CTR, GCM, and CMAC, and secure key derivation.
 ** Encrypt-only and decrypt-only versions reduce misuse, and versions with a preset IV or nonce keep it confidential. The modes work with AES-128, AES-192, AES-256, and other block ciphers such as SM4.
 ** The interface also covers hash functions, public-key and post-quantum algorithms, and SCA-resistant implementations.
 ** Implementations need not support every algorithm: following RISC-V practice, KLEE defines subextensions and leaves requirements to the RISC-V profiles.

* *Sealed contexts.* KLEE stores a CC to memory with authenticated encryption as a _Sealed Cryptographic Context_ (SCC), which can later be re-imported into a locker. A process given an SCC instead of a key never holds the key in its memory.

* *Scalability.* One ISA and ABI serve embedded to server cores, and KLEE supports sleep, hibernation, and VM migration.
(((design, scalable)))
(((VM migration)))

Rationale for atomic operations:::
If the primitive is secure, its key cannot be recovered from the inputs and outputs of the complete operation. ISAs that take the key between rounds or MAC stages lose this property, even when the key comes from a hidden register: an attacker with access to an instruction computing only 4 or 5 rounds of AES can efficiently recover the key cite:[Rijndael-revised].

[[KLEE-introduction-non-features]]
== Non-Goals

KLEE intentionally does not provide:

* **Variable-length inputs:** plaintexts, ciphertexts, and hash inputs are processed in fixed-size blocks.

* **Full key management:** KLEE provides only building blocks; the key-management logic resides in trusted software, such as TEE applets. External schemes do not provision keys directly: a local trusted software or hardware component obtains keys and policies and configures the CCs.

* **Key revocation**, because:

. it would cost significant implementation effort and performance, against KLEE's goals of simplicity and speed;
. a universal mechanism is impractical: protocols are numerous, revocation data may be unbounded, and the KLEE unit would need dynamic access to secure memory, whereas isolated software components can provide revocation with strong guarantees;
. revocation applies mainly to root keys, which the trusted entity managing them can revoke, while expiration dates and _Localities_ limit the lifetime and scope of derived keys; and
. applications that access root keys directly, such as link or storage encryption, usually run in protected environments with their own revocation mechanisms.

* **Full prevention of misuse by compromised processes:** a compromised process keeps access to its own CCs, so KLEE complements, but does not replace, vulnerability mitigations and process isolation. Modes that use one operation for both encryption and decryption, such as counter mode, remain open to such abuse.

[[KLEE-threat-model]]
== Threat Model

**Assets** are _keys_ and any information that helps an adversary recover plaintext or forge ciphertexts or MACs, such as the masks of tweakable XEX modes and the derived keys of AES-GCM-SIV.
Their _confidentiality_ and _integrity_ are protected; their _availability_ is not an architectural goal.

**Adversaries** can compromise processes through software vulnerabilities, and can access memory, for example by abusing hardware interfaces or interposing between the SoC and memory. Sophisticated hardware attacks, such as tampering with a focused ion beam or scanning electron microscope (FIB/SEM), are excluded. Side-channel attack (SCA) protection is optional: KLEE provides interfaces to SCA-unprotected and SCA-protected implementations, where these are implemented.

Where it can, KLEE neither accepts risks nor removes useful features. It _controls_ threats through its own mechanisms and _transfers_ the residual risk, key extraction, to the privileged or trusted software and hardware that manage keys. Trusted software can use control-flow integrity, memory encryption with integrity protection, and anti-replay mechanisms; hardware key-management blocks can be hardened.

Direct plaintext leakage, memory-corruption attacks against the process using KLEE, and Release of Unverified Plaintext (RUP) attacks are _accepted_: the processed data resides in the user's execution context, where KLEE cannot protect it.

== Discussion Points

These items are neither known defects nor a measure of the specification's maturity. They fall into two groups.

Group A — items requiring closure by the RISC-V Architecture Review Committee (ARC).:::

. *Opcode allocation.* The encodings are provisional, and the final allocation is the ARC's responsibility.
  The _core instructions_ use the MISC-MEM opcode, which currently has several unused `funct3` values; similar gaps elsewhere
  would serve as well. The _memory instructions_ are harder, since their offsets take all remaining bits once `opcode`,
  `funct3`, and source and destination registers are fixed: `kl.input` uses the only unused `funct3` value of LOAD, `kl.output` the same value of STORE, and
  `kl.load` and `kl.store` use two `funct3` slots of JALR and STORE, respectively.
+
`kl.load` under JALR `funct3` 6/7 is an I-type encoding whose `rd` is a locker number, not a GPR. Tools that decode JALR
without first checking `funct3` may mis-disassemble it.
+
`kl.size`, `kl.avail`, `kl.getmd*`, `kl.restrict*`, and `kl.clone` could move encoding bits [29:25] to [24:20] and fix
bits [29:25] to zero, freeing significant space in `funct7`.

. *`misa.L` and `mstatus[26:25]` (KLS).* Provisional and contested. `misa.L` may give way to another mechanism, such as
  Unified Discovery, and KLS may move to another offset or register, or to a mechanism other than a `*status`
  context-status field; the same holds for the corresponding bits of `sstatus` and `vsstatus`. The specification depends
  only on a two-bit context-status field with the semantics of <<Zkl-ISA-priv.adoc#KLEE-aces-encoding>>, analogous to
  `FS` and `VS`.

. *KLEE CSR addresses.* All addresses are `0xXXX` or “(Indirect)” placeholders, to be assigned by
  the ARC, as is the `Smstateen` bit of <<Zkl-ISA-priv.adoc#KLEE-CSRs-priv>>.
  Some CSRs have been marked as indirect, by which we mean that
  we envision we can use the Indirect CSR Access mechanism of `Smcsrind`/`Sscsrind`.
  The final word, either `*iselect` values or direct CSR access and the allocation of the indices,
  is to be determined by the ARC.

. *Exception cause codes.* The ARC must allocate `mcause` values: individual causes, or a single
  KLEE cause with a subcause register. Some form of reporting “`mtval`” the locker number is also
  needed; it would spare handlers from decoding direct and indirect locker references.
.. *specific* `*mtval*` *or KLEE Emulation Trap.* Currently we are using the illegal-instruction exception for the purpose of
  trap-and-emulate. It would be a good idea to define a new exception type for this purpose, especially
  since we are currently _not_ delegating emulation to any mode below M. Or getting a special `mtval`
  for the purpose.

. *KLV scope.* <<Zkl-ISA-unpriv.adoc#KLEE-KLV>> defines the vector subset KLEE requires, which we consider complete.
  These questions do not block candidacy but need ARC feedback:

  .. Should KLV vector instructions be gated by `*status.VS` or by another mechanism?
  .. How should KLV be discovered?
  .. How should `kl.exec` define element widths? `EGW`/`SEW` cannot represent sizes that are not powers of two; one
     option is to allow any value that divides the size, with `EGW`/`SEW` and the `vstart` increment defined per
     iteration (link:https://github.com/riscv/riscv-high-assurance-cryptography/issues/96[]).

. *RVWMO axiomatic integration.* <<Zkl-ISA-unpriv.adoc#KLEE-Memory-Model>> specifies the ordering of KLEE's component
  memory operations informally, through prefix-completeness, and <<Zkl-ISA-unpriv.adoc#KLEE-resumability>> gives a
  conflicting-access rule. Their integration into RVWMO's axiomatic formalism remains to be done with the ARC.

. *Discoverability of cipher/mode combinations.* Subextensions may be impractical (see the introduction to
  <<Zkl-ISA-machines.adoc#KLEE-Machines>>); `kl.avail` can serve, and Unified Discovery is an option.

. *Cross-hart CSR access.* Is there, or should there be, an architected way for M-mode on one hart to read or configure
  another hart's CSRs? <<Zkl-ISA-unpriv.adoc#KLEE-CSK-requirements>> and <<Zkl-ISA-priv.adoc#KLEE-CSR-mklcsk>> could
  then use it instead of platform-specific channels.

Group B — open design questions owned by this task group.:::

. *Effective data endianness.* Clarify UBE and its interaction with MPRV/MPP in the definition of
  _effective data endianness of the current privilege mode_ (<<Zkl-notation.adoc#KLEE-Notation>>).

// . *Guest- and host-settable CSKs*, instead of always switching to M-mode, or host-settable only.

// . *Delegate KLEE trap-and-emulate to HSx.* Important and necessary; to be defined.

. *Eliminate `kl.load` and `kl.store`?* `kl.mv` suffices: with vectors there is no performance penalty, and dropping them
  simplifies the logic and relieves encoding pressure. Without vectors, performance is already traded for compactness,
  and the KLIOBUF could serve, if the ARC keeps it.

. *Side-channel protection* of the Machines and the sealing path: levels, formalization, and the documents to refer to.

. *`kl.mgmt` interruptibility.* `kl.mgmt` can run relatively long, though much less than an ECC scalar multiplication or a
  signature verification. It is uninterruptible because preempting and resuming it may open new attack vectors: an
  interrupted encryption or decryption leaves a locker with both encrypted and unencrypted content, and unencrypted
  content cannot be exported as such. A precise interruption seems secure only if the KLEE unit works on an internal copy.

. *Nonces for SCC export and import.* An RFC 8452 nonce costs six AES-256 encryptions per export or import, whereas the
  current design recomputes the derived keys only when the CSK changes. A competing architecture also omits nonces from
  key export and import, probably for the same reason. We welcome input on this choice.

The algorithms could then use `enc_key xor (B @ A)` and `auth_key xor B xor A` instead of `enc_key` and `auth_key`. This construction is non-standard, but it is secure and faster: it requires only two additional AES-256 encryptions.

. *Additional inputs for random key generation.* KDFs with arbitrary inputs and unlimited outputs could easily be defined
  as Machines that feed a locker's key field through `kl.derive`. Should standard KDFs be defined?

. *`SCC_Encrypt` security claim.* Substantiate the claim “secure for up to 2^64^ 128-bit blocks.”

. *KLF capacity.* Residual KLF capacity is not discoverable, and exact requirements are impossible, since a locker's
  footprint depends on the implementation (ADS size, number of shares of a masked implementation). `kl.size`/`kl.avail`
  could report whether a provision, import or clone fits, and possibly which locker other than a given one to free first,
  for instance the largest or the least recently used. Intel may cache keys; KLEE manages them explicitly.

. *Random material in exportable States.* Compare and streamline Rules
  <<Zkl-ISA-unpriv.adoc#KLEE-IRR-long-running-no-data>>, <<Zkl-ISA-machines.adoc#KLEE-MGR-progress-discard>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-atomic-randomness>> and
  <<Zkl-ISA-unpriv.adoc#KLEE-GR-opening-locker-when>>, and establish how to implement “No State from which the locker can be
  exported or cloned holds random material that could be consumed against an input other than the
  one it was drawn for.”
