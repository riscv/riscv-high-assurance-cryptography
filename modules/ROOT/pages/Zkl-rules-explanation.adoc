_This chapter is informative and non-normative._

This chapter states fourteen Design Principles, and six Design Decisions taken on their basis, from which the Rules of <<Zkl-ISA-unpriv.adoc#KLEE-unpriv>> follow, from Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-locker-less-transfers>> onward.
The Principles name no individual instruction: each rule should read as one Principle applied to one instruction or State class.
Rules <<Zkl-ISA-unpriv.adoc#KLEE-GR-multiple-GPRs>>–<<Zkl-ISA-unpriv.adoc#KLEE-GR-klstart-vstart>>, which state operand conventions, and the SR rules are Design Decisions too, and are not covered.

== Vocabulary

The Principles use only the following categories, all defined in the specification.

*State groups.*

* _Unconfigured_: the locker holds no CC.
* _Valid_ States: the locker holds a usable CC. _Ready_, _Success_ and _Failure_ are the architected ones.
* _Error_ States: the locker holds only an MDH, which records why its CC became unusable.
* _Configuration_ States: the CC is in transit, being provisioned, imported or exported.
// * _Complete_ = Valid ∪ Error. _Inert_ = Unconfigured ∪ Error, plus the case of no locker at all (`klmanagedlocker` = 32).

*Instruction classes* (from <<Zkl-ISA-unpriv.adoc#KLEE-instruction-properties>> in Rule <<Zkl-ISA-unpriv.adoc#KLEE-GR-usage-policy>>).

* _Usage_ instructions operate on the CC through the Machine; _UsagePolicy_ gates them.
** _Derivations_ are usage instructions with two lockers, gated on each.
* _Configuration_ instructions operate on the locker as a container; _UsagePolicy_ does not gate them. They are of three kinds:
** _inspection_: read the MDH or a size, change nothing;
** _destructive_: zeroize or overwrite the locker without reading it;
** _transfer_: move a CC, or part of it, unchanged, between lockers or between a locker and memory or registers: the management transfers (`kl.load`, `kl.store`, `kl.mvin`, `kl.mvout`), `kl.rename` and `kl.swap`, and the closing of a management operation.
* _Memory_ instructions have a memory operand. The class cuts across the others: `kl.load` and `kl.store` are both transfer and memory instructions.

*The managed locker* is the locker whose CC is in transit. A pointer names it, not a locker number.

== Design Principles

The fourteen Principles fall into five groups.

* _Transparency_: the architecture describes all the state there is (<<KLEE-Principle-1>>). It precedes the definition of a locker.
* _Economy_: simple instructions and short code, the least encoding space, the least architectural state (<<KLEE-Principle-2>>–<<KLEE-Principle-4>>). The Metadata Header (<<KLEE-decision-1>>) follows from <<KLEE-Principle-1>>, <<KLEE-Principle-3>> and <<KLEE-Principle-4>>; the managed locker (<<KLEE-decision-5>>) from <<KLEE-Principle-2>> and <<KLEE-Principle-4>>.
* _Security_: what software may never gain, what it may always do, and what it keeps (<<KLEE-Principle-5>>–<<KLEE-Principle-8>>): the confidentiality of the keys, the availability of the lockers, and the persistence, confidentiality and integrity of the CCs. <<KLEE-Principle-5>> gives the other Principles their purpose.
* _Structure_: how a Machine is driven (<<KLEE-Principle-9>>) and how an operation executes (<<KLEE-Principle-10>>).
* _Outcomes_: what happens when an instruction cannot do what it is asked, one Principle per State group, and how a failure is reported (<<KLEE-Principle-11>>–<<KLEE-Principle-14>>). <<KLEE-Principle-11>> is also how the system defends itself; <<KLEE-Principle-12>> is one way to implement <<KLEE-Principle-2>>.

[[KLEE-Principle-1,P1]]
P1: _The entire resource management is architectural_::
+
--
The architecture, not the implementation, manages every resource that software relies on: a resource exists in an architected place, with an architected state that software can manage, and the architecture alone decides when it is available.
Hence no hidden state is needed to make the feature fit a particular use.

*Rationale.* Other architectures may rely on caching to make more than one key available to software. KLEE instead exposes its state machines and resources (<<Zkl-ISA-unpriv.adoc#KLEE-CC-management>>) and lets software manage them; the implementation is simpler as a result.

*Consequences.* There are 32 lockers, each with its MDH always present. The KLF capacity for Content is implementation-defined, but its exhaustion is an architected exception at the instruction that needs it, never a silent eviction; lack of memory is the only reason for which the KLF refuses a request. Context switching saves and restores the architected state. Whatever an implementation keeps beyond the MDH and the Content, the ADS included, can be discarded at any time without changing an architected outcome, and is identified by architected registers so that an import can tell whether it is usable (<<Zkl-ISA-unpriv.adoc#KLEE-CSR-impl-ids>>).

*Rules.* <<Zkl-ISA-unpriv.adoc#KLEE-KLF>>, the out-of-memory item of <<Zkl-ISA-unpriv.adoc#KLEE-error-architecture>>, <<Zkl-ISA-unpriv.adoc#KLEE-state-save-and-restore-order>>; among the General Rules, <<Zkl-ISA-unpriv.adoc#KLEE-GR-long-running-progress>> (progress outside the Content) and <<Zkl-ISA-unpriv.adoc#KLEE-GR-custom-locality>> (implementation-bound Metadata).
--

[[KLEE-Principle-2,P2]]
P2: _Make instructions as simple as possible, while still requiring short code sequences_::
+
--
Instructions are as simple as the RISC-V philosophy asks, and the code that uses them is short too: whatever a routine would otherwise repeat in every instruction, or check after every instruction, becomes architectural state or a single check. The number of the locker a management routine works on is held in an architectural register, so the same code serves every locker; the outcomes of asynchronous events are shaped so that one check at the end of a sequence suffices.

*Rationale.* Management and context-switch code runs in handlers and libraries: written once, audited once, it must not grow with the number of lockers or of steps. Moving a repeated operand or check into the architecture costs one CSR and one read-out, and removes a class of software errors. Hardware complexity is added only where it brings the largest saving: a management routine that works on any locker, instead of one instance per locker, is 32 times less code, whereas cryptographic code can address fixed lockers and needs no such help.

*Consequences.* <<KLEE-decision-5>>, with <<KLEE-Principle-4>>: the managed-locker pointer, its implicit and `KLML` operands, and the instructions that read and write it. The "check once" property of <<KLEE-Principle-12>>: an instruction that falls through never traps and never acts elsewhere, so a routine checks the _State_ only after its last step, through the pointer. One instruction clears every locker and the buffer. The KLIOBUF substitutes for vector operands, so one code path serves harts with and without vectors.

*Rules.* <<Zkl-ISA-unpriv.adoc#KLEE-GR-locker-less-transfers>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-klmanagedlocker-override>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-klml-no-managed-locker>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-klmanagedlocker-updates>>, the NOTE under <<Zkl-ISA-unpriv.adoc#KLEE-GR-cleared-under-management>> and the NOTE after <<Zkl-ISA-unpriv.adoc#KLEE-GR-memory-instructions>>; outside the GR series, the substitution rules of <<Zkl-ISA-unpriv.adoc#KLEE-usage-input-output>>.
--

[[KLEE-Principle-3,P3]]
P3: _Minimize the pressure on the encoding space_::
+
--
Instead of defining instructions for each cryptographic primitive, variant and mode of operation, KLEE defines a few generic instructions and encodes the algorithm, its mode and its parameters in the data, the MDH: one `kl.exec` and one `kl.setst` serve every Machine, present and future, and a new Machine needs a new _Machine_ value, never a new opcode.

*Rationale.* Opcode space is the scarcest resource of an ISA, and cryptographic algorithms are many and short-lived compared with an ISA. Binding them to the Metadata keeps the instruction set fixed while the set of Machines grows, and lets every Machine follow one protocol (<<KLEE-Principle-9>>).

*Consequences.* The _Machine_ and ancillary fields of the MDH name the algorithm, and the immediate of `kl.setst` names the State to enter or the operation to perform on the current one, so that `kl.setst` and `kl.exec` alone drive every state machine. The remaining instructions manage lockers, not algorithms: they clear, inspect, move, restrict and transfer lockers, and none depends on the Machine.

*Rules.* <<Zkl-ISA-unpriv.adoc#KLEE-Machine-field>>, <<Zkl-ISA-unpriv.adoc#KLEE-management-immeds>>, <<Zkl-ISA-unpriv.adoc#KLEE-instruction-properties>>.
--

[[KLEE-Principle-4,P4]]
P4: _Additional architectural state beyond the lockers is kept to a minimum_::
+
--
State that an operation needs only while it is under way exists once per hart, not once per locker. The authentication and implementation-identification registers `SIV`, `IMPQUAL` and `SIV2` are the main case: one set per hart serves every locker, at the price of one small CSR, `klmanagedlocker`, that names the locker they belong to (<<KLEE-Principle-2>>). The progress counter `klstart` and, with `Zklio`, the KLIOBUF follow the same rule. The remaining CSRs, unprivileged and privileged, configure or identify the KLEE unit and are not per-operation state.

*Rationale.* Every added register is state that a context switch must save and restore, that interposed software must preserve, and that may leak between contexts. The authentication and implementation-identification registers take 128 or 384 bits, depending on the features implemented; one set shared by all lockers, instead of one per locker, saves that hardware, and save-and-restore sequences tied to `klmanagedlocker` save software too.

*Consequences.* One set of authentication registers means at most one management operation per hart in flight, the premise of <<KLEE-decision-5>>: one pointer names its locker, a second operation on another locker must first save the first by a nested export, and management operations are not interleaved with each other or with cryptographic operations. One `klstart` means that every instruction honoring it starts from the value it finds, that an opening `kl.mgmt` clears it, and that interposed software saves and restores it. The authentication registers and the pointer are shared, so touching them while an operation is in flight is a conflicting access. A long-running operation records its progress in its locker, in _MachineUse_ and the ADS, not in a register of its own.

*Rules.* <<Zkl-ISA-unpriv.adoc#KLEE-GR-locker-less-transfers>>–<<Zkl-ISA-unpriv.adoc#KLEE-GR-klmanagedlocker-updates>> (through <<KLEE-decision-5>>), <<Zkl-ISA-unpriv.adoc#KLEE-GR-cleared-under-management>> and <<Zkl-ISA-unpriv.adoc#KLEE-exception-state-change>> (`klstart` cleared by `kl.mgmt`), <<Zkl-ISA-unpriv.adoc#KLEE-GR-long-running-progress>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-conflicting-access-rule>>; outside the GR series, Rules <<Zkl-ISA-unpriv.adoc#KLEE-SR-save-shared-state>>, <<Zkl-ISA-unpriv.adoc#KLEE-SR-klstart-save>>–<<Zkl-ISA-unpriv.adoc#KLEE-SR-klstart-restore>> and <<Zkl-ISA-unpriv.adoc#KLEE-SR-klmanagedlocker-write>>–<<Zkl-ISA-unpriv.adoc#KLEE-SR-never-clear-exporting>>.
--

[[KLEE-Principle-5,P5]]
P5: _Privileges are never elevated_::
+
--
No instruction yields a key, a locker or an output with more rights than its inputs and its issuer already hold, except where that is the purpose of the Machine (for instance, public output encrypted under a secret key). Four consequences cover the rules.

_No extraction._ Once a key is in a CC, it cannot be extracted in clear: it is used only through its Machine, no instruction reads it out, and an exported CC is sealed. Whoever obtains the CC obtains the right to use the key under its policies, never the key.

_Usage is gated._ An instruction exercises only the rights that the _UsagePolicy_ grants to the issuing mode; exercising any other is a privilege violation. A mode may use or alter only the lockers that its policies admit, so an instruction that can change the cryptographic state of a locker, the progress of its operation included, is gated; narrowing, copying and destroying are always allowed (<<KLEE-Principle-6>>), since they change no operation and elevate nothing.

_Secrets flow only downhill._ Material derived from a secret inherits every constraint of the secret: it moves only into a locker whose policies, after narrowing, are at least as strict as the source's. Narrowing never widens a policy, raises a protection level or changes a Machine policy. A transfer is exempt from narrowing exactly when the caller could obtain its result with admitted instructions anyway, so the exemption adds no attack surface. A secret bound to the system never leaves it, and a bound key field is never replaced from outside. Secrets do not linger: when a CC is destroyed, invalidated or restarted, the material that depended on it is released or zeroized, and a destructive configuration instruction zeroizes before any check that could trap.

_Nothing stale is returned._ An output that is not produced reads as zero: an instruction that performs no operation, or stops in an Error State, zeroes the part of its output window it has not written, and an inert locker reads as zeros, so that neither an input nor an earlier output can pass for a result.

*Rationale.* This invariant makes least privilege enforceable: policies granted at provisioning and narrowed later can be relied upon only if no operation can widen or bypass them. For derived material, NIST SP 800-57 Part 1 §6.2.1 and SP 800-108r1 §8 require exactly this inheritance.

*Rules.* <<Zkl-ISA-unpriv.adoc#KLEE-concepts>> (no extraction), <<Zkl-ISA-unpriv.adoc#KLEE-GR-usage-policy>> and <<Zkl-ISA-unpriv.adoc#KLEE-GR-outcome-by-state>> (gating), <<Zkl-ISA-unpriv.adoc#KLEE-GR-narrowing>>–<<Zkl-ISA-unpriv.adoc#KLEE-GR-DRBG-implies-unrestricted>>, the paragraphs after <<Zkl-ISA-unpriv.adoc#KLEE-GR-unrestricted>> and <<Zkl-ISA-unpriv.adoc#KLEE-GR-DRBG-implies-unrestricted>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-policy-narrowing-state>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-custom-locality>>; <<Zkl-ISA-unpriv.adoc#KLEE-GR-clear-locker-content-error-state>>, <<Zkl-ISA-unpriv.adoc#KLEE-exception-state-change>> (zeroizing step) and <<Zkl-ISA-unpriv.adoc#KLEE-GR-long-running-progress>> (restart) for lingering; <<Zkl-ISA-unpriv.adoc#KLEE-GR-usage-locker-error-state>> and <<Zkl-ISA-unpriv.adoc#KLEE-GR-cleared-under-management>> (zeros) for the last.
--

[[KLEE-Principle-6,P6]]
P6: _It must always be possible to configure new Cryptographic Contexts_::
+
--
Configuration instructions are admitted in every State group, and neither a Machine nor a _UsagePolicy_ may restrict them: even when all lockers are in use, a caller can reconfigure any of them. In particular, the return to _Ready_ and the exits from an Error State are always open, and a locker in a Configuration State can be cleared, re-provisioned or re-imported like any other.

*Rationale.* No denial of service on the KLEE resources.

*Rules.* <<Zkl-ISA-unpriv.adoc#KLEE-GR-opening-locker-when>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-error-state-can-be-reconfigured>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-config-instructions-config-state>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-transition-triggers>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-to-ready>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-setst-in-success-failure>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-success-failure>> (first paragraph), <<Zkl-ISA-unpriv.adoc#KLEE-GR-clearads>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-transition-to-from-unconfigured>> (last sentence), `kl.mgmt` exception of <<Zkl-ISA-unpriv.adoc#KLEE-exception-state-change>>.
--

[[KLEE-Principle-7,P7]]
P7: _Cryptographic Contexts persist: they can be stored and reloaded to survive context switches, power cycles, process and VM migrations_::
+
--
A CC is bound neither to the locker that holds it, nor to the hart, the power state or the machine: it can be saved from a locker and restored into any one. What is saved is the whole CC, its MDH and Content, and restoring it yields a locker that behaves as the saved one did, including an operation interrupted at an architected interruption point; an interruption at an implementation-defined point need not survive, and the operation then restarts (<<KLEE-decision-6>>).

*Rationale.* Persistence is the counterpart of <<KLEE-Principle-6>>: a CC evicted from a locker to make room is not destroyed, only saved. Only the consumer of a CC, or more privileged software, decides when a CC is destroyed.

*Consequences.* The SCC, and the export and import of lockers. The format is defined independently of the implementation and of the ISA, so that a CC can be restored elsewhere (<<Zkl-ISA-unpriv.adoc#KLEE-SCC>>, <<Zkl-books.adoc#KLEE-separation>>).

*Rules.* <<Zkl-ISA-unpriv.adoc#KLEE-GR-error-state-exported-as-MDH>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-completion-state>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-long-running-progress>>, <<Zkl-ISA-unpriv.adoc#KLEE-SCC-export>>, <<Zkl-ISA-unpriv.adoc#KLEE-SCC-import>>, <<Zkl-ISA-unpriv.adoc#KLEE-state-save-and-restore-order>>; outside the GR series, Rules <<Zkl-ISA-unpriv.adoc#KLEE-SR-isolation>>.
--

[[KLEE-Principle-8,P8]]
P8: _Cryptographic Contexts keep their confidentiality and integrity outside a locker_::
+
--
A CC outside a locker reveals nothing of its secret material and cannot be altered undetected: it is encrypted under a key that only the KLEE unit holds, and authenticated together with its MDH. The seal can be bound to a locality, a chip, a chip family or a system, and the CC is then restorable only there.

*Rationale.* Persistence (<<KLEE-Principle-7>>) moves a CC through memory, storage and networks that the KLEE unit does not control; the guarantees of <<KLEE-Principle-5>> hold outside a locker only if the saved form carries them.

*Consequences.* Export seals the CC with an AEAD under a key derived from a locality secret, with the MDH as associated data; import verifies the seal before anything is restored, and a failed verification leaves an Error State, not a usable locker. Metadata that only the issuing implementation can interpret is bound to that implementation.
// A locality secret must not be withdrawn while a CC bound to it may still be exported.

*Rules.* <<Zkl-ISA-unpriv.adoc#KLEE-SCC-AEAD>>, <<Zkl-ISA-unpriv.adoc#KLEE-Localities>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-custom-locality>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-completion-state>>; outside the GR series, Rule <<Zkl-ISA-unpriv.adoc#KLEE-SR-locality-unconfigure>>.
--

[[KLEE-Principle-9,P9]]
P9: _All Machines follow one state-machine protocol_::
+
--
Software drives every Machine the same way: a state-setting usage instruction names the next State, or an operation on the current one; an execute usage instruction performs the operation of the current State. The architecture and each Machine's specification say which transitions exist and which usage instructions each Valid State admits.

// Two conventions complete the protocol: re-entering the current State is admitted unless the implemented standard gives it no meaning, and the completion of a management operation leaves the locker in the State its MDH names, a fresh provisioning in _Ready_.

*Rules.* <<Zkl-ISA-unpriv.adoc#KLEE-GR-transition-triggers>>–<<Zkl-ISA-unpriv.adoc#KLEE-GR-clearads>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-success-failure>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-completion-state>>.
--

[[KLEE-Principle-10,P10]]
P10: _Every operation is atomic or prefix-complete with atomic component operations and bounded progress, and asynchrony is invisible_::
+
--
An _uninterruptible_ instruction completes, has no effect, or traps with only the effects that <<Zkl-ISA-unpriv.adoc#KLEE-exception-state-change>> lists. A _resumable_ instruction processes its input serially and halts only at a prefix-complete point, recorded in `klstart`, where it has committed exactly what a shorter instruction performing the completed prefix would commit. Its units, blocks or granules, are atomic, although the memory accesses that implement them need not be (<<Zkl-ISA-unpriv.adoc#KLEE-rule-memory-instruction-decomposed>>). A precise halt does not retire the instruction; a transition to an Error State after partial progress does. A committed prefix is never recomputed: prefix-completeness protects not only the consistency of the state but the one-time use of keystream and nonces.

The KLEE unit may execute asynchronously, but the issuing hart never observes it: a conflicting access waits for the instruction to complete or halt precisely. Memory instructions are RISC-V memory instructions in every respect, and touch only idempotent memory, so that a prefix can be replayed.

A management operation spans several instructions, and the same holds for it: between its instructions the locker is in a Configuration State, the prefix-complete state of the operation, which nothing consumes partially (<<KLEE-decision-4>>).

Progress is bounded. No instruction processes a potentially unbounded input, as some software libraries and some CISC architectures do. Every wait, retry and restart has a documented bound, past which the implementation either progresses or reports the condition with the _State_ unchanged. Key material is all-or-nothing: it enters a field in one uninterruptible step of exactly the field's length, or not at all, so no locker is ever usable with a partly written key.

*Rationale.* Context save and restore need a state that the locker, `klstart`, `vstart` and the ADS describe completely; for a management operation, that state is the locker in its Configuration State. The memory model must not acquire a new kind of access. Halting and resuming is meaningful only if resumption eventually completes.

*Rules.* <<Zkl-ISA-unpriv.adoc#KLEE-GR-memory-program-order>>–<<Zkl-ISA-unpriv.adoc#KLEE-GR-memory-instructions>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-derive-rule-both-fixed-size>> (interruption points, transfer size), <<Zkl-ISA-unpriv.adoc#KLEE-GR-long-running-progress>> (halt points), <<Zkl-ISA-unpriv.adoc#KLEE-GR-checks>> (key item), <<Zkl-ISA-unpriv.adoc#KLEE-GR-rbg-failure>> (temporary failure); for management operations, <<Zkl-ISA-unpriv.adoc#KLEE-GR-config-instructions-config-state>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-usage-locker-config-state>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-zkl-load-mv-allowed>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-zkl-store-mv-allowed>>.

[[KLEE-Principle-11,P11]]
P11: _Any misuse of a Valid locker makes it unavailable to software_::
+
--
A usage instruction that the Machine, the current Valid State or the current policies do not admit performs no operation and moves the locker to _Invalid_; so does an unrecoverable failure of a resource the operation needs. The architecture keeps no history: once in an Error State, the locker is inert (<<KLEE-Principle-12>>) until reconfigured (<<KLEE-Principle-6>>).

*Rationale.* Fail closed. A wrong instruction on a live key may be an attack; the only safe outcome is to make the key unusable until software, which can always reconfigure, decides.

*Rules.* <<Zkl-ISA-unpriv.adoc#KLEE-GR-no-exec-in-ready>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-success-failure>> (second paragraph), <<Zkl-ISA-unpriv.adoc#KLEE-GR-same-state>> (last sentence), <<Zkl-ISA-unpriv.adoc#KLEE-GR-policy-narrowing-state>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-checks>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-rbg-failure>> (permanent failure), <<Zkl-ISA-unpriv.adoc#KLEE-GR-state-after-setst>>.
--

[[KLEE-Principle-12,P12]]
P12: _Inert lockers let instructions fall through_::
+
--
On an inert locker, every instruction other than a destructive one performs no operation and raises no exception: the _State_ is unchanged and any output is zero. A transfer instruction leaves `klstart` as it would after a transfer with an empty window. Inspection instructions read what is there: zeros, or the MDH.

*Rationale.* A locker becomes inert asynchronously, when a handler clears or invalidates it. The instructions that follow must neither trap nor act on something else, and the original error must stay readable, so that one check at the end of the sequence suffices: fall-through is one way to implement <<KLEE-Principle-2>>. Since `klstart` does not advance on an inert locker, a transfer sequence is bounded by the caller's own count, never by `klstart` (Rule <<Zkl-ISA-unpriv.adoc#KLEE-SR-no-klstart-loop>>).

*Boundary.* <<KLEE-Principle-12>> governs lockers that hold nothing to act on. A misused Valid locker falls under <<KLEE-Principle-11>>, a locker in a Configuration State under <<KLEE-Principle-10>>.

*Rules.* <<Zkl-ISA-unpriv.adoc#KLEE-GR-usage-locker-error-state>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-transition-to-from-unconfigured>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-cleared-under-management>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-klml-no-managed-locker>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-getmd-to-from-unconfigured>>, second half of <<Zkl-ISA-unpriv.adoc#KLEE-GR-klml-openings>>, bullet 2 of <<Zkl-ISA-unpriv.adoc#KLEE-GR-klmanagedlocker-updates>>, second half of <<Zkl-ISA-unpriv.adoc#KLEE-GR-error-state-can-be-reconfigured>>, inspection part of <<Zkl-ISA-unpriv.adoc#KLEE-GR-config-instructions-config-state>>.
--

[[KLEE-Principle-13,P13]]
P13: _Failures are reported by their cause, errors are recorded in the CC that caused them_::
+
--
Each CC, in particular each locker, keeps its own error state, independently of every other locker and of the hart: a failure is recorded in the _State_ field of the locker whose precondition failed, as an Error State that names the class of the cause, _Invalid_ for a sequencing error, _Privilege Violation_ for a policy, _Unsupported_ for a capability, _Expired_ for the clock, _Authentication Failed_ for a seal. An exception is raised instead only for a condition that a more privileged handler may resolve, by emulating a Machine, freeing memory, granting a right, or supplying a clock or entropy, and it names that condition; an illegal-instruction exception is reserved for programming errors.

*Rationale.* A handler, or the owner of the locker, acts on the cause without decoding the instruction or reconstructing the sequence that led to it, and the error survives a context switch, an export and an import with the locker, since it is part of its MDH (<<KLEE-decision-1>>). Per-locker errors let lockers fail independently. The choice is fundamental and may be revisited; for now it fixes the format of the MDH and of the exported image, and simplifies both the implementation, which needs no error register, and the error handling, which needs one check per locker.

*Consequences.* The Error States are values of the _State_ field, hence part of the internal and the external format (<<KLEE-decision-3>>). A derivation checks its conditions in order of dependency, the source endpoint, the destination endpoint, the pair, then the request against the destination, and records a failed check on the locker whose condition it is: the source, the destination, or both for the pair. A failure of the environment is an error (_Invalid_); an outcome of the algorithm is not (_Failure_). The KLEE exception codes list conditions a handler can resolve, and Rule <<Zkl-ISA-unpriv.adoc#KLEE-SR-handler-duty>> says what a handler must do with one it cannot.

*Rules.* <<Zkl-ISA-unpriv.adoc#KLEE-error-architecture>>, <<Zkl-ISA-priv.adoc#KLEE-exception-codes>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-checks>> (which locker transitions), <<Zkl-ISA-unpriv.adoc#KLEE-GR-narrowing>> (_Privilege Violation_), <<Zkl-ISA-unpriv.adoc#KLEE-GR-rbg-failure>> (_Invalid_, not _Failure_); outside the GR series, Rule <<Zkl-ISA-unpriv.adoc#KLEE-SR-handler-duty>>.
--

[[KLEE-Principle-14,P14]]
P14: _Exceptions are raised only for error conditions that the fall-through mechanism would misreport_::
+
--
An instruction traps only for an error condition that falling through would misreport. There are four: a malformed or reserved encoding; a sequencing error that would silently lose a CC; a use of unconfigured infrastructure, as opposed to an inert locker; and a policy violation, which the policy owner must see, not the caller. These checks precede every check that depends on the locker's _State_, so that fall-through (<<KLEE-Principle-12>>) is never mistaken for an error.

*Rules.* First half of <<Zkl-ISA-unpriv.adoc#KLEE-GR-klml-openings>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-mgmt-klmanagedlocker-check>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-outcome-by-state>> (the trap legs), <<Zkl-ISA-unpriv.adoc#KLEE-GR-iobuf-configured>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-success-failure-cannot-be-set-directly>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-usage-locker-config-state>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-management-check-order>>.

== Design Decisions

A _Design Decision_ is a mechanism that two or more Principles select together, and from which a group of rules follows. It is not a Principle: another mechanism could satisfy the same Principles. It is stated separately because the rules derive more easily from it.

[[KLEE-decision-1,D1]]
D1: _The Metadata Header_::
+
--
A locker is described by a 128-bit header carried with its CC, the MDH, which alone determines what the locker is, what it admits and how large it is. It is the architected description that <<KLEE-Principle-1>> requires, it names the algorithm as <<KLEE-Principle-3>> asks, and it is one fixed-size header rather than a table or a set of registers (<<KLEE-Principle-4>>). Its layout minimizes the lookahead to identify a locker (<<KLEE-Principle-2>>): _Machine_, its policies, _State_ and _StateExtension_ lie in the first 32 bits, and the fields that fix every length in the first 64, so that one GPR on RV32 identifies the locker and two size it (<<Zkl-ISA-unpriv.adoc#KLEE-length-rule>>).

Hence the _State_ field alone identifies the points software must recognize; an Error-State locker _is_ its MDH, and is exported and imported as such; an _Unconfigured_ locker reads as the one MDH value that is not an MDH; a management operation restores exactly the MDH it was given; and implementation-defined progress lives outside the Content, so that every operation can restart from the Content.

*Rules.* <<Zkl-ISA-unpriv.adoc#KLEE-GR-state-identifies-cc>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-clear-locker-content-error-state>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-error-state-locker-is-only-MDH>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-error-state-exported-as-MDH>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-getmd-to-from-unconfigured>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-completion-state>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-long-running-progress>>.
--

[[KLEE-decision-2,D2]]
D2: _The outcome of an instruction on a locker_::
+
--
<<KLEE-Principle-11>>, <<KLEE-Principle-12>> and <<KLEE-Principle-14>> assign one outcome to each State group; <<KLEE-Principle-10>> adds the Configuration States and <<KLEE-Principle-6>> the configuration instructions. Together they select one rule, <<Zkl-ISA-unpriv.adoc#KLEE-GR-outcome-by-state>>, to which the rules below add their specifics: leg 1 is <<KLEE-Principle-12>>, leg 2 is <<KLEE-Principle-14>>, leg 3 combines <<KLEE-Principle-14>> and <<KLEE-Principle-11>>, and the last paragraph is the part of <<KLEE-Principle-14>> that does not depend on the locker. <<Zkl-ISA-unpriv.adoc#KLEE-GR-gate-order>> orders the checks within each leg.

*Rules.* <<Zkl-ISA-unpriv.adoc#KLEE-GR-outcome-by-state>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-klml-no-managed-locker>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-no-exec-in-ready>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-success-failure-cannot-be-set-directly>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-success-failure>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-policy-narrowing-state>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-usage-locker-error-state>>–<<Zkl-ISA-unpriv.adoc#KLEE-GR-cleared-under-management>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-usage-locker-config-state>>, and the summary table <<Zkl-ISA-unpriv.adoc#KLEE-insns-on-unconf-or-error-locker>>.
--

[[KLEE-decision-3,D3]]
D3: _The Error-State architecture_::
+
--
An Error State is a value of the _State_ field, so an Error-State locker is its MDH alone (<<KLEE-decision-1>>): it holds nothing else, and its Content and ADS are released on entry (<<KLEE-Principle-5>>). It got there by misuse or by an unrecoverable failure (<<KLEE-Principle-11>>), and stays there, inert (<<KLEE-Principle-12>>, leg 1 of <<KLEE-decision-2>>), so that the original error remains readable until software reconfigures it, which it always can (<<KLEE-Principle-6>>). Being only an MDH, it is exported and imported as one, without a management operation; a handler that cannot resolve a condition records it by setting the Error State itself.

*Rules.* <<Zkl-ISA-unpriv.adoc#KLEE-GR-clear-locker-content-error-state>>–<<Zkl-ISA-unpriv.adoc#KLEE-GR-usage-locker-error-state>>, <<Zkl-ISA-unpriv.adoc#KLEE-error-state-transfer>>, the error list of <<Zkl-ISA-unpriv.adoc#KLEE-error-architecture>>, Rule <<Zkl-ISA-unpriv.adoc#KLEE-SR-handler-duty>>.
--

[[KLEE-decision-4,D4]]
D4: _The management operation protocol_::
+
--
A management operation is one operation spanning several instructions (<<KLEE-Principle-10>>): a `kl.mgmt` opens it, transfer instructions move the image, a `kl.mgmt` closes it. Between them the locker is in a Configuration State, which only configuration instructions may touch. The opening for provisioning or import is a destructive configuration instruction: it is admitted in every State (<<KLEE-Principle-6>>) and zeroizes the locker and frees its resources before any check that can fail (<<KLEE-Principle-5>>), which also lets the capacity check count the locker's own allocation as free, so that a CC can be reconfigured in place. At most one operation per hart is in flight, named by the managed locker (<<KLEE-decision-5>>); a second one nests by exporting the first.

*Rules.* <<Zkl-ISA-unpriv.adoc#KLEE-GR-opening-locker-when>>–<<Zkl-ISA-unpriv.adoc#KLEE-GR-completion-state>>, <<Zkl-ISA-unpriv.adoc#KLEE-destructive-config>>, the `kl.mgmt` exception of <<Zkl-ISA-unpriv.adoc#KLEE-exception-state-change>>, <<Zkl-ISA-unpriv.adoc#KLEE-locker-management>>, <<Zkl-ISA-unpriv.adoc#KLEE-nested-mgmt>>; outside the GR series, Rules <<Zkl-ISA-unpriv.adoc#KLEE-SR-klmanagedlocker-write>>–<<Zkl-ISA-unpriv.adoc#KLEE-SR-never-clear-exporting>>.
--

[[KLEE-decision-5,D5]]
D5: _The managed locker architecture_::
+
--
At most one CC per hart is in transit at a time, together with its authentication and identification information `SIV`, `IMPQUAL` and `SIV2`: these registers exist once per hart (<<KLEE-Principle-4>>), so a second management operation must first save the first by a nested export. The pointer `klmanagedlocker` names the locker of the CC in transit, so that a management routine needs no locker number (<<KLEE-Principle-2>>). The pointer follows the CC when it moves, becomes "none" when the CC ceases to exist, is kept when the operation completes or fails so that the outcome stays readable, and is otherwise written only by software.

The instructions that take the pointer are the minimum that management routines need, since hardware complexity is added only where it saves the most code (<<KLEE-Principle-2>>): the management and inspection instructions take it, because one routine written for the pointer replaces 32 written for fixed lockers; the usage instructions do not, because cryptographic code can address fixed lockers.

With <<KLEE-Principle-12>> and <<KLEE-Principle-14>>: opening a second operation on another locker while the pointer is in use is a sequencing error and traps; naming the managed locker when there is none falls through for every instruction but an opening, which has nothing to open and traps.

*Rules.* <<Zkl-ISA-unpriv.adoc#KLEE-GR-locker-less-transfers>>–<<Zkl-ISA-unpriv.adoc#KLEE-GR-klmanagedlocker-updates>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-zkl-load-mv-allowed>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-zkl-store-mv-allowed>>, pointer bullet of <<Zkl-ISA-unpriv.adoc#KLEE-GR-conflicting-access-rule>>.
--

[[KLEE-decision-6,D6]]
D6: _The resumption architecture_::
+
--
Since every operation is atomic or prefix-complete (<<KLEE-Principle-10>>) and the hart keeps one progress register (<<KLEE-Principle-4>>), `klstart` records the prefix-complete point of whichever resumable instruction is in flight, in bytes, and `vstart` the same point in elements where a vector operand is involved. Interruption points are of two kinds. Those the architecture defines, per instruction and per Machine State, are part of the CC: `klstart` and the State record them, and a restored CC resumes from them (<<KLEE-Principle-7>>). Those an implementation defines, inside a long-running operation, are not: the operation records its progress in _MachineUse_ and the ADS, so that it is architected and not hidden (<<KLEE-Principle-1>>), but an import, a clone or another implementation may discard it and restart from the Content. The issuing hart never observes the asynchrony: a conflicting access waits for completion or a precise halt, and interposed software saves and restores `klstart` around its own use.

*Rules.* <<Zkl-ISA-unpriv.adoc#KLEE-GR-klstart-vstart>>, <<Zkl-ISA-unpriv.adoc#KLEE-CSR-klstart>>, <<Zkl-ISA-unpriv.adoc#KLEE-GR-uninterruptible-instructions>>–<<Zkl-ISA-unpriv.adoc#KLEE-GR-memory-instructions>>, <<Zkl-ISA-machines.adoc#KLEE-MGR-progress-discard>>; outside the GR series, Rules <<Zkl-ISA-unpriv.adoc#KLEE-SR-klstart-save>>–<<Zkl-ISA-unpriv.adoc#KLEE-SR-klstart-no-reset>>.
--
