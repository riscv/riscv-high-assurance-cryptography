[[ACE-priv]]
== Book 3. Privileged Architecture

The ACE Privileged Architecture consists of CSRs and optional custom instructions to implement parts of the unprivileged ISA.

We refer to the ACE Unprivileged Architecture for the definitions of ACE instructions and the categories of _configuration_ and _usage_ instructions, including the meaning of “to use a CR”.

If `Zklv` or `Zklio` is implemented and the hart is not an M-mode-only hart: `misa` must implement the `L` bit, `*status` must implement `ACES`.

On M-mode-only systems:::

* None of the extensions in <<ACE-priv-extensions>> are mandatory.
* `Smacecrstatus` implies `mlcrstatus` is implemented and shadowed in `slcrstatus`.
* `Smacecsk` is allowed.
* If `Smacelclt` is implemented, the `macelocality` CSR group is implemented to set the Locality MLocality (see <<ACE-Localities>>).
* If `Smacepbootscrt` is implemented, the `macephysbootscrt` CSR group is implemented to set the Physical Boot Secret Locality.

On an M+U system:::

* `Smacecrstatus` is mandatory: `mlcrstatus` is implemented and shadowed in `slcrstatus`.
* `Smacecsk` is allowed.
* If `Smacelclt` is implemented, the `macelocality` CSR group is implemented to set the Locality MLocality (see <<ACE-Localities>>).
* If `Smacepbootscrt` is implemented, the `macephysbootscrt` CSR group is implemented to set the Physical Boot Secret Locality.

On an M+S+U system:::

* `Smacecrstatus` is mandatory: `mlcrstatus` and `slcrstatus` are implemented and are distinct.
* `Smacecsk` is allowed.
* If `Smacelclt` is implemented, both `macelocality` and `sacelocality` CSR groups are implemented to set the Localities MLocality and SLocality, respectively. (see <<ACE-Localities>>).
* If `Smacepbootscrt` is implemented, the `macephysbootscrt` CSR group is implemented to set the Physical Boot Secret Locality.

On an M+S+U system with the H extension:::

* `Smacecrstatus` is mandatory: `mlcrstatus`, `slcrstatus`, and `vslcrstatus` are implemented and are distinct.
* `Smacecsk` is allowed.
* If `Smacelclt` is implemented, the `macelocality`, `hacelocality`, and `sacelocality` CSR groups are implemented to set the Localities MLocality, HLocality, and SLocality, respectively. (see <<ACE-Localities>>).
* If `Smacepbootscrt` is implemented, the `macephysbootscrt` CSR group is implemented to set the Physical Boot Secret Locality.
* If `Smacevbootscrt` is implemented, the `hacevirtbootscrt` CSR group is implemented to set the Virtual Boot Secret Locality.

These CSRs, with the exception of the `macecsk` group (if present),

Any attempt to read or write them in these situations will result in an illegal-instruction exception.
Therefore, ACE does not need integration in `Smstateen`/`Ssstateen`.

[[ACE-ACE-field-in-misa]]
==== ACE field in `misa`

{empty}
(((CSR, ACE field in `misa`)))
Bit `L` (11) of `misa` indicates that the ACE extension is present.
If ACE is implemented, this bit must not be read-only zero.

If an emulated ACE unit is provided by M-mode firmware, this bit can be set to 1 by the latter.
`misa.L` cannot be cleared by M-mode firmware without first zeroizing all (emulated) ACE state.

[WARNING]
====
This allocation is provisional and has not been agreed with the RISC-V Architecture
Review Committee. Presence of ACE may instead be discovered by other mechanisms, in
particular the unified discovery mechanism, which is the direction RISC-V has taken for
recent extensions and which does not consume a `misa` bit; bit `L` (11) may also be
allocated to another extension. Implementers should expect this subsection to change, and
should not treat `misa.L` as a stable interface until the question is settled.
====

[[ACE-ACES-field-in-mstatus]]
==== ACE Context Status in `mstatus` and `sstatus`

{empty}
(((CSR,ACES field in mstatus)))
(((CSR,ACES field in sstatus)))
An ACE context status field, `ACES`, is added to `mstatus`[26:25] and shadowed in `sstatus`[26:25].
It is defined analogously to the floating-point context status field, `FS`, and the vector context status field, `VS`.

[WARNING]
====
The choice of `mstatus`[26:25], and of the corresponding bits of `sstatus` and
`vsstatus`, is provisional and has not been agreed with the RISC-V Architecture Review
Committee. Those bit positions are contested by other extensions, and ACES may end up at a
different offset, in a different register, or be carried by a mechanism other than a
`*status` context-status field. Nothing in this specification depends on the particular
offset: only on there being a two-bit context-status field with the semantics of
<<ACE-aces-encoding>>, defined analogously to `FS` and `VS`.
====

[[ACE-aces-encoding]]
.Encoding of the ACES field
[float="center",align="center",width="100%",cols="^8%,<8%,<84%",options="header"]
|===
|Value |Name |Meaning
|   0   | Off     | ACE disabled. The ACE state is inaccessible. Executing any ACE instruction or accessing any ACE-specific CSR raises an illegal-instruction exception.
|   1   | Initial | ACE enabled. No CR or the ACEIOBUF is configured. The hart may issue any ACE instruction.
|   2   | Clean   | ACE enabled. At least one CR or ACEIOBUF is configured; state matches the last context swap.
|   3   | Dirty   | ACE enabled. At least one CR, ACEIOBUF, or ACE-specific CSR may have changed since the last context swap.
Unconfigured CRs that were previously configured also cause ACES to become Dirty, since context-switching code must erase any stale saved state.
|===


When `mstatus.ACES` is Initial or Clean, any instruction that modifies ACE state sets `mstatus.ACES` to Dirty.
Implementations may also set `mstatus.ACES` to Dirty from Initial or Clean at any time, even in the absence of a state change.

NOTE: Precise management of `mstatus.ACES` is an optimization that software may use to reduce context-switch overhead.

When `mstatus.ACES` is Dirty, `mstatus.SD` is 1;
otherwise, `mstatus.SD` is set in accordance with existing specifications.

NOTE: Writes to `mstatus.ACES` do not modify any ACE state.
Setting ACES to Off, Initial, or Clean does not clear CRs, ACEIOBUF, or ACE CSRs;
any state changes must be explicit and must precede such a write.

In implementations with a writable `misa.L`, the `mstatus.ACES` field may be present even when `misa.L` is clear, analogously to `mstatus.FS` and `mstatus.VS`.

[NOTE]
====
ACE memory instructions are allowed to trap so that implementations have more
flexibility when loading/storing large ACE contexts. Simpler implementations
may defer the load/store process to software using scalar or vector
loads/stores followed by an `ace.exec` move, whereas more performant
implementations may have dedicated hardware to speed up the instructions.
====

[[ACE-ACES-field-VS]]
==== ACE Context Status in `vsstatus`

{empty}
(((CSR,ACES field in vsstatus)))
When the H extension is present, an ACES field is added to `vsstatus`[26:25], defined analogously to `mstatus.FS` and `mstatus.VS`, and tracking the dirtiness of CRs, ACEIOBUF, and all ACE-specific CSRs.

When V=1:

* Both `vsstatus.ACES` and `mstatus.ACES` are in effect.
* Any ACE instruction, including access to ACE CSRs, raises an illegal-instruction exception if either field is Off.
* If neither field is Off, any instruction that modifies ACE state sets both `mstatus.ACES` and `vsstatus.ACES` to Dirty.
* Implementations may set `ACES` to Dirty from Initial or Clean at any time, even without a state change.
* When `vsstatus.ACES` is Dirty, `vsstatus.SD` is 1; otherwise, `vsstatus.SD` is set in accordance with existing specifications.

In implementations with a writable `misa.L`, `vsstatus.ACES` may be present even when `misa.L` is clear.

NOTE: `mstatus.ACES` and `vsstatus.ACES` are not considered ACE context state
for the purposes of state tracking, and hence writes to `vsstatus.ACES` do not set `mstatus.ACES` to Dirty.

[[ACE-CSR-lcrstatus]]
==== `mlcrstatus`, `slcrstatus`, and `vslcrstatus` for Dirtiness Tracking

{empty}
(((CSR, `mlcrstatus`)))
(((CSR, `slcrstatus`)))
(((CSR, `vslcrstatus`)))
The 64-bit registers `mlcrstatus`, `slcrstatus`, and `vslcrstatus` track per-CR status, including dirtiness, at all levels below M-mode, S-mode, and VS-mode, respectively.

For each of these 3 CSRs:

* `*lcrstatus`(__i__) = `*lcrstatus`[2{interpunct}__i__+1:2{interpunct}__i__] is a two-bit field that encodes four possible status values for ``K(``__i__``)``, as described in the following table.
+
--
[[ACE-lcrstatus-encoding]]
.Encoding of the `*lcrstatus` bits
[float="center",align="center",width="100%",cols="^8%,<12%,<80%",options="header"]
|===
| Value | Name           | Behavior
|   0   | Off            | The CR is inaccessible.
|   1   | Initial        | The CR is accessible and in an initial state as defined by software.
|   2   | Clean          | The CR is accessible and its state matches the last context swap.
|   3   | Dirty          | The CR is accessible and its state may not match the last context swap.
|===
--

`*lcrstatus` is evaluated only if the ACE instruction raises none of: an illegal-instruction
exception, on any of the grounds listed in <<ACE-error-architecture>>; `ace_exc_no_csk`;
`ace_exc_complete_cr_data_access`.

For `mlcrstatus`:::
+
--
When the privilege mode is (H)S, VS or U/VU:

* Attempts to execute an ACE instruction using ``K(``__i__``)``
when `mlcrstatus`(__i__) is 0 (Off) raise an `ace_exc_CR_off` exception.

* Any instruction that modifies ``K(``__i__``)`` sets `mlcrstatus`(__i__) to Dirty.

Any direct write to `mlcrstatus`(__i__) does not change either `slcrstatus`(__i__) or `vslcrstatus`(__i__) (if defined).

`mstatus.ACES` is also in effect.
--


For `slcrstatus`:::
+
--
When the privilege mode is VS, U, or VU:

* Attempts to execute an ACE instruction using ``K(``__i__``)``
when either `mlcrstatus`(__i__) or `slcrstatus`(__i__) is 0 (Off) raise an `ace_exc_CR_off` exception.

* Any instruction that modifies ``K(``__i__``)`` sets `slcrstatus`(__i__) and `mlcrstatus`(__i__) to Dirty.

Any direct write to `slcrstatus`(__i__) does not change either `mlcrstatus`(__i__) or `vslcrstatus`(__i__) (if defined).

`sstatus.ACES`, `mstatus.ACES`, and `mlcrstatus` are also in effect.
--


For `vslcrstatus`:::
+
--
`vslcrstatus` exists only when the H extension is implemented.

When V=1, `vslcrstatus` substitutes for `slcrstatus`: CSR accesses that would target `slcrstatus` instead access `vslcrstatus`, analogously to `vsstatus` and `sstatus`.

When the privilege mode is VU:

* Attempts to execute an ACE instruction using ``K(``__i__``)``
when any one of `mlcrstatus`(__i__), `vslcrstatus`(__i__), or `slcrstatus`(__i__) is 0 (Off) raise an `ace_exc_CR_off` exception.

* Any instruction that modifies ``K(``__i__``)`` sets `vslcrstatus`(__i__), `slcrstatus`(__i__) and `mlcrstatus`(__i__) to Dirty.

Any direct write to `vslcrstatus`(__i__) does not change either `mlcrstatus`(__i__) or `slcrstatus`(__i__) (if defined).

`sstatus.ACES`, `vsstatus.ACES`, `mstatus.ACES`, `slcrstatus`, and `mlcrstatus` are also in effect.
--

On RV32, 32-bit CSRs `mlcrstatush`, `slcrstatush`, and `vslcrstatush` shadow bits [63:32] of `mlcrstatus`, `slcrstatus`, and `vslcrstatus`,
respectively, allowing these bits to be accessed.

[NOTE]
====
The _Off_ value, with the `ace_exc_CR_off` exception, provides the architectural hook for on-demand (lazy) CR loading. At context restore, a handler may leave a CR unrestored and set its `*lcrstatus` field to _Off_, keeping the authoritative SCC in its own memory. The next access to the CR from a lower-privileged mode traps with `ace_exc_CR_off`, and the handler imports the SCC before resuming execution. There is no distinct architectural "lazy" state: tracking which privilege level holds the authoritative SCC for a CR marked _Off_ is the responsibility of the software that set it.
====

[[ACE-CSR-macecsk]]
==== `macecsk` Group

{empty}
(((CSR, `macecsk`)))
The optional `macecsk` group consists of XLEN-bit M-mode RW CSRs: eight in RV32, four in RV64.

A write to the __i__-th CSR sets bits [(_i_+1)·XLEN−1 : _i_·XLEN] of the CSK.

This CSR group is accessible whenever ACES is not Off and `misa.L` is set.
Access outside M-mode raises an illegal-instruction exception.

A CSK can only become active if all eight (respectively, four) CSRs have been written to.
A mechanism for ensuring this is the following:

* The implementation maintains a per-hart set of flags indicating which CSRs in the group have been written to.
* These flags are initially unset.
* When M-Mode firmware writes to a CSR in the `macecsk` group, the implementation sets the corresponding flag, and keeps a copy of the value written so far. While any of the flags is set, reading any of the registers in this group will return the old value.
* Once all flags have been set, the values written by M-mode firmware are activated and replace the old values atomically, and the flags are cleared. The new CSK can now be used for cryptographic operations, and reading any of the registers in this group will return the new value.
* Any mode change to M-mode resets the flags and discards the partially written value, so that M-mode always begins a configuration attempt from a clean state and a partial key is never activated.
* A transition of the hart out of M-mode does *not* clear the flags: a partially written CSK persists, and the ACE unit stays unavailable, until M-mode is next entered.
* Any ACE unit reset clears the write-tracking flags and discards the partially written value.
* While any of the flags is set, that is while a CSK is partially written, the ACE unit is not available: any attempt to execute an ACE instruction, or to access an ACE CSR other than those named in <<ACE-CSK-requirements>>, raises ACE exception `ace_exc_no_csk`. Because activation clears the flags, the unit becomes available again as soon as the group has been written in full.

[NOTE]
====
The last two rules work together. Since the flags survive leaving M-mode, a CSK write sequence
that was interrupted before completion is not silently lost: the next ACE access from any mode
traps with `ace_exc_no_csk` and M-mode learns of it. Because entering M-mode resets
the flags, the handler is free to restart the CSK provisioning sequence.
====

The ACE unit is unavailable until a CSK is established as described in <<ACE-CSK-requirements>> (immediately, in the case of a fixed or randomly regenerated hardwired CSK).

[[ACE-out-of-reset-priv]]
=== ACE Privileged State out of Reset

This section and <<ACE-out-of-reset-unpriv>> are the authoritative statement of ACE state out of
reset.

Out of ACE unit reset:

. The value of the bit `L` of `misa` is 1 if the ACE unit and the ACE ISA are at least partially implemented in hardware.
   In the case of an emulated ACE unit, `L` is 0.
. The `ACES` field of `mstatus`, of `sstatus` and, where implemented, of `vsstatus` is Off.
. The CSK is unconfigured, unless it is hardwired or randomly regenerated.
. `macephysbootscrt` and `hacevirtbootscrt` are zero.
. `macelocality`, `hacelocality`, and `sacelocality` are zero.
. All fields of `mlcrstatus`, `slcrstatus`, and `vslcrstatus` are set to _Initial_.

// ////////////////////////////////////////////////////////////////////
