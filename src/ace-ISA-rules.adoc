[[ACE-common-rules]]
== Common Rules

_This chapter is normative. It is not yet included by `ace.adoc`._

This chapter collects statements that the specification currently repeats at many sites. Each rule
is written so that it can be stated once here and deleted from the places listed under *Replaces*.
The counts are occurrences in the current text of Books 1, 2 and 3.

Three of the defects found in review — a GCM footnote that described a `last_blk_len` range
belonging to other modes, an `Smstateen` paragraph duplicated in two Books, and a transfer-counter
description given twice with different wording — arose from copies of one statement drifting apart.
Single-sourcing them is the point of this chapter; the reduction in length is secondary.

A rule is listed under <<ACE-rules-unverified>> instead of below when the sites it would replace are
*not* known to agree. Those must be checked site by site before the rule is adopted, because
adopting one of them silently changes behaviour wherever a site differs.

*Rules already applied.* R1, R2 and R4 are no longer listed in this chapter, which is why the
numbering has gaps. R3, R5, R7, R8, R9, R10, R12, R13, R16, R17, R18 and R20 are kept below, each with a *Status* paragraph, because
their consolidated wording is worth consulting. Their landing places are:

[[ACE-rules-instructions]]
=== Rules for the Instruction Descriptions


[[ACE-rule-cr-operand]]
==== R3. Direct and indirect CR addressing

An instruction that names one CR carries a selector bit `r` at the position shown in its encoding
diagram: `r` = 0 when the CR index is a 5-bit immediate, `r` = 1 when it is held in the GPR named by
the same field. An instruction that names two CRs carries a two-bit field `R` instead, encoded as in
<<ACE-instruction-clone>>. Using `X0` as an indirect CR index raises an illegal-instruction
exception except where an encoding assigns it a meaning, and an indirect index outside [0..31] does
likewise.

*Replaces:* the selector-bit sentence in `ace.exec`, `ace.setst`, `ace.mgmt`, `ace.getmd*` and
`ace.restrict*`, and the two `ace.mv` sentences that restate it.

*Status: applied.* Merged into `GR1`, which was previously “Indirect CR index” and carried only the
validity constraints. Encoding first, validity second, in one rule: “indirect” now has a definition
before `GR1` constrains it, and nothing had to be renumbered. The term is *addressing*, not indexing
and not indirect addressing, because the rule covers `r` = 0 as well and because that is the word
already used where CRs are introduced.

Five sentences went outright and two `ace.mv` sentences lost a clause. The five had drifted apart in
wording — “the context is encoded as an immediate”, “the context is an immediate”, “takes the value
0 if the context is encoded as an immediate in Bits [11:7]” — and each named a bit position that the
encoding diagram directly above it already showed.

Three things stayed. `ace.clone` keeps its definition of the two-bit field `R` and the four values it
takes, since that is what `GR1` points at; `ace.derive` keeps its one-line pointer to it. `ace.setst`
keeps the reason its selector sits at bit 20, reworded to stand alone now that the sentence it
referred to is gone: “The selector occupies bit 20 here rather than bit 26, as in `ace.exec`, because
bits [31:25] are taken by `#immed7`.” And the conceptual sentence where CRs are first introduced —
that a CR is addressed directly via an immediate or indirectly via a GPR — stays, since it
introduces the distinction rather than restating the encoding.


[[ACE-rule-mgmt-bookkeeping]]
==== R5. Bookkeeping common to every `ace.mgmt`

Every `ace.mgmt` first checks that `acemanagedcr` holds either the target CR's number or 32, and
raises an illegal-instruction exception if it holds anything else. An `ace.mgmt` that *opens* a
management operation then writes the CR's number to `acemanagedcr`; one that *completes* one writes
32. Both clear `acestart`.

*Replaces:* the first, second-to-last and last step of each of the five step lists in
<<ACE-instruction-manage>>. Each list keeps only the steps peculiar to its operation.

*Status: applied.* Twenty lines removed; the rule is stated in the lead-in of
<<ACE-instruction-manage>>. Applying it also resolved a divergence: four lists ended with
“`acestart` is cleared” and the fifth with “`acestart` is set to 0”. The complete-provisioning
list, left with one step, became a sentence.

[[ACE-rule-rv32-shadows]]
==== R7. RV32 high shadows

On RV32, a 64-bit ACE CSR `X` is accompanied by a 32-bit CSR `Xh` that shadows bits [63:32] of `X`,
so that those bits can be accessed. The shadow has the same privilege as the register it shadows.

*Replaces:* the shadow sentence in `acesivl`/`acesivh`, `acesiv2l`/`acesiv2h`, `aceiql`/`aceiqh` and,
in Book 3, the one covering `mlcrstatus`, `slcrstatus` and `vslcrstatus`.

*Status: applied.* Four sentences removed, three in Book 1 and one in Book 3, and replaced by one
sentence after each of the two CSR tables — six registers in the Book 1 copy, three in the Book 3
copy, which opens “Similarly to <<ACE-CSR-unpriv>>”.

I first wrote a single sentence in Book 1 scoped to both Books. That was wrong, and the general
point applies to every rule in this chapter whose sites straddle the Book boundary: Book 1 is
destined for the Unprivileged Architecture Part of the complete RISC-V specification and Book 3 for
the Privileged Architecture Part, so a rule written in one that governs the other's registers would
end up in a different document from the registers it governs. A cross-reference between the two
copies is welcome; a dependency is not.

Each copy is quantified over *every 64-bit ACE CSR of its own Book*, which is exactly the set that
has shadows: the six SIV, SIV2 and IMPQUAL halves in Book 1, the three `*lcrstatus` registers in
Book 3. Every other ACE CSR is XLEN-bit or 32-bit read-only, so neither quantifier over- or
under-reaches. Both state what the four original sentences left implicit — that a read or write of
the base register itself accesses bits [31:0] on RV32.

Contrary to what this rule first proposed, the shadow *rows* stay in the two CSR tables. Those tables
are register enumerations, and each row carries an address; dropping the rows because the names are
mechanical would leave nine CSRs without one.

[[ACE-rule-secret-csr-groups]]
==== R8. Secret-bearing CSR groups

A *secret CSR group* is a set of XLEN-bit RW CSRs, accessed through Indirect CSR Access, that
together hold one 128-bit or 256-bit secret: four CSRs on RV32 and two on RV64 for a 128-bit secret,
eight and four for a 256-bit one. A write to the __i__-th CSR of a group sets bits
[(_i_+1){middot}XLEN−1 : _i_{middot}XLEN] of the secret. Access from a mode lower than the group's,
or in non-authenticated Debug mode, raises an illegal-instruction exception. Out of ACE unit reset
every such secret is zero, unless it is hardwired or regenerated by hardware.

The groups are then given by one table with columns: group name, secret, privilege, and any rule
peculiar to it.

*Replaces:* five near-identical subsections in Book 3 — `macephysbootscrt`, `hacevirtbootscrt`,
`macelocality`, `hacelocality`, `sacelocality`. `macecsk` keeps a subsection of its own, because its
activation rules and its readback behaviour are not shared with the others.

*Status: applied.* The five subsections became one, <<ACE-CSR-locality-groups>>, plus the table
<<ACE-locality-csr-groups>>; Book 3 lost 38 lines. Two points needed care. The five anchors are
referenced from <<ACE-priv-extensions>> and from <<ACE-locality-indexes>> in Book 1, so each is kept
as an inline anchor with a reftext in its table row rather than deleted with its heading. And the
condition under which each group exists, which the subsections stated unevenly — only `hacelocality`
said so explicitly — is now a column of the table, so the five are stated in the same terms.

[[ACE-rule-reset-values]]
==== R9. Reset values are stated only in the reset sections

<<ACE-out-of-reset-unpriv>> and <<ACE-out-of-reset-priv>> are the authoritative statements of ACE
state out of reset. No CSR description restates its own reset value.

*Replaces:* the per-CSR reset sentences in Books 1 and 3.

*Status: applied.* Eight sentences removed, three from Book 1 — `aceiobuftop`, `acestart`,
`acemanagedcr` — and five from Book 3 — `misa.L`, `mstatus.ACES`, `vsstatus.ACES`, the CSK, and the
Locality Secrets. Both reset sections now open by declaring themselves authoritative. Three points
needed care.

One reset value was *not* in either reset section and had to be added before its statements could be
deleted: that the `ACES` field is Off out of reset, which only the two `*status` subsections gave.
Removing them first would have lost it.

Two statements of the `misa.L` reset value disagreed: its own subsection said “1 if the ACE unit is
implemented and 0 otherwise”, while <<ACE-out-of-reset-priv>> distinguishes a unit implemented in
hardware from an emulated one, for which `L` is 0. The latter is the one that survives, and it
agrees with the sentence immediately below it about M-mode firmware setting the bit for an emulated
unit.

One sentence was kept although it matched the search: “Their values out of ACE unit reset identify
the version of the ACE unit. Software cannot modify these values”, in <<ACE-CSR-impl-ids>>. It
states what those values *mean* and that they are read-only, not what they are, so the reset
sections do not cover it.

[[ACE-rules-algorithms]]
=== Rules for the Algorithm Descriptions

[[ACE-rule-block-iteration]]
==== R10. Block iteration

In a state that processes whole blocks, an `ace.exec` whose `ACELEN` is a whole multiple of the
block size `b` performs the state's per-block operation `ACELEN`/`b` times, taking the blocks of
`INPUT`, and producing the blocks of `OUTPUT`, from the least significant position upwards. A state
that this specification describes as processing a single block — every last-block, finalize, verify
and output state — is excluded and processes exactly one.

*Replaces:* the restatements across ECB, CTR/XCTR, XEX, GCM, GCM-SIV, OCB, CMAC, Ascon-AEAD128 and
Ascon-Hash256.

*Status: applied.* Seventeen restatements removed, not the fourteen first counted — two were written
`ACELEN > b` inside a single pair of backticks and escaped the search. Book 2 lost 62 lines. The
rule is item 4 of <<ACE-general-rules-for-algorithms>>, and it absorbed the `foreach` loop that <<ACE-ECB-mode>>
used to carry, which was the only place the block indexing was written out.

The sites stated their condition in three incompatible ways: “If `ACELEN` > `b`”, “If `ACELEN` is a
multiple of `b`”, and, in one case, “If `ACELEN` {ge} 128”. The first is strictly wrong — it
excludes `ACELEN` = `b`, the ordinary single-block case — and the rule now covers all of them by
giving the count as `ACELEN`/`b`. GCM's _Decrypt_ sentence also mixed the two notations, decrypting
“each 128-bit block of `INPUT` into the corresponding `b`-bit block of `OUTPUT`”.

Each of the states that lost the sentence now carries the marker “(multi-block)” before the Form it
expects, so that `AGR4` is visibly the thing that governs it. There are 18 such states: the 17 from
which text was removed, plus State _Encrypt_/_Decrypt_ of the generic tweakable block cipher, which
iterates by its Parameters but never carried the sentence.

The states left unmarked divide cleanly: either they process exactly one block, or they iterate by a
different mechanism — Subalgorithm `process_VLI`, the output-squeeze loop of the generic hash and
MAC section, or the long-field transfer counter of R17. `AGR4` governs none of those.

One sentence of the same shape was kept: <<ACE-Ascon-Hash256>>'s _Hash_Finalize_ writes successive
64-bit fields of `OUTPUT` and restarts at `OUTPUT`[63:0] when a further `ace.exec` is issued. That
is a different rule, not block iteration over an input.

[[ACE-rule-input-truncation]]
==== R11. An over-long input is truncated

Where a state consumes a single value of `X` bits, an `ACELEN` greater than `X` is truncated: only
the `X` least significant bits of `INPUT` are considered, and the rest are ignored. `X` is the width
of the field being set, which is not necessarily `b`.

*Rejected: not useful.* This was applied and reverted. The nine restatements were replaced by the
sentence “Rule AGR6 of <<ACE-general-rules-for-algorithms>> applies.”, and the result read worse
than what it replaced: the reader of a state lost a short, complete clause and gained a pointer to
another section, for no saving in length.

The general lesson, which applies to the rules still open in this chapter: consolidation is worth
doing when the restatement can simply be *deleted*, because a general rule already implies it and
the reader loses nothing — R10 and R13 are of that kind. It is not worth doing when a pointer has to
be left behind in its place. A cross-reference is only an improvement over a repeated sentence when
the sentence is long, or when the copies have drifted apart; here each was one clause, and they
agreed.

The nine sites were also more than the seven first counted: two are embedded mid-sentence, in the
generic tweakable block cipher and in CMAC's _Hash_Absorb_Last_Block_, and CMAC writes the words in
the other order. Should this ever be revisited, those are the two to notice.

[[ACE-rule-output-clearing]]
==== R12. Unwritten output bits are cleared

When a state writes fewer than `ACELEN` bits to `OUTPUT`, the remaining bits of `OUTPUT` are
cleared.

*Replaces:* nothing. The rule is stated, the local statements stay.

*Status: applied as a rule only.* `AGR7` gives the property a single normative home, but the three
Algorithms that state it keep their sentences, at the author's instruction: each is a clause in the
middle of a state description, exactly the case the R11 episode showed is worse off for being
replaced by a pointer.

What the rule did buy is concision, because the three sites had been cross-referencing *each other*
in the absence of a general rule. <<ACE-hash-functions>> ended with “This matches the rule stated for
CMAC in <<ACE-CMAC-mode>>”, and Ascon-Hash256 with “as in <<ACE-CMAC-mode>> and
<<ACE-hash-functions>>”. Both pointers are gone, and CMAC's sentence lost its redundant
`ACELEN` > `b` guard.

*Open: Ascon-AEAD128 says something else.* Its _Enc_Last_Block_ and _Hash_Output_ each end
“(Only the 128 lsbs of `OUTPUT` are written to.)”, which is not what `AGR7` says: not written is not
the same as cleared, and with `ACELEN` > 128 the two give different results. These two sentences were
counted among this rule's sites when it was first drafted, wrongly. They are untouched, and the
question of which behaviour is intended is open.

[[ACE-rule-ready]]
==== R13. State _Ready_ accepts no `ace.exec`

No `ace.exec` may be issued in State _Ready_; issuing one transitions the CR to Error State
_Invalid_, as <<ACE-general-rules-for-algorithms>> prescribes for any instruction a state does not allow.

*Replaces:* the per-Algorithm restatements.

*Status: applied.* Eleven restatements removed, not the nine first counted, and the rule is `AGR3`.
It is worded “unless the Algorithm explicitly allows it”, so it is a default rather than an
absolute; the _Ready_ row of the valid-states table in Book 1 was softened to match, since it
previously said flatly that no `ace.exec` may be executed in that state.

The eleven sites stated it in four different ways, and only one of them — the generic hash and MAC
section — gave the consequence, that the CR transitions to Error State _Invalid_. The rule states it
once and derives it from `AGR1`.

Applying the rule also supplies the statement where it was *missing*: CTR/XCTR, SHA-2, SHA-3, KMAC,
HMAC, ECC and ML-DSA never said anything about `ace.exec` in _Ready_, so eleven copies covered ten
Algorithms and left seven uncovered.

Two sites needed more than a deletion. In ECB the sentence was the whole of the _Ready_ behaviour
item, which therefore went with it. In ML-KEM it was the first line of an item whose second line
clears the state fields, so the item was rewritten to keep that clause.

[[ACE-rule-last-block-length]]
==== R14. Entering a last-block state

The transition into a last-block state is made with a Form B `ace.setst` whose auxiliary argument
`Xs` is the length, *in bits*, of the final block. A value outside the range the Algorithm admits
transitions the CR to Error State _Invalid_. The value is a truncation of a block already
transferred, not a transfer length (<<ACE-truncation-vs-length>>).

Each Algorithm states only its own admissible range, since these genuinely differ:

[%autowidth,float="center",align="center",cols="<,^,<",options="header"]
|===
| Algorithm | Admissible `Xs` | Note
| GCM               | 1 {ldots} 127                   | any bit length; cite:[nist-SP-800-38D] is defined over bit strings
| GCM-SIV           | 8 {ldots} 120, multiple of 8    | cite:[RFC8452] is defined over byte strings
| OCB               | 0 {ldots} 120, multiple of 8    | cite:[RFC7253] is defined over byte strings; 0 is the empty case
| CMAC              | 0 {ldots} `b`, multiple of 8    | 0 is the empty-message case
| Ascon-AEAD128     | 0 {ldots} 127                   | 0 transitions directly, with `pad(∅,128)` applied
|===

*Replaces:* five restatements of the shape, and removes the footnote in <<ACE-GCM-mode>> that
currently points at “the other modes that take a final-block length” as though their ranges agreed
with GCM's, which they do not.

[[ACE-rule-verification]]
==== R15. Verification outcomes

A state whose purpose is to verify a tag, a MAC or a signature transitions to _Success_ when the
value matches and to _Failure_ when it does not. Neither outcome is an error: no exception is
raised, the CR is not invalidated, and the Algorithm has performed as specified.

*Replaces:* eight restatements, in GCM, GCM-SIV, OCB, CMAC, Ascon-AEAD128, <<ACE-ECC>>,
<<ACE-EdDSA>> and <<ACE-PQC-ML-DSA>>. The final sentence is already stated once, under *Algorithmic
Errors* in <<ACE-error-architecture>>.

[[ACE-rule-derived-fields]]
==== R16. Derived fields are recomputed on import

A field that an Algorithm derives from other fields of the same CC is not carried in the Serialized
Context. It is recomputed when the import completes, that is by the `ace.mgmt` with
`#ace_CR_management_end`, and likewise when the value it derives from is set or replaced.

*Replaces:* the intra-Algorithm duplication of the statement, and the timing clause in the
behaviour bullets that state each derivation.

*Status: applied.* The rule is `AGR5`. The case for it was not the number of sites but that three
Algorithms stated it *twice each*, hundreds of lines apart: GCM and GCM-SIV in a Data Structures
NOTE and again in a behaviour bullet, OCB in a table cell and again in a behaviour paragraph. The
two NOTEs are gone — GCM's keeps its unrelated first sentence, about the AD and plaintext lengths
being the caller's business — and the two behaviour bullets shed the timing that `AGR5` now supplies,
keeping the formula, which is the part worth having in place:

`{fournbsp}` `** \`auth_key\` is a derived field (AGR5): \`auth_key <- enc_blk(key, zeros(128))\`.`

Four sites were deliberately left alone, because each says something `AGR5` does not. OCB's
paragraph gives an implementation trade-off — cache the `L` values in the Additional Data Section or
recompute them, the latter likely faster. ML-DSA's derivation of `tr` is conditional on `HasPrivKey`
and comes with the argument that a verification-only CC is functional immediately after import.
EdDSA's says the clamped scalar, `prefix` and public key may be cached rather than recomputed, and
are never exported. OCB's table cell is a one-clause annotation in a field table.

This is the pattern the R11 episode established: delete where the local text adds nothing, keep it
where it does, and state the rule once either way.

[[ACE-rule-long-field-transfer]]
==== R17. Loading and emitting a long field

A state that loads a long field from `INPUT`, or emits one to `OUTPUT`, over several `ace.exec`
instructions records its progress in the _AlgorithmUse_ field of the MDH, as a count of bits. The
count is zeroed on entry to the state, rises monotonically, and is never reset by the completion of
the field. When it reaches the size of the field, no further `ace.exec` is allowed in that state;
issuing one transitions the CR to Error State _Invalid_. On the input side, bits in excess of the
field size in the last transfer are ignored.

`ace.restrict*` may not write _AlgorithmUse_ while an Algorithm uses it in this way
(<<ACE-instruction-restrict>>).

*Replaces:* the counter descriptions in the ML-KEM and ML-DSA `_*_Input_` and `_*_Output_` states.

*Status: applied.* The rule is `AGR9`, and Book 2 lost about forty lines — the largest single
reduction of any rule so far, because here the local text really was bulk: ML-KEM spent a
`process_VLI` invocation plus a nine-line paragraph justifying why `cumul_len` and not `block_base`
carries the count, and ML-DSA repeated the same argument in different words. Each site is now one
sentence of the form asked for: “the fields `encapsk`, `decapsk` and `ciphertext` are loaded using
(multi-block) `ace.exec` instructions of Form B, following rule AGR9”.

Three divergences had to be settled, and two of them resolved themselves.

ML-DSA stated the overflow behaviour on both sides — excess bits of a final input transfer ignored,
an `ace.exec` issued past the end invalidating the CR — and ML-KEM stated neither. `AGR9` adopts
ML-DSA's, which is the complete pair and matches `AGR6`'s treatment of an over-long input, so ML-KEM
gains rules it was missing rather than losing any.

ECC was at first left out of scope, then brought in at the author's suggestion by widening _W_ from
“a field of the MDH” to “a state field _W_, usually _AlgorithmUse_ of the MDH”. Subsuming it took
three further generalisations, each of which the rule now carries: the unit is bits *or* bytes, as
the state says, since ECC counts bytes in `block_base`; the `process_VLI` invocation applies only
“where the loading is performed by `process_VLI`”, since ECC's set states do not use it; and
completion admits an exception — “unless the state defines a transition of its own” — because ECC's
_Output_ transitions to _Success_ where the other states forbid a further `ace.exec`.

That brought in four more sites: ECC's set/output lead-in, its _Set_Generator_, its _Set_ states for
`Scalar`, `Hash`, `SecondPt` and `Signature`, and EdDSA's _Set_Ctx_, which had described itself by
reference to ECC's. Two now-redundant “`block_base` <- 0” steps went with them, since `AGR9` zeroes
_W_ on entry.

The widened rule is worth watching. Three “unless” clauses is close to the point at which a general
rule states less than the sites it replaces; if a fourth exception appears, splitting `AGR9` into an
MDH-counter rule and a byte-counter rule would be better than adding it.

Two smaller things fell out. ML-DSA carried the “entering an _*_Input_ or _*_Output_ state zeroes
_AlgorithmUse_” bullet twice, once in the shared statement and once in its own; `AGR9` absorbs both.
And each site's surviving sentence keeps what is genuinely local: for ML-KEM that its field sizes
come from the size table, for ML-DSA that entering _pubkey_Output_ without `HasPubKey` invalidates
the CR.

[[ACE-rule-progress]]
==== R18. Progress of a long-running operation

Where an implementation interrupts and resumes a long-running operation that transfers no data —
a scalar multiplication, a signature operation, a key generation — it records progress in the
_AlgorithmUse_ field in an implementation-defined way, not in `acestart` (<<ACE-CSR-acestart>>). It
must then export a mandatory Additional Data Section holding the Implementation Qualifier and
whatever else resumption needs, and an importing implementation that does not recognise the
Implementation Qualifier restarts the operation instead of resuming it.

*Replaces:* the restatements in the ECC and PQC sections and the general half of the statement in
Book 1.

*Status: applied.* Six statements, not the three first counted: three paragraphs in the ECC section,
one trailing bullet each in ML-KEM and ML-DSA, two sentences in ML-DSA's Internal State, and four
lines in the `acestart` CSR description. The rule is `AGR8`.

The sites did not agree. ECC required the exporting implementation to provide the Additional Data
Section and told the *importer* to compare `acemvendorid`, `acemarchid` and `acemimpid` against
`IMPQUAL`; ML-KEM and ML-DSA required the Section but said nothing about the comparison. That
comparison is now performed by the import procedure itself, so `AGR8` states the consequence — an
operation interrupted on one implementation and imported on another always restarts — instead of
telling the importer to do the work again.

ECC also gave the importer discretion to discard even on a match, which the PQC sections did not.
`AGR8` resolves this in ECC's favour: an importing implementation may always discard the Section and
restart. Discarding is never unsafe, and ECC has a reason for it that survives as the only text left
in that section — that keeping the Section also means trusting the random number generator of the
originating implementation, and that an importer unwilling to do so discards `RndNum` with it.

[[ACE-rule-zero-padding-caller]]
==== R19. Zero-filling a final partial block is the caller's obligation

Where an Algorithm absorbs associated data, or any input for which it defines no last-block state,
the caller zero-fills the final block beyond the end of the data and the Algorithm absorbs that
block whole. Where an Algorithm *does* define a last-block state, the caller must not pad: padding
in software as well corrupts the result.

*Replaces:* the paragraph in <<ACE-GCM-mode>>, the one in <<ACE-GCM-SIV-mode>> and the one in
<<ACE-Ascon-AEAD128>>, which say the same thing at different lengths.

[[ACE-rule-mdh-row]]
==== FIXED: R20. The MDH is not listed

Every Provisioning Input and every Serialized Context begins with the 128-bit MDH, and every
Internal State contains it. The field tables do not list it.

*Replaces:* the leading `| i | 128 | MDH` row of the per-Algorithm tables and the leading
“Metadata Header.” bullet of the Internal State lists.

*Status: applied by the author.* A short section on data structures common to all Algorithms now
carries the two MDH rows once, and the per-Algorithm tables keep their original lettering, starting
at Position ii. That choice matters: every position reference in Book 2 — `SCC_content_size()` from
Position ii to Position viii, `RndNum` at Position viii, the padding at Pos. x of Ascon-AEAD128 that
Ascon with set Nonce replaces, and EdDSA's Positions xi and xiii — remains valid, which renumbering
from i would have broken. I verified all of them, and that no table now begins at Position i with a
field other than the MDH.

The Metadata Header is retained in an Internal State only where a field of it carries Algorithm
state: _AlgorithmUse_ and _AuxInfo_ in ML-DSA, _AlgorithmUse_ in ML-KEM, _StateExtension_ in ECC.

Two things the pass left behind, now fixed: SHA-2 carried two `*Internal State*` bullets, the first
a one-line summary still naming the Metadata Header, and the surviving list had lost its indentation
where the removed bullet used to sit.

[[ACE-rule-skid-row]]
==== R21. The System Key Identifier alternative is not listed

<<ACE-rules-system-keys>> already states that a key field carries a 64-bit SKID in place of the key
value when _KeyType_ = 1, and that one SKID may resolve to several keys. A field table therefore
gives the key width alone.

*Replaces:* the “`k` or 64 {vbar} `key` or System Key Identifier” form in 25 table rows.

[[ACE-rule-padding-row]]
==== R22. Padding is implicit

The length of a Provisioning Input and of a Serialized Context is understood to be padded at the end
to a multiple of 128 bits, whether or not the Algorithm's table shows a padding row
(<<ACE-Algorithms>>).

*Replaces:* the padding rows of the tables that have them, and the accompanying paragraphs that
enumerate the padding width and the block count for each key size — five such paragraphs. This rule
is already in force; what remains is to remove the rows it makes redundant.

[[ACE-rules-unverified]]
=== Candidate Rules Requiring Per-Site Verification

The following are patterns rather than established rules. Each looks uniform but has at least one
site that may not conform, so none may be adopted before the sites are checked.

. *Entry to State _Ready_ clears the Algorithm's working state and retains its key material.* True
  of the symmetric Algorithms, but <<ACE-PQC-ML-DSA>> deliberately retains `privkey`, `pubkey` and
  their flags, <<ACE-ECC>> makes retention selectable bit by bit through the auxiliary argument of a
  Form B `ace.setst`, and the symmetric Algorithms differ in which working fields they name. Any
  rule here must be a default with explicit overrides.

. *A transition to a state that sets an auxiliary value uses a Form B `ace.setst` when the value
  fits in a GPR and a Form C one when it does not.* Holds at most sites, but GCM uses Form B for a
  length and then Form B `ace.exec` for the value itself, and Ascon-AEAD128 uses Form B for
  `tag_len` without changing the _State_ field at all.

. *An out-of-range auxiliary argument transitions the CR to Error State _Invalid_.* This is the
  single most repeated statement in Book 2, 36 occurrences, and <<ACE-general-rules-for-algorithms>> arguably
  already covers it. Before collapsing them, each site must be checked for whether the consequence
  really is _Invalid_ and not a no-operation: <<ACE-usage-input-output>> already distinguishes the
  two for the ACEIOBUF, and `ace_exc_unconfigured_buffer` is explicitly exempt.

. *`ace.exec` in a state that does not allow the Form issued transitions the CR to Error State
  _Invalid_.* Stated once in <<ACE-Algorithms>> under *State Machine* and again in
  <<ACE-general-rules-for-algorithms>>; the two wordings differ on whether an unavailable Form raises an
  illegal-instruction exception instead, which <<ACE-usage-input-output>> settles. Consolidate the
  three into one statement rather than deleting two of them.

[[ACE-rules-effect]]
=== Estimated Effect

Books 1, 2 and 3 are about 9300 lines. Applying R1–R22 removes on the order of 400 lines outright
and replaces perhaps as many again with four tables — the extension matrix already exists, and R4,
R8 and R14 add one each. The proportion is modest; the reason to do it is that each rule closes a
class of divergence rather than an instance of it.

The largest single item is R1, at about 216 lines, and it is also the safest: the blocks it removes
are already declared subordinate to the matrix that would replace them.
