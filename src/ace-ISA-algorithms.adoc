[[ACE-Algorithms]]
== Book 2. Unprivileged Architecture: Algorithms

_This chapter is normative._

All values, bit slices, concatenations, and finite-field operations in this chapter follow the conventions of <<ACE-Notation>>. Specifically, the byte at the lowest address occupies the least significant bits, and the `@` operator places its left operand in the more significant bits—opposite to the `{vvert}` used by referenced standards. No Algorithm may deviate from these conventions.

This chapter specifies ACE instruction behavior for supported cryptographic Algorithms. Some Algorithms are defined generically for primitives meeting certain properties (e.g., GCM works with AES or SM4), while others are tied to specific primitives (e.g., Ascon).

<<ACE-exec-encodings>> defines the encoding in the MDH field _Algorithm_ of the Algorithms defined in this specification.
This encoding uses two sub-fields: _Type_ in bits [11:4] and _Mode_ in bits [3:0].
For certain classes of Algorithms, _Mode_ is used to specify a subtype.
Other groups of Algorithms may subdivide the _Algorithm_ field differently.

IMPORTANT: Instead of using subextensions, the discovery of the supported Algorithms is done using the instruction `ace.avail`.
The reason is to avoid a proliferation of subextensions.
For instance, we could define `Zklaes128p`, `Zklaes192p`, and `Zklaes256p` for the three key sizes supported by the AES
and also `Zklsm4p` for SM4, whereas we would also define, say,
`Zklctrm`, `Zklxexm`, `Zklgcmm`, and `Zklgcmsivm` for counter mode, XCTR, GCM and GCM-SIV modes, respectively.
So, it is reasonable that an ACE unit implements the four block ciphers and the four modes.
However, an implemented may decide to not support the combination of `SM4` with `GCM-SIV`, since it has not been standardized (this may change at any moment, but the substance of the example does not change).
How would a user that sees `Zklsm4p` and `Zklgcmsivm` know that the combination is not supported?
Providing extension names for all combinations would be unreasonable, therefore we opt for discoverability via `ace.avail`.

=== Definition of an Algorithm in ACE

Each Algorithm is fully defined by the following information:

Parameters:::
+
--
These include:

* The _block size_ `b`, which is the bit length of the basic unit of information processed by the Algorithm, usually the block size of the main underlying primitive;
* The _key size_ `k`, also in bits, for keyed Algorithms; and
* Any other parameter needed to instantiate the Algorithm with compatible primitives.
* The granularity, which is usually the same as `b`. There is always a possible exception for “last blocks”, such as those of AD or plaintext/ciphertext sections, which may be shorter than `b`. If the length of such a “last block” is set explicitly and the next input is longer, the input is automatically truncated: enough of its most significant bits are ignored to bring it to the expected size.
--

Data Structures:::
+
--
These include:

. *Provisioning Input*:
The fields are listed in the order they appear in the PI,
each with its length.
The Provisioning Input is implicitly zero-padded at the end, if necessary, so that its length is a multiple of
128 bits.

. *Internal State*:
Information maintained in the internal state of a CC.
Field ordering is unspecified, and field lengths may differ from those listed—for example, in masked, threshold, or fault-tolerant implementations.
This information is necessary to define the Algorithms and their semantics, and must exist internally, though not necessarily in a prescribed format.

. *Serialized Context*:
The plaintext of the SCC.
The fields are listed in the order they appear in an SCC, each with its length.
The Serialized Context is implicitly zero-padded at the end, if necessary, so that its length is a multiple of
128 bits.
--

Algorithm-Specific Functions:::
Any other function that is specific to the Algorithm.

State Machine:::
+
--
The state machine is defined by the following information:

. A list of the *States* which the Algorithm may assume, including each state's representation as specified in <<ACE-State-field>>.
. A complete list of *allowed state transitions*, including the prerequisites for each transition, the required `ace.setst` Form, and the meaning of any auxiliary parameter, and any other condition that may trigger a transition even without an `ace.setst` instruction.
. The *allowed or expected instructions* and their *semantics* in each State.
  In addition to configuration and export instruction sequences, an Algorithm state typically permits only certain Forms of `ace.exec`, `ace.setst`, and `ace.derive`.
The operation may instead use Form D `ace.exec` or Form C `ace.setst`, with the required ACEIOBUF setup.
Other Forms are prohibited.
Issuing any other instruction that accesses a CR raises an ACE exception.
Use of `ace.input` and `ace.output` is allowed because these operations do not access a CR, and thus are not directly related to its state machine.
The precise statement of the behavior is given by Rule AGR1 in <<ACE-algorithms-other-rules>>.
--

[[ACE-algo-notation]]
==== Notation in the Algorithm Descriptions

The general notation, the representation of values and byte strings, and the
finite-field operations `Galoismul`, `Montmul`, `update_mask` and `double` are defined
in <<ACE-Notation>>. The following symbols are specific to the Algorithm
descriptions.

* `INPUT`: The input data to be processed by `ace.exec` or `ace.setst`. This
  can be the input vector register, or the ACEIOBUF, as described in
  <<ACE-usage-input-output>>.

* `OUTPUT`: The output data produced by `ace.exec`. This can be the output
  vector register, or the ACEIOBUF, as described in <<ACE-usage-input-output>>.

* `ACELEN`: Either `VL*SEW` or the length `aceiobuftop` of the ACEIOBUF in
  bits, that is `aceiobuftop` {times} 8, depending on whether vector registers or
  the ACEIOBUF are used. `ACELEN` is always a number of bits; `aceiobuftop`, like every
  other ACEIOBUF CSR and like `acestart`, is a number of bytes.
  For ACEIOBUF operands, `aceiobuftop` plays the role of `VL` and `acestart` that of
  `vstart`: the operand window is always [0, `aceiobuftop`) bytes, and `acestart` is
  the position within it at which processing starts or resumes
  (<<ACE-CSR-aceiobuftop>>).

[[ACE-algorithm-rules]]
=== General Rules for Algorithms

[[ACE-algorithms-other-rules]]
==== Other General Rules

Besides the SGR (State-Specific General Rules) defined in <<ACE-State-field>>,
the following rules apply to all ACE-supported Algorithms, except when explicitly stated otherwise.

[horizontal]
AGR1:: (Unallowed instructions in Algorithm States.) If
any usage instruction, or Form thereof, that may modify the state of a CR is issued,
which is not explicitly allowed by the current state of the Algorithm
encoded in the CC in the CR, then the CR transitions to Error State _Invalid_.
+
An illegal-instruction exception is raised instead only where the Form is unavailable to the
implementation at all, rather than merely wrong for the state (<<ACE-usage-input-output>>).

AGR2:: (Granularity constraints.)
If `ACELEN` does not satisfy the granularity constraints of the Algorithm in its current state — for instance, it is not a whole multiple of the block size where the Algorithm requires one — the instruction performs no operation and the CR transitions to Error State _Invalid_.

AGR3:: (``ace.exec`` in State _Ready.)
No `ace.exec` instruction may be issued in State _Ready_ unless the Algorithm explicitly allows it;
issuing one otherwise transitions the CR to Error State _Invalid_, by AGR1.

AGR4:: (``ace.exec`` iteration over blocks.)
In a state that processes whole blocks, one `ace.exec` performs the state's per-block operation
`ACELEN`/`b` times, where `b` is the block size: for `i` = 0, `b`, `2b`, {ellipsis}, `ACELEN` − `b`,
in that order, it consumes `INPUT[i+b-1:i]` (if it consumes inputs) and produces `OUTPUT[i+b-1:i]`
(if it produces outputs). Blocks are therefore
taken and produced from the least significant position upwards, here and throughout this
specification, and `ACELEN` = `b` is the single-block case. The states that an Algorithm describes
as processing one block — its last-block, finalize, verify and output states — are excluded, and
process exactly one block whatever `ACELEN` is.
+
This rule applies to all places where `ace.exec` is used in Algorithm descriptions, unless it is explicitly mentioned that `ace.exec` consumes only one block.

AGR5:: (Derived fields are recomputed, not serialized.)
A field that an Algorithm derives from other fields of the same CC is not carried in the Serialized
Context. It is recomputed when an import completes, that is by the `ace.mgmt` with
`#ace_CR_management_end`, and again whenever a field it is derived from is set or replaced. An
Algorithm states only the derivation itself, and marks such a field “(derived)” where it lists it in
its *Internal State*.

AGR6:: (An over-long input is truncated.)
Where a state consumes from `INPUT` a single value of fixed width — the field it assigns, or the
operand it is defined over — an `ACELEN` greater than that width is truncated: only that many least
significant bits of `INPUT` are considered, and the rest are ignored. The width is not necessarily
the block size `b`.

AGR7:: (Unwritten output bits are cleared.)
When a state writes fewer than `ACELEN` bits to `OUTPUT`, the remaining bits of `OUTPUT` are
cleared. This concerns the bits *within* the operand; the elements beyond `VL`, governed by the
tail-agnostic policy of <<ACE-ACEV>>, are a separate matter.

AGR8:: (Progress of a long-running operation.)
An Algorithm may define a long-running operation that transfers no data to or from vector registers or the ACEIOBUF. Examples include: scalar multiplication, key generation, or signature generation or verification. The progress is recorded in the _AlgorithmUse_ field, in an implementation-defined format; `acestart` remains reserved for byte counts (<<ACE-CSR-acestart>>). If progress is recorded, the implementation exports the data necessary to support resumption in the ADS. Any importing implementation may discard this Section and restart the operation. In case of an Implementation Qualifier mismatch, the operation must be restarted. Hence, no internal algorithm-dependent state may be committed until the operation completed, and intermediate results must be

AGR9:: (Loading and emitting a long field.)
A state that loads a long field from `INPUT`, or emits one to `OUTPUT`, using multiple `ace.exec`
instructions records the amount transferred so far in a state field _W_ (e.g., _AlgorithmUse_ of
the MDH). Each such state names _W_ and its unit, bits or bytes. _W_ is zeroed on entry, rises
monotonically, and is not reset when the field completes; entering a loading state also zeroes the
field, so that reloading replaces it. Where the loading is performed by `process_VLI`
(<<ACE-process-VLI>>), it is invoked with `block` = `state` = the field, `max_len` = `b` = `n` = its
size, `cumul_len` = _W_, `mode` = `assign`, and `process_block` and `finalize` both equal to `None`.
+
Once _W_ reaches the size of the field, the transfer is complete. Unless the state defines a
transition of its own at that point, no further `ace.exec` is allowed in it and issuing one
transitions the CR to Error State _Invalid_. Excess data in a final loading transfer is ignored; an
emitting `ace.exec` that would carry _W_ past the field size invalidates the CR. Where _W_ is a
field of the MDH, `ace.restrict*` may not write it (<<ACE-instruction-restrict>>).

[[ACE-truncation-vs-length]]
=== Input and Output Padding, Truncation, Byte Granularity

As a general rule, the caller must pad inputs shorter than a full vector length and pass their actual lengths to the Algorithm, typically through `ace.setst`. This rule does not apply where an Algorithm specifies different handling for cryptographic-security reasons.

Cryptographic inputs are normally supplied through GPRs or vector registers in whole bytes. Standards that permit arbitrary bit lengths are supported by specifying the bit length of the final input piece—usually as an `ace.setst` parameter. The Algorithm then truncates that input internally to the specified length. Outputs are not necessarily truncated; the caller must discard any excess bits.

This occurs, for instance, with the `last_blk_len` parameters in <<ACE-GCM-mode>>, <<ACE-GCM-SIV-mode>>, <<ACE-OCB-mode>>, <<ACE-Ascon-AEAD128>>, and <<ACE-hash-functions>>. Such a parameter specifies a truncation of the passed input, not its length, with the only restriction being that `ACELEN` ≥ `last_blk_len`. Procedure `process_VLI` receives field lengths in bits, but what is received through the `ace.exec` instructions is always at byte granularity, and the last input may be internally truncated.

Where a standard's formula requires a bit count, it is obtained by multiplying the byte count by 8, as with the length block of GHASH in <<ACE-GCM-mode>>.

[[ACE-keystream-modes]]
==== CTR/XCTR Keystream Generation

In CTR mode, the sum of the lengths of IV and counter equals the block size of the underlying keyed PRP or PRF, to whose input they are concatenated.
(((ACE, Algorithm, keystream generation)))

In XCTR modes, both IV and counter have the same size as the block size of the underlying keyed PRP or PRF, and are ``xor``ed together to form its input.

Parameters:::
* `b` = block size (8|`b`).
* `k` = key size (8|`k`).
* `j` = counter size (8|`j`).
* `n` = IV size (8|`n`).
* If the mode is CTR, it is `b = n + j`.
* If the mode is XCTR, it is `b = n = j`.
* Granularity: `b`.

Data Structures:::
* *Provisioning Input*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)   | Field
|  ii  | `k` or 64     | `key` or System Key Identifier
|===
--

* *Internal State*:
 ** `key`: `k` bits.
 ** `IV`: `n` bits.
 ** `ctr`: `j` bits.

* *Serialized Context*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
|  Pos. | Size (Bits)   | Field
|   ii  | `k` or 64       | `key` or System Key Identifier
|  iii  | `n`             | `IV`
|   iv  | `j`             | `ctr`
|===
--

Algorithm-Specific Functions:::
* `keystream_block(p) -> c` -- usually an encryption function.
* `tick_ctr()` -- increases the counter `ctr` by one.

State Machine:::
* *States:*
  ** _Ready_: The CC is ready.
  ** _Operate_: In this state the CC will produce a keystream.

* *Allowed State Transitions:*
 ** _Ready_ -> _Operate_.
 ** _Operate_ -> _Ready_.

* *Behavior:*
 ** In State _Ready_, the `ctr` and `IV` fields are set to 0.
// (`ctr` is set to 1 if the Algorithm is LFSR-based).

 ** To transition to State _Operate_, a Form C ``ace.setst`` instruction must be issued.
  *** This sets the value of `IV` to `INPUT`.
  *** If `ACELEN` > `n`, only the `n` least significant bits of `INPUT` are
      considered. The bound is `n`, the width of the `IV` field, and not `b`: in the
      non-X modes `b` = `n` + `j`, so the IV is narrower than a block and the remaining
      `j` bits of the counter block are supplied by `ctr`, not by `INPUT`. In the X modes
      `n` = `b` and the two readings coincide.

  ** In State _Operate_, (multi-block) ``ace.exec`` instructions are expected to be of Form C.
     “``ace.exec OUTPUT, Kn|K{Xn}``” performs:
+
--
  . If in CTR mode, then:
  .. `tmp ← keystream_block(bswap(ctr) @ IV)`,
  . else: (i.e., if in a XCTR mode)
  .. `tmp ← keystream_block(IV xor ctr)`,
  . `tick_ctr()`, and
  . `OUTPUT ← tmp`.


--

 ** In States _Ready_ and _Operate_, a Form B
    ``ace.setst Kn|K{Xn}, \#ace_state_set_aux_value, Xs`` sets the initial
    counter: `ctr` {leftarrow} `lsb~j~(Xs)`. This is the “set initial counter”
    capability of `Zklctrm` and `Zklxctrm`; it supports random access into a
    keystream, for example to resume an interrupted stream. The _State_ field
    is unchanged: setting the counter is an _operation_, not a state, exactly
    as setting the tweak is in <<ACE-tweakable>>.

NOTE: There is no check on `ctr` wrapping around to its initial value, since a
malicious user could always save the initial CR and reuse it to simulate
a wraparound of the `ctr` even if this were prevented by the Algorithm.
Keystream-reuse discipline for CTR and XCTR remains thus the caller's
responsibility, as in cite:[nist-SP-800-38A-1].

If `ace.setst` is issued to return to State _Ready_, the CC can be reused with a new IV.

Example pseudocode is given in <<ACE-pseudocode-keystream-modes>> (for the case `b` = `ACELEN` = 128).

[[ACE-XEX-XTS-modes]]
==== XEX/XTS modes

The XTS mode was designed for storage confidentiality cite:[DBLP-journals-ieeesp-Martin10] and made into a Recommendation by NIST in 2010 cite:[nist-SP-800-38E]. XTS is based on the XEX construction, formalized by Phillip Rogaway cite:[DBLP-conf-asiacrypt-Rogaway04], to design _Tweakable Block Ciphers_ cite:[DBLP-conf-crypto-LiskovRW02]. A Tweakable Block Cipher (TBC) is a block cipher which, besides the key and the plaintext or ciphertext, also takes a tweak as input. The tweak is used together with the key to select the permutation computed by the block cipher.

The XEX construction builds a TBC `Ẽ` from a block cipher `E`, with key `K`, tweak `T`, and plaintext `P`, as follows:

`{fournbsp}{fournbsp}` `Ẽ(K, T, P) = E(K, P xor M) xor M` `{nbsp}{nbsp}` where `{nbsp}{nbsp}` `M = E(K, T)` `{nbsp}{nbsp}` is called a _mask_.

In XEX mode, once a mask is computed, it is then updated by using a Galois Multiplication for any successive block instead of updating the tweak and encrypting it again.

The NIST standard uses two different keys, one for the data encryption path and one for the encryption of the tweak. We follow this convention.
(((ACE, Algorithm, XEX)))

Parameters:::

* `b` = block size (8|`b`).
* `k` = key size (8|`k`).
* Granularity: `b`.

Data Structures:::

* *Provisioning Input*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
|  Pos. | Size (Bits)     | Field
|  ii   | `k` or 64       | `key1` or System Key Identifier
| iii   | `k` or 0        | `key2` if _KeyType_ = 0, else empty (a single SKID retrieves both keys)
|===
--

* *Internal State*:
 ** `key1`: `k` bits.
 ** `key2`: `k` bits -- omitted if both keys come from an entry in the SKS.
 ** `mask`: `b` bits.

* *Serialized Context*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)   | Field
|  ii  | `k` or 64     | `key1` or System Key Identifier
| iii  | `k` or 0      | `key2` if _KeyType_ = 0, else empty (a single SKID retrieves both keys)
|  iv  | `b`           | `mask`
|===
--

Algorithm-Specific Functions:::

* `enc_blk(K, p) -> c` encrypts block `p` using the key `K`, and returns the result `c`.
* `dec_blk(K, c) -> p` decrypts block `c` using the key `K`, and returns the result `p`.
* `update_mask(mask) -> mask` updates the mask by multiplication with a generator
of GF(2^b^). For `b` = 128 this is the operation defined in
<<ACE-XEX-XTS-modes>>, i.e. multiplication by `x` modulo
`x^128^ + x^7^ + x^2^ + x + 1` in little-endian byte order.  That is,
+
`{fournbsp}{fournbsp}` `update_mask(V)` = `V << 1` `{fournbsp}` if `V[127]` = `0`
+
and
+
`{fournbsp}{fournbsp}` `update_mask(V)` = `(V << 1) xor (zeros(120) @ 0b10000111)`
`{nbsp}{nbsp}` otherwise.
+
An instantiation with `b` {ne} 128 must state its own reduction polynomial.

//  For `b` = 128 the field is GF(2)[`x`] modulo
//  `x^128^ + x^7^ + x^2^ + x + 1`.
//
//  A 128-bit value `V` represents the element whose coefficient of `x^k^` is `V[k]`,
//  as in cite:[nist-SP-800-38E] and IEEE 1619. `update_mask(V)` is multiplication by
//
//  An Algorithm instantiating XEX or XTS with a block size `b` {ne} 128 must state its own
//  reduction polynomial; this specification defines `update_mask` only for `b` = 128.

State Machine:::

* *States:* _Ready_, _Encrypt_, and _Decrypt_ (defined as before, cf. <<ACE-ECB-mode>>).

* *Allowed State Transitions:*
 ** _Ready_ -> _Encrypt_, if encryption is allowed.
 ** _Ready_ -> _Decrypt_, if decryption is allowed.
 ** _Encrypt_, _Decrypt_ -> _Ready_.

* *Behavior:*
 ** In State _Ready_:
  *** The `mask` field is set to zero.
 ** The ``ace.setst`` instruction to transition to either _Encrypt_ or _Decrypt_ is expected to be of Form C.
    It sets the tweak, and the `mask` field is used to store it: `mask <- INPUT`.
  *** If `ACELEN` > `b`, only the `b` least significant bits of `INPUT` are considered.
  *** Then, the following operations are performed:
  . `mask <- enc_blk(key2, mask)`
+
--
ACE architects only the two-key construction of cite:[nist-SP-800-38E]: the tweak is
always encrypted under `key2`, which the data path never evaluates, so the raw value is
safe to use as the initial mask. The single-key XEX construction, in which the mask is
`{alpha}` {interpunct} `enc_blk(key1, T)`, is *not* architected: provisioning `key2`
equal to `key1` re-creates it *without* the required multiplication by `{alpha}`, which
cite:[DBLP-conf-asiacrypt-Rogaway04] shows to be attackable. Provisioners must therefore
supply two independent keys, and a System Key Identifier must resolve to two independent
keys in the SKS.
--
// The extra `update_mask` in the single-key case is required, not incidental. With one key
// the raw value `enc_blk(key1, T)` is both a mask and a value the same key can be asked to
// encrypt, which cite:[DBLP-conf-asiacrypt-Rogaway04] shows to be attackable; the
// construction therefore starts from `{alpha}` {interpunct} `enc_blk(key1, T)`. With two
// independent keys the data path never evaluates `key2`, so the raw value is safe to use and
// no multiplication is needed. An implementation must not "simplify" the two branches into
// one.

  ** In States _Encrypt_ and _Decrypt_, (multi-block) ``ace.exec`` instructions are expected to be of Form A.
    “``ace.exec OUTPUT, Kn|K{Xn}, INPUT``” performs the following operations:
+
--
  . `OUTPUT` is computed as follows:
  .. In State _Encrypt_, `OUTPUT <- mask xor enc_blk(key1, INPUT xor mask)`.
  .. In State _Decrypt_, `OUTPUT <- mask xor dec_blk(key1, INPUT xor mask)`.
  . `mask <- update_mask(mask)`.
--
//

Note that if `ace.setst` is issued to return to State _Ready_, the CC can be reused with a new tweak.

Encryption pseudocode is provided in <<ACE-pseudocode-basic-IV-mode>>;
decryption is similar.


[[ACE-XTS-from-XEX]]
===== Procedure: XTS and Ciphertext Stealing from an XEX Context

cite:[nist-SP-800-38E] adds two things to the XEX construction above: the tweak is the
data unit sequence number, and a data unit whose length is not a multiple of `b` is
completed by ciphertext stealing. Both are obtained from the XEX CC as specified, with no
further architectural support; this subsection says how, so that an implementation of
`Zklxexm` can be used to realize SP 800-38E without invention.

*The tweak.* The value supplied as `INPUT` on the transition to _Encrypt_ or _Decrypt_ is
the data unit sequence number encoded on `b` bits in little-endian order, i.e., `bin(i, b)` in the
notation of <<ACE-Notation>>.

*Ciphertext stealing.* Let the data unit be `m` full blocks followed by a final partial
block of `s` bits, with `0` < `s` < `b` and `s` a multiple of 8, and number the blocks
`P~0~` {ellipsis} `P~m-1~`, `P~m~`. Recall that each `ace.exec` uses the current `mask`
and then advances it, so the `j`-th `ace.exec` issued after the tweak was set is the one
that operates at mask index `j`.

Encryption needs no reordering, because SP 800-38E consumes the mask indices in their
natural order:

  . Issue `ace.exec` for `P~0~` {ellipsis} `P~m-2~`, obtaining `C~0~` {ellipsis} `C~m-2~`.
  . Issue `ace.exec` for `P~m-1~`, obtaining `CC` at mask index `m-1`.
  . `C~m~` {leftarrow} `CC[s-1:0]` and `CP` {leftarrow} `CC[b-1:s]`.
  . Issue `ace.exec` for `CP @ P~m~`, obtaining `C~m-1~` at mask index `m`.
  . The ciphertext is `C~0~` {ellipsis} `C~m-2~`, `C~m-1~`, `C~m~`, in that order, with
    `C~m~` the final `s` bits.

Decryption consumes mask index `m` before mask index `m-1`, and a mask only ever advances.
The two are obtained from one context by cloning it once, immediately before the last two blocks:

  . Issue `ace.exec` for `C~0~` {ellipsis} `C~m-2~`, obtaining `P~0~` {ellipsis} `P~m-2~`.
    The `mask` of the CR is now at index `m-1`.
  . `ace.clone` the CR into a second CR, which is therefore also at mask index `m-1`.
  . On the clone, issue one `ace.exec` whose output is discarded. This consumes mask index
    `m-1` and leaves the clone at index `m`.
  . On the clone, issue `ace.exec` for `C~m-1~`, obtaining `PP` at mask index `m`.
  . `P~m~` {leftarrow} `PP[s-1:0]` and `CP` {leftarrow} `PP[b-1:s]`.
  . On the original CR, still at mask index `m-1`, issue `ace.exec` for `CP @ C~m~`,
    obtaining `P~m-1~`.
  . Clear the clone.

The cost of decryption is therefore one `ace.clone` and one discarded block operation per
data unit, independently of its length. Note that `CP @ P~m~` and `CP @ C~m~` place the
partial block in the least significant bits, where the first `s` bytes of the
string live under <<ACE-Notation>>.

If `s` = 0 no stealing takes place and both directions are the plain XEX sequence over
`m` blocks.

[[ACE-tweakable]]

The specification of a generic tweakable block cipher resembles that of a block cipher in ECB mode.

[[ACE-process-VLI]]
==== Procedure: Processing Variable Length Inputs into a Fixed Length Output

Many Algorithms need to process variable-length inputs into fixed-length outputs, such as hash functions or deriving internal fixed-length IVs from variable-length external ones. This occurs in specific states of the Algorithms (e.g., _Hash_Absorb_), referred to here as _Current_State_, whose semantics are described below.

The Procedure must follow the granularity of the caller Algorithm, which implies that in some cases the inner loop and the computation of `amount` may be simplified in obvious ways.

The use of this functionality in an Algorithm is written in the following way:

```
process_VLI(max_len,
            block, b,        state, n,
            input_base,      block_base,      state_offset,      cumul_len,
            process_block(), finalize(),      mode,              granularity).
```
where the parameters are all _references_ to certain variables of the caller Algorithm:

 * `max_len` is the total length of the data to be absorbed, *in bits*. If not defined by the caller or by the Algorithm, `max_len` is zero for the purpose of defining this procedure.
 * `block` contains the current block being filled internally before processing. Its size is `b` bits.
 * `state` is the output buffer. It may be the same as `block`. Its size is `n` bits.
 * `input_base` is the base offset of the data moved from the `ace.exec`'s input into `block`.
 * `block_base` is the base bit-offset within `block`. Each time this value reaches `b`, the data in `block` is processed.
 * `state_offset` is the offset within `state` for XORing with the input data, for instance, for sponge constructions.
 * `cumul_len` is the cumulative length of the data absorbed so far by the procedure, or `None` if not tracked.
 * `mode` is either `assign` or `xor_accumulate`, and selects how incoming data is combined with
   the destination, as specified in Step 4.b below. It is *not* inferred from whether `block` and
   `state` denote the same variable.

[IMPORTANT]
====
`input_base`, `block_base` and `cumul_len` — the last whenever it is tracked — shall denote
distinct storage locations. They
advance independently — `input_base` is reset at the start of every `ace.exec`, whereas
`block_base` and `cumul_len` persist across instructions — so binding any two of them to the same
location makes the procedure advance that location several times per iteration and is a malformed
invocation.

When `mode` is `xor_accumulate`, the caller shall satisfy `state_offset` + `b` {le} `n`. The
destination index reaches `block_base` + `amount` + `state_offset`, while `amount` is bounded only
by `b` − `block_base`, so a larger `state_offset` would write past the end of `state`.

`mode` is an explicit parameter because the two combining rules are not interchangeable.
`xor_accumulate` is required by sponge constructions, which XOR the input directly into the rate
portion of the state; `assign` is required wherever a field is *loaded* rather than absorbed, in
particular for key and key-like material. Selecting `xor_accumulate` where `assign` is meant
combines the incoming value with whatever the field already held, which for a key field yields a
key that neither party chose, silently and without any error indication.
====

The state variables `input_base`, `block_base`, and `cumul_len` are not initialized by this procedure, so that several calls to it can concatenate their results.
It is the caller's responsibility to ensure that any necessary variable is initialized to zero.
An Algorithm that enters a state with `mode` = `assign`, and whose destination field must hold a
defined value once loading completes, shall zero that field on entry to the state.

*Units.* `max_len`, `b`, `n`, `input_base`, `block_base`, `state_offset`, `cumul_len`, and `amount` are
all counted in bits, to support values of `max_len` that are not multiples of 8 bits.
However, the routine only supports values of `b` and `n` that are multiples of 8 bits,
and all `ace.exec` instructions transfer whole bytes and never a fraction of a byte.
As a consequence, `input_base` and `block_base` are always multiples of 8.

Finally, two parameters are functions of the called Algorithm:

* `process_block()=process_block(block, state)` is a function that processes the current block into `state`.
It may
   be given as `None`, in which case no such call is made and `state` is not used.
* `finalize()` is a function that finalizes the processing of the input data. It may have to complete the current block according to rules defined in the Algorithm as part of the finalization. It may also be given as `None`, in which case no such call is made.

Passing `None` for both reduces the procedure to its accounting of partial progress across
`ace.exec` instructions, which is what an Algorithm needs when it merely has to fill a long
field from memory and has no per-block processing to perform.

If the caller Algorithm needs to process the last block separately, it may invoke this procedure twice with the length of the last block as the `max_len` parameter and a different `process_block()` function.

The optional parameter `granularity` specifies the transfer unit for inputs: every transfer in a sequence (`INPUT` of `ace.exec` or the auxiliary vector input of `ace.setst`) — except possibly the last — must have an `ACELEN` that is a whole multiple of `granularity`.
The final transfer may be shorter or internally truncated to `max_len` − `cumul_len` (cf. <<ACE-truncation-vs-length>>); consequently, `max_len` need not be a multiple of `granularity`.
For example, with `granularity` = 128, a 96-bit IV is supplied in a single transfer, either as a 96-bit vector or as a 128-bit vector with excess bits truncated.

//

*Internal State Variables*:::
Beside `max_len`, `block`, and `state`, which are fixed for the duration of the hash computation, and `input_base`, `block_base`, and `cumul_len`, additional variables may be defined by the Algorithm and used by `process_block()` and `finalize()`.

*State Machine Behavior*:::

** When entering State _Current_State_:
 . If `max_len` is set by the caller, it is passed as a parameter to a Form B `ace.setst` instruction and `max_len` is set to the auxiliary argument `Xs`.
 . Otherwise, `max_len` is set by the Algorithm, and the `ace.setst` instruction used to transition to this state must be of Form A.

** While in State _Current_State_, only ``ace.exec`` instructions of Form B are expected, whereby
 “`ace.exec Kn|K{Xn}, INPUT`” processes the data block `INPUT` as follows.
+
--
. If `max_len != 0` and `cumul_len >= max_len`, then the CR transitions to Error State _Invalid_.
. If starting an ``ace.exec`` instruction, then `input_base <- 0`
. If resuming an ``ace.exec`` instruction, then `input_base <- 8` {interpunct} `acestart`.
  `input_base` is counted in bits (see *Units* above) while `acestart` is a number of bytes
  (<<ACE-CSR-acestart>>), hence the conversion.
. While `(input_base < ACELEN)` do
.. If `max_len` != 0 then `amount <- min(ACELEN - input_base, b - block_base, max_len - cumul_len)`,
   else `amount <- min(ACELEN - input_base, b - block_base)`.
   `amount` is always strictly positive, so the loop terminates.
.. if `mode` = `assign` then:
 ... ``block[block_base + amount - 1 : block_base] <- INPUT[input_base + amount - 1 : input_base]``.
.. else, that is if `mode` = `xor_accumulate`:
 ...  XOR ``INPUT[input_base + amount - 1 : input_base]`` to ``state[block_base + amount + state_offset - 1 : block_base + state_offset]``.
.. `input_base <- input_base + amount`.
.. `block_base <- block_base + amount`.
.. If `max_len != 0` then `cumul_len <- cumul_len + amount`.
.. If (`block_base` = `b`) then:
 ... `process_block(block, state)`, if it is not `None`.
 ... `block_base <- 0`.
.. If `max_len` != 0 and `cumul_len = max_len` then:
 ... `finalize()`, if it is not `None`.
 ... The instruction is terminated, even if `input_base < ACELEN`.
.. *Here*, and only here, the instruction may be interrupted, with
   `acestart <- input_base / 8`.
   `input_base` is a whole number of bytes at this point, so the division is exact; the
   procedure defines no interruption point at a finer granularity, so `acestart` never has
   to describe a position inside a byte. The conversion matches the one State
   _Hash_Output_ performs on the output side (<<ACE-hash-functions>>).
--
+

** If the caller transitions to a different state, `finalize()` is performed before transitioning, unless `finalize` = `None`.
   Transitioning to the same State `_Current_State_` is not allowed, and any attempt to do so causes the CR to transition to Error State _Invalid_.

[[ACE-GCM-mode]]
==== GCM Mode

The GCM mode was designed by David McGrew and John Viega cite:[DBLP-conf-indocrypt-McGrewV04] and became a NIST Recommendation in 2007 cite:[nist-SP-800-38D].
It is currently defined only for 128-bit block ciphers, but the definition will be updated to support other block sizes if required by SDOs.
(((ACE, Algorithm, GCM)))

Parameters:::

* `k` = key size (64|`k`).
* `b` = 128 = block size in bits.
* `c` = 32 = counter size in bits.
* Granularity: `b`.

Data Structures:::

* *Provisioning Input*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)   | Field
|  ii  | `k` or 64     | `key` or System Key Identifier
|===
--

* *Internal State*:
+
--
** `key`: `k` bits.
** `J0`:  `128` bits. Big-endian as in the AES-GCM spec. `J0`[127:96] is the current GCTR counter, and `start_ctr` its initial value; the counter occupies bytes 12 to 15 of the counter block, big-endian, as in cite:[nist-SP-800-38D].
** `auth_key` (derived): `128` bits.
** `tag`: `128` bits. This field stores the authentication tag.
** `start_ctr`: an integer in the range 0 to 2^32^-1. The initial value of the GCTR counter. It is serialized as `bin(start_ctr,32)`.
** `last_blk_len`: an integer in the range 0 to 127. The length of the last block of a plaintext or ciphertext.
--
+
In the internal state, variables `len`, `input_base`, `block_base`, `cumul_len`, `J0_padding` may overlap with `J0` or be separate fields.
The latter may be necessary if the implementation of Subalgorithm _ACE-process-VLI_ (cf. <<ACE-process-VLI>>) works with integers of a different length.

* *Serialized Context*:
+
--
[cols="^8%,<15%,<15%,<62%",options="header"]
|===
|  Pos. | Size (Bits)   | Field          | Description
|  ii   | `k` or 64     | `key`          | Key value or System Key Identifier
| iii   | 128           | `J0`           | Big-endian as in the AES-GCM spec. `J0`[127:96] is the current GCTR counter.
|  iv   | 128           | `tag`          | {empty}
|   v   | 32            | `start_ctr`    | The initial counter: `start_ctr` = `int(bswap(J0[127:96]))`, the last four bytes of the *initial* `J0` read as a big-endian integer, serialized here as `bin(start_ctr,32)`. If the running counter returns to this value, an error is returned. It is also used to generate the tag mask.
|  vi   | 16            | `last_blk_len` | {empty}
|===

While in state _Set_Aux_Value_, `J0` is replaced by the following fields:

[cols="^8%,<15%,<15%,<62%",options="header"]
|===
| Pos.  | Size (Bits)     | Field       | Description
| iv.a  | 16 bits         | `len`       | Total length of the IV, in bits. Maximum supported size is 1024 bytes (8192 bits).
| iv.b  | 16 bits         | `input_base`| Internal offset within input/output to read from/write to. Each time this value reaches `b`, the data in `block` is processed.
| iv.c  | 16 bits         | `block_base`| Internal amount of absorbed data so far for the current block.
| iv.d  | 48 bits         | `cumul_len` | Internal cumulative length of data absorbed so far.
|===
--

NOTE: There are no fields for the lengths of the AD and of the plaintext, as they are maintained by the calling software.

Algorithm-Specific Functions:::
+
--
* `enc_blk(key, p) -> c` encrypts block `p` using the key, and returns the
  result `c`.

* `absorb(data)` absorbs data into the hash function by performing:
  . `tag <- tag xor data`.
  . `tag <- Galoismul(tag, auth_key)`.

* `Galoismul` is multiplication in the GHASH field of cite:[nist-SP-800-38D] {sect}6.3.
+
The field is GF(2)[x] modulo `x^128^ + x^7^ + x^2^ + x + 1`.
A 128-bit value `V` represents the element whose coefficient of
`x^8i+j^`, for `0` {le} `i` < `16` and `0` {le} `j` {le} `7`, is `V[8i + (7-j)]`.
+
In other words, the byte order runs forward (“little endian”:
the byte at offset 0 contains the coefficients of `x^0^` through `x^7^`,
the byte at offset 1 contains the coefficients of `x^8^` through `x^15^`,
and so on) while the bit order is reversed within each byte, i.e.,
in the byte at offset 0, bit 0, the least significant bit, is the coefficient of `x^7^`,
bit 1 is the coefficient of `x^6^`, and so on.
This is the representation of cite:[nist-SP-800-38D] {sect}6.3.
+
`Galoismul(a, b)` is multiplication in this field.
--

State Machine:::

* *States:*
+
--
Besides _Ready_, _Success_, and _Failure_, the GCM Mode Algorithms make use of the following states:

 ** _Set_Aux_Value_: Used to set the IV and then compute `J0` once left.
 ** _Hash_Absorb_: Process Associated Data (AD) into the tag.
 ** _Encrypt_: Encrypt the plaintext and absorb the ciphertext into the tag.
 ** _Enc_Last_Block_: Encrypt the final, fractional block of the plaintext.
 ** _Enc_Tag_Finalize_: Finalize the encryption tag, prepare to return its value.
 ** _Decrypt_: Absorb the ciphertext into the tag and decrypt it.
 ** _Dec_Last_Block_: Decrypt the final, fractional block of the ciphertext.
 ** _Dec_Tag_Finalize_: Finalize the encryption tag and keep it internally.
 ** _Hash_Verify_: Compare the tag against a user supplied value.

There is an asymmetry between the handling of the Associated Data (AD) and that of the
plaintext or ciphertext when absorbing into `GHASH`, and it places one obligation on the
caller:

* *For the AD*, the caller must zero every bit of the final block beyond the actual end
  of the AD. `GHASH` absorbs that block whole, following cite:[nist-SP-800-38D].
  No state is required to process a fractional last AD block.

* *For the plaintext and ciphertext*, the caller must not rely on zero-padding, and must
  instead use States _Enc_Last_Block_ and _Dec_Last_Block_ for a final block that is
  shorter than `b`, because zero-padding is *not* sufficient here: it
  would both leak keystream and produce a non-conforming tag.
--

* *Allowed State Transitions:*
 ** _Ready_ -> _Set_Aux_Value_ -> _Hash_Absorb_.
 ** _Hash_Absorb_ -> _Encrypt_, if encryption is allowed.
 ** _Hash_Absorb_ -> _Decrypt_, if decryption is allowed.
 ** _Encrypt_ -> { _Enc_Last_Block_ -> } _Enc_Tag_Finalize_ -> _Success_.
 ** _Decrypt_ -> { _Dec_Last_Block_ -> } _Dec_Tag_Finalize_ -> _Hash_Verify_ -> _Success_ or _Failure_.

* *Behavior:*
 ** In State _Ready_ :
  *** The following initialization operations are performed:
   . `auth_key <- enc_blk(key, zeros(b))`, and
   . `tag <- zeros(b)`

  ** To transition to State _Set_Aux_Value_, a Form B ``ace.setst`` instruction is
     expected, “``ace.setst Kn|K{Xn}, #ace_state_set_aux_value, Xs``”, whose auxiliary
     parameter sets the length of the IV in bits: `len <- Xs`.
     `Xs` must satisfy `8` {le} `Xs` {le} `8192`;
     for any other value, `0` included, the CR transitions to Error State _Invalid_.
     Upon entering the state, `tag` is cleared: `tag <- zeros(b)`.

  ** When entering State _Set_Aux_Value_, `input_base`, `block_base`, `cumul_len` are set to zero.

  ** State _Set_Aux_Value_ is implemented as
  Subalgorithm `process_VLI` (cf. <<ACE-process-VLI>>) as: +
  `process_VLI(len, block=tag, b, state=tag, b, input_base, block_base, 0, cumul_len, process_block(), finalize(), mode=xor_accumulate, granularity=b)`, where `len` is the IV length in bits, and
  `mode` is `xor_accumulate` because `GHASH` absorbs each block by XORing it into the accumulator
  before multiplying, and
   *** if `len != 96`, `process_block()`, performs `tag <- Galoismul(tag, auth_key)`, otherwise it does nothing.
   *** `finalize()` is defined as follows:
    . If `len = 96`, then:
      .. `J0 <- bswap(bin(1,32)) @ tag[95:0]`.
+
The value of `J0` is `IV {vvert} 0^31^ {vvert} 1` of cite:[nist-SP-800-38D] {sect}7.1, where the IV occupies bytes 0 to 11, i.e.
`J0[95:0]`, and the counter occupies bytes 12 to 15 as a *big-endian* integer.

    . If `len != 96`, then let `s <- 128 ⎡len/128⎤ - len`, and the computation of `J0 := GHASH(IV {vvert} 0^s+64^ {vvert} bswap(bin(len,64)), auth_key)` is completed by performing:
      .. if `block_base != 0`, then `tag <- Galoismul(tag, auth_key)`
      .. `tag <- tag xor (bswap(bin(len,64)) @ zeros(64))`
      .. `tag <- Galoismul(tag, auth_key)`
      .. `J0 <- tag`
    . `start_ctr <- int(bswap(J0[127:96]))`,
    . `tag <- zeros(b)`, so that State _Hash_Absorb_ starts the Associated Data hash from the
      value `GHASH` requires and does not inherit the hash of the IV.
    . Transitions to state _Hash_Absorb_.

[NOTE]
====
The IV is absorbed into `tag`, not into `J0`, and only the finished value is copied to `J0`.
`tag` is free for this because `_Set_Aux_Value_` is reachable only from _Ready_, which clears it,
and zero is GHASH's initial value in any case — whereas `J0`'s slot in the Serialized Context
carries `len`, `input_base`, `block_base` and `cumul_len` while this state is active. Accumulating
into `J0` would place the running hash and those counters in the same 128 bits, so a CC exported
part-way through a non-96-bit IV could not resume.
====

 ** In State _Hash_Absorb_, (multi-block) ``ace.exec`` instructions of Form B are expected, whereby ``ace.exec Kn|K{Xn}, INPUT`` absorbs a data block into `tag`, i.e.:
+
--
 . `absorb(INPUT)`.
--
** In State _Encrypt_, (multi-block) ``ace.exec`` instructions are expected to be of Form A.
   “``ace.exec OUTPUT, Kn|K{Xn}, INPUT``” encrypts `INPUT` into `OUTPUT`, and
   absorbs `OUTPUT` into the `tag`, namely:
+
--
  * `local ctr : int` - the running counter, as an integer.

[]
  . `ctr <- int(bswap(J0[127:96]))`   // convert counter from big-endian to little-endian
  . `ctr <- (ctr + 1) mod 2^32^`.
  . If `ctr` = `(start_ctr - 1) mod 2^32^`, then: (process at most  2^32^ - 2 blocks)
   .. the CR transitions to Error State _Invalid_.
   . else:
  .. `J0[127:96] <- bswap(bin(ctr,32))`.  // convert updated counter back to big-endian
  .. `tmp <- INPUT xor enc_blk(key, J0)`.
  .. `absorb(tmp)`.
  .. `OUTPUT <- tmp`.
--
** To transition to State _Enc_Last_Block_, a Form B `ace.setst` instruction is issued, whereby
`last_blk_len`, the bit length of the last block, is set to the auxiliary argument `Xs`.
A value of zero, or larger than 127, causes the CR to transition to Error State _Invalid_, as it does in the other modes that take a final-block length (cf. <<ACE-OCB-mode>>, <<ACE-CMAC-mode>>, <<ACE-Ascon-AEAD128>>).
Note that `last_blk_len` is not restricted to multiples of 8: Every value from 1 to 127 is conformant here per cite:[nist-SP-800-38D].
Any excess bits provided by the following Form A ``ace.exec`` are ignored.

** In State _Enc_Last_Block_, a single Form A ``ace.exec`` instruction can be issued.
   “``ace.exec OUTPUT, Kn|K{Xn}, INPUT``” encrypts `INPUT` into `OUTPUT`, and
   absorbs `OUTPUT` into the `tag`, namely:
+
--
  * local `ctr : int` – the running counter, as an integer.
  * `local tmp : bits(b)`

[]
  . If `last_blk_len = 0`, then: terminate the instruction.
  . `ctr <- int(bswap(J0[127:96]))`
  . `ctr <- (ctr + 1) mod 2^32^`.
  . If `ctr` = `(start_ctr - 1) mod 2^32^`, then:
   .. the CR transitions to Error State _Invalid_.
  . else:
   .. `J0[127:96] <- bswap(bin(ctr,32))`
   .. `tmp <- (zeros(128-last_blk_len) @ INPUT[last_blk_len-1:0]) xor (zeros(128-last_blk_len) @ enc_blk(key, J0)[last_blk_len-1:0])`.
   .. `absorb(tmp)`.
   .. `OUTPUT <- tmp`.
   .. `last_blk_len <- 0`
--


** To transition to State _Enc_Tag_Finalize_, a Form C `ace.setst` instruction is issued with the following value, computed by the software itself:
+
--
[none]
* `INPUT <- bswap(bin(len_in_bits(plaintext), 64)) @` +
 {fournbsp}{fournbsp} `@ bswap(bin(len_in_bits(AD), 64))` .

The authentication tag is then computed and retained internally, as follows:

. `absorb(INPUT)`.
  . `tag <- tag xor enc_blk(key, bswap(bin(start_ctr,32)) @ J0[95:0])`.

If `ACELEN` > 128, only the 128 least significant bits of `INPUT` are considered.
--

** {empty}
In State _Enc_Tag_Finalize_, a single ``ace.exec`` instruction of Form C is expected.
“``ace.exec OUTPUT, Kn|K{Xn}``” writes the `tag` to `OUTPUT`, and the state transitions to _Success_.

** {empty}
+
--
In State _Decrypt_, (multi-block) ``ace.exec`` instructions are expected to be of Form A.
``ace.exec OUTPUT, Kn|K{Xn}, INPUT`` absorbs the ciphertext `INPUT` into `tag`, then decrypts `INPUT` into `OUTPUT`, namely:

 * local `ctr : int` – the running counter, as an integer.
 * `local tmp : bits(b)`

[]
 . `ctr <- int(bswap(J0[127:96]))`.
 . `ctr <- (ctr + 1) mod 2^32^`.
 . If `ctr` = `(start_ctr - 1) mod 2^32^`, then:
  .. the CR transitions to Error State _Invalid_.
 . else:
  .. `absorb(INPUT)`.
  .. `J0[127:96] <- bswap(bin(ctr,32))`.
  .. `OUTPUT <- INPUT xor enc_blk(key, J0)`.
--

** To transition to State _Dec_Last_Block_, a Form B `ace.setst` instruction is issued, whereby
`last_blk_len`, the bit length of the last block, is set to the auxiliary argument `Xs`.
A value of zero, or larger than 127, causes the CR to transition to Error State _Invalid_.
// , as it does in the other modes that take a final-block length (cf. <<ACE-OCB-mode>>, <<ACE-CMAC-mode>>, <<ACE-Ascon-AEAD128>>).

** In State _Dec_Last_Block_, a single Form A ``ace.exec`` instruction can be issued.
   “``ace.exec OUTPUT, Kn|K{Xn}, INPUT``” absorbs the zero-padded final block of the
   ciphertext into the `tag` and decrypts `INPUT` into `OUTPUT`, namely:
+
--
  * local `ctr : int` – the running counter, as an integer.
  * `local tmp : bits(b)`

[]
  . If `last_blk_len = 0`, then: terminate the instruction.
  . `ctr <- int(bswap(J0[127:96]))`
  . `ctr <- (ctr + 1) mod 2^32^`.
  . If `ctr` = `(start_ctr - 1) mod 2^32^`, then:
   .. the CR transitions to Error State _Invalid_.
  . else:
  .. `tmp <- zeros(128-last_blk_len) @ INPUT[last_blk_len-1:0]`.
  .. `absorb(tmp)`.
  .. `J0[127:96] <- bswap(bin(ctr,32))`.
  .. `OUTPUT <- tmp xor (zeros(128-last_blk_len) @ enc_blk(key, J0)[last_blk_len-1:0])`.
  .. `last_blk_len <- 0`
--

** To transition to State _Dec_Tag_Finalize_, a Form C ``ace.setst`` instruction is expected to provide the following value, which must be set by the software:
+
--
[none]
* `INPUT <- bswap(bin(len_in_bits(plaintext), 64)) @ bswap(bin(len_in_bits(AD), 64))`

The authentication tag is computed as follows:

. `absorb(INPUT)`.
  . `tag <- tag xor enc_blk(key, bswap(bin(start_ctr,32)) @ J0[95:0])`.
--
+
If `ACELEN` > 128, only the 128 least significant bits of `INPUT` are considered.

** To transition to State _Hash_Verify_, a Form C ``ace.setst`` instruction
   must be used to provide the value against which the internally computed tag
   must be compared. If the values match, the state
   transitions to _Success_; otherwise, it transitions to _Failure_.

** `auth_key` is a derived field (AGR5): `auth_key <- enc_blk(key, zeros(128))`.

[[ACE-GCM-with-IV-mode]]
==== GCM with Set IV

The mode of operation “GCM with a Set IV” is a variant of GCM in which the initialization vector (IV) is predefined rather than generated randomly.
This variant _cannot_ be emulated with an ECB CC because that would reveal the internal data.

A key difference between GCM and GCM with Set IV is in the format of the Provisioning Input:

Data Structures:::

* *Provisioning Input*:
+
--
[cols="^8%,<15%,<15%,<62%",options="header"]
|===
|  Pos. | Size (Bits)   | Field       | Description
|  ii   | `k` or 64     | `key`       | Key value or System Key Identifier
| iii   | 128           | `J0`        | {empty}
|  iv   | 32            | `budget`    | Number of blocks this CC is permitted to process, as `bin(budget,32)`. See the State Machine Behavior below.
|===
--

* *Internal State*: {empty}
+
--
Same as for GCM, with the addition of

** `budget`: an integer in the range 0 to 2^32^-1, the number of blocks that this CC may
   still process.

Upon provisioning, `start_ctr <- int(bswap(J0[127:96]))`, i.e. the last four bytes of `J0` read as a big-endian integer, and `budget` is set to the value carried in the Provisioning Input.
--

* *Serialized Context*: {empty}
+
--
The `budget` is inserted in `GCM` mode's serialized context after `last_blk_len` in place of the original Padding field, and is followed by the remaining padding.

[cols="^8%,<15%,<15%,<62%",options="header"]
|===
|  Pos. | Size (Bits)   | Field          | Description
| vii   | 32            | `budget`       | Remaining block budget, serialized as `bin(budget,32)`.
|===
--

* *States and Allowed Transitions:* {empty}
+
--
Same as for GCM, with the following exceptions:

** There is no state _Set_Aux_Value_. The transition is from _Ready_ to _Hash_Absorb_.
--

* *State Machine Behavior:* {empty}
+
--
The differences with respect to GCM are:

 ** To transition to State _Hash_Absorb_: The ``ace.setst`` instruction must be of Form A, i.e., _without any additional inputs_, since the IV is already included in the PI.
 ** No transition back to State _Ready_ is allowed. This is one of the Algorithm-specific
    prohibitions contemplated by <<ACE-State-field>>.
 ** Every `ace.exec` that *consumes* blocks decreases `budget` by the number of blocks it
    processed, which is `ACELEN`/`b` in States _Hash_Absorb_, _Encrypt_ and _Decrypt_, and
    1 in States _Enc_Last_Block_ and _Dec_Last_Block_. A Form C `ace.exec` does *not*
    decrease `budget`: in State _Enc_Tag_Finalize_ it only emits the tag, which consumes no
    block.
 ** If an `ace.exec` would decrease `budget` below zero, it performs no operation, and the CR transitions to Error State _Invalid_.
--

NOTE: This Algorithm protects IV confidentiality, not against reuse.
Preventing IV reuse (e.g., by restoring older SCC copies) is the caller's responsibility.

[[ACE-GCM-SIV-mode]]
==== GCM-SIV Mode

The GCM-SIV mode is described in cite:[DBLP-journals-iacr-GueronLL17] and cite:[RFC8452].
It is currently defined only for 128-bit block ciphers, but the definition will be updated to support other block sizes if required by SDOs.
(((ACE, Algorithm, GCM-SIV)))

While the decryption state machine of GCM-SIV is similar to that of GCM, the encryption state machine is different:

* During encryption, the _Hash_Absorb_ state absorbs the entire associated data and plaintext. The _Enc_Tag_Finalize_ state then absorbs the lengths and produces the SIV/tag. Finally, the _Encrypt_ state performs a second pass to encrypt the plaintext using the SIV/tag as the initialization vector.
* During decryption, the _Hash_Absorb_ state absorbs only the associated data. The _Decrypt_ state decrypts the ciphertext and simultaneously absorbs the plaintext into the hash. Finally, the _Dec_Tag_Finalize_ state absorbs the lengths, produces the SIV/tag, and internally compares it to the provided SIV/tag.

//

Parameters:::

* `k` = key size, either 128 or 256: cite:[RFC8452] defines AES-GCM-SIV only for these two.
* `b` = 128 = block size.
* `c` = 32 = counter size.
* Granularity: `b`.
* The authentication tag is `b` = 128 bits long.

Data Structures:::

* *Provisioning Input*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)   | Field
|  ii  | `k` or 64     | `key` or System Key Identifier
|===
--

* *Internal State*:
  ** `key`: `k` bits.
 ** `enc_key` (derived): `k` bits.
 ** `auth_key` (derived): 128 bits.
 ** `nonce`: 96 bits.
 ** `ctr`: an integer in the range 0 to 2^32^-1, serialized on 32 bits.
 ** `SIV`: 128 bits.
 ** `tmp`: 128 bits.
 ** `last_blk_len`: 7 bits (value between 0 and 127).

* *Serialized Context*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
|  Pos. | Size (Bits)     | Field
|   ii  |  `k` or 64      | `key` or System Key Identifier
|  iii  |  96             | `nonce`
|   iv  |  32             | `ctr`
|    v  |  128            | `SIV`
|   vi  |  128            | `tmp`
|  vii  |  16             | `last_blk_len`
|===
--

Algorithm-Specific Functions:::

* `enc_blk(key, p) -> c` encrypts block `p` using the key, and returns the result `c`.
* `RFC8452_KeyDeriv(k, key, nonce)` derives the per-nonce message-encryption and
  message-authentication keys of cite:[RFC8452] {sect}4:
+
[[ACE-GCM-SIV-KeyDeriv]]
.AES-GCM-SIV Key Derivation
[]
----
function RFC8452_KeyDeriv(k : int, key : bits(k), nonce : bits(96))
    → struct{enc_key : bits(k), auth_key : bits(128)} =
{
  local A : array [0..5] of bits(128);
  local E : bits(k);
  local i : int;

  foreach(i from 0 to k/64 + 1) do:
    A[i] ← enc_blk(key, nonce @ bin(i,32));
  foreach(i from 2 to k/64 + 1) do:
    E[64*i-65 : 64*i-128] ← A[i][63:0];

  return struct { enc_key = E, auth_key = A[1][63:0] @ A[0][63:0] };
}
----
+
The loop makes `k`/64 + 2 calls, four for `k` = 128 and six for `k` = 256, and keeps the low
64 bits of each: these are the “first eight bytes” of cite:[RFC8452] under <<ACE-Notation>>.
* `absorb(data)` absorbs data into the hash function by performing a step of POLYVAL:
  . `tmp <- tmp xor data`.
  . `tmp <- Montmul(tmp, auth_key)`

State Machine:::
  * *States:*
+
--
Besides _Ready_, _Success_, and _Failure_, the GCM-SIV Algorithm makes use of the following states:

 ** _Set_Aux_Value_: Set the value of `nonce`.
 ** _Set_Aux_Value_2_: Set the `SIV`.
 ** _Hash_Absorb_: Process AD and, if encrypting, also the plaintext into the partial tag (this is accumulated in the state variable `tmp`).
 ** _Encrypt_: Encrypt the plaintext.
 ** _Enc_Last_Block_: Encrypt the final, fractional block of the plaintext.
 ** _Enc_Tag_Finalize_: Finalize the SIV with the AD and PT lengths, prepare to return its value.
 ** _Decrypt_: Absorb the ciphertext into the partial tag and decrypt it.
 ** _Dec_Last_Block_: Decrypt the final, fractional block of the ciphertext.
 ** _Dec_Tag_Finalize_: Finalize the tag with the AD and CT lengths, then compare it against the `SIV`.
--

* *Allowed State Transitions:*
 ** _Ready_ -> _Set_Aux_Value_.
 ** _Set_Aux_Value_ -> _Set_Aux_Value_2_ or _Hash_Absorb_.
 ** _Set_Aux_Value_2_ -> _Hash_Absorb_.
 ** For encryption: _Hash_Absorb_ -> _Enc_Tag_Finalize_ -> _Encrypt_ { -> _Enc_Last_Block_ }.
  *** Transition to _Enc_Tag_Finalize_ possible only if encryption is allowed.
 ** For decryption: _Hash_Absorb_ -> _Decrypt_ -> { _Dec_Last_Block_ -> } _Dec_Tag_Finalize_ -> _Success_ or _Failure_.
  *** Transition to _Decrypt_ possible only if decryption is allowed.

* *Behavior:*
** In State _Ready_ :
  *** Upon entering the state, the following initialization operations are performed:
   . `nonce`, `ctr`, `tmp`, `SIV <- 0`.

** To enter state _Set_Aux_Value_, a Form C `ace.setst Kn|K{Xn}, #ace_state_set_aux_value, INPUT`  must be issued.
    Then, the following operations are performed:
+
--
   . `nonce` <- `INPUT[95:0]`
   .  (`enc_key`, `auth_key`) `<-` `RFC8452_KeyDeriv(k, key, nonce)`
--
+
If the instruction is repeated, there is no harm: it just overwrites the `nonce` and recomputes `enc_key` and `auth_key` before any other operation is performed.

 ** To enter state _Set_Aux_Value_2_, a Form C `ace.setst Kn|K{Xn}, #ace_state_set_aux_value_2, INPUT` must be issued.
    Then:
+
--
   . `SIV` <- `INPUT`
--
+
[NOTE]
====
This state is used during decryption.
It is harmless to invoke it during encryption, as the `SIV` field will be overwritten later with the correct synthetic value.
It is also harmless to skip it during decryption, as this is equivalent to setting `SIV` to zero.
If the instruction is repeated, there is no harm either: it simply overwrites the `SIV` field, and no other state depends on it.
====

** The transitions to States _Hash_Absorb_, _Enc_Tag_Finalize_, _Encrypt_, _Decrypt_, and _Dec_Tag_Finalize_ are
   performed with Form A `ace.setst` instructions.

** {empty}
+
--
In State _Hash_Absorb_, (multi-block) Form B ``ace.exec`` instructions are expected.

Such an instruction absorbs its `INPUT` into the internal state variable `tmp`, i.e., it performs `absorb(INPUT)`.

The caller must zero every bit of a final partial block beyond the actual
end of the data being absorbed—the AD, and on the encryption path also the plaintext.
cite:[RFC8452] {sect}4 specifies both the AD and the plaintext as zero-padded to a multiple of 16 bytes.
--

** In State _Enc_Tag_Finalize_, an ``ace.exec`` instruction of Form A is expected. Its input value
+
--
[none]
  *** `INPUT <- bin(len_in_bits(plaintext), 64) @ bin(len_in_bits(AD), 64)`,
--
+
is set by the user.
Then, “``ace.exec``” finalizes the SIV computation by performing:
+
--
  . `absorb(INPUT)`.
  . `tmp <- enc_blk(enc_key, 0 @ tmp[126:96] @ (tmp[95:0] xor nonce))`.
  . `SIV <- tmp` and `OUTPUT <- SIV`,
--
+
If `ACELEN` > 128, only the 128 least significant bits of `INPUT` are considered.

** In State _Encrypt_, (multi-block) Form A ``ace.exec`` instructions are expected.
      Issuing “``ace.exec OUTPUT, Kn|K{Xn}, INPUT``,” encrypts `INPUT` into `OUTPUT`
      as follows:
+
--
  . If `ctr` = 2^32^-1, then the CR transitions to Error State _Invalid_.
  . ``OUTPUT <- INPUT xor enc_blk(enc_key, 1 @ SIV[126:32] @ bin((int(SIV[31:0]) + ctr) mod 2^32^, 32)),``
  . `ctr <- ctr + 1`.
--
** To transition to State _Enc_Last_Block_, a Form B `ace.setst` instruction is issued, whereby
`last_blk_len`, the bit length of the last block, is set to the auxiliary argument `Xs`.
Note that cite:[RFC8452] expresses this length in bytes and therefore `last_blk_len` must be a multiple of 8.
A value of zero, larger than 120, or not a multiple of 8, causes the CR to transition to Error State _Invalid_.

** In State _Enc_Last_Block_, a single Form A ``ace.exec`` instruction is expected.
      Issuing “``ace.exec OUTPUT, Kn|K{Xn}, INPUT``,” encrypts `INPUT` into `OUTPUT`
      as follows:
+
--
. If `last_blk_len = 0`, then: terminate the instruction.
. If `ctr` = 2^32^-1, then the CR transitions to Error State _Invalid_.
    . ``OUTPUT <- zeros(128-last_blk_len) @ (INPUT xor enc_blk(enc_key, 1 @ SIV[126:32] @ bin((int(SIV[31:0]) + ctr) mod 2^32^, 32)))[last_blk_len-1:0],``
    . `ctr <- ctr + 1`.
    . `last_blk_len <- 0`
--

** In State _Decrypt_, (multi-block) Form A ``ace.exec`` instructions are expected.
   “``ace.exec OUTPUT, Kn|K{Xn}, INPUT``” decrypts `INPUT` into `OUTPUT` and then absorbs the plaintext `OUTPUT` into `tmp`:
+
--
. If `ctr` = 2^32^-1, then the CR transitions to Error State _Invalid_.
. ``OUTPUT <- INPUT xor enc_blk(enc_key, 1 @ SIV[126:32] @ bin((int(SIV[31:0]) + ctr) mod 2^32^, 32))``,
. `absorb(OUTPUT)`.
. `ctr <- ctr + 1`.
--
** To transition to State _Dec_Last_Block_, a Form B `ace.setst` instruction is issued, whereby
`last_blk_len`, the bit length of the last block, is set to the auxiliary argument `Xs`.
A value of zero, larger than 120, or not a multiple of 8, causes the CR to transition to Error State _Invalid_: cite:[RFC8452] defines the mode over byte strings, so the same rule applies on both the encryption and the decryption path.

** In State _Dec_Last_Block_, a single Form A ``ace.exec`` instruction is expected.
      Issuing “``ace.exec OUTPUT, Kn|K{Xn}, INPUT``,” decrypts `INPUT` into `OUTPUT` and
      absorbs the zero-padded plaintext into the partial tag, as follows:
+
--
. If `last_blk_len = 0`, then: terminate the instruction.
. If `ctr` = 2^32^-1, then the CR transitions to Error State _Invalid_.
    . ``OUTPUT <- zeros(128-last_blk_len) @ (INPUT xor enc_blk(enc_key, 1 @ SIV[126:32] @ bin((int(SIV[31:0]) + ctr) mod 2^32^, 32)))[last_blk_len-1:0],``
    . `absorb(OUTPUT)`.
    . `ctr <- ctr + 1`.
    . `last_blk_len <- 0`
--

** In State _Dec_Tag_Finalize_,
    a single ``ace.exec`` instruction of Form B is expected,
    namely “``ace.exec Kn|K{Xn}, INPUT```,” where the user is responsible for setting
+
--
[none]
  ***  `INPUT <- bin(len_in_bits(plaintext), 64) @ bin(len_in_bits(AD), 64)`.
--
+
``ace.exec`` then performs the following operations:
+
--
  . `absorb(INPUT)` (which modifies `tmp`).
  . `tmp <- enc_blk(enc_key, 0 @ tmp[126:96] @ (tmp[95:0] xor nonce))`.
    . If `tmp` = `SIV` match, then:
    ..  `State <- ace_state_success`
    . else:
    ..  `State <- ace_state_failure`
--
+
If `ACELEN` > 128, only the 128 least significant bits of `INPUT` are considered.

** `enc_key` and `auth_key` are derived fields (AGR5):
(`enc_key`, `auth_key`) <- `RFC8452_KeyDeriv(k, key, nonce)`.

[[ACE-OCB-mode]]
==== OCB Mode

Only the OCB3 variant of OCB is architected, following RFC{nbsp}7253 cite:[RFC7253] and cite:[DBLP-journals-joc-KrovetzR21].
The state machine closely follows RFC{nbsp}7253, with two differences: little-endian bit numbering is used instead of big-endian, and zero-based indexing instead of one-based.
This specification defines OCB only for block ciphers with 128-bit blocks.
Generalization to other widths is straightforward, supported by the security proof of the original algorithm and a lower bound on nonce length from cite:[cryptoeprint-2023-326].

Parameters:::
+
--
* `b` = 128 = block size, assumed to be a power of 2.
* `k` = key size. Currently, it can only be 128, 192, or 256.
* `MAX_BLOCKS` = 2^48^ = maximum number of blocks in the AD or in the plaintext.
* Granularity: `b`.
--

Data Structures:::

* *Provisioning Input*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)   | Field
|  ii  | `k` or 64      | `key` or System Key Identifier
|===
--

* *Internal State*:
  ** `key`: `k` bits.
 ** `N`: `120` bits.
 ** `N_len`: 7 bits. Bit length of the nonce. It cannot exceed 120.
 ** `L*`, `offset`, `hash_A`, `checksum_P` : 128 bits each. The derived values `L$` and `L[0]` (cf. Behavior) may be cached or recomputed.
 ** `tag_len`: 8 bits. Bit length of the tag. Currently, the allowed values are 64, 96, and 128.
 ** `last_blk_len`: `7` bits. Length of the last block of AD or plaintext/ciphertext in bits. It is between 0 and 120 (`b` - 8) and must be a multiple of 8, since cite:[RFC7253] defines OCB over byte strings. A value that is not a multiple of 8, or that exceeds 120, causes the CR to transition to Error State _Invalid_.
 ** `index`: int, corresponding to `i` in the loops in RFC{nbsp}7253. It cannot exceed `MAX_BLOCKS` = 2^48^-1.
 **  `L~i~` (derived): array of 128 bit values, with `i` up to `floor(log_2(MAX_BLOCKS))`.

* *Serialized Context*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
|  Pos. | Size (Bits) | Field
|   ii  | `k` or 64   | `key` or System Key Identifier
|  iii  | 120         | `N`
|   iv  |   7         | `N_len`, the bit length of the nonce
|    v  |   1         | Padding
|   vi  | 128         | `L*`; the derived `L$` and `L[i]` are recomputed or re-derived upon import
|  vii  | 128         | `offset` (current offset)
| viii  | 128         | `hash_A`
|   ix  | 128         | `checksum_P` (used also for the final tag)
|    x  |  48         | `index`
|   xi  |   2         | `tag_len`, encoded as `tag_len`/32 − 2
|  xii  |   7         | `last_blk_len`
|===
--

Algorithm-Specific Functions:::

* `enc_blk(K,p) -> c` encrypts block `p` using the key `K` and returns the result `c`.
* `dec_blk(K,c) -> p` decrypts block `c` using the key `K` and returns the result `p`.
* `ntz(n)` = the number of trailing zero bits in the base-2 representation of the positive integer `n`.
Formally, `ntz(n)` is the largest integer `x` for which `2^x^` divides `n`.
* `ocb_pad(X, n)` = the `b`-bit value holding the `n`-bit partial block `X[n-1:0]`
  followed, in string order, by a single `1` bit and then zeros. This is
  `X {vvert} 1 {vvert} 0^127-n^` of cite:[RFC7253] {sect}4.2, and under
  <<ACE-Notation>> it is
+
`{fournbsp}{fournbsp}` `ocb_pad(X, n)` = `zeros(120-n) @ 0b10000000 @ X[n-1:0]`.
+
The terminating `1` is the *most significant* bit of byte `n/8`, not bit `n` of the
value: in string order it immediately follows the last data bit, and within a byte the
first bit of the string is that byte's most significant bit. `ocb_pad` is defined for
`n` a multiple of 8 with `0` {le} `n` {le} 120; for `n` = 0 it is
`zeros(120) @ 0b10000000`.
* `double(S)`: doubling in the OCB3 field.
Note that cite:[RFC7253] specifies this operation over a big-endian string, hence:
+
`{fournbsp}{fournbsp}` `double(S) <- bswap(update_mask(bswap(S)))`.
* `nonce_be(N, n)` = the big-endian view of the `n`-bit nonce bit string held in `N`.
  cite:[RFC7253] treats the nonce as a bit string whose first bit is the most significant, so
  when it is serialized into bytes the final, possibly partial byte is *left-aligned*: its
  `r` = `n` mod 8 most significant bits carry nonce and its remaining bits are padding. With
  `q` = {lceil}`n`/8{rceil} the number of bytes so occupied,
+
`{fournbsp}{fournbsp}` `nonce_be(N, n)` = `bswap(N[8q-1:0], q) >> ((8 - r) mod 8)`.
+
The first bit of the nonce string is `nonce_be(N, n)[n-1]` and the last is bit `0`.
For `r` = 0 this reduces to `bswap(N[n-1:0])`, so a nonce occupying a whole number of bytes is
unaffected. `bswap` alone cannot express the general case, since it is defined only over byte
strings.

//

State Machine:::
* *States:*
+
--
Besides _Ready_, _Success_, and _Failure_, the OCB Mode Algorithms make use of the following states:

 ** _Set_Aux_Value_: Set the length and the value of the nonce.
 ** _Hash_Absorb_: Set the tag length, and process the AD.
 ** _Hash_Absorb_Last_Block_: Set the length of the final block (mandatory, can be zero) of the AD and process it.
 ** _Encrypt_: Process the plaintext by absorbing it into the tag and encrypting it.
 ** _Enc_Last_Block_: Provide the last block of the plaintext, then process it.
 ** _Enc_Tag_Finalize_: Return the tag.
 ** _Decrypt_: Process the ciphertext by decrypting it and absorbing the plaintext into the tag.
 ** _Dec_Last_Block_: Provide the last block of the ciphertext, then process it.
 ** _Hash_Verify_: Compare a user-provided value with the internally computed tag.
--

* *Allowed State Transitions:*
 ** _Ready_ -> _Set_Aux_Value_ -> _Hash_Absorb_ -> _Hash_Absorb_Last_Block_
 ** _Hash_Absorb_Last_Block_ -> _Encrypt_, if encryption is allowed.
 ** _Hash_Absorb_Last_Block_ -> _Decrypt_, if decryption is allowed.
 ** _Encrypt_ -> _Enc_Last_Block_ -> _Enc_Tag_Finalize_ -> _Success_.
 ** _Decrypt_ -> _Dec_Last_Block_ -> _Hash_Verify_ -> _Success_ or _Failure_.

* *Behavior:*
** In general, the Algorithm needs to make frequent use of the following values
+
--
  . `L* = enc_blk(K, zeros(128))`
  . `L$ = double(L*)`
  . `L[0] = double(L$)`
  . `L[i] = double(L[i-1])`, computed for all `i`  with `0 < i < floor(log_2(MAX_BLOCKS))` (possibly lazily).

These values can be precomputed and stored in the implementation specific data section upon SCC export and retrieved upon SCC import, or recomputed upon SCC import. The latter option is likely to be faster.
--

** In State _Ready_ :
  *** The following initialization operations are performed:
   . `N <- zeros(120)`.
   . `N_len <- 0`.
   . `hash_A <- zeros(128)`
   . `checksum_P <- zeros(128)`
   . `index <- 0`

** To move to _Set_Aux_Value_, a Form B `ace.setst` is expected, where the auxiliary argument `Xs` sets the nonce length `N_len`. `N_len` must satisfy `6` {le} `N_len` {le} `120`; any other value causes the CR to transition to Error State _Invalid_.
Every bit length in that range is admissible: the nonce is a bit string and need not occupy a whole number of bytes.
+
[NOTE]
====
cite:[RFC7253] itself places no lower bound on the nonce length. ACE requires at least 6 bits
because a shorter nonce leaves the `bottom` and `Stretch` derivation of cite:[RFC7253] {sect}4.2
without enough entropy to remain sound, as analyzed in cite:[cryptoeprint-2023-326]. An
implementation of this specification is therefore not a general RFC{nbsp}7253 implementation for
nonces shorter than 6 bits.
====

** In State _Set_Aux_Value_, ``ace.exec`` instructions are expected to be of Form B, namely
   “``ace.exec Kn|K{Xn}, INPUT``”, which sets `N` to the `q` = {lceil}`N_len`/8{rceil} bytes of
   `INPUT` that carry the nonce, namely `N <- zeros(120 - 8q) @ INPUT[8q-1:0]`, with the
   `(8 - N_len) mod 8` least significant bits of byte `q-1` cleared. Those bits are the padding
   of the final, partial byte of the nonce string; they are not part of the nonce and are ignored.
  *** If “``ace.exec Kn|K{Xn}, INPUT```,” is repeated, it rewrites `N`.

** To move to _Hash_Absorb_, a Form B `ace.setst` instruction is expected, where the auxiliary argument `Xs` sets the tag length `tag_len`.
   The admissible values for this argument are 64, 96, or 128.
   Any other value causes the CR to transition to Error State _Invalid_.
  *** The following operations are performed:
  . `index <- 1`
  . `tag_len <- Xs`.
  . `offset <- zeros(b)` – this is `Offset~0~` in the RFC.
  . `L* <- enc_blk(key, zeros(b))` – this is `L~*~` in the RFC.
  . `L$ <- double(L*)`
  . `L[0] <- double(L$)`
  . `L[i] <- double(L[i-1])`, performed lazily for all `i`  with `0 < i < 48`.

** In State _Hash_Absorb_, (multi-block) `ace.exec` instructions are expected to be of Form B, whereby “``ace.exec Kn|K{Xn}, INPUT``” absorbs a data block into `tag`, i.e.:
+
--
 . If `index = ones(48)`, then the CR transitions to Error State _Invalid_, and the instruction terminates.
 . `offset = offset xor L~ntz(index)~`.
 . `hash_A <- hash_A xor enc_blk(key, INPUT xor offset)`.
 . `index <- index + 1`.
--
** To move to _Hash_Absorb_Last_Block_, a Form B `ace.setst` operation is expected, to set the length of the final block of the AD in `last_blk_len`.

** In State _Hash_Absorb_Last_Block_, only a single `ace.exec` instruction of Form B may be executed if `last_blk_len` != `0`. “``ace.exec Kn|K{Xn}, INPUT``” which absorbs the last data block in `tag`, i.e.:
+
--
  * `tmp : bits(b)`

[]
  . If `index = ones(48)`, then the CR transitions to Error State _Invalid_, and the instruction terminates.
  . if `last_blk_len` != `0`, then:
  .. `offset <- offset xor L*`
  .. `tmp <- ocb_pad(INPUT, last_blk_len) xor offset`
  .. `hash_A <- hash_A xor enc_blk(key, tmp)`
--
+
If `last_blk_len` = 0, however, no `ace.exec` can be executed, and only an `ace.setst` instruction is allowed, to enter State _Encrypt_ or _Decrypt_.

** Upon entering states `_Encrypt_` or `_Decrypt_`, the “setup” and “init” stages of the OCB Algorithm are performed:
+
--
 * `Nonce_be : bits(128)` – this is `Nonce` in the RFC, in the big-endian view.
 * `Ktop : bits(128)`, `Ktop_be : bits(128)`
 * `Stretch_be : bits(192)` – this is `Stretch` in the RFC, in the big-endian view.
 * `bottom : int`

[]
 . `offset`, `L*`, `L$` are defined as when entering State _Hash_Absorb_.
 . `Nonce_be <- bin(tag_len mod 128, 7) @ zeros(120 - N_len) @ 1 @ nonce_be(N, N_len)`
 . `bottom <- int(Nonce_be[5:0])`
 . `Ktop <- enc_blk(key, bswap(Nonce_be[127:6] @ zeros(6)))`
 . `Ktop_be <- bswap(Ktop)`
 . `Stretch_be <- Ktop_be @ (Ktop_be[127:64] xor Ktop_be[119:56])`
 . `index <- 1`
 . `offset <- bswap(Stretch_be[191-bottom : 64-bottom])`
--
+
[NOTE]
====
cite:[RFC7253] {sect}4.2 specifies these variables over a big-endian bit string, with
positions numbered from 1. They are therefore computed here in the `bswap` view of <<ACE-Notation>>.
====

** In State _Encrypt_, (multi-block) `ace.exec` instructions are expected to be of Form A:
“``ace.exec OUTPUT, Kn|K{Xn}, INPUT``” absorbs the plaintext `INPUT` into the `tag` and encrypts `INPUT` into `OUTPUT`, namely:
+
--
 . If `index = ones(48)`, then the CR transitions to Error State _Invalid_, and the instruction terminates.
 . `offset = offset xor L~ntz(index)~`.
 . `checksum_P <- checksum_P xor INPUT`
 . `OUTPUT <- offset xor enc_blk(key, INPUT xor offset)`
 . `index <- index + 1`.
--
** To move to _Enc_Last_Block_, a Form B `ace.setst` instruction is expected to be issued to set the bit length of the final block of the plaintext in `last_blk_len`.

** {empty}
+
--
In State _Enc_Last_Block_, if `last_blk_len` is nonzero, a single ``ace.exec`` instruction of Form A
   “``ace.exec OUTPUT, Kn|K{Xn}, INPUT``` is expected.
In this case, the following operations are performed:

 * `tmp : bits(b)`

[]
 . If `index = ones(48)`, then the CR transitions to Error State _Invalid_, and the instruction terminates.
 . `offset <- offset xor L*`
 . `tmp[last_blk_len-1:0] <- enc_blk(key, offset)[last_blk_len-1:0]` // PAD in RFC{nbsp}7253
 . `OUTPUT <- zeros(128-last_blk_len) @ (INPUT[last_blk_len-1:0] xor tmp[last_blk_len-1:0])`
 . `tmp <- offset xor ocb_pad(INPUT, last_blk_len)`
 . `checksum_P <- enc_blk(key, checksum_P xor tmp xor L$) xor hash_A` // tag

On the other hand, if `last_blk_len` is zero, only an ``ace.exec`` instruction
of Form D, “``ace.exec Kn|K{Xn}```,” is expected, which performs:

. `checksum_P <- enc_blk(key, checksum_P xor offset xor L$) xor hash_A`

In both cases the state then transitions to _Enc_Tag_Finalize_.
--

** In State _Enc_Tag_Finalize_, only a single ``ace.exec`` instruction of Form C,
   “``ace.exec OUTPUT,Kn|K{Xn}```,” is expected, which performs `OUTPUT <-
   zeros(b-tag_len) @ checksum_P[tag_len-1:0]`. The state then transitions to _Success_.

** In State _Decrypt_, (multi-block) ``ace.exec`` instructions are expected to be of Form A.
   Such an ``ace.exec`` decrypts `INPUT` into `OUTPUT`, and absorbs the
   plaintext `OUTPUT` into the `tag`, namely:
+
--
  * `tmp : bits(b)`

[]
  . If `index` = `ones(48)`, then the CR is invalidated, and the instruction terminates.
  . `offset = offset xor L~ntz(index)~`.
  . `tmp <- offset xor dec_blk(key, INPUT xor offset)`
  . `checksum_P <- checksum_P xor tmp`
  . `OUTPUT <- tmp`
  . `index <- index + 1`.
--
** To move to State _Dec_Last_Block_, a Form B `ace.setst` operation must be
   used to also contextually set the bit length of the final block of the
   ciphertext in `last_blk_len`.

** In State _Dec_Last_Block_, if `last_blk_len` is nonzero,
only a single ``ace.exec`` instruction of Form A “``ace.exec OUTPUT, Kn|K{Xn}, INPUT``” is expected.
In this case, the following operations are performed:
+
--
   * `tmp : bits(b)`

[]
   . If `index = ones(48)`, then the CR transitions to Error State _Invalid_, and the instruction terminates.
   . `offset <- offset xor L*`
   . `tmp[last_blk_len-1:0] <- enc_blk(key, offset)[last_blk_len-1:0]` // PAD in RFC{nbsp}7253
   . `OUTPUT <- zeros(128-last_blk_len) @ (INPUT[last_blk_len-1:0] xor tmp[last_blk_len-1:0])`
   . `tmp <- offset xor ocb_pad(OUTPUT, last_blk_len)`
   . `checksum_P <- enc_blk(key, checksum_P xor tmp xor L$) xor hash_A` // tag
   . The state transitions to _Hash_Verify_.

On the other hand, if `last_blk_len` is zero, only an ``ace.exec`` instruction
of Form D, “``ace.exec Kn|K{Xn}```,” is expected, which performs:

. `checksum_P <- enc_blk(key, checksum_P xor offset xor L$) xor hash_A`
  . The state transitions to _Hash_Verify_.
--

** To complete the Algorithm in the decryption branch, a Form C ``ace.setst``
   operation is expected, to (confirm the) transition to State _Hash_Verify_
   and compare the `tag_len` least significant bits of `INPUT` with the
   `tag_len` least significant bits of `checksum_P`:
+
--
  . If the values match, the state transitions to _Success_; otherwise, it transitions to _Failure_.
--

[[ACE-CMAC-mode]]
==== CMAC Functions

{empty}
(((ACE, Algorithm, CMAC)))
CMAC is an algorithm for message authentication codes constructed from a block
cipher. It was designed by Tetsu Iwata and Kaoru Kurosawa and became a NIST
Recommendation in May 2005 cite:[nist-SP-800-38B].

Parameters:::

* `b` = block size of the underlying block cipher.
* `k` = key size (8|`k`).
* Granularity: `b`.

Data Structures:::

* *Provisioning Input*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)   | Field
|  ii  | `k` or 64     | `key` or System Key Identifier
|===
--

* *Internal State*:
  ** `key`: `k` bits.
 ** `hash`: `b` bits.
 ** `last_blk_len`: an integer in the range 0 to `b`, serialized on 32 bits.
 ** `block_base`: int. Amount of data absorbed so far into the block being assembled;
    zero when the last block absorbed was complete.

* *Serialized Context*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
|  Pos. | Size (Bits)   | Field
|   ii  | `k` or 64     | `key` or System Key Identifier
|  iii  | `b`           | `hash`
|   iv  | 32            | `last_blk_len`
|    v  | 32            | `block_base`
|===
--

//

Algorithm-Specific Functions:::

* `enc_blk(key, p) -> c` encrypts block `p` using the key `key`, and returns the result `c`.
* `double` is the OCB3 doubling of <<ACE-OCB-mode>>.
* `gen_subkeys(K) -> (K1,K2)` generates subkeys `K1` and `K2` from the master key `K` as follows:

 . `L <- enc_blk(K, zeros(b))`
 . `K1 <- double(L)`
 . `K2 <- double(K1)`
 . return `(K1, K2)`.


State Machine:::

* *States:*
 ** _Ready_: The CC is ready.
 ** _Hash_Absorb_: Absorb data into the CMAC function.
 ** _Hash_Absorb_Last_Block_: Set the length of the last block to absorb, then absorb it.
 ** _Hash_Output_: Output the CMAC.
 ** _Success_: The CC has completed the CMAC operation.
 ** _Failure_: A CMAC verification has failed.

* *Allowed State Transitions:*
 ** _Ready_ -> _Hash_Absorb_ -> _Hash_Absorb_Last_Block_ -> _Hash_Output_ -> _Success_.
 ** _Hash_Output_ -> _Failure_ (via the verification operation below).
 ** From any valid state to State _Ready_.
* *Behavior:*
 ** In State _Ready_:
  *** `last_blk_len <- 0`
  *** `block_base <- 0`
  *** `hash <- zeros(b)`

 ** In State _Hash_Absorb_, (multi-block) ``ace.exec`` instructions are expected to be of Form B. +
 “``ace.exec Kn|K{Xn}, INPUT```,” absorbs the data block `INPUT` into the hash as follows:
+
--
   . `hash <- enc_blk(key, hash xor INPUT)`.
--
 ** Upon issuing a Form B “``ace.setst Kn|K{Xn}, #ace_state_hash_last_block, Xs``” where `Xs` contains the bit length of the last block, the following happens:
   . if `block_base` != 0, then the CR transitions to Error State _Invalid_, because the previous block is
     not complete and CMAC has no way to absorb a partial block other than as the last one.
   . if `Xs > b`, or if `Xs` is not a multiple of 8, then the CR transitions to Error State _Invalid_.
     The multiple-of-8 requirement is what makes the position of the padding bit below
     well-defined; `Xs` = 0 is admissible and is the empty-message case.
   . `last_blk_len <- Xs`.

 ** In State _Hash_Absorb_Last_Block_, only a single ``ace.exec`` instruction of Form B may be issued, i.e., “`ace.exec Kn|K{Xn}, INPUT`”, to absorb the data block `INPUT`. If `ACELEN` > `b`, only the least significant `b` bits of `INPUT` are considered.
+
--
  . `(K1, K2) <- gen_subkeys(key)`.
  . if `last_blk_len` = `b`, then:
    .. `tmp <- hash xor INPUT xor K1`
  . else, that is if `0` {le} `last_blk_len` < `b`:
    .. `tmp <- hash xor (zeros(b - 8 - last_blk_len) @ 0b10000000 @ INPUT[last_blk_len-1:0]) xor K2`
    .. If `last_blk_len` = 0, `INPUT` is not read and the padded value is `zeros(b-8) @ 0b10000000`.
  . `hash <- enc_blk(key, tmp)`
  . The state is changed to _Hash_Output_.
--

** In State _Hash_Output_, there are two options:

. A single ``ace.exec`` instruction of Form C can be issued, i.e., “``ace.exec OUTPUT, Kn|K{Xn}``”, to output the hash into `OUTPUT`.
   Bits of `OUTPUT` beyond the `b`-th are cleared.
   Upon issuing that instruction, the CC transitions to State _Success_.

 . Alternatively, a Form C ``ace.setst Kn|K{Xn}, #ace_state_hash_verify, INPUT`` may be issued to verify the CMAC without disclosing it: the `b` least significant bits of `INPUT` are compared with `hash`, and the state transitions to _Success_ if they match, to _Failure_ otherwise. Verification of a truncated CMAC is instead performed in software, after emitting the tag.

//

[[ACE-hash-functions]]
==== Hash and MAC Functions, and XOFs

{empty}
(((ACE, Algorithm, general hashing)))
(((ACE, Algorithm, MAC functions)))
(((ACE, Algorithm, XOF)))
This section defines an interface for hash and MAC functions.
A completely general interface cannot be defined because of the variety of constructions.
However, the one given here is general enough to describe most common functions, such as SHA2 cite:[nist-fips-180-4], SHA3, and SHAKE cite:[nist-fips-202].

Parameters:::

* `b` = block size (8|`b`). This is the size of an absorbed block and may be different from the size of the internal state that is kept by the function. For a sponge function, this value is the _rate_.
* `t` = tag length (8|`t`). This is the size of the digest, or of the block output each time in a XOF. The present description assumes `t` {le} `b`.
* `n` = size of the internal state kept by the function (8|`n`). For a sponge function, `n-b` is the _capacity_ of the function. Either the block size is an integer multiple of the vector length or the vector length is an integer multiple of the block size.
* `k` = key size (8|`k`). Present only if keyed, i.e., a MAC.
* `state_offset` = offset into the state where the block is to be absorbed.
* `tag_offset` = offset of the tag into the state (for instance, when squeezing sponges).
* Granularity: can vary depending on the Algorithm. This is usually the full length of a vector or vector group.

Data Structures:::

* *Provisioning Input*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)             | Field
|  ii  | If keyed: `k`, else 64  | `key` or System Key Identifier
|===
--

* *Internal State*:
  ** `key`: `k` bits. Present only if keyed, i.e., a MAC.
 ** `state`: `n` bits.
 ** `last_blk_len`: int. Present only if the Hash/MAC needs to provide special handling of a final block beyond caller-managed padding and appending the length.
 ** `input_base`: int. Offset within input/output to read from/write to.
 ** `block_base`: int. Length of absorbed data so far for the current block. Only if required by the Algorithm.
 ** `cumul_len`: int. Cumulative length of data absorbed so far.
 ** `block`: `b` bits.  Included only if a partial block is maintained separately—for instance when the inputs are not directly absorbed into `state`.

* *Serialized Context*:
+
--
[cols="^6%,<21%,<18%,<55%",options="header"]
|===
|  Pos. | Size (Bits)          | Field             | Notes
.2+| ii | If keyed: `k` or 64  | `key` or SKID     | --
<|        If unkeyed: 0        | none              | --
|   iii | `n`                  | `state`           | --
|    iv | 16                   | `last_blk_len`    | Present only if the Hash/MAC needs to provide special handling of a final block beyond caller-managed padding and appending the length.
|    v | 16                    | `block_base`      | Amount of data stored so far into `block` or accumulated (usually XORed) into `state`.  Only if used by the Algorithm, else zero padding.
|    vi|  32                   | Padding           |--
|   vii | 64                   | `cumul_len`       | Cumulative length of the data absorbed so far. Present only if incorporated into the hash by the Algorithm, or under HMAC (<<ACE-HMAC>>), else absent.
|  viii | `b`                  | `block`           | Only if `block_base` is defined and the block is stored separately from the `state`.
|===
--

//

NOTE: If any of the fields `last_blk_len`/`block_base`/`cumul_len` is not used, it is replaced by a corresponding padding block.
If all three are unused by the hashing Algorithm, the entire group is omitted, as well as `block`.

Algorithm-Specific Functions:::

* `process_block()`: Process `block` into the hash or MAC.
* `process_last_block()`: Process `block` into the hash or MAC, using a function
  for the last block.
* `finalize()`: Process the `state` into the digest value. We assume this
  either re-uses `block` (the entire digest, or a unit of XOF output should not
  be bigger than that) or the digest will be part of `state`.
* `update()`: Updates the `state` during the digest output stage.

State Machine:::

* *States:* _Ready_, _Hash_Absorb_, _Hash_Absorb_Last_Block_ (optionally), _Hash_Output_ and _Success_.

 ** _Ready_: The CC is ready.
 ** _Hash_Absorb_: Absorb data into the hash function.
 ** _Hash_Absorb_Last_Block_: Set the length of the last block to absorb, then absorb it.
    Some Algorithms may not support this state.
 ** _Hash_Output_: Output the hash.
 ** _Success_: The CC has completed the operation (XOFs do not have this state).

* *Allowed State Transitions:*
 ** _Ready_ -> _Hash_Absorb_ -> { _Hash_Absorb_Last_Block_ -> } _Hash_Output_ -> _Success_.
 ** From any valid state to State _Ready_.

* *Behavior:*
 ** In State _Ready_:
  *** `last_blk_len`, `block_base`, `cumul_len` and `block` are set to zero.
  *** `state`: the initial value is set as specified by the Algorithm.

 ** In State _Hash_Absorb_, we enter Subalgorithm `process_VLI` (cf. <<ACE-process-VLI>>) as:
`process_VLI(max_len, block, b, state, n, input_base, block_base, state_offset, cumul_len, process_block(), finalize(), mode)`,
where `max_len` is the Algorithm-defined maximum length of the data to be absorbed, in bits, and `state_offset` is Algorithm-defined.
`mode` is `assign` for a construction that fills a separate `block` and then processes it into
`state` through `process_block()`, and `xor_accumulate` for one that absorbs the input directly into
`state`, as a sponge does; each instantiation states which it uses.

 ** Upon issuing a Form B “`ace.setst Kn|K{Xn}, \#ace_state_hash_last_block,
    Xs`” where `Xs` contains the length of the last block, the following
    happens:
+
--
 . if `block_base` != 0, then the CR transitions to Error State _Invalid_. (The previous block is not complete.)
 . if `Xs > b`, then the CR transitions to Error State _Invalid_.
 . if `Xs = 0`, then the CR transitions to Error State _Invalid_.
 . `last_blk_len <- Xs`.
--
+
Then, state transitions to _Hash_Absorb_Last_Block_ as expected.

** State _Hash_Absorb_Last_Block_ is very similar to _Hash_Absorb_; the differences
   are:
 *** `last_blk_len` is used in place of `b` for the amount of data to be absorbed.
 *** `process_last_block()` is called instead of `process_block()` in Step 4.g.
 *** The instruction is terminated after `process_last_block()`—only one block
     is absorbed—and the state transitions to _Hash_Output_.

** In State _Hash_Output_, hash functions and XOFs behave differently.
 *** Upon entering the state, the following operations are first performed:
 . `block[t - 1 : 0] <- finalize()`
 . `block_base <- 0`
*** For each Form C `ace.exec` instruction “`ace.exec OUTPUT, Kn|K{Xn}`”, the
    following operations are performed:
+
--
    * `amount : int`, `{nbsp}` amount of data to copy from `block` to `OUTPUT`
    * `#define output_base input_base`

[]
   . `output_base <- 0` // upon resumption, `output_base <- 8 {interpunct} acestart`
    . while (`output_base` < `ACELEN`) do: // as long as there is room in the OUTPUT
     .. `amount <- min(ACELEN - output_base, t - block_base)`
     .. ``OUTPUT[output_base + amount - 1 : output_base] <- `` +
           ``{fournbsp}{fournbsp}<- block[block_base + amount - 1 : block_base]``
     .. `output_base <- output_base + amount`
     .. `block_base <- block_base + amount`
     .. if (`block_base` = `t`) then:
      ... if we are in a Hash function, any bits of `OUTPUT` beyond `output_base` are cleared,
          the state transitions to _Success_, and the instruction returns.
      ... `update()`
      ... `block_base <- 0`
      ... *Here* the instruction can be interrupted, with `acestart <- output_base / 8`.
--

[[ACE-SHA-2]]
==== SHA-2 Family Specific Rules

{empty}
(((ACE, Algorithm, SHA-2)))
The primitives of the SHA-2 family cite:[nist-fips-180-4] — SHA-224, SHA-256, SHA-384,
SHA-512, SHA-512/224, and SHA-512/256 — are instantiations of the Algorithm specified in
<<ACE-hash-functions>>, and only the differences with respect to the behavior described
there are given here.

Parameters:::

* The word size `w`, and `b`, `n`, and `t`, as given in <<ACE-SHA-2-parameters>>; the
  internal state consists of the eight `w`-bit chaining variables of
  cite:[nist-fips-180-4].
* Granularity: 32 bits, with the same meaning as in <<ACE-SHA-3>>.

[[ACE-SHA-2-parameters]]
.Parameters of the SHA-2 family
[%autowidth,float="center",align="center",cols="<,^,^,^,^",options="header"]
|===
| Function    | `w` | `b`  | `n`  | `t`
| SHA-224     |  32 |  512 |  256 | 224
| SHA-256     |  32 |  512 |  256 | 256
| SHA-384     |  64 | 1024 |  512 | 384
| SHA-512     |  64 | 1024 |  512 | 512
| SHA-512/224 |  64 | 1024 |  512 | 224
| SHA-512/256 |  64 | 1024 |  512 | 256
|===

// *Endianness.* cite:[nist-fips-180-4] is written with big-endian `w`-bit words. Under the
// conventions of <<ACE-Notation>>, the `j`-th message word of a block, for `0` {le} `j` <
// `b`/`w`, is the big-endian interpretation of bytes `j` {interpunct} `w`/8 to
// (`j`+1) {interpunct} `w`/8 − 1 of the absorbed string, that is,
// `int(bswap(block[(j+1) {interpunct} w − 1 : j {interpunct} w]))`. The digest is emitted
// symmetrically: the `i`-th chaining variable occupies bytes `i` {interpunct} `w`/8
// onward as its big-endian encoding `bswap(bin(H~i~, w))`, truncated to `t` bits overall
// for the truncated variants, as cite:[nist-fips-180-4] prescribes.

Data Structures:::

* *Provisioning Input*: as for <<ACE-SHA-3>>, the MDH only.

* *Internal State*:

   ** `state`: `n` bits.
   ** `block` (`b` bits).
   ** `block_base`.
   ** `cumul_len` only when operating under HMAC (<<ACE-HMAC>>).

* *Serialized Context*: as prescribed by <<ACE-hash-functions>>, with `last_blk_len`
  unused (replaced by padding) and `block` present.

Algorithm-Specific Functions:::

* `process_block()`: applies the compression function of cite:[nist-fips-180-4] {sect}6 for the
  selected function to absorb the current `block` into `state`.
* `finalize()`: `None` for stand-alone hashing — padding and length encoding are the
  caller's responsibility. When operating under HMAC, `finalize()` applies the padding of
  cite:[nist-fips-180-4] {sect}5.1 internally; see <<ACE-HMAC>>.

State Machine:::

* *States:* _Ready_, _Hash_Absorb_, _Hash_Output_, and _Success_. There is no
  _Hash_Absorb_Last_Block_ state: the caller supplies the padded message as whole blocks.

* *Allowed State Transitions:*
 ** _Ready_ -> _Hash_Absorb_ -> _Hash_Output_ -> _Success_.
 ** From any valid state to State _Ready_.

* *Behavior:*
 ** In State _Ready_, `state` is set to the initial hash value of the selected function
    per cite:[nist-fips-180-4] {sect}5.3, and `block_base` and `cumul_len` are zeroed.
 ** In State _Hash_Absorb_, Subalgorithm `process_VLI` (cf. <<ACE-process-VLI>>) is
    entered as
    `process_VLI(max_len, block, b, state, n, input_base, block_base, 0, cumul_len, process_block(), None, mode=assign)`,
    where `max_len` is a system-defined maximum length in bits, or zero if none is
    enforced. `mode` is `assign`: the SHA-2 family fills a separate `block` and then applies
    the compression function to it and `state` with a result in `state`.
 ** Upon transitioning to State _Hash_Output_ in stand-alone hashing, `block_base` must
    be zero — the padded message is a whole number of blocks — otherwise the CR
    transitions to Error State _Invalid_.
 ** In State _Hash_Output_, the `t`-bit digest is taken from `state`, not from `block`. The
    output loop of <<ACE-hash-functions>> therefore reads
    `state[block_base + amount - 1 : block_base]` in place of
    `block[block_base + amount - 1 : block_base]`, and the entry step
    `block[t - 1 : 0] <- finalize()` is not performed, `finalize()` being `None` here. The bytes
    so emitted are the chaining variables in the big-endian encoding, truncated to `t` bits.
    Once `t` bits have been made available the state transitions to _Success_.

[[ACE-HMAC]]
==== HMAC

While hash function acceleration is sufficient to compute HMACs, an environment may want to provide a secret or hidden key for HMAC computation.
This section extends <<ACE-hash-functions>> to support HMAC computation with secret or hidden keys.

When a hash function is operating under HMAC, padding and length encoding are performed internally by the HMAC Algorithm during finalization, and not by the caller. For SHA-2 (<<ACE-SHA-2>>) and SM3 (<<ACE-SM3>>), standard padding is applied over the total absorbed length (`b` + `cumul_len` bits for the inner hash, `b` + `d` bits for the outer) using `cumul_len`, which is maintained under HMAC. For SHA-3, the suffix-and-padding of <<ACE-SHA-3>> applies.

Parameters:::
+
--
* `b` = input block size of the underlying hash function.
* `d` = digest size of the underlying hash function, i.e. the length of its output.
* Granularity: same as that of the underlying hash function.

The two padding constants of cite:[nist-fips-198-1] are:

* `ipad` = the byte `0x36` repeated `b`/8 times, and
* `opad` = the byte `0x5c` repeated `b`/8 times,

both therefore `b` bits long. Every byte of each constant has the same value, so their
representation does not depend on the byte order of <<ACE-Notation>>.
--

Data Structures:::

* *Provisioning Input*:
+
--
All HMAC Algorithms exist in two variants, distinguished by a different encoding in the `mode` field.

The PI of the variant that starts with “No Initial Key” (NIK) contains only the MDH.

The PI of the variant with the “Key in PI” (KIP) has the following format:

[cols="^7%,<23%,<70%",options="header"]
|===
| Pos. | Size (Bits)               | Field
|  ii  | `b^*^`                    | `K0`, the key already reduced to `b` bits (see below), or 64 bits if a system key or randomly generated.
|===

The key provisioned or held in a CC is the value `K0` as defined in cite:[nist-fips-198-1] {sect}3: the key padded with zeros to `b` bits if it is shorter, or hashed and then padded if it is longer.
Deriving `K0` from the original key is the responsibility of whoever provisions it.
--

* *Internal State*:
  ** `hash_fn_state`: this is the entire state of the underlying hash function.
     We assume it has fields corresponding to the following ones:
  *** `state`: `n` bits.
  *** `last_blk_len`: int. Present only if the underlying hash function provides special treatment for a last block that goes beyond padding and appending the length. The latter is the caller's responsibility.
  *** `input_base`: int. Offset within input/output to read from/write to.
  *** `block_base`: int. Length of absorbed data so far for the current block. Only if needed by the Algorithm.
  *** `cumul_len`: int. Cumulative length of data absorbed so far (if the Algorithm processes and incorporates it in the hash on its own).
  *** `block`: `b` bits.  Included only if a partial block is maintained—for instance when the inputs are not directly absorbed into `state`.
 ** `K0`: `b` bits, the value `K0` as per cite:[nist-fips-198-1] {sect}3.

* *Serialized Context*:
+
--
[cols="^7%,<23%,<70%",options="header"]
|===
| Pos. | Size (Bits)              | Field
|  ii  | variable                 | Serialized Content of the underlying hash function, in its entirety, including its own padding to a multiple of 128 bits.
| iii  | `b^*^` or 64             | `K0`, where `b^*^` = `b` as in the Provisioning Input; 64 bits for a System Key Identifier.
|===
--

//

State Machine::: {empty}
+
--
This Meta-Algorithm inserts one state between _Ready_ and _Hash_Absorb_, called _Set_Key_.

The two variants differ only in how the key first reaches the CC.

In the KIP variant, `K0` is carried in the Provisioning Input.
The key may be given by value or, with _KeyType_ = 1, as an SKID, which includes a randomly generated value.
A KIP CC cannot be re-keyed.

In the NIK variant, the Provisioning Input carries no key. `K0` must be explicitly loaded in State _Set_Key_ before _Hash_Absorb_ can be entered.
--
+
* *Allowed State Transitions:*
 ** For the NIK variant: _Ready_ -> _Set_Key_ -> _Hash_Absorb_ -> and the rest as in the underlying hash function
 ** For the KIP variant: _Ready_ -> _Hash_Absorb_ -> and the rest as in the underlying hash function
 ** From any valid state to State _Ready_.

* *Behavior:*
 ** Upon entering State _Set_Key_, `K0` is zeroed and `input_base`, `block_base` and
    `cumul_len` are set to zero. Re-entering _Set_Key_ therefore replaces the key rather than
    combining the new value with the old one.

 ** In State _Set_Key_ the `b`-bit value `K0` is loaded by one or more Form B
    ``ace.exec`` instructions, through Subalgorithm `process_VLI`
    (cf. <<ACE-process-VLI>>) entered as
+
`{fournbsp}` `process_VLI(b, block=K0, b, state=K0, n=b,` +
`{fournbsp}{fournbsp}{fournbsp}{fournbsp}{fournbsp}` `input_base, block_base, state_offset=0, cumul_len,` +
`{fournbsp}{fournbsp}{fournbsp}{fournbsp}{fournbsp}` `process_block=None, finalize=None, mode=assign)`,
+
where `mode` is `assign` because `K0` is *loaded* into its field, not absorbed into it.

** Upon entering _Hash_Absorb_:
  . `state` is set to the initial value of the underlying hash function.
  . `K0 xor ipad` is computed and absorbed in the underlying hash function.
  . Then the semantics of the underlying hash function are executed, absorbing the message.
** When entering state _Hash_Output_:
+
--
   * local `inner : bits(d)`

[]
   . If needed, finalize the inner hash `H((K0 xor ipad) {vvert} message)`, whose `d`-bit
    value is then in `state[d+tag_offset-1 : tag_offset]`.
  . `inner <- state[d+tag_offset-1 : tag_offset]`.
  . Reinitialize `state` to the initial value of the underlying hash function `H`.
  . `absorb(K0 xor opad)` as per `H`.
  . `absorb(inner)` as per `H`, so that the outer hash digests
    `(K0 xor opad) {vvert} H((K0 xor ipad) {vvert} message)`, as
    cite:[nist-fips-198-1] {sect}4 requires.
  . Finalize `H`. The `d`-bit HMAC value is available in State
    _Hash_Output_ exactly as for `H`, and is provided to the caller following `H`'s semantics.
--

[[ACE-SHA-3]]
==== SHA-3 Family Specific Rules

{empty}
(((ACE, Algorithm, SHA-3)))
We describe here the Algorithms for the primitives of the SHA-3 family, currently including SHA3-224, SHA3-256, SHA3-384, SHA3-512, SHAKE128, and SHAKE256-
all parameter choices of KECCAK cite:[DBLP-conf-eurocrypt-BertoniDPA13] as standardized by NIST cite:[nist-fips-202].
They are instantiations of the Algorithm of <<ACE-hash-functions>>: only the differences with respect to the generic behavior need to be described.

//

Parameters:::

* `n` = 1600.
* `c` = capacity, `b` = rate = 1600 - `c`, and `t` = the number of bits made available by
  each application of `P()` in the output stage, all as given in
  <<ACE-SHA-3-parameters>>.
* Granularity: 32 bits. This is the smallest element width that may be used for the
  vector inputs of `ace.exec`, not a constraint on the length of the hashed message.

[[ACE-SHA-3-parameters]]
.Parameters of the SHA-3 family
[%autowidth,float="center",align="center",cols="<,^,^,^,^,<",options="header"]
|===
| Function | `c` | `b` = 1600 - `c` | `t` | XOF? | Suffix `D`
| SHA3-224 |  448 | 1152 |  224 | no  | `01`
| SHA3-256 |  512 | 1088 |  256 | no  | `01`
| SHA3-384 |  768 |  832 |  384 | no  | `01`
| SHA3-512 | 1024 |  576 |  512 | no  | `01`
| SHAKE128 |  256 | 1344 | 1344 | yes | `1111`
| SHAKE256 |  512 | 1088 | 1088 | yes | `1111`
|===

For the four fixed-output functions, `t` is the digest length, which is `c`/2, and a
single squeeze suffices. For the two extendable-output functions, `t` is the full rate
`b`, since a sponge makes exactly `b` bits available between successive applications of
the permutation.

Data Structures:::

The *Provisioning Input* contains only the MDH.

* *Internal State*:
  ** `state`: `n` bits.
 ** `input_base`: int.
 ** `block_base`: int.

* *Serialized Context*:
+
--
[%autowidth,cols="^,<,<",options="header"]
|===
| Pos. | Size (Bits)   | Field
|  ii  | 1600            | `state`
| iii  | 16              | `block_base`
|===

`input_base` is not serialized: it is reset at the start of every `ace.exec` and restored from
`acestart` on resumption (<<ACE-process-VLI>>), so it carries no state across a context switch.
`last_blk_len` and `cumul_len` are absent because SHA-3 uses neither.
--

//

Algorithm-Specific Functions::: {empty}
 * `P()`: computes `KECCAK-p[1600, 24]` on `state`, with result in place.
 * `process_block()`: there is no explicit operation to copy data into
   `state`, as the inputs are directly XORed into it; instead, `process_block`
   applies `P()` to the state.
 * `update()`: updates the `state` during the digest output stage.  It applies `P()` to the state.

//

State Machine::: {empty}
* *States:* _Ready_, _Hash_Absorb_,
  _Hash_Output_ and _Success_.

* *Allowed State Transitions:*
 ** _Ready_ -> _Hash_Absorb_ -> _Hash_Output_ -> _Success_.
 ** From any valid state to State _Ready_.

* *Behavior:*
 ** In State _Ready_, `state` is zeroed.
 ** In State _Hash_Absorb_, the input data is directly XORed to `state`.
 This is done in
 Subalgorithm `process_VLI` (cf. <<ACE-process-VLI>>) as:
`process_VLI(max_len=0, state, b, state, n, input_base, block_base, 0, None, process_block(), None, mode=xor_accumulate)`,
 ** Upon transitioning to State _Hash_Output_:
 The suffix-and-padding string `S` = `pad10*1`, appended to `D`, is generated, where `D` is the domain-separation suffix given in <<ACE-SHA-3-parameters>> and `pad10*1` appends a `1`, then as many `0` bits as required, then a final `1`, so that `block_base` + `|S|` is a positive multiple of `b`. Then, the resulting additional block is absorbed:

 . If the bit length of `S` is `b - block_base`:
    .. `S` is directly XORed to the rate part of the state, and
    .. `P()` is applied.
   . If the bit length of `S` is `2 b - block_base`:
    .. The first `b - block_base` bits are XORed to the rate part of the state,
    .. `P()` is applied,
    .. the remaining `b` bits are XORed to the rate part of the state, and
    .. `P()` is applied again.

 ** In State _Hash_Output_, a digest or XOF is extracted following the generic hash function/XOF rules.
  The four SHA3-``n`` functions make a single `t`-bit digest available and then transition to _Success_.
  SHAKE128 and SHAKE256 are XOFs: they never transition to _Success_, and output may be squeezed indefinitely.

The rest of the Algorithm follows <<ACE-hash-functions>>.

[[ACE-KMAC]]
==== KMAC128, KMAC256, KMACXOF128, and KMACXOF256

{empty}
(((ACE, Algorithm, KMAC)))
KMAC is the keyed MAC built on cSHAKE, standardized by NIST in cite:[nist-SP-800-185].
It is defined only over the SHA-3 permutation, so its implementation depends on implementing SHA-3.
This section describes only the differences with respect to <<ACE-SHA-3>>, on which it builds.

Parameters:::

* `n` = 1600.
* KMAC128 and KMACXOF128 use `c` = 256 and rate `b` = 1344 bits (168 bytes);
  KMAC256 and KMACXOF256 use `c` = 512 and rate `b` = 1088 bits (136 bytes).
* `t` = `b`, as for the extendable-output functions of <<ACE-SHA-3-parameters>>.
* `L` = the requested output length in bits, set on the transition to _Hash_Output_.
* Granularity: 32 bits, with the same meaning as in <<ACE-SHA-3>>.

Data Structures:::

A CC does not hold the key `K` and the customization string `S` in their raw form. It
holds the two rate-sized blocks that cite:[nist-SP-800-185] derives from them,
prepared by whoever provisions the CC:
+
`{fournbsp}{fournbsp}` `cshake_block` = `bytepad(encode_string("KMAC") {vvert} encode_string(S), b/8)`, and +
`{fournbsp}{fournbsp}` `key_block{nbsp}{nbsp}{nbsp}` = `bytepad(encode_string(K), b/8)`,
+
where `bytepad`, `encode_string` and `left_encode` are as defined in cite:[nist-SP-800-185] {sect}2.3:
+
[%autowidth,float="center",align="center",cols="<,^,^,^",options="header"]
|===
| Function           | rate `b`/8 | maximum \|`K`\| | maximum \|`S`\|
| KMAC128/KMACXOF128 | 168 bytes | 163 bytes | 157 bytes
| KMAC256/KMACXOF256 | 136 bytes | 131 bytes | 125 bytes
|===
+
A provisioner presented with a longer key must reduce it beforehand; this specification
does not define how, since cite:[nist-SP-800-185] does not.

* *Provisioning Input*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)   | Field
|  ii  | `b`           | `cshake_block`
| iii  | `b`           | `key_block`
|===
--

* *Internal State*: as for <<ACE-SHA-3>>, with the addition of
 ** `cshake_block`, `key_block`: `b` bits each; and
 ** `L`: 32 bits, the requested output length in bits.

* *Serialized Context*: as for <<ACE-SHA-3>>, with `cshake_block`, `key_block` and `L`
  appended, and padding to a multiple of 128 bits. Explicitly:
+
--
[%autowidth,cols="^,<,<",options="header"]
|===
| Pos. | Size (Bits) | Field
|  ii  | 1600        | `state`
| iii  | 16          | `block_base`
|  iv  | 48          | Padding
|   v  | `b`         | `cshake_block`
|  vi  | `b`         | `key_block`
| vii  | 32          | `L`
|===
--

//

Algorithm-Specific Functions:::

 * `P()`, `process_block()` and `update()` are as in <<ACE-SHA-3>>.
 * `right_encode(x)` is as defined in cite:[nist-SP-800-185] {sect}2.3: the value `x`
   written as an unsigned big-endian integer on the smallest possible positive number `m`
   of bytes, followed by a single byte holding `m`.

//

State Machine:::

* *States:* _Ready_, _Hash_Absorb_, _Hash_Output_ and _Success_.

* *Allowed State Transitions:* as in <<ACE-SHA-3>>.

* *Behavior:* as in <<ACE-SHA-3>>, with the following differences.

 ** In State _Ready_:
  . `state` is zeroed.
  . `cshake_block` is XORed into the rate and `P()` is applied.
  . `key_block` is XORed into the rate and `P()` is applied.

 ** To transition to State _Hash_Output_, a Form B `ace.setst` instruction is expected for `KMAC128` and `KMAC256`,
    whose auxiliary argument sets `L`, the output length in bits.
    `L` must be non-zero: a zero value causes the CR to transition to Error State _Invalid_.
    If `L` is *not* a multiple of 8, the output is delivered in whole bytes, and the last byte may
    be zero-padded in its significant bits.
+
For `KMACXOF128` and `KMACXOF256`, a Form A `ace.setst` instruction is expected, and `L` is assumed to be zero in the following.

 ** Upon transitioning to State _Hash_Output_:
  . `right_encode(L)` is absorbed, continuing from the current `block_base`.
  . The suffix and padding string `S` = `pad10*1` appended to `D` is generated and
    absorbed exactly as in <<ACE-SHA-3>>, but with the cSHAKE domain-separation suffix
    `D` = `00` in place of the `1111` of the raw SHAKE functions.

 ** In State _Hash_Output_, for `KMAC128` and `KMAC256` exactly `L` bits are made available—that is,
    {lceil}`L`/8{rceil} bytes, the last one zero-padded if `L` is not a multiple of 8 —
    at `b` bits per application of `P()`, after which the state transitions to _Success_.
+
For `KMACXOF128` and `KMACXOF256`, arbitrarily many bits can be squeezed, and these
Algorithms never transition to _Success_.

[[ACE-Ascon-AEAD128]]
==== Ascon-AEAD128

{empty}
(((ACE, Algorithm, Ascon)))
Ascon is a public permutation cite:[DBLP-journals-joc-DobraunigEMS21] standardized by NIST cite:[nist-SP-800-232] together with various cryptographic algorithms designed around it.

In Ascon-AEAD128, the caller is responsible for applying `pad(`{nbsp}{interpunct}`, 128)` to the associated data, so that what State _Hash_Absorb_ absorbs is a whole number of 128-bit blocks.
The final block of the plaintext or ciphertext must *not* be padded by the caller: it is supplied through State _Enc_Last_Block_, resp. _Dec_Last_Block_, whose `last_blk_len` argument gives its length in bits, and the Algorithm applies `pad(`{nbsp}{interpunct}`, 128)` to it internally.
Padding it in software as well corrupts both the ciphertext and the tag.

Parameters:::

* `b` = 128.
* `k` = 128.
* Granularity: 128 bits.

Data Structures:::

* *Provisioning Input*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)   | Field
|  ii  | 128 or 64     | `key` or System Key Identifier
|===
--

* *Internal State*:
  ** `key`: 128 bits, or 64 bits if it is a System Key Identifier.
 ** `state[0 .. 4]`: five 64-bit words, i.e., 320 bits.
 ** `tag_len`: 8 bits as int.
 ** `last_blk_len`: 9 bits as int.

* *Serialized Context*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)     | Field
|   ii | 128 or 64 (padded to 128)       | `key` or System Key Identifier
|  iii | 64              | `state`[0]
|   iv | 64              | `state`[1]
|    v | 64              | `state`[2]
|   vi | 64              | `state`[3]
|  vii | 64              | `state`[4]
| viii | 16              | `last_blk_len`
|   ix | 16              | `tag_len`
|===
--

Algorithm-Specific Functions:::
* `ASCON(p)` applies `p` rounds of ASCON to the `state`.
* `pad(x,r)` appends the bit 1 to the bit string `x`, followed by the bit string `0^j^` where `j` = `(- |x| - 1) mod r`: `pad(x,r) = 0^j^ @ 1 @ x`.

State Machine:::

* *States:*
 ** _Ready_: The CC is ready.
 ** _Hash_Absorb_: Set the nonce, and process the AD.

 ** _Encrypt_: Encrypt the plaintext.
 ** _Enc_Last_Block_: Encrypt the last block of the plaintext.
 ** _Hash_Output_: Return the tag.

 ** _Decrypt_: Decrypt the ciphertext.
 ** _Dec_Last_Block_: Decrypt the last block of the ciphertext.
 ** _Hash_Verify_: Compare a user-provided value with the internally computed tag.

 ** _Success_: The Algorithm has completed its operation without errors.
 ** _Failure_: The Algorithm has completed its operation with an authentication failure.

* *Allowed State Transitions:*
 ** _Ready_ -> _Hash_Absorb_.
 **  _Hash_Absorb_ -> _Encrypt_, if encryption is allowed.
 **  _Hash_Absorb_ -> _Decrypt_, if decryption is allowed.
 ** _Encrypt_ -> { _Enc_Last_Block_ -> } _Hash_Output_ -> _Success_.
 ** _Decrypt_ -> { _Dec_Last_Block_ -> } _Hash_Verify_ -> _Success_ or _Failure_.

* *Behavior:*
** In State _Ready_ :
  *** The following initialization operations are performed:
   . `state[0] <- 0x00001000808c0001`
   . `state[1] <- key[63:0]`
   . `state[2] <- key[127:64]`
   . `state[3] <- zeros(64)`
   . `state[4] <- zeros(64)`
   . `tag_len <- 128`

** In State _Ready_, a Form B `ace.setst Kn|K{Xn}, \#ace_state_set_aux_value, Xs` sets
   `tag_len` {leftarrow} `Xs`. Admissible values satisfy 64 {le} `Xs` {le} 128; any other
   value causes the CR to transition to Error State _Invalid_
   (cite:[nist-SP-800-232] forbids tags shorter than 64 bits).
   The _State_ field is unchanged: setting the tag
   length is an _operation_, not a state.

** To transition to State _Hash_Absorb_, a Form C ``ace.setst`` is expected, whose `INPUT` sets the nonce of the Algorithm as follows:
+
--
  . `state[3] <- INPUT[63:0]`
    . `state[4] <- INPUT[127:64]`
    . `ASCON(12)`
    . `state[3] <- state[3] xor key[63:0]`
    . `state[4] <- state[4] xor key[127:64]`
--
+
If `ACELEN` > 128, only the 128 least significant bits of `INPUT` are considered.

** In State _Hash_Absorb_, only (multi-block) ``ace.exec`` instructions of Form B are expected.
“``ace.exec Kn|K{Xn}, INPUT``” absorbs a data block into the state, i.e.:
+
--
 . `state[0] <- state[0] xor INPUT[63:0]`
 . `state[1] <- state[1] xor INPUT[127:64]`
 . `ASCON(8)`
--
+
If the associated data is empty, the caller must issue no ``ace.exec`` instruction in this state (hence, no permutation is applied).

** Upon entering State _Encrypt_ or _Decrypt_, the following domain separation
   operation is performed:
 . `state[4] <- state[4] xor (1 << 63)`

** In State _Encrypt_, (multi-block) ``ace.exec`` instructions are expected to be of Form A, whereby “``ace.exec OUTPUT, Kn|K{Xn}, INPUT``” encrypts `INPUT` into `OUTPUT`, namely:
+
--
 . `state[0] <- state[0] xor INPUT[63:0]`
 . `state[1] <- state[1] xor INPUT[127:64]`
 . `OUTPUT <- state[1] @ state[0]`
 . `ASCON(8)`
--
** To transition to State _Enc_Last_Block_, a Form B ``ace.setst`` instruction must be issued, whose
auxiliary argument `Xs` is the bit length of the final block. It performs:
+
--
. If `Xs` > 127, then: the CR transitions to Error State _Invalid_.
. If `Xs` is zero, then:
.. `state[0] <- state[0] xor 1` (this is `pad(∅,128)` = `zeros(127) @ 1`)
..  The state machine then transitions to State _Hash_Output_.
. else:
.. `last_blk_len <- Xs`
--
+
If `last_blk_len` is non-zero, the instruction does _not_ cause a transition to State _Hash_Output_; instead, the Algorithm's state machine waits for a Form A `ace.exec`, as described next.

** State _Enc_Last_Block_ is entered only when `last_blk_len` is non-zero. In it,
exactly one `ace.exec` instruction of Form A is expected, to encrypt the last block.
It performs:
+
--
* `tmp : bits(b)`

[]
. `tmp <- pad(INPUT[last_blk_len-1:0], 128)`
. `state[0] <- state[0] xor tmp[63:0]`
. `state[1] <- state[1] xor tmp[127:64]`
. `tmp <- state[1] @ state[0]`
. `OUTPUT <- zeros(128-last_blk_len) @ tmp[last_blk_len-1:0]`
(Only the 128 lsbs of `OUTPUT` are written to.)
.  The state machine then transitions to State _Hash_Output_.
--
+
In State _Enc_Last_Block_ only one 128-bit block is processed.

** In State _Hash_Output_, only one ``ace.exec`` instruction of Form C is expected to be issued, to compute the tag.
“`ace.exec OUTPUT, Kn|K{Xn}`”  performs:
+
--
 . `state[2] <- state[2] xor key[63:0]`
 . `state[3] <- state[3] xor key[127:64]`
 . `ASCON(12)`
 . `state[3] <- state[3] xor key[63:0]`
 . `state[4] <- state[4] xor key[127:64]`
 . `OUTPUT <- zeros(128 - tag_len) @ (state[4] @ state[3])[tag_len-1:0]` (Only the 128 lsbs of `OUTPUT` are written to.)
 . The state machine then transitions to State _Success_.
--
+
In this state only one 128-bit block is processed.

** In State _Decrypt_, (multi-block) ``ace.exec`` instructions are expected to be of Form A, i.e.,
 `ace.exec OUTPUT,Kn|K{Xn},INPUT`. This operation performs:
+
--
* `tmp : bits(128)`

[]
. `tmp <- (state[1] xor INPUT[127:64]) @ (state[0] xor INPUT[63:0])`
. `state[0] <- INPUT[63:0]`
. `state[1] <- INPUT[127:64]`
. `ASCON(8)`
. `OUTPUT <- tmp`
--

** To transition to State _Dec_Last_Block_, a Form B ``ace.setst`` instruction must be issued, whose
auxiliary argument `Xs` is the bit length of the final block. It performs:
+
--
. If `Xs` > 127, then: the CR transitions to Error State _Invalid_.
//A partial final block of 127 bits is legal:
//  `Xs` is a truncation of an already-transferred block, not a transfer length, so
//  <<ACE-truncation-vs-length>> applies and it need not be a multiple of 8. Ascon's
//  `pad` places the terminating `1` at bit position `Xs` for any `Xs`, because
//  cite:[nist-SP-800-232] is written in little-endian bit order.
. If `Xs` is zero, then:
.. `state[0] <- state[0] xor 1`
..  The state machine then transitions to State _Hash_Verify_.
. else:
.. `last_blk_len <- Xs`
--
+
If `last_blk_len` is non-zero, the instruction does _not_ cause a transition to State _Hash_Verify_; instead, the Algorithm's state machine waits for a Form A `ace.exec`, as described next.

** In State _Dec_Last_Block_, only one ``ace.exec`` instruction of Form A is expected to be issued, to decrypt the last block.
The `ace.exec` instruction performs:
+
--
* `S_r : bits(128)` – the rate part of the state
* `P : bits(128)`

[]
. `S_r <- state[1] @ state[0]`
. `P <- zeros(128-last_blk_len) @ (S_r[last_blk_len-1:0] xor INPUT[last_blk_len-1:0])`
. `OUTPUT <- P`
. `S_r <- S_r xor pad(P[last_blk_len-1:0], 128)`
. `state[0] <- S_r[63:0]`
. `state[1] <- S_r[127:64]`
. The state machine transitions to State _Hash_Verify_
--
+
In State _Dec_Last_Block_, only one 128-bit block is processed.

** In State _Hash_Verify_, only one ``ace.exec`` instruction of Form B is expected to be issued, to verify the tag.
“``ace.exec Kn|K{Xn}, INPUT``” performs
+
--
. `state[2] <- state[2] xor key[63:0]`
. `state[3] <- state[3] xor key[127:64]`
. `ASCON(12)`
. `state[3] <- state[3] xor key[63:0]`
. `state[4] <- state[4] xor key[127:64]`
. `INPUT[tag_len-1:0]` is compared to `(state[4] @ state[3])[tag_len-1:0]`.
. If the values match, the state transitions to _Success_;
  otherwise, it transitions to _Failure_.
--
+

[[ACE-Ascon-AEAD128-wsn]]
==== Ascon-AEAD128 with set Nonce

Similarly to GCM with Set IV, Ascon-AEAD128 can also be made into a version with a set nonce.
In this case, the nonce is not supplied on the transition into State _Hash_Absorb_, which
therefore uses a Form A ``ace.setst`` instead of the Form C of <<ACE-Ascon-AEAD128>>, and the
PI has the following form.

Data Structures:::

* *Provisioning Input*:
+
--
[cols="^8%,<15%,<15%,<62%",options="header"]
|===
| Pos. | Size (Bits)   | Field    | Description
|  ii  | 128 or 64     | `key`    | Key value or System Key Identifier
| iii  | 128           | `nonce`  | {empty}
|  iv  | 32            | `budget` | Number of blocks this CC is permitted to process, as `bin(budget,32)`. See the State Machine Behavior below.
|===
--

* *Internal State*: {empty}
+
--
Same as for Ascon-AEAD128, with the addition of

** `budget`: an integer in the range 0 to 2^32^-1, the number of blocks that this CC may
   still process.

In State _Ready_, words 3 and 4 of `state` are initialized thus:

. `state[3] <- nonce[63:0]`
. `state[4] <- nonce[127:64]`

Upon provisioning, `budget` is set to the value carried in the Provisioning Input.
--

* *Serialized Context*: {empty}
+
--
The `budget` is appended to Ascon-AEAD128's serialized context, serialized as `bin(budget,32)`.
It occupies exactly what the implicit padding would have, so the total length is unchanged.
--

* *States and Allowed Transitions:* {empty}
+
--
Same as for Ascon-AEAD128, with the following exception:

** No transition back to State _Ready_ is allowed. This is one of the Algorithm-specific
   prohibitions contemplated by <<ACE-State-field>>: allowing it would reinstall the same
   nonce and permit keystream reuse, which Ascon-AEAD128, unlike a misuse-resistant mode,
   does not survive.
--

* *State Machine Behavior:* {empty}
+
--
The differences with respect to Ascon-AEAD128 are:

 ** To transition to State _Hash_Absorb_, the ``ace.setst`` instruction must be of Form A,
    i.e., _without any additional inputs_, since the nonce is already included in the PI.
 ** Every `ace.exec` that *consumes* blocks decreases `budget` by the number of blocks it
    processed, which is `ACELEN`/128 in States _Hash_Absorb_, _Encrypt_ and _Decrypt_, and
    1 in States _Enc_Last_Block_ and _Dec_Last_Block_. The Form C `ace.exec` of State
    _Hash_Output_ and the Form B `ace.exec` of State _Hash_Verify_ do *not* decrease
    `budget`: they only emit, resp., compare the tag, which consumes no block.
 ** If an `ace.exec` would decrease `budget` below zero, it performs no operation, and the
    CR transitions to Error State _Invalid_.
--

NOTE: The rules do not forbid keeping an older copy of the SCC in memory to restart the
state machine with a restored `budget` and use many-time pads. It is the responsibility of
the caller to make sure that the SCC is not abused. This Algorithm only protects the
confidentiality of the nonce, not against its reuse.

Everything else is as for Ascon-AEAD128.

[[ACE-Ascon-AEAD128-N-masking]]
==== Ascon-AEAD128 with Nonce Masking

The NIST specification also describes a version of Ascon-AEAD128 with _Nonce
Masking_, described as follows:

Data Structures:::
* *Provisioning Input*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
| Pos. | Size (Bits)   | Field
|  ii  | 128 or 64     | `K1` or System Key Identifier
| iii  | 128 or 0      | `K2` or System Key Identifier in Pos. ii
|===
--

* *Internal State*:
  ** `K1`: 128 bits, or 64 bits if it is a System Key Identifier.
 ** `K2`: 128 bits, omitted if a System Key is used.
 ** `state[0 .. 4]`: five 64-bit words, i.e., 320 bits.
 ** `tag_len`: 8 bits.
 ** `last_blk_len`: 9 bits as int, as in <<ACE-Ascon-AEAD128>>, whose
    _Enc_Last_Block_ and _Dec_Last_Block_ states this Algorithm inherits.

* *Serialized Context*:
+
--
[%autowidth,cols="^1,<2,<3",options="header"]
|===
|  Pos. | Size (Bits)   | Field
|   ii  | 128 or 64     | `K1` or System Key Identifier
|  iii  | 128 or 0      | `K2` or System Key Identifier in Pos. ii
|   iv  | 64            | `state`[0]
|    v  | 64            | `state`[1]
|   vi  | 64            | `state`[2]
|  vii  | 64            | `state`[3]
| viii  | 64            | `state`[4]
|   ix  | 16            | `last_blk_len`
|    x  | 16            | `tag_len`
|===
--

The Algorithm has the same states as Ascon-AEAD128, as described in
<<ACE-Ascon-AEAD128>>, with the key `key` equal to `K1` and the nonce `N`
replaced throughout by `N xor K2`.

For encryption and decryption with both nonce masking and a set nonce, the
Algorithm described in <<ACE-Ascon-AEAD128-wsn>> is used, giving `K1` as the
key `key` and providing `N xor K2` as the nonce value. All rules of
<<ACE-Ascon-AEAD128-wsn>> apply to this combination, including the `budget`
mechanism and the prohibition of transitions back to State _Ready_.

[[ACE-Ascon-Hash256]]
==== Ascon-Hash256

In this mode, the caller is responsible for applying proper padding to
the inputs.

Parameters:::

* `b` = 64.
* Granularity: `b`.

Data Structures:::

The *Provisioning Input* contains only the MDH.

* *Internal State*:
  ** `state[0 .. 4]`: five 64-bit words, i.e., 320 bits.
 ** A `countdown`, an integer going from 3 down to 0, is stored in bits [1:0] of _AlgorithmUse_

* *Serialized Context*:
+
--
[%autowidth,cols="^1,<1,<3",options="header"]
|===
|  Pos. | Size (Bits)   | Field
|   ii  | 64              | `state`[0]
|  iii  | 64              | `state`[1]
|   iv  | 64              | `state`[2]
|    v  | 64              | `state`[3]
|   vi  | 64              | `state`[4]
|===
--

Algorithm-Specific Functions:::

* `ASCON(p)` applies `p` rounds of ASCON to the `state`.

State Machine:::

* *States:* _Ready_, _Hash_Absorb_, _Hash_Finalize_, and _Success_.

* *Allowed State Transitions:*
 ** _Ready_ -> _Hash_Absorb_ -> _Hash_Finalize_ -> _Success_.

* *Behavior:*
 ** In State _Ready_ :
  *** The following initialization operations are performed:
   . `state[0] <- 0x0000080100cc0002`
   . `state[1] <- zeros(64)`
   . `state[2] <- zeros(64)`
   . `state[3] <- zeros(64)`
   . `state[4] <- zeros(64)`
   . `ASCON(12)`

  ** In State _Hash_Absorb_, only (multi-block) ``ace.exec`` instructions of Form B are expected to be issued.
 “``ace.exec Kn|K{Xn}, INPUT``” absorbs a data block into the state, i.e.:
+
--
 . `state[0] <- state[0] xor INPUT`
 . `ASCON(12)`
--
** Upon entering _Hash_Finalize_, `countdown` is set to 3.

** In State _Hash_Finalize_, at most four ``ace.exec`` instructions of Form C
   are expected to be issued. To compute the tag, "```ace.exec OUTPUT, Kn|K{Xn}```"  performs
+
--
. If `countdown` != 3, then:
.. `ASCON(12)`
. `OUTPUT[63:0] <- state[0]`
. If `countdown` = 0 then:
.. Transition to State _Success_.
. else:
.. `countdown <- countdown - 1`
--
+
If `ACELEN` {ge} `128`, these operations are executed `ACELEN/64` times, writing to `OUTPUT`[63:0] the first time, then to `OUTPUT`[127:64], `OUTPUT`[191:128], and `OUTPUT`[255:192]. If more than one ``ace.exec`` instruction is required, writing restarts from `OUTPUT`[63:0].
If `countdown` reaches zero before the entire output register is written, the unwritten bits are cleared: this may occur, for instance, if `ACELEN` = `192` or `ACELEN` = `256`.
This is usually not a problem, since the output vectors will usually be configured for 64-bit, 128-bit, or 256-bit blocks, in which case four, two, or one ``ace.exec`` instructions are required, respectively.

//

NOTE: There is no need to provide keyed versions of this Algorithm.
A trusted entity can achieve the same effect by providing a CC after first absorbing some secret content into it, and the same CC can be reused for multiple invocations by keeping a copy of the original SCC.

[[ACE-Ascon-XOF128]]
==== Ascon-XOF128

The Algorithm is the same as Ascon-Hash256 (<<ACE-Ascon-Hash256>>) with the following differences:

. The IV written to `state[0]` in State _Ready_ is `0x0000080000cc0003`.
. `countdown` is not used: output may be squeezed without limit, so there is nothing to count down. The field it would occupy—bits [1:0] of _AlgorithmUse_ in the MDH—is simply left at zero, and since Ascon-Hash256 holds `countdown` there too rather than in the Serialized Context, the Serialized Context of Ascon-XOF128 is identical to that of Ascon-Hash256.
. As much output as desired can be produced in State _Hash_Finalize_, and the Algorithm never transitions to State _Success_.

// ////////////////////////////////////////////////////////////////////

[[ACE-Ascon-CXOF128]]
==== Ascon-CXOF128

Ascon-CXOF128 differs from Ascon-XOF128 in two ways:
the IV is `0x0000080000cc0004`, and the message is prepended with the customization string. The states and their semantics are otherwise identical to Ascon-XOF128, and the management and padding of the customization string are left to the caller.

[[ACE-ECC]]
=== State Machines of the Elliptic Curve Asymmetric Algorithms

Elliptic curve asymmetric Algorithms provide the following functionality:

. Scalar multiplication with known and unknown base point.
//This can be used to implement Diffie-Hellman key exchange.
. ECDSA/EdDSA signature generation and verification.

[NOTE]
====
Due to the wide variety of KDFs, hash functions, and formats, general KEM and PKE support is impractical.
Among all elliptic curve standards, only the Chinese SM2 standards fully specify an integrated encryption scheme cite:[GMT-0003-4-2012].
Their implementation is left to user code via scalar multiplication.
Any resulting key exposed in environment memory should be immediately used to provision a CR and then erased.
====

When an elliptic curve is provisioned into a CR, the default base point (“generator”) according to the standards listed is configured as the `Generator` field in the CR.
This field may be overwritten, and when `ace.setst` is issued on the CR with _Ready_ as destination state, the default base point may be restored.

All values (integers, coordinates, etc.) are in little-endian format.

Parameters:::
+
--
The parameters used in this section are:

 . The bit length `b` of the main fields, such as coordinates, signature R and S fields, scalars;
 . The bit length `h` of the hash used in the signature scheme. For the ECDSA curves, the
   value placed in the `Hash` field is the message digest already reduced as prescribed by
   cite:[nist-fips-186-5] {sect}6.4, that is, its leftmost `min(N, outlen)` bits, where `N`
   is the bit length of the group order and `outlen` that of the digest. Performing that
   reduction is the caller's responsibility, as is choosing an approved hash function.
   For SM2 the value placed in `Hash` is `e` = `SM3(Z~A~ {vvert} M)` of
   cite:[GMT-0003-2-2012], where `Z~A~` = `SM3(ENTL~A~ {vvert} ID~A~ {vvert} a {vvert} b {vvert} x~G~ {vvert} y~G~
   {vvert} x~A~ {vvert} y~A~)`. Both are computed by the caller, which is possible because every
   input to `Z~A~` is public; the ACE unit computes neither.
   For the Edwards curves the field is used differently, and only in pre-hash mode; see
   <<ACE-EdDSA>>;
 . The bit length `j` of the random number used as nonce in signature generation;
 . The number `u` of coordinates used to represent a point (`u` can be 1 or 2); and
 . The number `v` of elements used to represent a signature (`v` can be 1 or 2).

The parameters for the defined curves are:

* NIST cite:[NIST-SP-800-186,nist-fips-186-5]:
  ** secp256r1 (NIST P-256): `b` = `h` = `j` = 256, `u` = `v` = 2.
  ** secp384r1 (NIST P-384): `b` = `h` = `j` = 384, `u` = `v` = 2.
  ** secp521r1 (NIST P-521): `b` = 576 (55 msbs set to zero), `h` = `j` = 576 (55 msbs set to zero), `u` = `v` = 2.
 * Edwards cite:[RFC8032,nist-fips-186-5]:
  ** ed25519:  `b` = 256, `h` = 512; `u` = 1, `v` = 2.
  ** ed448: `b` = 456, `h` = 512; `u` = 1, `v` = 2.
+
--
For the Edwards curves, `u` = 1 because a point is transmitted in the compressed form of
cite:[RFC8032] {sect}5, a single `b`-bit string, and `v` = 2 because a signature is the pair
(`R`, `S`), each a `b`-bit string: an Ed25519 signature is 512 bits and an Ed448
signature 912 bits. Note that `b` = 456 for ed448, the compressed point and each
signature component being 57 bytes rather than 56. `h` = 512 for both because the `Hash`
field, in pre-hash mode, holds the 64-byte `PH(M)`; no value of `j` is given because
these curves do not use `RndNum` (cf. <<ACE-EdDSA>>).
--
 * Brainpool cite:[RFC5639,RFC8734]:
  ** brainpoolP256r1: `b` = `h` = `j` = 256; `u` = `v` = 2.
  ** brainpoolP384r1: `b` = `h` = `j` = 384; `u` = `v` = 2.
  ** brainpoolP512r1: `b` = `h` = `j` = 512; `u` = `v` = 2.
 * SM2 cite:[GMT-0003-1-2012,GMT-0003-2-2012,GMT-0003-3-2012,GMT-0003-4-2012]: `b` = `h` = `j` = 256; `u` = `v` = 2.

Depending on the specification of the Algorithm, non-compressed or compressed points may be used.

All curves specified here are defined over prime fields.
Since the all-ones `b`-bit string does not represent any valid field value, it is used as the coordinate value(s) of a point to represent the point at infinity.
For secp521r1 this sentinel is exempt from the rule that the 55 most significant bits of a coordinate be zero.
--

State Machine::: {empty}
+
--
* *States:*
Besides
_Ready_ (1),
_Success_ (22),
_Failure_ (23),
ECC Algorithms define:
 ** _Set_Generator_ (2)
 ** _Set_Scalar_ (3)
 ** _Point_Mul_ (4)
 ** _Sign_Generate_ (5)
 ** _Sign_Verify_ (6)
 ** _Set_Hash_ (7)
 ** _Set_SecondPt_ (8)
 ** _Set_Signature_ (9)
 ** _Output_ (10)
--

* *Allowed State Transitions:*
+
--
The five states _Set_Generator_, _Set_Scalar_, _Set_Hash_, _Set_SecondPt_, and
_Set_Signature_ are collectively termed the _Set_ states.

 ** _Ready_ -> any _Set_ state.
 ** One can freely transition between any two _Set_ states, and from a _Set_ state to
    itself. Re-entering a _Set_ state erases the field it sets and clears the
    corresponding ``Has``__Var__ flag, so a value may be replaced by loading it again.
 ** From _Ready_ or from any _Set_ state -> one of:
  *** _Point_Mul_;
  *** _Sign_Generate_ only if `HasHash` holds *and* `Scalar` holds a
      configured private key, that is `1` {le} `int(Scalar)` `<` `n`, where `n` is the order
      of the group. A freshly provisioned CC has `Scalar` = 0 and so does not qualify.
      Attempting to enter State _Sign_Generate_ via `ace.setst` without a configured private key
      causes the CR to transition to Error State _Invalid_.
    (For the EdDSA curves, <<ACE-EdDSA>>, the behavior is different.)
  *** _Sign_Verify_ only if `HasSecondPt`, `HasHash`, and `HasSignature`.
 ** _Point_Mul_ -> _Output_ -> _Success_.
 ** _Sign_Generate_ -> _Output_ -> _Success_.
 ** _Sign_Verify_ -> _Success_ or _Failure_.

[none]
* In State _Set_Generator_ we can set a group generator, or a default one.
* In State _Set_Scalar_ we can either set a scalar for scalar multiplication or private key.
* For each __Var__ {in} {`SecondPt`, `Signature`, `Hash`, `RndNum`},
the Boolean variable ``Has``__Var__ is set when all operations required in the corresponding
_Set_ state have been successfully executed, and is held in the _StateExtension_ field as
given in <<ACE-ECC-StateExtension>>. There is no such flag for `Generator` or for `Scalar`:
`Generator` always holds a value, the curve's default one from
provisioning onwards, and `Scalar` is zero until set, which is not a legal private key and
therefore needs no flag.
--

* *Behavior:*

 ** When the CC is created, i.e., provisioned, the `Generator` is set to the default parameter, and `Scalar` is set to zero.

 ** All the “set” and “output” operations follow rule AGR9 of
<<ACE-algorithms-other-rules>>, with the progress recorded in `block_base`, in bytes.

 ** To transition to State _Set_Generator_, a Form A or B `ace.setst` is used.

 *** If no parameter is given, or the value of the GPR used in the Form B `ace.setst` is zero:
  . The default generator of the curve is set.
  . A state change operation can be issued, including to states that require a set `Generator`.

 *** Otherwise:
  . `Generator`, of length `ub`/8 bytes, is loaded using (multi-block) `ace.exec` instructions of Form B, following AGR9.
  . Once it is complete, a state change operation can be issued, including to states that require a set `Generator`.

 ** To transition to any of the States _Set_Scalar_, _Set_Hash_, _Set_SecondPt_, or _Set_Signature_ a Form A `ace.setst` is used.
  *** If there is a current value in the corresponding field _X_ = `Scalar`, `Hash`, `SecondPt`, or
      `Signature`, it is erased, and, for the three fields that have one, the Boolean ``Has``_X_ is
      set to False. `Scalar` has no such flag: it is simply set to zero, which is not a legal
      private key.
  *** Field _X_ is then loaded using (multi-block) `ace.exec` instructions of Form B, following
      AGR9, and ``Has``_X_ is set once the field is complete, where that flag exists.

 ** It is also allowed to transition to _Set_Scalar_ using a Form B `ace.setst` with a non-zero value in the GPR.
    In this case, a random value is set, no further
    `ace.exec` is issued, and the generated value is never disclosed: it leaves
    the CR only as part of an SCC.

 ** *Random numbers and retry rules.*
  *** For signature generation the ACE unit uses a random number.
    `HasRndNum` is set while it is in use. It is never supplied by
    software and never leaves the CR except, when a signature operation is interrupted, in the
    encrypted part of an SCC.
  *** For the ECDSA curves—the NIST and Brainpool parameter sets of this section—the signature is recomputed with a fresh secret whenever a degenerate value arises. cite:[nist-fips-186-5] {sect}6.4.1 requires a retry whenever `r` = 0 or `s` = 0.

  *** For SM2 the corresponding conditions of cite:[GMT-0003-2-2012] apply instead, namely a retry
if `r` = 0, if `r` + `k` = `n`, or if `s` = 0.

  *** The Edwards curves do not use a random secret and thus do not have retry rules.

 ** In State _Point_Mul_, a single Form D ``ace.exec Kn|K{Xn}`` performs a scalar
    multiplication:

  . If `Scalar` does not hold a value with `1` {le} `int(Scalar)` < `n`, the CR
    transitions to Error State _Invalid_.
  . The base point `P` is `SecondPt` if `HasSecondPt` is set (multiplication by an
    unknown point, e.g., a Diffie-Hellman peer value), and `Generator` otherwise
    (multiplication of the known base, e.g., public-key generation).
  . The implementation must verify that `P` is a point of the curve, and, where the
    cofactor is not 1, of the prime-order subgroup; if not, the CR transitions to
    Error State _Invalid_.
  . `SecondPt` {leftarrow} `int(Scalar)` {interpunct} `P`, encoded as in
    <<ACE-ECC>> (the point at infinity by its sentinel value), and `HasSecondPt` is
    set.
  . `OutputType` {leftarrow} False, and the state transitions to _Output_.

 ** In State _Sign_Generate_, a single Form D ``ace.exec Kn|K{Xn}`` generates a
    signature over the base point `Generator`, with private key `d` = `int(Scalar)`
    and message value `e` = `int(Hash)`:

  . For the NIST and Brainpool curves, the signature (`r`, `s`) is computed as
    specified in cite:[nist-fips-186-5] {sect}6.4.1; for SM2, as specified in
    cite:[GMT-0003-2-2012]. The per-signature secret `k` is drawn from the RBG
    (<<ACE-RBG>>) into `RndNum`, with `HasRndNum` set for the duration of the
    operation, and the retry rules above apply.
  . On completion, `Signature` {leftarrow} (`r`, `s`) and `HasSignature` is set;
    `RndNum` is destroyed and `HasRndNum` cleared.
  . `OutputType` {leftarrow} True, and the state transitions to _Output_.

 ** In State _Sign_Verify_, a single Form D ``ace.exec Kn|K{Xn}`` verifies
    `Signature` against the public key held in `SecondPt` and the message value
    `e` = `int(Hash)`, as specified in cite:[nist-fips-186-5] {sect}6.4.2 for the
    NIST and Brainpool curves and in cite:[GMT-0003-2-2012] for SM2. All checks
    those specifications require — the ranges of `r` and `s`, and the validity of
    the public key as a curve point — are performed; if any fails, or the signature
    equation does not hold, the state transitions to _Failure_, else to _Success_.

 ** When the operations in states _Point_Mul_ and _Sign_Generate_ are completed, the state transitions to _Output_ and:
   . If the output is a point, then `OutputType` <- False, and if the output is a signature, then `OutputType` <- True.
     This allows the ACE implementation to determine not only which output must be written out, but also its length.
     *** If `OutputType` = False, the output is in `SecondPt`.
     *** If `OutputType` = True,  the output is in `Signature`.
   . In State _Output_, the result is emitted using (multi-block) `ace.exec` instructions of Form C, following AGR9.
     . Data beyond the length of the output is replaced with zeros in the last exported part.
     . Once the output is complete the state transitions to _Success_; this is the transition of its own that AGR9 admits.

 ** If, after any computation, either `Generator` or `SecondPt` is the point at infinity, the corresponding field is set to the special value that encodes it.

 ** Upon returning to State _Ready_:
  *** If a Form B `ace.setst` is used, the parameter `Xs` determines which of the fields
 `Generator`, `Scalar`, `SecondPt`, `Hash`, and `Signature` are reset, erased, or kept for
 further operations. This is determined by Bits 0 to 6 of `Xs` as follows:
   **** If Bit 0 is set, then `Generator` is reset to the default value.
   **** If Bit 1 is set, then `SecondPt` is erased and flag `HasSecondPt` is unset.
   **** If Bit 2 is set, then `Scalar` is erased.
   **** If Bit 3 is set, then `Hash` is erased and flag `HasHash` is unset.
   **** If Bit 4 is set, then `Generator` is copied onto `SecondPt`. If Bit 0 is set, then `Generator` is set to the default value.
   **** If Bit 5 is set, then `SecondPt` is copied onto `Generator`. If Bit 1 is set, then `SecondPt` is erased afterwards and `HasSecondPt` is set to False.
   **** If Bit 6 is set, then `Signature` is erased and flag `HasSignature` is unset.
  *** Every field whose bit is clear is retained. A Form A `ace.setst` sets no bit and
      therefore leaves `Generator`, `Scalar`, `SecondPt`, `Hash`, and `Signature`
      unmodified.
//
// [NOTE]
// ====
// Retaining `Signature` by default is what allows one CC whose _AlgorithmPolicy_ permits both
// operations to generate a signature and then verify it, since a CR in State _Success_ may only
// transition to _Ready_ or _Unconfigured_ (<<ACE-State-field>>) and must therefore pass through
// _Ready_ between the two operations. The sequence is:
//
// . _Ready_ {rightarrow} _Set_Scalar_ (load the private key) {rightarrow} _Point_Mul_ {rightarrow}
//   _Output_ {rightarrow} _Success_, leaving the public key in `SecondPt`;
// . _Success_ {rightarrow} _Ready_, retaining `Generator`, `SecondPt`, and `Scalar`;
// . _Ready_ {rightarrow} _Set_Hash_ (load the message value) {rightarrow} _Sign_Generate_
//   {rightarrow} _Output_ {rightarrow} _Success_;
// . _Success_ {rightarrow} _Ready_, retaining `SecondPt`, `Hash`, and `Signature`;
// . _Ready_ {rightarrow} _Sign_Verify_, whose preconditions `HasSecondPt`, `HasHash`, and
//   `HasSignature` are all met.
//
// Steps 2 and 4 may use a Form A `ace.setst`, or a Form B one with the bits of the fields to be
// discarded set. The ordinary verification flow, in which `SecondPt`, `Hash`, and `Signature` are
// loaded through their respective _Set_ states, is unaffected.
// ====

** {empty}
+
--
`Progress`, bits [15:1] of _AlgorithmUse_, is the field used following rule AGR8 for Point Multiplication,
Signature Generation and Signature Verification; what an implementation exports to allow resumption
typically includes precomputed multiples of the base point.

An importing implementation that keeps the Additional Data Section must also be willing to trust the
random number generator of the originating implementation. If it is not, it discards that Section
together with `RndNum` (Position viii, if present) and restarts the operation.

[[ACE-EdDSA]]
==== EdDSA-Specific Rules

{empty}
(((ACE, Algorithm, EdDSA)))
EdDSA, standardized in cite:[RFC8032] and cite:[nist-fips-186-5], does not fit the
division of labour used by the other curves of <<ACE-ECC>>, under which the caller hashes
the message and the ACE unit performs only the group arithmetic. Both of its hash
invocations take material the caller does not hold:

`{fournbsp}{fournbsp}` `r{nbsp}`  = `H(dom {vvert} prefix {vvert} M)`, where `prefix` is secret, and +
`{fournbsp}{fournbsp}` `k'` = `H(dom {vvert} R {vvert} A {vvert} M)`, where `R` = `r` {interpunct} `B` is computed inside.

The ACE unit therefore performs the hashing itself. This subsection states the
consequences; everything not restated here follows <<ACE-ECC>>.

Parameters:::

* `H` is `SHA-512` for ed25519 and `SHAKE256`, with a 114-byte output, for ed448.
* The private key is the *seed*: 32 bytes for ed25519 and 57 for ed448, in both cases
  exactly `b` bits, held in the `Scalar` field.
* `dom` is `dom2(x, ctx)` for ed25519 and `dom4(x, ctx)` for ed448, as defined in
  cite:[RFC8032] {sect}2 and {sect}5.2, with `x` = 0 in pure mode and 1 in pre-hash mode.
  For ed25519 in pure mode with an empty context, `dom` is the empty string.

Pure and pre-hash modes:::
+
--
In *pure* mode the unit hashes the message itself; in *pre-hash* mode the caller supplies
`PH(M)`, 64 bytes for both curves, in the `Hash` field. Which modes an implementation
offers depends on the hash extensions it provides:

[%autowidth,float="center",align="center",cols="<,<,<",options="header"]
|===
| Curve extension | Also implements | Modes available
| `Zkled25519c` | --          | Ed25519ph only
| `Zkled25519c` | `Zklesha2h`  | Ed25519 and Ed25519ph
| `Zkled448c`   | --          | Ed448ph only
| `Zkled448c`   | `Zklesha3h`  | Ed448 and Ed448ph
|===

The curve extension alone must provide enough of `H` to hash the fixed-size inputs above,
which are a few hundred bytes at most. Absorbing a message of arbitrary length is what
requires the general hashing machinery, and hence `Zklesha2h` or `Zklesha3h`, respectively. Requesting
pure mode on an implementation that lacks it transitions the CR to Error State `ace_state_unsupported`.
--

Data Structures:::
+
--
In addition to the fields of <<ACE-ECC>>:

* `ctx`: 255 bytes, and `ctxlen`: 8 bits, the context string of cite:[RFC8032]. It is
  optional for ed25519 and mandatory, though possibly empty, for ed448. Both are zero
  upon provisioning and upon entering State _Ready_, and are set in State _Set_Ctx_.
* `msg_pass`: 8 bits, the number of message-absorption passes completed.
* `r`: `b` bits, the secret scalar produced by the first signing pass, reduced modulo the
  group order `L`. Like `RndNum` for the ECDSA curves, it never leaves the CR except in
  the encrypted part of an SCC while a signing operation is in progress.

There is no stored pre-hash mode selector: the mode is inferred from the path taken, as
described below.

`RndNum` is *not* used, and `HasRndNum` is never set: the EdDSA nonce is deterministic by
construction, being derived from `prefix` and the message. Its absence is deliberate.

The clamped scalar `s` and the 32-byte or 57-byte `prefix`, respectively, are derived from the seed
by hashing it with `H`, as cite:[RFC8032] {sect}5.1.5 and {sect}5.2.5 prescribe. An
implementation may recompute them on each use or cache them in the Additional Data Section;
they are never exported in the Algorithm Data Section. The public key `A` is likewise
derived from the seed, or cached in the Additional Data Section.

* *Serialized Context*: the Serialized Context of <<ACE-ECC>>, with the following fields
  appended; `SCC_content_size()` extends past Position xiii.
+
[%autowidth,cols="^1,<3,<5",options="header"]
|===
|  Pos. | Size (Bits)  | Field
|   ix  | 8            | `ctxlen`
|    x  | 2040         | `ctx`
|   xi  | 8            | `msg_pass`
|  xii  | `b`          | `r`
|===

`r` is present unconditionally, and holds zero whenever no signing operation is in progress.
Making its presence conditional on `msg_pass` would be unimplementable: `msg_pass` is carried in
the Content, at Position xi, so the length of the Content could not be computed without first
decrypting it, whereas <<ACE-length-rule>> requires that length to follow from bits [63:0] of the
MDH alone. `r` is `b` bits — 32 bytes for ed25519 and 57 for ed448 — which is a negligible
addition to an SCC of this size, and it remains confidential in either case, being carried in the
encrypted Algorithm Data Section.
--

State Machine:::

* *States:* those of <<ACE-ECC>>, except _Point_Mul_, which is removed, and in addition
 ** _Msg_Absorb_ (11), in which message data is absorbed.
 ** _Set_Ctx_ (12), in which the context string is set.

* *Allowed State Transitions:* those of <<ACE-ECC>>, with the following changes:
 ** _Set_Ctx_ is reachable from, and can transition to, the same states as the _Set_
    states of <<ACE-ECC>>.
 ** _Msg_Absorb_ is entered from _Ready_, any _Set_ state, or _Msg_Absorb_ itself, by the
    Form B `ace.setst` described below; the re-entry from _Msg_Absorb_ into _Msg_Absorb_
    is an explicitly allowed same-state transition, marking a pass boundary.
 ** The entry conditions for _Sign_Generate_ and _Sign_Verify_ of <<ACE-ECC>> are
    replaced by those below; in particular `HasHash` is required only on the pre-hash
    paths.

* *Behavior:*

** Signature generation requires *two* passes over the message, and verification one.
   This is inherent to EdDSA, whose second hash takes `R`, which is not known until the
   first pass has completed. `msg_pass` records the completed passes; it is cleared upon
   entering State _Ready_.

** To transition to State _Set_Ctx_, a Form B `ace.setst` is used whose auxiliary
   argument `Xs` sets `ctxlen`. Values greater than 255 cause the CR to transition to
   Error State _Invalid_. If `ctxlen` {ne} 0, the `ctx` value is then loaded with
   (multi-block) Form B `ace.exec` instructions, following AGR9 as the _Set_ states of
   <<ACE-ECC>> do, with the progress recorded in `block_base`.

** To enter State _Msg_Absorb_ (pure mode only; on an implementation that does not
   support pure mode, see the table above), a Form B `ace.setst` is used whose auxiliary
   argument `Xs` selects the pass:

  . `Xs` = 0, *signing pass 1*: requires that signature generation be allowed and that
    `Scalar` hold a configured seed; `msg_pass` {leftarrow} 0, and `H` is initialized
    with `dom {vvert} prefix`.
  . `Xs` = 1, *signing pass 2*: requires `msg_pass` = 1; `H` is initialized with
    `dom {vvert} R {vvert} A`, with `R` from `Signature` and `A` derived from the seed.
  . `Xs` = 2, *verification pass*: requires that signature verification be allowed and
    that `HasSignature` and `HasSecondPt` hold; `msg_pass` {leftarrow} 0, and `H` is
    initialized with `dom {vvert} R {vvert} A`, with `R` from `Signature` and
    `A` = `SecondPt`.
  . Any other value of `Xs`, or an unmet precondition, causes the CR to transition to
    Error State _Invalid_.

** In State _Msg_Absorb_, Form B ``ace.exec`` instructions absorb message bytes through
   Subalgorithm `process_VLI` (cf. <<ACE-process-VLI>>), with `process_block()` applying
   the compression function of `H`, and with the `mode` of the underlying hash function:
   `assign` for ed25519, whose `H` is `SHA-512` (<<ACE-SHA-2>>), and `xor_accumulate` for
   ed448, whose `H` is `SHAKE256` (<<ACE-SHA-3>>).

** Leaving State _Msg_Absorb_ — by the same-state re-entry above or by a transition to
   another state — finalizes the current pass:
  . after pass `Xs` = 0: `r` {leftarrow} `H(dom {vvert} prefix {vvert} M) mod L`,
    `Signature.R` {leftarrow} `r` {interpunct} `B`, and `msg_pass` {leftarrow} 1
    (`HasSignature` is *not* set: `Signature.R` holds an intermediate value);
  . after pass `Xs` = 1: `k'` {leftarrow} `H(dom {vvert} R {vvert} A {vvert} M)` and
    `msg_pass` {leftarrow} 2;
  . after pass `Xs` = 2: `k'` as above and `msg_pass` {leftarrow} 3.
+
The verification pass records 3 rather than 1 so that it cannot be confused with the completion of
signing pass 1, which also computes a hash but leaves `k'` unset. Were both to record 1, a caller
could run signing pass 1 and then enter _Sign_Verify_, which would verify against a `k'` that was
never computed.

** In State _Sign_Generate_, a single Form D ``ace.exec Kn|K{Xn}`` completes the
   signature per cite:[RFC8032] {sect}5.1.6, resp., {sect}5.2.6:
  . In *pure* mode, entered with `msg_pass` = 2:
    `S` {leftarrow} `(r + k'` {interpunct} `s) mod L`.
  . In *pre-hash* mode, entered with `msg_pass` = 0 and `HasHash` set: both hashes are
    computed internally over the fixed-size inputs, with `Hash` (holding `PH(M)`)
    standing in for the message.
  . Any other combination causes the CR to transition to Error State _Invalid_.
  . `Signature` {leftarrow} (`R`, `S`), `HasSignature` is set, `r` is destroyed,
    `msg_pass` {leftarrow} 0, `OutputType` {leftarrow} True, and the state transitions
    to _Output_.

** In State _Sign_Verify_, a single Form D ``ace.exec Kn|K{Xn}`` verifies `Signature`
   per cite:[RFC8032] {sect}5.1.7, resp., {sect}5.2.7, in *pure* mode when entered with
   `msg_pass` = 3 and in *pre-hash* mode when entered with `msg_pass` = 0 and `HasHash`
   set (any other combination causes the CR to transition to Error State _Invalid_).
   All checks those sections require — the range of `S` and the validity of the
   encodings of `R` and `A` — are performed; if any fails, or the verification equation
   does not hold, the state transitions to _Failure_, else to _Success_.

NOTE: It is the caller's responsibility to present the same message in both signing passes.
A caller that presents different messages produces a signature that verifies against neither.

[[ACE-PQC-ML-KEM]]
==== ML-KEM

The _Module-Lattice-Based Key-Encapsulation Mechanism Standard_ was announced by NIST in August 2024 cite:[nist-fips-203].
The standard defines several procedures, including:

* `ML-KEM.KeyGen`: Generates an encapsulation key `encapsk` and a corresponding decapsulation key `decapsk`.
* `ML-KEM.Encaps`: Uses the encapsulation key `encapsk` to generate a shared secret key `sharedkey` and an associated ciphertext.
* `ML-KEM.Decaps`: Uses the decapsulation key `decapsk` to produce a shared secret key `sharedkey` from a ciphertext.

ML-KEM comes in three versions, ML-KEM-512, ML-KEM-768, and ML-KEM-1024, with increasing cryptographic strength.
They require RBGs of corresponding strength: 128, 192, and 256 bits, respectively.
The sizes of keys and ciphertexts of the three subtypes of ML-KEM are summarized in <<ACE-ML-KEM-sizes>>.

[[ACE-ML-KEM-sizes]]
.Sizes (in bytes) of keys and ciphertexts of ML-KEM
[%autowidth,float="center",align="center",cols="^1,^1,^1,^1,^1",options="header"]
|===
| Subtype     | `encapsk` | `decapsk` | `ciphertext` | `sharedkey`
| ML-KEM-512  |       800 |      1632 |          768 |        32
| ML-KEM-768  |      1184 |      2400 |         1088 |        32
| ML-KEM-1024 |      1568 |      3168 |         1568 |        32
|===

The ML-KEM Algorithms also support the `ace.derive` instruction
(<<ACE-instruction-derive>>), which takes the `sharedkey` already held in the CC—produced by
`_Encapsulate_` or by `_Decapsulate_`—and writes it into a secret field of a second CR. The
destination CC is provisioned beforehand in the ordinary way, which is what selects the symmetric
Algorithm it will run; `ace.derive` only supplies its key.

[NOTE]
====
In ACE's implementation of ML-KEM, the shared key is not treated as an output.
ML-KEM produces key material for a symmetric Algorithm; `ace.derive` moves that
material directly into a second CR as a Cryptographic Context, so the shared secret is
handled entirely inside the ACE unit and never appears in the memory of the process using it.
====

Data Structures:::

* The *Provisioning Input* contains only the MDH.

* *Internal State*:
+
--
 ** `decapsk`: 13056 / 19200 / 25344 bits (1632 / 2400 / 3168 bytes).
 Note that `decapsk` contains `encapsk` whose size is 6400 / 9472 / 12544 bits (800 / 1184 / 1568 bytes).
 ** `ciphertext`: 6144 / 8704 / 12544 bits (768 / 1088 / 1568 bytes).
 ** `sharedkey` 256 bits.

`encapsk`, `decapsk`, resp., `sharedkey` corresponds to `ek`, `dk`, resp.,`K` in cite:[nist-fips-203],

The ML-KEM Algorithms use the _AlgorithmUse_ field of the metadata header to record how many
bits of a long field have been transferred so far: read from memory in the _encapsk_Input_,
_decapsk_Input_, and _ciphertext_Input_ states, or written to memory in the
_encapsk_Output_ and _ciphertext_Output_ states. This is similar to what is done in the
hashing and Elliptic Curve Algorithms.

The size of the internal state of the three variants is 3232, 4704, and 6336 bytes, excluding metadata

The _AuxInfo_ field records the policies that a CC receiving the `sharedkey` through `ace.derive`
is required to carry: the format is the same as bits [79:64] of the MDH, that is the _UsagePolicy_
and _Locality_ fields together with the two Reserved bits that follow them. The destination CC is
provisioned independently, so the _UsagePolicy_ and _Locality_ of the destination will be set
to the union of its current policies, the policies of the source CR, and the ones encoded in
_AuxInfo_ value.
Alternatively: these bits are a *requirement on it*, not a value copied into it: if
bits [79:64] of the destination CC's MDH are not at least as restrictive as _AuxInfo_, the
destination CR transitions to Error State _Invalid_ and no key material is transferred.

Algorithm-Specific Functions:::
+
--
The procedures implemented by ML-KEM are taken directly from cite:[nist-fips-203]:

* `ML-KEM.KeyGen(d, z)` generates encapsulation key `encapsk` and decapsulation key `decapsk` from random seeds `d, z` (cite:[nist-fips-203] Algorithm 19).
* `ML-KEM.Encaps(encapsk, m)` generates ciphertext `ciphertext` and shared key `sharedkey` from encapsulation key `encapsk` and randomness `m` (cite:[nist-fips-203] Algorithm 20).
* `ML-KEM.Decaps(decapsk, ciphertext)` computes shared key `sharedkey` from decapsulation key `decapsk` and ciphertext `ciphertext` (cite:[nist-fips-203] Algorithm 21).

State Machine:::
+
--
* *States:*
Besides
_Ready_ (1),
_Success_ (22),
_Failure_ (23),
ML-KEM Algorithms define:
 ** _GenerateKeyPair_ (2)
 ** _Encapsulate_ (3)
 ** _Decapsulate_ (4)
 ** _encapsk_Input_ (5)
 ** _decapsk_Input_ (6)
 ** _encapsk_Output_ (7)
 ** _ciphertext_Input_ (8)
 ** _ciphertext_Output_ (9)
--

* *Allowed State Transitions:*
 ** State transitions are allowed between any two valid states.

* *Behavior:*

** Upon transitioning to State _Ready_, the fields `encapsk`, `decapsk`, `ciphertext` and `sharedkey` are cleared.

 ** All uses of `ace.setst` do not require an auxiliary parameter.

 ** The ML-KEM Algorithms do not carry state information as to whether
 `encapsk`, `decapsk`, `ciphertext`, and `sharedkey` have been assigned values.
   The input checks that cite:[nist-fips-203] {sect}7.2 and {sect}7.3 require are therefore
   performed when a field finishes loading, and are split according to what a failure means:
+
--
 . Upon completion of State _encapsk_Input_, the *encapsulation key check* of
     cite:[nist-fips-203] {sect}7.2 is performed: the type check (`encapsk` has the length required
     by the parameter set) and the modulus check (`encapsk` re-encodes to itself, i.e. every
     coefficient is reduced modulo `q`).
 . Upon completion of State _decapsk_Input_, the *decapsulation key check* of
     cite:[nist-fips-203] {sect}7.3 is performed: the type check and the hash check (the copy of
     `H(encapsk)` embedded in `decapsk` matches the embedded `encapsk`).
 . A failure of either key check is a *configuration* error: the CR transitions to Error State
     _Invalid_, and the CC must be reconfigured before it can be used.
 . Upon completion of State _ciphertext_Input_, the *ciphertext type check* of
     cite:[nist-fips-203] {sect}7.3 is performed. A failure is a *data* error: the state machine
     transitions to State _Failure_, which is a valid state, and the caller may supply another
     ciphertext.
--
+
These checks do not affect the implicit rejection of `ML-KEM.Decaps`: a ciphertext that passes the
type check but does not decapsulate correctly still yields the `z`-derived shared key, the state
machine still transitions to _Success_, and the two cases remain indistinguishable to the caller.

 ** In State _GenerateKeyPair_, Form D ``ace.exec Kn|K{Xn}`` generates a new key pair using procedure `ML-KEM.KeyGen` of cite:[nist-fips-203] (Algorithm 19).

. If `ML-KEM.KeyGen` fails, the state machine transitions to state _Failure_.
. Otherwise, the state machine transitions to state _Success_.

** In State _Encapsulate_, Form D ``ace.exec Kn|K{Xn}`` executes encapsulation using procedure `ML-KEM.Encaps` of cite:[nist-fips-203] (Algorithm 20), applied to the `encapsk` state field, which must have been set—by `_encapsk_Input_` or by `_GenerateKeyPair_`—before this state is entered. The procedure draws a random value internally and derives from it *both* the shared key and the ciphertext, which are stored in the `sharedkey` and `ciphertext` state fields, respectively; the shared key is not drawn independently of the ciphertext.

  . If `ML-KEM.Encaps` succeeds:
  .. The state machine transitions to state _ciphertext_Output_.
  . else:
  .. The state machine transitions to state _Failure_.

** In State _Decapsulate_, Form D ``ace.exec Kn|K{Xn}`` decapsulates the ciphertext using procedure `ML-KEM.Decaps` of cite:[nist-fips-203] (Algorithm 21).
`ML-KEM.Decaps` is executed unconditionally. The shared key, either derived from the ciphertext or returned via “implicit rejection” is placed in the `sharedkey` state field, and the state machine transitions to state `_Success_`. The caller cannot distinguish the two cases.

** In States _encapsk_Input_, _decapsk_Input_ and _ciphertext_Input_, the fields `encapsk`,
`decapsk` and `ciphertext` are loaded using (multi-block) `ace.exec` instructions of Form B,
following rule AGR9 of <<ACE-algorithms-other-rules>>, with the progress recorded in
_AlgorithmUse_. The size of each field in bits is 8
times the size in bytes given in <<ACE-ML-KEM-sizes>>, so it is determined by the KEM variant and
the state and no variable need hold it.

** In States _encapsk_Output_ and _ciphertext_Output_, the fields `encapsk` and `ciphertext` are
emitted using (multi-block) `ace.exec` instructions of Form C, following rule AGR9, with the
progress recorded in _AlgorithmUse_. Both fields are public, so no restriction applies to where they
are written.

** The `ace.derive` instruction (<<ACE-instruction-derive>>) is used to move the shared key from
this CC into a secret field of a second CR, without it becoming visible to software.
`sharedkey` is the only exportable field of an ML-KEM CC, and its index is 1.
The instruction is of `Form` `00` — an exportable field of the source into a secret field of the
destination — with the source index `i` = 1 and the destination index `j` naming the key field of
the destination CC.
The destination CC must have been provisioned beforehand with a supported single-key Algorithm that
accepts a key of at most 256 bits, and must be in State _Ready_.
`length` gives the number of bytes transferred: if the key of the destination Algorithm is `m` bits
long, `length` = {lceil}`m`/8{rceil} and the `m` least significant bits of the shared key are used.
// The destination CC's _UsagePolicy_ and _Locality_ must satisfy the requirement recorded in the
// _AuxInfo_ field of this CC, as described above.

// independently is through CR provisioning.

[[ACE-PQC-ML-DSA]]
==== ML-DSA

The _Module-Lattice-Based Digital Signature Standard_ was announced by NIST in August 2024 cite:[nist-fips-204] in three variants: ML-DSA-44, ML-DSA-65, and ML-DSA-87.

[[ACE-ML-DSA-sizes]]
.Sizes (in bytes) of keys and signatures of ML-DSA
[%autowidth,float="center",align="center",cols="^1,^1,^1,^1",options="header"]
|===
| Subtype   | Private Key | Public Key | Signature Size
| ML-DSA-44 |     2560    |    1312    |     2420
| ML-DSA-65 |     4032    |    1952    |     3309
| ML-DSA-87 |     4896    |    2592    |     4627
|===

The principal functions offered by ML-DSA are:

* `ML-DSA.KeyGen`: Generates a public-private key pair.
* `ML-DSA.Sign`:   Generates a digital signature for a given message.
* `ML-DSA.Verify`: Verifies a digital signature for a given message.
* `HashML-DSA.Sign`:   Generates a digital signature for a given pre-hashed message.
* `HashML-DSA.Verify`: Verifies a digital signature for a given pre-hashed message.

The ACE ML-DSA Algorithms execute the core lattice operations of signing and verification, specifically `ML-DSA.Sign_internal` and `ML-DSA.Verify_internal` as defined in cite:[nist-fips-204] (Algorithms 7 and 8).

Message hashing and domain formatting (cite:[nist-fips-204] {sect}5) are structured as follows:

* *Pure ML-DSA:* The caller formats the domain-separated message string `M' = 0x00 @ bin(|ctx|, 8) @ ctx @ M` and computes the 64-byte message representative `mu = SHAKE256(tr @ M', 64)`, which is supplied to the ACE unit via State _mu_Input_.
* *HashML-DSA (Pre-Hash):* The caller pre-hashes message `M` with the hash function `PH` specified in the _AuxInfo_ field of the MDH, constructs `M' = 0x01 @ bin(|ctx|, 8) @ ctx @ OID(PH) @ PH(M)`, and computes `mu = SHAKE256(tr @ M', 64)` to be loaded into State _mu_Input_.
* *Public Key Hash (`tr`):* `tr = SHAKE256(pubkey, 64)` is computed inside the ACE unit upon key generation (`_GenerateKeyPair_`) or public key derivation (`_compute_pubKey_`), or loaded via State _tr_Input_ when configuring a CC for verification only.
* *Context String (`ctx`):* The context string `ctx` (up to 255 bytes) and its length `ctxlen` are maintained in the CC to bind the context of the protocol to the hardware session. In implementations supporting internal message absorption, `ctx` and `tr` are used internally to derive `mu`; when `mu` is supplied directly by the caller, `ctx` and `ctxlen` attest that bound in the serialized SCC.


Algorithm-Specific Functions:::
+
--
The procedures implemented by ML-DSA are taken directly from cite:[nist-fips-204]:

* `ML-DSA.KeyGen(xi)` generates public key `pubkey` and private key `privkey` from random seed `xi` (cite:[nist-fips-204] Algorithm 1).
* `ML-DSA.Sign_internal(privkey, mu, rnd)` generates digital signature `signature` from private key `privkey`, message representative `mu`, and randomness `rnd` (cite:[nist-fips-204] Algorithm 7).
* `ML-DSA.Verify_internal(pubkey, mu, signature)` verifies signature `signature` against public key `pubkey` and message representative `mu` (cite:[nist-fips-204] Algorithm 8).
--

Data Structures:::

* The *Provisioning Input* contains only the MDH.
+
--
The _AlgorithmPolicy_ field in the MDH has the following meaning:

. _AlgorithmPolicy_[0] is set to 1 if the Algorithm can generate signatures, and
. _AlgorithmPolicy_[1] is set to 1 if the Algorithm can verify signatures.
. An _AlgorithmPolicy_ of 0 is not valid, and it causes the CR to transition to Error State _Invalid_.

The _AuxInfo_ field records the hash function that the caller is expected to use when it computes _μ_, and, for the `HashML-DSA` variants, when it pre-hashes the message. It cannot be enforced. It also provides information to the recipients of the CC, since it is in the clear
in the MDH, but recipients need not support the hash function.
This parameter has the same format as the _Algorithm_ and _AlgorithmPolicy_ Fields and the next two Reserved bits.
The value must encode a hash function that cite:[nist-fips-204] admits for that purpose;
any other value causes the CR to transition to Error State _Invalid_.
--

* *Internal State*:
+
--
 ** In the Metadata Header, the field _AlgorithmUse_ is used to keep track of input and output of long fields in an architecturally defined way and to track
  long-running operations in an implementation-specific way.
  The field _AuxInfo_ contains the description of the Hash Function used by the Algorithm.
 ** `HasPrivKey`, `HasPubKey`: Booleans recording whether `privkey`, resp. `pubkey`, holds
    a configured value. They are therefore readable with `ace.getmdl`.
 ** `privkey`: 2560/4032/4896 bytes (20480/32256/39168 bits) for ML-DSA-44/65/87, resp.
 ** `pubkey` : 1312/1952/2592 bytes (10496/15616/20736 bits) for ML-DSA-44/65/87, resp.
 ** `signature`: 2420/3309/4627  bytes (19360/26472/37016 bits) for ML-DSA-44/65/87, resp.
 ** `ctxlen`: 1 byte (8 bits)
 ** `ctx`: 255 bytes (2040 bits)
 ** `mu`: 64 bytes (512 bits), contains the hashed formatted message
 ** `tr` (derived): 64 bytes (512 bits), contains the hash of the public key
 ** `rnd`: 32 bytes (256 bits), contains a random number which is used in hedged signing, or is zero for deterministic signing.

The ML-DSA Algorithm in ACE does not hash the message itself before signing, but only performs the subsequent hash operations.
Therefore it is the responsibility of the caller to compute the public-key hash _tr_ and compute the 64-byte message representative _μ_ using the same hash function.

Besides `rnd`, the internal state may contain several additional variables, for instance intermediate values of the computation of the NTT.
The definition of all these values is implementation dependent, as is their occupancy.
They must be saved in an SCC in the Additional Data Section, allowing resumption of an interrupted operation on the same implementation, as AGR8 prescribes.
--

* *Serialized Context*:
+
--
[%autowidth,cols="^1,<3,<5",options="header"]
|===
|  Pos. | Size (Bits) +
for ML-DSA-44/65/87 | Field
|  ii   | 20480 / 32256 / 39168            | `privkey` (contains `tr`)
|  iii  | 10496 / 15616 / 20736            | `pubkey`
|  iv   | 19360 / 26472 / 37016            | `signature`
|   v   | 8                                | `ctxlen`
|  vi   | 2040                             | `ctx`
|  vii  | 512                              | `mu`
|  viii | 256                              | `rnd`
|===

These contexts are large: for ML-DSA-44, ML-DSA-65 and ML-DSA-87 the Serialized Context is
6672, 9664 and 12496 bytes, that is 417, 604 and 781 blocks of 128 bits, including the MDH and padding.

Apart from `HasPrivKey` and `HasPubKey` (which are stored in _StateExtension_)
the ML-DSA Algorithms do not carry state information as to whether `signature`,
`ctxlen`, `ctx`, `mu` and `tr` have been assigned values.  If those values are not valid,
a malformed `privkey` or `pubkey` is a configuration error and causes the CR to transition to Error
State _Invalid_, while a `signature`, `mu`, `ctx` or `ctxlen` that is well formed but does not
verify is a data error and transitions the state machine to State _Failure_, which is a valid state.

* *States:*
Besides
_Ready_ (1),
_Success_ (22),
_Failure_ (23),
ML-DSA Algorithms define:
 ** _GenerateKeyPair_ (2)
 ** _pubkey_Output_ (3)
 ** _pubkey_Input_ (4)
 ** _ctx_Input_ (5)
 ** _mu_Input_ (6)
 ** _tr_Input_ (7)
 ** _Sign_Generate_ (8)
 ** _Sign_Output_ (9)
 ** _Sign_Verify_ (10)
 ** _Sign_Input_ (11)
 ** _privkey_Input_ (12)
 ** _compute_pubKey_ (13)

* *Allowed State Transitions:*

** State transitions are allowed between any two valid states.

* *Behavior:*

** Upon provisioning, fields `privkey` and `pubkey` are cleared, both flags `HasPrivKey` and `HasPubKey` are false, and the state machine transitions to State _Ready_.

** To transition to any one of the states _Ready_, _GenerateKeyPair_, _privkey_Input_, _pubkey_Input_, _mu_Input_, _tr_Input_, _Sign_Input_, _pubkey_Output_, _compute_pubKey_, _Sign_Verify_, _Sign_Output_, a Form A `ace.setst` instruction must be used.

** Upon transitioning to _Ready_, the fields `signature`, `ctxlen`, `ctx`, `mu`, and `rnd` are cleared.
   Note that the fields `privkey` and `pubkey` are not changed, nor the flags `HasPrivKey` and `HasPubKey`.

** In State _GenerateKeyPair_, Form D ``ace.exec Kn|K{Xn}`` generates a new key pair, replacing `privkey`, `pubkey`, and `tr`, and setting both `HasPrivKey` and `HasPubKey` using procedure `ML-DSA.KeyGen` of cite:[nist-fips-204] (Algorithm 1).

** Upon entering State _privkey_Input_, `HasPrivKey` is set to false, and `pubkey` is
    erased and `HasPubKey` set to false. A private key and a public key held together in a
    CC must be a matching pair, and the incoming private key is in general unrelated to
    the public key that was there before; keeping the latter would leave the CC able to
    verify under one key while signing under another. When the loaded value is complete,
    `HasPrivKey` is set to true.

** Upon entering State _pubkey_Input_, `HasPubKey` is set to false; when the loaded value
    is complete, it is set to true. `privkey` and `HasPrivKey` are not affected: loading a
    public key alone is the normal way to configure a CC for verification only.

** Upon completion of an import (`ace.mgmt` with `#ace_CR_management_end`), if `HasPrivKey` is
    false, the ACE unit recomputes `tr` {leftarrow} `SHAKE256(pubkey, 64)`.
    `tr` is therefore never serialized on its own: in a CC that holds a private key it is embedded
    in `privkey`, and in a verification-only CC it is derivable from `pubkey`. This costs nothing
    architecturally, because `ML-DSA.Verify_internal` does not consume `tr` — the caller uses it to
    form _μ_ — so a verification-only CC is fully functional immediately after import.

** To transition to state _ctx_Input_, a Form B `ace.setst` instruction must be used where the GPR contains the parameter `ctxlen`. Only values of `ctxlen` from 0 to 255 are valid. Passing an invalid `ctxlen` value causes the CR to transition to Error State _Invalid_.

** In States _privkey_Input_, _pubkey_Input_, _ctx_Input_, _mu_Input_, _tr_Input_, and _Sign_Input_,
the fields `privkey`, `pubkey`, `ctx`, `mu`, `tr` and `signature`, respectively, are loaded using
(multi-block) `ace.exec` instructions of Form B, following rule AGR9 of
<<ACE-algorithms-other-rules>>, with the progress recorded in _AlgorithmUse_.

** In State _compute_pubKey_ a single Form D `ace.exec` instruction performs the following operations:

. If `HasPrivKey` is false, the CR transitions to Error State _Invalid_.
. Derive `pubkey` from `privkey`,  as specified in cite:[nist-fips-204] {sect}3.6 and Algorithm 1.
. Check whether the public key correctly hashes to `tr` (embedded in `privkey`), and if not, the CR transitions to Error State _Invalid_.
. Write the result of cite:[nist-fips-204] {sect}3.6 and Algorithm 1. into `pubkey` and set `HasPubKey`.

** To transition to State _Sign_Generate_, a Form B `ace.setst` is
   used, and the auxiliary parameter `Xs` selects the signing mode of cite:[nist-fips-204] {sect}3.4

. If `HasPrivKey` is false, the CR transitions to Error State _Invalid_.
. If `Xs` = 0 (for instance, if `Xs = X0`), then _hedged_ signing is selected.
  A 256 bits random value is drawn from an approved random bit generator and stored in `rnd`.
. If `Xs` is non-zero, then *deterministic* signing is selected. `rnd` is set to `zeros(256)`.

** In State _Sign_Generate_, Form D ``ace.exec Kn|K{Xn}`` generates a digital signature using procedure `ML-DSA.Sign_internal` of cite:[nist-fips-204] (Algorithm 7).
If `HasPrivKey` is true, the output of `ML-DSA.Sign_internal` is written in `signature`, otherwise, the CR transitions to Error State _Invalid_.

** In State _Sign_Verify_, Form D ``ace.exec Kn|K{Xn}`` verifies a digital signature using procedure `ML-DSA.Verify_internal` of cite:[nist-fips-204] (Algorithm 8):

. If `HasPubKey` is false, the CR transitions to Error State _Invalid_.
. If `ML-DSA.Verify_internal` returns `true`, the state machine transitions to State _Success_;
otherwise it transitions to State _Failure_. cite:[nist-fips-204] Algorithm 8 returns a Boolean
only, so nothing is written to `signature` on this path.

** In States _pubkey_Output_ and _Sign_Output_, the fields `pubkey` and `signature` are emitted
using (multi-block) `ace.exec` instructions of Form C, following rule AGR9, with the progress
recorded in _AlgorithmUse_.
Entering _pubkey_Output_ while `HasPubKey` is false causes the CR to transition to Error State _Invalid_.

** _AlgorithmPolicy_ can be modified using `ace.restrictl`.
The value 0 is not admissible.
An attempt to clear the field using `ace.restrictl` causes the CR to transition to Error State _Invalid_.
