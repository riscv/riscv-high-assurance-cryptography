[[ACE-lazy-loading]]
==== Use of ``*lcrstatus`` for Lazy Context Switching and CR Loading (new)

_This section is non-normative._

Since importing and exporting the CR state is expected to be slow, software might want to resort to optimization techniques that minimize the amount of imports and exports.
EE manager may do that by keeping keys from other contexts in the ACE unit or
by postponing import until the key is actually used in the EE.

The design of ACE accelerates that by providing two mechanisms:
1. Trap any access to a selected CR by setting `*lcrstatus` field to Off.
2. Trap import failures because of insufficient ACE CR file space.

There are two additional possible designs that we intentionally did not implement:
1. Constrain the size of software context's imports -- this would allow partitioning and virtualization of the CR file size.  (Implementation: add a signed CR size counter and an unsigned size limit along with `*lcrstatus` -- every operation that changes the occupation in CR file modifies the counter and traps with `ace_exc_CR_sizelimit` instead if the operation would have increased occupancy above the limits in parent privilege mode.)
2. Allow import while trapping export or use -- this would allow EE manager to avoid a trap in scenarios where the old CR contents are either not loaded or belong to a different context and have already been saved and the EE wants to import a different key in that CR -- the ACE unit would allow trap-less import.  (Implementation: add a new state to `*lcrstatus` with this behavior.)

A few examples follow, to give a better idea on how software stack can manage the state.

.Nested example with accelerated trap delegation for slcrstatus Off
[plantuml, ,svg]
....
@startuml
skinparam backgroundColor transparent
skinparam defaultFontColor black
skinparam sequenceArrowColor black
skinparam sequenceLifeLineBorderColor black
skinparam sequenceParticipantBorderColor black
skinparam sequenceGroupBorderColor black
skinparam noteBorderColor black
skinparam noteBackgroundColor white

autonumber

participant "M-mode" as M
participant "HS-mode" as HS
participant "VS-mode" as VS
participant "VU-mode" as VU

note across : "`mlcrstatus.CR0` is Off,  slcrstatus.CR0 is Clean, `vslcrstatus.CR0` is Off"

VU -> M : `ace_exc_CR_off` trap because VU-mode accesses CR0

note over M : manipulates `CR0` and sets `mlcrstatus.CR0` to Clean

M -> VU : mret

VU -> VS : `ace_exc_CR_off` trap because U-mode accesses CR0

note over VS : manipulates `CR0` and sets `vslcrstatus.CR0` to Clean
note over M, HS : VS manipulation changed `mlcrstatus.CR0` and slcrstatus.CR0 to Dirty

VS -> VU : sret

note over VU : U-mode successfully accesses CR0
@enduml
....

NOTE: The accelerated trap delegation closely depends on how traps are structured, since we will not get a separate cause for each trap (they will likely be sub-causes of an ACE unit cause).
The delegation can only be done with the `medeleg` and `hedeleg` CSRs, which have fairly coarse granularity.
