We consider separately MDH,SIV1, SIV1,IMPQUAL
and Content1 + Content2 are just m+n consecutive blocks

the new, reorganized format is

MDH
SIV1
if MDH._AuxDataLen_ > 1, then we know we have an Auxiliary Data Section and so
      IMPQUAL
      SIV2
Content1
Content2

(Note, _AuxDataLen_ = 1 is a flag that means that there was some ADS, but we discarded it either because longer than the max on the current implementation for that algorithm, or IMPQUAL mismatch. However we cannot pass a zero to the ace.mgmt, because  we need to signal the algorithm that at the first instruction it needs to know that it must restart the operation or do something else to replace the ADS)

which means that in an IMPORT of a fully configured and completely exported SCC we read the MDH and compute immediately an offset for Content1 || Content2.
If MDH._AuxDataLen_ <  2, then: there is only Content1 at base + 32 (base = address of the MDH), we read it
If MDH._AuxDataLen_ ≥  2, then: there is also Content2, and Content1||Content2 starts at base+64

then we start reading. SIV1, goes into the CSR. 
If we are in the second case, we next read IMPQUAL, goes into a CSR, read SIV2, goes into a CSR.
Now we have the loop that loads either m, or m+n blocks. This is ace.load or a series of ace.mv.

The HW would be simplified. The SW gets marginally more complicated, but it is ok.

We can have ace.load and ace.store do everything, i.e. look at the MDH, decide whether it must set one or three internal registers, and then load everything progressively. Same for ace.mv. But everything would be still simpler.

And also simpler to write in the specification.

Now, when we are exporting incomplete stuff, we can still do exactly the same, but we skip the encryption.
When we are reimporting an export of something exported that was incomplete before, we skip the decryption.
And, since these cases are relatively rare, the SIV1/IMPQUAL/SIV2/ can be exported and reimported again which helps in these rare cases, but overall does not cost much. Because if we do this AND also save them (through CSRs) at context switch (we have a register that has values 0–31 if a CR is being reconfigured and 32 if none is) we can easily interrupt and resume whatever we want. So we even increase flexibility a bit.

So, a lot of words for describing a format change. Apparently just a reshuffle of fields, but very​ important,

Rethink the semantics of ace.size.
ace.size just does a lookup and finds the size of Content1.
Then we get the size of Content2, _AuxDataLen_, directly from the MDH.

if _ConfigStatus_ = `ace_cfgst_complete`, then:
   size_SCC_content1(MDH) = Length of MDH || SIV1 || Content1[]
   ace.size(MDH) = size_SCC_content1(MDH) + (0 if _AuxDataLen_ {le} 2 else 16 * _AuxDataLen_) // SIV2 || IMPQUAL || Content2[]
else if _ConfigStatus_ = `ace_cfgst_provisioning`, then:
   size_SCC_content1(MDH) = Length of MDH || PI_Content[]
   ace.size(MDH) = size_SCC_content1(MDH)
else if _ConfigStatus_ = `ace_cfgst_importing` or `ace_cfgst_exporting` then:
   size_SCC_content1(MDH) = Length of MDH || Content1[]
   ace.size(MDH) = size_SCC_content1(MDH) + (0 if _AuxDataLen_ {le} 2 else 16 * _AuxDataLen_-32) // Content2[]

ace.size has an entire five bit field (s2) set to zero.
hence we can use it to extract the sizes of the various parts without having to do shifts and masking

if the ARC does no like it, we can have pseudo instructions
ace.size.tot = returns the total length, i.e., the memory to allocate
ace.size.c1  = returns the length of the PI or of the Content1[] // This comes from internal data
ace.size.c2  = returns the length of Content2[]                  // This comes from _AuxDataLen_
ace.size.pre = returns 0 for a PI, 1 if there is only Content1[] (i.e. only SIV1), or if we have also Content2[] (i.e.,SIV, SIV2 and IMPQUAL)

therefore ace.size.tot = 1 + ace.size.pre + ace.size.c1 + ace.size.c2
