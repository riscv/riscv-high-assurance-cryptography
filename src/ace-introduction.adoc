== Introduction

This brief introduction to the _Atomic Cryptography Extension_ (ACE) is not
part of the specification.

The ratification plan can be found
https://riscv.atlassian.net/wiki/spaces/HACX/pages/484966423/High+Assurance+Crypto+Ratification+Plan[here].

=== Features

ACE defines an interface to high-performance cryptographic operations without giving software access to the keys.
(((design, high performance)))
Its development has been prompted by use cases such as content protection (including local LLM decryption), link and storage encryption, secure boot, and attestation.

ACE's main features are:

* To mitigate key misuse, ACE binds cryptographic secrets (such as keys) and metadata into an indivisible structure called a _Cryptographic Context_ (CC). The architecture uses the metadata to restrict each secret to a specific algorithm and, optionally, to enforce usage constraints based on the process, VM, security state, boot cycle, expiration date, or other policies.

* To implement CCs, ACE introduces _Cryptographic Registers_ (CRs)—architectural containers that conceal their secrets from software. A CC is created by _provisioning_ (i.e., writing) secrets and metadata into a CR. ACE instructions operate on CRs instead of explicit key values. As a result, software can use keys without holding them explicitly in the process's memory, and also benefit from higher performance and side-channel-protected implementations when available.

* Cryptographic operations are performed _atomically_ to avoid leaking data through architectural side-channels.
  Instructions can be interrupted only between cryptographic operations, or at the points that the algorithms they execute define for their long-running operations.

* ACE provides a unified interface to multiple cryptographic primitives, avoiding the need for separate instructions per primitive.
 ** Exposing only the primitives is insufficient for modes like AES-GCM-SIV, XTS, and OCB, because leakage of derived keys or intermediate values can compromise security. Therefore, ACE also defines modes of operation and secure key derivation.
 ** In addition to GCM-SIV, XTS, and OCB, ACE defines modes such as CTR, GCM, and CMAC. Where applicable, encrypt-only or decrypt-only versions and versions with a preset IV or nonce are also defined to reduce the potential for misuse. These modes can be instantiated not only with AES-128/256 but also with other block ciphers such as SM4.
 ** The interface supports various hash functions.
 ** The interface supports SCA-resistant implementations of the algorithms.
 ** The interface provides access to public-key and post-quantum algorithms.
 ** Not all algorithms defined in this specification are required in every ACE implementation; following RISC-V practice, ACE defines several sub-extensions and delegates profile requirements to the RISC-V profile process.

* ACE provides a secure mechanism to store a CC to memory via authenticated
  encryption, producing a _Sealed Cryptographic Context_ (SCC). Once generated,
  an SCC can later be re-imported into a CR. If an SCC is passed to a process
  in place of the key value, the key is not exposed in that process' memory.


* ACE scales from embedded to server cores with a unified ISA and ABI.
* ACE is compatible with sleep, hibernation, and VM migration.
(((design, scalable)))
(((VM migration)))

//

Rationale for atomic operations:::
Assuming the primitive is secure, the key cannot be recovered from the input and output of the full cryptographic operation. Typical round-based ISAs require keys to be supplied between rounds or MAC stages. This allows easy key recovery from the input and output, even if the key came from a hidden register. In fact, even if an instruction computed only 4 or 5 rounds of AES, an attacker with access to the instruction oracle could efficiently recover the key cite:[Rijndael-revised].

[[ACE-introduction-non-features]]
=== Non-Goals

ACE intentionally excludes the following:

* **Variable-length complete ciphertext and plaintext inputs:** Plaintexts, ciphertexts, and hash inputs are processed in fixed-size blocks.

* **Full key management:** ACE provides only architectural building blocks for key management; the key-management logic resides in trusted software (e.g., TEE applets). ACE does not support external schemes for directly provisioning keys into a key store. Instead, a local trusted SW or HW component obtains keys and policies from external components and configures CCs for the ACE unit.

* **Key revocation:**
This specification does not define a key revocation mechanism. The rationale is:

. A revocation mechanism would impose significant implementation and performance costs, contrary to ACE’s goals of simplicity and speed.
. A universal revocation mechanism would be impractical to implement because of the numerous protocols, and revocation data may be unbounded. Implementing it in the ACE unit would require dynamic access to secure memory. Isolated software components integrated with the local software stack can provide this functionality while maintaining strong security guarantees.
. Revocation generally applies to root keys, not derived keys such as session keys. The trusted entity that manages the root keys can therefore manage revocation. The expiration-date mechanism and _Localities_ can limit the lifetime and scope of derived keys.
. Applications that require direct software access to root keys, such as link or storage encryption, typically run in protected environments that can implement their own revocation mechanisms.

* **Full prevention of misuse by compromised processes:** ACE cannot fully prevent misuse by compromised processes, as they retain access to their own CCs. ACE complements but does not replace existing software vulnerability mitigations and process isolation. Additionally, some modes, such as counter mode encryption, use the same operation for both encryption and decryption, which can be abused by malicious software; this risk is inherent and cannot be mitigated.

[[ACE-threat-model]]
=== Threat Model

_This section is informative and non-normative._

The ACE threat model is straightforward.

**Assets** are _keys_ and any information that may help an adversary recover plaintext or forge ciphertexts or MACs.
Examples include masks in tweakable XEX modes and derived keys in AES-GCM-SIV. The critical properties of these assets are _confidentiality_ and _integrity_.
Asset _availability_ is not an architectural goal.

**Adversaries** are assumed capable of compromising processes by exploiting software vulnerabilities. They may also access memory contents by, for example, abusing hardware interfaces or interposing between the SoC and memory. The model excludes adversaries capable of sophisticated hardware attacks, such as tampering using a focused ion beam or scanning electron microscope (FIB/SEM). Side-channel attack (SCA) protection is optional. ACE provides interfaces to both SCA-unprotected and SCA-protected implementations of cryptographic algorithms, where these options are implemented.

Threats can be addressed in four ways:

[horizontal]
**C:**:: _Control_ the threat by implementing full or partial mitigations.
**A:**:: _Accept_ the threat and its associated risks.
**T:**:: _Transfer_ the threat to another party better suited to address it.
**S:**:: _Suppress_ the features that give rise to the threat.

ACE is designed to avoid the “*A*” and “*S*” options as much as possible. It _controls_ threats through its own mechanisms and _transfers_ residual risk—specifically, the risk of key extraction—to the privileged or trusted software and hardware environments that manage keys. For example, trusted software can employ control-flow integrity, memory encryption with integrity protection, and anti-replay mechanisms, while hardware key-management blocks can be hardened to protect entrusted keys.

Direct plaintext leakage, memory-corruption attacks against the ACE-using process, and Release of Unverified Plaintext (RUP) attacks are out of scope. ACE cannot mitigate these threats because the processed information resides within the user's execution context; they are therefore _accepted_.

=== Open Points

_This section is informative and non-normative._

The items below are *not* known defects in this specification or a measure of its maturity.
They fall into two groups. This distinction matters when assessing the document.

Group A — items requiring closure by the RISC-V Architecture Review Committee (ARC).:::

. *Opcode allocation.* The instruction encodings use `custom-1` and `custom-2`
  as placeholders. ACE needs two opcodes, but the 32-bit instruction opcode space
  is essentially exhausted. Although broadly useful, ACE would be used only in specific
  parts of code and libraries. A mechanism such as Composable Extensions would therefore
  be beneficial. ACE would remain a *non-custom extension*, with ratification as its goal.

. *`misa.L` and `mstatus[26:25]` (ACES) placement.* These placements are provisional,
  contested, and only resolvable by the the ARC.
  `misa.L` may be replaced by another mechanism, such as
  Unified Discovery, and the `*status` CSRs may be replaced by other CSRs.

. *ACE CSR addresses.* All addresses are `0xXXX` or “(Indirect)” placeholders,
  to be assigned by the ARC, as is the `Smstateen` bit of <<ACE-CSRs-priv>>.

. *Exception cause codes.* `mcause` values must be allocated by the ARC, using either
  individual cause values or a single ACE cause with a subcause register.
  We also need some form of “`mvalue`” to report the CR number directly.
  This would simplify handlers by removing the need to decode direct and indirect CR references.

. *ACEV scope.* <<ACE-ACEV>> defines the vector subset required by ACE, which we consider complete.
  The following questions remain. We do not consider them barriers to candidacy, but they must
  be resolved, and we request ARC feedback.

  .. Should ACEV vector instructions be gated by `*status.VS` or another mechanism?
  .. How should ACEV be discovered?
  .. How should element widths be defined for operations performed by `ace.exec`?
     For primitives with input/output sizes that are not powers of two, `EGW`/`SEW` cannot
     represent those sizes. One option is to allow any value that divides the size,
     defining `EGW`/`SEW` and the corresponding `vstart` increment per iteration.
     See link:https://github.com/riscv/riscv-high-assurance-cryptography/issues/96[].

. *RVWMO axiomatic integration.* <<ACE-Memory-Model>> informally specifies the memory-ordering
  behavior of ACE's component memory operations in terms of prefix-completeness, and
  a conflicting-access rule is given in <<ACE-resumability>>.
  Integrating ACE into RVWMO's axiomatic formalism
  remains work to be done with the ARC during ratification.

. *Naming.* This document uses “`ace.`”; the ratified names will use “`kl`”, as proposed in
  <<ACE-new-names>>, subject to RVI's confirmation of the sub-domain; the same holds for the
  `Sm`/`Ss` split of the privileged extensions (<<ACE-priv-extensions>>).

. *Discoverability of cipher/mode combinations.* Subextensions may be impractical for this purpose,
  as argued in the introduction to <<ACE-Algorithms>>. Discovery may also use `ace.avail`.
  We are open to migrating to Unified Discovery once it is finalized.

. *Debug-mode interaction.* This is specified in <<ACE-interaction-with-debug>>.
  We consider it resolved but welcome a second opinion from the Debug task group or the ARC, or both.

Group B — open design questions owned by this task group.:::

. *Effective data endianness.* Clarify UBE and its interaction with MPRV/MPP in the definition
  of _effective data endianness of the current privilege mode_ in <<ACE-Notation>>.

. *Cross-hart CSR access.* For <<ACE-CSK-requirements>> and <<ACE-CSR-macecsk>>, is there,
  or should there be, an architected mechanism for M-mode on one hart to read or configure
  another hart's CSRs? If such a mechanism exists or is planned, <<ACE-CSK-requirements>>
  could use it instead of platform-specific channels.

. *`ace.mgmt` interruptibility.* `ace.mgmt` is currently uninterruptible. Making it preemptible
and resumable may introduce an attack vector that we have not fully studied, so no decision
has been made so far. +
The instruction can be relatively long-running, though not on the scale of ECC scalar
multiplication or signature verification. If this asymmetry is considered inelegant,
an alternative is to allow a preempted import or export to resume only immediately,
without an intervening context switch. In this model, management _instructions_ cannot nest. +
We ask the ARC to assess whether the current behavior is suitable for the RISC-V architecture.


. *Nonces for SCC export and import.* Adding a nonce following RFC 8452 requires six AES-256
  encryptions per export or import operation. The current design recomputes derived keys only
  when the CSK changes. A competing architecture also omits nonces from key export and import,
  likely for the same reason. We welcome input on this design choice.
// One alternative is to encrypt `nonce @ constant1` and `nonce @ constant2` under the _derived encryption key_, producing `A` and `B`. The algorithms could then use `enc_key xor (B @ A)` and `auth_key xor B xor A` instead of `enc_key` and `auth_key`. This construction is non-standard, but it is secure and faster: it requires only two additional AES-256 encryptions.

. *Additional inputs for random key generation.* It would be straightforward to define KDFs
  that accepts arbitrary inputs and produce unlimited outputs as an Algorithm.
  With `ace.derive`, they could be used to feed a CR's key field.
  Do we want to define some standard KDFs?

. *`ace.mv` piecewise transfers.* Is the idiom in <<ACE-management-code-snippets>> consistent
  with the illegal-instruction-on-completion rule and the content-only transfer model?

. *Zkr requirements.* Verify Zkr's exact scope and DRBG requirements.

. *`SCC_Encrypt` security claim.* Add support for the claim “secure for up to
  2^64 128-bit blocks.”

. *Form B of `ace.size` and future MDH formats.* Form B receives only MDH bits [63:0] and
  treats the remaining bits as zero, thus assuming the current MDH format. The rules in
  <<ACE-length-rule>> require all length-determining fields, including those for custom Algorithms,
  to reside in the lower half, but little space remains there. If a future MDH _Version_ or
  system-specific format (<<ACE-Algorithm-version>>) requires a length-determining field in the
  upper half, Form B may have to be dropped.

. Add handling of a “last block” to Rule <<ACE-AGR-load-long-field>>, if needed. (Is it needed?)

. *CRF capacity.* No minimum CRF capacity is required and no residual capacity is discoverable.
  The capacity a CR consumes depends on the internal representation of the implementation
  (size of the ADS, number of shares of a masked implementation), so exact requirements are
  not possible; the task group may want to discuss approximate mechanisms.

. Compare and streamline Rules <<ACE-IRR-long-running-no-data>>, <<ACE-AGR-progress-discard>>, <<ACE-GR-atomic-randomness>>,
and <<ACE-GR-opening-cr-when>>
and make sure we know how to implement the clause “No State from which the CR can be
exported or cloned holds random material that could be consumed against an
input other than the one it was drawn for.” For instance, the implementation may have to
include some information in the ADS such as the _State_ it is for, the address of the instruction
or other information such as quick hashes of the inputs, in order to hinder any attempt
to bring the Algorithm off course. The security principle is: if the implementor wants
to implement an optimization using a path that we consider optional, they are allowed to,
but they are also responsible for the security.
