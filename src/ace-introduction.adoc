== Introduction

This brief introduction to the
_Cryptographic Locker Extensions_ (KLEE) – formerly known as the _Atomic Cryptography Extension_ (ACE) – is not
part of the specification.

=== Features

KLEE defines an interface to high-performance cryptographic operations without giving software access to the keys.
(((design, high performance)))
Its development has been prompted by use cases such as content protection (including local LLM decryption), link and storage encryption, secure boot, and attestation.

KLEE's main features are:

* To mitigate key misuse, KLEE binds cryptographic secrets (such as keys) and metadata into an indivisible structure called a _Cryptographic Context_ (CC). The architecture uses the metadata to restrict each secret to a specific algorithm and, optionally, to enforce usage constraints based on the process, VM, security state, boot cycle, an expiration date, or other policies.

* To implement CCs, KLEE introduces _Cryptographic Lockers_ (CLs)—architectural containers that conceal their secrets from software. A CC is created by _provisioning_ (i.e., writing) secrets and metadata into a CL. KLEE instructions operate on CLs instead of explicit key values. As a result, software can use keys without holding them explicitly in the process's memory, and also benefit from higher performance and side-channel-protected implementations when available.

* Operations such as full AES block encryption/decryption or absorption of data blocks into a hash function are performed _atomically_—i.e., in a single step

* To enable CC reuse and support OS features like context switching, KLEE provides a secure mechanism to store a CC to memory via authenticated encryption, producing a _Sealed Cryptographic Context_ (SCC). Once generated, an SCC can later be re-imported into a CL. If an SCC is passed to a process in place of the key value, the key is not exposed in that process's memory.

* KLEE provides a unified interface to multiple cryptographic primitives, avoiding the need for separate instructions per primitive.
 ** Exposing only the primitives is insufficient for modes like AES-GCM-SIV, XTS, and OCB, because leakage of derived keys or intermediate values can compromise security. Therefore, KLEE also defines modes of operation and secure key derivation.
 ** In addition to GCM-SIV, XTS, and OCB, KLEE defines modes such as CTR, GCM, and CMAC. Where applicable, encrypt-only or decrypt-only versions and versions with a preset IV or nonce are also defined to reduce the potential for misuse. These modes can be instantiated not only with AES-128/256 but also with other block ciphers such as SM4.
 ** Support for various hash functions.
 ** Support for SCA-resistant implementations of the algorithms.
 ** The interface can also be used to provide access to public-key and post-quantum algorithms.
 ** Not all the algorithms defined in the specification are intended to be supported by an KLEE implementation: following RISC-V practice, KLEE defines several sub-extensions and delegates the choice to RV profiles, which are defined by a separate process.

* KLEE scales from embedded to server cores with a unified ISA and ABI.
* KLEE is compatible with sleep, hibernation, and VM migration.

Rationale for atomic operations:::
Assuming the primitive is secure, the key cannot be recovered from the input and output of the full cryptographic operation. Typical round-based ISAs require keys to be supplied between rounds or MAC stages. This allows easy key recovery from the input and output, even if the key came from a hidden register. In fact, even if an instruction computed only 4 or 5 rounds of AES, an attacker with access to the instruction oracle could efficiently recover the key cite:[Rijndael-revised].

=== Non-Goals

KLEE intentionally excludes the following features:

* **Debugging support:** The internal representation of a CL remains concealed even during unauthenticated debug.

* **Variable-length complete ciphertext and plaintext inputs:** Plaintext and ciphertexts, as well as messages of which digests are computed, are processed in fixed-size blocks.
* **Full key management:** KLEE provides only architectural building blocks that can be used for key management, whose logic resides in trusted software (e.g., TEE applets). KLEE does not support external schemes for directly provisioning keys into a key store. Instead, a local trusted SW or HW component manages the external schemes and uses the resulting keys and policies to configure CCs for the KLEE unit.

* **Key revocation:**
This specification does not define a key revocation mechanism. The rationale is:

. A revocation mechanism would add a significant implementation burden and adversely affect performance, conflicting with KLEE's emphasis on simplicity and speed.
. A universal revocation mechanism is impractical because of the variety of protocols, and potentially unbounded revocation data. Managing revocation within the KLEE unit would require dynamic access to secure memory. Such functionality is better suited to isolated software components that integrate with the local software stack while maintaining strong security guarantees.
. Revocation typically applies to root keys, not the derived keys (e.g., session keys) used by user software. It can therefore be handled by the trusted entity managing the root keys. The expiration-date mechanism and _Localities_ can be used to limit the lifetime and scope of derived keys.
. Applications requiring direct software access to root keys (e.g., link or storage encryption) typically execute in protected environments that can handle their own revocation mechanisms.

* **Full prevention of misuse by compromised processes:** KLEE cannot fully prevent misuse by compromised processes because they retain access to their own CCs. KLEE complements, but does not replace, existing software vulnerability mitigations and process isolation techniques. Additionally, certain modes (e.g., counter mode encryption) use the same operation for both encryption and decryption, which may enable misuse by malicious software. This risk is inherent to such modes, and cannot be mitigated.

[[KLEE-threat-model]]
=== Threat Model

The KLEE threat model is straightforward.

**Assets** are _keys_ and any information that could aid an adversary in recovering plaintext or forging ciphertext. This includes, e.g., masks in tweakable XEX modes and derived keys in AES-GCM-SIV. The critical properties of these assets are their _confidentiality_ and _integrity_.
Protecting the _Availability_ of the keys is not an architectural goal.

**Adversaries** are assumed capable of compromising processes by exploiting software vulnerabilities.
They are also able to gain access to memory contents, for instance, by abusing hardware interfaces or by SoC/memory interposition.
The model does not include adversaries capable of sophisticated hardware attacks, such as using
a Focused Ion Beam/Scanning Electron Microscope (FIB/SEM) to tamper with the hardware's functionality.
Side-channel attacks are addressed optionally. KLEE offers interfaces to both SCA-unprotected and SCA-protected implementations of cryptographic algorithms, if these options are provided by the designer.

KLEE is designed to avoid accepting risks or suppressing useful features as much as possible. It _controls_ threats through its own mechanisms and _transfers_ residual risk—specifically, the risk of key extraction—to the privileged or trusted software and hardware environments that manage keys. For example, trusted software can employ control-flow integrity, memory encryption with integrity protection, and anti-replay mechanisms, while hardware key-management blocks can be hardened to protect entrusted keys.

Direct plaintext leakage, memory corruption attacks against the KLEE-using process, and Release of Unverified Plaintext (RUP) attacks on the cryptographic algorithms are out of scope. These threats cannot be mitigated by KLEE because the processed information resides within the user execution context. Thus, these threats are _accepted_.

=== Discussion Points

These items are *not* known defects and do not indicate a lack of maturity of the specification's maturity.

Group A — items requiring resolution by the RISC-V Architecture Review Committee (ARC).:::

. *Opcode allocation.* The encodings are provisional.
  The _core instructions_ currently use the MISC-MEM opcode because it has two unused `funct3`
  values. Similar encodings gaps could be used instead.
  The _memory instructions_ are more difficult to encode because their offsets consume all
  remaining bits after `opcode` and `funct3` are allocated. LOAD-FP and STORE-FP have four and five
  unused `funct3` values, respectively. Because the scalar ISA is unlikely to support many more
  floating-point formats, KLEE provisionally uses `funct3` values 5, 6, and 7.
  Another option for `kl.size`, `kl.avail`, `kl.getmd*`, `kl.setmd*`, `kl.restrict*`, and `kl.clone`
  is to move encoding bits [29:25] to [24:20] and fix bits [29:25] to zero, thereby freeing
  significant space in `funct7`.

. *`misa.L` and `mstatus[26:25]` (KLS).* These choices are provisional, contested, and can be
  resolved only by the ARC. `misa.L` may be replaced by another mechanism, such as Unified
  Discovery, and the `*status` fields may be replaced by other CSRs. The selected bits,
  `mstatus[26:25]`, and the corresponding bits in `sstatus` and `vsstatus` may also change.
  KLS may use a different offset, or an other register than the `*status` context-status field.
  This specification only requires only a two-bit context-status field with the semantics defined
  in <<KLEE-aces-encoding>>, analogous to `FS` and `VS`.

. *KLEE CSR addresses.* All `0xXXX` addresses and “(Indirect)” designations are placeholders to be
  assigned by the ARC, as is the `Smstateen` bit in <<KLEE-CSRs-priv>>.
  CSRs marked as indirect are intended to use the Indirect CSR Access mechanism defined by
  `Smcsrind`/`Sscsrind`. ARC allocates `*iselect` values or direct CSR addresses.

. *Exception cause codes.* We need `mcause` values, either as separate causes or as a
  single KLEE cause with a subcause. An “`mvalue`” mechanism to reports the CL
  number is desirable.

. *KLV scope.* <<KLEE-KLV>> defines the RVV subset required by KLEE.
  Non-blocking questions:
  Should KLV vector instructions be gated by `*status.VS` or another mechanism?
  How should KLV be discovered?

. *RVWMO axiomatic integration.* <<KLEE-Memory-Model>> informally specifies the ordering of KLEE's
  component memory operations through prefix-completeness, while <<KLEE-resumability>> defines a
  conflicting-access rule. KLEE must be integrated into RVWMO's axiomatic formalism with the ARC
  during ratification.

. *Discoverability of cipher/mode combinations.* As discussed in the introduction to
  <<KLEE-Machines>>, subextensions may be impractical.
  We still define them, but `kl.avail` seems better to us, since it talks to the actual
  implementation, which can be a separate IP block from the hart.
  Unified Discovery is also an option.

Group B — open design questions owned by this task group.:::

. *Effective data endianness.* Clarify UBE and its interaction with MPRV/MPP in the definition of
  the _effective data endianness of the current privilege mode_ (<<KLEE-Notation>>).

. *Guest- and host-settable CSKs.* Determine whether guests and hosts should be able to set CSKs
  without always switching to M-mode.

. *Delegating KLEE unit trap-and-emulate to HS.* Determine whether trap-and-emulate should be
  delegated to HS rather than always switching to M-mode.

. *Side-channel protection for Machines and the sealing path.* Define protection levels and their
  formalization, and identify the relevant reference documents. Use security model.

. *`kl.mgmt` interruptibility.* `kl.mgmt` can be relatively long-running, although not as long as
  ECC scalar multiplication or signature verification. It is currently uninterruptible because
  preemption and resumption may introduce new attack vectors. Interrupting internal encryption or
  decryption also complicates export: a CL may contain both encrypted and unencrypted content, and
  the unencrypted content cannot be exported. So the unencrypted content would have to be encrypted
  anyway before any access ot it to write it out.
  Precise interruption appears secure only if the KLEE unit operates on an internal copy.
  Since such a `kl.mgmt` does not perform any memory or register access, we recommend background
  completion until a handler needs to access the CL.

. *Nonces for SCC export and import.* Using a nonce as specified in RFC 8452 requires six AES-256
  encryptions per export or import, whereas the current design recomputes derived keys only when
  the CSK changes. A competing architecture also omits nonces from key export and import, likely
  for the same reason. Input on this choice is welcome.
