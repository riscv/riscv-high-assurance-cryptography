[[KLEE-instruction-exec]]
=== kl.exec/kl.mv

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x0F, attr: ['MISC-MEM'] },
    { bits:  5, name: 'rd', attr: ['Vd','—','Vd','—'] },
    { bits:  3, name: 0x4, attr: ['kl.exec'] },
    { bits:  5, name: "'rs1' (n)", attr: ['Kn|K{Xn}'] },
    { bits:  5, name: 'rs2', attr: ['Vs2','Vs2','—','—'] },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'r' },
    { bits:  1, name: 0x0 },
    { bits:  2, name: 'Form', attr: ['0    0','0    1','1    0','1    1'] },
    { bits:  2, name: 0x0, attr: ['funct2'] },
]}
....

`kl.mv  uses `Form` = `0b01`/`0b10` with `rd`/`rs2` = `0b00001` or `0b00010`.

[[KLEE-options]]
== Options

MISC-MEM, with Opcode Value: `0001111`, with two currently reserved `funct3` values: `100` and `101`.
This can cover the base instructions.
Instruction Format: Typically I-type, but not strictly (?).

OP (Integer Register-Register Operations), with Opcode Value: `0110011`.
Every single funct3 slot from 000 to 111 is structurally assigned to a base instruction (like ADD, SLL, XOR, etc.). However, R-type instructions rely on the `funct7` field to differentiate operations. Standard RISC-V extensions only occupy a tiny fraction of `funct7` space (e.g., `0000000` for base, `0100000` for SUB/SRA, and `0000001` for the M-extension multiplication/division). This leaves dozens of funct7 patterns wide open across all 8 funct3 paths for your hardware. Would this work by moving a lot of the info currently in `funct7` to the zeros in `rs2`?

AMO (Atomic Memory Operations), with Opcode Value: `0101111`.
Free `funct3` Count: 6 free values.
(`010` is reserved for 32-bit atomics, and `011` is reserved for 64-bit atomics.)
RISC-V leaves these entirely unmapped for alternative data-width atomic configurations.
Can two be sacrificed?

For the KLEE memory instructions, we could share the STORE-FP (Floating-Point Stores, opcode `0100111`) and LOAD-FP (Floating-Point Loads, opcode `0000111`)
which have respectively 5 and 4 free `funct3` values. We would probably need 3 from the STORE-FP (for kl.store, kl.input and kl.output) and 1 from the LOAD-FP (for kl.load).
