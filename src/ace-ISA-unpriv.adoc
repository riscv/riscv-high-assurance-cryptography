[[ACE-unpriv-intro]]
=== Introduction

We introduce here the fundamental concepts around which ACE is designed.

[[ACE-concepts]]
==== Fundamental Concepts and Definitions

Cryptographic Context:::
(((Cryptographic Context)))
The *Cryptographic Context* (CC) is the foundation of ACE.
All cryptographic operations performed by ACE execute within the constraints defined by a CC.
A CC contains secrets, usually keys, but it is more than just a key container:
it is an indivisible structure consisting of a *Metadata Header* (MDH) and *Content*.
The MDH has a fixed format and specifies the algorithm that can be used with the secrets, and various optional policies associated with the CC.
(((Cryptographic Context, Metadata Header)))
The Content has an Algorithm-specific format and holds the secrets and other sensitive material, as well as a representation of the Algorithm's state.
(((Cryptographic Context, Content)))
The Metadata requires integrity; the Content requires both integrity and confidentiality.
These requirements are architecturally enforced by ACE and by the algorithms it implements.

Cryptographic Register:::
(((Cryptographic Register)))
To create CCs, ACE uses *Cryptographic Registers* (CRs), per-hart architectural containers that safeguard their contents.
A CR is *provisioned* by writing Metadata and Content into it; this operation binds the latter to form a CC.
There is no store-like instruction to extract the Content of the CR in a manner that compromises its confidentiality.
A CC may be used for cryptographic operations only while resident in a CR.
Only the ACE unit may access or modify a CC residing in a CR, in accordance with the rules set by the architecture and by the Algorithm bound to the CC.

Sealed Cryptographic Context:::
(((Cryptographic Context, sealed)))
To support context switching while protecting CCs outside architectural state, a CC may be *exported* from a CR as a *Sealed Cryptographic Context* (SCC)—an encrypted and authenticated representation of a CC that can later be *imported* into a CR. Export and import use a _Context Sealing Key_ (CSK), which may be programmable by M-mode. An SCC sealed under one CSK cannot be imported under a different CSK, providing cryptographic domain separation across spatial and temporal domains.

Algorithm:::
(((Algorithms)))
(((Cryptographic Context, object-oriented)))
An *Algorithm* (written with an upper-case "A")
is a state machine that performs cryptographic operations through the interface defined in this specification.
In the metadata of a CR, it is encoded as 16 bits of information.
ACE provides a small set of instructions for interacting with these state machines.
These instructions take the 16-bit identifier from the CR's metadata, along with standard RISC-V inputs and outputs such as GPRs, vector registers, and memory. Their semantics depend on the selected Algorithm. Consequently, a CC in a CR encapsulates Algorithm-specific behavior, allowing different primitives (e.g., AES-128, AES-256, and SM4) to be used interchangeably in the same modes (e.g., ECB, GCM-SIV, and XTS) without changes to the compiled code. Side-channel-attack-resistant variants are supported transparently.

Usage Control Policy:::
(((Cryptographic Context, usage control)))
(((Cryptographic Context, management operations)))
(((Cryptographic Context, usage operations)))
ACE distinguishes between CC/CR *management* and *usage* operations.
(((Cryptographic Context, export)))
Management operations include *configuration* (e.g., CR provisioning, SCC import, and cloning), *export* of a CR as an SCC, and *clearing* a CR.
Usage operations include cryptographic operations and state changes.
To prevent denial-of-service scenarios, management operations, in particular configuration operations, are less restricted than usage operations. _Usage Control_ policies restrict only certain CC/CR usage operations.

Localities:::
(((Cryptographic Context, Locality)))
ACE can bind CCs to *Localities*, i.e., restrict usage to specific devices or device classes, hardware configurations, physical or virtual boot cycles, and process domains at various privilege modes. This binding is achieved by using the Localities as _tweaks_ in the encryption and decryption of SCCs.

[[ACE-architectural-model]]
==== Architectural Model

ACE is architected as an interface to an _attached_ unit. ACE instructions are modeled as messages sent over a tightly coupled coprocessor interface. The ACE unit receives operations from the hart, executes them independently, and returns results.
This model minimizes hart-side implementation complexity: for instance, software implements the logic for CR configuration instructions, while the ACE unit implements cryptographic operations.
This allows multiple cores to share an ACE unit, with separate architectural state for each hart, while minimizing the hardware footprint.

The specification only defines the architectural behavior, not implementation.
ACE may be integrated into a CPU core or implemented as a distinct hardware unit, with separate architectural state for each client hart, and both approaches will be supported by the same code.

ACE may be partially or completely emulated in M-mode firmware.
For example, an implementation may perform symmetric cipher operations (cf. <<ACE-states-symmetric>>) in the ACE unit while emulating public-key cryptography (cf. <<ACE-ECC>> and <<ACE-PQC>>).
Public-key primitives may require very large states. Emulating them in M-mode firmware avoids storing those states in the ACE unit, provided that the relevant CRs reside in secure memory such as on-chip SRAM reserved to M-mode (see <<ACE-CRF>> for the requirements of this memory).

CR state must never be accessible in the clear to any privileged mode except M-mode and authenticated Debug mode.
This forbids ACE implementations in S/VS-mode or HV-mode.
Instructions and Algorithms may be emulated only in M-mode.
Trap-and-emulate and on-demand (lazy) SCC import rely on the ``*lcrstatus`` CSRs (cf. <<ACE-CSR-lcrstatus>>).

=== Programmer-Visible Architectural State

[[ACE-cryptographic-registers]]
==== Cryptographic Registers

{empty}
(((Cryptographic Context)))
ACE defines 32 Cryptographic Registers (CRs), numbered 0 to 31 and denoted `K0`–`K31`.

CRs are per-hart architectural state, like GPRs or vector registers.

CRs are not separated by privilege Mode: when a hart changes Mode, it sees the same set of CRs.

Unlike a conventional register, a CR can be _unconfigured_, meaning it does not contain a CC.

A CR is addressed either directly, via a 5-bit immediate, or indirectly, via a GPR value; an additional instruction-encoding bit selects the mode.

[NOTE]
====
Indirect CR addressing implies that CR renaming, while still possible, would significantly increase microarchitectural complexity.
We posit that CR renaming is not expected to be necessary, and may even be detrimental, for ACE, for the reasons outlined below.

. Excluding implicit internal state changes, CRs are redefined far less frequently than GPRs or FP registers; and
. Speculating on the results of cryptographic operations usually leads to security issues.
====

As mentioned in <<ACE-concepts>>, (the CC in) each CR contains two types of information: the Metadata and the Content.
The latter is a structure containing the cryptographic secrets and other information needed by the algorithm encoded in the CR.
Let the _i_-th CR be denoted `K(i)`.
Its Metadata Header is referred to as `K(i)`.MDH, and the content as `K(i)`.`Content[]`.
`Content[]` is further partitioned into `Content1[]`, the architecturally defined content of the CR, and `Content2[]`, any implementation-defined content. The structure of `Content1[]` is given in <<ACE-Algorithms>> for each Algorithm defined in this specification. The structure of `Content2[]` is implementation dependent.

[[ACE-CRF]]
==== The Cryptographic Register File and Authentication Information

CRs reside in a dedicated, per-hart _CR file_ (CRF), a memory accessible only to the ACE implementation.
If the implementation is (partially) emulated, only M-mode firmware can access the CRF and an implementation-defined mechanism to access the CRF must be provided.
(((Cryptographic Register File)))

The CRF guarantees the confidentiality and integrity of its contents, including protection against rollback through any access not explicitly permitted by this specification.
CRF accesses do not require hardware-level hardening against physical side-channel attacks.
However, side-channel-protected implementations of Algorithms in the ACE unit must protect also the CRF accesses.
It is recommended that `SCC_KeyDeriv`, `SCC_Encrypt`, `SCC_Decrypt`, and every use of the CSK and of the keys derived from it, be implemented by the ACE implementation with side-channel protection not weaker than the highest _SCProtection_ level, under the implementation's ordering, that it supports for any Algorithm.

Architecturally, the CRF contains:

. An array of 32 128-bit blocks, where the _i_-th entry contains the MDH of `K(i)`.
. An implementation-defined amount of memory that can be dynamically allocated to the various registers.
  The region of this memory allocated to a CR contains `Content[]` while provisioning and
   `Content[] := Content1[] || Content2[]` during other configuration and export operations.

These two types of information are conceptually distinct, regardless of implementation.
The MDH array is always present and is not subject to allocation, so every CR always holds its MDH, even if only to signal that the CR is not configured.
Only the second part is dynamically allocated and capacity-limited; “CRF capacity” refers only to this part.
A CR that holds only its MDH therefore consumes no CRF capacity.

The amount of CRF capacity consumed by each CR depends on the Algorithm encoded in the MDH, and it may differ from one CR to another.

Insufficient residual CRF capacity may prevent execution of a configuration instruction.

Capacity is freed by unconfiguring other CRs.

Any corruption of the CRF associated with a hart is an unrecoverable error condition.
The ACE architectural state associated with the hart is reset, and ACE exception `ace_exc_fatal` is raised (see <<ACE-exceptions>> and <<ACE-error-architecture>> for the behavior when the Privileged Architecture is not implemented).
A hart reset resets the ACE state of the hart (<<ACE-reset-and-m-mode-only>>); on power down, that state is zeroized.

The ACE unit also contains the following per-hart information:

. An integer register (accessed via CSR `acemanagedcr`, cf. <<ACE-CSR-acemanagedcr>>), which holds the index of the CR being currently managed, or 32 if no CR is currently managed.
. Three 128-bit registers which hold authentication data (the `SIV`, `IMPQUAL`, and SIV2) of the CR being currently managed.
These registers are accessed via three CSR pairs:
`acesivl`/`acesivh`
`acesiv2l`/`acesiv2h`
`aceiql`/`aceiqh` (cf. <<ACE-CSR-six-auth-CSRs>>).

[NOTE]
====
The 128 or 384 bits used to hold `SIV`, `IMPQUAL`, and `SIV2` are allocated per hart and not per CR to reduce their hardware cost.
This prevents concurrent non-clearing management operations in the same code: starting a second operation may overwrite the first operation's in-flight values.
The CSRs holding these values must therefore be saved and restored on a context switch.
Within a single process, multiple such operations require careful coordination through a lightweight threads library with ACE context-switching support or serialization using a mutex.
Clearing a CR is always possible, whether or not it is the currently managed CR.
====

==== Providing Inputs and Outputs

[[ACE-ACEV]]
===== RVV/ACEV

// [WARNING]
// ====
// [.red]#ACEV need not be finalized before ACE ratification begins; it
// may be defined later, and the ACE specification amended accordingly.
// This allows additional requirements to be collected.#
// ====

ACE inputs and outputs may use vector registers or an architectural input/output buffer (ACEIOBUF)
that can be loaded from and stored to external memory. Both mechanisms may be supported simultaneously.

When vector registers are used, the full V extension is not required. ACE depends only on a minimal subset, termed _ACEV_.
(((ACEV)))
ACEV must be fully opcode-compatible with RVV: code written for ACEV executes with identical behavior under V together with Zvbc.
The current set of features is:

* Vector registers of at least 128 bits.
* Configuration-setting instructions (`vsetvli`/`vsetivli`/`vsetvl`):
** ACE does not use vector masking and does not define masked versions of its instructions.
Therefore, ACEV only requires tail-agnostic and mask-agnostic configurations, and ACE operations on vector registers always use a tail-agnostic policy;
Bit 25 of the `ace.exec` instruction encoding is reserved for potential future adoption of masked operations, should a compelling use case arise.
** Support for `LMUL` integer values of 1, 2, 4, and 8;
** A `vsetvl`/`vsetvli`/`vsetivli` requesting a configuration ACEV does not support sets `vtype.vill` and `vl` = 0, as in RVV; an ACE instruction with a vector operand issued while `vtype.vill` is set raises an illegal-instruction exception.
* Unit-strided vector loads and stores;
* `vmv.x.s` and `vmv.s.x` and the slide instructions `vslideup.v[xi]`, `vslidedown.v[xi]`, `vslide1up.vx`, and `vslide1down.vx`, to insert data into and extract data from vector registers;
* Vector logical operations: `vand.v[vxi]`, `vor.v[vxi]`, and `vxor.v[vxi]` (the immediate variants allow obtaining, for instance, a bitwise NOT); and
* `vclmul.v[vx]` and `vclmulh.v[vx]` from `Zvbc`. They may be implemented as trap-and-emulate.

NOTE: ACE does not depend on a concept of element.
From a logical point of view, the operations are not performed in the vector unit.
A vector register (group) is seen as a bit string of length `VL` * `SEW`, where `VL` is the vector length in effect (`vl`).

Floating-point, fixed-point, and general arithmetic vector operations are not required.

When vector registers are used, ACE determines the lengths of its operands from `VL*SEW`.
The specific choice of `VL` and `SEW` is irrelevant; for example, `VL` = 2, `SEW` = 64 and `VL` = 4, `SEW` = 32 both define a 128-bit input.
The CPU instruction-decoding side of ACE uses `VL` and `SEW` to determine how much data to send to the ACE unit proper, but the ACE unit itself requires only the product `VL*SEW` (or `aceiobuftop`).

===== ACEIOBUF

ACEIOBUF is an optional architectural input/output buffer that may be used in place of vector registers.

ACEIOBUF is not part of the CRF.

Two instructions, `ace.input` and `ace.output`, load and store data from/to the ACEIOBUF to/from the external memory.
When the ACEIOBUF is used, `ace.exec` and `ace.setst` are used in forms with implicit input and output provided by the ACEIOBUF,
as described in <<ACE-usage-input-output>>.

[[ACE-Metadata]]
==== Metadata

ACE recognizes two types of metadata that may be contained in a CC or associated with it.

. A 128-bit _MDH_ that determines the Algorithm, the type of key, and various usage policies associated with the key.
This information is always present in a CC.
The fields are arranged so that the first 64 bits suffice to determine the length of a PI or SCC.

. An optional 128-bit _Implementation Qualifier_ block, denoted by `IMPQUAL`.
It holds copies of three architectural registers that are the ACE analogues of the hart's `mvendorid`, `marchid`, and `mimpid` CSRs (see <<ACE-CSR-impl-ids>>).
This qualifier appears only in an SCC which carries an implementation-specific content segment.
An implementation uses it to decide whether it can use the latter.

This section deals with the 128-bit MDH.
Its fields are summarized in <<ACE-metadata-header>>.
All _Reserved_ bits, as well as bits unused by a given Algorithm, are zero.

[[ACE-Algorithm-field]]
===== _Algorithm_ and _AlgorithmPolicy_ Fields

Algorithms are encoded in a 12-bit field.
Values 0–3071 are architecture-defined.
The list of encodings is maintained by RVI (see <<ACE-Algorithms>>).
The remaining values are available for custom Algorithms.

For encryption/decryption primitives and modes, the _AlgorithmPolicy_ field indicates whether the CC may be used for encryption (lower bit set), decryption (upper bit set), or both. At least one of the bits must be set.

For asymmetric primitives supporting signatures, the lower bit permits signature generation and the upper bit permits verification. In this case, both bits may be zero.

For other primitives, the _AlgorithmPolicy_ field may encode additional Algorithm identifiers to expand the effective encoding space of the _Algorithm_ field.

[[ACE-KeyType-field]]
===== _KeyType_ Field

This field takes the value 0 if the key is given by an explicit value, and 1 if the key is given by a system-specific, 64-bit System Key Identifier (SKID).
Values 2 and 3 are currently reserved: a PI or SCC whose _KeyType_ carries one of them is invalid Metadata (see <<ACE-MVR-open>>). See <<ACE-system-keys>>.

If the value is 0, keys are provisioned, exported, and imported by value.

If the value is 1, keys are provisioned, exported, and imported as a System Key Identifier (SKID), except for the all-ones (i.e., `ones(64)`) SKID value.

If the SKID is the all-ones value, the key material is randomly generated when provisioning completes, and the CR's _KeyType_ field is then set to 0, so that the key is thereafter exported by value.
Unless otherwise specified, random generation applies to all keys in an Algorithm at once.

NOTE: A system key identifier may refer to keys with unrelated purposes on different devices; see <<ACE-system-keys>>.
The SKS supplies an appropriate _Locality_ (see <<ACE-Localities>>) during CR provisioning to bind the key to the system (<<ACE-system-keys>>).

[[ACE-State-field]]
===== _State_ and _StateExtension_ Fields

The _State_ field is used to track the current state of a CR and of the Algorithm encoded in its MDH.
Examples include whether the CR is _Unconfigured_, encrypting or decrypting data, initializing a hash function, absorbing data in it, and finalizing the digest,
computing elliptic curve point multiples, generating or verifying signatures, or is in an error state.

The _StateExtension_ field can be used by an Algorithm to store additional state information, usually orthogonal to the _State_ field, such as whether certain values have been provisioned or computed.

The architected values of _State_ common to all Algorithms are defined in the following three tables.

[[ACE-state-off]]
.Global CC State Numbers: Unconfigured State
[float="center",align="center",width="100%",cols="^7%,<30%,<16%,<47%",options="header"]
|===
| Value | Mnemonic                  | State Name     | Description
|   0   | `ace_state_unconfigured`  | _Unconfigured_ | The CR is not configured, i.e., it does not contain a valid CC.
|===

[[ACE-states-valid]]
.Global CC State Numbers: Valid States
[float="center",align="center",width="100%",cols="^7%,<30%,<16%,<47%",options="header"]
|===
| Value | Mnemonic                  | State Name     | Description
|   1   | `ace_state_ready`         | _Ready_        | The state of a new (i.e., just provisioned) CC; ready for operation.
| 2-45  3+| Defined by the specification of the Algorithm encoded in the _Algorithm_ field.
|  46   | `ace_state_success`       | _Success_      | Algorithm completed successfully. No further cryptographic operations may be performed until the CR is reconfigured or transitioned to _Ready_, with the two exceptions given in <<ACE-State-field>>.
|  47   | `ace_state_failure`       | _Failure_      | Failure in an Algorithm, usually an authentication failure in AE(AD) Algorithms or a signature verification failure. No further cryptographic operations may be performed until the CR is reconfigured or transitioned to _Ready_, with the two exceptions given in <<ACE-State-field>>.
|===

[float="center",align="center",width="100%",cols="^7%,<30%,<16%,<47%"]

|  48    | `ace_state_unsupported`         | _Unsupported_     | Not supported (i.e., not implemented) Algorithm.
|  49    | `ace_state_invalid`             | _Invalid_         | The CR has been invalidated by invalid Metadata or by an operation not permitted in its current State.
|  50    | `ace_state_out_of_memory`       | _Out of Memory_   | Insufficient CRF memory for a configuration instruction. This may be set by privileged code if it does not handle CR allocation or fails to do so, returning an error instead.
|  51    | `ace_state_import_auth`         | _Authentication Failed_     | Authentication failure while completing an SCC import.
|  52    | `ace_state_priv_violation`      | _Privilege Violation_       | Violation of Usage Control policies.
|  53    | `ace_state_expired`             | _Expired_         | The CR has expired.
| 54, 55 | (Reserved)                      | {empty}           | Reserved for future use.

State 0 is the _Unconfigured_ state.  It denotes that the CR is unconfigured.
When a CR is in the _Unconfigured_ state, no other field of the MDH has a meaning and it reads zero.
For instance, there are no Usage Policies, Expiration Dates, or Key Types on _Unconfigured_ CRs.

States 1–55 are called _Complete_.
They include States from 1–47, which are called _Valid_, and
(((ACE, Algorithm, error states)))
States 48–55, which are termed _Error States_. The latter are used to report ACE errors.
State 1 is the _Ready_ state.
All Algorithms must support State _Ready_ as their initial State.
The Valid States include both _Success_ (46) and _Failure_ (47) states, which must be used for normal completion of an Algorithm in the cases of its successful completion or failure.

(((ACE, Algorithm, invalid state)))
(((Cryptographic Register, invalidation)))
We say that a CR has been _invalidated_ when it has been transitioned to Error State `ace_state_invalid`.
Upon entering an Error State, the CR retains only its MDH (Rule <<ACE-SGR-error-state-CR-is-only-MDH>>).

The currently defined Error States are listed in decreasing severity order, with Error State 48 being the most severe and Error State 53 the least severe.
Error States 54 and 55, if defined, will not necessarily have a lower priority than Error State 53, so the ordering may not hold for them.

Error conditions that lead to exceptions are treated in <<ACE-exceptions>>. See <<ACE-error-architecture>> for the behavior when the Privileged Architecture is not implemented.

If an Algorithm defines 47 or fewer valid states (including _Ready_, _Success_, and _Failure_), the current state is stored in the _State_ field.
For Algorithms with more than 47 valid states, additional state information may reside in the Content section in an Algorithm-specific format.

When a CR is being provisioned, exported, or imported, it is in one of the following states, which are called _Configuration_ States:

[float="center",align="center",cols="^7%,<33%,<60%",options="header"]
|===
| Value    | Mnemonic                  | Description
|   56     | `ace_cfg_provisioning` | The CR is being configured.
|   57     | `ace_cfg_exporting`    | The CR, which was in a _Valid_ state, has been placed in exporting mode, i.e., its contents have been encrypted and authenticated for export.
|   58     | `ace_cfg_importing`    | The CR, which was in a _Valid_ state, has been placed in importing mode.
|   59     | `ace_cfg_exporting_partial_pi` | The CR, whose base operation is a provisioning, has been placed in exporting mode; its image follows the format of a PI.
|   60     | `ace_cfg_importing_partial_pi` | Such an image is being reimported.

|   63     | (Reserved)                      | Reserved.

(((ACE, Algorithm, partial states)))
States 56–63, i.e., the states used during management operations, are called the _Partial States_, and are exactly the States that are neither _Unconfigured_ nor Complete.

The four Configuration States whose mnemonics contain `_partial_` are the _Nested_ States: a CR
enters one of them when a management operation is opened on a CR that is already under management
(<<ACE-nested-CR-management>>). The _base operation_ of such a group is its outermost management
process.  Clearing a CR is an atomic operation that resets the CR to the _Unconfigured_ state, and
as such it is not part of nested management operations.

[[ACE-nested-state-base-types,Nested State Base Types]]
Nested State Base Types:::
The `pi` and `scc` base types of the nested States record whether the image the CR holds originates
from a PI or an SCC, following from the base operation: the base type of a Configuration State is `pi` for
`ace_cfg_provisioning`, `ace_cfg_exporting_partial_pi` and `ace_cfg_importing_partial_pi`, and `scc` for
`ace_cfg_exporting`, `ace_cfg_importing`, `ace_cfg_exporting_partial_scc` and `ace_cfg_importing_partial_scc`.
They determine its length
(<<ACE-instruction-size>>), which could not otherwise be recovered once the nested management
operations have overwritten the original _State_.

The immediate in the `ace.setst` instruction (<<ACE-instruction-setst>>) is a 7-bit value, whereas the _State_ field is only 6 bits long.
This allows `ace.setst` to encode additional operations related to state changes.
The only architected such operation is encoded with the value 64 (`ace_cfg_clear_ads`), which clears any ADS so that the CR can be exported without it; values 65–127 are available to Algorithms
(see <<ACE-instruction-clearads>>).

* Valid States have single rounded rectangular borders.
* Error States have double rounded rectangular borders.
* Continuous edges denote state transitions induced by usage instructions.
* Dashed edges denote state transitions induced by reaching the expiration date.
* Dotted edges denote state transitions induced by configuration operations.

The following rules are generic and apply to all Algorithms (*SGR* means "State-Specific General Rules"):

[horizontal]
SGR1:: The MDH's _State_ field reflects the current state whenever the CC is in _Ready_, _Success_, _Failure_, or any Error State.
This ensures that these states can be unambiguously determined from the _State_ field alone, without inspecting other fields or the Content.

[[ACE-SGR-no-exec-in-ready,SGR2]] SGR2:: No `ace.exec` instruction may be executed in State _Ready_ unless the Algorithm explicitly allows it.
Issuing one otherwise transitions the CR to Error State _Invalid_ (Rule <<ACE-AGR-not-allowed-instructions>> in Book 2).

SGR3:: Any transition listed in an Algorithm's specification may be triggered by performing an explicit `ace.setst` operation (<<ACE-instruction-setst>>), or may be induced by certain conditions specified in the Algorithm's specification. Transitions to and between _Configuration_ States use `ace.mgmt`; transitions from a Configuration State use `ace.mgmt`, `ace.clear`, an Error State-setting `ace.setst`, or an `ace.clone` naming the CR as destination.

SGR4:: In States _Success_ and _Failure_, only the following ACE instructions are permitted: `ace.mgmt`, `ace.size`, `ace.setst` (subject to Rule <<ACE-SGR-setst-in-success-failure>> below), `ace.getmd*`, `ace.getst`, `ace.clone`, `ace.restrict*`, and `ace.derive`.
An `ace.exec` other than those permitted below, or an `ace.setst` not allowed by the architecture or by the Algorithm in its current _State_ and _StateExtension_, transitions the CR to Error State _Invalid_ (cf. Rule <<ACE-AGR-not-allowed-instructions>> in Book 2).
+
Also permitted, in State _Success_ only, is an `ace.exec` whose sole purpose is to squeeze further output from an Algorithm
that produces an arbitrarily long one, such as a XOF, whether issued directly or as the source
endpoint of an `ace.derive` (even if squeezing is per se a cryptographic operation).
+
`ace.derive` is also permitted in State _Success_ only, and is limited to the following two cases: where the source endpoint is one of its exportable fields (<<ACE-instruction-derive>>); and under the conditions of use of `ace.exec`.
+
A CR in State _Success_ or _Failure_ may not be the *destination* of an `ace.derive`.
+
NOTE: `ML-KEM.Decaps` (<<ACE-PQC-ML-KEM>>) is the motivating case for this `ace.derive` behavior:
it leaves the shared secret in `sharedkey` and
transitions to _Success_, from which the only other exit is _Ready_, and _Ready_ clears
`sharedkey`. Without this provision the shared secret would be unreachable and ML-KEM could not
be used for its stated purpose.

[[ACE-SGR-setst-in-success-failure,SGR5]] SGR5:: In States _Success_ and _Failure_, `ace.setst` is only permitted to transition to _Ready_ if the Algorithm does not forbid it, to _Unconfigured_ using `#immed7` = `ace_state_unconfigured`, or to an explicitly given Error State.
It is also permitted with `#immed7` = `ace_cfg_clear_ads` (<<ACE-instruction-clearads>>), which clears any ADS and leaves the _State_ unchanged, when this does not violate usage-control policy.

SGR6:: States _Success_ and _Failure_ cannot be set directly using `ace.setst`: the immediates 46 and 47 are reserved (<<ACE-illegal-instruction-grounds>>).

SGR7:: A transition from any valid state to _Ready_ using instruction `ace.setst` is always permitted, unless the Algorithm explicitly forbids it.
// +
// NOTE: Since a CR can always be restored from a backup SCC, preventing transitions to _Ready_--as "GCM with Set IV" (<<ACE-GCM-with-IV-mode>>) does--is not an effective mitigation against the attacks that would be enabled by transitioning to _Ready_.

SGR8:: The CR state after `ace.setst` completes does not always match the instruction's immediate operand.
Beyond Error State transitions, some operations determine the next state dynamically.
For example, issuing `ace.setst` with an `ace_state_hash_verify` immediate and a verification parameter transitions the CR to either _Success_ or _Failure_.
Instructions such as `ace.exec` may also cause _State_ changes.

[[ACE-SGR-clear-cr-content-error-state,SGR9]] SGR9:: Upon transitioning to an Error State, the Content of a CR beyond the MDH is cleared:
Internal resources associated with the Content shall also be released,
including any ADS, and the _AuxDataLen_ field is set to 0.
// Since the CR is in an Error State, it is in a Complete State.

[[ACE-SGR-error-state-CR-is-only-MDH,SGR10]] SGR10::
A CR in an Error State then retains only the MDH.
Requesting its size (<<ACE-instruction-size>>) returns 16 bytes for `ace.size` and zero for `ace.csize`.

[[ACE-SGR-transition-to-from-unconfigured,SGR11]] SGR11:: Transitions from _Unconfigured_ to any Complete State (Error or Valid) may only result from a configuration instruction.
Any usage-controlled instruction (<<ACE-instruction-properties>>) in State _Unconfigured_ raises an illegal-instruction exception.
Transitions from an Error State to _Unconfigured_ result from explicitly clearing the CR, or from re-opening it for provisioning or import.

SGR12:: The MDH of a CR in the _Unconfigured_ State can be read using `ace.getmd*` (<<ACE-instruction-getmd>>), returning all zero values.

SGR13:: Exporting a CR in an Error State exports only the MDH (all fields and values), and requires no
`ace.mgmt`:
The MDH of a CR in an Error State is read by software using `ace.getmd*` (<<ACE-instruction-getmd>>) and stored to memory.
The image can be reimported with a single `ace.mgmt`, allowing software to take appropriate actions even after a context switch.

SGR14:: If a CR is in any Error State, it can still be reconfigured, cloned, or cleared;
apart from clearing, `ace.setst` can only be used to change the Error State.

[[ACE-SGR-usage-cr-error-state,SGR15]] SGR15:: Attempts to _use_ a CR in any Error State will not perform any operation, and in particular leave the _State_ field unchanged.
Such an attempt can be considered an operation that would cause a transition to  Error State `ace_state_invalid`, so the _State_ field is left unchanged to allow software to address the original error condition. No history of Error States is maintained by the architecture.

[[ACE-SGR-usage-policy,SGR16]] SGR16:: Any _usage_ instruction that would violate the Usage Control policies will not perform its operation, and raises ACE exception `ace_exc_privilege_violation`. See <<ACE-error-architecture>> for the exact behavior, including when the Privileged Architecture is not implemented.

[[ACE-SGR-usage-cr-config-state,SGR17]] SGR17:: Usage of a CR in a Configuration State, cloning from it, and restricting it, are not allowed:
Any attempt to do so raises ACE exception `ace_exc_privilege_violation`.
For a CR in a Configuration State used as the destination of an `ace.clone`, or named as both its source and its destination, see <<ACE-instruction-clone>>.

[[ACE-SGR-gate-order,SGR18]] SGR18:: For a usage-controlled instruction (<<ACE-instruction-properties>>), after the illegal-instruction grounds decided without reference to the CR (the first group of <<ACE-illegal-instruction-grounds>> and the `acestart`/`vstart` check of <<ACE-CSR-acestart>>), the conditions on a CR are evaluated in this order, and the first that applies decides the outcome:
+
--
. _Unconfigured_: illegal-instruction exception (Rule <<ACE-SGR-transition-to-from-unconfigured>>);
. Error State: no operation and no exception (Rule <<ACE-SGR-usage-cr-error-state>>);
. Configuration State: ACE exception `ace_exc_privilege_violation` (Rule <<ACE-SGR-usage-cr-config-state>>);
. _UsagePolicy_: ACE exception `ace_exc_privilege_violation` (Rule <<ACE-SGR-usage-policy>>);
. _ExpirationDate_: transition to Error State `ace_state_expired`, then no operation (<<ACE-Metadata-expiration-date>>);
. an ACEIOBUF required by a substitution but unconfigured: ACE exception `ace_exc_unconfigured_buffer` (Rule <<ACE-GR-iobuf-configured>>);
. the Algorithm's own rules.

For `ace.derive`, each condition is evaluated for both endpoints before the next; an Error State on either endpoint makes the whole instruction a no-op.
--

[[ACE-SGR-config-instructions-partial,SGR19]] SGR19:: Instructions `ace.size`, `ace.getmd*`, `ace.getst`, `ace.setst` with the 7-bit immediate equal to `ace_state_unconfigured` or an
Error State, `ace.clear`, and `ace.clear.all`, which are configuration instructions and are not gated by Usage Control policies, are also allowed
when the CR is in a _Partial_ State.

[[ACE-SGR-ace-load-mv-allowed,SGR20]] SGR20:: `ace.load` and `ace.mv` with a destination CR
are allowed in States `ace_cfg_provisioning`, `ace_cfg_importing` and `ace_cfg_importing_partial_{pi, scc}`.

[[ACE-SGR-ace-store-mv-allowed,SGR21]] SGR21:: `ace.store` and `ace.mv` with a source CR
are allowed in States `ace_cfg_exporting`, and `ace_cfg_exporting_partial_{pi, scc}`.

[[ACE-extra-content]]
===== _AuxDataLen_ Field

The _AuxDataLen_ MDH field records the length of the _Auxiliary Data Section_ (ADS) of the content, a variable-size, implementation-dependent part, as a number of 128-bit blocks. The maximum value is 2^14^-1, corresponding to 262128 bytes.

If _AuxDataLen_ is zero or one, there is no ADS.
The value one is used by the SCC import procedure to signal the state machine in the CR that ADS was present in the SCC, but it was discarded (see <<ACE-SCC-import>>).

If _AuxDataLen_ {ge} 2 a copy of the implementation qualifier from the originating machine

``{fournbsp}{fournbsp}IMPQUAL := zeros(32) @ acemimpid @ acemarchid @ acemvendorid``

(cf. <<ACE-CSR-impl-ids>>) is included in the SCC.
These 16 bytes, as well as a separate authentication tag for the ADS are counted within the length recorded by the _AuxDataLen_ field. The importing implementation uses this value to determine whether the ADS can be used.

Since an ADS contains at least an authentication tag (16 bytes) and the originating implementation qualifier (also 16 bytes), the minimum length is 32 bytes, corresponding to an _AuxDataLen_ value of 2.

// The format of the ADS is described in <<ACE-data-formats>>.

[[ACE-UsagePolicy]]
===== _UsagePolicy_ Field

The _UsagePolicy_ field determines which modes are allowed to use the CR.

Bits 0, 1, 2, and 3 of the field, when set, disallow CC usage in U-mode, VS-mode, HS-mode, and M-mode, respectively. Bit 4 grants usage in Debug mode only if set. Bit 0 governs both U-mode and VU-mode, and bit 2 governs S-mode whether or not the H extension is implemented.

Any bit of this field is ignored if the corresponding mode is not supported or not enabled.

[[ACE-Localities]]
===== _Locality_ Field

The _Locality_ field identifies 128-bit Locality Secrets (LSs) listed in <<ACE-locality-indexes>>. The LSs are stored in a (possibly virtual) Locality Secrets Table (LST). Some entries are fixed or configurable only through an implementation-specific, authenticated hardware process. These entries are shared by all ACE units in the same SoC. The remaining entries are software-programmable, per-hart architectural state.

At SCC export and import, any Locality defined by the _Locality_ field cryptographically binds an SCC to the corresponding _current_ hardware and software environments. This binding ends when the SCC is imported into a CR. If a Locality Secret later changes, a subsequent export binds the SCC to the new value. Software is responsible to prevent unauthorized parties from directly accessing CRs.

<<ACE-locality-indexes>> lists the architected Localities. Eleven LST entries are defined. Entries 0–5 form the _HW Binding Group_, which binds SCCs to the hardware; entries 6–7 form the _Boot Session Group_; and entries 8–10 form the _SW Filter Group_. For each Locality, the table specifies its LST index, domain (SoC-wide, device-wide, VM-wide, or per-process), configurability, bit-field encoding, and value.

either — then the Metadata is invalid (see <<ACE-Metadata-validity>>).

A Locality Secret of the Boot Session Group or of the SW Filter Group whose value is `zeros(128)` is _unconfigured_ (its CSR is defined in <<ACE-priv>>).
A PI or SCC whose _Locality_ field names an unconfigured entry, or carries the reserved value `3` in bits [5:4], is invalid Metadata (see <<ACE-Metadata-validity>>).

_HLocality_ is active only when the H extension is enabled and V=1; otherwise, it mirrors _MLocality_.

Up to six architected Localities may be active concurrently: up to two from the HW Binding Group; at most one of _PhysBootScrt_ or _VirtBootScrt_; and up to three from the SW Filter Group.  The SCC generation and import algorithms described in <<ACE-CC-management>> enforce the policies associated with these Localities.

[[ACE-Metadata-expiration-date]]
===== _ExpirationDate_ Field

This field is only in effect if extension _Zklexpire_ is supported.

If _Zklexpire_ is supported, the ACE implementation must have access to a secure clock.

If _Zklexpire_ is not supported, a non-zero _ExpirationDate_ in a PI or SCC is invalid Metadata (see <<ACE-Metadata-validity>>).

If non-zero, the 20-bit _ExpirationDate_ field specifies the CC's expiration time as whole hours elapsed since 00:00 UTC on 1 January 2027. The maximum representable time span is approximately 119 years and 7 months. The epoch is UTC so that a CC exported on one device and imported on another expires at the same instant regardless of the local time each observes.

[NOTE]
====
This specification cannot enumerate requirements for a trustworthy clock, as
what constitutes adequacy depends on threat models, platforms, and integration
specifics — a challenge common to all time-dependent security features. As a rule
of thumb: *if a clock is adequate for M-mode security features or an on-SoC TPM, it is adequate for ACE.*
ACE imposes no stricter requirements. Crucially, software below M-mode must not be able to set the
clock, as that would allow indefinite extension of a CC's lifetime by moving
time backward.
====

This section is the only authoritative statement in this specification of when the _ExpirationDate_ field is evaluated.

The _ExpirationDate_ field is evaluated normatively at the following points:

* At issue of any `ace.exec`, usage-controlled `ace.setst`, or `ace.derive`.
* For `ace.derive`, both endpoints are checked.
* At every architectural resumption point.

The _ExpirationDate_ of a CR that is not in a Valid State is not evaluated.
A transition to Error State `ace_state_expired` is only triggered when an expired CR is being actively used, while still permitting expired contexts to be cleanly evicted, saved, or unconfigured.

The evaluation of _ExpirationDate_ is performed as follows:

. If _ExpirationDate_ is zero, the instruction may proceed.
. The date from the secure clock is converted to the format of the _ExpirationDate_ field; a reading earlier than 00:00 UTC, 1 January 2027 converts to 0.
. The converted date is then compared to the _ExpirationDate_ itself.
. If the converted value is not smaller than the _ExpirationDate_, the ACE implementation transitions the CR's _State_ field to Error State `ace_state_expired`.
. Otherwise, the instruction may proceed.

[[ACE-Algorithm-version]]
===== _Version_ Field

This two-bit field denotes the version of the MDH format.

If _Version_ = 0, then the format is the current version.

The value _Version_ = 1 is used to denote newer revisions of the MDH format.
Additional version information must be encoded in other fields of the MDH.

If _Version_ = 3, the format is system-specific.
System-specific formats are allowed only for import operations.
Any such format must be preceded by an ACE-format MDH to allow import to begin.
The system-specific format may contain its own usage and access policies or locality bindings.
This information must be converted to an ACE-compatible representation without weakening any usage policy or locality binding.
When `ace.mgmt` completes import, the MDH policies may be replaced accordingly.
_Version_ is then set to 0 (or 1 in a future version of this specification).

Support for loading system-specific formats is optional.
The resulting CRs can be exported only in the ACE-specified format.
To prevent loading on different implementations, specific localities may be set, or all information may be stored in the ADS to gate it using IMPQUAL.

An implementation may support multiple system-specific formats;
The ACE specification does not specify how to distinguish between them: this is up to the implementation.

The value _Version_ = 2 is reserved.

A PI or SCC with a _Version_ not supported by the implementation
is invalid Metadata (cf. <<ACE-Metadata-validity>>).

[[ACE-Metadata-validity]]
===== Validity of Metadata

Metadata is _unsupported_ when the combination of _Algorithm_, _AlgorithmPolicy_ and _SCProtection_, or a non-zero _AlgorithmExtension_, is not implemented.

Metadata is _invalid_ when a Reserved bit is non-zero; _AlgorithmPolicy_ is zero for an Algorithm that requires a bit; _KeyType_ is 2 or 3; _Locality_[5:4] is 3, or _Locality_ names an unconfigured Locality Secret (<<ACE-Localities>>); _AuxInfo_ is non-zero for an Algorithm that does not use it; _ExpirationDate_ is non-zero and `Zklexpire` is not implemented; _Version_ is unsupported; the MDH carries a custom value without _ChipFamScrt_ or _ChipScrt_ in _Locality_ (Rule <<ACE-GR-custom-locality>>); _AuxDataLen_ is non-zero in the MDH of a PI; or, in a supplied MDH, _State_ is 63 or, at import, _Unconfigured_, the _Version_ number is not supported by the implementation.

[horizontal]
[[ACE-MVR-open, Metadata Validity Rule]] Metadata Validity Rule:: An `ace.mgmt` that opens a provisioning or import on unsupported Metadata raises ACE exception `ace_exc_unsupported`; on invalid Metadata it transitions the CR to Error State _Invalid_.
These checks are not applied to the short import of an Error-State MDH (<<ACE-error-state-transfer>>).
The CR also transitions to Error State _Invalid_ when, at completion of provisioning, import or export, the System Key Store does not resolve a SKID, or the `Content1[]` of an SCC whose restored _State_ is a Complete State carries the all-ones SKID.

[[ACE-Memory-Alignment]]
==== Memory Alignment Constraints

All accesses to the `Content[]` of a CR have a 16-byte granularity: `ace.load`, `ace.store` and `ace.mv` transfer whole 16-byte blocks, and every offset and length they use, `acestart`, `size`, `max_admissible` and `end` (<<ACE-instruction-load>>), is a multiple of 16 bytes.

The effective address of an `ace.load` or an `ace.store` must be a multiple of 16 bytes.
If it is not, no data is transferred and a load, resp. store, address-misaligned exception is
raised on that address.
A PI or an SCC must therefore be held at a 16-byte aligned address.
For `ace.load` and `ace.store` the conditions are evaluated in this order: the illegal-instruction grounds of both groups (<<ACE-illegal-instruction-grounds>>); address-misaligned on the effective address; then, per component access in offset order, access and page faults.

`ace.input` and `ace.output` are byte-granular and impose no alignment constraint of their own:
a misaligned effective address behaves as it does for an ordinary load or store on the
implementation.

There are no atomicity requirements for any ACE memory instruction.

[[ACE-error-architecture]]
==== Error Handling Architecture

First of all, we address the behavior of ACE in case of error when the ACE Privileged Architecture is not implemented.
For ACE, this may only occur in an M-mode-only hart.
In this case, ACE exceptions are replaced by direct transitions of the CR to an Error State, per the mapping in <<ACE-exception-error-correspondence>>.

[[ACE-exception-error-correspondence]]
.Behavior upon exception conditions when the Privileged Architecture is not available.
[float="center",align="center",cols="<1,<2",options="header"]
|===
| ACE Exception                      | Behavior when the Privileged Architecture is not available.
| `ace_exc_fatal`                    | Implementation and platform defined behavior.
| `ace_exc_no_csk` (See <<ACE-CSK-requirements>> and <<ACE-CSR-macecsk>>.) | The instruction raises an illegal-instruction exception; on an M-mode-only hart M-mode is both the only mode that can observe it and the only one that can establish a CSK.
| `ace_exc_CR_off` (See <<ACE-CSR-lcrstatus>>.)| Does not apply without Privileged Architecture, since the `*lcrstatus` CSRs are not available.
| `ace_exc_unsupported`              | Transition to Error State _Unsupported_.
| `ace_exc_out_of_memory`            | Transition to Error State `ace_state_out_of_memory`.
| `ace_exc_privilege_violation`      | Transition to Error State `ace_state_priv_violation`.
| `ace_exc_unconfigured_buffer`      | The instruction raises an illegal-instruction exception.
|===
The error conditions in <<ACE-exception-error-correspondence>> are placed in their natural priority order.

Conversely, when the Privileged Architecture is implemented, the transition is the duty of the exception handler: it must set the CR's _State_ to Error State
_Unsupported_,
_Out of Memory_, resp.,
_Privilege Violation_
when the following three conditions are met: it cannot resolve exception
`ace_exc_unsupported`,
`ace_exc_out_of_memory`, resp.,
`ace_exc_privilege_violation`; cannot forward it to another handler, including an in-process handler; and does not suppress the process that caused it.
In that case the handler must also resume execution at the instruction following the trapping one, by advancing `xepc`; otherwise the same exception is raised again.
Where the trapping instruction left the CR _Unconfigured_, the handler performs the transition with the short import of <<ACE-error-state-transfer>>, as Rule <<ACE-SGR-transition-to-from-unconfigured>> requires.

In the following, as well
as in <<ACE-Algorithms>>, <<ACE-priv>>, and <<ACE-pseudocode-examples>>,
we shall always describe the behavior when the Privileged Architecture is in effect, with the understanding that raising exceptions will be replaced by the above behaviors when the Privileged Architecture is not implemented.

[horizontal]
State change rule for exceptions:: Whenever an an illegal-instruction exception or an ACE exception other than `ace_exc_fatal` is raised, no change to ACE state is made, except for the initial zeroizing of the target CR by an opening `ace.mgmt`, which is performed even if the instructions raises an exception later (<<ACE-instruction-setst>>). `ace_exc_fatal` resets the ACE state (see _Fatal_ below).

We now give additional explanation of some of the types of error conditions that may occur during the lifecycle of an ACE unit:

Fatal Conditions:::
+
--
This category has the highest priority amongst the ACE specific error categories.
The detection of the errors in this category can not be disabled by any CPU state.

A fatal condition causes an entire reset of the state associated with the hart
including all CSRs and the CSK, if configurable. A CSK generated at boot under the fourth model of <<ACE-CSK-requirements>> is shared by the harts of its subsystem and is not re-generated.
Then, the condition raises ACE exception `ace_exc_fatal`.

The main fatal condition is an integrity failure of the CRF associated with a hart (<<ACE-cryptographic-registers>>), but implementations may define additional fatal conditions.
CRF corruption may be detected synchronously or asynchronously, recorded in the ACE unit, and the ACE state reset may also occur asynchronously.
The first ACE instruction or ACE CSR access issued (or in flight) after detection performs no operation and raises `ace_exc_fatal`; `xepc` holds that instruction's address.
If every `ACES` field in effect is Off at the time of detection, the condition is retained rather than discarded.
It is reported on the first ACE instruction or ACE CSR access issued once `ACES` ceases to be Off.
Detection is therefore never disabled; only its reporting is deferred.
An instruction issued while `ACES` is Off raises an illegal-instruction exception, which <<ACE-exception-codes>> ranks above `ace_exc_fatal`.
The ACE state reset completes before the trap is taken, and the latter is not delegable below M-mode.
--

[[ACE-illegal-instruction-grounds]]
Illegal-Instruction Exceptions:::
+
--
There are two groups of conditions upon which an illegal-instruction exception is raised:

* In the first group, the grounds for raising the exception come from the instruction encoding, the GPRs and the vector configuration alone, without accessing the state of the ACE unit; they therefore take precedence over `ace_exc_fatal` (<<ACE-exception-codes>>):

. A reserved encoding point (Rule <<ACE-GR-reserved-encodings>>), including `ace.setst` with `#immed7` in 59–62 or 46–47, a reserved `#immed7` of `ace.setst` with `r` = 1 and CR register `X0` (<<ACE-instruction-setst>>), and an ACE instruction with a vector operand issued while `vtype.vill` is set (<<ACE-ACEV>>).
. An indirect CR index outside [0..31], or `X0` used as one where not expressly encoded (Rule <<ACE-GR-GPR-indirect>>), and `ace.derive` with equal CR indices (<<ACE-instruction-derive>>).
. A GPR pair or quartet not meeting Rule <<ACE-GR-multiple-GPRs>>.
. A vector operand carrying an MDH with `VL` {times} `SEW` < 128 (Rule <<ACE-GR-vector-MDH-operand>>), or a vector `ace.mv` whose `vl * (SEW/8)` is not a multiple of 16 (<<ACE-instruction-mv>>).
. An encoding assigned to an extension that is not implemented, such as Forms A–C of `ace.exec` without `Zklv` (Rule <<ACE-GR-vector-legality>>).
. An ACE instruction issued while `ACES` is Off (see _Fatal_ below), an ACE instruction issued under big-endian effective data endianness (<<ACE-Notation>>), and an access to a CSR that <<ACE-CSRs-unpriv>> declares unavailable.

* For the second group, the grounds for raising the exception require the state of the ACE unit and are raised only if no fatal condition is pending, otherwise `ace_exc_fatal` is raised:

. A usage-controlled instruction issued on a CR in State _Unconfigured_ (Rule <<ACE-SGR-transition-to-from-unconfigured>>), including `ace.derive` with an _Unconfigured_ endpoint.
. `ace.load`, `ace.store` or `ace.mv` on a CR whose _State_ does not admit the transfer, or with an inconsistent `acestart` (Rules <<ACE-SGR-ace-load-mv-allowed>> and <<ACE-SGR-ace-store-mv-allowed>>).
. `ace.mgmt` when `acemanagedcr` names another CR, when opening an export on an _Unconfigured_ CR, when completing with an `ml`._State_ inconsistent with the CR's Configuration State, or when `ace_cfg_management_end` is issued with no management operation open (<<ACE-instruction-setst>>).
. An ACEIOBUF substitution that <<ACE-usage-input-output>> forbids, including any substitution without `Zklio`, since whether a Form is a substitution depends on the operation the CR's State defines.
. A Form A `ace.mgmt` that must take the MDH from the ACEIOBUF with `aceiobuftop` < 16 (Rule <<ACE-GR-vector-MDH-operand>>).
. An `ace.clone` whose source is _Unconfigured_ and differs from its destination (<<ACE-instruction-clone>>).
. A Form A–C `ace.exec` with `acestart` {ne} `vstart` {times} `SEW` / 8 (<<ACE-CSR-acestart>>).
. A Form A `ace.exec` with `Vd` = `Vs2` for an operation whose output blocks do not have the length of its input blocks (<<ACE-instruction-exec>>).
. If the Privileged Architecture is not implemented, an instruction issued without a CSK, or one that requires the ACEIOBUF while it is unconfigured or absent (<<ACE-exception-error-correspondence>>).
--

// Exceptions and State Changes::: [[ACE-exceptions-and-state-changes,Exceptions and State Changes]]
// When an ACE instruction raises `ace_exc_no_csk`, `ace_exc_CR_off`, `ace_exc_unsupported`, `ace_exc_out_of_memory`, `ace_exc_privilege_violation` or `ace_exc_unconfigured_buffer`, it has changed no ACE state, unless its description states a change that precedes the exception. `ace.mgmt` is the one instruction that does: it zeroizes the target CR before its checks.

Unsupported Algorithms:::
+
--
Unsupported Metadata at provisioning or import raises ACE exception `ace_exc_unsupported` and leaves the CR _Unconfigured_.
A handler that instead intends to emulate the Algorithm sets the
CR's `*lcrstatus` field to _Off_ (<<ACE-CSR-lcrstatus>>), after which every access to that CR
traps and is serviced by the emulator; the emulator then holds the CR in its own protected memory
and services every operation on it, including SCC import and export.

ACE exception `ace_exc_unsupported` is _not_ raised when accessing or using a CR in State `ace_state_unsupported`.
--

Algorithmic Errors:::
+
--
Algorithmic errors may occur in import processes or in the Algorithms themselves:

. In the first case, the error is Error State _ace_state_import_auth_.
. Algorithm-specific errors may cause the CR to transition to Error State _Invalid_, or transition it to some other Error State, according to the behavior specified by the Algorithm.

Successful or failed verification of an authentication tag in an AEAD Algorithm
(_not_ the SCC export and import procedures)
or of a signature is _not_ an algorithmic error, as in this case the Algorithm has performed as expected.
--

On RV32 every 64-bit ACE CSR _X_, in this Book, is accompanied by a 32-bit CSR
named _X_`h` giving access to bits [63:32] of _X_; a read or write of _X_ itself then accesses bits
[31:0]. The shadow has the same privilege as the register it shadows. The six such registers are
`acesivl`, `acesivh`, `acesiv2l`, `acesiv2h`, `aceiql`, `aceiqh`.

If the ACE extension is not present or if an ACES field is Off,
these CSRs, with the exception of
the read-only identification CSRs `acemvendorid`, `acemarchid`,
`acemimpid` and `acemaxiobuflen`,
are not available. Accessing them will raise an illegal-instruction exception.
Therefore, ACE does not need integration in `Smstateen`/`Ssstateen`.

The WARL policy of an ACE CSR that has a maximum is uniform: writing a value larger than the maximum
sets the register to the maximum, so software must read the register back after writing it. Each
such register is given its maximum in its own description below.

The RW CSRs constitute state that must be saved and restored at context switches, following the same software convention as `vstart`:

. `acestart`, `aceiobuflen`, and `acemanagedcr` must always be saved and restored.
. If `aceiobuflen` is non-zero, then `aceiobuflen`, `aceiobuftop`, and the ACEIOBUF contents up to `aceiobuflen` must be saved and restored.
. If `acemanagedcr` {ne} 32 and the CR it names is importing or exporting an SCC, i.e., its _State_ is one of `ace_cfg_importing`, `ace_cfg_exporting`, `ace_cfg_importing_partial_scc`, or `ace_cfg_exporting_partial_scc`, then also `acesivl`, `acesivh`, `acesiv2l`, `acesiv2h`, `aceiql`, `aceiqh` must be saved and restored.
The `_scc` States are included because their outermost operation is an import or an export of an SCC,
whose authentication data must survive the nesting; the `_pi` States are excluded because a
provisioning produces no `SIV`.
Software writes these six CSRs only while `acemanagedcr` names a CR in one of those States;
a value written to them at any other time is not preserved across a context switch.

[[ACE-CSR-impl-ids]]
===== `acemvendorid`, `acemarchid`, and `acemimpid`

{empty}
(((CSR, `acemvendorid`)))
(((CSR, `acemarchid`)))
(((CSR, `acemimpid`)))
`acemvendorid`, `acemarchid`, and `acemimpid` identify the version of the ACE unit, analogously to the `mvendorid`, `marchid`, and `mimpid` CSRs for the hart.

. Their values out of ACE unit reset identify the version of the ACE unit. Software cannot modify these values.

. The `acemvendorid` CSR is a 32-bit read-only register providing the JEDEC manufacturer ID of the provider of the ACE unit (or 0 if not commercial).

. The `acemarchid` CSR is a 32-bit read-only register encoding the base microarchitecture of the ACE unit.
Non-commercial IDs are allocated globally by RVI exactly as for the `marchid` values, while commercial IDs are specific to the `acemvendorid`.

. The `acemimpid` CSR is a 32-bit read-only register that provides a unique encoding of the version of the ACE unit implementation. This register must be readable in any implementation, but a value of 0 can be returned to indicate that the field is not implemented. The implementation value should reflect the design of the ACE unit itself and not any surrounding system. An implementation that produces an ADS must report a non-zero `acemimpid`.

These three CSRs, together, form the _Implementation Qualifier_ (see <<ACE-extra-content>>).

// ////////////////////////////////////////////////////////////////////

[[ACE-CSR-acemaxiobuflen]]
===== `acemaxiobuflen`

{empty}
(((CSR, `acemaxiobuflen`)))
`acemaxiobuflen` is an XLEN-bit RO CSR that reports the maximum configurable length of the ACEIOBUF in bytes.
The value is hardwired and specific to the implementation of the ACE unit.

`acemaxiobuflen` must be at least 16 bytes and at least as large as the largest basic processing unit (granularity) of any implemented Algorithm.

If `Zklio` is not implemented, the ACEIOBUF does not exist: `acemaxiobuflen` reads as zero, and the CSRs `aceiobuflen` and `aceiobuftop` are not present.

// ////////////////////////////////////////////////////////////////////

[[ACE-CSR-aceiobuflen]]
===== `aceiobuflen`

{empty}
(((CSR, `aceiobuflen`)))
`aceiobuflen` is an XLEN-bit URW CSR that programs the ACEIOBUF length in bytes for use by `ace.input` and `ace.output`.
Writing this register—even when re-writing the current value—also zeroes the buffer and sets `aceiobuftop` to the same length.

When `aceiobuflen` is zero, the ACEIOBUF is _unconfigured_.
Attempting to execute an operation that expects an input or an output in the ACEIOBUF while the latter is unconfigured raises exception `ace_exc_unconfigured_buffer`.

The maximum of `aceiobuflen` is `acemaxiobuflen`.

Context switching code must save and restore the contents of the ACEIOBUF up to `aceiobuflen`.

[NOTE]
====
As per the ACE Privileged Architecture, the dirtiness of the ACEIOBUF is not tracked except as part of the entire ACE state in `*status`.
Software should set `aceiobuflen` to zero once the contents of the ACEIOBUF are no longer needed.
Context switching code would then not save and restore the contents of the ACEIOBUF.
====

// ////////////////////////////////////////////////////////////////////

[[ACE-CSR-aceiobuftop]]
===== `aceiobuftop`

{empty}
(((CSR, `aceiobuftop`)))
`aceiobuftop` is an XLEN-bit URW CSR that sets the upper bound in bytes of the buffer range used by `ace.input` and `ace.output`.

`aceiobuftop` plays for the ACEIOBUF the role that `VL` plays in the V extension: it defines the operand length `ACELEN` = `aceiobuftop` {times} 8 and the transfer window [0, `aceiobuftop`).

For operations involving the ACEIOBUF, `acestart` (cf. <<ACE-CSR-acestart>>) is the position within that window at which processing starts or resumes, analogously to `vstart`; when `acestart` {ne} 0, the bytes processed are those at offsets [`acestart`, `aceiobuftop`).
Shortening an operand is done by lowering `aceiobuftop`, never by raising `acestart`.

The maximum of `aceiobuftop` is `aceiobuflen`.

Modifying `aceiobuftop` does not alter buffer contents. It allows per-operation length adjustments without reconfiguring the ACEIOBUF via `aceiobuflen`, an expensive operation that clears the buffer and may trigger internal garbage collection. This mirrors the use of `VL*SEW` reconfiguration to supply a partial “last block” or a short IV/nonce to Algorithms.

Writing a value that is invalid or unsupported for a given Algorithm may still cause the CR to transition to Error State _Invalid_ when an instruction expecting an input from or an output to the ACEIOBUF is later issued or restarted.
This may occur, for instance, when `aceiobuftop` is a length not supported by the Algorithm, or when `acestart` does not correspond to an interruption point the Algorithm allows.

// ////////////////////////////////////////////////////////////////////

[[ACE-CSR-acestart]]
===== `acestart`

{empty}
(((CSR, `acestart`)))
`acestart` is an XLEN-bit RW CSR.

`acestart` tracks the progress of resumable ACE instructions, e.g., `ace.load`, `ace.store`, `ace.input` and `ace.output`.

Progress tracking by `acestart` also applies to `ace.exec` when iteratively processing a multi-block operand, as `ace.exec` may be interrupted between blocks, as well as to `ace.derive`, whose `ace.exec` endpoints advance the state machines of the source and destination CRs in the same way.
The vector input and output Forms of `ace.mv` honor acestart, like the non-vector versions, to track the CR transfer point, and also use `vstart` to track the position in the vector register corresponding to the CR transfer point in case the input/output is multi-block.

ACE does not have an _intrinsic_ concept of element length, hence `acestart` counts the number of _bytes_ processed so far by `ace.exec`, or read/written by `ace.input`/`ace.output` or `ace.store`/`ace.load`.

`acestart` is always a byte count. Progress that is not byte-structured — that of the point
multiplications and signature operations of <<ACE-ECC>> and <<ACE-PQC>>, for instance — is recorded
in the _AlgorithmUse_ field instead, as Rule <<ACE-IRR-long-running-no-data>>
prescribes.

Only these instructions honor a nonzero `acestart`; every other instruction leaves it unchanged, except `ace.mgmt` and `ace.clear.all`, which clear it.

The ACE implementation writes this register on a precise halt, recording a prefix-complete point of the transfer (see <<ACE-Memory-Model>>): the point of progress, or 0 in an implementation that selects the restart option of Rule <<ACE-IRR-resumability-options>> for `ace.load`, `ace.store`, `ace.input` and `ace.output`, which then re-transfer the prefix on re-execution.
Software may save and restore the register across context switches.

`acestart` is the position within the transfer window at which processing starts or resumes, analogously to `vstart` in the V extension; for ACEIOBUF operands the window itself is always [0, `aceiobuftop`) (see <<ACE-CSR-aceiobuftop>>).

An instruction that honors `acestart` sets it to 0 when it retires, unless the specification of the instruction explicitly states otherwise (<<ACE-instruction-mv>>, <<ACE-usage-input-output>>).
The only exception is `ace.mv`, which by design advances `acestart` by the bytes transferred and retains the result across instructions to support piecewise transfers and, if used in the vector version, uses `vstart` to track progress within the vector register. The `vstart` value depends on the chosen vector element size.

The transfer window is empty when `acestart` {ge} `aceiobuftop` for an ACEIOBUF operand (with `aceiobuflen` nonzero), or `acestart` {ge} `VL` {times} `SEW` / 8 for a vector operand.
An instruction with an empty window performs no operation.
This rule does not apply to `ace.mv`, whose vector window is [`vstart`, `vl`) in elements and whose `acestart` is a CR offset (<<ACE-instruction-mv>>).

For Forms A–C of `ace.exec`, `acestart` {ne} `vstart` {times} `SEW` / 8 at issue raises an illegal-instruction exception; this check precedes the empty-window rule.
For an operand used as input, the interruption-point check below, which transitions the CR to Error State _Invalid_, also precedes the empty-window rule; for an operand used only as output, both yield no operation.

For CR-directed transfers (`ace.load`, `ace.store`, `ace.mv`), `acestart` is bounded above by the length in bytes of the serialized `Content[]` being transferred, as determined from the first 8 bytes of the MDH; each of these instructions states the bound it applies.

For certain Algorithms, writing zero to `acestart` to force a full restart of `ace.exec` would
produce an inconsistent result, and it is not permitted once per-block state effects have been
committed (see <<ACE-Memory-Model>>).
An *interruption point* of an Algorithm in a given state is an `acestart` value that the Algorithm
can itself produce on a precise halt in that state. Unless the Algorithm defines a coarser set,
these are the whole multiples of its granularity within the transfer window, together with the
value 0; Subalgorithm `process_VLI` (<<ACE-process-VLI>>) defines its own, at the boundaries
at which its inner loop yields. An Algorithm that admits a different set states it.

More generally, writing a value that is invalid or unsupported for a given Algorithm — including a
value that is not an interruption point the Algorithm allows — causes the CR to transition to Error
State _Invalid_ when an instruction is later issued or restarted with that operand as input; an instruction whose only operand is an output performs no operation instead.

[[ACE-CSR-acemanagedcr]]
===== `acemanagedcr`

{empty}
(((CSR, `acemanagedcr`)))
`acemanagedcr` is an XLEN-bit RW CSR, but currently only 6 bits are used.

It contains the number of the currently managed CR, or 32 if no CR is currently being managed.
If the CR it names ceases to be in a Configuration State otherwise than through a completing `ace.mgmt` — because it is
cleared, also by the zeroizing step of an `ace.mgmt` whose opening then fails, because it is the destination of an `ace.clone`, or because it transitions to an Error State — `acemanagedcr` is set to 32.
Otherwise, an ACE exception raised during a management operation that does not transition the CR to an Error State leaves `acemanagedcr` unchanged: the handler either resolves the condition or sets `acemanagedcr` to 32 itself.

Internal values of `SIV`, `SIV2`, `IMPQUAL` are associated with this CR.

Values 33 and above are reserved; writing one leaves `acemanagedcr` unchanged.

NOTE: The `acemanagedcr` check that `ace.mgmt` performs (<<ACE-instruction-setst>>) detects an accidentally
interleaved management operation. A handler that must manage another CR while one is under management
saves `acemanagedcr` and the six authentication CSRs, writes 32 to `acemanagedcr`, performs its operations,
and restores the saved values (<<ACE-state-save-and-restore-order>>). Writing 32 without saving loses the in-flight `SIV`,
`SIV2` and `IMPQUAL` values, which the next `ace.mgmt` overwrites.

[[ACE-CSK-requirements]]
=== Architectural Requirements on the Context Sealing Key

The ACE unit must have a configured Context Sealing Key (CSK) before it can operate. Without an active CSK, every ACE instruction and every ACE CSR access raises `ace_exc_no_csk`, except access to the `macecsk` CSR group and the read-only identification CSRs `acemvendorid`, `acemarchid`, `acemimpid`, and `acemaxiobuflen` (<<ACE-CSR-impl-ids>>, <<ACE-CSR-acemaxiobuflen>>).  The latter CSRs remain readable to allow firmware to identify the ACE unit without having to configure it.

A CSK can be set in one of four mutually exclusive ways:

. A value programmed by M-mode through the `macecsk` CSR group (see <<ACE-CSR-macecsk>>).
. A separate secure HW block (e.g., Caliptra cite:[caliptra]), or a port to a secure HW block, which is exclusive to M-mode, is used to configure CSK values and export them using a dedicated interface based on public key encryption.
. A fixed, hardwired value, generated at manufacturing time (either per die or shared across batches).
. A value generated by a secure RBG (see <<ACE-RBG>>) at boot and not accessible to any software.

The four models have different applicability. The third and fourth are primarily suited to specialized embedded deployments: a hardwired CSK cannot be reconfigured or revoked, while a boot-generated CSK does not survive power loss and therefore cannot preserve SCCs.
Under the fourth model the CSK is shared by all harts of a well-documented subsystem of the SoC, which therefore cannot exchange SCCs with other subsystems; it survives the reset, and the fatal condition, of a single hart, and is regenerated only at power-on reset of the subsystem.

In the second model, only M-mode may request the secure hardware block configure the CSK for its hart. The request must use a handle or wrapped key.
In this model the clear key must not be exposed to software, including M-mode.
Addressing and key transport are platform-specific and outside the scope of this specification.

The ACE unit is immediately available under the third model. Under the other models, it becomes available only after a CSK has been established. A hart reset resets the associated ACE state, including a configurable CSK, and leaves the unit unavailable until the CSK is re-established (<<ACE-reset-and-m-mode-only>>); a boot-generated CSK, being shared by its subsystem, survives the reset of one of its harts.

NOTE: When the CSK is shared across devices, CCs intended to be device-bound must set `_Locality_` to include `ChipScrt` or `DevScrt`.

Except for M-mode and in first model, CSK values must _never_ be readable by software in clear.
//An implementation that permits CSK reprogramming via the `macecsk` CSR group must follow the activation rules in <<ACE-CSR-macecsk>>.

[IMPORTANT]
====
When a process is migrated between harts, its SCCs must remain importable. This requires the destination hart to use the same CSK as the source hart. The OS and hypervisor are responsible for ensuring that M-mode establishes the required CSK on the destination hart. The mechanism by which supervisor software requests this operation is platform-dependent and outside the scope of this specification.
Under the fourth model this holds within the subsystem sharing the CSK and is impossible across subsystems.
Software may migrate a process only between harts whose ACE units have equal `acemvendorid`, `acemarchid`, `acemimpid` and `acemaxiobuflen` and implement the same extensions and Algorithms, or must itself handle the differences.
====

M-mode firmware must account for the configuration model used for the CSK. Persistence mechanisms for configurable CSKs are implementation-specific. Transferring a CSK to another endpoint—such as the M-mode firmware of another device, a local TPM (for example, to preserve the CSK across suspension or host hibernation), or a cloud-based HSM—*requires* an authenticated public-key wrapping mechanism. Such a mechanism is outside the scope of this specification.

[[ACE-interaction-with-debug]]
=== Interaction with Debug Mode

All ACE state is inaccessible in Debug mode, and no ACE instruction may be
executed in it, unless an implementation-defined _authenticated-debug_ signal
is asserted.

[NOTE]
====
The natural source for the authenticated-debug signal is the authentication
interface of the Debug Module defined by the RISC-V Debug specification
(`dmstatus.authenticated`); the mapping is implementation-defined.
====

In authenticated Debug mode:

. ACE instructions and CSRs are accessible with M-mode privilege, subject to the exceptions below.
. The `macecsk` CSR group is inaccessible for both reads and writes. Entering authenticated Debug mode neither zeroizes nor replaces the CSK; the active CSK remains available to management instructions.
. A CC may be _used_ only if bit 4 of its _UsagePolicy_ field (<<ACE-Metadata>>) is set. Debug code is otherwise limited to management operations. It may export existing contexts as SCCs, provision and use contexts created for Debug mode, and restore the saved state before exiting. An existing CC may be used only if its _UsagePolicy_ explicitly authorizes Debug-mode use.

Upon entering Debug mode while the authenticated-debug signal is _deasserted_:

. All CRs are zeroized and set to _Unconfigured_.
. The ACEIOBUF is zeroized, and `aceiobuflen`, `aceiobuftop`, and `acestart` are set to zero.
. All applicable `*lcrstatus` fields and `*status.ACES` fields are accessible and set to _Dirty_.
. The software-configurable Locality Secrets — _PhysBootScrt_, _VirtBootScrt_, _MLocality_, _HLocality_, and _SLocality_ — are zeroized. Their CSRs subsequently read as zero.
. The HW Binding Group entries cannot be zeroized and are therefore _masked_. Until the next ACE unit reset, the ACE unit receives zero for each such entry instead of its hardwired value.
. The CSK is zeroized. If the CSK is hardwired, the ACE unit receives the all-zero value instead of the hardwired key until the next ACE unit reset.

[NOTE]
====
Normal execution cannot resume after entry into unauthenticated Debug mode because the ACE state has been destroyed.

Debugging that preserves ACE state therefore requires authenticated Debug mode. Recovery requires an ACE unit reset, which restores access to the hardwired HW Binding values and, under the third CSK model, the hardwired CSK, followed by re-establishment of the CSK and Locality Secrets by the privileged software stack and re-provisioning of the contexts.

Under the programmable CSK models, if M-mode re-establishes the same CSK, SCCs exported before entry into Debug mode become importable again, providing a complete recovery path through the ordinary context-saving mechanisms.
====

[[ACE-instructions-detailed]]
=== Instructions

ACE provides a number of unprivileged instructions.
This section specifies their semantics and encodings.
The `custom-1`, and `custom-2` opcodes used throughout this section are placeholders, all other fields are specified.

The notation `K{Xd}` denotes the CR whose index is held in GPR `Xd`.
`Kn|K{Xn}` indicates two alternative encodings: a 5-bit immediate CR index (`Kn`) or a CR number supplied by GPR `Xn`.
In every encoding that offers both, bit `r`, the _CR indexing mode selector_, chooses between them: `r` = 0 makes the 5-bit register field the CR index itself, `r` = 1 makes it the number of the GPR holding the index.

`%offset` denotes the immediate of the corresponding base-ISA instruction format, sign-extended to
XLEN and added to the base register: the I-type `immed12` for `ace.load`, and the S-type pair
`immed[11:5]`/`immed[4:0]` for `ace.store`, `ace.input`, and `ace.output`. The effective address of
a transfer is `X[rs1] + sext(%offset)`. For a multi-byte or resumed transfer that value is the
address corresponding to the *first* byte of the transfer, not to the byte at which the transfer
resumes: a byte offset of `acestart` is added to `X[rs1] + sext(%offset)` to form the restart
address.
The correspondence between addresses and transfer offsets is given by each instruction.

[NOTE]
====
ACE has no counterparts to the vector crypto extension's Element Group Width (EGW), Effective Element Width (EEW), or Element Group Size (EGS). Because ACE instructions such as `ace.exec` are decoupled from the operations they perform, ACE specifies only the total input or output size, `ACELEN`, in bytes. For vector operands, `ACELEN` is `VL * SEW` bits; for ACEIOBUF operands, it is `aceiobuftop * 8` bits (see <<ACE-algo-notation>>).
====

[[ACE-general-rules-instructions]]
==== General Rules

The following rules apply to all ACE instructions, unless expressly stated otherwise.

[horizontal]
[[ACE-GR-GPR-indirect, GR1]] GR1:: _Use of a GPR as indirect CR index:_
An indirect index outside [0..31] raises an illegal-instruction exception.
Using `X0` as an indirect CR index raises an illegal-instruction exception, unless this is expressly used to encode an instruction, for instance `ace.clear.all`.

[[ACE-GR-multiple-GPRs,GR2]] GR2:: _Use of multiple GPRs for longer inputs:_ A 64-bit operand is one GPR on RV64 and encoded in a pair `(X[s+1],X[s])` as `X[s+1] @ X[s]` on RV32,
and a 128-bit operand is encoded as `X[s+1] @ X[s]` on RV64 and using a GPR quartet on RV32
as `X[s+3] @ X[s+2] @ X[s+1] @ X[s]`. This holds whether the operand is a source or a destination.
The lowest register number of a pair must be even and that of a quartet a multiple of four;
otherwise an illegal-instruction exception is raised.
A pair or quartet is read, resp. written, as a whole.

GR3:: _If `X0` is used as a destination or source register, but not to index a CR,_ then
anything written to it is discarded, and it reads as zero. When the lowest register of a
pair or quartet is `X0`, no register of the group is written and the group reads as zero.

[[ACE-GR-acestart-vstart,GR4]] GR4:: ACE instructions with vector operands that use `acestart` for resumption update `acestart` and `vstart` simultaneously and independently, each according to its own semantics: both denote the same point of progress, `acestart` counting it in bytes and `vstart` in elements of the width in effect. Neither is derived from the other.
This allows the ACE unit and the vector unit to work in sync while accessing local information more efficiently, but also to explicitly “desync” the two values in certain contexts (such as in the implementation of nested CR management operations).
+
NOTE: For Forms A–C of `ace.exec` the hardware raises an illegal-instruction exception if `acestart` and `vstart` denote different points (<<ACE-CSR-acestart>>). `ace.mv` keeps the two independent by design, since its `acestart` is a CR offset that accumulates across instructions while `vstart` tracks the vector register.
+
NOTE: The uninterruptible vector-form instructions (`ace.getmdv`, `ace.restrictv`, Form C of `ace.size`, `ace.setst`, and `ace.mgmt`) do not produce `vstart` values and therefore do not consume one. Similarly to RVV 1.0 {sect}3.7, which lets an implementation either raise an illegal-instruction exception on a `vstart` value the instruction can never produce or ignore it, ACE leaves the same options to the implementation regarding `vstart`.

GR5:: The _UsagePolicy_ of the MDH determines whether certain instruction can be issued, and sometimes when, in a given privilege mode.
Furthermore, certain instructions may modify the state of the CR.
For all instructions, the authoritative table for these two properties is <<ACE-instruction-properties>>.
No instruction description restates them.
+

State.
+

+
For the restrictions on `ace.clone`, cf. <<ACE-instruction-clone>>.

+
NOTE: This mitigation is not sufficient: if the ACE unit is implemented in emulation, different versions of the firmware may have different features while running on the same hardware. It is, however, a first line of defense against accidental abuse.

[[ACE-management-operations]]
==== Provisioning, Import, and Export

_This subsection is informative._

Broadly speaking, and setting aside error handling, *Provisioning* consists of the following three steps:

. Use `ace.mgmt` (<<ACE-instruction-setst>>) to prepare a CR to be provisioned, check the validity of MDH[63:0], and load the entire MDH in the CR.
. Use `ace.load` (<<ACE-instruction-load>>) to load the rest of the provisioning information into the CR.
. Use `ace.mgmt` to complete the provisioning process and make the CR available to software.

*Importing* an SCC into a CR is similar:

. Use `ace.mgmt` to prepare a CR to accept an SCC, check the validity of MDH[63:0], and load the entire MDH in the CR.
. Move authentication data from memory to CSRs to set up the decryption and authentication process.
. Use `ace.load` to load the rest of the SCC information into the CR.
. Use `ace.mgmt` to complete the import process by authenticating and decrypting the SCC, and make the CR available to software.

*Exporting* a CR as an SCC consists of the following steps:

. Use `ace.getmd` or `ace.getmdv` (<<ACE-instruction-getmd>>) to get the MDH of the CR to be exported, in order to determine its size and allocate resources.
. Store the MDH into memory.
. Use `ace.mgmt` to prepare a CR to produce an SCC. This includes encrypting its contents and computing the authentication tag(s).
. Move authentication data from CSRs to memory.
. Use `ace.store` (<<ACE-instruction-store>>) to store the rest of the SCC to memory.
. Use `ace.mgmt` to complete the export process by restoring the CR in a form available to software.

A CR in an Error State takes shorter paths in both directions, since it is an MDH and nothing else
(<<ACE-error-state-transfer>>): its export uses no `ace.mgmt` at all, and its import is a single one.

While the CRF, as a memory device, must resist rollback attacks, individual CRs do not have to resist rollback via export and import, and cannot.
While re-importing previous CC states may allow multi-time pad attacks on modes such as CTR, XCTR, and GCM, exploiting this would require a level of control over the target software that typically also implies access to plaintext.
Re-importing a previous CC state is also desirable, however. For instance, it allows restarting an operation that failed because a payload was corrupted in transit. Adding and enforcing policies to control resumability and cover every legitimate case would overcomplicate the feature.

Lower-privileged modes may save, restore, or overwrite CRs configured by higher-privileged modes.
Hence, higher-privileged software must clear any CRs it uses before relinquishing control to lower-privileged modes.
If it uses the ACEIOBUF, `acestart`, `acemanagedcr` or the authentication CSRs while a lower-privileged context's ACE state is live, it must save that state beforehand and restore it afterwards, as at a context switch (<<ACE-state-save-and-restore-order>>), so that the lower-privileged context observes its own values and none of the higher-privileged mode's data; on return to a different context the ACEIOBUF holds that context's saved contents or, with `aceiobuflen` = 0, nothing.
When switching to a lower-privileged component, only CRs previously saved for that same component may be restored, and CRs that component was not using must be erased.
This aligns with standard context-switching hygiene.

[[ACE-instruction-load]]
==== ace.load

_Encoding_::
`ace.load` is an I-type instruction.
+
[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x2b, attr: ['custom-1'] },
    { bits:  5, name: 'context', attr: ['Kd','K{Xd}'] },
    { bits:  3, name: 'ace.load', attr: [0x0,0x1] },
    { bits:  5, name: 'Xs1' },
    { bits: 12, name: 'immed12' },
]}
....
+
`funct3` = `0b000` selects the immediate CR index in the `context` field and `funct3` = `0b001` selects the CR indexed by the GPR named by that field.

_Mnemonics_::
`ace.load{fournbsp}{nbsp}{nbsp}{nbsp}Kd|K{Xd}, %offset(Xs1)`

_Description_::
+
--
`ace.load` imports the Content of a PI or an SCC into the CR `Kd` or `K{Xd}`.
Neither `ace.load` nor `ace.store` nor `ace.mv` transfers the MDH or the authentication fields `SIV`, `SIV2` and `IMPQUAL`: the MDH is carried by `ace.mgmt` and `ace.getmd*`, the authentication fields by their CSRs.

This instruction also requires that the CR be ready to accept information (being either provisioned or imported) and that the MDH has already been loaded by passing it as a parameter in a GPR pair (quartet for RV32), resp., vector register, to the `ace.mgmt` instruction used to open the CR for provisioning or import.

If the CR's _State_ is not one of the States admitted by Rule <<ACE-SGR-ace-load-mv-allowed>> — which excludes every Complete State and the _Unconfigured_ State — or `acestart` is not a multiple of 16, an illegal-instruction exception is raised.

Neither `ace.load` nor `ace.store` nor `ace.mv` is ever used on a CR in an Error State (Rule <<ACE-SGR-error-state-CR-is-only-MDH>>, <<ACE-error-state-transfer>>).

Let `size` be the length in bytes of the serialized `Content[]` of the CR, that is the value that
`ace.csize` (<<ACE-instruction-size>>) reports for it: the `Content[]` of a PI, or `Content1[]`
together with `Content2[]` of an SCC, according to the image the CR holds (<<ACE-length-rule>>).
Since `size` must be determined by `ace.load` itself, the caller must have transferred at least the `MDH` into the CR beforehand.

Let `max_admissible` be the length of the longest image of the CR's current base type that the implementation can hold for the Algorithm: for an SCC-shaped image, `content1_size` + `content2_size` (<<ACE-instruction-size>>) at the largest _AuxDataLen_ the implementation supports; for a PI-shaped image, `pi_content_size`. Bytes of an SCC beyond it belong to an ADS that is discarded (<<ACE-SCC-import>>) and are neither read from memory nor written to the CR.
Offsets of the serialized `Content[]` at or beyond `max_admissible` hold no CR data; they read as zero through every architectural access.
`ace.load` transfers offsets `[acestart, end)` where

{fournbsp}{fournbsp}``end`` = `min(size, max_admissible)`.

Being accesses to a CR (<<ACE-Memory-Alignment>>), `acestart`, `size`, `max_admissible` and `end` are all multiples of 16 bytes.

For each _j_ from `acestart` to `end` − 1, the byte at memory address ``Xs1 + %offset + ``_j_ is loaded into the _j_-th byte of the
serialized `Content[]` of the CR.  `acestart` tracks a prefix-complete number of bytes loaded.
If `acestart` {ge} `end`, nothing is transferred.

When a system-defined format is used, the semantics of `ace.load` are implementation-dependent.
--

[[ACE-instruction-store]]
==== ace.store

_Encoding_::
`ace.store` is an S-type instruction.
+
[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x2b, attr: ['custom-1'] },
    { bits:  5, name: 'immed[4:0]' },
    { bits:  3, name: 'ace.store', attr: [0x2,0x3] },
    { bits:  5, name: 'Xs1' },
    { bits:  5, name: 'context', attr: ['Ks2','K{Xs2}'] },
    { bits:  7, name: 'immed[11:5]' },
]}
....

_Mnemonic_::
`ace.store %offset(Xs1), Ks2|K{Xs2}`
(((ACE, instruction, ace.store)))

_Description_::
+
--
Exports raw data from the `Content[]` of the CR `Ks2` or `K{Xs2}`, starting with the first byte of `Content[]`, to memory at address `%offset(Xs1)`.
`acestart` tracks the prefix-complete number of bytes stored.
Transfers follow the same constraints as those of `ace.load` (<<ACE-instruction-load>>, <<ACE-Memory-Alignment>>), with `size` and `end` as defined there. `ace.store` transfers offsets `[acestart, size)`: offsets below `end` are stored from the CR, offsets in `[end, size)` are stored as zero.
Then, for each _j_ from `acestart` to `size` − 1, the _j_-th byte of the serialized `Content[]` of the CR is stored at memory address ``Xs1 + %offset + ``_j_.
If `acestart` {ge} `size`, nothing is transferred.

As for `ace.load` (<<ACE-instruction-load>>), a _State_ not admitted by Rule <<ACE-SGR-ace-store-mv-allowed>>, or an `acestart` that violates those constraints, raises an illegal-instruction exception.
--

For the four Forms A–D above, the encodings are:

[[ACE-instruction-mv]]
==== ace.mv

The `Zklmv` subextension adds dedicated move instructions between scalar/vector registers and a CR.
The instructions in this extension are encoded as new forms of `ace.exec`:
`r` is the CR indexing mode selector.

_Mnemonics_::
+
--
The `ace.mv` instruction admits the following variants:
(((ACE, instruction, ace.mv)))

[upperalpha]
. `ace.mv  Kd|K{Xd}, Xs2` copies 128 bits of content from two or four GPRs into a CR.
. `ace.mv  Kd|K{Xd}, Vs2` copies one or more 128-bit blocks of content from a vector register into a CR.
. `ace.mv  Xd,  Ks1|K{Xs1}` extracts 128 bits of content from a CR into two or four GPRs.
. `ace.mv  Vd,  Ks1|K{Xs1}` extracts one or more 128-bit blocks of content from a CR into a vector register.
--

_Encodings_::
+
--
The hart adds the following encodings to Forms B and C of `ace.exec`. As throughout
`ace.exec`, the CR operand is encoded in `rs1`. The sub-opcode occupies the register field that the
corresponding Form of `ace.exec` leaves unused: `rd` in Form B, `rs2` in Form C.

[upperalpha]
. `ace.mv  Kd|K{Xd}, Xs2`   is encoded as `Form` = `0b01` and `rd` = `0b00001`.
. `ace.mv  Kd|K{Xd}, Vs2`   is encoded as `Form` = `0b01` and `rd` = `0b00010`.
. `ace.mv  Xd,  Ks1|K{Xs1}` is encoded as `Form` = `0b10` and `rs2` = `0b00001`.
. `ace.mv  Vd,  Ks1|K{Xs1}` is encoded as `Form` = `0b10` and `rs2` = `0b00010`.

`rs1` always specifies the source or destination CR. In Forms A and B, `rs2` specifies the source GPR or vector register.
In Forms C and D, `rd` specifies the destination GPR or vector register.
For forms B and D, the vector length must be a multiple of 16 bytes.
--
//
// In the mnemonics of variants A and B the CR is written first because it is the
// destination of the move; it is nonetheless encoded in `rs1`, not in `rd`.

_Description_::
+
--
In each variant the CR is the one named by `rs1`.

*Bound.* Transfers follow the same constraints as those of `ace.load` (<<ACE-instruction-load>>, <<ACE-Memory-Alignment>>), with `size`, `max_admissible` and `end` as defined there:
`ace.mv` transfers whole 16-byte blocks, never a part of one, and each block the variant would transfer lies either wholly below `end` or wholly at or beyond it.

* A block at an offset below `end` is transferred.
* A block at an offset at or beyond `end` is not: no CR byte is written for it; the destination
  GPR operand, resp. the corresponding elements of `Vd`, are written with zero; and `acestart` does not advance past `end`.
* If `acestart` {ge} `end`, the CR-writing variants write nothing; the CR-reading variants write their
  destination GPR operand, resp. every element of `Vd` from `vstart` to `vl` − 1, with zero; in all variants
  `acestart` is unchanged.

For each 16-byte block transferred by `ace.mv`, `acestart` advances by 16 bytes.
In vector variants, `vstart` is also used, to track progress in vector elements: for instance each 16-byte block advances `vstart` by 4 for 32-bit elements or by 2 for 64-bit elements.
If a vector transfer is interrupted, `acestart` records the total number of bytes transferred, and `vstart` identifies the first untransferred vector element for resumption.
Element _k_ of the vector operand, for _k_ from `vstart` to `vl` − 1, corresponds to byte offset `acestart` + (_k_ − `vstart`) × `SEW`/8 of the serialized `Content[]`.
If `vstart` {ge} `vl`, the instruction performs no operation and leaves `acestart` unchanged.
Writes to, resp., reads of, an offset at or beyond `end` are ignored, resp., read as zero.

The four variants are given by the following table.
For all variants, if the CR's _State_ is not one of the values in the fourth column of its row,
an illegal-instruction exception is raised. A vector variant for which `vl * (SEW/8)` is not a multiple of 16 raises an illegal-instruction exception; the V-enabled check is performed first. `vstart` must likewise point to a multiple of 16 bytes: a vector variant for which `vstart * (SEW/8)` is not a multiple of 16 raises an illegal-instruction exception. As for `ace.load` (<<ACE-instruction-load>>), so does an `acestart` that violates the constraints above.

[[ACE-mv-variants]]
.Variants of `ace.mv`
[float="center",align="center",width="100%",cols="^10%,^16%,<39%,<35%",options="header"]
|===
| `Form` | Sub-opcode | Transfer | Admissible _State_ values

| `0b01` | `rd` = `0b00001`
| The 128-bit GPR operand at `rs2` is copied into the CR at offset `acestart`.
| `ace_cfg_provisioning`, `ace_cfg_importing`, `ace_cfg_importing_partial_pi`, `ace_cfg_importing_partial_scc`

| `0b01` | `rd` = `0b00010`
| `vl` elements of `V[rs2]` are moved into the CR at offset `acestart`.
| `ace_cfg_provisioning`, `ace_cfg_importing`, `ace_cfg_importing_partial_pi`, `ace_cfg_importing_partial_scc`

| `0b10` | `rs2` = `0b00001`
| 16 bytes of the CR at offset `acestart` are copied to the 128-bit GPR operand at `rd`.
| `ace_cfg_exporting`, `ace_cfg_exporting_partial_pi`, `ace_cfg_exporting_partial_scc`

| `0b10` | `rs2` = `0b00010`
| `vl` elements of the CR at offset `acestart` are moved to `V[rd]`.

|===

If `ace.mv` and `ace.load` or `ace.store` are combined within one management operation, the value of each byte of
`Content[]` is the value last written to that offset, by whichever instruction wrote it.

[[ACE-instruction-setst]]
==== ace.setst/ace.mgmt

_Synopsis_::
Change the state of the Algorithm encoded in the CC in a CR.

_Mnemonic_::
The `ace.setst/ace.mgmt` instruction admits four Forms, namely
(((ACE, instruction, ace.setst)))
(((ACE, instruction, ace.mgmt)))
+
[upperalpha]
. `ace.{setst|mgmt} Kd|K{Xd}, #immed7{fournbsp}{nbsp}{nbsp}` with no auxiliary input.
. `ace.{setst|mgmt} Kd|K{Xd}, #immed7, Xs{nbsp}` with auxiliary input in one or two GPRs (RV64/RV32).
. `ace.{setst|mgmt} Kd|K{Xd}, #immed7, Vs{nbsp}` — in a vector register.
. `ace.{setst|mgmt} Kd|K{Xd}, #immed7, Xs{nbsp}` — in two or four GPRs (RV64/RV32).

//

_Encoding_::
`ace.setst` is an R-type instruction.
`ace.mgmt` is a synonym for `ace.setst`.
+
--
[wavedrom, ,svg]
....
{reg:[
    { bits:  7, name: 0x5b, attr: ['custom-2'] },
    { bits:  5, name: 'Kd|K{Xd}' },
    { bits:  3, name: 'ace.setst', attr: ['0    0    1','0    1    0','0    1    1','1    0    0'] },
    { bits:  5, name: 'rs1', attr: ["no aux input (0)",'Xs (64-bit)','Vs','Xs (128-bit)'] },
    { bits:  1, name: 'r' },
    { bits:  4, name: 0x0 },
    { bits:  7, name: 'immed7' },
]}
....

`r` is the CR indexing mode selector.
When `r` = 1 and the CR register is `X0`: Form A with `#immed7` = 0 is `ace.clear.all` (<<ACE-instruction-clear>>); every other combination of Form and `#immed7` is reserved (Rule <<ACE-GR-reserved-encodings>>).

The encodings of the four Forms are:
[upperalpha]
. `ace.setst` = `0b001`. `rs1` = `0b00000`.
. `ace.setst` = `0b010`.
. `ace.setst` = `0b011`.
. `ace.setst` = `0b100`.
--

// ////////////////////////////////////////////////////////////////////

_Description_::
+
--
The instruction changes the _State_ and _StateExtension_ fields of the MDH of `Kd` or `K{Xd}`.
It is used for three purposes:
[loweralpha]
. Advance from one stage of an Algorithm to another (for instance, from initialization of a hash function to data absorption and then to digest finalization); and
. Set specific state information of an Algorithm (such as elliptic curve points or private/public keys), which is intended to be orthogonal to the states mentioned in the previous point, or to provide prerequisites for entering another state that can be set independently.
. Set up a management operation and complete it.

`#immed7` is a constant from a set of admissible values.
These values include both general values, which apply to all Algorithms, as well as values specific to the Algorithm encoded in a CR.

Issuing `ace.setst` or `ace.mgmt` with certain state values may require passing an auxiliary input to the operation, which may be a 64-bit or 128-bit operand passed in one or more GPRs or a vector (group) `Vs`.

Normally, `#immed7` contains the _State_ value to be set. In most cases, after the instruction is retired, the _State_ field takes the value specified in `#immed7`.
Some states may transition to a different state automatically after completing `ace.setst`.
The latter behavior is the norm in the case of nested CR management operations.

The allowed state transitions are described in <<ACE-State-field>> and in the specifications of each Algorithm.
Note that:

* It is allowed to issue `ace.setst` instructions to the current state.
When the Algorithm needs to prevent this, it will automatically transition to a different state after completing `ace.setst`.
* If `#immed7` is zero, i.e., the value corresponding to the _Unconfigured_ state, the CR is cleared, in any Form; an auxiliary operand is ignored.
* An Error State code (see <<ACE-states-error>>) is accepted for `#immed7` in any State: in a Complete or Partial State the CR transitions to that Error State (54 and 55 to _Invalid_); in the _Unconfigured_ State the instruction performs no operation, the short import of <<ACE-error-state-transfer>> being the only way to configure a CR directly into an Error State.
* Setting an Error State does _not_ trigger an exception, even if reaching that state implicitly would normally raise one.
Further usage of the same CR—for instance, a later `ace.exec` or `ace.setst` to a valid state—performs no operation and raises no exception, leaving the _State_ field unchanged (Rule <<ACE-SGR-usage-cr-error-state>>) until software detects the Error State.

Values of `#immed7` from 65 to 127, depending on the Algorithm, may be used to change other state information in the CR, such as _StateExtension_; those the Algorithm does not define are unsupported.

Using an `#immed7` that is not supported by the architecture or by the current Algorithm causes the CR to transition to Error State _Invalid_.

When the `#immed7` value is one of 56, 57, or 58, the instruction is used to initiate provisioning, export, or import operations, as described in <<ACE-management-immeds>>; for these values it receives the MDH of `Kd` or `K{Xd}` in Form C or D, and the change to _State_ is performed after the MDH has been loaded.
The values 46, 47 and 59–62 are reserved as `#immed7` (Rule <<ACE-GR-reserved-encodings>>).

[[ACE-management-immeds]]
.Values (decimal) of `#immed7` to be used for provisioning, importing, and exporting
[float="center",align="center",width="100%",cols="^7%,<27%,<66%",options="header"]
|===
| Value | Mnemonic                  |  Description
|  56   | `ace_cfg_provisioning`    |  Prepare a CR for provisioning.
|  57   | `ace_cfg_exporting`       |  Prepare a CR for export.
|  58   | `ace_cfg_importing`       |  Prepare a CR for import.
|  63   | `ace_cfg_management_end`  |  Complete current management operation.
|===

The values of `#immed7` in <<ACE-management-immeds>> can be used in all Forms, whereby
[upperalpha]
. Form A carries no auxiliary input. Where the operation requires the MDH, Form A is a substitution (<<ACE-usage-input-output>>) and reads it from bytes [0, 16) of the ACEIOBUF, ignoring `acestart`; after the `acemanagedcr` check, Rule <<ACE-GR-iobuf-configured>> is applied, then `aceiobuftop` < 16 raises an illegal-instruction exception (Rule <<ACE-GR-vector-MDH-operand>>), both before any change to the target CR.
. In Form B, the lower 64 bits of the MDH are in the 64-bit GPR operand at `Xs` or in a GPR pair. Rule <<ACE-GR-multiple-GPRs>> applies. The instruction receives the upper 64 bits of the MDH as zero.
. In Form C, the MDH is in the 128 lowest bits of `Vs`.
. In Form D, the MDH is the 128-bit operand in two or four GPRs starting at `Xs`. Rule <<ACE-GR-multiple-GPRs>> applies.

Depending on the previous state of the CR, the actual _State_ after a non-faulting `ace.mgmt` instruction may be different:

. After `ace.mgmt`, with #immed7 = `ace_cfg_importing`, the CR's _State_ becomes
.. `ace_cfg_importing` if the data to import corresponds to a CR in a Valid State,
.. `ace_cfg_importing_partial_pi` or `ace_cfg_importing_partial_scc` if the data to import corresponds to a CR whose management operation had not been completed.
. After `ace.mgmt`, with #immed7 = `ace_cfg_exporting`, the CR's _State_ becomes
.. `ace_cfg_exporting` if the CR is in a Valid State,
.. `ace_cfg_exporting_partial_pi` or `ace_cfg_exporting_partial_scc` if the CR being exported is a CR whose management operation had not been completed.

If a CR is in an Error State, it is exported by simply copying the MDH to memory and imported by a single atomic `ace.mgmt` instruction as detailed in <<ACE-error-state-transfer>>.

We now proceed to describe the semantics of `ace.mgmt`.

First, three steps are common to every operation below and are not repeated in the description of each of them:

. `ace.mgmt` first checks that `acemanagedcr` holds either the target CR's number or 32, and raises an illegal-instruction exception if it holds any other value;
. It affects `acemanagedcr` according to the _State_ in which it leaves the target CR:
.. if that _State_ is a Configuration State, it writes the target CR's number to `acemanagedcr`;
.. if that _State_ is a Complete State, including any Error State, it writes 32 to `acemanagedcr`; and
.. if the instruction raises an exception without leaving the target CR in an Error State, `acemanagedcr` is left unchanged, or set to 32 if the zeroizing step has left the target CR _Unconfigured_: the handler either resolves the condition or sets `acemanagedcr` to 32 itself (<<ACE-CSR-acemanagedcr>>).
. `ace.mgmt` also clears `acestart` (it is the duty of software to restore `acestart` to allow interrupted management operations to be resumed).

Now we consider the specific semantics of `ace.mgmt` for each of the four operations it supports:
--
+
. *`ace.mgmt` is used to start a provisioning, resp., import process.*
+
--
Before issuing `ace.mgmt`, software must obtain the MDH. Let `ml` be this value.

NOTE: In the case we are starting an import process, `ml` must be first saved by software in its local state.
`ml` is then provided to the `ace.mgmt` operation used to complete the process in order to restore the _State_ the CR was in before the import process started.

The `ace.mgmt` operation used to start a provisioning, resp., import process must provide `ml`, and should be
Form C or D in order to provide it in full.
`ace.mgmt` then performs following operations:

.. The target CR is zeroized. Bytes of the serialized `Content[]` that a management operation has not yet written read as zero through every architectural access (`ace.store`, `ace.mv`, verbatim export).
.. If `#immed7` = `ace_cfg_importing` and `ml`._State_ is an Error State (54 and 55 are taken as _Invalid_), the CR is immediately
    fully configured in that Error State, with the entire MDH given by the auxiliary input except that _AuxDataLen_ is set to 0 (Rule <<ACE-SGR-clear-cr-content-error-state>>).
    The steps below are not applied: the CR holds only its MDH (<<ACE-cryptographic-registers>>), no Algorithm is selected for execution,
    and no CRF capacity is allocated, so this configuration cannot fail.
    Provisioning is not a way to do this: with `#immed7` = `ace_cfg_provisioning` the _State_ field of
    `ml` is ignored, as the provisioning branch below prescribes.
    The whole configuration is performed by this one instruction, which is uninterruptible (Rule <<ACE-IRR-uninterruptible-instructions>>):
    no management operation is opened, no `ace.mgmt` with `#immed7` = `ace_cfg_management_end` is needed,
    and in fact it will be an illegal instruction.
    This is the short import path of <<ACE-error-state-transfer>>.
.. If `ml` is unsupported Metadata (see <<ACE-MVR-open>>), ACE exception `ace_exc_unsupported` is raised.
.. In case of *provisioning*:
... _State_ is initially set to _Unconfigured_. This means that during the pre-flight checks described below, _State_ is _Unconfigured_ until it is successfully configured.
... _StateExtension_ and _AlgorithmUse_ are set to 0; the values in the PI are ignored.
... `AuxDataLen` must be 0. If `AuxDataLen` is not zero in the MDH of a PI,
the CR is transitioned to Error State _Invalid_ (which is a Complete State) and the instruction terminates.
.. If `ml` is invalid Metadata (see <<ACE-MVR-open>>), the CR is transitioned to Error State _Invalid_.
.. The implementation attempts to allocate CRF capacity according to the requirements of the _Algorithm_, _AlgorithmPolicy_, and _SCProtection_ fields of the MDH, as prescribed by <<ACE-length-rule>>. No other field must affect the amount of capacity required.
    If capacity allocation is not possible, ACE exception `ace_exc_out_of_memory` is raised.
.. If *provisioning*: CR._State_ is set to `ace_cfg_provisioning`;
.. If *importing*: CR._State_ depending on `ml`._State_:
... If `ml`._State_ is a Valid State, then CR._State_ is set to `ace_cfg_importing`;
... If `ml`._State_ is a Partial State, then CR._State_ is set to `ace_cfg_importing_partial_pi` or
    `ace_cfg_importing_partial_scc` according to the base type of `ml`._State_ (<<ACE-nested-state-base-types>>);
... If `ml`._State_ is _Unconfigured_, the Metadata is invalid (see <<ACE-MVR-open>>).
.. In every case above in which a check fails, that is in which an ACE exception is raised or the CR
transitions to Error State _Unsupported_ or _Invalid_, all fields of the MDH other than _State_ remain
zero and no CRF capacity is allocated; after `ace_exc_out_of_memory` the CR remains _Unconfigured_.
This does not apply to the configuration of a CR directly into an Error State from `ml`, which installs
the entire MDH.
--
+
. *`ace.mgmt` is used to start an export process.*
+
--
Let `ml` <- the MDH of the CR.
Software must first save this value in its local state to restore its _State_ when completing the export process.
`ace.mgmt` can be of any form, but any auxiliary input provided through Forms B, C, or D is ignored.
`ace.mgmt` performs following operations:

.. If `ml`._State_ is _Unconfigured_, then: an illegal-instruction exception is raised.

.. If `ml`._State_ is an Error State, then: the CR is left unchanged and no management operation is opened (Rule <<ACE-SGR-error-state-CR-is-only-MDH>>; the short export path is given in <<ACE-error-state-transfer>>).

.. If `ml`._State_ is a Valid State, then:
The instruction prepares the CR to produce an SCC.
This includes encrypting its contents and computing the authentication tag(s)
as specified in <<ACE-CC-management>>. Then, CR's _State_ is set to `ace_cfg_exporting`.
The opening `ace.mgmt` causes no changes to any field of the MDH other than _State_: an implementation that creates or changes an ADS, or uses _AlgorithmUse_, keeps _AuxDataLen_ and _AlgorithmUse_ current at all times, so that the MDH software reads before opening the export is the MDH the export authenticates.

.. If `ml`._State_ is in a Partial State (we are exporting a not fully configured CR or we are initiating a nested CR export), then:

... No encryption or authentication occurs; the contents of the CR are exported verbatim, in the same order in which they appear in the PI (for a partially provisioned CR) or in the SCC (for a partially imported CR, or a CR previously prepared for export whose export process was itself interrupted).
`acesivl`/`acesivh`, `acesiv2l`/`acesiv2h` and `aceiql`/`aceiqh` are not written.

... The CR's _State_ is set to `ace_cfg_exporting_partial_pi` or `ace_cfg_exporting_partial_scc`
according to its base type (<<ACE-nested-state-base-types>>).
+
These values of CR._State_  are the value on which `ace.store` (<<ACE-instruction-store>>) and the CR-reading variants of `ace.mv` (<<ACE-instruction-mv>>) are gated, so no export can proceed until CR._State_ is set.
--
+
. *`ace.mgmt` is issued with `ace_cfg_management_end`*:
+
--
`ace.mgmt` with immediate `ace_cfg_management_end` reads first the MDH of the target CR.
Depending on whether MDH._State_ is

* `ace_cfg_provisioning`,
* `ace_cfg_importing`, `ace_cfg_importing_partial_pi`, `ace_cfg_importing_partial_scc`, resp.
* `ace_cfg_exporting`, `ace_cfg_exporting_partial_pi`, `ace_cfg_exporting_partial_scc`,

the instruction will proceed to complete a provisioning, importing, resp., exporting process, as are described next.

When completing an import or an export, the auxiliary operand `ml` is consumed only for its _State_ field,
which restores the CR's _State_ to the value that field held when the management operation was started.
No other field of the MDH is written from `ml`.

If CR.MDH._State_ is `ace_cfg_importing` or `ace_cfg_exporting`, `ml`._State_ must be a Complete State;
if it is one of the four nested States, `ml`._State_ must be a Configuration State of the same base type (<<ACE-nested-state-base-types>>).
Otherwise the instruction raises an illegal-instruction exception.

NOTE: When completing the import, resp., export of a SCC, resp, CR in a Complete State, the authenticity
of the CR will be checked anyway after replacing CR.MDH._State_ with ml._State_, and so the likelihood that a wrong _State_ will be accepted is vanishingly small.
This check is therefore a defense-in-depth measure, and we add it because the complexity of its logic is negligible.
--
+
.. *`ace.mgmt` is used to complete a provisioning process.*
+
--
`ace.mgmt` does not need a saved MDH from the start of the provisioning process, hence if a Form B, C, or D, was used in place of Form A, the auxiliary input is simply ignored.

Completing a provisioning requires _AuxDataLen_ = 0; if CR.MDH._State_ is `ace_cfg_provisioning` and _AuxDataLen_ {ne} 0, the CR transitions to Error State _Invalid_ and the instruction terminates.

The operation makes the provisioned CR available to software by

... For _KeyType_ = 1, applying the SKS narrowing of <<ACE-system-keys>>;
... Performing any necessary readjustment of the CR's content to turn it into the format internally consumed by the ACE Unit; and
... Setting _State_ to _Ready_, and _StateExtension_ and _AlgorithmUse_ to 0.

A process may be preempted during a CR's provisioning.
Only the information in the original PI is exported, and it remains unencrypted.
The configuration of the CR may require random generation of some material which is intended to remain secret. This material must be generated only at this stage (i.e., when `ace.mgmt` is used to complete a provisioning process). The same applies to key material retrieved from a System Key Store, and any value derived, expanded, or re-shared from it.
This guarantees that such material is not leaked.
--
+
.. *`ace.mgmt` is used to complete an import process.*
+
--
The software uses Form B, C, or D of `ace.mgmt` to pass along the value of `ml` saved when the import process was started.
The image authenticated as ``AD[0]`` is the MDH held in the target CR — the image carried in the SCC and
loaded when the import was started — with its _State_ field restored from `ml` (<<ACE-SCC-import>>).

The semantics are:

... If `ml`._State_ is a Complete State (we are importing the export of a fully configured CR)
.... CR.MDH._State_ is set to `ml`._State_.
.... The ACE unit decrypts and authenticates the CR's content.
.... If authentication fails, the target CR is transitioned to Error State _Authentication Failed_. No exception is raised.
.... The ACE unit performs any necessary readjustment of the CR's content to turn it into the format internally consumed by the ACE Unit.
This makes the CR available to software.
... If `ml`._State_ is not a Complete State (we are either importing the export of a not fully configured CR or a nested CR export):
.... CR.MDH._State_ is set to `ml`._State_.
--
+
.. [[ace-mgmt-completes-export,Use of ace.mgmt to complete an export process]]*`ace.mgmt` is used to complete an export process.*
+
--
Software uses Form B, C, or D of `ace.mgmt` to supply the MDH value saved when the export process began.

Let `ml` be this auxiliary input.
Then:

.. The CR's _State_ is set to `ml`._State_.
.. If `ml`._State_ is a Complete State (i.e., including Error States), the instruction
restores the internal state of the CR to the clear format it was in when the export process was initiated and allows software to access it:
... The contents are decrypted and authenticated as when completing an import, with the MDH held in the CR as `AD[0]`.
... If the `SIV` check fails, the CR transitions to Error State _Authentication Failed_ and the instruction terminates; no exception is raised.
+
NOTE: An implementation may instead restore the clear contents from an internal copy only if the outcome is identical: the copy is usable only while the CR, its MDH, `acesivl`/`acesivh` and, when _AuxDataLen_ ≥ 2, `acesiv2l`/`acesiv2h` and `aceiql`/`aceiqh` still hold the values written by the opening `ace.mgmt`, and `ml`._State_ equals the _State_ at that time.  The specification does not define any internal mechanisms by which an implementation can achieve this.

.. If `ml`._State_ is not a Complete State, no further changes to the CR's contents are made.
--
+
. *If `ace_cfg_management_end` is issued when the target CR's _State_ is _Unconfigured_ or a Complete State* (i.e., no management operation open on the target CR), the instruction raises an illegal-instruction exception.

//

[NOTE]
====
The definition of `ace.mgmt` allows an interrupted import to resume on another hart and even on a different implementation of the ACE unit, provided the target supports the Algorithm encoded in the SCC.
Software must allow resumption of interrupted configuration or export procedures while remaining binary-compatible across implementations that may or may not support it.
A context-switch handler can always force a restart by clearing partially provisioned or imported CRs at context save and restore time, and, with the care described in <<ACE-resumability>>, partially exported ones.
Such clearing must be the exception, however:
Since an SCC can span several kilobytes, a handler that unconditionally clears partially provisioned or imported CRs at every context switch may prevent a long management process from ever completing.
The ACE ISA has been co-designed with the CR management sequences in <<ACE-management-code-snippets>> to support resumption, nested context switching and lazy SCC loading.
====

==== ace.getmd*

_Synopsis_::
Export the MDH of a CR.

_Mnemonics_::
+
--
[%hardbreaks]
`ace.getmdl{nbsp}Xd, Ks|K{Xs}`(((ACE, instruction, ace.getmdl)))
`ace.getmd{nbsp}{nbsp}Xd, Ks|K{Xs}`(((ACE, instruction, ace.getmd)))
`ace.getmdv{nbsp}Vd, Ks|K{Xs}`(((ACE, instruction, ace.getmdv)))

_Encoding_::
+
--
`ace.getmd` is an R-type instruction and its encoding shares opcode and `funct3` with `ace.exec`, but `funct2` is set to `0b11`.

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x5b, attr: ['custom-2'] },
    { bits:  5, name: 'Xd' },
    { bits:  3, name: 0x0, attr: ['ace.exec'] },
    { bits:  5, name: 'rs1', attr: ['Ks|K{Xs}'] },
    { bits:  5, name: 0x00  },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'r' },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'h' },
    { bits:  1, name: 'v' },
    { bits:  2, name: 0x3, attr: ['funct2'] },
]}
....

`r` is the CR indexing mode selector.

If bit `h` (bit 28) is 0, the instruction is `ace.getmdl`; if `h` is 1, it is `ace.getmd`.

If bit `v` (bit 29) is 0, the result is written to a GPR (GPR pair for RV32).
If `v` is 1, the entire MDH is written to the lowest 128 bits of a vector register (group).
In this case, bit `h` must be 0; the combination `v` = `h` = 1 is reserved (Rule <<ACE-GR-reserved-encodings>>).

_Description_::
+
--
If the CR has _State_ = _Unconfigured_, these instructions return an all-zero MDH.

On RV64:

* `ace.getmdl` copies bits [63:0] of the MDH of CR `Ks` or `K{Xs}` into GPR `Xd`.

* For `ace.getmd` the destination is a GPR pair. The instruction copies bits [63:0] of the MDH of CR `Ks` or `K{Xs}` into GPR `Xd` and bits [127:64] of the MDH of the CR into GPR `X[d+1]`.

* `ace.getmdv` (vector register output version) copies bits [127:0] into vector register `Vd`.

On RV32:

* The destination is the GPR pair `X[d+1] @ X[d]` for `ace.getmdl`, the GPR quartet `X[d+3] @ X[d+2] @ X[d+1] @ X[d]` for `ace.getmd`.

* The semantics of `ace.getmdv` are the same as on RV64.
--

[[ACE-instruction-restrict]]
==== ace.restrict*

_Synopsis_::
Restrict the policies encoded in a CC in a CR.

_Mnemonic_::
+
--
[%hardbreaks]
`ace.restrictl{nbsp}{nbsp}Kd|K{Xd}, Xs1`(((ACE, instruction, ace.restrict)))
`ace.restricth{nbsp}{nbsp}Kd|K{Xd}, Xs1`
`ace.restrictv{nbsp}{nbsp}Kd|K{Xd}, Vs1`
--

_Encoding_::
+
--
`ace.restrict` is an R-type instruction.
The encoding shares opcode and `funct3` with `ace.exec`, but `funct2` (i.e., the two msbs of `funct7`) is `0b01`.
[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x5b, attr: ['custom-2'] },
    { bits:  5, name: 'Kd|K{Xd}' },
    { bits:  3, name: 0x0, attr: ['ace.exec'] },
    { bits:  5, name: 'Xs1' },
    { bits:  5, name: 0x0 },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'r' },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'h' },
    { bits:  1, name: 'v' },
    { bits:  2, name: 0x1, attr: ['funct2'] },
]}
....

`r` is the CR indexing mode selector.

If bit `h` (bit 28) is 0, the instruction is `ace.restrictl`; if `h` is 1, it is `ace.restricth`.

If bit `v` (bit 29) is 0, the input is taken from a GPR (GPR pair for RV32), and the instruction is `ace.restrictl` or `ace.restricth` depending on `h`.
If bit `v` is 1, bit `h` must be 0, and the input is taken from the lowest 128 bits of a vector register (group).
The combination `v` = `h` = 1 is reserved (Rule <<ACE-GR-reserved-encodings>>).
--

// comment

_Description_::
+
--
`ace.restrictl` modifies the fields _AlgorithmPolicy_ and _SCProtection_ in bits [63:0] of the MDH of the CR.

`ace.restricth` modifies fields _Locality_, _UsagePolicy_, _ExpirationDate_, and possibly _AlgorithmUse_ in bits [127:64] of the MDH of the CR.

`ace.restrictv` applies the rules of `ace.restrictl` to `Vs1[63:0]` and those of `ace.restricth` to `Vs1[127:64]` as a single instruction under the same all-or-nothing rule.

Let MDH be the MDH of the CC in the destination CR.

On RV64, the semantics of the instructions are:

* For `ace.restrictl`, `Xs` follows the format of bits [63:0] of the MDH,
and for `ace.restricth`, `Xs` follows the format of bits [127:64] of the MDH.

* Only the fields _AlgorithmPolicy_, _SCProtection_, _Locality_, _UsagePolicy_, _ExpirationDate_
and _AlgorithmUse_ of MDH can be modified, and only where the corresponding field of `Xs` is
non-zero. How each one is modified is given by the rules below, which in most cases narrow the
field rather than overwrite it. A zero field of `Xs` leaves its counterpart in MDH unchanged,
and every other field of `Xs` is ignored.

* Every check, including those that transition the CR to _Invalid_, is performed before the capacity allocation of a _SCProtection_ request, as in `ace.mgmt` (<<ACE-instruction-setst>>), and all modifications of the MDH are applied together after every check has passed. The validity (see <<ACE-Metadata-validity>>) of the changed fields is evaluated on the MDH that would result; fields the instruction does not change are not re-examined. A subfield of `Xs`._Locality_ that is zero, or equal to the corresponding subfield of MDH._Locality_, requests no change and is accepted.

* Applying restrictions to _AlgorithmPolicy_:

** If the Algorithm configured in the CR does not make use of the field _AlgorithmPolicy_,
  or, for the encoded value of MDH._Algorithm_, _AlgorithmPolicy_ is used to encode an extension of _Algorithm,
  then `Xs`._AlgorithmPolicy_ must be zero as well,
  else the CR transitions to Error State _Invalid_.

** If the Algorithm configured in the CR makes use of the field _AlgorithmPolicy_ to encode algorithm-specific function permissions, then the following holds:
  If `Xs`._AlgorithmPolicy_ is non-zero, then MDH._AlgorithmPolicy_ {leftarrow} `Xs`._AlgorithmPolicy_, provided every bit set in the new value was set in the old one. This means that no functions of an Algorithm that are disabled can be enabled.
 Otherwise, or if the new value is invalid for any other reason for the Algorithm (see <<ACE-Metadata-validity>>), the CR transitions to Error State _Invalid_.

** If the CR's current state is _only_ allowed while performing an operation currently
  permitted by MDH._AlgorithmPolicy_, a change to _AlgorithmPolicy_ that would
  disable that operation causes the CR to transition to Error State _Invalid_.

* If `Xs`._SCProtection_ is zero, MDH._SCProtection_ is _not_ changed. A non-zero
  `Xs`._SCProtection_ is a _request_ to raise the side-channel protection of the CC to
  that level, and is subject to the following rules.

** Side-channel protection may not be downgraded.
   Any such request causes the CR to transition to Error State _Invalid_.
   The ordering of the implementation-custom level (6 or 7) relative to the architected levels is implementation-defined.

** The request may fail because a stronger SCA protection level may require more CRF capacity.
   If the implementation cannot allocate that capacity,
   ACE exception `ace_exc_out_of_memory` is raised.

* If `Xs`._Locality_ is non-zero, it is used to update MDH._Locality_, subject
   to the following rules, applied independently to each subfield of the
   _Locality_ field (<<ACE-locality-indexes>>), the subfields being bits [1:0], [3:2], [5:4], and each of bits 6, 7 and 8:

  . If a subfield of MDH._Locality_ was zero, the corresponding subfield of `Xs`._Locality_ is its new value.
  . If a subfield of MDH._Locality_ was non-zero, its Locality may be replaced with a stricter one only within the two HW Binding chains:
   ** _SiPScrt_ {rightarrow} _ChipFamScrt_, _ChipScrt_; _ChipFamScrt_ {rightarrow} _ChipScrt_; and
   ** _OEMScrt_ {rightarrow} _ProdScrt_, _DevScrt_; _ProdScrt_ {rightarrow} _DevScrt_.
  . A non-zero Boot Session Group or SW Filter Group subfield cannot be changed.
  . Any other change, and in particular generalizing (i.e., weakening) a Locality, is not permitted: attempting to do so causes the CR to transition to Error State _Invalid_.
  . Once the _Locality_ field has been modified,
  when the CR is exported, it will use the new Locality values to tweak the export algorithm.

* Applying restrictions to _UsagePolicy_:

** A zero in any of the bits `Xs`._UsagePolicy_ means that the corresponding policy is _not_ changed.

** A one in any of the bits `Xs`._UsagePolicy_ makes the corresponding policy stricter.
  For bits 0 to 3, which disallow use by a mode when set, the corresponding bit of
  MDH._UsagePolicy_ is set to 1, so that usage by that mode is no longer allowed.
  For bit 4, which _grants_ use in Debug when set, the corresponding bit of
  MDH._UsagePolicy_ is instead cleared to 0, withdrawing that grant.
+
In both cases a one in `Xs`._UsagePolicy_ can only remove a permission and never add
one, so `ace.restrict` cannot be used to widen the set of modes that may use a CC.

* A request that would set a field to an unsupported or invalid value (see <<ACE-Metadata-validity>>)—including a non-zero `Xs`._ExpirationDate_ without `Zklexpire`, or a _Locality_ subfield naming an unconfigured entry—causes the CR to transition to Error State _Invalid_.

* Applying restrictions to _ExpirationDate_:

** If `Xs`._ExpirationDate_ is zero, the corresponding policy in MDH._ExpirationDate_ is _not_ changed.

** If MDH._ExpirationDate_ = 0, or `Xs`._ExpirationDate_ {le} MDH._ExpirationDate_, then MDH._ExpirationDate_ ← `Xs`._ExpirationDate_; otherwise the CR transitions to Error State _Invalid_.

* MDH._AlgorithmUse_ is changed only if the Algorithm in the CR defines it as writable by
  `ace.restrict*`, and then only as that Algorithm prescribes. Where the Algorithm uses the field
  to hold state — a transfer or output counter, as in <<ACE-PQC-ML-KEM>>, <<ACE-PQC-ML-DSA>> and
  <<ACE-ECC>>, or a squeeze counter, as in <<ACE-Ascon-Hash256>> — `Xs`._AlgorithmUse_ must be
  zero, else the CR transitions to Error State _Invalid_. Permitting software to rewind or advance
  such a counter would let it reload part of a key field or skip the checks performed when a field
  finishes loading.

On RV32, the input is a register pair `X[s]` and `X[s+1]`, and
  `X[s+1] @ X[s]` replaces `Xs` in the RV64 description.

`ace.restrictl/ace.restricth/ace.restrictv` may be used in any Complete State; in the _Unconfigured_ State it performs no operation, and in a Configuration State Rule <<ACE-SGR-usage-cr-config-state>> applies. Care is required:
Disabling a currently permitted operation, such as encryption or signature generation, while in a State corresponding to the disabled operation causes the CR to transition to Error State _Invalid_.

`ace.restrict*` is exempt from usage control because every change it can make narrows the CC: policies are only removed, side-channel protection only strengthened, Localities only tightened, and an expiration date only brought forward.
Permitting it in a mode that the CC's _UsagePolicy_ excludes therefore cannot grant that mode any capability it did not already have.
This mirrors `ace.clear` (<<ACE-instruction-clear>>), which is likewise not usage-controlled and is a strictly stronger denial primitive.
--

[NOTE]
====
This instruction enables several practical use cases:

*   Enabling side-channel protection when supported by the microarchitecture,
    even if the original CC was not configured with it.
*   Allowing privileged code to give a CC to several processes in a
    fine-grained manner. This can be achieved by cloning the CR and customizing
    the Localities for each clone.
*   Similarly, enabling privileged code to split a CC capable of both
    encryption and decryption into two CCs, one only capable of encryption and
    the other only capable of decryption, thereby creating a one-way channel
    between processes.

The ability to perform such customizations saves both time and computational
resources by avoiding additional round-trips to trusted environments.

_Description_::
+

Clones the source CR `Ks` (or the CR indexed by `Xs`) into the destination CR `Kd` (or the CR indexed by `Xd`):

* If source and destination are the same CR the instruction performs no operation, even if the CR is _Unconfigured_ or in a Configuration State, which is excepted from Rule <<ACE-SGR-usage-cr-config-state>>.

I suggest something similar to "Architect a generic KDF" where the output of one Algorithm, say in CR1, that would be produced by the output of an ace.exec, can be piped directly to the input of a second CR2.
So, instead of, say,  ace.exec V1, CR1, {optional INPUT1} followed by ace.exec {optional OUTPUT2}, CR2, {INPUT1}, we would just have ace.derive CR2, CR1, length.
We more flexibility for the other cases. For instance if we are piping a secret value indexed by  index i   from CR1 into a secret value indexed by index j into CR2, we would have ace.derive CR2, CR1, (length, i, j) and we have to encode the tuple somehow in the aux input, like length << 32 | i << 16 | j.
Finally, we need the case where we pipe the output of an ace.exec on CR1 into a secret in CR2 and the case of a secret in CR1 into an input of CR2. These are four cases, and sadly there is no encoding space left in ace.derive. We reduce ace.derive to one form only, with an aux input in a GPR only.
Summarizing:
* Form = 0 => pipe secret into secret, encode GPR as length << 32 | i << 16 | j on RV64 (on RV32 it would be s2 even, X[s2] contains  i << 16 | j X[s2+1] contains length).
* Form = 1 => pipe ace.exec CR1 output into secret. Encode GPRs in the same way, but i is now zero.
* Form = 2 => pipe CR1 secret into ace.exec CR2 input. Encode GPRs in the same way, but j is now zero.
* Form = 3 => pipe ace.exec CR1 output into ace.exec CR2 input. Encode GPRs as above.

In all cases, the length determines the amount of data that is transferred.

A fixed size output from CR1 (such as a secret) is transferred in full, or truncated, or zero padded, depending on the length.
A variable size size output from CR1 (such as output from ace.exec in case it can be repeated, such as squeezing a XOF,) may be truncated at the end if length is between multiples of the output sizes).

A fixed size input to CR2 (such as a secret) is received in full, or truncated by ignoring it after a certain point, or zero padded, depending on the length.
A variable size size input to CR2 (such as multiple inputs to ace.exec in case it can be repeated, such as absorbing data) may be truncated at the end if length is between multiples of the output sizes, but it can also be left open if, for instance, it is provided to a process_VLI state, in which case the called can complete it by adding their own padding with additional ace.exec calls.

[[ACE-instruction-derive]]
==== ace.derive

_Synopsis_::
Pipe data from one CR into another without exposing it to software.

_Mnemonic_::
`ace.derive Kd|K{Xd}, Ks1|K{Xs1}, Xs2`
(((ACE, instruction, ace.derive)))

_Encoding_::
+
--
The encoding is almost identical to `ace.clone`, with bit 27 set to 1 instead of 0.
The instruction is an R-type instruction.

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x5b, attr: ['custom-2'] },
    { bits:  5, name: 'Kd|K{Xd}' },
    { bits:  3, name: 0x0, attr: ['ace.exec'] },
    { bits:  5, name: 'Ks1|K{Xs1}' },
    { bits:  5, name: 'Xs2' },
    { bits:  2, name: 'R' },
    { bits:  1, name: 0x1 },
    { bits:  2, name: 'Form' },
    { bits:  2, name: 0x2, attr: ['funct2'] },
]}
....

Bits [26:25], i.e., field `R`, are encoded as for `ace.clone` (<<ACE-instruction-clone>>).

The auxiliary input is always a GPR: `ace.derive` has no form without one and no vector form.

Bits [29:28], i.e., field `Form`, select which endpoint is used on each side:

[[ACE-derive-forms]]
.Endpoints selected by the `Form` field of `ace.derive`
[float="center",align="center",width="100%",cols="^10%,<40%,<40%",options="header"]
|===
| `Form` | Source, in CR `Ks1`{nbsp}\|{nbsp}``K{Xs1}`` | Destination, in CR `Kd`{nbsp}\|{nbsp}``K{Xd}``
|  `00`  | Exportable field `i`                        | Importable field `j`
|  `01`  | Output of an `ace.exec` (`i` is zero)       | Importable field `j`
|  `10`  | Exportable field `i`                        | Input of an `ace.exec` (`j` is zero)
|  `11`  | Output of an `ace.exec` (`i` is zero)       | Input of an `ace.exec` (`j` is zero)
|===
--

_Description_::
+
--
`ace.derive` moves `length` bytes from an endpoint of the source CR to an endpoint of the
destination CR. The data never becomes visible to software: it is the mechanism by which the output
of one Algorithm becomes the input, or the key, of another.

The source and the destination CRs must be different.

The auxiliary GPR carries the transfer length and the two field indices:

* On RV64, `Xs2` = `length << 32 {vvert} i << 16 {vvert} j`.
* On RV32, the auxiliary operand is the GPR pair `X[s2+1] @ X[s2]`, subject to Rule <<ACE-GR-multiple-GPRs>>, with
  `X[s2]` = `i << 16 {vvert} j` and `X[s2+1]` = `length`;

`length` is a number of bytes. The index `i` selects an _exportable_ field of the source CC and the
index `j` an _importable_ field of the destination CC. Each Algorithm defines the indices of its own
exportable and importable fields; they start at 1, so that the value 0 — used on whichever side
carries an `ace.exec` endpoint instead — never names a field. An index that names no such field of
the corresponding Algorithm causes that CR to transition to Error State _Invalid_.

An _exportable field_ is a field that the Algorithm makes available as the source of an `ace.derive`; a field from the System Key Store is never exportable.
A field the Algorithm does not also return to software through `ace.exec` may be the source of a `Form` `00` transfer only; naming it as the source of a `Form` `10` transfer transitions the destination CR to Error State _Invalid_ and transfers nothing.

An _importable field_ is a field that the Algorithm makes available as the destination of an `ace.derive`; it is never returned to software through `ace.exec`, and a field configured by a System Key Identifier is never importable.

Whether the MDH of the destination is constrained by that of the source is a property of the source Algorithm and of the endpoint: for each exportable field and for each `ace.exec` output it makes available as the source of an `ace.derive`, the Algorithm's description states which constraints, if any, apply to the _UsagePolicy_, _Locality_, _ExpirationDate_ and _SCProtection_ of the destination CR, and may make them depend on the source's MDH.
A violation transitions the destination CR to Error State _Invalid_ and transfers nothing.
Where the description states none, the destination is unconstrained.
No constraint applies where the source data is also freely obtainable through `ace.exec` and the destination field or state accepts arbitrary software-supplied input through `ace.exec`, as when the output of a XOF is squeezed into a state implemented by Subalgorithm `process_VLI` (<<ACE-process-VLI>>).

// Each exportable field is designated _public_—a value the Algorithm also returns to software through `ace.exec`—or _secret-only_.
// A secret-only field may be the source of a `Form` `00` transfer, or of a `Form` `10` transfer whose destination state the destination Algorithm designates as a _secret-input_ state, one whose input is consumed only as key material and never transformed into an output; any other `Form` `10` transfer from a secret-only field transitions the destination CR to Error State _Invalid_ and transfers nothing.
// When the source is a secret-only field, the destination CR must satisfy: MDH._SCProtection_ not lower than the source's, under the ordering of `ace.restrictl`; bits 0–3 of MDH._UsagePolicy_ a superset of the source's, and bit 4 set only if set in the source; MDH._Locality_ one that `ace.restricth` could produce from the source's; if the two _Algorithm_ fields are equal, MDH._AlgorithmPolicy_ one that `ace.restrictl` could produce from the source's; and, if the source's _ExpirationDate_ is non-zero, a non-zero _ExpirationDate_ not later than it.
// Otherwise the destination CR transitions to Error State _Invalid_ and no data is transferred.

`length` = 0 transfers nothing and, if the preflight checks below pass, changes no state.

`ace.derive` endpoints behave exactly as the corresponding `ace.exec` instructions would:
For `Form` `01` and `11` the source CR advances as if the `ace.exec` producing that output had been
issued on it; and for `Form` `10` and `11` the destination CR advances as if the `ace.exec`
consuming that input had been issued on it. A single `ace.derive` with `Form` `11` therefore
replaces the pair of instructions it collapses, with the same state effects on both CRs, but without
exposing the transferred data to software. The main restriction is that `ace.derive` must replace
`ace.exec` instructions that do not set `acestart` or do it in a synchronized way,
i.e., the block size of the destination must divide the block size `b` of the source, and `length`
must be a multiple of `b`, unless the destination State is one implemented by Subalgorithm `process_VLI`
(<<ACE-process-VLI>>), in which case `length` is unconstrained and the last unit is truncated as described below.

How `length` relates to the size of each endpoint depends on whether that endpoint's size is fixed or
variable:

* A *fixed-size source*, such as a secret field, is transferred in full, truncated, or zero-padded
  to `length`. There is no mechanism to transfer only a partial segment of the source.
* A *variable-size source*, such as the repeatable output of an `ace.exec` — squeezing a XOF, for
  instance — is produced until `length` bytes have been delivered, and is truncated inside a unit
  of output if `length` is not a whole multiple of that unit. The transfer respects the granularity
  offered by the source algorithm in the following way: if the length of the transfer is not a multiple
  of that granularity, the last output of what would be an `ace.exec` is truncated and the unused
  part of the output is discarded.
* A *fixed-size destination*, such as a secret field, is filled in full, or truncated by ignoring
  the data beyond its end, or zero-padded, according to `length`.
* A *variable-size destination*, such as the repeatable input of an `ace.exec` — absorbing data,
  for instance — consumes up to `length` bytes and is truncated inside a unit in the same way. Such
  a destination may also be left *open*: if it is a state implemented by Subalgorithm `process_VLI`
  (<<ACE-process-VLI>>), the caller may continue supplying data to it with ordinary `ace.exec`
  instructions after the `ace.derive`, and complete it in the usual way.

Preflight checks: `ace.derive` performs the following checks, in order before any data movement or state change.

. Decode both CR indices; illegal-instruction if either is invalid (Rule <<ACE-GR-GPR-indirect>>).
. Raise illegal-instruction if the resolved indices are equal.
. If either CR is _Unconfigured_, raise illegal-instruction (Rule <<ACE-SGR-transition-to-from-unconfigured>>).
. If either CR is in an Error State, perform no operation (Rules <<ACE-SGR-gate-order>> and <<ACE-SGR-usage-cr-error-state>>).
. If either CR is in a Configuration State, raise ACE exception `ace_exc_privilege_violation`
(Rule <<ACE-SGR-usage-cr-config-state>>).
. Evaluate _UsagePolicy_, then _ExpirationDate_, of both CRs (Rule <<ACE-SGR-gate-order>>); on any violation,
raise the corresponding exception or perform the corresponding transition (for expiration, transition each expired CR to `ace_state_expired`).
. Validate _State_ and _StateExtension_ of both CRs against the endpoints
selected by Form; the source CR must be in a state that allows it to output values
(this can be either that it contains information that can be transferred or that it
accepts Form C `ace.exec` instructions), and the destination CR be in a state that allows it to receive values
(this means that it contains provisionable fields, or that it
accepts Form B `ace.exec` instructions); on failure, transition only the offending CR to _Invalid_
and leave the other CR untouched, or both if both offend.
. Validate `i`, `j` against the Algorithms' field tables, `length` against the
  block-size rule, the source field against the exportability rule above, and the destination
  against the constraints the source Algorithm defines for that endpoint; on violation,
  transition the offending CR to _Invalid_, leave the other CR untouched, or both if both offend.

Only then begin the transfer; on a mid-transfer fault, commit the prefix per Rule <<ACE-IRR-which-resumable-instructions>>.

Whether the transferred data is deterministic depends entirely on the Algorithm in the source CR:
`ace.derive` itself performs no key derivation and draws no random material.

If `ace.derive` writes a key of the destination CR, that CR must be in State _Ready_;
if it is not, the destination CR transitions to Error State _Invalid_ and no data is transferred.

Both CRs are endpoints of a usage operation. The _UsagePolicy_ of each is evaluated independently
against the current privilege mode, as is its expiration; an Error State on either of them makes the
instruction a no-op (Rule <<ACE-SGR-gate-order>>).
--

Examples of piping between Cryptographic Contexts with ace.derive:::

. *Form `11` — output of one `ace.exec` into the input of another.* The pair

`{fournbsp}{fournbsp}` `ace.exec V1, K1, {INPUT}` +
`{fournbsp}{fournbsp}` `ace.exec {OUTPUT}, K2, V1`

leaks the intermediate value `V1` to software. The single instruction

`{fournbsp}{fournbsp}` `ace.derive K2, K1, Xs2` `{nbsp}{nbsp}` with `Form` = `11`

performs the same two operations, advancing both state machines exactly as the two `ace.exec`
instructions would, and the intermediate value never leaves the ACE unit.

. *Form `01` — output of an `ace.exec` into a secret.* A key agreed or derived by the Algorithm in
`K1` becomes a key of the CC in `K2`. `K2` is provisioned beforehand in the ordinary way — a CC
whose _KeyType_ selects a randomly generated key serves as a placeholder — and must be in State
_Ready_; the `ace.derive` then overwrites its secret field `j`.

. *Form `00` — field into secret.* An exportable field of one CC is copied into a secret field of
another, for instance to give two CCs with different _UsagePolicy_ or _Locality_ the same
underlying key. Both indices are significant here. This is the shape used by <<ACE-PQC-ML-KEM>>.

. *Form `10` — secret into the input of an `ace.exec`.* A stored secret is absorbed by the Algorithm
in `K2`, for instance as the key of a MAC or as a customization string, without being materialized
in a register.

In every case `length` gives the number of bytes transferred, and the truncation, zero-padding and
open-destination rules of <<ACE-instruction-derive>> apply.

[[ACE-instruction-size]]
==== ace.size/ace.csize/ace.avail

_Synopsis_::
Return the total size of a memory buffer that would be needed to store the data of a PI, SCC, or Partially Configured Cryptographic Context (PCCC, <<ACE-data-formats>>, the equivalent of an SCC for incompletely managed CRs) in bytes. `ace.size` returns 0 in case of error (such as unsupported Algorithm or invalid MDH).

_Mnemonic_::
+
--
There are three Forms of the `ace.size` instruction:
(((ACE, instruction, ace.size)))

[upperalpha]
. `ace.size/ace.csize  Xd, Ks|K{Xs}` - Size from a context.
. `ace.size/ace.csize  Xd, Xs` - Size from MDH[63:0] in one (RV64) or two (RV32) GPRs.
. `ace.size/ace.csize  Xd, Vs` - Size from MDH in one vector register.
--

_Encoding_::
+
--
The encoding shares opcode, `funct3`, and `funct2` (the two msbs of `funct7`) with `ace.exec`, but with bit 27 equal to 1.

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x5b, attr: ['custom-2'] },
    { bits:  5, name: 'Xd' },
    { bits:  3, name: 0x0, attr: ['ace.exec'] },
    { bits:  5, name: 'Ks/K{Xs}/Xs/Vs' },
    { bits:  5, name: 0x0 },
    { bits:  1, name: 'q' },
    { bits:  1, name: 'r' },
    { bits:  1, name: 0x1 },
    { bits:  2, name: 'F' },
    { bits:  2, name: 0x0, attr: ['funct2'] },
]}
....

The `F` field and the `r` bit may assume the following values:

* `F` = `0b00`, `r` = `0` {implies} Form A: Size/availability from a context given as `Ks`.
* `F` = `0b00`, `r` = `1` {implies} Form A: Size/availability from a context given indirectly as `K{Xs}`.
* `F` = `0b01`, `r` = `0` {implies} Form B: Size/availability from MDH in one (RV64) or two (RV32) GPRs.
* `F` = `0b10`, `r` = `0` {implies} Form C: Size/availability from MDH in a 128-bit vector register.

For `ace.size`, `q` is `0`, and for `ace.csize`, `q` is `1`.
Bit `q` is `0` if we are evaluating the total size of an SCC, or `1` for only the `Content[]` size.
--

_Description_:: {empty}
+
--
`ace.size` returns in GPR `Xd` the total size in bytes of the memory buffer needed to hold the
external image that the MDH describes: a PI, an SCC, a PCCC, or, for a CR in an Error State, the MDH
alone (<<ACE-data-formats>>, <<ACE-length-rule>>). For an SCC the size includes the
authentication tag(s) and the ADS; for a PI it is the size of the entire
PI. Knowing this size is necessary for any feature that relies on exporting a CR, including context
switching.

`ace.avail` is an alias for `ace.size`.

`ace.csize` is the analogous instruction to `ace.size` that returns only the `Content[]` size.

The three Forms for the two instructions differ only in where the MDH is taken from,
as the mnemonics above give:
from the CR itself for Form A, from Bits [63:0] supplied in `Xs` (in `X[s+1] @ Xs` on RV32) for Form B,
and from Bits [127:0] supplied in `Vs` for Form C.

// `ace.size.ex` is computed as follows:
//
// . If the MDH._State_ is a Valid State, then:
//   ..  If _AuxDataLen_ < 2, then: 32 + size of a PI's `Content[]`.
//   ..  If _AuxDataLen_ {ge} 2, then: 32 + size of a PI's `Content[]` + 16 * _AuxDataLen_.
// . If the MDH._State_ is an Error State, then: 16 (only MDH).
// . If the MDH._State_ is a Partial State, then:
//   .. If the MDH._State_ is `ace_cfg_{importing|exporting}_partial`, then: 32 + size of a PI's `Content[]`.
//   .. If the MDH._State_ is `ace_cfg_{importing|exporting}`, then:
//     ...  If _AuxDataLen_ < 2, then: 32 + size of a SCC's `Content1[]`.
//     ...  If _AuxDataLen_ {ge} 2, then: 32 + size of a SCC's `Content1[]` + 16 * _AuxDataLen_.
//
// `ace.size.im` is computed as follows:
//
// . If the MDH._State_ is a Valid State, then:
//   ..  If _AuxDataLen_ < 2, then: size of a PI's `Content[]`.
//   ..  If _AuxDataLen_ {ge} 2, then: size of a PI's `Content[]` + 16 * (_AuxDataLen_ - 2).
// . If the MDH._State_ is an Error State, then: 0.
// . If the MDH._State_ is a Partial State, then:
//   .. If the MDH._State_ is `ace_cfg_{importing|exporting}_partial`, then: size of a PI's `Content[]`.
//   .. If the MDH._State_ is `ace_cfg_{importing|exporting}`, then:
//     ...  If _AuxDataLen_ < 2, then: size of a SCC's `Content1[]`.
//     ...  If _AuxDataLen_ {ge} 2, then: size of a SCC's `Content1[]` + 16 * (_AuxDataLen_ - 2).

Let `content1_size` be the length in bytes of the `Content1[]` of an SCC for the _Algorithm_,
_AlgorithmPolicy_, _KeyType_ and _StateExtension_ of the MDH, and `pi_content_size` the length in bytes
of the `Content[]` of a PI for its _Algorithm_, _AlgorithmPolicy_ and _KeyType_ (<<ACE-length-rule>>).
These are two distinct quantities and are not interchangeable.
Let `content2_size` = 16 * (_AuxDataLen_ - 2) if _AuxDataLen_ {ge} 2, and 0 otherwise.

`ace.size/ace.csize` is computed as follows:

. If the CR is _Unconfigured_, then: 0.
. If the supplied MDH (Forms B and C) is unsupported or invalid Metadata (see <<ACE-Metadata-validity>>), or its _State_ is _Unconfigured_, then: 0.
. If the MDH._State_ is an Error State, then: 16 * (1 - `q`).
. If the MDH._State_ is a Valid State, then:
  ..  If _AuxDataLen_ < 2, then: 32 * (1 - `q`) + `content1_size`.
  ..  If _AuxDataLen_ {ge} 2, then: 64 * (1 - `q`) + `content1_size` + `content2_size`.
. If the MDH._State_ is a Partial State, then:
  .. If the MDH._State_ is `ace_cfg_provisioning`, then: 16 * (1 - `q`) + `pi_content_size`.
  .. If the MDH._State_ is `ace_cfg_{importing|exporting}_partial_pi`, then: 16 * (1 - `q`) + `pi_content_size`.
  .. If the MDH._State_ is `ace_cfg_{importing|exporting}_partial_scc`, then: 16 * (1 - `q`) + `content1_size` + `content2_size`,
     since `IMPQUAL` and `SIV2` are held in the CSRs and not in the PCCC (<<ACE-PCCC>>).
  .. If the MDH._State_ is `ace_cfg_{importing|exporting}`, then:
    ...  If _AuxDataLen_ < 2, then: 32 * (1 - `q`) + `content1_size`.
    ...  If _AuxDataLen_ {ge} 2, then: 64 * (1 - `q`) + `content1_size` + `content2_size`.
--

[[ACE-instruction-input]]
==== ace.input

_Synopsis_::
Load data into the ACEIOBUF.

_Mnemonic_::
`ace.input %offset(Xs), Xl`
(((ACE, instruction, ace.input)))

_Encoding_::
+
--
`ace.input` is an S-type instruction. The base address `Xs` occupies the `rs1` field and the
length `Xl` the `rs2` field, as in `ace.store` (<<ACE-instruction-store>>).

// [IMPORTANT]
// ====
// Under opcode `custom-1` the direction of the memory access is given by `funct3`, not by the
// opcode: `ace.input` reads memory while `ace.store` and `ace.output` write it, and all three
// share the opcode and the S-type format. This differs from the base ISA, where `LOAD` and
// `STORE` have distinct opcodes. An implementation that derives the direction of a transfer
// from the opcode alone will mis-handle these three instructions.
// ====

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x2b, attr: ['custom-1'] },
    { bits:  5, name: 'immed[4:0]' },
    { bits:  3, name: 0x4, attr: ['ace.input'] },
    { bits:  5, name: 'Xs' },
    { bits:  5, name: 'Xl' },
    { bits:  7, name: 'immed[11:5]' },
]}
....
--

_Description_::
+
--
If `Zklv` is not implemented, inputs can be read directly from memory and outputs written directly to memory.
For this reason, the architecture defines `ace.input` and `ace.output` (cf. next section).

[[ACE-iobuf-transfer-window,the ACEIOBUF transfer window]]
The following holds for `ace.input` and for `ace.output`, and is
stated here once. Both transfer the bytes of the transfer window: for each `j` from `acestart` to
min(`Xl`, `aceiobuftop`) − 1,
`ace.input` copies the byte at memory address `%offset(Xs)` + `j` to byte `j` of the ACEIOBUF,
whereas
`ace.output` copies byte `j` of the ACEIOBUF to the byte at memory address `%offset(Xs)` + `j`.
Bytes below `acestart`,
and bytes at or beyond min(`Xl`, `aceiobuftop`), are not accessed on either side.
If `Xl` = 0, or `acestart` {ge} min(`Xl`, `aceiobuftop`), the operation transfers nothing.
If `Xl` is greater than `aceiobuftop`, only the bytes of the window are transferred; software can
detect this case by comparing `Xl` with `aceiobuftop`.

The usage of `ace.input` and `ace.output` is explained in detail in
<<ACE-usage-input-output>>.

[[ACE-usage-input-output]]
=== Replacing Vector Inputs and Outputs with ace.input and ace.output

When `Zklio` is available, some instructions with vector inputs and outputs may be replaced by instruction sequences without vector inputs and outputs.

`ace.input` and `ace.output` only supply inputs to cryptographic operations and read their outputs.
They perform no computation and, apart from the ACEIOBUF and `acestart`, do not change state.
All computation and all other state changes remain in `ace.exec`, `ace.setst`, `ace.mgmt`, and `ace.derive`.

. A Form D `ace.exec` can replace any of Forms A, B, or C.
Any input and any output will be read from or written to the ACEIOBUF if `Zklio` is available.
If `Zklio` is not available, an illegal-instruction exception is raised.
+
A substituted Form A behaves as a Form A with `Vd` = `Vs2` (<<ACE-instruction-exec>>): each block's output replaces its input at the same offset of the window.
An operation whose output blocks do not have the length of its input blocks may be substituted only if its Algorithm states where its output is written in the ACEIOBUF; otherwise the substitution raises an illegal-instruction exception.
A substituted Form C writes its output to [`acestart`, `aceiobuftop`); bytes of the window it does not write are unchanged, and no byte at or beyond `aceiobuftop` is written.
`ace.exec` never modifies `aceiobuftop`.

. A Form D `ace.exec`, resp. a Form A `ace.setst` or `ace.mgmt`, is a substitution when the operation
it performs defines an input or an output, and is native otherwise.
A native Form D, resp. Form A, neither reads nor writes the ACEIOBUF; it ignores `acestart` and leaves it unchanged.

. Mixing vector and ACEIOBUF inputs and output is not allowed:
A Form A `ace.exec` cannot be replaced by a Form B or C `ace.exec`.
Attempts to do so raise an illegal-instruction exception.

. `ace.setst` and `ace.mgmt` follow the same rule: if `Zklio` is available, the form with a vector
input (Form C) can be replaced by a Form A, and the ACEIOBUF is used for the input. If `Zklio` is
not available and a Form A is issued where a Form C is expected, an illegal-instruction exception
is raised.
// +
// NOTE: These exceptions signal that the substitution is unavailable, not that the Form is wrong for
// the Algorithm's current state. The latter invalidates the CR instead (<<ACE-algorithms-other-rules>>).

. Any substitution is allowed only if the ACEIOBUF is enabled and `aceiobuflen` is non-zero.
  Otherwise, ACE exception `ace_exc_unconfigured_buffer` is raised.
+
If `aceiobuflen` is non-zero but `aceiobuftop` is a length invalid for the Algorithm, or, for `ace.exec`, `acestart` is not an interruption point the Algorithm allows, then: if the ACEIOBUF is used as an input, the CR transitions to Error State _Invalid_; if it is used only as an output, the instruction performs no operation — nothing is written and no state transition occurs.

NOTE: Because of these rules, the Algorithms sections say that a certain Form of `ace.exec`, `ace.setst`, or `ace.mgmt` is _expected_ rather than _required_ (or _only [...] allowed_). The substitutions are implicit and are not restated for each occurrence.

Examples of alternative sequences for `ace.exec`, `ace.setst`, and `ace.mgmt` using `ace.input` and `ace.output`
are given in <<ACE-replacement-instructions>>.

|===

The architecture does not enforce the use or ordering of these alternative sequences.
The caller may omit `ace.input` to reuse the ACEIOBUF contents or `ace.output` to ignore the output.
This does not expand the attack surface: the caller already has full control over the inputs and outputs.

[[ACE-reset-and-m-mode-only]]
=== ACE Unit Reset and M-mode-only Harts

An _ACE unit reset_ of a hart resets that hart's ACE architectural state
(cf. <<ACE-out-of-reset-unpriv>> and <<ACE-out-of-reset-priv>>);
in an ACE unit shared by several harts it affects only that hart's state, any shared Locality Secrets excepted.
A hart reset implies an ACE unit reset of that hart.
A hardwired CSK is not affected by reset.

On a hart without the ACE Privileged Architecture (<<ACE-error-architecture>>), the CSK is established by M-mode through a model of <<ACE-CSK-requirements>>, every software-programmable Locality Secret is unconfigured (<<ACE-Localities>>), and `ACES` is treated as On; which CSRs of <<ACE-priv>> exist on such a hart is stated there.

[[ACE-Memory-Model]]
=== Memory Model

// [WARNING]
// ====
// A full axiomatic integration of the ACE component memory operations
// into the RVWMO formalism remains to be produced together with the
// ARC during ratification.
// ====

MMR means “Memory Model Rule.”

[horizontal]
MMR1:: ACE memory instructions appear to execute in program order on the local hart.

MMR2:: ACE memory instructions follow RVWMO at the instruction level.
If `Ztso` is implemented, they additionally follow RVTSO at the instruction level.

MMR3:: ACE memory instructions are supported only for idempotent memory: no component access is made to a non-idempotent or side-effecting PMA region.
If any byte of the transfer maps to such a region, the instruction halts precisely, with the completed prefix committed and `acestart` at a prefix-complete point not beyond the offending byte (0 under the restart option of Rule <<ACE-IRR-resumability-options>>), as in Rule <<ACE-IRR-which-resumable-instructions>>;
on the next execution attempt a load/store access-fault exception is raised before any component access of that attempt.

MMR4:: ACE memory instructions may be decomposed into component memory operations of any granularity.
Their issue order is not architecturally constrained beyond the applicable memory model and the semantics of
`ace.exec`, `ace.load`, `ace.store`, `ace.input`, and `ace.output`.
Intra-instruction ordering follows RVWMO, even when `Ztso` is implemented.
Upon precise interruption, `acestart` must record a _prefix-complete_ point of the transfer.

MMR5:: Other harts observe these component memory operations as ordinary memory operations under RVWMO.
No ordering among them is guaranteed before the instruction completes.
Sharing a buffer accessed by an ACE memory instruction requires the same synchronization as sharing it with an ordinary software loop.

MMR6:: For the purposes of `FENCE`, `FENCE.I`, `SFENCE.VMA` and the `.aq`/`.rl` annotations, the component accesses of an ACE memory instruction are ordinary loads (`ace.load`, `ace.input`) or stores (`ace.store`, `ace.output`) of the issuing hart.

[[ACE-resumability]]
=== Interruptibility and Resumability of ACE instructions

IRR means “Interruptibility and Resumability Rule.”

[horizontal]
[[ACE-IRR-uninterruptible-instructions,IRR1]] IRR1:: Instructions `ace.mgmt`, `ace.getmd*`, `ace.restrict*`, `ace.clone`, non-vector `ace.mv`, and `ace.size` are _uninterruptible_: each either completes or has no architecturally visible effect, writing no destination vector register, GPR, CR byte, ACEIOBUF byte, or memory location.
An implementation realizes this in one of three ways: by completing the instruction before taking an asynchronous interrupt; where Rule <<ACE-IRR-long-running-no-data>> permits, by letting it complete in the background, subject to Rule <<ACE-IRR-conflicting-access-rule>> below; or by discarding its partial work before taking the trap and restarting upon return.
Software must not rely on whether an uninterruptible instruction has retired when a handler runs, and interacts with it only as Rule <<ACE-IRR-conflicting-access-rule>> prescribes.

IRR2:: `ace.setst` is uninterruptible under every architectural condition defined by this specification. Rule <<ACE-IRR-long-running-no-data>> gives the ways an implementation may realize this.

[[ACE-IRR-resumability-options,IRR3]] IRR3:: In general, the following behaviors are allowed when an interrupt or exception handler accesses an input or output of a preempted operation, the associated CR, or any ACE state that may be affected by the operation:

. Background completion: The hart waits for the operation to complete when the privileged handler accesses affected state.
. Atomic completion: The operation completes before any asynchronous interrupt is taken.
. Precise halt and resumption: The operation halts with `acestart` recording a prefix-complete point (<<ACE-Memory-Model>>), and resumes from `acestart`, advancing by at least one granule per execution attempt.
. Timeout followed by precise halt and resumption: The system may impose a timeout before halting as described above.
. Precise halt and restart, provided that restart is not the unconditional response to asynchronous
interrupts: repeated interruption of the same instruction must not prevent its eventual completion. For this reason, this option is discouraged.
It is available only for `ace.load`, `ace.store`, `ace.input`, and `ace.output`, whose transfers are idempotent; `ace.exec`, `ace.derive`, and vector `ace.mv` use option 3 or 4 (Rule <<ACE-IRR-block-iterated-instructions>> below).

[[ACE-IRR-long-running-no-data,IRR4]] IRR4:: Long-running ACE operations that access no external memory—including `ace.setst`, `ace.mgmt`, and `ace.exec` or `ace.derive` forms that do not access GPRs, vector registers, or the ACEIOBUF—may continue while the hart is preempted. If such an instruction is still running when a handler accesses its CR, the hart waits for completion before resuming. Should another interrupt occur while the instruction continues to execute, the second handler must wait as well.
+
An Algorithm may define such operations; examples include scalar multiplication, key generation, and signature generation or verification.
Such operations must either advance their recorded progress towards completion of the operation, restart, or allow resumption using the recorded progress.
+
The progress is recorded in the _AlgorithmUse_ field, in an implementation-defined format; `acestart` remains reserved for byte counts (<<ACE-CSR-acestart>>). If progress is recorded, the implementation exports the data necessary to support resumption in the ADS. Any importing implementation may discard this Section and restart the operation, and must restart it on an Implementation Qualifier mismatch, or if the ADS is removed from the CR (using `ace.clear.ads`, cf. <<ACE-instruction-clearads>>).
+
Hence the architected Content of the CR must not depend on the progress of the operation: an implementation that records progress keeps every intermediate result in the ADS, and the operation restarts correctly from the architected Content alone.

[[ACE-IRR-conflicting-access-rule,IRR5]] IRR5:: All the approaches in Rule <<ACE-IRR-resumability-options>> are subject to one rule: Before the hart performs a _conflicting access_, the in-flight operation must either have completed or have been precisely halted with `acestart` set per <<ACE-Memory-Model>>. A conflicting access is any of the following:
+
--
* An ordinary load or store overlapping the memory region of the in-flight ACE operation.
* An access to a CR used by the operation, including the issue of another ACE instruction involving a CR used by the operation.
* A read or write of `acestart` or an ACEIOBUF CSR. In case of management instructions, also a read or write to the following CSRs: `acemanagedcr`, `acesivl`/`acesivh`, `acesiv2l`/`acesiv2h`, and `aceiql`/`aceiqh`.
* A read or write of a GPR or vector register that the operation writes as its destination.
* A write to a vector register or to the ACEIOBUF that the operation reads as an operand, including the issue of an `ace.input` targeting it. Scalar operands held in GPRs are captured when the instruction issues, so accessing one is not a conflicting access.

Rules <<ACE-IRR-resumability-options>> and <<ACE-IRR-conflicting-access-rule>> make asynchronous execution by the attached ACE unit invisible to same-hart program order, as <<ACE-Memory-Model>> requires. Beyond this rule, the architecture specifies only the allowed interruption points for its instructions and Algorithms.
--

[[ACE-IRR-which-resumable-instructions,IRR6]] IRR6:: The resumable instructions are `ace.exec`, vector `ace.mv`, `ace.derive`, `ace.load`, `ace.store`, `ace.input`, and `ace.output`. Architecturally, they process units serially. If an instruction halts precisely, the completed prefix is committed, the failing and subsequent units have no effect, `acestart` records a prefix-complete point, the instruction does not retire, and `xepc` contains its address. If an instruction transitions its CR to an Error State after partial progress, the completed prefix remains committed and the instruction retires (<<ACE-CSR-acestart>>).

[[ACE-IRR-block-iterated-instructions,IRR7]] IRR7:: For block-iterated `ace.exec`, `ace.mv`, and `ace.derive`, fully processed blocks remain written or transferred, and `acestart` records their total byte count. For transfer instructions, bytes below `acestart` remain transferred at both endpoints. A partially executed instruction commits exactly the state that a shorter instruction performing only the completed operations would have committed. This includes the CR, `acestart`, `acemanagedcr`, `acesivl`/`acesivh`, `acesiv2l`/`acesiv2h`, and `aceiql`/`aceiqh`, `*lcrstatus`, and effective `ACES` fields, ensuring consistent context save, restore, and resumption. Implementations must honor `acestart` for `ace.exec` and `ace.derive`. Handlers must not reset it to zero to force a restart, as this could reapply state changes or corrupt data.
// +
// NOTE: `ace.derive` is included because it may modify the source CR's state (for example, when squeezing a sponge) and destructively modify the destination. Restarting could process state twice and overwrite data already consumed. Interruption points include block boundaries and Algorithm-specific points, as well as implementation specific ones within long-running computations (for instance in <<ACE-ECC>> and <<ACE-PQC>>). If input and output overlap, the result may be unpredictable, but it remains a function only of architectural state that the executing context is otherwise permitted to observe.

IRR8:: For ACE memory instructions `ace.load`, `ace.store`, `ace.input`, and `ace.output`, the usual rule applies:
An implementation may treat such an instruction as complete (by retiring it or taking an interrupt with `xepc` past it) only after address translation and permission checks succeed for every byte. Otherwise, it must halt the instruction precisely, with `acestart` at a prefix-complete point allowed by the instruction, and report any fault synchronously on re-execution or resumption.
// For `ace.load` and `ace.store`, this point must be a multiple of sixteen bytes.
Component accesses after the instruction is treated as complete must not fault.
+
NOTE: After each `ace.load` the caller must check whether the CR is _Unconfigured_, in which case the entire configuration operation (not just the `ace.load` instruction, but the software using it) must be restarted: an exception handler may have cleared the CR and advanced `xepc` to force this behavior.
+
NOTE: Clearing a CR in an exporting State (<<ACE-instruction-setst>>) calls for particular care from an
exception handler, because until the export completes, the ciphertext the CR holds may be the only copy of
the CC. A handler that intends to clear such a CR must first see the export through to completion — if
necessary across preemptions of its own by a more privileged mode — and store the resulting image.
If it clears the CR earlier, by mistake or on an unrecoverable error, the CC is lost: the caller detects
this by the same check after `ace.store`, must treat the error as unrecoverable, and a further
`ace.store` on the cleared CR raises an illegal-instruction exception (<<ACE-instruction-store>>).
This allows the error to propagate to the outermost caller.

// [[ACE-IRR-algorithms-specific,IRR9]] IRR9:: Algorithm-specific resumable long-running operations that transfer no data
// in an `ace.setst`, in a (block-processing step of) `ace.exec` operation,
// or in an `ace.derive` operation,
// must either advance its recorded progress towards completion of the operation, or restart.
// The manner in which progress is recorded is implementation-defined, but it cannot use `acestart`
// (for instance, it can use _AlgorithmUse_, as in <<ACE-ECC>> and <<ACE-PQC>>).
// Implementations capable of resuming these operations also support their restart.

ACE defines two external CC formats:

. The _Sealed Cryptographic Context_ (SCC), an encrypted and authenticated representation of a CC used when exporting a CR to memory for later import.

[[ACE-length-rule]]
==== Fields Determining the Length of a PI, of an SCC, of a PCCC, and of a CR

Except when the CR is in an Error State, the MDH fields that determine the length
of a PI, of an SCC and of a PCCC, as well as the CRF capacity occupied by a CR, are all
contained in the lower 64 bits of the MDH:

. The length of a *Provisioning Input* is determined by, and only by, the fields
_Algorithm_, _AlgorithmPolicy_ and _KeyType_.
It does *not* depend on _AuxDataLen_: a PI carries no ADS, and _AuxDataLen_
must be zero in the MDH of a PI.
It also does not depend on _StateExtension_ or _AlgorithmUse_, whose values are ignored and are
replaced with zero by `ace.mgmt` upon provisioning, nor on _SCProtection_.
During provisioning, the information of a CR reflects the external format of a PI.
The internal representation is finalized into the CR's internal state upon using
`ace.mgmt` to complete the provisioning, which may include the computation of
information such as derived keys, or multiple shares.

. The length of a *Sealed Cryptographic Context* is determined by, and only by, the
fields _Algorithm_, _AlgorithmPolicy_, _KeyType_, _StateExtension_, and _AuxDataLen_
(see <<ACE-extra-content>>).  Note that this length does not depend on _State_.
It also does *not* depend on _SCProtection_ (see <<ACE-rules-masked-implementations>>).

. The length of a *Partially Configured Cryptographic Context* is that of the MDH plus the image
the CR holds, which the base type of its Configuration State (<<ACE-nested-state-base-types>>) identifies: the `Content[]` of a PI for a
`_pi` State, and `Content1[]` together with `Content2[]` for an `_scc` State. Once the image is
identified, its length is given by the rule above for that format, and depends on no further field.

. The *CRF capacity* occupied by a CR is determined by, and only by, the fields
_Algorithm_, _AlgorithmPolicy_ and _SCProtection_.
It does not depend on _KeyType_, because a CR holds the expanded key material whether the
key was provisioned by value or retrieved through a System Key Identifier,
nor on _StateExtension_, because a CR is allocated with room for every field the
Algorithm may come to use.

No other MDH field may affect any of these four quantities.

A CR in an Error State is its MDH alone (Rule <<ACE-SGR-error-state-CR-is-only-MDH>>, <<ACE-error-state-transfer>>).
//and the CR occupies only the capacity of its MDH (Rule <<ACE-SGR-clear-cr-content-error-state>>).
A PI cannot be in an Error State.

[[ACE-rules-masked-implementations]]
==== Single-Share Key Export Rule for Masked Implementations

Any multi-share implementation of an Algorithm will always provision, import and export _all_ its keys and secrets as reconstructed values.
This keeps SCCs compact and ensures interoperability across architectures with different implementations.
(((ACE, Algorithm, side-channel protection variants)))
Architecturally, all values are represented as a single share.
Side-channel analysis (SCA)-protected Algorithms are implementation variants of the same unprotected Algorithm, not separate specifications.
The only difference is the _SCProtection_ field of the MDH.

NOTE: While reconstructing or re-randomizing a key is in general inexpensive, for instance if the masks are generated
by a block cipher in counter mode,
an implementation that is using a slower method to generate the masks
may include shares or masks in the ADS to accelerate multiple-share reconstruction of a key.

// ////////////////////////////////////////////////////////////////////

[[ACE-system-keys]]
==== System Keys and Randomly Generated Key Values

In a PI or SCC, System Keys are encoded as a 64-bit SKID used to retrieve the key from a system-specific SKS.
This replaces the key value itself with a usually smaller field, and may reduce the size of the PI or SCC.

The SKS resolves a SKID different from the all-ones value as a function of the SKID, _Algorithm_ and _AlgorithmPolicy_, never of the current privilege mode; a SKID it does not resolve transitions the CR to Error State _Invalid_ (see <<ACE-Metadata-validity>>).
Whenever a SKID is resolved, the _UsagePolicy_ of the CR becomes the intersection of the permissions in the PI or SCC and those of the key (bits 0–3 or-ed, bit 4 and-ed), and its _Locality_ the union of the Localities in the PI or SCC and those of the key (the stricter entry in each HW Binding chain, bits 6–8 or-ed); if the two Boot Session entries are non-zero and differ, the CR transitions to Error State _Invalid_.

The all-ones SKID (<<ACE-KeyType-field>>) is not resolved by the SKS.

In multi-share implementations, ACE may copy System Key material from the SKS into the CR and expand it into multiple shares.
The key must still be exported as a SKID.
Any shares or masks included in the ADS (see <<ACE-rules-masked-implementations>>) must not allow or facilitate recovery of the key's value from those values alone.

[[ACE-data-formats]]
==== Formats of PIs, SCCs, and Partially Configured Cryptographic Contexts

The Provisioning Input (PI) consists of two sections of data, MDH and `Content[]`, which do not have to be contiguous in memory.
The length of `Content[]` must be a multiple of 128 bits.

A Sealed Cryptographic Context (SCC) consists of (up to) five sections of data, which also do not have to be contiguous in memory, as in the following table:

[[ACE-SCC]]
.Plaintext of the Sealed Cryptographic Context (SCC) Format, all Sections in Order
[width="100%",cols="^8%,15%,30%,47%",options="header"]
|===
| Section | Section Name | Size                 | Description
| 1       | `MDH`        | 128 bits             | See <<ACE-Metadata>>.
| 2       | `SIV`        | 128 bits             | Authentication tag for `MDH` and `Content1[]`.
| 3       | `IMPQUAL`    | 128 bits, if present | Identifies the implementation of the ACE Unit.
| 4       | `SIV2`       | 128 bits, if present | Authentication tag for `IMPQUAL` and `Content2[]`.
//
| 5.a
| `Content1[]`
| A multiple of 128 bits. See <<ACE-length-rule>>.
| Contains keys and other Algorithm-specific information. Encrypted in memory and during partial import.
 The data in this section is necessary for the correct functioning of the Algorithm.
//
| 5.b
| `Content2[]`
| A multiple of 128 bits.
| ADS: The data in this section is _not_ necessary for the correct functioning of the Algorithm.
  Encrypted in memory and during partial import.
|===

The MDH's _AuxDataLen_ field specifies the total size of the Implementation-Specific ADS (`SIV2`, `IMPQUAL`, and `Content2[]`), except for the special value 1 (see <<ACE-extra-content>> and <<ACE-SCC-import>>).
If _AuxDataLen_ < 2, then the ADS is empty.
If _AuxDataLen_ {ge} 2 then the ADS contains _AuxDataLen_ blocks.

// A CR may contain more information than an SCC (excluding `SIV`, `IMPQUAL`, and `SIV2`), which in turn may contain more information than a PI.
// This occurs because some information may not be serialized and instead be (re)computed at provisioning or import.
// A CR may also contain optional, implementation-specific auxiliary data to improve performance.
// This data may be exported in whole or in part in the ADS.
// An importing implementation must be able to safely ignore it after checking `IMPQUAL`.

For a CR in an Error State, see Rule <<ACE-SGR-error-state-CR-is-only-MDH>>.

A third format is the Partially Configured Cryptographic Context (PCCC), which is used when a partially configured or exported SCC is exported and reimported upon preemption of the management procedures.

During import of an (encrypted and authenticated) SCC, or during export of a CR to a SCC, the `Content[]` is kept encrypted in the CR until
the `ace.mgmt` operation to complete the management operation is issued, which decrypts and authenticates the `Content[]`.
This requires that the MDH and `Content[]` have been loaded, and that
the corresponding `SIV`, and if _AuxDataLen_ {ge} 2, also `SIV2` and `IMPQUAL`, are configured.

During export of a CR to a SCC, the initial `ace.mgmt` operation encrypts the contents and generates `SIV` and, if _AuxDataLen_ {ge} 2, also `SIV2` and `IMPQUAL`. The contents remain encrypted in the CR until the completion operation re-decrypts and authenticates them, with the same requirements as for completing an import—or restores the clear contents from an internal copy, as described in <<ace-mgmt-completes-export>>.

At nested levels, no additional encryption or authentication is performed. Data is exported as-is:

* If a partially provisioned CR is exported, the data is in the clear and its image is PI-shaped (State `ace_cfg_exporting_partial_pi`). This is not a security issue, as the plaintext was already available to software and thus to its more privileged modes.

* If a partially imported SCC is exported, the data is already encrypted and its image is SCC-shaped (State `ace_cfg_exporting_partial_scc`).

* If the partial export of a CR into a SCC is preempted and the CR must be exported again, the data is already encrypted and its image is SCC-shaped.

In these cases, it is not necessary to include `SIV`, `SIV2` and `IMPQUAL` in the export.
It suffices to save, resp., restore them at context save, resp., restore, under the condition given in <<ACE-CSR-unpriv>>.

By saving metadata headers in its own state, software implicitly maintains a stack of _State_ values.
The top value corresponds to the previous nesting level, which the `ace.mgmt` completion operation restores.

To track progress of `ace.load`, `ace.store`, and `ace.mv`, software must save and restore `acestart` at context save and restore.
The same requirement applies to `SIV`, `SIV2`, and `IMPQUAL` whenever a Complete CR is being imported or exported, under the condition given in <<ACE-CSR-unpriv>>.

The format of the exported data for _partially configured_ SCCs is therefore the following:

[[ACE-PCCC]]
.Format of a Partially Configured Cryptographic Context
[width="100%",cols="^8%,22%,70%",options="header"]
|===
| Section | Section Name | Size
| 1       | MDH          | 128 bits
| 2.a     | `Content1`   | Cf. Section 5.a in <<ACE-SCC>>, or the `Content[]` of the PI for a `_pi` State.
| 2.b     | `Content2`   | Cf. Section 5.b in <<ACE-SCC>>. Absent for a `\_pi` State, whose _AuxDataLen_ is zero.
|===

NOTE: If the outermost operation is not a provisioning operation, an attempt to close a nested management operation by providing the wrong _State_ value will cause authentication to fail either immediately (for instance, during import, because not all data has been imported) or at the outermost level, because SIV verification will use the ciphertext rather than the plaintext.

[[ACE-error-state-transfer]]
==== Export and Import of a CR in an Error State

A CR in an Error State holds only its MDH (Rule <<ACE-SGR-clear-cr-content-error-state>>), so there is nothing to
encrypt and nothing to authenticate. No SCC and no PCCC are produced, and neither direction opens a
management operation. Both paths are therefore shorter than those of <<ACE-management-operations>>,
and both are exempt from the resumption machinery, since no `ace.load` or `ace.store` is issued.

*Exporting* a CR in an Error State consists of two steps and uses no `ace.mgmt`:

. Read the _State_ field with `ace.getst` (<<ACE-instruction-getst>>) and find it to be an Error State.
. Read the MDH with `ace.getmd` or `ace.getmdv` (<<ACE-instruction-getmd>>) and store those 16 bytes
  to memory. `ace.size` reports 16 and `ace.csize` reports 0 for such a CR.

Issuing `ace.mgmt` with `#immed7` = `ace_cfg_exporting` on a CR in an Error State is permitted but
useless: it leaves the CR unchanged and opens no management operation
(<<ACE-instruction-setst>>).

*Importing* such an image consists of one step:

. Issue `ace.mgmt` with `#immed7` = `ace_cfg_importing` and the 16-byte MDH
  as the auxiliary operand. The instruction configures the CR into the Error State the MDH names
  (54 and 55 as _Invalid_), installing the entire MDH, and completes the configuration by itself,
  without applying the checks of <<ACE-Metadata-validity>>; it is uninterruptible
  (Rule <<ACE-IRR-uninterruptible-instructions>>), so the CR is never observed part-configured.
  Form C or D carries the whole MDH, as does a Form A taking it from the ACEIOBUF. Form B is not
  forbidden, but it supplies only bits [63:0] and zeroes the upper half, so _UsagePolicy_, _Locality_,
  _AlgorithmUse_, _ExpirationDate_ and _Version_ are lost; that is rarely what the caller intends.

No `ace.mgmt` with `#immed7` = `ace_cfg_management_end` follows, and issuing one is an illegal
instruction. The `SIV`, `SIV2` and `IMPQUAL` CSRs take no part in either path and need not be saved
for it.

[[ACE-SCC-AEAD]]
==== The SCC Authenticated Encryption Scheme

The cryptographic scheme used in the export and import of SCCs is
a variant of AES-GCM-SIV cite:[DBLP-journals-iacr-GueronLL17,RFC8452].
The differences with respect to AES-GCM-SIV are:

. The block containing the lengths of Associated Data and Plaintext is not included in the evaluation of POLYVAL.
This is intentional: the information needed to fully determine the lengths of
all sections is already included in the MDH, and thus in the POLYVAL.
. The optional Nonce is omitted.
. A domain separation bit, `sep`, has been added to distinguish the two segments of the content that are sealed in a SCC: the fixed architecture-defined content (`sep` = 0) and the optional implementation-dependent content (`sep` = 1).

We define the Key Derivation (<<ACE-SCC-key-derivation>>) and POLYVAL (<<ACE-SCC-POLYVAL>>) functions first.
The generation of an SCC from a CR (<<ACE-SCC-export>>) and the import of an SCC into a CR (<<ACE-SCC-import>>) are defined next.

In the pseudocode of this section, `AESE256(K, B)` denotes the AES-256 encryption of the
128-bit block `B` under the 256-bit key `K`, as specified in FIPS 197 cite:[nist-fips-197].

[[ACE-SCC-key-derivation]]
.RFC8452 Key Derivation
[]
----
function SCC_KeyDeriv(key : bits(256), nonce : bits(96))
    → struct{enc_key : bits(256), auth_key : bits(128)} =
{
  local A : array [0..5] of bits(128);
  local i : int;

  foreach(i from 0 to 5) do:
    A[i] ← AESE256(key, nonce @ bin(i,32));

  return struct {
    enc_key  = A[5][63:0] @ A[4][63:0] @ A[3][63:0] @ A[2][63:0],
    auth_key = A[1][63:0] @ A[0][63:0]
  }
}
----

NOTE: Due to the computational cost of the key derivation function, implementations may cache the derived keys.

[NOTE]
====
To reduce payload size, the AES-GCM-SIV-derived construction used for SCC import and export omits the nonce.
It relies instead on AES-GCM-SIV's resistance to nonce reuse and misuse. The construction remains secure for up to 2^64^ 128-bit blocks observed by an adversary.

This provides practical protection for client applications. On cloud servers, each virtual machine and supervisor domain should use a unique CSK. To transfer CCs between domains, M-mode firmware can import an SCC using the source domain's CSK and re-export it using the target domain's CSK.

The `SIV` (Synthetic IV), which is also the GCM-SIV authentication tag, is the encryption of the `POLYVAL` hash of the MDH, Locality Secrets, and Content, concatenated in that order. In the `POLYVAL` pseudocode below, the input is represented as an array of 128-bit blocks, which are absorbed in increasing index order.
====

[[ACE-SCC-POLYVAL]]
.Polyval Hashing Function
[]
----
function POLYVAL(auth_key : bits(128), blocks[0..n-1] : bits(128), n : int)
    → bits(128) =
{
  local tmp : bits(128) ← zeros(128);
  local i : int;

  foreach(i from 0 to n-1) do:
    tmp ← tmp xor blocks[i];
    tmp ← Montmul(tmp, auth_key);

  return tmp;
}
----

We now define `Montmul(a, b)`, the Montgomery multiplication operation used in POLYVAL.

The field F is GF(2)[`x`] modulo `x^128^ + x^127^ + x^126^ + x^121^ + 1`.

A 128-bit value `V` represents the element whose coefficient of `x^k^` is `V[k]`.
Both the byte order and the bit order run forward; this is the representation of
cite:[RFC8452] {sect}3, under which `x^0^` is the byte string `0x01` followed by
fifteen zero bytes, i.e., the value `1`.

`Montmul(a, b)` is not plain multiplication but Montgomery multiplication; it is: +
 +
`{fournbsp}{fournbsp}` `Montmul(a, b)` = `a` {interpunct} `b` {interpunct} `x^-128^` `{nbsp}{nbsp}` in the field F.

We now give the notation used for the inputs and outputs of the SCC encryption and decryption functions,
i.e., <<ACE-SCC-GCM-SIV-enc>> and <<ACE-SCC-GCM-SIV-dec>>:

* `AD[]` denotes the Associated Data as an array of `len_AD` 128-bit blocks, that is
  `AD[0] {vvert} AD[1] {vvert} {ellipsis} {vvert} AD[len_AD-1]`, in that order;
* `P[]`, resp., `C[]`, denotes a Plaintext, resp., a Ciphertext, as arrays of `len_PC`
  128-bit blocks, that is `P[0] {vvert} P[1] {vvert} {ellipsis} {vvert} P[len_PC-1]`,
  resp. `C[0] {vvert} C[1] {vvert} {ellipsis} {vvert} C[len_PC-1]`, in that order;
* `K` is a 256-bit Key;
* `N` is a 96-bit Nonce; and
* `SIV` is a 128-bit SIV/tag.

[NOTE]
====
As in AES-GCM-SIV, we use bit 127 to distinguish tag inputs (bit 127 takes the value 0) from
keystream inputs (1). This construction adds a second domain separation bit, `sep`, in bit
126 to distinguish architecture-defined content (`sep` = 0) from the ADS (`sep` = 1).
The security reduction is just one bit: the tag input carries 126 bits of the `POLYVAL`
result rather than 127, and the keystream counter block carries 94 bits of the `SIV` rather than
95.
====

// Both segments derive their keys from the same CSK and all-zero nonce.
// Without `sep`,
// only their Associated Data and SIV values would distinguish them. This does not imply an
// attack: a collision between `SIV` and `SIV2` has negligible probability. However, separation
// would then depend on those values rather than on the construction itself.
// Placing `sep` in bit 126 of both AES inputs makes the separation unconditional.
//
// * in the *tag* computation, `0 @ sep @ POLYVAL({ellipsis})[125:0]`, so that the same
//   Associated Data and plaintext yield different tags in the two segments; and
// * in the *keystream* counter block, `1 @ sep @ SIV[125:32] @` counter, so that the two segments
//   cannot share a keystream even if their SIVs were to collide.

[[ACE-SCC-GCM-SIV-enc]]
.AES-GCM-SIV Encryption for SCC Generation
[]
----
function SCC_Encrypt(AD[] : array of bits(128), N : bits(96), sep: bits(1),
    P[] : array of bits(128), K : bits(256), len_AD : int, len_PC : int)
  → {SIV : bits(128), C[] : array of bits(128)} =
{
  enc_key, auth_key ← SCC_KeyDeriv(K,N);
  SIV ← POLYVAL(auth_key, AD || P, len_AD + len_PC);
  SIV[95:0] ← SIV[95:0] xor N;
  SIV ← AESE256(enc_key, 0 @ sep @ SIV[125:0]);

  foreach(i from 0 to len_PC - 1) do:
    C[i] ← P[i] xor AESE256(enc_key,
             1 @ sep @ SIV[125:32] @ bin((int(SIV[31:0]) + i) mod 2**32, 32));

  return ( SIV, C[] );
}
----

`len_PC` never exceeds `max_admissible` / 16 (<<ACE-instruction-load>>), and `len_AD` never exceeds 7.

[[ACE-SCC-GCM-SIV-dec]]
.AES-GCM-SIV Decryption for SCC Import
[]
----
function SCC_Decrypt(AD[] : array of bits(128), N : bits(96), sep: bits(1),
    SIV : bits(128), C[] : array of bits(128), K : bits(256),
    len_AD : int, len_PC : int)
  → {correct : bool, P[] : array of bits(128)} =
{
  enc_key, auth_key ← SCC_KeyDeriv(K,N);

  foreach(i from 0 to len_PC - 1) do:
    P[i] ← C[i] xor AESE256(enc_key,
             1 @ sep @ SIV[125:32] @ bin((int(SIV[31:0]) + i) mod 2**32, 32));

  s ← POLYVAL(auth_key, AD || P, len_AD + len_PC);
  tmp ← s;
  tmp[95:0] ← tmp[95:0] xor N;
  tmp ← AESE256(enc_key, 0 @ sep @ tmp[125:0]);

  if (tmp != SIV) then:
    foreach(i from 0 to len_PC - 1)
      P[i] ← zeros(128);
    return ( false, P[] );

  return ( true, P[] );
}
----

NOTE:  *Design Rationale for the Sealing Construction.*
The Locality Secrets are supplied to the AEAD as _associated data_ rather than mixed into the
Context Sealing Key through a KDF. Both approaches bind the SCC to the Locality set, but
using associated data is computationally less expensive. POLYVAL, requires one `Montmul`
per 128-bit block and is thus significantly faster than most KDFs. This approach also
avoids re-deriving `enc_key` and `auth_key` when the Locality set changes.
Distinct Locality sets lead to the same SIV with collision probability 2^-128^.

[[ACE-SCC-export]]
==== Generation of an SCC from a Fully Configured CR

If the _State_ field is set to a Valid State, then ``K(i)`` is fully provisioned,
and opening the CR for export (`ace.mgmt Kd|K{Xd}, #ace_cfg_exporting`) performs the following steps
to create the serialized, encrypted and authenticated SCC from the CR.

Regarding the Localities, the substitution rules in <<ACE-Localities>> and <<ACE-interaction-with-debug>> apply.
We define `LST_eff[j]` as the value of `LST` entry j after applying these substitution rules;
a non-implemented entry with no configured replacement contributes `zeros(128)` and makes the Metadata invalid at provisioning/import.
In the export and import algorithms we then replace `LST[j]` with `LST_eff[j]`.

Exporting a CR may produce an _AuxDataLen_ value of 1, both for fully configured (cf. <<ACE-instruction-clearads>>) and non-fully configured CRs.

.Exporting a Fully Configured CR ``K(i)``
--
. First, the Algorithm-dependent data is processed:
.. `saved_MDH` <- the MDH of ``K(i)`` immediately before its _State_ is set to `ace_cfg_exporting` (the image software saved beforehand), ``len_AD`` <- 1
.. ``AD[0]`` <- `saved_MDH`
.. foreach(_j_ from 0 to 10) do:
... If `saved_MDH`._Locality_ includes Locality #j, then ``AD[len_AD]`` <-  ``LST_eff[``_j_``]``, ``len_AD`` <- ``len_AD`` + 1
.. `len_PC` <- the number of 128-bit blocks of `Content1[]` (Section 5.a of <<ACE-SCC>>).
.. `SIV`, `Content1~CT~[]` <- `SCC_Encrypt(AD, zeros(96), 0, K(i).Content1~PT~[], CSK, len_AD, len_PC)`
. Second, if _AuxDataLen_ {ge} 2 then: the implementation-dependent data is processed:
.. `len_AD2` <- 2, ``AD2[0]`` <- ``K(i)``.`IMPQUAL`, ``AD2[1]`` <- `SIV`.
.. `len_PC2` <- the number of 128-bit blocks of `Content2[]` (Section 5.b of <<ACE-SCC>>), that is _AuxDataLen_ − 2.
.. `SIV2`, `Content2~CT~[]` <- `SCC_Encrypt(AD2, zeros(96), 1, K(i).Content2~PT~[], CSK, len_AD2, len_PC2)`
. Finally, if _AuxDataLen_ < 2, then:
.. return(`saved_MDH`, `SIV`, `Content1~CT~[]`)
. else:
.. return(`saved_MDH`, `SIV`, `IMPQUAL`, `SIV2`, `Content1~CT~[]` and `Content2~CT~[]`) (note that `Content2~CT~[]` may be empty)
--

Of the returned values, `SIV`, `SIV2` and `IMPQUAL` are placed in the CSRs `acesivl`/`acesivh`,
`acesiv2l`/`acesiv2h` and `aceiql`/`aceiqh`, from which software stores them to memory; the ciphertext
remains in the CR, whence `ace.store` (<<ACE-instruction-store>>) transfers it; and `saved_MDH` is the
image software already holds, which `ace.getmd*` (<<ACE-instruction-getmd>>) also returns.

If _AuxDataLen_ < 2, then `SIV2` and `IMPQUAL` are not generated, and therefore
`acesiv2l`/`acesiv2h` and `aceiql`/`aceiqh` are not written to.
They may contain stale values, but this is not an issue as they are not exported to memory in this case.

[NOTE]
====
A CR in an Error State is not exported by this procedure (Rule <<ACE-SGR-error-state-CR-is-only-MDH>>).
====

[IMPORTANT]
====
Taking `SIV` as ``AD2[1]`` binds the two payloads together, so that `SIV2` and
the keystream of the second segment change whenever the
first payload changes; an attacker cannot graft the Implementation-Specific ADS of one SCC onto the architecture-dependent part of another.
====

[NOTE]
====
If an export operation is completed prematurely, an authentication error results upon import (see next section).
If an import operation is completed prematurely, an authentication error results.
If any of the two operations is not completed, various types of error conditions will occur because _State_ is a Complete State.
====

[[ACE-SCC-import]]
==== Decryption and Authentication of a complete SCC into a CR

The following algorithm describes the import of the SCC of a fully configured CR as a whole.
Steps 1 to 8 are performed by the `ace.mgmt Kd|K{Xd}, #ace_cfg_importing` that opens the import
(<<ACE-instruction-setst>>), step 9 by the `ace.load` instructions that follow it
(<<ACE-instruction-load>>), and the remaining steps by
`ace.mgmt Kd|K{Xd}, #ace_cfg_management_end`, which decrypts and authenticates the SCC.

.Importing a Fully Configured CR ``K(i)``
--
 . Clear ``K(i)``.
 . Load `M`, the MDH from the SCC, into ``K(i)``.MDH.
 . Check correctness of `M`, and whether the Algorithm is supported.
 . Determine the length of the entire SCC.
 . `actual_impdatalen` <- `M`._AuxDataLen_.
 . If `actual_impdatalen` exceeds the implementation's maximum for the given Algorithm, the SCC contains an Implementation-Specific ADS that the importing implementation does not support.
 . If `actual_impdatalen` is 1, then we are importing a partially exported SCC that results from an interrupted import with discarded ADS. We keep the value 1 so that the state machine in the CR is notified that ADS was present but discarded when this import is finally completed.
 . In the last two cases, the SCC length is adjusted by excluding the Implementation-Specific ADS, and `actual_impdatalen` <- 1.
 . Load the rest of the SCC, up to the determined length.
 . `saved_MDH` <- the MDH image held in ``K(i)``, that is `M`, the image carried in the SCC and loaded at `#ace_cfg_importing`, with its _State_ field restored from the auxiliary operand of the completing `ace.mgmt`. This is the same value that the exporting side used under that name.
 . ``AD[0]`` <- `saved_MDH`, ``len_AD`` <- 1
 . foreach (`j` from 0 to 10) do:
 .. If `saved_MDH`._Locality_ includes Locality #j, then ``AD[len_AD]`` <-  ``LST_eff[j]``, ``len_AD`` <- ``len_AD`` + 1
 . `len_PC` <- the number of 128-bit blocks of `Content1[]` (Section 5.a of <<ACE-SCC>>).
 . `correct`, ``K(i)``.`Content1[]` <- `SCC_Decrypt(AD, zeros(96), 0, SIV, K(i).Content1[], CSK, len_AD, len_PC)`.
 . If `correct` {ne} `true`, the SCC is rejected: ``K(i)`` transitions to Error State `ace_state_import_auth` (Rule <<ACE-SGR-clear-cr-content-error-state>>).
 . Second, if `actual_impdatalen` {ge} 2, the implementation-dependent data is processed:
.. `len_AD2` <- 2, ``AD2[0]`` <- ``K(i)``.`IMPQUAL`, ``AD2[1]`` <- `SIV`.
.. If ``K(i)``.`IMPQUAL = `zeros(32) @ acemimpid @ acemarchid @ acemvendorid` then:
... `len_PC2` <- the number of 128-bit blocks of `Content2[]` (Section 5.b of <<ACE-SCC>>), that is `actual_impdatalen` − 2.
... `correct`, `K(i).Content2[]` <- `SCC_Decrypt(AD2, zeros(96), 1, `SIV2`, K(i).Content2[], CSK, len_AD2, len_PC2)`.
.. else:
... `correct` <- `false`.
 . If `correct` {ne} `true`, then `Content2[]` is dropped and `actual_impdatalen` <- 1.
 . ``K(i)``.MDH._AuxDataLen_ <- `actual_impdatalen`. If this value is 0 or 1, import completes using only the architecture-dependent content. The value 1 signals to the imported CR's state machine that the ADS was dropped. The state machine must then establish a consistent internal state and set _AuxDataLen_ to 0. If new auxiliary data is created, _AuxDataLen_ must be set to the appropriate value when the auxiliary data is created.
--

[NOTE]
====
This procedure ensures that if the SCC's optional implementation-specific ADS makes the SCC too large to fit in a CR, or if that ADS is incompatible, the implementation ignores the optional data, but keeps the architecture-dependent content: Only a failure of the first authentication (SIV) rejects the entire SCC.
====

[[ACE-import-and-DIEL]]
==== Import and Data-Independent Execution Latency

_This section is informative and non-normative._

In ACE, Data-Independent Execution Latency (DIEL) applies only to the cryptographic operations it performs, including the decryption and authentication of SCC contents.

All CR management instructions are split into three phases: An initial `ace.mgmt`, load/store instructions, and a final `ace.mgmt`.
The two `ace.mgmt` instructions perform no memory accesses.

The dependencies of the `ace.mgmt` instructions' timing are limited to very few factors:

. Actual size of the SCC to export, including the implementation-dependent part.
. `SIV` or `SIV2` authentication failures on import;
. `IMPQUAL` mismatches on import; and
. Attempts to import SCCs whose total length exceeds what the target machine supports for the given Algorithm.
  In this case, the implementation-dependent part is necessarily unsupported; it is skipped or only partially loaded, to be discarded without authenticating it; and only the architecture-dependent part is authenticated and decrypted (if the resulting _State_ is a Complete State) and used.

Apart from these factors, only the number of blocks to process may affect the timing of the `ace.mgmt` instructions.
The timing of the processing of each block is independent of the actual data being processed.

[[ACE-state-save-and-restore-order]]
=== ACE State Save and Restore Order

_This section is informative and non-normative._

This is the recommended order for saving and restoring the ACE state.

* Save order:

. `acestart` first, since every later step may clear it.
. `acemanagedcr` and, if it is not 32, the six authentication CSRs, before any `ace.mgmt`, which writes them.
. `aceiobuflen` and `aceiobuftop`.
. If `aceiobuflen` is nonzero, the buffer contents by `ace.output` with `acestart` = 0 and `aceiobuftop` raised to `aceiobuflen`; this precedes any CR export, whose `ace.mgmt` may take `ml` from the ACEIOBUF (<<ACE-usage-input-output>>).
. If the saved `acemanagedcr` is not 32, export the CR it indexes; its export leaves `acemanagedcr` naming it.
. Set `acemanagedcr` to 32, since `ace.mgmt` requires it to hold its target's number or 32.
. Export all other configured CRs.

* Restore order:

. The CRs not indexed by the saved `acemanagedcr` first, with `acemanagedcr` set at 32 before and after the import.
. If `acemanagedcr` {ne} 32, then:
.. restore the CR indexed by the saved `acemanagedcr`, with `acemanagedcr` set at the saved value before the import; and then
.. the saved six authentication CSRs;
. `aceiobuflen`, which zeroes the buffer and sets `aceiobuftop`;
. The buffer contents, if saved, by `ace.input`, with `acestart` = 0 and `aceiobuftop` = `aceiobuflen`;
. then, `aceiobuftop`, and
. `acemanagedcr`.
. Last, `acestart`, since every earlier step may clear it.
