[[ACE-unpriv-intro]]
=== Introduction

We introduce here the fundamental concepts around which ACE is designed.

[[ACE-concepts]]
==== Fundamental Concepts and Definitions

Cryptographic Context:::
(((Cryptographic Context)))
The *Cryptographic Context* (CC) is the foundation of ACE.
All cryptographic operations performed by ACE execute within the constraints defined by a CC.
A CC contains secrets, usually keys, but it is more than just a key container:
it is an indivisible structure consisting of a *Metadata Header* (MDH) and *Content*.
The MDH has a fixed format and specifies the algorithm that can be used with the secrets, and various optional policies associated with the CC.
(((Cryptographic Context, Metadata Header)))
The Content has an Algorithm-specific format and holds the secrets and other sensitive material, as well as a representation of the Algorithm's state.
(((Cryptographic Context, Content)))
The Metadata requires integrity, except for explicitly identified non-authoritative format hints such as _ADSDropped_ and layout-preserving fields that the hint makes semantically inactive; the Content requires both integrity and confidentiality.
These requirements are architecturally enforced by ACE and by the algorithms it implements.

Cryptographic Register:::
(((Cryptographic Register)))
To create CCs, ACE uses *Cryptographic Registers* (CRs), per-hart architectural containers that safeguard their contents.
A CR is *provisioned* by writing Metadata and Content into it; this operation binds the latter to form a CC.
There is no store-like instruction to extract the Content of the CR in a manner that compromises its confidentiality.
A CC may be used for cryptographic operations only while resident in a CR.
Only the ACE unit may access or modify a CC residing in a CR, in accordance with the rules set by the architecture and by the Algorithm bound to the CC.

Sealed Cryptographic Context:::
(((Cryptographic Context, sealed)))
To support context switching while protecting CCs outside architectural state, a CC may be *exported* from a CR as a *Sealed Cryptographic Context* (SCC)—an encrypted and authenticated representation of a CC that can later be *imported* into a CR. Export and import use a _Context Sealing Key_ (CSK), which may be programmable by M-mode. An SCC sealed under one CSK cannot be imported under a different CSK, providing cryptographic domain separation across spatial and temporal domains.

Algorithm:::
(((Algorithms)))
(((Cryptographic Context, object-oriented)))
An *Algorithm* (written with an upper-case "A")
is a state machine that performs cryptographic operations through the interface defined in this specification.
In the metadata of a CR, it is encoded as 16 bits of information.
ACE provides a small set of instructions for interacting with these state machines.
These instructions take the 16-bit identifier from the CR's metadata, along with standard RISC-V inputs and outputs such as GPRs, vector registers, and memory. Their semantics depend on the selected Algorithm. Consequently, a CC in a CR encapsulates Algorithm-specific behavior, allowing different primitives (e.g., AES-128, AES-256, and SM4) to be used interchangeably in the same modes (e.g., ECB, GCM-SIV, and XTS) without changes to the compiled code. Side-channel-attack-resistant variants are supported transparently.

Usage Control Policy:::
(((Cryptographic Context, usage control)))
(((Cryptographic Context, management operations)))
(((Cryptographic Context, usage operations)))
ACE distinguishes between CC/CR *management* and *usage* operations.
(((Cryptographic Context, export)))
Management operations include *configuration* (e.g., CR provisioning, SCC import, and cloning), *export* of a CR as an SCC, and *clearing* a CR.
Usage operations include cryptographic operations and state changes.
To prevent denial-of-service scenarios, management operations, in particular configuration operations, are less restricted than usage operations. _Usage Control_ policies restrict only certain CC/CR usage operations.

Localities:::
(((Cryptographic Context, Locality)))
ACE can bind CCs to *Localities*, i.e., restrict usage to specific devices or device classes, hardware configurations, physical or virtual boot cycles, and process domains at various privilege modes. This binding is achieved by using the Localities as _tweaks_ in the encryption and decryption of SCCs.

[[ACE-architectural-model]]
==== Architectural Model

ACE is architected as an interface to an _attached_ unit. ACE instructions are modeled as messages sent over a tightly coupled coprocessor interface. The ACE unit receives operations from the issuing hart, executes them independently, and returns results.
This model minimizes hart-side implementation complexity: for instance, software implements the logic for CR configuration instructions, while the ACE unit implements cryptographic operations.
This allows multiple cores to share an ACE unit, with separate architectural state for each hart, while minimizing the hardware footprint.

The specification only defines the architectural behavior, not implementation.
ACE may be integrated into a CPU core or implemented as a distinct hardware unit, with separate architectural state for each client hart, and both approaches will be supported by the same code.

ACE may be partially or completely emulated in M-mode firmware.
For example, an implementation may perform symmetric cipher operations (cf. <<ACE-states-symmetric>>) in the ACE unit while emulating public-key cryptography (cf. <<ACE-ECC>> and <<ACE-PQC>>).
Public-key primitives may require very large states. Emulating them in M-mode firmware avoids storing those states in the ACE unit, provided that the relevant CRs reside in secure memory such as on-chip SRAM reserved to M-mode (see <<ACE-CRF>> for the requirements of this memory).

CR state must never be accessible in the clear to any privileged mode except M-mode and authenticated Debug mode.
This forbids ACE implementations in S/VS-mode or HV-mode.
Instructions and Algorithms may be emulated only in M-mode.
Trap-and-emulate and on-demand (lazy) SCC import rely on the ``*lcrstatus`` CSRs (cf. <<ACE-CSR-lcrstatus>>).

* `ace.mgmt` (<<ACE-instruction-mgmt>>) transitions a CR between stages of its management lifecycle, and,

* `ace.exec` (<<ACE-instruction-exec>>) performs cryptographic operations as specified by the Algorithm configured in a CR and according to the state of the CR.
* `ace.setst` (<<ACE-instruction-setst>>) transitions a CC inside a CR between states of an Algorithm.
* `ace.getmd*` (<<ACE-instruction-getmd>>) reads the metadata of a CR; `ace.getmdl` is used to implement the pseudo-instruction `ace.getst` (<<ACE-instruction-getst>>), which extracts the state of a CR from the MDH of a CR. `ace.getst` also provides error reporting.

=== Programmer-Visible Architectural State

[[ACE-cryptographic-registers]]
==== Cryptographic Registers

{empty}
(((Cryptographic Context)))
ACE defines 32 Cryptographic Registers (CRs), numbered 0 to 31 and denoted `K0`–`K31`.

CRs are per-hart architectural state, like GPRs or vector registers.

CRs are not separated by privilege Mode: when a hart changes Mode, it sees the same set of CRs.

Unlike a conventional register, a CR can be _unconfigured_, meaning it does not contain a CC.

A CR is addressed either directly, via a 5-bit immediate, or indirectly, via a GPR value; an additional instruction-encoding bit selects the mode.

[NOTE]
====
Indirect CR addressing implies that CR renaming, while still possible, would significantly increase microarchitectural complexity.
We posit that CR renaming is not expected to be necessary, and may even be detrimental, for ACE.
First, excluding internal state changes, CRs are redefined far less frequently than GPRs or FP registers, and
conditional situations where a CR may take one key or a different one are uncommon.
Second, speculating on the results of cryptographic operations usually leads to security issues.
====

As described in <<ACE-concepts>>, the CC in each configured CR consists of a Metadata Header (MDH) and `Content`.
The _i_-th CR is denoted `K(i)`, its MDH `K(i).MDH`, and its content `K(i).Content`.
During provisioning and in derived import/export structures, `K(i).Content` is an array of 128-bit blocks.
During import and export, and in an SCC, this array is partitioned into two consecutive arrays of 128-bit blocks:
`Content1`, the architecturally defined content specified for each Algorithm in <<ACE-Algorithms>>,
and `Content2`, any implementation-defined content.

[[ACE-CRF]]
==== The Cryptographic Register File and Authentication Information

CRs reside in a dedicated, per-hart _CR file_ (CRF), a memory accessible only to the ACE implementation.
If the implementation is (partially) emulated, only M-mode firmware can access the CRF and an implementation-defined mechanism to access the CRF must be provided.
(((Cryptographic Register File)))

The CRF guarantees the confidentiality and integrity of its contents, including protection against rollback through any access not explicitly permitted by this specification.
CRF accesses do not require hardware-level hardening against physical side-channel attacks.
However, side-channel-protected implementations of Algorithms in the ACE unit must protect also the CRF accesses.
It is recommended that `SCC_KeyDeriv`, `SCC_Encrypt`, `SCC_Decrypt`, and every use of the CSK and of the keys derived from it, be implemented by the ACE implementation with side-channel protection not weaker than the highest _SCProtection_ level, under the implementation's ordering, that it supports for any Algorithm.

NOTE: While the CRF, as a memory device, must resist rollback attacks, individual CRs do not have to resist rollback via export and import, and cannot.
While re-importing previous CC states may allow multi-time pad attacks on modes such as CTR, XCTR, and GCM, exploiting this would require a level of control over the target software that typically also implies access to plaintext.
Reuse of an internal random value through re-import or cloning is excluded by Rule <<ACE-GR-atomic-randomness>>.
Re-importing a previous CC state is also desirable, however. For instance, it allows restarting an operation that failed because a payload was corrupted in transit. Adding and enforcing policies to control resumability and cover every legitimate case would overcomplicate the feature.

Architecturally, the CRF contains:

. An array of 32 128-bit blocks, where the _i_-th entry contains the MDH of `K(i)`.
. An implementation-defined amount of memory that can be dynamically allocated to the various registers. This region contains the
   `Content` sections of all configured CRs.

These two types of information are conceptually distinct, regardless of implementation.
The MDH array is always present and is not subject to allocation, so every CR always holds its MDH, even if only to signal that the CR is not configured.
Only the second part is dynamically allocated and capacity-limited; “CRF capacity” refers only to this part.
A CR that holds only its MDH therefore consumes no CRF capacity.

The amount of CRF capacity consumed by each CR depends on the Algorithm encoded in the MDH, and it may differ from one CR to another.

Insufficient residual CRF capacity may prevent execution of a configuration instruction.

Capacity is freed by unconfiguring other CRs.

The corruption of a hart's CRF is an unrecoverable error condition.
The ACE architectural state associated with the hart is then reset (<<ACE-reset-and-m-mode-only>>), and ACE exception `ace_exc_fatal` is raised (see <<ACE-exceptions>> and <<ACE-error-architecture>> for the behavior when the Privileged Architecture is not implemented).

A hart reset resets the ACE state of the hart; on power down, that state is zeroized.

The ACE unit holds three 128-bit registers which hold authentication data (the `SIV`, `IMPQUAL`, and `SIV2`) of the CR being currently managed. These registers are accessed using the `ace.load`, `ace.store` and `ace.mv` instructions, as the leading bytes of the image they transfer (<<ACE-instruction-load>>).
They are zeroized by an ACE unit reset, by `ace.clear.all`, and by an `ace.mgmt` that opens an import; the `ace.mgmt` that opens an export of a CR in a Valid State writes `SIV` and, when _AuxDataLen_ {ge} 2, `IMPQUAL` and `SIV2`.

[NOTE]
====
The 128 or 384 bits used to hold `SIV`, `IMPQUAL`, and `SIV2` are allocated per hart and not per CR to reduce their hardware cost.
This prevents concurrent non-clearing management operations in the same code: starting a second operation may overwrite the first operation's in-flight `SIV`, `IMPQUAL`, and `SIV2` values.
In a single process space, multiple such operations require careful coordination such as lightweight threads with ACE context-switching support or serialization using a mutex.
Clearing and provisioning a CR do not touch `SIV`, `IMPQUAL`, and `SIV2` and are thus not subject to these restrictions.
====

==== Providing Inputs and Outputs

[[ACE-ACEV]]
===== RVV/ACEV

ACE inputs and outputs may use vector registers or an architectural input/output buffer (ACEIOBUF)
that can be loaded from and stored to external memory. Both mechanisms may be supported simultaneously.

When vector registers are used, the full V extension is not required. ACE depends only on a minimal subset, termed _ACEV_.
(((ACEV)))
ACEV must be fully opcode-compatible with RVV: code written for ACEV executes with identical behavior under V together with Zvbc.
The current set of features is:

* Vector registers of at least 128 bits.
* Configuration-setting instructions (`vsetvli`/`vsetivli`/`vsetvl`):
** ACE does not use vector masking and does not define masked versions of its instructions.
Therefore, ACEV only requires tail-agnostic and mask-agnostic configurations, and ACE operations on vector registers always use a tail-agnostic policy;
Bit 25 of the `ace.exec` instruction encoding is reserved for potential future adoption of masked operations, should a compelling use case arise.
** Support for `LMUL` integer values of 1, 2, 4, and 8;
** A `vsetvl`/`vsetvli`/`vsetivli` requesting a configuration ACEV does not support sets `vtype.vill` and `vl` = 0, as in RVV; an ACE instruction with a vector operand issued while `vtype.vill` is set raises an illegal-instruction exception.
* Unit-strided vector loads and stores;
* `vmv.x.s` and `vmv.s.x` and the slide instructions `vslideup.v[xi]`, `vslidedown.v[xi]`, `vslide1up.vx`, and `vslide1down.vx`, to insert data into and extract data from vector registers;
* Vector logical operations: `vand.v[vxi]`, `vor.v[vxi]`, and `vxor.v[vxi]` (the immediate variants allow obtaining, for instance, a bitwise NOT); and
* `vclmul.v[vx]` and `vclmulh.v[vx]` from `Zvbc`. They may be implemented as trap-and-emulate.

NOTE: ACE does not depend on a concept of element.
From a logical point of view, the operations are not performed in the vector unit.
A vector register (group) is seen as a bit string of length `ACELEN` = `VL` * `SEW`, where `VL` is the vector length in effect (`vl`).

Floating-point, fixed-point, and general arithmetic vector operations are not required.

When vector registers are used, ACE determines the lengths of its operands from `VL*SEW`.
The specific choice of `VL` and `SEW` is irrelevant; for example, `VL` = 2, `SEW` = 64 and `VL` = 4, `SEW` = 32 both define a 128-bit input.
The CPU instruction-decoding side of ACE uses `VL` and `SEW` to determine how much data to send to the ACE unit proper, but the ACE unit itself requires only the product `VL*SEW` (or `aceiobuftop`).

===== ACEIOBUF

ACEIOBUF is an optional architectural input/output buffer that may be used in place of vector registers.

ACEIOBUF is not part of the CRF.

Two instructions, `ace.input` and `ace.output`, load and store data from/to the ACEIOBUF to/from the external memory.
When the ACEIOBUF is used, `ace.exec`, `ace.setst` and `ace.mgmt` are used in forms with implicit input and output provided by the ACEIOBUF, as described in <<ACE-usage-input-output>>.

The definition of `ACELEN` for ACEIOBUF inputs is given in <<ACE-CSR-aceiobuftop>>.

[[ACE-Metadata]]
==== Metadata

ACE recognizes two types of metadata that may be contained in a CC or associated with it.

. A 128-bit _MDH_ that determines the Algorithm, the type of key, and various usage policies associated with the key.
This information is always present in a CC.
The fields are arranged so that the first 64 bits suffice to determine the length of a PI or SCC.

. An optional 128-bit _Implementation Qualifier_ block, denoted by `IMPQUAL`.
It holds copies of three architectural registers that are the ACE analogues of the hart's `mvendorid`, `marchid`, and `mimpid` CSRs (see <<ACE-CSR-impl-ids>>).
This qualifier appears when an SCC has _AuxDataLen_ {ge} 2, including when its implementation-specific content segment has been dropped but its header layout is retained.
An implementation uses it to decide whether it can use the implementation-specific content segment when that segment is present. When _ADSDropped_ = 1, the retained `IMPQUAL` and `SIV2` blocks are non-authoritative layout-preserving values and are ignored.

This section deals with the 128-bit MDH.
Its fields are summarized in <<ACE-metadata-header>>.
All _Reserved_ bits, as well as bits unused by a given Algorithm, are zero.

[[ACE-Algorithm-field]]
===== _Algorithm_ and _AlgorithmPolicy_ Fields

Algorithms are encoded in a 12-bit field.
Values 0–3071 are architecture-defined.
The list of encodings is maintained by RVI (see <<ACE-Algorithms>>).
The remaining values are available for custom Algorithms.

For encryption/decryption primitives and modes, the _AlgorithmPolicy_ field indicates whether the CC may be used for encryption (lower bit set), decryption (upper bit set), or both. At least one of the bits must be set.

For asymmetric primitives supporting signatures, the lower bit permits signature generation and the upper bit permits verification. In this case, both bits may be zero.

For other primitives, the _AlgorithmPolicy_ field may encode additional Algorithm identifiers to expand the effective encoding space of the _Algorithm_ field.

===== _SCProtection_ Field

[[ACE-KeyType-field]]
===== _KeyType_ Field

This field takes the value 0 if the key is given by an explicit value, and 1 if the key is given by a system-specific, 64-bit System Key Identifier (SKID).
Values 2 and 3 are currently reserved: a PI or SCC whose _KeyType_ carries one of them is invalid Metadata (see <<ACE-MVR-open>>). See <<ACE-system-keys>>.

If the value is 0, keys are provisioned, exported, and imported by value.

If the value is 1, keys are provisioned, exported, and imported as a System Key Identifier (SKID), except for the all-ones (i.e., `ones(64)`) SKID value.

If the SKID is the all-ones value, the key material is randomly generated when provisioning completes, and the CR's _KeyType_ field is then set to 0, so that the key is thereafter exported by value.
Unless otherwise specified, random generation applies to all keys in an Algorithm at once.

NOTE: A system key identifier may refer to keys with unrelated purposes on different devices; see <<ACE-system-keys>>.
The SKS supplies an appropriate _Locality_ (see <<ACE-Localities>>) during CR provisioning to bind the key to the system (<<ACE-system-keys>>).

[[ACE-State-field]]
===== _State_ and _StateExtension_ Fields

The _State_ field is used to track the current state of a CR and of the Algorithm encoded in its MDH.
Examples include whether the CR is _Unconfigured_, encrypting or decrypting data, initializing a hash function, absorbing data in it, and finalizing the digest,
computing elliptic curve point multiples, generating or verifying signatures, or is in an error state.

The _StateExtension_ field can be used by an Algorithm to store additional state information, usually orthogonal to the _State_ field, such as whether certain values have been provisioned or computed.

State 0 is the _Unconfigured_ state.  It denotes that the CR is unconfigured.
When a CR is in the _Unconfigured_ state, no other field of the MDH has a meaning and it reads zero.
For instance, there are no Usage Policies, Expiration Dates, or Key Types on _Unconfigured_ CRs.

States 1–55 are called _Complete_.
They include States from 1–47, which are called _Valid_, and
(((ACE, Algorithm, error states)))
States 48–55, which are termed _Error States_. The latter are used to report ACE errors.
State 1 is the _Ready_ state.

(((ACE, Algorithm, partial states)))
States 56–63, i.e., the states used during management operations, are called the _Partial States_, and are exactly the States that are neither _Unconfigured_ nor Complete.

The architected values of _State_ common to all Algorithms are defined in <<ACE-State-management>>.

// ////////////////////////////////////////////////////////////////////

[[ACE-Auxiliary-Data-Section]]
===== _AuxDataLen_ and _ADSDropped_ Fields

The _AuxDataLen_ MDH field records the length of the _Auxiliary Data Section_ (ADS) of the content, a variable-size, implementation-dependent part, as a number of 128-bit blocks. When _ADSDropped_ = 1, it retains the length of the ADS before `Content2` was dropped. Zero means that no ADS is present. The value 1 is invalid. The maximum value is 2^14^-1, corresponding to 262128 bytes.

If _AuxDataLen_ {ge} 2, a copy of the implementation qualifier from the originating machine

``{fournbsp}{fournbsp}IMPQUAL := zeros(32) @ acemimpid @ acemarchid @ acemvendorid``

(cf. <<ACE-CSR-impl-ids>>) is included in the SCC.
These 16 bytes, as well as a separate authentication tag for the ADS are counted within the length recorded by the _AuxDataLen_ field. The importing implementation uses this value to determine whether the ADS can be used.

Since an ADS contains at least an authentication tag (16 bytes) and the originating implementation qualifier (also 16 bytes), the minimum length is 32 bytes, corresponding to an _AuxDataLen_ value of 2.

_ADSDropped_ is an unauthenticated format hint, ignored when _AuxDataLen_ = 0. When _AuxDataLen_ {ge} 2 and _ADSDropped_ = 1, `Content2` is absent, while `IMPQUAL` and `SIV2` remain as non-authoritative padding so that the `Content1` offset does not change. First-segment authentication clears bit 47 only in its local MDH copy.

Toggling _ADSDropped_ cannot affect `Content1` or any policy. Setting it drops optional `Content2`; clearing it requests second-segment processing, whose failure drops `Content2` without rejecting authenticated `Content1` (<<ACE-SCC-import>>). Manipulation can therefore cause optional ADS loss or an unsuccessful second-segment attempt, but cannot make unauthenticated `Content2` usable or bypass first-segment authentication.

// The format of the ADS is described in <<ACE-data-formats>>.

[[ACE-UsagePolicy]]
===== _UsagePolicy_ Field

The _UsagePolicy_ field determines which modes are allowed to use the CR.

Bits 0, 1, 2, and 3 of the field, when set, disallow CC usage in U-mode, VS-mode, HS-mode, and M-mode, respectively. Bit 4 grants usage in Debug mode only if set. Bit 0 governs both U-mode and VU-mode, and bit 2 governs S-mode whether or not the H extension is implemented.

Any bit of this field is ignored if the corresponding mode is not supported or not enabled.

[[ACE-Localities]]
===== _Locality_ Field

The _Locality_ field identifies 128-bit Locality Secrets (LSs) listed in <<ACE-locality-indexes>>. The LSs are stored in a (possibly virtual) Locality Secrets Table (LST). Some entries are fixed or configurable only through an implementation-specific, authenticated hardware process. These entries are shared by all ACE units in the same SoC. The remaining entries are software-programmable, per-hart architectural state.

At SCC export and import, any Locality defined by the _Locality_ field cryptographically binds an SCC to the corresponding _current_ hardware and software environments. This binding ends when the SCC is imported into a CR. If a Locality Secret later changes, a subsequent export binds the SCC to the new value. Software is responsible to prevent unauthorized parties from directly accessing CRs.

<<ACE-locality-indexes>> lists the architected Localities. Eleven LST entries are defined. Entries 0–5 form the _HW Binding Group_, which binds SCCs to the hardware; entries 6–7 form the _Boot Session Group_; and entries 8–10 form the _SW Filter Group_. For each Locality, the table specifies its LST index, domain (SoC-wide, device-wide, VM-wide, or per-process), configurability, bit-field encoding, and value.

[[ACE-Metadata-locality-interoperability]]
===== Interoperability under _Locality_ configurations

_This section is informative and non-normative._

The SW Filter Group binds an SCC to the software that exports it. The register behind each entry depends on the mode:

[float="center",align="center",width="100%",cols="<40%,<30%,<30%",options="header"]
|===
| Mode of the export or import | Entry 9 (_HLocality_) | Entry 10 (_SLocality_)
| S or U, no H extension | unconfigured | `sacelocality`
| VS or VU (V=1) | `hacelocality`, set by the hypervisor for the VM | `vsacelocality`
| HS or U with the H extension (V=0) | `hacelocality` of the VM loaded | `sacelocality` of the hypervisor
| M | `hacelocality` of the VM loaded (unconfigured without the H extension) | `sacelocality`
|===

Four scenarios illustrate this:

An OS becomes a guest.::: An OS runs on a hart without the H extension and sets `sacelocality`. Its state and the SCCs it exported are cloned into a virtual machine, which resumes under a hypervisor. The OS still writes `sacelocality`, now reaching `vsacelocality`, so entry 10 keeps its value; entry 9 was unconfigured before cloning and cannot have been named. The SCCs exported before cloning therefore import unchanged, whatever the hypervisor holds in `sacelocality` and `hacelocality`, provided the new host has the same CSK (<<ACE-CSK-requirements>>) and the CCs are not bound to the HW Binding Group, _MLocality_ or _PhysBootScrt_, which exist to prevent such migration; _VirtBootScrt_ was unconfigured too.

A hypervisor separates its virtual machines.::: The hypervisor may give each virtual machine a distinct `hacelocality`, which the guest can neither read nor write. A guest that names _HLocality_ binds its SCCs to its machine, so the SCCs of two machines differ even when the guests, cloned from one image, hold the same `vsacelocality`.

A hypervisor saves and restores guest CRs, or hands a CC to a guest.::: At V=0, entry 9 is the `hacelocality` of the machine loaded and entry 10 the hypervisor's `sacelocality`. A save and its restore are performed at the same level, so their bindings match. Before saving, the hypervisor configures `hacelocality` for the machine and, if a guest CC names _SLocality_, its own `sacelocality`, to which that export is bound; an unconfigured entry makes the restore fail as invalid Metadata. To hand a CC to a guest, the hypervisor provisions it naming _HLocality_: the export at V=0 binds it to the tag of the machine, and the import at V=1 uses the same block. A CC naming _SLocality_ cannot cross levels this way, since entry 10 denotes a different register at each level.

Migration between hosts with the H extension.::: The guest's `vsacelocality` travels with its VS CSRs, and its `hacelocality` with the identity of the machine, for the destination hypervisor to install before the guest runs; each hypervisor keeps its own `sacelocality`. The SCCs of the machine then import on any host with the same CSK.

In every mode the three entries denote three different registers; no ordering or exclusivity among `macelocality`, `hacelocality`, `sacelocality` and `vsacelocality` is required. Host software running under a hypervisor does not name _HLocality_, whose value follows the virtual machine loaded. The same holds for _VirtBootScrt_, whose register the hypervisor sets for the machine loaded.

[[ACE-Metadata-expiration-date]]
===== _ExpirationDate_ Field

This field is only in effect if extension _Zklexpire_ is supported.

If _Zklexpire_ is supported, the ACE implementation must have access to a secure clock.

If _Zklexpire_ is not supported, a non-zero _ExpirationDate_ in a PI or SCC is invalid Metadata (see <<ACE-Metadata-validity>>).

If non-zero, the 20-bit _ExpirationDate_ field specifies the CC's expiration time as whole hours elapsed since 00:00 UTC on 1 January 2027. The maximum representable time span is approximately 119 years and 7 months. The epoch is UTC so that a CC exported on one device and imported on another expires at the same instant regardless of the local time each observes.

[NOTE]
====
This specification cannot enumerate requirements for a trustworthy clock, as
what constitutes adequacy depends on threat models, platforms, and integration
specifics — a challenge common to all time-dependent security features. As a rule
of thumb: *if a clock is adequate for M-mode security features or an on-SoC TPM, it is adequate for ACE.*
ACE imposes no stricter requirements. Crucially, software below M-mode must not be able to set the
clock, as that would allow indefinite extension of a CC's lifetime by moving
time backward.
====

This section is the only authoritative statement in this specification of when the _ExpirationDate_ field is evaluated.

The _ExpirationDate_ field is evaluated normatively at the following points:

* At issue of any `ace.exec`, usage-controlled `ace.setst`, or `ace.derive`.
* For `ace.derive`, both endpoints are checked.
* At every architectural resumption point.

The _ExpirationDate_ of a CR that is not in a Valid State is not evaluated.
A transition to Error State `ace_state_expired` is only triggered when an expired CR is being actively used, while still permitting expired contexts to be cleanly evicted, saved, or unconfigured.

The evaluation of _ExpirationDate_ is performed as follows:

. If _ExpirationDate_ is zero, the instruction may proceed.
. The date from the secure clock is converted to the format of the _ExpirationDate_ field; a reading earlier than 00:00 UTC, 1 January 2027 converts to 0.
. The converted date is then compared to the _ExpirationDate_ itself.
. If the converted value is not smaller than the _ExpirationDate_, the ACE implementation transitions the CR's _State_ field to Error State `ace_state_expired`.
. Otherwise, the instruction may proceed.

[[ACE-Algorithm-version]]
===== _Version_ Field

This two-bit field denotes the version of the MDH format.

If _Version_ = 0, then the format is the current version.

The value _Version_ = 1 is used to denote newer revisions of the MDH format.
Additional version information must be encoded in other fields of the MDH.

If _Version_ = 3, the format is system-specific.
System-specific formats are allowed only for import operations.
Any such format must be preceded by an ACE-format MDH to allow import to begin.
The system-specific format may contain its own usage and access policies or locality bindings.
This information must be converted to an ACE-compatible representation without weakening any usage policy or locality binding.
When `ace.mgmt` completes import, the MDH policies may be replaced accordingly.
_Version_ is then set to 0 (or 1 in a future version of this specification).

Support for loading system-specific formats is optional.
The resulting CRs can be exported only in the ACE-specified format.
To prevent loading on different implementations, specific localities may be set, or all information may be stored in the ADS to gate it using IMPQUAL.

An implementation may support multiple system-specific formats;
The ACE specification does not specify how to distinguish between them: this is up to the implementation.

The value _Version_ = 2 is reserved.

A PI or SCC with a _Version_ not supported by the implementation
is invalid Metadata (cf. <<ACE-Metadata-validity>>).

[[ACE-Metadata-validity]]
===== Validity of Metadata

Metadata is _unsupported_ when the combination of _Algorithm_, _AlgorithmPolicy_ and _SCProtection_, or a non-zero _AlgorithmExtension_, is not implemented.

Metadata is _invalid_ when a Reserved bit is non-zero; _AuxDataLen_ is 1; _ADSDropped_ is non-zero in a PI or in a PCCC whose Configuration State has base type `pi`; _AlgorithmPolicy_ is zero for an Algorithm that requires a bit; _KeyType_ is 2 or 3; _Locality_[5:4] is 3, or _Locality_ names an unconfigured Locality Secret (<<ACE-Localities>>); _AuxInfo_ is non-zero for an Algorithm that does not use it; _ExpirationDate_ is non-zero and `Zklexpire` is not implemented; _Version_ is unsupported; the MDH carries a custom value without _ChipFamScrt_ or _ChipScrt_ in _Locality_ (Rule <<ACE-GR-custom-locality>>); _AuxDataLen_ is non-zero in the MDH of a PI or in a PCCC whose Configuration State has base type `pi`; or, in a supplied MDH, _State_ is not _Unconfigured_ at provisioning, or is _Unconfigured_ or 61–63 at import (cf. <<ACE-State-management>>).

[horizontal]
[[ACE-MVR-open, Metadata Validity Rule]] Metadata Validity Rule:: An `ace.mgmt` that opens a provisioning or import on unsupported Metadata raises ACE exception `ace_exc_unsupported`; on invalid Metadata it transitions the CR to Error State _Invalid_.
These checks are not applied to the short import of an Error-State MDH (<<ACE-error-state-transfer>>).
The CR also transitions to Error State _Invalid_ when, at completion of provisioning, import or export, the System Key Store does not resolve a SKID other than the all-ones value, or the `Content1` of an SCC whose restored _State_ is a Complete State carries the all-ones SKID.

[[ACE-Memory-Alignment]]
==== Memory Alignment Constraints

All accesses to the `Content` of a CR have a 16-byte granularity: `ace.load`, `ace.store` and `ace.mv` transfer whole 16-byte blocks, and every offset and length they use, `acestart`, `content_size`, `max_admissible`, `image_size` and `image_end` (<<ACE-instruction-load>>), is a multiple of 16 bytes.

The effective address of an `ace.load` or an `ace.store` must be a multiple of 16 bytes.
If it is not, no data is transferred and a load, resp. store, address-misaligned exception is
raised on that address.
A PI or an SCC must therefore be held at a 16-byte aligned address.
For `ace.load` and `ace.store` the conditions are evaluated in this order: the illegal-instruction grounds of both groups and the ACE exceptions, in the order of <<ACE-exception-codes>>; the address breakpoint of the first component access, if any; address-misaligned on the effective address; then, per component access in offset order, address breakpoint, and access, page and guest-page faults. The address-misaligned check is performed also when the transfer window is empty.

`ace.input` and `ace.output` are byte-granular and impose no alignment constraint of their own:
a misaligned effective address behaves as it does for an ordinary load or store on the
implementation.

There are no atomicity requirements for any ACE memory instruction.

[[ACE-error-architecture]]
==== Error Handling Architecture

Without the ACE Privileged Architecture, which only an M-mode-only hart may omit, the ACE
exceptions are replaced by the behaviors of <<ACE-exception-error-correspondence>>, listed in their
natural priority order.

[[ACE-exception-error-correspondence]]
.Behavior upon exception conditions when the Privileged Architecture is not available.
[float="center",align="center",cols="<1,<2",options="header"]
|===
| ACE Exception                      | Behavior when the Privileged Architecture is not available.
| `ace_exc_fatal`                    | Implementation and platform defined behavior.
| `ace_exc_no_csk` (See <<ACE-CSK-requirements>> and <<ACE-CSR-macecsk>>.) | The instruction raises an illegal-instruction exception; on an M-mode-only hart M-mode is both the only mode that can observe it and the only one that can establish a CSK.
| `ace_exc_CR_off` (See <<ACE-CSR-lcrstatus>>.)| Does not apply without Privileged Architecture, since the `*lcrstatus` CSRs are not available.
| `ace_exc_unsupported`              | Transition to Error State _Unsupported_.
| `ace_exc_out_of_memory`            | Transition to Error State `ace_state_out_of_memory`.
| `ace_exc_privilege_violation`      | Transition to Error State `ace_state_priv_violation`.
| `ace_exc_unconfigured_buffer`      | The instruction raises an illegal-instruction exception.
|===

For `ace.clone` and `ace.derive`, which name two CRs, the behavior above and the handler's duty
below concern the CR on which the exception is raised: for `ace.clone`, the source for
`ace_exc_privilege_violation` and the destination for `ace_exc_out_of_memory`; for `ace.derive`,
the endpoint on which the failing check is detected, each check being applied to the source before
the destination (Rule <<ACE-SGR-gate-order>>).

With the Privileged Architecture, the transition is the duty of the exception handler. A handler
that cannot resolve `ace_exc_unsupported`, `ace_exc_out_of_memory` or
`ace_exc_privilege_violation`, cannot forward it to another handler, including an in-process
handler, and does not suppress the process that caused it, must:

. set the _State_ of the CR on which the exception was raised to the corresponding Error State of
  <<ACE-exception-error-correspondence>>, using the short import of <<ACE-error-state-transfer>>
  where the instruction left the CR _Unconfigured_, as Rule
  <<ACE-SGR-transition-to-from-unconfigured>> requires; and
. resume execution at the instruction following the trapping one by advancing `xepc`, since
  otherwise the same exception is raised again. A handler that advances `xepc` past a usage
  instruction should write zeros to its output operand, as the instruction would have done had it
  performed no operation (Rule <<ACE-SGR-usage-cr-error-state>>).

Elsewhere, including <<ACE-Algorithms>>, <<ACE-priv>> and <<ACE-pseudocode-examples>>, behavior is
described with the Privileged Architecture in effect; without it, the behaviors above replace the
exceptions.

[horizontal]
State change rule for exceptions:: An illegal- or virtual-instruction exception, or an ACE
exception other than `ace_exc_fatal`, makes no change to ACE state, except the zeroizing of the
target CR by an opening `ace.mgmt`, which is performed even if the instruction later raises an
exception (<<ACE-CR-management>>). `ace_exc_fatal` resets the ACE state (_Fatal Conditions_ below).

The categories of error conditions are:

Fatal Conditions:::
+
--
Fatal conditions have the highest priority among the ACE-specific error categories, and no CPU
state disables their detection. The main one is an integrity failure of the CRF of a hart
(<<ACE-cryptographic-registers>>); implementations may define others.

A fatal condition causes an ACE unit reset of the hart
(<<ACE-reset-and-m-mode-only>>) and then
raises ACE exception `ace_exc_fatal`, whose trap is taken only after the reset completes
and is not delegable below M-mode. The reset differs from an ordinary one in three ways:

. `misa.L` keeps its value, and every `ACES` field that is not Off becomes Dirty rather than Off,
  so that `ace_exc_fatal` can be reported, the modes below M-mode are not silently disabled, and
  context-switching code discards its stale saved state;
. every `*lcrstatus` field becomes _Dirty_ rather than _Initial_, as on entry into unauthenticated
  Debug mode (<<ACE-interaction-with-debug>>);
. the masks that unauthenticated Debug mode installs are not lifted.

A CSK generated at boot under the fourth model of <<ACE-CSK-requirements>> is shared by the harts of
its subsystem and is not regenerated.

Detection and reset may be synchronous or asynchronous, the condition being recorded in the ACE
unit. The first ACE instruction or ACE CSR access issued, or in flight, after detection performs no
operation and raises `ace_exc_fatal`, with `xepc` holding its address. If, at detection, an `ACES`
field in effect is Off or the ACE bit of an `*stateen0` CSR in effect is clear, the condition is
retained and reported on the first ACE instruction or ACE CSR access that is not illegal or virtual
on those grounds; until then such instructions raise an illegal- or virtual-instruction exception,
which <<ACE-exception-codes>> ranks above `ace_exc_fatal`. Detection is thus never disabled; only
its reporting is deferred.
--

[[ACE-illegal-instruction-grounds,Grounds for Illegal-Instruction Exceptions]]
Grounds for Illegal-Instruction Exceptions:::
+
--
The grounds for an illegal- or virtual-instruction exception form two groups:

* In the first group, the grounds come from the instruction encoding, the GPRs and the vector
  configuration alone, without accessing the state of the ACE unit, and therefore take precedence
  over `ace_exc_fatal` (<<ACE-exception-codes>>):

. A reserved encoding, including `ace.setst` with `#immed7` 46 or 47, `ace.mgmt` with `#immed7` in 59–62 or in Form B, a reserved `#immed7` of `ace.setst` with `r` = 1 and CR register `X0` (<<ACE-instruction-setst>>), and an ACE instruction with a vector operand issued while `vtype.vill` is set (<<ACE-ACEV>>).
. An indirect CR index outside [0..31], or `X0` used as one where not expressly encoded (Rule <<ACE-GR-GPR-indirect>>), and `ace.derive` with equal CR indices (<<ACE-instruction-derive>>).
. A GPR pair or quartet not meeting Rule <<ACE-GR-multiple-GPRs>>.
. A vector operand carrying an MDH with `VL` {times} `SEW` < 128 (Rule <<ACE-GR-vector-MDH-operand>>), or a vector `ace.mv` whose `vl * (SEW/8)` or `vstart * (SEW/8)` is not a multiple of 16 (<<ACE-instruction-mv>>).
. An encoding assigned to an extension that is not implemented, for instance as Forms A–C of `ace.exec` without `Zklv`.
. An ACE instruction or ACE CSR access gated by a clear `Smstateen` bit (<<ACE-CSRs-priv>>), which raises an illegal- or virtual-instruction exception as that extension prescribes; an ACE instruction issued while `ACES` is Off (see _Fatal_ above), an ACE instruction issued under big-endian effective data endianness (<<ACE-Notation>>), and an access to a CSR that <<ACE-CSRs-unpriv>> declares unavailable or that <<ACE-CSRs-priv>> makes inaccessible from the current mode (an illegal- or virtual-instruction exception, as stated there).

* In the second group, the grounds require the state of the ACE unit: for most of them the
  contents of a CR, which for a CR marked _Off_ (<<ACE-CSR-lcrstatus>>) exist only once it has been
  lazily loaded, or in the M-mode code that emulates it. They are evaluated only after
  `ace_exc_no_csk` and the _Off_ gate, once the CR is loaded or by the emulator, and only if no
  fatal condition is pending, `ace_exc_fatal` being raised otherwise:

. A usage-controlled instruction issued on a CR in State _Unconfigured_ (Rule <<ACE-SGR-transition-to-from-unconfigured>>), including `ace.derive` with an _Unconfigured_ endpoint.
. `ace.load`, `ace.store` or `ace.mv` on a CR whose _State_ does not admit the transfer, or with an inconsistent `acestart` (Rules <<ACE-SGR-ace-load-mv-allowed>> and <<ACE-SGR-ace-store-mv-allowed>>).
. `ace.mgmt` when `acemanagedcr` names another CR, when opening an export on an _Unconfigured_ CR, when completing with an `ml`._State_ inconsistent with the CR's Configuration State, or when `ace_cfg_management_end` is issued with no management operation open (<<ACE-CR-management>>).
. An ACEIOBUF substitution that <<ACE-usage-input-output>> forbids, including any substitution without `Zklio`, since whether a Form is a substitution depends on the operation the CR's State defines.
. A Form A `ace.mgmt` that must take the MDH from a configured ACEIOBUF with `aceiobuftop` < 16 (Rule <<ACE-GR-vector-MDH-operand>>).
. An `ace.clone` whose source is _Unconfigured_ and differs from its destination (<<ACE-instruction-clone>>).
. A Form A–C `ace.exec` with `acestart` {ne} `vstart` {times} `SEW` / 8 (<<ACE-CSR-acestart>>).
. A Form A `ace.exec` with `Vd` = `Vs2` for an operation whose output blocks do not have the length of its input blocks (<<ACE-instruction-exec>>).
. If the Privileged Architecture is not implemented, an instruction issued without a CSK, or one that requires the ACEIOBUF while it is unconfigured or absent (<<ACE-exception-error-correspondence>>).
--

// Exceptions and State Changes::: [[ACE-exceptions-and-state-changes,Exceptions and State Changes]]
// When an ACE instruction raises `ace_exc_no_csk`, `ace_exc_CR_off`, `ace_exc_unsupported`, `ace_exc_out_of_memory`, `ace_exc_privilege_violation` or `ace_exc_unconfigured_buffer`, it has changed no ACE state, unless its description states a change that precedes the exception. `ace.mgmt` is the one instruction that does: it zeroizes the target CR before its checks.

Unsupported Algorithms:::
+
--
Unsupported Metadata at provisioning or import raises `ace_exc_unsupported` and leaves the CR
_Unconfigured_. A handler below M-mode that receives the delegated exception cannot emulate the
Algorithm and treats the exception as unresolvable.

An M-mode handler that emulates the Algorithm instead sets the CR's `*lcrstatus` field to _Off_
(<<ACE-CSR-lcrstatus>>): every later access to the CR that <<ACE-CSR-lcrstatus>> does not exempt
then traps, and the emulator, holding the CR in its own protected memory, services every operation
on it, including SCC import and export. For this it needs either the inputs of `SCC_Encrypt` and
`SCC_Decrypt` (<<ACE-SCC-AEAD>>) that it cannot otherwise obtain, namely the CSK and the Locality
Secrets of the HW Binding Group, or access to primitives that compute these functions on its
behalf, provided in an implementation-specific way. An implementation that provides neither cannot
emulate Algorithms, and reports `ace_exc_unsupported` to software instead.

An emulator keeps one copy per CR slot, and replaces it:

. at the next `ace_exc_unsupported` on that slot; or
. at an emulated `ace.clone` naming the slot as destination, which also clears the hardware CR of
  that slot and marks it _Off_, since the clone of an emulated CR is emulated too.

A copy orphaned by an instruction that <<ACE-CSR-lcrstatus>> exempts is never used again but lingers
until replaced, so an emulator that must not retain key material longer than necessary checks
`mlcrstatus` whenever it runs and zeroizes the copies whose _Off_ mark is gone.

`ace_exc_unsupported` is _not_ raised when accessing or using a CR in State `ace_state_unsupported`.
--

Algorithmic Errors:::
+
--
Algorithmic errors may occur:

. in import processes, as Error State `ace_state_import_auth`;
. in the Algorithms themselves, which may transition the CR to Error State _Invalid_ or to another
  Error State, as the Algorithm specifies.

The verification of an authentication tag by an AEAD Algorithm (_not_ by the SCC export and import
procedures), or of a signature, is _not_ an algorithmic error, whether it succeeds or fails: the
Algorithm has performed as expected.
--

[[ACE-CSR-impl-ids]]
===== `acemvendorid`, `acemarchid`, and `acemimpid`

{empty}
(((CSR, `acemvendorid`)))
(((CSR, `acemarchid`)))
(((CSR, `acemimpid`)))
`acemvendorid`, `acemarchid`, and `acemimpid` identify the version of the ACE unit, analogously to the `mvendorid`, `marchid`, and `mimpid` CSRs for the hart.

. Their values out of ACE unit reset identify the version of the ACE unit. Software cannot modify these values.

. The `acemvendorid` CSR is a 32-bit read-only register providing the JEDEC manufacturer ID of the provider of the ACE unit (or 0 if not commercial).

. The `acemarchid` CSR is a 32-bit read-only register encoding the base microarchitecture of the ACE unit.
Non-commercial IDs are allocated globally by RVI exactly as for the `marchid` values, while commercial IDs are specific to the `acemvendorid`.

. The `acemimpid` CSR is a 32-bit read-only register that provides a unique encoding of the version of the ACE unit implementation. This register must be readable in any implementation, but a value of 0 can be returned to indicate that the field is not implemented. The implementation value should reflect the design of the ACE unit itself and not any surrounding system. An implementation that produces an ADS must report a non-zero `acemimpid`.

These three CSRs, together, form the _Implementation Qualifier_ (see <<ACE-Auxiliary-Data-Section>>).

[[ACE-CSR-acemaxiobuflen]]
===== `acemaxiobuflen`

{empty}
(((CSR, `acemaxiobuflen`)))
`acemaxiobuflen` is an XLEN-bit RO CSR that reports the maximum configurable length of the ACEIOBUF in bytes.
The value is hardwired and specific to the implementation of the ACE unit.

If `Zklio` is implemented, `acemaxiobuflen` must be at least 16 bytes and at least as large as the largest basic processing unit (granularity) of any implemented Algorithm.

If `Zklio` is not implemented, the ACEIOBUF does not exist: `acemaxiobuflen` reads as zero, and the CSRs `aceiobuflen` and `aceiobuftop` are not present.

[[ACE-CSR-aceiobuflen]]
===== `aceiobuflen`

{empty}
(((CSR, `aceiobuflen`)))
`aceiobuflen` is an XLEN-bit URW CSR that programs the ACEIOBUF length in bytes for use by `ace.input` and `ace.output`.
Writing this register—even when re-writing the current value—also zeroes the buffer and sets `aceiobuftop` to the same length.

When `aceiobuflen` is zero, the ACEIOBUF is _unconfigured_.
Attempting to execute an operation that expects an input or an output in the ACEIOBUF while the latter is unconfigured raises exception `ace_exc_unconfigured_buffer`.

The maximum of `aceiobuflen` is `acemaxiobuflen`.

Context switching code must save and restore the contents of the ACEIOBUF up to `aceiobuflen`.

[NOTE]
====
As per the ACE Privileged Architecture, the dirtiness of the ACEIOBUF is not tracked except as part of the entire ACE state in `*status`.
Software should set `aceiobuflen` to zero once the contents of the ACEIOBUF are no longer needed.
Context switching code would then not save and restore the contents of the ACEIOBUF.
====

[[ACE-CSR-aceiobuftop]]
===== `aceiobuftop`

{empty}
(((CSR, `aceiobuftop`)))
`aceiobuftop` is an XLEN-bit URW CSR that sets the upper bound in bytes of the buffer range used by `ace.input` and `ace.output`.

`aceiobuftop` plays for the ACEIOBUF the role that `VL` plays in the V extension: it defines the operand length `ACELEN` as `aceiobuftop` {times} 8 and the transfer window [0, `aceiobuftop`).

// For operations involving the ACEIOBUF, `acestart` (cf. <<ACE-CSR-acestart>>) is the position within that window at which processing starts or resumes, analogously to `vstart`; when `acestart` {ne} 0, the bytes processed are those at offsets [`acestart`, `aceiobuftop`).
// Shortening an operand is done by lowering `aceiobuftop`, never by raising `acestart`.

The maximum of `aceiobuftop` is `aceiobuflen`.

Modifying `aceiobuftop` does not alter buffer contents. It allows per-operation length adjustments without reconfiguring the ACEIOBUF via `aceiobuflen`, an expensive operation that clears the buffer and may trigger internal garbage collection. This mirrors the use of `VL*SEW` reconfiguration to supply a partial “last block” or a short IV/nonce to Algorithms.

Writing a value that is invalid or unsupported for a given Algorithm may still cause the CR to transition to Error State _Invalid_ when an instruction expecting an input from or an output to the ACEIOBUF is later issued or restarted.

[[ACE-CSR-acestart]]
===== `acestart`

{empty}
(((CSR, `acestart`)))
`acestart` is an XLEN-bit RW CSR that records, as a number of bytes, the progress of the
instructions that _honor_ it:

* `ace.load`, `ace.store`, `ace.input` and `ace.output`: the bytes read or written;
* `ace.exec` processing a multi-block operand, which may be interrupted between blocks: the bytes
  processed;
* `ace.derive`, whose `ace.exec` endpoints advance the source and destination CRs in the same way;
* `ace.mv`, vector and non-vector: the CR transfer point. A vector `ace.mv` also tracks, in
  `vstart`, the corresponding position in the vector register when its operand is multi-block.

ACE has no intrinsic element length and
no counterparts to the vector crypto extension's Element Group Width (EGW), Effective Element Width (EEW), or Element Group Size (EGS).
ACE instructions such as `ace.exec` are architecturally decoupled from the operations the ACE unit performs when they are issued.
Therefore `acestart` is defined as a byte count: progress that is not
byte-structured, such as that of the point multiplications and signature operations of <<ACE-ECC>>
and <<ACE-PQC>>, is recorded in the _AlgorithmUse_ field instead, as Rule
<<ACE-IRR-long-running-no-data>> prescribes. Every other instruction leaves `acestart` unchanged,
except `ace.mgmt` and `ace.clear.all`, which clear it.


`acestart` is the position within the transfer window at which processing starts or resumes,
like `vstart` in the V extension; for an ACEIOBUF operand the window is always
[0, `aceiobuftop`) (<<ACE-CSR-aceiobuftop>>). Software saves and restores `acestart` across
context switches. The ACE implementation writes it:

. on a precise halt, with a prefix-complete point of the transfer (<<ACE-Memory-Model>>): the point
  of progress, or 0 in an implementation that selects the restart option of Rule
  <<ACE-IRR-resumability-options>> for `ace.load`, `ace.store`, `ace.input` and `ace.output`, which
  then transfer the prefix again on re-execution;
. with 0 when an instruction that honors it retires, except for `ace.mv`, which by design advances
  `acestart` by the bytes transferred and keeps the result across instructions, to support
  piecewise transfers (<<ACE-instruction-mv>>); a vector `ace.mv` tracks its progress within the
  vector register in `vstart`, whose value depends on the chosen element size.

The transfer window is empty when `acestart` {ge} `aceiobuftop` for an ACEIOBUF operand (with
`aceiobuflen` non-zero), or `acestart` {ge} `VL` {times} `SEW` / 8 for a vector operand; an
instruction with an empty window performs no operation. This rule does not apply to `ace.mv`, whose
vector window is [`vstart`, `vl`) in elements and whose `acestart` is a CR offset. Two checks
precede it:

. For Forms A–C of `ace.exec`, `acestart` {ne} `vstart` {times} `SEW` / 8 at issue raises an
  illegal-instruction exception.
. For an operand used as input, an `acestart` that is not an interruption point the Algorithm
  allows transitions the CR to Error State _Invalid_; for an operand used only as output, both this
  check and the empty-window rule yield no operation.

For the CR-directed transfers `ace.load`, `ace.store` and `ace.mv`, `acestart` is bounded above by
the length in bytes of the serialized image `S` (<<ACE-instruction-load>>), determined from the
first 8 bytes of the MDH; each of these instructions states the bound it applies.

An _interruption point_ of an Algorithm in a given State is an `acestart` value that the Algorithm
can itself produce on a precise halt in that State: unless the Algorithm states a coarser or a
different set, the whole multiples of its granularity within the transfer window, and 0; Subalgorithm
`process_VLI` (<<ACE-process-VLI>>) defines its own, at the boundaries at which its inner loop
yields. Writing an `acestart` value that is invalid or unsupported for the Algorithm, including one
that is not an interruption point it allows, transitions the CR to Error State _Invalid_ when an
instruction that relies on `acestart` is later issued or restarted.

Software must not write 0 to `acestart` to force a full restart of `ace.exec` or `ace.derive`
once per-block state effects have been committed (Rule
<<ACE-IRR-block-iterated-instructions>>).

[[ACE-CSR-acemanagedcr]]
===== `acemanagedcr`

{empty}
(((CSR, `acemanagedcr`)))
`acemanagedcr` is an XLEN-bit RW CSR, but currently only 6 bits are used.

It contains the number of the currently managed CR, or 32 if no CR is currently being managed.
If the CR it names ceases to be in a Configuration State otherwise than through a completing `ace.mgmt` — because it is
cleared, also by the zeroizing step of an `ace.mgmt` whose opening then fails, because it is the destination of an `ace.clone`, or because it transitions to an Error State — `acemanagedcr` is set to 32.
Otherwise, an ACE exception raised during a management operation that does not transition the CR to an Error State leaves `acemanagedcr` unchanged: the handler either resolves the condition or sets `acemanagedcr` to 32 itself.

Internal values of `SIV`, `SIV2`, `IMPQUAL` are associated with this CR.

Values 33 and above are reserved; writing one leaves `acemanagedcr` unchanged.

NOTE: The `acemanagedcr` check that `ace.mgmt` performs (<<ACE-CR-management>>) detects an accidentally
interleaved management operation. A handler that must manage another CR while one is under management
must first save the currently managed CR, write 32 to `acemanagedcr`, perform its operations,
and then restore the exported CR (<<ACE-state-save-and-restore-order>>).
Writing 32 without completing an export loses the in-flight `SIV`, `SIV2` and `IMPQUAL` values, which the next `ace.mgmt` that opens an import or an export overwrites.

[[ACE-instructions-detailed]]
=== Instructions

This section specifies the semantics and encodings of ACE's unprivileged instructions.
The `custom-1` and `custom-2` opcodes are placeholders; all other fields are specified.
In every encoding, fields shown with fixed values must hold those values. Any deviation from a fixed value or any unlisted combination of field values is a reserved encoding and raises an illegal-instruction exception (first group of <<ACE-illegal-instruction-grounds>>).

The notation `K{Xd}` denotes the CR whose index is held in GPR `Xd`.
`Kn|K{Xn}` indicates two alternative encodings: a 5-bit immediate CR index (`Kn`) or a CR number supplied by GPR `Xn`.
In every encoding that offers both, bit `r`, the _CR indexing mode selector_, chooses between them: `r` = 0 makes the 5-bit register field the CR index itself, `r` = 1 makes it the number of the GPR holding the index.

`%offset` denotes the immediate of the corresponding base-ISA instruction format, sign-extended to
XLEN and added to the base register: the I-type `immed12` for `ace.load`, and the S-type pair
`immed[11:5]`/`immed[4:0]` for `ace.store`, `ace.input`, and `ace.output`. The effective address of
a transfer is `X[rs1] + sext(%offset)`. For a multi-byte or resumed transfer that value is the
address corresponding to the *first* byte of the transfer, not to the byte at which the transfer
resumes: a byte offset of `acestart` is added to `X[rs1] + sext(%offset)` to form the restart
address.
The correspondence between addresses and transfer offsets is given by each instruction.

[[ACE-general-rules-instructions]]
==== General Rules

The following rules apply to all ACE instructions, unless expressly stated otherwise.

[horizontal]
[[ACE-GR-GPR-indirect, GR1]] GR1:: _Use of a GPR as indirect CR index:_
An indirect index outside [0..31] raises an illegal-instruction exception.
Using `X0` as an indirect CR index raises an illegal-instruction exception, unless this is expressly used to encode an instruction, for instance `ace.clear.all`.

[[ACE-GR-multiple-GPRs,GR2]] GR2:: _Use of multiple GPRs for longer inputs:_ A 64-bit operand is one GPR on RV64 and encoded in a pair `(X[s+1],X[s])` as `X[s+1] @ X[s]` on RV32,
and a 128-bit operand is encoded as `X[s+1] @ X[s]` on RV64 and using a GPR quartet on RV32
as `X[s+3] @ X[s+2] @ X[s+1] @ X[s]`. This holds whether the operand is a source or a destination.
The lowest register number of a pair must be even and that of a quartet a multiple of four;
otherwise an illegal-instruction exception is raised.
A pair or quartet is read, resp. written, as a whole.
Here and in every instruction description, RV32 and RV64 denote an XLEN of 32, resp. 64, in the privilege mode that executes the instruction.

GR3:: _If `X0` is used as a destination or source register, but not to index a CR,_ then
anything written to it is discarded, and it reads as zero. When the lowest register of a
pair or quartet is `X0`, no register of the group is written and the group reads as zero.

[[ACE-GR-acestart-vstart,GR4]] GR4:: ACE instructions with vector operands that use `acestart` for resumption update `acestart` and `vstart` simultaneously and independently, each according to its own semantics: both denote the same point of progress, `acestart` counting it in bytes and `vstart` in elements of the width in effect. Neither is derived from the other.
This allows the ACE unit and the vector unit to work in sync while accessing local information more efficiently, but also to explicitly “desync” the two values in certain contexts (such as in the implementation of nested CR management operations).
+
NOTE: For Forms A–C of `ace.exec` the hardware raises an illegal-instruction exception if `acestart` and `vstart` denote different points (<<ACE-CSR-acestart>>). `ace.mv` keeps the two independent by design, since its `acestart` is a CR offset that accumulates across instructions while `vstart` tracks the vector register.
+
NOTE: The uninterruptible vector-form instructions (`ace.getmdv`, `ace.restrictv`, Form C of `ace.size` and `ace.avail`, `ace.setst`, and `ace.mgmt`) do not produce `vstart` values and therefore do not consume one (Rule <<ACE-GR-vector-legality>>).

GR5:: The _UsagePolicy_ of the MDH determines whether certain instruction can be issued, and sometimes when, in a given privilege mode.
Furthermore, certain instructions may modify the state of the CR.
For all instructions, the authoritative table for these two properties is <<ACE-instruction-properties>>.
No instruction description restates them.
+
[[ACE-instruction-properties]]
.State modification and usage control, per instruction

| `ace.store`                  | Only `acestart` | Yes | No^*^                | Updates `acestart`.
| `ace.exec`                   | Yes             | Yes | Yes                  | {empty}
| `ace.mv`                     | Yes             | Yes | No^*^                | ACE/other state change depends on direction. It advances `acestart` by the bytes it transfers.

[[ACE-GR-opening-cr-when,GR6]] GR6:: _When a CR can be opened for import or export:_
Opening a CR for provisioning or import, as well as executing `ace.clear`, is always allowed in any State, since the
target CR is zeroized first; opening it for export is always allowed in any Complete or Configuration
State.
+
No Algorithm-specific rule may restrict whether a CR can be opened for export or for import, or cleared.
+
For the restrictions on `ace.clone`, cf. <<ACE-instruction-clone>>.

[[ACE-GR-vector-MDH-operand,GR7]] GR7:: Where a Form of an ACE instruction carries the whole 128-bit MDH in a vector register or group, that
operand must satisfy `VL` {times} `SEW` {ge} 128; otherwise an illegal-instruction exception is
raised. This includes the MDH-formatted operand of `ace.restrictv` and the destination of `ace.getmdv`. <<ACE-extensions-overview-unpriv>> records which vector extensions provide such a register.
The same requirement applies to an MDH taken from the ACEIOBUF: `aceiobuftop` {ge} 16.

[[ACE-GR-iobuf-configured,GR8]] GR8:: Instructions that access the ACEIOBUF, such as `ace.input` and `ace.output`, may be used only if the
ACEIOBUF is enabled and `aceiobuflen` is nonzero; otherwise ACE exception
`ace_exc_unconfigured_buffer` is raised.

[[ACE-GR-vector-legality,GR9]] GR9:: A vector register (group) operand of an ACE instruction whose register number, when the LMUL in effect is greater than 1, is not a multiple of that LMUL is a reserved encoding and raises an illegal-instruction exception (similarly to RVV 1.0).
Every ACE instruction with a vector operand sets `vstart` to 0 when it retires; on a precise halt it sets `vstart` as <<ACE-CSR-acestart>> and Rule <<ACE-GR-acestart-vstart>> prescribe. An instruction with a vector operand that produces no `vstart` value (`ace.getmdv`, `ace.restrictv`, Form C of `ace.size` and `ace.avail`, `ace.setst` and `ace.mgmt`), issued with `vstart` {ne} 0, either raises an illegal-instruction exception, as RVV 1.0 {sect}3.7 permits for a `vstart` value the instruction can never produce, or ignores `vstart`; which of the two is implementation-defined.

[[ACE-GR-custom-locality,GR10]] GR10:: A CC whose MDH carries any custom, implementation-defined value — a custom _Algorithm_ (<<ACE-Algorithm-field>>), a custom _SCProtection_ level (<<ACE-SCProtection-field>>), a system-specific _Version_ (<<ACE-Algorithm-version>>), or any other custom value — must name _ChipFamScrt_, or the stricter _ChipScrt_, in its _Locality_; otherwise the Metadata is invalid (see <<ACE-Metadata-validity>>).
+
NOTE: Note that if the ACE unit is implemented through emulation, different versions of ACE firmware may have different features while running on the same hardware, and a hardware-fixed locality will not be able to distinguish it. Rule <<ACE-GR-custom-locality>> is, however, a first line of protection against accidental abuse.

[[ACE-GR-atomic-randomness,GR11]] GR11:: An Algorithm that requires an internal random value, such as a signing nonce or an ephemeral scalar, generates it and consumes it within one instruction.
No State from which the CR can be exported or cloned holds random material that could be consumed against an input other than the one it was drawn for; for an interrupted long-running operation this is ensured by Rule <<ACE-AGR-progress-discard>> of Book 2. Rule <<ACE-GR-opening-cr-when>> is not relaxed to obtain this.

[[ACE-management-operations]]
==== Provisioning, Import, and Export

_This subsection is informative._

Broadly speaking, and setting aside error handling, *Provisioning* consists of the following three steps:

. Use `ace.mgmt` (<<ACE-instruction-mgmt>>) to prepare a CR to be provisioned, check the validity of the MDH, and load the entire MDH in the CR.
. Use `ace.load` (<<ACE-instruction-load>>) to load the rest of the provisioning information into the CR.
. Use `ace.mgmt` to complete the provisioning process and make the CR available to software.

*Importing* an SCC into a CR is similar:

. Use `ace.mgmt` to prepare a CR to accept an SCC, check the validity of the MDH, and load the entire MDH in the CR.
. Use `ace.load` to load the rest of the SCC, the authentication data first, into the CR.
. Use `ace.mgmt` to complete the import process by authenticating and decrypting the SCC, and make the CR available to software.

*Exporting* a CR as an SCC consists of the following steps:

. Use `ace.getmd` or `ace.getmdv` (<<ACE-instruction-getmd>>) to get the MDH of the CR to be exported, in order to determine its size and allocate resources.
. Store the MDH into memory.
. Use `ace.mgmt` to prepare a CR to produce an SCC. This includes encrypting its contents and computing the authentication tag(s).
. Use `ace.store` (<<ACE-instruction-store>>) to store the rest of the SCC, the authentication data first, to memory.
. Use `ace.mgmt` to complete the export process by restoring the CR in a form available to software.

A CR in an Error State takes shorter paths in both directions, since it is an MDH and nothing else
(<<ACE-error-state-transfer>>): its export uses no `ace.mgmt` at all, and its import is a single one.

We also anticipate how the _State_ of a configured CR changes under management:

. If it is not being managed, it is in a Valid State.

. If it is being provisioned from a PI, then its _State_ is `ace_cfg_provisioning`.
.. If this provisioning is preempted before it completes, its _State_ is saved by software,
   and upon export the _State_ becomes `ace_cfg_ppi_exporting`. “`ppi`” means “partial provisioning input”.
.. Upon any further preemption and export, the current _State_ is saved by software in its own process space and
   the state remains `ace_cfg_ppi_exporting`.
.. When the export terminates, the value of the _State_ before the export started is restored by software by passing it to the `ace.mgmt` that completes the export operation.
.. If the CR is re-imported again, the value of _State_ is first saved and CR's _State_ becomes `ace_cfg_ppi_importing`.
.. When such a nested management operation is completed, the previous state is restored.
.. Hence, when the last nested management operation is completed, the _State_ is restored to `ace_cfg_provisioning`.

. If an export operation is initiated from a CR in a Valid State, that _State_ is saved by software, and the _State_ becomes `ace_cfg_exporting`.
.. Nested management operations lead to States `ace_cfg_exporting` and `ace_cfg_importing`.

. If an import operation is started on an SCC generated from a CR in a Valid state: the _State_ becomes `ace_cfg_importing`, and the nested management states are `ace_cfg_exporting` and `ace_cfg_importing`.

The values of these States are given in <<ACE-SC-sealing-status>>.

[[ACE-instruction-size]]
==== ace.size/ace.avail

_Synopsis_::
`ace.size` returns the total size of a memory buffer that would be needed to store the data of a PI or SCC, in bytes, or 0 in case of error (such as unsupported Algorithm or invalid MDH).
`ace.avail` returns 1 if the Algorithm the MDH names is available in the requested variant, and 0 otherwise.

_Mnemonic_::
+
--
There are three Forms of the `ace.size` instruction, and the same three Forms of `ace.avail`:
(((ACE, instruction, ace.size)))
(((ACE, instruction, ace.avail)))

[upperalpha]
. `ace.size  Xd, Ks|K{Xs}` - Size from a context.
. `ace.size  Xd, Xs` - Size from MDH[63:0] in one (RV64) or two (RV32) GPRs.
. `ace.size  Xd, Vs` - Size from MDH in one vector register.
--

_Encoding_::
+
--
The encoding shares opcode, `funct3`, and `funct2` (the two msbs of `funct7`) with `ace.exec`, but with bit 27 equal to 1.
Bit 25, `q`, selects the instruction: `q` = 0 is `ace.size`, `q` = 1 is `ace.avail`.

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x5b, attr: ['custom-2'] },
    { bits:  5, name: 'Xd' },
    { bits:  3, name: 0x0, attr: ['ace.exec'] },
    { bits:  5, name: 'Ks/K{Xs}/Xs/Vs' },
    { bits:  5, name: 0x0 },
    { bits:  1, name: 'q' },
    { bits:  1, name: 'r' },
    { bits:  1, name: 0x1 },
    { bits:  2, name: 'F' },
    { bits:  2, name: 0x0, attr: ['funct2'] },
]}
....

The `F` field and the `r` bit may assume the following values:

* `F` = `0b00`, `r` = `0` {implies} Form A: Size/availability from a context given as `Ks`.
* `F` = `0b00`, `r` = `1` {implies} Form A: Size/availability from a context given indirectly as `K{Xs}`.
* `F` = `0b01`, `r` = `0` {implies} Form B: Size/availability from MDH in one (RV64) or two (RV32) GPRs.
* `F` = `0b10`, `r` = `0` {implies} Form C: Size/availability from MDH in a 128-bit vector register.

--

_Description_:: {empty}
+
--
`ace.size` returns in GPR `Xd` the total size in bytes of the memory buffer needed to hold the
external image that the MDH describes: a PI, an SCC, or, for a CR in an Error State, the MDH
alone (<<ACE-data-formats>>, <<ACE-length-rule>>). For an SCC the size includes the
authentication tag(s) and the ADS; for a PI it is the size of the entire
PI. Knowing this size is necessary for any feature that relies on exporting a CR, including context
switching.

`ace.avail` (`q` = 1) evaluates only the _Algorithm_, _AlgorithmPolicy_, _AlgorithmExtension_, _KeyType_ and _SCProtection_ fields of the MDH and returns 1 in `Xd` if that combination is implemented (a non-zero _AlgorithmExtension_ never is), 0 otherwise; no other field is examined, and a CR in the _Unconfigured_ State yields 0.

The three Forms for the two instructions differ only in where the MDH is taken from,
as the mnemonics above give:
from the CR itself for Form A, from Bits [63:0] supplied in `Xs` (in `X[s+1] @ Xs` on RV32) for Form B,
and from Bits [127:0] supplied in `Vs` for Form C.

Let `content1_size` be the length in bytes of the `Content1` of an SCC for the _Algorithm_,
_AlgorithmPolicy_, _KeyType_ and _StateExtension_ of the MDH, and `pi_content_size` the length in bytes
of the `Content` of a PI for its _Algorithm_, _AlgorithmPolicy_ and _KeyType_ (<<ACE-length-rule>>).
These are two distinct quantities and are not interchangeable.
Let `content2_size` = 16 * (_AuxDataLen_ - 2) if _AuxDataLen_ {ge} 2 and _ADSDropped_ = 0, and 0 otherwise.

`ace.size` is computed as follows:

. If the CR is _Unconfigured_, then: 0.
. If the supplied MDH (Forms B and C) is not in an Error State and is unsupported or invalid Metadata (see <<ACE-Metadata-validity>>), or its _State_ is 61–63, then: 0.
  Form B applies only to bits [63:0]: the fields in bits [127:64] are not examined, since none of them affects the size of any structure (<<ACE-length-rule>>), and the invalidity conditions on them, including Rule <<ACE-GR-custom-locality>>, are not applied.
. If the MDH._State_ is an Error State, then: 16.
. If the MDH._State_ is a Valid State or `ace_cfg_{importing|exporting}`, then:
  ..  If _AuxDataLen_ = 0, then: 32 + `content1_size`.
  ..  If _AuxDataLen_ {ge} 2, then: 64 + `content1_size` + `content2_size`. The 64-byte fixed part includes `IMPQUAL` and `SIV2` even when _ADSDropped_ = 1.
. If the MDH._State_ is `ace_cfg_provisioning` or `ace_cfg_ppi_{importing|exporting}`, or, for a supplied MDH, _Unconfigured_ (the MDH of a PI), then: 16 + `pi_content_size`.
--

[[ACE-instruction-load]]
==== ace.load

_Encoding_::
`ace.load` is an I-type instruction.
+
[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x2b, attr: ['custom-1'] },
    { bits:  5, name: 'context', attr: ['Kd','K{Xd}'] },
    { bits:  3, name: 'ace.load', attr: [0x0,0x1] },
    { bits:  5, name: 'Xs1' },
    { bits: 12, name: 'immed12' },
]}
....
+
`funct3` = `0b000` selects the immediate CR index in the `context` field and `funct3` = `0b001` selects the CR indexed by the GPR named by that field.

_Mnemonics_::
`ace.load{fournbsp}{nbsp}{nbsp}{nbsp}Kd|K{Xd}, %offset(Xs1)`

_Description_::
+
--
`ace.load` imports the Content of a PI or an SCC into the CR `Kd` or `K{Xd}`.
None of `ace.load`, `ace.store` and `ace.mv` transfers the MDH, which is carried by `ace.mgmt` and `ace.getmd*`. The authentication fields `SIV`, `IMPQUAL` and `SIV2` are the leading bytes of the image they transfer, and are held in the three per-hart registers of <<ACE-CRF>> while the CR is under management.

This instruction also requires that the CR be ready to accept information (being either provisioned or imported) and that the MDH has already been loaded by the `ace.mgmt` that opened the CR for provisioning or import (<<ACE-instruction-mgmt>>).

If the CR's _State_ is not one of the States admitted by Rule <<ACE-SGR-ace-load-mv-allowed>> — which excludes every Complete State and the _Unconfigured_ State — or `acestart` is not a multiple of 16, an illegal-instruction exception is raised.

Neither `ace.load` nor `ace.store` nor `ace.mv` is ever used on a CR in an Error State (Rule <<ACE-SGR-error-state-CR-is-only-MDH>>, <<ACE-error-state-transfer>>).

Let `content_size` be the length in bytes of the serialized `Content` of the CR, namely the `Content` of a PI or an SCC,
according to the base type of the image the CR holds (<<ACE-length-rule>>).
Since `content_size` must be determined by `ace.load` itself, the caller must have transferred at least the `MDH` into the CR beforehand.

The instruction needs to know a _ContentOffset_ value of 0, 16, or 48, to signal the start of the `Content` in the external formats depending on the MDH, the current operation, and base type of the image the CR holds (<<ACE-length-rule>>).
Let `content2_size` = 16 * (_AuxDataLen_ - 2) if _AuxDataLen_ {ge} 2 and _ADSDropped_ = 0, and 0 otherwise.

`_ContentOffset_` is computed using the same case distinction of `ace.size` (<<ACE-instruction-size>>) but excluding the `Content` and the MDH._ADSDropped_ never affects _ContentOffset_.

. If the MDH._State_ is a Valid State or `ace_cfg_{importing|exporting}`, then:
  ..  If _AuxDataLen_ = 0, then: 16.
  ..  If _AuxDataLen_ {ge} 2, then: 48.
. If the MDH._State_ is `ace_cfg_provisioning` or `ace_cfg_ppi_{importing|exporting}`, then: 0.

The _serialized image_ `S` of the CR is `Content`, `SIV {vvert} Content`, or `SIV {vvert} IMPQUAL {vvert} SIV2 {vvert} Content` for _ContentOffset_ = 0, 16, or 48, respectively, and
`image_size` = _ContentOffset_ + `content_size`, which is the value `ace.size` reports minus 16.

Let `max_admissible` be the length of the longest image of the CR's current base type that the implementation can hold for the Algorithm: for an image with a SCC base type, `content1_size` plus the largest `content2_size` the implementation supports (<<ACE-instruction-size>>); for an image with a PI base type, `pi_content_size`. When _ADSDropped_ = 1, `content2_size` is zero, so no `Content2` byte is part of the image. Bytes of an SCC beyond `max_admissible` belong to an ADS that is discarded (<<ACE-SCC-import>>) and are neither read from memory nor written to the CR.
Let

{fournbsp}{fournbsp}``image_end`` = _ContentOffset_ + `min(content_size, max_admissible)`.

Offsets of `S` at or beyond `image_end` hold no CR data; they read as zero through every architectural access.
`ace.load` transfers the offsets `[acestart, image_end)` of `S`: for each _j_ from `acestart` to `image_end` − 1, the byte at memory address ``Xs1 + %offset + ``_j_ is loaded into the _j_-th byte of `S`.
`acestart` tracks a prefix-complete number of bytes loaded.
If `acestart` {ge} `image_end`, nothing is transferred.

Being related to accesses to a CR (<<ACE-Memory-Alignment>>), `acestart`, `content_size`, `max_admissible`, `image_size` and `image_end` are all multiples of 16 bytes.

When a system-defined format is used, the semantics of `ace.load` are implementation-dependent.
--

==== ace.store

_Encoding_::
`ace.store` is an S-type instruction.
+
[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x2b, attr: ['custom-1'] },
    { bits:  5, name: 'immed[4:0]' },
    { bits:  3, name: 'ace.store', attr: [0x2,0x3] },
    { bits:  5, name: 'Xs1' },

....

_Mnemonic_::
`ace.store %offset(Xs1), Ks2|K{Xs2}`
(((ACE, instruction, ace.store)))

_Description_::
+
--
Let `S` be `Content` of the target CR `Ks2` or `K{Xs2}`, `SIV {vvert} Content`, or `SIV {vvert} IMPQUAL {vvert} SIV2 {vvert} Content`, depending on whether _ContentOffset_, computed as for `ace.load`, is 0, 16, or 48.

_Mnemonic_::

[wavedrom, , svg]

For the four Forms A–D above, the encodings are:

[upperalpha]

+

If `Zklv` is not implemented, only Form D `ace.exec`
is supported, Forms A–C raise an illegal-instruction exception, and `ace.input`, `ace.output` are used to provide inputs and
extract outputs from `ace.exec`, as described in <<ACE-usage-input-output>>.

[[ACE-instruction-mv]]
==== ace.mv

The `Zklmv` subextension adds dedicated move instructions between scalar/vector registers and a CR.
The instructions in this extension are encoded as new forms of `ace.exec`:
`r` is the CR indexing mode selector.

_Mnemonics_::
+
--
The `ace.mv` instruction admits the following variants:
(((ACE, instruction, ace.mv)))

[upperalpha]
. `ace.mv  Kd|K{Xd}, Xs2` copies 128 bits of content from two or four GPRs into a CR.
. `ace.mv  Kd|K{Xd}, Vs2` copies one or more 128-bit blocks of content from a vector register into a CR.
. `ace.mv  Xd,  Ks1|K{Xs1}` extracts 128 bits of content from a CR into two or four GPRs.
. `ace.mv  Vd,  Ks1|K{Xs1}` extracts one or more 128-bit blocks of content from a CR into a vector register.
--

_Encodings_::
+
--
The hart adds the following encodings to Forms B and C of `ace.exec`. As throughout
`ace.exec`, the CR operand is encoded in `rs1`. The sub-opcode occupies the register field that the
corresponding Form of `ace.exec` leaves unused: `rd` in Form B, `rs2` in Form C.

[upperalpha]
. `ace.mv  Kd|K{Xd}, Xs2`   is encoded as `Form` = `0b01` and `rd` = `0b00001`.
. `ace.mv  Kd|K{Xd}, Vs2`   is encoded as `Form` = `0b01` and `rd` = `0b00010`.
. `ace.mv  Xd,  Ks1|K{Xs1}` is encoded as `Form` = `0b10` and `rs2` = `0b00001`.
. `ace.mv  Vd,  Ks1|K{Xs1}` is encoded as `Form` = `0b10` and `rs2` = `0b00010`.

`rs1` always specifies the source or destination CR. In Forms A and B, `rs2` specifies the source GPR or vector register.
In Forms C and D, `rd` specifies the destination GPR or vector register.
For forms B and D, the vector length must be a multiple of 16 bytes.
--
//
// In the mnemonics of variants A and B the CR is written first because it is the
// destination of the move; it is nonetheless encoded in `rs1`, not in `rd`.

_Description_::
+
--
In each variant the CR is the one named by `rs1`.

*Bound.* Transfers follow the same constraints as those of `ace.load` (<<ACE-instruction-load>>, <<ACE-Memory-Alignment>>), with `S`, `image_end`, and _ContentOffset_ as defined there:
`ace.mv` transfers whole 128-bit blocks, never a part of one, and each block the variant would transfer lies either wholly below `image_end` or wholly at or beyond it.

* A block at an offset below `image_end` is transferred.
* A block at an offset at or beyond `image_end` is not: no CR byte is written for it; the destination
  GPR operand, resp. the corresponding elements of `Vd`, are written with zero; and `acestart` does not advance past `image_end`.
* If `acestart` {ge} `image_end`, the CR-writing variants write nothing; the CR-reading variants write their
  destination GPR operand, resp. every element of `Vd` from `vstart` to `vl` − 1, with zero; in all variants
  `acestart` is unchanged.

For each 16-byte block transferred by `ace.mv`, `acestart` advances by 16 bytes.
In vector variants, `vstart` is also used, to track progress in vector elements: for instance each 16-byte block advances `vstart` by 4 for 32-bit elements or by 2 for 64-bit elements.
If a vector transfer is interrupted, `acestart` records the total number of bytes transferred, and `vstart` identifies the first untransferred vector element for resumption.
Element _k_ of the vector operand, for _k_ from `vstart` to `vl` − 1, corresponds to byte offset `acestart` + (_k_ − `vstart`) × `SEW`/8 of the serialized image `S` (<<ACE-instruction-load>>).
If `vstart` {ge} `vl`, the instruction performs no operation and leaves `acestart` unchanged.
Writes to, resp., reads of, an offset at or beyond `image_end` are ignored, resp., read as zero.

The four variants are displayed in the following table.
For all variants, if the CR's _State_ is not one of the values in the fourth column of its row,
an illegal-instruction exception is raised. A vector variant for which `vl * (SEW/8)` is not a multiple of 16 raises an illegal-instruction exception; the V-enabled check is performed first. `vstart` must likewise point to a multiple of 16 bytes: a vector variant for which `vstart * (SEW/8)` is not a multiple of 16 raises an illegal-instruction exception. As for `ace.load` (<<ACE-instruction-load>>), so does an `acestart` that violates the constraints above.

==== ace.setst

_Synopsis_::
Change the state of the Algorithm encoded in the CC in a CR.

_Mnemonic_::
The `ace.setst` instruction admits four Forms, namely
(((ACE, instruction, ace.setst)))
+
[upperalpha]

_Encoding_::

    { bits:  1, name: 'r' },
    { bits:  4, name: 0x0 },
    { bits:  7, name: 'immed7' },
]}
....

`r` is the CR indexing mode selector.

The encodings of the four Forms are:
[upperalpha]
. `ace.setst` = `0b001`. `rs1` = `0b00000`.
. `ace.setst` = `0b010`.
. `ace.setst` = `0b011`.
. `ace.setst` = `0b100`.
--

_Description_::
+
--
The instruction is used to advance the Algorithm expressed in the CR `Kd` or `K{Xd}`
from one stage to another – for instance, from initializing a hash
function to absorbing data and finalizing the digest. The reached State is normally
the one expressed in `#immed7`, but some States transition automatically to another
State when the instruction completes. The allowed transitions are given in <<ACE-State-management>> and in the specification of each Algorithm.

`ace.setst` may also set state information orthogonal to those stages,
possibly as a prerequisite for entering another State.

The following categories of values for `#immed7` apply to all Algorithms:

* 0 (`ace_state_unconfigured`) clears the CR, in any Form; an auxiliary operand is ignored.
* 1–55 name a _State_ a CR can transition to:
** Values 1–47 are called _Valid_ States.
   Value 1 is called _Ready_ and it is the starting state of any freshly provisioned CR.
   46 and 47 correspond to _Success_ and _Failure_ of the Algorithm, respectively, and cannot be set directly.
   _Failure_ is an outcome, not an error.
** Values 48–55 are the Error States, used to report ACE errors (<<ACE-states-error>>); 54 and 55 are reserved.
   An Error State is accepted as `#immed7` in any State.
   With an Error State as `#immed7`, a CR in a Complete or Partial State transitions to it
   (54 and 55 to _Invalid_) _without raising an exception_, even where reaching that State implicitly would
   raise one, and later usage of the CR performs no operation (Rule <<ACE-SGR-usage-cr-error-state>>).
   On a CR in the _Unconfigured_ State the instruction performs no operation: only the short import
   of <<ACE-error-state-transfer>> configures a CR directly into an Error State.
* 56–63, i.e., when the top four bits of `#immed7` are `0b0111`, encode `ace.mgmt` (<<ACE-instruction-mgmt>>).
* 64 encodes `ace_cfg_clear_ads` (<<ACE-instruction-clearads>>).
* 65–127 are Algorithm-defined and may change other state information, such as _StateExtension_.

Any other `#immed7` that the architecture or the current Algorithm does not support transitions the CR to
Error State _Invalid_. Some values require an auxiliary operand of 64 or 128 bits, in one or more
GPRs or in a vector register (group) `Vs`.
--

[[ACE-instruction-mgmt]]
==== ace.mgmt

_Synopsis_::
Open or complete a management operation on a CR.

_Mnemonic_::
The `ace.mgmt` instruction is a separate instruction and admits only Forms A, C, and D of `ace.setst`.
(((ACE, instruction, ace.mgmt)))

//

_Encoding_::
`ace.mgmt` is an R-type instruction with the encoding of `ace.setst` (<<ACE-instruction-setst>>) and `#immed7`[6:3] = `0b0111`, that is, `#immed7` in 56–63.

_Description_::
+
--
The instruction brackets the body of a CR management operation (<<ACE-management-operations>>):
it opens a provisioning, an export or an import on the CR `Kd` or `K{Xd}`,
and completes it.
Like `ace.setst` it changes the _State_ of the CR, but with different semantics,
so it is a separate instruction.
The State reached depends on the previous State of the CR as well as on `#immed7`.

Besides a management command expressed in the `#immed7`,
`ace.mgmt` receives an MDH for two purposes: to decide which variant of the operation to perform,
which may also modify the MDH of the CR, and, when completing an import or an export, to restore
the _State_ the CR had when the operation started from a copy saved by the caller.

The following values of `#immed7` apply (<<ACE-management-immeds>>):

* 56 (`ace_cfg_provisioning`), 57 (`ace_cfg_exporting`) and 58 (`ace_cfg_importing`) open a
  provisioning, an export and an import, respectively. For 56 and 58 the instruction receives the
  MDH of the CR, as the Forms below supply it, and changes _State_ only after loading it.
* 59–62 are reserved. _State_ takes 59 and 60 only as the result of an `ace.mgmt` with 57 or 58.
* 63 (`ace_cfg_management_end`) completes the current management operation.

The MDH is supplied as follows:

* Form A carries no auxiliary operand. Where the operation requires the MDH, Form A is a
  substitution (<<ACE-usage-input-output>>) and reads it from bytes [0, 16) of the ACEIOBUF,
  ignoring `acestart`. After the `acemanagedcr` check and before any change to the CR, Rule
  <<ACE-GR-iobuf-configured>> applies and, with the ACEIOBUF configured, `aceiobuftop` < 16 raises
  an illegal-instruction exception (Rule <<ACE-GR-vector-MDH-operand>>).
* Form C carries the MDH in the lowest 128 bits of `Vs`.
* Form D carries the MDH as a 128-bit operand in two or four GPRs starting at `Xs` (Rule
  <<ACE-GR-multiple-GPRs>>).

Form B is a reserved encoding (<<ACE-illegal-instruction-grounds>>).

The precise semantics of each operation are given in <<ACE-CR-management>>.
--

[[ACE-instruction-restrict]]
==== ace.restrict*

_Synopsis_::
Restrict the policies encoded in a CC in a CR.

_Mnemonic_::
+
--
[%hardbreaks]
`ace.restrictl{nbsp}{nbsp}Kd|K{Xd}, Xs1`(((ACE, instruction, ace.restrict)))
`ace.restricth{nbsp}{nbsp}Kd|K{Xd}, Xs1`

_Encoding_::
+
--
`ace.restrict` is an R-type instruction.
The encoding shares opcode and `funct3` with `ace.exec`, but `funct2` (i.e., the two msbs of `funct7`) is `0b01`.
[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x5b, attr: ['custom-2'] },
    { bits:  5, name: 'Kd|K{Xd}' },
    { bits:  3, name: 0x0, attr: ['ace.exec'] },
    { bits:  5, name: 'Xs1' },
    { bits:  5, name: 0x0 },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'r' },
    { bits:  1, name: 0x0 },
    { bits:  1, name: 'h' },
    { bits:  1, name: 'v' },
    { bits:  2, name: 0x1, attr: ['funct2'] },
]}
....

`r` is the CR indexing mode selector.

If bit `h` (bit 28) is 0, the instruction is `ace.restrictl`; if `h` is 1, it is `ace.restricth`.

If bit `v` (bit 29) is 0, the input is taken from a GPR (GPR pair for RV32), and the instruction is `ace.restrictl` or `ace.restricth` depending on `h`.
If bit `v` is 1, bit `h` must be 0, and the input is taken from the lowest 128 bits of a vector register (group).
The combination `v` = `h` = 1 is reserved.
--

// comment

_Description_::
+
--
The instructions narrow the policies of the CC in CR `Kd` or `K{Xd}`, with Metadata Header `md`,
as requested by the operand `Xs1` (`Vs1` for `ace.restrictv`), which has the same format as an
MDH. `ace.restrictl` takes bits [63:0] of that format and may change _AlgorithmPolicy_ and
_SCProtection_; `ace.restricth` takes bits [127:64] and may change _Locality_, _UsagePolicy_,
_ExpirationDate_ and _AlgorithmUse_; `ace.restrictv` takes both halves and applies both sets of
rules as a single instruction.

A zero field of `Xs1` leaves the corresponding field of `md` unchanged, and the fields of `Xs1`
not named above are ignored. Every check, including those that transition the CR to Error State
_Invalid_, is performed before any CRF capacity is allocated for a _SCProtection_ request, as in
`ace.mgmt` (<<ACE-CR-management>>), and all changes are applied together once every check has
passed. The validity of the changed fields (<<ACE-Metadata-validity>>) is evaluated on the
resulting MDH, and unchanged fields are not re-examined: a request that would produce an
unsupported or invalid value, such as a non-zero _ExpirationDate_ without `Zklexpire` or a
_Locality_ subfield naming an unconfigured entry, transitions the CR to _Invalid_.

The rules for each non-zero field of `Xs1` are:

* _AlgorithmPolicy_: if the Algorithm does not use the field, or uses it to extend _Algorithm_,
  the CR transitions to _Invalid_. Otherwise the new value replaces the old one only if every bit
  it sets was already set, so that a disabled function cannot be enabled; any other value, or one
  invalid for the Algorithm, transitions the CR to _Invalid_, as does disabling an operation, such
  as encryption or signature generation, while in a State allowed only while performing it.

* _SCProtection_: the value requests that the side-channel protection be raised to that level. A
  request for a weaker level transitions the CR to _Invalid_; the ordering of the custom levels 6
  and 7 relative to the architected ones is implementation-defined. If the stronger level needs
  CRF capacity that cannot be allocated, ACE exception `ace_exc_out_of_memory` is raised.

* _Locality_: each subfield (<<ACE-locality-indexes>>) — bits [1:0], [3:2] and [5:4], and each of
  bits 6, 7 and 8 — is treated independently. A subfield of `Xs1` that is zero, or equal to that of
  `md`, requests no change. A zero subfield of `md` takes the value of `Xs1`. A non-zero HW Binding
  subfield may only be replaced by a stricter entry of its chain: _SiPScrt_ by _ChipFamScrt_ or
  _ChipScrt_, _ChipFamScrt_ by _ChipScrt_, _OEMScrt_ by _ProdScrt_ or _DevScrt_, and _ProdScrt_ by
  _DevScrt_. Any other change, including any change of a non-zero Boot Session or SW Filter
  subfield and any weakening, transitions the CR to _Invalid_. A later export binds the SCC to the
  new _Locality_.

* _UsagePolicy_: each set bit removes a permission and each clear bit changes nothing: bits 0–3
  set the corresponding disallow bits of `md`, and bit 4 clears its Debug grant. No request can
  widen the set of modes that may use the CC.

* _ExpirationDate_: if `md`._ExpirationDate_ is zero or `Xs1`._ExpirationDate_ {le}
  `md`._ExpirationDate_, the value in `Xs1` replaces it; otherwise the CR transitions to _Invalid_.

* _AlgorithmUse_: the CR transitions to _Invalid_ where the Algorithm uses the field to hold
  state, such as the transfer or output counters of <<ACE-PQC-ML-KEM>>, <<ACE-PQC-ML-DSA>> and
  <<ACE-ECC>> or the squeeze counter of <<ACE-Ascon-Hash256>>, since rewinding or advancing such a
  counter would let software reload part of a key field or skip the checks performed when a field
  finishes loading, and wherever the Algorithm does not define the field as writable by
  `ace.restrict*`; otherwise the field changes only as the Algorithm prescribes.

The instructions may be issued in any Complete State; in the _Unconfigured_ State they perform no
operation, and in a Configuration State Rule <<ACE-SGR-usage-cr-config-state>> applies. They are
not usage-controlled because every change narrows the CC — policies are only removed,
side-channel protection only strengthened, Localities only tightened, and an expiration date only
brought forward — so they cannot give a mode that the _UsagePolicy_ excludes any capability it did
not already have; likewise `ace.clear` (<<ACE-instruction-clear>>), a strictly stronger denial
primitive, is not usage-controlled.
--

// ////////////////////////////////////////////////////////////////////

[NOTE]
====
Two practical use cases enabled by this instruction are:

*   Allowing privileged code to give a CC to several processes in a
    fine-grained manner, as opposed to all processes.
    This can be achieved by cloning the CR and customizing
    the Localities for each clone.
*   Enabling privileged code to split a CC capable of both
    encryption and decryption into two CCs, one only capable of encryption and
    the other only capable of decryption, thereby creating a one-way channel
    between processes.

The ability to perform such customizations saves both time and computational
resources by avoiding additional round-trips to trusted environments.
====

* The destination CR is then cleared and the clone is created.

* The destination CR becomes a perfect copy of the source CR: all internal data, including MDH and internal state, are copied verbatim:
The instruction achieves the same result as exporting the source CR to an SCC and importing the SCC into the destination CR.

See <<ACE-CSR-lcrstatus>> for the behavior under emulation, i.e., when the source CR is _Off_ in some `*lcrstatus`.

[[ACE-instruction-derive]]
==== ace.derive

_Synopsis_::
Pipe data from one CR into another without exposing it to software.

_Mnemonic_::
`ace.derive Kd|K{Xd}, Ks1|K{Xs1}, Xs2`
(((ACE, instruction, ace.derive)))

_Encoding_::
+
--
The encoding is almost identical to `ace.clone`, with bit 27 set to 1 instead of 0.
The instruction is an R-type instruction.

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x5b, attr: ['custom-2'] },
    { bits:  5, name: 'Kd|K{Xd}' },
    { bits:  3, name: 0x0, attr: ['ace.exec'] },
    { bits:  5, name: 'Ks1|K{Xs1}' },
    { bits:  5, name: 'Xs2' },
    { bits:  2, name: 'R' },
    { bits:  1, name: 0x1 },
    { bits:  2, name: 'Form' },
    { bits:  2, name: 0x2, attr: ['funct2'] },
]}
....

Bits [26:25], i.e., field `R`, are encoded as for `ace.clone` (<<ACE-instruction-clone>>).

The auxiliary input is always a GPR: `ace.derive` has no form without one and no vector form.

Bits [29:28], i.e., field `Form`, select which endpoint is used on each side:

[[ACE-derive-forms]]
.Endpoints selected by the `Form` field of `ace.derive`
[float="center",align="center",width="100%",cols="^10%,<40%,<40%",options="header"]
|===
| `Form` | Source, in CR `Ks1`{nbsp}\|{nbsp}``K{Xs1}`` | Destination, in CR `Kd`{nbsp}\|{nbsp}``K{Xd}``
|  `00`  | Exportable field `i`                        | Importable field `j`
|  `01`  | Output of an `ace.exec` (`i` is zero)       | Importable field `j`
|  `10`  | Exportable field `i`                        | Input of an `ace.exec` (`j` is zero)
|  `11`  | Output of an `ace.exec` (`i` is zero)       | Input of an `ace.exec` (`j` is zero)
|===
--

_Description_::
+
--
`ace.derive` moves up to `length` bytes from an endpoint of the source CR to an endpoint of the
destination CR without making them visible to software: the output of one Algorithm becomes an
input, possibly a key, of another. The source and the destination CRs must be different,
otherwise an illegal-instruction exception is raised.

The auxiliary GPR carries `length`, a number of bytes, and the indices `i` and `j`:

* On RV64, `Xs2` = `length << 32 {vvert} i << 16 {vvert} j`.
* On RV32, the GPR pair `X[s2+1] @ X[s2]` (Rule <<ACE-GR-multiple-GPRs>>), with
  `X[s2]` = `i << 16 {vvert} j` and `X[s2+1]` = `length`.

//

Allowed pairs:::
The number `i` selects an _exportable field_ of the source CC, a field its Algorithm makes available as the
source of an `ace.derive`, and `j` an _importable field_ of the destination CC, one made
available as the destination; each Algorithm numbers these fields from 1, and 0 is used on the
side that carries an `ace.exec` endpoint.
+
A field from the System Key Store is never exportable,
a field configured by a SKID is never importable, and a field that its Algorithm does not return
to software through `ace.exec` may be the source of a `Form` `00` transfer only.
+
A transfer is allowed only if the specification lists its (source, destination) endpoint pair,
or if software can obtain its data through `ace.exec` and its destination accepts arbitrary input
through `ace.exec`, as for the output of a XOF squeezed into a state implemented by Subalgorithm
`process_VLI` (<<ACE-process-VLI>>) or into a multi-block `ace.exec`. Either way, the block sizes
of the endpoints, in their current States, must be compatible: one divides the other, one endpoint
transfers any number of bytes directly from or to a field, or the destination is a `process_VLI`
state. A listed pair depends on both Algorithms; it defines a minimum transfer length and may
define an upper limit, a granularity, and constraints on the _UsagePolicy_, _Locality_,
_ExpirationDate_ and _SCProtection_ of the destination CR, to which the source Algorithm may add.

Checks:::
The checks of Rule <<ACE-SGR-gate-order>> apply to both CRs. Then, each check being applied to
the source before the destination, and with nothing transferred on any failure:
+
. The _State_ and _StateExtension_ of each CR must admit its endpoint, and a destination whose
  key is written must be in State _Ready_; otherwise the offending CR, or both, transition to
  Error State _Invalid_.
. An index that names no allowed endpoint transitions its CR to _Invalid_; a transfer that is
  not allowed, including one that the field rules above exclude, transitions both CRs to
  _Invalid_.
. A destination that violates the constraints of the pair or of the source Algorithm
  transitions to _Invalid_.
. A transfer whose effective length (see <<ACE-derive-rule-both-fixed-size>>) is below the pair's minimum, or violates its upper limit or granularity, transitions the destination CR to _Invalid_.

[[ACE-derive-rule-both-fixed-size,Transfer Size Rules]]
Transfer:::
A destination field of `dest_length` bytes receives `eff_length` = min(`length`, `dest_length`)
bytes and is zero-filled beyond them; any other destination receives `eff_length` = `length`
bytes. `length` = 0 transfers nothing and, if the checks above pass, changes no state.
+
The source supplies `eff_length` bytes: the transferred part of a field is truncated to `eff_length` bytes if longer or zero-padded if shorter; a source producing output in blocks of `b` bytes produces the blocks needed to cover
them, and the unused part of the last block is discarded. No mechanism to save the unused part is provided unless it is part of the Algorithm.
+
The destination consumes the bytes
in its blocks of `b'` bytes, a field being a single block, and a final block shorter than `b'`
is supplied as an `ace.exec` with that shorter input would be. Each endpoint advances as the
`ace.exec` operations producing or consuming these blocks would advance it; a destination
state implemented by `process_VLI` may be left open and continued with `ace.exec`.
+
The interruption points of an `ace.derive` (<<ACE-CSR-acestart>>) are the `acestart` values that
are interruption points of both endpoints, each in its current State.
--

////

Examples of piping between Cryptographic Contexts with ace.derive:::

. *Form `11` — output of one `ace.exec` into the input of another.* The pair

`{fournbsp}{fournbsp}` `ace.exec V1, K1, {INPUT}` +
`{fournbsp}{fournbsp}` `ace.exec {OUTPUT}, K2, V1`

leaks the intermediate value `V1` to software. The single instruction

`{fournbsp}{fournbsp}` `ace.derive K2, K1, Xs2` `{nbsp}{nbsp}` with `Form` = `11`

performs the same two operations, advancing both state machines exactly as the two `ace.exec`
instructions would, and the intermediate value never leaves the ACE unit.

. *Form `01` — output of an `ace.exec` into a secret.* A key agreed or derived by the Algorithm in
`K1` becomes a key of the CC in `K2`. `K2` is provisioned beforehand in the ordinary way — a CC
whose _KeyType_ selects a randomly generated key serves as a placeholder — and must be in State
_Ready_; the `ace.derive` then overwrites its secret field `j`.

. *Form `00` — field into secret.* An exportable field of one CC is copied into a secret field of
another, for instance to give two CCs with different _UsagePolicy_ or _Locality_ the same
underlying key. Both indices are significant here. This is the shape used by <<ACE-PQC-ML-KEM>>.

. *Form `10` — secret into the input of an `ace.exec`.* A stored secret is absorbed by the Algorithm
in `K2`, for instance as the key of a MAC or as a customization string, without being materialized
in a register.

In every case `length` gives the number of bytes transferred, and the truncation, zero-padding and
open-destination rules of <<ACE-instruction-derive>> apply.

[[ACE-instruction-input]]
==== ace.input

_Synopsis_::
Load data into the ACEIOBUF.

_Mnemonic_::
`ace.input %offset(Xs), Xl`
(((ACE, instruction, ace.input)))

_Encoding_::
+
--
`ace.input` is an S-type instruction. The base address `Xs` occupies the `rs1` field and the
length `Xl` the `rs2` field, as in `ace.store` (<<ACE-instruction-store>>).

[wavedrom, , svg]
....
{reg:[
    { bits:  7, name: 0x2b, attr: ['custom-1'] },
    { bits:  5, name: 'immed[4:0]' },
    { bits:  3, name: 0x4, attr: ['ace.input'] },
    { bits:  5, name: 'Xs' },
    { bits:  5, name: 'Xl' },
    { bits:  7, name: 'immed[11:5]' },
]}
....
--

_Description_::
+
--
Without `Zklv`, inputs and outputs are exchanged with memory through the ACEIOBUF,
which `ace.input` and `ace.output` fill and drain (<<ACE-usage-input-output>>).

[[ACE-iobuf-transfer-window,the ACEIOBUF transfer window]]
The following holds for `ace.input` and for `ace.output`, and is
stated here once. Both transfer the bytes of the transfer window: for each `j` from `acestart` to
min(`Xl`, `aceiobuftop`) − 1,
`ace.input` copies the byte at memory address `%offset(Xs)` + `j` to byte `j` of the ACEIOBUF,
whereas
`ace.output` copies byte `j` of the ACEIOBUF to the byte at memory address `%offset(Xs)` + `j`.
Bytes below `acestart`,
and bytes at or beyond min(`Xl`, `aceiobuftop`), are not accessed on either side.
If `Xl` = 0, or `acestart` {ge} min(`Xl`, `aceiobuftop`), the operation transfers nothing.
If `Xl` is greater than `aceiobuftop`, only the bytes of the window are transferred; software can
detect this case by comparing `Xl` with `aceiobuftop`.

The usage of `ace.input` and `ace.output` is explained in detail in
<<ACE-usage-input-output>>.
--

[[ACE-instruction-clear]]
==== ace.clear, ace.clear.all

_Synopsis_::
Clears and unconfigures a CR, or the ACE state.

_Mnemonic_::
`ace.clear Kd|K{Xd}` +
(((ACE, instruction, ace.clear)))
`ace.clear.all`
(((ACE, instruction, ace.clear.all)))

_Encoding_::
The pseudo-instructions `ace.clear`/`ace.clear.all` are implemented as `ace.setst` (see <<ACE-instruction-setst>>) with no auxiliary operands and the immediate for _State_ set to `ace_state_unconfigured` (as defined in <<ACE-State-field>>).

_Description_::
+
--
`ace.clear` clears and unconfigures the CR `Kd` or `K{Xd}`–and any internal copies thereof–, marks it as _Unconfigured_ in its metadata, and releases the resources in the CRF.

Clearing (i.e., unconfiguring) a CR that was not already _Unconfigured_, or whose `*lcrstatus` field in effect is _Off_ (<<ACE-CSR-lcrstatus>>), sets the `*lcrstatus` fields in effect for the current privilege mode, and the `ACES` fields in effect, to _Dirty_. The CR's own _State_ field becomes _Unconfigured_.

`ace.clear` with indirect CR addressing and `Xd` = `X0` encodes `ace.clear.all`.
This instruction unconfigures all the CRs and the ACEIOBUF, zeroing the buffer and setting
`aceiobuflen`, `aceiobuftop` and `acestart` to 0, zeroizes the three authentication registers of <<ACE-CRF>>, and writes 32 to `acemanagedcr`.
--

[[ACE-instruction-clearads]]
==== ace.clear.ads

_Synopsis_::
Clears any ADS from the target CR

_Mnemonic_::
`ace.clear.ads Kd|K{Xd}`
(((ACE, instruction, ace.clear.ads)))

_Encoding_::
This pseudo-instruction is implemented as `ace.setst` (see <<ACE-instruction-setst>>) with no auxiliary operands and the immediate for _State_ set to `ace_cfg_clear_ads`, i.e., the value 64.

_Description_::
+
--
`ace.clear.ads` deletes any ADS from the target CR.
This instruction is used when exporting a CR for use by some other target, possibly some different implementation.
_AuxDataLen_ and _ADSDropped_ are set to 0. The operation therefore produces a more compact layout without ADS that a destination with a different ACE Unit may have to drop anyway.
Exporting a CR into a SCC in this state will result in an ADS-free SCC being generated.
The first usage instruction that needs to access the ADS regenerates it.
--

[[ACE-instruction-getst]]
==== ace.getst, ace.getstx

_Synopsis_::
Returns the _State_ field, resp. the _StateExtension_ field, of the metadata of the source CR.
This is useful to determine whether a CR is in an Error State, as defined in <<ACE-State-field>>.

_Mnemonic_::
`ace.getst Xd, Ks|K{Xs}`
`ace.getstx Xd, Ks|K{Xs}`

_Encoding_::

_Description_::

and `ace.getstx` as

Nested Management Operations:::
A _nested_ management operation is one opened on a CR that is already under management;
the _base operation_ of a group of nested operations is its outermost management process.
The two Configuration States whose mnemonics contain `ppi` (“partial provisioning input”)
are reached only by a nested management operation whose base operation is a provisioning.
When an import or an export of a CR in a Complete State is interrupted, a nested management operation reuses
`ace_cfg_exporting` and `ace_cfg_importing`, and the base operation is that import or export.
Clearing a CR is an atomic operation that resets the CR to the _Unconfigured_ state, and
as such it is not a nested management operation.

[[ACE-nested-state-base-types,Nested State Base Types]]
Nested State Base Types:::
The `pi` and `scc` base types of the nested States record whether the image the CR holds originates
from a PI or an SCC, following from the base operation: the base type of a Configuration State is `pi` for
`ace_cfg_provisioning`, `ace_cfg_ppi_exporting` and `ace_cfg_ppi_importing`, and `scc` for
`ace_cfg_exporting` and `ace_cfg_importing`.
They determine its length
(<<ACE-instruction-size>>), which could not otherwise be recovered once the nested management
operations have overwritten the original _State_.

The immediate in the `ace.setst` instruction (<<ACE-instruction-setst>>) is a 7-bit value, whereas the _State_ field is only 6 bits long.
This allows `ace.setst` to encode additional operations related to state changes.
The only architected such operation is encoded with the value 64 (`ace_cfg_clear_ads`), which clears any ADS so that the CR can be exported without it; values 65–127 are available to Algorithms
(see <<ACE-instruction-clearads>>).

* Error States have double rounded rectangular borders.

* Dashed edges denote state transitions induced by reaching the expiration date.
* Dotted edges denote state transitions induced by configuration operations.

The following rules are generic and apply to all Algorithms (*SGR* means "State-Specific General Rules"):

[horizontal]
SGR1:: The MDH's _State_ field reflects the current state whenever the CC is in _Ready_, _Success_, _Failure_, or any Error State.
This ensures that these states can be unambiguously determined from the _State_ field alone, without inspecting other fields or the Content.

[[ACE-SGR-no-exec-in-ready,SGR2]] SGR2:: No `ace.exec` instruction may be executed in State _Ready_ unless the Algorithm explicitly allows it.
Issuing one otherwise transitions the CR to Error State _Invalid_ (Rule <<ACE-AGR-not-allowed-instructions>> in Book 2).

SGR3:: Any transition listed in an Algorithm's specification may be triggered by performing an explicit `ace.setst` operation (<<ACE-instruction-setst>>), or may be induced by certain conditions specified in the Algorithm's specification. Transitions to and between _Configuration_ States use `ace.mgmt`; transitions from a Configuration State use `ace.mgmt`, `ace.clear`, an Error State-setting `ace.setst`, or an `ace.clone` naming the CR as destination.

SGR4:: In a Valid State other than _Success_ and _Failure_, `ace.setst` may be issued with the immediate of the current State.
When the Algorithm needs to prevent this, it transitions to a different State upon completing the instruction.

[[ACE-SGR-success-failure,SGR5]] SGR5:: In States _Success_ and _Failure_, only the following ACE instructions are permitted: `ace.mgmt`, `ace.size`, `ace.avail`, `ace.setst` (subject to Rule <<ACE-SGR-setst-in-success-failure>> below), `ace.getmd*`, `ace.getst`, `ace.clone`, `ace.restrict*`, and `ace.derive`.
An `ace.exec` other than those permitted below, or an `ace.setst` not allowed by the architecture or by the Algorithm in its current _State_ and _StateExtension_, transitions the CR to Error State _Invalid_ (cf. Rule <<ACE-AGR-not-allowed-instructions>> in Book 2).
+
In State _Success_ `ace.exec` is also permitted solely to extract further output from an Algorithm that produces arbitrarily long output, such as a XOF.
Also permitted is `ace.derive` in the following two cases: where the source endpoint is one of its exportable fields (<<ACE-instruction-derive>>); and under the conditions of use of `ace.exec`.
+
A CR in State _Success_ or _Failure_ may not be the *destination* of an `ace.derive`.
+
NOTE: `ML-KEM.Decaps` (<<ACE-PQC-ML-KEM>>) is the motivating case for this `ace.derive` behavior:
it leaves the shared secret in `sharedkey` and
transitions to _Success_, from which the only other exit is _Ready_, and _Ready_ clears
`sharedkey`. Without this provision the shared secret would be unreachable and ML-KEM could not
be used for its stated purpose.

[[ACE-SGR-setst-in-success-failure,SGR6]] SGR6:: In States _Success_ and _Failure_, `ace.setst` is only permitted to transition to _Ready_ if the Algorithm does not forbid it, to _Unconfigured_ using `#immed7` = `ace_state_unconfigured`, or to an explicitly given Error State.
It is also permitted with `#immed7` = `ace_cfg_clear_ads` (<<ACE-instruction-clearads>>), which clears any ADS and leaves the _State_ unchanged, when this does not violate usage-control policy.

SGR7:: States _Success_ and _Failure_ cannot be set directly using `ace.setst`: the immediates 46 and 47 are reserved (<<ACE-illegal-instruction-grounds>>).

SGR8:: A transition from any valid state to _Ready_ using instruction `ace.setst` is always permitted, unless the Algorithm explicitly forbids it.
// +
// NOTE: Since a CR can always be restored from a backup SCC, preventing transitions to _Ready_--as "GCM with Set IV" (<<ACE-GCM-with-IV-mode>>) does--is not an effective mitigation against the attacks that would be enabled by transitioning to _Ready_.

SGR9:: The CR state after `ace.setst` completes does not always match the instruction's immediate operand.
Beyond Error State transitions, some operations determine the next state dynamically.
For example, issuing `ace.setst` with an `ace_state_hash_verify` immediate and a verification parameter transitions the CR to either _Success_ or _Failure_.
Instructions such as `ace.exec` may also cause _State_ changes.

[[ACE-SGR-clear-cr-content-error-state,SGR10]] SGR10:: Upon transitioning to an Error State, the Content of a CR beyond the MDH is cleared:
Internal resources associated with the Content shall also be released,
including any ADS, and the _AuxDataLen_ and _ADSDropped_ fields are set to 0.

[[ACE-SGR-error-state-CR-is-only-MDH,SGR11]] SGR11::
A CR in an Error State then retains only the MDH.
Requesting its size (<<ACE-instruction-size>>) returns 16 bytes.

[[ACE-SGR-transition-to-from-unconfigured,SGR12]] SGR12:: Transitions from _Unconfigured_ to any Complete State may only result from a configuration instruction.
Any usage-controlled instruction (<<ACE-instruction-properties>>) in State _Unconfigured_ raises an illegal-instruction exception.
Transitions from an Error State to _Unconfigured_ result from explicitly clearing the CR, or from re-opening it for provisioning or import.

SGR13:: The MDH of a CR in the _Unconfigured_ State can be read using `ace.getmd*` (<<ACE-instruction-getmd>>), returning all zero values.

SGR14:: Exporting a CR in an Error State exports only the MDH (all fields and values), and requires no
`ace.mgmt`:
The MDH of a CR in an Error State is read by software using `ace.getmd*` (<<ACE-instruction-getmd>>) and stored to memory.
The image can be reimported with a single `ace.mgmt`, allowing software to take appropriate actions even after a context switch.

SGR15:: If a CR is in any Error State, it can still be reconfigured, cloned, or cleared;
apart from clearing, `ace.setst` can only be used to change the Error State.

[[ACE-SGR-usage-cr-error-state,SGR16]] SGR16:: Attempts to _use_ a CR in any Error State will not perform any operation, and in particular leave the _State_ field unchanged.
Such an attempt can be considered an operation that would cause a transition to  Error State `ace_state_invalid`, so the _State_ field is left unchanged to allow software to address the original error condition. No history of Error States is maintained by the architecture.
+
A usage instruction with an output operand that performs no operation under this Rule or under Rule <<ACE-SGR-gate-order>> (Error State, expiration), or that transitions its CR to an Error State during execution, writes zeros to every byte of its output window that it has not written: elements `vstart` to `vl` − 1 of `Vd` for a vector output, bytes [`acestart`, `aceiobuftop`) for an ACEIOBUF output. An in-place operation thus never leaves its input in place of the output it did not produce.

[[ACE-SGR-usage-policy,SGR17]] SGR17:: Any _usage_ instruction that would violate the Usage Control policies will not perform its operation, and raises ACE exception `ace_exc_privilege_violation`. See <<ACE-error-architecture>> for the exact behavior, including when the Privileged Architecture is not implemented.

[[ACE-SGR-usage-cr-config-state,SGR18]] SGR18:: Usage of a CR in a Configuration State, cloning from it, and restricting it, are not allowed:
Any attempt to do so raises ACE exception `ace_exc_privilege_violation`.
For a CR in a Configuration State used as the destination of an `ace.clone`, or named as both its source and its destination, see <<ACE-instruction-clone>>.

[[ACE-SGR-gate-order,SGR19]] SGR19:: For a usage-controlled instruction (<<ACE-instruction-properties>>), after the illegal-instruction grounds decided without accessing the state of the ACE unit (the first group of <<ACE-illegal-instruction-grounds>>), `ace_exc_fatal`, `ace_exc_no_csk` and `ace_exc_CR_off` (<<ACE-CSR-lcrstatus>>), and then the `acestart`/`vstart` check of <<ACE-CSR-acestart>>, the conditions on a CR are evaluated in this order, and the first that applies decides the outcome:
+
--
. _Unconfigured_: illegal-instruction exception (Rule <<ACE-SGR-transition-to-from-unconfigured>>);
. Error State: no operation and no exception (Rule <<ACE-SGR-usage-cr-error-state>>);
. Configuration State: ACE exception `ace_exc_privilege_violation` (Rule <<ACE-SGR-usage-cr-config-state>>);
. a forbidden ACEIOBUF substitution, or a Form A `ace.exec` with `Vd` = `Vs2` that <<ACE-instruction-exec>> forbids: illegal-instruction exception (<<ACE-illegal-instruction-grounds>>);
. _UsagePolicy_: ACE exception `ace_exc_privilege_violation` (Rule <<ACE-SGR-usage-policy>>);
. _ExpirationDate_: transition to Error State `ace_state_expired`, then no operation (<<ACE-Metadata-expiration-date>>);
. an ACEIOBUF required by a substitution but unconfigured: ACE exception `ace_exc_unconfigured_buffer` (Rule <<ACE-GR-iobuf-configured>>);
. the Algorithm's own rules.

For `ace.derive`, each condition is evaluated for both endpoints, the source first, before the next; an Error State on either endpoint makes the whole instruction a no-op.
--

[[ACE-SGR-config-instructions-partial,SGR20]] SGR20:: Instructions `ace.size`, `ace.avail`, `ace.getmd*`, `ace.getst`, `ace.setst` with the 7-bit immediate equal to `ace_state_unconfigured` or an
Error State, `ace.clear`, and `ace.clear.all`, which are configuration instructions and are not gated by Usage Control policies, are also allowed
when the CR is in a _Partial_ State.

[[ACE-SGR-ace-load-mv-allowed,SGR21]] SGR21:: `ace.load` and `ace.mv` with a destination CR
are allowed in States `ace_cfg_provisioning`, `ace_cfg_importing` and `ace_cfg_ppi_importing`.

[[ACE-SGR-ace-store-mv-allowed,SGR22]] SGR22:: `ace.store` and `ace.mv` with a source CR
are allowed in States `ace_cfg_exporting` and `ace_cfg_ppi_exporting`.

[[ACE-Memory-Model]]
=== Memory Model

// [WARNING]
// ====
// A full axiomatic integration of the ACE component memory operations
// into the RVWMO formalism remains to be produced together with the
// ARC during ratification.
// ====

MMR means “Memory Model Rule.”

[horizontal]
MMR1:: ACE memory instructions appear to execute in program order on the local hart.

MMR2:: ACE memory instructions follow RVWMO at the instruction level.
If `Ztso` is implemented, they additionally follow RVTSO at the instruction level.

MMR3:: ACE memory instructions are supported only for idempotent memory: no component access is made to a non-idempotent or side-effecting PMA region.
If a component access would touch such a region, the instruction halts precisely at the last prefix-complete point before the offending byte (0 under the restart option of Rule <<ACE-IRR-resumability-options>>), with the completed prefix committed as in Rule <<ACE-IRR-which-resumable-instructions>>, and raises a load, resp. store, access-fault exception with `xepc` at the instruction and `xtval` the offending address; re-execution raises the same exception before any component access unless the offending byte no longer maps to such a region.

MMR4:: ACE memory instructions may be decomposed into component memory operations of any granularity.
Their issue order is not architecturally constrained beyond the applicable memory model and the semantics of
`ace.exec`, `ace.load`, `ace.store`, `ace.input`, and `ace.output`.
Intra-instruction ordering follows RVWMO, even when `Ztso` is implemented.
Upon precise interruption, `acestart` must record a _prefix-complete_ point of the transfer.

MMR5:: Other harts observe these component memory operations as ordinary memory operations under RVWMO.
No ordering among them is guaranteed before the instruction completes.
Sharing a buffer accessed by an ACE memory instruction requires the same synchronization as sharing it with an ordinary software loop.

MMR6:: For the purposes of `FENCE`, `FENCE.I`, `SFENCE.VMA` and the `.aq`/`.rl` annotations, the component accesses of an ACE memory instruction are ordinary loads (`ace.load`, `ace.input`) or stores (`ace.store`, `ace.output`) of the issuing hart.

[[ACE-resumability]]
=== Interruptibility and Resumability of ACE instructions

IRR means “Interruptibility and Resumability Rule.”

[horizontal]
[[ACE-IRR-uninterruptible-instructions,IRR1]] IRR1:: Instructions `ace.mgmt`, `ace.getmd*`, `ace.restrict*`, `ace.clone`, non-vector `ace.mv`, `ace.size` and `ace.avail` are _uninterruptible_: each either completes or has no architecturally visible effect, including no writes to destination vector registers, GPRs, CR bytes, ACEIOBUF bytes, or memory.
An implementation realizes this in one of three ways: completing the instruction before taking an asynchronous interrupt; completing it in the background where Rule <<ACE-IRR-long-running-no-data>> permits, subject to Rule <<ACE-IRR-conflicting-access-rule>>; or discarding partial work before taking the trap and restarting upon return.
Software must not rely on whether an uninterruptible instruction has retired when a handler runs and must interact with it only as Rule <<ACE-IRR-conflicting-access-rule>> prescribes.

IRR2:: The architecture specifies no interruption points for `ace.setst`, nor within a single block-processing unit of `ace.exec`. An implementation may nonetheless make a long-running instruction of either interruptible, in the ways Rule <<ACE-IRR-long-running-no-data>> gives.

[[ACE-IRR-resumability-options,IRR3]] IRR3:: In general, the following behaviors are allowed when an interrupt or exception handler accesses an input or output of a preempted instruction, the associated CR, or any ACE state that may be affected by the instruction:

. _Background completion:_ The hart waits for the instruction to complete when the privileged handler accesses affected state. This option is not available for `ace.load`, `ace.store`, `ace.input` and `ace.output`, since these are treated as RISC-V memory instructions.
. _Atomic completion_ of the instruction before any asynchronous interrupt is taken.
. _Precise halt and resumption:_ The instruction halts with `acestart` recording a prefix-complete point (<<ACE-Memory-Model>>), and resumes from `acestart`, advancing by at least one granule per execution attempt.
. _Timeout followed by precise halt and resumption:_ The system may impose a timeout before halting as described above.
. _Precise halt and restart,_ provided that restart is not the unconditional response to asynchronous
interrupts: repeated interruption of the same instruction must not prevent its eventual completion. This option is available for `ace.load`, `ace.store`, `ace.input`, and `ace.output`, whose transfers are idempotent, and for the long-running instructions of Rule <<ACE-IRR-long-running-no-data>>; block-iterated `ace.exec`, `ace.derive`, and vector `ace.mv` use option 3 or 4 (Rule <<ACE-IRR-block-iterated-instructions>> below).

[[ACE-IRR-long-running-no-data,IRR4]] IRR4:: An Algorithm's semantics for `ace.exec`, `ace.setst` or `ace.derive` forms that access no vector register or ACEIOBUF, and no GPR other than scalar operands captured at issue (Rule <<ACE-IRR-conflicting-access-rule>>), may perform long-running instructions that access no external memory.
Examples of such long-running instructions include scalar multiplication, key generation, and signature generation or verification.
+
Upon preemption, they may follow any of the behaviors described in <<ACE-IRR-resumability-options>>, compatibly with the requirements of the interrupt or exception.
The implementation must support at least one of options 3, 4 and 5 of Rule <<ACE-IRR-resumability-options>> for these operations; under option 5 it guarantees, and documents, a minimum uninterrupted execution quantum or a maximum number of consecutive restarts of one instruction, so that repeated interruption cannot prevent completion.
If an operation continues while the hart is preempted and the hart waits for completion before accessing the affected state, any nested interrupt handler must also wait before accessing that state.
+
If such an operation can advance its recorded progress towards completion of the operation, interrupt at well defined points, and resume from the recorded progress point, the progress must be recorded in the _AlgorithmUse_ field, in an implementation-defined format; `acestart` remains reserved for byte counts (<<ACE-CSR-acestart>>). An implementation may interrupt such an operation and record its progress only where the recorded state, including the ADS, cannot be consumed against inputs other than those the operation started with; Rule <<ACE-AGR-progress-discard>> of Book 2 guarantees this by discarding the recorded state on any transition of the CR's _State_ other than the completion of the operation (Rule <<ACE-GR-atomic-randomness>>). If progress is recorded, the implementation exports the data necessary to support resumption in the ADS. Any importing implementation may discard this Section and restart the operation, and must restart it on an Implementation Qualifier mismatch, or if the ADS is removed from the CR (using `ace.clear.ads`, cf. <<ACE-instruction-clearads>>).
+
The architected Content of the CR does not depend on the progress of the operation: an implementation that records progress keeps every intermediate result in the ADS, and if the operation restarts, it does so from the architected Content alone.

[[ACE-IRR-conflicting-access-rule,IRR5]] IRR5:: All the approaches in Rule <<ACE-IRR-resumability-options>> are subject to one rule: Before the issuing hart performs a _conflicting access_, the in-flight operation must either have completed or have been precisely halted with `acestart` set per <<ACE-Memory-Model>>. A conflicting access is any of the following:
+
--
* An ordinary load or store overlapping the memory region of the in-flight ACE operation.
* An access to a CR used by the operation, including the issue of another ACE instruction involving a CR used by the operation.
* A read or write of `acestart` or an ACEIOBUF CSR.
* A read or write of a GPR or vector register that the operation writes as its destination.
* A write to a vector register or to the ACEIOBUF that the operation reads as an operand, including the issue of an `ace.input` targeting it. Scalar operands held in GPRs are captured when the instruction issues, so accessing one is not a conflicting access.

Rules <<ACE-IRR-resumability-options>> and <<ACE-IRR-conflicting-access-rule>> make asynchronous execution by the attached ACE unit invisible to same-hart program order, as <<ACE-Memory-Model>> requires. Beyond this rule, the architecture specifies only the allowed interruption points for its instructions and Algorithms.
--

[[ACE-IRR-which-resumable-instructions,IRR6]] IRR6:: The resumable instructions are `ace.exec`, vector `ace.mv`, `ace.derive`, `ace.load`, `ace.store`, `ace.input`, and `ace.output`. Architecturally, they process input units serially. If an instruction halts precisely, the completed prefix is committed, the failing and subsequent units have no effect, `acestart` records a prefix-complete point, the instruction does not retire, and `xepc` contains its address. If an instruction transitions its CR to an Error State after partial progress, the completed prefix remains committed, the unwritten part of its output window is zeroed (Rule <<ACE-SGR-usage-cr-error-state>>), and the instruction retires (<<ACE-CSR-acestart>>).

[[ACE-IRR-block-iterated-instructions,IRR7]] IRR7:: For block-iterated `ace.exec`, `ace.mv`, and `ace.derive`, fully processed blocks remain written or transferred, and `acestart` records their total byte count. For transfer instructions, bytes below `acestart` remain transferred at both endpoints. A partially executed instruction commits exactly the state that a shorter instruction performing only the completed operations would have committed. This includes the CR, `acestart`, `*lcrstatus`, and effective `ACES` fields, ensuring consistent context save, restore, and resumption. Implementations must honor `acestart` for `ace.exec` and `ace.derive`. Handlers must not reset it to zero to force a restart, as this could reapply state changes or corrupt data.

IRR8:: ACE memory instructions (`ace.load`, `ace.store`, `ace.input`, and `ace.output`) are RISC-V memory instructions: such an instruction is complete, and may retire or take a trap with `xepc` past it, only after every component access has passed address translation and permission checks and has been performed.
Otherwise, similarly to vector memory operations, the implementation halts the instruction precisely, with `acestart` at a prefix-complete point allowed by the instruction, and raises the corresponding load/store page-fault, guest-page-fault or access-fault exception synchronously for that execution attempt.
+
NOTE: After each `ace.load` the caller must check whether the CR is _Unconfigured_, in which case the entire configuration operation (not just the `ace.load` instruction, but the software using it) must be restarted: an exception handler may have cleared the CR and advanced `xepc` to force this behavior.
// +
// NOTE: Clearing a CR in an exporting State (<<ACE-instruction-setst>>) calls for particular care from an
// exception handler, because until the export completes, the ciphertext the CR holds may be the only copy of
// the CC. A handler that intends to clear such a CR must first see the export through to completion — if
// necessary across preemptions of its own by a more privileged mode — and store the resulting image.
// If it clears the CR earlier, by mistake or on an unrecoverable error, the CC is lost: the caller detects
// this by the same check after `ace.store`, must treat the error as unrecoverable, and a further
// `ace.store` on the cleared CR raises an illegal-instruction exception (<<ACE-instruction-store>>).
// This allows the error to propagate to the outermost caller.

// [[ACE-IRR-algorithms-specific,IRR9]] IRR9:: Algorithm-specific resumable long-running operations that transfer no data
// in an `ace.setst`, in a (block-processing step of) `ace.exec` operation,
// or in an `ace.derive` operation,
// must either advance its recorded progress towards completion of the operation, or restart.
// The manner in which progress is recorded is implementation-defined, but it cannot use `acestart`
// (for instance, it can use _AlgorithmUse_, as in <<ACE-ECC>> and <<ACE-PQC>>).
// Implementations capable of resuming these operations also support their restart.

[[ACE-usage-input-output]]
=== Replacing Vector Inputs and Outputs with ace.input and ace.output

When `Zklio` is available, a Form of `ace.exec`, `ace.setst`, or `ace.mgmt` that reads inputs
from vector registers or writes outputs to them may be replaced by the corresponding Form with no
vector operands.
That Form is the one where the inputs or outputs that would be provided through vector registers
are omitted completely.
That Form is _native_ when the operation requires no input or output.
When issued in an Algorithm's State where vector inputs or outputs are expected, it is instead
a _substitution_, and it uses the ACEIOBUF for the expected inputs or outputs, rather than
raising an illegal-instruction exception.

The instructions `ace.input` and `ace.output` perform no computation and change no state other than the ACEIOBUF
and `acestart`; all computation and all other state changes remain in `ace.exec`, `ace.setst`, and `ace.mgmt`.

The substitutions are:

. A Form D `ace.exec` replaces a Form A, B or C `ace.exec`.
. A Form A `ace.setst`, or `ace.mgmt`, replaces the Form C of the same instruction.

// A Form D `ace.exec`, or a Form A `ace.setst` or `ace.mgmt`, is a _substitution_ when the operation
// it performs defines an input or an output, and is _native_ otherwise. A native Form neither reads
// nor writes the ACEIOBUF, and ignores `acestart`, which it leaves unchanged; `ace.mgmt`, in every
// Form, and `ace.clear.all` nevertheless clear it (<<ACE-instruction-setst>>, <<ACE-instruction-clear>>).

A substitution reads its inputs from, and writes its outputs to, the ACEIOBUF:

* A substituted Form A `ace.exec` behaves as a Form A with `Vd` = `Vs2` (<<ACE-instruction-exec>>):
  each block's output replaces its input at the same offset of the window.
* A substituted Form C `ace.exec` writes its output to [`acestart`, `aceiobuftop`); bytes of the
  window it does not write are unchanged, and no byte at or beyond `aceiobuftop` is written.
* A substituted Form A `ace.setst` reads its auxiliary input from bytes [0, `aceiobuftop`) of the
  ACEIOBUF, ignoring `acestart`; the truncation to the operand width of
  <<ACE-algorithms-other-rules>> applies.
* `ace.exec` never modifies `aceiobuftop`.

A substitution fails as follows:

* Without `Zklio`, it raises an illegal-instruction exception.
* Mixing vector and ACEIOBUF operands is not allowed: replacing a Form A `ace.exec` by a Form B or
  C `ace.exec` raises an illegal-instruction exception.
* An operation whose output blocks do not have the same length as its input blocks may be substituted
  only if its Algorithm states where its output is written in the ACEIOBUF; otherwise the
  substitution raises an illegal-instruction exception.
* If the ACEIOBUF is not enabled or `aceiobuflen` is zero, ACE exception
  `ace_exc_unconfigured_buffer` is raised.
* If `aceiobuflen` is non-zero but `aceiobuftop` is a length invalid for the Algorithm, or, for
  `ace.exec`, `acestart` is not an interruption point the Algorithm allows:
** if the ACEIOBUF is used as an input, the CR transitions to Error State _Invalid_;
** if it is used only as an output, the instruction performs no operation:
   no state changes.

In <<ACE-Algorithms>>, when a Form of `ace.exec`, `ace.setst`, or `ace.mgmt` is
_expected_ (rather than _required_ or _the only Form allowed_), the substitutions above apply
implicitly and are not repeated for each occurrence.

<<ACE-replacement-instructions>> gives examples of alternative sequences using `ace.input` and
`ace.output`.

[[ACE-CC-management]]
=== Management of Cryptographic Contexts

In keeping with RISC-V philosophy, ACE splits complex CR management operations into sequences of simpler instructions rather than implementing them as single instructions driving very large state machines or triggering microcode. Even a trap-and-emulate implementation of complex monolithic instructions would have to support such a splitting by definition.

This has several effects:

. The state machine for managing keys and algorithms, hidden from software in key-protection solutions on other CISC architectures (cf cite:[IBM-z-arch] “Protection of Cryptographic Keys” or cite:[intel-keylocker]), is exposed to software.
Moving its sequencing out of hardware nevertheless significantly simplifies the hardware. However, the exposure may make the state machine managed by software more complex, and increase the set of rules the hardware must enforce, since management operations must withstand malicious attempts to tamper with them.
. Management sequences can be interrupted between instructions by interrupts and exceptions.
Explicit support is therefore required for context switching, process and virtual machine migration, hibernation, and interoperability between ACE implementations.
. Dynamic CR management, including lazy context loading, must be supported explicitly rather than relying on implicit caching for repeated key use, as other architectures may do.
The confidentiality and integrity of a CC's MDH and Content must be preserved under these conditions.

ACE meets these requirements while maintaining binary compatibility across implementations.
However, an implementation need not support resumption of interrupted management operations. In that case, the implementation may force a restart, or a context-switch handler may do so by explicitly clearing partially provisioned or imported CRs during context save or restore. Both the architected instructions and the software that uses them must be able to support both scenarios without requiring code changes.

// [NOTE]
// ====
// Such clearing must remain the exceptio: since an SCC can span several kilobytes, unconditionally clearing partially provisioned or imported CRs at every context switch may prevent a long management process from completing.
// The ACE ISA and the CR management sequences in <<ACE-management-code-snippets>> were co-designed to support resumption, nested context switching, and lazy SCC loading.
// ====

This section describes how the ACE ISA supports management of CRs and SCCs for all use cases.

ACE defines three external CC formats:

. The _Provisioning Input_ (PI), loaded into a CR to create a CC; and
. The _Sealed Cryptographic Context_ (SCC), an encrypted and authenticated representation of a CC used when exporting a CR to memory for later import.
. The _Partially Configured Cryptographic Context_ (PCCC), which is used to export a CR in the case a management operation has been preempted in order to be able to reimport its contents for a later resumption of the interrupted operation. Its format is identical to that of a PI or an SCC,
depending on the base type of the CR's Configuration State (see <<ACE-nested-state-base-types>>), except that no additional encryption or authentication is applied.

{empty}
(((Cryptographic Context,Metadata)))
(((Cryptographic Context,Metadata,Header)))
All three formats begin with the 128-bit MDH described in <<ACE-Metadata>>.

[[ACE-data-formats]]
==== Formats of PIs, SCCs, and Partially Configured Cryptographic Contexts

Provisioning Input (PI).:::
The MDH, whose _State_ is _Unconfigured_, followed by `Content`. The
`ace.mgmt` that completes the provisioning sets _State_ to _Ready_.

Sealed Cryptographic Context (SCC).:::
+
--
Up to five sections, in this order:

[[ACE-SCC]]
.Plaintext of the Sealed Cryptographic Context (SCC) Format, all Sections in Order
[width="100%",cols="^8%,15%,30%,47%",options="header"]
|===
| Section | Section Name | Size                 | Description
| 1       | `MDH`        | 128 bits             | See <<ACE-Metadata>>.
| 2       | `SIV`        | 128 bits             | Authentication tag for `MDH`, the Locality Secrets its _Locality_ names, and `Content1` (<<ACE-SCC-export>>).
| 3       | `IMPQUAL`    | 128 bits, if present | Identifies the implementation of the ACE Unit. Non-authoritative and ignored when _ADSDropped_ = 1.
| 4       | `SIV2`       | 128 bits, if present | Authentication tag for `IMPQUAL`, `SIV` and `Content2`. Non-authoritative and not verified when _ADSDropped_ = 1.
//
| 5.a
| `Content1`
| A multiple of 128 bits. See <<ACE-length-rule>>.
| Contains keys and other Algorithm-specific information. Encrypted in memory and during partial import.
 The data in this section is necessary for the correct functioning of the Algorithm.
//
| 5.b
| `Content2`
| A multiple of 128 bits.
| ADS: The data in this section is _not_ necessary for the correct functioning of the Algorithm.
  Encrypted in memory and during partial import.
|===

The _AuxDataLen_ field of the MDH gives the size, in 128-bit blocks, of the Implementation-Specific ADS (`IMPQUAL`, `SIV2` and `Content2`), or its size before `Content2` was dropped when _ADSDropped_ = 1. The ADS is empty if _AuxDataLen_ = 0; the value 1 is invalid. ACE generates an image with _ADSDropped_ = 1 only as an SCC-shaped PCCC: a nested export preserves an interrupted import after `Content2` was dropped. In that image, `IMPQUAL` and `SIV2` remain, `Content2` is absent, and the `Content1` offset is unchanged (<<ACE-Auxiliary-Data-Section>>). Because _ADSDropped_ is unauthenticated, import also accepts the same layout when the bit was set by modifying an SCC.
A CR in an Error State is its MDH alone (Rule <<ACE-SGR-error-state-CR-is-only-MDH>>).
--

Encryption during management.:::
While an SCC is imported, or a CR is exported as an SCC, the
`Content` held in the CR is encrypted:

. The `ace.mgmt` that opens an export encrypts it and generates `SIV` and, if _AuxDataLen_ {ge} 2,
  `IMPQUAL` and `SIV2`.
. The `ace.mgmt` that completes an import or an export decrypts and authenticates it. This requires
  the MDH and `Content` to have been loaded, and `SIV`, and if _AuxDataLen_ {ge} 2 also `IMPQUAL`
  and `SIV2`, to be in place. When _ADSDropped_ = 1, no `Content2` is loaded or authenticated. An export completion may instead restore the clear contents from an
  internal copy (<<ace-mgmt-completes-export>>).

Partially Configured Cryptographic Context (PCCC).:::
+
--
A CR under management that is exported at a nested level produces a PCCC: its data is exported verbatim, with no
further encryption or authentication, in a shape given by the base type of the CR's Configuration
State (<<ACE-nested-state-base-types>>):

* `pi` (State `ace_cfg_ppi_exporting`, a partially provisioned CR): a _PI-shaped_ image, the MDH
  followed by the clear `Content` of a PI. This is not a security issue, as the plaintext was
  already available to software, and thus to its more privileged modes.
* `scc` (State `ace_cfg_exporting`, a partially imported SCC, or a CR whose export was itself
  preempted): an _SCC-shaped_ image, the MDH followed by `SIV` and, when present, `IMPQUAL` and
  `SIV2`, as _ContentOffset_ prescribes (<<ACE-instruction-load>>), and by the ciphertext `Content`
  already held in the CR.

By saving each MDH in its own local state, software keeps an implicit stack of _State_ values,
whose top belongs to the previous nesting level and is restored by the completing `ace.mgmt`.
To track the progress of `ace.load`, `ace.store` and `ace.mv`, context switching handlers
must save and restore `acestart`.
--

[[ACE-length-rule]]
==== Determination of the Length of a PI/SCC/PCCC and the CRF capacity usage of a CR

Except when the CR is in an Error State, the MDH fields that determine the length
of a PI, of an SCC and of a PCCC, as well as the CRF capacity occupied by a CR, are all
contained in the lower 64 bits of the MDH:

. The length of a *Provisioning Input* is determined by, and only by, the fields
_Algorithm_, _AlgorithmPolicy_ and _KeyType_.
It does *not* depend on _AuxDataLen_ or _ADSDropped_: a PI and a PCCC whose Configuration State has base type `pi` carry no ADS, and _AuxDataLen_ and _ADSDropped_ must be zero in their MDH.
It also does not depend on _StateExtension_ or _AlgorithmUse_, whose values are ignored and are
replaced with zero by `ace.mgmt` upon provisioning, nor on _SCProtection_.
During provisioning, the information of a CR reflects the external format of a PI.
The internal representation is finalized into the CR's internal state upon using
`ace.mgmt` to complete the provisioning, which may include the computation of
information such as derived keys, or multiple shares.

. The length of a *Sealed Cryptographic Context*
is determined by, and only by, the
fields _Algorithm_, _AlgorithmPolicy_, _KeyType_, _StateExtension_, _AuxDataLen_, and _ADSDropped_ (see <<ACE-Auxiliary-Data-Section>>). _ADSDropped_ can remove only `Content2`; it never changes the presence of `IMPQUAL` or `SIV2`, or the offset or length of `Content1`. Note that this length does not depend on _State_.
It also does *not* depend on _SCProtection_ (see <<ACE-rules-masked-implementations>>).

. The length of a *Partially Configured Cryptographic Context* is that of a
Provisioning Input if the base type of its Configuration State (<<ACE-nested-state-base-types>>) is a PI,
and that of a Sealed Cryptographic Context if the base type of its Configuration State is an SCC.
// identifies: the `Content` of a PI for a
// `_pi` State, and `Content1` together with `Content2` for an `_scc` State. Once the image is
// identified, its length is given by the rule above for that format, and depends on no further field.

. The *CRF capacity* occupied by a CR is determined by, and only by, the fields
_Algorithm_, _AlgorithmPolicy_ and _SCProtection_.
It does not depend on _KeyType_, because a CR holds the expanded key material whether the
key was provisioned by value or retrieved through a System Key Identifier,
nor on _StateExtension_, because a CR is allocated with room for every field the
Algorithm may come to use.

No other MDH field and no information in the `Content` may affect any of these four quantities. _ADSDropped_ affects the lengths of SCCs and SCC-shaped PCCCs, but does not affect CRF capacity.

A CR in an Error State is its MDH alone (Rule <<ACE-SGR-error-state-CR-is-only-MDH>>, <<ACE-error-state-transfer>>).
A PI cannot be in an Error State.

[[ACE-rules-masked-implementations]]
==== Single-Share Key Export Rule for Masked Implementations

Any multi-share implementation of an Algorithm will always provision, import and export _all_ its keys and secrets as reconstructed values.
This keeps SCCs compact and ensures interoperability across architectures with different implementations.
(((ACE, Algorithm, side-channel protection variants)))
Architecturally, all values are represented as a single share.
Side-channel analysis (SCA)-protected Algorithms are implementation variants of the same unprotected Algorithm, not separate specifications.
The only difference is the _SCProtection_ field of the MDH.

NOTE: While reconstructing or re-randomizing a key is in general inexpensive, for instance if the masks are generated
by a block cipher in counter mode,
an implementation that is using a slower method to generate the masks
may include shares or masks in the ADS to accelerate multiple-share reconstruction of a key.

[[ACE-system-keys]]
==== System Keys and Randomly Generated Key Values

In a PI or SCC, System Keys are encoded as a 64-bit SKID used to retrieve the key from a system-specific SKS.
This replaces the key value itself with a usually smaller field, and may reduce the size of the PI or SCC.

The SKS resolves a SKID different from the all-ones value only as a function of the SKID,
provided it is allowed for the given _Algorithm_ and _AlgorithmPolicy_.
The value of the key does not depend on _Algorithm_ and _AlgorithmPolicy_.
For an Algorithm whose _AlgorithmPolicy_ encodes permissions, a SKID allowed for an _AlgorithmPolicy_ is allowed for every _AlgorithmPolicy_ whose set bits are a subset of it.
The current privilege mode does not affect whether the SKS may resolve a given SKID.

A SKID other than the all-ones value that it does not or is not allowed to resolve transitions the CR to Error State _Invalid_ (see <<ACE-Metadata-validity>>).

Whenever a SKID is resolved, the _UsagePolicy_ of the CR becomes the intersection of the permissions already encoded in the PI or SCC and those of the key (bits 0–3 or-ed, bit 4 and-ed), and its _Locality_ the union of the Localities in the PI or SCC and those of the key (the stricter entry in each HW Binding chain, bits 6–8 or-ed); if the two Boot Session entries are non-zero and differ, or the resulting _Locality_ names an unconfigured entry (<<ACE-Localities>>), the CR transitions to Error State _Invalid_, as it does for a supplied MDH at provisioning.

The all-ones SKID (<<ACE-KeyType-field>>) is not resolved by the SKS.
A SKID carried in an SCC is resolved only after the SCC has been authenticated.

In multi-share implementations, ACE may copy System Key material from the SKS into the CR and expand it into multiple shares.
The key must still be exported as a SKID.
Any shares or masks included in the ADS (see <<ACE-rules-masked-implementations>>) must not allow or facilitate recovery of the key's value from those values alone.

[[ACE-CR-management]]
==== CR Management Operations

Here we give the values of the `#immed7` field for `ace.mgmt`, and the semantics of the operations that they perform.

[[ACE-management-immeds]]
.Values (decimal) of `#immed7` to be used for provisioning, importing, and exporting
[float="center",align="center",width="100%",cols="^7%,<27%,<66%",options="header"]
|===
| Value | Mnemonic                  |  Description
|  56   | `ace_cfg_provisioning`    |  Prepare a CR for provisioning.
|  57   | `ace_cfg_exporting`       |  Prepare a CR for export.
|  58   | `ace_cfg_importing`       |  Prepare a CR for import.
|  63   | `ace_cfg_management_end`  |  Complete current management operation.
|===

Depending on the previous state of the CR, the actual _State_ after a non-faulting `ace.mgmt` instruction may be different:

. After `ace.mgmt`, with #immed7 = `ace_cfg_importing`, the CR's _State_ becomes
.. `ace_cfg_ppi_importing` if the data originates from a CR whose provisioning operation had not been completed,
.. `ace_cfg_importing` otherwise, also when the data originates from a CR whose import or export had not been completed.
. After `ace.mgmt`, with #immed7 = `ace_cfg_exporting`, the CR's _State_ becomes
.. `ace_cfg_ppi_exporting` if the CR being exported contains the image of a CR whose provisioning operation had not been completed,
.. `ace_cfg_exporting` otherwise, also when the CR is in `ace_cfg_importing` or `ace_cfg_exporting`.

We now proceed to describe the semantics of `ace.mgmt`.

Three steps are common to every operation below and are not repeated in the description of each of them:

. `ace.mgmt` first checks that `acemanagedcr` holds either the target CR's number or 32, and raises an illegal-instruction exception if it holds any other value;
. It affects `acemanagedcr` according to the _State_ in which it leaves the target CR:
.. if that _State_ is a Configuration State, it writes the target CR's number to `acemanagedcr`;
.. if that _State_ is a Complete State, including any Error State, it writes 32 to `acemanagedcr`; and
.. if the instruction raises an exception without leaving the target CR in an Error State, `acemanagedcr` is left unchanged, or set to 32 if the zeroizing step has left the target CR _Unconfigured_: the handler either resolves the condition or sets `acemanagedcr` to 32 itself (<<ACE-CSR-acemanagedcr>>).
. `ace.mgmt` also clears `acestart` (it is the duty of software to restore `acestart` to allow interrupted management operations to be resumed).

Now we consider the specific semantics of `ace.mgmt` for each of the four operations it supports:

. *`ace.mgmt` is used to start a provisioning, resp., import process.*
+
--
Before issuing `ace.mgmt`, software must obtain the MDH. Let `ml` be this value.

NOTE: In the case we are starting an import process, `ml` must be first saved by software in its local state.
`ml` is then provided to the `ace.mgmt` operation used to complete the process in order to restore the _State_ the CR was in before the import process started.

An `ace.mgmt` of Form A, C or D is used to start a provisioning, resp., import process and provide `ml`.
It performs following operations:

.. The target CR is zeroized. Bytes of the serialized `Content` that a management operation has not yet written read as zero through every architectural access (`ace.store`, `ace.mv`, verbatim export).
.. If `#immed7` = `ace_cfg_importing` and `ml`._State_ is an Error State, the CR is immediately
    fully configured in that Error State, with the entire MDH given by the auxiliary input except that _AuxDataLen_ and _ADSDropped_ are set to 0 (Rule <<ACE-SGR-clear-cr-content-error-state>>).
    The steps below are not applied: the CR holds only its MDH (<<ACE-cryptographic-registers>>), no Algorithm is selected for execution,
    and no CRF capacity is allocated, so this configuration cannot fail.
//    Provisioning is not a way to do this: with `#immed7` = `ace_cfg_provisioning` the _State_ field of
//    `ml` must be _Unconfigured_, as the provisioning branch below prescribes.
    The whole configuration is performed by this one instruction, which is uninterruptible (Rule <<ACE-IRR-uninterruptible-instructions>>) and opens no management operation, so
    no `ace.mgmt` with `#immed7` = `ace_cfg_management_end` follows.
//    and in fact it will be an illegal instruction.
    This is the _short import path_ of <<ACE-error-state-transfer>>.
.. If `ml` is unsupported Metadata (see <<ACE-MVR-open>>), ACE exception `ace_exc_unsupported` is raised.
.. In case of *provisioning*:
... `ml`._State_ must be _Unconfigured_, else the Metadata is invalid (<<ACE-MVR-open>>). _State_ is initially set to _Unconfigured_. This means that during the pre-flight checks described below, _State_ is _Unconfigured_ until it is successfully configured.
... _StateExtension_ and _AlgorithmUse_ are set to 0; the values in the PI are ignored.
... `_AuxDataLen_` and `_ADSDropped_` must be 0. If either is non-zero in the MDH of a PI,
the CR is transitioned to Error State _Invalid_ (which is a Complete State) and the instruction terminates.
.. If `ml` is invalid Metadata (see <<ACE-MVR-open>>), the CR is transitioned to Error State _Invalid_.
.. The implementation attempts to allocate CRF capacity according to the requirements of the _Algorithm_, _AlgorithmPolicy_, and _SCProtection_ fields of the MDH, as prescribed by <<ACE-length-rule>>. No other field must affect the amount of capacity required.
    If capacity allocation is not possible, ACE exception `ace_exc_out_of_memory` is raised.
.. If *provisioning*: CR._State_ is set to `ace_cfg_provisioning`;
.. If *importing*: CR._State_ depending on `ml`._State_:
... In every case the opening applies steps 1–5 of <<ACE-SCC-import>>, determining whether the ADS is retained from the MDH it loads and the implementation's supported maximum.
... If `ml`._State_ is a Valid State, then CR._State_ is set to `ace_cfg_importing`;
... If `ml`._State_ is `ace_cfg_importing` or `ace_cfg_exporting` (the image of an interrupted import or export of a CR in a Complete State), then CR._State_ is set to `ace_cfg_importing`;
... If the base type of `ml`._State_ is `pi`, then CR._State_ is set to `ace_cfg_ppi_importing` (<<ACE-nested-state-base-types>>);
... If `ml`._State_ is _Unconfigured_, the Metadata is invalid (see <<ACE-MVR-open>>).
.. In every case above in which a check fails, that is in which an ACE exception is raised or the CR
transitions to Error State _Unsupported_ or _Invalid_, all fields of the MDH other than _State_ remain
zero and no CRF capacity is allocated; after `ace_exc_out_of_memory` the CR remains _Unconfigured_.
This does not apply to the configuration of a CR directly into an Error State from `ml`, which installs
the entire MDH.
--
+
. *`ace.mgmt` is used to start an export process.*
+
--
Let `ml` <- the MDH of the CR.
Software must first save this value in its local state to restore its _State_ when completing the export process.
`ace.mgmt` can be of Form A, C or D; its auxiliary input is ignored.
`ace.mgmt` performs following operations:

.. If `ml`._State_ is _Unconfigured_, then: an illegal-instruction exception is raised.

.. If `ml`._State_ is an Error State, then: the CR is left unchanged and no management operation is opened (Rule <<ACE-SGR-error-state-CR-is-only-MDH>>; the short export path is given in <<ACE-error-state-transfer>>).

.. If `ml`._State_ is a Valid State, then:
The instruction prepares the CR to produce an SCC.
This includes encrypting its contents and computing the authentication tag(s)
as specified in <<ACE-CC-management>>. Then, CR's _State_ is set to `ace_cfg_exporting`.
The opening `ace.mgmt` causes no changes to any field of the MDH other than _State_: an implementation that creates or changes an ADS, or uses _AlgorithmUse_, keeps _AuxDataLen_ and _AlgorithmUse_ current at all times, so that the MDH software reads before opening the export is the MDH the export authenticates.

.. If `ml`._State_ is a Partial State (we are exporting a not fully configured CR or we are initiating a nested CR export), then:

... No encryption or authentication occurs; the contents of the CR are exported verbatim, in the same order in which they appear in the PI (for a partially provisioned CR) or in the SCC (for a partially imported CR, or a CR previously prepared for export whose export process was itself interrupted).

... The CR's _State_ is set to `ace_cfg_ppi_exporting` or `ace_cfg_exporting` according to its base type (<<ACE-nested-state-base-types>>).
+
These values of CR._State_ are the value on which `ace.store` (<<ACE-instruction-store>>) and the CR-reading variants of `ace.mv` (<<ACE-instruction-mv>>) are gated, so no export can proceed until CR._State_ is set.
--
+
. *`ace.mgmt` is issued with `ace_cfg_management_end`*:
+
--
`ace.mgmt` with immediate `ace_cfg_management_end` reads first the MDH of the target CR.
Depending on whether MDH._State_ is

* `ace_cfg_provisioning`,
* `ace_cfg_importing`, `ace_cfg_ppi_importing`, resp.
* `ace_cfg_exporting`, `ace_cfg_ppi_exporting`,

the instruction will proceed to complete a provisioning, importing, resp., exporting process, as are described next.

When completing an import or an export, the auxiliary operand `ml` is consumed only for its _State_ field,
which restores the CR's _State_ to the value that field held when the management operation was started.
No other field of the MDH is written from `ml`.

If CR.MDH._State_ is `ace_cfg_importing` or `ace_cfg_exporting`, `ml`._State_ must be a Complete State or a Configuration State of base type `scc`, i.e., `ace_cfg_importing` or `ace_cfg_exporting`;
if it is `ace_cfg_ppi_importing` or `ace_cfg_ppi_exporting`, `ml`._State_ must be a Configuration State of base type `pi`, i.e., `ace_cfg_provisioning`, `ace_cfg_ppi_importing` or `ace_cfg_ppi_exporting` (<<ACE-nested-state-base-types>>).
Any other `ml`._State_, including a Complete State for a CR of base type `pi` and the values 61–63, raises an illegal-instruction exception.
A Complete `ml`._State_ is accepted only for a CR of base type `scc`, so that the clear `Content` of a partially provisioned CR can become usable only through the completion of its provisioning.

NOTE: When an SCC import or CR export restores a Complete State, authentication is checked after
setting CR.MDH._State_ to `ml`._State_, so the probability of accepting an incorrect _State_ is negligible.
For a nested completion, no authentication occurs; the base-type rule is the only check.
--
+
.. *`ace.mgmt` is used to complete a provisioning process.*
+
--
`ace.mgmt` does not need a saved MDH from the start of the provisioning process, hence if a Form C or D was used in place of Form A, the auxiliary input is simply ignored.

Completing a provisioning requires _AuxDataLen_ = 0 and _ADSDropped_ = 0; if CR.MDH._State_ is `ace_cfg_provisioning` and either field is non-zero, the CR transitions to Error State _Invalid_ and the instruction terminates.

The operation makes the provisioned CR available to software by

... For _KeyType_ = 1, generating the key for the all-ones SKID (<<ACE-KeyType-field>>) or applying the SKID resolution of <<ACE-system-keys>>;
... Performing any necessary readjustment of the CR's content to turn it into the format internally consumed by the ACE Unit; and
... Setting _State_ to _Ready_, and _StateExtension_ and _AlgorithmUse_ to 0.

A process may be preempted during a CR's provisioning.
Only the information in the original PI is exported by `ace.store` or `ace.mv`,
and it remains unencrypted.
During provisioning, any secret random material required to configure the CR must be generated only by the `ace.mgmt` instruction that completes provisioning. The same restriction applies to retrieving key material from a System Key Store and to deriving, expanding, or re-sharing that material.
This prevents such material from being exposed in an unencrypted export of a partially provisioned CR.
--
+
.. *`ace.mgmt` is used to complete an import process.*
+
--
The software uses Form A, C or D of `ace.mgmt` to pass along the value of `ml` saved when the import process was started.
The image authenticated as ``AD[0]`` is the MDH held in the target CR — the image carried in the SCC and loaded when the import was started — with its _State_ field restored from `ml` and _ADSDropped_ cleared in the copy used for authentication (<<ACE-SCC-import>>). The actual MDH field is not cleared by this computation.

The semantics are:

... If `ml`._State_ is a Complete State (we are importing the export of a fully configured CR)
.... CR.MDH._State_ is set to `ml`._State_.
.... The ACE unit decrypts and authenticates the CR's content.
.... If authentication fails, the target CR is transitioned to Error State _Authentication Failed_. No exception is raised. Otherwise, if _KeyType_ = 1, the SKID is resolved and the narrowing of <<ACE-system-keys>> is applied.
.... The ACE unit performs any necessary readjustment of the CR's content to turn it into the format internally consumed by the ACE Unit.
This makes the CR available to software.
... If `ml`._State_ is not a Complete State (we are either importing the export of a not fully configured CR or a nested CR export):
.... CR.MDH._State_ is set to `ml`._State_.
--
+
.. [[ace-mgmt-completes-export,Use of ace.mgmt to complete an export process]]*`ace.mgmt` is used to complete an export process.*
+
--
Software uses Form A, C or D of `ace.mgmt` to supply the MDH value saved when the export process began.

Let `ml` be this auxiliary input.
Then:

.. The CR's _State_ is set to `ml`._State_.
.. If `ml`._State_ is a Complete State (i.e., including Error States), the instruction
restores the internal state of the CR to the clear format it was in when the export process was initiated and allows software to access it:
... The contents are decrypted and authenticated as when completing an import, with the MDH held in the CR as `AD[0]` and _ADSDropped_ cleared in the copy consumed by first-segment authentication.
... If the `SIV` check fails, the CR transitions to Error State _Authentication Failed_ and the instruction terminates; no exception is raised. Otherwise, if _KeyType_ = 1, the SKID is resolved and the narrowing of <<ACE-system-keys>> is applied.
+
NOTE: An implementation may instead restore the clear contents from an internal copy only if the outcome is identical: the copy is usable only while the CR, its MDH, `SIV` and, when _AuxDataLen_ ≥ 2, `IMPQUAL` and `SIV2` still hold the values written by the opening `ace.mgmt`, and `ml`._State_ equals the _State_ at that time.  The specification does not define any internal mechanisms by which an implementation can achieve this.

.. If `ml`._State_ is not a Complete State, no further changes to the CR's contents are made.
--
+
. *If `ace_cfg_management_end` is issued when the target CR's _State_ is _Unconfigured_ or a Complete State* (i.e., no management operation open on the target CR), the instruction is an illegal instruction.

[[ACE-error-state-transfer]]
==== Export and Import of a CR in an Error State

A CR in an Error State holds only its MDH (Rule <<ACE-SGR-clear-cr-content-error-state>>), so there is nothing to
encrypt and nothing to authenticate. No SCC and no PCCC are produced, and neither direction opens a
management operation. Both paths are therefore shorter than those of <<ACE-management-operations>>,
and both are exempt from the resumption machinery, since no `ace.load` or `ace.store` is issued.

*Exporting* a CR in an Error State consists of two steps and uses no `ace.mgmt`:

. Read the _State_ field with `ace.getst` (<<ACE-instruction-getst>>) and find it to be an Error State.
. Read the MDH with `ace.getmd` or `ace.getmdv` (<<ACE-instruction-getmd>>) and store those 16 bytes
  to memory. `ace.size` reports 16.

Issuing `ace.mgmt` with `#immed7` = `ace_cfg_exporting` on a CR in an Error State is permitted but
useless: it leaves the CR unchanged and opens no management operation
(<<ACE-CR-management>>).

*Importing* such an image consists of one step:

. Issue `ace.mgmt` with `#immed7` = `ace_cfg_importing` and the 16-byte MDH
  as the auxiliary operand. The instruction configures the CR into the Error State the MDH names
  (54 and 55 as _Invalid_), installing the entire MDH except that _AuxDataLen_ and _ADSDropped_ are set to 0, and completes the configuration by itself,
  without applying the checks of <<ACE-Metadata-validity>>; it is uninterruptible
  (Rule <<ACE-IRR-uninterruptible-instructions>>), so the CR is never observed part-configured.
  Form C or D carries the whole MDH, as does a Form A taking it from the ACEIOBUF.

No `ace.mgmt` with `#immed7` = `ace_cfg_management_end` follows, and issuing one is an illegal
instruction. The `SIV`, `SIV2` and `IMPQUAL` registers take no part in either path and need not be saved
for it.

[[ACE-SCC-AEAD]]
==== The SCC Authenticated Encryption Scheme

The cryptographic scheme used in the export and import of SCCs is
a variant of AES-GCM-SIV cite:[DBLP-journals-iacr-GueronLL17,RFC8452].
The differences with respect to AES-GCM-SIV are:

. The block containing the lengths of Associated Data and Plaintext is not included in the evaluation of POLYVAL.
This is intentional: the information needed to fully determine the lengths of
all sections is already included in the MDH, and thus in the POLYVAL.
. The optional Nonce is omitted.
. A domain separation bit, `sep`, has been added to distinguish the two segments of the content that are sealed in a SCC: the fixed architecture-defined content (`sep` = 0) and the optional implementation-dependent content (`sep` = 1).

We define the Key Derivation (<<ACE-SCC-key-derivation>>) and POLYVAL (<<ACE-SCC-POLYVAL>>) functions first.
The generation of an SCC from a CR (<<ACE-SCC-export>>) and the import of an SCC into a CR (<<ACE-SCC-import>>) are defined next.

In the pseudocode of this section, `AESE256(K, B)` denotes the AES-256 encryption of the
128-bit block `B` under the 256-bit key `K`, as specified in FIPS 197 cite:[nist-fips-197].

[[ACE-SCC-key-derivation]]
.RFC8452 Key Derivation
[]
----
function SCC_KeyDeriv(key : bits(256), nonce : bits(96))
    → struct{enc_key : bits(256), auth_key : bits(128)} =
{
  local A : array [0..5] of bits(128);
  local i : int;

  foreach(i from 0 to 5) do:
    A[i] ← AESE256(key, nonce @ bin(i,32));

  return struct {
    enc_key  = A[5][63:0] @ A[4][63:0] @ A[3][63:0] @ A[2][63:0],
    auth_key = A[1][63:0] @ A[0][63:0]
  }
}
----

NOTE: Due to the computational cost of the key derivation function, implementations may cache the derived keys.

[NOTE]
====
To reduce payload size, the AES-GCM-SIV-derived construction used for SCC import and export omits the nonce.
It relies instead on AES-GCM-SIV's resistance to nonce reuse and misuse. The construction remains secure for up to 2^64^ 128-bit blocks observed by an adversary.

This provides practical protection for client applications. On cloud servers, each virtual machine and supervisor domain should use a unique CSK. To transfer CCs between domains, M-mode firmware can import an SCC using the source domain's CSK and re-export it using the target domain's CSK.

The `SIV` (Synthetic IV), which is also the GCM-SIV authentication tag, is the encryption of the `POLYVAL` hash of the MDH with _ADSDropped_ cleared in the authentication copy, the Locality Secrets, and Content, concatenated in that order. In the `POLYVAL` pseudocode below, the input is represented as an array of 128-bit blocks, which are absorbed in increasing index order.
====

[[ACE-SCC-POLYVAL]]
.Polyval Hashing Function
[]
----
function POLYVAL(auth_key : bits(128), blocks[0..n-1] : bits(128), n : int)
    → bits(128) =
{
  local tmp : bits(128) ← zeros(128);
  local i : int;

  foreach(i from 0 to n-1) do:
    tmp ← tmp xor blocks[i];
    tmp ← Montmul(tmp, auth_key);

  return tmp;
}
----

We now define `Montmul(a, b)`, the Montgomery multiplication operation used in POLYVAL.

The field F is GF(2)[`x`] modulo `x^128^ + x^127^ + x^126^ + x^121^ + 1`.

A 128-bit value `V` represents the element whose coefficient of `x^k^` is `V[k]`.
Both the byte order and the bit order run forward; this is the representation of
cite:[RFC8452] {sect}3, under which `x^0^` is the byte string `0x01` followed by
fifteen zero bytes, i.e., the value `1`.

`Montmul(a, b)` is not plain multiplication but Montgomery multiplication; it is: +
 +
`{fournbsp}{fournbsp}` `Montmul(a, b)` = `a` {interpunct} `b` {interpunct} `x^-128^` `{nbsp}{nbsp}` in the field F.

We now give the notation used for the inputs and outputs of the SCC encryption and decryption functions,
i.e., <<ACE-SCC-GCM-SIV-enc>> and <<ACE-SCC-GCM-SIV-dec>>:

* `AD[]` denotes the Associated Data as an array of `len_AD` 128-bit blocks, that is
  `AD[0] {vvert} AD[1] {vvert} {ellipsis} {vvert} AD[len_AD-1]`, in that order;
* `P[]`, resp., `C[]`, denotes a Plaintext, resp., a Ciphertext, as arrays of `len_PC`
  128-bit blocks, that is `P[0] {vvert} P[1] {vvert} {ellipsis} {vvert} P[len_PC-1]`,
  resp. `C[0] {vvert} C[1] {vvert} {ellipsis} {vvert} C[len_PC-1]`, in that order;
* `K` is a 256-bit Key;
* `N` is a 96-bit Nonce; and
* `SIV` is a 128-bit SIV/tag.

[NOTE]
====
As in AES-GCM-SIV, we use bit 127 to distinguish tag inputs (bit 127 takes the value 0) from
keystream inputs (1). This construction adds a second domain separation bit, `sep`, in bit
126 to distinguish architecture-defined content (`sep` = 0) from the ADS (`sep` = 1).
The security reduction is just one bit: the tag input carries 126 bits of the `POLYVAL`
result rather than 127, and the keystream counter block carries 94 bits of the `SIV` rather than
95.
====

// Both segments derive their keys from the same CSK and all-zero nonce.
// Without `sep`,
// only their Associated Data and SIV values would distinguish them. This does not imply an
// attack: a collision between `SIV` and `SIV2` has negligible probability. However, separation
// would then depend on those values rather than on the construction itself.
// Placing `sep` in bit 126 of both AES inputs makes the separation unconditional.
//
// * in the *tag* computation, `0 @ sep @ POLYVAL({ellipsis})[125:0]`, so that the same
//   Associated Data and plaintext yield different tags in the two segments; and
// * in the *keystream* counter block, `1 @ sep @ SIV[125:32] @` counter, so that the two segments
//   cannot share a keystream even if their SIVs were to collide.

[[ACE-SCC-GCM-SIV-enc]]
.AES-GCM-SIV Encryption for SCC Generation
[]
----
function SCC_Encrypt(AD[] : array of bits(128), N : bits(96), sep: bits(1),
    P[] : array of bits(128), K : bits(256), len_AD : int, len_PC : int)
  → {SIV : bits(128), C[] : array of bits(128)} =
{
  local AD_auth : array [0..len_AD-1] of bits(128) ← AD[];

  enc_key, auth_key ← SCC_KeyDeriv(K,N);
  if (sep = 0) then:
    AD_auth[0][47] ← 0;
  SIV ← POLYVAL(auth_key, AD_auth || P, len_AD + len_PC);
  SIV[95:0] ← SIV[95:0] xor N;
  SIV ← AESE256(enc_key, 0 @ sep @ SIV[125:0]);

  foreach(i from 0 to len_PC - 1) do:
    C[i] ← P[i] xor AESE256(enc_key,
             1 @ sep @ SIV[125:32] @ bin((int(SIV[31:0]) + i) mod 2**32, 32));

  return ( SIV, C[] );
}
----

`len_PC` never exceeds `max_admissible` / 16 (<<ACE-instruction-load>>), and `len_AD` never exceeds 7.

[[ACE-SCC-GCM-SIV-dec]]
.AES-GCM-SIV Decryption for SCC Import
[]
----
function SCC_Decrypt(AD[] : array of bits(128), N : bits(96), sep: bits(1),
    SIV : bits(128), C[] : array of bits(128), K : bits(256),
    len_AD : int, len_PC : int)
  → {correct : bool, P[] : array of bits(128)} =
{
  local AD_auth : array [0..len_AD-1] of bits(128) ← AD[];

  enc_key, auth_key ← SCC_KeyDeriv(K,N);
  if (sep = 0) then:
    AD_auth[0][47] ← 0;

  foreach(i from 0 to len_PC - 1) do:
    P[i] ← C[i] xor AESE256(enc_key,
             1 @ sep @ SIV[125:32] @ bin((int(SIV[31:0]) + i) mod 2**32, 32));

  s ← POLYVAL(auth_key, AD_auth || P, len_AD + len_PC);
  tmp ← s;
  tmp[95:0] ← tmp[95:0] xor N;
  tmp ← AESE256(enc_key, 0 @ sep @ tmp[125:0]);

  if (tmp != SIV) then:
    foreach(i from 0 to len_PC - 1)
      P[i] ← zeros(128);
    return ( false, P[] );

  return ( true, P[] );
}
----

NOTE:  *Design Rationale for the Sealing Construction.*
The Locality Secrets are supplied to the AEAD as _associated data_ rather than mixed into the
Context Sealing Key through a KDF. Both approaches bind the SCC to the Locality set, but
using associated data is computationally less expensive. POLYVAL, requires one `Montmul`
per 128-bit block and is thus significantly faster than most KDFs. This approach also
avoids re-deriving `enc_key` and `auth_key` when the Locality set changes.
Distinct Locality sets lead to the same SIV with collision probability 2^-126^.

[[ACE-SCC-export]]
==== Generation of an SCC from a Fully Configured CR

If the _State_ field is set to a Valid State, then ``K(i)`` is fully provisioned,
and opening the CR for export (`ace.mgmt Kd|K{Xd}, #ace_cfg_exporting`) performs the following steps
to create the serialized, encrypted and authenticated SCC from the CR.

Regarding the Localities, the substitution rules in <<ACE-Localities>> and <<ACE-interaction-with-debug>> apply.
We define `LST_eff[j]` as the value of `LST` entry j after applying these substitution rules;
a non-implemented entry with no configured replacement contributes `zeros(128)` and makes the Metadata invalid at provisioning/import; an export is not refused on this ground, the resulting SCC being rejected at import. Entry 9 of `LST` is `hacelocality`, and entry 10 the effective register of <<ACE-Localities>>: `sacelocality`, or `vsacelocality` when V=1.
In the export and import algorithms we then replace `LST[j]` with `LST_eff[j]`.

After `ace.clear.ads`, a fully configured CR has _AuxDataLen_ = 0 and _ADSDropped_ = 0 (<<ACE-instruction-clearads>>). An SCC-shaped PCCC may instead carry _ADSDropped_ = 1 to preserve an interrupted import after `Content2` was dropped.

.Exporting a Fully Configured CR ``K(i)``
--
. First, the Algorithm-dependent data is processed:
.. `saved_MDH` <- the MDH of ``K(i)`` immediately before its _State_ is set to `ace_cfg_exporting` (the image software saved beforehand), ``len_AD`` <- 1
.. ``AD[0]`` <- `saved_MDH`. `SCC_Encrypt` clears _ADSDropped_ in its local copy of this block before computing `SIV`; the `saved_MDH` returned in the SCC is unchanged.
.. foreach(_j_ from 0 to 10) do:
... If `saved_MDH`._Locality_ includes Locality #j, then ``AD[len_AD]`` <-  ``LST_eff[``_j_``]``, ``len_AD`` <- ``len_AD`` + 1
.. `len_PC` <- the number of 128-bit blocks of `Content1` (Section 5.a of <<ACE-SCC>>).
.. `SIV`, `Content1~CT~[]` <- `SCC_Encrypt(AD, zeros(96), 0, K(i).Content1~PT~[], CSK, len_AD, len_PC)`
. Second, if _AuxDataLen_ {ge} 2 then: the implementation-dependent data is processed:
.. `len_AD2` <- 2, ``AD2[0]`` <- ``K(i)``.`IMPQUAL`, ``AD2[1]`` <- `SIV`.
.. `len_PC2` <- the number of 128-bit blocks of `Content2` (Section 5.b of <<ACE-SCC>>), that is _AuxDataLen_ − 2.
.. `SIV2`, `Content2~CT~[]` <- `SCC_Encrypt(AD2, zeros(96), 1, K(i).Content2~PT~[], CSK, len_AD2, len_PC2)`
. Finally, if _AuxDataLen_ = 0, then:
.. return(`saved_MDH`, `SIV`, `Content1~CT~[]`)
. else:
.. return(`saved_MDH`, `SIV`, `IMPQUAL`, `SIV2`, `Content1~CT~[]` and `Content2~CT~[]`) (note that `Content2~CT~[]` may be empty)
--

// Of the returned values, `SIV`, `SIV2` and `IMPQUAL` are placed in the CSRs `acesivl`/`acesivh`,
// `acesiv2l`/`acesiv2h` and `aceiql`/`aceiqh`, from which software stores them to memory; the ciphertext
// remains in the CR, whence `ace.store` (<<ACE-instruction-store>>) transfers it; and `saved_MDH` is the
// image software already holds, which `ace.getmd*` (<<ACE-instruction-getmd>>) also returns.
//
// If _AuxDataLen_ = 0, then `SIV2` and `IMPQUAL` are not generated, and therefore
// `acesiv2l`/`acesiv2h` and `aceiql`/`aceiqh` are not written to.
// They may contain stale values, but this is not an issue as they are not exported to memory in this case.

[NOTE]
====
A CR in an Error State is not exported by this procedure (Rule <<ACE-SGR-error-state-CR-is-only-MDH>>).
====

[IMPORTANT]
====
Taking `SIV` as ``AD2[1]`` binds the two payloads together, so that `SIV2` and
the keystream of the second segment change whenever the
first payload changes; an attacker cannot graft the Implementation-Specific ADS of one SCC onto the architecture-dependent part of another.
====

[NOTE]
====
If an export operation is completed prematurely, an authentication error results upon import (see next section).
If an import operation is completed prematurely, an authentication error results.
If any of the two operations is not completed, various types of error conditions will occur because _State_ is a Configuration State.
====

[[ACE-SCC-import]]
==== Decryption and Authentication of a complete SCC into a CR

The following algorithm describes the import of the SCC of a fully configured CR as a whole.
Steps 1 to 5 are performed by the `ace.mgmt Kd|K{Xd}, #ace_cfg_importing` that opens the import
(<<ACE-CR-management>>), step 6 by the `ace.load` or CR-writing `ace.mv` instructions that follow it
(<<ACE-instruction-load>>, <<ACE-instruction-mv>>), and the remaining steps by
`ace.mgmt Kd|K{Xd}, #ace_cfg_management_end`, which decrypts and authenticates the SCC.

.Importing a Fully Configured CR ``K(i)``
--
 . Clear ``K(i)``.
 . Load `M`, the MDH from the SCC, into ``K(i)``.MDH.
 . Check correctness of `M`, and whether the Algorithm is supported.
 . Determine the SCC layout from `M`.
 . If `M`._AuxDataLen_ {ge} 2 and either `M`._ADSDropped_ = 1 or `M`._AuxDataLen_ exceeds the implementation's maximum for the given Algorithm, set ``K(i)``.MDH._ADSDropped_ to 1. Otherwise set it to 0. This changes only the length of `Content2`: when _AuxDataLen_ {ge} 2, `IMPQUAL` and `SIV2` remain present and _ContentOffset_ remains 48.
 . Load the rest of the SCC up to the length described by the resulting working MDH. If _ADSDropped_ = 1, this includes `SIV`, `IMPQUAL`, `SIV2`, and `Content1`, but no `Content2`.
 . `saved_MDH` <- the MDH image held in ``K(i)``, that is `M` with the working value of _ADSDropped_ and with its _State_ field restored from the auxiliary operand of the completing `ace.mgmt`.
 . ``AD[0]`` <- `saved_MDH`, ``len_AD`` <- 1. `SCC_Decrypt` clears _ADSDropped_ in its local copy of `AD[0]` before authenticating it; the MDH held in ``K(i)`` is unchanged by that computation.
 . foreach (`j` from 0 to 10) do:
 .. If `saved_MDH`._Locality_ includes Locality #j, then ``AD[len_AD]`` <-  ``LST_eff[j]``, ``len_AD`` <- ``len_AD`` + 1
 . `len_PC` <- the number of 128-bit blocks of `Content1` (Section 5.a of <<ACE-SCC>>).
 . `correct`, ``K(i)``.`Content1` <- `SCC_Decrypt(AD, zeros(96), 0, SIV, K(i).Content1, CSK, len_AD, len_PC)`.
 . If `correct` {ne} `true`, the SCC is rejected: ``K(i)`` transitions to Error State `ace_state_import_auth` (Rule <<ACE-SGR-clear-cr-content-error-state>>).
 . Second, if ``K(i)``.MDH._AuxDataLen_ {ge} 2 and ``K(i)``.MDH._ADSDropped_ = 0, the implementation-dependent data is processed:
.. `len_AD2` <- 2, ``AD2[0]`` <- ``K(i)``.`IMPQUAL`, ``AD2[1]`` <- `SIV`.
.. If ``K(i)``.`IMPQUAL` = `zeros(32) @ acemimpid @ acemarchid @ acemvendorid` then:
... `len_PC2` <- the number of 128-bit blocks of `Content2` (Section 5.b of <<ACE-SCC>>), that is ``K(i)``.MDH._AuxDataLen_ − 2.
... `correct`, `K(i).Content2` <- `SCC_Decrypt(AD2, zeros(96), 1, `SIV2`, K(i).Content2, CSK, len_AD2, len_PC2)`.
.. else:
... `correct` <- `false`.
 . If second-segment processing was attempted and `correct` {ne} `true`, drop `Content2` and set ``K(i)``.MDH._ADSDropped_ to 1.
 . If ``K(i)``.MDH._AuxDataLen_ = 0 or ``K(i)``.MDH._ADSDropped_ = 1, import completes using only the architecture-dependent content. The state machine must establish a consistent internal state and set _ADSDropped_ to 0. If no replacement ADS is generated, it sets _AuxDataLen_ to 0; if it generates replacement ADS, during completion or later, it sets _AuxDataLen_ to the appropriate value, which is at least 2. Otherwise the successfully imported ADS is retained, _AuxDataLen_ is preserved, and _ADSDropped_ is set to 0. A later export uses these current values: it emits no ADS when _AuxDataLen_ = 0, or emits the newly generated or retained ADS when _AuxDataLen_ {ge} 2.
--

[NOTE]
====
This procedure ensures that if the SCC's optional implementation-specific ADS makes the SCC too large to fit in a CR, or if that ADS is incompatible, the implementation ignores the optional data, but keeps the architecture-dependent content: Only a failure of the first authentication (SIV) rejects the entire SCC.
====

[[ACE-import-and-DIEL]]
==== Import and Data-Independent Execution Latency

_This section is informative and non-normative._

In ACE, Data-Independent Execution Latency (DIEL) applies only to the cryptographic operations it performs, including the decryption and authentication of SCC contents.

All CR management instructions are split into three phases: An initial `ace.mgmt`, load/store instructions, and a final `ace.mgmt`.
The two `ace.mgmt` instructions perform no memory accesses.

The dependencies of the `ace.mgmt` instructions' timing are limited to very few factors:

. Actual size of the SCC to export, including the implementation-dependent part.
. `SIV` or `SIV2` authentication failures on import;
. `IMPQUAL` mismatches on import; and
. Attempts to import SCCs whose total length exceeds what the target machine supports for the given Algorithm.
  In this case, the implementation-dependent part is necessarily unsupported; it is skipped or only partially loaded, to be discarded without authenticating it; and only the architecture-dependent part is authenticated and decrypted (if the resulting _State_ is a Complete State) and used.

Apart from these factors, only the number of blocks to process may affect the timing of the `ace.mgmt` instructions.
The timing of the processing of each block is independent of the actual data being processed.

[[ACE-state-save-and-restore-order]]
=== Context Switching, ACE State Save and Restore Order

Lower-privileged modes may save, restore, or overwrite CRs configured by higher-privileged modes.
Hence, higher-privileged software must clear any CRs it uses before relinquishing control to lower-privileged modes.
If it uses the ACEIOBUF, `acestart`, `acemanagedcr` or the authentication registers while a lower-privileged context's ACE state is live, it must save that state beforehand and restore it afterwards, as at a context switch (below), so that the lower-privileged context observes its own values and none of the higher-privileged mode's data; on return to a different context the ACEIOBUF holds that context's saved contents or, with `aceiobuflen` = 0, nothing.
When switching to a lower-privileged component, only CRs previously saved for that same component may be restored, and CRs that are not part of that component's ACE state must be erased.

_The remainder of this section is informative and non-normative._

This aligns with standard context-switching hygiene.

// ////////////////////////////////////////////////////////////////////

This is the recommended order for saving and restoring the ACE state.

* Save order:

. Save `acestart` first, since every later step may clear it.
. Save the raw value of `acemanagedcr`.
. If `Zklio` is present:
.. Save `aceiobuflen` and `aceiobuftop`.
.. If `aceiobuflen` is nonzero, save the buffer contents using `ace.output` with `acestart` = 0 and `aceiobuftop` raised to `aceiobuflen`, since the `ace.mgmt` of a CR export may take `ml` from the ACEIOBUF (<<ACE-usage-input-output>>).
. If the saved `acemanagedcr` is in [0..31], read the MDH of the CR it indexes using `ace.getmd*` and select the State-appropriate save path:
.. If the CR is _Unconfigured_, save no CR image.
.. If the CR is in an Error State, save its MDH using the short Error-State path (<<ACE-error-state-transfer>>).
.. Otherwise, export the CR using the applicable Complete- or Configuration-State path. This export precedes every other `ace.mgmt` that could overwrite the authentication registers.
. Set `acemanagedcr` to 32, since `ace.mgmt` requires it to hold its target's number or 32.
. Save every other non-Unconfigured CR using the path appropriate to its State.

* Restore order:

. Restore the CRs other than the CR indexed by the saved `acemanagedcr`, with the working value of `acemanagedcr` set to 32 before and after each import.
. If the saved `acemanagedcr` is in [0..31] and an image was saved for the CR it indexes, restore that CR using the path appropriate to its saved State, with the working value of `acemanagedcr` set to 32 before opening its import.
. If `Zklio` is present:
.. Restore `aceiobuflen`, which zeroes the buffer and sets `aceiobuftop`.
.. Restore the buffer contents, if saved, using `ace.input` with `acestart` = 0 and `aceiobuftop` = `aceiobuflen`.
.. Restore `aceiobuftop`.
. Restore the raw saved value of `acemanagedcr`.
. Restore `acestart` last, since every earlier step may clear it.

A handler that passes `ml` through the ACEIOBUF configures `aceiobuflen` {ge} 16 for the CR exports and imports and restores the saved value afterwards.

A handler must treat `acemanagedcr` as a hint and check the MDH of the CR it names before selecting a save path. For example, user software may clear `K0`, write `acemanagedcr` = 0, and then enter a handler. Reading the all-zero MDH identifies `K0` as _Unconfigured_, so the handler saves no image for it and does not attempt an export that would raise an illegal-instruction exception.

[[ACE-CSK-requirements]]
=== Architectural Requirements on the Context Sealing Key

The ACE unit must have a configured Context Sealing Key (CSK) before it can operate. Without an active CSK, every ACE instruction and every ACE CSR access raises `ace_exc_no_csk`, except access to the `macecsk` CSR group, to the Locality Secret CSR groups (<<ACE-CSR-locality-groups>>), which are configured independently of the CSK, and to the read-only identification CSRs `acemvendorid`, `acemarchid`, `acemimpid`, and `acemaxiobuflen` (<<ACE-CSR-impl-ids>>, <<ACE-CSR-acemaxiobuflen>>).  The latter CSRs remain readable to allow firmware to identify the ACE unit without having to configure it.

A CSK can be set in one of four mutually exclusive ways:

. A value programmed by M-mode through the `macecsk` CSR group (see <<ACE-CSR-macecsk>>).
. A separate secure HW block (e.g., Caliptra cite:[caliptra]), or a port to a secure HW block, which is exclusive to M-mode, is used to configure CSK values and export them using a dedicated interface based on public key encryption.
. A fixed, hardwired value, generated at manufacturing time (either per die or shared across batches).
. A value generated by a secure RBG (see <<ACE-RBG>>) at boot and not accessible to any software.

The third and fourth models are primarily suited to specialized embedded deployments: a hardwired CSK cannot be reconfigured or revoked, while a boot-generated CSK cannot preserve SCCs across power loss.
Under the fourth model, all harts in a well-defined subsystem of a SoC share a CSK and cannot exchange SCCs with other subsystems. The CSK survives a single hart's reset or fatal condition and is regenerated only at subsystem power-on reset.

In the second model, only M-mode may request that the secure hardware block configure its hart's CSK, using a handle or wrapped key. The clear key must not be exposed to any software, including M-mode.
Addressing and key transport are platform-specific and outside the scope of this specification.

The ACE unit is immediately available under the third model; under the other models, it becomes available only after a CSK has been established. A hart reset resets the associated ACE state (<<ACE-reset-and-m-mode-only>>). In the first and second models, this includes the configurable CSK, leaving the unit unavailable until the CSK is re-established.

NOTE: When the CSK is shared across devices, CCs intended to be device-bound must set `_Locality_` to include `ChipScrt` or `DevScrt`.

Except for M-mode and in the first model, CSK values must _never_ be readable by software in clear.
//An implementation that permits CSK reprogramming via the `macecsk` CSR group must follow the activation rules in <<ACE-CSR-macecsk>>.

[IMPORTANT]
====
When a process migrates between harts, its SCCs must remain importable, requiring the destination hart to use the same CSK as the source. The OS and hypervisor must ensure that M-mode establishes this CSK on the destination hart. The mechanism for supervisor software to request this operation is platform-dependent and outside the scope of this specification.
Under the fourth model, this requirement can be met only within the subsystem sharing the CSK, not across subsystems.
Unless software handles the differences, it may migrate a process only between harts whose ACE units have identical values for `acemvendorid`, `acemarchid`, `acemimpid`, and `acemaxiobuflen` and implement the same extensions and Algorithms.
====

M-mode firmware must account for the configuration model used for the CSK. Persistence mechanisms for configurable CSKs are implementation-specific. Transferring a CSK to another endpoint—such as the M-mode firmware of another device, a local TPM (for example, to preserve the CSK across suspension or host hibernation), or a cloud-based HSM—*requires* an authenticated public-key wrapping mechanism. Such a mechanism is outside the scope of this specification.

// ////////////////////////////////////////////////////////////////////

[[ACE-reset-and-m-mode-only]]
=== ACE Unit Reset and M-mode-only Harts

An _ACE unit reset_ of a hart resets that hart's ACE architectural state
(cf. <<ACE-out-of-reset-unpriv>> and <<ACE-out-of-reset-priv>>);
in an ACE unit shared by several harts it affects only that hart's state, any shared Locality Secrets excepted.
A hart reset implies an ACE unit reset of that hart, and so does a fatal condition, with the differences stated in <<ACE-error-architecture>>.
A hardwired CSK is not affected by reset.

On a hart without the ACE Privileged Architecture (<<ACE-error-architecture>>), the CSK is established by M-mode through a model of <<ACE-CSK-requirements>>, every software-programmable Locality Secret whose CSR group is not implemented is unconfigured (<<ACE-Localities>>), and `ACES` is treated as Initial; which CSRs of <<ACE-priv>> may exist on such a hart is stated there.

[[ACE-out-of-reset-unpriv]]
=== ACE Unprivileged State out of Reset

This section and <<ACE-out-of-reset-priv>> are the authoritative statement of ACE state out of
reset. Out of ACE unit reset:

. All CRs are in State _Unconfigured_ with zeroized contents.
. If `Zklio` is available, `aceiobuflen` = 0 (i.e., the ACEIOBUF unconfigured), `aceiobuftop` = 0, and the ACEIOBUF is zeroized;
. `acestart` = 0;
. The value of `acemanagedcr` is 32;
. The three authentication registers of <<ACE-CRF>> are zero.

[[ACE-interaction-with-debug]]
=== Interaction with Debug Mode

All ACE state is inaccessible in Debug mode, and no ACE instruction may be
executed in it, unless an implementation-defined _authenticated-debug_ signal
is asserted.

[NOTE]
====
The natural source for the authenticated-debug signal is the authentication
interface of the Debug Module defined by the RISC-V Debug specification
(`dmstatus.authenticated`); the mapping is implementation-defined.
====

In authenticated Debug mode:

. ACE instructions and CSRs are accessible with M-mode privilege, subject to the exceptions below.
. The `macecsk` CSR group is inaccessible for both reads and writes. Entering authenticated Debug mode neither zeroizes nor replaces the CSK; the active CSK remains available to management instructions.
. A CC may be _used_ only if bit 4 of its _UsagePolicy_ field (<<ACE-Metadata>>) is set; bits 0–3 are not evaluated in Debug mode. Debug code is otherwise limited to management operations. It may export existing contexts as SCCs, provision and use contexts created for Debug mode, and restore the saved state before exiting. An existing CC may be used only if its _UsagePolicy_ explicitly authorizes Debug-mode use.

Upon entering Debug mode while the authenticated-debug signal is _deasserted_:

. All CRs are zeroized and set to _Unconfigured_.
. The ACEIOBUF is zeroized, and `aceiobuflen`, `aceiobuftop`, and `acestart` are set to zero.
. All applicable `*lcrstatus` fields are set to _Dirty_; every `ACES` field that is not Off is set to _Dirty_.
. The software-configurable Locality Secrets — _PhysBootScrt_, _VirtBootScrt_, _MLocality_, _HLocality_, and _SLocality_ (`macephysbootscrt`, `hacevirtbootscrt`, `macelocality`, `hacelocality`, `sacelocality`, `vsacelocality`) — are zeroized. Their CSRs subsequently read as zero.
. The HW Binding Group entries cannot be zeroized and are therefore _masked_. Until the next hart reset, the ACE unit receives zero for each such entry, for this hart, instead of its hardwired value.
. The CSK is zeroized. If the CSK is hardwired, or shared under the fourth model of <<ACE-CSK-requirements>>, the ACE unit of the hart receives the all-zero value in its place until the next hart reset; a shared CSK itself is not modified.

[NOTE]
====
Normal execution cannot resume after entry into unauthenticated Debug mode because the ACE state has been destroyed.

Debugging that preserves ACE state therefore requires authenticated Debug mode. Recovery requires a hart reset, which restores access to the hardwired HW Binding values and, under the third CSK model, the hardwired CSK, followed by re-establishment of the CSK and Locality Secrets by the privileged software stack and re-provisioning of the contexts.

Under the programmable CSK models, if M-mode re-establishes the same CSK, SCCs exported before entry into Debug mode become importable again, providing a complete recovery path through the ordinary context-saving mechanisms.
====

// ////////////////////////////////////////////////////////////////////
